# Open Data Portal API — Product Requirements Document

## 1. Introduction

The city's open data programme has outgrown the spreadsheet that used to track it. Publishing departments hold hundreds of candidate extracts, each with its own privacy exposure, its own promised refresh cadence, and its own constituency of journalists, civic developers and researchers waiting for it. Today a department can promise a monthly refresh and quietly miss it for a year; a privacy analyst can clear a dataset without anyone recording who measured the cross-tab cell sizes; and a resident who reports a broken column has no path from that report to a corrected extract. This API replaces that spreadsheet with an auditable publishing pipeline in which every dataset's inventory position, privacy clearance, metadata quality, automation health, currency against its promise, and community engagement are all first-class, computed state.

The system is organised around one central record — the **Dataset** — that carries two independent state dimensions simultaneously. Its `publication_status` tracks where the extract sits in the editorial pipeline, from raw inventory entry through screening, readiness, publication, remediation and retirement. Its `currency_status` tracks, entirely separately, whether the published extract still honours the cadence the department declared. A dataset can therefore be perfectly published and badly stale at the same time, and the portal must be able to say so. Around that record sit the artefacts that gate it: a metadata standard record whose completeness is scored against six weighted components, a reidentification assessment computed twice under two deliberately different variants, an automated republication pipeline that reserves a window on a shared ingest worker and escrows the credits its runs will consume, and an append-only version ledger that supports compensating retraction.

Two technical constraints shape every rule that follows. First, the programme office is fiscally accountable for the compute its automation consumes, so every department holds a four-bucket stewardship credit ledger that must balance after every single request — credits are moved between buckets, never created or destroyed outside an explicit grant. Second, every temporal rule in the system reads a **logical clock** rather than wall-clock time. The logical clock starts at `2026-08-01T00:00:00Z` and is advanced only by an administrative test-driving capability that accepts a `to_iso8601` instant and answers with the new `current_utc`; setting it recomputes nothing on its own, so staleness, service-level breaches and posture changes only materialise on the next write or on the next portal sweep. Throughout this document, *the logical clock* or *the current logical instant* means the value that capability last set.

## 2. Global Specifications & System-Wide Principles

Everything in this section applies across the whole surface, which is mounted under the `/open-data` prefix.

### 2.1. User and Role-Based Access Control

Every request carries its caller in two mandatory HTTP headers: `X-User-Role` names the operational capacity the caller is acting in, and `X-User-ID` identifies the acting principal. Five roles exist, spelled exactly as follows: `PortalAdmin`, `DataCoordinator`, `PrivacyReviewer`, `CommunityMember`, and `Anonymous`. A request whose `X-User-Role` is missing or is not one of those five strings, or whose `X-User-ID` is missing for a role that requires an identity, is rejected with `ERR_UNAUTHENTICATED` (401). `Anonymous` is the sole exception: it requires no `X-User-ID`. A syntactically valid caller whose role is not listed among an endpoint's authorised roles is rejected with `ERR_ROLE_NOT_PERMITTED` (403).

The five roles differ in how `X-User-ID` relates to persisted data, and that difference is load-bearing:

- When `X-User-Role` is `DataCoordinator`, `X-User-ID` is the `id` of the acting `Department`. Ownership checks on any dataset-scoped write compare the target dataset's `department_id` to `X-User-ID`; when a coordinator inventories a new dataset, the comparison is against the `department_id` supplied in the request body instead. A mismatch is rejected with `ERR_DEPARTMENT_SCOPE_VIOLATION` (403). A coordinator therefore acts as the departmental data steward: it owns inventory, screening, the aggregation choice, metadata drafting, pipeline configuration and arming, version publication, and quality-issue triage and correction. It cannot grant credits, accept its own metadata record, decide a privacy clearance, or moderate community content.
- When `X-User-Role` is `CommunityMember`, `X-User-ID` is the `id` of the acting `CommunityMember`. Ownership checks compare `X-User-ID` to whichever member reference the body carries — `reporter_member_id` when filing a quality issue, `requester_member_id` when asking for a new dataset, `member_id` when casting a vote, `submitter_member_id` when submitting a showcase application. A mismatch is rejected with `ERR_MEMBER_SCOPE_VIOLATION` (403). Community members are registered data reusers: they file quality issues, submit showcase applications, request new datasets and cast reputation-weighted votes.
- When `X-User-Role` is `PortalAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server never compares it to any entity's `id`. The programme office holds the shared registries (departments, licences, ingest runners, credit grants), metadata acceptance, usage-analytics ingestion, high-value commitments, showcase moderation, community-request adjudication, the operational sweep and the logical clock. It cannot author or clear privacy assessments, and it cannot inventory or publish a department's datasets.
- When `X-User-Role` is `PrivacyReviewer`, `X-User-ID` is likewise an opaque operator identifier not tied to any persisted entity. The server does record it — as `assessor_user_id` on the assessment the reviewer creates, and as `decided_by_user_id` on the assessment the reviewer clears or blocks — but it never resolves it against any entity's `id`. Segregation of duties is enforced by comparing those two recorded operator identifiers to each other: a reviewer whose `X-User-ID` equals the assessment's `assessor_user_id` may not decide that assessment, and the attempt is rejected with `ERR_SEGREGATION_OF_DUTIES` (403). Privacy reviewers have no publication, pipeline or credit authority.
- When `X-User-Role` is `Anonymous`, there is no `X-User-ID` at all and nothing is compared to any entity's `id`. Anonymous callers may browse the public catalogue and register themselves as a community member; they hold no other write authority.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and Catalogue Filtering

Every collection endpoint is paginated by two query parameters. `limit` caps the number of rows returned; when it is omitted it defaults to 10, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` is the number of rows to skip; when omitted it defaults to 0 and its minimum accepted value is 0. A `limit` outside 1 through 100, or a negative `offset`, is a request-shape failure and is rejected with `ERR_INVALID_REQUEST` (400).

Unless a specific endpoint says otherwise, every list endpoint returns its rows sorted by `created_at` in ascending order. Every list response carries `limit`, `offset`, `total_count` and `has_more` in the `meta` object of the envelope, where `total_count` is the number of rows matching the filters before pagination is applied.

Two collections additionally accept exact-match filters, all of them optional and all of them combinable with each other and with pagination. The department register filters on a department's `code` and on its `compliance_posture`. The metadata-record collection filters on the `dataset_id` the record describes, on the `license_id` it is drafted against, and on the record's `status`. No other collection endpoint defines a named filter; the remaining list endpoints accept `limit` and `offset` only.

### 2.4. Resource Identity, Timestamps and Version Counters

Every persisted resource in this system — `Department`, `LicenseTerm`, `IngestRunner`, `Dataset`, `MetadataRecord`, `PrivacyAssessment`, `PublicationPipeline`, `PipelineRun`, `DatasetVersion`, `QualityIssue`, `CommunityMember` and `DatasetRequest` — carries the same four system-managed properties:

- `id` (string): a server-minted UUID. It carries no type prefix and clients never supply it.
- `created_at` (string): an ISO 8601 UTC timestamp with three fractional digits, recording the logical instant the row was created.
- `updated_at` (string): an ISO 8601 UTC timestamp in the same format, refreshed on every mutation of the row.
- `version` (integer): a counter that starts at 1 on creation and increments by exactly 1 on every mutation of that row, including mutations the server performs on its own initiative as a cascade from some other resource's transition.

Because the cascades described in §2.11 mutate several rows inside one request, a single request routinely increments the `version` of more than one resource — and it does so once per mutated row, not once per request. Recomputing a derived field counts as a mutation: when a department's `risk_points` is re-derived, that department's `updated_at` and `version` both move.

Two collections are held inline on their owning row rather than as addressable resources, and their members are therefore not UUID-addressed. `Dataset.usage_epochs` is an append-only array of objects, each holding an `epoch_index`, an `api_call_count`, a `download_count` and a `recorded_at` instant. `Dataset.showcase_apps` is an append-only array of objects, each holding a `label`, a `name`, a `url`, a `submitter_member_id`, a `status` that is one of `SUBMITTED`, `APPROVED` or `REJECTED`, and a `decided_at` instant that stays null until the entry is moderated. `DatasetRequest.votes` is an append-only array of objects, each holding a `member_id`, the `weight` that was snapshotted at cast time, and a `cast_at` instant.

### 2.5. Numeric Precision and Rounding Discipline

Unless a rule below states otherwise, every derived numeric quantity in this system is carried to exactly 2 decimal places and rounded half up. That applies to all four departmental credit buckets (`credits_issued_units`, `credit_balance_units`, `credits_escrowed_units`, `credits_consumed_units`), to every settlement field on a run, to `escrow_required_units` and `escrowed_credit_units`, to `priority_score`, `engagement_index`, `observed_demand_score`, `completeness_score`, `screening_risk_score`, `clearance_risk_score`, `risk_score`, `reputation_score` and `demand_signal`. Counters such as `risk_points`, `days_overdue`, `weighted_vote_total`, `vote_weight`, `k_anonymity_k`, `column_count`, `version_index` and every `*_count` field are integers with no fractional part.

Three rounding orders in this system are **pinned**, meaning the sequence of rounding operations is part of the contract and a mathematically equivalent-looking reordering produces a different answer:

1. The metadata completeness score rounds each of its six weighted component contributions to 2 decimal places first, stores them in `component_contributions`, sums the already-rounded values, and rounds that sum again. Summing the unrounded contributions and rounding once at the end is wrong and can differ by 0.01 — which is enough to flip the acceptance gate.
2. The reidentification risk score rounds once, after multiplying all four of its factors together, and only then applies its ceiling.
3. Run settlement rounds at the discount step and at the total step only; the reliability tier is keyed on the pre-discount subtotal and is never re-evaluated against the discounted total.

The priority score is rounded once, applied to the finished weighted sum and never to the individual weighted terms.

### 2.6. Optimistic Concurrency Against the Dataset Row

Two write operations take a mandatory optimistic-concurrency token, and both name the same parent: the `Dataset`.

Creating a `DatasetVersion` requires a non-optional `expected_dataset_version` field in the request body, carrying the `version` value of the target dataset that the client last observed. If that value does not equal the dataset's current `version`, the request is rejected with `ERR_STALE_DATASET_VERSION` (412). The protection exists because a new version legitimately supersedes whichever version is currently `LIVE`: a writer holding a stale view of the dataset would silently push aside a published version it never saw.

Creating a `PublicationPipeline` likewise requires a non-optional `expected_dataset_version` field carrying the client's last observed dataset `version`, and a value that does not equal the dataset's current `version` is rejected with the same `ERR_STALE_DATASET_VERSION` (412). Here the protection exists because configuring a pipeline decommissions the dataset's previous non-decommissioned pipeline and records it as `superseded_pipeline_id`; a stale writer would discard a configuration it never observed.

No other endpoint in this system takes a version field. Operations that are not one of those two creates do not accept `expected_dataset_version` and perform no concurrency comparison.

### 2.7. Validation Precedence

Many operations are guarded by several independent checks at once, and which error a caller sees is part of the contract. All validations are evaluated in the ascending priority order below, and the **first** failing check decides the response; later checks are not consulted. Priorities 1 through 5 form the generic preamble that every applicable request passes through before any domain rule runs.

1. Authentication, on every endpoint: `X-User-Role` and `X-User-ID` are present and the role is one of the five declared names, with `Anonymous` exempt from `X-User-ID` — otherwise `ERR_UNAUTHENTICATED` (401).
2. Role authorisation, on every endpoint: the acting role appears in the endpoint's authorised list — otherwise `ERR_ROLE_NOT_PERMITTED` (403).
3. Path resolution, on every endpoint that has path parameters: each addressed resource resolves, checked left to right (see §2.8), answering with the not-found code for the *first* unresolvable segment — one of `ERR_DATASET_NOT_FOUND`, `ERR_DEPARTMENT_NOT_FOUND`, `ERR_LICENSE_NOT_FOUND`, `ERR_RUNNER_NOT_FOUND`, `ERR_METADATA_NOT_FOUND`, `ERR_ASSESSMENT_NOT_FOUND`, `ERR_PIPELINE_NOT_FOUND`, `ERR_RUN_NOT_FOUND`, `ERR_VERSION_NOT_FOUND`, `ERR_ISSUE_NOT_FOUND`, `ERR_MEMBER_NOT_FOUND`, `ERR_REQUEST_NOT_FOUND` or `ERR_SHOWCASE_NOT_FOUND`, all 404.
4. Request shape, on every write endpoint and on every paginated list endpoint: required fields present, enum members recognised, and numeric values inside their declared ranges — all declared scores between 0 and 100 inclusive, `window_start_minute` between 0 and 1439 inclusive, `window_duration_minutes` between 1 and 480 inclusive, `attribution_element_count` between 0 and 6 inclusive, `credit_units` strictly greater than zero, `cooldown_minutes` between 0 and 120 inclusive, `column_count` at least 1, `declared_quasi_identifier_count` between 0 and 20 inclusive, `declared_smallest_cell_size` and `verified_smallest_cell_size` and `population_size` each at least 1, `data_dictionary_field_count` and `provenance_detail_lines` and `row_count` and `rows_ingested` each at least 0, `limit` between 1 and 100 and `offset` at least 0 — otherwise `ERR_INVALID_REQUEST` (400).
5. Body foreign keys, on `POST /open-data/datasets`, `POST /open-data/metadata-records`, `POST /open-data/privacy-assessments`, `POST /open-data/publication-pipelines`, `POST /open-data/pipeline-runs`, `POST /open-data/dataset-versions`, `POST /open-data/quality-issues`, `POST /open-data/dataset-requests`, `POST /open-data/dataset-requests/{requestId}/votes`, `POST /open-data/dataset-requests/{requestId}/fulfill`, `POST /open-data/quality-issues/{issueId}/link-correction` and `POST /open-data/datasets/{datasetId}/showcase-apps`: every foreign key supplied in the body resolves to an existing row — otherwise the corresponding 404 from the same family as priority 3 (`ERR_DEPARTMENT_NOT_FOUND`, `ERR_DATASET_NOT_FOUND`, `ERR_LICENSE_NOT_FOUND`, `ERR_RUNNER_NOT_FOUND`, `ERR_MEMBER_NOT_FOUND`, `ERR_VERSION_NOT_FOUND`, `ERR_ISSUE_NOT_FOUND` or `ERR_PIPELINE_NOT_FOUND`).
6. Departmental scope, on every `DataCoordinator`-only endpoint: `ERR_DEPARTMENT_SCOPE_VIOLATION` (403) as described in §2.1.
7. Member self-scope, on `POST /open-data/quality-issues`, `POST /open-data/dataset-requests`, `POST /open-data/dataset-requests/{requestId}/votes` and `POST /open-data/datasets/{datasetId}/showcase-apps`: `ERR_MEMBER_SCOPE_VIOLATION` (403) as described in §2.1.
8. Segregation of duties, on `POST /open-data/privacy-assessments/{assessmentId}/decide` only: `ERR_SEGREGATION_OF_DUTIES` (403).
9. Scalar uniqueness, on `POST /open-data/departments`, `POST /open-data/licenses`, `POST /open-data/datasets` and `POST /open-data/members/register`: `Department.code`, `LicenseTerm.code`, `Dataset.slug` and `CommunityMember.email` are each unique across their own collection, answering `ERR_DUPLICATE_DEPARTMENT_CODE`, `ERR_DUPLICATE_LICENSE_CODE`, `ERR_DUPLICATE_DATASET_SLUG` or `ERR_DUPLICATE_MEMBER_EMAIL` (409).
10. Per-dataset singletons, on `POST /open-data/metadata-records` and `POST /open-data/privacy-assessments`: a dataset may hold at most one metadata record whose `status` is `DRAFT`, `SUBMITTED` or `ACCEPTED` (`ERR_METADATA_RECORD_EXISTS`, 409) and at most one privacy assessment whose `status` is `DRAFT`, `SUBMITTED` or `CLEARED` (`ERR_ASSESSMENT_EXISTS`, 409).
11. Collection-member uniqueness, on `POST /open-data/datasets/{datasetId}/usage-report`, `POST /open-data/datasets/{datasetId}/showcase-apps` and `POST /open-data/dataset-requests/{requestId}/votes`: `epoch_index` is unique per dataset (`ERR_DUPLICATE_USAGE_EPOCH`), showcase `label` is unique per dataset (`ERR_DUPLICATE_SHOWCASE_LABEL`), and a member may hold at most one vote per request (`ERR_DUPLICATE_VOTE`), all 409.
12. Optimistic concurrency, on `POST /open-data/dataset-versions` and `POST /open-data/publication-pipelines`: `ERR_STALE_DATASET_VERSION` (412) as described in §2.6.
13. Transition legality, on every state-changing endpoint: the target resource is in a state from which the requested transition exists. Terminal states are locked down — a `RETIRED` dataset, a `CLOSED` or `REJECTED` quality issue, a `DECOMMISSIONED` pipeline, a `SUCCEEDED` or `SKIPPED` run, a `RETRACTED` version and a `DECLINED` or `FULFILLED` request all accept no further transitions. The rejection is `ERR_INVALID_STATE_TRANSITION` in the general case, and the more specific `ERR_DATASET_NOT_PUBLISHED`, `ERR_PIPELINE_NOT_ARMED` or `ERR_VERSION_NOT_LIVE` where the guard is precisely about the dataset being published, the pipeline being armed, or the version being live. All four are 409.
14. Cross-entity readiness, on `POST /open-data/datasets/{datasetId}/mark-ready` and `POST /open-data/datasets/{datasetId}/publish`: readiness requires an `ACCEPTED` metadata record (`ERR_METADATA_NOT_ACCEPTED`) and a `CLEARED` privacy assessment (`ERR_PRIVACY_CLEARANCE_REQUIRED`); publication requires the metadata record to still be `ACCEPTED`. Both are 409.
15. Aggregation sufficiency, on `POST /open-data/datasets/{datasetId}/mark-ready` and `POST /open-data/datasets/{datasetId}/publish`: `ERR_AGGREGATION_UNMET` (422), described in §3.3.

18. Licence still current, on `POST /open-data/metadata-records/{metadataRecordId}/decide` and `POST /open-data/datasets/{datasetId}/publish`: the backing licence has `retired` false — otherwise `ERR_LICENSE_RETIRED` (409).
19. Embargo, on `POST /open-data/datasets/{datasetId}/publish` and `POST /open-data/pipeline-runs/{runId}/start`: `ERR_EMBARGO_ACTIVE` (409).
20. Run schedule sanity, on `POST /open-data/pipeline-runs`, `POST /open-data/pipeline-runs/{runId}/requeue` and `POST /open-data/pipeline-runs/{runId}/start`: `ERR_RUN_SCHEDULE_INVALID` (422).
21. Run inside the window, on `POST /open-data/pipeline-runs` and `POST /open-data/pipeline-runs/{runId}/requeue`: `ERR_RUN_OUTSIDE_WINDOW` (422).

23. Runner exclusivity, on `POST /open-data/publication-pipelines/{pipelineId}/arm` and `POST /open-data/publication-pipelines/{pipelineId}/resume`: `ERR_RUNNER_WINDOW_CONFLICT` (409), described in §3.5.

26. Metadata acceptance floor, on a metadata decision whose `decision` is `ACCEPT`: `ERR_METADATA_INCOMPLETE` (422).
27. Attribution readiness, on a metadata decision whose `decision` is `ACCEPT`: `ERR_ATTRIBUTION_MISSING` (422).
28. Community demand floor, on `POST /open-data/dataset-requests/{requestId}/review`: `ERR_INSUFFICIENT_DEMAND` (422).
29. Member standing, on `POST /open-data/quality-issues` and `POST /open-data/dataset-requests/{requestId}/votes`: a `THROTTLED` member may neither file issues nor vote — `ERR_MEMBER_THROTTLED` (422).
30. High-value eligibility, on `POST /open-data/datasets/{datasetId}/high-value-commitment`: `ERR_NOT_HIGH_VALUE_ELIGIBLE` (422).
31. Retraction predecessor, on `POST /open-data/dataset-versions/{versionId}/retract`: `ERR_NO_PREDECESSOR_VERSION` (409).
32. Clean issue queue before retirement, on `POST /open-data/datasets/{datasetId}/retire`: `ERR_OPEN_ISSUES_BLOCK_RETIRE` (409).
33. Departmental posture gate, on `POST /open-data/datasets/{datasetId}/screen`, `POST /open-data/datasets/{datasetId}/mark-ready`, `POST /open-data/datasets/{datasetId}/publish`, `POST /open-data/publication-pipelines/{pipelineId}/arm` and `POST /open-data/quality-issues/{issueId}/decide`: `ERR_DEPARTMENT_SUSPENDED` or `ERR_RESTRICTED_POSTURE_TIER` (403), described in §2.9.
34. Credit sufficiency, on `POST /open-data/publication-pipelines/{pipelineId}/arm`: `ERR_INSUFFICIENT_CREDITS` (402), described in §2.10.

Two consequences of this ordering deserve emphasis. Because the posture gate sits at priority 33, a department that has drifted into `SUSPENDED` surfaces as `ERR_DEPARTMENT_SUSPENDED` only after every structural and state check on the request has already passed — a publish attempt on a dataset that is not in `READY` reports the transition failure, not the posture failure. And because credit sufficiency sits last, an arming request that both conflicts on the runner window and lacks credits reports `ERR_RUNNER_WINDOW_CONFLICT`.

### 2.8. Left-to-Right Resolution of Addressed Resources

Resources in this system are addressed from flat collections rather than nested under their owners, so most paths carry a single identifier: `{departmentId}`, `{licenseId}`, `{runnerId}`, `{datasetId}`, `{metadataRecordId}`, `{assessmentId}`, `{pipelineId}`, `{runId}`, `{versionId}`, `{issueId}`, `{memberId}` or `{requestId}`. Where an inline collection member is addressed, the path carries two segments — the showcase moderation path names the dataset and then the `{showcaseLabel}` within it. In that case the identifiers are resolved strictly left to right: a request naming a dataset that does not exist answers `ERR_DATASET_NOT_FOUND` without ever looking for the showcase entry, and only once the dataset resolves does a missing label answer `ERR_SHOWCASE_NOT_FOUND`. Foreign keys carried in the request body are resolved after all path identifiers, never before.

### 2.9. Departmental Compliance Posture as a Publication Gate

Every `Department` carries a computed `compliance_posture` of `OPEN`, `RESTRICTED` or `SUSPENDED`, derived from a weighted count of the trouble its portfolio is currently in. The department's four risk counters are recomputed from scratch whenever a dataset of theirs changes `currency_status` or `publication_status`, whenever a correction breach is detected, and during the portal sweep:

- `breached_dataset_count` is the number of the department's datasets whose `currency_status` is `BREACHED` and whose `publication_status` is `PUBLISHED` or `UNDER_REMEDIATION`.
- `stale_dataset_count` is the number of the department's datasets whose `currency_status` is `STALE` and whose `publication_status` is `PUBLISHED` or `UNDER_REMEDIATION`.
- `remediation_dataset_count` is the number of the department's datasets whose `publication_status` is `UNDER_REMEDIATION`.
- `overdue_correction_count` is the number of quality issues on the department's datasets whose `status` is `ACCEPTED` and whose `correction_breached` flag is true.

`risk_points` is then three points for each breached dataset, plus two points for each stale dataset, plus two points for each dataset under remediation, plus one point for each overdue correction. Datasets that are `RETIRED` or that have not yet been published never contribute. From `risk_points` the posture follows on inclusive boundaries: at least 6 points is `SUSPENDED`, from 2 through 5 points is `RESTRICTED`, and 1 point or 0 points is `OPEN`.

The posture gate then bites on five operations — moving a dataset into screening, declaring it ready, publishing it, arming one of its pipelines, and deciding a quality issue on it. A `SUSPENDED` posture blocks all five outright with `ERR_DEPARTMENT_SUSPENDED` (403). A `RESTRICTED` posture blocks only publication, and only for low-priority work: the dataset's stored `priority_tier` **as it stands at the moment the publish request begins** must be `TIER_1` or `TIER_2`, and a `TIER_3` dataset is refused with `ERR_RESTRICTED_POSTURE_TIER` (403). This ordering matters because publication itself re-scores the dataset under a different variant; the gate reads the tier that is stored before that re-scoring happens.

### 2.10. The Stewardship Credit Ledger

Automation is not free, and each department pays for its own. A department holds four credit buckets, all of them 2-decimal numbers and all of them starting at 0.00 when the department is registered. `credits_issued_units` is the lifetime total the programme office has granted, and it is increased by nothing except an explicit credit grant. `credit_balance_units` holds credits that are neither escrowed nor spent and are therefore available to arm a pipeline or settle a run. `credits_escrowed_units` holds credits reserved by the department's pipelines. `credits_consumed_units` holds credits permanently spent on settled run charges.

The invariant is absolute and must hold after **every** request: `credit_balance_units` plus `credits_escrowed_units` plus `credits_consumed_units` equals `credits_issued_units`. Arming a pipeline moves credits from balance to escrow; decommissioning moves them back; settling a run moves them from escrow and balance into consumed. None of those movements changes the issued total. Only a grant changes it, and a grant raises the issued total and the balance by the same amount, leaving escrow and consumed untouched.

### 2.11. Cascades, Floors and the Recompute Discipline

A large share of this system's behaviour is *secondary*: one caller-initiated transition drags several other rows with it, and those secondary effects are as much part of the contract as the primary one. Three chains are deep enough to name here, and each is described in full in §3.

Accepting a quality issue that is both `CRITICAL` in `severity` and `PRIVACY` in `category` against a `PUBLISHED` dataset runs four hops: the issue moves to `ACCEPTED`, the dataset moves `PUBLISHED → UNDER_REMEDIATION`, that dataset's `ARMED` pipeline moves to `SUSPENDED`, and because the pipeline is now suspended the dataset's `currency_status` takes a `STALE` floor while its pipeline's pending runs are skipped — after which the department's counters, `risk_points` and `compliance_posture` are re-derived.

Reporting a run failure that takes a pipeline to its failure-streak limit runs a comparable chain: the run moves to `FAILED`, the pipeline moves `ARMED → SUSPENDED`, the dataset's `currency_status` takes the `STALE` floor and its `staleness_alert_count` increments, and the department's posture is re-derived.

Retiring a dataset cascades downward through its automation: every pipeline of the dataset that is `ARMED` or `SUSPENDED` becomes `DECOMMISSIONED` with its escrow released, every run of those pipelines that is `SCHEDULED` or `RETRY_QUEUED` becomes `SKIPPED`, and the department's counters and posture are re-derived.

Two general disciplines follow. First, a **floor** is not a transition but a lower bound: while any pipeline of a dataset sits in `SUSPENDED`, that dataset's `currency_status` can never be milder than `STALE`, however healthy the clock says it is; the floor is lifted only when no pipeline of the dataset is suspended any longer. Second, every row a cascade touches has its `updated_at` refreshed and its `version` incremented, exactly once per mutated row per request.

## 3. Business Logic & Workflows

### 3.1. Building the Departmental Inventory

Everything begins with a publishing department. The programme office registers one by supplying its `name`, a short `code` and a `contact_email` for the programme relationship. The `code` must be unique across all departments and is a 2-to-12-character uppercase string. A freshly registered department starts with all four credit buckets at 0.00, all four risk counters at zero, `risk_points` at 0 and `compliance_posture` at `OPEN`. Credits arrive only by grant: the programme office supplies a `credit_units` amount, strictly greater than zero, together with an optional `memo` recording why, and the grant raises `credits_issued_units` and `credit_balance_units` by that amount while leaving `credits_escrowed_units` and `credits_consumed_units` untouched. A departmental scorecard capability exposes the posture arithmetic and the credit reconciliation side by side, answering with the department's `department_id`, its `compliance_posture`, `risk_points`, `breached_dataset_count`, `stale_dataset_count`, `remediation_dataset_count` and `overdue_correction_count`, all four credit buckets, and a boolean `credit_ledger_balanced` asserting that the conservation invariant of §2.10 currently holds.

A `DataCoordinator` then inventories datasets into its own department. Inventorying a dataset takes the owning `department_id` — which must equal the coordinator's own identity and is immutable thereafter — a catalog `title`, a unique lowercase kebab-case `slug`, a public catalog `description`, the declared `update_frequency` (one of `DAILY`, `WEEKLY`, `MONTHLY`, `QUARTERLY`, `ANNUAL` or `IRREGULAR`), the `column_count` of the extract as published, its `sensitivity_class` (`PUBLIC`, `SENSITIVE` or `RESTRICTED`), and two coordinator-declared judgements on a 0.00-to-100.00 scale with two decimals: `public_demand_score` and `policy_value_score`. A newly inventoried dataset sits at `publication_status` `INVENTORIED` and `currency_status` `CURRENT`, with `public_access_suspended` and `high_value_committed` both false, `engagement_index` and `observed_demand_score` both 0.00, `usage_epochs` and `showcase_apps` both empty, `live_row_count` and `version_index_high_water` and `days_overdue` and `staleness_alert_count` all zero, and `last_published_at`, `next_due_at`, `last_staleness_alert_at` and `remediation_opened_at` all null.

Prioritisation is what turns that inventory into a work queue, and it is computed the moment the dataset is created. The score has three weighted terms. The first is a demand term weighted at 0.45. The second is `policy_value_score` weighted at 0.35. The third is **community pressure**, weighted at 0.20, which is the demand the community has transferred onto this dataset through its own requests: take every dataset request whose `linked_dataset_id` is this dataset and whose `status` is either `ACCEPTED` or `FULFILLED` — requests still `OPEN`, still `UNDER_REVIEW`, or `DECLINED` contribute nothing, and there is no time window, so every qualifying row counts — sum their `weighted_vote_total` values, multiply that sum by 4, and cap the result at 100. The three weighted terms are then added together and the finished sum is rounded half up to two decimal places exactly once, never term by term, giving `priority_score`. From that score, `priority_tier` follows on inclusive thresholds: `TIER_1` at 75.00 or above, `TIER_2` at 50.00 or above, and `TIER_3` otherwise.

Which figure plays the demand term is the interesting part, and it is recorded on the dataset itself in `priority_score_variant`. While the dataset's `publication_status` is `INVENTORIED`, `SCREENING` or `READY` — before its catalog page has any traffic worth trusting — the demand term is the coordinator's declared `public_demand_score` and the variant is `AS_DECLARED`. Once the dataset's `publication_status` is `PUBLISHED` or `UNDER_REMEDIATION`, the demand term becomes the measured `observed_demand_score` and the variant is `AS_OBSERVED`. The same stored inputs therefore produce a different `priority_score` and possibly a different `priority_tier` after publication than before it, which is precisely why the `RESTRICTED` posture gate of §2.9 is defined against the tier that is still stored when the publish request begins.

Moving a dataset out of raw inventory is the coordinator's declaration that readiness review has started: the dataset advances `INVENTORIED → SCREENING`. The coordinator's identity must match the dataset's `department_id`, and the department's posture must not be `SUSPENDED`. Screening re-scores `priority_score` under the `AS_DECLARED` variant and stamps `priority_score_variant` accordingly, makes the dataset eligible for catalog-page usage reporting, and increments the dataset's `version`.

### 3.2. Licence Terms and the Metadata Standard Record

Reuse permissions are defined centrally. The programme office creates a licence with a unique `code` such as `CC-BY-4.0`, a human-readable `name`, three booleans — `attribution_required` (defaulting to false), `commercial_use_allowed` (defaulting to true) and `share_alike` (defaulting to false) — and an optional `attribution_text_template` carrying the exact wording reusers must reproduce, which may be null whenever `attribution_required` is false. From the three booleans the server derives `reuse_permission_class` by taking the **first** matching clause of four, in this exact order, deliberately overlapping: if attribution is not required, commercial use is allowed and share-alike is not required, the class is `UNRESTRICTED`; otherwise, if attribution is required, commercial use is allowed and share-alike is not required, the class is `ATTRIBUTION`; otherwise, if share-alike is required, the class is `COPYLEFT` — and this clause wins even when commercial use is forbidden; otherwise the class is `NONCOMMERCIAL`. A new licence has `retired` false. Retiring a licence sets `retired` to true; metadata records already accepted against it keep the reference, but no further record may be accepted against it and no dataset backed by it may be published.

While a dataset is in `SCREENING`, its coordinator drafts the metadata standard record that will ship with it. The draft carries the `dataset_id` it describes, the `license_id` governing reuse, a `data_dictionary_field_count` giving how many of the extract's columns are documented, a `provenance_detail_lines` count giving how many lineage steps have been written down, a steward `contact_email` published alongside the dataset, a `declared_update_frequency` promised in the metadata (drawn from the same six-member enumeration as the dataset's own cadence), and an optional `attribution_element_count` between 0 and 6 recording how many of the six required attribution elements have been filled in, defaulting to 0. The record starts at `status` `DRAFT` with `returned_reason` null.

Completeness is scored on creation, on every revision of a draft, and again when the record is submitted. Six components are assessed, each producing a value between 0 and 1 inclusive:

1. **Dictionary coverage**, weighted 0.30: `data_dictionary_field_count` divided by the dataset's `column_count`, capped at 1.
2. **Provenance depth**, weighted 0.20: `provenance_detail_lines` divided by the target of 24 documented lineage steps, capped at 1.
3. **Contact information**, weighted 0.15: 1 when `contact_email` contains an at-sign, 0 when it does not.
4. **Cadence agreement**, weighted 0.15: 1 when `declared_update_frequency` is exactly the dataset's own `update_frequency`, 0 otherwise.
5. **Licence currency**, weighted 0.10: 1 when `license_id` resolves to a licence whose `retired` flag is false, 0 otherwise.
6. **Attribution fill**, weighted 0.10: `attribution_element_count` divided by the six total attribution elements, capped at 1.

Each component's weight is multiplied by its value and by 100, and that product is rounded half up to two decimal places **immediately**. The six rounded results are stored, in exactly the declaration order above — dictionary, provenance, contact, frequency, licence, attribution — in `component_contributions`. Their sum is then rounded half up to two decimal places again and stored as `completeness_score`. Summing the six unrounded products and rounding only at the end is not an acceptable substitute: the two orders can differ by 0.01, and 0.01 is enough to decide whether the record clears the acceptance floor.

Revising a `DRAFT` record is permitted only while it is in `DRAFT`, and any of `license_id`, `data_dictionary_field_count`, `provenance_detail_lines`, `contact_email`, `declared_update_frequency` and `attribution_element_count` may be supplied; the six contributions and `completeness_score` are recomputed and the record's `version` increments. Submitting the record moves it `DRAFT → SUBMITTED`; it requires that the acting coordinator own the dataset's department and that the dataset's `publication_status` be exactly `SCREENING`, and it recomputes `component_contributions` and `completeness_score` one final time before the reviewer sees them.

The programme office then decides the submitted record, supplying a `decision`. An `ACCEPT` decision moves the record `SUBMITTED → ACCEPTED` and is guarded by three conditions: the backing licence's `retired` flag must be false, or the record is refused with `ERR_LICENSE_RETIRED`; when that licence has `attribution_required` true, `attribution_element_count` must be at least 1, or the record is refused with `ERR_ATTRIBUTION_MISSING`; and `completeness_score` must be at least 85.00 under the pinned rounding order above, or the record is refused with `ERR_METADATA_INCOMPLETE`. A `RETURN` decision moves the record `SUBMITTED → RETURNED` and requires a `returned_reason` in the body, which is stored on the record as the reviewer's note. A returned record is not dead: the coordinator revising it moves it `RETURNED → DRAFT`, which clears `returned_reason` and recomputes the six contributions and `completeness_score`. The `RETURNED → DRAFT → SUBMITTED` loop may repeat without limit. Every one of these transitions increments the record's `version`.

### 3.3. Privacy Screening and Reidentification Clearance

A dataset cannot be published on a privacy analyst's word alone; it needs an assessment that is authored by one reviewer and decided by a different one. A `PrivacyReviewer` opens an assessment against a dataset in screening by supplying the `dataset_id`, the `declared_quasi_identifier_count` the department believes the extract carries (between 0 and 20 inclusive), the `declared_smallest_cell_size` the department measured on its own cross-tabs (at least 1), and the `population_size` the extract covers (at least 1). The server stamps `assessor_user_id` with the authoring reviewer's `X-User-ID`, leaves `verified_smallest_cell_size` and `decided_by_user_id` null, and sets `status` to `DRAFT`.

The reidentification score multiplies four factors. The **quasi-identifier factor** is 8 points per declared quasi-identifier column, capped at 40. The **cell-size factor** is keyed on a cell size: 0.5 when that cell size is 11 or greater, 1.0 when it is 5 through 10, and 2.0 when it is 1 through 4 — small cells are what make individuals findable, so they multiply the risk. The **population factor** is either 1.00 or 1.25. The **sensitivity multiplier** is read off the dataset's own `sensitivity_class`: 0.8 for `PUBLIC`, 1.0 for `SENSITIVE`, 1.4 for `RESTRICTED`. All four are multiplied together, the product is rounded half up to two decimal places exactly once, and the result is then capped at 100.00. Only the assessment's own declared and verified figures and its dataset's `sensitivity_class` feed the calculation; other assessments on the same dataset, including ones sitting in `BLOCKED`, are ignored entirely.

The same arithmetic runs twice, under two variants that differ in two places, and the difference is the whole point of having a second pass. The **screening** variant runs at creation, uses `declared_smallest_cell_size` as the cell size, and forces the population factor to 1.00 — the screening pass deliberately ignores how small the covered population is. Its result is stored in `screening_risk_score`, and while the assessment's `status` is `DRAFT` the assessment's headline `risk_score` mirrors it. The **clearance** variant runs when the assessment is submitted, uses `verified_smallest_cell_size` — the figure the reviewer measured on the actual extract — as the cell size, and applies a population factor of 1.25 when `population_size` is below 5000 and 1.00 otherwise. Its result is stored in `clearance_risk_score`, and from `SUBMITTED` onward `risk_score` mirrors that instead. With identical stored inputs the two variants can land on opposite sides of the aggregation threshold, flipping `aggregation_required` from false to true.

Three derived fields hang off whichever score is current. `k_anonymity_k` is simply the cell size in play — the `verified_smallest_cell_size` when it has been set, and the `declared_smallest_cell_size` before that. `aggregation_required` is true when the score is at least 35.00. And `min_aggregation_geography` names the coarsest geography the extract must be rolled up to before publication: `COUNTY` when the score is at least 60.00, `TRACT` when the score is at least 35.00 but below 60.00, and `BLOCK` otherwise.

While the assessment is still `DRAFT`, the reviewer records measurements and corrects declarations against it, supplying any of `verified_smallest_cell_size`, `declared_quasi_identifier_count`, `declared_smallest_cell_size` and `population_size`; `screening_risk_score` is recomputed and the assessment's `version` increments. Submitting the assessment moves it `DRAFT → SUBMITTED` and requires two things: `verified_smallest_cell_size` must have been measured, or the submission is refused with `ERR_VERIFIED_CELL_SIZE_MISSING`, and the dataset's `publication_status` must be exactly `SCREENING`. Submission computes `clearance_risk_score` under the clearance variant, points `risk_score` at it, and re-derives `k_anonymity_k`, `aggregation_required` and `min_aggregation_geography` from that clearance figure.

A second reviewer then decides, supplying a `decision`. Both outcomes stamp `decided_by_user_id` with the deciding reviewer's `X-User-ID`, both require that this identifier differ from the recorded `assessor_user_id`, and both increment the assessment's `version` — but their conditions and their recorded results diverge. A `CLEAR` decision moves the assessment `SUBMITTED → CLEARED` and additionally requires `clearance_risk_score` to be strictly below 60.00; an assessment at exactly 60.00 or above cannot be cleared and is refused with `ERR_REIDENTIFICATION_RISK_TOO_HIGH`. Clearing freezes `aggregation_required` and `min_aggregation_geography` at their clearance-variant values, and it is that frozen pair the publication pipeline is later measured against. A `BLOCK` decision moves the assessment `SUBMITTED → BLOCKED`, imposes no risk ceiling of its own, and instead requires a `block_reason` in the body — one of `RISK_TOO_HIGH`, `AGGREGATION_UNMET` or `REVIEWER_JUDGEMENT` — which is recorded on the assessment. Blocking grants no clearance whatsoever.

A blocked assessment is reopened rather than replaced. Reopening it moves it `BLOCKED → DRAFT`, requires the dataset to still be in `SCREENING`, and clears `decided_by_user_id`, `block_reason` and `clearance_risk_score`, pointing `risk_score` back at `screening_risk_score`. The `BLOCKED → DRAFT → SUBMITTED → CLEARED` path is the standard remediation route, and it may be walked as many times as the analysis requires.

Aggregation is the department's side of that bargain. The coordinator sets or changes the `aggregation_geography` the published extract will be rolled up to — `BLOCK`, `TRACT` or `COUNTY` — and may do so only while the dataset's `publication_status` is `SCREENING` or `READY`. The value supplied simply replaces whatever was there, in either direction, because the sufficiency check is applied afresh at readiness and again at publication. That check compares ranks, where `BLOCK` ranks 1, `TRACT` ranks 2, `COUNTY` ranks 3 and a dataset whose `aggregation_geography` has never been set ranks 0: when the dataset's cleared assessment has `aggregation_required` true, the dataset's own geography rank must be greater than or equal to the rank of the assessment's `min_aggregation_geography`, and a shortfall is refused with `ERR_AGGREGATION_UNMET`.

### 3.4. Readiness, Publication and Retirement

Declaring a dataset ready is the coordinator's assertion that both gating artefacts have landed. The dataset advances `SCREENING → READY` only when exactly one metadata record for it sits in `ACCEPTED` and exactly one privacy assessment for it sits in `CLEARED`; a missing acceptance is `ERR_METADATA_NOT_ACCEPTED` and a missing clearance is `ERR_PRIVACY_CLEARANCE_REQUIRED`. If that cleared assessment has `aggregation_required` true, the geography sufficiency comparison of §3.3 must also pass. The department's posture must not be `SUSPENDED`. The transition increments the dataset's `version` and changes nothing else.

Publication is the moment the extract becomes public, and it is where the dataset's whole history begins. The coordinator supplies an `initial_row_count` for the first published extract. Four preconditions guard the transition `READY → PUBLISHED`. Any embargo must have expired: when `embargo_until_utc` is set, the logical clock must have reached or passed it, and an embargo still in the future is refused with `ERR_EMBARGO_ACTIVE`. The department must not be `SUSPENDED`, and if it is `RESTRICTED` the dataset's stored `priority_tier` at the start of the request must be `TIER_1` or `TIER_2`. And the metadata record backing the dataset must reference a licence whose `retired` flag is false.

Publication then does a great deal at once. A first `DatasetVersion` is minted with `version_index` set to the dataset's `version_index_high_water` plus one — which is 1 — a `version_label` of `"v"` followed by that index, a `change_type` of `INITIAL`, a `row_count` equal to the supplied `initial_row_count`, a `status` of `LIVE`, a `published_at` stamped at the current logical instant, and `supersedes_version_id` null because there is nothing before it. On the dataset, `version_index_high_water` becomes 1, `live_row_count` becomes the initial row count, and `last_published_at` becomes the current logical instant. `engagement_index` is recomputed and then `priority_score` is recomputed under the `AS_OBSERVED` variant with `priority_score_variant` set to `AS_OBSERVED` — and this happens strictly *after* the `RESTRICTED` tier gate above has been evaluated, which is why that gate reads the pre-publication tier. `next_due_at`, `days_overdue` and `currency_status` are re-derived, leaving `currency_status` at `CURRENT`. The owning department's `risk_points` and `compliance_posture` are re-derived. The dataset's `version` increments.

Retirement is available from two states, and the two behave differently in scope while sharing their guard. From either state, retirement takes an optional `reason`, is refused with `ERR_OPEN_ISSUES_BLOCK_RETIRE` when any quality issue on the dataset still sits in `SUBMITTED`, `TRIAGED` or `ACCEPTED`, sets `public_access_suspended` to true, and increments the dataset's `version`. From `READY` the transition `READY → RETIRED` does only that — a dataset that never published has no automation and no version history to unwind. From `PUBLISHED` the transition `PUBLISHED → RETIRED` additionally cascades: every pipeline of the dataset whose `status` is `ARMED` or `SUSPENDED` becomes `DECOMMISSIONED` and releases its `escrowed_credit_units` back into the department's `credit_balance_units`, every run of those pipelines whose `status` is `SCHEDULED` or `RETRY_QUEUED` becomes `SKIPPED` with a `skip_reason` of `DATASET_RETIRED`, and the department's counters, `risk_points` and `compliance_posture` are re-derived. `RETIRED` is terminal; nothing moves a dataset out of it.

### 3.5. Automated Republication Pipelines and Runner Windows

Recurring publication runs on shared ingest workers, and those workers are a scarce resource. The programme office registers an `IngestRunner` with a `name` and an optional `cooldown_minutes` between 0 and 120, defaulting to 15, which is the mandatory buffer appended after every armed window on that worker so that consecutive jobs cannot crowd each other. A new runner has `status` `ACTIVE` and `armed_window_count` 0. The office may later update the runner's `status` — to `DRAINING` or `OFFLINE` to take it out of service, or back to `ACTIVE` — and may adjust `cooldown_minutes`; a cooldown change re-scopes future overlap checks only and never retroactively invalidates a pipeline that is already armed. Only a runner whose `status` is `ACTIVE` may have a pipeline armed or resumed against it, or a run started on it; otherwise the request is refused with `ERR_RUNNER_NOT_ACTIVE`.

A coordinator configures a pipeline for one of its published datasets by supplying the `dataset_id`, the `runner_id` of the worker that will execute the job, the `cadence` of the recurrence (`DAILY`, `WEEKLY`, `MONTHLY`, `QUARTERLY` or `ANNUAL`), a `window_start_minute` giving the daily window's opening as minutes after midnight UTC (0 through 1439), a `window_duration_minutes` giving its length (1 through 480), the `alert_email` that will be notified when a run fails or the dataset goes stale, and the `expected_dataset_version` token of §2.6. The server derives `window_end_minute` as the start plus the duration, and refuses the configuration with `ERR_WINDOW_WRAPS_MIDNIGHT` if that sum exceeds 1440 — windows may not wrap past midnight UTC. The new pipeline starts at `status` `DRAFT` with `escrowed_credit_units` 0.00, `consecutive_failure_count` 0 and `suspend_reason` null. Configuring a pipeline also supersedes whatever configuration the dataset had: any existing pipeline of that dataset in `DRAFT`, `ARMED` or `SUSPENDED` is moved to `DECOMMISSIONED` with its escrow released, and the new pipeline records that predecessor's identifier in `superseded_pipeline_id`. The dataset's own `version` increments as part of the create.

Escrow is sized from the cadence alone; the window length and the choice of runner do not affect it. Over a thirty-day funding horizon, the number of runs the cadence implies is the horizon divided by the cadence length in days and rounded **up** to a whole number — a `DAILY` cadence spans 1 day, `WEEKLY` 7 days, `MONTHLY` 30 days, `QUARTERLY` 91 days and `ANNUAL` 365 days. That run count is multiplied by 2 credits per run, and the product is capped at 60 credits, giving `escrow_required_units`.

Arming the pipeline is what reserves the window and moves the money. The transition `DRAFT → ARMED` requires that the acting coordinator own the dataset's department, that the dataset's `publication_status` be `PUBLISHED`, that the department's posture not be `SUSPENDED`, that the runner be `ACTIVE`, that both interval rules below hold, and that the department's `credit_balance_units` be greater than or equal to the pipeline's `escrow_required_units` — a shortfall is refused with `ERR_INSUFFICIENT_CREDITS`. On success, `escrow_required_units` is subtracted from the department's `credit_balance_units`, added to its `credits_escrowed_units`, and recorded as the pipeline's `escrowed_credit_units`; the runner's `armed_window_count` increases by 1; and the pipeline's `version` increments.

The first interval rule is **runner exclusivity**, and it is half-open with a trailing buffer. The candidate pipeline occupies the span of minutes from its `window_start_minute` up to but excluding its `window_end_minute`. Each occupant on the same runner — meaning every other pipeline on that runner whose `status` is `ARMED` or `SUSPENDED`, since a suspended pipeline keeps its reservation — occupies the span from its own `window_start_minute` up to but excluding its own `window_end_minute` plus the runner's `cooldown_minutes`. If the candidate's span and any occupant's span share even one minute, the request is refused with `ERR_RUNNER_WINDOW_CONFLICT`. Because both spans exclude their upper endpoint, a candidate that begins at exactly the minute where an occupant's window plus cooldown ends is accepted: exact-boundary adjacency after the buffer is legal.

The second interval rule is **departmental steward capacity**, and it is deliberately stricter about endpoints. Here each of the same department's `ARMED` pipelines is treated as covering the closed span of minutes from its `window_start_minute` through its `window_end_minute` inclusive, and the candidate is treated the same way. Counting the candidate together with all of those, no single minute may be covered by more than two windows — that is, at most one other armed pipeline of the department may share any minute with the candidate. Because these spans include both endpoints, two windows that merely touch at a single minute *do* collide under this rule, unlike the runner rule. A breach is refused with `ERR_DEPARTMENT_WINDOW_CAPACITY`.

Suspension takes a pipeline out of service without giving up its money. The transition `ARMED → SUSPENDED` may be requested directly, in which case `suspend_reason` is `ADMIN_REQUEST`, or it may arrive as a cascade — with `suspend_reason` `FAILURE_STREAK` when a run failure hits the streak limit, or `REMEDIATION_HOLD` when the dataset enters remediation. However it arrives, its effects are the same: `escrowed_credit_units` are retained and remain counted in the department's `credits_escrowed_units`; the runner's `armed_window_count` decreases by 1 while the window itself stays reserved against the cooldown buffer; every run of the pipeline whose `status` is `SCHEDULED` or `RETRY_QUEUED` becomes `SKIPPED` with a `skip_reason` of `PIPELINE_SUSPENDED`; the dataset's `currency_status` takes the `STALE` floor and its `staleness_alert_count` increases by 1; the department's `stale_dataset_count`, `risk_points` and `compliance_posture` are re-derived; and the pipeline's `version` increments.

Resuming reverses it. The transition `SUSPENDED → ARMED` requires the acting coordinator to own the dataset's department, requires the dataset's `publication_status` to be `PUBLISHED` — a dataset sitting in `UNDER_REMEDIATION` cannot have its pipeline resumed — requires the runner to be `ACTIVE`, and re-applies both interval rules exactly as at arming time. It sets `consecutive_failure_count` back to 0, clears `suspend_reason`, increases the runner's `armed_window_count` by 1, lifts the `STALE` floor so that the dataset's `currency_status` is re-derived purely from the logical clock, re-derives the department's `stale_dataset_count`, `risk_points` and `compliance_posture`, and increments the pipeline's `version`. The `ARMED → SUSPENDED → ARMED` cycle may repeat indefinitely.

Decommissioning is terminal and reachable from all three live states, with the credit and counter consequences differing by where it starts. From `DRAFT`, `DRAFT → DECOMMISSIONED` moves no credits at all, because no escrow was ever taken, and leaves the runner's `armed_window_count` unchanged; the pipeline's `version` increments. A `DRAFT` pipeline also reaches this state silently when its dataset is given a replacement configuration, which is the case in which the successor records `superseded_pipeline_id`. From `ARMED`, `ARMED → DECOMMISSIONED` releases the escrow — the pipeline's current `escrowed_credit_units` are added back to the department's `credit_balance_units` and subtracted from its `credits_escrowed_units`, and the pipeline's `escrowed_credit_units` is set to 0.00 — moves every `SCHEDULED` or `RETRY_QUEUED` run to `SKIPPED` with a `skip_reason` of `PIPELINE_DECOMMISSIONED`, decreases the runner's `armed_window_count` by 1, and increments the pipeline's `version`. From `SUSPENDED`, `SUSPENDED → DECOMMISSIONED` requires the acting coordinator to own the dataset's department, releases the escrow by exactly the same arithmetic, does **not** decrease the runner's `armed_window_count` again because leaving `ARMED` already released that count, lifts the `STALE` floor and re-derives the dataset's `currency_status`, and increments the pipeline's `version`. In all three cases the release uses the pipeline's *current* `escrowed_credit_units`, which earlier run settlements may already have drawn down, not the original `escrow_required_units`.

### 3.6. Run Execution, Credit Settlement and the Published Version Ledger

Each occurrence of an automated publication is a `PipelineRun`. Scheduling one takes the `pipeline_id` and a `scheduled_for_utc` instant. That instant must not be in the past — the logical clock must not yet have passed it, or the request is refused with `ERR_RUN_SCHEDULE_INVALID` — and its minute-of-day must fall inside the pipeline's half-open window, at or after `window_start_minute` and strictly before `window_end_minute`, or the request is refused with `ERR_RUN_OUTSIDE_WINDOW`. A new run has `status` `SCHEDULED`, `alert_dispatched` false, `rows_ingested` 0, `started_at` and `finished_at` and `failure_code` and `skip_reason` all null, and `consecutive_failure_index` initialised from the pipeline's current `consecutive_failure_count`.

Starting a run moves it `SCHEDULED → RUNNING`, or `RETRY_QUEUED → RUNNING` when it is a retry, and stamps `started_at` at the current logical instant. Both paths require that the pipeline's `status` be `ARMED` — otherwise `ERR_PIPELINE_NOT_ARMED` — that the runner be `ACTIVE`, and that the logical clock have reached or passed `scheduled_for_utc`, a start before its time being refused with `ERR_RUN_SCHEDULE_INVALID`. Starting a run for the first time additionally requires that any embargo on the dataset have expired and that the dataset's `publication_status` be `PUBLISHED`.

Reporting success moves the run `RUNNING → SUCCEEDED` and takes a `rows_ingested` count of at least zero. Reporting failure moves the run `RUNNING → FAILED` and takes a `failure_code` of `SOURCE_UNAVAILABLE`, `SCHEMA_DRIFT`, `TIMEOUT` or `TRANSFORM_ERROR`. Both stamp `finished_at`, both settle a charge against the department's credits, and both increment the run's `version` — and there the resemblance ends.

Settlement is a strictly sequential six-step calculation, and the sequence is pinned because the reliability tier looks circular at first glance. Step one computes `compute_credits`: divide `rows_ingested` by 10000 rows per compute unit, round that quotient **up** to a whole number of units, and charge 4 credits per unit. A failed run has `rows_ingested` of 0, so its `compute_credits` is 0.00. Step two computes `alert_credits`: 3 credits when `alert_dispatched` is true, and 0.00 when it is false. Step three adds the two into `subtotal_credits`. Step four keys `reliability_discount_pct` on that subtotal and on nothing else: 0.10 when `subtotal_credits` is 40 or more, 0.05 when it is 20 or more but below 40, and 0.00 below 20. Step five computes `discount_credits` as `subtotal_credits` multiplied by `reliability_discount_pct`, rounded half up to two decimal places. Step six computes `total_charge_credits` as `subtotal_credits` minus `discount_credits`, again rounded half up to two decimal places. The tier is never re-evaluated against the discounted figure: a subtotal of exactly 40 settles at 36.00 credits, not at 38.00. Only the run being settled matters; earlier runs of the same pipeline affect the failure streak and nothing about this charge.

The charge is then drawn through a two-bucket waterfall, escrow first. `escrow_drawn_units` is the lesser of the pipeline's current `escrowed_credit_units` and `total_charge_credits`; `balance_drawn_units` is whatever remains of the charge after that. The pipeline's `escrowed_credit_units` and the department's `credits_escrowed_units` are each reduced by `escrow_drawn_units`, the department's `credit_balance_units` is reduced by `balance_drawn_units`, and the department's `credits_consumed_units` is increased by the full `total_charge_credits` — which keeps the conservation invariant of §2.10 intact.

A successful run rolls the dataset forward. Its `alert_credits` is 0.00 because no alert was dispatched. A new `DatasetVersion` is minted with `change_type` `SCHEDULED_REFRESH`, `source_run_id` pointing at the run, `row_count` equal to `rows_ingested`, `status` `LIVE`, `published_at` at the current logical instant, and `supersedes_version_id` pointing at the version that was `LIVE` immediately before — and that predecessor moves `LIVE → SUPERSEDED` with `superseded_at` stamped at the same instant. On the dataset, `live_row_count` becomes `rows_ingested`, `version_index_high_water` increases by one and supplies the new version's `version_index`, `last_published_at` becomes the current logical instant, and `next_due_at`, `days_overdue` and `currency_status` are re-derived — which lands `currency_status` at `CURRENT` and `days_overdue` at 0 provided no pipeline of the dataset is suspended. The pipeline's `consecutive_failure_count` resets to 0. The department's counters, `risk_points` and `compliance_posture` are re-derived. The run's `version`, the pipeline's `version` and the dataset's `version` each increment by one.

A failed run does none of that and instead escalates, in four hops. Hop one records the outcome: `failure_code` is stored, `alert_dispatched` is set to true and an alert is dispatched to the pipeline's `alert_email`, `rows_ingested` stays 0, the pipeline's `consecutive_failure_count` increases by 1 and that new value is copied into the run's `consecutive_failure_index`, and the alert-only charge is settled through the same waterfall. Note that the dataset's `staleness_alert_count` is *not* touched by this hop — the failure alert goes to `alert_email`, whereas staleness alerting is emitted only by the portal sweep and by the cascade that suspends a pipeline. Hop two fires when `consecutive_failure_count` has reached 3: the pipeline transitions `ARMED → SUSPENDED` with `suspend_reason` `FAILURE_STREAK`, which skips its pending runs as described in §3.5. Hop three follows from the pipeline having become suspended: the dataset's `currency_status` takes the `STALE` floor — formally, the dataset's currency becomes the more severe of what the clock alone would say and `STALE`, so a dataset that was perfectly fresh moves `CURRENT → STALE` in one step, skipping `AGING` entirely — and its `staleness_alert_count` increases by 1 with `last_staleness_alert_at` stamped at the current logical instant. Hop four follows from the dataset having become stale: the department's `stale_dataset_count`, `risk_points` and `compliance_posture` are re-derived. Only the dataset's `publication_status` being `PUBLISHED` or `UNDER_REMEDIATION` allows hops three and four to apply.

A failed run may be requeued rather than abandoned. The transition `FAILED → RETRY_QUEUED` takes a replacement `scheduled_for_utc`, requires the pipeline to still be `ARMED`, requires that instant to be at or after the logical clock and its minute-of-day to fall inside the pipeline's half-open window, and then overwrites `scheduled_for_utc`, clears `failure_code`, `started_at` and `finished_at`, and sets `alert_dispatched` back to false. The `FAILED → RETRY_QUEUED → RUNNING` cycle may repeat. Runs that never get their chance are skipped by cascade rather than by request: a run whose owning pipeline leaves `ARMED` in the same request moves `SCHEDULED → SKIPPED` or `RETRY_QUEUED → SKIPPED` as its own current state dictates, with `finished_at` stamped at the current logical instant and `skip_reason` set to `PIPELINE_SUSPENDED` when the pipeline was suspended, `PIPELINE_DECOMMISSIONED` when it was decommissioned directly, and `DATASET_RETIRED` when the cascade came from the dataset being retired. No credits are charged for a skipped run. `SUCCEEDED` and `SKIPPED` are both terminal.

Versions can also be published by hand, which is how corrections reach the public. A coordinator publishes one by supplying the `dataset_id`, a `change_type` of `INITIAL`, `SCHEDULED_REFRESH`, `CORRECTION` or `SCHEMA_CHANGE`, a `row_count` of at least zero, optional `notes` for the public version history, an optional `correction_issue_id` naming the quality issue the version answers, and the mandatory `expected_dataset_version` token. This is permitted while the dataset's `publication_status` is `PUBLISHED` and also while it is `UNDER_REMEDIATION`, because a corrective version is precisely what lifts remediation; any other state is refused with `ERR_DATASET_NOT_PUBLISHED`. The new version takes `version_index` equal to the dataset's `version_index_high_water` plus one, a matching `version_label`, `status` `LIVE`, `published_at` at the current logical instant, and `supersedes_version_id` pointing at the previously `LIVE` version, which moves to `SUPERSEDED` with `superseded_at` stamped. On the dataset, `live_row_count` becomes the supplied `row_count`, `version_index_high_water` becomes the new index, `last_published_at` becomes the current logical instant, and `next_due_at`, `days_overdue` and `currency_status` are re-derived. Supplying `correction_issue_id` merely tags the version as the remedy for that issue; it does not by itself move the issue, and it does not by itself lift remediation. The dataset's `version` increments.

Retraction is the compensating action for a version that should not have gone out, and it conserves the published record rather than deleting it. Retracting the `LIVE` version takes an optional `reason` and requires a predecessor to restore: the version's `version_index` must be at least 2 and the immediately preceding version must currently be `SUPERSEDED`, or the request is refused with `ERR_NO_PREDECESSOR_VERSION`. A version that is not `LIVE` cannot be retracted, which surfaces as `ERR_VERSION_NOT_LIVE`. On success the version moves `LIVE → RETRACTED` with `retracted_at` stamped, and its predecessor moves `SUPERSEDED → LIVE` with `superseded_at` cleared back to null. The dataset's `live_row_count` is restored to the predecessor's `row_count` and its `last_published_at` to the predecessor's `published_at`, while `version_index_high_water` is deliberately **not** decreased — index numbers are never reused. `next_due_at`, `days_overdue` and `currency_status` are then re-derived from the restored publication instant. Both the retracted version's `version` and the dataset's `version` increment; the restored predecessor's `version` increments as well. `RETRACTED` is terminal. At any moment a dataset that has been published at least once and never fully retracted has exactly one version in `LIVE`.

### 3.7. Community Participation: Quality Issues and Corrections

Anyone may join the programme as a community member, either by self-registration or on the programme office's behalf, by supplying an `email` that is unique across all members, a public `display_name` and an optional `organization` shown on showcase entries. A new member begins with `accepted_issue_count`, `rejected_issue_count`, `approved_showcase_count` and `decay_epochs` all zero, `reputation_score` 50.00, `vote_weight` 2, `status` `ACTIVE`, and `last_credited_at` initialised to the member's own `created_at`.

Reputation is what gives a member's voice weight, and it decays if the member stops contributing. The raw figure starts from a base of 50, adds 6 points for each accepted issue in `accepted_issue_count`, subtracts 4 points for each rejected issue in `rejected_issue_count`, and adds 2 points for each approved showcase in `approved_showcase_count`. `accepted_issue_count` counts the member's quality issues whose `status` is `ACCEPTED`, `CORRECTED` or `CLOSED`; `rejected_issue_count` counts those whose `status` is `REJECTED`; issues still `SUBMITTED` or `TRIAGED` count in neither. Decay is measured in whole thirty-day epochs: `decay_epochs` is the elapsed time from `last_credited_at` to the current logical instant divided by thirty days and floored to a whole number, never below zero. The distance of the raw figure from the base of 50 is then multiplied by 0.80 raised to the power of `decay_epochs`, and that shrunken distance is added back to the base. The result is clamped to lie between 0 and 100 inclusive and rounded half up to two decimal places once, after clamping, giving `reputation_score`. `vote_weight` follows on inclusive thresholds: 3 when `reputation_score` is at least 70.00, 2 when it is at least 40.00 but below 70.00, and 1 below 40.00. Independently of the score, a member's `status` becomes `THROTTLED` as soon as `rejected_issue_count` minus `accepted_issue_count` reaches 3, and is `ACTIVE` otherwise. Reputation is re-derived whenever a member is read individually, whenever one of their issues is accepted or rejected, whenever one of their showcase submissions is approved, and whenever they cast a vote.

Filing a quality issue is a member's main lever. The member supplies the `dataset_id` the defect was found in, their own `reporter_member_id`, a `severity` of `LOW`, `MEDIUM`, `HIGH` or `CRITICAL`, a `category` of `ACCURACY`, `COMPLETENESS`, `TIMELINESS`, `SCHEMA` or `PRIVACY`, and a free-text `description` of the defect. A `THROTTLED` member is refused with `ERR_MEMBER_THROTTLED`. The issue starts at `status` `SUBMITTED` with `triage_breached` and `correction_breached` both false, `resolution_version_id` null, and a `triage_due_at` computed as its `created_at` plus a severity-dependent allowance: seven days for `LOW`, three days for `MEDIUM`, one day for `HIGH`, and eight hours for `CRITICAL`.

The owning department triages the issue, moving it `SUBMITTED → TRIAGED`, which is permitted only while the dataset's `publication_status` is `PUBLISHED` or `UNDER_REMEDIATION`. Triage stamps `triaged_at` at the current logical instant and latches `triage_breached` to true when the logical clock is strictly past `triage_due_at`; arriving exactly at the deadline is on time, not late. Both breach flags in this system latch: once true they are never cleared by a later observation, and `correction_breached` is cleared only by the correction itself.

The coordinator then decides the triaged issue with a `decision`, and the two outcomes have disjoint consequences. A `REJECT` decision requires a `reject_reason` of `NOT_REPRODUCIBLE`, `OUT_OF_SCOPE` or `DUPLICATE`, moves the issue `TRIAGED → REJECTED`, increases the reporter's `rejected_issue_count` by 1, sets the reporter's `last_credited_at` to the current logical instant, and re-derives the reporter's `reputation_score`, `vote_weight` and `status` — which is where a member can tip from `ACTIVE` into `THROTTLED`. No dataset or pipeline side effect fires at all. The issue's `version` increments. `REJECTED` is terminal.

An `ACCEPT` decision moves the issue `TRIAGED → ACCEPTED`, is blocked when the department's posture is `SUSPENDED`, and heads a four-hop cascade. Hop one records the acceptance: `accepted_at` is stamped at the current logical instant, `correction_due_at` is set to `accepted_at` plus a severity-dependent allowance of 90 days for `LOW`, 30 days for `MEDIUM`, 14 days for `HIGH` and 5 days for `CRITICAL`, the reporter's `accepted_issue_count` increases by 1, the reporter's `last_credited_at` becomes the current logical instant, and the reporter's `reputation_score` and `vote_weight` are re-derived. Hop two fires only when the issue's `severity` is `CRITICAL` **and** its `category` is `PRIVACY` **and** the dataset's `publication_status` is `PUBLISHED`: the dataset transitions `PUBLISHED → UNDER_REMEDIATION`, `public_access_suspended` becomes true and `remediation_opened_at` is stamped at the current logical instant. Hop three follows from the dataset having left `PUBLISHED`: every pipeline of that dataset whose `status` is `ARMED` transitions to `SUSPENDED` with `suspend_reason` `REMEDIATION_HOLD`. Hop four follows from that suspension: the pipeline's `SCHEDULED` and `RETRY_QUEUED` runs become `SKIPPED` with `skip_reason` `PIPELINE_SUSPENDED`, and the dataset's `currency_status` takes the `STALE` floor. Finally the department's `remediation_dataset_count` and its other counters, `risk_points` and `compliance_posture` are re-derived. The issue's `version` increments, as does the dataset's.

Correction closes the loop. The coordinator publishes a corrective version as described in §3.6 and then attaches it to the accepted issue by supplying the `dataset_version_id` of that version. The attachment requires the acting coordinator to own the dataset's department and requires the referenced version to belong to the same dataset, to carry `change_type` `CORRECTION` and to currently be `LIVE`. It sets the issue's `resolution_version_id` to that version, sets that version's own `correction_issue_id` back to the issue, moves the issue `ACCEPTED → CORRECTED`, and clears `correction_breached`. When the dataset is sitting in `UNDER_REMEDIATION` and no *other* quality issue on that dataset is still `ACCEPTED` with `severity` `CRITICAL` and `category` `PRIVACY`, the same request returns the dataset `UNDER_REMEDIATION → PUBLISHED`: `public_access_suspended` becomes false, `remediation_opened_at` is cleared to null, and `currency_status` is re-derived — though the `STALE` floor imposed by a still-suspended pipeline continues to apply for as long as that pipeline stays suspended. The department's `overdue_correction_count`, `risk_points` and `compliance_posture` are re-derived, and both the issue's `version` and the dataset's `version` increment. A corrected issue is finally closed, moving `CORRECTED → CLOSED`, which requires `resolution_version_id` to be set and increments the issue's `version`. `CLOSED` is terminal.

### 3.8. Dataset Requests, Showcase Applications and Usage Analytics

Community demand also arrives as a request for data the portal does not yet hold. A member opens one with their own `requester_member_id`, a `title` naming the dataset they want and a `rationale` explaining why. The request starts at `status` `OPEN` with an empty `votes` array, `weighted_vote_total` 0, `demand_signal` 0.00, `linked_dataset_id` null and `decision_note` null.

Voting is how the community ranks those requests against each other. A member casts a vote by supplying their own `member_id`; a `THROTTLED` member may not vote and is refused with `ERR_MEMBER_THROTTLED`, and a member who has already voted on that request is refused with `ERR_DUPLICATE_VOTE`. The vote is appended to `votes` as an entry holding the `member_id`, a `weight` snapshotting the member's `vote_weight` at the moment of casting, and a `cast_at` instant. Snapshots are never re-weighted: if the member's reputation later rises or falls, the stored `weight` stands. `weighted_vote_total` is then the plain sum of every stored `weight` across the whole array with no time window, and `demand_signal` is that total multiplied by 5, capped at 100, and rounded half up to two decimal places. If the request is already linked to a dataset, that dataset's community-pressure input and its `priority_score` are re-derived as well.

The programme office takes a sufficiently supported request under review, moving it `OPEN → UNDER_REVIEW`, which requires `weighted_vote_total` to have reached at least 4 — anything below that is refused with `ERR_INSUFFICIENT_DEMAND` — and which stores the optional `decision_note` supplied with it. Deciding an `UNDER_REVIEW` request takes a `decision` and a mandatory `decision_note`, which is stored in every case. An `ACCEPT` decision moves the request `UNDER_REVIEW → ACCEPTED`. A `DECLINE` decision moves it `UNDER_REVIEW → DECLINED`, which is terminal. A `DEFER` decision moves it `UNDER_REVIEW → OPEN`, deliberately preserving every stored vote so the request can be reviewed again once more demand accrues; the `OPEN → UNDER_REVIEW → OPEN` deferral cycle may repeat. All three increment the request's `version`.

Fulfilment is the moment community demand transfers onto a real catalogue entry. The programme office supplies the `dataset_id` that satisfies an `ACCEPTED` request, which must have a `publication_status` of `SCREENING`, `READY` or `PUBLISHED`. The request moves `ACCEPTED → FULFILLED`, its `linked_dataset_id` is set to that dataset, and the linked dataset's community-pressure input and `priority_score` are recomputed under whichever variant its current `priority_score_variant` names. Both the request's `version` and the dataset's `version` increment. `FULFILLED` is terminal.

Showcase applications are the other half of community engagement. A member submits one against a dataset by supplying a `label` that must be unique within that dataset, the application's `name`, its `url`, and their own `submitter_member_id`. The entry is appended to the dataset's `showcase_apps` with `status` `SUBMITTED` and `decided_at` null. The programme office then moderates the entry by addressing it by its label and supplying a `decision`, which sets that entry's `status` to `APPROVED` or `REJECTED` and stamps its `decided_at`. On approval the submitter's `approved_showcase_count` increases by 1 and their `reputation_score` and `vote_weight` are re-derived; a rejection credits nothing.

Usage analytics feed the observed-demand half of prioritisation. The programme office records one usage epoch at a time against a dataset by supplying an `epoch_index` that must be unique for that dataset, an `api_call_count` and a `download_count`; the epoch is appended to `usage_epochs` together with a `recorded_at` instant. Recording usage is allowed from `SCREENING` onward, because a catalogue page draws traffic before the extract itself is published; any earlier state is refused with `ERR_DATASET_NOT_PUBLISHED`.

The engagement index reads only those epochs, and it reads only three of them. Sort the dataset's `usage_epochs` by `epoch_index` descending and take the first three rows — because `epoch_index` is unique per dataset the ordering is total and no tie-break is needed, and were two rows ever to tie, the earlier `recorded_at` would come first. Each selected epoch is valued at 0.60 times its `api_call_count` plus 0.40 times its `download_count`. Those values are then combined positionally, with the highest-indexed epoch weighted 0.50, the next 0.30 and the next 0.20. The positional weights are deliberately **not** renormalised when fewer than three epochs exist: a dataset with a single epoch keeps only the 0.50 weight and the remaining 0.50 is simply lost. The weighted total is divided by 50, rounded half up to two decimal places once, and capped at 100.00, giving `engagement_index`; `observed_demand_score` is set to the same value. A dataset whose `usage_epochs` is empty has an `engagement_index` of 0.00. Recording an epoch recomputes `engagement_index` and `observed_demand_score`, then recomputes `priority_score` under the variant that the dataset's current `publication_status` selects — `AS_DECLARED` while `INVENTORIED`, `SCREENING` or `READY`, and `AS_OBSERVED` from `PUBLISHED` onward — updating `priority_score_variant` and `priority_tier` accordingly.

A per-dataset analytics capability exposes all of that in one computed read, answering with the `dataset_id`, `engagement_index`, `observed_demand_score`, `priority_score`, `priority_score_variant`, `priority_tier`, both variants side by side as `priority_score_as_declared` and `priority_score_as_observed`, a `usage_epoch_count`, the `approved_showcase_count` of approved showcase entries on the dataset, an `open_issue_count`, and the currency picture as `currency_status`, `days_overdue` and `next_due_at`.

### 3.9. Currency Service Levels, Staleness Detection and the Portal Sweep

A published dataset carries a promise about how fresh it will stay, and `currency_status` is the portal's honest answer about whether that promise is being kept. It is derived, never set by hand. First, `next_due_at` is the dataset's `last_published_at` plus the number of days its `update_frequency` implies — 1 day for `DAILY`, 7 for `WEEKLY`, 30 for `MONTHLY`, 91 for `QUARTERLY`, 365 for `ANNUAL` — and is null both when `update_frequency` is `IRREGULAR` and when the dataset has never been published. Second, `days_overdue` is zero whenever `next_due_at` is null or the logical clock has not yet passed it, and is otherwise the elapsed seconds from `next_due_at` to the current logical instant divided by 86400 and floored to a whole number of days. Third, a grace allowance is read off the dataset's `priority_tier`: 2 days for `TIER_1`, 7 days for `TIER_2`, 14 days for `TIER_3` — the more valuable the dataset, the shorter its rope.

The clock's verdict then follows. It is `CURRENT` when `next_due_at` is null or the logical clock has not passed it. It is `AGING` when `days_overdue` is greater than zero but no greater than the grace allowance; the boundary is inclusive, so a `days_overdue` exactly equal to the grace is still `AGING` and one day beyond it is `STALE`. It is `STALE` when `days_overdue` exceeds the grace but does not exceed twice the grace. Beyond twice the grace it is `BREACHED` — but only for a dataset whose `high_value_committed` flag is true; a dataset without that commitment floors at `STALE` and never reaches `BREACHED` however long it is neglected. Independently of all of that, a suspended pipeline imposes a floor: if any pipeline of the dataset has `status` `SUSPENDED`, the dataset's currency is at least `STALE`. Pipelines in `DRAFT` or `DECOMMISSIONED` impose no floor. The stored `currency_status` is the more severe of the clock's verdict and the pipeline floor, where severity ascends `CURRENT`, `AGING`, `STALE`, `BREACHED`. This derivation runs on publication, on every successful run, on every manually published version, on every retraction, on every pipeline transition into or out of `SUSPENDED`, and on every portal sweep.

The high-value commitment is what unlocks the strictest tier of that scale. The programme office commits a dataset to the high-value currency service level, which requires the dataset's `priority_tier` to be `TIER_1` and its `publication_status` to be `READY` or `PUBLISHED`; anything else is refused with `ERR_NOT_HIGH_VALUE_ELIGIBLE`. The commitment sets `high_value_committed` to true, which both enables the `BREACHED` state for that dataset and exposes its department to the heaviest risk weight in §2.9.

Publishing forward is what escapes a bad currency state. When a new version becomes `LIVE` at the current logical instant — whether from a successful automated run or from a manually published version — a dataset in `STALE` returns `STALE → CURRENT` and a dataset in `BREACHED` returns `BREACHED → CURRENT`, provided no pipeline of that dataset is still `SUSPENDED`. Both recompute `next_due_at` from the new `last_published_at` and set `days_overdue` to 0, both re-derive the department's counters, `risk_points` and `compliance_posture` — the breached case specifically retiring a unit of `breached_dataset_count` — and both increment the dataset's `version`.

Drifting the other way is the portal sweep's job. The sweep is an operational capability held by the programme office alone, and it walks five steps in a fixed order. Step one recomputes `days_overdue` and `currency_status` for every non-retired published dataset by the derivation above, which is where the clock-driven transitions `CURRENT → AGING`, `AGING → STALE` and `STALE → BREACHED` all happen; a dataset only participates when its `publication_status` is `PUBLISHED` or `UNDER_REMEDIATION`, and the `CURRENT → AGING` step additionally requires `next_due_at` to be non-null. Step two emits staleness alerting: every dataset that is entering or remaining in `STALE` or `BREACHED` emits exactly one alert per sweep, increasing `staleness_alert_count` by 1 and setting `last_staleness_alert_at` to the current logical instant. A dataset that merely became `AGING` emits nothing. Step three recomputes `engagement_index` and then `priority_score` under the `AS_OBSERVED` variant for every published dataset, which can move `priority_tier` and therefore change the grace allowance the *next* sweep applies. Step four walks the quality issues in ascending `created_at` order, inspecting only those whose `status` is `SUBMITTED` or `ACCEPTED`: a still-`SUBMITTED` issue whose `triage_due_at` the logical clock has strictly passed latches `triage_breached` to true, and a still-`ACCEPTED` issue whose `correction_due_at` the logical clock has strictly passed latches `correction_breached` to true. In both cases equality with the deadline is not a breach. Step five walks the departments in ascending `created_at` order — deliberately after every dataset has been recomputed in step one — re-deriving each department's four counters, its `risk_points` and its `compliance_posture`.

The sweep reports what it did: a count of `datasets_recomputed`, a count of `currency_transitions`, a count of `staleness_alerts_emitted`, counts of `issues_triage_breached` and `issues_correction_breached`, and a count of `departments_recomputed` alongside `postures_changed`.
