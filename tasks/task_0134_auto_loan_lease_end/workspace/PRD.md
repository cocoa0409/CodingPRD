# Auto Loan & Lease End API — Product Requirements Document

## 1. Introduction

The Auto Loan & Lease End API is the backbone of a retail auto-finance platform that originates car loans and consumer leases, prices them against a customer's FICO-derived credit tier, schedules monthly payments, handles delinquency and re-pricing, and ultimately runs the end-of-lease process — purchase, renewal, or return — with a full accounting of disposition fees and mileage overage penalties. The system serves five constituencies: customers who shop, sign, and pay; loan officers who originate and approve contracts; finance managers who handle gap insurance and lease-end assessments; collections agents who work delinquent loans; and platform administrators who manage the customer base and the deterministic simulation clock.

The product's hardest requirements come from the intersection of three concerns. **Pricing is dual-variant**: every loan exposes both a "book" payoff and a "cash" payoff with prepayment penalty, and every lease exposes both an "at-maturity" and an "early-buyout" purchase quote — the two answers differ on the same contract by design, and the API must return each precisely. **Delinquency cascades forward but not backward**: when a customer crosses a lifetime threshold of defaulted payments, future loan payments are re-priced at a higher APR, but past amortization is never rewritten. **Lease-end is a three-way branch with disposition consequences**: the customer's election among purchase, renew, and return determines whether a disposition fee is charged, whether a purchase option price is computed, and what the vehicle's downstream status becomes. The deterministic per-customer clock makes all of this testable: time only advances when a privileged caller explicitly advances it.

## 2. Global Specifications & System-Wide Principles

This section defines the system-wide rules — authentication, response envelope, pagination, common resource fields, precision, concurrency, hierarchical consistency, and the cross-cutting business safeguards — that apply to every endpoint in the API. Where a numeric constant or threshold has business meaning, it is named here and re-applied in §3 inside the workflow that depends on it.

### 2.1. User and Role-Based Access Control

Every request to the API must carry two HTTP headers: `X-User-ID` identifies the acting principal and `X-User-Role` declares the principal's operational capacity. Missing or malformed headers are rejected at the front door with `ERR_MISSING_OR_INVALID_USER_CONTEXT_HEADER`. When the headers are well-formed but the named role is not permitted to invoke the requested operation, the request is rejected with `ERR_FORBIDDEN_ROLE`.

The system recognizes exactly five roles, spelled as follows: `PlatformAdmin`, `LoanOfficer`, `FinanceManager`, `CollectionsAgent`, and `Customer`.

The four operator roles — `PlatformAdmin`, `LoanOfficer`, `FinanceManager`, and `CollectionsAgent` — all carry an opaque identity. When `X-User-Role` is any of these four, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it for audit but does not compare it to any entity's `id`. The `Customer` role is entity-backed: when `X-User-Role` is `Customer`, `X-User-ID` is the `id` of the acting `Customer`, and ownership checks on any resource that references a `Customer` (loan contract, lease contract, payment, lease-end assessment, gap rider) compare the resource's `customer_id` to `X-User-ID`. In particular, a `Customer` calling pay on a payment whose parent contract's `customer_id` does not equal `X-User-ID` is treated as an unauthorized actor and rejected.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two pagination query parameters. The `limit` parameter caps the page size; if omitted it defaults to 10, with a minimum accepted value of 1 and a maximum accepted value of 100. The `offset` parameter is the number of items to skip and defaults to 0. Unless otherwise specified, list endpoints return results sorted by `created_at` in ascending order. Every list response's `meta` object carries the four pagination fields `limit`, `offset`, `total_count`, and `has_more`.

### 2.4. Common Resource Properties

Most top-level entities in this system — `Customer`, `Vehicle`, `LoanContract`, `LeaseContract`, `GapInsuranceRider`, and `LeaseEndAssessment` — carry the full common-fields set: a server-minted `id` formatted as a UUID with no type prefix, a `created_at` ISO 8601 UTC timestamp with three fractional digits, an `updated_at` ISO 8601 UTC timestamp updated on every mutation, and a monotonically increasing integer `version` that begins at 1 on creation and increments by one on every mutation. Updates to derived fields — for example, recomputation of a loan's `monthly_payment_cents` after a default uplift, or of a lease-end assessment's `total_due_cents` after a mileage revision — are mutations and therefore increment `version` and refresh `updated_at`.

Two entities in this system are treated as immutable event records and carry only `id` and `created_at`: `Payment` and `DelinquencyEvent`, plus the read-only `ClockEvent` audit row. For `Payment`, state transitions (`SCHEDULED` to `PAID`, `LATE`, or `DEFAULTED`) update the row's status field and the relevant denormalized counters in place, but neither `updated_at` nor `version` exist on the row. `DelinquencyEvent` and `ClockEvent` rows are append-only and never mutated.

### 2.5. Nested Resource Retrieval and Path Validation

Every endpoint whose path nests resources — for example, a payment under a customer, or an assessment under a lease contract under a customer — validates path identifiers strictly left to right. The first identifier that does not resolve to an existing row determines the error: a request for a payment under a non-existent customer returns `ERR_CUSTOMER_NOT_FOUND`, never `ERR_PAYMENT_NOT_FOUND`. The same principle applies to lease contracts and loan contracts (`ERR_CONTRACT_NOT_FOUND`), to lease-end assessments (`ERR_ASSESSMENT_NOT_FOUND`), to gap riders (`ERR_RIDER_NOT_FOUND`), and to vehicles when looked up directly (`ERR_VEHICLE_NOT_FOUND`). Cross-customer leakage — addressing a contract or payment that exists but belongs to a different `customer_id` than the one in the URL — is reported as a not-found on the inner resource, never as a successful read.

### 2.6. Optimistic Concurrency Control

Every mutating endpoint that targets an entity with the common-fields set accepts an optional `version` value in the request body. When the field is present, the server compares it against the persisted entity's current `version` and rejects mismatches with `ERR_VERSION_CONFLICT`. When the field is omitted, the server proceeds without the check. A successful mutation increments `version` by exactly one. Two concurrent advances of the same customer's clock are an example of the OCC contract in action: the platform serializes them on the customer's `version`, so the first writer wins, the second receives `ERR_VERSION_CONFLICT`, and the loser is expected to refetch and retry — the clock never interleaves.

### 2.7. Hierarchical State Consistency and Cascades

State transitions in this system frequently propagate to related entities. The PRD's general rule is that every cascade mentioned in §3 is part of the same logical transaction as the operation that triggered it, and every mutation participant has its own `updated_at` and `version` refreshed. Two patterns recur. **Contract-to-rider cancellation**: when a loan reaches `PAID_OFF` or `CHARGED_OFF`, or when a lease reaches `CLOSED`, any linked `GapInsuranceRider` that is still `ACTIVE` is auto-transitioned to `CANCELLED`. **Customer-to-contract delinquency**: when a customer's lifetime `default_count` crosses the uplift threshold for the first time, every `ACTIVE` loan owned by that customer has its `apr_bps` raised and its still-`SCHEDULED` payments re-priced — a four-step cascade from `Payment` (defaulted) to `Customer` (counter bumped and rate recomputed) to `LoanContract` (rate uplifted) and back to `Payment[]` (schedule re-priced). When the system performs these cascades, each affected entity is mutated independently with its own `updated_at` and `version` increment.

### 2.8. Monetary Values, Precision, and Rounding

All monetary values are integer cents. Where a calculation produces a value that requires rounding, the rounding mode is pinned per calculation: monthly loan payments and per-mile penalty totals use ceiling rounding; the per-component lease payment uses floor rounding for the depreciation and finance components and ceiling rounding for the tax component; amortization interest accrual uses floor rounding. The customer's lifetime `default_rate` is stored to six decimal places using round-half-up. Basis points (`apr_bps`, `residual_factor_bps`) and money factor micro-units (`money_factor_micro`) are integers as well — no fractional basis points and no fractional micro-units are ever stored. The rounding order for any composite formula is fixed and is described inside that formula's narrative in §3; in particular, the lease monthly payment uses round-per-component-then-sum, while the loan monthly payment computes the unrounded amortization quotient and rounds once at the end.

### 2.9. The Deterministic Per-Customer Clock

Time in this system is not wall-clock time. Every customer carries a `clock_day_index` integer that begins at 0 on customer creation and only advances when a privileged caller explicitly advances it. This per-customer clock drives three behaviors that would otherwise be untestable: it is captured into a contract's `origination_day_index` at approval; it determines a payment's `due_day_index` (origination plus thirty days per period); and it triggers the automatic transitions of `SCHEDULED` payments to `LATE`, of `LATE` payments to `DEFAULTED`, and of `ACTIVE` leases that have run their full term to `MATURED`. The clock is also reproducible per customer — advancing one customer's clock does not affect any other customer's payments, lease maturity, or default counters. The `ClockEvent` row appended on every advance records `days_advanced` (the integer the caller submitted), the resulting `new_clock_day_index`, the count of `payments_due_now` (payments whose `due_day_index` fell inside the advance window), and the count of `payments_defaulted_now` (payments whose status auto-transitioned from `LATE` to `DEFAULTED` during the advance), so the cumulative effect of any clock motion can be inspected after the fact.

### 2.10. The Stickiness of Default and the Forward-Looking Re-Pricing Convention

Defaults in this platform are sticky for accounting purposes. Once a `Payment` has reached `DEFAULTED`, paying it later transitions the `Payment.status` back to `PAID` and applies amortization, but it does not decrement the customer's `default_count`. This is intentional: the customer's `default_count` is a lifetime tally of how many payments have ever defaulted, not a snapshot of currently-defaulted rows. The `default_rate` derived from this counter is therefore monotonically non-decreasing as defaults occur and is updated, but not reduced, when defaulted payments are later cured.

The same forward-looking principle governs APR uplift. When the system raises a loan's `apr_bps` after a delinquency threshold is crossed, the uplift re-prices only the still-`SCHEDULED` payments — already-`PAID` payments keep their original amortization split, and `total_principal_paid_cents` and `total_interest_paid_cents` are not retroactively recomputed. The platform does not support chronological re-amortization that would back-fill historical interest and principal portions; this distinction matters because the two approaches produce different total-interest-paid figures on identical inputs, and this scaffold pins the forward-looking approach.

### 2.11. Validation Priority Ordering

When multiple validations could apply to the same request, they are evaluated in a fixed priority order so that the rejection a caller receives is deterministic. Authentication-header validity is checked first; then role authorization; then path existence (the left-to-right rule from §2.5); then target-resource state (e.g., approve requires `PENDING_APPROVAL`, lease-end requires `MATURED`, settle requires `ISSUED`); then business-safety rules such as the gap-rider-parent-terminal protection; then business-referential rules such as cross-customer ownership of a rider's contract; then tier-based eligibility for leases; then temporal uniqueness rules (payment due-date collision, lease window overlap); then fiscal floors (down-payment minimums, claim-not-exceeding-gap); and finally the OCC `version` check. This ordering matters most when two failures coexist: a request with an out-of-date `version` against a contract that is already in the wrong state still returns the state error, not the version error, because the state check sits at priority four and the OCC check sits at priority twelve.

## 3. Business Logic & Workflows

### 3.1. Customer Onboarding and the FICO Tier Derivation

A new customer enters the system with two inputs supplied by a `PlatformAdmin` or `LoanOfficer`: `full_name`, the legal name that will appear on contracts, and `fico_score`, an integer credit score. The server validates that `fico_score` lies between 300 and 850 inclusive; values outside that range are rejected with `ERR_FICO_OUT_OF_RANGE`. On a successful create, the customer's `status` is set to `ACTIVE`, the per-customer `clock_day_index` is initialized to 0, and the cumulative counters `default_count`, `lifetime_payment_count`, and `default_rate` start at 0, 0, and 0.0 respectively.

The customer's `fico_tier` is a derived enum and is recomputed every time `fico_score` is created or updated. The derivation uses inclusive lower thresholds: a score of at least 720 maps to `TIER_1`; a score below 720 but at least 660 maps to `TIER_2`; a score below 660 but at least 600 maps to `TIER_3`; a score below 600 but at least 540 maps to `TIER_4`; any score below 540 maps to `TIER_5_DECLINED`. The boundaries are crisp: 720 is `TIER_1` and 719 is `TIER_2`; 660 is `TIER_2` and 659 is `TIER_3`; and so on. A subsequent update to the customer that changes `fico_score` re-derives `fico_tier` immediately as part of the same response. A customer update may carry an optional `version` to enforce OCC.

A `PlatformAdmin` may suspend an `ACTIVE` customer; the customer's `status` transitions from `ACTIVE` to `SUSPENDED`. While suspended, no new loan or lease contracts may be originated for that customer, and any loan or lease contracts still in `PENDING_APPROVAL` are blocked from advancing to `APPROVED`. The customer may later be reinstated by a `PlatformAdmin`, transitioning `status` back from `SUSPENDED` to `ACTIVE`.

### 3.2. The Vehicle Catalog

A `PlatformAdmin` registers a vehicle by supplying its `vin` (a 17-character vehicle identification number that must be unique across all vehicles), its `model` label, its `msrp_cents` manufacturer-suggested retail price (which must be strictly greater than zero, expressed in cents), and its `residual_factor_bps` — the residual value as basis points of MSRP for a 36-month lease, constrained to lie between 1000 and 8000 inclusive (so 5500 represents a 55% residual). The vehicle's `status` begins at `AVAILABLE` on creation. The lifecycle then moves through `RESERVED`, `SOLD`, or `LEASED` according to the financing path taken: loan approval transitions the vehicle from `AVAILABLE` to `SOLD`; lease approval transitions it from `AVAILABLE` to `LEASED`; a lease that ends in a `RETURN` election sends the vehicle back to `AVAILABLE`; and a lease that ends in a `PURCHASE` election sends the vehicle to `SOLD`. The vehicle list endpoint supports pagination via `limit` and `offset` and an optional `status` filter so that originators can search the catalog by availability.

### 3.3. Loan Origination, Approval, and Activation

A `LoanOfficer` begins loan origination by posting a payload that names the `vehicle_id` to be financed, the customer's `down_payment_cents`, and the requested `term_months`. The `term_months` value must be one of the four supported terms — 36, 48, 60, or 72 months — and a request that names any other value is rejected with `ERR_INVALID_REQUEST`. On creation, the contract's `principal_cents` is derived as the vehicle's `msrp_cents` minus the `down_payment_cents` provided in the body, and the contract enters `PENDING_APPROVAL`. The contract's `customer_id` is taken from the URL.

Approval is a separate operator action and is where the cross-entity preconditions concentrate. Before transitioning a loan from `PENDING_APPROVAL` to `APPROVED`, the system verifies four things: the parent customer's `status` is `ACTIVE` (a suspended customer cannot be approved, and the rejection is `ERR_CUSTOMER_NOT_ACTIVE`); the customer's `fico_tier` is not `TIER_5_DECLINED` (a declined applicant cannot take a loan, and the rejection is `ERR_LOAN_TIER_DECLINED`); the customer's `down_payment_cents` meets the tier-based minimum described below (otherwise `ERR_DOWN_PAYMENT_BELOW_MINIMUM`); and the vehicle's `status` is still `AVAILABLE` (otherwise `ERR_VEHICLE_NOT_AVAILABLE`). The vehicle is then transitioned to `SOLD`, the loan's `base_apr_bps` and `apr_bps` are set from the FICO-tier rate table, the `monthly_payment_cents` is computed via the standard amortization formula described below, `remaining_principal_cents` is initialized to `principal_cents`, `payments_scheduled_count` is set equal to `term_months`, and the loan's `origination_day_index` captures the customer's current `clock_day_index`. Two concurrent approvals on the same `PENDING_APPROVAL` loan are serialized: the first writer wins and the loser receives `ERR_LOAN_NOT_PENDING_APPROVAL` because the second sees the contract no longer in `PENDING_APPROVAL`. Any approve attempt against a loan that is not in `PENDING_APPROVAL` is rejected with the same `ERR_LOAN_NOT_PENDING_APPROVAL`; the lease counterpart is `ERR_LEASE_NOT_PENDING_APPROVAL` for approve attempts against a lease that is not in `PENDING_APPROVAL`.

The minimum down payment for a loan is a tiered fraction of the vehicle's `msrp_cents`. For `TIER_1` it is 5% (500 basis points), for `TIER_2` it is 10% (1000 basis points), for `TIER_3` it is 20% (2000 basis points), and for `TIER_4` it is 35% (3500 basis points). Customers in `TIER_5_DECLINED` never reach the minimum-down-payment check because the declined tier blocks the loan earlier. The minimum cents amount is the ceiling of the vehicle's `msrp_cents` multiplied by the tier fraction, and approval requires the supplied `down_payment_cents` to be at least that minimum.

The FICO tier also determines the loan's annual percentage rate at origination, expressed in basis points: `TIER_1` carries an APR of 450 basis points (4.50%), `TIER_2` carries 650 (6.50%), `TIER_3` carries 950 (9.50%), and `TIER_4` carries 1450 (14.50%). The chosen rate becomes both `base_apr_bps` (which is immutable after `APPROVED`) and the initial `apr_bps`; subsequent default-related uplifts modify `apr_bps` without changing `base_apr_bps`.

The standard amortization formula computes the loan's `monthly_payment_cents` from three inputs: the principal `P` (the contract's `principal_cents`), the monthly periodic rate `r` (the contract's `apr_bps` divided by 10000 to convert basis points to a decimal rate, then divided by 12 to convert annual to monthly), and the term `n` (the contract's `term_months`). When `r` is zero, the monthly payment is the ceiling of `P` divided by `n`. Otherwise, the monthly payment is the ceiling of `P` multiplied by `r` multiplied by one-plus-`r`-raised-to-the-`n`, divided by one-plus-`r`-raised-to-the-`n`-minus-one. The intermediate floating-point monthly payment is computed first without rounding any of `r` or `P` early, and only the final dollar amount is rounded up to integer cents.

After approval, the `LoanOfficer` activates the contract, transitioning it from `APPROVED` to `ACTIVE`. An activate attempt against any contract — loan or lease — that is not currently in `APPROVED` is rejected with `ERR_CONTRACT_NOT_ACTIVATABLE`. Activation is the step that materializes the payment schedule: the system generates `term_months` child `Payment` rows with `period_index` running from 1 to `term_months`, each row's `due_day_index` set to the loan's `origination_day_index` plus `period_index` multiplied by 30. Each row is created with `status` set to `SCHEDULED`, `amount_due_cents` snapshotted from the current `monthly_payment_cents`, `principal_portion_cents` and `interest_portion_cents` empty until the row is paid, `contract_type` set to `LOAN`, and `customer_id` denormalized from the parent for default-rollup purposes. Two `SCHEDULED`, `LATE`, or `DEFAULTED` payments on the same contract may never share a `due_day_index`; the generator enforces this on activation, and any manual payment-creation path is rejected with `ERR_PAYMENT_DUE_DATE_COLLISION` if it would collide.

### 3.4. Lease Origination, Approval, Activation, and the Term Window

A `LoanOfficer` originates a lease by supplying the `vehicle_id`, the customer's `down_payment_cents`, the `term_months`, and a `mileage_allowance` — the total contractual miles the lease is sold against, constrained to lie between 10000 and 75000 inclusive (so a typical 36-month lease at 12k miles per year is 36000). The `term_months` for a lease must be one of 24, 36, or 48 months. On creation, `capitalized_cost_cents` is computed as the vehicle's `msrp_cents` minus the `down_payment_cents`, and the contract enters `PENDING_APPROVAL` with `customer_id` from the URL.

Lease approval differs from loan approval in two important ways. First, leases are restricted to higher-quality credit tiers: only `TIER_1`, `TIER_2`, and `TIER_3` are eligible. A customer in `TIER_4` or `TIER_5_DECLINED` is rejected with `ERR_LEASE_TIER_INELIGIBLE`, even if the down payment exceeds the minimum. Second, the lease minimum down payment uses a different schedule than the loan: `TIER_1` requires 8% (800 basis points), `TIER_2` requires 12% (1200 basis points), and `TIER_3` requires 18% (1800 basis points). Insufficient down payment is rejected with `ERR_DOWN_PAYMENT_BELOW_MINIMUM`. As with loans, the parent customer must be `ACTIVE` (otherwise `ERR_CUSTOMER_NOT_ACTIVE`) and the vehicle must be `AVAILABLE` (otherwise `ERR_VEHICLE_NOT_AVAILABLE`).

Lease approval also enforces a temporal uniqueness rule: no two non-terminal `LeaseContract` rows owned by the same customer may have overlapping term windows. The window for a lease is the half-open interval from its `origination_day_index` to its `maturity_day_index`. Half-open semantics mean that exact adjacency — where one lease's `maturity_day_index` equals another's `origination_day_index` — is allowed, but a one-day overlap is not. A new lease whose term window collides with an existing non-terminal lease for the same customer is rejected with `ERR_LEASE_WINDOW_OVERLAP`.

When approval succeeds, the vehicle is transitioned from `AVAILABLE` to `LEASED`. The lease's `money_factor_micro` is set from the FICO-tier money-factor table — `TIER_1` carries 2000 (a money factor of 0.00200), `TIER_2` carries 2800 (0.00280), and `TIER_3` carries 4000 (0.00400); `TIER_4` and `TIER_5_DECLINED` never reach this assignment because they are blocked at the tier check. The `residual_value_cents` is computed as the floor of the vehicle's `msrp_cents` multiplied by the vehicle's `residual_factor_bps`, divided by 10000 — and once set on approval, `residual_value_cents` is immutable for the remainder of the lease's lifetime (with the sole exception of being decremented by a successful gap-rider claim, described in §3.7). The `payments_scheduled_count` is set equal to `term_months`, `origination_day_index` is set to the customer's current `clock_day_index`, and `maturity_day_index` is set to `origination_day_index` plus `term_months` multiplied by 30.

The lease monthly payment is built by per-component rounding rather than by computing a single floating total. Depreciation cents is the floor of the difference of `capitalized_cost_cents` minus `residual_value_cents`, divided by `term_months`. Finance cents is the floor of the sum of `capitalized_cost_cents` plus `residual_value_cents`, multiplied by `money_factor_micro`, divided by one million. Those two integer components are summed to produce a base cents. The tax cents is the ceiling of base cents multiplied by 800 — the local lease tax of 8%, expressed as basis points — divided by 10000. The final `monthly_payment_cents` is base cents plus tax cents. The order matters: depreciation and finance are independently floored before being summed, the tax ceiling is taken on the integer base, and the monthly payment is never computed as a single floating-point figure rounded once.

Activation of an `APPROVED` lease mirrors loan activation: the system generates `term_months` child `Payment` rows with `period_index` 1 through `term_months`, `due_day_index` set to `origination_day_index` plus `period_index` multiplied by 30, `amount_due_cents` snapshotted from `monthly_payment_cents`, `contract_type` set to `LEASE`, and the due-date uniqueness rule again enforced. For lease payments, the eventual amortization split is trivial — `principal_portion_cents` and `interest_portion_cents` are both 0 — because a lease is not a principal-amortizing instrument.

### 3.5. Payment Lifecycle, Delinquency, and Default Cascades

Every `Payment` row begins life with `status` set to `SCHEDULED`. The customer pays a scheduled payment to transition it to `PAID`; the precondition is that the payment is currently `SCHEDULED` and that the parent contract is `ACTIVE` or `DEFAULTED` — a payment against a contract that has not been activated, or against a `CHARGED_OFF` contract, is rejected with `ERR_PAYMENT_NOT_PAYABLE`. On the successful transition, `paid_day_index` is set to the customer's current `clock_day_index`, and for a `LOAN`-type payment the amortization step (described below) splits the `amount_due_cents` into `principal_portion_cents` and `interest_portion_cents`, decrements the loan's `remaining_principal_cents`, and increments `total_principal_paid_cents` and `total_interest_paid_cents`. The parent contract's `payments_made_count` is incremented in the same transaction. Two concurrent pay attempts on the same payment serialize on `Payment.status`: at most one of the transitions from `SCHEDULED`, `LATE`, or `DEFAULTED` to `PAID` succeeds, and the loser is rejected with `ERR_PAYMENT_NOT_PAYABLE`.

A `SCHEDULED` payment becomes `LATE` when the customer's clock advances past the payment's `due_day_index` while the payment is still unpaid. This transition is system-generated and happens during clock advancement, not in response to any direct caller action. While in `LATE`, the customer may still pay — transitioning `LATE` to `PAID` — provided that the gap between the customer's `clock_day_index` and the payment's `due_day_index` is still strictly less than the configured grace-days threshold for default; the amortization side effects are the same as for the scheduled-to-paid path. Once that gap reaches or exceeds the grace-days threshold, the next clock advance transitions the payment from `LATE` to `DEFAULTED`. A defaulted payment may still be paid — transitioning `DEFAULTED` to `PAID` — but the precondition is that the parent contract itself is in `DEFAULTED`; paying a defaulted payment against a `CHARGED_OFF` contract is rejected. Defaults are sticky for accounting per §2.10: paying a previously defaulted payment does not decrement the customer's `default_count`.

The `LATE`-to-`DEFAULTED` transition carries a cluster of side effects beyond the payment row itself. The customer's `default_count` is incremented by one, the customer's `default_rate` is recomputed via the aggregation rule (the count of payments currently in `DEFAULTED` divided by the maximum of one and the customer's `lifetime_payment_count`, expressed to six decimal places using round-half-up), and a `DelinquencyEvent` row is appended whose `customer_id` and `payment_id` identify the trigger, whose `default_count_after` records the customer's new lifetime tally, whose `apr_uplift_bps_applied` field records the basis points of uplift applied by this event (0 if no uplift fired), and whose `affected_contract_ids` array enumerates the `LoanContract.id` values that were re-priced. The `lifetime_payment_count` is the count of `Payment` rows owned by this customer whose status has ever been `PAID`, `LATE`, or `DEFAULTED` — the "state-ever-touched" set.

Two further cascades are conditional. **APR uplift on the parent customer's loans.** If this default causes the customer's `default_count` to reach or exceed the uplift threshold of 3 lifetime defaults for the first time, and the parent contract is a loan, then every `ACTIVE` `LoanContract` owned by this customer has its `apr_bps` raised by an APR uplift of 300 basis points (3.00%). For each such contract, `monthly_payment_cents` is then recomputed using the new `apr_bps` and the contract's current `remaining_principal_cents`, and every still-`SCHEDULED` `Payment` row on that contract has its `amount_due_cents` re-snapshotted to the new monthly payment. Already-`PAID` payments are not touched — the system uses the forward-looking re-pricing convention from §2.10, never the chronological back-fill. For lease contracts, the money factor is fixed at origination and is not re-priced on default; the `DelinquencyEvent` row for a lease default therefore records `apr_uplift_bps_applied = 0`. **Loan-status cascade**. If the count of `DEFAULTED` `Payment` rows on the parent contract reaches or exceeds 3, the parent contract itself auto-transitions from `ACTIVE` to `DEFAULTED`. This is the four-deep cascade from §2.7 — payment, customer, loan, payments-on-loan — and it executes in one logical transaction.

The amortization step that runs when a loan payment is marked `PAID` is straightforward. The monthly rate `r` is the contract's `apr_bps` divided by 10000 and then by 12. The interest portion of this payment is the floor of the contract's `remaining_principal_cents` multiplied by `r`, in integer cents. The principal portion is the payment's `amount_due_cents` minus that interest portion. If the resulting principal portion exceeds the contract's `remaining_principal_cents` — which happens only on the final payment — the principal portion is trimmed down to exactly `remaining_principal_cents`, so the final payment is "trued" rather than overshooting. The contract's `remaining_principal_cents` is then decremented by the principal portion, `total_principal_paid_cents` is incremented by it, and `total_interest_paid_cents` is incremented by the interest portion. For a lease payment, both portions are 0; the step is a no-op on the contract.

When the final scheduled payment of a loan reaches `PAID` and the contract's `remaining_principal_cents` reaches 0, the loan auto-transitions from `ACTIVE` to `PAID_OFF`. The customer-facing payoff balance returns 0 thereafter, and any linked `ACTIVE` `GapInsuranceRider` auto-transitions to `CANCELLED` because the claim window closes with the contract.

### 3.6. Collections: Reinstatement and Charge-Off

A `CollectionsAgent` works `DEFAULTED` loan contracts. There are two terminal-or-near-terminal paths. The first is reinstatement: a `DEFAULTED` loan may be returned to `ACTIVE` only after every one of its `DEFAULTED` child `Payment` rows has been paid (transitioned to `PAID`). If any `DEFAULTED` payment remains unpaid on the contract, reinstatement is rejected with `ERR_REINSTATE_HAS_OUTSTANDING_DEFAULTS`. When reinstatement succeeds, the loan returns to `ACTIVE`; the APR uplift applied during the original default cascade is retained — the `apr_bps` is not reset to `base_apr_bps`, consistent with the forward-looking convention.

The second path is charge-off, which is terminal. A `DEFAULTED` loan may be charged off, transitioning to `CHARGED_OFF`. On charge-off, any linked `ACTIVE` `GapInsuranceRider` is auto-transitioned to `CANCELLED`, and the contract's remaining `SCHEDULED` payments are effectively frozen — they remain in `SCHEDULED` for record-keeping, but no further amortization occurs because the contract is terminal. Any attempt to pay a payment against a `CHARGED_OFF` contract is rejected with `ERR_PAYMENT_NOT_PAYABLE`.

A loan that is neither `DEFAULTED` nor in any prior state expected by these endpoints — for example, a `PENDING_APPROVAL` loan submitted for reinstatement — is rejected with `ERR_LOAN_NOT_DEFAULTED`.

### 3.7. Gap Insurance Riders

A gap insurance rider is a financial side-rider that attaches to an `ACTIVE` loan or lease and pays out, on claim, an amount up to the contract's "gap" — that is, the loan's `remaining_principal_cents` or the lease's `residual_value_cents`. A `FinanceManager` or `Customer` creates a rider by posting the `contract_id` and `contract_type` (one of `LOAN` or `LEASE`) of the parent contract. The rider's `monthly_premium_cents` is computed as the ceiling of the contract's financed amount multiplied by the gap premium of 50 basis points (0.50% per month), divided by 10000 — where the financed amount is the loan's `principal_cents` for `LOAN`-type riders and the lease's `capitalized_cost_cents` for `LEASE`-type riders. The rider is created with `status` set to `ACTIVE`, and `attached_day_index` captures the customer's current `clock_day_index`. A rider's `contract_id` must reference a contract owned by the same `Customer` whose `id` appears in the URL; a cross-customer reference is rejected with `ERR_RIDER_CONTRACT_OWNERSHIP_MISMATCH`, even if the contract id is otherwise a valid id elsewhere in the system.

A rider may be cancelled by the customer at any time while it is `ACTIVE`, transitioning to `CANCELLED`. A rider also auto-cancels when its parent contract reaches `PAID_OFF` (loan), `CHARGED_OFF` (loan), or `CLOSED` (lease).

A claim is filed by a `FinanceManager` against an `ACTIVE` rider, supplying `payout_cents` as the amount of the claim. Three preconditions must hold: the rider must be `ACTIVE`, the parent contract must be in either `ACTIVE` or `DEFAULTED` (this is the cross-entity safety dependency), and the requested `payout_cents` must not exceed the contract's gap — `remaining_principal_cents` for a loan, `residual_value_cents` for a lease. A claim whose parent contract is `CLOSED`, `PAID_OFF`, or `CHARGED_OFF` is rejected with `ERR_GAP_RIDER_PARENT_TERMINAL` — the rider has auto-cancelled with the contract and cannot pay out posthumously. A claim whose `payout_cents` exceeds the relevant gap is rejected with `ERR_GAP_CLAIM_EXCEEDS_GAP`. A claim against a rider that is not `ACTIVE` is rejected with `ERR_GAP_RIDER_NOT_CLAIMABLE`.

When a claim succeeds, the rider transitions from `ACTIVE` to `CLAIMED`, and `claim_payout_cents` records the paid amount. For a loan, the contract's `remaining_principal_cents` is decremented by `payout_cents`; if this drives `remaining_principal_cents` to 0 the loan cascades to `PAID_OFF`. For a lease, the contract's `residual_value_cents` is decremented by `payout_cents`, which directly affects any subsequent purchase election. Two concurrent operations on the rider — a claim attempt and a parent-contract closure that triggers auto-cancellation — serialize on `GapInsuranceRider.status`: exactly one wins, and if the auto-cancel wins, the claim is rejected with `ERR_GAP_RIDER_NOT_CLAIMABLE`.

### 3.8. The Loan Payoff Quote — Two Variants on the Same Loan

A read-only quoting capability returns the payoff balance for a loan and exposes the system's pricing duality. The endpoint accepts a `variant` query parameter and returns the payoff in cents along with its components.

The book variant — `variant=BOOK` — returns the chronological book payoff: `payoff_cents` equals the contract's `remaining_principal_cents`. Nothing is accrued, no penalty is applied.

The cash variant — `variant=CASH` — returns the forward-looking cash payoff that a customer would actually pay to close the loan today. The accrued interest is the floor of `remaining_principal_cents` multiplied by the monthly rate (the contract's `apr_bps` divided by 10000 and then by 12), multiplied by the elapsed-days portion of a month — that is, the difference between the customer's `clock_day_index` and the day index of the last paid payment or origination, divided by 30. The prepayment penalty is the ceiling of `remaining_principal_cents` multiplied by 200 — the prepayment penalty of 2.00% expressed as basis points — divided by 10000. The cash `payoff_cents` is the sum of `remaining_principal_cents`, the accrued interest, and the prepayment penalty.

The two variants produce different cents on the same loan whenever `remaining_principal_cents` is greater than 0 and the clock has advanced past origination. Both variants are valid and both are exposed by the same endpoint; the caller selects which one is returned via the `variant` query value.

### 3.9. Lease Maturity, the End-of-Lease Election, and the Assessment

A lease that is `ACTIVE` matures automatically when two conditions are both true: the customer's `clock_day_index` has reached or exceeded the lease's `maturity_day_index`, and the lease's `payments_made_count` equals its `payments_scheduled_count`. When the lease auto-transitions from `ACTIVE` to `MATURED`, the system creates a `LeaseEndAssessment` row in `DRAFT` status as a side effect of the same transaction. The assessment's `odometer_reading` is left unset at draft creation; it is supplied later by a `FinanceManager` through the assessment-update path. A lease that defaults — when three or more of its child payments have reached `DEFAULTED` — transitions from `ACTIVE` to `DEFAULTED` instead of maturing, and a `DelinquencyEvent` is appended with `apr_uplift_bps_applied` set to 0 because the lease's money factor is fixed at origination. A linked rider on a defaulted lease remains `ACTIVE`; the gap may still claim on lease default.

Once the lease is `MATURED`, the `Customer` submits the lease-end election by posting `election` with one of three values — `PURCHASE`, `RENEW`, or `RETURN`. Any other value is rejected with `ERR_INVALID_LEASE_END_ELECTION`. Submitting an election against a lease that is not in `MATURED` (for example, an `ACTIVE` lease where the customer wants to buy out early — which is not the path for early buyout) is rejected with `ERR_LEASE_NOT_MATURED`. The election must be accompanied by a `LeaseEndAssessment` for this lease that is in `DRAFT` or `ISSUED` and that already has its `odometer_reading` set; if not, the election cannot be honored. On a successful `PURCHASE` election, the lease transitions from `MATURED` to `PURCHASED`, the `lease_end_election` field on the lease is set to `PURCHASE`, the assessment's `purchase_option_cents` is set to the lease's `residual_value_cents` plus the purchase option fee of 35000 cents ($350.00), its `disposition_fee_cents` is set to 0 (the disposition fee is waived on purchase), `total_due_cents` is recomputed, the assessment is moved to `ISSUED` if it was not already, and the vehicle's `status` is set to `SOLD`. On a successful `RENEW` election, the lease transitions to `RENEWED`, `lease_end_election` is set to `RENEW`, the assessment's `disposition_fee_cents` and `purchase_option_cents` are both set to 0, `total_due_cents` is recomputed, and the assessment is moved to `ISSUED` if it was not already; no new lease row is created automatically — renewal is recorded as an election, and the customer subsequently originates a new lease through the normal origination path. On a successful `RETURN` election, the lease transitions to `RETURNED`, `lease_end_election` is set to `RETURN`, the assessment's `disposition_fee_cents` is set to the disposition fee of 39500 cents ($395.00), `purchase_option_cents` is set to 0, `total_due_cents` is recomputed, the assessment is moved to `ISSUED` if it was not already, and the vehicle's `status` returns to `AVAILABLE`.

Two simultaneous lease-end elections on the same `MATURED` lease — for example, one caller submitting `PURCHASE` and another submitting `RETURN` — serialize on `LeaseContract.status`. Exactly one election succeeds; the loser sees the lease no longer in `MATURED` (it is in one of `PURCHASED`, `RENEWED`, or `RETURNED`) and is rejected with `ERR_LEASE_NOT_MATURED`.

The `LeaseEndAssessment` itself has its own lifecycle. Each assessment row carries a `lease_contract_id` that points back to the parent lease. A `FinanceManager` updates the draft assessment by submitting an `odometer_reading` (a non-negative integer; a negative or non-integer reading is rejected with `ERR_INVALID_ODOMETER_READING`). Setting the reading transitions the assessment from `DRAFT` to `ISSUED` and triggers three recomputations: `mileage_overage` becomes the larger of zero and the difference between `odometer_reading` and the lease's `mileage_allowance` (at exactly the allowance, overage is zero and the penalty is zero); `mileage_penalty_cents` becomes `mileage_overage` multiplied by the per-mile penalty of 25 cents ($0.25 per mile); and `total_due_cents` is recomputed via the aggregation rule below.

The `total_due_cents` aggregation is the unconditional sum of the three component fields on the same assessment row: `mileage_penalty_cents` plus `disposition_fee_cents` plus `purchase_option_cents`. The invariant is direct: `total_due_cents` always equals the sum of those three components after every state change on the assessment that mutates a component.

A `Customer` settles an `ISSUED` assessment to close out the lease. The precondition is that all child `Payment` rows on the parent `LeaseContract` are in status `PAID`; if any payment is still outstanding, the settle is rejected with `ERR_ASSESSMENT_NOT_ISSUED` (the precondition for settle requires not only the assessment to be `ISSUED` but the cross-entity payment-completeness precondition; a settle attempt against an assessment that is not `ISSUED` is also rejected with `ERR_ASSESSMENT_NOT_ISSUED`). On successful settle, the assessment transitions from `ISSUED` to `SETTLED`, `settled_day_index` captures the customer's current `clock_day_index`, and the parent `LeaseContract` auto-transitions to `CLOSED` as a cascade. The lease's linked `ACTIVE` gap rider also cascades to `CANCELLED` when the lease reaches `CLOSED`.

The customer may instead dispute an `ISSUED` assessment, transitioning it from `ISSUED` to `DISPUTED`; a dispute attempt against an assessment that is not `ISSUED` is rejected with `ERR_ASSESSMENT_NOT_ISSUED`. A disputed assessment is resolved by a `FinanceManager` who submits a `revised_odometer_reading`; the assessment transitions from `DISPUTED` to `RESOLVED`, the `odometer_reading` on the row is replaced, `mileage_penalty_cents` and `total_due_cents` are recomputed using the same rules as the first issuance, `settled_day_index` captures the current `clock_day_index`, and the parent `LeaseContract` again auto-transitions to `CLOSED`. A resolve attempt against an assessment that is not `DISPUTED` is rejected with `ERR_ASSESSMENT_NOT_DISPUTED`.

### 3.10. The Purchase Quote — Two Variants on the Same Lease

A read-only purchase-quoting capability returns what the customer would pay to take title of the vehicle, again with a `variant` query parameter selecting the answer.

The at-maturity variant — `variant=AT_MATURITY` — is the default behavior at `MATURED` and returns the lease's `residual_value_cents` plus the purchase option fee of 35000 cents as `purchase_option_cents`.

The early-buyout variant — `variant=EARLY_BUYOUT` — is allowed only while the lease is in `ACTIVE` and adds the value of the remaining payments to the at-maturity figure. The unpaid payments count is `payments_scheduled_count` minus `payments_made_count`; the remaining lease value is that count multiplied by the current `monthly_payment_cents`. The early-buyout `purchase_option_cents` is `residual_value_cents` plus the purchase option fee plus the remaining lease value.

The two variants produce different cents on the same lease whenever `payments_made_count` is less than `payments_scheduled_count`. Both are valid and both are exposed by the same quoting endpoint.

### 3.11. The Clock Advance Capability

A privileged test-driving capability advances a single customer's `clock_day_index` by an integer `days_advanced`. The supplied `days_advanced` value must be between 1 and 365 inclusive; an out-of-range value is rejected with `ERR_CLOCK_ADVANCE_OUT_OF_RANGE`. The advance performs three sweeps over the customer's payments and contracts within the same logical transaction. First, every `SCHEDULED` payment on any of the customer's contracts whose `due_day_index` is now strictly less than the customer's `clock_day_index` transitions to `LATE`. Second, every `LATE` payment whose elapsed delinquency (the customer's `clock_day_index` minus the payment's `due_day_index`) has reached or exceeded the configured grace-days threshold transitions to `DEFAULTED`, dragging with it the full cascade from §3.5 — `default_count` increment, `default_rate` recomputation, `DelinquencyEvent` append, conditional APR uplift on all of this customer's `ACTIVE` loans, and conditional contract-level `DEFAULTED` transition once a contract accrues three defaulted payments. Third, every `ACTIVE` `LeaseContract` that has reached its `maturity_day_index` and whose `payments_made_count` equals its `payments_scheduled_count` auto-transitions to `MATURED` (creating a `DRAFT` `LeaseEndAssessment`).

The advance returns the resulting `ClockEvent` row, whose `new_clock_day_index` reports the customer's clock after the advance, whose `payments_due_now` counts the payments whose `due_day_index` fell inside the closed interval from the previous index to the new index, and whose `payments_defaulted_now` counts the `LATE`-to-`DEFAULTED` transitions that this advance produced. Two concurrent clock-advance requests for the same customer serialize on the customer's `version` via OCC; the loser receives `ERR_VERSION_CONFLICT` and must retry with the fresh version.

### 3.12. Reading the Delinquency History

A read-only event-stream capability returns the customer's `DelinquencyEvent` rows in chronological order, paginated by `limit` and `offset`. The list is consumed by collections agents, finance managers, and platform administrators who need to reconstruct what happened on a given customer's loans — which payment defaulted, what the `default_count_after` was at that moment, whether an APR uplift fired (`apr_uplift_bps_applied`) and which contracts it touched (`affected_contract_ids`). The event stream is append-only: rows are never modified after creation, only added.
