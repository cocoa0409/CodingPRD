# Carbon Sequestration Project Permitting API — Product Requirements Document

## 1. Introduction

Permitting a geologic carbon storage project is a decade-long regulatory conversation in which almost nothing can be decided in isolation. A developer cannot know how much financial assurance the state will demand until the area of review is delineated; the area of review cannot be delineated until a plume migration simulation has been run; the simulation cannot be run until the injection rate has been capped by the confining zone's fracture margin; and the injection rate the developer actually receives depends on whether the seal integrity assessment passed under the parameter set the developer nominated. Meanwhile the same project is negotiating pore space with dozens of individual landowners, screening abandoned wellbores that may leak, designing a monitoring programme that spans subsurface, surface and atmospheric methods, and assembling a tax credit claim whose dollar value shifts the moment a reporting period is voided. Today this coordination lives in spreadsheets, e-mail threads and paper filings, and the resulting inconsistencies — a permit approved against a superseded geologic model, an injection authorization granted while a corrective-action obligation is still open, a credit claimed on tonnage that was later reversed — are exactly the failures a regulator cannot tolerate.

This document specifies the Carbon Sequestration Project Permitting API, a single system of record mounted under the `/ccs` path prefix that carries a storage project from an empty file through site characterization, injection well permitting, pore space acquisition, corrective action on legacy wellbores, monitoring plan approval, financial assurance, active injection, tax credit verification, post-injection site care and finally site closure certification. Its central design commitment is that every derived number — the seal integrity index, the area-of-review radius, each wellbore's leakage risk score, the monitoring coverage score, the required assurance amount, the ledger of net stored tonnes, the tiered credit rate — is computed by the server from a pinned evaluation order and re-derived whenever an upstream input moves. Clients never post a derived value; they post facts, and the server reconciles.

The second commitment is procedural rather than numerical. Regulatory decisions are gated by explicit, ordered preconditions, and where a decision would be tainted by a conflict of interest the system refuses it: the reviewer who opened technical review on a project's injection well may not later certify that project's closure, and the developer who submitted a credit claim may not be the party who verifies it. Where an emergency arises, the system freezes the project rather than allowing work to continue, and it draws real dollars out of the posted emergency reserve. The sections that follow define the global contract first, then the domain workflows in the order a project actually experiences them, then the endpoint surface and the error catalogue.

## 2. Global Specifications & System-Wide Principles

This section defines the system-wide contract: authentication, response shape, pagination, resource identity, precision, concurrency and the cross-cutting gates that apply irrespective of which workflow a request belongs to.

### 2.1. User and Role-Based Access Control

Every request to the API must carry two mandatory HTTP headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring the capacity in which that user acts. Five roles exist, and their spellings are exact: `ProgramAdmin`, `ProjectDeveloper`, `RegulatoryReviewer`, `IndependentVerifier`, and `Landowner`. If either header is absent, or if `X-User-Role` holds any value outside those five, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). If the headers are well formed but the declared role is not among the roles authorized for the requested operation, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

`ProgramAdmin` is the state program administrator: it alone opens project files and it alone controls the server's logical clock. `ProjectDeveloper` is the carbon capture and storage project developer, and it authors essentially every artefact the regulator later rules on — geologic models, plume simulations, legacy wellbore registrations, corrective-action schedules, pore space tracts and lease offers, unitization petitions, injection well permit applications, construction progress, mechanical integrity tests, monitoring plans and their methods, financial instruments and their allocations, injection period reports, and tax credit claims — as well as beginning post-injection site care. `RegulatoryReviewer` is the permitting authority: it rules on geologic models, injection well permits and monitoring plans, waives corrective action, rules on unitization petitions, authorizes injection, opens and resolves emergency remediation orders, and certifies site closure. `IndependentVerifier` is the third-party verifier of secure geologic storage reports and lifecycle-adjusted credit claims; its only mutating capability is ruling on a submitted claim. `Landowner` is the surface and pore-space owner negotiating a storage lease, and its only mutating capability is responding to an outstanding lease offer on its own tract.

All five roles use an opaque identity model. When `X-User-Role` is `ProgramAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server does not compare it to any entity's `id`. The same holds when `X-User-Role` is `ProjectDeveloper`: the identifier is opaque, though the server records it as `submitted_by_user_id` on a `TaxCreditClaim` at submission. When `X-User-Role` is `RegulatoryReviewer`, `X-User-ID` is likewise opaque and not tied to any persisted entity, but the server records it in several places where a scaffolded transition writes it — as `reviewer_user_id` on a geologic model that was ruled on, as `technical_reviewer_user_id` on a permit whose technical review was opened, as `approved_by_user_id` on an approved monitoring plan, as `waiver_reviewer_user_id` on a wellbore whose corrective action was waived, and as `closure_certified_by_user_id` on a project whose closure was certified. When `X-User-Role` is `IndependentVerifier`, `X-User-ID` is an opaque identifier recorded as `verifier_user_id` on the claim that was ruled on. When `X-User-Role` is `Landowner`, `X-User-ID` is an opaque identifier that is not the `id` of any persisted entity, but it is nevertheless compared: a tract stores the opaque identifier of the landowner entitled to negotiate it in its `landowner_user_id` field, and a landowner responding to an offer must present an `X-User-ID` equal to that stored value. A mismatch is rejected with `ERR_NOT_TRACT_LANDOWNER` (HTTP 403).

Two duties are mutually exclusive, and the system enforces the separation on identity rather than on role. Closure certification requires that the acting `X-User-ID` differ from the `technical_reviewer_user_id` of every one of the project's injection well permits — a reviewer who passed technical judgement on any well of the project is disqualified from certifying that project's closure. Claim verification requires that the acting `X-User-ID` differ from the claim's `submitted_by_user_id`. Either violation is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters, `limit` and `offset`. `limit` defaults to 10 when omitted, must be at least 1, and must not exceed 100. `offset` defaults to 0 and must be at least 0. A `limit` below 1 or above 100, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

List results are ordered by `created_at` ascending unless a specific workflow states a different ordering for a specific computation. The `meta` object of a list response carries four pagination fields — `limit` and `offset` echoing the effective values applied, `total_count` giving the number of rows matching the filter before pagination, and `has_more` indicating whether rows remain beyond the returned window.

### 2.4. Resource Identity, Timestamps and the Version Counter

Every persisted resource is addressed by an `id` that the server mints as a UUID. Identifiers carry no type prefix; a project id and a permit id are indistinguishable by shape, and clients must not attempt to infer a resource's type from its identifier. Clients never supply an `id` on creation.

Most resources also carry three common properties. `created_at` is an ISO 8601 UTC timestamp with three fractional digits, fixed at creation. `updated_at` is an ISO 8601 UTC timestamp with three fractional digits, refreshed on every mutation of that resource. `version` is an integer that starts at 1 on creation and increments by exactly 1 on every mutation of that resource — including mutations that arrive as a cascade from a sibling or parent operation rather than as a direct request against the resource. Where a workflow below says that an operation "bumps the project's version", that means the project's `version` increments by one and its `updated_at` is refreshed, even though the request was addressed at a child resource.

One entity is deliberately leaner. An injection period record carries only `id` and `created_at`; it has neither `updated_at` nor `version`, and neither field appears in its response payload. Voiding such a record therefore leaves no version trail on the record itself — the audit trail lives in the record's `status` and `voided_at` fields and in the project's own version counter, which does increment. Every other entity in the system — storage projects, geologic models, legacy wellbores, pore space tracts, injection well permits, monitoring plans, monitoring methods, financial instruments, tax credit claims and remediation orders — carries the full set of `id`, `created_at`, `updated_at` and `version`.

Time in this system is logical, not real. A single server-wide logical clock supplies every timestamp the server writes and every elapsed-time comparison it makes, and it can be moved by a `ProgramAdmin` supplying a `to_iso8601` instant; the response reports the resulting `current_utc`. At startup the logical clock reads exactly `2026-08-01T00:00:00Z`, and until it is explicitly moved it continues to read that instant — it never falls back to wall-clock time. Corrective-action window comparisons, post-injection elapsed-time computations, and every recorded `opened_at`, `resolved_at`, `activated_at`, `last_mit_at`, `voided_at`, `released_at`, `pisc_start_at` and `closure_certified_at` all read the logical clock.

### 2.5. Stale-Version Guards on Parent Records

Three write operations in this system can silently destroy work the client never observed, and each is therefore guarded by an optimistic-concurrency check against the parent record's `version`. In each case the version field is a required, non-optional part of the request body, and it carries the `version` value the client last read from the parent. Endpoints not named here take no version field at all.

Creating a geologic model must carry `expected_project_version` equal to the target storage project's current `version`. A newly created model legitimately supersedes the developer's prior characterization once it is accepted, so nothing in the create's own state preconditions would catch a writer working from a stale view of the project; the version check is the only thing that pins it. If `expected_project_version` does not equal the project's stored `version`, the create is rejected with `ERR_STALE_PROJECT_VERSION` (HTTP 412).

Sending a lease offer on a pore space tract must carry `expected_tract_version` equal to that tract's current `version`. A fresh offer legitimately replaces the outstanding offer under the negotiation cycle, so a developer holding a stale view of the tract would otherwise overwrite a landowner counter it never saw. If `expected_tract_version` does not equal the tract's stored `version`, the offer is rejected with `ERR_STALE_TRACT_VERSION` (HTTP 412).

Running the assurance waterfall on a financial instrument must carry `expected_instrument_version` equal to that instrument's current `version`. Allocation is idempotent by design and may legitimately be re-run after the assurance requirement changes, so nothing in the instrument's own state would reject a writer working from a stale picture of the buckets; the version check pins the requirement snapshot the allocation answers. If `expected_instrument_version` does not equal the instrument's stored `version`, the allocation is rejected with `ERR_STALE_INSTRUMENT_VERSION` (HTTP 412).

### 2.6. Validation Precedence

Multiple checks frequently apply to the same request, and the order in which they are evaluated determines which error the client sees. The system evaluates checks in a fixed precedence ladder, and the first failing check produces the response; later checks are not evaluated. Reading the ladder from highest precedence to lowest:

1. **Header authentication.** Presence of `X-User-ID` and `X-User-Role`, and membership of the role in the five declared roles — `ERR_UNAUTHENTICATED`.
2. **Role authorization.** The acting role appears in the requested operation's authorized-role list — `ERR_UNAUTHORIZED`.
3. **Tract ownership.** For a `Landowner` responding on a tract, `X-User-ID` equals the tract's `landowner_user_id` — `ERR_NOT_TRACT_LANDOWNER`.
4. **Segregation of duties.** On closure certification and on claim verification, the identity conflicts described in §2.1 — `ERR_SEGREGATION_OF_DUTIES`.
5. **Request shape.** Required body fields present, enum values inside their declared sets, numbers inside their declared ranges, timestamps parseable as ISO 8601, `limit` between 1 and 100, `offset` at least 0, and the conditional mechanical-integrity requirements (an `annulus_pressure_loss_psi` value is required when `test_type` is `ANNULUS_PRESSURE`, and an `anomaly_detected` value is required for the other two test types) — `ERR_INVALID_REQUEST`.
6. **Existence, left to right.** Path and body resources are resolved in a fixed order: the project first, then the geologic model, then the wellbore, the tract, the permit, the plan, the method, the instrument, the injection period, the claim, and finally the remediation order. A missing storage project yields `ERR_PROJECT_NOT_FOUND`; a missing geologic model yields `ERR_GEOLOGIC_MODEL_NOT_FOUND`; a missing legacy wellbore yields `ERR_WELLBORE_NOT_FOUND`; a missing pore space tract yields `ERR_TRACT_NOT_FOUND`; a missing injection well permit yields `ERR_PERMIT_NOT_FOUND`; a missing monitoring plan yields `ERR_MONITORING_PLAN_NOT_FOUND` (this also guards the plan reference carried in a claim-creation body); a missing monitoring method yields `ERR_MONITORING_METHOD_NOT_FOUND` on retirement; a missing financial instrument yields `ERR_INSTRUMENT_NOT_FOUND`; a missing injection period record yields `ERR_INJECTION_PERIOD_NOT_FOUND` on a void; a missing tax credit claim yields `ERR_CLAIM_NOT_FOUND`; and a missing remediation order yields `ERR_REMEDIATION_ORDER_NOT_FOUND` on a resolve.
7. **Foreign-key coherence.** When a permit application, a tax credit claim or a geologic model is created, the geologic model or monitoring plan it names must belong to the same project named in the body. A cross-project reference is reported as `ERR_PROJECT_NOT_FOUND` (HTTP 404), not as a validation error.
8. **Frozen posture.** Described in §2.9 — `ERR_PROJECT_POSTURE_FROZEN`.
9. **State admissibility.** Each entity's own current state must admit the requested transition, and each entity has its own error code: the project's `status` or `unitization_status` yields `ERR_INVALID_PROJECT_STATE`; a geologic model's `status` or `plume_status` yields `ERR_INVALID_MODEL_STATE`; a wellbore's `corrective_action_status` yields `ERR_INVALID_WELLBORE_CA_STATE`; a tract's `lease_status` yields `ERR_INVALID_TRACT_STATE`; a permit's `permit_status` yields `ERR_INVALID_PERMIT_STATE` (this also guards reporting an injection period against a permit); the construction sequence yields `ERR_INVALID_CONSTRUCTION_SEQUENCE`; an unproven mechanical integrity test yields `ERR_MIT_NOT_PASSED`; a monitoring plan's `status` or an already-closed review track yields `ERR_INVALID_PLAN_STATE` (this also guards adding or retiring a method); an instrument's `status` yields `ERR_INVALID_INSTRUMENT_STATE`; and a claim, injection period record or remediation order in the wrong `status` yields `ERR_INVALID_CLAIM_STATE`.
10. **Stale parent version.** The three optimistic-concurrency checks of §2.5, in the order project, tract, instrument — `ERR_STALE_PROJECT_VERSION`, `ERR_STALE_TRACT_VERSION`, `ERR_STALE_INSTRUMENT_VERSION`.
11. **Safety and referential business rules.** In this internal order: seal integrity (`ERR_SEAL_INTEGRITY_FAIL`), injection pressure (`ERR_INJECTION_PRESSURE_EXCEEDS_LIMIT`), construction standards (`ERR_CASING_PROGRAM_NONCOMPLIANT`), non-endangerment attestation (`ERR_NON_ENDANGERMENT_NOT_DEMONSTRATED`), monitoring plan approval status (`ERR_MRV_PLAN_NOT_APPROVED`), area-of-review delineation (`ERR_AOR_NOT_DELINEATED`), and open remediation orders (`ERR_OPEN_REMEDIATION_ORDER`).
12. **Temporal business rules.** Injection period overlap (`ERR_INJECTION_PERIOD_OVERLAP`), corrective-action rig capacity (`ERR_CA_RIG_CAPACITY_EXCEEDED`), and post-injection elapsed time (`ERR_PISC_DURATION_NOT_ELAPSED`), in that order.
13. **Remaining business constraints.** Corrective-action completeness (`ERR_CORRECTIVE_ACTION_INCOMPLETE`), waiver eligibility (`ERR_CA_WAIVER_NOT_ELIGIBLE`), monitoring domain coverage (`ERR_MRV_DOMAIN_COVERAGE_MISSING`), monitoring coverage minimum (`ERR_MRV_COVERAGE_BELOW_MINIMUM`), pore-space consent sufficiency (`ERR_PORE_SPACE_CONSENT_INSUFFICIENT`), unitization consent threshold (`ERR_UNITIZATION_CONSENT_BELOW_THRESHOLD`), duplicate tax year (`ERR_DUPLICATE_TAX_YEAR_CLAIM`), and duplicate well identifier (`ERR_DUPLICATE_API_NUMBER`), in that order.
14. **Fiscal rules, last.** Assurance coverage (`ERR_ASSURANCE_INSUFFICIENT`, HTTP 402) precedes the allocation-requirement check (`ERR_ALLOCATION_EXCEEDS_FACE_AMOUNT`).

The practical consequence of this ladder is worth stating plainly. A frozen project surfaces as `ERR_PROJECT_POSTURE_FROZEN` even when the target child is also in an inadmissible state, because the posture gate outranks every per-entity state check. A stale parent version surfaces only after every per-entity state check has passed, so a client that is both looking at stale data and requesting an inadmissible transition sees the state error, not the version error. And an underfunded project attempting injection authorization sees the assurance error only after its corrective-action and consent obligations have been found satisfied.

### 2.7. Numeric Precision and Rounding

Unless a specific rule says otherwise, every monetary amount is carried to 2 decimal places and every rounding operation in this system rounds half up. The rules that depart from the two-decimal default are these: both seal integrity indices carry 3 decimal places; every plume and pressure-front radius carries 3 decimal places; per-method monitoring scores and each of the three domain subscores carry 4 decimal places; tract net acreage, project secured acreage and project outstanding acreage carry 4 decimal places; every tonnage figure — per-period net storage, the project's cumulative ledger, and a claim's reported, verified and lifecycle-deducted tonnages — carries 3 decimal places; the post-injection elapsed-time figure carries 3 decimal places; and post-injection site care duration is a whole number of years. The maximum annual injection rate is floored to a whole number of tonnes rather than rounded, and the area-of-review radius is rounded *up* to the next tenth of a kilometre rather than rounded half up.

Where a total is assembled from parts, the order of rounding is pinned and is part of the contract. Two cases matter especially. The project's pore-space bonus total is the sum of the already-rounded per-tract settlements, not the rounding of an unrounded aggregate — the two orders differ in cents, and the former is correct. Likewise the required financial assurance amount is the sum of the five already-rounded cost buckets, each rounded to 2 decimal places before the addition.

### 2.8. Parallel State Dimensions and Cascade Propagation

Several entities in this system carry more than one independent state dimension on a single row, and the dimensions advance on separate operations without disturbing one another. A storage project carries `status` (the permitting lifecycle) alongside `operational_posture` (an emergency and funding gate) and `unitization_status` (the statutory petition track) and `closure_status` (the certification track). An injection well permit carries `permit_status` (the regulatory track) alongside `construction_status` (the physical track); activation is the single point at which both dimensions must agree. A geologic model carries `status` (the review lifecycle) alongside `plume_status` (the simulation and delineation track). Advancing one dimension never implicitly advances a sibling dimension unless a rule below says so explicitly.

Because so many project-level figures are derived, a single request routinely mutates several rows. Whenever the system recomputes a project-level derived field as a consequence of a child mutation, the project's `version` increments by one and its `updated_at` is refreshed; likewise for a child row that a parent operation sweeps. A request that both mutates a child and recomputes the project therefore produces two version bumps — one on each row. The recomputation chains themselves are described where the workflows that trigger them are described, but three of them recur often enough to name here: any change to the population of wellbores bearing a corrective-action obligation forces a recomputation of the project's corrective-action completion percentage and its required financial assurance; any change to the required financial assurance forces a re-comparison against the allocated amount and therefore a possible change of assurance coverage status; and any change of assurance coverage status while injection is authorized or active can move the project's operational posture.

### 2.9. The Operational Posture Gate

A project's `operational_posture` is one of `OPEN`, `RESTRICTED` or `FROZEN`, and it starts at `OPEN`. It is an independent dimension: it changes without changing the project's `status`, and it can change from any `status` value.

`FROZEN` is the emergency stop. While a project is `FROZEN`, every mutating operation on that project or on any of its children is refused with `ERR_PROJECT_POSTURE_FROZEN` (HTTP 409), with exactly two exceptions: opening a new remediation order is still permitted, and resolving an existing remediation order is still permitted — otherwise the project could never be un-frozen. Read operations are unaffected.

`RESTRICTED` is the funding warning. It is entered from `OPEN` whenever a recomputation of the required financial assurance leaves the project's assurance coverage status at `UNDERFUNDED` while the project's `status` is `INJECTION_AUTHORIZED` or `INJECTION_ACTIVE`; that transition bumps the project's `version`. It returns to `OPEN` on any subsequent recomputation that leaves assurance coverage status at `FUNDED` with no open remediation orders, again bumping `version`. `RESTRICTED` does not itself block child mutations; the fiscal gates that care about funding test the assurance coverage status directly.

### 2.10. Sub-Resource Listing and Filters

Child collections are discovered either through a project-scoped sub-resource listing or through a filtered top-level listing; child resources are never nested more deeply than one level in a path. A project's own sub-resource listings accept a filter on the child's state — `corrective_action_status` for legacy wellbores, `lease_status` for pore space tracts, and `status` for monitoring plans, financial instruments and remediation orders — alongside `limit` and `offset`.

The top-level listings accept the filters that matter for their entity. Storage projects may be filtered by `status`. Geologic models may be filtered by `project_id`, by `supersedes_model_id` (which retrieves the revisions that replaced a given predecessor), or by `status`. Injection well permits may be filtered by `project_id`, by `geologic_model_id`, or by `permit_status`. Tax credit claims may be filtered by `project_id`, by `monitoring_plan_id`, by `tax_year`, or by `status`. A permit's injection periods may be filtered by `status`, and a plan's monitoring methods by `domain` and by `status`. Every filter is optional, combinable, and applied before pagination so that `total_count` reflects the filtered population.

When a single storage project is read, the server recomputes its derived fields against the current logical clock before responding — in particular `pisc_elapsed_years`, which is a function of elapsed logical time and therefore changes without any write having occurred.

## 3. Business Logic & Workflows

### 3.1. Opening a Project File and Fixing Its Statutory Parameters

A `ProgramAdmin` opens the file. Creation captures the project `name` (non-empty, at most 200 characters), the `operator_name` of the legal operator of record (non-empty), the `basin_code` identifying the geologic basin (non-empty, at most 20 characters), the `total_project_acreage` of pore space inside the project boundary (strictly greater than zero), the developer's `requested_annual_injection_rate_tpy` in tonnes per year (strictly greater than zero), and the `annual_monitoring_cost_usd` that the financial-assurance calculation will use as its baseline (zero or greater). Two further parameters are optional and carry statutory defaults: `required_consent_pct`, the pore-space consent percentage a unitization ruling must meet, defaults to 60 and must be greater than 0 and at most 100; and `ca_rig_slots`, the number of workover rigs the project can run concurrently during overlapping corrective-action windows, defaults to 2 and must be at least 1.

A newly created project is initialised into a well-defined resting state: `status` is `DRAFT`, `operational_posture` is `OPEN`, `unitization_status` is `NOT_FILED`, and `closure_status` is `NOT_REQUESTED`. Its `governing_geologic_model_id` is null because no model has yet been accepted, its `aor_radius_km` is 0 because no area of review has been delineated, its `secured_acreage` is 0 and its `outstanding_acreage` therefore equals the whole `total_project_acreage`, its `pore_space_consent_pct` and `pore_space_bonus_total_usd` are 0, its `corrective_action_completion_pct` is 100 (an empty obligation set is vacuously complete), its `cumulative_stored_tonnes` and `pending_credit_usd` are 0, its `required_financial_assurance_usd` and `allocated_assurance_usd` are 0 with `assurance_coverage_status` at `UNFUNDED`, its `effective_annual_monitoring_cost_usd` equals the supplied `annual_monitoring_cost_usd`, its `pisc_duration_years` is 50, its `open_remediation_count` is 0, and `unitization_consent_pct_at_filing`, `statutory_bonus_per_acre_usd`, `alternative_timeframe_years`, `pisc_start_at`, `closure_certified_by_user_id` and `closure_certified_at` are all null with `non_endangerment_demonstrated` false and `pisc_elapsed_years` at 0.

The permitting lifecycle dimension runs `DRAFT → SITE_CHARACTERIZATION → PERMITTING → INJECTION_AUTHORIZED → INJECTION_ACTIVE → PISC → CLOSED`, with `CLOSED` terminal. Only two of those six advances are requested directly by a user; the other four are driven as side effects of decisions taken on child resources, and they are described where those decisions are described.

### 3.2. Site Characterization: Geologic Models, Seal Integrity and Plume Migration

Site characterization begins when a `ProjectDeveloper` registers a geologic model revision against a project, supplying the `project_id` and the `expected_project_version` guard described in §2.5, a developer-chosen `model_label` (non-empty), and — where this revision replaces an earlier one — the `supersedes_model_id` of its predecessor, which is null for a project's first model. The subsurface parameters are all strictly positive numbers: `injection_zone_top_depth_m` recording the depth to the top of the injection zone in metres, `injection_zone_thickness_m` recording its net thickness in metres, `seal_thickness_m` and `capillary_entry_pressure_psi` recording the best-estimate confining-zone thickness in metres and its capillary entry pressure in psi, `p10_seal_thickness_m` and `p10_capillary_entry_pressure_psi` recording the conservative tenth-percentile counterparts of those two, `reservoir_pressure_psi` recording initial reservoir pressure, `fracture_pressure_psi` recording the confining-zone fracture pressure (which must be strictly greater than `reservoir_pressure_psi`), `permeability_md` recording injection-zone permeability in millidarcy, and `porosity_fraction` recording injection-zone porosity as a fraction strictly between 0 and 1. An optional `assessment_variant` nominates which parameter set governs the model's classification and is one of `DETERMINISTIC` or `PROBABILISTIC_P10`, defaulting to `DETERMINISTIC`. A new model rests at `status` `DRAFT` with `plume_status` `NOT_RUN` and `revision_round_count` at 0; the create bumps the parent project's `version` by one.

Before a model can be reviewed, the developer must run the plume migration simulation, supplying `injection_years` — the injection duration in years, which must be at least 1 — in the request body. The simulation may only be requested while the model's own `status` is `DRAFT` or `REVISION_REQUESTED`. It records `injection_years` on the model and then performs a chain of computations whose evaluation order is pinned, each step consuming the stored output of the step before it rather than re-deriving it.

The first step is the rate cap. The allowable pressure buildup is nine tenths of the fracture margin: take the difference between `fracture_pressure_psi` and `reservoir_pressure_psi`, multiply it by 0.90, and round the result half up to 2 decimal places. The largest annual rate the confining zone tolerates, `max_injection_rate_tpy`, is that allowable buildup multiplied by `permeability_md`, multiplied by `porosity_fraction`, multiplied by 1000, divided by the injection buildup coefficient of 45.0, and then floored to a whole number of tonnes. The rate the project will actually be able to use, `effective_injection_rate_tpy`, is the smaller of the parent project's `requested_annual_injection_rate_tpy` and that `max_injection_rate_tpy` — a developer who asks for more than the rock allows receives the rock's answer, and a developer who asks for less receives what they asked for.

The second step is the seal integrity assessment, and it is computed twice — once under each parameter set — with only one of the two results governing the classification. The simulated pressure buildup common to both is the injection buildup coefficient of 45.0 multiplied by `effective_injection_rate_tpy`, divided by the product of `permeability_md`, `porosity_fraction` and 1000, rounded half up to 2 decimal places. Under the deterministic parameter set, the seal capacity is `capillary_entry_pressure_psi` multiplied by the ratio of `seal_thickness_m` to the reference seal thickness of 30.0 metres, and `seal_integrity_index` is that capacity divided by the simulated pressure buildup multiplied by the deterministic safety factor of 1.0, rounded half up to 3 decimal places. Under the probabilistic parameter set, the conservative seal capacity is `p10_capillary_entry_pressure_psi` multiplied by the ratio of `p10_seal_thickness_m` to the same reference thickness of 30.0 metres, and `seal_integrity_index_p10` is that conservative capacity divided by the simulated pressure buildup multiplied by the probabilistic safety factor of 1.25, rounded half up to 3 decimal places. Both indices are always computed and both are always stored and returned, whatever the model's `assessment_variant`.

`seal_classification` bands whichever index the `assessment_variant` nominates — `seal_integrity_index` when the variant is `DETERMINISTIC`, `seal_integrity_index_p10` when it is `PROBABILISTIC_P10` — and never a blend of the two. The governing index is banded as `PASS` when it is at least 1.500, `CONDITIONAL` when it is at least 1.000 but below 1.500, and `FAIL` when it is below 1.000. Because the probabilistic path applies a 25 percent conservatism penalty on top of using tenth-percentile inputs, the same row of subsurface parameters can classify `PASS` under one variant and `FAIL` under the other; nominating the variant is therefore a substantive engineering declaration, not a formatting preference.

The third step is the plume geometry. The total mass the well will place underground is `effective_injection_rate_tpy` multiplied by `injection_years`. Converting that mass to a pore volume in cubic metres means multiplying it by 1000.0 to reach kilograms and dividing by the supercritical carbon dioxide density of 700.0 kilograms per cubic metre. The swept area in square metres is that pore volume divided by the product of pi, `injection_zone_thickness_m`, `porosity_fraction` and the sweep efficiency of 0.35. `plume_radius_km` is the square root of that swept area, divided by 1000.0 to convert metres to kilometres, rounded half up to 3 decimal places. `pressure_front_radius_km` is `plume_radius_km` multiplied by the pressure-front multiplier of 1.8, rounded half up to 3 decimal places. The model's own `aor_radius_km` takes the larger of those two radii, multiplies it by 10.0, rounds that product *up* to the next whole number, and divides by 10.0 — in other words, the area-of-review radius is the greater of the free-phase plume and pressure-front radii, rounded up to the next tenth of a kilometre. Completing the simulation moves `plume_status` from `NOT_RUN` to `SIMULATED` and bumps the model's `version`.

### 3.3. Regulatory Review of a Model, Supersession, and Delineating the Area of Review

A developer submits a simulated model for regulatory review, optionally attaching a `submission_note`. Submission is admissible only from `status` `DRAFT` or `REVISION_REQUESTED`, requires the model's `plume_status` to already be `SIMULATED` or `AOR_FINALIZED`, and requires the parent project not to be `FROZEN`. Each submission increments `revision_round_count` by one and sets `status` to `SUBMITTED`, bumping the model's `version`. The very first submission for a project also drives the project's own `status` from `DRAFT` to `SITE_CHARACTERIZATION`, bumping the project's `version` — a project that is already past `DRAFT` is left where it is.

A `RegulatoryReviewer` then rules on the submission with a `decision` of `ACCEPT`, `REQUEST_REVISION` or `REJECT`, optionally attaching a `review_note`. Every ruling requires the model to be in `SUBMITTED` and records the reviewer's `X-User-ID` in the model's `reviewer_user_id`. A `REQUEST_REVISION` decision moves the model `SUBMITTED → REVISION_REQUESTED`, from which the developer may revise and resubmit; each resubmission again increments `revision_round_count`, so the counter is a durable record of how many rounds the review took. A `REJECT` decision moves the model `SUBMITTED → REJECTED`, which is terminal. An `ACCEPT` decision additionally requires that the model's `seal_classification` be `PASS` or `CONDITIONAL`; accepting a model classified `FAIL` is refused with `ERR_SEAL_INTEGRITY_FAIL` (HTTP 422).

Acceptance is the most consequential ruling in the characterization phase, and it cascades. The model moves `SUBMITTED → ACCEPTED`. If the project already had an accepted model, that predecessor moves `ACCEPTED → SUPERSEDED` in the same request and its own `version` is bumped — which is why at most one accepted model ever exists for a project, and why the project's `governing_geologic_model_id` is unambiguously the id of the model whose `status` is `ACCEPTED`, or null when no such model exists. The project's `governing_geologic_model_id` is set to the newly accepted model. The project's `status` advances `SITE_CHARACTERIZATION → PERMITTING`. And because the governing model has changed, the project's `required_financial_assurance_usd` and `assurance_coverage_status` are recomputed. Both the model's `version` and the project's `version` increment.

Delineating the area of review is a separate, deliberate act taken by the developer after acceptance: it is admissible only when the model's `status` is `ACCEPTED`, its `plume_status` is `SIMULATED`, and the project is not `FROZEN`. It takes no request body. Its effect is a four-link cascade that is the single largest recomputation in the system.

The first link copies the model's computed `aor_radius_km` onto the project's `aor_radius_km`, publishing the delineation. The second link re-screens legacy wellbores: because the project's area of review has changed, every legacy wellbore of the project whose `corrective_action_status` is `OUT_OF_AOR` and whose `distance_from_injector_km` is less than or equal to the project's new `aor_radius_km` moves `OUT_OF_AOR → IDENTIFIED`, and every wellbore now inside the area of review has its `risk_score` and `ca_cost_estimate_usd` recomputed against the new radius. Immediately afterwards, each wellbore that has just reached `IDENTIFIED` and either has `penetrates_seal` true or carries a `risk_score` of at least 40.00 auto-advances `IDENTIFIED → CA_REQUIRED` in the same request — a wellbore that penetrates the confining zone is always obligated regardless of its score, and a wellbore that does not penetrate the seal is obligated only once its score reaches the 40.00 threshold. The third link recomputes the project's `corrective_action_completion_pct` and `required_financial_assurance_usd`, because the population of obligated wellbores has changed. The fourth link re-compares the project's `allocated_assurance_usd` against the new requirement and resets `assurance_coverage_status` to `FUNDED` or `UNDERFUNDED` accordingly; when the outcome is `UNDERFUNDED` and the project's `status` is `INJECTION_AUTHORIZED` or `INJECTION_ACTIVE`, the project's `operational_posture` moves `OPEN → RESTRICTED`. Finally the model's `plume_status` moves `SIMULATED → AOR_FINALIZED`, and both the model's `version` and the project's `version` increment by one.

Until this delineation has happened for some accepted model, the project's `aor_radius_km` remains 0, and every operation that depends on a delineated area of review is refused with `ERR_AOR_NOT_DELINEATED` (HTTP 422). Two operations depend on it: submitting an injection well permit application, and authorizing injection for the project.

### 3.4. Legacy Wellbores: Screening, Risk Scoring and Corrective Action

Legacy wellbores are the pre-existing penetrations that could turn a competent seal into a leak path, and the developer registers each one with its `project_id`, its regulatory `api_number` (non-empty and unique among the wellbores of the same project), its `distance_from_injector_km` from the proposed injector (zero or greater), its `total_depth_m` in metres (strictly positive), a `penetrates_seal` boolean recording whether it crosses the confining zone, a `plug_condition` drawn from `CEMENTED`, `PARTIALLY_PLUGGED`, `OPEN_HOLE` or `UNKNOWN`, and a `plug_record_available` boolean recording whether the state archive holds a plugging record. Registering a second wellbore with an `api_number` already used inside the same project is refused with `ERR_DUPLICATE_API_NUMBER` (HTTP 409).

Registration scores the wellbore immediately, against whatever `aor_radius_km` the project currently holds. Four multiplicative factors combine. The seal factor is 1.0 when `penetrates_seal` is true and 0.85 when it is false. The plug factor is 1.00 for `OPEN_HOLE`, 0.70 for `PARTIALLY_PLUGGED`, 0.85 for `UNKNOWN` and 0.25 for `CEMENTED` — an uncemented open hole is the worst case and a properly cemented well the best. The record factor is 0.60 when `plug_record_available` is true and 1.00 when it is false, so an undocumented well is penalised. The proximity factor is 0.20 flat whenever the project's `aor_radius_km` is zero or below, because an undelineated area of review carries no meaningful proximity signal; otherwise it is one minus the ratio of `distance_from_injector_km` to the project's `aor_radius_km`, clamped so that it is never above 1.00 and never below 0.20. The `risk_score` is 100.0 multiplied by the seal factor, multiplied by the plug factor, multiplied by the record factor, multiplied by the quantity 0.40 plus 0.60 times the proximity factor, rounded half up to 2 decimal places — so 40 percent of the score is fixed by the wellbore's own condition and 60 percent is modulated by how close it sits to the injector. The `ca_cost_estimate_usd` is a base mobilisation cost of 150,000.00 dollars, plus 120.00 dollars for every metre of `total_depth_m`, plus 2,000.00 dollars for every point of `risk_score`, with the total rounded half up to 2 decimal places.

Registration also decides the wellbore's starting `corrective_action_status`. When the project's `aor_radius_km` is 0, or when the wellbore's `distance_from_injector_km` exceeds the project's `aor_radius_km`, the wellbore begins at `OUT_OF_AOR` and waits for a future delineation to pull it in. Otherwise it begins at `IDENTIFIED` and is immediately put through the same obligation screening described in §3.3, advancing to `CA_REQUIRED` when it penetrates the seal or when its `risk_score` is at least 40.00. Either way, registration recomputes the project's `corrective_action_completion_pct` and `required_financial_assurance_usd`.

The completion percentage is computed over a carefully bounded population. Wellbores whose `corrective_action_status` is `OUT_OF_AOR` are excluded entirely, from both numerator and denominator — they are outside the regulator's concern. Of the remaining in-area-of-review wellbores, those bearing `IDENTIFIED` are counted as in-scope for cost purposes but are not yet obligated; the obligated set is those whose status is `CA_REQUIRED`, `CA_SCHEDULED`, `CA_COMPLETE` or `CA_WAIVED`, and the closed set is the subset of those whose status is `CA_COMPLETE` or `CA_WAIVED`. When the obligated set is empty, `corrective_action_completion_pct` is exactly 100.00. Otherwise it is 100.0 multiplied by the count of closed wellbores divided by the count of obligated wellbores, rounded half up to 2 decimal places. Any operation requiring complete corrective action is refused with `ERR_CORRECTIVE_ACTION_INCOMPLETE` (HTTP 422) while this figure is below 100; the two operations that require it are authorizing injection for the project and approving an injection well permit.

Scheduling corrective action on an obligated wellbore is the developer's move, and the request supplies `window_start` and `window_end` for the work window. It is admissible only from `CA_REQUIRED`, requires the project not to be `FROZEN`, and requires `window_end` to be strictly later than `window_start`. It also competes for rigs. Consider the sibling wellbores of the same project whose `corrective_action_status` is already `CA_SCHEDULED` and whose closed window running from `ca_window_start` through `ca_window_end` intersects the requested closed window — a shared endpoint counts as an intersection, since one rig cannot be in two places on the same day. If the count of such siblings is not strictly fewer than the project's `ca_rig_slots`, the request is refused with `ERR_CA_RIG_CAPACITY_EXCEEDED` (HTTP 409). On success the supplied window is stored as `ca_window_start` and `ca_window_end`, `corrective_action_status` moves `CA_REQUIRED → CA_SCHEDULED`, and the wellbore's `version` increments.

Completing the work moves the wellbore `CA_SCHEDULED → CA_COMPLETE`, and may optionally carry a `completion_note`. The system will not accept a completion before the work could have begun: the logical clock must read at or after the wellbore's `ca_window_start`. Completion recomputes the project's `corrective_action_completion_pct`, then its `required_financial_assurance_usd` and `assurance_coverage_status`, and bumps both the wellbore's `version` and the project's `version`.

A `RegulatoryReviewer` may instead waive the obligation, supplying a `waiver_rationale`. A waiver is admissible only from `CA_REQUIRED` and only for a wellbore that does not threaten the confining zone: `penetrates_seal` must be false and `risk_score` must be at most 60.00. A waiver requested on a wellbore that penetrates the seal, or whose `risk_score` exceeds 60.00, is refused with `ERR_CA_WAIVER_NOT_ELIGIBLE` (HTTP 422). On success `corrective_action_status` moves `CA_REQUIRED → CA_WAIVED`, the reviewer's `X-User-ID` is recorded in `waiver_reviewer_user_id`, and — exactly as with a completion — the project's `corrective_action_completion_pct` is recomputed and then its `required_financial_assurance_usd` and `assurance_coverage_status`, with both the wellbore's `version` and the project's `version` incrementing. `CA_COMPLETE` and `CA_WAIVED` are both terminal; a wellbore never leaves either.

### 3.5. Pore Space Acquisition: Lease Negotiation, Unitization and Settlement

Pore space must be acquired tract by tract before injection can be authorized. The developer registers each tract with its `project_id`, a `tract_label` (non-empty and unique among the tracts of the same project), its gross `acreage` (strictly positive), the opaque `landowner_user_id` of the landowner entitled to negotiate it (non-empty), and an optional `ownership_pct` recording the undivided pore-space interest that landowner actually holds, which defaults to 100 and must be greater than 0 and at most 100. A new tract rests at `lease_status` `UNLEASED` with `negotiation_round_count`, `bonus_settlement_usd` and `net_acreage` all at 0.

Negotiation is cyclic. A developer sends an offer carrying the `expected_tract_version` guard of §2.5 together with a `bonus_per_acre_usd` and a `royalty_rate_pct`; these land on the tract as `current_offer_bonus_per_acre_usd` and `current_offer_royalty_rate_pct`. An offer is admissible from `lease_status` `UNLEASED` or `COUNTERED`, and requires the project not to be `FROZEN`. Sending an offer over an outstanding counter clears `counter_bonus_per_acre_usd` back to null, since the developer's new offer supersedes it. Every offer increments `negotiation_round_count` by one and sets `lease_status` to `OFFER_SENT`, bumping the tract's `version`. The cycle `OFFER_SENT → COUNTERED → OFFER_SENT` may repeat indefinitely until the landowner accepts or rejects.

The landowner responds to an outstanding offer with a `response` of `COUNTER`, `ACCEPT` or `REJECT`. All three require the tract to be at `OFFER_SENT` and require the acting `X-User-ID` to equal the tract's `landowner_user_id`. A `COUNTER` response must supply a `counter_bonus_per_acre_usd` strictly greater than the tract's `current_offer_bonus_per_acre_usd` — a counter that does not improve on the developer's own number is not a counter — and it stores that figure and moves the tract `OFFER_SENT → COUNTERED`. A `REJECT` response clears both `current_offer_bonus_per_acre_usd` and `current_offer_royalty_rate_pct` to null and moves the tract `OFFER_SENT → REJECTED`. An `ACCEPT` response must supply `lease_term_start` and `lease_term_end`, with `lease_term_end` strictly later than `lease_term_start`; the term is a half-open interval, inclusive of its start and exclusive of its end. Acceptance locks the terms: `executed_bonus_per_acre_usd` takes the value of `current_offer_bonus_per_acre_usd`, `executed_royalty_rate_pct` takes the value of `current_offer_royalty_rate_pct`, and the supplied term dates are stored. Whatever the response, the tract's `version` increments.

Acceptance also settles the money, and the rounding order here is part of the contract. Per tract, `net_acreage` is `acreage` multiplied by `ownership_pct` divided by 100.0, rounded half up to 4 decimal places, and `bonus_settlement_usd` is that `net_acreage` multiplied by `executed_bonus_per_acre_usd`, rounded half up to 2 decimal places. At project level the holders are the tracts whose `lease_status` is `EXECUTED` or `UNITIZED`, summed in `created_at` ascending order: `secured_acreage` is the sum of their `net_acreage` values rounded half up to 4 decimal places, `outstanding_acreage` is `total_project_acreage` less `secured_acreage` rounded half up to 4 decimal places, `pore_space_consent_pct` is 100.0 multiplied by `secured_acreage` divided by `total_project_acreage` rounded half up to 2 decimal places, and `pore_space_bonus_total_usd` is the sum of the holders' already-rounded `bonus_settlement_usd` values rounded half up to 2 decimal places. That last figure must be assembled from the rounded per-tract settlements and not from an unrounded aggregate. Every one of these four project figures is recomputed on acceptance, and both the tract's `version` and the project's `version` increment.

Terminating an executed lease is the developer's exit, and it supplies a `termination_reason`. It is admissible only from `lease_status` `EXECUTED`, and only while the project's `status` is `DRAFT`, `SITE_CHARACTERIZATION` or `PERMITTING` — once injection has been authorized, acreage cannot be handed back. Termination clears `executed_bonus_per_acre_usd`, `executed_royalty_rate_pct`, `lease_term_start` and `lease_term_end` to null, zeroes both `bonus_settlement_usd` and `net_acreage`, and moves the tract `EXECUTED → TERMINATED`, which is terminal. The same four project figures — `secured_acreage`, `outstanding_acreage`, `pore_space_consent_pct` and `pore_space_bonus_total_usd` — are recomputed, and both versions increment.

When voluntary negotiation stalls, the developer may petition for statutory unitization, optionally attaching a `petition_note`. A petition is admissible only when the project's `unitization_status` is `NOT_FILED` and the project's `status` is `SITE_CHARACTERIZATION` or `PERMITTING`. Filing snapshots the project's current `pore_space_consent_pct` into `unitization_consent_pct_at_filing` — a permanent record of the consent level at the moment the developer went to the regulator — and moves `unitization_status` `NOT_FILED → FILED`, bumping the project's `version`.

A `RegulatoryReviewer` then rules on the filed petition with a `decision` of `GRANT` or `DENY`. A `DENY` ruling moves `unitization_status` `FILED → DENIED`, changes no tract whatsoever, and bumps the project's `version`. A `GRANT` ruling is admissible only when the project's `pore_space_consent_pct` is at least its `required_consent_pct`; a grant requested below that threshold is refused with `ERR_UNITIZATION_CONSENT_BELOW_THRESHOLD` (HTTP 422). A granted ruling supplies `statutory_bonus_per_acre_usd`, which is stored on the project, together with a `statutory_royalty_rate_pct` carrying the royalty rate the ruling imposes. The grant then sweeps every tract of the project whose `lease_status` is `UNLEASED` or `REJECTED` — both populations, not merely the unleased ones — into `UNITIZED`, setting each swept tract's `executed_bonus_per_acre_usd` to the project's `statutory_bonus_per_acre_usd` and its `executed_royalty_rate_pct` to the ruling's royalty rate, recomputing each swept tract's `net_acreage` and `bonus_settlement_usd` by exactly the per-tract rules above, and bumping each swept tract's `version`. The project's `secured_acreage`, `outstanding_acreage`, `pore_space_consent_pct` and `pore_space_bonus_total_usd` are then recomputed over the enlarged holder set, `unitization_status` moves `FILED → GRANTED`, and the project's `version` increments. Tracts already at `OFFER_SENT`, `COUNTERED`, `EXECUTED` or `TERMINATED` are untouched by the sweep.

Injection authorization tests pore space acquisition through a single disjunction: either the project's `pore_space_consent_pct` is at least its `required_consent_pct`, or its `unitization_status` is `GRANTED`. If neither holds, authorization is refused with `ERR_PORE_SPACE_CONSENT_INSUFFICIENT` (HTTP 422).

### 3.6. Injection Well Permitting: Construction Standards, the Regulatory Track and Mechanical Integrity

A Class VI injection well application is drafted by the developer against an accepted geologic model. The body carries the `project_id`, the `geologic_model_id` of the model revision the application relies upon, a `well_name` (non-empty and unique among the permits of the same project), a `casing_program` drawn from `LONG_STRING_CEMENTED_TO_SURFACE`, `LINER` or `SINGLE_STRING`, a `corrosion_resistant_material` boolean declaring whether the tubing and long-string casing use carbon-dioxide-resistant material, the `requested_injection_pressure_psi` the developer wants as a maximum surface injection pressure (strictly positive), and an optional `tubing_packer_installed` boolean declaring whether injection is through tubing set on a packer, which defaults to false. The named model must belong to the same project as the named project; a cross-project reference is reported as `ERR_PROJECT_NOT_FOUND`.

Creation immediately derives the well's pressure ceiling: `max_injection_pressure_psi` is 90 percent of the referenced model's `fracture_pressure_psi`, rounded half up to 2 decimal places. The permit rests at `permit_status` `DRAFT` and `construction_status` `NOT_STARTED`, with `authorized_injection_rate_tpy` at 0, `revision_round_count` at 0, and `last_mit_type`, `last_mit_result`, `last_mit_at` and `activated_at` all null with `mit_pass_count` at 0. Because a drafted permit does not yet count toward the plugging bucket, creation nonetheless recomputes the project's `required_financial_assurance_usd`.

Submitting the application for review, optionally with a `submission_note`, is where the construction standards bite. Submission is admissible from `permit_status` `DRAFT` or `REVISION_REQUESTED`, and it enforces three construction requirements together: `casing_program` must be `LONG_STRING_CEMENTED_TO_SURFACE`, `corrosion_resistant_material` must be true, and `tubing_packer_installed` must be true. A `LINER` or `SINGLE_STRING` programme, or a missing corrosion-resistant completion, or injection that is not through tubing on a packer, is refused with `ERR_CASING_PROGRAM_NONCOMPLIANT` (HTTP 422). Submission further requires the project's `aor_radius_km` to be strictly greater than 0, and requires `requested_injection_pressure_psi` to be at most `max_injection_pressure_psi` — a request above the 90-percent-of-fracture ceiling is refused with `ERR_INJECTION_PRESSURE_EXCEEDS_LIMIT` (HTTP 422). On success `revision_round_count` increments by one, `permit_status` moves to `SUBMITTED`, and the permit's `version` increments.

The regulatory track is driven by a `RegulatoryReviewer` supplying a `decision` of `BEGIN_TECHNICAL_REVIEW`, `APPROVE`, `REQUEST_REVISION` or `DENY`, optionally with a `review_note`. Opening technical review is admissible only from `SUBMITTED`, and it re-checks the underlying geology: the referenced geologic model must have `status` `ACCEPTED`, and its `seal_classification` must not be `FAIL` — a model that has drifted to `FAIL` blocks the review with `ERR_SEAL_INTEGRITY_FAIL`. Opening review records the reviewer's `X-User-ID` in `technical_reviewer_user_id` — the field that later disqualifies that same identity from certifying the project's closure — and moves `permit_status` `SUBMITTED → TECHNICAL_REVIEW`.

From `TECHNICAL_REVIEW` the three remaining decisions branch with equal weight. `REQUEST_REVISION` moves `permit_status` `TECHNICAL_REVIEW → REVISION_REQUESTED`, from which a resubmission returns the permit to `SUBMITTED` and increments `revision_round_count` again; a resubmission from `REVISION_REQUESTED` carries no construction-standard or pressure re-check, since those were satisfied on the original submission. `APPROVE` is admissible from `TECHNICAL_REVIEW` and additionally requires the project's `corrective_action_completion_pct` to equal 100; approval moves `permit_status` `TECHNICAL_REVIEW → APPROVED`, recomputes the project's `required_financial_assurance_usd` and `assurance_coverage_status` because an approved permit now counts toward the plugging bucket, and increments both the permit's `version` and the project's `version`. `DENY` is admissible from `TECHNICAL_REVIEW` and moves `permit_status` `TECHNICAL_REVIEW → DENIED`, which is terminal; denial likewise recomputes the project's `required_financial_assurance_usd` and `assurance_coverage_status` — because a denied permit stops counting toward the plugging bucket, denial usually *reduces* the requirement — and increments both the permit's `version` and the project's `version`.

The construction dimension advances entirely independently, one step at a time, and the developer names the step it wants in `to_construction_status`. The sequence is `NOT_STARTED → DRILLING → CASING_SET → CEMENT_LOGGED → MIT_PENDING → COMPLETED`, and only the immediate successor of the permit's current `construction_status` is accepted; naming any other value, including a value further along the chain or a value already passed, is refused with `ERR_INVALID_CONSTRUCTION_SEQUENCE` (HTTP 409). The first step, into `DRILLING`, has two extra preconditions the later steps do not: the permit's `permit_status` must already be `APPROVED`, and the project must not be `FROZEN`. The last step, into `COMPLETED`, requires that the permit's `last_mit_result` be `PASS`; attempting it without a passing test is refused with `ERR_MIT_NOT_PASSED` (HTTP 409). The intermediate steps into `CASING_SET`, `CEMENT_LOGGED` and `MIT_PENDING` require only that the current `construction_status` be their immediate predecessor. Every accepted step bumps the permit's `version`.

Mechanical integrity is recorded as a separate developer action naming a `test_type` of `ANNULUS_PRESSURE`, `TEMPERATURE_LOG` or `CASING_INSPECTION_LOG`. An annulus pressure test must carry an `annulus_pressure_loss_psi` value and produces a `PASS` verdict when that loss is at most 3.00 psi and a `FAIL` verdict when it exceeds 3.00 psi — a loss of exactly 3.00 psi is a `PASS`, and the comparison is made on the submitted value at 2 decimal places. A temperature log or a casing inspection log must instead carry an `anomaly_detected` boolean, and produces a `FAIL` verdict when an anomaly was detected and a `PASS` verdict when none was. Recording a test writes `last_mit_type` from the submitted `test_type`, writes the verdict to `last_mit_result`, stamps `last_mit_at` with the logical clock, and increases `mit_pass_count` by one when and only when the verdict was `PASS`. Only the most recent test governs the gates that require demonstrated integrity: a well that passed once and then failed cannot be completed or activated, even though its `mit_pass_count` is non-zero.

Activation is the single point where the two dimensions must agree, and it is a `RegulatoryReviewer` action optionally carrying an `activation_note`. It requires the permit's `permit_status` to be `APPROVED`, its `construction_status` to already be `COMPLETED` (otherwise `ERR_INVALID_CONSTRUCTION_SEQUENCE`), its `last_mit_result` to be `PASS` (otherwise `ERR_MIT_NOT_PASSED`), the project's `status` to be `INJECTION_AUTHORIZED` or `INJECTION_ACTIVE`, the project's `operational_posture` not to be `FROZEN`, and the project's `assurance_coverage_status` to be `FUNDED` (otherwise `ERR_ASSURANCE_INSUFFICIENT`, HTTP 402). On success the permit's `authorized_injection_rate_tpy` is set to the governing model's `effective_injection_rate_tpy`, `activated_at` is stamped with the logical clock, `permit_status` moves `APPROVED → ACTIVE`, and the permit's `version` increments. The first activation for a project also drives the project's `status` from `INJECTION_AUTHORIZED` to `INJECTION_ACTIVE`, bumping the project's `version`; later activations on the same project find it already at `INJECTION_ACTIVE` and leave it alone.

A permit can lose its authorization without any request being addressed to it. Whenever the project's `operational_posture` becomes `FROZEN`, and whenever the developer begins post-injection site care, every permit of that project whose `permit_status` is `ACTIVE` is driven `ACTIVE → SUSPENDED` with `authorized_injection_rate_tpy` reset to 0 and its `version` bumped. Suspension in turn cascades onto the project's credit claims: because the permit has left `ACTIVE`, every tax credit claim of the project whose `status` is `SUBMITTED` reverts `SUBMITTED → DRAFT`, each such claim's `version` increments, and the project's `pending_credit_usd` is recomputed over the claims whose `status` is `SUBMITTED` or `ALLOWED`. The reverse path exists only for the remediation case: when resolving a remediation order clears the last open order and the project's `status` is `INJECTION_ACTIVE`, every permit of that project whose `permit_status` is `SUSPENDED` is restored `SUSPENDED → ACTIVE` with `authorized_injection_rate_tpy` set once again to the governing model's `effective_injection_rate_tpy`, and each such permit's `version` increments. Reverted claims are *not* automatically resubmitted; the developer must submit them again.

### 3.7. Monitoring, Reporting and Verification: Plan Design and the Two-Track Review

A monitoring, reporting and verification plan is created by the developer against a `project_id` with a `plan_label`, and it rests at `status` `DRAFT` with `technical_review_complete` and `public_comment_complete` both false, all three domain subscores at 0, `coverage_score` at 0, `condition_count` at 0, `approved_by_user_id` null and `revision_round_count` at 0. Methods are then added to it, and a method may only be added to — or retired from — a plan whose `status` is `DRAFT` or `REVISION_REQUESTED`; attempting either against a plan in any other status is refused with `ERR_INVALID_PLAN_STATE` (HTTP 409).

Each method declares its `monitoring_plan_id` implicitly through the plan it is added to, a `domain` of `SUBSURFACE`, `SURFACE` or `ATMOSPHERIC`, a non-empty `technique` naming the measurement approach (for instance time-lapse seismic, soil flux or eddy covariance), a strictly positive `detection_threshold_tpy` giving the smallest annual leakage rate the method can detect in tonnes per year, a `frequency_per_year` of at least 1 campaign, and a `spatial_coverage_pct` greater than 0 and at most 100 recording the percentage of the area of review the method covers. A new method rests at `status` `ACTIVE`.

Scoring a method combines three terms, each capped at 1.00 so that no single dimension can compensate for another. The coverage term is `spatial_coverage_pct` divided by 100.0, capped at 1.00. The frequency term is `frequency_per_year` divided by the reference campaign count for the method's own domain, capped at 1.00; the reference is 2 campaigns per year for `SUBSURFACE`, 4 for `SURFACE` and 12 for `ATMOSPHERIC`, reflecting how much more often a cheap surface or atmospheric measurement is expected to be repeated. The detection term is the reference detection threshold for the method's domain divided by the method's own `detection_threshold_tpy`, capped at 1.00; the reference is 1000.0 tonnes per year for `SUBSURFACE`, 100.0 for `SURFACE` and 25.0 for `ATMOSPHERIC`, so a method claiming better sensitivity than its domain reference earns the full term while a less sensitive method is scaled down proportionally. The `method_score` is the product of those three terms, rounded half up to 4 decimal places.

Each domain subscore is the sum of the `method_score` values of that domain's methods whose `status` is `ACTIVE`, capped at 1.0000 and rounded half up to 4 decimal places — so `subsurface_subscore`, `surface_subscore` and `atmospheric_subscore` each saturate, and piling a fourth seismic survey onto an already-saturated subsurface domain adds nothing. Methods whose `status` is `RETIRED` contribute exactly 0 to their domain. The plan's `coverage_score` is 100.0 multiplied by the weighted sum of the three subscores, where `subsurface_subscore` carries a weight of 0.50, `surface_subscore` a weight of 0.30 and `atmospheric_subscore` a weight of 0.20, rounded half up to 2 decimal places. Adding a method computes that method's `method_score`, recomputes all three subscores and the plan's `coverage_score`, and bumps the plan's `version`. Retiring a method requires a `retirement_reason`, sets the method's `status` to `RETIRED`, recomputes the same four figures, and bumps both the method's `version` and the plan's `version`.

Submitting a plan for review, optionally with a `submission_note`, is admissible from `status` `DRAFT` or `REVISION_REQUESTED` and requires the plan to hold at least one method whose `status` is `ACTIVE`. Submission resets both `technical_review_complete` and `public_comment_complete` to false, increments `revision_round_count` by one, recomputes all three subscores and the `coverage_score` from the current active methods, sets `status` to `SUBMITTED`, and bumps the plan's `version`.

Review is a fork-join, and this is the one place in the system where two independent regulatory tracks must both close before a ruling becomes possible. A `RegulatoryReviewer` closes the technical track with a `decision` of `COMPLETE_TECHNICAL_REVIEW`, which is admissible only while `status` is `SUBMITTED` and `technical_review_complete` is still false; it sets `technical_review_complete` to true and, when `public_comment_complete` is already true, auto-advances the plan `SUBMITTED → REVIEW_COMPLETE` in the same request. Symmetrically, the reviewer closes the public comment track with a `decision` of `COMPLETE_PUBLIC_COMMENT`, admissible only while `status` is `SUBMITTED` and `public_comment_complete` is still false; it sets `public_comment_complete` to true and sets `status` to `REVIEW_COMPLETE` only when `technical_review_complete` is already true, otherwise leaving `status` at `SUBMITTED`. Either track may be closed first, and closing whichever track comes second is what joins the fork. Attempting to close a track that is already closed is refused with `ERR_INVALID_PLAN_STATE`. Every track closure bumps the plan's `version`.

From `REVIEW_COMPLETE` the reviewer rules with a `decision` of `APPROVE`, `REQUEST_REVISION` or `REJECT`, optionally with a `review_note`. A `REQUEST_REVISION` ruling resets both `technical_review_complete` and `public_comment_complete` to false and moves the plan `REVIEW_COMPLETE → REVISION_REQUESTED`, from which the developer may add or retire methods and submit again — a full second pass through both review tracks. A `REJECT` ruling moves the plan `REVIEW_COMPLETE → REJECTED`, which is terminal. Both bump the plan's `version`.

An `APPROVE` ruling first enforces two quality gates in order. Every one of `subsurface_subscore`, `surface_subscore` and `atmospheric_subscore` must be strictly greater than 0 — a plan that monitors only the subsurface, however well, is refused with `ERR_MRV_DOMAIN_COVERAGE_MISSING` (HTTP 422). Then the plan's `coverage_score` must be at least 70.00; below that it is refused with `ERR_MRV_COVERAGE_BELOW_MINIMUM` (HTTP 422). Above that threshold the ruling branches on the score, and the two branches carry different side effects.

When `coverage_score` is at least 85.00, the plan moves `REVIEW_COMPLETE → APPROVED`. Its `condition_count` is set to 0 regardless of anything supplied in the body, the reviewer's `X-User-ID` is recorded in `approved_by_user_id`, and the project's `effective_annual_monitoring_cost_usd` is left equal to its `annual_monitoring_cost_usd` — an unconditioned approval carries no cost uplift. The project's `required_financial_assurance_usd` and `assurance_coverage_status` are recomputed, and both the plan's `version` and the project's `version` increment.

When `coverage_score` is at least 70.00 but below 85.00, the plan instead moves `REVIEW_COMPLETE → APPROVED_WITH_CONDITIONS`. Its `condition_count` is set to the `condition_count` supplied in the request body, the reviewer's `X-User-ID` is recorded in `approved_by_user_id`, and the project's `effective_annual_monitoring_cost_usd` is set to its `annual_monitoring_cost_usd` multiplied by 1.15 — a 15 percent uplift representing the extra surveillance the conditions impose — rounded half up to 2 decimal places. That uplifted figure feeds directly into the post-injection site care cost bucket, so a conditioned approval grows the project's `required_financial_assurance_usd`; the requirement and `assurance_coverage_status` are recomputed, and both the plan's `version` and the project's `version` increment. The uplift persists on the project for as long as any of its plans holds `status` `APPROVED_WITH_CONDITIONS`.

Two downstream gates read a plan's approval state. Authorizing injection requires that some monitoring plan of the project have `status` `APPROVED` or `APPROVED_WITH_CONDITIONS`, and submitting a tax credit claim requires that the specific plan the claim names have one of those two statuses; either failure is refused with `ERR_MRV_PLAN_NOT_APPROVED` (HTTP 422).

### 3.8. Financial Assurance: Sizing the Requirement, Filling the Buckets, Authorizing Injection and Emergency Draws

Financial assurance is the state's guarantee that the project can be made safe even if the operator walks away, and its size is derived rather than negotiated. Because the inputs form a chain that looks circular — the assurance depends on the area of review, which depends on the injection rate, which is capped by the geologic model — the evaluation order is pinned, and every step reads the *stored* output of the previous step rather than re-deriving it. The order is: first the governing model's `max_injection_rate_tpy`; then its `effective_injection_rate_tpy`, being the smaller of the project's `requested_annual_injection_rate_tpy` and that cap; then the project's `aor_radius_km`, as copied onto the project when the area of review was delineated; then the in-area-of-review wellbore screening together with each wellbore's `ca_cost_estimate_usd`; then the five cost buckets in the order written below; and finally the total and the coverage status.

The corrective-action bucket totals the `ca_cost_estimate_usd` of the project's wellbores whose `corrective_action_status` is `IDENTIFIED`, `CA_REQUIRED` or `CA_SCHEDULED` — work that is still outstanding — with the sum of those already-rounded per-wellbore figures rounded half up to 2 decimal places. Wellbores at `OUT_OF_AOR`, `CA_COMPLETE` or `CA_WAIVED` contribute nothing, which is why completing or waiving corrective action reduces the requirement. The post-injection site care bucket is the project's `pisc_duration_years` multiplied by its `effective_annual_monitoring_cost_usd`, rounded half up to 2 decimal places — fifty years of monitoring at the uplifted rate is by far the largest line item on most projects. The plugging bucket is 850,000.00 dollars for each injection well permit of the project whose `permit_status` is `SUBMITTED`, `TECHNICAL_REVIEW`, `REVISION_REQUESTED`, `APPROVED`, `ACTIVE` or `SUSPENDED`; permits still at `DRAFT` and permits that reached `DENIED` are not counted. The emergency reserve bucket is the larger of a two-million-dollar floor and the area-based figure obtained by multiplying 500,000.00 dollars per square kilometre by pi and by the square of the project's `aor_radius_km`, that area-based figure being rounded half up to 2 decimal places before the comparison. The administrative fee is tiered on the governing model's `effective_annual_injection_rate_tpy`: it is 250,000.00 dollars when that rate is at most 500,000 tonnes per year, 500,000.00 dollars when the rate exceeds 500,000 but is at most 1,500,000 tonnes per year, and 900,000.00 dollars when the rate exceeds 1,500,000 tonnes per year. The project's `required_financial_assurance_usd` is the sum of those five already-rounded buckets, itself rounded half up to 2 decimal places.

`assurance_coverage_status` is then derived by comparing `allocated_assurance_usd` against `required_financial_assurance_usd`, and the tests are applied in this order: the status is `UNFUNDED` when `allocated_assurance_usd` is zero or below; otherwise it is `FUNDED` when `allocated_assurance_usd` is at least `required_financial_assurance_usd`; otherwise it is `UNDERFUNDED`. A project with nothing allocated therefore reads `UNFUNDED` even when its requirement happens to be zero.

Instruments are posted before they are allocated. The developer posts one with the `project_id`, an `instrument_type` drawn from `TRUST_FUND`, `SURETY_BOND`, `LETTER_OF_CREDIT` or `INSURANCE`, and a strictly positive `face_amount_usd`. A posted instrument rests at `status` `POSTED` with all four allocated buckets — `allocated_ca_usd`, `allocated_plugging_usd`, `allocated_pisc_usd` and `allocated_emergency_usd` — at 0, `unallocated_usd` equal to the full `face_amount_usd`, `drawn_usd` at 0 and `released_at` null.

Allocation runs a waterfall, and the order in which the buckets are filled is fixed. Allocation carries the `expected_instrument_version` guard of §2.5, is admissible from `status` `POSTED` or `ALLOCATED` (so it may legitimately be re-run after the requirement moves), and requires the project's `required_financial_assurance_usd` to be strictly greater than 0; running it against a zero requirement, where no bucket requirement exists to fill, is refused with `ERR_ALLOCATION_EXCEEDS_FACE_AMOUNT` (HTTP 422). Four requirement figures are taken from the current computation: the corrective-action requirement is the corrective-action bucket, the plugging requirement is the plugging bucket, the post-injection requirement is the post-injection site care bucket, and the emergency requirement is the emergency reserve bucket plus the administrative fee combined into one figure. Starting with the whole `face_amount_usd` as the remaining balance, the buckets are filled in the order corrective action, plugging, post-injection site care, emergency: each bucket receives the smaller of the remaining balance and its own requirement, rounded half up to 2 decimal places, and the remaining balance is then reduced by the amount just assigned, again rounded half up to 2 decimal places. Those four amounts land in `allocated_ca_usd`, `allocated_plugging_usd`, `allocated_pisc_usd` and `allocated_emergency_usd` respectively, and whatever remains becomes `unallocated_usd`, rounded half up to 2 decimal places. The waterfall never assigns more than the face amount in aggregate, so an instrument too small to cover the whole requirement fills the earlier buckets completely and leaves the later ones short. Dollars are conserved at all times: the four allocated buckets plus `unallocated_usd` plus `drawn_usd` always add back to `face_amount_usd`, and that invariant holds after every allocation, deallocation and emergency draw. Allocation sets the instrument's `status` to `ALLOCATED`, recomputes the project's `allocated_assurance_usd` as the sum, over the project's instruments whose `status` is `ALLOCATED`, of their four allocated buckets (rounded half up to 2 decimal places), resets `assurance_coverage_status`, and bumps both the instrument's `version` and the project's `version`.

Deallocation reverses it. It requires a `deallocation_reason`, is admissible only from `status` `ALLOCATED`, and is only permitted while the project's `status` is `DRAFT`, `SITE_CHARACTERIZATION` or `PERMITTING` — assurance cannot be pulled back once injection has been authorized. It zeroes the four allocated buckets, restores `unallocated_usd` to the full `face_amount_usd`, sets `status` back to `POSTED`, recomputes the project's `allocated_assurance_usd` and `assurance_coverage_status`, and bumps both versions.

With characterization, permitting, corrective action, pore space and assurance all in place, a `RegulatoryReviewer` authorizes injection for the project, optionally attaching an `authorization_note`. This is the system's gate of record, and it enforces nine preconditions. The project's `status` must be `PERMITTING`, otherwise `ERR_INVALID_PROJECT_STATE`. Its `operational_posture` must be `OPEN`. Its `governing_geologic_model_id` must be non-null and that model's `seal_classification` must be `PASS` or `CONDITIONAL`, otherwise `ERR_SEAL_INTEGRITY_FAIL`. Its `aor_radius_km` must be strictly greater than 0, otherwise `ERR_AOR_NOT_DELINEATED`. At least one injection well permit of the project must have `permit_status` `APPROVED`. Some monitoring plan of the project must have `status` `APPROVED` or `APPROVED_WITH_CONDITIONS`, otherwise `ERR_MRV_PLAN_NOT_APPROVED`. Its `corrective_action_completion_pct` must equal 100, otherwise `ERR_CORRECTIVE_ACTION_INCOMPLETE`. Either its `pore_space_consent_pct` must be at least its `required_consent_pct` or its `unitization_status` must be `GRANTED`, otherwise `ERR_PORE_SPACE_CONSENT_INSUFFICIENT`. And its `assurance_coverage_status` must be `FUNDED`, otherwise `ERR_ASSURANCE_INSUFFICIENT`. On success the project's `status` moves `PERMITTING → INJECTION_AUTHORIZED` and its `version` increments. When several of these preconditions fail together, the precedence ladder of §2.6 decides which error the developer sees: `ERR_SEAL_INTEGRITY_FAIL` outranks `ERR_AOR_NOT_DELINEATED`, which outranks `ERR_MRV_PLAN_NOT_APPROVED`, which outranks `ERR_CORRECTIVE_ACTION_INCOMPLETE`, which outranks `ERR_PORE_SPACE_CONSENT_INSUFFICIENT`, which outranks `ERR_ASSURANCE_INSUFFICIENT`.

Emergencies are opened by a `RegulatoryReviewer` as a remediation order carrying the `project_id`, a `trigger_type` drawn from `SEAL_BREACH_INDICATION`, `WELL_INTEGRITY_LOSS`, `PLUME_EXCURSION` or `GROUNDWATER_IMPACT`, a `severity` of `MINOR`, `MAJOR` or `CRITICAL`, and a non-empty `narrative` describing the event. An order may only be opened while the project's `status` is `INJECTION_AUTHORIZED`, `INJECTION_ACTIVE` or `PISC`. Opening stamps `opened_at` with the logical clock, sets the order's `status` to `OPEN`, and computes its `reserve_draw_usd`.

The draw is zero — exactly 0.00 — for `MINOR` and `MAJOR` severity. For `CRITICAL` severity it is the smaller of the chosen instrument's `allocated_emergency_usd` and one quarter of the project's `required_financial_assurance_usd`, rounded half up to 2 decimal places. The instrument chosen is the project's instrument whose `status` is `ALLOCATED`; where several qualify, the one with the largest `allocated_emergency_usd` is chosen, breaking ties by `created_at` ascending; where none qualifies, the draw is 0.00 and no instrument changes state at all. When a draw does occur, that instrument's `drawn_usd` is set to the order's `reserve_draw_usd`, its `allocated_emergency_usd` is reduced by the drawn amount, its `status` moves `ALLOCATED → DRAWN`, the project's `allocated_assurance_usd` and `assurance_coverage_status` are recomputed, and both the instrument's `version` and the project's `version` increment.

Opening an order also cascades along the posture chain. The project's `open_remediation_count` increments by one. When the `severity` is `MAJOR` or `CRITICAL`, the project's `operational_posture` is set to `FROZEN` — which then drives every `ACTIVE` permit of the project to `SUSPENDED` with its `authorized_injection_rate_tpy` zeroed, which in turn reverts every `SUBMITTED` claim of the project to `DRAFT`, which in turn forces a recomputation of the project's `pending_credit_usd`. A `MINOR` order increments the count and is recorded, but does not freeze the project. The project's `version` increments.

Resolving an order requires a non-empty `remediation_summary` and is admissible only from the order's `status` `OPEN`; a resolve attempted against an already-resolved order is refused with `ERR_INVALID_CLAIM_STATE`. Resolution sets the order's `status` to `RESOLVED`, stamps `resolved_at` with the logical clock, and decrements the project's `open_remediation_count` by one. When that decrement brings `open_remediation_count` to 0, the posture is restored — to `OPEN` when the project's `assurance_coverage_status` is `FUNDED`, and to `RESTRICTED` when it is not — and every permit of the project whose `permit_status` is `SUSPENDED` is restored to `ACTIVE` with its `authorized_injection_rate_tpy` set to the governing model's `effective_injection_rate_tpy`. While any order remains open, neither the posture nor the suspended permits are touched. Both the order's `version` and the project's `version` increment. Resolving a remediation order is one of only two mutating operations permitted on a `FROZEN` project.

### 3.9. Injection Reporting, Tax Credits, Post-Injection Site Care and Site Closure

Once a well is `ACTIVE`, the developer reports what it injected; a report against a well whose `permit_status` is anything other than `ACTIVE` is refused with `ERR_INVALID_PERMIT_STATE`. Each reporting period is bound to the well it covers, and the server records that binding as the record's own `permit_id`; the developer identifies the well through the path rather than in the body. Each reporting period carries a `period_start` and a `period_end`, a `mass_injected_tonnes` figure of zero or greater, and an optional `measured_leakage_tonnes` figure which defaults to 0 and must be zero or greater and at most the period's own `mass_injected_tonnes`. `period_end` must be strictly later than `period_start`, and the interval is half-open — inclusive of `period_start`, exclusive of `period_end`. Two periods of the same well may not overlap: a requested half-open interval that overlaps any existing period of that permit whose `status` is `ACCEPTED` is refused with `ERR_INJECTION_PERIOD_OVERLAP` (HTTP 409), while two periods that merely touch at an endpoint — one ending exactly where the next begins — do not overlap and are both accepted. Each record's `net_stored_tonnes` is its `mass_injected_tonnes` less its `measured_leakage_tonnes`, rounded half up to 3 decimal places, and the record rests at `status` `ACCEPTED` with `voided_at` null. Reporting a period recomputes the project's `cumulative_stored_tonnes` and bumps the project's `version`; because an injection period record carries no `version` of its own, the project's counter is the only version trail the report leaves.

The secure-storage ledger is the project's `cumulative_stored_tonnes`: the sum of `net_stored_tonnes` over every injection period record belonging to any permit of that project whose `status` is `ACCEPTED`, processed in `period_start` ascending order with ties broken by `created_at` ascending, and rounded half up to 3 decimal places. Records whose `status` is `VOIDED` are excluded entirely. A zero-mass period contributes exactly 0.000. Tonnes are conserved: after a record is created and then voided, the project's `cumulative_stored_tonnes` equals the sum over the remaining accepted records exactly.

Voiding a record is the developer's correction mechanism and requires a `void_reason`. It is admissible only from the record's `status` `ACCEPTED`, and it is blocked while any tax credit claim of the project covering that record's tax year has `status` `ALLOWED` — an allowed credit cannot have its tonnage retroactively withdrawn. Voiding sets the record's `status` to `VOIDED`, stamps `voided_at` with the logical clock, recomputes the project's `cumulative_stored_tonnes` over the remaining accepted records, then recomputes `reported_tonnes`, `verified_tonnes`, `credit_rate_usd_per_tonne` and `credit_amount_usd` on every tax credit claim of the project whose `status` is `DRAFT` or `SUBMITTED` and whose `tax_year` covers the voided period, then recomputes the project's `pending_credit_usd`, and bumps the project's `version`.

A tax credit claim is opened by the developer against a `project_id` and the `monitoring_plan_id` of the plan whose approval underwrites the secure-storage report, for a `tax_year` between 2020 and 2100 inclusive that no other claim of the same project already uses — a duplicate is refused with `ERR_DUPLICATE_TAX_YEAR_CLAIM` (HTTP 409). An optional `claim_variant` names the tonnage basis and is one of `REPORTED` or `VERIFIED`, defaulting to `REPORTED`. An optional `lca_upstream_emissions_factor` records the lifecycle-analysis upstream emissions in tonnes of carbon dioxide equivalent per tonne reported; it defaults to 0 and must be at least 0 and at most 0.5. The named plan must belong to the named project. Creation computes the claim's tonnages, rate and credit amount against the current ledger and rests the claim at `status` `DRAFT`.

The tonnage window for a claim is the set of injection period records belonging to the project's permits whose `status` is `ACCEPTED` and which fall entirely inside the tax year — that is, whose `period_start` is at or after midnight UTC on the first of January of the `tax_year` and whose `period_end` is at or before midnight UTC on the first of January of the following year. A period straddling a year boundary belongs to neither year. `reported_tonnes` is the sum of `mass_injected_tonnes` over that window, rounded half up to 3 decimal places. The leakage total is the sum of `measured_leakage_tonnes` over the same window, rounded half up to 3 decimal places. The lifecycle deduction is `reported_tonnes` multiplied by the claim's `lca_upstream_emissions_factor`, rounded half up to 3 decimal places. `verified_tonnes` is `reported_tonnes` less the leakage total less the lifecycle deduction, rounded half up to 3 decimal places.

The rate is tiered on the project's ledger rather than on the claim's own tonnage, and it degrades as the project stores more: `credit_rate_usd_per_tonne` is 85.00 dollars per tonne while the project's `cumulative_stored_tonnes` is at most 500,000 tonnes, 70.00 dollars per tonne while it exceeds 500,000 but is at most 2,000,000 tonnes, and 55.00 dollars per tonne once it exceeds 2,000,000 tonnes. The rate is selected using the project's `cumulative_stored_tonnes` as it stands at the moment of the transition that triggers the calculation. `credit_amount_usd` is the basis multiplied by `credit_rate_usd_per_tonne`, rounded half up to 2 decimal places, where the basis is `reported_tonnes` when the claim's `claim_variant` is `REPORTED` and `verified_tonnes` when it is `VERIFIED`. The `REPORTED` basis is the gross figure — no leakage subtraction and no lifecycle deduction — and it is the basis in force while the claim's `status` is `DRAFT` or `SUBMITTED`. The `VERIFIED` basis nets out both the measured leakage and the lifecycle deduction, so whenever either the leakage total or the `lca_upstream_emissions_factor` is non-zero the allowed credit is strictly smaller than the credit as submitted.

Submitting a claim, optionally with a `submission_note`, is admissible only from `status` `DRAFT`, requires the referenced monitoring plan to have `status` `APPROVED` or `APPROVED_WITH_CONDITIONS`, requires the claim's `reported_tonnes` to be strictly greater than 0, and requires the project not to be `FROZEN`. Submission recomputes all four derived claim figures on the current ledger, records the developer's `X-User-ID` in `submitted_by_user_id`, moves the claim `DRAFT → SUBMITTED`, recomputes the project's `pending_credit_usd` as the sum of `credit_amount_usd` over the project's claims whose `status` is `SUBMITTED` or `ALLOWED`, and bumps both the claim's `version` and the project's `version`.

An `IndependentVerifier` then rules on a submitted claim with a `decision` of `ALLOW` or `DISALLOW`, optionally attaching a `verification_note`. Both rulings require the claim's `status` to be `SUBMITTED` and require the acting `X-User-ID` to differ from the claim's `submitted_by_user_id`. An `ALLOW` ruling additionally requires the claim's `verified_tonnes` to be strictly greater than 0 — a claim whose leakage and lifecycle deductions consume the whole reported tonnage cannot be allowed. Allowing sets the claim's `claim_variant` to `VERIFIED`, recomputes `credit_amount_usd` on the verified tonnage basis, records the verifier's `X-User-ID` in `verifier_user_id`, and moves the claim `SUBMITTED → ALLOWED`. A `DISALLOW` ruling records `verifier_user_id` and moves the claim `SUBMITTED → DISALLOWED`. Both are terminal, both recompute the project's `pending_credit_usd`, and both bump the claim's `version` and the project's `version`.

Closing out injection is the developer's decision and it may optionally supply an `alternative_timeframe_years` figure requesting a shortened post-injection site care period. Beginning post-injection site care requires the project's `status` to be `INJECTION_ACTIVE`, requires its `operational_posture` not to be `FROZEN`, requires that no remediation order of the project have `status` `OPEN` (otherwise `ERR_OPEN_REMEDIATION_ORDER`, HTTP 409), and requires that no permit of the project sit at `permit_status` `ACTIVE` with a `construction_status` other than `COMPLETED`. It stamps `pisc_start_at` with the logical clock, records the supplied `alternative_timeframe_years` on the project when one was supplied, recomputes `pisc_duration_years`, moves the project's `status` `INJECTION_ACTIVE → PISC`, drives every permit of the project whose `permit_status` is `ACTIVE` to `SUSPENDED` with `authorized_injection_rate_tpy` zeroed (which reverts that project's `SUBMITTED` claims to `DRAFT` and recomputes `pending_credit_usd`), recomputes `required_financial_assurance_usd` and `assurance_coverage_status`, and bumps the project's `version`.

The duration itself is a threshold decision. The alternative timeframe is available only when all three of the following hold: an `alternative_timeframe_years` value was supplied and is therefore not null, the governing geologic model's `seal_classification` is `PASS` (a `CONDITIONAL` seal does not qualify), and the best plan coverage score is at least 85.00. The best plan coverage score is the `coverage_score` of the project's monitoring plan whose `status` is `APPROVED` or `APPROVED_WITH_CONDITIONS`; where several such plans exist, the one with the highest `coverage_score` is used, breaking ties by `created_at` ascending; where none exists, the best plan coverage score is 0. When the alternative is not available, `pisc_duration_years` is the statutory default of 50 years. When it is available, `pisc_duration_years` is the requested `alternative_timeframe_years` clamped into the range from a floor of 10 years to a ceiling of 50 years — a request below 10 years yields 10, a request above 50 yields 50, and a request inside the range is honoured exactly.

Elapsed time is measured against the logical clock. `pisc_elapsed_years` is the number of days between `pisc_start_at` and the current logical clock instant, divided by 365.25, rounded half up to 3 decimal places, and it is recomputed on every read of the project rather than being written by any mutation.

Certifying closure is the final act, and it is a `RegulatoryReviewer` decision carrying a `non_endangerment_demonstrated` boolean and an optional `closure_note`. It requires the project's `status` to be `PISC`. It requires that no remediation order of the project have `status` `OPEN` (otherwise `ERR_OPEN_REMEDIATION_ORDER`). It requires `pisc_elapsed_years` to be at least `pisc_duration_years`; certifying early is refused with `ERR_PISC_DURATION_NOT_ELAPSED` (HTTP 422). It requires the body's `non_endangerment_demonstrated` to be true; a certification requested with that attestation false is refused with `ERR_NON_ENDANGERMENT_NOT_DEMONSTRATED` (HTTP 422). And it requires the acting `X-User-ID` to differ from the `technical_reviewer_user_id` of every injection well permit of the project.

Certification records `non_endangerment_demonstrated` as true on the project, sets `closure_status` `NOT_REQUESTED → CERTIFIED`, records the certifying reviewer's `X-User-ID` in `closure_certified_by_user_id` and stamps `closure_certified_at` with the logical clock, and moves the project's `status` `PISC → CLOSED`, which is terminal. It also releases the money: every financial instrument of the project whose `status` is `ALLOCATED` moves `ALLOCATED → RELEASED`, has `released_at` stamped with the logical clock, has its four allocated buckets zeroed back into `unallocated_usd`, and has its own `version` bumped. The project's `allocated_assurance_usd` is reset to 0 and its `assurance_coverage_status` therefore becomes `UNFUNDED`, and the project's `version` increments. An instrument already at `DRAWN` or `POSTED` is not swept by the release; only `ALLOCATED` instruments are.

## 4. Endpoint Definitions

The endpoint surface below is flat: every entity is addressed as its own top-level collection under the `/ccs` prefix, parent linkage travels as a foreign-key field in the request body rather than as a nested URL segment, and child discovery happens through a project-scoped sub-resource listing or a filtered top-level listing. Status codes follow one rule throughout: an operation that brings a new resource into existence responds with 201 Created, and every other successful operation — including every action endpoint that advances a state machine, every listing and every read — responds with 200 OK. Request and response payloads are not repeated here; the fields each operation accepts and the side effects it produces are specified in the §3 narratives, and the errors it can raise are catalogued in §5.
