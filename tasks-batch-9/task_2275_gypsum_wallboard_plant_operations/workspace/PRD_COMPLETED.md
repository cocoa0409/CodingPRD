# Gypsum Wallboard Plant Ops API — Product Requirements Document

## 1. Introduction

A wallboard plant is a single continuous chain of physical constraints, and the accounting that governs it has historically lived in spreadsheets that disagree with one another. Gypsum arrives from two very different worlds — quarried natural rock and synthetic flue-gas desulphurisation byproduct — with moisture and purity that swing lot to lot, and the calciner has to be told what it is being fed before it can produce usable stucco. Downstream, the board line consumes that stucco at a rate set by line speed, slurry formulation and paper tension; the kiln then trades fuel against exit moisture; and the finished bundles are only worth shipping if the laboratory can certify core hardness, nail pull and flexural strength against the published standard. Every one of those handoffs is a place where a plant loses money silently.

This document specifies the API that makes that chain auditable. The system is mounted under `/plant-ops` and models the plant as a set of peer resources — plants, board lines, gypsum lots, calciner batches, product specifications, production runs, maintenance outages, destination markets and load orders — bound together by explicit references rather than by nested ownership URLs. Two ideas dominate the design. The first is that the stucco silo is a shared balance: a batch credits it, a scheduled run commits against it, and a completed run debits it, so any two writers touching the same plant must be serialised against the plant's version. The second is that quality is an independent dimension of a production run, not a phase of it — board can be produced, released, and then retroactively held days later when a retained stucco sample fails, and the loads already staged against that board must be held with it.

The API is also written for a plant that plans around housing-market seasonality. Maintenance outages compete directly with saleable production, so the system quantifies the opportunity cost of every proposed window and refuses to approve non-urgent work in the months when the market is strongest — unless the work has already been pushed twice, at which point it must happen regardless.

## 2. Global Specifications & System-Wide Principles

This section defines the contract-level rules that hold across every endpoint: authentication, response shape, pagination, identity and audit fields, numeric precision, interval semantics, the shared silo balance, the plant posture gate, concurrency control, request screening order, and segregation of duties.

### 2.1. Plant Personnel and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting operator, and `X-User-Role`, declaring the capacity in which they act. Seven roles are recognised, spelled exactly as follows: `PlantAdmin`, `MaterialsController`, `ProductionScheduler`, `QualityInspector`, `QualityManager`, `MaintenancePlanner`, and `PlantManager`. A request that omits either header, or that presents an `X-User-Role` value outside those seven strings, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A request that is authenticated but whose role is not listed for the target endpoint in §4 is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

Role responsibilities divide as follows. `PlantAdmin` configures plants, board lines, product specifications and destination markets, and is the only role permitted to drive the server's logical clock. `MaterialsController` receives and assays gypsum lots, rejects quarantined lots, plans calciner batches, feeds them, closes the feed side and aborts them. `ProductionScheduler` drafts, schedules, starts and completes board runs, and stages, loads and cancels freight. `QualityInspector` records stucco samples and board specimens and runs the run-level quality evaluation, but may never disposition a hold that arose from a specimen it recorded. `QualityManager` dispositions held runs — release, downgrade or scrap — and does nothing else. `MaintenancePlanner` proposes, defers, re-proposes, starts and closes outages, and never approves one. `PlantManager` approves outages and releases loaded trailers to ship. Cancelling a production run is the one mutating capability shared by two roles: both `ProductionScheduler` and `PlantManager` may perform it. Every read endpoint is open to all seven roles.

None of the seven roles is backed by a persisted entity. When `X-User-Role` is `PlantAdmin`, `MaterialsController`, `ProductionScheduler`, `QualityInspector`, `QualityManager`, `MaintenancePlanner`, or `PlantManager`, the accompanying `X-User-ID` is an opaque operator identifier that is not tied to any stored record and is never compared against any entity's `id`. The server does, however, record it in four places where the scaffolded workflow demands an audit trail or a duty separation: `recorded_by_user_id` on a `StuccoTest`, `recorded_by_user_id` on a `BoardTest`, `last_failing_test_recorded_by_user_id` on a `ProductionRun` (refreshed whenever a specimen fails), and `proposed_by_user_id` / `approved_by_user_id` on a `MaintenanceOutage`. Those four fields hold whatever string arrived in `X-User-ID`; they are compared to a later request's `X-User-ID` only for the segregation-of-duties checks described in §2.12.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two query parameters. `limit` caps the number of rows returned; it defaults to 10, may not be smaller than 1, and may not be larger than 100. `offset` skips rows from the front of the result set and defaults to 0. Both are optional on every list endpoint. A `limit` or `offset` that is not an integer, a `limit` below 1 or above 100, or a negative `offset`, is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

Unless a specific endpoint says otherwise, list results are ordered by `created_at` ascending, with rows sharing an identical `created_at` ordered by the sequence in which they were written. List responses populate `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the envelope, where `total_count` counts the rows matching the filter before the page window is applied.

Filtering is available on the collection reads, and every filter is optional. Plants may be filtered by `code` and by `production_posture`. Board lines accept `plant_id` and `status`. Product specifications accept `plant_id`, `board_type` and `fire_rated`; the plant-scoped listing of specifications accepts `board_type`, and the plant-scoped listing of board lines accepts `status`. Gypsum lots accept `plant_id`, `status` and `source_type`. Calciner batches accept `plant_id`, `status` and `stucco_quality_flag`. Batch feeds accept `batch_id` and `lot_id`. Stucco tests accept `batch_id` and `result`. Production runs accept `plant_id`, `line_id`, `product_spec_id`, `calciner_batch_id`, `prior_run_id`, `status` and `quality_state` — note that the self-referential predecessor reference is filterable exactly like any other reference. Board tests accept `run_id` and `result`. Maintenance outages accept `line_id`, `status` and `outage_type`. Load orders accept `run_id`, `market_id` and `status`. Markets accept `rate_zone`. The child listings reachable from a parent path — a lot's feeds, a batch's feeds, a batch's stucco tests, a run's board tests — take only `limit` and `offset`. Filter values are compared as strings against the stored field and are never themselves validated, so a filter naming a value outside its enumeration simply matches nothing and yields an empty page; query parameters that are not declared filters for the endpoint are ignored.

### 2.4. Resource Identity, Audit Fields and Version Semantics

Every resource in the system carries an `id`, which is a server-minted UUID with no type prefix, and a `created_at`, which is an ISO 8601 UTC timestamp with three fractional digits recording when the row was first written.

Most resources additionally carry `updated_at`, an ISO 8601 UTC timestamp refreshed on every mutation, and `version`, an integer that starts at 1 when the resource is created and increments by exactly 1 on every mutation of that resource. A `Plant`, `BoardLine`, `GypsumLot`, `CalcinerBatch`, `ProductSpec`, `ProductionRun`, `MaintenanceOutage`, `Market` and `LoadOrder` all behave this way. Recomputation of a derived field counts as a mutation: when a batch completes and credits the silo, the plant's `stucco_on_hand_tons`, `stucco_available_tons` and `production_posture` change, `updated_at` is refreshed and `version` advances by 1 even though no client sent a field for the plant.

Three resources are append-only records of a measurement and therefore carry only `id` and `created_at`: `BatchFeed`, `StuccoTest` and `BoardTest`. For those three, both `updated_at` and `version` are absent from the response entirely. They are never edited or deleted; a re-test adds a row rather than replacing one, and an aborted batch retains its feed rows even though those rows stop counting toward consumed tonnage.

### 2.5. Numeric Precision and Rounding Discipline

All arithmetic in this system uses decimal semantics, and every rounding operation is round-half-up. The scale differs by quantity and is fixed:

- Tonnages that touch the silo or a lot balance — `stucco_on_hand_tons`, `stucco_committed_tons`, `stucco_available_tons`, `received_tons`, `consumed_tons`, `remaining_tons`, `tons_fed`, `feed_tons_total`, `stucco_yield_plan_tons`, `stucco_yield_actual_tons`, `stucco_reserved_tons`, `stucco_consumed_tons` — are carried to 3 decimals.
- Board volumes in thousand square feet — `requested_planned_msf`, `capacity_msf`, `effective_planned_msf`, `actual_msf`, `scrap_msf`, `net_good_msf`, `scrapped_msf`, `available_msf`, `total_msf`, `at_risk_msf` — are carried to 3 decimals. The per-bundle intermediate `bundle_msf` is carried to 4 decimals and the per-board intermediate `board_msf_each` to 6.
- Blended assay percentages `feed_moisture_plan_pct`, `feed_moisture_as_fed_pct` and `feed_purity_plan_pct`, together with `projected_exit_moisture_pct`, `seasonality_index` and `planned_downtime_hours`, are carried to 2 decimals.
- Money — `kiln_energy_cost_usd`, `opportunity_cost_usd`, `quoted_freight_usd`, `settled_freight_usd`, `overweight_fee_usd`, `freight_variance_usd` — is carried to 2 decimals and returned as a JSON number, not a string.
- `kiln_energy_mmbtu` is carried to 3 decimals; `fail_rate` to 4.
- `required_paper_tension_lb`, `bundle_weight_lb` and `trailer_weight_lb` are carried to 2 decimals.
- The two per-feed dry-tonnage intermediates, `dry_tons_plan` and `dry_tons_as_fed`, are persisted at 6 decimals and are deliberately *not* rounded to the tonnage scale, because they feed a sum that is rounded only once.

Where a calculation is described later as rounding "once at the end", intermediate products and quotients must be kept unrounded until that final step; where it is described as rounding after each step, the rounded value is what the next step reads. This distinction is load-bearing — two of the calculations in §3 deliberately produce different answers from the same inputs precisely because one rounds early and the other rounds late.

Minute arithmetic is separate from decimal arithmetic. Durations expressed in whole minutes — `gap_minutes`, `available_minutes`, `changeover_minutes`, `in_window_changeover_minutes` — are obtained by taking the elapsed seconds between two instants, dividing by 60, and discarding any fractional part (that is, truncating toward zero for the non-negative spans this system produces).

### 2.6. The Logical Plant Clock

No temporal *decision* in this system reads wall-clock time, though the server's own audit stamps — `created_at`, `updated_at`, and the envelope's `api_request_timestamp` — are taken from the host clock rather than from the logical one. The server maintains a single logical clock that, before any client has set it, reads exactly `2026-08-01T00:00:00Z`. A `PlantAdmin` may advance or reset it by supplying a `to_iso8601` instant; the response reports the new value as `current_utc`. Every temporal decision consults this clock and only this clock: the `assayed_at` stamp on a lot, the `tested_at` stamp on a stucco sample or board specimen, the thirty-day assay-validity check at feed time, and the two window-start gates that guard starting a run and starting an outage.

### 2.7. Occupancy Window Semantics

Three entities occupy time windows, and the interval convention differs between them in a way that changes which requests conflict.

A calciner batch occupies `[feed_window_start, feed_window_end)` — the start instant is inside the window and the end instant is outside it. A production run likewise occupies `[window_start, window_end)`. Consequently two runs on the same line whose windows merely touch, where one ends at exactly the instant the other begins, do **not** overlap and both may be scheduled. A maintenance outage, by contrast, occupies the closed interval `[window_start, window_end]`: both endpoints are inside the window. A run whose window begins at exactly the instant an approved outage ends therefore *does* conflict with that outage, and two outages on one line that touch at an endpoint conflict with each other.

On every entity that has one, `window_end` must be strictly later than `window_start`; a window that is empty or inverted is rejected with `ERR_INVALID_WINDOW` (HTTP 400). This applies when drafting a production run, when planning a calciner batch, when proposing a maintenance outage, and when re-proposing a deferred outage on a fresh window.

### 2.8. The Stucco Silo as a Shared Balance

Each plant owns one stucco silo, and the API treats it as a three-account balance rather than a single number. `stucco_on_hand_tons` is physical inventory: it is credited when a calciner batch reaches `COMPLETED` and debited when a production run reaches `COMPLETED`. `stucco_committed_tons` is the sum of `stucco_reserved_tons` across every production run of that plant whose `status` is `SCHEDULED` or `RUNNING`. `stucco_available_tons` is the on-hand figure minus the committed figure, rounded half-up to 3 decimals, and it is the only figure a new reservation is tested against. All three initialise to `0.000` when the plant is registered, alongside `held_run_count` at 0.

The balance is conserved by construction. Every path that removes a run from the committed set puts its reservation back: an operator cancelling a `SCHEDULED` run, a cascade cancelling a `SCHEDULED` run because an outage was approved, and a run completing all subtract that run's `stucco_reserved_tons` from `stucco_committed_tons`. Cancellation additionally zeroes the run's own `stucco_reserved_tons` to `0.000`. Cancelling a run that never left `DRAFT` moves no tonnage, because a `DRAFT` run never reserved any.

Gypsum mass is conserved on the same principle one stage upstream. A lot's `consumed_tons` is the sum of `tons_fed` across every feed drawn from it whose owning batch is not `ABORTED`, and `remaining_tons` is `received_tons` minus `consumed_tons`, rounded half-up to 3 decimals. Aborting a batch therefore restores tonnage to every lot it drew from, because those feed rows stop counting — and a lot that had been drawn down to nothing comes back into service. Finished board volume follows the same discipline: a run's `available_msf` is its `net_good_msf` less the `total_msf` of every load order against it whose `status` is `STAGED`, `HELD`, `LOADED` or `SHIPPED`, so cancelling a load returns its volume to the run.

### 2.9. Plant Production Posture

Every plant carries a derived gate, `production_posture`, with exactly three values: `OPEN`, `RESTRICTED` and `FROZEN`. It is re-derived immediately after any mutation that changes `held_run_count`, `stucco_on_hand_tons`, `stucco_committed_tons`, or the status of an emergency outage, and each re-derivation is a mutation of the plant that refreshes `updated_at` and increments `version`.

The derivation runs in this order. First, `held_run_count` is the number of production runs belonging to the plant whose `quality_state` is `HELD`. Second, `stucco_available_tons` is recomputed as described in §2.8. Third, the plant is considered to have an emergency in progress when at least one maintenance outage on one of its board lines has `status` equal to `IN_PROGRESS` and `outage_type` equal to `EMERGENCY`. The posture is then `FROZEN` if `held_run_count` is 3 or more, or if an emergency is in progress. Otherwise it is `RESTRICTED` if `held_run_count` is 1 or more, or if `stucco_available_tons` is strictly below 40.0 tons. Otherwise it is `OPEN`. Note the asymmetry: the held-run comparisons are inclusive of the threshold, while the stucco comparison is strict, so a plant sitting on exactly 40.0 available tons with no held runs is `OPEN`.

A freshly registered plant is therefore `RESTRICTED`, not `OPEN`: its silo is empty, so `stucco_available_tons` of `0.000` is below the 40.0-ton floor.

Posture gates two operations. Scheduling a run and starting a run are both refused while the posture is `FROZEN`, with `ERR_PLANT_POSTURE_FROZEN` (HTTP 409). Scheduling is additionally refused while the posture is `RESTRICTED` when the SKU being produced is fire-rated, with `ERR_POSTURE_RESTRICTED_FIRE_RATED` (HTTP 409); a `RESTRICTED` plant may still schedule non-fire-rated SKUs.

### 2.10. Stale-Version Guards on Shared Parents

Two write operations mutate a parent whose state other writers are simultaneously entitled to change, and both are guarded by an optimistic concurrency check against that parent's `version`. These are the only two endpoints in the system that accept a version field; every other endpoint takes none, and supplying one elsewhere has no effect. Both fields must arrive as integers of zero or greater, screened at band 4 before the guard itself is evaluated.

Scheduling a production run — the operation addressed as `POST /plant-ops/production-runs/{runId}/schedule` — requires a non-optional `expected_plant_version` in the request body, carrying the `version` of the owning `Plant` as the client last observed it. If that value does not equal the plant's current `version` at the moment the request is processed, the request is rejected with `ERR_STALE_PLANT_VERSION` and HTTP 412. The reason is that scheduling commits silo tonnage against a shared balance: if another writer has advanced the plant since the client read it — a different run scheduled, a batch credited, a run completed, a posture re-derived — then the `stucco_available_tons` and `production_posture` the client reasoned about are obsolete and the reservation it computed may no longer fit. Scheduling a second, different run against the same plant is entirely legitimate product behaviour, which is why this is resolved by a version comparison rather than by a state precondition.

Creating a batch feed — the operation addressed as `POST /plant-ops/calciner-batches/{batchId}/feeds` — requires a non-optional `expected_lot_version` in the request body, carrying the `version` of the source `GypsumLot` as the client last observed it. A mismatch with the lot's current `version` is rejected with `ERR_STALE_LOT_VERSION` and HTTP 412. Drawing tonnage from a lot supersedes the client's view of that lot's `remaining_tons`, its assay values and its `status`, any of which may have moved because the lot was re-assayed, drawn down by another feed, or restored by a batch abort. Feeding the same lot again is itself legitimate, so again the conflict is resolved by the version check.

### 2.11. Request Screening Order

When more than one rule could reject a request, the system evaluates checks in a fixed order and returns the error belonging to the first check that fails. Lower-numbered bands are evaluated first; checks sharing a band are mutually exclusive in practice.

1. **Authentication.** Both headers present and `X-User-Role` among the seven declared roles, else `ERR_UNAUTHENTICATED`.
2. **Authorisation.** The acting role appears in the endpoint's role list in §4, else `ERR_UNAUTHORIZED`.
3. **Path resolution, left to right.** Identifiers embedded in the URL are resolved in the order they appear, and the first one that does not exist decides the error: `{plantId}` yields `ERR_PLANT_NOT_FOUND`, `{lotId}` yields `ERR_LOT_NOT_FOUND`, `{batchId}` yields `ERR_BATCH_NOT_FOUND`, `{runId}` yields `ERR_RUN_NOT_FOUND`, `{outageId}` yields `ERR_OUTAGE_NOT_FOUND`, `{loadOrderId}` yields `ERR_LOAD_ORDER_NOT_FOUND`, and the read-only addresses `{lineId}`, `{specId}`, `{feedId}`, `{stuccoTestId}`, `{boardTestId}` and `{marketId}` resolve their own collections and report a miss with the generic `ERR_NOT_FOUND`. All are HTTP 404. Because resolution is strictly left to right, a request for a board line under a non-existent plant reports the plant miss, never the line miss.
4. **Request shape.** On every write endpoint: the body parses, required fields are present, every value carries its declared JSON type (a numeric field rejects strings and booleans, a string field rejects numbers, an integer field rejects fractional values), enum values are members of their declared sets, numbers fall inside their declared ranges, every required string — including each body-supplied reference identifier — is non-empty, and the uniqueness rules hold — `code` unique across all plants, `sku_code` unique within a plant, `designation` unique within a plant, `sample_seq` unique within a batch, `specimen_seq` unique within a run. This band also catches `fire_rated` disagreeing with `board_type`, `scrap_msf` greater than `actual_msf`, `loaded_bundles_count` greater than `bundles_count`, and an odd `boards_per_bundle`. All of these are `ERR_INVALID_REQUEST` (HTTP 400).
5. **Body-supplied reference resolution.** Foreign keys named in the body — `plant_id`, `line_id`, `product_spec_id`, `calciner_batch_id`, `lot_id`, `run_id`, `market_id` — must resolve, else `ERR_REFERENCE_NOT_FOUND` (HTTP 404). This band applies when receiving a gypsum lot, planning a calciner batch, creating a batch feed, drafting a production run, and staging a load order.
6. **Plant scoping.** Cross-referenced entities must belong to the same plant: a feed's source lot must belong to the batch's plant, and a run's line, product specification and calciner batch must all belong to the run's plant. A violation is `ERR_PLANT_SCOPE_MISMATCH` (HTTP 409). This band applies to feed creation and run drafting.
7. **Stale-version guards.** The two optimistic concurrency checks of §2.10: `ERR_STALE_PLANT_VERSION` on run scheduling and `ERR_STALE_LOT_VERSION` on feed creation, both HTTP 412.
8. **State preconditions.** The target resource must be in a state from which the requested transition is declared. The generic failure is `ERR_INVALID_STATE` (HTTP 409). The dedicated codes evaluated in this same band, each replacing the generic one on its own endpoint, are: `ERR_NO_BOARD_TEST_SPECIMENS` (HTTP 422) when a run quality evaluation is requested on a run whose `quality_state` is still `UNTESTED`, meaning `specimen_count` is 0 — this is the one documented exception where the generic invalid-state error must *not* be returned; `ERR_LOT_NOT_APPROVED` (HTTP 409) when a feed names a lot whose `status` is anything other than `APPROVED`, which covers `RECEIVED`, `QUARANTINED`, `REJECTED` and `DEPLETED` alike; `ERR_MAX_ASSAYS_REACHED` (HTTP 409) on a fourth assay attempt; `ERR_MAX_DEFERRALS_REACHED` (HTTP 409) on a third deferral attempt; `ERR_RUN_QUALITY_NOT_RELEASED` (HTTP 409) when shipping a load whose source run is not `RELEASED` or `DOWNGRADED`; `ERR_LINE_NOT_AVAILABLE` (HTTP 409) when the line's `status` is not `AVAILABLE`, which guards both starting a run and approving an outage; and `ERR_RUN_ACTIVE_ON_LINE` (HTTP 409) when starting an outage on a line that has a `RUNNING` run.
9. **Segregation of duties.** `ERR_SEGREGATION_OF_DUTIES` (HTTP 403), on outage approval and on run quality disposition.
10. **Posture gates.** `ERR_PLANT_POSTURE_FROZEN` on run scheduling and run starting; `ERR_POSTURE_RESTRICTED_FIRE_RATED` on run scheduling.
11. **Material conformance gates.** `ERR_FIRE_RATED_STUCCO_NONCONFORMING` (HTTP 422) on run scheduling; `ERR_ASSAY_EXPIRED` (HTTP 409) on feed creation.
12. **Window well-formedness and clock gates.** `ERR_INVALID_WINDOW` on run drafting, batch planning, outage proposal and outage re-proposal; `ERR_RUN_WINDOW_NOT_STARTED` (HTTP 409) on run starting; `ERR_OUTAGE_WINDOW_NOT_STARTED` (HTTP 409) on outage starting.
13. **Outage window conflict.** `ERR_OUTAGE_WINDOW_CONFLICT` (HTTP 409), on run scheduling and on outage approval.
14. **Line window conflict between runs.** `ERR_LINE_WINDOW_CONFLICT` (HTTP 409), on run scheduling.
15. **Changeover buffer.** `ERR_CHANGEOVER_BUFFER_VIOLATION` (HTTP 409), on run scheduling.
16. **Seasonality gate.** `ERR_SEASONALITY_WINDOW_UNFAVORABLE` (HTTP 409), on outage approval.
17. **Process-envelope constraints.** On run drafting: `ERR_LINE_SPEED_EXCEEDS_SPEC`, `ERR_PAPER_TENSION_OUT_OF_RANGE` and `ERR_KILN_PROFILE_INFEASIBLE`, all HTTP 422. On run scheduling: `ERR_WINDOW_TOO_SHORT_FOR_CHANGEOVER` (HTTP 422). On load staging: `ERR_BUNDLE_CONFIG_INVALID` (HTTP 422). On run quality evaluation: `ERR_INSUFFICIENT_SPECIMENS` (HTTP 422). On run quality disposition: `ERR_RETEST_REQUIRED` (HTTP 409).
18. **Calciner aggregate capacity.** `ERR_CALCINER_CAPACITY_EXCEEDED` (HTTP 409), on batch planning.
19. **Weight and vessel ceilings.** `ERR_TRAILER_WEIGHT_EXCEEDED` (HTTP 422) on both load staging and load recording; `ERR_SILO_CAPACITY_EXCEEDED` (HTTP 409) on recording a stucco sample that would complete a batch.
20. **Balance sufficiency.** `ERR_LOT_TONS_INSUFFICIENT` (HTTP 409) on feed creation; `ERR_STUCCO_INSUFFICIENT` (HTTP 409) on run scheduling; `ERR_RUN_MSF_INSUFFICIENT` (HTTP 409) on load staging.

Two consequences of this ordering deserve emphasis. Because the posture gates sit at band 10 while window conflicts sit at bands 13 and 14, a schedule attempt on a frozen plant reports the posture, not the conflicting window, even when both are true. And because the stale-version guards sit at band 7, ahead of every state and business check, a client acting on an out-of-date read of the plant or the lot learns that first, before it learns anything about capacity, tonnage or conformance.

### 2.12. Segregation of Duties and Cascade Propagation

Two decisions in this plant may not be made by the person who set them up. A maintenance outage may not be approved by the operator who proposed it: the `X-User-ID` presented at approval is compared with `proposed_by_user_id`, and equality is rejected with `ERR_SEGREGATION_OF_DUTIES`. Likewise, a held production run may not be dispositioned by the inspector who recorded the specimen that caused the hold: the `X-User-ID` presented at disposition is compared with `last_failing_test_recorded_by_user_id`, and equality is rejected with the same code, on all three disposition branches without exception.

Cascades in this system are immediate and multi-hop. When one operation changes a parent, the consequences reach the children within the same request, and every touched row is a mutation in its own right — its `updated_at` is refreshed and its `version` increments by 1. There is no deferred reconciliation and no eventual consistency: a client that reads a plant, a line, a run and its load orders immediately after an outage approval sees all four already settled. Because a plant's derived fields sit at the end of several of these chains, a single request can bump `Plant.version` while also bumping `BoardLine.version`, several `ProductionRun.version` values and several `LoadOrder.version` values. §3 states each cascade chain hop by hop where it belongs in the workflow.

## 3. Business Logic & Workflows

### 3.1. Standing Up a Plant: Lines, SKUs, Markets and the Clock

A `PlantAdmin` begins by registering the plant itself, supplying a short `code` of between 1 and 16 characters that must be unique across every plant in the system (a duplicate is an `ERR_INVALID_REQUEST`), a display `name`, and the physical and commercial parameters that the rest of the system reads. `calciner_capacity_tph` is the aggregate feed-rate ceiling in tons per hour and must be greater than zero; `stucco_silo_capacity_tons` is the maximum tonnage the silo may hold and must likewise be greater than zero. Two assay thresholds may be supplied or left to their defaults: `natural_gypsum_purity_floor_pct` accepts a value from 50.0 through 100.0 and defaults to 88.0, and `synthetic_free_moisture_ceiling_pct` accepts a value from 0.0 through 30.0 and defaults to 12.0. Finally `energy_price_per_mmbtu`, which must be greater than zero, prices kiln fuel, and `contribution_margin_per_msf`, which may be zero or greater, prices the board that a maintenance outage would displace. On registration the silo accounts and the held-run counter are all set as described in §2.8, and the posture is derived at once — which, for an empty silo, means the plant opens for business `RESTRICTED`.

Board lines are added under the plant. Each requires a `designation` unique among that plant's lines, a mechanical ceiling `max_speed_fpm` given as an integer between 100 and 1200 feet per minute inclusive, and a forming-table `web_width_in` greater than zero. A new line's `status` is `AVAILABLE`, and it moves only under maintenance control: `AVAILABLE → MAINTENANCE_SCHEDULED` when an outage on it is approved, `MAINTENANCE_SCHEDULED → UNDER_MAINTENANCE` when that outage starts, and `UNDER_MAINTENANCE → AVAILABLE` when it closes. Each of those three system-driven transitions increments the line's `version` by 1. Nothing else changes a line's status, and a line never reaches a terminal state; the maintenance cycle can repeat indefinitely.

SKUs are registered as product specifications, and this is the densest configuration payload in the system. Identity comes from `sku_code`, unique within the plant. Geometry comes from `thickness_in`, which must be exactly one of `0.375`, `0.5` or `0.625`; `board_width_in` and `board_length_ft`, both greater than zero. Note that `board_width_in` is deliberately *not* validated against any line's `web_width_in` — specifications are line-agnostic, and the plant is trusted to pair them sensibly. `board_type` is one of `REGULAR`, `TYPE_X`, `TYPE_C`, `MOLD_RESISTANT` or `ABUSE_RESISTANT`, and the boolean `fire_rated` is constrained rather than free: it must be `true` when `board_type` is `TYPE_X` or `TYPE_C`, and `false` for the other three families. A disagreement is rejected with `ERR_INVALID_REQUEST`. Formulation comes from `target_board_weight_lb_per_msf` and `stucco_lb_per_msf`, both greater than zero, and `slurry_water_stucco_ratio`, which expresses slurry water as a fraction of board weight per MSF and must lie between 0.30 and 1.20 inclusive. Operating limits come from `line_speed_max_fpm` (an integer, 100 to 1200 inclusive), `paper_tension_min_lb` greater than zero, and `paper_tension_max_lb`, which must be strictly greater than `paper_tension_min_lb`. Standards minima come from `core_hardness_min_lbf`, `nail_pull_min_lbf` and `flexural_cross_min_lbf`, all greater than zero. Warehouse configuration comes from `max_boards_per_bundle`, an even integer from 2 through 80. And `changeover_family`, one of `STANDARD`, `FIRE_RATED` or `SPECIALTY`, is the axis the changeover matrix reads.

Destination markets are registered independently of plants. A market carries a `name`, a one-way haul `distance_miles` greater than zero, a `fuel_surcharge_pct` between 0.0 and 60.0, a `min_charge_usd` of zero or more that acts as a freight floor per load, and an optional `backhaul_credit_usd` that also defaults to `0.00` and may not be negative. From `distance_miles` the system immediately derives the market's `rate_zone` and its `base_rate_per_msf`: a haul under 150 miles is `ZONE_1` at 8.50 dollars per MSF, a haul of at least 150 but under 350 miles is `ZONE_2` at 12.75, a haul of at least 350 but under 600 miles is `ZONE_3` at 17.40, and anything from 600 miles upward is `ZONE_4` at 23.10. Each zone boundary is inclusive at its lower edge and exclusive at its upper edge, so a market exactly 350 miles out is `ZONE_3`.

Finally, an admin-only test-driving capability sets the logical clock, taking `to_iso8601` as its single input and reporting the resulting `current_utc`, which echoes the supplied string verbatim rather than re-formatting it, inside a `data` object that carries that one field and nothing else. Its semantics are given in §2.6.

### 3.2. Receiving Gypsum, Assaying It, and the Quarantine Cycle

A `MaterialsController` receives each inbound lot against a bill of lading, naming the destination plant, the `source_type` — either `NATURAL` for quarried rock or `SYNTHETIC` for FGD byproduct — the `supplier_name`, and the as-received `received_tons`, which must be greater than zero and is carried to 3 decimals. The controller also records what the supplier claimed: `declared_free_moisture_pct` between 0.0 and 40.0, and `declared_purity_pct` between 0.0 and 100.0. These two declared values are recorded for commercial dispute purposes and are never consulted by any calculation or gate in this system — no assay disposition, no blend metric and no yield figure reads them. A new lot enters `status` `RECEIVED` with `assay_count` at 0, `remaining_tons` equal to `received_tons`, and `version` at 1. Until a laboratory result arrives, `free_moisture_pct`, `purity_pct`, `chloride_ppm`, `assayed_at` and `quarantine_reason` are all null.

Recording an assay is where the lot's fate is decided. The controller submits a `free_moisture_pct`, a `purity_pct` and an integer `chloride_ppm`, all measured in the laboratory and all constrained only to be zero or greater — the laboratory numbers carry no upper bound, unlike the supplier's declared pair. An assay is accepted only while the lot is `RECEIVED` or `QUARANTINED`; an `APPROVED`, `REJECTED` or `DEPLETED` lot is refused with `ERR_INVALID_STATE`, and the assay-count ceiling below is tested before that state check, so a lot that is both terminal and out of attempts reports `ERR_MAX_ASSAYS_REACHED`. The submitted values overwrite whatever was there before, `assayed_at` is stamped from the logical clock, and `assay_count` increases by 1. The disposition rule then runs three checks in a strictly pinned order, and the *first* one that fails both quarantines the lot and decides `quarantine_reason`. Check one applies only to a `SYNTHETIC` lot: if its laboratory `free_moisture_pct` is strictly greater than the plant's `synthetic_free_moisture_ceiling_pct`, the reason is `MOISTURE_CEILING` — a value exactly equal to the ceiling passes. Check two applies only to a `NATURAL` lot: if its `purity_pct` is strictly below the plant's `natural_gypsum_purity_floor_pct`, the reason is `PURITY_FLOOR` — a value exactly equal to the floor passes. Check three applies to every lot regardless of source: if `chloride_ppm` is 250 or more, the reason is `CHLORIDE_CEILING` — here equality *fails*, unlike the two preceding checks. If all three checks are survived, the lot becomes `APPROVED` and `quarantine_reason` is set to null. Comparisons use the values as supplied, at two decimal places, with no rounding applied. Every assay, whatever its outcome, increments the lot's `version` by 1.

The re-assay cycle is bounded. A `RECEIVED` lot moves to either `APPROVED` or `QUARANTINED` on its first assay. A `QUARANTINED` lot may be assayed again: if the disposition still comes back quarantined the lot loops `QUARANTINED → QUARANTINED` with its reason recomputed, and if the fresh numbers clear all three checks it moves `QUARANTINED → APPROVED` with `quarantine_reason` cleared to null. What bounds the loop is that a lot may receive at most three assays in total. Any attempt to record a fourth — that is, an attempt made when `assay_count` has already reached 3 — is refused with `ERR_MAX_ASSAYS_REACHED`. The third assay is the last chance a lot gets.

A quarantined lot that cannot be salvaged is rejected outright, with an optional `reject_note` supplied by the controller — the note is accepted and validated as a string but is not persisted on the lot, and omitting it is legal. Rejection is permitted only from `QUARANTINED`, and only while the lot has never been drawn from: `consumed_tons` must be exactly `0.000`. Either condition failing yields `ERR_INVALID_STATE`. Rejection sets `remaining_tons` to `0.000`, moves the lot to the terminal `REJECTED` state, and increments its `version`.

The remaining two states are reached by the system rather than by an operator. A lot moves `APPROVED → DEPLETED` at the moment a feed draws it down so that `received_tons` minus `consumed_tons`, rounded half-up to 3 decimals, equals exactly `0.000`; from `DEPLETED` no further feed is accepted, and one attempted anyway is refused with `ERR_LOT_NOT_APPROVED`. And a lot moves `DEPLETED → APPROVED` when a batch that drew from it is aborted and the restoration leaves `remaining_tons` strictly above `0.000`. That compensating transition recomputes both `consumed_tons` and `remaining_tons` and increments the lot's `version`; it is what keeps gypsum mass conserved across an abort. `REJECTED` and `DEPLETED` are the lifecycle's terminal states, though `DEPLETED` is escapable by exactly that one compensating route.

### 3.3. Calcination: Planning a Batch, Feeding It, and the Two Blend Bases

A `MaterialsController` plans a calcination batch against a feed window, supplying the owning plant, a `target_stucco_tons` greater than zero, a `calcination_temp_f` setpoint between 250.0 and 400.0 degrees, a `feed_rate_tph` greater than zero, and the window bounds `feed_window_start` and `feed_window_end`. Calciner windows are permitted to overlap — the plant runs one calciner train and several batches can be in flight against it — so what is bounded is not occupancy but the *aggregate instantaneous feed rate*. To test a proposed batch, the system gathers every sibling batch at the same plant whose `status` is `PLANNED`, `FEEDING` or `CALCINING`; batches that have reached `COMPLETED` or `ABORTED` have released their window and are ignored. It then breaks the union of the new half-open window with each of those siblings' windows into sub-intervals at every boundary instant, and for each sub-interval sums the new batch's `feed_rate_tph` together with the `feed_rate_tph` of every sibling overlapping that sub-interval. If any sub-interval's total is strictly greater than the plant's `calciner_capacity_tph`, the plan is refused with `ERR_CALCINER_CAPACITY_EXCEEDED`; a total exactly equal to capacity is accepted. Rates are compared exactly as supplied, with no rounding applied to either the summed load or the capacity. A batch that survives the test is created in `status` `PLANNED` with `stucco_quality_flag` at `PENDING`, `feed_tons_total`, `stucco_yield_plan_tons` and `stucco_yield_actual_tons` all at `0.000`, `abort_reason` null, and the three blend metrics `feed_moisture_plan_pct`, `feed_purity_plan_pct` and `feed_moisture_as_fed_pct` null until the first feed arrives.

Feeding is how gypsum becomes stucco feedstock. Each feed increment names the source lot, the `tons_fed` drawn from it — greater than zero, three decimals — the belt-scale `measured_free_moisture_pct` observed as that increment went in (0.0 to 40.0), and the `expected_lot_version` guard described in §2.10. A feed is subject to five preconditions, and they hold identically for the first feed and for every subsequent one; they are evaluated not in the order listed here but in the band order of §2.11 — plant scoping, then the version guard, then the state checks, then assay currency, then tonnage — and within the state band the batch's own posture is tested first, so a feed offered to a `CALCINING` batch from a quarantined lot reports `ERR_INVALID_STATE` rather than `ERR_LOT_NOT_APPROVED`: the lot's `status` must be `APPROVED` or the request fails with `ERR_LOT_NOT_APPROVED`; the lot must belong to the same plant as the batch or the request fails with `ERR_PLANT_SCOPE_MISMATCH`; the lot's assay must still be current, meaning the logical clock must be no more than 30 days past the lot's `assayed_at`, or the request fails with `ERR_ASSAY_EXPIRED`; the `expected_lot_version` must equal the lot's current `version` or the request fails with `ERR_STALE_LOT_VERSION`; and `tons_fed` must not exceed the lot's `remaining_tons` or the request fails with `ERR_LOT_TONS_INSUFFICIENT`.

A successful feed writes an append-only record. Its `feed_seq` is 1 for the first feed of the batch and, for each subsequent feed, one more than the number of feeds already recorded against that batch. At the moment it is written it snapshots the lot's laboratory values as `assay_free_moisture_pct` and `assay_purity_pct` — these are frozen copies, so a later re-assay of the lot does not retroactively change any feed already taken. It also persists two dry-tonnage intermediates at six decimals: `dry_tons_plan`, which is `tons_fed` multiplied by one minus `assay_free_moisture_pct` divided by 100, and `dry_tons_as_fed`, which is `tons_fed` multiplied by one minus `measured_free_moisture_pct` divided by 100. On the lot side, `consumed_tons` increases by `tons_fed`, `remaining_tons` is recomputed, and the lot's `version` increments by 1 — and if the draw takes `remaining_tons` to exactly `0.000` the lot moves on to `DEPLETED` in the same request. On the batch side, the first feed drives `PLANNED → FEEDING` and every subsequent feed keeps the batch in `FEEDING`; `feed_tons_total` is recomputed as the sum of `tons_fed` across the batch's feeds to three decimals, both blend metrics are recomputed, and the batch's `version` increments by 1.

The two blend metrics are computed from the same feed rows and are designed to disagree. Both read the batch's feeds ordered by `created_at` ascending, which is the same as `feed_seq` order, and both ignore the feeds of an aborted batch entirely — an `ABORTED` batch reports `0.00` on all three, at the two-decimal blend scale rather than the tonnage scale. The **plan basis** answers "what did the laboratory say we blended?" and rounds only once: `feed_moisture_plan_pct` is the sum over all feeds of `tons_fed` multiplied by `assay_free_moisture_pct`, divided by the sum of `tons_fed` over all feeds, with the single final quotient rounded half-up to two decimals. `feed_purity_plan_pct` is computed identically but with `assay_purity_pct` in place of the moisture term. The **as-fed basis** answers "what did the belt scale see, increment by increment?" and rounds after every feed: starting from an accumulated tonnage of zero and an accumulated moisture of zero, each feed in chronological order produces a new accumulated tonnage equal to the previous accumulated tonnage plus that feed's `tons_fed`, and a new accumulated moisture equal to the previous accumulated moisture multiplied by the previous accumulated tonnage, plus that feed's `measured_free_moisture_pct` multiplied by that feed's `tons_fed`, all divided by the new accumulated tonnage — and that quotient is rounded half-up to two decimals before the next feed is processed. `feed_moisture_as_fed_pct` is the accumulated moisture after the last feed. Because the running average is re-rounded at every step, the order in which increments were fed changes the answer, which is precisely the point: it is a measured history, not a recomputed average.

Closing the feed side moves the batch `FEEDING → CALCINING`. It requires the batch to be in `FEEDING` — otherwise `ERR_INVALID_STATE` — and requires `feed_tons_total` to be greater than zero, so an empty batch cannot be closed. Closing stamps `feed_purity_plan_pct` and the planned yield, and thereafter no further feed is accepted; a feed attempted on a `CALCINING` batch is refused with `ERR_INVALID_STATE`. The batch's `version` increments by 1.

Stucco yield is computed by the same routine in two variants, and only the difference between them matters commercially. In both, the batch's feeds are walked in chronological order and each feed contributes to a running total that is *not* rounded along the way. For each feed, the dry tonnage is `tons_fed` multiplied by one minus the chosen moisture basis divided by 100; the gypsum portion of that dry tonnage is the dry tonnage multiplied by that feed's `assay_purity_pct` divided by 100; the inert portion is the dry tonnage minus the gypsum portion; and the feed's contribution is the gypsum portion multiplied by the dihydrate-to-hemihydrate conversion factor of 0.8437 plus the inert portion multiplied by a pass-through factor of 1.0 — inerts survive calcination unchanged. Once every feed has contributed, and only then, the batch total is rounded half-up to three decimals. The **planned yield** variant uses each feed's `assay_free_moisture_pct` as its moisture basis and is stamped on `stucco_yield_plan_tons` when the feed side closes. The **actual yield** variant uses each feed's `measured_free_moisture_pct` instead and is stamped on `stucco_yield_actual_tons` when the batch reaches `COMPLETED`; only this second variant ever moves silo tonnage. An aborted batch yields `0.000` on both.

Aborting a batch is available from `PLANNED`, `FEEDING` or `CALCINING`, with a free-text `abort_reason` recorded — the field is optional and `abort_reason` stays null when it is omitted; from any other state the request is refused with `ERR_INVALID_STATE`. Aborting from `CALCINING` carries one extra precondition: no production run may name this batch as its stucco provenance while sitting in `SCHEDULED` or `RUNNING`, and one that does blocks the abort with `ERR_INVALID_STATE`. An abort from `PLANNED` simply releases the batch's window from the aggregate-capacity pool and increments the batch's `version`. An abort from `FEEDING` or `CALCINING` additionally unwinds every feed: for each feed row the source lot's `consumed_tons` decreases by that feed's `tons_fed`, its `remaining_tons` is recomputed, its `version` increments by 1, and a lot that had been `DEPLETED` returns to `APPROVED` whenever the restoration leaves `remaining_tons` strictly above `0.000`. The batch's own `feed_tons_total`, `stucco_yield_plan_tons` and `stucco_yield_actual_tons` are all set to `0.000`, its three blend metrics to `0.00`, and its `version` increments by 1. The feed rows themselves are retained — they are append-only history — but because the batch is now `ABORTED` they no longer count toward any lot's consumption or any blend metric.

### 3.4. Stucco Quality, Batch Completion, and the Nonconformance Cascade

A `QualityInspector` records stucco samples against a batch, each identified by a `sample_seq` of 1 or greater that must be unique within that batch. The sample reports `combined_water_pct` (0.0 to 25.0), the chemically combined water remaining after calcination; `free_water_pct` (0.0 to 5.0), the residual free water; `set_time_minutes` (0.0 to 60.0), the Vicat set time; and `normal_consistency_cc` (40.0 to 140.0), the water demand per hundred grams of stucco. The last of these is recorded for the laboratory record and never gates anything. Each sample stamps `recorded_by_user_id` from the acting `X-User-ID` and `tested_at` from the logical clock. Sampling is accepted only while the batch is `CALCINING` or `COMPLETED`; a batch still `PLANNED` or `FEEDING`, or one already `ABORTED`, is refused with `ERR_INVALID_STATE` — and because `sample_seq` uniqueness is a request-shape rule, a duplicate sequence number on a wrongly-posed batch reports `ERR_INVALID_REQUEST` first.

The sample's `result` is graded in a pinned sequence of four tests against the sample values as supplied, at two decimals. First, if `combined_water_pct` is below 4.20 or above 6.50, the result is `FAIL`. Second, if `free_water_pct` is above 0.50, the result is `FAIL`. Third, if `set_time_minutes` is below 3.00 or above 15.00, the result is `FAIL`. Only if all three fail-band tests are survived does the fourth test run: if `free_water_pct` is above 0.30, or `set_time_minutes` is below 4.00, or `set_time_minutes` is above 12.00, the result is `MARGINAL`. A sample that survives all four is `PASS`. Whatever the outcome, the batch's `stucco_quality_flag` is overwritten with the new result, so the flag always reflects the most recent sample rather than the best or the worst one.

What the sample does to the batch depends on where the batch stands. A sample recorded on a `CALCINING` batch whose result is `FAIL` leaves the batch in `CALCINING` — the transition is a self-loop — sets `stucco_quality_flag` to `FAIL`, credits the silo with nothing at all, and increments the batch's `version` by 1. The batch can be sampled again. A sample recorded on a `CALCINING` batch whose result is `PASS` or `MARGINAL` completes it: the batch moves `CALCINING → COMPLETED`, the actual-yield variant is computed and stamped on `stucco_yield_actual_tons`, `stucco_quality_flag` takes the sample's result, that actual yield is added to the plant's `stucco_on_hand_tons`, `stucco_available_tons` and `production_posture` are re-derived, the plant's `version` increments by 1, and the batch's `version` increments by 1. Completion is gated on the silo having room: if the plant's `stucco_on_hand_tons` plus this batch's `stucco_yield_actual_tons`, rounded half-up to three decimals, would exceed `stucco_silo_capacity_tons`, the request is refused with `ERR_SILO_CAPACITY_EXCEEDED`; a total exactly equal to capacity is accepted.

Retained samples are the reason a completed batch is never truly closed. A sample may be recorded against a batch already in `COMPLETED`, keeping it in `COMPLETED` and overwriting `stucco_quality_flag` with the new result. If that new result is `FAIL`, a four-hop cascade fires within the same request. Hop one to two: every production run naming this batch as its stucco provenance whose `status` is `RUNNING` or `COMPLETED`, and whose `quality_state` is `UNTESTED`, `IN_TEST`, `RELEASED` or `DOWNGRADED`, has its `quality_state` moved to `HELD` with `held_reason` set to `STUCCO_NONCONFORMING` and `saleable_grade` reset to `UNGRADED`. Hop two to three: each such run increments the plant's `held_run_count`, which re-derives `production_posture` and increments the plant's `version` by 1. Hop three to four: because each of those runs is now `HELD`, every load order sourced from it whose `status` is `STAGED` moves to `HELD` with `hold_source` set to `RUN_QUALITY_HELD`. The batch's own `version` increments by 1. This is the mechanism by which board that was already released, and freight that was already staged, is pulled back on the strength of a laboratory result days after the fact.

### 3.5. Drafting and Scheduling a Board Run

Drafting is where a `ProductionScheduler` commits to a process envelope, and it is deliberately separated from scheduling so that the envelope can be validated before any shared resource is touched. A draft names the plant, the line it will occupy, the product specification it will produce and the calciner batch supplying its stucco; it declares the occupancy window as `window_start` and `window_end`; and it declares the operator's four process choices. `requested_planned_msf`, greater than zero and carried to three decimals, is how much board the scheduler is asking for. `line_speed_fpm`, an integer from 100 to 1200, is the chosen line speed. `paper_tension_lb`, greater than zero, is the chosen paper tension. `kiln_dwell_minutes`, an integer from 10 to 120, and `kiln_exit_moisture_target_pct`, from 0.05 to 2.00, are the two halves of the kiln profile. A new draft has `status` `DRAFT`, `quality_state` `UNTESTED` and `saleable_grade` `UNGRADED`, with `prior_run_id`, `cancel_reason`, `held_reason` and `last_failing_test_recorded_by_user_id` all null. Its tonnage and volume counters stand at their zero defaults — `effective_planned_msf`, `stucco_reserved_tons`, `actual_msf`, `scrap_msf`, `stucco_consumed_tons`, `net_good_msf`, `scrapped_msf` and `available_msf` are each `0.000` — and so do its quality counters: `specimen_count`, `failing_specimen_count` and `retest_count` are 0 and `fail_rate` is `0.0000`. The figures that only a later operation computes are null at draft time rather than zero: `changeover_minutes`, `gap_minutes`, `in_window_changeover_minutes`, `available_minutes`, `capacity_msf`, `kiln_energy_mmbtu` and `kiln_energy_cost_usd`, which belong to the scheduling chain, and `edge_defect_ppm` and `end_defect_ppm`, which the completion payload supplies.

Three process-envelope checks run at draft time, all reported as HTTP 422. The speed check is a double ceiling: `line_speed_fpm` may not exceed the lower of the line's mechanical `max_speed_fpm` and the SKU's `line_speed_max_fpm`, and a breach of either is `ERR_LINE_SPEED_EXCEEDS_SPEC`.

The tension check is speed-scaled, because paper must be pulled harder the faster the forming table runs. The system computes `required_paper_tension_lb` as the SKU's `paper_tension_min_lb` plus the quantity of `line_speed_fpm` less 250 multiplied by 0.06, with the result rounded half-up to two decimals and stamped on the run as `required_paper_tension_lb` at draft time — 250 feet per minute is the base speed at which the SKU's stated minimum applies, and each additional foot per minute adds six hundredths of a pound. Note that the term is not floored: a run chosen below 250 feet per minute therefore requires *less* tension than the SKU's nominal minimum. The chosen `paper_tension_lb` is then valid if and only if it is greater than or equal to `required_paper_tension_lb` and less than or equal to the SKU's `paper_tension_max_lb`; both comparisons are inclusive, so landing exactly on either bound is acceptable. A value outside that window is `ERR_PAPER_TENSION_OUT_OF_RANGE`.

The kiln check tests whether the chosen dwell can physically remove the water the slurry puts in. The slurry water load is `target_board_weight_lb_per_msf` multiplied by `slurry_water_stucco_ratio`, rounded half-up to two decimals. Dryer efficiency is tiered by dwell, with each tier's upper edge inclusive: a dwell of 32 minutes or less runs at an efficiency of 0.72, a dwell above 32 and up to and including 45 minutes runs at 0.81, and a dwell above 45 minutes runs at 0.86. Drying capacity per MSF is that efficiency multiplied by `kiln_dwell_minutes` multiplied by 38.0 pounds of evaporation per minute per MSF, and is left unrounded. The projected retained water is the slurry water load minus that drying capacity, floored at zero so it can never go negative. `projected_exit_moisture_pct` is then that projected retained water divided by `target_board_weight_lb_per_msf`, multiplied by 100, rounded half-up to two decimals; it is stamped on the run at draft time and is entirely independent of tonnage. The profile is feasible if and only if `projected_exit_moisture_pct` is less than or equal to `kiln_exit_moisture_target_pct` plus a tolerance of 0.10 percentage points; an infeasible profile is `ERR_KILN_PROFILE_INFEASIBLE`. This is the tradeoff the scheduler is being asked to make: shortening the dwell reduces the fuel the kiln burns holding the board, but raises projected exit moisture until it breaches the tolerance.

Scheduling a draft onto the line, which advances `status` from `DRAFT` to `SCHEDULED`, is the single most heavily guarded operation in the system. Its only input is the `expected_plant_version` guard of §2.10. Beyond the version check and the posture gates already described, scheduling requires that the run be in `DRAFT` and that its calciner batch be in `CALCINING` or `COMPLETED` — a batch still `PLANNED`, `FEEDING` or `ABORTED` yields `ERR_INVALID_STATE`. When the SKU is fire-rated there is a stricter material gate: the batch's `stucco_quality_flag` must be exactly `PASS`, and `MARGINAL`, `FAIL` and `PENDING` all fail with `ERR_FIRE_RATED_STUCCO_NONCONFORMING`. Scheduling also requires that the window be clear on two independent axes: it must not intersect any maintenance outage on the same line whose `status` is `APPROVED` or `IN_PROGRESS`, judged under the closed-interval convention of §2.7, or the request fails with `ERR_OUTAGE_WINDOW_CONFLICT`; and it must not overlap any other run on the same line whose `status` is `SCHEDULED` or `RUNNING`, judged under the half-open convention, or the request fails with `ERR_LINE_WINDOW_CONFLICT`.

The capacity and reservation chain then runs in a pinned six-step order. The apparent circularity — how much board a window can hold depends on how many minutes changeover eats, which depends on which run precedes this one — is resolved exactly by following these steps in sequence, each step reading only the outputs of earlier steps.

**Step one selects the changeover predecessor.** Candidates are the runs on the same line, excluding this run itself, whose `status` is `SCHEDULED`, `RUNNING` or `COMPLETED` and whose `window_end` is at or before this run's `window_start`. Runs in `DRAFT` or `CANCELLED` are invisible to this selector. Among the candidates, the one with the latest `window_end` wins; if two tie on `window_end`, the one with the later `created_at` wins. That run's identifier is stamped as `prior_run_id`. If the candidate pool is empty, this is a cold start and `prior_run_id` stays null.

**Step two computes `changeover_minutes` from a matrix.** On a cold start the changeover is 45 minutes. Otherwise, if the predecessor produced the very same product specification, the changeover is 0 minutes. If not, and the predecessor's SKU matches this SKU on both `thickness_in` and `changeover_family`, the changeover is 20 minutes. If only `thickness_in` matches, it is 55 minutes. If only `changeover_family` matches, it is 75 minutes. If neither matches, it is 110 minutes. One adder then applies, and only when there is a predecessor: if this SKU is fire-rated and the predecessor's SKU was not, 25 minutes of purge time are added to whatever the matrix produced. Going the other way — fire-rated to non-fire-rated — carries no adder, and a cold start carries no adder either.

**Step three tests the buffer.** When there is a predecessor, `gap_minutes` is the whole number of minutes from the predecessor's `window_end` to this run's `window_start`, obtained by truncation as described in §2.5. On a cold start `gap_minutes` is null. If there is a predecessor and `gap_minutes` is strictly less than `changeover_minutes`, the schedule is refused with `ERR_CHANGEOVER_BUFFER_VIOLATION`; a gap exactly equal to the required changeover is acceptable. The consequence is that on a warm start the changeover happens in the dead time *between* windows and costs the run no production minutes at all.

**Step four computes the minutes actually available for board.** `in_window_changeover_minutes` is 45 on a cold start and 0 otherwise — a cold start is the only case where changeover is absorbed inside the run's own window. `available_minutes` is the whole number of minutes between `window_start` and `window_end`, again by truncation, less `in_window_changeover_minutes`.

**Step five caps the request against physical capacity.** The line lays down board at a rate, in MSF per minute, of `line_speed_fpm` multiplied by `board_width_in` divided by 12 and then divided by 1000, rounded half-up to six decimals — the division by twelve converts board width from inches to feet, and the division by a thousand converts square feet to thousands of square feet. `capacity_msf` is `available_minutes` multiplied by that per-minute rate, rounded half-up to three decimals. If `capacity_msf` is `0.000` or less, the window is too short to be useful once changeover is absorbed and the schedule is refused with `ERR_WINDOW_TOO_SHORT_FOR_CHANGEOVER`. Otherwise `effective_planned_msf` is the smaller of `requested_planned_msf` and `capacity_msf`; a scheduler who asks for more board than the window can produce silently gets the window's worth.

**Step six reserves stucco.** `stucco_reserved_tons` is `effective_planned_msf` multiplied by the SKU's `stucco_lb_per_msf`, divided by 2000 to convert pounds to tons, rounded half-up to three decimals. If that reservation is strictly greater than the plant's `stucco_available_tons`, the schedule is refused with `ERR_STUCCO_INSUFFICIENT`; a reservation exactly equal to what is available is accepted.

Only after all six steps succeed is the kiln energy figure stamped, using `effective_planned_msf` rather than the requested figure. The retained water per MSF is `target_board_weight_lb_per_msf` multiplied by `kiln_exit_moisture_target_pct` divided by 100, rounded half-up to two decimals; the water that must be evaporated per MSF is the slurry water load of §3.5 minus that retained figure, floored at zero. The unrounded base energy is that evaporation load multiplied by `effective_planned_msf`, multiplied by a latent heat of 1150 BTU per pound, divided by the dwell-tiered efficiency, and divided by one million to express the result in MMBtu. A speed penalty factor is one plus the excess of `line_speed_fpm` over 350 feet per minute — floored at zero, so a run at or below 350 attracts no penalty — multiplied by 0.0004, rounded half-up to four decimals. A thickness multiplier is one plus the quantity of `thickness_in` less 0.5 multiplied by 0.6, capped at 1.35; because the thinnest board is 0.375 inches, a thin-board run gets a multiplier below one, and the cap never binds at these thicknesses. A formulation adder contributes, per MSF, 0.0 MMBtu for `REGULAR`, 0.018 for `TYPE_X`, 0.026 for `TYPE_C`, 0.010 for `MOLD_RESISTANT` and 0.014 for `ABUSE_RESISTANT`, multiplied by `effective_planned_msf`. A hold term is `kiln_dwell_minutes` multiplied by 0.004 MMBtu per minute, rounded half-up to three decimals. `kiln_energy_mmbtu` is then the unrounded base energy multiplied by the thickness multiplier and by the speed penalty factor, plus the formulation adder, plus the hold term, with that whole sum rounded half-up to three decimals — the base energy and the drying capacity are the two intermediates that must be left unrounded. `kiln_energy_cost_usd` is `kiln_energy_mmbtu` multiplied by the plant's `energy_price_per_mmbtu`, rounded half-up to two decimals.

Scheduling then settles the plant. `stucco_reserved_tons` is added to the plant's `stucco_committed_tons`, `stucco_available_tons` and `production_posture` are re-derived, and the plant's `version` increments by 1. The run's own `version` increments by 1.

### 3.6. Running, Completing and Cancelling a Run

Starting a scheduled run advances `status` from `SCHEDULED` to `RUNNING` and is gated on five conditions beyond the run being in `SCHEDULED`. They are evaluated in the band order of §2.11 rather than in the order narrated here, which means the line and batch state checks come first, the posture gate second and the clock gate last. The line's `status` must be `AVAILABLE`, so a line whose outage has been approved and is therefore `MAINTENANCE_SCHEDULED`, or that is already `UNDER_MAINTENANCE`, blocks the start with `ERR_LINE_NOT_AVAILABLE`. The stucco must actually exist and be conforming: the calciner batch must have reached `COMPLETED` and its `stucco_quality_flag` must not be `FAIL`, each failure reported as `ERR_INVALID_STATE`. The plant's posture must not be `FROZEN`. And the logical clock must have reached the run's `window_start`, or the request fails with `ERR_RUN_WINDOW_NOT_STARTED` — reaching the instant exactly is sufficient. Note that starting is stricter than scheduling about the batch — scheduling accepts a batch still `CALCINING`, starting does not. The reservation stays committed across the start; only the run's `version` increments.

Completing a run advances `status` from `RUNNING` to `COMPLETED` and is where the shift's actual numbers arrive. The operator supplies `actual_msf`, the board actually produced, which must itself be zero or greater — a shift that made nothing is a legal completion; `scrap_msf`, the board scrapped at the line, which must be zero or greater and must not exceed `actual_msf` (a larger value is `ERR_INVALID_REQUEST`, screened at band 4 ahead of the run's own state check); and two defect rates in parts per million, `edge_defect_ppm` from the edge trim and `end_defect_ppm` from the end cut, each supplied as an integer of zero or greater. Completion stamps `stucco_consumed_tons` as `actual_msf` multiplied by the SKU's `stucco_lb_per_msf` divided by 2000, rounded half-up to three decimals, and `net_good_msf` as `actual_msf` less `scrap_msf`, rounded half-up to three decimals; `available_msf` is then derived from `net_good_msf` per §2.8, which at this point means it equals `net_good_msf` because no load has yet been staged. On the plant side, the run's `stucco_reserved_tons` is subtracted from `stucco_committed_tons`, `stucco_consumed_tons` is subtracted from `stucco_on_hand_tons`, `stucco_available_tons` and `production_posture` are re-derived, and the plant's `version` increments by 1. The run's `version` increments by 1.

Completion also carries an automatic quality hold. If `edge_defect_ppm` exceeds 1500 parts per million, or `end_defect_ppm` exceeds 900 parts per million, the run's `quality_state` moves from `UNTESTED` straight to `HELD` in the same request. The two ceilings are checked in a fixed order with edge first, so a run that breaches both records `held_reason` as `EDGE_DEFECT`; a run that breaches only the end-cut ceiling records `END_DEFECT`. Both comparisons are strict, so a run sitting exactly at 1500 and 900 is not held. When the hold fires, the plant's `held_run_count` increases by 1, `production_posture` is re-derived and the plant's `version` increments.

Cancelling a run is permitted from `DRAFT` or `SCHEDULED` and from nowhere else — a `RUNNING`, `COMPLETED` or already-`CANCELLED` run rejects the request with `ERR_INVALID_STATE`. It is the one mutating capability open to two roles, either a `ProductionScheduler` or a `PlantManager`, and it records a free-text `cancel_reason` that is optional and stays null when omitted. Cancelling from `DRAFT` simply sets the reason and increments the run's `version`; nothing on the plant moves, because a draft never reserved anything. Cancelling from `SCHEDULED` additionally subtracts the run's `stucco_reserved_tons` from the plant's `stucco_committed_tons`, sets the run's own `stucco_reserved_tons` to `0.000`, re-derives `stucco_available_tons` and `production_posture`, and increments the plant's `version` by 1, before incrementing the run's `version`. `COMPLETED` and `CANCELLED` are the lifecycle dimension's terminal states.

The system may also cancel a run on its own initiative. When a maintenance outage is approved on the run's line and the run's half-open window intersects the outage's closed window, a run in `DRAFT` or `SCHEDULED` is moved to `CANCELLED` with `cancel_reason` written by the server as the literal text `OUTAGE_APPROVED:` immediately followed by the approving outage's identifier. That cascade releases stucco in exactly the same way the operator-driven cancel does, and it additionally cancels every load order of the run whose `status` is `STAGED`, `HELD` or `LOADED`, each such order keeping its `cancel_reason` null since the server writes the reason only onto the run. The operator-driven cancel sweeps the same three load-order states for the same reason; in practice neither sweep ever finds anything, because a run that is still `DRAFT` or `SCHEDULED` has no `net_good_msf` for a load to draw against.

### 3.7. Board Testing, Quality Evaluation and Disposition

The quality dimension of a production run is tracked by `quality_state`, which evolves independently of `status` and takes one of six values: `UNTESTED`, `IN_TEST`, `RELEASED`, `DOWNGRADED`, `HELD` and `SCRAPPED`. A new run begins `UNTESTED`; only `SCRAPPED` is terminal. Critically, `RELEASED` is *not* terminal — released board can be held again — and the cycle `RELEASED → HELD → IN_TEST → RELEASED` is a normal, repeatable path.

A `QualityInspector` records board specimens against a completed run. Each specimen carries a `specimen_seq` of 1 or greater, unique within the run, and five measurements: `core_hardness_lbf`, `nail_pull_lbf`, `flexural_cross_lbf`, `flexural_parallel_lbf` — all zero or greater — and `exit_moisture_pct` between 0.00 and 5.00. Parallel flexural strength is recorded for the standards file and does not gate anything. Each specimen stamps `recorded_by_user_id` from the acting `X-User-ID` and `tested_at` from the logical clock. Recording is permitted only when the run's `status` is `COMPLETED` and its `quality_state` is `UNTESTED`, `IN_TEST` or `HELD`; from `RELEASED`, `DOWNGRADED` or `SCRAPPED` the request is refused with `ERR_INVALID_STATE`.

The specimen's own `result` is decided by four inclusive-threshold comparisons against the SKU's published minima and the run's own kiln target, and each failure appends an attribute to `failing_attributes` in a fixed order. If `core_hardness_lbf` is below the SKU's `core_hardness_min_lbf`, `CORE_HARDNESS` is appended. If `nail_pull_lbf` is below `nail_pull_min_lbf`, `NAIL_PULL` is appended. If `flexural_cross_lbf` is below `flexural_cross_min_lbf`, `FLEXURAL_CROSS` is appended. If `exit_moisture_pct` is above the run's `kiln_exit_moisture_target_pct` plus the 0.10-point tolerance, `EXIT_MOISTURE` is appended. All three strength comparisons fail only on a strictly lower reading, so a specimen landing exactly on a minimum passes; the moisture comparison fails only on a strictly higher reading. A specimen with an empty `failing_attributes` has `result` `PASS`; otherwise `result` is `FAIL` and `failing_attributes` lists every attribute that missed, not just the first.

Every recorded specimen recomputes three counters on the run: `specimen_count`, the number of specimens; `failing_specimen_count`, the number whose `result` is `FAIL`; and `fail_rate`, which is `failing_specimen_count` divided by `specimen_count`, rounded half-up to four decimals, and which reads `0.0000` when no specimen has been recorded. A failing specimen also writes the acting `X-User-ID` into `last_failing_test_recorded_by_user_id`, always overwriting the previous holder, because it is the *most recent* failing inspector who is barred from dispositioning.

Where the specimen lands the quality dimension depends on where that dimension already stood. From `UNTESTED`, the first specimen moves the run `UNTESTED → IN_TEST`; a further specimen while already `IN_TEST` leaves it there. From `HELD`, recording a specimen is a re-test: the run moves `HELD → IN_TEST`, `retest_count` increases by 1, and because the run is no longer held the plant's `held_run_count` decreases by 1, `production_posture` is re-derived and the plant's `version` increments by 1. Either way the run's `version` increments by 1, and no specimen row is ever deleted — a re-test adds to the evidence base rather than replacing it.

Running the quality evaluation is what branches the dimension, and it takes no input beyond the run it targets. Three entry gates apply in order. First, the run must have at least one specimen: a run whose `quality_state` is still `UNTESTED`, which is exactly the condition `specimen_count` equal to 0, is refused with `ERR_NO_BOARD_TEST_SPECIMENS` rather than with the generic invalid-state error. Second, the `quality_state` must be exactly `IN_TEST`: a run already sitting in `RELEASED`, `DOWNGRADED`, `HELD` or `SCRAPPED` is refused with `ERR_INVALID_STATE`, so the way back into an evaluation after a hold is always a fresh specimen. Third, the run must have at least three specimens; one or two yields `ERR_INSUFFICIENT_SPECIMENS`.

The run rule then decides among three outcomes, evaluated in this order over every specimen ever recorded for the run including those recorded before an earlier hold. If the SKU is fire-rated and `failing_specimen_count` is 1 or more, the outcome is `HELD` — fire-rated board tolerates no failing specimen whatsoever, regardless of how many passed. Otherwise, if `fail_rate` is exactly `0.0000`, the outcome is `RELEASED`. Otherwise, if `fail_rate` is less than or equal to 0.2500, the outcome is `DOWNGRADED`; the ceiling is inclusive, so a fail rate of exactly one specimen in four downgrades rather than holds. Otherwise the outcome is `HELD`.

The three branches carry deliberately different consequences, and each is stated in full. A `RELEASED` outcome moves the run `IN_TEST → RELEASED`, sets `saleable_grade` to `FIRST_QUALITY`, clears any `held_reason` left over from an earlier hold to null, recomputes `available_msf` from `net_good_msf`, returns every load order of the run whose `status` is `HELD` to `STAGED` with `hold_source` cleared to null, and increments the run's `version` by 1; it does not touch the plant, because a run reaching `IN_TEST` has already given its held-run slot back. A `DOWNGRADED` outcome moves the run `IN_TEST → DOWNGRADED`, sets `saleable_grade` to `SECONDS`, likewise clears `held_reason` to null, recomputes `available_msf` from `net_good_msf`, likewise returns every `HELD` load order of the run to `STAGED`, and increments the run's `version` by 1, again leaving the plant untouched. A `HELD` outcome moves the run `IN_TEST → HELD` and sets `held_reason` to `BOARD_TEST_FAIL` when any specimen failed one of the three strength attributes, and to `MOISTURE_EXCEEDANCE` when the only failures were on exit moisture; it increments the plant's `held_run_count` by 1, re-derives `production_posture`, increments the plant's `version` by 1, moves every load order of the run whose `status` is `STAGED` to `HELD` with `hold_source` set to `RUN_QUALITY_HELD`, and increments the run's `version` by 1.

The retained-sample cascade of §3.4 reaches into this dimension from outside it. A run sitting in `RELEASED` and a run sitting in `DOWNGRADED` are treated identically: when the batch supplying the run has its `stucco_quality_flag` driven to `FAIL` by a retained sample and the run's `status` is `RUNNING` or `COMPLETED`, the run moves `RELEASED → HELD` or `DOWNGRADED → HELD` respectively, `held_reason` becomes `STUCCO_NONCONFORMING`, `saleable_grade` reverts to `UNGRADED`, the plant's `held_run_count` increases by 1 with `production_posture` re-derived and the plant's `version` incremented, and every `STAGED` load order of the run moves to `HELD` with `hold_source` set to `RUN_QUALITY_HELD`. Neither branch differs from the other in any respect.

Dispositioning a held run is reserved to a `QualityManager` and is the only way out of `HELD` other than a re-test. The request supplies an `action`, which is one of `RELEASE`, `DOWNGRADE` or `SCRAP`, together with a `disposition_note` that is optional and, when supplied, is validated as a string but not persisted anywhere on the run. All three branches require the run's `quality_state` to be exactly `HELD`, else `ERR_INVALID_STATE`, and all three enforce the segregation-of-duties comparison of §2.12 against `last_failing_test_recorded_by_user_id`, else `ERR_SEGREGATION_OF_DUTIES`. All three decrement the plant's `held_run_count` by 1, re-derive `production_posture`, increment the plant's `version` by 1, and increment the run's `version` by 1.

Beyond that shared core the branches diverge, and one of them carries a precondition the others do not. A `RELEASE` disposition moves the run `HELD → RELEASED`, and it is the *only* branch that requires evidence of a re-test: `retest_count` must be 1 or more, else the request is refused with `ERR_RETEST_REQUIRED`. On success it sets `saleable_grade` to `FIRST_QUALITY`, clears `held_reason` to null, and returns every load order of the run whose `status` is `HELD` to `STAGED`. A `DOWNGRADE` disposition moves the run `HELD → DOWNGRADED` with no re-test requirement at all — a manager may downgrade held board on the original evidence. It sets `saleable_grade` to `SECONDS`, clears `held_reason` to null, and likewise returns every `HELD` load order of the run to `STAGED`. A `SCRAP` disposition moves the run `HELD → SCRAPPED`, which is terminal. It writes the run's current `net_good_msf` into `scrapped_msf`, then sets `net_good_msf` to `0.000` and `available_msf` to `0.000`, sets `saleable_grade` to `SCRAP`, clears `held_reason` to null just as the other two branches do, and cancels every load order of the run whose `status` is `STAGED`, `HELD` or `LOADED`, writing the literal text `RUN_SCRAPPED` into each one's `cancel_reason`. A load that has already shipped is untouched by a scrap.

### 3.8. Warehouse Loading, Freight Quoting and Settlement

A `ProductionScheduler` stages a load by naming the source run and the destination market and declaring a bundle configuration: `bundles_count`, at least 1, is how many bundles are planned onto the trailer, and `boards_per_bundle` is how many boards go into each. The bundle configuration is checked against the SKU: `boards_per_bundle` must be an even number, at least 2, and no greater than the SKU's `max_boards_per_bundle`. An odd value is caught as a malformed request, and so is any `bundles_count` or `boards_per_bundle` below 1, which leaves `ERR_BUNDLE_CONFIG_INVALID` reachable in practice only by an even count that exceeds the SKU's ceiling. Staging imposes no condition on the source run's `status` or `quality_state`; the volume test below is the only thing standing between a load and a run, so a load may legitimately be staged against a run that is `HELD`.

Bundle geometry is derived in a fixed sequence, each step feeding the next. `board_msf_each` is `board_length_ft` multiplied by `board_width_in`, divided by 12 to bring width into feet, then divided by 1000 to express the area in thousands of square feet, rounded half-up to six decimals. `bundle_msf` is `boards_per_bundle` multiplied by `board_msf_each`, rounded half-up to four decimals. `bundle_weight_lb` is `boards_per_bundle` multiplied by `target_board_weight_lb_per_msf` multiplied by `board_msf_each`, rounded half-up to two decimals. Two further figures depend on which bundle count is billable — `bundles_count` before the trailer is loaded, `loaded_bundles_count` afterwards: `total_msf` is the billable bundle count multiplied by `bundle_msf`, rounded half-up to three decimals, and `trailer_weight_lb` is the billable bundle count multiplied by `bundle_weight_lb`, rounded half-up to two decimals.

Two ceilings then apply. `trailer_weight_lb` may not exceed 48000 pounds — the comparison is inclusive, so a trailer at exactly 48000 pounds is legal — and a breach is `ERR_TRAILER_WEIGHT_EXCEEDED`. And `total_msf` may not exceed the source run's `available_msf`, which nets out the volume already committed to sibling loads in `STAGED`, `HELD`, `LOADED` or `SHIPPED`; a breach is `ERR_RUN_MSF_INSUFFICIENT`. A load that clears both is created in `status` `STAGED` with `hold_source` null, `backhaul` defaulting to `false`, `loaded_bundles_count` null, `overweight_fee_usd` at `0.00`, and `settled_freight_usd` and `freight_variance_usd` both null; the run's `available_msf` is recomputed to reflect the new commitment. That recomputation is the one derived-field refresh in the system that is *not* treated as a mutation of its owner: staging, loading and cancelling a load order all rewrite the source run's `available_msf` in place while leaving the run's `updated_at` and `version` exactly as they were.

Freight is computed by one routine in two variants, and the order in which it rounds is pinned because it changes the answer in cents. The market's `rate_zone` and `base_rate_per_msf` come from `distance_miles` as described in §3.1. The charge is then built up in this exact sequence: first, a per-bundle charge equal to `bundle_msf` multiplied by `base_rate_per_msf`, rounded half-up to two decimals; second, a subtotal equal to that already-rounded per-bundle charge multiplied by the billable bundle count — the rounding happens per bundle and *then* the multiplication happens, never the other way round; third, a fuel component equal to the subtotal multiplied by the market's `fuel_surcharge_pct` divided by 100, rounded half-up to two decimals; fourth, an overweight accessorial equal to the excess of `trailer_weight_lb` over 44000 pounds, floored at zero, multiplied by 0.02 dollars per pound and rounded half-up to two decimals; fifth, a backhaul credit equal to the market's `backhaul_credit_usd`; and last, the charge itself, which is the subtotal plus fuel plus the overweight accessorial less the credit, rounded half-up to two decimals, and then raised to the market's `min_charge_usd` if it falls below that floor. The floor is applied last and the floored value is never rounded again.

The **quoted** variant runs at staging and is stamped on `quoted_freight_usd`. It bills the planned `bundles_count`, and it applies neither the overweight accessorial nor the backhaul credit — both of those terms are zero in a quote. The **settled** variant runs at shipment and is stamped on `settled_freight_usd`. It bills `loaded_bundles_count`, it does apply the overweight accessorial above the 44000-pound target — note that the target is four thousand pounds below the 48000-pound hard maximum, so a perfectly legal trailer can still incur the fee — and it subtracts `backhaul_credit_usd` when and only when the load ships with `backhaul` set to `true`. The accessorial actually charged is recorded on `overweight_fee_usd`, and `freight_variance_usd` is `settled_freight_usd` less `quoted_freight_usd`, rounded half-up to two decimals; it stays null until the load has shipped. Identical board volume therefore routinely settles at a different amount than it quoted.

Recording the load advances the order `STAGED → LOADED` and supplies `loaded_bundles_count`, which must be at least 1 and no greater than the planned `bundles_count`. `total_msf` and `trailer_weight_lb` are recomputed on the loaded count, the 48000-pound ceiling is re-tested against the recomputed weight and a breach is again `ERR_TRAILER_WEIGHT_EXCEEDED`, the run's `available_msf` is recomputed, and the order's `version` increments by 1. A load that is not in `STAGED` — one held by a quality cascade, for instance — cannot be loaded and yields `ERR_INVALID_STATE`.

Shipping is reserved to a `PlantManager` and advances the order `LOADED → SHIPPED`, supplying the `backhaul` flag, which is optional and defaults to `false` when omitted. Beyond requiring the order to be in `LOADED`, shipping enforces the quality chain end to end: the source run's `quality_state` must be `RELEASED` or `DOWNGRADED`, and anything else — `UNTESTED`, `IN_TEST`, `HELD` or `SCRAPPED` — blocks the shipment with `ERR_RUN_QUALITY_NOT_RELEASED`. Shipment stamps `settled_freight_usd`, `overweight_fee_usd` and `freight_variance_usd`, and increments the order's `version`. `SHIPPED` is terminal.

Cancelling a load order is permitted from `STAGED`, `HELD` or `LOADED`, and from all three it behaves identically: a free-text `cancel_reason` is recorded — optional, and left null when omitted — the order moves to the terminal `CANCELLED` state, its `total_msf` is released so that the source run's `available_msf` increases by that amount, and the order's `version` increments by 1. From `SHIPPED` or `CANCELLED` the request is refused with `ERR_INVALID_STATE`.

The two system-driven transitions of the load lifecycle are the hold and its release, and together they make the load machine cyclic. When a source run's `quality_state` moves to `HELD` by any route — an automatic defect hold at completion, a `HELD` outcome from the quality evaluation, or the retained-sample stucco cascade — every load order of that run sitting in `STAGED` moves to `HELD` with `hold_source` set to `RUN_QUALITY_HELD`, and while held it can be neither loaded nor shipped. When the run's `quality_state` later returns to `RELEASED` or `DOWNGRADED`, whether by evaluation or by disposition, every `HELD` load order of that run returns to `STAGED` and `hold_source` is cleared to null. Both transitions increment the order's `version` by 1.

### 3.9. Maintenance Outages, Deferral and the Seasonality Gate

A `MaintenancePlanner` proposes an outage against a board line, declaring an `outage_type` of either `PLANNED` for campaign work or `EMERGENCY` for forced work, the window bounds `window_start` and `window_end`, and an optional `scope_note` describing the work, which stays null when omitted. The proposal is stamped with `proposed_by_user_id` taken from the acting `X-User-ID`, enters `status` `PROPOSED` with `deferral_count` at 0 and `approved_by_user_id`, `deferred_reason` and `close_note` all null, and immediately carries four derived figures so that the plant can see what the window would cost before anyone approves it.

Those four figures are computed as follows. `seasonality_index` is read from a fixed housing-market table by the calendar month of `window_start` in UTC: January 0.62, February 0.66, March 0.85, April 1.05, May 1.18, June 1.24, July 1.20, August 1.16, September 1.06, October 0.90, November 0.80, December 0.68. `planned_downtime_hours` is the elapsed seconds between `window_start` and `window_end` divided by 3600, rounded half-up to two decimals. `at_risk_msf` is the sum of `effective_planned_msf` over every production run on the same line whose `status` is `SCHEDULED` or `RUNNING` and whose window intersects the outage window under closed-interval semantics — that is, whose `window_start` is at or before the outage's `window_end` and whose `window_end` is at or after the outage's `window_start` — rounded half-up to three decimals. Runs in `DRAFT`, `COMPLETED` or `CANCELLED` contribute nothing. `opportunity_cost_usd` is `at_risk_msf` multiplied by the plant's `contribution_margin_per_msf`, rounded half-up to two decimals.

Approving an outage is reserved to a `PlantManager` and moves it `PROPOSED → APPROVED`. Five preconditions apply, evaluated in the band order of §2.11 rather than in the order narrated here. The outage must be in `PROPOSED`. The line's `status` must be `AVAILABLE`, else `ERR_LINE_NOT_AVAILABLE` — and because that state check sits a band ahead of the duty check, a proposer who tries to approve his own outage on a line already under maintenance is told about the line, not about the duty. The approver's `X-User-ID` must differ from `proposed_by_user_id`. No other outage on the same line whose `status` is `APPROVED` or `IN_PROGRESS` may intersect this window under closed-interval semantics, else `ERR_OUTAGE_WINDOW_CONFLICT`. And the seasonality gate must allow the window; the four derived figures are refreshed immediately before that gate runs, so a seasonality refusal leaves the refreshed `at_risk_msf` and `opportunity_cost_usd` on the outage even though nothing was approved and its `version` did not move.

The gate itself is a three-way escape hatch evaluated in order. An `EMERGENCY` outage is always allowed, whatever the month. An outage whose `deferral_count` has reached 2 is always allowed, because work that has already been pushed twice must happen. Otherwise the outage is allowed only when its `seasonality_index` is less than or equal to 0.90; the ceiling is inclusive, so October, whose index is exactly 0.90, is an allowed month, while April through September and any month above the ceiling are not. A blocked window is refused with `ERR_SEASONALITY_WINDOW_UNFAVORABLE`. In practice this means routine campaign work is confined to the November-through-March shoulder plus October, which is precisely the housing-market shape the plant is optimising against.

Approval stamps `approved_by_user_id` from the acting `X-User-ID` and refreshes `seasonality_index`, `planned_downtime_hours`, `at_risk_msf` and `opportunity_cost_usd`, then sets off a four-hop cascade. Hop one to two: the line moves `AVAILABLE → MAINTENANCE_SCHEDULED`, which is what will later block any attempt to start a run on it. Hop two to three: because the line is now `MAINTENANCE_SCHEDULED`, every production run on that line whose `status` is `DRAFT` or `SCHEDULED` and whose window intersects the outage window moves to `CANCELLED`, with the `OUTAGE_APPROVED:` reason described in §3.6. Hop three to four: each cancelled run that had been `SCHEDULED` releases its `stucco_reserved_tons` back out of the plant's `stucco_committed_tons`, which re-derives `production_posture` and increments the plant's `version`, and every load order of that run in `STAGED`, `HELD` or `LOADED` is cancelled. The outage's own `version` increments by 1, and so does the `version` of the line, of every affected run and of every affected load order.

Deferral is the alternative to approval and belongs to the planner rather than the manager. Deferring moves the outage `PROPOSED → DEFERRED`, records an optional `deferred_reason` that stays null when omitted, increases `deferral_count` by 1 and increments the outage's `version`. An outage may be deferred at most twice: a third attempt, made when `deferral_count` has already reached 2, is refused with `ERR_MAX_DEFERRALS_REACHED`. Re-proposing moves a deferred outage back `DEFERRED → PROPOSED` on a fresh `window_start` and `window_end`, which overwrite the old bounds and force `seasonality_index` and `planned_downtime_hours` — and with them `at_risk_msf` and `opportunity_cost_usd` — to be recomputed against the new window. The new window must satisfy `window_end` strictly after `window_start`, else `ERR_INVALID_WINDOW`, and that well-formedness test runs only after the outage has been confirmed `DEFERRED`. A re-proposal may also carry a replacement `scope_note`, which overwrites the old text when supplied and leaves it untouched when omitted. `deferral_count` is never reset by a re-proposal, which is what makes the deferral cycle self-limiting: after two rounds of push-and-re-propose the seasonality gate stops applying altogether and the work must be approved into whatever month it lands in.

Starting an approved outage moves it `APPROVED → IN_PROGRESS` and requires three things, tested in the band order of §2.11: the outage must be in `APPROVED`; no production run on the line may be `RUNNING`, else `ERR_RUN_ACTIVE_ON_LINE`; and only then must the logical clock have reached its `window_start`, else `ERR_OUTAGE_WINDOW_NOT_STARTED`. The line's own `status` is not re-tested here. Starting moves the line `MAINTENANCE_SCHEDULED → UNDER_MAINTENANCE`. When the outage's `outage_type` is `EMERGENCY`, starting it also re-derives the plant's `production_posture`, which the emergency condition of §2.9 forces to `FROZEN`, and increments the plant's `version` by 1; a `PLANNED` outage does not freeze the plant and leaves the plant's `updated_at` and `version` untouched. The outage's `version` increments by 1.

Closing an in-progress outage moves it `IN_PROGRESS → CLOSED`, which is terminal, and records an optional `close_note` that stays null when omitted. Closing returns the line `UNDER_MAINTENANCE → AVAILABLE`, re-derives the plant's `production_posture` — which is how an emergency freeze lifts, since the outage is no longer `IN_PROGRESS` — and increments the plant's `version` by 1 along with the outage's own. The line is then free to be scheduled again, and the whole maintenance cycle can repeat.
