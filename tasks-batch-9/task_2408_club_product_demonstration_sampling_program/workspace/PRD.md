# Club Demo Sampling API — Product Requirements Document

## 1. Introduction

Club Demonstration Services operates the in-club product demonstration and sampling programme on behalf of consumer-goods manufacturers inside a chain of warehouse clubs. A single demonstration looks simple from the aisle — a table, a demonstrator, a tray of samples — but behind it sits a booking that has to clear a manufacturer's credit standing, a club's daily calendar, a merchandising-category quota, a finite weekly pool of sample cases, a food-safety permit, a certified worker who is not already double-booked somewhere else that day, a sanitised piece of powered equipment, and a health-code sign-off. When any one of those preconditions fails on the morning of the event, somebody has to be credited, the samples have to be counted back in, and the manufacturer still expects a defensible invoice and a believable sales-lift number.

This API is the system of record for that programme. It governs the commercial booking of a demonstration and, independently, the staffing coverage of the same demonstration — two dimensions that advance under different triggers, are driven by different offices, and gate each other at exactly two points. It allocates scarce sample cases out of a per-club, per-week pool with a privileged emergency reserve behind it. It measures incremental sales against a recorded pre-demo baseline over an attribution window, in two deliberately different variants. And it bills the manufacturer per event, applies volume discounts, and offsets cancellation credits against the receivable ledger while keeping the head-office approver of a credit distinct from the head-office user who issued that event's invoice.

Every deadline, expiry, lookback and attribution window in this specification is evaluated against a server-side **logical clock**, never against wall-clock time. Reference data, bookings, staffing, logistics, measurement and billing are all exposed as one flat API surface mounted at the root path, with resources addressed by server-minted identifiers rather than by nesting depth.

## 2. Global Specifications & System-Wide Principles

This section defines the contracts that hold everywhere: authentication, the response envelope, pagination, resource identity, the logical clock, monetary precision, concurrency guards, the order in which a request is rejected, and the cross-cutting integrity rules that bind the entity graph together.

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, declaring the capacity in which it acts. Five roles are recognised, spelled exactly as follows: `ProgramAdmin`, `ClubOperations`, `Manufacturer`, `StaffingCoordinator`, and `Demonstrator`. A request that omits either header, or whose `X-User-Role` is not one of those five strings, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). A request whose role is syntactically valid but is not listed among the authorised roles for the endpoint it targets is rejected with `ERR_ROLE_NOT_PERMITTED` (HTTP 403). The same `ERR_ROLE_NOT_PERMITTED` code covers the finer-grained case where a role reaches a multi-action endpoint it is generally allowed to call but requests an action reserved for a different office.

Two of the five roles are operator identities and three are entity-backed identities, and the distinction determines exactly how ownership is enforced.

- When `X-User-Role` is `Manufacturer`, `X-User-ID` is the `id` of the acting `Manufacturer` row; ownership checks on any resource that references a `Manufacturer` compare the resource's `manufacturer_id` — or, for a demo event's descendants, the owning event's `manufacturer_id` — to `X-User-ID`.
- When `X-User-Role` is `ClubOperations`, `X-User-ID` is the `id` of the acting `Club` row; ownership checks compare the resource's `club_id`, or the hosting event's `club_id`, to `X-User-ID`.
- When `X-User-Role` is `Demonstrator`, `X-User-ID` is the `id` of the acting `Demonstrator` row; ownership checks on an assignment compare the assignment's `demonstrator_id` to `X-User-ID`.
- When `X-User-Role` is `ProgramAdmin`, `X-User-ID` is an opaque head-office operator identifier not tied to any persisted entity. The server may record it — it is stamped into `issued_by_user_id` when an invoice is issued and into `approved_by_user_id` when a cancellation credit is decided — but it is never compared to any entity's `id`.
- When `X-User-Role` is `StaffingCoordinator`, `X-User-ID` is likewise an opaque field-staffing operator identifier not tied to any persisted entity, and the server does not compare it to any entity's `id`.

An entity-backed role that acts on a resource it does not own is rejected with `ERR_RESOURCE_OWNERSHIP` (HTTP 403): a `Manufacturer` touching another vendor's event, a `ClubOperations` principal touching another club's event, a `Demonstrator` touching another worker's assignment. `ProgramAdmin` may act on any resource in the system, subject to one deliberate exception — the segregation-of-duties rule described in §2.10, which forbids the same `X-User-ID` from both issuing an event's invoice and approving that event's cancellation credit, and which surfaces as `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints accept two query parameters. `limit` caps the number of items returned; it defaults to 10, may not be smaller than 1, and may not be larger than 100. `offset` is the number of items to skip; it defaults to 0 and may not be negative. A `limit` outside the inclusive range from 1 to 100, a negative `offset`, or a non-integer value for either is rejected with `ERR_VALIDATION` (HTTP 400).

Unless a specific endpoint states otherwise, list results are ordered by `created_at` ascending. There is exactly one documented exception: an event's sales-lift measurements are returned newest first, ordered by `created_at` descending, because the most recently posted measurement is the operative one.

Every list response includes `limit`, `offset`, `total_count` and `has_more` inside the envelope's `meta` object, where `total_count` is the number of rows matching the filters before the window is applied and `has_more` states whether any rows remain beyond the window.

### 2.4. Resource Identity, Audit Stamps and the Append-Only Measurement Ledger

Almost every resource in this system carries the same four system-managed properties:

- `id` (string): a server-minted UUID. It carries no type prefix and no embedded semantics; clients never supply it.
- `created_at` (string): an ISO 8601 timestamp in UTC with three fractional digits, recording the logical-clock instant at which the row was inserted.
- `updated_at` (string): an ISO 8601 UTC timestamp, likewise with three fractional digits, refreshed on every mutation of the row — including mutations the server performs on its own initiative to keep a derived field consistent.
- `version` (integer): a monotonically increasing counter that begins at 1 on creation and increments by exactly 1 on every mutation of the row, including server-initiated recomputation of derived fields.

The manufacturers, clubs, products, club-product baselines, demo events, demonstrators, food-safety certifications, event assignments, equipment units, equipment reservations, sample shipments, sample reconciliations, event invoices and cancellation credits all carry all four.

`SalesLiftMeasurement` is the single deliberate exception. It is an **append-only ledger**: a measurement row declares only `id` and `created_at`, and carries neither `updated_at` nor `version`. There is no update operation for a measurement anywhere in this API. A correction is expressed by posting a new measurement row, which supersedes the earlier one of the same variant; the earlier row is retained with its original figures intact.

### 2.5. The Logical Clock and the Demonstration Day Calendar

Time in this system is a server-controlled value, not a reading of the host machine's wall clock. Until an operator sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`, and it must never fall back to real time. `POST /_clock/set_current_utc` is a `ProgramAdmin`-only test-driving capability that moves the clock to the instant supplied as `to_iso8601` and returns the new value as `current_utc`. Moving the clock recomputes every certificate's `cert_status` against the new date, but it never retroactively fires a state transition: an event whose date has passed does not self-complete, and an assignment whose shift has ended does not self-close.

A second `ProgramAdmin`-only test-driving capability, `POST /_inject/assignment-history`, seeds historical assignment rows for one worker without replaying the booking workflow. It takes a `demonstrator_id`, a `demo_event_id` to hang the rows from, and an `entries` array whose members each supply `scheduled_start_utc`, `scheduled_end_utc`, `assignment_status` and `role`, optionally with `check_in_at` and `check_out_at`. One assignment row is inserted per entry with the supplied status, and `hours_worked`, `billable_hours` and `late_check_in` are computed from the supplied stamps. This capability deliberately bypasses the certification, overlap and cap gates; it recomputes the worker's `reliability_score_rolling_90`, `reliability_score_program_to_date`, `no_show_strike_count` and `completed_event_count`, but it does not touch any event's `staffing_status` and it never creates a cancellation credit.

Calendar dates — `event_date`, `health_permit_expires_on`, `issued_on`, `expires_on`, `baseline_week_start_date`, `window_start_date`, `window_end_date` — are plain `YYYY-MM-DD` strings. Instants are ISO 8601 UTC. A malformed date or instant is rejected with `ERR_VALIDATION`.

Each demonstration occupies a fixed four-hour window in UTC, selected purely by its `day_part`; the club's local timezone is irrelevant because the window is expressed directly in UTC. A `MORNING` demo runs from 09:00Z to 13:00Z, a `MIDDAY` demo from 12:00Z to 16:00Z, and an `AFTERNOON` demo from 15:00Z to 19:00Z, all on the event's `event_date`. Those two instants are stored as `event_window_start_utc` and `event_window_end_utc`; in every case the end instant is the start instant plus four hours.

The demonstrator's shift is that window padded asymmetrically. Setup begins 45 minutes before the window opens, giving the assignment's `scheduled_start_utc`, and teardown runs for 75 minutes after the window closes, giving `scheduled_end_utc`. Because the teardown pad is deliberately half an hour longer than the setup pad, the three shifts are `MORNING` from 08:15Z to 14:15Z, `MIDDAY` from 11:15Z to 17:15Z, and `AFTERNOON` from 14:15Z to 20:15Z — so a `MORNING` shift ends at exactly the instant an `AFTERNOON` shift on the same date begins. That coincidence is not an accident, and §3.4 and §3.5 explain why the demonstrator resource and the equipment resource disagree about whether it constitutes a clash.

All date arithmetic in this specification is in whole days and all instant arithmetic is in whole minutes.

### 2.6. Money, Counts and Rounding Discipline

Every monetary amount in this system is an integer number of cents. There are no decimal currency fields anywhere: `credit_limit_cents`, `unit_cost_cents`, `hourly_rate_cents`, `baseline_unit_price_cents`, `base_fee_cents`, `addon_fee_cents`, `staffing_fee_cents`, `sample_handling_fee_cents`, `subtotal_cents`, `discount_cents`, `credit_applied_cents`, `total_due_cents`, `write_off_cost_cents`, `incremental_revenue_cents`, `gross_base_cents`, `prior_applied_cents`, `billable_base_cents`, `credit_amount_cents`, `outstanding_balance_cents` and `credit_note_balance_cents` are all whole cents.

Wherever a monetary result is produced by multiplication, the product is rounded to whole cents using the round-half-up method: a fractional part of exactly one half rounds away from zero. Wherever a monetary result is produced only by adding or subtracting values that are already whole cents, no rounding is applied and none is needed.

One ordering rule governs the invoice and is normative rather than advisory: **each line is rounded to whole cents before it enters any sum, and the sums themselves are never rounded again**. Round per line, then add — not add, then round. §3.9 spells out the line inventory this applies to.

Non-monetary decimals are held to two decimal places, also round-half-up. That covers `hours_worked`, `billable_hours`, `reliability_score_rolling_90`, `reliability_score_program_to_date`, `variance_pct`, `baseline_units_expected`, `cannibalization_units`, `lift_units` and `lift_pct`. Reliability scores are additionally clamped into the inclusive range from 0.00 to 100.00. Case counts, unit counts, day counts and event counts are integers and are never rounded: `requested_sample_cases`, `allocated_sample_cases`, `pool_cases_used`, `reserve_cases_used`, `cases_shipped`, `cases_received`, `short_cases`, `cases_delivered`, `units_per_case`, `units_delivered`, `units_sampled`, `units_wasted`, `units_returned`, `variance_units`, `units_sold_in_window`, `attribution_days`, `attribution_window_days`, `notice_hours`, `monthly_completed_event_count`, `restatement_count`, `no_show_strike_count`, `completed_event_count` and `buffer_minutes` are all integer-valued. The percentage-shaped multipliers `volume_discount_pct`, `notice_tier_pct` and `reason_multiplier` are stored as decimal fractions of one, not as whole-number percentages.

### 2.7. Stale Event Version Guards

Two write operations hang a new financial or analytical artefact off a demo event whose surrounding state may have moved. Both are guarded by an optimistic-concurrency check on the parent event's `version`.

Posting a sales-lift measurement — the operation described in §3.8 — requires the request body to carry `expected_demo_event_version`, a non-optional integer holding the `version` of the parent `DemoEvent` as the client last observed it. If that value does not equal the event's current `version`, the request is rejected with `ERR_STALE_EVENT_VERSION` (HTTP 412) and nothing is written. This matters because a newly posted measurement of a given variant legitimately retires the previous measurement of the same variant; a client working from a stale view of the event would silently supersede a measurement it never saw, and the guard turns that into a deterministic refusal instead.

Creating an event invoice — the operation described in §3.9 — likewise requires `expected_demo_event_version` carrying the client's last observed `version` of the parent `DemoEvent`, and a mismatch against the event's current `version` is rejected with `ERR_STALE_EVENT_VERSION` (HTTP 412). A fresh draft invoice legitimately supersedes a previously voided one, and the invoice snapshots `credit_terms_days` together with the entire line-item set from the event's state at that moment, so a client billing from a retired view of the event would produce figures nobody can reconcile.

Those two operations are the only ones in this API that take a version field. No other create, update, transition, receipt, decision or write-off accepts `expected_demo_event_version`, and none of them performs a version comparison.

### 2.8. The Rejection Ladder

Requests are validated in a fixed global order, and the first failing rung determines the response. Where several rules could reject the same request, the earlier rung wins and the later ones are never reached — so a caller with a bad role never learns whether the body was also malformed, and a mid-flight capacity conflict never masks a missing header. The ladder, in order, is:

1. **Authentication.** `X-User-ID` and `X-User-Role` present, and the role one of the five declared names — otherwise `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. **Endpoint role.** The acting role appears in the endpoint's authorised-role list in §4 — otherwise `ERR_ROLE_NOT_PERMITTED` (403). Applies to every endpoint.
3. **Action role.** On the two multi-action transition endpoints — the demo-event transition endpoint and the assignment transition endpoint — the role must be permitted to perform the specific requested `action`. `SUBMIT`, and `CANCEL` from `DRAFT` or `SUBMITTED`, require `Manufacturer` or `ProgramAdmin`. `APPROVE`, `REJECT`, `REVOKE_APPROVAL` and `CLOSE_OUT` require `ClubOperations` or `ProgramAdmin`. `CONFIRM`, `CHECK_IN` and `CHECK_OUT` require `Demonstrator` or `ProgramAdmin`. `NO_SHOW` and `RELEASE` require `StaffingCoordinator` or `ProgramAdmin`. A mismatch is `ERR_ROLE_NOT_PERMITTED` (403).
4. **Body schema.** Every required field present, every enum member legal, every numeric range respected, every date and instant well formed — otherwise `ERR_VALIDATION` (400). Applies to every endpoint. The ranges are: `requested_sample_cases` from 1 through 40 inclusive; `attribution_window_days` from 3 through 28 inclusive; `daily_event_capacity` from 1 through 12 inclusive; `food_station_count` from 0 through 8 inclusive; `max_weekly_events` from 1 through 14 inclusive; `cases_shipped` from 1 through 40 inclusive; `credit_limit_cents`, `unit_cost_cents`, `weekly_sample_case_pool`, `emergency_reserve_cases`, `baseline_weekly_units`, `baseline_unit_price_cents`, `units_sampled`, `units_wasted`, `units_returned` and `units_sold_in_window` all at least 0; `samples_per_case` and `hourly_rate_cents` at least 1; `credit_terms_days` one of 15, 30, 45 or 60; `addon_services` members drawn from the legal set, free of duplicates, and no more than five in total; `window_end_utc` strictly later than `window_start_utc`; `expires_on` strictly later than `issued_on`.
5. **Pagination bounds.** On every list endpoint that accepts `limit` and `offset`, `limit` must be an integer from 1 through 100 and `offset` an integer of at least 0 — otherwise `ERR_VALIDATION` (400).
6. **Path resolution.** Each identifier in the URL path is resolved left to right, and the first one that does not resolve determines the 404. A request for a certificate under a non-existent demonstrator fails on the demonstrator, before the certificate is ever looked for. The 404 family is: `ERR_MANUFACTURER_NOT_FOUND`, `ERR_CLUB_NOT_FOUND`, `ERR_PRODUCT_NOT_FOUND`, `ERR_DEMO_EVENT_NOT_FOUND`, `ERR_DEMONSTRATOR_NOT_FOUND`, `ERR_ASSIGNMENT_NOT_FOUND`, `ERR_INVOICE_NOT_FOUND`, and `ERR_RESOURCE_NOT_FOUND` for every other resource type — equipment units, equipment reservations, sample shipments, sample reconciliations, cancellation credits, club-product baselines and certifications.
7. **Body reference resolution.** Each foreign-key identifier in the request body is resolved in the order the endpoint declares its inputs. Booking a demo event, for instance, resolves `manufacturer_id` first, then `club_id`, then `product_id`, so a request naming a bad manufacturer and a bad product reports the manufacturer. This rung guards demo-event creation, product creation, baseline creation, demonstrator creation, equipment-unit creation, equipment-reservation creation, assignment creation, and the assignment-history injection capability, and it uses whichever member of the 404 family matches the unresolved reference.
8. **Ownership.** For the three entity-backed roles, the acting `X-User-ID` must own the target, as defined in §2.1 — otherwise `ERR_RESOURCE_OWNERSHIP` (403). Applies to every write endpoint whose authorised roles include `Manufacturer`, `ClubOperations` or `Demonstrator`.
9. **Transition legality.** The target resource's current state must be a declared source state of the requested transition — otherwise `ERR_INVALID_STATE` (409). This catches a second cancellation of an already cancelled event, a confirmation of an already confirmed assignment, an issue of an already issued invoice, a decision on an already decided credit, an activation of a released reservation, a receipt against an already received shipment, and a write-off against a balanced reconciliation. Applies to every transition endpoint, the shipment receipt endpoint, the write-off endpoint and the credit decision endpoint.
10. **Draft-only revision.** A demo event may only be patched while its `booking_status` is `DRAFT`; any other booking state yields `ERR_INVALID_STATE` (409).
11. **Execution readiness.** `CLOSE_OUT` requires the event's `staffing_status` to be `EXECUTED` and every assignment on the event to have reached `COMPLETED`, `NO_SHOW` or `RELEASED` — otherwise `ERR_EVENT_NOT_EXECUTED` (409).
12. **Completion readiness.** Invoice creation and reconciliation filing both require the event's `booking_status` to be `COMPLETED` — otherwise `ERR_EVENT_NOT_COMPLETED` (409).
13. **Invoice singleton.** At most one invoice per event may sit in `DRAFT`, `ISSUED` or `PAID`; a second creation attempt while such an invoice exists is `ERR_INVOICE_ALREADY_EXISTS` (409).
14. **Stale parent version.** On the two operations described in §2.7, `expected_demo_event_version` must equal the event's current `version` — otherwise `ERR_STALE_EVENT_VERSION` (412).
15. **Health permit.** Approving a `FOOD_SAMPLING` event requires the club's `health_permit_expires_on` to be on or after the event's `event_date` — otherwise `ERR_CLUB_HEALTH_PERMIT_EXPIRED` (422).
16. **Worker availability.** Creating an assignment requires the demonstrator's `employment_status` to be `ACTIVE` — otherwise `ERR_DEMONSTRATOR_NOT_ACTIVE` (422).
17. **Food-handler certification.** Creating an assignment on a `FOOD_SAMPLING` event requires the demonstrator to hold a certification whose `cert_type` is `FOOD_HANDLER`, whose `revoked_at` is unset, and whose `expires_on` is on or after the event's `event_date` — otherwise `ERR_FOOD_CERT_INVALID` (422).
18. **Specialty certification.** When the demonstrated product has `requires_heat_equipment` set, the demonstrator must additionally hold a `HEAT_EQUIPMENT` certification, and when the product has `allergen_flag` set, an `ALLERGEN_AWARENESS` certification — each judged valid by the same test as rung 17. A missing one is `ERR_SPECIALTY_CERT_MISSING` (422).
19. **Equipment sanitation.** Activating a reservation requires the unit's `sanitation_status` to be `SANITIZED`; checking in to a `FOOD_SAMPLING` event requires the event's active reservation's unit to be `IN_USE`. Either failure is `ERR_EQUIPMENT_NOT_SANITIZED` (422).
20. **Product ownership.** The demonstrated product's `manufacturer_id` must equal the event's `manufacturer_id`, checked both when the event is booked and when its booking dimension is advanced — otherwise `ERR_PRODUCT_MANUFACTURER_MISMATCH` (422).
21. **Home club.** The demonstrator's `home_club_id` must equal the event's `club_id` unless the assignment request sets `travel_authorized` to true — otherwise `ERR_DEMONSTRATOR_CLUB_MISMATCH` (422).
22. **Equipment locality.** The reserved unit's `club_id` must equal the event's `club_id` — otherwise `ERR_EQUIPMENT_CLUB_MISMATCH` (422).
23. **Baseline presence.** Posting a lift measurement requires a baseline row for the event's club and product pairing — otherwise `ERR_BASELINE_MISSING` (422).
24. **Booking lead time.** `SUBMIT` requires the event's `event_date` to be at least 7 days after the logical clock's UTC date — otherwise `ERR_BOOKING_LEAD_TIME_TOO_SHORT` (422).
25. **Booking horizon.** `SUBMIT` requires the event's `event_date` to be no more than 120 days after the logical clock's UTC date — otherwise `ERR_BOOKING_HORIZON_EXCEEDED` (422).
26. **Reservation coverage.** A reservation's `window_start_utc` must be at or before 45 minutes ahead of the event's `event_window_start_utc`, and its `window_end_utc` at or after the event's `event_window_end_utc` — otherwise `ERR_RESERVATION_WINDOW_INSUFFICIENT` (422).
27. **Equipment clash.** The requested reservation window must not collide with any `HELD` or `ACTIVE` reservation on the same unit under the buffered geometry of §3.5 — otherwise `ERR_EQUIPMENT_WINDOW_CONFLICT` (409).
28. **Demonstrator clash.** The new shift must not touch or overlap any `ASSIGNED`, `CONFIRMED` or `CHECKED_IN` shift of the same demonstrator under the closed geometry of §3.4 — otherwise `ERR_DEMONSTRATOR_DOUBLE_BOOKED` (409).
29. **Attendance instant.** The instant recorded by a check-in or check-out — `occurred_at_utc` when the caller supplies it, the logical clock otherwise — must be at or before the logical clock's current instant; a check-in instant must also fall within the closed interval beginning 60 minutes before `scheduled_start_utc` and ending at `scheduled_end_utc`; a check-out instant must be strictly later than `check_in_at`. Any violation is `ERR_CHECK_IN_WINDOW_INVALID` (422).
30. **No-show earliest.** Declaring a no-show requires the logical clock to have reached or passed 15 minutes after `scheduled_start_utc` — otherwise `ERR_NO_SHOW_TOO_EARLY` (422).
31. **Club operating state.** `APPROVE` requires the hosting club's `club_status` to be `OPEN`, or `RESTRICTED` together with an `event_type` of `NON_FOOD_DEMO`. A `CLOSED` club blocks every approval; a `RESTRICTED` club blocks `FOOD_SAMPLING` approvals only. Either refusal is `ERR_CLUB_NOT_OPEN` (409).
32. **Day capacity.** The count of events at the same club on the same `event_date` whose `booking_status` is `CONFIRMED` or `COMPLETED` must be strictly below the club's `daily_event_capacity` — otherwise `ERR_CLUB_DAY_CAPACITY_FULL` (409).
33. **Food station capacity.** For a `FOOD_SAMPLING` event, the count of same-club same-date `FOOD_SAMPLING` events in `CONFIRMED` or `COMPLETED` must be strictly below the club's `food_station_count` — otherwise `ERR_FOOD_STATION_UNAVAILABLE` (409).
34. **Category calendar.** The count of same-club same-date `CONFIRMED` or `COMPLETED` events whose product shares this product's `category` must be strictly below 2 — otherwise `ERR_CATEGORY_CALENDAR_CONFLICT` (409).
35. **Worker daily cap.** The demonstrator's count of same-date assignments in `ASSIGNED`, `CONFIRMED`, `CHECKED_IN` or `COMPLETED` must be strictly below 2 — otherwise `ERR_DEMONSTRATOR_DAILY_CAP_EXCEEDED` (409).
36. **Worker weekly cap.** The demonstrator's count of same-ISO-week assignments in those four statuses must be strictly below that demonstrator's `max_weekly_events` — otherwise `ERR_DEMONSTRATOR_WEEKLY_CAP_EXCEEDED` (409).
37. **Single lead.** An event may hold at most one assignment whose `role` is `LEAD` and whose `assignment_status` is `ASSIGNED`, `CONFIRMED`, `CHECKED_IN` or `COMPLETED` — a second is `ERR_LEAD_ALREADY_ASSIGNED` (409).
38. **Uniqueness.** `club_number` is unique across all clubs; `sku` is unique within one `manufacturer_id`; `asset_tag` is unique within one `club_id`; a baseline is unique per club-and-product pairing; and at most one reconciliation may exist per event. A collision on club creation, product creation, equipment-unit creation, baseline creation or reconciliation filing is `ERR_DUPLICATE_RESOURCE` (409).
39. **Product flag coherence.** A product may only set `requires_heat_equipment` when `requires_food_handling` is also set — otherwise `ERR_PRODUCT_FLAG_INCONSISTENT` (422).
40. **Suspension.** The manufacturer's `account_status` must not be `SUSPENDED` when an event is booked, when the booking dimension is advanced, or when an invoice is advanced — otherwise `ERR_MANUFACTURER_SUSPENDED` (402).
41. **Credit hold.** `SUBMIT` and `APPROVE` both require the manufacturer's `account_status` to be exactly `ACTIVE`; an account on `HOLD` may still edit drafts but may not advance a booking, and the refusal is `ERR_MANUFACTURER_ON_CREDIT_HOLD` (402).
42. **Sample availability.** The allocation waterfall of §3.3 must yield at least 1 case — otherwise `ERR_SAMPLE_POOL_EXHAUSTED` (409).
43. **Food-sampling minimum.** For a `FOOD_SAMPLING` event, the waterfall must yield at least 2 cases — otherwise `ERR_SAMPLE_ALLOCATION_BELOW_MINIMUM` (422).
44. **Receipt bound.** A load's `cases_received` may not exceed its `cases_shipped` — otherwise `ERR_RECEIVED_EXCEEDS_SHIPPED` (422).
45. **Samples on site.** Closing out a `FOOD_SAMPLING` event requires the total `cases_received` across that event's shipments in `DELIVERED` or `SHORT` to be at least 1 — otherwise `ERR_SAMPLES_NOT_RECEIVED` (409).
46. **Reconciliation resolved.** Issuing an invoice requires the event's reconciliation to be in `BALANCED` or `WRITTEN_OFF`, and posting a `FINAL` lift measurement requires a reconciliation row to exist at all. Either failure is `ERR_RECONCILIATION_UNRESOLVED` (409).
47. **Payment exactness.** Recording a payment requires the supplied `amount_cents` to equal the invoice's `total_due_cents` exactly — otherwise `ERR_PAYMENT_AMOUNT_MISMATCH` (422).
48. **Segregation of duties.** When an invoice for the credit's event sits in `ISSUED` or `PAID`, the `X-User-ID` deciding that credit must differ from that invoice's `issued_by_user_id` — otherwise `ERR_SEGREGATION_OF_DUTIES` (403).

### 2.9. Two Independent Event Dimensions and Cascade Propagation

A demo event carries two state fields on the same row, and they are genuinely independent. `booking_status` is the commercial dimension, moving through `DRAFT`, `SUBMITTED`, `CONFIRMED`, and then either `COMPLETED` or `CANCELLED`; it is advanced only by the event's own transition action. `staffing_status` is the coverage dimension, moving through `UNSTAFFED`, `PARTIALLY_STAFFED`, `FULLY_STAFFED`, `EXECUTED` and `CLOSED_OUT`; it is advanced by assignment inserts, by assignment transitions, and by close-out. The two dimensions gate each other at exactly two points: an assignment may only be created while `booking_status` is `CONFIRMED`, and `CLOSE_OUT` may only run while `staffing_status` is `EXECUTED`.

Both dimensions contain cycles by design. The booking dimension re-enters `DRAFT` when a club rejects a submission, and re-enters `SUBMITTED` when a club revokes an approval, so `DRAFT → SUBMITTED → DRAFT → SUBMITTED → CONFIRMED → SUBMITTED → CONFIRMED` is a legal history. The coverage dimension re-enters `FULLY_STAFFED` after a downgrade, so `FULLY_STAFFED → PARTIALLY_STAFFED → FULLY_STAFFED` is a legal history. An invoice contains a third cycle, `DRAFT → ISSUED → VOID → DRAFT`, and may be re-issued from there without limit.

Several fields on the event and the manufacturer are **denormalised mirrors**: they hold no independent truth and are recomputed from their sources on every mutation that touches those sources. `settlement_status` mirrors the money position of the event: it reads `PAID` when an invoice for the event sits in `PAID`; otherwise `INVOICED` when one sits in `ISSUED`; otherwise `CREDITED` when no such invoice exists but at least one cancellation credit on the event has reached `APPLIED`; otherwise `UNBILLED`. It is recomputed on every invoice or credit mutation touching the event. `required_support_count` mirrors the sample allocation, and is recomputed whenever `allocated_sample_cases` changes. `outstanding_balance_cents` and `credit_note_balance_cents` mirror the manufacturer's ledger and are described in §3.9. Recomputing a mirror is a mutation of its owning row: it refreshes that row's `updated_at` and increments that row's `version` by 1, exactly as a client-driven change would.

Cascades in this system are multi-hop and must be applied in full. A single request routinely mutates an event, its assignments, the demonstrators behind those assignments, other events those demonstrators were booked onto, the equipment units held for the event, an invoice, and the manufacturer's account standing — each hop incrementing the `version` of the row it touches. The §3 narratives state each cascade hop explicitly at the point it fires, and the implementation must perform all of them; a cascade that stops after its first hop leaves the graph inconsistent.

Two compensating invariants are guaranteed and are worth stating up front. First, sample-case conservation: because only events in `CONFIRMED` or `COMPLETED` consume the club-week pool, revoking an approval or cancelling a confirmed booking returns the pool remaining to exactly its pre-approval value, with no drift. Second, receivable conservation: a manufacturer's `outstanding_balance_cents` is at every instant exactly the sum of `total_due_cents` over that manufacturer's invoices in `ISSUED`, so issuing an invoice and then voiding it returns the field to its exact pre-issue integer value.

### 2.10. Health-Code Governance and Segregation of Duties

Health-code compliance is enforced at three separate points rather than once. A club holds a `health_permit_expires_on` date, and a `FOOD_SAMPLING` approval requires that date to be on or after the event's `event_date`; the boundary is inclusive, so a permit expiring on the day of the demo is still good for that demo. Every demonstrator assigned to a `FOOD_SAMPLING` event must hold a valid food-handler certificate, with heat-equipment and allergen-awareness certificates required on top when the product demands them. And every powered or refrigerated unit tracks a sanitation state that must read `SANITIZED` before it can be activated onto an event and `IN_USE` at the moment the lead demonstrator checks in.

Segregation of duties applies to exactly one pairing. `ProgramAdmin` is a single role that both issues invoices and decides cancellation credits, but the same human must not do both for one event. Concretely: when an invoice for the credit's event is in `ISSUED` or `PAID`, the `X-User-ID` on the credit decision must differ from the `issued_by_user_id` recorded on that invoice, and a match is refused with `ERR_SEGREGATION_OF_DUTIES`. The check does not fire when the event's only invoice is still in `DRAFT` or has been voided, because in those cases no `issued_by_user_id` is recorded — voiding an invoice clears that stamp back to unset.

## 3. Business Logic & Workflows

### 3.1. Programme Reference Data and Manufacturer Account Standing

Nothing can be booked until head office has registered the four kinds of reference data the programme runs on: the vendors who pay for demonstrations, the clubs that host them, the SKUs that get demonstrated, and the pre-demo sales baselines against which lift is later measured.

Registering a vendor captures its `legal_name` — the registered name that will appear on every per-event invoice, non-empty and no longer than 160 characters — together with a `billing_email` that must contain an at-sign, a `program_tier` of `PLATINUM`, `GOLD` or `STANDARD`, a `credit_limit_cents` of at least zero, and `credit_terms_days` chosen from 15, 30, 45 or 60 days. The tier does double duty: it seeds the invoice volume discount and it is the sole gate on the emergency sample reserve. A newly registered vendor starts with `account_status` set to `ACTIVE`, and both ledger mirrors — `outstanding_balance_cents` and `credit_note_balance_cents` — at zero. Head-office maintenance may later revise `account_status`, `credit_limit_cents`, `credit_terms_days` or `billing_email`; changing the credit limit re-evaluates the automatic credit-standing transition described in §3.9 immediately, because raising a limit above a vendor's current exposure should release a hold without waiting for the next invoice event.

The three account states are not interchangeable. `ACTIVE` is the only state that permits a booking to advance: both `SUBMIT` and `APPROVE` require it. `HOLD` still permits draft editing but blocks both of those advances, and it is the state the system moves an account into on its own when exposure passes the credit limit. `SUSPENDED` is the hardest state — it blocks event creation outright as well as every booking advance and every invoice advance — and it is only ever set or cleared by head-office maintenance, never by an automatic transition.

A club is registered with a `club_number` that must be unique across the whole chain and must read as the letter C followed by exactly four digits, a display `name`, a `region_code` used only for reporting and never as an input to any selector or ranking, a `club_tier` of `FLAGSHIP`, `STANDARD` or `SATELLITE` that feeds the invoice base-fee multiplier, a `daily_event_capacity` from 1 through 12 that caps how many demonstrations may be live at that site on one date, a `food_station_count` from 0 through 8 counting the health-code-approved sampling stations, and a `health_permit_expires_on` date from the local health department. A new club opens with `club_status` set to `OPEN`. Club maintenance may revise `club_status`, `daily_event_capacity`, `food_station_count` and `health_permit_expires_on`. `OPEN` permits every approval; `RESTRICTED` blocks approval of `FOOD_SAMPLING` events while still allowing `NON_FOOD_DEMO` ones; and `CLOSED` blocks every approval and additionally triggers the mass-cancellation cascade set out at the end of §3.3.

A demonstrable SKU is registered against its owning vendor through a payload carrying `manufacturer_id`, a `sku` string that must be unique within that one vendor, a display `name`, and a `category` drawn from `BAKERY`, `DAIRY`, `FROZEN`, `BEVERAGE`, `SNACK`, `HOUSEHOLD`, `ELECTRONICS` or `APPAREL`. Three booleans describe how the demo must be run: `requires_food_handling` is true when samples are consumed on site, `requires_heat_equipment` is true when a powered cooking unit is needed, and `allergen_flag` is true when the product carries a top-nine allergen. `allergen_flag` defaults to false when omitted. `requires_heat_equipment` may only be true when `requires_food_handling` is also true — a heat-equipment demo with no food handling is incoherent and is refused with `ERR_PRODUCT_FLAG_INCONSISTENT`. Economics come from `unit_cost_cents`, the landed cost of one sample unit and the price at which reconciliation write-offs are valued; `samples_per_case`, at least 1, which converts shipped cases into sample units; `weekly_sample_case_pool`, the number of cases this SKU may consume per club and ISO week; and `emergency_reserve_cases`, a second pool that defaults to zero. Products may be listed with `manufacturer_id` and `category` filters.

Baselines are recorded per club and SKU pairing, one row per pairing, through a payload carrying `club_id`, `product_id`, `baseline_weekly_units` — the units the SKU sells at that club in a normal, no-demo week — `baseline_unit_price_cents` as the shelf price used to convert lift into revenue, and `baseline_week_start_date`, the Monday of the week the baseline was observed. That Monday is a reporting attribute only and is never an input to any selector. Every new baseline starts with `restatement_count` at zero. Baselines may be listed with `club_id` and `product_id` filters, and revised later; §3.8 describes what a revision does to already-posted measurements.

One computed read exposes a club-day's calendar pressure to whoever needs to negotiate for a slot. Supplied with an `event_date`, it reports the `club_id`, that `event_date`, the club's `daily_event_capacity`, the `confirmed_count` of live events on that date, the `remaining_slots` still open — which is the capacity less the confirmed count, floored at zero so it never reads negative — the `food_station_count`, the `food_confirmed_count` of live food events, and a `category_counts` object breaking the live events down by merchandising category. When the caller also supplies a `product_id`, the same read adds the club-week sample position for that SKU: the `week_start_date` of the ISO week, the SKU's `weekly_sample_case_pool`, the `pool_cases_used` already drawn, the `pool_remaining`, the SKU's `emergency_reserve_cases`, the `reserve_cases_used`, and the `reserve_remaining`.

### 3.2. Booking a Demonstration: Draft, Submission and the Revision Cycle

A vendor opens a booking by naming the three parties and the slot: a payload carrying `manufacturer_id`, `club_id`, `product_id`, an `event_date`, and a `day_part` of `MORNING`, `MIDDAY` or `AFTERNOON`, together with the `requested_sample_cases` it would like the club to stage — from 1 through 40 inclusive. Two optional inputs round out the booking. `attribution_window_days`, from 3 through 28 inclusive, sets the length of the final sales-lift attribution window and defaults to 14 when omitted. `addon_services` is an array of billable extras drawn from `EXTRA_TABLE`, `VIDEO_LOOP`, `ALLERGEN_SIGNAGE`, `PREMIUM_PLACEMENT` and `BILINGUAL_DEMONSTRATOR`, with no duplicates and no more than five members; it defaults to an empty array. Each member becomes exactly one rounded invoice line, as §3.9 explains.

Three things are derived server-side at booking time and may not be dictated by the client. `event_type` reads `FOOD_SAMPLING` when the named product has `requires_food_handling` set and `NON_FOOD_DEMO` otherwise — a client-supplied value for this field is ignored, not rejected. `event_window_start_utc` and `event_window_end_utc` are derived from `event_date` and `day_part` exactly as §2.5 specifies. And the booking opens in a known posture: `booking_status` `DRAFT`, `staffing_status` `UNSTAFFED`, `settlement_status` `UNBILLED`, and `allocated_sample_cases`, `pool_cases_used` and `reserve_cases_used` all zero, with `submitted_at`, `approved_at` and `cancellation_reason` all unset, `required_support_count` zero and `no_show_recovery_open` false.

While a booking is still in `DRAFT`, the vendor may revise `event_date`, `day_part`, `requested_sample_cases`, `attribution_window_days` and `addon_services`. Changing either `event_date` or `day_part` recomputes `event_window_start_utc` and `event_window_end_utc` from the new pair. Revision is refused with `ERR_INVALID_STATE` in every other booking state, which is what makes the draft the only mutable form of a booking.

Submitting the booking moves `booking_status` from `DRAFT` to `SUBMITTED`. Only the owning vendor or head office may do it, and it is refused unless the vendor's `account_status` is `ACTIVE`, the `event_date` is at least 7 days after the logical clock's UTC date, the `event_date` is no more than 120 days after that same date, and the named product genuinely belongs to the named vendor. On success the submission stamps `submitted_at` with the logical clock's current instant and increments the event's `version` by 1.

Club floor management reviews the submission and may push it back: rejecting a submission moves `booking_status` from `SUBMITTED` back to `DRAFT`, and requires that the acting `X-User-ID` be the hosting club. Rejection clears `submitted_at` back to unset and increments the event's `version` by 1. `DRAFT` is therefore re-enterable — the vendor revises the draft and submits again, and the pair `SUBMITTED → DRAFT → SUBMITTED` may repeat as many times as the two parties need. Both the rejection and every other booking action accept an optional free-text `reason` alongside the required `action`.

Walking away from an early booking is cheap. Cancelling from `DRAFT` moves the event straight to `CANCELLED`, sets `cancellation_reason` to `MANUFACTURER_CANCELLED_EARLY`, and increments `version` by 1 — and it creates no cancellation credit at all, because nothing was ever allocated and nothing was ever billable. Cancelling from `SUBMITTED` behaves identically: `booking_status` becomes `CANCELLED`, `cancellation_reason` becomes `MANUFACTURER_CANCELLED_EARLY`, `version` increments by 1, and no credit is created. Only the owning vendor or head office may cancel from these two states.

### 3.3. Club Approval: Calendar Competition and the Sample Case Waterfall

Approval is the single densest gate in the system, and it moves `booking_status` from `SUBMITTED` to `CONFIRMED`. It is performed by the hosting club's floor management — the acting `X-User-ID` must be the event's `club_id` — or by head office. Beyond the state and ownership requirements, approval demands all of the following, and §2.8 fixes the order in which failures are reported: the vendor's `account_status` is `ACTIVE`; the club's `club_status` is `OPEN`, or is `RESTRICTED` while the event's `event_type` is `NON_FOOD_DEMO`; the event is a `NON_FOOD_DEMO`, or the club's `health_permit_expires_on` falls on or after the `event_date`; the product still belongs to the vendor; the club-day calendar has room; and the sample waterfall yields cases.

Calendar competition is evaluated over a precise scope: the other demo events at the same club on the same `event_date` whose `booking_status` is `CONFIRMED` or `COMPLETED`. The event being approved is *not* part of that scope, because its own `booking_status` is still `SUBMITTED` while the checks run — which is why a club whose `daily_event_capacity` is 2 accepts exactly two approvals for a date and refuses the third. Three comparisons run against that scope, in exactly this order, and all three reject at capacity rather than above it. First, if the count of scoped events has already reached the club's `daily_event_capacity`, the approval is refused with `ERR_CLUB_DAY_CAPACITY_FULL`. Second, for a `FOOD_SAMPLING` event only, if the count of scoped events that are themselves `FOOD_SAMPLING` has already reached the club's `food_station_count`, the approval is refused with `ERR_FOOD_STATION_UNAVAILABLE` — a club with no approved food stations can never host a food demo. Third, if two scoped events already share this product's `category`, the approval is refused with `ERR_CATEGORY_CALENDAR_CONFLICT`; no more than two demonstrations of one merchandising category may run at a club on a single date, so a third bakery demo waits for another day even when the club still has slots and stations free.

Sample cases are then drawn through a two-bucket waterfall, and the arithmetic is worth stating step by step. The relevant bucket is a club-week bucket: take the Monday of the ISO week containing the event's `event_date`, and consider the other demo events sharing this event's `product_id` and `club_id` whose `event_date` falls on or after that Monday and strictly before the Monday plus seven days, and whose `booking_status` is `CONFIRMED` or `COMPLETED`. Sum their `pool_cases_used` to get the pool already consumed, and sum their `reserve_cases_used` to get the reserve already consumed. The first bucket's remaining capacity is the SKU's `weekly_sample_case_pool` less the pool already consumed, floored at zero; the cases drawn from it are the smaller of `requested_sample_cases` and that remaining capacity. Whatever the request still needs after the first bucket is the requested figure less what the first bucket supplied. The second bucket's remaining capacity is zero unless the vendor's `program_tier` is `PLATINUM`, in which case it is the SKU's `emergency_reserve_cases` less the reserve already consumed, floored at zero; the cases drawn from it are the smaller of the remaining need and that capacity. Those two draws are written to `pool_cases_used` and `reserve_cases_used` respectively, and their sum is written to `allocated_sample_cases`.

Two outcomes of the waterfall are fatal to the approval. If the waterfall yields zero cases in total, the approval is refused with `ERR_SAMPLE_POOL_EXHAUSTED`. If the event is a `FOOD_SAMPLING` event and the waterfall yields fewer than 2 cases, it is refused with `ERR_SAMPLE_ALLOCATION_BELOW_MINIMUM` — you cannot credibly run a tasting on one case. A partial allocation, where the waterfall supplies at least one case but fewer than requested, is perfectly acceptable for a `NON_FOOD_DEMO` event, and equally acceptable for a `FOOD_SAMPLING` event that still reaches the two-case floor. Note that only events in `CONFIRMED` or `COMPLETED` consume the pool at all: draft, submitted and cancelled events consume nothing, which is precisely what makes revocation and cancellation exact compensations.

A successful approval writes `pool_cases_used`, `reserve_cases_used` and `allocated_sample_cases`; recomputes `required_support_count`, which reads 1 when the event is a `FOOD_SAMPLING` event whose `allocated_sample_cases` has reached at least 6 cases and reads 0 in every other case; stamps `approved_at` with the logical clock's current instant; and increments the event's `version` by 1.

Approval is reversible. Revoking an approval moves `booking_status` from `CONFIRMED` back to `SUBMITTED`, and the hosting club (or head office) may do it only while `staffing_status` is `UNSTAFFED`, `PARTIALLY_STAFFED` or `FULLY_STAFFED`, and only while no shipment on the event has reached `DELIVERED` or `SHORT` — once cases are physically on the dock, the booking has passed the point of clean reversal. Revocation is a full compensation and touches six things. It resets `pool_cases_used`, `reserve_cases_used` and `allocated_sample_cases` to zero, which restores the club-week pool remaining to exactly its pre-approval value. It recomputes `required_support_count` to 0. It sets every assignment on the event whose `assignment_status` is `ASSIGNED` or `CONFIRMED` to `RELEASED`, and each such release in turn recomputes that demonstrator's `reliability_score_rolling_90`, `reliability_score_program_to_date` and `completed_event_count`. It sets every reservation on the event whose `reservation_status` is `HELD` or `ACTIVE` to `RELEASED`, and any reservation that was `ACTIVE` leaves its equipment unit's `sanitation_status` at `SOILED`. It recomputes `staffing_status`, which lands on `UNSTAFFED` once no assignment on the event remains in `ASSIGNED`, `CONFIRMED` or `CHECKED_IN`. And it clears `approved_at` back to unset. The event's `version` increments by 1. Because `CONFIRMED` is re-enterable through a further approval, the cycle `CONFIRMED → SUBMITTED → CONFIRMED` is a legal history and re-runs the waterfall from scratch.

Cancelling a confirmed booking is the expensive path, and it may be initiated by the owning vendor, by the hosting club, or by head office. When the vendor initiates it, the acting `X-User-ID` must be the event's `manufacturer_id`; when the club initiates it, the acting `X-User-ID` must be the event's `club_id`. The attribution of blame follows the actor: `cancellation_reason` is set to `CLUB_CANCELLED` when club floor management cancelled, and to `MANUFACTURER_CANCELLED_LATE` otherwise. From there the cascade runs in full. The allocation fields `pool_cases_used`, `reserve_cases_used` and `allocated_sample_cases` are all reset to zero, restoring the club-week pool remaining. Every assignment on the event in `ASSIGNED` or `CONFIRMED` is set to `RELEASED` — that is the first hop — and each of those releases then recomputes its demonstrator's `reliability_score_rolling_90` and `reliability_score_program_to_date`, which is the second hop, caused by the first. Every reservation on the event in `HELD` or `ACTIVE` is set to `RELEASED`, and any that was `ACTIVE` sets its unit's `sanitation_status` to `SOILED`. One cancellation credit is created on the event, with its `credit_reason` copied from the event's `cancellation_reason` and its `credit_status` opening at `PENDING_APPROVAL`, valued by the notice-tier arithmetic of §3.9. `staffing_status` is recomputed to `UNSTAFFED`, `settlement_status` is recomputed, and the event's `version` increments by 1.

The same cascade fires without any client action on the event when a club is closed. Setting a club's `club_status` to `CLOSED` cancels every demo event at that club whose `booking_status` is `CONFIRMED` and whose `event_date` falls on or after the logical clock's UTC date. Each of those events has its `cancellation_reason` set to `CLUB_CANCELLED`, receives the identical side-effect set as a club-initiated cancellation — including one `PENDING_APPROVAL` cancellation credit each — and has its `version` incremented by 1. Events dated before the clock date are left alone, as are events that were never confirmed. The club row's own `version` also increments by 1.

Once a booking reaches `CANCELLED`, the coverage dimension freezes. Coverage that stood at `UNSTAFFED` or `PARTIALLY_STAFFED` is first recomputed to `UNSTAFFED` and then locked; coverage that stood at `FULLY_STAFFED` moves directly to `CLOSED_OUT`, incrementing the event's `version` by 1. Both `COMPLETED` and `CANCELLED` are terminal for the booking dimension: no further booking action is accepted, and a second cancellation attempt is refused with `ERR_INVALID_STATE`.

### 3.4. Staffing the Event: the Roster, Certification Gates, Conflicts and Coverage

The field staffing office maintains the roster. Adding a demonstrator captures a `home_club_id` naming the club the worker is rostered to, a `full_name`, an `hourly_rate_cents` of at least 1 that will price the invoice's staffing lines, and an optional `max_weekly_events` from 1 through 14 that defaults to 5. A new worker starts with `employment_status` set to `ACTIVE`, both reliability variants — `reliability_score_rolling_90` and `reliability_score_program_to_date` — at 100.00, and `no_show_strike_count` and `completed_event_count` both at zero. Workers may be listed with `home_club_id` and `employment_status` filters.

Roster maintenance may revise `employment_status`, `hourly_rate_cents` and `max_weekly_events`. Moving a worker to `ON_LEAVE` or `TERMINATED` is not a bookkeeping change: it releases every assignment of that worker whose `assignment_status` is `ASSIGNED` or `CONFIRMED` and whose event's `event_date` falls on or after the logical clock's UTC date, and downgrades each of those events' `staffing_status` accordingly. The worker's own `version` increments by 1. Only `ACTIVE` permits a new assignment; both `ON_LEAVE` and `TERMINATED` block one, and the refusal is `ERR_DEMONSTRATOR_NOT_ACTIVE`.

Food-safety credentials are filed against a worker one certificate at a time. Each filing carries a `cert_type` of `FOOD_HANDLER`, `ALLERGEN_AWARENESS` or `HEAT_EQUIPMENT`, the issuing authority's `certificate_number`, an `issued_on` date and an `expires_on` date that must be strictly later than `issued_on`. A certificate's `cert_status` is derived rather than stored: it reads `REVOKED` when `revoked_at` has been set; otherwise `EXPIRED` when `expires_on` falls strictly before the logical clock's UTC date; otherwise `VALID`. Revoking a certificate — optionally with a `reason` — stamps `revoked_at` with the logical clock's current instant, drives `cert_status` to `REVOKED`, and increments the certificate's `version` by 1; the worker fails the certification gate from that instant onward. A worker's certificates may be listed, optionally filtered by `cert_type`, and each is returned with its derived `cert_status`.

For the purpose of staffing an event, a certificate is valid when its `revoked_at` is unset **and** its `expires_on` falls on or after the event's `event_date` — the boundary is inclusive, so a certificate expiring on the day of the demo still covers that demo. Note carefully that the assignment gate compares `expires_on` against the event's `event_date`, whereas the derived `cert_status` compares it against the logical clock's date; the two answers can differ for a future-dated event, and it is the event-date comparison that governs whether a worker may be assigned.

Assignments are created against a confirmed event by the staffing office or head office, with a payload carrying the `demonstrator_id`, a `role` of `LEAD` or `SUPPORT`, an optional `travel_authorized` flag that defaults to false, and an optional `replaces_assignment_id` that defaults to unset. The event's `booking_status` must be `CONFIRMED`; that is the first of the two gates between the commercial and coverage dimensions. The shift the assignment occupies is derived, not supplied: `scheduled_start_utc` is the event's `event_window_start_utc` less 45 minutes of setup lead, and `scheduled_end_utc` is the event's `event_window_end_utc` plus 75 minutes of teardown. The remaining checks then run in the ladder order of §2.8: the worker must be `ACTIVE`; a `FOOD_SAMPLING` event demands a valid `FOOD_HANDLER` certificate, with a valid `HEAT_EQUIPMENT` certificate on top when the product has `requires_heat_equipment` set and a valid `ALLERGEN_AWARENESS` certificate on top when it has `allergen_flag` set; the worker's `home_club_id` must equal the event's `club_id` unless the request sets `travel_authorized` to true; and then the schedule and cap tests below.

The demonstrator's schedule test uses **closed interval geometry with no buffer at all**, and this is deliberately different arithmetic from the equipment geometry in §3.5. Consider the worker's assignments whose `assignment_status` is `ASSIGNED`, `CONFIRMED` or `CHECKED_IN`. The new shift clashes with such an existing shift when the new `scheduled_start_utc` is at or before the existing `scheduled_end_utc` and the existing `scheduled_start_utc` is at or before the new `scheduled_end_utc`. Because both comparisons are inclusive, two shifts that merely touch at a single instant still clash, and the refusal is `ERR_DEMONSTRATOR_DOUBLE_BOOKED`. The consequence is concrete and matters: a `MORNING` shift on some date runs from 08:15Z to 14:15Z and a `MIDDAY` shift on the same date runs from 11:15Z to 17:15Z, so they overlap across three hours and clash; a `MORNING` shift and an `AFTERNOON` shift on the same date merely meet at 14:15Z, where one shift's `scheduled_end_utc` equals the other's `scheduled_start_utc`, and under this closed geometry that still counts as a clash. Assignments in `COMPLETED`, `NO_SHOW` or `RELEASED` are never candidates for the overlap test.

Two aggregate caps sit behind the overlap test, and they draw on a wider row set: for both caps, the worker's assignments in `ASSIGNED`, `CONFIRMED` or `CHECKED_IN` are counted **together with** those in `COMPLETED`, while `NO_SHOW` and `RELEASED` assignments count toward neither. The daily cap refuses a third assignment on one `event_date` — that is, the request is refused when the count on that date has already reached 2 — with `ERR_DEMONSTRATOR_DAILY_CAP_EXCEEDED`. The weekly cap takes the Monday of the ISO week containing the new event's `event_date`, counts the worker's assignments whose event dates fall on or after that Monday and strictly before the Monday plus seven days, and refuses the request with `ERR_DEMONSTRATOR_WEEKLY_CAP_EXCEEDED` once that count has reached the worker's `max_weekly_events`. Both caps reject at the limit, not above it.

One further structural rule: an event may hold at most one `LEAD`. If the event already carries an assignment whose `role` is `LEAD` and whose `assignment_status` is `ASSIGNED`, `CONFIRMED`, `CHECKED_IN` or `COMPLETED`, a second lead is refused with `ERR_LEAD_ALREADY_ASSIGNED`. A released or no-showed lead does not block a replacement, which is exactly how no-show recovery works.

Coverage is then recomputed from scratch, and it is a pure function of the live rows. Take the event's assignments whose `assignment_status` is `ASSIGNED`, `CONFIRMED` or `CHECKED_IN` — call these the held assignments — and count how many have `role` `LEAD` and how many have `role` `SUPPORT`. The event's `required_support_count` reads 1 when its `event_type` is `FOOD_SAMPLING` and its `allocated_sample_cases` has reached at least 6, and 0 otherwise. Coverage then reads `UNSTAFFED` when there are no held leads and no held supports; `FULLY_STAFFED` when there is at least one held lead and the held support count has reached at least `required_support_count`; and `PARTIALLY_STAFFED` in every remaining case. Assignments in `COMPLETED`, `NO_SHOW` or `RELEASED` contribute nothing to coverage. Neither `EXECUTED` nor `CLOSED_OUT` is ever produced by this computation — those two come only from the lead's check-in and from close-out respectively.

Inserting an assignment therefore advances the coverage dimension in one of three ways, each incrementing the event's `version` by 1. From `UNSTAFFED`, if the recomputation after the insert still reports fewer than one held lead or fewer held supports than `required_support_count`, coverage moves to `PARTIALLY_STAFFED`. From `UNSTAFFED`, if the recomputation reports at least one held lead and held supports at or above `required_support_count`, coverage moves straight to `FULLY_STAFFED` and `no_show_recovery_open` is set to false. From `PARTIALLY_STAFFED`, the same fully-covered recomputation moves coverage to `FULLY_STAFFED` and likewise sets `no_show_recovery_open` to false — this is the step that closes the revision cycle a no-show or a release opened.

Downgrades run in the opposite direction whenever an assignment leaves the held set by reaching `NO_SHOW` or `RELEASED`. If the recomputation over the remaining rows reports `PARTIALLY_STAFFED`, coverage moves from `FULLY_STAFFED` to `PARTIALLY_STAFFED`. If it reports `UNSTAFFED` — meaning no assignment on the event remains in `ASSIGNED`, `CONFIRMED` or `CHECKED_IN` — coverage moves to `UNSTAFFED`, whether it started from `FULLY_STAFFED` or from `PARTIALLY_STAFFED`. In all three downgrades, `no_show_recovery_open` is set to true when and only when the triggering assignment reached `NO_SHOW`, and the event's `version` increments by 1. One boundary is worth pinning down: when `required_support_count` is 0 and the lead assignment is still live, the recomputation still reports `FULLY_STAFFED`, so losing a `SUPPORT` assignment on such an event does not fire a downgrade at all.

Reliability is scored on every assignment transition into `COMPLETED`, `NO_SHOW` or `RELEASED`, and by the history-injection capability of §2.5. Two variants are computed and stored side by side, and they differ only in the window of history they consider. Start from every assignment of the worker whose `scheduled_start_utc` falls strictly before the logical clock's current instant — future shifts are excluded from both variants. The `ROLLING_90` variant then narrows that set to assignments whose `scheduled_start_utc` falls at or after 90 days before the current instant and strictly before it, so older completions and older no-shows drop out of both the penalty and the bonus terms; the result is written to `reliability_score_rolling_90` and is what staffing dashboards read. The `PROGRAM_TO_DATE` variant applies no lower bound at all and keeps every past assignment, so the completion bonus keeps accumulating; the result is written to `reliability_score_program_to_date` and is what the annual review reads. The same worker will generally score differently under the two variants, and that divergence is intended.

Within whichever set the variant selects, count the assignments in `COMPLETED`, count those in `NO_SHOW`, and count those that are in `COMPLETED` and additionally have `late_check_in` set to true. The raw score starts at 100, subtracts 12 points for each no-show, subtracts a further 4 points for each late completion, and adds half a point for each completion. The stored score is that raw figure clamped into the inclusive range from 0.00 to 100.00 and then rounded half-up to two decimal places. Assignments in `RELEASED` contribute nothing to either variant — they are recomputed on release only because releasing changes which rows are in the set.

`no_show_strike_count` is a separate counter and is deliberately *not* part of the score. It counts the worker's assignments in `NO_SHOW` whose `scheduled_start_utc` falls at or after 180 days before the logical clock's current instant, and it is the counter that drives the automatic stand-down described in §3.6. `completed_event_count` is likewise a plain counter: the number of the worker's assignments in `COMPLETED`, with no time filter of any kind.

Assignments may be listed with filters on `demo_event_id`, `demonstrator_id`, `replaces_assignment_id` and `assignment_status` — the third of which is how a coordinator finds the recovery row that took over from a failed one.

### 3.5. Equipment Reservations and Health-Code Sanitation

Each club physically holds its own demo equipment. Registering a unit captures the `club_id` that holds it, an `asset_tag` unique within that one club, and an `equipment_type` of `CONVECTION_OVEN`, `INDUCTION_COOKTOP`, `REFRIGERATED_CART`, `DISPLAY_TABLE` or `TV_CART`. From the type the server derives `requires_food_cert`, which reads true for a `CONVECTION_OVEN`, an `INDUCTION_COOKTOP` or a `REFRIGERATED_CART` and false for a `DISPLAY_TABLE` or a `TV_CART`; a client-supplied value for that field is ignored. A new unit is registered with `sanitation_status` set to `SANITIZED` and `last_sanitized_at` unset. Units may be listed with `club_id`, `equipment_type` and `sanitation_status` filters.

The sanitation state is the health-code log, and it has four values. `SANITIZED` is the only state from which a unit may be activated onto an event. `IN_USE` is where activation puts it. `SOILED` is where releasing an active reservation leaves it. `OUT_OF_SERVICE` takes it out of circulation entirely. Club staff record a state change directly by supplying a new `sanitation_status`; setting it to `SANITIZED` stamps `last_sanitized_at` with the logical clock's current instant, and any such change increments the unit's `version` by 1.

Holding a unit for an event takes a payload carrying `equipment_unit_id`, `demo_event_id`, and the occupation interval as `window_start_utc` and `window_end_utc`, where the end must be strictly later than the start. The unit's `club_id` must equal the event's `club_id`, or the request is refused with `ERR_EQUIPMENT_CLUB_MISMATCH`. The interval must genuinely cover the demonstration plus its setup: `window_start_utc` must be at or before the event's `event_window_start_utc` less 45 minutes, and `window_end_utc` must be at or after the event's `event_window_end_utc`; anything narrower is refused with `ERR_RESERVATION_WINDOW_INSUFFICIENT`. A successful hold opens with `reservation_status` `HELD` and `buffer_minutes` fixed at 30 — that value is not a client input and is always 30 minutes.

The clash test on a unit uses **buffered half-open geometry**, which is the deliberate counterpart to the demonstrator's unbuffered closed geometry. A unit is a capacity-one resource: only the reservations on that same `equipment_unit_id` whose `reservation_status` is `HELD` or `ACTIVE` are candidates, and released reservations are ignored entirely. Each stored interval runs from its `window_start_utc` up to but not including its `window_end_utc`, and is padded by the 30-minute sanitation buffer on both sides before comparison. The new hold clashes with an existing one when the new `window_start_utc` falls strictly before the existing `window_end_utc` plus 30 minutes and the existing `window_start_utc` falls strictly before the new `window_end_utc` plus 30 minutes; a clash is refused with `ERR_EQUIPMENT_WINDOW_CONFLICT`. Because both comparisons are strict, a reservation that begins exactly 30 minutes after another one ends is accepted, while one that begins 29 minutes after is refused. That is the crux of the disagreement between the two resource types: an equivalent 30-minute separation is fine for a unit and fatal for a worker.

Activating a hold moves `reservation_status` from `HELD` to `ACTIVE`. Club floor management (or head office) may do it only while the event's `booking_status` is `CONFIRMED`, only while the unit's `sanitation_status` reads `SANITIZED` — otherwise `ERR_EQUIPMENT_NOT_SANITIZED` — and only while the logical clock's current instant falls within the closed interval that begins 60 minutes before the reservation's `window_start_utc` and ends at its `window_end_utc`. Activation sets the unit's `sanitation_status` to `IN_USE` and increments the reservation's `version` by 1.

Releasing a hold moves `reservation_status` to `RELEASED`, and it happens either because club floor management asks for it or because a system cascade from the event's cancellation, revoked approval or close-out sweeps it up. The two source states diverge in exactly one respect. Releasing from `HELD` leaves the unit's `sanitation_status` untouched — nothing was ever set up, so nothing needs cleaning — and increments the reservation's `version` by 1. Releasing from `ACTIVE` sets the unit's `sanitation_status` to `SOILED`, because a unit that has been in service must be cleaned before it can serve again, and likewise increments the reservation's `version` by 1. `RELEASED` is terminal: activating a released reservation is refused with `ERR_INVALID_STATE`. Reservations may be listed with `equipment_unit_id`, `demo_event_id` and `reservation_status` filters.

### 3.6. Event Day: Attendance, No-Show Recovery and Close-Out

An assignment starts life in `ASSIGNED` and the worker acknowledges it first. Confirming an assignment moves `assignment_status` from `ASSIGNED` to `CONFIRMED`, may be performed only by the worker named on the assignment — the acting `X-User-ID` must equal the assignment's `demonstrator_id` — or by head office on that worker's behalf, and requires the event's `booking_status` to still be `CONFIRMED`. The assignment's `version` increments by 1. Every assignment action supplies a required `action` and accepts an optional free-text `note`; the attendance actions additionally accept an optional `occurred_at_utc` that backdates the stamp inside the legal window.

Checking in moves `assignment_status` from `CONFIRMED` to `CHECKED_IN` and is where the health-code chain closes. Besides the worker's own identity and the event still being `CONFIRMED`, the check-in demands that either the event carries a reservation whose `reservation_status` is `ACTIVE`, or the event's `event_type` is `NON_FOOD_DEMO` — a food demonstration cannot begin without a unit actually activated onto it. When such an active reservation does exist, its equipment unit's `sanitation_status` must read `IN_USE`, and a unit in any other sanitation state is refused with `ERR_EQUIPMENT_NOT_SANITIZED`. The instant recorded is `occurred_at_utc` when the caller supplies it and the logical clock's current instant otherwise; it must fall within the closed interval that begins 60 minutes before `scheduled_start_utc` and ends at `scheduled_end_utc`, and it must not be later than the logical clock's current instant. A violation of either bound is `ERR_CHECK_IN_WINDOW_INVALID`.

A successful check-in writes the recorded instant to `check_in_at` and then sets `late_check_in` to true when that instant falls strictly after 10 minutes past `scheduled_start_utc`, and to false otherwise — the ten-minute grace period is what separates a punctual arrival from a late one, and a late completion later costs the worker reliability points. When the checking-in assignment has `role` `LEAD`, the check-in also drives the event's coverage dimension from `FULLY_STAFFED` to `EXECUTED`, which requires the event's `booking_status` to be `CONFIRMED` and requires that the transitioning assignment is indeed the lead; the event's `version` increments by 1 for that move. A `SUPPORT` worker checking in never produces `EXECUTED`. The assignment's own `version` increments by 1.

Checking out moves `assignment_status` from `CHECKED_IN` to `COMPLETED`. The recorded instant — again `occurred_at_utc` when supplied, the logical clock otherwise — must be strictly later than `check_in_at` and must not be later than the logical clock's current instant, or the request is refused with `ERR_CHECK_IN_WINDOW_INVALID`. The write order on success is normative: `check_out_at` first, then `hours_worked`, then `billable_hours`. `hours_worked` is the elapsed time from `check_in_at` to `check_out_at` expressed in hours and rounded half-up to two decimal places, and it reads 0.00 for as long as either stamp is unset. `billable_hours` is the greater of `hours_worked` and a four-hour minimum, so a worker who is on site for two and a quarter hours still bills 4.00 hours; `billable_hours` reads 0.00 until the assignment actually reaches `COMPLETED`. Check-out then increments the worker's `completed_event_count` by 1 and recomputes both `reliability_score_rolling_90` and `reliability_score_program_to_date`, and increments the assignment's `version` by 1.

A worker who never turns up is declared a no-show by the staffing office (or head office), and the declaration is legal from either `ASSIGNED` or `CONFIRMED`. Both source states carry exactly the same requirement — the logical clock must have reached or passed 15 minutes after `scheduled_start_utc`, or the declaration is refused with `ERR_NO_SHOW_TOO_EARLY` — and both carry exactly the same side-effect set; a no-show from `ASSIGNED` and a no-show from `CONFIRMED` are indistinguishable in their consequences. Those consequences run four hops deep. The first hop recomputes the worker's `no_show_strike_count`, `reliability_score_rolling_90` and `reliability_score_program_to_date`. The second hop, caused by the first, is the automatic stand-down: when the recomputed `no_show_strike_count` has reached 3 or more and the worker's `employment_status` is still `ACTIVE`, that `employment_status` is set to `ON_LEAVE`. The third hop, caused by the second, sweeps the worker's other commitments: every other assignment of that worker whose `assignment_status` is `ASSIGNED` or `CONFIRMED` and whose event's `event_date` falls on or after the logical clock's UTC date is set to `RELEASED`. The fourth hop, caused by the third, propagates to those other events: each of them recomputes its `staffing_status` downward — from `FULLY_STAFFED` to `PARTIALLY_STAFFED` or to `UNSTAFFED` as the remaining rows dictate — and increments its own `version`. Alongside those four hops, the no-show downgrades *this* event's `staffing_status` and sets its `no_show_recovery_open` to true, creates one cancellation credit on this event with `credit_reason` `DEMONSTRATOR_NO_SHOW` and `credit_status` `PENDING_APPROVAL`, valued by the arithmetic of §3.9, and increments the assignment's `version` by 1.

Releasing an assignment is the quiet counterpart, and the divergence from a no-show is the point of having both. Release is legal from `ASSIGNED` and from `CONFIRMED`, with no timing requirement whatsoever, and the two source states again share an identical side-effect set: the worker's `reliability_score_rolling_90` and `reliability_score_program_to_date` are recomputed, the event's `staffing_status` is downgraded, and the assignment's `version` increments by 1. What release does *not* do is the whole story: it adds no strike to `no_show_strike_count`, it never triggers the automatic stand-down or its downstream sweep, it creates no cancellation credit, and it leaves `no_show_recovery_open` alone rather than setting it to true. `COMPLETED`, `NO_SHOW` and `RELEASED` are all terminal for an assignment.

`no_show_recovery_open` is the operational flag the staffing office watches. It reads true from the moment any assignment on the event reaches `NO_SHOW`, and stays true until either the event's `staffing_status` returns to `FULLY_STAFFED` or its `booking_status` becomes terminal. Recovery itself is an ordinary assignment insert that names the failed row in `replaces_assignment_id`, pointing at the `NO_SHOW` or `RELEASED` assignment the new row takes over from; an original assignment leaves that field unset. A `replaces_assignment_id` that does not resolve to an existing assignment is refused with `ERR_ASSIGNMENT_NOT_FOUND`. Because the failed row is no longer in the held set, the single-lead rule does not stand in the way of appointing a replacement lead, and once the replacement lands the coverage recomputation restores `FULLY_STAFFED` and clears `no_show_recovery_open` to false.

Closing out is the club's final act on the demonstration, and it advances both dimensions in one request: `booking_status` moves from `CONFIRMED` to `COMPLETED` and `staffing_status` moves from `EXECUTED` to `CLOSED_OUT`. The hosting club's floor management — the acting `X-User-ID` must be the event's `club_id` — or head office may perform it, and it demands that `staffing_status` already reads `EXECUTED` and that every assignment on the event has settled into `COMPLETED`, `NO_SHOW` or `RELEASED`; a straggler still sitting in `ASSIGNED`, `CONFIRMED` or `CHECKED_IN` blocks the close-out with `ERR_EVENT_NOT_EXECUTED`. For a `FOOD_SAMPLING` event there is a further requirement: the total `cases_received` across that event's shipments in `DELIVERED` or `SHORT` must be at least 1, or the close-out is refused with `ERR_SAMPLES_NOT_RECEIVED`. A `NON_FOOD_DEMO` event carries no such requirement. On success, close-out sets `staffing_status` to `CLOSED_OUT`, sets every reservation on the event whose `reservation_status` is `HELD` or `ACTIVE` to `RELEASED` — with any that was `ACTIVE` leaving its unit's `sanitation_status` at `SOILED` — sets `no_show_recovery_open` to false, and increments the event's `version` by 1.

### 3.7. Sample Logistics: Dispatch, Dock Receipt and Post-Event Reconciliation

Once a booking is confirmed, the vendor ships the cases. A dispatch is recorded with a payload carrying `cases_shipped`, from 1 through 40 inclusive, and a `carrier_reference` tracking string. The shipment opens with `shipment_status` `IN_TRANSIT`, `shipped_at` stamped with the logical clock's current instant, `cases_received` and `received_at` both unset, and `short_cases` at zero. An event may carry several shipments; they may be listed for the event with a `shipment_status` filter.

Receipt is the club's count at the dock, and it is a three-way fork on a single supplied `cases_received`. The shipment must still be `IN_TRANSIT` and the event's `booking_status` must be `CONFIRMED` or `COMPLETED`. `cases_received` may not exceed `cases_shipped`, and a count that does is refused with `ERR_RECEIVED_EXCEEDS_SHIPPED`. `short_cases` is in every case the shortfall — `cases_shipped` less `cases_received`, floored at zero — and it reads zero for as long as the load is unreceived.

When `cases_received` equals `cases_shipped`, the shipment lands `DELIVERED`: `cases_received` and `received_at` are written, `short_cases` settles at zero, and the shipment's `version` increments by 1. Nothing else changes, because the club got exactly what the allocation promised.

When `cases_received` is greater than zero but strictly less than `cases_shipped`, the shipment lands `SHORT`, and this is the branch with teeth. `cases_received`, `received_at` and `short_cases` are written. The first hop overwrites the event's `allocated_sample_cases` with the total `cases_received` across that event's shipments whose `shipment_status` is `DELIVERED` or `SHORT` — the allocation is restated downward to what physically arrived. The second hop, caused by the first, recomputes the event's `required_support_count` from the new `allocated_sample_cases`, so a food event that dropped below the six-case support threshold no longer demands a support worker. The third hop, caused by the second, recomputes the event's `staffing_status` against that new `required_support_count`, which can move coverage from `PARTIALLY_STAFFED` up to `FULLY_STAFFED` — a short load can, paradoxically, make an event fully covered. Additionally, and only when the event's `event_type` is `FOOD_SAMPLING`, one cancellation credit is created on the event with `credit_reason` `PRODUCT_SHORT` and `credit_status` `PENDING_APPROVAL`, valued by §3.9; a short load on a `NON_FOOD_DEMO` event creates no credit. Both the event's `version` and the shipment's `version` increment by 1.

When `cases_received` is zero, the shipment lands `REJECTED`: `cases_received` is written as zero, `received_at` is written, and `short_cases` settles at the full `cases_shipped`. The divergence from the `SHORT` branch is deliberate and complete — a wholly rejected load does **not** touch the event's `allocated_sample_cases`, does not recompute `required_support_count` or `staffing_status`, and creates no cancellation credit — precisely so that the vendor can re-ship against the same intact allocation. Only the shipment's `version` increments by 1. All three of `DELIVERED`, `SHORT` and `REJECTED` are terminal, and a second receipt against a received shipment is refused with `ERR_INVALID_STATE`.

After the event closes out, the club files the sample count. Reconciliation requires the event's `booking_status` to be `COMPLETED` — otherwise `ERR_EVENT_NOT_COMPLETED` — and exactly one reconciliation may exist per event, so a second filing is refused with `ERR_DUPLICATE_RESOURCE`. The filing supplies three counts, each at least zero: `units_sampled`, the units handed to members during the demo; `units_wasted`, the units spoiled, dropped or discarded; and `units_returned`, the units put back into club stock intact.

Everything else on the reconciliation is derived. `cases_delivered` is the total `cases_received` across the event's shipments whose `shipment_status` is `DELIVERED` or `SHORT`; shipments still `IN_TRANSIT` and shipments `REJECTED` contribute nothing. `units_per_case` is a snapshot of the product's `samples_per_case` taken at the moment the reconciliation is created, so a later change to the SKU never rewrites a filed reconciliation. `units_delivered` is `cases_delivered` multiplied by `units_per_case`. `variance_units` is `units_delivered` less the sum of `units_sampled`, `units_wasted` and `units_returned`; a positive figure means units nobody can account for, a negative figure means more units were accounted for than were ever delivered. The conservation identity that must hold on every row is that `units_delivered` equals `units_sampled` plus `units_wasted` plus `units_returned` plus `variance_units`. `variance_pct` reads 0.00 whenever `units_delivered` is zero — that zero-denominator guard is part of the contract, not an implementation nicety — and otherwise is the absolute value of `variance_units` divided by `units_delivered`, multiplied by 100, rounded half-up to two decimal places.

The reconciliation exists in `OPEN` only for the instant of its creation and is auto-forked inside the same request. It settles at `BALANCED` when `variance_units` is exactly zero, or when `variance_pct` is at or below a tolerance of 2.00 percent; it settles at `VARIANCE_FLAGGED` when `variance_units` is non-zero **and** `variance_pct` is strictly above 2.00 percent. In both cases `write_off_cost_cents` stays at zero. A `BALANCED` reconciliation is terminal and lets billing proceed. A `VARIANCE_FLAGGED` one blocks the event's invoice from being issued until somebody resolves it.

Resolution is a head-office write-off, legal only from `VARIANCE_FLAGGED`, optionally annotated with a `note`. It moves `recon_status` to `WRITTEN_OFF`, sets `write_off_cost_cents` to the absolute value of `variance_units` multiplied by the product's `unit_cost_cents`, rounded half-up to whole cents, and increments the reconciliation's `version` by 1. A write-off attempted against a `BALANCED` row is refused with `ERR_INVALID_STATE`. The event's reconciliation is read back as an array of length zero or one, which is how a caller distinguishes "not yet filed" from "filed and balanced" without guessing at a 404.

### 3.8. Sales Lift Measurement and Baseline Restatement

The commercial justification for a demonstration is incremental sales, and the programme measures it twice with deliberately different arithmetic. A measurement is posted against an event by the owning vendor or by head office, with a payload carrying a `measurement_variant` of `PROVISIONAL` or `FINAL`, the `units_sold_in_window` — the point-of-sale units for that SKU at that club inside the measurement window, supplied by the caller and at least zero — and the `expected_demo_event_version` guard described in §2.7.

Measurement needs a yardstick. The baseline row for the event's club and product pairing is looked up first, and if none exists the posting is refused with `ERR_BASELINE_MISSING`. When it does exist, its `baseline_weekly_units` and `baseline_unit_price_cents` are **snapshotted onto the measurement row** under those same two names. The snapshot is permanent: a later restatement of the baseline marks the measurement stale but never rewrites the figures it was computed from.

The `PROVISIONAL` variant is the fast read, typically posted within days of the event. Its `attribution_days` is fixed at 3, its `window_boundary` is `CLOSED`, its `window_start_date` is the event's `event_date`, and its `window_end_date` is the `event_date` plus two days — that is, the `event_date` plus one day fewer than `attribution_days` — with that end date **included** in the window. Its `cannibalization_units` is 0.00; no deduction is taken for the samples the demo itself gave away.

The `FINAL` variant is the settled read, posted after the event's attribution window has elapsed and after the samples have been reconciled. Its `attribution_days` is the event's own `attribution_window_days`, its `window_boundary` is `HALF_OPEN`, its `window_start_date` is again the event's `event_date`, and its `window_end_date` is the `event_date` plus `attribution_days` days with that end date **excluded** from the window. Before it can be computed it requires the event's reconciliation row to exist; when none does, the posting is refused with `ERR_RECONCILIATION_UNRESOLVED`. Its `cannibalization_units` is the reconciliation's `units_sampled` multiplied by a cannibalisation rate of 0.15 — fifteen percent of the units handed out are assumed to be sales the club would have made anyway — rounded half-up to two decimal places.

Because of those two differences — the shorter, inclusive window and the absent cannibalisation deduction — the `PROVISIONAL` variant systematically reports a larger lift than the `FINAL` variant does for the same `units_sold_in_window`, and both are retained side by side rather than one overwriting the other.

The remaining figures follow the same three steps in both variants. `baseline_units_expected` prorates the weekly baseline over the window: it is the snapshotted `baseline_weekly_units` multiplied by `attribution_days`, divided by 7, rounded half-up to two decimal places. `lift_units` is `units_sold_in_window` less `baseline_units_expected` less `cannibalization_units`, rounded half-up to two decimal places; it may legitimately be negative when a demo underperformed its own baseline. `lift_pct` reads 0.00 whenever `baseline_units_expected` is zero, and otherwise is `lift_units` divided by `baseline_units_expected`, multiplied by 100, rounded half-up to two decimal places. `incremental_revenue_cents` is `lift_units` multiplied by the snapshotted `baseline_unit_price_cents`, rounded half-up to whole cents.

A new measurement opens with `measurement_status` `POSTED`, and posting it retires the event's previous measurement of the *same* variant: any earlier measurement on the same event with the same `measurement_variant` whose `measurement_status` is `POSTED` or `STALE` is moved to `SUPERSEDED`. A `PROVISIONAL` posting never disturbs a `FINAL` measurement and vice versa. Posting also increments the parent event's `version` by 1 — which is precisely why the stale-version guard on this operation matters. `SUPERSEDED` is terminal for a measurement.

Restating a baseline is head-office work and revises `baseline_weekly_units` and `baseline_unit_price_cents`. When either value actually changes, three things happen: the baseline's `restatement_count` increments by 1, every measurement whose `measurement_status` is `POSTED` and which belongs to an event at that same club for that same product moves to `STALE`, and the baseline row's own `version` increments by 1. A patch that supplies the same values it already held changes nothing and marks nothing stale. `STALE` is not terminal — a stale measurement can still be superseded later by a fresh posting of the same variant.

Measurements are read back for an event newest first, ordered by `created_at` descending, optionally filtered by `measurement_variant`, and each row carries its own `id` and `created_at` and no other system stamps, per §2.4.

### 3.9. Billing the Manufacturer: Invoices, Cancellation Credits and Receivable Governance

Billing is head-office-only work. The per-event invoice is created against a completed event by `ProgramAdmin`, with a request body whose only content is the `expected_demo_event_version` guard of §2.7. The event's `booking_status` must be `COMPLETED`, or the creation is refused with `ERR_EVENT_NOT_COMPLETED`, and no other invoice for the event may currently sit in `DRAFT`, `ISSUED` or `PAID`, or the creation is refused with `ERR_INVOICE_ALREADY_EXISTS`. On creation the invoice copies the event's `manufacturer_id` into its own `manufacturer_id` and snapshots the vendor's `credit_terms_days` into its own `credit_terms_days`, so a later change to the vendor's payment terms never rewrites an existing invoice. The invoice opens in `DRAFT` with `issued_by_user_id`, `issued_at` and `paid_at` all unset and `credit_applied_cents` at zero. Creating the invoice increments the parent event's `version` by 1.

The invoice body is a list of individually rounded lines held in `line_items`, where each member is an object carrying a `line_type` of `BASE`, `ADDON`, `STAFFING` or `HANDLING`, a human-readable `label`, and an `amount_cents`. The list is emitted in that `line_type` order — every base line, then every add-on line, then every staffing line, then every handling line — and within one `line_type` the lines follow the `created_at` ascending order of the rows that produced them. Recall the normative rounding rule from §2.6: each line is rounded to whole cents before it enters any sum, and the sums are never re-rounded.

There is exactly one `BASE` line. Its raw value is a base fee selected by `event_type` — 42,000 cents for a `FOOD_SAMPLING` event and 28,000 cents for a `NON_FOOD_DEMO` event — multiplied by a club-tier multiplier of 1.25 for a `FLAGSHIP` club, 1.00 for a `STANDARD` club or 0.85 for a `SATELLITE` club, and multiplied again by a day-part multiplier of 1.00 for `MORNING`, 1.15 for `MIDDAY` or 1.05 for `AFTERNOON`. That product is rounded half-up to whole cents and becomes the `BASE` line's `amount_cents`, which is also written to `base_fee_cents`.

`ADDON` lines follow, one per member of the event's `addon_services`, taken in the order the array declares them. Three of the five add-ons are flat charges: `EXTRA_TABLE` bills 5,000 cents, `VIDEO_LOOP` bills 7,500 cents, and `ALLERGEN_SIGNAGE` bills 2,200 cents. The other two are proportions of the already-rounded `BASE` line: `PREMIUM_PLACEMENT` bills 18 percent of it and `BILINGUAL_DEMONSTRATOR` bills 12 percent of it, each rounded half-up to whole cents on its own. The sum of the add-on lines is written to `addon_fee_cents`, which is zero when the event carries no add-ons.

`STAFFING` lines follow, one per assignment on the event whose `assignment_status` is `COMPLETED`, ordered by that assignment's `created_at` ascending. Each line is the assignment's `billable_hours` multiplied by that demonstrator's `hourly_rate_cents` and multiplied again by a role multiplier of 1.20 for a `LEAD` or 1.00 for a `SUPPORT`, rounded half-up to whole cents. Assignments in `NO_SHOW` or `RELEASED` produce no staffing line at all — the programme does not bill for a worker who never worked. The sum of the staffing lines is written to `staffing_fee_cents`.

`HANDLING` lines close the list. Let the billable case count be the event's reconciliation's `cases_delivered`, or zero when no reconciliation row exists. One per-case handling line bills that case count multiplied by 900 cents. For a `FOOD_SAMPLING` event only, a second cold-chain line bills the same case count multiplied by 350 cents; a `NON_FOOD_DEMO` event gets no cold-chain line. The sum of the handling lines is written to `sample_handling_fee_cents`. Because only shipments in `DELIVERED` or `SHORT` feed `cases_delivered`, a wholly rejected load bills no handling whatsoever.

`subtotal_cents` is the sum of every line's `amount_cents`, and it is pure integer arithmetic over values that were each already rounded. The discount is then keyed on two things at once. `monthly_completed_event_count` is the number of that vendor's demo events whose `booking_status` is `COMPLETED` and whose `event_date` falls in the same calendar month as this event's `event_date`, evaluated at the moment the invoice is built. A volume step is derived from it: 0.05 once that count has reached 12, 0.02 once it has reached 5, and 0.00 below 5. `volume_discount_pct` is the vendor's tier base discount — 0.06 for `PLATINUM`, 0.03 for `GOLD`, 0.00 for `STANDARD` — plus that volume step, capped so it can never exceed 0.10 however generous the tier and the month. `discount_cents` is `subtotal_cents` multiplied by `volume_discount_pct`, rounded half-up to whole cents. Finally `total_due_cents` is `subtotal_cents` less `discount_cents` less `credit_applied_cents`, floored at zero so an invoice can never owe the vendor money.

Issuing a draft invoice moves `invoice_status` from `DRAFT` to `ISSUED`. It requires the event's `booking_status` to be `COMPLETED`, the event's reconciliation to have settled into `BALANCED` or `WRITTEN_OFF` — an `OPEN`, `VARIANCE_FLAGGED` or entirely absent reconciliation blocks issuance with `ERR_RECONCILIATION_UNRESOLVED` — and the vendor's `account_status` not to be `SUSPENDED`. Issuance stamps `issued_by_user_id` with the acting `X-User-ID` and `issued_at` with the logical clock's current instant. It then cascades: the vendor's `outstanding_balance_cents` is recomputed, and when the recomputed exposure exceeds the vendor's `credit_limit_cents` while `account_status` is `ACTIVE`, that `account_status` is automatically moved to `HOLD`. The event's `settlement_status` is recomputed to `INVOICED` and the event's `version` increments by 1; the invoice's own `version` increments by 1.

The receivable rollup is a single, exact aggregation. A vendor's `outstanding_balance_cents` is the sum of `total_due_cents` over that vendor's invoices whose `invoice_status` is `ISSUED`; invoices in `DRAFT`, `VOID` and `PAID` contribute exactly zero, and invoices of other vendors never contribute. A vendor's `credit_note_balance_cents` is the sum of `credit_amount_cents` over that vendor's cancellation credits whose `credit_status` is `APPLIED` and whose `applied_to_invoice_id` is unset — credits in `PENDING_APPROVAL`, `APPROVED` or `REJECTED` contribute zero. Both sums are computed first, and only then are the automatic account transitions evaluated: exposure strictly above `credit_limit_cents` while the account is `ACTIVE` moves it to `HOLD`, and exposure at or below `credit_limit_cents` while the account is on `HOLD` moves it back to `ACTIVE`. `SUSPENDED` is never entered or left by this rollup.

Voiding an issued invoice moves `invoice_status` from `ISSUED` to `VOID`. It clears both `issued_by_user_id` and `issued_at` back to unset, recomputes `outstanding_balance_cents` — which by the conservation invariant of §2.9 returns to its exact pre-issue integer value — and, when the recomputed exposure is at or below `credit_limit_cents` while the account is on `HOLD`, automatically returns `account_status` to `ACTIVE`. The event's `settlement_status` is recomputed and the event's `version` increments by 1; the invoice's `version` increments by 1.

Redrafting moves `invoice_status` from `VOID` back to `DRAFT` and rebuilds the invoice against current data. It re-runs the whole line-item computation and overwrites every `line_items` entry along with `base_fee_cents`, `addon_fee_cents`, `staffing_fee_cents`, `sample_handling_fee_cents`, `subtotal_cents`, `monthly_completed_event_count`, `volume_discount_pct`, `discount_cents` and `total_due_cents`. One field is deliberately preserved rather than recomputed: `credit_applied_cents` survives the redraft untouched, so credits already applied to this invoice are not silently forgotten. The invoice's `version` increments by 1. Because `VOID` re-enters `DRAFT`, the cycle `DRAFT → ISSUED → VOID → DRAFT → ISSUED` is legal and may repeat without limit.

Recording a payment moves `invoice_status` from `ISSUED` to `PAID` and requires the supplied `amount_cents` to equal the invoice's `total_due_cents` exactly; a partial or excess payment is refused with `ERR_PAYMENT_AMOUNT_MISMATCH`. Payment stamps `paid_at` with the logical clock's current instant, recomputes `outstanding_balance_cents` — a paid invoice drops out of the issued rollup, so exposure falls — and, when the recomputed exposure is at or below `credit_limit_cents` while the account is on `HOLD`, returns `account_status` to `ACTIVE`. The event's `settlement_status` is recomputed to `PAID` and the event's `version` increments by 1; the invoice's `version` increments by 1. `PAID` is terminal for an invoice. Invoices may be listed with `demo_event_id`, `manufacturer_id` and `invoice_status` filters.

Cancellation credits are never created by a client request. Every credit arrives through one of four cascades: a confirmed booking being cancelled, an assignment being declared a no-show, a shipment landing `SHORT` on a `FOOD_SAMPLING` event, or a club being closed. Each credit records the `demo_event_id` of the disrupted event, copies the event's `manufacturer_id` into its own `manufacturer_id`, and carries a `credit_reason` of `CLUB_CANCELLED`, `MANUFACTURER_CANCELLED_EARLY`, `MANUFACTURER_CANCELLED_LATE`, `PRODUCT_SHORT` or `DEMONSTRATOR_NO_SHOW`, set by the creating cascade. Credits are discovered by listing them, with filters on `demo_event_id`, `manufacturer_id`, `applied_to_invoice_id` and `credit_status`.

Valuing a credit runs in seven ordered steps, and the order is normative — computing the notice tier before netting off prior credits produces a different answer, which is why the tier lookup deliberately sits downstream of the netting.

1. `prior_applied_cents` is the sum of `credit_amount_cents` over the *other* credits on the same event whose `credit_status` is `APPLIED`. Credits in `PENDING_APPROVAL`, `APPROVED` or `REJECTED` contribute zero.
2. `gross_base_cents` is taken from the event's invoice when one exists whose `invoice_status` is `DRAFT`, `ISSUED` or `PAID` — at most one can — in which case it is that invoice's `subtotal_cents`. When no such invoice exists, `gross_base_cents` is instead the projected base fee: the base fee for the event's `event_type` multiplied by the club-tier multiplier for the club's `club_tier` and by the day-part multiplier for the event's `day_part`, rounded half-up to whole cents, using the same three constant tables as the `BASE` invoice line. Invoices in `VOID` are excluded from this lookup, so voiding an invoice pushes a subsequent credit back onto the projected base.
3. `billable_base_cents` is `gross_base_cents` less `prior_applied_cents`, floored at zero. This step depends on both step 1 and step 2.
4. `notice_hours` is the whole number of hours from the logical clock's current instant to the event's `event_window_start_utc`, discarding any fractional hour; when the event window has already begun the figure is clamped to zero rather than going negative.
5. The notice tier is selected from a two-by-three table using a base bracket and a notice bracket. The base bracket is `HIGH` when `billable_base_cents` has reached at least 50,000 cents and `LOW` below that — so this step depends on step 3. The notice bracket is the 72-hours-or-more band when `notice_hours` is at least 72, the middle band when `notice_hours` is at least 24 but below 72, and the under-24 band otherwise. In the `HIGH` base bracket, `notice_tier_pct` reads 0.25, 0.50 and 0.85 across those three bands respectively; in the `LOW` bracket it reads 0.15, 0.35 and 0.70. Late notice on a large booking is therefore the most expensive combination.
6. `reason_multiplier` is selected by `credit_reason`: 1.00 for `CLUB_CANCELLED`, 1.00 for `DEMONSTRATOR_NO_SHOW`, 0.60 for `PRODUCT_SHORT`, and 0.00 for both `MANUFACTURER_CANCELLED_LATE` and `MANUFACTURER_CANCELLED_EARLY`. A vendor that cancels its own booking earns no credit, whatever the notice.
7. `credit_amount_cents` is the smaller of `billable_base_cents` and the product of `billable_base_cents`, `notice_tier_pct` and `reason_multiplier` rounded half-up to whole cents. Rounding happens once, at this step, after both multiplications — never between them. The cap means a credit can never exceed the base it was computed from.

A credit opens in `PENDING_APPROVAL` with `approved_by_user_id` and `applied_to_invoice_id` both unset. Head office decides it by supplying a `decision` of `APPROVE` or `REJECT`, optionally with a `note`, and the segregation-of-duties rule of §2.10 gates the approval path: when an invoice for the credit's event sits in `ISSUED` or `PAID`, the acting `X-User-ID` must differ from that invoice's `issued_by_user_id`.

Approval stamps `approved_by_user_id` with the acting `X-User-ID` and moves `credit_status` to `APPROVED` — a state that exists only transiently inside the request, because the credit immediately auto-advances to `APPLIED` in the same request, incrementing its `version`. The application cascade then runs four hops. The first hop places the money: when an invoice for the event has `invoice_status` `DRAFT` or `ISSUED`, `applied_to_invoice_id` is set to that invoice and that invoice's `credit_applied_cents` increases by this credit's `credit_amount_cents`; when no such invoice exists, `applied_to_invoice_id` stays unset and the vendor's `credit_note_balance_cents` increases by `credit_amount_cents` instead. The second hop, caused by the first, recomputes the touched invoice's `total_due_cents` as `subtotal_cents` less `discount_cents` less the new `credit_applied_cents`, floored at zero, and increments that invoice's `version`. The third hop, caused by the second, recomputes the vendor's `outstanding_balance_cents` from the issued-invoice rollup. The fourth hop, caused by the third, returns the vendor's `account_status` from `HOLD` to `ACTIVE` when the recomputed exposure is at or below `credit_limit_cents`. Alongside those hops, the event's `settlement_status` is recomputed and the event's `version` increments by 1. The credit's `version` increments by 1 for the application as well.

Rejection is far simpler and is the symmetric branch: it stamps `approved_by_user_id` with the acting `X-User-ID`, moves `credit_status` to `REJECTED`, leaves every invoice untouched along with both `outstanding_balance_cents` and `credit_note_balance_cents`, and increments the credit's `version` by 1. Both `APPLIED` and `REJECTED` are terminal, and a second decision on a decided credit is refused with `ERR_INVALID_STATE`.

## 5. Error Code Catalogue

Every failure returns the error envelope of §2.2 with one of the following `error_id` values and its stated HTTP status. When several conditions are simultaneously violated, the earliest rung of the ladder in §2.8 wins.

| Error ID | HTTP Status | Condition |
|---|---|---|
| `ERR_UNAUTHENTICATED` | 401 | `X-User-Role` or `X-User-ID` header missing, or `X-User-Role` is not a declared role. |
| `ERR_ROLE_NOT_PERMITTED` | 403 | The role is absent from the endpoint's authorised list, or may not perform the requested action on a multi-action endpoint. |
