# County Address and Emergency Response GIS API — Product Requirements Document

## 1. Introduction

When a resident dials 911, the dispatcher's screen is only as trustworthy as the county's address database. A house number that sits outside its road's range, a subdivision cell that no fire district has claimed, or a road name spelled two different ways by two agencies are not cartographic curiosities — they are the difference between an ambulance arriving and an ambulance circling. This document specifies the API for the county's authoritative geographic data system: the service of record for address points, road centerlines, emergency service boundaries, and the version-controlled releases that flow out to dispatch, mapping and public consumers.

The system serves six distinct professional communities whose interests deliberately do not align. The address authority wants to mint addresses quickly for new construction; the quality-control office wants nothing provisioned until it has been scanned and blessed; the responding agencies want their service boundaries recognised and will argue with each other about road names and ranges; the permitting office wants a house number before the foundation is poured. Rather than papering over that friction, the API encodes it: records move through explicit lifecycles, contested records freeze until the dispute is resolved, quality reports must be certified by a human other than the one who generated them, and a release cannot be published by the same person who certified the report authorising it.

Two further concerns shape almost every rule below. First, **time is data**: emergency service coverage is expressed as half-open effective windows, and the system must be able to answer not only "is this cell covered right now?" but "will it still be covered thirty days from now?" — because a coverage gap that opens next week is still a coverage gap that will misroute a call. Second, **history is never deleted**: retired addresses remain queryable forever so that a title researcher can walk a supersession chain back through decades of renumbering. All geography in this system is expressed as membership in a **coverage cell** — a deterministic grid primitive — so that overlap and gap analysis is exact integer set arithmetic rather than floating-point geometry. Every endpoint described here is mounted under the `/gis` prefix.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to every endpoint must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the role under which the principal is acting. If `X-User-ID` is absent or empty, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401) before any other evaluation takes place. If the role named in `X-User-Role` is not among the roles authorised for the requested operation, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

Six roles exist, spelled exactly as follows.

- **`SystemAdmin`** — the county GIS administrator. Registers jurisdictions, agencies and coverage cells, adopts or arbitrates discrepancy resolutions, and drives the logical clock.
- **`GisAnalyst`** — the address authority. Maintains road centerlines and address points, reviews assignment requests, mints addresses, and runs QC scans.
- **`QcCertifier`** — the quality-control officer. Publishes centerlines, waives defects, and certifies or rejects QC validation reports.
- **`ProvisioningOfficer`** — the data provisioning officer. Opens, seals, publishes and rolls back the packages that feed the dispatch, mapping and public channels.
- **`PermitCoordinator`** — the permitting and utility liaison. Opens address assignment requests for new construction, records utility clearances and holds, and voids requests.
- **`AgencyLiaison`** — the representative of a responding agency. Creates and drives emergency service boundaries, and litigates discrepancy cases on its agency's behalf.

Five of the six roles carry an **opaque** identity. When `X-User-Role` is `SystemAdmin`, `GisAnalyst`, `QcCertifier`, `ProvisioningOfficer` or `PermitCoordinator`, the value of `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity; the server may record it — for example as `generated_by_user_id` and `certified_by_user_id` on a QC validation report, as `waived_by_user_id` on a defect, or as `sealed_by_user_id` and `published_by_user_id` on a provisioning package — but it never compares it to any entity's `id`.

`AgencyLiaison` is different. When `X-User-Role` is `AgencyLiaison`, `X-User-ID` is the `id` of the acting `Agency`; ownership checks on any resource that references an `Agency` compare the resource's agency-referencing field to `X-User-ID`. Concretely, a liaison may only propose, claim cells for, activate or retire an `EmergencyServiceBoundary` whose `agency_id` equals `X-User-ID`, and may only file proposals on or concur with a `DiscrepancyCase` in which `X-User-ID` appears as either `opened_by_agency_id` or `counterparty_agency_id`. A liaison creating a boundary or a case may not name an agency other than itself. Any violation of these ownership rules is rejected with `ERR_AGENCY_IDENTITY_MISMATCH` (HTTP 403), which is evaluated immediately after the role check and before any existence, schema or state evaluation.

Read endpoints are open to all six roles. Write endpoints are narrowly scoped: coverage-cell creation is shared between `SystemAdmin` and `GisAnalyst`, and every other mutating operation belongs to exactly one role, as enumerated in the endpoint table of §4.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every endpoint that returns a collection accepts two optional query parameters. `limit` controls page size; it defaults to 10, must be at least 1, and must be at most 100. `offset` controls the starting position; it defaults to 0 and must not be negative. A `limit` outside the range of 1 through 100, or a negative `offset`, is a schema-level failure and is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

Collections are always sorted by `created_at` in ascending order. Sorting by `id` is never performed, and no endpoint offers a client-selectable sort key. List responses carry `response_type` of `"array"`, the array itself in `data`, and four pagination fields inside `meta` alongside the request identifier and timestamp: `limit`, `offset`, `total_count` and `has_more`. `total_count` is the number of rows matching the supplied filters *before* `limit` and `offset` are applied. `has_more` is true when the offset plus the number of rows actually returned in this page is still less than `total_count`.

### 2.4. The Logical Clock and Temporal Representation

Nothing in this system reads the wall clock. The server maintains a **logical UTC clock** whose value at startup is exactly `2026-08-01T00:00:00Z`, and every temporal decision — coverage window containment, the forward coverage horizon, publication cadence, defect staleness horizons, and every `retired_at`, `certified_at`, `sealed_at`, `published_at`, `staled_at`, `waived_at`, `escalated_at` and `adopted_at` stamp — reads that logical instant. An administrative test-driving capability sets the clock to a supplied instant, taking a single field `to_iso8601` and answering with the new value under the key `current_utc`. Setting the clock mutates no stored entity and recomputes no counter by itself; only subsequent operations observe the new instant.

Every datetime crossing the API boundary, in either direction — including `created_at`, `updated_at`, `effective_start`, `effective_end` and `published_at` — is ISO 8601 UTC with exactly three fractional-second digits and a trailing `Z`, in the shape `YYYY-MM-DDTHH:MM:SS.mmmZ`. An input supplied with zero fractional digits, such as `2026-09-01T00:00:00Z`, is accepted and normalised by zero-padding the fractional part to `.000Z`. Responses always emit the three-digit form. A datetime that is not valid ISO 8601 is rejected with `ERR_INVALID_REQUEST`.

Service windows in this system are **half-open**. A window whose `effective_start` is inclusive and whose `effective_end` is exclusive covers an instant when the instant is at or after the start and strictly before the end; an `effective_end` of null means the window never closes. Window comparisons are performed at millisecond resolution. Two windows that merely touch — where one window's `effective_end` equals the next window's `effective_start` — do not intersect and leave no gap between them; a separation of even one second does leave a gap.

### 2.5. Record Identity, Timestamps and the `version` Counter

Every stored record carries a server-minted `id`, which is a UUID with no type prefix, and a `created_at` timestamp recorded at the logical clock instant of creation. Clients never supply either.

Most records additionally carry `updated_at`, refreshed at the logical clock instant of every mutation, and `version`, an integer that starts at 1 on creation and increases by exactly 1 on every mutation of that record. The `version` counter is the backbone of two separate mechanisms described below: optimistic concurrency control (§2.6) and provisioning pin freshness (§2.9). Because a great many operations in this system cascade, a single request can legitimately increment the `version` of a dozen records; each affected record's `updated_at` moves with its own `version`.

One entity is exempt. `DiscrepancyProposal` is an append-only log row: it carries only `id` and `created_at`. It has no `updated_at` and no `version`, because a filed proposal is never rewritten — its `status` is a pure projection computed from its sibling rows and its parent case, as described in §3.8. Every other entity in the system — `Jurisdiction`, `Agency`, `CoverageCell`, `RoadCenterline`, `AddressPoint`, `AddressAssignmentRequest`, `EmergencyServiceBoundary`, `BoundaryCellAssignment`, `QcValidationReport`, `QcDefect`, `ProvisioningPackage` and `PackageRecord` — carries the full set of `id`, `created_at`, `updated_at` and `version`.

### 2.6. Optimistic Concurrency on Parent Records

Three write operations edit or extend a record whose meaning depends on state the client must have observed first. Each of them requires a non-optional expected-version field, and each rejects a mismatch with HTTP 412.

A centerline edit must carry `expected_road_version`, holding the client's last observed `version` of the target `RoadCenterline`. If it does not equal the centerline's current `version`, the edit is rejected with `ERR_STALE_ROAD_VERSION` (HTTP 412). This matters because a second edit of the same fields would otherwise be accepted on its own merits: the stale version is the only signal that the editor never saw the intervening change — a validation, a publication, an adopted discrepancy, or another analyst's range edit — that the new values would silently overwrite.

Adding a cell claim to an emergency service boundary must carry `expected_boundary_version`, holding the client's last observed `version` of the parent `EmergencyServiceBoundary`. A mismatch with the boundary's current `version` is rejected with `ERR_STALE_BOUNDARY_VERSION` (HTTP 412). Claiming the same cell twice with different windows is a legitimate operation — the later claim supersedes the earlier one in the agency's intent — so nothing in the boundary state machine refuses the second write; the stale version is what tells the server the liaison composed the claim against an out-of-date cell set.

Filing a proposal on a discrepancy case must carry `expected_case_version`, holding the client's last observed `version` of the parent `DiscrepancyCase`. A mismatch with the case's current `version` is rejected with `ERR_STALE_CASE_VERSION` (HTTP 412). Filing a further proposal is itself a legitimate act — each filing supersedes the previous one as the current proposal — so the stale version is the only way the server can tell that the liaison drafted a counter-offer without seeing the round it purports to answer.

No other endpoint in this system accepts an expected-version field, and no other endpoint may reject a request for version staleness.

### 2.7. Validation Precedence and Nested Path Resolution

Validation is strictly ordered, and the **first** failing check determines the response; later checks are never reported for the same request. The order is: authentication (`ERR_UNAUTHENTICATED`), then role authorisation (`ERR_UNAUTHORIZED`), then agency identity ownership (`ERR_AGENCY_IDENTITY_MISMATCH`), then path-entity existence, then referenced-entity existence, then request-schema validity (`ERR_INVALID_REQUEST`), then target-state legality, then expected-version staleness, and only then the domain-specific business rules of §2.8 onwards in the order in which they are introduced there.

Path parameters are resolved left to right. When a path names a parent and a child — the cell assignments of a boundary, the defects of a report, the records of a package, the proposals of a case — the parent is resolved first, and if the parent identifier does not name a stored row the request fails with that parent's not-found code before the child segment is examined at all. Each entity has its own 404 code: `ERR_JURISDICTION_NOT_FOUND`, `ERR_AGENCY_NOT_FOUND`, `ERR_COVERAGE_CELL_NOT_FOUND`, `ERR_ROAD_NOT_FOUND`, `ERR_ADDRESS_POINT_NOT_FOUND`, `ERR_REQUEST_NOT_FOUND`, `ERR_BOUNDARY_NOT_FOUND`, `ERR_CELL_ASSIGNMENT_NOT_FOUND`, `ERR_REPORT_NOT_FOUND`, `ERR_DEFECT_NOT_FOUND`, `ERR_PACKAGE_NOT_FOUND`, `ERR_CASE_NOT_FOUND` and `ERR_PROPOSAL_NOT_FOUND`.

The same codes govern references supplied in a request body or a query filter. A `jurisdiction_id`, `agency_id`, `road_centerline_id`, `cell_id`, `parent_address_point_id`, `superseded_by_address_point_id`, `qc_report_id`, `counterparty_agency_id` or `proposal_id` that does not resolve raises the referenced entity's own not-found code. Three fields are deliberately polymorphic — `subject_ref_id` on a discrepancy case, `entity_ref_id` on a QC defect, and `record_id` on a package record — and each is resolved against the entity named by its sibling type field, raising that entity's not-found code. These three fields are intentionally *not* canonical foreign keys and no referential integrity is enforced on them after the initial resolution.

Schema-level failures all collapse into `ERR_INVALID_REQUEST` (HTTP 400): a required field missing or null, a field of the wrong JSON type, a string outside its length bound, an enum value outside its declared set, a negative integer where a non-negative one is required, a `latitude` outside the range of −90 through 90 or a `longitude` outside −180 through 180, a malformed datetime, a bad pagination parameter, or a mutually exclusive scope pair supplied wrongly.

Attempting a transition that the target record's current state does not define — including repeating a transition already performed, since idempotency is *not* granted anywhere in this system, and including any action on a terminal state — yields that entity's invalid-state code with HTTP 409: `ERR_ROAD_INVALID_STATE`, `ERR_ADDRESS_POINT_INVALID_STATE`, `ERR_BOUNDARY_INVALID_STATE`, `ERR_REPORT_INVALID_STATE`, `ERR_DEFECT_INVALID_STATE`, `ERR_PACKAGE_INVALID_STATE` or `ERR_CASE_INVALID_STATE`. The address assignment request is the one entity that splits this code in two, because it carries three parallel state dimensions: when the fulfillment dimension is wrong for the requested action the code is `ERR_REQUEST_NOT_READY`, and when the review or utility dimension is wrong the code is `ERR_REQUEST_INVALID_STATE`.

### 2.8. Numeric Precision and Rounding

Every score in this system is a JSON number, never a string, carried to exactly two decimal places and rounded half up. That applies to `confidence_score`, `certified_confidence_score`, `quality_score`, `advisory_quality_score` and `provisioning_eligibility_score` alike.

Where a calculation clamps a value into a range, the clamp is applied **after** all terms have been summed and **before** the two-decimal rounding. Where a calculation rounds more than once — the quality score rounds once per scoring category and then once again on the sum of the categories — the declared order is normative and must not be collapsed into a single final rounding, because the two orders produce observably different results. Counters (`cell_count`, `defect_count`, `round_count`, `package_version` and their kin) are plain integers, and interval and house-number arithmetic is integer arithmetic throughout.

### 2.9. Version Pinning, Drift and the Cascade Discipline

A sealed provisioning package holds a **pin** for each record it captured: a `PackageRecord` row carrying `pinned_version`, the pinned record's `version` at the moment of sealing. A pin is `FRESH` while `pinned_version` still equals the live record's `version`, and it flips to `STALE` the instant that live version advances, stamping `staled_at` with the logical clock instant. Whenever any mutation increments the `version` of a record that some `FRESH` pin refers to — matched on the pin's `record_type` together with its `record_id` — that pin flips to `STALE` and its owning package recounts `fresh_pin_count` and `stale_pin_count` and re-derives `drift_detected`, which is true exactly when `stale_pin_count` is greater than zero.

What that drift *costs* depends on why it happened, and the distinction is one of the most consequential rules in this specification. **Destructive drift** occurs when the mutation moved the pinned record into a terminal status — an `AddressPoint` reaching `RETIRED` or `VOIDED`, a `RoadCenterline` reaching `RETIRED`, or an `EmergencyServiceBoundary` reaching `RETIRED`. The snapshot can then never be published, because the record no longer exists in the field, so a `SEALED` package transitions to `INVALIDATED` with `invalidated_reason` set to `PIN_STALE`. **Non-destructive drift** occurs when the pinned record merely changed while remaining in service — re-scored by a confidence refresh, re-validated, re-published, stamped by a QC certification, or edited. In that case the package **stays** `SEALED` with `drift_detected` true and `stale_pin_count` above zero, and is refused at publication time with `ERR_PACKAGE_PINS_STALE`. That refusal is the only path to that error code. A drifted sealed package is never repaired in place: the provisioning officer opens a fresh package and seals it again. A package that is already `PUBLISHED` stays `PUBLISHED` under either kind of drift, merely flagged with `drift_detected` true; a `DRAFT` package holds no pins at all and is therefore immune.

When a package has already been invalidated, the `invalidated_reason` recorded by the *first* invalidating rule to fire in the declared cascade order is kept. Later invalidating rules in the same request neither overwrite that reason nor increment the package's `version` a second time.

Pin staleness is evaluated after each individual record mutation, in the declared cascade order of the triggering transition, before the cascade advances to its next level. Three other refresh rules obey the same discipline. Whenever a `BoundaryCellAssignment` row is created or changes status, or a `CoverageCell` is created, the owning `Jurisdiction` recomputes `cell_count`, `covered_cell_count`, `gap_pair_count` and `forward_gap_pair_count`, and each affected `CoverageCell` recomputes `active_assignment_count`. Whenever an address point on a centerline is created or changes status, or the centerline's range or parity fields change, that centerline recomputes `assignable_slot_count_left` and `assignable_slot_count_right`. And whenever a centerline's `status` changes or an address point's own scoring inputs change, every address point on that centerline whose `status` is `PENDING` or `ACTIVE` recomputes its `confidence_score` under the provisional variant — processed in order of `house_number` ascending and then `created_at` ascending, each point incrementing its own `version` by 1.

### 2.10. Segregation of Duties

Three separations of duty are enforced because the data being handled routes emergency calls, and one person must not be able to both produce it and bless it.

A QC validation report records the operator who ran the scan in `generated_by_user_id`. That same identifier may not certify the report: if `X-User-ID` on the certify request equals the report's `generated_by_user_id`, the request is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). Certification records the certifier in `certified_by_user_id`, and that identifier in turn may not publish a provisioning package built on the report: if `X-User-ID` on the publish request equals the referenced report's `certified_by_user_id`, the same `ERR_SEGREGATION_OF_DUTIES` is returned. The third separation lives in the discrepancy workflow: the agency side that authored the currently pending proposal may neither concur with it nor counter it, and either attempt is rejected with `ERR_SELF_CONCURRENCE` (HTTP 403).

### 2.11. Uniqueness, Immutability and Historical Retention

Four uniqueness constraints are enforced, each with its own code and all at HTTP 409. A jurisdiction's `code` is globally unique, violated with `ERR_DUPLICATE_JURISDICTION_CODE`. A coverage cell's `cell_code` is unique within its `jurisdiction_id`, violated with `ERR_DUPLICATE_CELL_CODE`. An assignment request's `permit_number` is globally unique, and the constraint holds against voided and rejected requests as well, violated with `ERR_DUPLICATE_PERMIT_NUMBER`. And an address point is unique on the combination of its `road_centerline_id`, `side`, `house_number`, `house_number_suffix` and `unit_id`, treating nulls as equal, but **only among points whose `status` is `PENDING` or `ACTIVE`** — violated with `ERR_DUPLICATE_ADDRESS`. Points in `RETIRED` or `VOIDED` status do not block reuse of their key, and that is precisely what makes permanent historical retention compatible with re-issuing an address to a rebuilt structure.

Retention is absolute: nothing is ever hard-deleted. Retired and voided address points remain stored forever and remain reachable to records research, which reads them by asking for historical rows explicitly rather than by default.

## 3. Business Logic & Workflows

### 3.1. Jurisdictions, Responding Agencies and the Coverage Cell Grid

Everything in the county rests on three configuration records that a `SystemAdmin` establishes first. Registering a **jurisdiction** captures its display `name` (one to 120 characters, non-blank), a short `code` used on provisioning exports (two to eight characters drawn from uppercase letters and digits, globally unique), a `jurisdiction_type` of `COUNTY`, `MUNICIPAL` or `UNINCORPORATED`, and the authoritative `postal_city` string for addresses inside it (one to 60 characters, stored uppercased whatever case the caller sent). A new jurisdiction begins with all four of its coverage counters — `cell_count`, `covered_cell_count`, `gap_pair_count` and `forward_gap_pair_count` — initialised to zero. Jurisdictions may be listed and narrowed by `jurisdiction_type` or by `code`.

Registering a **responding agency** captures its `name` (one to 120 characters, non-blank), its `agency_type` — exactly one of `LAW`, `FIRE` or `EMS` — the `jurisdiction_id` of the jurisdiction that charters it, and an optional `contact_phone` that defaults to null and is purely informational. A new agency's `status` is initialised to `ACTIVE`, and its `suspended_reason` is null. An administrator may suspend an agency, supplying `suspended_reason`; the agency's `status` becomes `SUSPENDED` and its `version` increments by 1. A `SUSPENDED` agency retains its existing active boundaries but may not activate new ones and may not be named as a party to a new discrepancy case — either attempt is refused with `ERR_AGENCY_NOT_ACTIVE`. Agencies may be listed and narrowed by `jurisdiction_id`, `agency_type` or `status`.

A **coverage cell** is the atomic geographic unit of this system: emergency service boundaries claim cells, and address points are stamped with the cell they fall in. Creating one — the single write operation shared between `SystemAdmin` and `GisAnalyst` — captures a `cell_code` (one to 12 characters of uppercase letters and digits, unique inside its `jurisdiction_id`), the `jurisdiction_id` it belongs to, and optional informational `centroid_lat` and `centroid_lon` values that default to null and are never consulted in any business decision. The new cell's `active_assignment_count` starts at zero, and creating it refreshes the owning jurisdiction's counters — which means `cell_count` rises and, since a brand-new cell is claimed by nobody, the gap counters rise with it. Cells may be listed and narrowed by `jurisdiction_id` or `cell_code`.

Coverage integrity is measured two different ways, and the difference between them decides whether a dispatch release may go out. Under the **instantaneous** view, a boundary cell assignment covers an instant when its `status` is `ACTIVE` and the instant falls within its half-open window. For every pairing of a cell with one of the three service types, the covering set is the set of `ACTIVE` assignments of that service type on that cell that cover the logical clock instant now: a covering set of size zero makes the pair a **gap**, and a covering set of size two or more makes it an **overlap** — a condition reachable in practice only through pending rows, because activation refuses active overlaps outright. A jurisdiction's `gap_pair_count` is the number of gap pairs across all of its cells taken against all three service types; its `covered_cell_count` is the number of its cells that have exactly one covering `ACTIVE` assignment for **all three** service types simultaneously; and a cell's own `active_assignment_count` is the number of `ACTIVE` assignments covering the current instant on that cell, summed across service types.

Under the **forward-window** view, the horizon runs from the current logical instant up to but not including thirty days later. For each cell-and-service-type pair, the `ACTIVE` assignments' half-open windows are clipped to that thirty-day horizon and merged, and the pair counts as a **forward gap** when the merged union does not cover the whole horizon. The count of forward-gap pairs is the jurisdiction's `forward_gap_pair_count`, and it is the only counter the dispatch publication gate reads. The two views diverge exactly when an assignment covers the present instant but expires inside the horizon, or when a successor assignment starts later than its predecessor ends. Consider a cell whose three service types are all covered by open-ended active assignments: both `gap_pair_count` and `forward_gap_pair_count` are zero. Retire the `LAW` boundary and both become 1. Instead give the `LAW` assignment an `effective_end` ten days out with no successor and the two disagree — `gap_pair_count` stays at 0 because the assignment covers this instant, while `forward_gap_pair_count` becomes 1 — and only the forward number blocks a dispatch release.

A computed read on a single cell exposes both views side by side, answering with the `cell_id`, an `evaluated_at` stamp of the logical instant the answer was computed at, the `covered_service_types` array, the `gap_service_types` array, the `proposed_conflict_service_types` array (service types on which two assignments with intersecting windows exist where at least one is still pending), a `responding_assignment_count` giving the number of active assignments answering on that cell now, and the `forward_gap_service_types` array derived from the thirty-day horizon. The three service types form an **ordered** constant, `LAW` then `FIRE` then `EMS`, and every one of those four arrays is produced by filtering that sequence in that order. Alphabetical ordering and insertion ordering are both wrong.

### 3.2. Road Centerline Maintenance: Names, Ranges and the Validation Ladder

A `GisAnalyst` creates a **road centerline** by supplying its `primary_name` — the road name exactly as the county maintains it, spelling preserved verbatim, one to 120 characters and non-blank — the `jurisdiction_id` the segment falls in, and both address ranges in full: `from_addr_left`, `to_addr_left` and `parity_left` for the left side, and `from_addr_right`, `to_addr_right` and `parity_right` for the right. Each bound is an integer from 0 through 999999, each parity is `EVEN` or `ODD`, and the two sides' parities must differ from each other. Both sides are mandatory at creation. The new centerline lands in `DRAFT` status with `qc_dirty` true, `open_discrepancy_case_count` at zero, and both slot counters set to the side's full capacity. Centerlines may be listed and narrowed by `jurisdiction_id`, by `normalized_name` or by `status`.

The county's spelling is preserved, but road *identity* is not the county's spelling — it is a derived key. The `normalized_name` is computed from `primary_name` at creation and recomputed whenever `primary_name` changes, in five steps. First, uppercase the primary name. Second, delete every character that is not a letter, a digit or a space. Third, collapse every run of consecutive spaces into a single space and strip leading and trailing spaces. Fourth, split the result on spaces and examine only the **last** token: if that last token is one of the recognised road-type abbreviations, replace it with its expansion — `ST` becomes `STREET`, `RD` becomes `ROAD`, `AVE` becomes `AVENUE`, `DR` becomes `DRIVE`, `LN` becomes `LANE`, `HWY` becomes `HIGHWAY`, `CT` becomes `COURT`, and `BLVD` becomes `BOULEVARD`. An abbreviation appearing in any earlier position — a directional prefix, or a name that merely happens to match — is left exactly as it is. Fifth, re-join the tokens with single spaces. So "N. Maple St" uppercases to "N. MAPLE ST", loses its punctuation to become "N MAPLE ST", and expands its final token to `N MAPLE STREET`. "Oak Ln" and "Oak Lane" both normalize to `OAK LANE`, which is exactly why they collide in the overlap and duplicate checks. "St Andrews Ct" normalizes to `ST ANDREWS COURT`, because the leading `ST` is not the last token and is therefore untouched.

Range geometry is checked on creation and on every edit. For either side, the low bound must not exceed the high bound, both bounds must have the parity declared for that side, and a side may not supply only one of its two bounds. On an edit the check is evaluated against the **merged** result of the stored record and the supplied changes, not against the changes alone. A failure here is `ERR_RANGE_GEOMETRY_INVALID` (HTTP 422).

Editing a centerline is the system's first optimistic-concurrency operation. The payload carries `expected_road_version` and may carry any subset of `primary_name`, `from_addr_left`, `to_addr_left`, `parity_left`, `from_addr_right`, `to_addr_right` and `parity_right`. Three preconditions must hold: the supplied `expected_road_version` equals the centerline's stored `version`, the centerline's `open_discrepancy_case_count` is zero, and the resulting range geometry is valid. An edit of a `DRAFT` centerline leaves it in `DRAFT` — `DRAFT → DRAFT` is a real transition, not a no-op — while an edit of a `VALIDATED` centerline **demotes** it, `VALIDATED → DRAFT`, because a validated road whose name or ranges have moved must be re-validated before it may be published again. Either way the edit recomputes `normalized_name` when `primary_name` changed, sets `qc_dirty` to true, refreshes both assignable-slot counters, and increments the centerline's `version` by 1, after which pin staleness is evaluated for that centerline. The demoting edit additionally triggers a confidence refresh across the road's non-terminal address points, because the road-status penalty in the confidence formula moves from 5 up to 15 as the road falls back to `DRAFT`, and pin staleness is then evaluated for the centerline and for every recomputed address point.

Validating a `DRAFT` centerline advances it `DRAFT → VALIDATED`. Three preconditions apply: the centerline's `open_discrepancy_case_count` is zero, its range geometry is valid, and its ranges do not overlap any *other* centerline's ranges under the conflict test below when that peer's `status` is `VALIDATED` or `PUBLISHED`. Peers still in `DRAFT` do **not** block validation — they surface later as a QC scan finding instead. A blocking overlap is `ERR_ROAD_RANGE_OVERLAP` (HTTP 409). Validation sets `qc_dirty` to false, increments the centerline's `version` by 1, triggers a confidence refresh in which the road-status penalty moves from 15 down to 5, and then evaluates pin staleness for the centerline and each recomputed address point.

The conflict test itself works on closed integer intervals. A centerline contributes up to two of them: its left interval running from `from_addr_left` through `to_addr_left` inclusive and carrying `parity_left`, and its right interval running from `from_addr_right` through `to_addr_right` inclusive and carrying `parity_right`. Two intervals belonging to *different* centerlines conflict when all four of the following hold: they share the same `jurisdiction_id`; they share the same `normalized_name`; they carry the same parity value; and the closed intervals intersect, meaning the greater of the two low bounds is less than or equal to the lesser of the two high bounds. The left and right intervals of the *same* centerline are never compared against each other. Because a conflicting pair always carries the same parity, two intervals that are separated by a gap of one — an `EVEN` interval ending at 198 and an `EVEN` interval starting at 199 — cannot share any house number and therefore do not conflict; the smallest genuinely conflicting configuration shares exactly one endpoint value, as when an `EVEN` interval running 100 through 198 meets an `EVEN` interval running 198 through 298 and 198 belongs to both. Adjacency with no shared value, such as `EVEN` 100 through 198 against `EVEN` 200 through 298, is explicitly permitted. For a worked case: a centerline named "N Maple St" with left interval 100 through 198 `EVEN` conflicts with a candidate named "N. Maple Street" whose left interval is 150 through 248 `EVEN`, because the normalized names both reduce to `N MAPLE STREET`, the parities match, and the greater low bound 150 does not exceed the lesser high bound 198; the same candidate shifted to 200 through 298 is allowed, because 200 exceeds 198.

Publication of a centerline belongs to the `QcCertifier`, not the analyst, and advances it `VALIDATED → PUBLISHED`. It requires that `qc_dirty` be false and that `open_discrepancy_case_count` be zero. Publication increments the centerline's `version` by 1 and triggers a confidence refresh in which the road-status penalty moves from 5 down to 0, followed by pin-staleness evaluation for the centerline and each recomputed point. A published centerline is what makes a road eligible to appear in a provisioning package.

A published road does not stay published unconditionally. When a discrepancy case is adopted or arbitrated against that centerline, the system writes the resolved value into it and demotes it `PUBLISHED → VALIDATED`, and it must be re-published afterwards. The demotion mechanics are described in §3.8.

The number of addresses a side can still absorb is tracked continuously. For each side, capacity is computed as the difference between the side's high bound and its low bound, divided by two with any fraction discarded, plus one. Consumption is the number of address points on that centerline and that side whose `unit_id` is null and whose `status` is `PENDING` or `ACTIVE` and whose `house_number` lies within the side's inclusive bounds. The side's assignable slot count is the capacity minus the consumption, floored at zero so it never goes negative. Subaddress units never consume a slot, because they share their parent's `house_number`; and points in `RETIRED` or `VOIDED` status release the slot they were holding. A left range of 100 through 198 `EVEN` therefore has a capacity of ninety-eight halved and floored, giving 49, plus one, giving 50; one `ACTIVE` base point at 100 and one `PENDING` base point at 102 consume two, leaving `assignable_slot_count_left` at 48. Adding four subaddress units beneath the point at 100 leaves it at 48. Voiding the point at 102 returns it to 49.

Retiring a centerline is available from `DRAFT`, from `VALIDATED` and from `PUBLISHED`, is performed by a `GisAnalyst` supplying `retire_reason`, and requires only that `open_discrepancy_case_count` be zero. The centerline moves to `RETIRED`, which is terminal, with `retired_at` stamped at the logical clock instant and `retire_reason` recorded from the payload, and its `version` increments by 1. The retirement then cascades in strictly ordered levels. At level 2, every **base** address point on that road — those whose `unit_id` is null — whose `status` is `PENDING` or `ACTIVE`, processed in order of `house_number` ascending and then `created_at` ascending, transitions to `RETIRED` with `retire_reason` set to `ROAD_RETIRED`. At level 3, caused by level 2 rather than by the retire call itself, every subaddress point whose `parent_address_point_id` is one of the base points just retired and whose `status` is `PENDING` or `ACTIVE` transitions to `RETIRED` with `retire_reason` set to `PARENT_RETIRED`; units are reached **only** through their parent and never directly by level 2. At level 4, caused by level 3, every `FRESH` package pin referring to any record retired in levels 1 through 3 flips to `STALE`. At level 5, caused by level 4, every provisioning package whose `status` is `SEALED` and whose `stale_pin_count` has just become greater than zero transitions to `INVALIDATED` with `invalidated_reason` set to `PIN_STALE` — this is destructive drift, because the retired records no longer exist in the field. The road's assignable-slot counters are refreshed as part of the same request.

A contested centerline is frozen. Whenever `open_discrepancy_case_count` is greater than zero, five operations are refused with `ERR_ROAD_FROZEN_BY_DISCREPANCY` (HTTP 409): editing the centerline, validating it, publishing it, retiring it, and activating any address point that sits on it. The freeze lifts only when the case is adopted or arbitrated.

### 3.3. Authoring Address Points, Subaddress Units and Confidence Scoring

An address point is the county's assertion that a particular place has a particular address. A `GisAnalyst` authors one by supplying the required `house_number` (an integer from 0 through 999999), the `road_centerline_id` of the centerline the address is ranged against, the `side` of that centerline — `LEFT` or `RIGHT`, which selects which range-and-parity pair governs — the authoritative `source` the address was derived from (`PARCEL`, `PERMIT`, `POSTAL` or `FIELD`), the `postal_city` asserted for the address (one to 60 characters, stored uppercased), and the `cell_id` of the coverage cell the point falls in, which is what drives emergency response routing for that address. Six further fields are optional: `house_number_suffix`, an alpha suffix of up to four uppercase letters such as "A" that defaults to null and forms part of the duplicate-address key; `unit_type`, `unit_id` and `parent_address_point_id`, which together describe a subaddress unit and all default to null; `geometry_verified`, a boolean defaulting to false; and the informational `latitude` and `longitude`, both defaulting to null and never consulted in any business decision.

Two fields are never supplied by the caller. The point's `jurisdiction_id` is copied from the referenced centerline's `jurisdiction_id` at creation and is never independently editable afterwards. And `status` begins as `PENDING`, meaning authored but not yet authoritative. The other three statuses are `ACTIVE`, meaning provisionable and live; `RETIRED`, meaning historical but retained for records research; and `VOIDED`, meaning the address never existed in the field at all. `RETIRED` and `VOIDED` are both terminal.

Creation runs four domain checks in a fixed order, and the first to fail is the one reported. **First**, subaddress shape. `unit_id` may not be supplied without `parent_address_point_id`, nor `parent_address_point_id` without `unit_id`; `unit_type` may not be supplied without `unit_id`; the nominated parent may not itself have a non-null `parent_address_point_id`, because units may not nest; the parent's `status` may be neither `RETIRED` nor `VOIDED`; the parent's `road_centerline_id` and `side` must both equal the child's; and the child's `house_number` must equal the parent's, since a unit shares its parent's number. Any of these is `ERR_SUBADDRESS_PARENT_INVALID` (HTTP 422). **Second**, parity: the parity of `house_number` must match the referenced road's declared parity for the chosen `side`, or the creation fails with `ERR_ADDRESS_PARITY_MISMATCH` (HTTP 422). **Third**, range membership: `house_number` must lie inside the closed interval formed by the chosen side's low and high bounds, both endpoints being perfectly valid addresses, or the creation fails with `ERR_ADDRESS_OUTSIDE_RANGE` (HTTP 422). **Fourth**, duplication: the combination of `road_centerline_id`, `side`, `house_number`, `house_number_suffix` and `unit_id` must not already be held by a point whose `status` is `PENDING` or `ACTIVE`, or the creation fails with `ERR_DUPLICATE_ADDRESS` (HTTP 409). Placing subaddress shape ahead of the geometry checks is deliberate: a malformed unit payload is reported as a subaddress problem rather than being masked by a parity or range complaint on a number that was only ever inherited from its parent.

A successful creation computes the point's `confidence_score` under the provisional variant, sets `confidence_basis` to `PROVISIONAL`, leaves `certified_confidence_score` null, increments the nominated parent's `unit_child_count` when a `unit_id` was supplied, and refreshes the centerline's assignable-slot counters. The `unit_child_count` on any point is the number of points whose `parent_address_point_id` equals it and whose `status` is `PENDING` or `ACTIVE`. Valid subaddress designators for `unit_type` are `UNIT`, `APT`, `STE` and `BLDG`; `unit_id` itself is up to eight characters of uppercase letters and digits, such as "3B".

**Confidence scoring** is the system's quantified statement of how much it trusts an address, and it exists in two variants that deliberately diverge. The **provisional** variant is computed on creation, on activation, and on every confidence refresh; it writes `confidence_score` and leaves `certified_confidence_score` null with `confidence_basis` at `PROVISIONAL`. Its raw value is assembled by starting from the base weight for the point's `source` — 70 for `PARCEL`, 60 for `PERMIT`, 45 for `POSTAL`, and 80 for `FIELD` — then adding 12 when `geometry_verified` is true, adding 8 when the point's `postal_city` equals the postal city of its jurisdiction, adding 6 when `unit_id` is null (that is, when the point is a base address rather than a unit), and finally subtracting the road-status penalty, which is 15 while the centerline is `DRAFT`, 5 while it is `VALIDATED` and 0 once it is `PUBLISHED`. The raw sum is then clamped into the range 0 through 100 and rounded half up to two decimal places, in that order.

The **certified** variant is computed only inside the certification of a QC validation report, and only for the address points in that report's scope. It writes `certified_confidence_score`, sets `confidence_basis` to `CERTIFIED`, and deliberately leaves the provisional `confidence_score` untouched so that the delta between the two remains inspectable. Its raw value uses all of the same terms as the provisional variant and then adds two more: a bonus of 10 when the point's coverage cell has zero gap pairs at the logical clock instant — that is, when all three service types are covered there — and a penalty of 20 when the point's centerline has an `open_discrepancy_case_count` greater than zero. The result is likewise clamped into 0 through 100 and then rounded half up to two decimal places.

The clamp is where the two variants stop being a constant offset apart, and that is the point of having both. A `PARCEL`-sourced, geometry-verified, postal-matching base point on a `PUBLISHED` road scores 70 plus 12 plus 8 plus 6 with no penalty, giving a provisional 96.00. Certified on a fully covered cell it would raise to 106, which clamps to 100.00 — so the certified variant diverges by 4.00, not by the 10.00 the bonus suggests. A `FIELD`-sourced, geometry-verified base point on a `PUBLISHED` road already sits at 80 plus 12 plus 8 plus 6, which is 106 and clamps to a provisional 100.00, and certifies to 100.00 as well for a delta of zero. That same point, with its road under an open discrepancy case, certifies to 106 less 20, clamped and rounded to 86.00.

**Activation** advances a point `PENDING → ACTIVE` and is the analyst's declaration that the address is authoritative and provisionable. Three preconditions apply: the referenced centerline's `status` must be `VALIDATED` or `PUBLISHED`; that centerline's `open_discrepancy_case_count` must be zero; and when the point carries a non-null `unit_id`, its parent point's `status` must be `ACTIVE`. Activation recomputes `confidence_score` under the provisional variant, increments the point's `version` by 1, refreshes the road's slot counters — with no net change, since `PENDING` and `ACTIVE` both consume a slot — refreshes the parent's `unit_child_count` when the point is a unit, and evaluates pin staleness for the point. Activating a point whose centerline is still `DRAFT` or already `RETIRED` is refused with `ERR_ROAD_INVALID_STATE`, because the blocking state belongs to the road rather than to the point; activating a point that is not `PENDING` is refused with `ERR_ADDRESS_POINT_INVALID_STATE`; and activating a point on a contested road is refused with `ERR_ROAD_FROZEN_BY_DISCREPANCY`.

**Retirement** is available from `PENDING` and from `ACTIVE` alike, is performed by a `GisAnalyst` supplying `retire_reason` and optionally `superseded_by_address_point_id`, and behaves identically from either origin state. When a successor is supplied it must reference an address point whose `status` is `PENDING` or `ACTIVE`. The point moves to `RETIRED` with `retired_at` stamped at the logical clock instant, and `retire_reason` is recorded as `REPLACED` when a successor was supplied and as `ANALYST_RETIRED` when it was not. The point's `version` increments by 1. Every point whose `parent_address_point_id` equals the retired point and whose `status` is `PENDING` or `ACTIVE` then transitions to `RETIRED` with `retire_reason` set to `PARENT_RETIRED`. The road's slot counters are refreshed — retiring a base address frees exactly one slot, while retiring a unit frees none — and pin staleness is evaluated for every mutated record. Retiring an already `RETIRED` or `VOIDED` point is refused with `ERR_ADDRESS_POINT_INVALID_STATE`.

Two further paths into a terminal state are driven by the system rather than by an analyst. A point in `PENDING` or in `ACTIVE` is retired by cascade when its owning centerline is retired (level 2 of the road cascade, `retire_reason` `ROAD_RETIRED`) or when its parent point is retired (level 3, `retire_reason` `PARENT_RETIRED`); in either case `retired_at` is stamped at the logical clock instant, the point's `version` increments by 1, and pin staleness is evaluated. Separately, a point in `PENDING` or in `ACTIVE` is voided by cascade when the address assignment request that minted it is voided, provided the point's own `id` equals that request's `assigned_address_point_id` or its `parent_address_point_id` does; `retire_reason` is set to `REQUEST_VOIDED`, `retired_at` is stamped, the point's `version` increments by 1, the consumed slot is released through a slot refresh, and pin staleness is evaluated. The complete set of reasons a point may carry for leaving service is therefore `ROAD_RETIRED`, `PARENT_RETIRED`, `REPLACED`, `ANALYST_RETIRED` and `REQUEST_VOIDED`.

Reading address points supports records research directly. A single-point read returns both confidence numbers side by side. The listing operation excludes `RETIRED` and `VOIDED` points by default and includes them only when `include_retired` is requested as true — that flag is how a title researcher reaches historical addresses at all — and the listing may be narrowed by `road_centerline_id`, by `parent_address_point_id` to walk down a subaddress family, by `superseded_by_address_point_id` to walk a supersession chain, by `cell_id`, by `jurisdiction_id`, by `status` and by `side`.

### 3.4. Assigning Addresses to New Construction

New construction arrives at the county through the permit office, not through the GIS shop, and the assignment workflow reflects that split of authority. A `PermitCoordinator` opens an **address assignment request** carrying the building `permit_number` the assignment is requested for (one to 32 characters, globally unique across every request ever opened, including voided and rejected ones — a collision is `ERR_DUPLICATE_PERMIT_NUMBER`), the assessor's `parcel_id` supplied by the permit office (one to 32 characters), the `road_centerline_id` of the centerline the new construction fronts, and the `side` of that centerline the parcel fronts, which selects the range-and-parity pair used for number selection. Two optional fields shape the outcome: `requested_unit_count`, the number of subaddress units to mint beneath the base address, an integer from 0 through 99 that defaults to 0 and where 0 means a base address only; and `proposed_house_number`, an operator-preferred number that defaults to null.

A request carries **three parallel state dimensions**, and understanding that they are genuinely independent is the key to the whole workflow. The `review_status` dimension tracks GIS review and begins at `PENDING_REVIEW`, moving to either `GIS_APPROVED` or `GIS_REJECTED`. The `utility_status` dimension tracks utility coordination and begins at `PENDING_UTILITY`, moving to `UTILITY_CLEARED` or `UTILITY_HELD`. The `fulfillment_status` dimension is **derived** from the join of the first two plus the assignment and void outcomes; it begins at `OPEN` and may reach `READY_TO_ASSIGN`, `FULFILLED`, `CLOSED_REJECTED` or `VOIDED`, of which the last three are terminal.

The GIS review decision is recorded by a `GisAnalyst`, who supplies a `decision` of either `APPROVE` or `REJECT` and an optional free-text `review_note`. Review requires that `review_status` still be `PENDING_REVIEW` and that `fulfillment_status` be `OPEN`; reviewing an already-reviewed request is refused with `ERR_REQUEST_INVALID_STATE`. An approval moves `review_status` from `PENDING_REVIEW` to `GIS_APPROVED` and increments the request's `version` by 1; if `utility_status` is already `UTILITY_CLEARED` at that moment, the derived join promotes `fulfillment_status` to `READY_TO_ASSIGN`. A rejection moves `review_status` from `PENDING_REVIEW` to `GIS_REJECTED`, increments the `version` by 1, and drives `fulfillment_status` to `CLOSED_REJECTED` **regardless of what `utility_status` holds** — a rejected review closes the request outright, and no later utility action can reopen it.

The utility dimension is handled by the `PermitCoordinator`, who supplies a `decision` of either `CLEAR` or `HOLD` together with an optional free-text `utility_note`. Every utility action requires that `fulfillment_status` be `OPEN` or `READY_TO_ASSIGN`; clearing or holding utilities on a closed request is refused with `ERR_REQUEST_INVALID_STATE`. Unlike the review dimension, the utility dimension **cycles**: a hold may be lifted and a clearance may be re-held, without limit. Clearing from `PENDING_UTILITY` to `UTILITY_CLEARED` increments the `version` by 1 and, when `review_status` is already `GIS_APPROVED`, promotes `fulfillment_status` to `READY_TO_ASSIGN`. Holding from `PENDING_UTILITY` to `UTILITY_HELD` increments the `version` by 1 and leaves `fulfillment_status` at `OPEN`. Lifting a hold, `UTILITY_HELD → UTILITY_CLEARED`, increments the `version` by 1 and again promotes `fulfillment_status` to `READY_TO_ASSIGN` when `review_status` is `GIS_APPROVED`. Re-imposing a hold, `UTILITY_CLEARED → UTILITY_HELD`, increments the `version` by 1 and **demotes** `fulfillment_status` from `READY_TO_ASSIGN` back to `OPEN` when it was sitting there. All four of these utility transitions are equally available and are specified with the same force; the cycle is a designed feature of the workflow, not an accident.

**Minting the address** is performed by a `GisAnalyst` and moves `fulfillment_status` from `READY_TO_ASSIGN` to `FULFILLED`. It requires that `fulfillment_status` be exactly `READY_TO_ASSIGN` — any other value, whether because review is not approved, utility is not cleared, or the request is already fulfilled, is refused with `ERR_REQUEST_NOT_READY` — and that the referenced centerline's `status` be `DRAFT`, `VALIDATED` or `PUBLISHED`, which is to say not `RETIRED`. Two further preconditions come from number selection: the candidate set for the request's centerline and `side` must be non-empty, and when `proposed_house_number` was supplied it must be a member of that candidate set.

Number selection works on the request side's range on the referenced centerline. The candidate set is every integer at or above the side's low bound and at or below its high bound — the interval is closed, so both endpoints are themselves candidates — whose parity matches the side's declared parity, and for which no address point already exists on that same centerline and `side` with that `house_number`, a null `unit_id`, and a `status` of `PENDING` or `ACTIVE`. If the candidate set is empty the range is exhausted and the request is refused with `ERR_NO_ASSIGNABLE_ADDRESS` (HTTP 409). If `proposed_house_number` was supplied it must be a member of the candidate set — it may be taken already, of the wrong parity, or outside the range, and any of those refuses the request with `ERR_HOUSE_NUMBER_UNAVAILABLE` (HTTP 409) — and when it is a member it is used verbatim. Otherwise `assigned_house_number` is the **smallest** member of the candidate set, so the lowest gap is reused before the range is extended, and a retired 102 is handed out again ahead of an untouched 104. To make that concrete: on a left range of 100 through 198 `EVEN` with `ACTIVE` base points at 100 and 104, the candidate set begins 102, 106, 108 and onward, and the smallest is 102. With `PENDING` points occupying 100 through 196 and an `ACTIVE` point at 198, the set is empty and the assignment fails with `ERR_NO_ASSIGNABLE_ADDRESS`. A `proposed_house_number` of 198 on an otherwise empty range is accepted, because the upper bound is inclusive; a `proposed_house_number` of 200 is not in the range at all and so is not a member, yielding `ERR_HOUSE_NUMBER_UNAVAILABLE`.

A successful mint writes `assigned_house_number`, then creates the address points. One **base** point is minted in `PENDING` status with `source` set to `PERMIT`, `unit_id` null, `geometry_verified` false, `postal_city` taken from the postal city of the centerline's jurisdiction, and `cell_id` set to the coverage cell of that jurisdiction with the lowest `cell_code` — or null when the jurisdiction holds no cells at all. Then exactly as many subaddress points as `requested_unit_count` are minted, each in `PENDING` with `source` `PERMIT`, `unit_type` `UNIT`, `parent_address_point_id` pointing at the base point, and `unit_id` running "1" through the requested count in ascending numeric order. The request records `assigned_address_point_id` as the base point's identifier and `minted_point_count` as one plus `requested_unit_count` — a count that stands regardless of what happens to those points later. The centerline's slot counters are refreshed, the base point consuming exactly one slot while the units consume none, and the request's `version` increments by 1.

**Voiding** a request is the `PermitCoordinator`'s compensating action and is reachable from `OPEN`, from `READY_TO_ASSIGN` and from `FULFILLED`. The coordinator supplies `void_reason`; `fulfillment_status` becomes `VOIDED` and the request's `version` increments by 1. From `OPEN` or from `READY_TO_ASSIGN` there is nothing further to undo, since no points were ever minted. From `FULFILLED` the void reaches into the minted data: every address point the request created — the base point and each of its units, processed with the base point first and then the units in ascending `unit_id` order — transitions to `VOIDED` with `retire_reason` set to `REQUEST_VOIDED`, the centerline's slot counters are refreshed so that the assignable count for that side is restored to exactly its pre-assignment value, and pin staleness is evaluated for each voided point. Because voiding drives points into a terminal status, any sealed package that had pinned one of them suffers destructive drift and is invalidated.

Requests may be read individually, showing all three dimensions at once, and listed with narrowing on `road_centerline_id`, on `assigned_address_point_id`, on each of `review_status`, `utility_status` and `fulfillment_status` independently, and on `permit_number`.

### 3.5. Emergency Service Boundaries and Cell Claims

An **emergency service boundary** is one agency's claim to respond inside a set of coverage cells over a stated period of time. An `AgencyLiaison` creates one for its own agency, supplying the `agency_id` — which must equal `X-User-ID`, since a liaison may not create a boundary on another agency's behalf — together with `effective_start`, the inclusive beginning of the boundary's service window, and optionally `effective_end`, the **exclusive** end of that window, which defaults to null meaning open-ended. The boundary's `service_type` is not supplied by the caller: it is copied from the owning agency's `agency_type` at creation, so a boundary can never disagree with its agency about which emergency service it provides. The new boundary lands in `DRAFT` status with `assigned_cell_count` at zero and `retired_at` and `retire_reason` both null. A boundary whose `effective_end` is non-null and is at or before its `effective_start` is refused with `ERR_BOUNDARY_WINDOW_INVALID` (HTTP 422) — zero-length and inverted windows are both rejected.

Cells are claimed one at a time while the boundary is still `DRAFT`, and each claim becomes a **boundary cell assignment** row. The claim payload carries the `cell_id` being claimed, the claim's own `effective_start`, the mandatory `expected_boundary_version`, and optionally the claim's `effective_end` which defaults to null. The assignment's `boundary_id` is taken from the parent named in the path of the creating call, and its `service_type` is copied from the parent boundary, which matters because the overlap key throughout this system is the pairing of `cell_id` with `service_type`. A new assignment lands in `PENDING` status. Three refusals guard the claim. Adding a claim to a boundary that has left `DRAFT` is `ERR_BOUNDARY_INVALID_STATE` (HTTP 409). A stale `expected_boundary_version` is `ERR_STALE_BOUNDARY_VERSION` (HTTP 412). And a window problem is `ERR_BOUNDARY_WINDOW_INVALID` (HTTP 422), which covers three distinct situations: the claim's `effective_end` being non-null and at or before its `effective_start`; the claim's window not being wholly contained inside the parent boundary's own half-open window; and the claimed cell's `jurisdiction_id` differing from the jurisdiction of the boundary's agency.

Once at least one cell has been claimed, the liaison **proposes** the boundary, advancing it `DRAFT → PROPOSED`. Two preconditions apply: `X-User-ID` must equal the boundary's `agency_id`, and `assigned_cell_count` must be at least 1. The transition increments the boundary's `version` by 1. Proposing freezes the cell set — from `PROPOSED` onward no further claims may be added, which is why the claim operation refuses anything that is not `DRAFT`. A boundary's `assigned_cell_count` is the number of its cell assignments whose `status` is `PENDING` or `ACTIVE`.

**Activation** is where coverage integrity is actually enforced, and it advances the boundary `PROPOSED → ACTIVE`. Three preconditions must hold. `X-User-ID` must equal the boundary's `agency_id`. The owning agency's `status` must be `ACTIVE`; a `SUSPENDED` agency is refused with `ERR_AGENCY_NOT_ACTIVE` (HTTP 409). And for every cell assignment on this boundary, no *other* `ACTIVE` cell assignment on the same pairing of `cell_id` and `service_type` may have a half-open window that intersects this one; a collision is refused with `ERR_COVERAGE_OVERLAP` (HTTP 409). Windows that merely touch, where the predecessor's `effective_end` exactly equals the successor's `effective_start`, do not intersect and are permitted — that is how an agency hands a cell over to its successor cleanly. Activation transitions every cell assignment on the boundary from `PENDING` to `ACTIVE`, each incrementing its own `version` by 1 and refreshing its owning cell's `active_assignment_count`, then refreshes the jurisdiction's coverage counters, then increments the boundary's `version` by 1.

Note the asymmetry that this creates and that the QC scan later reports on: two *pending* claims on the same cell and service type with intersecting windows are perfectly legal, because proposed boundaries are allowed to conflict on paper and activation is the gate that resolves the conflict. Only `ACTIVE` rows are held to the non-intersection rule.

**Retirement** is reachable from `ACTIVE` and from `PROPOSED`, is performed by the owning liaison — `X-User-ID` must equal the boundary's `agency_id` — and supplies `retire_reason`. The boundary moves to `RETIRED`, which is terminal, with `retired_at` stamped at the logical clock instant and `retire_reason` recorded from the payload, and its `version` increments by 1. Retiring from `ACTIVE` transitions every cell assignment on the boundary from `ACTIVE` to `RETIRED`, each incrementing its own `version` by 1 and refreshing its cell's `active_assignment_count`, refreshes the jurisdiction's coverage counters so that `covered_cell_count` and `gap_pair_count` return to exactly their pre-activation values, and evaluates pin staleness for the boundary — which, because `RETIRED` is terminal, is destructive drift and invalidates any sealed package that had pinned it. Retiring from `PROPOSED` transitions every cell assignment from `PENDING` to `RETIRED`, each incrementing its own `version` by 1, and refreshes the jurisdiction's counters; no active coverage was ever established, so nothing was pinning it. Acting on an already-`RETIRED` boundary, proposing a boundary that is not `DRAFT`, or activating a boundary that is not `PROPOSED` are all `ERR_BOUNDARY_INVALID_STATE`.

Cell assignments are never mutated directly by a client: their `status` mirrors the parent boundary's lifecycle, sitting at `PENDING` while the boundary is `DRAFT` or `PROPOSED`, at `ACTIVE` once the boundary activates, and at `RETIRED` once the boundary retires. They are readable in three ways: as the claim list of one boundary, narrowable by `status`; individually by their own identifier; and as a flat collection narrowable by `boundary_id`, `cell_id`, `service_type` and `status`, which is the query behind agency-side overlap and gap analysis. Boundaries themselves are readable individually and as a collection narrowable by `agency_id`, `service_type` and `status`.

### 3.6. Quality Control Scanning, Waivers and Certification

Nothing reaches a downstream consumer until a **QC validation report** has scanned the data and a human other than the scanner has certified it. A `GisAnalyst` generates a report by naming a `scope` of `FULL`, `JURISDICTION` or `ROAD`. The scope fields are mutually exclusive and strictly enforced: a `JURISDICTION`-scoped report requires `jurisdiction_id` and forbids `road_centerline_id`, a `ROAD`-scoped report requires `road_centerline_id` and forbids `jurisdiction_id`, and getting that pairing wrong is `ERR_INVALID_REQUEST`. The new report lands in `GENERATED` status with `generated_by_user_id` set to the calling `X-User-ID`, `waived_blocking_count` at zero, and `certified_by_user_id`, `certified_at`, `rejection_reason` and `decertified_reason` all null. The other three statuses are `CERTIFIED`, meaning usable for provisioning; `REJECTED`, terminal; and `DECERTIFIED`, meaning invalidated by a later record change, also terminal.

What the scan looks at depends on the scope. A `JURISDICTION`-scoped scan covers every centerline in the named jurisdiction, every address point with `status` `PENDING` or `ACTIVE` on those centerlines, and every coverage cell of the jurisdiction. A `ROAD`-scoped scan covers the single named centerline and its address points with `status` `PENDING` or `ACTIVE`, and **no cells at all**. Terminal address points — those in `RETIRED` or `VOIDED` — lie outside every scope and never produce a finding. The rule set is also conditional: the three boundary-category rules and the uncovered-cell address rule are evaluated **only** for `JURISDICTION`-scoped reports, because coverage integrity is a jurisdiction-level concern. A `ROAD`-scoped report therefore never emits a boundary-category finding or an uncovered-cell finding, and its boundary category consequently always scores a perfect 100.

The scan emits one **QC defect** row per offending record per applicable rule. Each defect carries a `report_id` naming the scan that produced it, a `defect_code` naming the rule violated, a `severity`, a `defect_category` giving the scoring category the finding deducts from, an `entity_type` naming the kind of record the finding is anchored to (`ROAD_CENTERLINE`, `ADDRESS_POINT` or `COVERAGE_CELL`), an `entity_ref_id` holding the anchored record's identifier resolved according to that `entity_type`, and a human-readable `detail` string such as "LEFT range 150-248 EVEN overlaps 100-198 EVEN". The `severity` and the `defect_category` are fixed per `defect_code` and are never chosen by the caller; `severity` is one of `BLOCKING`, `WARNING` or `INFO`, and `defect_category` is one of `ADDRESS`, `ROAD` or `BOUNDARY`. Every emitted defect starts with `status` `OPEN`, and defects are created in a deterministic order: by `defect_code` ascending, then by `entity_type` ascending, then by the subject record's `created_at` ascending.

Thirteen rule codes exist, and each maps to a fixed severity and category.

- `ADDRESS_MISSING_GEOMETRY` — `BLOCKING`, category `ADDRESS`. Fires on an in-scope address point whose `geometry_verified` is false.
- `ADDRESS_UNCOVERED_CELL` — `BLOCKING`, category `ADDRESS`. Jurisdiction scope only. Fires on an address point whose `status` is `ACTIVE` and whose coverage cell currently has at least one gap service type.
- `ADDRESS_POSTAL_CITY_MISMATCH` — `WARNING`, category `ADDRESS`. Fires when the point's `postal_city` differs from its jurisdiction's postal city.
- `ADDRESS_UNIT_TYPE_MISSING` — `WARNING`, category `ADDRESS`. Fires when the point has a non-null `unit_id` but a null `unit_type`.
- `ADDRESS_LOW_CONFIDENCE` — `INFO`, category `ADDRESS`. Fires when the point's `confidence_score` is strictly below 70.
- `ROAD_UNVALIDATED` — `BLOCKING`, category `ROAD`. Fires when the centerline's `status` is `DRAFT`.
- `ROAD_RANGE_OVERLAP` — `BLOCKING`, category `ROAD`. Fires when the centerline conflicts under the interval test of §3.2 against any other centerline whose `status` is `DRAFT`, `VALIDATED` or `PUBLISHED` — note that the scan, unlike the validate gate, does count `DRAFT` peers.
- `ROAD_NAME_NOT_NORMALIZED` — `WARNING`, category `ROAD`. Fires when `primary_name` differs from `normalized_name`.
- `ROAD_QC_DIRTY` — `WARNING`, category `ROAD`. Fires when the centerline's `qc_dirty` is true.
- `ROAD_NO_ADDRESSES` — `INFO`, category `ROAD`. Fires when the centerline has no non-terminal address points at all.
- `BOUNDARY_COVERAGE_GAP` — `BLOCKING`, category `BOUNDARY`. Jurisdiction scope only. Fires once per uncovered pairing of a jurisdiction cell with a service type, evaluated at the current instant — so a jurisdiction holding one cell and no active boundaries yields exactly three of these.
- `PROPOSED_COVERAGE_OVERLAP` — `WARNING`, category `BOUNDARY`. Jurisdiction scope only. Fires when two cell assignments on the same pairing of cell and service type have intersecting windows and at least one of the two is still `PENDING`.
- `BOUNDARY_STALE_WINDOW` — `INFO`, category `BOUNDARY`. Jurisdiction scope only. Fires on an `ACTIVE` cell assignment whose `effective_end` falls at or after the current instant and strictly before thirty days from now.

Generation immediately populates the report's counters and both of its scores: `defect_count` is the number of defect rows on the report irrespective of status, `blocking_defect_count`, `warning_defect_count` and `info_defect_count` are the per-severity counts irrespective of status, `open_blocking_defect_count` is the number of `BLOCKING` defects whose `status` is `OPEN`, and `waived_blocking_count` is the number of `BLOCKING` defects whose `status` is `WAIVED`.

**The quality score exists in two variants that move in opposite directions as waivers accumulate.** Both use the same shape of arithmetic. For each of the three categories `ADDRESS`, `ROAD` and `BOUNDARY`, a deduction is accumulated over the defects in that category, using a per-severity weight of 12.5 for `BLOCKING`, 4.0 for `WARNING` and 1.5 for `INFO`. The category's score is 100 less that deduction, floored at zero so it never goes negative. That category score is then multiplied by the category's weight — 0.45 for `ADDRESS`, 0.30 for `ROAD`, 0.25 for `BOUNDARY` — and the product is rounded half up to two decimal places **at that point, once per category**. The three rounded per-category products are then summed and the sum is rounded half up to two decimal places again.

The **strict** variant writes `quality_score` and counts a defect only when its `status` is `OPEN`; waived defects leave the deduction base entirely. This is the number the certification threshold and the quality tier are read from. The **advisory** variant writes `advisory_quality_score` and differs in two ways at once: its deduction base is restricted to `BLOCKING` defects only, since `WARNING` and `INFO` findings are advisory noise the analyst is permitted to publish over, and it counts waived defects at full weight, because a waiver is an accepted risk rather than a repaired defect and the advisory view is meant to keep showing it.

The per-category round-then-sum ordering is normative and is observably different from summing first and rounding once. The divergence appears whenever two categories land on a weighted value whose third decimal digit is exactly 5, which happens when a category's deduction is an odd multiple of one half — `BLOCKING` at 12.5 and `INFO` at 1.5 each carry a half, while `WARNING` at 4.0 does not. Worked case: a `JURISDICTION`-scoped report on one cell with no active boundaries, one `DRAFT` centerline whose `primary_name` is not normalized, and one `PENDING` address point that is neither geometry-verified nor postal-matching. The `ADDRESS` category carries one `BLOCKING` and one `WARNING` finding, a deduction of 16.5, a category score of 83.5, and a weighted value of 37.575 that rounds to 37.58. The `ROAD` category carries one `BLOCKING` and two `WARNING` findings, a deduction of 20.5, a category score of 79.5, and a weighted value of 23.850 that rounds to 23.85. The `BOUNDARY` category carries three `BLOCKING` findings, a deduction of 37.5, a category score of 62.5, and a weighted value of 15.625 that rounds to 15.63. The `quality_score` is therefore 37.58 plus 23.85 plus 15.63, which is 77.06 — whereas summing the unrounded products first would have produced 77.05. That one-cent difference is the acceptance criterion for this rule. In the same report the advisory variant counts only the five `BLOCKING` findings and rises to 81.26, which is the divergence between the two variants.

The report's `quality_tier` is read from `quality_score` — the strict variant — and never from `advisory_quality_score`. It is `A` when `quality_score` is at least 95, otherwise `B` when it is at least 85, otherwise `C` when it is at least 70, and otherwise `D`.

**Provisioning eligibility** then applies a waiver penalty on top of the strict base. The base is `quality_score`. The tier used for the penalty rate is `quality_tier`, which is pinned to that base score and is **not** re-derived from the penalised result. The penalty is `waived_blocking_count` multiplied by the tier's rate — 1.0 at tier `A`, 2.5 at tier `B`, 5.0 at tier `C` and 8.0 at tier `D`. The `provisioning_eligibility_score` is the base minus the penalty, floored at zero, rounded half up to two decimal places. The `is_provisioning_eligible` flag is true when `provisioning_eligibility_score` is greater than or equal to 90.00 — the threshold is inclusive — **and** `open_blocking_defect_count` is zero.

The pinning of the tier is worth a worked example, because re-deriving it would give a different answer. Take a report with two `WARNING` and two `INFO` `ADDRESS` findings still `OPEN`, plus one `BLOCKING` finding that has been waived. The `ADDRESS` deduction counts only the open findings — two at 4.0 and two at 1.5, giving 11.0 — for a category score of 89 and a weighted 40.05. `ROAD` and `BOUNDARY` are both clean at 100, giving 30.00 and 25.00. The base `quality_score` is 95.05, so `quality_tier` is `A`. The penalty is one waived blocking finding at the tier-`A` rate of 1.0, giving 1.00, and `provisioning_eligibility_score` lands at 94.05. Because the tier is pinned to the base, the `A` rate applies even though the result itself falls in the `B` band; re-deriving the tier from 94.05 would have selected `B` and its rate of 2.5, yielding 92.55 instead. That 1.50 spread is the acceptance criterion for this rule. Note also the two-directional movement that waiving produces: a waiver always **raises** the strict base, because the waived defect leaves the open deduction base, and then **lowers** the eligibility score by the tier rate. The two movements must not be collapsed into one.

The inclusive threshold has its own worked boundary. On a `ROAD`-scoped report — so the `BOUNDARY` category scores 100.00 — with two `OPEN` `WARNING` `ADDRESS` findings, four `OPEN` `INFO` `ADDRESS` findings, one `OPEN` `WARNING` `ROAD` finding and one `WAIVED` `BLOCKING` `ADDRESS` finding, the `ADDRESS` category deducts eight plus six for a category score of 86 and a weighted 38.70, `ROAD` deducts four for a weighted 28.80, and `BOUNDARY` contributes 25.00. The base is 92.50, the tier is `B`, the penalty is one waiver at 2.5, and `provisioning_eligibility_score` is exactly 90.00 — precisely the minimum, so `is_provisioning_eligible` is true and a package on this report seals. Adding one more `INFO` `ADDRESS` finding, a fifth low-confidence point, drops the base to 91.83 and the eligibility to 89.33, and the report is no longer eligible.

**Waiving a defect** is the `QcCertifier`'s tool for accepting a known risk. The certifier supplies `waiver_reason`, and the defect advances `OPEN → WAIVED` with `waived_by_user_id` set to the calling `X-User-ID`, `waived_at` stamped at the logical clock instant, and the defect's own `version` incremented by 1. Two preconditions apply: the defect's `status` must be `OPEN`, and the owning report's `status` must still be `GENERATED`. Waiving an already-`WAIVED` defect, or waiving any defect on a report that has left `GENERATED`, is refused with `ERR_DEFECT_INVALID_STATE` (HTTP 409). The waiver then forces the owning report to recompute `open_blocking_defect_count`, `waived_blocking_count`, `quality_score`, `advisory_quality_score`, `quality_tier`, `provisioning_eligibility_score` and `is_provisioning_eligible`, and to increment its own `version` by 1. Waiving clears the certification gate but never removes the strict-score deduction retroactively — it moves the finding out of the open base and into the waiver penalty instead.

**Certification** advances the report `GENERATED → CERTIFIED` and is performed by a `QcCertifier`. Two preconditions apply, evaluated in this order: the report's `open_blocking_defect_count` must be zero, or the request is refused with `ERR_QC_BLOCKING_DEFECTS_OPEN` (HTTP 409); and the calling `X-User-ID` must differ from the report's `generated_by_user_id`, or the request is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). Certification sets `certified_by_user_id` to the calling `X-User-ID` and `certified_at` to the logical clock instant, increments the report's `version` by 1, and then stamps certified confidence onto the data: for every address point in the report's scope whose `status` is `PENDING` or `ACTIVE`, processed in order of `house_number` ascending and then `created_at` ascending, the certified variant of the confidence calculation is computed into `certified_confidence_score`, `confidence_basis` is set to `CERTIFIED`, and that point's `version` is incremented by 1. Pin staleness is then evaluated for each stamped point — and since those points remain live, this is non-destructive drift, so a sealed package pinning one of them stays `SEALED` and merely becomes drifted.

**Rejection** advances the report `GENERATED → REJECTED`, requires only that the report's `status` be `GENERATED`, records `rejection_reason` from the payload, and increments the report's `version` by 1. Rejection is terminal: there is no path back, and the analyst runs a fresh scan once the underlying data has been fixed. Certifying or rejecting a report that is not `GENERATED`, including certifying one that is already `CERTIFIED` or `DECERTIFIED`, is refused with `ERR_REPORT_INVALID_STATE` (HTTP 409).

A certified report can be taken away from underneath its owner. When a discrepancy adoption or arbitration invalidates an address point that lies in a `CERTIFIED` report's scope — specifically, when at least one point whose `confidence_basis` was flipped back to `PROVISIONAL` by that cascade falls inside the scope — the report transitions `CERTIFIED → DECERTIFIED` with `decertified_reason` set to `SUBJECT_RECORD_CHANGED` and its `version` incremented by 1, and every provisioning package referencing it whose `status` is `DRAFT` or `SEALED` is then invalidated. That chain is spelled out in §3.8.

Reports are readable individually, showing both score variants and the eligibility verdict, and as a collection narrowable by `jurisdiction_id`, `road_centerline_id`, `scope` and `status`. Defects are readable individually and as the defect list of one report, narrowable by `severity`, `defect_category`, `defect_code` and `status` — and that report-scoped listing is the only discovery channel for defect rows, since defects are created only by a scan and never by a direct client call.

### 3.7. Provisioning Releases: Sealing, Publication Cadence and Rollback

Downstream systems do not read the live database; they read **provisioning packages**, which are immutable version-controlled snapshots. A `ProvisioningOfficer` opens one by naming the `channel` it targets — `DISPATCH_E911`, `MAPPING` or `PUBLIC` — the `jurisdiction_id` whose records are being released, and the `qc_report_id` of the QC validation report that authorises the release. The new package lands in `DRAFT` with `package_version` null, `record_count`, `pinned_record_count`, `fresh_pin_count` and `stale_pin_count` all at zero, `drift_detected` false, and `sealed_at`, `published_at`, `sealed_by_user_id`, `published_by_user_id`, `invalidated_reason` and `rollback_reason` all null. The lifecycle runs `DRAFT` to `SEALED` to `PUBLISHED`, with `SUPERSEDED`, `INVALIDATED` and `ROLLED_BACK` as its exits; `ROLLED_BACK` and `INVALIDATED` are terminal.

**Sealing** advances the package `DRAFT → SEALED` and is where the snapshot is actually taken. Three preconditions are evaluated in this order. First, the referenced report's `status` must be `CERTIFIED`, or the seal is refused with `ERR_QC_REPORT_NOT_CERTIFIED` (HTTP 409). Second, the in-scope record set must be non-empty, or the seal is refused with `ERR_PACKAGE_EMPTY` (HTTP 422). Third, the referenced report's `is_provisioning_eligible` must be true — equivalently, its `provisioning_eligibility_score` must be at least 90.00 — or the seal is refused with `ERR_QC_SCORE_BELOW_THRESHOLD` (HTTP 422). Sealing a package that is not `DRAFT` is `ERR_PACKAGE_INVALID_STATE`.

The in-scope record set for a package on a given jurisdiction is drawn from exactly three record families. Every address point whose `status` is `ACTIVE` and whose centerline's `jurisdiction_id` is that jurisdiction is in scope as an `ADDRESS_POINT` record. Every centerline whose `status` is `PUBLISHED` and whose `jurisdiction_id` is that jurisdiction is in scope as a `ROAD_CENTERLINE` record. And every emergency service boundary whose `status` is `ACTIVE` and which holds at least one `ACTIVE` cell assignment on a cell in that jurisdiction is in scope as an `EMERGENCY_SERVICE_BOUNDARY` record.

Sealing assigns the package a monotonic release number scoped to the pairing of `channel` and `jurisdiction_id`. That number is one greater than the largest `package_version` held by any package on the same channel-and-jurisdiction pairing whose `package_version` is not null, or 1 when no such package exists. Invalidated and rolled-back packages continue to hold their numbers, so release numbers are never reused; a `DRAFT` package has a null `package_version` and is not counted. So the first `DISPATCH_E911` seal for a county is numbered 1; if it is invalidated, the next seal for that channel and county is numbered 2; and a `MAPPING` seal for the same jurisdiction is numbered independently, starting again at 1.

Sealing then creates one **package record** per in-scope record, ordered by `record_type` ascending and then `record_id` ascending. Each row carries the `package_id` of the snapshot it belongs to, a `record_type` of `ADDRESS_POINT`, `ROAD_CENTERLINE` or `EMERGENCY_SERVICE_BOUNDARY`, a `record_id` holding the pinned record's identifier resolved per that `record_type`, a `pinned_version` equal to that record's `version` at the moment of sealing, a `pin_state` of `FRESH`, and a null `staled_at`. The package then records `record_count`, `pinned_record_count` and `fresh_pin_count` all equal to the number of pins created, `stale_pin_count` at zero, `sealed_at` at the logical clock instant, and `sealed_by_user_id` from the calling `X-User-ID`, and increments its own `version` by 1. Package records are readable only as the record list of one package, narrowable by `record_type` and `pin_state`; that listing is their sole discovery channel.

Pin freshness and the destructive-versus-non-destructive drift distinction are specified in §2.9 and apply from the moment of sealing onward. In particular, a `SEALED` package suffering destructive drift transitions `SEALED → INVALIDATED` with `invalidated_reason` `PIN_STALE` and its `version` incremented by 1; a `DRAFT` package whose referenced report is decertified transitions `DRAFT → INVALIDATED` with `invalidated_reason` `REPORT_DECERTIFIED` and its `version` incremented by 1; and a `SEALED` package whose referenced report is decertified likewise transitions `SEALED → INVALIDATED` with `invalidated_reason` `REPORT_DECERTIFIED`. Non-destructive drift never invalidates anything — it leaves the package `SEALED` with `drift_detected` true, and the refusal only materialises at publication time.

**Publication** advances the package `SEALED → PUBLISHED` and carries four gates, evaluated in this order. First, the calling `X-User-ID` must differ from the referenced report's `certified_by_user_id`, or the request is refused with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403). Second, when the package's `channel` is `DISPATCH_E911`, the jurisdiction's `forward_gap_pair_count` must be zero, or the request is refused with `ERR_COVERAGE_GAP_BLOCKS_E911` (HTTP 409); the `MAPPING` and `PUBLIC` channels are not gated on coverage at all, and note that the gate reads the forward-window counter rather than the instantaneous one, so a gap that opens inside the thirty-day horizon blocks the release even though every cell is covered at this instant. Third, `stale_pin_count` must be zero, or the request is refused with `ERR_PACKAGE_PINS_STALE` (HTTP 409). Fourth, the cadence window for the package's channel-and-jurisdiction pairing must be open, or the request is refused with `ERR_CADENCE_WINDOW_NOT_OPEN` (HTTP 409). Publishing a package that is not `SEALED` is `ERR_PACKAGE_INVALID_STATE`.

The cadence window governs how often a channel may be refreshed. The reference point is the package on the same channel-and-jurisdiction pairing whose `status` is `PUBLISHED`, `SUPERSEDED` or `ROLLED_BACK` and whose `published_at` is the greatest, ties broken by `created_at` ascending. If no such package exists the window is open unconditionally. Otherwise the elapsed interval is the time from that reference package's `published_at` to the current logical instant, expressed in whole and fractional days at millisecond arithmetic, and the window is open when that elapsed interval is greater than or equal to the channel's cadence interval — seven days for `DISPATCH_E911`, fourteen days for `MAPPING`, and thirty days for `PUBLIC`. The comparison is inclusive: a `DISPATCH_E911` package published at `2026-08-01T00:00:00.000Z` reopens its window at exactly `2026-08-08T00:00:00.000Z`, where the elapsed interval is precisely seven days; at `2026-08-07T23:59:59.999Z` the window is still closed.

A successful publication stamps `published_at` at the logical clock instant and `published_by_user_id` from the calling `X-User-ID`, increments the package's `version` by 1, and then supersedes the incumbent: any other package on the same channel-and-jurisdiction pairing whose `status` is `PUBLISHED` transitions `PUBLISHED → SUPERSEDED`, incrementing its own `version` by 1. Exactly one package is published per channel and jurisdiction at any moment.

**Rollback** exists because a bad release must be retractable without leaving dispatch with nothing to read. The officer supplies `rollback_reason`; the package must currently be `PUBLISHED`, and a `SUPERSEDED` predecessor must exist on the same channel-and-jurisdiction pairing, or the request is refused with `ERR_NO_PUBLISHED_PREDECESSOR` (HTTP 409) — because rolling back the only release would leave the channel unserved. Rollback records `rollback_reason`, moves the package `PUBLISHED → ROLLED_BACK`, increments its `version` by 1, and restores the predecessor: the `SUPERSEDED` package on the same pairing with the highest `package_version`, ties broken by `created_at` ascending, transitions `SUPERSEDED → PUBLISHED` and increments its own `version` by 1. The restored package's `published_at` is deliberately **left at its original value** — the cadence baseline is the restored package's original publication instant, not the moment of restoration — which means a rollback does not buy the officer a fresh cadence window. Rolling back a package that is not `PUBLISHED`, including one that is `INVALIDATED` or already `ROLLED_BACK`, is `ERR_PACKAGE_INVALID_STATE`.

Packages are readable individually, showing their pin freshness counters, and as a collection narrowable by `channel`, `jurisdiction_id`, `qc_report_id` and `status`.

### 3.8. Inter-Agency Discrepancy Negotiation, Adoption and Arbitration

Agencies disagree, and the county needs a record of how each disagreement was settled. An `AgencyLiaison` opens a **discrepancy case** by naming a `subject_type` of `ROAD_NAME`, `ADDRESS_RANGE` or `BOUNDARY_CELL`; a `subject_ref_id` identifying the disputed record, which is resolved as a centerline identifier when `subject_type` is `ROAD_NAME` or `ADDRESS_RANGE` and as a coverage cell identifier when it is `BOUNDARY_CELL`, with existence validated per subject type at creation; a `counterparty_agency_id` naming the other party; and a `description` stating the disagreement, one to 500 characters. The case's `opened_by_agency_id` is set from the calling `X-User-ID`, and its `jurisdiction_id` is copied from the subject record's jurisdiction. The new case lands in `OPEN` status with `round_count` at zero, `current_proposal_id` null, and `concurred_by_side`, `resolved_value`, `escalated_at` and `adopted_at` all null.

Three refusals guard case creation. The `counterparty_agency_id` may not equal the acting agency, and the counterparty's `jurisdiction_id` may not differ from the subject record's `jurisdiction_id`; either is `ERR_COUNTERPARTY_INVALID` (HTTP 422). Neither the opening agency nor the counterparty may have a `status` of `SUSPENDED`, or the creation is refused with `ERR_AGENCY_NOT_ACTIVE` (HTTP 409). And no case may already exist on the same pairing of `subject_type` and `subject_ref_id` whose `status` is anything other than `ADOPTED` or `ARBITRATED`, or the creation is refused with `ERR_SUBJECT_CASE_ALREADY_OPEN` (HTTP 409). When the `subject_type` is `ROAD_NAME` or `ADDRESS_RANGE`, opening the case increments the subject centerline's `open_discrepancy_case_count`, which is what freezes that centerline as described at the end of §3.2. A centerline's `open_discrepancy_case_count` is the number of cases on it whose `status` is `OPEN`, `PROPOSAL_PENDING`, `COUNTERED` or `ESCALATED`.

Negotiation proceeds by filing **proposals**, which form an immutable append-only log. A liaison files one by supplying the `proposed_value` — the road name, range expression or cell claim being put forward, one to 120 characters — the mandatory `expected_case_version`, and an optional `rationale`. The proposal's `case_id` is taken from the parent named in the path of the creating call. Its `round_number` is the 1-based ordinal of the filing within the case, equal to the case's `round_count` after the filing. Its `proposed_by_side` is derived from the caller: `OPENER` when `X-User-ID` equals the case's `opened_by_agency_id`, and `COUNTERPARTY` when it equals the case's `counterparty_agency_id`. A caller who is neither party is refused with `ERR_AGENCY_IDENTITY_MISMATCH`.

A proposal row is never rewritten, so its `status` is a pure projection recomputed on every read and on every case mutation. For a proposal on a case: if the case's `status` is `ADOPTED` and this proposal is the case's `current_proposal_id`, the proposal projects to `ADOPTED`; otherwise, if the case's `status` is `ESCALATED` or `ARBITRATED`, it projects to `VOIDED`; otherwise, if some proposal on the same case has a greater `round_number`, it projects to `COUNTERED`; otherwise it projects to `PENDING`. In parallel, the case's `round_count` is the count of proposals filed on it, and its `current_proposal_id` is the proposal with the greatest `round_number`.

Filing is governed by three preconditions. The supplied `expected_case_version` must equal the case's `version`, or the filing is refused with `ERR_STALE_CASE_VERSION` (HTTP 412). The caller must be one of the case's two parties. And once a first proposal exists, the acting side must **differ** from the current proposal's `proposed_by_side` — an agency may not counter itself — or the filing is refused with `ERR_SELF_CONCURRENCE` (HTTP 403).

The negotiation is genuinely cyclic. The first filing on an `OPEN` case advances it `OPEN → PROPOSAL_PENDING`; the next filing, necessarily by the other side, advances it `PROPOSAL_PENDING → COUNTERED`; the one after that advances it `COUNTERED → PROPOSAL_PENDING`; and the cycle continues. Every one of these transitions appends a proposal whose `round_number` is one greater than the case's prior `round_count`, sets the case's `round_count` to that new value, updates `current_proposal_id` to the new proposal, and increments the case's `version` by 1. Filing is permitted while `round_count` is strictly below three. The filing that arrives while `round_count` already **equals** three is still accepted — it is recorded as `round_number` 4 and `round_count` is set accordingly — but instead of continuing the cycle it drives the case to `ESCALATED`, from either `PROPOSAL_PENDING` or `COUNTERED`, stamping `escalated_at` at the logical clock instant and incrementing the case's `version` by 1. Both escalation branches are identical in every respect other than their origin state. Once escalated, the case has left the negotiation cycle, every filed proposal projects to `VOIDED`, and only arbitration can set `resolved_value`. To trace the whole path: rounds 1 by the opener, 2 by the counterparty and 3 by the opener keep the case cycling `PROPOSAL_PENDING → COUNTERED → PROPOSAL_PENDING`; the fourth filing, by the counterparty, is recorded as `round_number` 4 and moves the case to `ESCALATED`, at which point all four proposals project to `VOIDED`.

**Concurrence** is the peaceful exit. A liaison concurs by supplying the `proposal_id` it is agreeing to, which must equal the case's `current_proposal_id` and must itself project to `PENDING`; a `proposal_id` that resolves to no proposal at all is `ERR_PROPOSAL_NOT_FOUND`. The acting side must differ from that proposal's `proposed_by_side`, since an agency may not concur with its own proposal, and a violation is `ERR_SELF_CONCURRENCE` (HTTP 403). Concurrence is available from `PROPOSAL_PENDING` and from `COUNTERED`, and both branches behave identically: the case advances to `CONCURRED`, `concurred_by_side` is set to the acting side (`OPENER` or `COUNTERPARTY`), and the case's `version` increments by 1. Concurring on a case with no current proposal is `ERR_CASE_INVALID_STATE`.

**Adoption** is a `SystemAdmin` act, available only from `CONCURRED`, and it is the most far-reaching cascade in the system. It runs in five strictly ordered levels. At **level 1** the case sets `resolved_value` to the current proposal's `proposed_value`, stamps `adopted_at` at the logical clock instant, moves to `ADOPTED`, and increments its own `version` by 1; the subject centerline's `open_discrepancy_case_count` consequently drops to zero and the centerline unfreezes. At **level 2**, caused by level 1, the subject centerline applies the resolved value — writing it into `primary_name` when the `subject_type` is `ROAD_NAME`, or into that side's range fields when the `subject_type` is `ADDRESS_RANGE` — recomputes `normalized_name`, sets `qc_dirty` to true, refreshes its assignable-slot counters, and increments its own `version` by 1; and if its `status` was `PUBLISHED` it is demoted `PUBLISHED → VALIDATED` and must be re-published. At **level 3**, caused by level 2, every address point on that centerline whose `status` is `PENDING` or `ACTIVE` has `confidence_basis` set back to `PROVISIONAL`, `certified_confidence_score` set back to null, `confidence_score` recomputed under the provisional variant, and its own `version` incremented by 1. At **level 4**, caused by level 3, every `CERTIFIED` QC validation report whose scope covers at least one of those address points transitions `CERTIFIED → DECERTIFIED` with `decertified_reason` set to `SUBJECT_RECORD_CHANGED` and its `version` incremented by 1. At **level 5**, caused by level 4, every provisioning package referencing such a report whose `status` is `DRAFT` or `SEALED` transitions to `INVALIDATED` with `invalidated_reason` set to `REPORT_DECERTIFIED` and its `version` incremented by 1. Pin staleness is evaluated after each individual record mutation inside levels 2 and 3.

**Arbitration** is the contested exit and is likewise a `SystemAdmin` act, available only from `ESCALATED`. The arbitrator supplies an `arbitration_value` of its own choosing and an optional `rationale`. The case sets `resolved_value` to that `arbitration_value`, stamps `adopted_at` at the logical clock instant, moves `ESCALATED → ARBITRATED`, and increments its `version` by 1; every filed proposal on the case projects to `VOIDED`; and levels 2 through 5 of the adoption cascade then run identically, using the arbitrated value in place of a proposed one. Adopting a case that is not `CONCURRED`, arbitrating a case that is not `ESCALATED`, and filing a proposal on an already-resolved case are all refused with `ERR_CASE_INVALID_STATE` (HTTP 409).

Cases are readable individually and as a collection narrowable by `opened_by_agency_id`, `counterparty_agency_id`, `jurisdiction_id`, `current_proposal_id`, `subject_type`, `subject_ref_id` and `status`. A case's proposal log is readable as a collection narrowable by `proposed_by_side` and `status`, each row carrying its projected status at the moment of the read.

### 3.9. Retirement, Supersession and Records Research

Two audiences read this system long after the field work is done: the title researcher tracing how a parcel's address changed hands, and the auditor reconstructing why a particular release was published. Both are served by the same discipline — nothing is destroyed and every consequential act leaves a named reason behind.

When an address is renumbered rather than simply abandoned, the analyst records the successor at retirement time by supplying `superseded_by_address_point_id`, which must reference a point whose `status` is `PENDING` or `ACTIVE`. The retired point keeps that reference forever and its `retire_reason` reads `REPLACED` rather than `ANALYST_RETIRED`, so a researcher can walk forward along a supersession chain from a nineteenth-century number to the current one by following each link, or walk backwards by filtering the historical rows on `superseded_by_address_point_id`. Because the duplicate-address constraint ignores points in `RETIRED` and `VOIDED` status, the successor is free to occupy a key the predecessor once held.

The reasons themselves are diagnostic. A point that reads `ROAD_RETIRED` was swept up when its centerline left service; one that reads `PARENT_RETIRED` was swept up when its base address did; one that reads `REQUEST_VOIDED` was never real, because the permit that produced it was voided. A centerline carries its own `retired_at` and its operator-supplied `retire_reason`. A boundary carries `retired_at` and `retire_reason` likewise. A report that reads `SUBJECT_RECORD_CHANGED` in `decertified_reason` was invalidated by an adopted or arbitrated dispute rather than by any failing of its own. A package that reads `PIN_STALE` in `invalidated_reason` lost a record to a terminal status, while one that reads `REPORT_DECERTIFIED` lost its authorising report; and because only the first invalidating rule to fire records its reason, that field tells the auditor which cause came first rather than which came last.

Every mutating act also leaves a `version` trail: because the counter advances by exactly one per mutation and every cascade increments each record it touches, the difference between a package's `pinned_version` for a record and that record's live `version` is a literal count of how many times the record moved since the snapshot was taken. That is why `drift_detected` is a reliable signal rather than a heuristic, and it is why a drifted snapshot is discarded and rebuilt rather than patched.
