# Vote-By-Mail Processing API — Product Requirements Document

## 1. Introduction

County elections offices carry an unusual burden: every mailed ballot is simultaneously a piece of mail, a legal instrument, a chain-of-custody artifact, and a secret. The staff who handle it must decide whether it arrived in time, whether the signature on the envelope belongs to the registered voter, whether the voter deserves a chance to cure a defect, and whether the paper inside can be separated from the identifying envelope without ever becoming re-associable with the person who cast it. Today that work is done across mail-house spreadsheets, signature-review clipboards, and hand-kept cure logs, which means the office cannot answer the two questions that matter most on canvass night — *how many ballots are unaccounted for?* and *can we prove every custody event we performed?*

This document specifies the Vote-By-Mail Processing API, a single service that carries a ballot from the moment a voter asks for one through mailing, receipt logging, signature verification, cure adjudication, envelope separation, remake, challenge adjudication, and certification. The service is mounted under `/vote-by-mail`. It is built around three commitments. First, **accountability**: every mailed packet is reconciled against a returned, outstanding, or undeliverable disposition, and the reconciliation must balance before an election may be certified. Second, **segregation of duties**: the reviewer who judged a signature may not judge it again on escalation and may not sit on the bipartisan team that remakes that same ballot, and the supervisor who adjudicates never submits a signature decision. Third, **transparency without disclosure**: an append-only log records every custody event for observers to read, and it never records a single ballot selection.

Because election administration is governed by statutory clocks rather than wall-clock convenience, the service keeps its own logical clock. Every timestamp the service stamps, every deadline comparison it performs, and every day-arithmetic derivation it computes is read from that clock, which allows an entire election cycle — mailing deadlines, the postmark grace window, the cure window, and the canvass lock — to be exercised deterministically.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to the service must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the role that principal is acting in. If either header is absent or empty, or if `X-User-Role` is not one of the five declared role names, the request is rejected with `ERR_UNAUTHENTICATED`. When the headers are well formed but the named role is not among the roles authorised for the target operation, the request is rejected with `ERR_ROLE_FORBIDDEN`.

The five roles are `ElectionsAdmin`, `ElectionsClerk`, `SignatureReviewer`, `CanvassSupervisor`, and `Observer`.

An `ElectionsAdmin` is the county elections official: they register elections, create and certify signature reviewers, advance the election posture, run the canvass checkpoint, and drive the logical clock. An `ElectionsClerk` works the processing floor: logging ballot requests and address-verification results, building and dispatching mailing batches, recording undeliverable packets, logging returned envelopes and cure evidence, opening signature-review rounds, issuing cure notices, and administering the permanent absentee list. A `SignatureReviewer` compares an envelope signature against the registration record and may act only on the reviews the server assigned to them. A `CanvassSupervisor` adjudicates cure evidence and observer challenges, runs separation and counting, and authorises bipartisan remakes. An `Observer` holds a scheduled floor-access window, may file challenges only while checked in, and may never read voter registration records.

Identity binding differs by role. When `X-User-Role` is `SignatureReviewer`, `X-User-ID` is the `id` of the acting `Reviewer`; ownership checks on any resource that references a `Reviewer` compare the resource's foreign-key field to `X-User-ID` — concretely, a signature decision is accepted only when `X-User-ID` equals the `reviewer_id` recorded on the review being decided, and any other value is rejected with `ERR_NOT_ASSIGNED_REVIEWER`. When `X-User-Role` is `ElectionsAdmin`, `ElectionsClerk`, `CanvassSupervisor`, or `Observer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it — for example as `actor_user_id` on a transparency log entry, which is left null for system-generated events — but does not compare it to any entity's `id`. The one place an opaque identifier is compared to stored data is observer check-in: an observer session stores the credential string the office issued in `observer_user_id`, and check-in requires the acting `X-User-ID` to equal that stored string. That comparison is against a recorded credential value, not against an entity primary key.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and Collection Filtering

Every collection endpoint accepts two optional query-string parameters. `limit` controls page size: it defaults to 10, its minimum accepted value is 1, and its maximum accepted value is 100. `offset` controls the starting position: it defaults to 0 and its minimum accepted value is 0. A `limit` below 1 or above 100, or a negative `offset`, is a schema failure and is rejected with `ERR_INVALID_REQUEST`. List responses carry `limit`, `offset`, `total_count`, and `has_more` inside `meta`, where `total_count` is the number of rows matching the filters before the page window is applied and `has_more` indicates whether any matching row remains beyond the current window.

Unless a collection states otherwise, list results are ordered by `created_at` ascending. The transparency log is the one collection with an explicit domain ordering: its entries are returned in append order, which is `sequence` ascending — and because `sequence` is assigned in append order, that ordering agrees with `created_at` ascending.

Collections also accept domain filters, each an exact-match filter on the named stored value. Elections may be filtered by `posture`. Voters may be filtered by `registration_status` and `uocava_status`. Reviewers may be filtered by `training_status` and `party_affiliation`. Ballot requests may be filtered by `voter_id`, `election_id`, and `status`. Address verifications may be filtered by `ballot_request_id` and `status`. Permanent absentee enrollments may be filtered by `voter_id` and `status`. Mailing batches may be filtered by `election_id`, `status`, and `batch_type`. Ballot packets may be filtered by `mailing_batch_id`, `ballot_request_id`, and `status`. Return envelopes may be filtered by `ballot_packet_id`, `remade_from_envelope_id`, and by any of the three state dimensions — `signature_status`, `custody_status`, and `challenge_status`. Signature reviews may be filtered by `return_envelope_id`, `reviewer_id`, and `status`. Cure notices may be filtered by `return_envelope_id` and `status`; cure evidence may be filtered by `cure_notice_id`. Remake records may be filtered by `original_envelope_id`, `remade_envelope_id`, `team_member_a_reviewer_id`, `team_member_b_reviewer_id`, and `status`. Observer sessions may be filtered by `election_id`, `party_affiliation`, `station_area`, and `status`. Transparency log entries may be filtered by `election_id`, `event_type`, `actor_role`, and `subject_id`.

### 2.4. Common Record Properties and the Logical Election Clock

Every persisted record carries a server-minted `id`, which is a UUID with no type prefix of any kind, and a `created_at` timestamp. Most records additionally carry `updated_at` and `version`: `updated_at` is refreshed on every mutation of that record, and `version` is an integer that begins at 1 when the record is created and increments by one on every mutation. All timestamps the service emits are ISO 8601 instants in UTC with exactly three fractional-second digits.

Two record types are immutable audit artifacts and therefore carry only `id` and `created_at` — both `updated_at` and `version` are absent from them entirely. Those are cure evidence submissions and transparency log entries. A cure evidence row's `accepted` flag and `deficiency_reason_code` are written by the adjudication of its notice, and a transparency log entry is never edited after it is appended.

Because statutory deadlines drive nearly every rule in this domain, the service maintains a **logical clock** rather than reading the host wall clock. When the clock has never been set, its value is `2026-08-01T00:00:00Z`. Every datetime the service stamps — receipt instants, seal and dispatch instants, submission instants, issuance instants, resolution instants — is read from the logical clock, and every deadline comparison is made against it. An `ElectionsAdmin` may reposition the clock by supplying `to_iso8601`; the response reports the new value as `current_utc`. The clock may only move forward: a `to_iso8601` that is not strictly greater than the current logical clock value is rejected with `ERR_CLOCK_REWIND_FORBIDDEN`.

### 2.5. Election Posture as the Master Gate

Every election occupies exactly one **posture**, and the posture gates what the processing floor may do. The five postures, in order, are `PRE_MAIL`, `MAILING`, `RECEIVING`, `CANVASS_LOCKED`, and `CERTIFIED`. A newly registered election begins in `PRE_MAIL`, and `CERTIFIED` is terminal.

The posture gate is uniform and is evaluated on every mutating operation scoped to an election. Logging a ballot request, approving one, and sealing a mailing batch all require the posture to be `PRE_MAIL` or `MAILING`. Logging a returned envelope requires the posture to be `MAILING` or `RECEIVING`. Opening a signature-review round, submitting a signature decision, and completing a remake all require the posture to be `RECEIVING` or `CANVASS_LOCKED`. Issuing a cure notice requires the posture to be exactly `RECEIVING`, because locking the canvass closes the cure window to new notices. A separation run also requires the posture to be exactly `RECEIVING`. Once the posture reaches `CERTIFIED`, no mutating child operation of that election is permitted at all. A posture advance may name only the immediate successor posture and only when that transition's own preconditions hold. Any violation of this paragraph is reported as `ERR_ELECTION_POSTURE_FORBIDS`.

### 2.6. Path Identifier Resolution Order

Identifiers are resolved strictly left to right as they appear in the request, and the first identifier that fails to resolve determines the error. An election identifier that resolves to nothing yields `ERR_ELECTION_NOT_FOUND`; a voter identifier yields `ERR_VOTER_NOT_FOUND`; a reviewer identifier — including either of the two remake team member identifiers — yields `ERR_REVIEWER_NOT_FOUND`; a return-envelope identifier yields `ERR_ENVELOPE_NOT_FOUND`. Every other addressable record type — ballot requests, address verifications, permanent absentee enrollments, mailing batches, ballot packets, signature reviews, cure notices, cure evidence, remake records, observer sessions, and transparency log entries — yields the generic `ERR_RECORD_NOT_FOUND`. Where a request carries a list of envelope identifiers, the elements are resolved in array order, so the first unresolvable element in the submitted order is the one reported.

### 2.7. Stale-View Protection on Voter and Envelope Writes

Two write operations in this service can be authorised only by a client that has observed the current state of a parent record, because both of them legitimately supersede earlier work and a stale view would silently destroy something the client never saw.

A `POST /vote-by-mail/ballot-requests` request must carry `expected_voter_version`, a non-optional field holding the client's last observed `version` of the target `Voter`. If it does not equal that voter's current `version`, the create is rejected with `ERR_STALE_VOTER_VERSION` (HTTP 412). This matters because a later request by the same voter for the same election supersedes the earlier one and can spoil an already-queued packet; the write is accepted only when the client's view of the voter — including any enrollment, address, or supersession side effect already applied to that voter — is current. A successful create increments `Voter.version` by one.

A `POST /vote-by-mail/return-envelopes/{id}/remakes` request must carry `expected_envelope_version`, a non-optional field holding the client's last observed `version` of the target `ReturnEnvelope`. If it does not equal that envelope's current `version`, the create is rejected with `ERR_STALE_ENVELOPE_VERSION` (HTTP 412). A remake legitimately supersedes an earlier remake of the same envelope, so a client whose view of the envelope's signature, custody, or challenge dimension has been overtaken cannot authorise a new remake session. A successful create increments `ReturnEnvelope.version` by one.

No other endpoint in this service accepts a version field, and no other operation performs a stale-view check.

### 2.8. Numeric Precision: Whole Cents and Four-Place Confidence

All money in this service is expressed in whole cents as integers — the election's postage authority, every per-packet postage figure, and every batch and election total. Postage rounding uses round-half-up and is applied **per packet before summation**, never once over a batch aggregate; a batch total is the sum of already-rounded per-packet figures. There are no proportional refunds and no re-estimation: a released commitment releases exactly the frozen figure that was committed.

Signature confidence is a decimal in the closed range from 0.0 to 1.0 carried at four decimal places, rounded half-up, and clamped into that range before rounding. Both the per-review `confidence_score` and the envelope-level `resolved_signature_confidence` carry four decimal places.

Day arithmetic on statutory deadlines adds exact 24-hour multiples to a stored instant, and instant comparisons are made at whole-second resolution in UTC. Derived deadline instants are stored as ISO 8601 UTC instants at whole-second resolution. Record counters are exact integers and are never rounded.

### 2.9. Cascade Discipline and Compensating Actions

Several operations in this domain mutate more than one record, and the service applies every link of the chain within the same request rather than deferring any of it. Two chains run three links deep. A failed address result or an undeliverable packet increments a counter on the voter's permanent absentee enrollment, which may suspend that enrollment, which in turn clears a flag on the voter and appends a transparency entry. A cure notice that expires at the canvass checkpoint rejects its envelope's signature dimension, which sequesters the envelope's custody dimension, which in turn refers the voter to the provisional process and appends a transparency entry. Every record touched by a cascade has its `updated_at` refreshed and its `version` incremented like any other mutation.

Two operations are true compensating actions and must restore an earlier value exactly rather than recompute it. Cancelling a sealed mailing batch releases the batch's frozen postage estimate in full. Voiding a completed remake returns the original envelope to the countable pool and withdraws its replacement. In both cases the invariants in §2.11 hold to the cent and to the ballot.

### 2.10. Segregation of Duties on the Processing Floor

Election integrity in this service is enforced by keeping people apart, not merely by logging what they did. Three separations are absolute. A reviewer who has any signature review on an envelope — of any status — can never be selected for a later escalation round on that same envelope. Neither member of a bipartisan remake team may hold a signature review on the envelope being remade. And a `CanvassSupervisor`, who adjudicates cures and challenges and authorises remakes, is never authorised to submit a signature decision at all. A violation of either of the first two separations is reported as `ERR_SEGREGATION_OF_DUTIES`; an attempt at the third is simply a role failure and yields `ERR_ROLE_FORBIDDEN`.

A remake team must additionally be bipartisan: the two nominated members must be different reviewers and must hold different `party_affiliation` values, otherwise the request is rejected with `ERR_REMAKE_TEAM_NOT_BIPARTISAN`. Party affiliation on both reviewers and observers is drawn from `DEM`, `REP`, `NPP`, and `OTHER`.

### 2.11. Ballot Accountability and the Conservation Invariants

The election carries a live accountability picture, recomputed on every ballot-packet status change, on every envelope custody change, and at every canvass checkpoint, and readable on demand. It is built from the packets whose carrying batch belongs to the election. `packets_mailed_count` is the number of those packets whose status is `MAILED`, `RETURNED`, or `UNDELIVERABLE`. `returned_packet_count` is the number whose status is `RETURNED`. `outstanding_packet_count` is the number whose status is `MAILED` — mailed but neither returned nor reported undeliverable. `undeliverable_packet_count` is the number whose status is `UNDELIVERABLE`. Packets that are still `QUEUED` and packets that were `SPOILED` are excluded from all four figures. `envelopes_received_count` is the number of return envelopes whose packet belongs to the election, counting remake replacements and superseded originals alike.

The reconciliation itself is a single subtraction: `accountability_delta` is `packets_mailed_count` minus the sum of `returned_packet_count`, `outstanding_packet_count`, and `undeliverable_packet_count`. When that difference is exactly zero the election's `reconciliation_status` is `IN_BALANCE`; for any other value it is `OUT_OF_BALANCE`.

Two further counts describe the ballots themselves. `countable_envelope_count` is the number of the election's return envelopes whose `signature_status` is `ACCEPTED`, whose `custody_status` is either `SEPARATED` or `COUNTED`, and whose `challenge_status` is anything other than `SUSTAINED`. `attributable_ballot_count` is the number whose `custody_status` is `SEALED`, `SEPARATED`, or `COUNTED` and whose `signature_status` is anything other than `REJECTED`.

`attributable_ballot_count` is a **conserved quantity** across the remake lifecycle. Take its value immediately before a remake is completed. Completion moves the original envelope to `SUPERSEDED_BY_REMAKE`, which removes it from the set, and mints a replacement in `SEALED` carrying the original's `signature_status`, which adds it to the set — so the count is unchanged. A subsequent void moves the replacement to `SEQUESTERED` with `signature_status` set to `REJECTED`, which removes it from the set, and returns the original to `SEALED` with its pre-remake `signature_status`, which adds it back — so the count is again unchanged. Any drift at all in `attributable_ballot_count` across that pair of operations is a defect. `envelopes_received_count`, by contrast, is deliberately **not** conserved: it increases by exactly one for every completed remake, because the replacement row is retained forever as an audit artifact.

Postage commitment is conserved the same way. `postage_committed_cents` on the election is by definition the sum of `estimated_postage_cents` over the election's mailing batches whose status is `SEALED` or `DISPATCHED`. Take its value immediately before a batch is sealed. After the seal it equals that prior value plus the batch's `estimated_postage_cents`. After that batch is cancelled it equals the prior value exactly — the frozen estimate is released in full, never a fresh estimate recomputed over the now-spoiled packets. `postage_actual_cents` is untouched by both seal and cancel and remains at its pre-seal value; it accumulates only at dispatch, as the sum of `actual_postage_cents` over dispatched batches.

### 2.12. Transparency Logging and the Secrecy Invariant

Every consequential custody event appends one entry to the election's append-only transparency log. An entry records the `election_id` it belongs to, a `sequence` number that is a 1-based monotone counter per election assigned in append order, an `event_type`, the `actor_role` that caused it, the `actor_user_id` of the acting principal (null when the service itself generated the event), the `subject_entity` naming which record type the event concerned, the `subject_id` of that record, a short human-readable `summary`, and the `recorded_at` logical-clock instant.

The `actor_role` on an entry is one of `ElectionsAdmin`, `ElectionsClerk`, `SignatureReviewer`, `CanvassSupervisor`, `Observer`, or `system`. The `subject_entity` is one of `ReturnEnvelope`, `CureNotice`, `RemakeRecord`, `MailingBatch`, `BallotPacket`, `PermanentAbsenteeEnrollment`, `ObserverAccessSession`, `Election`, or `Voter`. The `event_type` vocabulary is fixed and closed: `REQUEST_LOGGED`, `ENVELOPE_INTAKE`, `SIGNATURE_DECISION`, `SIGNATURE_ESCALATION`, `CURE_ISSUED`, `CURE_ADJUDICATED`, `CURE_EXPIRED`, `SEPARATION_RUN`, `REMAKE_COMPLETED`, `REMAKE_VOIDED`, `CHALLENGE_FILED`, `CHALLENGE_ADJUDICATED`, `OBSERVER_SESSION_OPENED`, `OBSERVER_SESSION_REVOKED`, `POSTURE_CHANGED`, `BATCH_DISPATCHED`, `BATCH_CANCELLED`, `PACKET_UNDELIVERABLE`, `ENROLLMENT_SUSPENDED`, `ENROLLMENT_REINSTATED`, and `PROVISIONAL_REFERRAL`.

One field on the log exists purely to make a promise auditable: `ballot_content_disclosed` is always false. The log records custody events only and never records a voter's ballot selections. That is the secrecy invariant, and it is the reason a separation run has a minimum pool size — see §3.9.

### 2.13. Rejection Precedence

When a single request violates more than one rule, the service reports the violation with the lowest precedence number below. This ordering is normative: a caller who fixes the reported error and retries will surface the next violation in turn.

1. **Authentication** — headers present and `X-User-Role` among the five declared roles, else `ERR_UNAUTHENTICATED`.
2. **Authorisation** — the acting role is authorised for the target operation, else `ERR_ROLE_FORBIDDEN`.
3. **Request schema** — required body fields present, enum values inside their declared sets, `similarity_score` at least 0 and at most 100, `packet_weight_grams` at least 1, `signature_on_file_count` at least 1, `limit` at least 1 and at most 100, `offset` at least 0, `session_end_at` strictly later than `session_start_at`, `window_end_at` strictly later than `window_start_at`, and `return_envelope_ids` an array of strings — else `ERR_INVALID_REQUEST`.
4. **Existence** — identifiers resolve, left to right, per §2.6.
5. **Stale-view protection** — the two version guards of §2.7.
6. **State preconditions** — the posture gate of §2.5 and every record-status gate named in §3.
7. **Integrity and safety** — assigned-reviewer identity, reviewer training validity, remake team bipartisanship, segregation of duties, and the non-empty separation set.
8. **Secrecy and floor access** — the separation-run minimum pool size and the observer session requirement for filing a challenge.
9. **Referential eligibility** — voter registration status, delivery-method eligibility, batch-type eligibility, request-to-batch election agreement, duplicate envelope for a packet, and duplicate remake serial.
10. **Capacity and interval constraints** — observer per-party slots, observer floor capacity, remake team double-booking, and reviewer candidate availability.
11. **Statutory deadlines** — mailing send-by dates, the cure deadline, the observer window, and the clock monotonicity rule.
12. **Fiscal authority** — the postage budget check, evaluated last of all.

## 3. Business Logic & Workflows

### 3.1. Registering an Election and Its Statutory Calendar

Everything in this service hangs off an **Election**, and an `ElectionsAdmin` registers one by supplying the statutory calendar the county will be held to. The registration payload carries a `name` such as "General Election 2026", the `election_date` as an ISO calendar date, the two last-lawful-send dates — `uocava_send_deadline_date` for military and overseas batches and `domestic_send_deadline_date` for the domestic initial mailing — and `return_deadline_at`, the instant polls close. Two grace parameters are optional. `postmark_grace_days` is the number of whole days after `return_deadline_at` during which a ballot postmarked on or before `election_date` may still count, and it defaults to 7 when the caller omits it. `cure_window_days` is the number of whole days after `return_deadline_at` that forms the statutory cure base deadline, and it defaults to 21. The payload also carries `postage_budget_cents`, the total postage authority for the election in whole cents.

A newly registered election opens in posture `PRE_MAIL`. Its `canvass_days` initialises to the standard canvass length of 17 whole days, and `canvass_lock_at` is accordingly `return_deadline_at` advanced by 17 days. Every derived counter initialises to zero — `packets_mailed_count`, `envelopes_received_count`, `outstanding_packet_count`, `undeliverable_packet_count`, `countable_envelope_count`, `attributable_ballot_count`, `rejected_envelope_count`, `provisional_referral_count`, `open_cure_count`, `postage_committed_cents`, and `postage_actual_cents` — as do the two monotone bookkeeping counters, `separation_run_sequence` and `canvass_sweep_index`. `reconciliation_status` initialises to `IN_BALANCE`.

Posture moves forward one step at a time along the chain `PRE_MAIL → MAILING → RECEIVING → CANVASS_LOCKED → CERTIFIED`, and the admin drives it by naming the desired `target_posture`. Two of the four steps also fire on their own as the third link of a business cascade. The advance `PRE_MAIL → MAILING` fires automatically the first time a mailing batch of this election dispatches, and it can also be taken explicitly before any dispatch has occurred; it requires the current posture to be `PRE_MAIL`, and it recomputes `packets_mailed_count` and `outstanding_packet_count`. The advance `MAILING → RECEIVING` fires automatically on the first returned-envelope intake for this election and can likewise be taken explicitly; it requires the current posture to be `MAILING`. When either fires automatically the appended transparency entry records `actor_role` as `system`; when taken explicitly it records the acting admin. Either way, a `POSTURE_CHANGED` entry is appended.

The advance `RECEIVING → CANVASS_LOCKED` is admin-driven only and requires the current posture to be `RECEIVING`. It hardens the floor: from that point on, no further returned envelope may be logged and no further cure notice may be issued, both attempts being reported as `ERR_ELECTION_POSTURE_FORBIDS`, and a `POSTURE_CHANGED` entry is appended.

Certification — the advance `CANVASS_LOCKED → CERTIFIED` — is the most heavily guarded transition in the service, and it is deliberately gated on four separate conditions. The current posture must be `CANVASS_LOCKED`; `reconciliation_status` must be `IN_BALANCE`; `open_cure_count` must be exactly zero; and the number of the election's return envelopes whose `challenge_status` is `CHALLENGED` must be exactly zero. Failing any one of the four is reported as `ERR_ELECTION_POSTURE_FORBIDS`. Certification appends a `POSTURE_CHANGED` entry and freezes every mutating child operation of the election permanently; `CERTIFIED` is terminal and there is no path out of it.

### 3.2. Ballot Requests, Address Verification, and the Permanent Absentee List

A voter record is created by an `ElectionsClerk` or an `ElectionsAdmin` with the registered `full_name` as printed on the registration record, a `party_affiliation`, the `residence_address`, and `last_signature_update_at` — the instant the newest signature exemplar was captured, which later feeds the staleness penalty in signature scoring. Four fields are optional at creation. `registration_status` defaults to `ACTIVE` and may otherwise be `INACTIVE` or `CANCELLED`. `mailing_address` defaults to null, and when it is null the `residence_address` is used for packet addressing; the `residence_address` itself is never overwritten by forwarding data. `uocava_status` defaults to `NONE` and may otherwise be `MILITARY` or `OVERSEAS`. `signature_on_file_count` — the number of signature exemplars on the registration record — defaults to 1 and must be at least 1. Two flags are derived rather than supplied and both initialise to false: `permanent_absentee_active` is true exactly when the voter has a permanent absentee enrollment whose status is `ACTIVE`, and `provisional_ballot_eligible` becomes true as soon as any of the voter's return envelopes reaches `signature_status` `REJECTED`.

Logging a ballot request is the `ElectionsClerk`'s entry point into the mail stream. The payload names the requesting `voter_id`, the `election_id` the request is scoped to, the `request_channel` — one of `ONLINE`, `PAPER`, or `PHONE` — and the `delivery_method`, which is either `MAIL` or `EMAIL_UOCAVA`. It also carries the stale-view guard `expected_voter_version` described in §2.7. An optional `permanent_flag` defaults to false and, when true, marks the request as also enrolling the voter on the permanent absentee list. Two eligibility rules bite here: the voter's `registration_status` must be `ACTIVE`, else `ERR_VOTER_REGISTRATION_INACTIVE`, and choosing `EMAIL_UOCAVA` requires the voter's `uocava_status` to be `MILITARY` or `OVERSEAS`, else `ERR_DELIVERY_METHOD_NOT_ELIGIBLE`.

A successful logging does four things beyond creating the request. The request opens in status `RECEIVED` with `forwarding_class` set to `UNKNOWN`, and its `mailing_address_snapshot` is frozen then and there: the voter's `mailing_address` when that is non-null, otherwise the voter's `residence_address`. One address verification is created in status `PENDING` and linked back to the request through its `ballot_request_id`. `Voter.version` increments by one. And any earlier request by the same voter for the same election that is still in `RECEIVED`, `ADDRESS_HOLD`, `ADDRESS_CLEARED`, or `APPROVED` transitions to `SUPERSEDED` — which in turn fails any of that older request's `PENDING` address verifications, and, if a still-`QUEUED` ballot packet exists for it, moves that packet `QUEUED → SPOILED`, removing it from the actual-postage input set of its batch. A `REQUEST_LOGGED` transparency entry is appended.

Recording the change-of-address result is what unblocks or blocks the mailing. The clerk submits an `ncoa_result` — one of `MATCH_SAME`, `MATCH_FORWARDABLE`, `MATCH_NON_FORWARDABLE`, or `NO_MATCH` — optionally with the `verified_mailing_address` returned by the change-of-address service and a `forwardable` boolean stating whether the carrier will forward election mail to that address. The verification must still be `PENDING`, else `ERR_VERIFICATION_ALREADY_RESOLVED`; its linked request must be in `RECEIVED` or `ADDRESS_HOLD`. Recording the result stamps `evaluated_at` with the logical-clock instant and resolves the verification's own status.

The two branches are symmetric in shape and opposite in consequence, and both are fully specified. On `MATCH_SAME` or `MATCH_FORWARDABLE` the verification moves `PENDING → CLEARED` and drives the request `RECEIVED → ADDRESS_CLEARED`. `forwarding_class` becomes `SAME_ADDRESS` when the result was `MATCH_SAME` and `FORWARDABLE` when it was `MATCH_FORWARDABLE`; on `MATCH_FORWARDABLE` only, `mailing_address_snapshot` is overwritten with the verification's `verified_mailing_address`. On `MATCH_NON_FORWARDABLE` or `NO_MATCH` the verification moves `PENDING → FAILED` and drives the request `RECEIVED → ADDRESS_HOLD`. `forwarding_class` becomes `NON_FORWARDABLE` when the result was `MATCH_NON_FORWARDABLE` and is left at `UNKNOWN` when it was `NO_MATCH`.

The `ADDRESS_HOLD` branch with `forwarding_class` of `NON_FORWARDABLE` is the head of a three-link cascade. Its second link reaches the voter's permanent absentee enrollment: if that enrollment's status is `ACTIVE`, its `consecutive_undeliverable_count` increments by one, and when the new value reaches two or more the enrollment transitions `ACTIVE → SUSPENDED` with `suspension_reason_code` set to `ADDRESS_NON_FORWARDABLE`. The third link follows from that suspension: the voter's `permanent_absentee_active` is set to false and an `ENROLLMENT_SUSPENDED` entry naming the enrollment as its subject is appended.

A request sitting in `ADDRESS_HOLD` is not dead. The clerk may re-open address verification for it, which creates a fresh verification in `PENDING` for that request and requires the request's status to be exactly `ADDRESS_HOLD`, else `ERR_REQUEST_STATE_INVALID`. When a result on that re-opened verification comes back `MATCH_SAME` or `MATCH_FORWARDABLE`, the request advances `ADDRESS_HOLD → ADDRESS_CLEARED` with `forwarding_class` set per the new result and the verification moving `PENDING → CLEARED`.

Approval is the gate to packeting. It requires the request to be in `ADDRESS_CLEARED`, else `ERR_REQUEST_STATE_INVALID`, and it re-checks the voter's `registration_status` — a voter who went inactive between logging and approval is rejected a second time with `ERR_VOTER_REGISTRATION_INACTIVE`. Approval moves the request `ADDRESS_CLEARED → APPROVED`. If `permanent_flag` was true and the voter has no enrollment in `ACTIVE` or `SUSPENDED`, approval also creates a permanent absentee enrollment in `ACTIVE` and sets the voter's `permanent_absentee_active` to true.

Rejection is available from `RECEIVED`, `ADDRESS_HOLD`, or `ADDRESS_CLEARED` — those three and no others, else `ERR_REQUEST_STATE_INVALID` — and records the operator-supplied `rejection_reason_code` while moving the request to `REJECTED`. Rejection from any of the three also sets every linked address verification still in `PENDING` to `FAILED`. `MAILED`, `REJECTED`, and `SUPERSEDED` are the three terminal request statuses; the transition `APPROVED → MAILED` is not a clerk action at all but a system event driven by batch dispatch, described in §3.3.

Permanent absentee enrollment can also be created directly against a voter, in which case it opens in `ACTIVE` with `consecutive_undeliverable_count` at 0 and `last_confirmation_at` stamped with the logical-clock instant, and sets the voter's `permanent_absentee_active` to true. `reinstated_count` begins at 0. Reinstatement returns a suspended enrollment to service: it requires the enrollment's status to be exactly `SUSPENDED`, else `ERR_ENROLLMENT_NOT_SUSPENDED`, and requires a `confirmation_evidence_type` of `SIGNED_CONFIRMATION_CARD`, `IN_PERSON_UPDATE`, or `ONLINE_PORTAL_UPDATE`. It resets `consecutive_undeliverable_count` to 0, clears `suspension_reason_code` back to null, stamps `last_confirmation_at` with the current logical-clock instant, increments `reinstated_count` by one, sets the voter's `permanent_absentee_active` to true, and appends an `ENROLLMENT_REINSTATED` entry. The `ACTIVE → SUSPENDED → ACTIVE` cycle may repeat any number of times, and `reinstated_count` records how many times it has. Removal is permitted from either `ACTIVE` or `SUSPENDED`, else `ERR_ENROLLMENT_NOT_SUSPENDED`; it sets the status to the terminal `REMOVED` and clears the voter's `permanent_absentee_active` to false.

### 3.3. Building, Sealing, and Dispatching the Mail

A **MailingBatch** is the unit the mail house actually works with. An `ElectionsClerk` opens one against an `election_id` with a `batch_type` of `UOCAVA`, `DOMESTIC_INITIAL`, or `SUPPLEMENTAL`, and a `scheduled_send_date` as an ISO calendar date. The batch opens in status `DRAFT` with `packet_count` at 0 and `estimated_postage_cents` at 0, while `actual_postage_cents`, `sealed_at`, `dispatched_at`, and `cancellation_reason_code` all start null. Its `required_send_by_date` is derived, not supplied: it is the election's `uocava_send_deadline_date` when `batch_type` is `UOCAVA`, and the election's `domestic_send_deadline_date` for every other batch type.

Adding a **BallotPacket** to a batch requires the batch to be in `DRAFT`, else `ERR_BATCH_STATE_INVALID`. The payload names the `ballot_request_id` the packet fulfils and the declared outbound `packet_weight_grams`, which must be at least 1. Three eligibility checks apply. The request must be in `APPROVED`, else `ERR_REQUEST_STATE_INVALID`. The request's election must be the batch's election, else `ERR_REQUEST_ELECTION_MISMATCH`. And the batch type must match the voter: a `UOCAVA` batch accepts only voters whose `uocava_status` is `MILITARY` or `OVERSEAS`, a `DOMESTIC_INITIAL` batch accepts only voters whose `uocava_status` is `NONE`, and a `SUPPLEMENTAL` batch accepts either — a mismatch is reported as `ERR_UOCAVA_BATCH_MISMATCH`. The new packet opens in status `QUEUED` with `mailing_batch_id` pointing at the carrying batch, `batch_sequence` set to the batch's `packet_count` plus one so that it records the packet's 1-based creation order within the batch, and `packet_serial` stamped as the batch's `scheduled_send_date`, a hyphen, and that `batch_sequence` rendered zero-padded. Its `packet_postage_cents` is computed and written immediately, `mailed_at` and `undeliverable_reason_code` start null, and the batch's `packet_count` increments by one. That count reflects the packets in the batch whose status is `QUEUED`, `MAILED`, `RETURNED`, or `UNDELIVERABLE`.

Postage is assessed per packet, in integer cents, from four components summed in one pass. The first is the **outbound** charge, priced by declared weight against a three-tier schedule with an overweight extension: a packet weighing at most 28 grams costs 73 cents; a heavier packet weighing at most 57 grams costs 129 cents; a heavier packet weighing at most 85 grams costs 185 cents; and a packet over 85 grams costs 185 cents plus 56 cents for each additional 28-gram step needed to cover the excess, where the number of steps is the excess weight over 85 grams divided by 28 and rounded up to the next whole number. The second is the **overseas surcharge**: for a voter whose `uocava_status` is anything other than `NONE`, fifteen percent of that packet's outbound charge, rounded half-up to a whole cent; for a domestic voter, nothing. The third is the **forwarding endorsement**: 8 cents when the fulfilled request's `forwarding_class` is `FORWARDABLE`, because that packet carries the forwarding endorsement imprint, and nothing otherwise — a `SAME_ADDRESS` packet never pays it, and neither does an `UNKNOWN` or `NON_FORWARDABLE` one. The fourth is the flat **prepaid return postage** of 68 cents, which every packet carries. The sum of those four components is the packet's `packet_postage_cents`.

The order of rounding in the batch total is pinned and must not be reordered. The overseas surcharge is rounded to a whole cent **per packet**, and the batch total is then the sum of the already-rounded per-packet figures. A batch total computed by summing outbound charges first, taking fifteen percent of that sum, and rounding once is wrong; the two orders differ by as much as one cent per packet. Spoiled packets are always excluded from a batch total and queued packets are always included.

Sealing a batch freezes the money. It requires the batch to be in `DRAFT`, else `ERR_BATCH_STATE_INVALID`, and requires `packet_count` to be at least 1. The **estimated** variant of the postage assessment is computed over the batch's packets whose status is `QUEUED` at that instant, written to `estimated_postage_cents`, and frozen there permanently. That figure is then added to the election's `postage_committed_cents`, and the batch moves `DRAFT → SEALED` with `sealed_at` stamped from the logical clock. The postage authority check runs before the commitment lands: the election's current `postage_committed_cents` plus this batch's estimated total must be at most the election's `postage_budget_cents`, and a seal that would breach the authority is rejected with `ERR_POSTAGE_BUDGET_EXCEEDED`.

Dispatching a batch requires it to be in `SEALED`, else `ERR_BATCH_STATE_INVALID`, and the logical clock's date must be on or before the batch's `required_send_by_date`. Missing that date is a statutory failure whose code depends on the batch type: a late `UOCAVA` batch is rejected with `ERR_UOCAVA_SEND_DEADLINE_PASSED`, and a late `DOMESTIC_INITIAL` or `SUPPLEMENTAL` batch with `ERR_DOMESTIC_SEND_DEADLINE_PASSED`. The **actual** variant of the postage assessment is then computed over the packets whose status is `QUEUED` at dispatch time and written to `actual_postage_cents`, and added to the election's `postage_actual_cents`. Because packets spoiled between seal and dispatch are excluded from the actual variant while the estimated variant already froze them in, the actual figure is strictly below the frozen estimate whenever a request was superseded after sealing, and equal to it otherwise. The postage authority is re-checked on the actual side: the election's `postage_actual_cents` plus this batch's actual total must be at most `postage_budget_cents`, else `ERR_POSTAGE_BUDGET_EXCEEDED`.

Dispatch is the depth-three cascade at the heart of the mailing phase, and every link fires. The batch moves `SEALED → DISPATCHED` with `dispatched_at` stamped. First link: every packet in the batch still in `QUEUED` moves `QUEUED → MAILED` with `mailed_at` stamped from the logical clock. Second link, caused by each packet mailing: that packet's ballot request moves `APPROVED → MAILED`. Third link, caused by the requests reaching `MAILED`: the election's `packets_mailed_count` and `outstanding_packet_count` are recomputed, and the election auto-advances `PRE_MAIL → MAILING` if it is still in `PRE_MAIL`. A `BATCH_DISPATCHED` entry is appended.

Cancellation is available from `DRAFT` or `SEALED` — those two and no others, else `ERR_BATCH_STATE_INVALID` — records the operator's `cancellation_reason_code`, and moves the batch to the terminal `CANCELLED`. From either status, every packet in the batch still in `QUEUED` moves `QUEUED → SPOILED` and a `BATCH_CANCELLED` entry is appended. Cancelling from `SEALED` additionally performs the compensating action: the batch's frozen `estimated_postage_cents` is subtracted from the election's `postage_committed_cents`, restoring the exact pre-seal value as required by §2.11. Cancelling from `DRAFT` has no postage effect, because nothing was ever committed.

When the carrier hands a mailed packet back, the clerk logs it as undeliverable with an `undeliverable_reason_code` of `NO_SUCH_ADDRESS`, `MOVED_NO_FORWARD`, `REFUSED`, or `VACANT`. The packet must be in `MAILED`, else `ERR_PACKET_STATE_INVALID`, and moves `MAILED → UNDELIVERABLE`. The election's `undeliverable_packet_count` and `outstanding_packet_count` are recomputed, and a `PACKET_UNDELIVERABLE` entry is appended. This is the second head of the enrollment-suspension cascade and behaves exactly as the address-failure head does: the voter's enrollment, if `ACTIVE`, has its `consecutive_undeliverable_count` incremented by one and transitions `ACTIVE → SUSPENDED` with `suspension_reason_code` set to `PACKET_UNDELIVERABLE` once the new value reaches two or more, and that suspension in turn clears the voter's `permanent_absentee_active` to false and appends an `ENROLLMENT_SUSPENDED` entry. `SPOILED`, `RETURNED`, and `UNDELIVERABLE` are the three terminal packet statuses.

### 3.4. Logging Returned Envelopes and Judging Timeliness

When a voted ballot comes back, an `ElectionsClerk` logs a **ReturnEnvelope** against the packet it was mailed in. The payload names the `ballot_packet_id` and the `intake_channel`, which is `USPS`, `DROPBOX`, or `IN_PERSON`, and may carry the carrier's `postmark_date` as an ISO calendar date together with `postmark_legible`, a boolean that defaults to true and is set false when the postmark is missing, smudged, or unreadable. Drop-box and counter returns carry no postmark at all, so `postmark_date` is null for them and they get no grace window whatsoever.

Intake requires the election's posture to be `MAILING` or `RECEIVING`; once the posture reaches `CANVASS_LOCKED` intake is refused with `ERR_ELECTION_POSTURE_FORBIDS`. The addressed packet must be in `MAILED` or `RETURNED`; any other packet status is reported as `ERR_PACKET_STATE_INVALID`. Allowing an already-`RETURNED` packet through that gate is deliberate: a second scan of the same packet should surface as a duplicate rather than as a packet-state problem, and it does — if a return envelope already exists for this `ballot_packet_id` and was not itself minted by a remake (that is, its `remade_from_envelope_id` is null), the intake is rejected with `ERR_DUPLICATE_ENVELOPE_FOR_PACKET`.

A successful intake creates the envelope with all three of its state dimensions at their initial values — `signature_status` of `UNVERIFIED`, `custody_status` of `SEALED`, and `challenge_status` of `NONE` — with `received_at` stamped from the logical clock, `review_round_count` at 0, and `remade_from_envelope_id`, `final_timeliness`, `resolved_signature_confidence`, `separation_run_sequence`, `challenge_reason_code`, and `challenge_findings` all null. The carrying packet moves `MAILED → RETURNED`. The election's `envelopes_received_count`, `returned_packet_count`, and `outstanding_packet_count` are recomputed, the election auto-advances `MAILING → RECEIVING` if this is its first intake, and an `ENVELOPE_INTAKE` entry is appended.

Timeliness is judged twice with two different burdens of proof, and the two verdicts are stored in separate fields. The **preliminary** judgment is written to `preliminary_timeliness` at intake and gives an unreadable postmark the benefit of the doubt. The **final** judgment is written to `final_timeliness` by the canvass checkpoint of §3.9 and does not, because the statutory record must show a legible postmark on or before `election_date`. Both judgments share one derived boundary: the **grace limit** is the election's `return_deadline_at` advanced by the election's `postmark_grace_days` whole days — seven days by default. Day arithmetic adds exact 24-hour multiples and all instant comparisons are at whole-second resolution in UTC.

For the two channels that carry no carrier postmark — `DROPBOX` and `IN_PERSON` — both judgments are identical and there is no grace at all: the verdict is `TIMELY` when `received_at` is at or before `return_deadline_at`, and `UNTIMELY` otherwise. Arrival exactly at `return_deadline_at` counts as `TIMELY`.

For the `USPS` channel the evaluation proceeds in three steps. If `received_at` is at or before `return_deadline_at`, the verdict is `TIMELY` in both variants; equality is timely. Otherwise, if `received_at` is strictly after the grace limit, the verdict is `UNTIMELY` in both variants; arrival exactly at the grace limit is still inside the window. What remains is arrival strictly after `return_deadline_at` and at or before the grace limit, and here the two variants diverge and each branch is spelled out.

In the preliminary variant, an envelope inside the grace window whose `postmark_legible` is false, or whose `postmark_date` is null, is recorded as `PROVISIONAL_TIMELY_POSTMARK` — intake presumes a timely postmark. An envelope with a legible postmark whose `postmark_date` is on or before the election's `election_date` is likewise recorded as `PROVISIONAL_TIMELY_POSTMARK`. An envelope with a legible postmark dated strictly after `election_date` is recorded as `UNTIMELY`.

In the final variant, an envelope inside the grace window whose `postmark_legible` is false, or whose `postmark_date` is null, becomes `UNTIMELY` — no presumption survives the canvass. An envelope with a legible postmark whose `postmark_date` is on or before `election_date` is recorded as `TIMELY_BY_POSTMARK`, a distinct value from the plain `TIMELY` reserved for envelopes that beat the deadline outright. An envelope with a legible postmark dated strictly after `election_date` is `UNTIMELY`. So the two variants differ on exactly one row of the table: an illegible or missing postmark inside the grace window, which the preliminary judgment calls `PROVISIONAL_TIMELY_POSTMARK` and the final judgment calls `UNTIMELY`.

### 3.5. Signature Comparison, Reviewer Certification, and Escalation

Signature reviewers are created by an `ElectionsAdmin` with a `full_name` and a `party_affiliation`, the latter driving bipartisan remake-team composition later on. `training_status` may be supplied and defaults to `UNTRAINED`, the other two values being `TRAINED` and `CERTIFIED_LEAD`. When `training_completed_at` — the instant the reviewer completed the signature-comparison curriculum — is supplied, the reviewer's `training_expires_at` is derived as that instant advanced by 365 whole days; when `training_completed_at` is null, `training_expires_at` is null too. A `curriculum_version` records the curriculum edition of the most recent completion and defaults to null. Both workload counters initialise to 0: `active_review_count` is the number of the reviewer's signature reviews still in `ASSIGNED`, and `completed_review_count` is the number in `SUBMITTED`. A training completion may be recorded later by the admin with a `completed_at` instant and a `curriculum_version`, optionally naming a new `training_status` which defaults to `TRAINED` when omitted; recording it sets `training_completed_at` from `completed_at` and refreshes `training_expires_at` to that instant advanced by 365 days.

Opening a review round is a clerk action, and the reviewer is chosen by the server — never named by the client. A round may be opened when the envelope's `signature_status` is `UNVERIFIED` or `ESCALATED`; any other value is rejected with `ERR_ENVELOPE_SIGNATURE_STATE_INVALID`. Opening the first round additionally requires the envelope's `custody_status` to be `SEALED`. The election's posture must be `RECEIVING` or `CANVASS_LOCKED`. The round number under construction is the envelope's `review_round_count` plus one, and it may never exceed three — three rounds is the ceiling, and a request that would open a fourth is refused with `ERR_ENVELOPE_SIGNATURE_STATE_INVALID`.

The **selector policy** picks the reviewer. A reviewer is a candidate only if all of the following hold: their `training_status` is `TRAINED` or `CERTIFIED_LEAD`; their `training_expires_at` is strictly later than the logical clock's current value; their `active_review_count` is strictly below the open-review ceiling of 12; they hold no signature review at all on this envelope, of any status, which is the segregation-of-duties exclusion of §2.10; and, when the round being opened demands a lead, their `training_status` is specifically `CERTIFIED_LEAD`. A lead is demanded in exactly two situations: the round being opened is round three, or the immediately preceding round's outcome was the lead-restricted escalation described below. Reviewers are drawn from the county's whole pool with no election scoping. Candidates are ranked by `active_review_count` ascending, then by `completed_review_count` ascending, then by `created_at` ascending as the deterministic final tie-break — never by `id` — and the first candidate under that ranking is selected. If the candidate set is empty, the request is rejected with `ERR_NO_ELIGIBLE_REVIEWER`, no signature review row is created, and the envelope's `signature_status` is left exactly as it was.

A successful opening creates a **SignatureReview** in status `ASSIGNED` with `return_envelope_id` pointing at the envelope, `reviewer_id` set to the selected reviewer, and `review_round` set to the round number, and increments the selected reviewer's `active_review_count` by one. Its `decision`, `similarity_score`, `confidence_score`, `notes`, and `submitted_at` all start null. The envelope's signature dimension moves `UNVERIFIED → PENDING_REVIEW` for round one, and `ESCALATED → PENDING_REVIEW` for rounds two and three.

Submitting a decision is the assigned `SignatureReviewer`'s act alone. The review must be in `ASSIGNED`; a second submission on the same review, or one on a review already voided, is rejected with `ERR_REVIEW_ALREADY_SUBMITTED`. The acting `X-User-ID` must equal the review's `reviewer_id`, else `ERR_NOT_ASSIGNED_REVIEWER`. The reviewer's `training_status` must be `TRAINED` or `CERTIFIED_LEAD` and their `training_expires_at` must be strictly later than the logical clock's current value — a null or already-passed expiry is rejected with `ERR_REVIEWER_TRAINING_INVALID`. The envelope's `signature_status` must be `PENDING_REVIEW`, else `ERR_ENVELOPE_SIGNATURE_STATE_INVALID`. The payload carries the `decision`, optionally a `similarity_score`, and optionally free-text `notes` preserved for the audit trail. The four decisions are `MATCH`, `NO_MATCH`, `MISSING_SIGNATURE`, and `ABSTAIN`. A `similarity_score` is the reviewer's visual similarity judgment as a whole number from 0 through 100 inclusive; it is required for `MATCH` and for `NO_MATCH`, and forbidden for `MISSING_SIGNATURE`.

Submission stamps `submitted_at` from the logical clock, moves the review `ASSIGNED → SUBMITTED`, decrements the reviewer's `active_review_count` by one, increments their `completed_review_count` by one, increments the envelope's `review_round_count` by one, and appends a `SIGNATURE_DECISION` entry whose subject is the envelope.

The **confidence score** is computed at submission and written to `confidence_score`. Four ingredients feed it. The **signature age in days** is the whole number of days between the voter's `last_signature_update_at` and the envelope's `received_at`, obtained by dividing the elapsed time by 86400 seconds and discarding any fraction. The **on-file factor** rewards a registration record with more than one exemplar: it is 0.025 for each exemplar beyond the first — that is, 0.025 multiplied by the voter's `signature_on_file_count` less one — capped at 0.10, so the reward stops growing once five exemplars are on file. The **staleness penalty** is 0.05 when the signature age in days is strictly greater than 1460 days, which is four years, and zero otherwise. The **lead bonus** is 0.03 when the submitting reviewer's `training_status` is `CERTIFIED_LEAD` and zero otherwise.

From those, the raw score is the `similarity_score` divided by 100, multiplied by the quantity one plus the on-file factor plus the lead bonus, minus the staleness penalty. That raw value is then clamped into the closed range from 0.0 to 1.0 — anything below 0.0 becomes 0.0 and anything above 1.0 becomes 1.0 — and the clamped value is rounded half-up to four decimal places to give `confidence_score`. Because `MISSING_SIGNATURE` and `ABSTAIN` carry no `similarity_score`, a review bearing either of those decisions has a null `confidence_score`. Reviews in `VOIDED` never contribute to any of this and never advance `review_round_count`.

Two confidence thresholds govern the outcome: the auto-accept threshold of 0.72 and the reject floor of 0.55. The envelope's signature dimension is then resolved by walking the envelope's submitted reviews ordered by `review_round` ascending with `created_at` ascending as the tie-break — never by `id` — and reading the round-one, round-two, and round-three decisions, treating absent rounds as absent rather than as any particular value. Reviews in `VOIDED` are excluded from that set.

One rule overrides every round. If any submitted decision on the envelope is `MISSING_SIGNATURE`, the outcome is a cure requirement with a reason of `MISSING_SIGNATURE`, and it is dispositive at whatever round it appears.

Otherwise, at **round one** five cases are enumerated. A `MATCH` whose `confidence_score` is at or above 0.72 accepts the signature. A `MATCH` whose `confidence_score` is at or above 0.55 but strictly below 0.72 escalates. A `MATCH` whose `confidence_score` is strictly below 0.55 escalates with a lead restriction. A `NO_MATCH` escalates. An `ABSTAIN` escalates.

At **round two**, with both round-one and round-two decisions in hand, five cases are again enumerated, and confidence no longer gates the result. Two `MATCH` decisions accept. Two `NO_MATCH` decisions produce a cure requirement with a reason of `SIGNATURE_MISMATCH`. Exactly one `ABSTAIN` with the other decision being `MATCH` accepts. Exactly one `ABSTAIN` with the other decision being `NO_MATCH` escalates with a lead restriction. One `MATCH` against one `NO_MATCH` — a split — escalates with a lead restriction.

**Round three** is dispositive and is decided by a `CERTIFIED_LEAD`. A `MATCH` accepts. A `NO_MATCH` produces a cure requirement with a reason of `SIGNATURE_MISMATCH`. An `ABSTAIN` also produces a cure requirement with a reason of `SIGNATURE_MISMATCH`, as the empty-outcome fallback — there is no fourth round.

The two escalation flavours differ only in who may take the next round. A plain escalation moves the envelope `PENDING_REVIEW → ESCALATED` and leaves the next round open to any `TRAINED` or `CERTIFIED_LEAD` reviewer. A lead-restricted escalation moves the envelope `PENDING_REVIEW → ESCALATED` and restricts the next round to a `CERTIFIED_LEAD` reviewer. Either way a `SIGNATURE_ESCALATION` entry is appended, and no new review row is created by the escalation itself — the envelope simply waits until a clerk opens the next round, which is when the `ESCALATED → PENDING_REVIEW` step occurs. That `PENDING_REVIEW → ESCALATED → PENDING_REVIEW` cycle repeats until a dispositive outcome lands or `review_round_count` reaches three.

An acceptance moves the envelope `PENDING_REVIEW → ACCEPTED` and sets `resolved_signature_confidence` to the submitted review's `confidence_score`. A cure requirement moves the envelope `PENDING_REVIEW → CURE_REQUIRED` and sets `resolved_signature_confidence` to the dispositive review's `confidence_score`. In general, `resolved_signature_confidence` is the `confidence_score` of the dispositive review — the submitted review with the highest `review_round`, with `created_at` ascending as the tie-break — carried at four decimal places. Acceptance does not by itself change the countable tally, because countability is governed by the custody dimension and only separation brings an envelope into it. A cure requirement does not by itself change `open_cure_count` either; that counter moves only when a notice is actually issued.

There is exactly one situation in which a signature mismatch does **not** earn the voter a cure. When the envelope under review is itself a remake replacement — its `remade_from_envelope_id` is non-null — and a mismatch outcome is reached at round two or later, the outcome is a rejection without cure, because the voter already exhausted their cure opportunity on the superseded envelope. The envelope's signature dimension moves `PENDING_REVIEW → REJECTED`, its custody dimension moves `SEALED → SEQUESTERED`, the voter's `provisional_ballot_eligible` is set to true, and the election's `provisional_referral_count` increments by one. `ACCEPTED` and `REJECTED` are the two terminal values of the signature dimension.

### 3.6. Cure Notices, Evidence, and the Propagated Cure Deadline

A voter whose envelope signature is missing or mismatched is entitled to fix it, and a **CureNotice** is the instrument that gives them the chance. A clerk issues one against an envelope whose `signature_status` is `CURE_REQUIRED` — any other signature state is refused with `ERR_ENVELOPE_SIGNATURE_STATE_INVALID` — and only when that envelope has no notice already open, meaning none in `ISSUED` and none in `UNDER_EVIDENCE_REVIEW`; a second open notice on the same envelope is refused with `ERR_CURE_STATE_INVALID`. The election's posture must be `RECEIVING`. Issuance takes no body fields: everything on the notice is derived. The notice opens in `ISSUED` with `return_envelope_id` pointing at the envelope, `issued_at` stamped from the logical clock, `reason_code` copied from the dispositive review outcome — either `MISSING_SIGNATURE` or `SIGNATURE_MISMATCH` — `evidence_submission_count` and `deficiency_count` at 0, and `resolved_at` null. The election's `open_cure_count` increments by one and a `CURE_ISSUED` entry is appended.

The deadline written onto that notice is the most delicate derivation in the service, because the cure deadline is bounded by the canvass lock while the canvass length itself depends on how many cures are open. The dependency looks circular and is resolved by a **pinned evaluation order** that must not be reordered.

Step one: insert the new notice in `ISSUED`, then count the election's open cure notices — those whose status is `ISSUED` or `UNDER_EVIDENCE_REVIEW`, reached from the election through its batches, packets, and envelopes — inclusive of the notice being issued. Step two: the election's `canvass_days` becomes the extended canvass length of 21 whole days when that open-cure count is at least 3, and otherwise remains the standard 17 whole days. Step three: the election's `canvass_lock_at` becomes `return_deadline_at` advanced by `canvass_days` days. Step four: the cure base deadline is `return_deadline_at` advanced by the election's `cure_window_days` whole days. Step five: `cure_deadline_at` on the notice is the earlier of that cure base deadline and the canvass lock instant reduced by one whole day.

Three values are frozen on the notice at issuance and are never recomputed afterwards: `cure_deadline_at`, `canvass_days_at_issue` — the `canvass_days` value that was used to derive it — and `open_cure_count_at_issue`, the open-cure count observed at issuance inclusive of this notice. A later notice that pushes the open-cure count past the threshold does **not** extend an earlier notice's deadline. The election's own `canvass_days` and `canvass_lock_at`, by contrast, are monotone: once the extended 21-day length has been reached they never return to the standard 17, even if every cure subsequently closes.

The voter answers a notice by submitting evidence, which a clerk logs. Submission requires the notice to be in `ISSUED`, else `ERR_CURE_STATE_INVALID`, requires the logical clock to be at or before the notice's frozen `cure_deadline_at`, else `ERR_CURE_DEADLINE_PASSED`, and requires the election's posture to be anything other than `CERTIFIED`. The payload names the `evidence_type` — `SIGNED_AFFIDAVIT`, `ID_COPY`, or `WITNESS_ATTESTATION` — the `submission_channel` — `MAIL`, `EMAIL`, `IN_PERSON`, or `PORTAL` — and `affirmation_signed`, a boolean stating whether the statutory affirmation block was signed by the voter. A **CureEvidence** row is created with `cure_notice_id` pointing at the notice and `received_at` stamped from the logical clock; its `accepted` and `deficiency_reason_code` both start null and are written only by adjudication. The notice's `evidence_submission_count` increments by one and the notice moves `ISSUED → UNDER_EVIDENCE_REVIEW`. No transparency entry is appended on submission — the log carries only issuance and adjudication events for cures.

A `CanvassSupervisor` adjudicates. The notice must be in `UNDER_EVIDENCE_REVIEW`, else `ERR_CURE_STATE_INVALID`, and the adjudication names an `outcome` of either `CURE` or `DEFICIENT`, optionally with a `deficiency_reason_code` drawn from `AFFIRMATION_UNSIGNED`, `WRONG_EVIDENCE_TYPE`, and `ILLEGIBLE`. Both branches carry the same weight of specification. The newest evidence row on the notice — the one with the highest `received_at`, with `created_at` ascending as the tie-break — is the one adjudicated.

On a `CURE` outcome the newest evidence row must have `affirmation_signed` true, and the logical clock must still be at or before `cure_deadline_at`, else `ERR_CURE_DEADLINE_PASSED`. The notice moves `UNDER_EVIDENCE_REVIEW → CURED`, `resolved_at` is stamped from the logical clock, the newest evidence row's `accepted` is set to true, the envelope's signature dimension moves `CURE_REQUIRED → ACCEPTED` while its `resolved_signature_confidence` is deliberately left unchanged — a cure resolves identity, not visual similarity — the election's `open_cure_count` decrements by one, and a `CURE_ADJUDICATED` entry is appended.

On a `DEFICIENT` outcome the newest evidence row's `accepted` is set to false and its `deficiency_reason_code` is recorded, the notice's `deficiency_count` increments by one, and the notice returns `UNDER_EVIDENCE_REVIEW → ISSUED` so the voter may submit again. A `CURE_ADJUDICATED` entry is appended here too. `cure_deadline_at` is emphatically **not** extended by a deficient round: the `ISSUED → UNDER_EVIDENCE_REVIEW → ISSUED` cycle may repeat any number of times against the same frozen deadline, and `deficiency_count` records how many times it has. The election's `open_cure_count` is unaffected, since the notice remains open throughout.

`CURED`, `EXPIRED`, and `WITHDRAWN` are the three terminal notice statuses. A notice expires at the canvass checkpoint, described in §3.9, and is withdrawn when the envelope it belongs to is superseded by a remake, described in §3.8.

### 3.7. Observer Access, Challenges, and Adjudication

Transparency is a scheduled activity in this domain, not an open door. An **ObserverAccessSession** is booked against an election by an `ElectionsClerk` or by the `Observer` themselves, naming the `observer_user_id` credential the office issued, the `observer_name` for the transparency log, the `organization` — a party committee, campaign, or media organisation — the `party_affiliation`, the `station_area` the observer will watch, and the half-open access window bounded by `window_start_at` inclusive and `window_end_at` exclusive. The `station_area` is one of `INTAKE`, `SIGNATURE_REVIEW`, `SEPARATION`, or `REMAKE`. The window must have `window_end_at` strictly later than `window_start_at`, else `ERR_INVALID_REQUEST`. The session opens in `SCHEDULED` with `revocation_reason_code` null, and an `OBSERVER_SESSION_OPENED` entry is appended.

Two capacity constraints protect the floor, and both use **half-open interval geometry**: a new window collides with an existing one when the new window's start is strictly before the existing window's end **and** the existing window's start is strictly before the new window's end. Touching endpoints therefore do not collide — a session ending at exactly the instant another begins is fine. Sessions whose status is `REVOKED` are excluded from the occupancy set entirely. The per-party constraint allows at most one overlapping session per `party_affiliation` for the same election; a second overlapping session of the same party is rejected with `ERR_OBSERVER_PARTY_SLOT_CONFLICT`. The floor constraint aggregates occupancy across all parties under the same geometry and requires it to stay at 3 or fewer at every instant of the new window; a booking that would push it past 3 is rejected with `ERR_OBSERVER_FLOOR_CAPACITY`.

Check-in activates floor access. The session must be in `SCHEDULED`, else `ERR_SESSION_STATE_INVALID`; the acting `X-User-ID` must equal the session's `observer_user_id`; and the logical clock must lie inside the half-open window — at or after `window_start_at` and strictly before `window_end_at` — else `ERR_OBSERVER_WINDOW_NOT_ACTIVE`. Check-in moves the session `SCHEDULED → CHECKED_IN` and appends an `OBSERVER_SESSION_OPENED` entry recording `actor_role` as `Observer`.

Access can be withdrawn. An `ElectionsAdmin` or a `CanvassSupervisor` may revoke a session that is in `SCHEDULED` or in `CHECKED_IN` — those two and no others, else `ERR_SESSION_STATE_INVALID` — recording the `revocation_reason_code`. Revocation from either status moves the session to the terminal `REVOKED`, frees the party slot for the remainder of that window, and appends an `OBSERVER_SESSION_REVOKED` entry. `CLOSED` is the other terminal status, reached by the canvass checkpoint when the window has run out.

Filing a challenge is the observer's substantive power, and it is tightly fenced. The envelope's `challenge_status` must be `NONE`, else `ERR_CHALLENGE_STATE_INVALID`. Its `custody_status` must be `SEALED` or `SEQUESTERED`: an envelope that has already been separated can no longer be tied back to a voter, so it cannot be challenged, and an attempt is rejected with `ERR_ENVELOPE_CUSTODY_STATE_INVALID`. The acting observer must hold a session for this election that is in `CHECKED_IN`, whose half-open window contains the current logical clock, and whose `station_area` is `INTAKE` or `SIGNATURE_REVIEW` — the two stations from which a challenge can legitimately be raised. Any failure of that access test is reported as `ERR_OBSERVER_SESSION_REQUIRED`. Once a session has been closed by the canvass checkpoint, no further challenge may be filed under it.

The filing names a `challenge_reason_code` of `SIGNATURE_DISPUTE`, `IDENTITY_DISPUTE`, `DUPLICATE_VOTE`, or `ENVELOPE_TAMPERING`. It moves the envelope's challenge dimension `NONE → CHALLENGED`, moves its custody dimension `SEALED → SEQUESTERED` when it was `SEALED`, and appends a `CHALLENGE_FILED` entry recording `actor_role` as `Observer`.

Adjudication belongs to the `CanvassSupervisor` and requires the envelope's `challenge_status` to be `CHALLENGED`, else `ERR_CHALLENGE_STATE_INVALID`. The adjudication names an `outcome` of `SUSTAIN` or `OVERRULE` together with the `challenge_findings` recorded for the record. Both branches are fully specified and a `CHALLENGE_ADJUDICATED` entry is appended in either case.

Sustaining a challenge moves the challenge dimension `CHALLENGED → SUSTAINED`, sets the envelope's `signature_status` to `REJECTED` while leaving its custody dimension at `SEQUESTERED`, sets the voter's `provisional_ballot_eligible` to true, increments the election's `provisional_referral_count` by one, and appends a `PROVISIONAL_REFERRAL` entry whose subject is the voter. Overruling moves the challenge dimension `CHALLENGED → OVERRULED` and returns the envelope to the separable pool by moving its custody dimension `SEQUESTERED → SEALED`, but **only** when nothing else disqualifies it — that is, only when its `signature_status` is `ACCEPTED` and its `final_timeliness` is anything other than `UNTIMELY`. If either of those fails, the envelope stays `SEQUESTERED` even though the challenge was overruled. That `SEALED → SEQUESTERED → SEALED` round trip is the only cycle on the custody dimension. `SUSTAINED` and `OVERRULED` are the two terminal values of the challenge dimension.

### 3.8. Remaking Damaged and Duplicate Ballots

Some ballots cannot be fed through a tabulator: the paper is torn, the marks are unreadable, the envelope was damaged in transit, or the same voter's ballot arrived twice. In those cases a two-person bipartisan team transcribes the voter's intent onto a fresh ballot, and a **RemakeRecord** is the audit artifact that proves they did it together.

A `CanvassSupervisor` opens a remake session against an envelope. The payload names `team_member_a_reviewer_id` and `team_member_b_reviewer_id` as the two team members, a `reason_code` of `DAMAGED`, `UNREADABLE_MARKS`, `DUPLICATE_BALLOT`, or `TORN_ENVELOPE`, the `session_start_at` and `session_end_at` bounding the two-person session, and the stale-view guard `expected_envelope_version` of §2.7. The `session_end_at` must be strictly later than `session_start_at`, else `ERR_INVALID_REQUEST`. A `remade_serial` may optionally be supplied at this point; it defaults to null and is in any case required at completion. The record opens in `OPEN` with `original_envelope_id` pointing at the envelope under remake, and `remade_envelope_id`, `completed_at`, and `voided_reason_code` all null. Opening it increments the envelope's `version` by one.

Four gates protect the opening. The envelope's `custody_status` must be `SEALED` or `SEQUESTERED`, else `ERR_ENVELOPE_CUSTODY_STATE_INVALID`. The team must be bipartisan — the two nominated identifiers must not be the same reviewer and the two reviewers' `party_affiliation` values must differ — else `ERR_REMAKE_TEAM_NOT_BIPARTISAN`. Neither member may hold a signature review on the envelope being remade, else `ERR_SEGREGATION_OF_DUTIES`. And neither member may be double-booked.

The double-booking test uses **closed-interval geometry widened by a changeover buffer**, which is deliberately the opposite of the observer geometry in §3.7. For either team member, the proposed session collides with any remake record in `OPEN` or `COMPLETED` on which that reviewer already sits when the proposed `session_start_at` reduced by fifteen minutes is at or before the existing session's `session_end_at` **and** the existing session's `session_start_at` is at or before the proposed `session_end_at` increased by fifteen minutes. Touching endpoints therefore **do** collide, and so does a gap of less than a quarter of an hour, because the team needs that long to clear one ballot off the table before the next arrives. A collision is rejected with `ERR_REMAKE_TEAM_DOUBLE_BOOKED`. Records in `VOIDED` are excluded from the occupancy set.

Completing the session is the moment the replacement ballot legally exists. It requires the record to be in `OPEN`, else `ERR_REMAKE_STATE_INVALID`; the original envelope's `custody_status` to be `SEALED` or `SEQUESTERED`, else `ERR_ENVELOPE_CUSTODY_STATE_INVALID`; the original envelope's `challenge_status` to be anything other than `CHALLENGED`, else `ERR_CHALLENGE_STATE_INVALID`; and the election's posture to be `RECEIVING` or `CANVASS_LOCKED`. A `remade_serial` must be present, and it must be unique among the completed remake records of the same election — a repeat is rejected with `ERR_DUPLICATE_REMAKE_SERIAL`.

Completion moves the record `OPEN → COMPLETED`, stamps `completed_at` from the logical clock, and drives a three-link cascade on the custody dimension. First link: a replacement return envelope is minted with `remade_from_envelope_id` set to the original envelope's `id`, copying the original's `ballot_packet_id`, `intake_channel`, `postmark_date`, `postmark_legible`, `received_at`, `preliminary_timeliness`, `final_timeliness`, and `signature_status`, and opening with `custody_status` of `SEALED` and `challenge_status` of `NONE`; the record's `remade_envelope_id` is written to point at it, and the original envelope's custody dimension moves to `SUPERSEDED_BY_REMAKE`. Second link, caused by that supersession: the election's `countable_envelope_count` is recomputed — the original leaves the countable set immediately, and the replacement enters it only once it has been separated. Third link, caused by the count change: the election's `reconciliation_status` is recomputed, and `attributable_ballot_count` is recomputed so that the conservation invariant of §2.11 holds exactly.

Two further clean-ups ride along with completion, because the cure and the review follow the replacement rather than the superseded envelope. Any cure notice on the original envelope whose status is `ISSUED` or `UNDER_EVIDENCE_REVIEW` transitions to `WITHDRAWN` with `resolved_at` stamped and the election's `open_cure_count` decremented. Any signature review on the original envelope still in `ASSIGNED` transitions to `VOIDED`, and that reviewer's `active_review_count` decrements by one. A `REMAKE_COMPLETED` entry whose subject is the remake record is appended.

Voiding a remake is available from `OPEN` or from `COMPLETED` — those two and no others, else `ERR_REMAKE_STATE_INVALID` — records the `voided_reason_code`, frees both team members' session interval for future bookings, moves the record to the terminal `VOIDED`, and appends a `REMAKE_VOIDED` entry. Voiding a record that had already reached `COMPLETED` carries one extra precondition and one extra obligation. The precondition: the replacement envelope's `custody_status` must not be `COUNTED`, since a tabulated ballot cannot be un-tabulated, and an attempt is rejected with `ERR_REMAKE_STATE_INVALID`. The obligation is the compensating action: the replacement envelope's `signature_status` is set to `REJECTED` and its `custody_status` to `SEQUESTERED`, removing it from the countable pool, and the original envelope returns `SUPERSEDED_BY_REMAKE → SEALED` carrying its pre-remake `signature_status`. The election's `attributable_ballot_count` must land back on its exact pre-completion value; `envelopes_received_count`, as §2.11 says, does not come back down, because the replacement row is retained forever. `COMPLETED` and `VOIDED` are the two terminal remake statuses.

### 3.9. Separation, Counting, and the Canvass Checkpoint

Separation is the moment secrecy is created: the ballot leaves the envelope that names its voter, and from then on the two can never be re-associated. Because that is only true if enough ballots are separated together, a `CanvassSupervisor` performs separation in **runs** rather than one envelope at a time, submitting `return_envelope_ids` as an array of envelope identifiers. The election's posture must be exactly `RECEIVING`.

Two guards protect the run itself, and they are distinct. An empty `return_envelope_ids` array is rejected with `ERR_SEPARATION_SET_EMPTY`, because an empty run would write a transparency entry with no custody effect at all. A non-empty run containing fewer than 3 distinct envelopes is rejected with `ERR_BALLOT_SECRECY_POOL_TOO_SMALL`, because a pool that small would let a separated ballot be re-associated with its voter. Every listed envelope is resolved in array order, and the first identifier that resolves to nothing yields `ERR_ENVELOPE_NOT_FOUND`.

Each listed envelope must independently qualify. Its `custody_status` must be `SEALED`, else `ERR_ENVELOPE_CUSTODY_STATE_INVALID`. Its `signature_status` must be `ACCEPTED`, else `ERR_ENVELOPE_SIGNATURE_STATE_INVALID`. Its `challenge_status` must be anything other than `CHALLENGED`, else `ERR_CHALLENGE_STATE_INVALID`. And its `final_timeliness` must be anything other than `UNTIMELY`. A sequestered envelope is excluded from every separation run for as long as it remains sequestered.

An accepted run increments the election's `separation_run_sequence` by one and stamps that new value onto the `separation_run_sequence` field of every envelope in the run, so each ballot carries the identity of the batch it was anonymised in. Each listed envelope moves `SEALED → SEPARATED`, and the election's `countable_envelope_count` is recomputed. Exactly one `SEPARATION_RUN` entry is appended for the whole run, with the election as its subject and `ballot_content_disclosed` false. The run reports back the `election_id`, the `run_sequence` just assigned, the `separated_count` of envelopes it moved, the `secrecy_pool_size` of the submitted pool, and the election's fresh `countable_envelope_count` and `attributable_ballot_count`.

Counting a separated ballot is the supervisor's final custody act. It requires the envelope's `custody_status` to be `SEPARATED`, else `ERR_ENVELOPE_CUSTODY_STATE_INVALID`; its `challenge_status` to be either `NONE` or `OVERRULED`, else `ERR_CHALLENGE_STATE_INVALID`; and its `final_timeliness` to be either `TIMELY` or `TIMELY_BY_POSTMARK`, which means the canvass checkpoint must already have run and written that verdict. Counting moves the envelope `SEPARATED → COUNTED` and recomputes the election's `countable_envelope_count` and `attributable_ballot_count`. `COUNTED` and `SUPERSEDED_BY_REMAKE` are the two terminal values of the custody dimension.

The **canvass checkpoint** is the periodic sweep an `ElectionsAdmin` runs to let statutory time actually take effect, and it performs five jobs in one pass while incrementing the election's `canvass_sweep_index` by one.

Its first job is expiring overdue cures. Every cure notice of the election whose status is `ISSUED` or `UNDER_EVIDENCE_REVIEW` and whose frozen `cure_deadline_at` is strictly earlier than the current logical clock transitions to `EXPIRED`, with `resolved_at` stamped, the election's `open_cure_count` decremented, and a `CURE_EXPIRED` entry appended. Any evidence row still awaiting adjudication on such a notice has its `accepted` set to false and its `deficiency_reason_code` set to `ILLEGIBLE`, except that an already-recorded `deficiency_reason_code` is left as it stands. Each expiry then drives the three-link rejection cascade: the envelope's signature dimension moves `CURE_REQUIRED → REJECTED` and the election's `rejected_envelope_count` is recomputed; caused by that, the envelope's custody dimension moves `SEALED → SEQUESTERED`; and caused by the rejection, the voter's `provisional_ballot_eligible` is set to true, the election's `provisional_referral_count` increments by one, and a `PROVISIONAL_REFERRAL` entry naming the voter as its subject is appended.

Its second job is finalising timeliness. The final variant of the timeliness rule in §3.4 is written to `final_timeliness` on every return envelope of the election whose `custody_status` is anything other than `SUPERSEDED_BY_REMAKE`. Its third job follows directly: every envelope whose freshly written `final_timeliness` is `UNTIMELY` moves its custody dimension `SEALED → SEQUESTERED`. Its fourth job closes stale floor access: every observer session in `CHECKED_IN` whose `window_end_at` is at or before the current logical clock moves `CHECKED_IN → CLOSED`, after which no further challenge may be filed under it. Its fifth job is to recompute the accountability picture of §2.11 in full.

The checkpoint reports only what **this** sweep changed, not cumulative totals. It returns the new `canvass_sweep_index`, the `expired_cure_count` of notices this sweep expired, the `finalized_envelope_count` of envelopes whose `final_timeliness` this sweep wrote, the `sequestered_envelope_count` of envelopes this sweep moved to `SEQUESTERED` — whether by untimely finalisation or by the cure-expiry rejection cascade — the `rejected_envelope_count` of envelopes whose `signature_status` this sweep moved to `REJECTED`, the `closed_observer_session_count` of sessions this sweep closed, and the election's resulting `reconciliation_status`.

Stepping back, three separate events drive an envelope's custody dimension from `SEALED` to `SEQUESTERED`: its `signature_status` reaching `REJECTED`, its `challenge_status` reaching `CHALLENGED`, and its `final_timeliness` being written as `UNTIMELY` at the checkpoint. Only one event drives it back: a challenge being overruled while the signature is `ACCEPTED` and the final timeliness is not `UNTIMELY`, as described in §3.7.

Finally, the accountability picture is available as a computed read at any time. It reports the `election_id` alongside `packets_mailed_count`, `returned_packet_count`, `outstanding_packet_count`, `undeliverable_packet_count`, `envelopes_received_count`, `countable_envelope_count`, `attributable_ballot_count`, `rejected_envelope_count`, `provisional_referral_count`, `open_cure_count`, the `accountability_delta`, the resulting `reconciliation_status`, and both money figures, `postage_committed_cents` and `postage_actual_cents`. That read is what a canvass board looks at before it asks for certification, because certification cannot proceed while the delta is non-zero.
