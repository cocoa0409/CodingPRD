# Brokered Deposit Funding Compliance API — Product Requirements Document

## 1. Introduction

A bank funding desk lives with an uncomfortable asymmetry. Raising wholesale money through deposit brokers, listing services and reciprocal placement networks is fast and operationally cheap; getting the regulatory characterisation of that money wrong is slow and expensive. The same dollar can be a brokered deposit, a listing-service non-brokered deposit, a core deposit or a reciprocal deposit excluded from the brokered tally, and which one it is depends on the counterparty's legal authority over placement, on whether a primary purpose exception has been filed and is still reliable, and on whether the institution's reciprocal capacity still has room. That characterisation then propagates outward: it drives the call report line the balance lands on, the concentration metric it consumes, the rate ceiling the deposit must respect, and the liquidity buffer the treasurer must hold.

This document specifies the Brokered Deposit & Listing Service Funding Compliance API — a single system of record for the whole chain. It is built around four commitments. First, every classification is an immutable, attributable determination rather than an editable field, so an examiner can reconstruct why a balance sat where it sat. Second, every derived balance, ratio and posture is recomputed by the system from the placement book, never typed in by an operator, so the reported figure and the computed figure can be compared honestly. Third, no operator may both prepare and bless the same artefact: the desk originates, the second line determines and approves, the supervisor examines. Fourth, arithmetic is exact — money is an integer number of cents and every rate or ratio is an integer number of basis points, so a reconciliation either balances or it does not.

The system also has to behave deterministically under test and under audit. All time is read from a server-side logical clock rather than wall-clock time, all rejections are single-error and priority-ordered, and every write that could silently overwrite a determination the caller never observed is guarded by the caller's last-seen version of the parent record. The sections that follow define the global contract (§2), the business behaviour of each workflow (§3), the endpoint surface (§4) and the complete error catalogue (§5).

## 2. Global Specifications & System-Wide Principles

This section defines the system-wide contract: authentication, envelopes, pagination, arithmetic discipline, record identity, concurrency guards, rule precedence and the cascade semantics that hold the derived balances together. Every rule here applies across the whole API unless a §3 workflow narrows it explicitly.

### 2.1. User and Role-Based Access Control

Every request, without exception, carries two headers: `X-User-ID` identifying the acting operator and `X-User-Role` declaring the capacity in which that operator acts. If either header is absent, or if `X-User-Role` is not one of the six role names the system recognises, the request is refused with `ERR_UNAUTHENTICATED` (HTTP 401) before anything else about it is inspected. The six roles are `SystemAdmin`, `FundingDeskOfficer`, `ComplianceReviewer`, `TreasuryController`, `Examiner` and `BrokerRepresentative`. When the headers are well formed but the acting role does not appear on the authorised-role list of the addressed endpoint (§4), the request is refused with `ERR_UNAUTHORIZED` (HTTP 403).

Five of the six roles carry an opaque identity. When `X-User-Role` is `SystemAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server records it where a transition writes it (for example as `published_by_user_id` on a published rate benchmark) but never compares it to any entity's `id`. The same holds for `FundingDeskOfficer`, whose identifier is stamped into `prepared_by_user_id` on the artefacts it originates; for `ComplianceReviewer`, whose identifier is stamped into `reviewed_by_user_id`, `determined_by_user_id`, `checked_by_user_id`, `attested_by_user_id` and `approved_by_user_id` depending on which review it performs; for `TreasuryController`, whose identifier is stamped into `prepared_by_user_id` on a contingency plan; and for `Examiner`, whose identifier is recorded only through the notes and status changes it makes. None of these five identifiers is ever matched against a stored `id`.

`BrokerRepresentative` is different: its identity is entity-backed. When `X-User-Role` is `BrokerRepresentative`, `X-User-ID` is the `id` of the acting `Broker` row, and ownership checks on any resource that references a `Broker` compare the resource's broker foreign-key field to `X-User-ID`. A broker representative is read-only and narrowly scoped — it may read its own broker record, its own agreements and its own fee summary, and nothing else. Any request whose addressed resource resolves to a different broker is refused with `ERR_UNAUTHORIZED`.

Holding the right role is necessary but never sufficient. Both review chains are additionally guarded on `X-User-ID`, so the same human operator may not both prepare and bless the same artefact even when the role permits both actions; §2.9 states that rule in full. `SystemAdmin` is not exempt: it may perform any business operation for setup purposes, and it is still subject to every duty-segregation comparison, because those comparisons look at `X-User-ID` and ignore the role entirely.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size: it defaults to 10, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` controls the starting position within the result set, defaults to 0, and has a minimum of 0. Both are echoed in the `meta` object of the response alongside `total_count`, the number of records matching the filter before the page window is applied, and `has_more`, which is true when records remain beyond the current window.

Unless a specific list endpoint declares otherwise in §4, results are ordered by `created_at` ascending. Several collections declare their own ordering that supersedes that default: banks are listed by `created_at` ascending with ties broken by `cert_id` ascending; counterparties by `created_at` ascending with ties broken by `legal_name` ascending; published rate benchmarks by `effective_date` descending with ties broken by `created_at` descending, which is exactly the ranking the ceiling calculation uses to pick the governing publication; classification determinations by `effective_at` ascending with ties broken by `created_at` ascending; placements by `issue_date` ascending with ties broken by `created_at` ascending; rate-cap checks by `check_date` ascending with ties broken by `created_at` ascending; contingency plans by `effective_from` ascending with ties broken by `created_at` ascending; and call report filings by `report_period` ascending with ties broken by `created_at` ascending.

### 2.4. Money, Rates and Rounding Discipline

There are no floating-point numbers and no decimal strings anywhere in this contract. Money is always an integer number of cents carried in a field whose name ends in `_cents`; rates, ratios and thresholds are always an integer number of basis points carried in a field whose name ends in `_bps`. One basis point is one hundredth of one percent, so 10000 basis points is exactly 100 percent and a supplied threshold may never exceed 10000.

Two rounding modes are used, and which one applies is fixed per calculation rather than chosen at runtime. Ratio and capacity arithmetic uses floor division: the exact integer quotient, discarding any remainder, never a floating-point intermediate. Settlement arithmetic — accrued interest, contractual withdrawal penalties, per-line broker fees, weighted diligence scores and required liquidity buffers — evaluates the expression as an exact rational and then rounds halves away from zero, which for these non-negative quantities means a remainder of exactly one half rounds up to the next whole cent or whole point. Where a total is built from several rounded parts, the order is pinned by the rule that produces it and is stated with that rule in §3; rounding a sum of exact rationals once at the end, where the rule says to round each part first, is a different number and is wrong.

Any division whose denominator is zero yields zero rather than an error. This matters in practice for a newly registered bank whose `total_deposits_cents` is zero and for an exception filing that declares no transaction counts.

### 2.5. Record Identity, Timestamps and Versioning

Every resource carries a server-minted `id` that is a UUID string with no type prefix, and a `created_at` timestamp in ISO 8601 UTC with exactly three fractional digits. Most resources additionally carry `updated_at`, refreshed to the current logical-clock instant whenever any field of the record changes, and `version`, an integer that starts at 1 on creation and increases by exactly 1 on each mutation of the record.

Three record types are append-only ledger entries and deliberately carry neither `updated_at` nor `version`: a published national rate benchmark, a classification determination and a rate-cap check. Each of those is written once and never edited — a correction to a published benchmark is a new publication with a later `effective_date`, a correction to a classification is a new determination that supersedes the prior one, and a correction to a rate-cap review is simply a later review. For those three, only `id` and `created_at` are present.

A cascade that touches a related record mutates that record for versioning purposes as well. When a diligence action changes a counterparty's mirrored status, the counterparty's own `version` advances and its `updated_at` is refreshed; when a supervisory re-categorisation re-derives every program's ceiling, each of those programs advances its own `version`. The precise increments matter to two guards and are spelled out in §2.6 and §3.4.

### 2.6. Observed-Version Guards on Determinations and Re-Categorisations

Two writes in this system can legitimately succeed from any prior state, which means no lifecycle precondition would ever reject a second one. Both are therefore guarded by the caller's last observed version of the parent record.

A classification determination request must carry `expected_program_version`, a required input field holding the `version` of the target `DepositProgram` as the client last read it. If that value does not equal the program's current `version`, the determination is rejected with `ERR_STALE_PROGRAM_VERSION` (HTTP 412). Without the guard, a client holding an older view of the program could supersede a governing determination it never saw; with it, the outcome is a deterministic rejection that tells the client to re-read the program first.

A supervisory capital re-categorisation must carry `expected_institution_version`, a required input field holding the `version` of the target `Institution` as the client last read it. If that value does not equal the institution's current `version`, the re-categorisation is rejected with `ERR_STALE_INSTITUTION_VERSION` (HTTP 412). Any capital category is a legitimate successor to any other, so nothing else would stop a writer holding a stale view from silently reverting a supervisory downgrade.

No other write in the system takes a version field. Placement funding actions, program state actions, diligence actions, filing and review actions, plan lifecycle actions, call report workflow actions, balance adjustments, limit creation and plan drafting are all unversioned, and supplying a version field to them has no meaning.

### 2.7. Reference Resolution and Path Segments

Several collections are addressed underneath a parent — a bank's concentration limits, contingency plans and call report filings, and a counterparty's agreements — while the rest are flat top-level collections whose relationships travel in the request body or query string. Where a path carries a parent segment, that parent is resolved left to right before anything nested is considered: an unknown bank in the path yields `ERR_INSTITUTION_NOT_FOUND` and an unknown counterparty yields `ERR_BROKER_NOT_FOUND`, in both cases without the nested payload ever being validated. For those nested creates, the parent identifier is taken from the path segment and never from the body, so `institution_id` on a concentration limit, a contingency plan and a call report filing, and `broker_id` on a broker agreement, are system-sourced rather than client-supplied. The same is true of `placement_id` on a rate-cap check.

Foreign keys travelling in a body or query string are resolved with the same not-found codes as their addressed counterparts: an unknown bank reference yields `ERR_INSTITUTION_NOT_FOUND`, an unknown counterparty `ERR_BROKER_NOT_FOUND`, an unknown agreement `ERR_AGREEMENT_NOT_FOUND`, an unknown exception filing `ERR_EXCEPTION_NOT_FOUND`, an unknown program `ERR_PROGRAM_NOT_FOUND`, an unknown classification `ERR_CLASSIFICATION_NOT_FOUND`, an unknown placement `ERR_PLACEMENT_NOT_FOUND`, an unknown contingency plan `ERR_PLAN_NOT_FOUND` and an unknown call report filing `ERR_FILING_NOT_FOUND`. All nine are HTTP 404.

### 2.8. Rule Precedence: How a Rejected Request Chooses Its Error

A request never accumulates errors. Every request is evaluated against the rules below in ascending priority order and, on the first rule it violates, is rejected with that rule's error and nothing else is evaluated. The lower priority number always wins, even when a later and more interesting rule is also violated; the engine never collects several failures and never re-orders by apparent severity. The ordering follows a deliberate domain progression: identity first, then request shape, then existence of everything referenced, then the observed-version guards, then lifecycle admissibility, then supervisory and compliance safety, then calendar coherence, then structural constraints, then referential coherence, and finally balance-sheet capacity. Capacity checks run last on purpose — a request that is unsafe or mis-referenced must be reported as unsafe or mis-referenced, not as a capacity problem.

The full ordering, with the endpoints each rule guards:

1. Identity: `X-User-ID` and `X-User-Role` present and the role recognised — `ERR_UNAUTHENTICATED`. All endpoints.
2. Authorisation: the acting role appears on the target endpoint's list, and a `BrokerRepresentative`'s `X-User-ID` equals the `Broker` id reachable from the addressed resource — `ERR_UNAUTHORIZED`. All endpoints.
3. Request shape: every input field that has no declared default is present, every enum-typed field carries a declared member, integer fields are integers, `_cents` and `_bps` fields are not negative, diligence sub-scores lie within 0 to 100 inclusive, calendar-date fields are formatted as year-month-day and instant fields are ISO 8601 UTC — `ERR_INVALID_REQUEST`. All write endpoints.
4. Bank existence — `ERR_INSTITUTION_NOT_FOUND`. The bank read, the capital-category change, balance adjustments, the wholesale funding summary, and both the create and list forms of concentration limits, contingency plans and call report filings; also the `institution_id` body field of an exception filing and of a program create.
5. Counterparty existence — `ERR_BROKER_NOT_FOUND`. The counterparty read, both forms of the agreements collection under a counterparty, an exception filing create, and a program create carrying `broker_id`.
6. Agreement existence — `ERR_AGREEMENT_NOT_FOUND`. The agreement read, diligence actions, the fee summary read, and the `agreement_id` body field of a program create.
7. Exception filing existence — `ERR_EXCEPTION_NOT_FOUND`. The exception read, filing actions, review actions, and the `relied_exception_id` body field of a classification create.
8. Program existence — `ERR_PROGRAM_NOT_FOUND`. The program read, program state actions, the `program_id` body field of a classification create, and the `program_id` body field of a placement create.

A placement that both exceeds the rate ceiling and names an ineligible rollover source reports `ERR_RATE_CAP_EXCEEDED`, not `ERR_ROLLOVER_SOURCE_INVALID`. A placement whose calendar terms are incoherent and whose principal also exceeds the remaining reciprocal capacity reports `ERR_MATURITY_DATE_INVALID`, not `ERR_RECIPROCAL_CAP_EXCEEDED`.

### 2.9. Segregation of Duties

The system's role model is segregation of duties, enforced on the acting `X-User-ID` rather than on the role. Five comparisons implement it, and each one, when violated, produces `ERR_SEGREGATION_OF_DUTIES` (HTTP 403):

- Approving or rejecting a broker agreement requires an acting identifier different from the agreement's `prepared_by_user_id`.
- Granting, denying or revoking a primary purpose exception requires an acting identifier different from the filing's `prepared_by_user_id`.
- Attesting a program's classification requires an acting identifier different from the `determined_by_user_id` of the governing determination — the only one of the five that compares against a different record's field rather than the addressed record's own preparer.
- Approving a liquidity contingency plan requires an acting identifier different from the plan's `prepared_by_user_id`.
- Attesting a call report filing requires an acting identifier different from the filing's `prepared_by_user_id`.

Because the comparison ignores `X-User-Role`, a `SystemAdmin` that prepared an artefact cannot bless it either.

### 2.10. The Logical Clock

Time in this system is a server-side logical clock, never the host's wall clock. Before any caller sets it, the clock reads exactly `2026-08-01T00:00:00Z`, and it must not fall back to real time under any circumstance. A platform operator may advance or rewind it by supplying a `current_utc` instant. Every temporal rule in the specification is measured against this clock: the filing deadline stamped as `reporting_due_date`, the earliest permissible `issue_date`, the ninety-day maturing-soon horizon that sizes a liquidity buffer, the as-of date used to select the governing rate benchmark for a program-level recompute, and the `effective_at` instant stamped onto each classification determination.

### 2.11. Derived Balances, Cascade Ordering and Conserved Quantities

An operator never types a wholesale balance. A bank's `brokered_deposits_cents`, `listing_service_deposits_cents` and `reciprocal_deposits_cents` are each the sum of `principal_cents` over that bank's placements whose `funding_status` is exactly `ACTIVE` and whose `classified_as` matches the bucket — `BROKERED` for the first, `LISTING_SERVICE_NON_BROKERED` for the second, `RECIPROCAL_EXCLUDED` for the third. Placements in `PENDING`, `MATURED`, `WITHDRAWN_EARLY`, `ROLLED_OVER` or `CANCELLED` contribute to none of them. `total_deposits_cents` is `core_deposits_cents` plus those three buckets. A placement classified `CORE` is added to no wholesale bucket and is also not added to `core_deposits_cents`, which stays exactly the operator-supplied baseline — that is what keeps the reconciliation below exactly checkable.

The reconciliation is a hard invariant: after any sequence of funding actions, each wholesale bucket equals the sum of `principal_cents` over the bank's `ACTIVE` placements of the matching class. In particular, an activation followed by its compensating early withdrawal must return the bucket to its exact pre-activation value, and a full sweep followed by rollovers must leave the arithmetic consistent to the cent. A second conserved quantity governs exception reliance: `reliant_program_count` on an exception filing equals the number of programs whose `governing_classification_id` names a determination whose `relied_exception_id` is that filing, so a classification relying on a filing followed by a reclassification that does not rely on it must return the count to its exact prior value.

Cascades are transitive and are processed in a pinned order so that results are reproducible. Whenever a cascade fans out over child records, programs are processed in `created_at` ascending order and placements in `created_at` ascending order within each program. The maturity sweep is the one exception and declares its own ordering in §3.8. Each record a cascade touches has its own `updated_at` refreshed; version increments happen only where a rule says so, and only two things ever advance a program's `version` — a classification determination and the supervisory capital re-categorisation cascade. Program state actions, attestation and movements of `outstanding_principal_cents` deliberately do not advance it.

Wholesale metrics are refreshed as part of the same request that moved the money, never lazily. Each recomputation of the balance buckets is immediately followed by a recomputation of the point-in-time wholesale funding ratio and of the concentration posture, in that order, so a caller reading the bank straight after a funding action sees the posture that already reflects it.

## 3. Business Logic & Workflows

The workflows below follow the funding book from left to right: the bank and its benchmark reference data, the counterparty and its diligence file, the primary purpose exception, the program and its classification, the deposits themselves, rate-cap surveillance, the balance-sheet guardrails, the maturity sweep, and finally the call report the examiner reads. Rules that cut across several of those stages are stated where the business first needs them rather than being collected in one place.

### 3.1. Registering a Bank and Publishing the Rate Benchmark

A platform operator registers an insured depository institution with its chartered `legal_name` and its deposit-insurance certificate number `cert_id`, which must be non-empty and unique across every bank on the platform — a collision is refused with `ERR_DUPLICATE_KEY`. Four balance baselines are supplied at registration and are the bank's own figures rather than anything the system derives: `core_deposits_cents`, the baseline non-wholesale deposit balance, which may be zero but never negative; `total_liabilities_cents`, which must be strictly greater than zero because it is the denominator of both the wholesale-to-liabilities metric and the reciprocal exclusion cap; `tier1_capital_cents`, reported alongside the capital category for examiner review; and `liquidity_buffer_cents`, the unencumbered high-quality liquid asset buffer that a contingency plan's requirement is measured against. The prompt-corrective-action capital category may be supplied as `capital_category` and defaults to `WELL_CAPITALIZED`; the accepted members are `WELL_CAPITALIZED`, `ADEQUATELY_CAPITALIZED`, `UNDERCAPITALIZED`, `SIGNIFICANTLY_UNDERCAPITALIZED` and `CRITICALLY_UNDERCAPITALIZED`.

From the capital category the system immediately derives `rate_cap_regime`, which is `EXEMPT` when the category is `WELL_CAPITALIZED` and `CAPPED` for every other category. A newly registered bank starts with all four derived deposit figures at their empty values: `brokered_deposits_cents`, `listing_service_deposits_cents` and `reciprocal_deposits_cents` are 0, `total_deposits_cents` equals `core_deposits_cents`, `wholesale_funding_ratio_bps` and `single_broker_max_ratio_bps` are 0, `breached_metric_count` is 0 and `concentration_posture` is `OPEN`.

The national rate benchmark is reference data the platform operator publishes per maturity bucket. A publication names its `tenor_bucket` — one of `NON_MATURITY`, `DAYS_1_30`, `DAYS_31_90`, `DAYS_91_180`, `DAYS_181_365` or `DAYS_366_PLUS` — a `published_national_rate_bps` of zero or more, and the `effective_date` from which it governs. Two derived figures are stamped on it for convenience: `cap_bps` is the published rate plus 75 basis points, and `non_maturity_cap_bps` is the published rate plus 50 basis points, the tighter ceiling that clamps non-maturity products. The acting operator's identifier is recorded as `published_by_user_id` for audit only and is never a decision input. A publication governs the half-open interval that begins on its own `effective_date` and ends the day the next publication for the same bucket becomes effective, and the pair of `tenor_bucket` and `effective_date` must be unique across all publications — a duplicate is refused with `ERR_DUPLICATE_KEY`. Publications are immutable; a correction is a new publication with a later effective date.

Whenever a ceiling has to be computed, the governing publication is selected deterministically. Only publications for the subject's own `tenor_bucket` are candidates, and only those whose `effective_date` falls on or before the applicable as-of date; among those, the one with the latest `effective_date` wins, and if two share that date the one created most recently wins. The as-of date is the placement's `issue_date` when a deposit is being booked, the supplied `check_date` when a surveillance review is being recorded, and the logical clock's date when a program-level ceiling is being refreshed. If the candidate pool is empty while the bank's regime is `CAPPED`, the request fails with `ERR_NO_RATE_CAP_PUBLISHED` — an unpublished benchmark is a missing input, not a ceiling of zero.

Once a publication has been selected, the ceiling is built in a pinned order. The national leg is the publication's `published_national_rate_bps` plus 75 basis points. If the program asserts no local comparison — that is, its `local_prevailing_rate_bps` is null — the combined figure is the national leg alone. If the program does assert a local comparison, the combined figure is the greater of the national leg and the program's `local_prevailing_rate_bps` plus 75 basis points, so a strong local market can lift the ceiling above the national floor. Then, and only for a subject whose bucket is `NON_MATURITY`, the combined figure is clamped down to the smaller of itself and the publication's `published_national_rate_bps` plus 50 basis points. The greater-of step always runs before the smaller-of step. For a maturity-bucket subject there is no clamp and the combined figure stands. When the bank's regime is `EXEMPT` the whole computation is skipped and `effective_cap_bps` is null: no ceiling applies at all.

A supervisor may re-categorise a bank's capital. The request carries the new `capital_category` and the observed `expected_institution_version` described in §2.6, and it is refused with `ERR_EXAMINER_REVIEW_LOCK` while any of the bank's call report filings sits in `UNDER_EXAMINER_REVIEW`, because the baselines an examiner is reading may not shift underneath them. A successful re-categorisation re-derives `rate_cap_regime` and then cascades. Every one of the bank's programs whose `state` is not `CLOSED` has its `effective_cap_bps` recomputed and its `version` incremented by exactly 1, processed in `created_at` ascending order; because a program's version moved, each program's standing determination is now stale for the purpose of booking new deposits, which is what §3.5 reports as `ERR_CLASSIFICATION_STALE` until the program is re-classified. Every `ACTIVE` placement of the bank is then re-measured against its program's new ceiling, and each placement whose rate now sits above the ceiling has its `compliance_status` moved to `FLAGGED`. Finally the concentration posture is recomputed.

Balance-baseline maintenance is a separate, narrower operation available to the platform operator and the asset-liability desk. It accepts any subset of `core_deposits_cents`, `total_liabilities_cents`, `tier1_capital_cents` and `liquidity_buffer_cents`, and only the fields actually supplied change; the derived wholesale buckets are never touched by it. Because moving `core_deposits_cents` or `total_liabilities_cents` moves the denominators of the concentration metrics, a baseline adjustment re-runs the balance rollup, the point-in-time wholesale funding ratio, the single-broker exposure and the concentration posture. Like a re-categorisation, it is refused with `ERR_EXAMINER_REVIEW_LOCK` while one of the bank's filings is under examiner review.

### 3.2. Counterparty Onboarding and the Diligence Cycle

A counterparty is registered with its `legal_name` and its `broker_type`, which is `DEPOSIT_BROKER`, `LISTING_SERVICE`, `DEPOSIT_PLACEMENT_NETWORK` or `AFFILIATE`. The single most consequential attribute is `has_placement_discretion`, the boolean that records whether the counterparty has legal authority to choose where customer funds are placed; the classification decision tree in §3.4 reads it first among the deposit-broker prongs. A headline fee construct is also captured: `fee_structure` is one of `FLAT_FEE`, `BASIS_POINT_FEE`, `VOLUME_TIERED` or `PER_ACCOUNT_FEE`, with `fee_bps` defaulting to 0 and ignored when the structure is `FLAT_FEE`, and `fee_flat_cents` defaulting to 0 and ignored whenever the structure is anything other than `FLAT_FEE`. A fresh counterparty starts with `diligence_status` of `NOT_STARTED` and `approved_agreement_count` of 0; the status is a mirror of the counterparty's governing agreement and is only ever moved by the diligence cascade below, never written directly.

Agreements are filed underneath the counterparty. A filing supplies the counterparty-assigned `agreement_ref`, which must be unique within that one counterparty — a repeat is refused with `ERR_DUPLICATE_KEY` — the contracted `fee_structure` with its `fee_bps` and `fee_flat_cents` (each defaulting to 0, and each read only under the structure it belongs to, so a basis-point fee reads `fee_bps` and a flat fee reads `fee_flat_cents`), the `termination_notice_days` notice period of zero days or more, the `effective_date` on which the agreement becomes contractually effective, and four diligence sub-scores each within 0 to 100 inclusive: `aml_program_score` for the anti-money-laundering programme, `financial_condition_score` for the counterparty's financial condition, `insurance_coverage_score` for fidelity and errors-and-omissions cover, and `recordkeeping_score` for deposit-insurance recordkeeping capability. The contracted fee construct may legitimately differ from the counterparty's headline construct. A new agreement lands in `DRAFT` with `diligence_score` of 0, `rfi_round_count` of 0 and `accrued_fee_cents` of 0; the filer's identifier is stamped as `prepared_by_user_id`, which is the identity every later approval is compared against, and `reviewed_by_user_id` stays null until the first review action.

The composite `diligence_score` is a weighted blend of the four sub-scores: thirty-five parts of `aml_program_score`, thirty parts of `financial_condition_score`, twenty parts of `insurance_coverage_score` and fifteen parts of `recordkeeping_score`, summed as an exact rational and divided by one hundred, with that single final quotient rounded half up to a whole point in the 0 to 100 range. It is recomputed on every entry into diligence and never at any other time.

Diligence runs as a cycle. Starting diligence moves the agreement from `DRAFT` to `UNDER_DILIGENCE`, recomputes the composite score, stamps `reviewed_by_user_id` with the acting identifier, sets the counterparty's `diligence_status` to `IN_DILIGENCE`, and increments both the agreement's `version` and the counterparty's `version` by 1. From `UNDER_DILIGENCE` the reviewer may issue a request for information, moving the agreement `UNDER_DILIGENCE → RFI_ISSUED`, incrementing `rfi_round_count` by 1 and re-stamping `reviewed_by_user_id`; the round is admitted only while `rfi_round_count` is below the ceiling of two rounds, and a third attempt is refused with `ERR_REVIEW_ROUND_LIMIT`. When the counterparty answers, resuming diligence closes the loop `RFI_ISSUED → UNDER_DILIGENCE` and recomputes the composite score, so the cycle `UNDER_DILIGENCE → RFI_ISSUED → UNDER_DILIGENCE` can be travelled at most twice.

Approval from `UNDER_DILIGENCE` is one action with two divergent destinations chosen by the score band, and both destinations carry the same shape of side effect. When the composite score is at least 70 and `aml_program_score` is at least 60, the agreement becomes `APPROVED`, the counterparty's `diligence_status` becomes `APPROVED` and `approved_agreement_count` increases by 1. When the composite score is at least 60 but below 70 and `aml_program_score` is at least 60, the agreement becomes `CONDITIONAL`, the counterparty's `diligence_status` becomes `CONDITIONAL` and `approved_agreement_count` likewise increases by 1. Both branches require an acting identifier different from `prepared_by_user_id`. An agreement whose composite score is below 60, or whose `aml_program_score` is below 60, cannot be approved at all and is refused with `ERR_DILIGENCE_SCORE_INSUFFICIENT`; the anti-money-laundering floor bites independently of the composite, so a composite of 78 sitting on an anti-money-laundering sub-score of 55 is still refused. Such an agreement can only be rejected, which moves it `UNDER_DILIGENCE → REJECTED` — also requiring an acting identifier different from the preparer — and sets the counterparty's `diligence_status` to `REJECTED`. `REJECTED` is terminal.

Suspension is where the diligence file reaches into the funding book. Suspending an agreement is permitted from either `APPROVED` or `CONDITIONAL`, and both produce an identical three-hop cascade. The first hop moves the agreement's own `status` to `SUSPENDED`. The second hop, caused by the first, sets the counterparty's `diligence_status` to `SUSPENDED` and decrements `approved_agreement_count` by 1. The third hop, caused by the counterparty's suspension, walks every program underwritten by that agreement whose `state` is `CLASSIFIED` or `OPEN_FOR_PLACEMENT` and moves it to `SUSPENDED`, in program `created_at` ascending order, and for each such program moves every placement whose `funding_status` is `PENDING` to `CANCELLED`, in placement `created_at` ascending order. The bank's balance rollup and concentration posture are then recomputed. A suspended agreement can be brought back: resuming diligence moves it `SUSPENDED → UNDER_DILIGENCE`, recomputes the composite score and sets the counterparty's `diligence_status` back to `IN_DILIGENCE`, which is how the cycle `APPROVED → SUSPENDED → UNDER_DILIGENCE → APPROVED` is travelled. Alternatively a suspended agreement may be terminated, which moves it `SUSPENDED → TERMINATED` and closes out the book: every program underwritten by that agreement whose `state` is not already `CLOSED` moves to `CLOSED`, in program `created_at` ascending order. `TERMINATED` is terminal. Any diligence action that is not a declared transition out of the agreement's current status — including a repeat of an action already taken — is refused with `ERR_AGREEMENT_STATE_INVALID`. An optional free-text `note` may accompany any diligence action.

Fees accrue against the agreement rather than against the counterparty, and they are recomputed as a side effect of a placement entering `ACTIVE`, of an early withdrawal, and of the maturity sweep. Each contributing line is one placement whose `funding_status` is `ACTIVE` and whose program names that agreement, and the lines are processed in placement `created_at` ascending order. A line's `fee_accrual_cents` depends on the agreement's contracted structure: under `FLAT_FEE` and under `PER_ACCOUNT_FEE` the line fee is the agreement's `fee_flat_cents`; under `BASIS_POINT_FEE` it is the line's `principal_cents` multiplied by the agreement's `fee_bps`, divided by 10000, rounded half up to whole cents; and under `VOLUME_TIERED` the rate is selected by that one placement's own principal — 15 basis points while `principal_cents` is below 100,000,000 cents (one million dollars), 10 basis points while it is below 500,000,000 cents (five million dollars), and 7 basis points at or above that, with the resulting product likewise divided by 10000 and rounded half up. The rounding order is pinned: every line is rounded to whole cents first and the rounded lines are then added together to give the agreement's `accrued_fee_cents`. Summing the exact fractional lines and rounding once at the end is a different number and is not what this system computes — three lines each ending in half a cent differ by a full cent between the two methods. A placement leaving `ACTIVE` has its own `fee_accrual_cents` reset to 0 and drops out of the sum, and a placement under a program with no `agreement_id` has a `fee_accrual_cents` of 0 because no agreement governs it.

The fee position is readable as a computed summary that names the `agreement_id` it belongs to, echoes the governing `fee_structure`, reports `line_count` as the number of contributing placements — counting only those whose `funding_status` is `ACTIVE` — and returns the round-then-sum total as `accrued_fee_cents` alongside the parallel arrays `line_fee_cents` and `line_placement_ids`. A broker representative may read that summary, its own counterparty record and its own agreements, and the agreement list may be narrowed by `status`.

### 3.3. Claiming a Primary Purpose Exception

A primary purpose exception is the funding desk's argument that a counterparty's business line places customer funds for a purpose other than obtaining deposit insurance, and therefore that the resulting deposits are not brokered. A filing names the counterparty it is claimed for through `broker_id` and the filing bank through `institution_id`, describes the agent's business line in `designated_business_line`, and declares the statutory basis relied upon in `exception_basis`: `TWENTY_FIVE_PERCENT_TEST`, `ENABLING_TRANSACTIONS_TEST` or `OTHER_APPLICATION`. Two of the three carry arithmetic; the third does not.

The basis determines `filing_type`, which the system derives rather than accepting: the twenty-five-percent basis and the enabling-transactions basis are both `NOTICE` filings, while the other-application basis is an `APPLICATION` filing. That single derived value is what makes the submission step branch, so a filer who chooses a basis is also choosing whether the filing self-executes or enters supervisory review.

Four numeric inputs support the two tests. `total_customer_assets_cents` is the total customer assets under administration in the designated business line and is the denominator of the twenty-five-percent test; it must be strictly greater than zero. `deposits_placed_at_ifs_cents` is the portion of those customer funds placed at insured depository institutions and is that test's numerator. `enabling_transaction_count`, defaulting to 0, is the number of deposit accounts in the business line whose purpose is enabling transactions, and `total_transaction_count`, also defaulting to 0, is the total number of deposit accounts in the line and the denominator of the enabling-transactions test. The declared basis must be supported by its own inputs: a twenty-five-percent filing requires `total_customer_assets_cents` strictly above zero with `deposits_placed_at_ifs_cents` no larger than it, and an enabling-transactions filing requires `total_transaction_count` strictly above zero with `enabling_transaction_count` no larger than it. A zero denominator or a numerator larger than its denominator is refused with `ERR_EXCEPTION_INPUTS_INCOHERENT`.

Both ratios are computed at creation and recomputed on submission, from the filing's own fields alone — no program or placement data enters. `business_line_deposit_ratio_bps` is `deposits_placed_at_ifs_cents` multiplied by 10000 and then divided by `total_customer_assets_cents`, discarding any remainder. `enabling_transaction_ratio_bps` is `enabling_transaction_count` multiplied by 10000 and then divided by `total_transaction_count`, again discarding the remainder, and is 0 when `total_transaction_count` is zero. The two tests then read those ratios with deliberately opposite boundary directions. Under the twenty-five-percent basis, `test_outcome` is `QUALIFIED` only when `business_line_deposit_ratio_bps` is strictly below 2500 basis points, which is 25 percent — a ratio of exactly 2500 fails. Under the enabling-transactions basis, `test_outcome` is `QUALIFIED` when `enabling_transaction_ratio_bps` is at or above 7500 basis points, which is 75 percent — a ratio of exactly 7500 qualifies. Anything else in each case is `NOT_QUALIFIED`. An other-application filing carries no arithmetic test and its `test_outcome` stays `NOT_EVALUATED`, which is also the value a filing starts with.

At creation the filing lands in `DRAFT` with `info_request_round_count` and `reliant_program_count` both at 0, `prepared_by_user_id` stamped from the drafting officer's identifier and `reviewed_by_user_id` null. It is also stamped with `reporting_due_date`, a calendar date set to the logical clock's date plus 90 days. That date wears two hats over the filing's life. While the filing is in `DRAFT` it is the deadline by which submission must happen: a submission on the due date itself is accepted, a submission after it is refused with `ERR_FILING_WINDOW_CLOSED`. Once the filing reaches `ACKNOWLEDGED` or `GRANTED` the same field is re-based to the logical clock's date plus 90 days again and becomes the next periodic reporting deadline. Denial, withdrawal and revocation all null it out.

Submission branches on `filing_type`, and only from `DRAFT`. A `NOTICE` filing is self-effecting: it moves `DRAFT → ACKNOWLEDGED` with no review at all, and re-bases `reporting_due_date` to the logical clock's date plus 90 days. It may only do so when the arithmetic qualified — a notice whose `test_outcome` is `NOT_QUALIFIED` is refused with `ERR_PRIMARY_PURPOSE_TEST_NOT_MET`, and because no supervisory review path exists for a notice, the filer's only remedy is to withdraw it and re-file on the other-application basis. An `APPLICATION` filing takes the other branch, moving `DRAFT → UNDER_REVIEW`, and deliberately leaves `reporting_due_date` at its creation-time value: entering supervisory review does not re-base the deadline. Submission from any state other than `DRAFT`, and any second submission, are both refused with `ERR_EXCEPTION_STATE_INVALID`.

Supervisory review is a cycle mirroring the diligence cycle. From `UNDER_REVIEW` the reviewer may request further information, moving `UNDER_REVIEW → INFO_REQUESTED`, incrementing `info_request_round_count` by 1 and stamping `reviewed_by_user_id`; the round is admitted only while that counter is below two, and a third request is refused with `ERR_REVIEW_ROUND_LIMIT`. Resuming review closes the loop `INFO_REQUESTED → UNDER_REVIEW` and re-stamps `reviewed_by_user_id`. From `UNDER_REVIEW` the filing may be granted, moving to `GRANTED` and re-basing `reporting_due_date` to the logical clock's date plus 90 days, or denied, moving to `DENIED` and nulling `reporting_due_date`. Both decisions require an acting identifier different from `prepared_by_user_id`.

Withdrawal is the filer's own exit and is admitted while the filing's status is `DRAFT`, `ACKNOWLEDGED`, `UNDER_REVIEW` or `INFO_REQUESTED`. It moves the filing to `WITHDRAWN` and nulls `reporting_due_date`, and it is permitted only while `reliant_program_count` is exactly 0 — a filing that some program's governing determination still leans on cannot be pulled out from underneath it. `DENIED`, `WITHDRAWN` and `REVOKED` are terminal; any filing or review action against a filing in one of those three is refused with `ERR_EXCEPTION_STATE_INVALID`. Both filing actions and review actions accept an optional `note`.

Revocation is the heaviest operation in the system and is admitted from `ACKNOWLEDGED` and from `GRANTED`, with identical consequences from either. It also requires an acting identifier different from `prepared_by_user_id`. The cascade runs four hops deep. Hop one sets the filing's own status to `REVOKED` and nulls `reporting_due_date`. Hop two, caused by hop one, walks every program whose `governing_classification_id` names a determination whose `relied_exception_id` is this filing and whose `state` is `CLASSIFIED` or `OPEN_FOR_PLACEMENT`, moves each to `RECLASSIFICATION_PENDING` in program `created_at` ascending order, and resets `reliant_program_count` to 0. Hop three, caused by hop two, walks the placements of each program just moved: every placement whose `funding_status` is `ACTIVE` has its `compliance_status` set to `FLAGGED` and its `classified_as` set to `BROKERED`, since the reliance that carried it out of the brokered class has been withdrawn, processed in placement `created_at` ascending order; the bank's balance rollup then re-runs over the new classes. Hop four, caused by hop three's balance movement, re-runs the concentration posture, and if the bank's `concentration_posture` comes out as `FROZEN`, every contingency plan of that bank whose `status` is `APPROVED` moves to `ACTIVATED` and has its `activation_stage` selected by the stage rule in §3.7.

Exception filings can be listed and narrowed by `broker_id`, `institution_id`, `status` and `test_outcome`, which is how the desk finds the reliable filings it may lean on when a program is classified.

### 3.4. Opening a Funding Program and Determining Its Class

A funding program is the desk's standing arrangement to raise deposits of one product form, on one set of terms, through one channel. It names the funding bank through `institution_id` and carries an internal `program_name`. A program raised through a counterparty names that counterparty through `broker_id` and the underwriting agreement through `agreement_id`; a purely self-originated programme omits both. Where `broker_id` is present, `agreement_id` is required and must name an agreement belonging to that same counterparty — an agreement borrowed from another counterparty, or an `agreement_id` supplied for a program with no counterparty at all, is refused with `ERR_AGREEMENT_BROKER_MISMATCH`. Where a counterparty is named, both the agreement's `status` and the counterparty's `diligence_status` must be `APPROVED` or `CONDITIONAL`; a `DRAFT`, `SUSPENDED`, `REJECTED` or `TERMINATED` file cannot underwrite new funding and the attempt is refused with `ERR_AGREEMENT_NOT_APPROVED`.

The desk asserts a channel before anything is determined. `funding_channel_claim` is `BROKERED`, `LISTING_SERVICE`, `CORE` or `RECIPROCAL_NETWORK`, and the classification tree is free to overrule it. The product form is `product_type`, one of `TIME_DEPOSIT`, `MONEY_MARKET`, `SAVINGS` or `NOW`, and `tenor_days` carries the contractual tenor of placements issued under the program — zero or more days, and required to be 0 for a non-maturity product. From those two the system assigns `tenor_bucket`: a program whose `product_type` is `MONEY_MARKET`, `SAVINGS` or `NOW` is `NON_MATURITY` regardless of tenor, and otherwise the bucket follows `tenor_days` with inclusive upper edges — up to and including 30 days is `DAYS_1_30`, 31 through 90 days is `DAYS_31_90`, 91 through 180 days is `DAYS_91_180`, 181 through 365 days is `DAYS_181_365`, and anything beyond 365 days is `DAYS_366_PLUS`. A tenor of exactly 30 days therefore lands in the first maturity bucket and a tenor of exactly 31 days in the second.

Pricing terms come next. `offered_rate_bps` is the rate the program advertises, and `local_prevailing_rate_bps` is the prevailing rate in the bank's local market for the same bucket; the latter defaults to null, meaning the desk asserts no local comparison, and when it is supplied it can lift the ceiling as §3.1 describes. On creation the system derives `effective_cap_bps` from the governing benchmark publication, leaving it null when the bank's `rate_cap_regime` is `EXEMPT`, and re-derives it whenever the bank's regime changes. For a bank in the `CAPPED` regime, `offered_rate_bps` must not exceed `effective_cap_bps`: equality passes, one basis point above is refused with `ERR_RATE_CAP_EXCEEDED`. A program cannot be opened at all while the bank's `concentration_posture` is `FROZEN`, which is reported as `ERR_CONCENTRATION_FROZEN`.

Early-withdrawal terms and insurance mechanics complete the program. `early_withdrawal_penalty_days` is the number of days of interest a depositor forfeits on early withdrawal, and `principal_erosion_allowed`, defaulting to false, records whether the contractual penalty may exceed the interest actually earned and bite into principal — it is the flag that selects between the two penalty variants in §3.5. `pass_through_insurance`, defaulting to false, records reliance on pass-through deposit insurance to the underlying customers, and `titling_convention` describes how the account is titled at the bank: `SINGLE_FIDUCIARY_ACCOUNT`, `FBO_SUBACCOUNTS` or `DIRECT_TITLED`. Pass-through coverage is only coherent with subaccount titling and a real counterparty, so claiming it requires `titling_convention` to be `FBO_SUBACCOUNTS` and `broker_id` to be non-null; a program titled `DIRECT_TITLED` or `SINGLE_FIDUCIARY_ACCOUNT`, or one with no counterparty, cannot claim it. The same rule polices the reciprocal declaration: a `funding_channel_claim` of `RECIPROCAL_NETWORK` requires `reciprocal_arrangement_cents` — the contractual reciprocal placement capacity, defaulting to 0 — to be strictly greater than zero. Either violation is refused with `ERR_PASS_THROUGH_TITLING_INVALID`. Finally `rollover_enabled`, defaulting to false, decides whether a matured placement is automatically rolled into a successor by the sweep.

A new program lands in `PENDING_CLASSIFICATION` with `governing_classification_id` null, `outstanding_principal_cents` at 0, `prepared_by_user_id` stamped from the opening officer's identifier and `attested_by_user_id` null. Programs are listable and can be narrowed by `institution_id`, `broker_id`, `agreement_id`, `governing_classification_id` and `state`.

Classification is a second-line determination, not an edit. A determination names its `program_id`, carries the observed `expected_program_version` of §2.6, records a free-form `rationale_code` for examiner review, and optionally names the exception filing relied upon through `relied_exception_id`. It is admitted only while the program's `state` is `PENDING_CLASSIFICATION` or `RECLASSIFICATION_PENDING`; from any other state the request is refused with `ERR_PROGRAM_NOT_CLASSIFIABLE`. Where an exception is named, that filing's `status` must be `ACKNOWLEDGED` or `GRANTED` — a `DRAFT`, `UNDER_REVIEW`, `INFO_REQUESTED`, `DENIED`, `WITHDRAWN` or `REVOKED` filing cannot be relied upon and the attempt is refused with `ERR_EXCEPTION_NOT_RELIABLE` — and that filing's `broker_id` must equal the program's `broker_id` while its `institution_id` must equal the program's `institution_id`, failing which the attempt is refused with `ERR_EXCEPTION_COUNTERPARTY_MISMATCH`. Determinations are listable and can be narrowed by `program_id`, `relied_exception_id` and `determined_class`.

The determination itself walks five branches strictly top to bottom, and the first branch that matches wins. First, reciprocal exclusion: when the program's `funding_channel_claim` is `RECIPROCAL_NETWORK` and the bank's remaining reciprocal capacity is at least the program's `reciprocal_arrangement_cents`, the `determined_class` is `RECIPROCAL_EXCLUDED`. That remaining capacity is computed as 2500 basis points — 25 percent — of the bank's `total_liabilities_cents`, taking the integer part, less the bank's current `reciprocal_deposits_cents`, and floored at zero so it is never negative. Second, when the program names no counterparty at all, the `determined_class` is `CORE`. Third, when a relied exception is present, its `status` is `ACKNOWLEDGED` or `GRANTED` and its `test_outcome` is either `QUALIFIED` or `NOT_EVALUATED`, the reliance carries the program out of the brokered class and the `determined_class` is `LISTING_SERVICE_NON_BROKERED`. Fourth, a bare listing service with no discretion over placement is not a deposit broker: when the counterparty's `broker_type` is `LISTING_SERVICE` and its `has_placement_discretion` is false, the `determined_class` is again `LISTING_SERVICE_NON_BROKERED`. Fifth and last, the deposit-broker prongs apply and the `determined_class` is `BROKERED`; which prong drove it is recorded in `deposit_broker_prong`, again first match wins — `PLACEMENT_DISCRETION` when the counterparty has placement discretion, otherwise `MATCHING_DRIVER` when its `broker_type` is `DEPOSIT_PLACEMENT_NETWORK`, and otherwise `FEE_FOR_PLACEMENT`. For each of the first four branches `deposit_broker_prong` is `NOT_APPLICABLE`.

Each determined class maps one-to-one onto the call report line recorded as `call_report_line`: `BROKERED` maps to `RC_E_M1_BROKERED`, `LISTING_SERVICE_NON_BROKERED` to `RC_E_M2_LISTING`, `CORE` to `RC_E_CORE` and `RECIPROCAL_EXCLUDED` to `RC_O_M_RECIPROCAL`. The determining reviewer's identifier is stamped as `determined_by_user_id` — the identity the later attestation is compared against — and the logical-clock instant is stamped as `effective_at`. The determination also captures `program_version_at_determination`, which is the program's `version` immediately after this determination has been applied, that is the observed `expected_program_version` plus the determination's own increment of 1. That stamped witness is what the booking gate in §3.5 compares against the program's live version.

Applying a determination moves the program from `PENDING_CLASSIFICATION` (or from `RECLASSIFICATION_PENDING`) to `CLASSIFIED`, sets `governing_classification_id` to the new determination's `id`, increments the program's `version` by 1, and re-derives `effective_cap_bps`. Reliance accounting travels with it: when the new determination names an exception, that filing's `reliant_program_count` increases by 1, and when the determination being superseded named a different exception, that other filing's `reliant_program_count` decreases by 1. A reclassification — a determination applied to a program sitting in `RECLASSIFICATION_PENDING` — does everything above and two things more: every placement of that program whose `funding_status` is `ACTIVE` has its `classified_as` refreshed to the new `determined_class`, and any such placement whose `compliance_status` was `FLAGGED` is moved to `REMEDIATED`; then the bank's balance rollup and concentration posture are recomputed over the new classes. This is how the cycle `CLASSIFIED → RECLASSIFICATION_PENDING → CLASSIFIED`, and equally `OPEN_FOR_PLACEMENT → RECLASSIFICATION_PENDING → CLASSIFIED`, closes.

A determination alone does not open the funding tap. Attestation by a funding-desk officer moves the program `CLASSIFIED → OPEN_FOR_PLACEMENT` and stamps `attested_by_user_id` with the acting identifier. It requires a non-null `governing_classification_id`, without which the request is refused with `ERR_CLASSIFICATION_REQUIRED`; it requires an acting identifier different from the governing determination's `determined_by_user_id`; and where the program names a counterparty it requires the agreement named by `agreement_id` to still be `APPROVED` or `CONDITIONAL`, failing which it is refused with `ERR_AGREEMENT_NOT_APPROVED`.

Four further state actions drive the program, each accepting an optional `note`. Suspension moves an open program `OPEN_FOR_PLACEMENT → SUSPENDED` and cancels every placement of that program whose `funding_status` is `PENDING`, in placement `created_at` ascending order. Resumption moves it `SUSPENDED → OPEN_FOR_PLACEMENT`, again requiring an `APPROVED` or `CONDITIONAL` agreement where a counterparty is named and otherwise refusing with `ERR_AGREEMENT_NOT_APPROVED`; it has no placement side effects, because cancelled placements are never revived. Starting a reclassification is admitted from `CLASSIFIED` and from `OPEN_FOR_PLACEMENT`, moves the program to `RECLASSIFICATION_PENDING`, and clears `attested_by_user_id` back to null so the program must be attested afresh once the new determination lands. Closing is admitted from `PENDING_CLASSIFICATION`, `CLASSIFIED`, `OPEN_FOR_PLACEMENT`, `SUSPENDED` and `RECLASSIFICATION_PENDING`, moves the program to the terminal `CLOSED`, and likewise cancels every `PENDING` placement of the program in placement `created_at` ascending order. Any state action that is not a declared transition out of the program's current `state`, including any action at all against a `CLOSED` program, is refused with `ERR_PROGRAM_STATE_INVALID`. Two of these transitions are also reachable without an operator asking for them: the counterparty-suspension cascade of §3.2 drives programs to `SUSPENDED`, its termination cascade drives them to `CLOSED`, and the exception-revocation cascade of §3.3 drives them to `RECLASSIFICATION_PENDING`.

### 3.5. Booking, Funding and Settling Deposits

A placement is one tranche of money raised under a program. Booking one names its `program_id` and supplies `principal_cents`, which must be strictly greater than zero; `rate_bps`, the rate actually paid, which may be zero but never negative; `issue_date`, the calendar date the deposit is issued; and `tenor_days`, this tranche's own tenor, which is 0 for a non-maturity product. A tranche that rolls a matured predecessor names it through `rolled_from_placement_id`, which defaults to null for new money. From those inputs the system derives `maturity_date` as `issue_date` advanced by `tenor_days` calendar days — equal to `issue_date` itself when the tenor is zero — and assigns `tenor_bucket` by the same rule the program uses, reading the program's `product_type` together with this tranche's `tenor_days`. The placement also inherits `classified_as` from the class determined by the program's governing determination; that inherited value is what the concentration and balance rules read once the money is live.

Booking is the most heavily gated operation in the system, and the gates are evaluated in the precedence order of §2.8. The program must already have a governing determination, without which the booking is refused with `ERR_CLASSIFICATION_REQUIRED`, and it must be sitting in `OPEN_FOR_PLACEMENT`: a `CLASSIFIED` but un-attested program, a `SUSPENDED` program and a program under reclassification all refuse new money with `ERR_PROGRAM_NOT_OPEN`. Where the bank's `rate_cap_regime` is `CAPPED`, the tranche's `rate_bps` must not exceed the ceiling computed as of its own `issue_date`; equality passes and one basis point above is refused with `ERR_RATE_CAP_EXCEEDED`, while an unpublished benchmark for the tranche's bucket surfaces as `ERR_NO_RATE_CAP_PUBLISHED`. The governing determination must also still be current: the determination's `program_version_at_determination` must equal the program's live `version` at the instant of booking, and when it does not — which happens precisely when a supervisory capital re-categorisation has bumped every program's version since the determination was made — the booking is refused with `ERR_CLASSIFICATION_STALE` until the program is re-classified. An unchanged program funds freely, because nothing else advances a program's version: state actions, attestation and movements of `outstanding_principal_cents` deliberately do not. A bank whose `concentration_posture` is `FROZEN` accepts no new money at all, which is `ERR_CONCENTRATION_FROZEN`.

Calendar coherence is checked next. A maturity product must carry a `tenor_days` strictly greater than zero with `maturity_date` exactly `tenor_days` after `issue_date`, and a `NON_MATURITY` product must carry a `tenor_days` of 0 with `maturity_date` equal to `issue_date`; either incoherence is refused with `ERR_MATURITY_DATE_INVALID`. Deposits also cannot be back-dated before the paperwork that permits them: `issue_date` must fall on or after the underwriting agreement's `effective_date` and on or after the logical clock's date, and an earlier date is refused with `ERR_ISSUE_BEFORE_AGREEMENT`. Where `rolled_from_placement_id` is supplied it must name a placement of the *same* program whose `funding_status` is `MATURED` and which has not already been rolled; an `ACTIVE`, `PENDING` or `CANCELLED` source, a source belonging to another program, or a source already consumed by an earlier successor, is refused with `ERR_ROLLOVER_SOURCE_INVALID`.

Two balance-sheet capacity gates run last. For a program whose governing determination came out as `RECIPROCAL_EXCLUDED`, the tranche's `principal_cents` must not exceed the bank's remaining reciprocal capacity — 25 percent of `total_liabilities_cents`, taking the integer part, less the bank's current `reciprocal_deposits_cents`, floored at zero — and a principal above that capacity is refused with `ERR_RECIPROCAL_CAP_EXCEEDED`. Then the maturity ladder is inspected. Consider a candidate tranche maturing on a given date: the system takes the closed window running from 15 calendar days before that `maturity_date` to 15 calendar days after it, both endpoints inclusive, so a neighbour maturing exactly 15 days away is inside the window. Neighbours are the bank's other placements whose `funding_status` is `PENDING` or `ACTIVE`, whose effective class is `BROKERED` or `LISTING_SERVICE_NON_BROKERED`, and whose own `maturity_date` falls inside that window; a neighbour's effective class is its `classified_as` when it is already `ACTIVE`, and otherwise the `determined_class` of its program's governing determination. Placements that are `MATURED`, `WITHDRAWN_EARLY`, `ROLLED_OVER` or `CANCELLED` never contribute. The exposure is the candidate's own `principal_cents` plus the `principal_cents` of every neighbour, and the cap is 3500 basis points — 35 percent — of the bank's `total_deposits_cents`, taking the integer part. The cap is an inclusive bound: an exposure that reaches the cap, not merely one that passes it, is refused with `ERR_MATURITY_WINDOW_CONCENTRATION`. This is a buffered aggregate rule rather than an exclusive-occupancy rule — each neighbour on its own is perfectly admissible, and only the aggregate breaches.

A booked tranche starts in `PENDING` on the funding dimension and `UNREVIEWED` on the surveillance dimension, with `accrued_interest_cents`, `early_withdrawal_penalty_cents`, `net_settlement_cents` and `fee_accrual_cents` all at 0 and `settlement_date` null. The booking officer's identifier is stamped as `prepared_by_user_id`. Placements are listable and can be narrowed by `program_id`, `rolled_from_placement_id`, `funding_status`, `compliance_status` and `classified_as`.

The two state dimensions on a placement row are genuinely independent. `funding_status` tracks where the money is in its funding lifecycle and moves only on funding actions, on the maturity sweep, and on program or agreement cascades — never on a surveillance review. `compliance_status` tracks where the tranche stands in rate-cap surveillance and moves only on surveillance reviews and reclassification cascades — never on a funding action. A tranche can therefore be `RATE_CHECKED` while still `PENDING`, or `FLAGGED` while already `MATURED`.

Activation is the funding desk saying the money has landed. It moves the tranche `PENDING → ACTIVE` and requires three things beyond the transition itself: the program must be in `OPEN_FOR_PLACEMENT`, otherwise `ERR_PROGRAM_NOT_OPEN`; the bank's `concentration_posture` must be `OPEN` or `RESTRICTED`, and a `FROZEN` bank is refused with `ERR_CONCENTRATION_FROZEN`; and, looking forward rather than backward, the value the matching concentration metric would take *after* this activation must stay strictly below that limit's `breach_threshold_bps`. That forward-looking gate is refused with `ERR_CONCENTRATION_BREACH`, and it is distinct from the frozen check — the frozen check refuses a bank that is already in breach, while this one refuses the single activation that would do the freezing. On success the tranche's `classified_as` is set from the `determined_class` of the program's governing determination, its `principal_cents` is added to the matching wholesale bucket on the bank and the concentration posture is re-run, the same amount is added to the program's `outstanding_principal_cents`, and the agreement's `accrued_fee_cents` together with this tranche's own `fee_accrual_cents` are recomputed by the fee rule of §3.2.

Early withdrawal is the exact compensating action. It moves the tranche `ACTIVE → WITHDRAWN_EARLY` and requires a `withdrawal_date` that is present and strictly before `maturity_date`; the field is required for this action and ignored for the others. Interest is settled first: `accrued_interest_cents` is `principal_cents` multiplied by `rate_bps`, multiplied by the number of whole calendar days from `issue_date` to the settlement date, divided by 10000 and then by a day-count basis of 365, with that single final quotient rounded half up to whole cents. The settlement date is the supplied `withdrawal_date` here and the `maturity_date` on maturity, and it is recorded as `settlement_date` — the field that closes the tranche's occupancy interval on the wholesale ladder and stays null while the tranche is `PENDING`, `ACTIVE` or `CANCELLED`.

The penalty has two variants selected by the program's `principal_erosion_allowed` flag, and both start from the same contractual figure: `principal_cents` multiplied by `rate_bps`, multiplied by the program's `early_withdrawal_penalty_days`, divided by 10000 and then by the day-count basis of 365, rounded half up to whole cents. Where the program allows principal erosion, `early_withdrawal_penalty_cents` is that contractual figure in full, even when it exceeds the interest actually earned, so `net_settlement_cents` can fall below `principal_cents`. Where the program does not allow it, the penalty is clamped to the smaller of the contractual figure and `accrued_interest_cents` — an exact comparison with no further rounding — so the depositor's principal is never eroded and `net_settlement_cents` can never fall below `principal_cents`. In both variants `net_settlement_cents` is `principal_cents` plus `accrued_interest_cents` less `early_withdrawal_penalty_cents`. The withdrawal then unwinds the balance sheet exactly: `principal_cents` is subtracted from the matching wholesale bucket and the concentration posture is re-run, the same amount is subtracted from the program's `outstanding_principal_cents`, and the agreement fee position is recomputed with this tranche dropped from the lines.

Cancellation moves a tranche `PENDING → CANCELLED` and moves no money whatsoever, because a `PENDING` tranche has never entered any wholesale bucket. `MATURED`, `WITHDRAWN_EARLY`, `ROLLED_OVER` and `CANCELLED` are all terminal on the funding dimension. Any funding action that is not a declared transition out of the tranche's current `funding_status` — a second activation, or an early withdrawal of an already-matured tranche — is refused with `ERR_PLACEMENT_STATE_INVALID`. Cancellation also arrives without being asked for, through the program suspension and closure cascades and through the counterparty suspension cascade of §3.2.

### 3.6. Rate-Cap Surveillance

Surveillance is a separate, append-only record of what the ceiling was and what the tranche was paying, taken as of a date the reviewer chooses. A review supplies only `check_date`, the calendar date as of which the ceiling is looked up, and the system fills in the rest: `placement_id` from the addressed tranche, `applied_tenor_bucket` copied from the tranche's `tenor_bucket`, `national_rate_bps_snapshot` holding the `published_national_rate_bps` of the benchmark publication the selector picked for that date, `local_prevailing_rate_bps_snapshot` holding the program's `local_prevailing_rate_bps` at check time or null when the program asserts none, `effective_cap_bps` holding the ceiling itself or null when the bank's regime is `EXEMPT`, `offered_rate_bps` holding the tranche's `rate_bps` at check time, and `checked_by_user_id` recording the reviewer. Each review is immutable and carries no version or update timestamp.

The arithmetic is deliberately small. `breach_bps` is the amount by which `offered_rate_bps` exceeds `effective_cap_bps`, floored at zero so it is never negative, and it is 0 whenever `effective_cap_bps` is null. The `outcome` follows: `EXEMPT_NO_CAP` when there is no ceiling because the bank is `WELL_CAPITALIZED` and therefore `EXEMPT`, `BREACH` when `breach_bps` is greater than zero, and `PASS` otherwise. Reviews are listable per tranche and can be narrowed by `outcome`.

The outcome drives the surveillance dimension and nothing else — `funding_status` never moves on a review. An `UNREVIEWED` tranche whose review comes back `PASS` or `EXEMPT_NO_CAP` moves `UNREVIEWED → RATE_CHECKED`; an `UNREVIEWED` tranche whose review comes back `BREACH` moves `UNREVIEWED → FLAGGED` and the appended review carries a `breach_bps` above zero. A tranche already `RATE_CHECKED` or `REMEDIATED` whose review comes back `BREACH` moves to `FLAGGED`, which is also the state the supervisory capital-re-categorisation cascade of §3.1 pushes breaching `ACTIVE` tranches into. A `FLAGGED` tranche whose review comes back `PASS` or `EXEMPT_NO_CAP` moves `FLAGGED → REMEDIATED`, with the appended review carrying a `breach_bps` of zero; that is also the transition the reclassification cascade of §3.4 performs when a re-determination lands. The cycle `FLAGGED → REMEDIATED → FLAGGED` therefore has no round limit and no terminal state: surveillance runs for as long as the tranche exists.

### 3.7. Board Limits, Headroom and Liquidity Contingency Planning

The asset-liability desk expresses the board's appetite as concentration limits, one per metric. A limit declares its `metric` — `BROKERED_TO_TOTAL_DEPOSITS`, `LISTING_TO_TOTAL_DEPOSITS`, `WHOLESALE_TO_TOTAL_LIABILITIES` or `SINGLE_BROKER_TO_TOTAL_DEPOSITS` — together with `warning_threshold_bps`, the level at or above which the metric is in warning, and `breach_threshold_bps`, the level at or above which it is in breach. Both live in the range 0 to 10000 basis points inclusive, and `warning_threshold_bps` must be strictly below `breach_threshold_bps`; thresholds that are not strictly increasing, or a threshold above 10000, are refused with `ERR_THRESHOLD_ORDER_INVALID`. The metric is deliberately not a uniqueness key. Creating a limit for a metric that already has an `ACTIVE` row supersedes that row: the prior limit moves to `status` of `RETIRED` with its `current_value_bps` reset to 0 and its `breach_state` reset to `WITHIN`, while the new row becomes the governing `ACTIVE` limit and is evaluated against current balances immediately. Limits are listable per bank and can be narrowed by `status` and `metric`.

Posture evaluation reads the four metrics in the order they are declared above. The brokered-to-deposits value is `brokered_deposits_cents` multiplied by 10000 and divided by `total_deposits_cents`, discarding the remainder. The listing-to-deposits value is `listing_service_deposits_cents` multiplied by 10000 and divided by `total_deposits_cents`, again discarding the remainder. The wholesale-to-liabilities value is the sum of `brokered_deposits_cents` and `listing_service_deposits_cents`, multiplied by 10000 and divided by `total_liabilities_cents`. The single-broker value is simply the bank's `single_broker_max_ratio_bps`. Any of these whose denominator is zero yields zero. Each `ACTIVE` limit then takes that value into its own `current_value_bps` and sets `breach_state` to `BREACH` when the value is at or above its `breach_threshold_bps`, to `WARNING` when the value is at or above its `warning_threshold_bps` but below the breach level, and to `WITHIN` otherwise. Both comparisons are inclusive lower bounds, so a value exactly equal to `breach_threshold_bps` is a breach, not a warning. Rows whose `status` is `RETIRED` are excluded from the whole exercise and keep a `current_value_bps` of 0 and a `breach_state` of `WITHIN`.

From those states the bank's own two fields follow. `breached_metric_count` is the number of `ACTIVE` limits whose `breach_state` is `BREACH`. The `concentration_posture` is `FROZEN` when at least one `ACTIVE` limit is in breach, `RESTRICTED` when none is in breach but at least one is in warning, and `OPEN` otherwise. A `FROZEN` bank opens no new programs and funds no new deposits, and the freeze lifts only when every `ACTIVE` limit has returned to `WITHIN` or `WARNING`.

The single-broker exposure deserves its own note because it reaches across programs. For each counterparty with at least one program at the bank, the exposure is the sum of `principal_cents` over that bank's placements whose `funding_status` is `ACTIVE` and whose program names that counterparty. `single_broker_max_ratio_bps` is the largest of those exposures multiplied by 10000 and divided by `total_deposits_cents`, discarding the remainder, and it is 0 when no counterparty has any exposure. Only the maximum value is ever exposed — no counterparty identity is selected, so no tie-break is needed.

The bank's headline funding ratio comes in two variants, and one of them is the persisted one. The point-in-time variant is the value carried on `wholesale_funding_ratio_bps`: the sum of `brokered_deposits_cents` and `listing_service_deposits_cents`, multiplied by 10000 and divided by `total_deposits_cents`, discarding the remainder, and 0 when `total_deposits_cents` is zero. It is refreshed on every balance rollup and it is always the variant that drives posture evaluation and contingency-stage selection. The average-daily variant is read-only and period-scoped, requested by supplying a `basis` of `AVERAGE_DAILY` together with `period_start` and `period_end`; `basis` defaults to `POINT_IN_TIME`, under which the average-daily figures are all reported as 0. Its `day_count` is the number of whole days between `period_start` and `period_end` plus one, so both endpoints are inclusive. A placement occupies the wholesale ladder on a given day when it has ever been funded — that is, its `funding_status` is `ACTIVE`, `MATURED`, `WITHDRAWN_EARLY` or `ROLLED_OVER` — when its effective class is `BROKERED` or `LISTING_SERVICE_NON_BROKERED`, and when the day falls on or after its `issue_date` and on or before the earlier of `period_end` and its `settlement_date`, treating a null `settlement_date` as `period_end`. The daily sum adds, for every day in the period, the `principal_cents` of each occupying placement; `avg_wholesale_cents` is that total divided by `day_count`, discarding the remainder; and `average_daily_ratio_bps` is `avg_wholesale_cents` multiplied by 10000 and divided by `total_deposits_cents`, again discarding the remainder, and 0 when `total_deposits_cents` is zero. The two divisions happen in that order — average first, then ratio — and averaging the per-day ratios instead produces a different number and is not what this system reports. Because the average-daily variant time-weights each tranche by its occupancy days, money funded late in a period produces a far lower ratio than the point-in-time snapshot taken on the same book.

The same computed read also answers the desk's most practical question: how much more brokered money can be taken before the board's brokered limit bites. `brokered_headroom_cents` is the largest whole number of additional cents that could be added such that the brokered-to-deposits metric stays strictly below the `breach_threshold_bps` of the `ACTIVE` `BROKERED_TO_TOTAL_DEPOSITS` limit — remembering that additional brokered money raises the numerator and the denominator together. That circularity is resolved once, in closed form, in a pinned order. If there is no `ACTIVE` limit on that metric, the answer is unbounded and reported as -1. If the limit's `breach_threshold_bps` is 10000 or more, the answer is likewise unbounded and reported as -1. If the bank is already at or past the limit — that is, `brokered_deposits_cents` multiplied by 10000 is greater than or equal to the threshold multiplied by `total_deposits_cents` — the answer is 0. Otherwise, take the numerator as the threshold multiplied by `total_deposits_cents` less 10000 times `brokered_deposits_cents`, take the divisor as 10000 less the threshold, subtract exactly one from that numerator, and divide by the divisor discarding the remainder. The subtraction of one is not cosmetic: the constraint is strictly below the threshold, so the answer is the largest integer strictly below the exact ratio, and the two differ by exactly one whenever the divisor divides the numerator evenly. The inequality is solved treating the ratio as exact, and only the final result is floored; flooring an intermediate ratio first is wrong.

Liquidity contingency planning is the treasury side of the same exposure. A plan carries a human-readable `plan_version_label` and covers the closed calendar interval from `effective_from` to `effective_to` inclusive, with `effective_from` strictly before `effective_to`. That interval must not intersect the closed interval of any other plan of the same bank whose `status` is `UNDER_REVIEW`, `APPROVED`, `ACTIVATED` or `DEACTIVATED`; plans in `DRAFT` and `REJECTED` occupy no window at all. Touching endpoints do overlap — a new plan starting on the day an existing plan ends is a conflict — while a one-day gap is not, and a conflict is refused with `ERR_PLAN_WINDOW_OVERLAP`. The plan also declares three escalation triggers, `stage_1_trigger_bps`, `stage_2_trigger_bps` and `stage_3_trigger_bps`, which must be strictly increasing and none above 10000 — otherwise `ERR_THRESHOLD_ORDER_INVALID` — and the three playbook action codes `stage_1_action_code`, `stage_2_action_code` and `stage_3_action_code` that name what the treasury does at each level. A new plan lands in `DRAFT` with `activation_stage` of `NONE`, `required_buffer_cents` and `buffer_shortfall_cents` at 0, `prepared_by_user_id` stamped from the drafting controller and `approved_by_user_id` null. Plans are listable per bank and can be narrowed by `status`.

The plan lifecycle is a cycle with one terminal exit. Submitting for review moves the plan `DRAFT → UNDER_REVIEW` and changes no derived field. From `UNDER_REVIEW` the second line either approves, moving the plan to `APPROVED` and stamping `approved_by_user_id`, or rejects, moving it to the terminal `REJECTED` with no derived-field change; both decisions require an acting identifier different from the plan's `prepared_by_user_id`. Approval additionally requires that no other plan of the same bank whose `status` is `APPROVED` or `ACTIVATED` occupies a closed interval intersecting this plan's own, and a conflict there is likewise refused with `ERR_PLAN_WINDOW_OVERLAP`. Activation moves the plan `APPROVED → ACTIVATED` and is where the arithmetic happens. Deactivation moves it `ACTIVATED → DEACTIVATED` and resets `activation_stage` to `NONE` with `required_buffer_cents` and `buffer_shortfall_cents` both back to 0, but it is blocked while `buffer_shortfall_cents` is greater than zero: the bank must first raise `liquidity_buffer_cents` to cover the `required_buffer_cents` computed at activation, and an attempt made too early is refused with `ERR_BUFFER_SHORTFALL_UNFUNDED`. Re-arming moves the plan `DEACTIVATED → APPROVED` with no derived-field change, `activation_stage` remaining `NONE` and both buffer figures remaining 0, which closes the cycle `APPROVED → ACTIVATED → DEACTIVATED → APPROVED`. Any lifecycle action that is not a declared transition out of the plan's current `status` is refused with `ERR_PLAN_STATE_INVALID`, and every lifecycle action accepts an optional `note`. `activation_stage` is `NONE` for any plan whose `status` is anything other than `ACTIVATED`.

Activation selects a stage from the bank's persisted point-in-time `wholesale_funding_ratio_bps`, comparing downward through the three triggers, each an inclusive lower bound: the stage is `STAGE_3_CRISIS` when the ratio is at or above `stage_3_trigger_bps`, otherwise `STAGE_2_CONTINGENT` when it is at or above `stage_2_trigger_bps`, otherwise `STAGE_1_MONITOR` when it is at or above `stage_1_trigger_bps`, and otherwise `NONE`. The buffer requirement then follows from the stage and from the near-term maturity wall. The maturing-soon amount is the sum of `principal_cents` over the bank's placements whose `funding_status` is `ACTIVE`, whose `classified_as` is `BROKERED` or `LISTING_SERVICE_NON_BROKERED`, and whose `maturity_date` falls inside the closed 90-day horizon beginning on the logical clock's date and ending 90 days later, both endpoints included. The stage supplies a multiplier: no coverage at all at `NONE`, 2500 basis points — a quarter of the wall — at `STAGE_1_MONITOR`, 5000 basis points — half — at `STAGE_2_CONTINGENT`, and 10000 basis points — the whole wall — at `STAGE_3_CRISIS`. `required_buffer_cents` is the maturing-soon amount multiplied by that multiplier and divided by 10000, with the single final quotient rounded half up to whole cents, and `buffer_shortfall_cents` is the amount by which `required_buffer_cents` exceeds the bank's `liquidity_buffer_cents`, floored at zero. Activation is also reachable without a controller asking for it: hop four of the exception-revocation cascade in §3.3 activates every `APPROVED` plan of a bank that has just gone `FROZEN`, and each such plan runs exactly the same stage selection and buffer sizing.

### 3.8. The Maturity Sweep and the Rollover Ladder

Deposits do not mature themselves. A system operator runs the sweep, supplying a single `as_of_date`, and the sweep covers every placement across the whole book whose `funding_status` is `ACTIVE` and whose `maturity_date` falls on or before that date. The sweep runs in two phases that never interleave: phase one matures, phase two rolls over, and phase two begins only after phase one has finished every placement it is going to touch.

Phase one processes the eligible placements in ascending `maturity_date`, and where two share a maturity date, in ascending `created_at`. Each one moves `ACTIVE → MATURED`. Its `accrued_interest_cents` is computed with a settlement date equal to its own `maturity_date` — not equal to the sweep's `as_of_date`, which may be later — and its `net_settlement_cents` becomes `principal_cents` plus `accrued_interest_cents`, with no penalty, because a deposit that runs to term is never penalised. Its `principal_cents` is then subtracted from the matching wholesale bucket of its bank and from its program's `outstanding_principal_cents`, and the bank's posture is re-evaluated; the counterparty agreement's `accrued_fee_cents` and the placement's own `fee_accrual_cents` are recomputed on the new book. Because a run can sweep several days' worth of maturities at once, several placements can release principal in the same run, and a bank that was `FROZEN` at the start of the run can be `OPEN` by the end of phase one.

Phase two considers exactly those placements that phase one just matured within this same run — never a placement that was already `MATURED` before the sweep started. Such a placement rolls `MATURED → ROLLED_OVER` when its program's `rollover_enabled` is true, its program's `state` is `OPEN_FOR_PLACEMENT`, and its bank's `concentration_posture` is anything other than `FROZEN`. Phase two also walks its candidates in ascending `maturity_date` then ascending `created_at`. Each roll creates one successor placement under the same program, with `rolled_from_placement_id` pointing at the placement it came from, `principal_cents` equal to that placement's `net_settlement_cents` — so matured interest compounds into the new tranche — `rate_bps` taken from the program's current `offered_rate_bps` rather than from the old tranche's rate, `issue_date` equal to the sweep's `as_of_date`, `tenor_days` taken from the program's current `tenor_days`, and therefore a `maturity_date` of `as_of_date` advanced by that many days. The successor is born `PENDING` on `funding_status` and `UNREVIEWED` on `compliance_status`, which means it has entered no wholesale bucket, has no `classified_as` yet, and still needs a funding activation and a fresh rate-cap check of its own before it counts anywhere. A program whose `rollover_enabled` is false, or that has been suspended or closed, simply leaves its matured tranches at `MATURED`, and `MATURED` and `ROLLED_OVER` are both terminal on the funding dimension.

The run reports what it did: the `as_of_date` it was given, `matured_count` for the number of placements phase one matured, `rolled_over_count` for the number phase two moved to `ROLLED_OVER`, `created_placement_count` for the number of successor placements created — which equals `rolled_over_count`, since each roll creates exactly one successor — and the two identifier lists `matured_placement_ids` and `created_placement_ids`, each in the processing order of its own phase. A sweep that finds nothing eligible is not an error: it succeeds with both counts at zero and both lists empty. After the sweep the bank's funding ratio, single-counterparty maximum and posture all reflect the released principal.

### 3.9. Call Report Accuracy and the Examiner Cycle

Every quarter the bank reports its deposit composition to its regulator, and the system's job is to tell the operator whether what is being reported matches what the book actually says. A filing is opened for one reporting period, identified by a `report_period` label of four digits followed by the letter Q and a quarter number 1 through 4 — `2026Q3` is well formed, and anything else is refused as an invalid request. The `report_period` is unique within one bank, so a second filing for a period that already has one is refused with `ERR_DUPLICATE_KEY`; the same label at a different bank is fine. The operator supplies the three figures actually being reported: `rc_e_brokered_reported_cents` for the brokered line of schedule RC-E memorandum line 1, `rc_o_listing_reported_cents` for listing-service non-brokered deposits, and `rc_e_core_reported_cents` for core deposits, each a non-negative whole number of cents and all three required at creation. A new filing opens in `DRAFT` with `computed_brokered_cents`, `computed_listing_cents`, `computed_core_cents`, `variance_cents`, `variance_bps` and `amendment_round` all at 0, `accuracy_status` of `NOT_ASSESSED`, and `examiner_finding_note`, `prepared_by_user_id` and `attested_by_user_id` all null. Nothing is compared at creation. Filings are listable per bank, narrowable by `status` and `report_period`, and individually readable with their computed figures, variance and accuracy tier.

Preparation is where the comparison happens. Preparing snapshots the bank's live derived balances at that instant — `computed_brokered_cents` from `brokered_deposits_cents`, `computed_listing_cents` from `listing_service_deposits_cents`, `computed_core_cents` from `core_deposits_cents` — and then measures the brokered line only: `variance_cents` is the absolute difference between `rc_e_brokered_reported_cents` and `computed_brokered_cents`, in either direction, so over-reporting and under-reporting by the same amount are equally material. `variance_bps` expresses that gap in basis points of `total_deposits_cents`, multiplying by 10000 and dividing with the remainder discarded, and is 0 when `total_deposits_cents` is zero. The tier follows: `accuracy_status` is `ACCURATE` when `variance_cents` is exactly zero, `VARIANCE_MINOR` when there is some variance but `variance_bps` is strictly below 25, and `VARIANCE_MATERIAL` when `variance_bps` is 25 or more. Twenty-five basis points is an inclusive lower bound, so a variance of exactly 25 basis points is material. Note that a non-zero `variance_cents` that is too small to register a single basis point still lands in `VARIANCE_MINOR`, never `ACCURATE`; only an exact match is accurate. Preparation also stamps `prepared_by_user_id` with the acting identifier and clears `attested_by_user_id` back to null, so any earlier attestation is void. The listing and core figures are snapshotted for the record but never scored — the variance gate watches the brokered line alone.

The filing then walks a workflow with an amendment cycle. Preparing moves the filing `DRAFT → PREPARED`. Attesting moves it `PREPARED → ATTESTED` and stamps `attested_by_user_id`, and it is the segregation-of-duties gate: the attesting identifier must differ from `prepared_by_user_id`. Attestation is also the accuracy gate — a filing whose `accuracy_status` is `VARIANCE_MATERIAL` cannot be attested and is refused with `ERR_FILING_VARIANCE_MATERIAL`; the operator must correct the reported numbers, or the underlying book must change, and the filing must be prepared again. Filing moves it `ATTESTED → FILED`, and needs no accuracy check of its own because the attestation gate has already guaranteed that a filed report was either `ACCURATE` or `VARIANCE_MINOR`. Opening an examination moves it `FILED → UNDER_EXAMINER_REVIEW`. From there the examiner either requires an amendment, moving it to `AMENDMENT_REQUIRED`, incrementing `amendment_round` by one and recording the supplied `examiner_finding_note`, or accepts it, moving it to the terminal `ACCEPTED` and likewise recording the note. An `AMENDMENT_REQUIRED` filing is prepared again, moving `AMENDMENT_REQUIRED → PREPARED` with exactly the same effects as the first preparation, which closes the cycle `FILED → UNDER_EXAMINER_REVIEW → AMENDMENT_REQUIRED → PREPARED`. That cycle is bounded: an amendment may be required only while `amendment_round` is still below 2, so the third attempt is refused with `ERR_REVIEW_ROUND_LIMIT` and the examiner's only remaining move is to accept. Any workflow action that is not a declared transition out of the filing's current `status` is refused with `ERR_FILING_STATE_INVALID`.

Which inputs a workflow action accepts depends on the action, and the rule is narrow on purpose. The three reported figures are accepted only with a preparation performed from `AMENDMENT_REQUIRED` — that is how an amendment corrects the numbers — and supplying them on a first preparation from `DRAFT`, or on any other action, is not how the figures change. When they are supplied on an amending preparation they overwrite the stored reported figures before the variance is recomputed. The `examiner_finding_note` is accepted only with the require-amendment and accept actions. All other actions take the action alone.

An open examination freezes the bank's books. While any filing of a bank sits in `UNDER_EXAMINER_REVIEW`, that bank's `capital_category` and its balance baselines are frozen against operator edits, and either edit attempted during that window is refused with `ERR_EXAMINER_REVIEW_LOCK`. The lock is per bank and covers only operator-driven edits: the sweep of §3.8, funding activations and every other balance movement driven by placement lifecycle continue to move the derived balances, which is why a filing prepared before an examination and re-prepared during the amendment cycle can produce a different variance on the same reported figures. The lock lifts as soon as no filing of that bank remains `UNDER_EXAMINER_REVIEW` — that is, once the examiner has accepted or required an amendment.
