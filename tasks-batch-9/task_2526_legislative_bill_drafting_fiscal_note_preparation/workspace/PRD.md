# Legislative Drafting & Fiscal Notes API — Product Requirements Document

## 1. Introduction

A legislative services agency sits at the exact point where political intent becomes enforceable statutory text, and it is judged on two things it cannot control: the calendar and the cost. Members arrive with subjects rather than sections; drafting attorneys must reconcile those subjects against code that already exists; executive agencies must price the consequences; and every one of those activities is bounded by three immovable session deadlines. Today that coordination lives in spreadsheets, email threads and institutional memory, which means a bill can reach the floor with a fiscal note that no longer describes the measure, a member can consume a priority slot on a request that was withdrawn weeks ago, and a committee can schedule two hearings into the same room-hour.

This document specifies the API for a system that makes that coordination mechanical. It governs the full arc of a measure: drafting request intake with confidentiality handling and member priority slots; drafter assignment against a real occupancy calendar; statutory research and conflict identification against existing code; drafting-style certification under a strict separation of duties; introduction, chamber-scoped numbering, companion-bill linkage and committee referral; fiscal note routing to affected agencies with two competing cost methodologies, contingency tiers and four-year revenue projections under alternative scenarios; amendment drafting under rapid — and near adjournment, compressed — turnaround, including the fiscal decertification cascade an adopted amendment triggers; enrolled bill preparation, non-substantive technical correction, presiding-officer signature routing and transmittal; and finally session adjournment, which closes every open workflow in a single fan-out.

Two design commitments run through everything that follows. First, **time is a server-held logical clock**, never wall-clock time: every deadline, hearing window, service-level target and turnaround is measured against a clock the test harness advances explicitly. Second, **the fiscal ledger must survive round trips exactly**: an amendment that decertifies a note and is then rescinded must leave the session's certified total bit-identical to its pre-adoption value. Any implementation that "recomputes approximately the same number" has failed the requirement.

## 2. Global Specifications & System-Wide Principles

This section defines the contract-level rules that hold for every endpoint in the API. Where §3 describes what a legislative workflow means, this section describes how a request is shaped, authenticated, ordered and refused.

### 2.1. User and Role-Based Access Control

Every request — reads included — must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the capacity in which that principal is acting. If either header is absent, or if `X-User-Role` is not one of the seven declared role names, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). If both headers are well formed but the named role is not among the roles authorized for the target endpoint (as listed in §4), the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

The seven roles are `PlatformAdmin`, `Clerk`, `FiscalOfficer`, `Member`, `Drafter`, `ReviewCounsel` and `AgencyAnalyst`.

- `PlatformAdmin` is the legislative services system administrator. It owns the reference data — sessions, members, drafting attorneys and agencies — and the logical clock, and it performs no legislative act of its own. When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may log it but never compares it to any entity's `id`.
- `Clerk` is the chamber clerk. It drives the public legislative record: convening and adjourning the session, introduction and numbering, companion linkage, committee referral and reporting, passage, enrollment, amendment disposition and signature routing. It never drafts text and never certifies fiscal numbers. When `X-User-Role` is `Clerk`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity and is never compared to any entity's `id`.
- `FiscalOfficer` is the legislative fiscal office analyst. It owns the fiscal note pipeline downstream of the agency — returning a note for revision, certifying it, and maintaining the session ledger those actions move. It cannot draft, introduce or amend. When `X-User-Role` is `FiscalOfficer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity and is never compared to any entity's `id`.
- `Member` is a legislator. When `X-User-Role` is `Member`, `X-User-ID` is the `id` of the acting `Member` row; ownership checks on any resource that references a `Member` compare the resource's member reference to `X-User-ID`. A drafting request's `member_id` is stamped from that header at intake and never accepted from the body, and an amendment's `requested_by_member_id` is stamped the same way.
- `Drafter` is a legislative services attorney who performs statutory research, records conflicts and drafts amendments. When `X-User-Role` is `Drafter`, `X-User-ID` is the `id` of the acting `Drafter` row; ownership checks compare the resource's `assigned_drafter_id` or `drafted_by_drafter_id` to `X-User-ID`.
- `ReviewCounsel` is a senior legislative services attorney who assigns drafters, waives statutory conflicts, certifies drafting-style compliance and applies technical corrections. When `X-User-Role` is `ReviewCounsel`, `X-User-ID` is the `id` of the acting `Drafter` row — the same table that backs `Drafter`, not a separate one. Because both roles resolve to the same table, the separation between drafting and reviewing is a separation of **identities**, not of role strings: one senior attorney may legitimately hold both roles, and every segregation rule therefore compares identifiers.
- `AgencyAnalyst` is an executive agency fiscal analyst. When `X-User-Role` is `AgencyAnalyst`, `X-User-ID` is the `id` of the acting `Agency` row; ownership checks compare a fiscal note request's `agency_id` to `X-User-ID`. This role cannot read the drafting pipeline at all — no drafting-request or statutory-conflict read is granted to it, so such an attempt is stopped by the endpoint role check with `ERR_UNAUTHORIZED` rather than by any confidentiality rule.

Acting under `ReviewCounsel` additionally requires seniority. Four operations are reserved to that role — drafter assignment, draft certification, applying a technical correction, and resolving a statutory conflict with the disposition `WAIVED` — and on each of them the `Drafter` row named by `X-User-ID` must exist and carry `is_senior` set to true. A junior attorney who presents `X-User-Role: ReviewCounsel` is refused with `ERR_SENIOR_COUNSEL_REQUIRED` (HTTP 403).

Ownership is enforced on exactly seven operations: withdrawing a drafting request and completing its research; recording a statutory conflict; appending a cost estimate line; submitting a fiscal note; drafting an amendment; and reading a single agency record when the acting role is `AgencyAnalyst`. A `Member` acts only on their own drafting requests and amendments; an `AgencyAnalyst` files and submits only notes routed to their own agency and reads only their own `Agency` row; a `Drafter` acts only where assigned. Any breach is `ERR_NOT_RESOURCE_OWNER` (HTTP 403). Answering a clarification carries the same sponsor-identity requirement as part of its own transition precondition.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every collection endpoint is paginated by two query parameters. `limit` controls page size: it defaults to 10 when omitted, may be no smaller than 1 and no larger than 100. `offset` controls the starting position: it defaults to 0 and may be no smaller than 0. A `limit` that is not an integer in the range 1 through 100 inclusive, or an `offset` that is not an integer of at least 0, is rejected with `ERR_PAGINATION_INVALID` (HTTP 400). All four pagination fields — `limit`, `offset`, `total_count` and `has_more` — appear in the `meta` object of every list response, where `total_count` is the number of rows matching the filter before the page window is applied and `has_more` is true when rows remain beyond the current window.

List responses are ordered by `created_at` ascending, oldest row first. The single exception is the session collection, which is a management view and is ordered by `created_at` descending so that the newest session appears first.

Filters are additive: supplying two filters narrows to rows matching both, and an unsupplied filter imposes no restriction. Each collection accepts the following filters, matched exactly against the field of the same name. The session list accepts `status`. The committees-of-a-session list accepts `chamber` and `is_fiscal_committee`. The drafting-request list accepts `session_id`, `member_id`, `assigned_drafter_id`, `status`, `confidentiality` and `priority_flag`. The statutory-conflicts-of-a-request list accepts `severity` and `resolution_status`. The bill list — which doubles as the bill status report — accepts `session_id`, `drafting_request_id`, `sponsor_member_id`, `companion_bill_id`, `chamber`, `legislative_status`, `fiscal_status` and `priority_bill`. The committee-referral list accepts `bill_id`, `committee_id` and `status`. The fiscal-note-request list accepts `bill_id`, `agency_id`, `reopened_by_amendment_id`, `status` and `methodology`. The cost-estimate list of a note accepts `fiscal_year`, `scenario`, `revision_round` and `included_in_certification`. The amendment list accepts `bill_id`, `committee_referral_id`, `requested_by_member_id`, `drafted_by_drafter_id`, `supersedes_amendment_id`, `stage` and `status`. The enrolled-bill list accepts `bill_id` and `status`. The technical-correction list accepts `enrolled_bill_id`, `proposed_by_drafter_id`, `applied_by_drafter_id`, `correction_type` and `status`.

### 2.4. The Logical Session Clock

Nothing in this domain is timed against real wall-clock time. The server holds a **logical clock**, and every deadline, hearing window, service-level target, turnaround limit and lateness determination in this specification is evaluated against that clock. Before any client sets it, the logical clock reads exactly `2026-08-01T00:00:00Z`; an implementation must not fall back to the host's real time at any point.

A `PlatformAdmin` may advance the clock through an administrative test-driving capability that takes a single input field, `current_utc`, and sets the clock to that instant. The clock is monotonic: the supplied instant must be greater than or equal to the current reading, and a request carrying an earlier instant is refused with `ERR_CLOCK_NOT_MONOTONIC` (HTTP 422). Advancing the clock mutates no entity and returns no resource body — deadlines are never evaluated retroactively, so a drafting service-level target that has quietly passed is discovered at the next write against that request, not at the moment the clock crosses it.

### 2.5. Common Resource Properties

Every persisted resource carries a server-minted `id`: a UUID string with no type prefix, no vendor prefix and no embedded semantics. Clients never supply an `id`; supplying one has no effect. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with exactly three fractional-second digits, recorded when the row is first written.

Most resources additionally carry `updated_at`, an ISO 8601 UTC timestamp in the same format that is refreshed on every mutation of the row, and `version`, an integer that begins at 1 when the row is created and increases by exactly 1 on each mutation. The `version` field is the observable currency of the concurrency rules in §2.6: a client that has read a resource and wants to write a child against it must be able to prove it saw the parent's latest state.

One resource is deliberately leaner. A cost estimate line is append-only: it is never edited and never deleted, so it carries only `id` and `created_at`. Neither `updated_at` nor `version` exists on a cost estimate line, and neither field appears in its response payload.

### 2.6. Optimistic Concurrency on Parent Records

Three write operations attach a child record to a parent whose meaning may have shifted since the client last looked. Each of them requires a non-optional version assertion in its request body, and each rejects a mismatch with its own error identifier. Endpoints not named below take no version field at all, and supplying one to them is meaningless.

Creating an amendment requires `expected_bill_version` in the body, carrying the client's last observed `version` of the target bill. An amendment is drafted against a specific version of the bill's text; if any other writer has advanced that bill's `version` since the requesting member read it — another amendment filed, drafted, adopted or rescinded, a referral added, a companion linked — the requester's view of the measure is stale and the creation is refused with `ERR_STALE_BILL_VERSION` (HTTP 412) rather than being silently attached to text the requester never saw. Because a bill may legitimately carry many amendments, nothing but this version comparison distinguishes the accepted case from the refused one.

Appending a cost estimate line requires `expected_fiscal_note_request_version` in the body, carrying the client's last observed `version` of the fiscal note request. A line is computed under the revision round and methodology the analyst last observed; if the note's `version` has moved on — because a prior line was appended, because the note was returned for revision, or because an adopted amendment re-opened it — the line is refused with `ERR_STALE_FISCAL_NOTE_VERSION` (HTTP 412) instead of being filed under a round the analyst did not intend. Note that appending a line itself advances the note's `version`, so a client filing several lines in sequence must refresh the value between calls by re-reading the note.

Proposing a technical correction requires `expected_enrolled_bill_version` in the body, carrying the client's last observed `version` of the enrolled bill. A correction cites a location in the enrolled text; if an earlier correction has already been proposed or applied, the enrollment's `version` has advanced, the citation may no longer point where the drafter believes, and the proposal is refused with `ERR_STALE_ENROLLMENT_VERSION` (HTTP 412). Many corrections per enrollment are legitimate; the version comparison is the only discriminator.

### 2.7. Reference Resolution: Paths First, Then Bodies

Identifiers that appear in a URL path are resolved strictly from left to right, and the first unresolvable segment decides the error. Each entity has its own not-found identifier, all of them HTTP 404: `ERR_SESSION_NOT_FOUND`, `ERR_MEMBER_NOT_FOUND`, `ERR_DRAFTER_NOT_FOUND`, `ERR_AGENCY_NOT_FOUND`, `ERR_COMMITTEE_NOT_FOUND`, `ERR_DRAFTING_REQUEST_NOT_FOUND`, `ERR_STATUTORY_CONFLICT_NOT_FOUND`, `ERR_BILL_NOT_FOUND`, `ERR_COMMITTEE_REFERRAL_NOT_FOUND`, `ERR_FISCAL_NOTE_REQUEST_NOT_FOUND`, `ERR_AMENDMENT_NOT_FOUND`, `ERR_ENROLLED_BILL_NOT_FOUND` and `ERR_TECHNICAL_CORRECTION_NOT_FOUND`. Left-to-right ordering matters when two segments are both wrong: a request naming a nonexistent session and a nonexistent committee beneath it reports the session failure, because the outer segment is consulted first.

Once every path identifier resolves, identifiers carried in the request body are resolved next, each raising the not-found identifier of the entity it names. This applies to the `session_id` on a new drafting request, the `drafting_request_id` on a new statutory conflict and on a bill introduction, the `drafter_id` on a drafter assignment, the `committee_id` on a referral, the `agency_id` on a fiscal note routing, the `companion_bill_id` on a companion link, and the `bill_id`, `committee_referral_id` and `supersedes_amendment_id` on a new amendment. A `companion_bill_id` that resolves to nothing is `ERR_BILL_NOT_FOUND`; a `supersedes_amendment_id` that resolves to nothing is `ERR_AMENDMENT_NOT_FOUND`.

Where a child is created beneath its parent's path, the parent link is taken from the path and never from the body — a body value naming a different parent is ignored rather than honoured. A committee's `session_id`, a referral's `bill_id`, a fiscal note request's `bill_id`, a cost estimate line's `fiscal_note_request_id`, a technical correction's `enrolled_bill_id` and an enrolled bill's `bill_id` are all path-derived in this way.

### 2.8. Confidentiality of Drafting Files

A drafting request declares its `confidentiality` as either `CONFIDENTIAL` or `PUBLIC`, defaulting to `PUBLIC`. A `CONFIDENTIAL` request, and every statutory conflict recorded beneath it, is readable by its sponsoring `Member`, by `Drafter` and `ReviewCounsel`, by `FiscalOfficer`, by `Clerk` and by `PlatformAdmin` — but never by a different `Member`.

The consequence of a denial depends on the shape of the read, and this distinction is deliberate. On the three targeted reads — a single drafting request, the statutory-conflict list beneath a request, and a single statutory conflict — a `Member` who is not the sponsor of a `CONFIDENTIAL` request is refused with `ERR_CONFIDENTIAL_ACCESS_DENIED` (HTTP 403), because the existence of the row is already implied by the identifier they supplied. On the unscoped drafting-request collection read, no error is raised at all: the confidential rows the acting member does not sponsor are simply **omitted from the page and excluded from `total_count`**, so a browsing member cannot infer their existence from a row count. An `AgencyAnalyst` never reaches this rule at all, since that role holds no drafting-request read permission and is stopped earlier with `ERR_UNAUTHORIZED`.

### 2.9. Cents, Rounding and Ledger Discipline

All money in this system is an integer number of cents. There are no decimal currency amounts, no floating-point accumulation anywhere a cent is observable, and no re-derivation of a stored total from its inputs once that total has been posted. Where a rate must be applied, the specification calls for **rounding half up**: compute the exact rational product, then round to the nearest whole cent, with a tie resolved away from zero. Each calculation in §3 states exactly how many rounding operations it performs and at which step; performing one more, one fewer, or the same number in a different order produces a different and incorrect number.

Non-monetary quantities have their own precision rules. Complexity scores are plain integers requiring no rounding. Drafting service-level windows are expressed in whole hours produced by a single ceiling operation. Amendment turnaround windows are expressed in whole minutes produced by a single floor operation. Fiscal note grants are expressed in whole days added to an instant, and adding whole days preserves the original instant's time-of-day exactly.

The session's `certified_fiscal_total_cents` is a **ledger**, not a projection. It equals the sum of `certified_total_cents` over every fiscal note request in status `CERTIFIED` whose bill belongs to that session; requests in `ROUTED`, `SUBMITTED`, `RETURNED_FOR_REVISION` or `LAPSED` contribute nothing, even when a re-opened request still retains a `certified_total_cents` value for later restoration. The ledger is maintained by exact addition when a note is certified and exact subtraction when a certified note is re-opened, and the incrementally maintained value must equal a full recomputation of that sum at every observable instant. Because the amount posted and the amount unposted are the very same retained figure, a certify → decertify → re-certify round trip returns the ledger to a bit-identical value. Drift is not tolerated.

Alongside the ledger the session maintains `fiscal_posture`, which is `CONSTRAINED` when `certified_fiscal_total_cents` is greater than or equal to `constrained_threshold_cents` and `NORMAL` otherwise. The boundary is inclusive: a total exactly equal to the threshold is already `CONSTRAINED`. A session is created with `certified_fiscal_total_cents` of 0 and `fiscal_posture` of `NORMAL`, and its `fiscal_cap_cents` — which must itself be at least `constrained_threshold_cents` — is the hard ceiling described in §3.7.

### 2.10. Cascades, Counters and Compensating Actions

Many operations in this domain mutate more than one row. Whenever a cascade reaches a row, that row's `updated_at` is refreshed and its `version` increases by 1, exactly as a direct write would do — a caller holding a stale `version` of a bill that was touched only indirectly is still stale.

Three properties govern every cascade in §3. First, **denormalized counters are derived, not narrative**: `priority_slots_used`, `clarification_pending_count`, `intake_hold`, `active_engagement_count`, `active_referral_count`, `open_request_count`, `late_submission_count`, `revision_count`, `responsiveness_score`, `blocking_conflict_count`, `open_blocking_conflict_count`, `advisory_conflict_count`, `referral_count`, `adopted_amendment_count`, `adopted_fiscal_delta_cents`, `bills_introduced_count`, `bills_enrolled_count`, `corrections_applied_count` and `open_corrections_count` each have a definition stated in §3, and their maintained value must always equal that definition recomputed from scratch. Second, **cascades are conditional where the specification says they are**: a level that fires only under a stated condition must not fire otherwise. Third, **compensating actions must be exact**: withdrawing a priority drafting request returns the member's slot count to precisely its pre-submission value, and rescinding an adopted amendment restores the fiscal ledger to precisely its pre-adoption value.

### 2.11. The Order of Refusal

When a single request violates several rules at once, exactly one error is reported, and which one is determined by a fixed ladder evaluated top to bottom. Evaluation stops at the first violated rung. The domain rationale is that a request which breaks the code or the separation of duties must be refused before the calendar is even consulted, and that money is checked last so that a fiscally clean but structurally broken request never reports a budget error.

The ladder, in order:

1. **Authentication.** Both headers present and `X-User-Role` one of the seven declared roles — otherwise `ERR_UNAUTHENTICATED`.
2. **Endpoint role.** The acting role appears in the target endpoint's authorized list — otherwise `ERR_UNAUTHORIZED`.
3. **Seniority.** On the four `ReviewCounsel`-only operations, the backing `Drafter` row has `is_senior` true — otherwise `ERR_SENIOR_COUNSEL_REQUIRED`.
4. **Path existence.** Every identifier in the path resolves, left to right — otherwise the matching not-found identifier.
5. **Ownership.** An entity-backed role acts only on what it owns — otherwise `ERR_NOT_RESOURCE_OWNER`.
6. **Confidentiality.** A non-sponsoring member is kept out of a confidential drafting file — otherwise `ERR_CONFIDENTIAL_ACCESS_DENIED`.
7. **Payload shape.** Every required field present, every enum value declared, every `*_cents` value honouring its minimum, every interval ending strictly after it starts, and `required_fiscal_years` a non-empty strictly ascending array of integers — otherwise `ERR_INVALID_REQUEST`. At this same rung, list endpoints validate pagination (`ERR_PAGINATION_INVALID`) and the clock-advance capability validates monotonicity (`ERR_CLOCK_NOT_MONOTONIC`).
8. **Body reference existence.** Every identifier carried in the body resolves — otherwise the matching not-found identifier.
9. **Optimistic concurrency.** The supplied `expected_bill_version`, `expected_fiscal_note_request_version` or `expected_enrolled_bill_version` equals the parent's current `version` — otherwise the matching stale-version identifier from §2.6.
10. **Session lifecycle.** The governing session is `CONVENED`, and is not already `ADJOURNED` — otherwise `ERR_SESSION_NOT_CONVENED` or `ERR_SESSION_ADJOURNED`.
11. **Target state.** The target row is in a state from which the requested transition is declared — otherwise the matching invalid-state identifier for that entity.
12. **Segregation of duties.** `ERR_SEGREGATION_OF_DUTIES`.
13. **Unresolved blocking conflicts.** `ERR_BLOCKING_CONFLICT_UNRESOLVED`.
14. **Drafting-style compliance.** `ERR_STYLE_NONCOMPLIANT`.
15. **Substantive correction refusal.** `ERR_SUBSTANTIVE_CORRECTION_FORBIDDEN`.
16. **Cost-estimate presence.** `ERR_NO_COST_ESTIMATES`.
17. **Fiscal-year completeness.** `ERR_ESTIMATE_YEARS_INCOMPLETE`.
18. **Referential business rules.** Companion linkage, supersession targets, amendment stage pairing, committee session and chamber matching, the fiscal-note prerequisite for favourable reporting, passage and enrolment, signature ordering, and the unapplied-correction bar on transmittal.
19. **Member intake hold.** `ERR_MEMBER_INTAKE_HOLD`.
20. **Temporal deadlines.** Introduction deadline, committee report deadline, amendment turnaround, sine die, and the hearing-window-after-deadline check.
21. **Capacity.** Committee hearing-window conflict, committee referral capacity, drafter engagement capacity, agency inactivity, agency open-request capacity, and the one-open-note-per-bill rule.
22. **Uniqueness.** `ERR_DUPLICATE_COST_ESTIMATE` and `ERR_DUPLICATE_AGENCY_CODE`.
23. **Fiscal.** Member priority slots, the session fiscal cap, and the constrained-posture fiscal-committee requirement.

Two rungs deserve emphasis. The session-lifecycle rung sits **above** the target-state rung, so a write attempted against a still-`PENDING` session reports `ERR_SESSION_NOT_CONVENED` rather than an invalid-state error, and any business write attempted after adjournment reports `ERR_SESSION_ADJOURNED` — including a second adjournment attempt. And within the business band, segregation of duties precedes the drafting-quality gates, so a drafter who tries to certify their own work is told about the conflict of interest even when their draft also carries open blocking conflicts or positive style findings.

## 3. Business Logic & Workflows

The subsections below follow a measure through the agency in the order the work actually happens: standing up the session, taking in a drafting request, researching and drafting it, introducing and referring the bill, pricing it, amending it, and finally enrolling and transmitting it. Cross-cutting concerns — occupancy calendars, ledgers, confidentiality, compensating actions — are woven into the stage where they bite rather than collected separately.

### 3.1. Standing Up a Session and Its Reference Data

Everything in this system hangs off a **legislative session**. A `PlatformAdmin` creates one with a human label in `name` and three ordered deadlines: `introduction_deadline_utc`, the last instant at which a bill may be introduced; `committee_report_deadline_utc`, the last instant at which a referral may be reported out; and `sine_die_utc`, the scheduled adjournment instant used by amendment turnaround compression. The three must be strictly increasing — `introduction_deadline_utc` earlier than `committee_report_deadline_utc`, which is earlier than `sine_die_utc`. Two fiscal thresholds are supplied at the same time: `constrained_threshold_cents`, which may not be negative, and `fiscal_cap_cents`, which must be at least as large as `constrained_threshold_cents`. Finally `required_fiscal_years` is a non-empty array of integers in strictly ascending order — the fiscal years every baseline cost estimate set must cover, for example the two years 2027 and 2028. An optional `fiscal_note_default_days` sets the baseline number of days an agency is granted for a fiscal note; it defaults to 21 and must be at least 1. Any breach of these shape rules is `ERR_INVALID_REQUEST`.

A newly created session opens in `status` `PENDING` with `convened_utc` and `adjourned_utc` both null, `certified_fiscal_total_cents` at 0, `fiscal_posture` `NORMAL`, `bills_introduced_count` and `bills_enrolled_count` at 0, and both numbering counters — `next_house_bill_number` and `next_senate_bill_number` — at 1. `bills_introduced_count` is the number of bills filed under this session regardless of their legislative state, while `bills_enrolled_count` counts only those bills whose legislative state has reached `ENROLLED` or `TRANSMITTED`.

A `Clerk` convenes the session, moving `status` from `PENDING` to `CONVENED` and stamping `convened_utc` with the logical clock. Convening a session that is not `PENDING` is `ERR_INVALID_SESSION_STATE`. The distinction matters operationally: committees, members, drafting attorneys and agencies may all be registered while the session is still `PENDING`, but no drafting request, bill, referral, fiscal note or amendment may be written until the session is `CONVENED`.

Committees are created beneath their session, so a committee's `session_id` comes from the path and is never read from the body. Either a `Clerk` or a `PlatformAdmin` may create one, supplying its `chamber` (`HOUSE` or `SENATE`), its `name`, an optional `is_fiscal_committee` flag defaulting to false, and an optional `max_concurrent_referrals` defaulting to 2 and required to be at least 1. A committee starts with `active_referral_count` at 0 — the number of its referrals currently sitting `IN_COMMITTEE` — and only a committee whose `is_fiscal_committee` is true satisfies the constrained-posture requirement described in §3.6.

Legislators are registered by a `PlatformAdmin` with a `full_name`, a `chamber` of `HOUSE` or `SENATE` that fixes the chamber of every bill they sponsor, a `party` label kept purely for audit, and an optional `priority_slots_total` defaulting to 2 and permitted to be 0 or more. A new member starts with `priority_slots_used` at 0, `clarification_pending_count` at 0 and `intake_hold` false. Drafting attorneys are registered the same way: a `full_name`, an optional `is_senior` flag defaulting to false — true is the precondition for acting under the `ReviewCounsel` role — and an optional `max_concurrent_engagements` defaulting to 2 and required to be at least 1. A new attorney starts with `active_engagement_count` at 0.

Affected executive agencies round out the reference data. An agency carries a `name`, a short `agency_code` that must be unique across all agencies — a repeat is `ERR_DUPLICATE_AGENCY_CODE` — an optional `status` of `ACTIVE` or `INACTIVE` defaulting to `ACTIVE`, and an optional `max_open_requests` defaulting to 3 and required to be at least 1. An `INACTIVE` agency may be registered deliberately, to model a body that cannot receive new routings. Every new agency starts with `open_request_count` at 0, `late_submission_count` at 0, `revision_count` at 0 and `responsiveness_score` at 100.

### 3.2. Drafting Request Intake and Member Priority Handling

A legislator opens the pipeline by filing a **drafting request** against a convened session. The body carries the `session_id`, a short `subject`, a narrative `summary` of the legislation wanted, a `requested_sections_count` of at least 1 recording how many statute sections the member believes must be touched, and a `target_code_chapter` retained for audit only. Three optional fields shape the request further: `confidentiality`, which is `CONFIDENTIAL` or `PUBLIC` and defaults to `PUBLIC`; `priority_flag`, defaulting to false, which declares that the request should consume one of the member's priority slots; and `appropriation_requested_cents`, defaulting to 0 and never negative, the appropriation the member is asking for. The request's `member_id` is stamped from `X-User-ID` and is never accepted from the body. The new row lands in `status` `SUBMITTED` with `assigned_drafter_id`, `engagement_start_utc`, `engagement_end_utc`, `affected_sections_count`, `research_completed_utc`, `sla_due_utc`, `actual_complexity_score` and `style_findings_count` all null, `revision_round` at 0, and all three conflict counters at 0.

Intake is gated twice. A member whose `intake_hold` is true is refused with `ERR_MEMBER_INTAKE_HOLD`: that flag is set exactly when the member's `clarification_pending_count` — the number of their drafting requests currently sitting in `RETURNED_FOR_CLARIFICATION` — has reached two or more. The intent is blunt: a legislator who is already sitting on two unanswered clarification requests may not open a third file until they answer one. Separately, a request that declares `priority_flag` true is refused with `ERR_PRIORITY_SLOTS_EXHAUSTED` unless the member's `priority_slots_used` is strictly less than their `priority_slots_total`. `priority_slots_used` is defined as the count of that member's drafting requests, across every session, whose `priority_flag` is true and whose `status` is neither `WITHDRAWN` nor `LAPSED`; when a priority request is accepted, that count rises by one.

At intake the system freezes the member's own view of how hard the work will be into `intake_complexity_estimate`, and this value is never recomputed afterwards. It is the sum of four terms. Four points are awarded for each section the member declared in `requested_sections_count`. Twelve points are added when `confidentiality` is `CONFIDENTIAL`, and nothing otherwise. Eight points are added when `priority_flag` is true, and nothing otherwise. Finally an appropriation tier bonus is added: nothing when `appropriation_requested_cents` is exactly 0; five points when it is at least 1 cent and at most 5,000,000 cents (that is, fifty thousand dollars); and fifteen points when it exceeds 5,000,000 cents. A confidential priority request naming six sections and asking for 12,000,000 cents therefore scores twenty-four for its sections, twelve for confidentiality, eight for priority and fifteen for the top appropriation band, for an `intake_complexity_estimate` of 59.

The sponsoring member may withdraw the request at any point before it is finished, supplying an optional `withdrawal_reason`. Withdrawal is available from `SUBMITTED`, `RESEARCH`, `DRAFTING`, `RETURNED_FOR_CLARIFICATION` and `DRAFT_READY`; attempting it on a request already in `CONVERTED`, `WITHDRAWN` or `LAPSED` is `ERR_INVALID_DRAFTING_REQUEST_STATE`, and only the sponsoring member may do it. Withdrawal is the domain's cleanest **compensating action**, and it has four effects. `sla_due_utc` is cleared to null. When `priority_flag` is true, `priority_slots_used` drops by one, returning the ledger to precisely the value it held before the request was filed. When the prior status was `RETURNED_FOR_CLARIFICATION`, `clarification_pending_count` drops by one and `intake_hold` is recomputed — which can release a member from hold. And when the prior status was `RESEARCH` or `DRAFTING`, the assigned attorney's `active_engagement_count` is recomputed, freeing the occupancy interval described in §3.3.

Conversion, by contrast, refunds nothing. When a `DRAFT_READY` request is introduced as a bill it moves to `CONVERTED`, and a converted priority request keeps consuming its slot for the remainder of the session: the slot is spent on the bill, not merely on the drafting queue.

### 3.3. Assignment, Statutory Research and the Drafter Occupancy Calendar

Assignment is a review-counsel act. Acting as `ReviewCounsel`, a senior attorney names the attorney who will do the work in `drafter_id` and reserves that attorney's working window with `engagement_start_utc` and `engagement_end_utc`, moving the request from `SUBMITTED` to `RESEARCH`. The named attorney must exist, or the request is `ERR_DRAFTER_NOT_FOUND`. On success the request records `assigned_drafter_id`, `engagement_start_utc` and `engagement_end_utc`, and the assigned attorney's `active_engagement_count` is recomputed upward by one because the request has entered that attorney's occupancy set.

Occupancy is the hard constraint here, and it is worth stating exactly. An attorney's **occupancy set** contains two kinds of interval drawn from a single shared pool. Every drafting request assigned to that attorney whose `status` is `RESEARCH` or `DRAFTING` contributes the interval running from its `engagement_start_utc` to its `engagement_end_utc`. Every amendment whose `drafted_by_drafter_id` is that attorney and whose `status` is `DRAFTED` contributes the interval running from its `drafting_start_utc` to its `drafting_due_utc`. Both kinds of interval are **closed at both ends**: two intervals that merely touch, where one ends at the very instant the other begins, do overlap and both count at that instant. A candidate interval is admitted only if, at every instant inside it, the number of existing occupancy intervals containing that instant plus one does not exceed the attorney's `max_concurrent_engagements`; equivalently, the maximum pointwise multiplicity of the existing intervals restricted to the candidate must be strictly below `max_concurrent_engagements`. This is an aggregate capacity rather than a pairwise conflict rule: with a cap of two, a third simultaneously overlapping engagement is the first thing refused, and drafting requests and amendments compete for the same slots. A refusal is `ERR_DRAFTER_ENGAGEMENT_CAPACITY_EXCEEDED`, and the same rule guards both drafter assignment and amendment drafting. The `active_engagement_count` on an attorney is simply the maintained size of that occupancy set. A request releases its interval the moment it leaves `RESEARCH` or `DRAFTING` — `RETURNED_FOR_CLARIFICATION`, `DRAFT_READY`, `CONVERTED`, `WITHDRAWN` and `LAPSED` all free it — and an amendment releases its interval on adoption, rejection or lapse and re-acquires it on rescission.

Statutory research concludes when the assigned attorney reports what the code actually requires. That call carries a single field, `affected_sections_count`, and moves the request from `RESEARCH` to `DRAFTING`; only the attorney named in `assigned_drafter_id` may make it. Alongside the state change, `research_completed_utc` is stamped with the logical clock, `actual_complexity_score` is computed, and `sla_due_utc` is derived from it.

The **actual complexity score** is deliberately not the intake estimate rescaled — it is a structurally different formula, because once research has established the true footprint the size of the appropriation is no longer a proxy for drafting effort. It is the sum of five terms: four points for each section in `affected_sections_count`; three points for each of the request's advisory conflicts as counted by `advisory_conflict_count`; nine points for each of its blocking conflicts as counted by `blocking_conflict_count`; twelve points when `confidentiality` is `CONFIDENTIAL`; and eight points when `priority_flag` is true. There is **no** appropriation tier bonus in this variant at all. Both conflict counters include every statutory conflict recorded against this request in any `resolution_status` — `OPEN`, `RESOLVED` and `WAIVED` all count, because a conflict that was later resolved still consumed drafting effort — and conflicts belonging to other drafting requests never contribute. Continuing the earlier example, if research on that confidential priority request finds nine affected sections, two advisory conflicts and one blocking conflict, the `actual_complexity_score` is thirty-six for sections, six for the advisory findings, nine for the blocking finding, twelve for confidentiality and eight for priority, totalling 71 — against an `intake_complexity_estimate` of 59 for the same row.

The drafting service-level target follows in four pinned steps. First a base window in hours is computed as the complexity score multiplied by six, then clamped into the range from a floor of 24 hours to a ceiling of 240 hours — the clamp is applied here, before any multiplier. Second, if `priority_flag` is true, the window is halved. Third, if the logical clock has reached the instant fourteen days before the session's `introduction_deadline_utc`, or any instant after it, the window is multiplied by three quarters — this is the deadline-pressure compression, and it applies at or after that instant, not only strictly after. Fourth, the resulting number of hours is rounded up to a whole number exactly once, after both multipliers have been applied. Because the clamp precedes the multipliers, a priority request can legitimately end up with a window below the 24-hour floor; that is intended, not a bug. Finally `sla_due_utc` is the earlier of `research_completed_utc` plus that many hours and the session's `introduction_deadline_utc` — the service target never promises a date past the day bills stop being accepted. A score of 71 on a priority request, for instance, produces a base of 426 hours, clamped to the 240-hour ceiling, halved to 120 hours by priority, left unmultiplied when the clock has not yet reached the pressure window, and added to the research completion instant as a flat five days.

`sla_due_utc` exists only while the request is actually being drafted. Every path out of `DRAFTING` clears it to null — the clarification bounce-back, style certification, withdrawal, and the end-of-session lapse alike — and re-entry into `DRAFTING` recomputes it from the clock at that moment.

### 3.4. Conflicts With Existing Code, Clarification Loops and Style Certification

While a request is under research or being drafted, the assigned attorney records each collision with existing code as a **statutory conflict**. The payload names the `drafting_request_id` it belongs to, the `code_citation` of the provision in conflict, a `conflict_type` of `AMENDS_SAME_SECTION`, `REPEALS_ACTIVE`, `DUPLICATE_ENACTMENT` or `STYLE_VIOLATION`, and a `severity` of `BLOCKING` or `ADVISORY`. Only the attorney named in `assigned_drafter_id` may file one, and only while the request's `status` is `RESEARCH` or `DRAFTING`; filing against a request in any other state is `ERR_INVALID_CONFLICT_STATE`. The new finding lands with `resolution_status` `OPEN`, `resolution_note` null and `resolved_utc` null.

Every filing updates the parent request's counters. A `BLOCKING` finding raises both `blocking_conflict_count` and `open_blocking_conflict_count` by one; an `ADVISORY` finding raises `advisory_conflict_count` by one. Beyond that, a `BLOCKING` finding recorded **while the request is already in `DRAFTING`** triggers a three-level cascade that bounces the file back to the sponsor. At the first level the counters move as just described. At the second level, caused by the status leaving `DRAFTING` for `RETURNED_FOR_CLARIFICATION`, three further things happen: `sla_due_utc` is cleared to null, the assigned attorney's `active_engagement_count` is recomputed downward by one as the request leaves the occupancy set, and the sponsoring member's `clarification_pending_count` rises by one. At the third level, caused by that member's `clarification_pending_count` reaching two, the member's `intake_hold` becomes true — which is what blocks their next drafting request with `ERR_MEMBER_INTAKE_HOLD`. The cascade is strictly conditional: an `ADVISORY` finding, or a `BLOCKING` finding recorded while the request is still in `RESEARCH`, updates the counters and stops there, leaving the status, the service target, the occupancy set and the member's counters untouched.

Open findings are cleared one of two ways, and the disposition decides who may act. Resolving a conflict supplies a `resolution_status` of `RESOLVED` together with a `resolution_note`, and the assigned attorney may do it themselves. Waiving a conflict supplies a `resolution_status` of `WAIVED` with the waiver justification in `resolution_note`, and it requires the `ReviewCounsel` role backed by a `Drafter` row whose `is_senior` is true — a junior attorney attempting it is refused with `ERR_SENIOR_COUNSEL_REQUIRED`. Either disposition stamps `resolved_utc` with the logical clock and recomputes the request's `open_blocking_conflict_count`. A conflict already in `RESOLVED` or `WAIVED` cannot be revisited: a second attempt is `ERR_INVALID_CONFLICT_STATE`. Note what a waiver does and does not do — the conflict stays on the record and keeps contributing to `blocking_conflict_count` and therefore to the complexity score; the waiver only stops it from blocking certification.

The sponsoring member answers a bounced file by supplying a `clarification_note`, which returns the request from `RETURNED_FOR_CLARIFICATION` to `DRAFTING`. Three preconditions guard it. The acting member must be the sponsor named in `member_id`. Every blocking finding must be disposed of, so `open_blocking_conflict_count` must be 0 or the call is refused with `ERR_BLOCKING_CONFLICT_UNRESOLVED`. And the attorney's occupancy set must be able to re-admit the stored interval from `engagement_start_utc` to `engagement_end_utc` under the same aggregate rule as the original assignment — if other work has filled the calendar in the meantime, the call is refused with `ERR_DRAFTER_ENGAGEMENT_CAPACITY_EXCEEDED`. On success, `revision_round` rises by one, recording how many clarification loops the file has completed; `actual_complexity_score` is recomputed, and because the conflict counters have grown it necessarily rises; `sla_due_utc` is recomputed from the current logical clock rather than from the original research instant; the attorney's `active_engagement_count` rises by one as the interval is re-acquired; and the member's `clarification_pending_count` falls by one with `intake_hold` recomputed. A single file may loop from `DRAFTING` to `RETURNED_FOR_CLARIFICATION` and back any number of times.

Certification of drafting-style compliance is the last gate before introduction, and it belongs to `ReviewCounsel`. The call carries a single field, `style_findings_count`, which is the number of drafting-style defects the reviewer found; the field is null on a request that has never been reviewed. Three refusals guard the action, and they are evaluated in the ladder order of §2.11. First, the reviewing counsel must not be the attorney who did the work: if `X-User-ID` equals the request's `assigned_drafter_id`, the call is `ERR_SEGREGATION_OF_DUTIES`. Second, `open_blocking_conflict_count` must be 0, or the call is `ERR_BLOCKING_CONFLICT_UNRESOLVED`. Third, `style_findings_count` must be exactly 0; a positive count is refused with `ERR_STYLE_NONCOMPLIANT` — and uniquely among the refusals in this specification, **the reported count is still recorded on the request** even though the state does not advance, so the reviewer's finding is preserved for the next attempt. When all three pass, the request moves from `DRAFTING` to `DRAFT_READY`, `style_findings_count` is stored, `sla_due_utc` is cleared to null, and the attorney's `active_engagement_count` is recomputed downward by one as the request leaves the occupancy set.

### 3.5. Introduction, Chamber Numbering, Companions and Committee Referral

Introduction converts a finished drafting file into a public measure, and only a `Clerk` may do it. The payload names a single field, `drafting_request_id`, and that request must be in `DRAFT_READY`; any other state is `ERR_INVALID_DRAFTING_REQUEST_STATE`. The session must be `CONVENED`, the logical clock must be at or before the session's `introduction_deadline_utc` — a later clock is `ERR_INTRODUCTION_DEADLINE_PASSED` — and the request's `open_blocking_conflict_count`, the number of its `BLOCKING` findings still sitting in `resolution_status` `OPEN`, must be 0, or introduction is refused with `ERR_BLOCKING_CONFLICT_UNRESOLVED` even though style certification already passed.

Numbering is the first thing the new bill receives. Each session holds two independent counters. A `HOUSE` bill takes the current value of `next_house_bill_number`, renders `bill_number` as the two characters `HB`, a single space, and that number in decimal with no zero padding, and then raises `next_house_bill_number` by one. A `SENATE` bill does the same with `next_senate_bill_number` and the prefix `SB`. The counters never interact, so `HB 1` and `SB 1` coexist in one session; a counter is never decremented and never reused, so a bill that later goes `DEAD` does not return its number to the pool, and introduction order within a chamber is therefore always recoverable from `bill_number`. Bills of other sessions never touch a session's counters, and `bill_number` is immutable once minted.

The rest of the new bill is copied rather than supplied. Its `session_id`, `sponsor_member_id`, `chamber`, `appropriation_requested_cents` and `priority_bill` are all taken from the originating drafting request — `priority_bill` mirroring that request's `priority_flag`, and `appropriation_requested_cents` frozen at its introduction value thereafter. `introduced_utc` is stamped with the logical clock. `legislative_status` opens at `INTRODUCED`; `companion_bill_id` is null; `adopted_fiscal_delta_cents`, `adopted_amendment_count` and `referral_count` all start at 0. The second, independent state dimension is decided here too: `fiscal_status` opens at `NOTE_PENDING` when `appropriation_requested_cents` is strictly greater than 0, and at `NOT_REQUIRED` when it is exactly 0. The originating request simultaneously moves from `DRAFT_READY` to `CONVERTED` without refunding its priority slot, and the session's `bills_introduced_count` rises by one.

A bill's two state dimensions advance **independently on the same row**. `legislative_status` runs `INTRODUCED`, `REFERRED`, `REPORTED`, `PASSED_CHAMBER`, `ENROLLED`, `TRANSMITTED`, with `TRANSMITTED` and `DEAD` as its terminal values. `fiscal_status` runs among `NOT_REQUIRED`, `NOTE_PENDING`, `NOTE_STALE` and `NOTE_COMPLETE` and has no terminal value at all — a bill can cycle through the fiscal dimension repeatedly while its legislative dimension stands still, and vice versa. Any write attempted against a bill whose `legislative_status` is `DEAD` or `TRANSMITTED` is `ERR_INVALID_BILL_STATE`.

Companion tracking links a measure to its opposite-chamber twin. A `Clerk` supplies `companion_bill_id`, and the link is written reciprocally: this bill's `companion_bill_id` is set to the named bill and the named bill's `companion_bill_id` is set back to this one, with the `version` of **both** rows rising by one. Four refusals guard the link, each carrying HTTP 422: naming the path bill itself is `ERR_COMPANION_SELF_LINK`; naming a bill in the same `chamber` is `ERR_COMPANION_CHAMBER_INVALID`; naming a bill belonging to a different session is `ERR_COMPANION_SESSION_MISMATCH`; and naming a bill when either side already carries a `companion_bill_id` is `ERR_COMPANION_ALREADY_LINKED`.

Referral sends a bill to committee and simultaneously books that committee's room-time. A `Clerk` supplies the `committee_id` and the exclusive hearing window as `hearing_window_start_utc` and `hearing_window_end_utc`, where the end must be strictly after the start. The bill's `legislative_status` must be `INTRODUCED` or `REFERRED`. The committee must belong to the bill's own session, or the call is `ERR_COMMITTEE_SESSION_MISMATCH`, and to the bill's own `chamber`, or it is `ERR_COMMITTEE_CHAMBER_MISMATCH`. The window must end at or before the session's `committee_report_deadline_utc`, since a window ending after the reporting deadline could never be reported out; a later end is `ERR_HEARING_WINDOW_AFTER_DEADLINE`. The committee's `active_referral_count` must be strictly below its `max_concurrent_referrals`, or the call is `ERR_COMMITTEE_REFERRAL_CAPACITY_EXCEEDED`.

Hearing windows themselves are **half-open**: a window covers its start instant and every instant up to, but not including, its end. A committee hears one bill at a time, so any overlap is a refusal — but the comparison is not made on the raw intervals. Before comparing, a thirty-minute changeover buffer is added to the end of every existing window belonging to the same committee whose referral is still `IN_COMMITTEE`. The candidate conflicts if its start falls strictly before that buffered end **and** the existing window's start falls strictly before the candidate's end. The practical consequence is that a truly back-to-back window is refused even though the raw half-open intervals do not overlap: against an existing window running from 14:00 to 16:00, a candidate starting at 16:00 is refused, while a candidate starting at 16:30 is accepted, because the buffered end boundary is itself exclusive. Any conflict is `ERR_COMMITTEE_HEARING_WINDOW_CONFLICT`. Only `IN_COMMITTEE` referrals occupy a window; a referral in `REPORTED_FAVORABLE`, `REPORTED_UNFAVORABLE` or `DIED_IN_COMMITTEE` frees its window immediately.

A successful referral is created in `status` `IN_COMMITTEE` with `reported_utc` null. Its `referral_order` is a 1-based sequence within the bill, computed as the bill's `referral_count` plus one at creation time. Its `report_deadline_utc` is the earlier of the hearing window's end plus seven days and the session's `committee_report_deadline_utc`. The committee's `active_referral_count` and the bill's `referral_count` each rise by one, and the bill's `version` rises by one. The first referral also advances the bill from `INTRODUCED` to `REFERRED`; subsequent referrals leave it in `REFERRED`, which is how a measure picks up an additional fiscal-committee referral under a constrained session posture.

### 3.6. Committee Action, Reporting and Passage

Reporting a bill out of committee carries one field, `outcome`, valued `FAVORABLE` or `UNFAVORABLE`, and belongs to the `Clerk`. The referral must still be `IN_COMMITTEE`, or the call is `ERR_INVALID_REFERRAL_STATE`, and the logical clock must be at or before that referral's `report_deadline_utc` regardless of outcome, or the call is `ERR_COMMITTEE_REPORT_DEADLINE_PASSED`.

The favourable branch is the gated one. It requires the bill's `fiscal_status` to be `NOT_REQUIRED` or `NOTE_COMPLETE`; a bill sitting at `NOTE_PENDING` or `NOTE_STALE` cannot be reported favourably until a note is certified, and the refusal is `ERR_FISCAL_NOTE_REQUIRED`. It additionally enforces the constrained-posture rule: while the session's `fiscal_posture` is `CONSTRAINED`, a bill carrying a `CERTIFIED` fiscal note whose `certified_total_cents` is strictly greater than 0 may only be reported out by a committee whose `is_fiscal_committee` is true. Stated as the precondition the report action evaluates: the session's posture is `NORMAL`, or the bill has no `CERTIFIED` note with a positive `certified_total_cents`, or the reporting committee is a fiscal committee. A report that satisfies none of those three is refused with `ERR_FISCAL_COMMITTEE_REFERRAL_REQUIRED`. On success the referral moves from `IN_COMMITTEE` to `REPORTED_FAVORABLE`, `reported_utc` is stamped with the logical clock, and the committee's `active_referral_count` drops by one. If — and only if — no referral of that bill remains `IN_COMMITTEE`, the bill advances from `REFERRED` to `REPORTED`; a bill with a second committee still holding it stays in `REFERRED`.

The unfavourable branch is ungated on the fiscal side, because killing a bill never requires the cost to be known: the `ERR_FISCAL_NOTE_REQUIRED` gate does not apply to it. The referral moves from `IN_COMMITTEE` to `REPORTED_UNFAVORABLE`, `reported_utc` is stamped with the logical clock, and the committee's `active_referral_count` drops by one — exactly as in the favourable branch. Then the cascade fires: the bill's `legislative_status` becomes `DEAD` immediately, irrespective of how many other referrals it still has in `IN_COMMITTEE`, and every one of those sibling referrals moves to `DIED_IN_COMMITTEE`, with each affected committee's `active_referral_count` recomputed downward accordingly. The bill's `version` rises by one in either branch.

Passage moves a reported bill through its chamber and takes no input fields at all. The bill's `legislative_status` must be `REPORTED`. Its `fiscal_status` must be `NOT_REQUIRED` or `NOTE_COMPLETE`, or the call is `ERR_FISCAL_NOTE_REQUIRED`. No amendment of the bill may still be sitting in `REQUESTED` or `DRAFTED` — pending amendment work must be adopted, rejected or allowed to lapse first, and a bill with outstanding amendment work is refused with `ERR_INVALID_BILL_STATE`. And the logical clock must be at or before the session's `sine_die_utc`, or the call is `ERR_SINE_DIE_PASSED`. On success the bill moves from `REPORTED` to `PASSED_CHAMBER` and its `version` rises by one.

### 3.7. Fiscal Note Routing, Cost Methodology and Multi-Year Projections

A bill that needs a price gets one from the executive agency that will bear it. Either a `Clerk` or a `FiscalOfficer` routes a **fiscal note request** beneath the bill, supplying the `agency_id` of the affected agency and the `methodology` the agency must use, either `INCREMENTAL_COST` or `FULL_ABSORPTION`. Routing is admitted only while the bill's `fiscal_status` is `NOTE_PENDING` or `NOTE_STALE` — a bill at `NOT_REQUIRED` or `NOTE_COMPLETE` has nothing to price, and the attempt is `ERR_INVALID_BILL_STATE`, as is any routing against a bill whose `legislative_status` has reached `DEAD` or `TRANSMITTED`. The agency's `status` must be `ACTIVE`, or the call is `ERR_AGENCY_INACTIVE`. The agency's `open_request_count` — the number of its notes currently in `ROUTED`, `SUBMITTED` or `RETURNED_FOR_REVISION` — must be strictly below its `max_open_requests`, or the call is `ERR_AGENCY_CAPACITY_EXCEEDED`. And no other note of this same bill may already be in `ROUTED`, `SUBMITTED` or `RETURNED_FOR_REVISION`, or the call is `ERR_FISCAL_NOTE_ALREADY_OPEN`; one open pricing exercise per bill at a time.

A routed note opens in `status` `ROUTED` with `revision_round` at 0, `routed_utc` stamped from the logical clock, `submitted_utc` and `certified_utc` null, `late_submission` false, `reopened_by_amendment_id` null, and every computed money field — `direct_cost_cents`, `contingency_pct`, `contingency_cents`, `certified_total_cents`, `projected_revenue_total_cents`, `high_scenario_total_cents` and `low_scenario_total_cents` — null until the first submission. The agency's `open_request_count` rises by one.

**The due date rewards nobody and accommodates everybody.** Each agency carries a `responsiveness_score` derived from its own history across all of its notes in every session: start at 100, subtract twelve for each entry in `late_submission_count`, subtract five for each entry in `revision_count`, then clamp the result into the range 0 through 100 inclusive. The score selects an extension band on top of the session's `fiscal_note_default_days`: no extra days when the score is 70 or above; five extra days when the score is at least 40 but below 70; ten extra days when the score is below 40. The total grant in whole days is added to `routed_utc` to produce `due_utc`, preserving `routed_utc`'s time-of-day exactly. A struggling agency is deliberately given **more** time, not less — the extension is a workload accommodation — so the band edges at 70 and at 40 are the observable boundaries. An agency with two late submissions and three revisions against a session default of 21 days scores 61, lands in the middle band, and is granted 26 days. `due_utc` is recomputed on every routing of the note, whether that routing is the initial one or the re-opening described in §3.8.

Cost estimate lines are filed by the `AgencyAnalyst` of the routed agency, one line per call, and they are **append-only**: a line is never edited and never deleted. Each line carries `expected_fiscal_note_request_version` (the concurrency guard of §2.6), a `fiscal_year` of at least 2000, a `scenario` of `BASELINE`, `HIGH` or `LOW`, three non-negative money fields — `personnel_cost_cents`, `operating_cost_cents` and `one_time_cost_cents` — a non-negative `fte_count` giving full-time-equivalent staffing, a signed `revenue_impact_cents` for the year, and an `assumption_note` recording the cost estimate methodology assumptions for audit. The line's `revision_round` is copied from the note's current `revision_round` at creation, and `included_in_certification` is set true. That flag has a single meaning throughout: a line's `included_in_certification` is true exactly when its `revision_round` equals its parent note's current `revision_round`. A line duplicating an existing line's combination of `fiscal_year`, `scenario` and `revision_round` on the same note is refused with `ERR_DUPLICATE_COST_ESTIMATE`. Filing a line against a note whose state does not admit it — a `LAPSED` note, for instance — is `ERR_INVALID_FISCAL_NOTE_STATE`. Each accepted line raises the note's `version` by one, which is why an analyst filing several lines in a row must re-read the note between calls to refresh `expected_fiscal_note_request_version`.

Submission is the analyst's handover, and it accepts an optional `submission_note`. It is admitted from `ROUTED` and from `RETURNED_FOR_REVISION`, in both cases evaluated against the note's **current** `revision_round`. At least one cost estimate line of that current round must exist, or the call is `ERR_NO_COST_ESTIMATES`. The `BASELINE` lines of that current round must cover every year listed in the session's `required_fiscal_years`, with no year missing, or the call is `ERR_ESTIMATE_YEARS_INCOMPLETE`. On success the note moves to `SUBMITTED`, `submitted_utc` is stamped with the logical clock, and `late_submission` is set true exactly when `submitted_utc` falls strictly after `due_utc`. When it is late, the agency's `late_submission_count` rises by one and its `responsiveness_score` is recomputed — which lengthens the grant on that agency's next routing. Every submission and resubmission recomputes the cost totals and all three projections from scratch; lines filed under earlier rounds stay on the record with `included_in_certification` false and are excluded from every total.

**The cost total is where the two methodologies diverge, on the very same rows.** In both variants the input set is the note's `BASELINE` lines whose `revision_round` equals the note's current `revision_round`; `HIGH` and `LOW` lines never enter the cost total at all, since they feed only the revenue projections.

Under `INCREMENTAL_COST` the agency asserts that existing staff absorb sub-half-FTE work, so `direct_cost_cents` is the sum over those lines of `operating_cost_cents` plus `one_time_cost_cents` plus — only when that line's `fte_count` is at least 0.5 — `personnel_cost_cents`. A line whose `fte_count` is below 0.5 contributes its operating and one-time costs but not a cent of personnel cost. No indirect overhead is applied at all, because incremental costing charges only marginal spend.

Under `FULL_ABSORPTION` the agency must show fully loaded cost. `personnel_cost_cents` counts on **every** line regardless of `fte_count`, so `direct_cost_cents` is the sum over those lines of `operating_cost_cents` plus `one_time_cost_cents` plus `personnel_cost_cents`, and then an indirect overhead charge is added on top: take the sum of `personnel_cost_cents` over the same lines, multiply by 0.185, round half up to whole cents once, and add that single figure to the subtotal.

Consider two baseline lines of the current round: the first for fiscal year 2027 with 14,000,000 cents of personnel cost, 4,100,000 of operating cost, 3,000,000 of one-time cost and an `fte_count` of 1.0; the second for fiscal year 2028 with 10,400,000 of personnel cost, 3,500,000 of operating cost, no one-time cost and an `fte_count` of 0.4. Under `INCREMENTAL_COST` the second line's personnel cost is excluded because 0.4 is below the half-FTE floor, and no overhead is added, giving a `direct_cost_cents` of 24,600,000. Under `FULL_ABSORPTION` the same two rows give a personnel total of 24,400,000, an indirect overhead of 4,514,000, and a `direct_cost_cents` of 39,514,000 — the same rows, priced almost 15,000,000 cents apart before contingency.

Contingency follows in three pinned steps, and the order removes any apparent circularity. First the tier is selected **from the direct subtotal, never from the running certified total**: `contingency_pct` is 0.05 when `direct_cost_cents` is at most 10,000,000 cents, 0.08 when it is at most 100,000,000 cents, and 0.12 for anything larger — both boundaries inclusive on the lower band, so a direct subtotal of exactly 10,000,000 takes the 0.05 rate. Second, `contingency_cents` is `direct_cost_cents` multiplied by `contingency_pct` and rounded half up to whole cents, once. Third, `certified_total_cents` is `direct_cost_cents` plus `contingency_cents`, with no further rounding. Carrying the two examples forward: the incremental subtotal of 24,600,000 draws the 0.08 rate for a contingency of 1,968,000 and a `certified_total_cents` of 26,568,000, while the full-absorption subtotal of 39,514,000 draws the same rate for a contingency of 3,161,120 and a `certified_total_cents` of 42,675,120. At the low boundary, a direct subtotal of exactly 10,000,000 yields a contingency of 500,000 and a certified total of 10,500,000.

**Revenue is projected, not summed.** Every submission also recomputes three four-year revenue projections. The base year is the earliest year in the session's `required_fiscal_years`. For a given scenario, the seed is the `revenue_impact_cents` of the single cost estimate line of this note whose `scenario` matches, whose `fiscal_year` equals the base year, and whose `revision_round` equals the note's current round. If the agency filed such a line, that value is used verbatim and the scenario multiplier is **not** applied on top of it. If no such line exists for `HIGH`, the seed is the `BASELINE` seed multiplied by 1.15 and rounded half up; if none exists for `LOW`, the seed is the `BASELINE` seed multiplied by 0.85 and rounded half up. `BASELINE` has no fallback — a note cannot be submitted without its baseline base-year line, which is precisely what `ERR_ESTIMATE_YEARS_INCOMPLETE` enforces. Later-year lines carry their own `revenue_impact_cents` for the record but never enter the projection, which is a growth curve off the base year rather than a sum of supplied years.

From a seed the projection runs over four fiscal years at an annual growth rate of 0.0325. **The rounding order is pinned: round each fiscal year to whole cents first, then sum the four rounded years.** For the first year the seed is used as-is; for the second, third and fourth the seed is multiplied by 1.0325 raised to the power one, two and three respectively, and each of those products is rounded half up to whole cents before being added. Summing exact rationals and rounding once at the end produces a different number and is wrong. The three results are stored as `projected_revenue_total_cents` for `BASELINE`, `high_scenario_total_cents` for `HIGH` and `low_scenario_total_cents` for `LOW`. As an illustration, a baseline base-year `revenue_impact_cents` of 3,333,333 yields per-year figures of 3,333,333, 3,441,666, 3,553,520 and 3,669,010 for a `projected_revenue_total_cents` of 13,997,529 — where rounding the exact sum once instead would have produced 13,997,530. With no `HIGH` line supplied, the high seed is 3,833,333 and the per-year figures 3,833,333, 3,957,916, 4,086,549 and 4,219,361 total 16,097,159. With a `LOW` line supplied as 2,000,000, the multiplier is not applied and the per-year figures 2,000,000, 2,065,000, 2,132,113 and 2,201,406 total 8,398,519.

A `FiscalOfficer` who is not satisfied returns the note for revision, supplying a `return_reason`. The note moves from `SUBMITTED` to `RETURNED_FOR_REVISION` and its `revision_round` rises by one, which flips `included_in_certification` to false on every cost estimate line of the prior round and drops them out of every total — the analyst must file a fresh set. The agency's `revision_count` rises by one and its `responsiveness_score` is recomputed. The agency's `open_request_count` is deliberately left unchanged, because the note is still open work on that agency's desk. A note may cycle from `SUBMITTED` to `RETURNED_FOR_REVISION` and back any number of times, and each return bumps the round again.

Certification is the `FiscalOfficer`'s final act on a note and accepts an optional `certification_note`. The note must be `SUBMITTED`. The `BASELINE` lines of the current round must again cover every year in `required_fiscal_years`, or the call is `ERR_ESTIMATE_YEARS_INCOMPLETE`. And the posting must fit under the ceiling: the session's `certified_fiscal_total_cents` plus this note's `certified_total_cents` must be at most the session's `fiscal_cap_cents`, or the call is `ERR_SESSION_FISCAL_CAP_EXCEEDED`. On success the note moves to `CERTIFIED`, `certified_utc` is stamped with the logical clock, the note's `certified_total_cents` is added to the session's `certified_fiscal_total_cents`, the session's `fiscal_posture` is recomputed against `constrained_threshold_cents` with the inclusive boundary of §2.9, the agency's `open_request_count` drops by one, and the bill's `fiscal_status` moves from `NOTE_PENDING` or `NOTE_STALE` to `NOTE_COMPLETE` with `reopened_by_amendment_id` cleared to null. Both the note's `version` and the session's `version` rise by one. Certification is not terminal — §3.8 explains how a note comes back.

### 3.8. Amendments, Rapid Turnaround and the Fiscal Re-Opening Cascade

A legislator requests an amendment against a specific version of a bill's text. The payload carries `expected_bill_version` (the concurrency guard of §2.6), the `bill_id` being amended, a `stage` of `COMMITTEE` or `FLOOR`, a `summary` describing the change, a signed `fiscal_impact_delta_cents` giving the change to the bill's fiscal footprint, and the drafter window the work will need as `drafting_start_utc` and `drafting_due_utc`, where the due instant must be strictly after the start. Two optional references complete it: `committee_referral_id` and `supersedes_amendment_id`. The session must be `CONVENED`.

Stage and referral must agree. A `COMMITTEE`-stage amendment must supply a `committee_referral_id` naming a referral **of this same bill** that is still `IN_COMMITTEE`. A `FLOOR`-stage amendment must supply no `committee_referral_id` at all and requires the bill's `legislative_status` to be `REPORTED`. Any mismatch — committee stage without a live referral of this bill, floor stage carrying a referral reference, or floor stage on a bill that is not `REPORTED` — is `ERR_AMENDMENT_STAGE_MISMATCH`. When `supersedes_amendment_id` is present it must name an amendment of the **same** bill whose `status` is `REJECTED` or `LAPSED`; naming an amendment of another bill, or one in any other status, is `ERR_SUPERSEDE_TARGET_INVALID`.

A new amendment lands in `status` `REQUESTED` with `requested_by_member_id` stamped from `X-User-ID`, `requested_utc` stamped from the logical clock, `drafted_by_drafter_id`, `drafted_utc` and `adopted_utc` all null, and `rescind_count` at 0. The bill's `version` rises by one, because the bill's amendment set has changed — which is exactly what makes any other client's `expected_bill_version` stale.

**Turnaround is rapid by design and compresses near adjournment.** A `COMMITTEE`-stage amendment is allowed a base window of four hours; a `FLOOR`-stage amendment is allowed one hour. If the interval from `requested_utc` to the session's `sine_die_utc` is 48 hours or less, that base window is halved and then floored to whole minutes; otherwise the base window stands unchanged. The result is added to `requested_utc` to give `turnaround_deadline_utc`. A floor amendment requested 32 hours before adjournment therefore gets 30 minutes rather than 60; the same request five days out keeps its full hour.

A `Drafter` drafts the requested amendment by supplying `draft_text`, moving it from `REQUESTED` to `DRAFTED`. The amendment must actually be in `REQUESTED`; drafting one that is already `DRAFTED`, `ADOPTED`, `REJECTED` or `LAPSED` is `ERR_INVALID_AMENDMENT_STATE`, and the same error answers an adopt, reject or rescind call whose amendment is not in the status that operation requires. Beyond the status gate, two further gates apply. The logical clock must be at or before `turnaround_deadline_utc`, or the call is `ERR_AMENDMENT_TURNAROUND_EXPIRED`. And the acting attorney's occupancy set must admit the closed interval from `drafting_start_utc` to `drafting_due_utc` under the aggregate rule of §3.3, or the call is `ERR_DRAFTER_ENGAGEMENT_CAPACITY_EXCEEDED` — amendment work and drafting-request work draw on the same pool of concurrent engagements. On success `drafted_by_drafter_id` is set from `X-User-ID`, `drafted_utc` is stamped from the logical clock, and the attorney's `active_engagement_count` rises by one as the amendment's window enters the occupancy set.

Adoption is a `Clerk` act taking no input fields. The amendment must be `DRAFTED`. A `COMMITTEE`-stage amendment additionally requires the referral it names to still be `IN_COMMITTEE`; a `FLOOR`-stage amendment requires the bill's `legislative_status` to still be `REPORTED`. On success `adopted_utc` is stamped with the logical clock, the bill's `adopted_amendment_count` rises by one, the amendment's `fiscal_impact_delta_cents` is added to the bill's `adopted_fiscal_delta_cents`, and the attorney's `active_engagement_count` drops by one as the amendment leaves the occupancy set. Both the amendment's `version` and the bill's `version` rise by one.

When the adopted amendment's `fiscal_impact_delta_cents` is exactly 0, that is the whole story. When it is non-zero, the bill's fiscal dimension moves, and which way depends on where it stood. A bill at `NOT_REQUIRED` moves to `NOTE_PENDING`: a fiscally material amendment creates a note obligation on a measure that previously had none, and nothing else happens. A bill at `NOTE_COMPLETE` moves to `NOTE_STALE`, and that is the head of a **four-level cascade**:

- **Level 1** sets the bill's `fiscal_status` to `NOTE_STALE`.
- **Level 2**, caused by the fiscal status becoming `NOTE_STALE`, re-opens the pricing exercise. The bill's fiscal note request in `CERTIFIED` moves back to `ROUTED`; its `revision_round` rises by one; `reopened_by_amendment_id` is set to the adopted amendment's identifier; `routed_utc` is re-stamped with the logical clock; `due_utc` is recomputed from the agency's current responsiveness band; and the agency's `open_request_count` rises by one. Crucially the note **retains** its `certified_total_cents` and its `certified_utc` so that a rescission can restore them exactly.
- **Level 3**, caused by the note leaving `CERTIFIED`, subtracts that retained `certified_total_cents` from the session's `certified_fiscal_total_cents`.
- **Level 4**, caused by that ledger change, recomputes the session's `fiscal_posture` against `constrained_threshold_cents` — which can flip a session from `CONSTRAINED` back to `NORMAL` mid-stream.

A bill already at `NOTE_PENDING` or `NOTE_STALE` has no declared transition for a fiscally material adoption, so its `fiscal_status` is left exactly where it is.

Rejection is the mirror of adoption and takes an optional `rejection_reason`. A `DRAFTED` amendment moves to `REJECTED`, the attorney's `active_engagement_count` drops by one as the window is released, and the amendment's `version` rises by one. Rejection touches neither the bill's `adopted_fiscal_delta_cents` nor its `adopted_amendment_count` nor its `fiscal_status` — nothing was ever added, so nothing is taken away.

Rescission unwinds an adoption and requires a `rescission_reason`. The amendment must be `ADOPTED`, and the bill's `legislative_status` must not yet be `ENROLLED`, `TRANSMITTED` or `DEAD`, or the call is `ERR_INVALID_BILL_STATE`. The amendment returns from `ADOPTED` to `DRAFTED`, its `rescind_count` rises by one to record how often this has happened, and `adopted_utc` is cleared to null. The bill's `adopted_amendment_count` drops by one and its `fiscal_impact_delta_cents` is subtracted from the bill's `adopted_fiscal_delta_cents`. The attorney's `active_engagement_count` rises by one again, because a `DRAFTED` amendment re-enters the occupancy set. An amendment may cycle from `ADOPTED` to `DRAFTED` and back as many times as the chamber wants.

**The fiscal restoration on rescission is the compensating action the ledger depends on.** When the bill's `fiscal_status` is `NOTE_STALE`, when a fiscal note request of that bill carries a `reopened_by_amendment_id` equal to the rescinded amendment's identifier, and when after the rescission no remaining `ADOPTED` amendment of the bill has a non-zero `fiscal_impact_delta_cents`, the whole of level 2 through level 4 is undone in reverse: the note moves from `ROUTED` back to `CERTIFIED` with its retained `certified_total_cents` intact, `reopened_by_amendment_id` is cleared to null, the agency's `open_request_count` drops by one, the retained `certified_total_cents` is added back to the session's `certified_fiscal_total_cents`, the session's `fiscal_posture` is recomputed, and the bill's `fiscal_status` returns from `NOTE_STALE` to `NOTE_COMPLETE`. Because the amount added back is the very same retained figure that was subtracted, an adopt-then-rescind round trip must leave `certified_fiscal_total_cents` bit-identical to its pre-adoption value. If another adopted amendment still carries a non-zero delta, none of this restoration fires and the note stays open.

A stale note can also be closed the ordinary way: re-submitting and re-certifying the re-opened note moves the bill's `fiscal_status` from `NOTE_STALE` to `NOTE_COMPLETE`, adds the freshly computed `certified_total_cents` to the session ledger, and clears `reopened_by_amendment_id`. Which of the two routes closes a stale note — rescission or re-certification — is a chamber decision, not a system one.

### 3.9. Enrollment, Technical Correction, Signature Routing and Adjournment

Enrollment freezes a passed bill into its final text. A `Clerk` prepares it with no input fields, and four preconditions apply: the bill's `legislative_status` must be `PASSED_CHAMBER`; its `fiscal_status` must be `NOT_REQUIRED` or `NOTE_COMPLETE`, or the call is `ERR_FISCAL_NOTE_REQUIRED`; when the bill carries a `companion_bill_id`, that companion's own `legislative_status` must already be one of `PASSED_CHAMBER`, `ENROLLED`, `TRANSMITTED` or `DEAD` — a bill may not run ahead of a companion still in committee — and a companion that is not yet that far along makes the call `ERR_INVALID_BILL_STATE`; and no enrolled bill may already exist for this bill, since there is exactly one enrollment per measure, with a second attempt likewise `ERR_INVALID_BILL_STATE`.

Four values are computed at that moment and then **frozen**. The enrollment's `adopted_amendment_count` is the number of the bill's amendments in `status` `ADOPTED`. Its `net_fiscal_delta_cents` is the sum of `fiscal_impact_delta_cents` over those same adopted amendments. Its `enrollment_sequence` is the ordered list of those amendments' identifiers, sorted with all `COMMITTEE`-stage amendments before all `FLOOR`-stage ones — committee work engrosses first — and, within a stage, by `created_at` ascending. That `created_at` ordering is the only tie-break; a row's identifier is never a decision input. Amendments in `REQUESTED`, `DRAFTED`, `REJECTED` or `LAPSED` are excluded from the count, the delta and the sequence alike. And `origin_signature_role` is `SPEAKER` when the bill's `chamber` is `HOUSE` and `SENATE_PRESIDENT` when it is `SENATE` — the presiding officer of the originating chamber, who must sign first — with `expected_next_signature` initialised to that same value. All four are a snapshot: a later rescission of an adopted amendment does not rewrite them.

The new enrollment opens in `status` `PREPARED` with `corrections_applied_count` and `open_corrections_count` at 0 and `origin_signed_utc`, `second_signed_utc` and `transmitted_utc` all null. The bill moves from `PASSED_CHAMBER` to `ENROLLED`, the session's `bills_enrolled_count` rises by one, and the bill's `version` rises by one.

Enrolled text may be corrected, but only in the narrowest sense. Either a `Drafter` or a `ReviewCounsel` proposes a **technical correction** beneath the enrollment, supplying `expected_enrolled_bill_version` (the concurrency guard of §2.6), a `correction_type` of `TYPO`, `CITATION`, `CROSS_REFERENCE` or `NUMBERING`, a `description` of what the correction changes, and an `is_substantive` self-declaration. `is_substantive` must be false: a correction declaring itself substantive is refused outright with `ERR_SUBSTANTIVE_CORRECTION_FORBIDDEN`, because enrolled text may only be corrected non-substantively. The enrollment must be in `PREPARED`, `ORIGIN_SIGNED` or `SECOND_SIGNED`; a correction against a `TRANSMITTED` enrollment is `ERR_INVALID_ENROLLMENT_STATE`. The proposal lands in `status` `PROPOSED` with `proposed_by_drafter_id` stamped from `X-User-ID` and `applied_by_drafter_id` and `applied_utc` null, and it raises the enrollment's `open_corrections_count` by one and its `version` by one.

Applying a correction belongs to `ReviewCounsel`, and the same segregation of duties that governs draft certification governs it here: `X-User-ID` must differ from the correction's `proposed_by_drafter_id`, or the call is `ERR_SEGREGATION_OF_DUTIES`. The correction must be `PROPOSED` — one already `APPLIED` or `REJECTED` yields `ERR_INVALID_CORRECTION_STATE` — and the enrollment must not have reached `TRANSMITTED`. On success the correction moves to `APPLIED` with `applied_by_drafter_id` set from `X-User-ID` and `applied_utc` stamped from the logical clock, the enrollment's `corrections_applied_count` rises by one, its `open_corrections_count` drops by one, and its `version` rises by one.

Signature routing is a strict three-step chain driven by a `Clerk`, one step per call, each call carrying a single `signature_role`. The supplied `signature_role` must equal the enrollment's current `expected_next_signature`, or the call is `ERR_SIGNATURE_OUT_OF_ORDER`. From `PREPARED`, presenting the origin chamber's presiding officer moves the enrollment to `ORIGIN_SIGNED`, stamps `origin_signed_utc` from the logical clock, and advances `expected_next_signature` to the other presiding officer — `SENATE_PRESIDENT` for a house bill, `SPEAKER` for a senate bill. From `ORIGIN_SIGNED`, presenting that second officer moves the enrollment to `SECOND_SIGNED`, stamps `second_signed_utc`, and advances `expected_next_signature` to `GOVERNOR_TRANSMITTAL`. From `SECOND_SIGNED`, presenting `GOVERNOR_TRANSMITTAL` moves the enrollment to `TRANSMITTED`, stamps `transmitted_utc`, sets `expected_next_signature` to `NONE`, and carries the bill from `ENROLLED` to `TRANSMITTED`. That final step has one extra gate: transmittal is refused while `open_corrections_count` is greater than 0, with `ERR_UNAPPLIED_CORRECTIONS` — a bill may not go to the governor with a proposed correction still hanging. Every signature step raises the enrollment's `version` by one.

Adjournment closes the session and is the widest fan-out in the system. A `Clerk` adjourns a `CONVENED` session — adjourning one that is not `CONVENED` is `ERR_INVALID_SESSION_STATE`, and a second adjournment of an already-`ADJOURNED` session is `ERR_SESSION_ADJOURNED`. The session's `status` becomes `ADJOURNED` and `adjourned_utc` is stamped from the logical clock. Every target below is reached **directly** from the adjourn action rather than by a chain of triggers:

- Every drafting request of this session in `SUBMITTED`, `RESEARCH`, `DRAFTING`, `RETURNED_FOR_CLARIFICATION` or `DRAFT_READY` moves to `LAPSED` with `sla_due_utc` cleared to null. For each such request the same counter recomputations as a withdrawal are applied, including release of the priority slot: the sponsoring member's `priority_slots_used`, `clarification_pending_count` and `intake_hold` are recomputed — `LAPSED` rows leave the slot ledger — and the assigned attorney's `active_engagement_count` is recomputed.
- Every amendment on a bill of this session in `REQUESTED` or `DRAFTED` moves to `LAPSED`, and the attorney's `active_engagement_count` is recomputed afterwards for any that had been `DRAFTED`.
- Every committee referral on a bill of this session still `IN_COMMITTEE` moves to `DIED_IN_COMMITTEE`, and each affected committee's `active_referral_count` is recomputed.
- Every fiscal note request on a bill of this session in `ROUTED`, `SUBMITTED` or `RETURNED_FOR_REVISION` moves to `LAPSED`, and each affected agency's `open_request_count` is recomputed downward.
- Every technical correction on an enrollment of this session still `PROPOSED` moves to `REJECTED`, and each affected enrollment's `open_corrections_count` is recomputed downward.
- Every bill of this session whose `legislative_status` is `INTRODUCED`, `REFERRED`, `REPORTED` or `PASSED_CHAMBER` moves to `DEAD`, and its `fiscal_status` is left exactly as it was. Bills already `ENROLLED` or `TRANSMITTED` are untouched.
- The session's `certified_fiscal_total_cents` and `fiscal_posture` are **not** changed: certified notes survive adjournment, and the ledger is a historical record rather than a work queue.

The session's `version` rises by one on both convening and adjournment.

Status reporting rides on the read endpoints rather than on a separate reporting surface. Reading a session exposes its live ledger, its `fiscal_posture`, both numbering counters and both bill counts. The bill collection is the bill status report: filtering it by `session_id`, `legislative_status`, `fiscal_status`, `chamber`, `sponsor_member_id`, `drafting_request_id`, `companion_bill_id` or `priority_bill` answers the questions a session desk actually asks, and because the two state dimensions are separate fields a caller can isolate, for example, every reported bill whose note has gone stale. The cost estimate list of a note deliberately includes superseded lines with `included_in_certification` false, so the audit trail of a revised note stays visible, and the fiscal note collection can be filtered by `reopened_by_amendment_id` to find exactly which measures an amendment destabilised.

Every other operation, including every state transition on an existing resource and the administrative clock advance, returns `200 OK`. All reads return `200 OK`.
