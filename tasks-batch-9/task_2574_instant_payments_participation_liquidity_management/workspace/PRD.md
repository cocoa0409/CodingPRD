# Instant Payments Participation & Liquidity Management API — Product Requirements Document

## 1. Introduction

Instant payments settle in seconds and, once accepted by the rail, cannot be unwound. That single property reshapes every operational control a participating bank needs: money leaves a prefunded position immediately, limits must be enforced *before* the message goes out rather than reconciled the next morning, and every remedy for a mistaken payment has to be a new payment rather than a reversal. This document specifies the service that a rail operator and its participating banks use to manage that reality end to end — enrolling and certifying participants, choosing and policing a participation model, monitoring prefunded liquidity around the clock, screening originations for fraud, negotiating requests for payment, handling return exceptions, assessing access fees at cutoff, reconciling against core deposit systems, and keeping payment obligations alive when the instant rail itself goes dark.

Three pressures shape the design. First, **liquidity is finite and shared**: a single prefunded position funds every outbound transfer a bank sends, so the service must know at all times how much of that position is already committed to in-flight traffic and must refuse a send that would breach the regulatory floor. Second, **authority is deliberately split**: the bank's own administrator configures limits and customers, a treasury officer funds the position and answers alerts, payment operations staff originate traffic, fraud analysts adjudicate holds they did not themselves create, the rail operator drives clearing and settlement, and the core deposit platform submits an independent view for reconciliation. No single actor can both create exposure and bless it. Third, **time is a first-class input**: response obligations, return windows, velocity windows, queue time-to-live, stabilization buffers and business dates all read from one server-controlled logical clock, so that operational behaviour is reproducible rather than dependent on wall-clock drift.

The API is a flat collection model: participants, position accounts, ledger entries, alerts, segment policies, customer accounts, credit transfers, requests for payment, fraud reviews, return requests, settlement cycles, reconciliation runs and outage events are each addressed as top-level resources joined by explicit references, and are mounted directly at the service root with no additional URL prefix. Sub-resource read paths exist purely as discovery channels for records the system creates as a side effect of some other operation.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting user or system, and `X-User-Role`, naming that user's role. If either header is missing or empty, or if `X-User-Role` does not name one of the six roles defined below, the request fails with `ERR_UNAUTHENTICATED` (HTTP 401). When both headers are well formed but the named role is not authorized for the operation being invoked, the request fails with `ERR_FORBIDDEN_ROLE` (HTTP 403). The six roles are `NetworkOperator`, `ParticipantAdmin`, `LiquidityOfficer`, `PaymentOperator`, `FraudReviewer` and `CoreBankingSystem`.

A `NetworkOperator` is the rail operator itself: it enrols and certifies participants, opens and cuts off settlement cycles, drives rail acceptance and settlement, delivers requests for payment, adjudicates return requests, declares and resolves outages, and drives the logical clock and the housekeeping sweep. When `X-User-Role` is `NetworkOperator`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it in audit-style fields but never compares it to any entity's `id`.

A `ParticipantAdmin` is a participating bank's own administrator. When `X-User-Role` is `ParticipantAdmin`, `X-User-ID` is the `id` of the acting `Participant`; ownership checks on any resource that references a `Participant` compare the resource's participant reference to `X-User-ID`. A `ParticipantAdmin` may only read or write resources whose owning participant equals its own `X-User-ID`, whether that participant is resolved from the path, from a `participant_id` in the body, or transitively through a referenced position account, customer account or credit transfer; a mismatch is rejected with `ERR_PARTICIPANT_SCOPE_VIOLATION` (HTTP 403).

The remaining four roles are all opaque identities. When `X-User-Role` is `LiquidityOfficer`, `X-User-ID` is an opaque treasury-operator identifier not tied to any persisted entity; the server records it as `acknowledged_by_user_id` on a `LiquidityAlert` when that officer acknowledges the alert, but never compares it to any entity's `id`. When `X-User-Role` is `PaymentOperator`, `X-User-ID` is an opaque payment-operations identifier; the server records it as `initiated_by_user_id` on every `CreditTransfer` that operator originates, and that stored value later feeds the segregation-of-duties test on fraud review, but it is never compared to an entity `id`. When `X-User-Role` is `FraudReviewer`, `X-User-ID` is an opaque analyst identifier; the server records it as `assigned_reviewer_user_id` on the `FraudReview` the analyst takes, and compares it only against other opaque user identifiers, never against an entity `id`. When `X-User-Role` is `CoreBankingSystem`, `X-User-ID` is an opaque platform identifier not tied to any persisted entity and not compared to any entity's `id`.

Two further identity comparisons are enforced as business rules rather than as ordinary authorization. On fraud review, the acting `X-User-ID` must differ from the reviewed transfer's `initiated_by_user_id` when the review is taken and when it is decided, and on the decision it must additionally equal the review's `assigned_reviewer_user_id`; any breach is rejected with `ERR_FRAUD_SEGREGATION_OF_DUTIES` (HTTP 403). On liquidity remediation, the `X-User-ID` acknowledging an alert must differ from the `X-User-ID` that posted the ledger adjustment which raised that alert, otherwise the acknowledgement is refused with `ERR_ALERT_SEGREGATION_OF_DUTIES` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters, `limit` and `offset`. `limit` defaults to 10, may not be smaller than 1, and may not be larger than 100; `offset` defaults to 0 and may not be negative. Unless a specific endpoint's description states another ordering, list results are sorted by `created_at` in ascending order. List responses populate `limit`, `offset`, `total_count` and `has_more` inside `meta`, where `total_count` counts every record matching the filters before pagination is applied and `has_more` indicates whether records remain beyond the current page.

### 2.4. Resource Identity, Timestamps and Record Versions

Every resource carries an `id` that the server mints as a UUID, with no type prefix or other decoration, and a `created_at` timestamp recorded as an ISO 8601 UTC instant with three fractional digits. Most resources additionally carry an `updated_at` timestamp in the same format and an integer `version` that starts at 1 when the record is created and increases by exactly 1 on every mutation of that record; whenever a rule below says a record's version is incremented, its `updated_at` is refreshed in the same step.

One entity is deliberately different. A `LiquidityLedgerEntry` is an append-only, immutable accounting fact: it carries only `id` and `created_at`. It has no `updated_at` and no `version`, because nothing ever modifies a posted entry. Every other entity — `Participant`, `PrefundedPositionAccount`, `LiquidityAlert`, `CustomerSegmentPolicy`, `CustomerAccount`, `CreditTransfer`, `RequestForPayment`, `FraudReview`, `ReturnRequest`, `SettlementCycle`, `ReconciliationRun` and `OutageEvent` — carries the full set of `id`, `created_at`, `updated_at` and `version`.

### 2.5. The Logical Rail Clock and Business Dates

All temporal reasoning in this service reads a single server-held logical UTC clock rather than wall-clock time. Before any caller sets it, the clock reads exactly `2026-08-01T00:00:00Z`, and it must never fall back to the host's real time. A `NetworkOperator` may move the clock by supplying a `current_utc` instant; the clock is monotonic, so a target instant strictly earlier than the currently stored instant is rejected with `ERR_CLOCK_NOT_MONOTONIC` (HTTP 422), while a target equal to the current instant is accepted and leaves the clock where it is. Setting the clock mutates no entity and performs no sweep — expiry and escalation only happen when the housekeeping sweep is explicitly run.

Wherever a rule speaks of a *business date*, it means the UTC calendar date (`YYYY-MM-DD`) of the logical clock at the moment the rule runs. This is the date stamped on a ledger entry's `business_date`, on a transfer's `settlement_business_date`, and on a participant's `go_live_business_date`, and it is the date a `SettlementCycle` covers.

Time windows in this specification are of three shapes, and the shape matters. A **half-open** window includes its start instant and excludes its end instant: segment-policy effective windows, velocity windows, the twenty-four-hour liquidity projection horizon, the return-request eligibility window and the outage stabilization reservation are all half-open. A **closed** interval includes both endpoints: an outage event's declared interval from `started_at` to `ended_at` is closed, which is why two touching outage intervals conflict. A **deadline** comparison is inclusive of the deadline itself: whenever a rule says an operation is refused once the clock has reached a deadline, an attempt at exactly that instant is already too late.

### 2.6. Stale-View Protection on Liquidity and Policy Writes

Two write operations require the caller to prove it is reasoning about current data by pinning the version of a parent record it read beforehand.

Originating a credit transfer requires the non-optional field `expected_position_account_version`, carrying the client's last observed `version` of the originating participant's `PrefundedPositionAccount`. Every accepted transfer origination, funding adjustment, withdrawal, settlement debit, fee debit and return credit increments that account's `version`, so a caller holding an older value is reasoning about liquidity headroom that no longer exists. If the supplied value does not equal the account's current `version`, the origination is rejected with `ERR_STALE_POSITION_VERSION` (HTTP 412) — including the case where the transfer would comfortably fit under fresh liquidity, because admitting it on a stale view is exactly what this control forbids. Reading the position account immediately before the write is how a caller obtains a fresh value.

Publishing a segment policy requires the non-optional field `expected_participant_version`, carrying the client's last observed `version` of the `Participant` the policy is scoped to. A publication may legitimately close the participant's existing open-ended window for that segment, so two publications can each be individually valid; the version pin is what stops a writer from superseding a policy set it never observed. A mismatch with the participant's current `version` is rejected with `ERR_STALE_PARTICIPANT_VERSION` (HTTP 412). Because a successful publication itself increments `Participant.version`, a caller publishing two policies in a row must re-read the participant between them.

No other operation takes a version field. In particular, acceptance, settlement, diversion, fraud decisions, alert acknowledgement, return honouring, cutoff, closure and reconciliation runs accept no expected-version input at all.

### 2.7. Cents, Rounding and Boundary Conventions

Every monetary quantity in this service is an integer number of cents. Balances, reservations, limits, thresholds, fees and variances are never fractional, and no monetary value is ever rounded when it is merely summed — the ledger identity, the reservation total, the daily usage totals and the reconciliation variance are all exact integer arithmetic on integer inputs.

Rounding appears in exactly three places, and each has a pinned method. The fraud score multiplies an integer subtotal by a segment multiplier and rounds the product **half up** to a whole number before applying its ceiling. The intraday liquidity access fee rounds **half up** to whole cents once per settled transfer, before those per-transfer figures are summed. The fee rebate takes the **floor** of a fraction of the gross fee. Nothing else rounds.

Comparison boundaries are stated explicitly wherever a rule is defined, and the reader should assume nothing by default. As a convenience summary of the tightest cases: a transfer amount exactly equal to a per-transaction limit is admitted; a send that lands available liquidity exactly on the regulatory floor is admitted; a balance exactly equal to the critical threshold is a `RED` band rather than `AMBER`; a balance exactly equal to the floor is also `RED`, because only a balance strictly below the floor is a `BREACH`; a reconciliation variance whose magnitude is exactly the tolerance is `BALANCED`; and an operation attempted at exactly a deadline or expiry instant is late.

### 2.8. The Prefunded Position Ledger Identity

A participant's funded position is never stored as a mutable number that operations increment and decrement by hand. It is always **derived**, and the derivation is the accounting identity of this system: `current_balance_cents` equals the account's `opening_balance_cents` plus the sum of the `amount_cents` of every `LiquidityLedgerEntry` whose `account_id` is this account. There is no status filter and no time window on that sum — entries are append-only and immutable, so the identity holds over all time. The opening deposit is *not* itself a ledger entry; it is the immutable baseline the entries move away from.

Ledger entries are signed, and the sign is derived from `entry_type` rather than supplied by the caller: a `FUNDING_CREDIT` and a `RETURN_CREDIT` carry a positive `amount_cents`, while a `WITHDRAWAL_DEBIT`, a `TRANSFER_DEBIT` and a `FEE_DEBIT` carry a negative `amount_cents`. Each entry records the `balance_after_cents` that the account showed immediately after it was posted, the `business_date` of the logical clock at posting time, and a `sequence_no` that is a per-account ordinal beginning at 1 and increasing by one for each entry, so ties cannot occur by construction. The account tracks the highest ordinal issued in `last_ledger_sequence_no`, which advances with each posting. An entry created by a transfer settlement or by a honoured return points at that transfer through `related_transfer_id`; funding, withdrawal and fee entries leave `related_transfer_id` null. An operator may attach a free-text `reference` to a funding or withdrawal movement.

The second half of the identity is the reservation. `reserved_cents` is the sum of `amount_cents` over the participant's `CreditTransfer` rows whose `direction` is `OUTBOUND` and whose `clearing_status` is one of exactly three reserving states: `INITIATED`, `FRAUD_HOLD` or `ACCEPTED`. Rows in `QUEUED_THROTTLED`, `SETTLED`, `REJECTED`, `DIVERTED` or `EXPIRED` are outside that set. Two consequences follow and are relied on throughout this document: parking a transfer releases its reservation, so `reserved_cents` falls and `available_cents` rises without any money moving; and settling a transfer moves the amount out of `reserved_cents` and into a `TRANSFER_DEBIT` ledger entry of the same magnitude, so `available_cents` is unchanged by settlement even though `current_balance_cents` drops. Finally, `available_cents` is `current_balance_cents` minus `reserved_cents`, and it is the quantity every send-eligibility test is measured against. Both sums are insensitive to evaluation order, so no tie-break is needed.

### 2.9. Liquidity Bands, the Derived Operational Posture, and Queue Release

Immediately after every ledger posting — funding, withdrawal, settlement debit, fee debit or return credit — the account's band is recomputed and written to `alert_tier`. The band is evaluated on `current_balance_cents`, the funded position, and never on `available_cents`: reserving or releasing a transfer must not move the band, only real money movement does. If the balance is strictly below `floor_cents` the tier is `BREACH`; otherwise, if it is at or below `critical_threshold_cents` the tier is `RED`; otherwise, if it is at or below `warning_threshold_cents` the tier is `AMBER`; otherwise the tier is `GREEN`.

Band changes emit and retire alerts. When the recomputed tier is not `GREEN`, and the account does not already have a `LiquidityAlert` whose `tier` equals the recomputed tier and whose `status` is `OPEN`, `ACKNOWLEDGED` or `ESCALATED`, one alert row is opened with `status` `OPEN`, its `tier` set to the recomputed tier, its `observed_balance_cents` set to the `current_balance_cents` just computed, and its `threshold_cents` set to the constant that was crossed — `warning_threshold_cents` for an `AMBER` alert, `critical_threshold_cents` for a `RED` alert, and `floor_cents` for a `BREACH` alert. When the recomputed tier is `GREEN`, every alert of that account whose `status` is `OPEN`, `ACKNOWLEDGED` or `ESCALATED` becomes `CLEARED` with `cleared_at` stamped at the logical clock.

At the end of any request that changes a participant's `enrollment_status`, changes its account's `alert_tier`, or changes any outage event's `status`, the participant's `operational_posture` is re-derived. The derivation is a strict precedence, evaluated top to bottom, where `OFFLINE` outranks `SEND_FROZEN`, which outranks `THROTTLED`, which outranks `NORMAL`. If any `OutageEvent` with `status` `DECLARED` covers this participant — meaning an event whose `scope` is `NETWORK_WIDE`, or one whose `scope` is `PARTICIPANT` and whose `participant_id` is this participant — the posture is `OFFLINE`. Otherwise, if the participant's `enrollment_status` is `SUSPENDED` or `WITHDRAWN`, the posture is `SEND_FROZEN`. Otherwise, if the participant has no prefunded position account at all, the posture is `NORMAL`. Otherwise, if the account's `alert_tier` is `RED` or `BREACH`, the posture is `SEND_FROZEN`. Otherwise, if the account's `alert_tier` is `AMBER`, the posture is `THROTTLED`. In all remaining cases the posture is `NORMAL`. Because the posture is derived, no endpoint targets it directly; it changes only as a consequence of some other mutation, and each such change increments the participant's `version`.

Re-derivation then propagates in a pinned two-step order. **First**, if the new posture is `SEND_FROZEN` or `OFFLINE`, every `CreditTransfer` of that participant whose `clearing_status` is `INITIATED` becomes `QUEUED_THROTTLED` with `queued_at` stamped, taken in ascending `created_at` order, which removes each of them from the reservation input set. **Second**, if the new posture is `NORMAL` or `THROTTLED` and the previous posture was `SEND_FROZEN` or `OFFLINE`, the queue release pass runs. The order matters: freezing releases reservations before any release pass could consume them.

The **queue release pass** is a strict waterfall over the participant's `QUEUED_THROTTLED` transfers. Candidates are ordered by an obligation priority first and by age second: a transfer that carries an `rfp_id` ranks ahead of one that does not, because it discharges an accepted request for payment, and within the same rank the older `created_at` goes first; the record `id` is never used as a tie-break. The pass starts from a running availability figure equal to the account's `current_balance_cents` minus its `reserved_cents` at the start of the pass — a figure that by definition excludes the queued candidates. Each candidate in turn is admitted only if the running availability minus that transfer's `amount_cents` is greater than or equal to `floor_cents`; on admission the transfer returns to `INITIATED`, its `queued_at` is cleared, its amount re-enters the reservation set, and the running availability is reduced by that amount. At the first candidate that does not fit, the pass **stops**. It does not skip that candidate in order to release a smaller, later one — a skip-and-continue reading releases a different set of transfers and is explicitly not the rule. Because the fit test is an at-least comparison, a release that lands availability exactly on `floor_cents` is admitted. An empty candidate set is a no-op, never an error.

### 2.10. Path Resolution and Reference Checking

Path parameters are resolved strictly left to right, and each segment must resolve before the next is considered, so a request naming a participant that does not exist is answered `ERR_PARTICIPANT_NOT_FOUND` (HTTP 404) regardless of whether the sub-resource named further right would have existed. Each addressable collection has its own not-found code: `ERR_POSITION_ACCOUNT_NOT_FOUND`, `ERR_LIQUIDITY_ALERT_NOT_FOUND`, `ERR_CUSTOMER_ACCOUNT_NOT_FOUND`, `ERR_CREDIT_TRANSFER_NOT_FOUND`, `ERR_RFP_NOT_FOUND`, `ERR_FRAUD_REVIEW_NOT_FOUND`, `ERR_RETURN_REQUEST_NOT_FOUND`, `ERR_SETTLEMENT_CYCLE_NOT_FOUND`, `ERR_RECONCILIATION_RUN_NOT_FOUND` and `ERR_OUTAGE_EVENT_NOT_FOUND`, each answered with HTTP 404.

References carried in a request body are checked after every path identifier has resolved, and they use the same codes as the paths they mirror. A `participant_id` in a body, and equally an `originator_participant_id`, a `requestor_participant_id` or a `requested_by_participant_id`, must resolve to an existing participant or the request fails with `ERR_PARTICIPANT_NOT_FOUND`. A `customer_account_id` or `debtor_customer_account_id` must resolve to an existing customer account or the request fails with `ERR_CUSTOMER_ACCOUNT_NOT_FOUND`. A `settlement_cycle_id` must resolve to an existing settlement cycle or the request fails with `ERR_SETTLEMENT_CYCLE_NOT_FOUND`. A `credit_transfer_id` must resolve to an existing transfer or the request fails with `ERR_CREDIT_TRANSFER_NOT_FOUND`. An `rfp_id` is optional, but when it is supplied and non-null it must resolve to an existing request for payment or the request fails with `ERR_RFP_NOT_FOUND`.

Sub-resource read paths are reverse-reachability channels only. Nothing is ever written through them, and they are the sole discovery route for records that other operations create as a side effect: the fraud review raised by an origination cascade, the ledger entries generated by a settlement or a honoured return, the alerts raised on an account, and the outage events scoped to a participant.

### 2.11. The Order in Which a Request Is Rejected

When a single request violates more than one rule, the caller must receive a predictable answer, so the checks form one global ladder and the **first** violated rung determines the response. The ladder is not a set of independent checks in arbitrary order; the relative order below is normative, and later sections describe each rung's condition in the context of the workflow it guards.

1. **Authentication.** Both headers present, non-empty, and naming a declared role — otherwise `ERR_UNAUTHENTICATED`. Applies to every endpoint.
2. **Role authorization.** The caller's role appears in the invoked operation's authorized-role list — otherwise `ERR_FORBIDDEN_ROLE`. Applies to every endpoint.
3. **Participant ownership scope.** Applies to every operation whose authorized roles include `ParticipantAdmin`; a scope breach yields `ERR_PARTICIPANT_SCOPE_VIOLATION`.
4. **Path identifier existence**, resolved left to right, then **body reference existence** — the not-found codes enumerated in §2.10.
5. **Payload shape.** Required inputs present, enum values inside their declared sets, JSON types correct, and every `*_cents` input that must be positive actually a positive integer — all of these yield `ERR_INVALID_REQUEST` (HTTP 400). Then the two structural well-formedness checks: position-account threshold ordering, yielding `ERR_INVALID_THRESHOLD_ORDERING`, and interval well-formedness, yielding `ERR_INVALID_INTERVAL`.
6. **Optimistic concurrency.** `expected_position_account_version` on origination, yielding `ERR_STALE_POSITION_VERSION`; `expected_participant_version` on segment-policy publication, yielding `ERR_STALE_PARTICIPANT_VERSION`. These are checked before any state, compliance, limit or liquidity rule, so a caller with a stale view is told its view is stale rather than being told about a downstream condition it cannot yet see.
7. **State preconditions**, in this internal order: participant not live (`ERR_PARTICIPANT_NOT_LIVE`), participant offline (`ERR_PARTICIPANT_OFFLINE`), participant send-frozen (`ERR_PARTICIPANT_SEND_FROZEN`), undeclared transition for the entity's current state (`ERR_INVALID_STATE_TRANSITION`), fraud review not yet assigned (`ERR_FRAUD_REVIEW_NOT_ASSIGNED`), transfer not settled (`ERR_TRANSFER_NOT_SETTLED`), transfer already irrevocable (`ERR_TRANSFER_IRREVOCABLE`), alert not acknowledgeable (`ERR_ALERT_NOT_ACKNOWLEDGEABLE`), settlement cycle not open (`ERR_CYCLE_NOT_OPEN`) and cycle not reconcilable (`ERR_CYCLE_NOT_RECONCILABLE`).
8. **Compliance and safety**, in this internal order: participation model forbids sending (`ERR_SEND_NOT_PERMITTED_FOR_MODEL`), participation model forbids requesting (`ERR_REQUEST_NOT_PERMITTED_FOR_MODEL`), customer account restricted (`ERR_CUSTOMER_ACCOUNT_RESTRICTED`), fraud segregation of duties (`ERR_FRAUD_SEGREGATION_OF_DUTIES`), alert segregation of duties (`ERR_ALERT_SEGREGATION_OF_DUTIES`) and activation prerequisites (`ERR_ACTIVATION_PREREQUISITES_NOT_MET`).
9. **Referential coherence**, in this internal order: customer account belongs to another participant (`ERR_CUSTOMER_ACCOUNT_PARTICIPANT_MISMATCH`), no governing segment policy (`ERR_NO_GOVERNING_SEGMENT_POLICY`), request-for-payment fulfilment mismatch (`ERR_RFP_FULFILMENT_MISMATCH`), return requested by the wrong side (`ERR_RETURN_REQUESTOR_NOT_RECEIVER`), invalid return amount (`ERR_RETURN_AMOUNT_INVALID`) and, for a reconciliation run, a participant with no prefunded position account (`ERR_POSITION_ACCOUNT_NOT_FOUND`).
10. **Temporal windows**, in this internal order: clock monotonicity (`ERR_CLOCK_NOT_MONOTONIC`), return-request window elapsed (`ERR_RETURN_WINDOW_EXPIRED`), segment-policy window overlap (`ERR_POLICY_WINDOW_OVERLAP`), outage window conflict (`ERR_OUTAGE_WINDOW_CONFLICT`), request-for-payment closing instant reached (`ERR_RFP_EXPIRED`), return response deadline reached (`ERR_RETURN_RESPONSE_DEADLINE_PASSED`) and business date not yet reached (`ERR_BUSINESS_DATE_NOT_REACHED`).
11. **Uniqueness and capability limits**, in this internal order: duplicate routing number (`ERR_DUPLICATE_ROUTING_NUMBER`), duplicate resource (`ERR_DUPLICATE_RESOURCE`), duplicate settlement cycle (`ERR_DUPLICATE_SETTLEMENT_CYCLE`), duplicate return request (`ERR_DUPLICATE_RETURN_REQUEST`), per-transaction limit (`ERR_PER_TRANSACTION_LIMIT_EXCEEDED`), throttled cap (`ERR_THROTTLED_CAP_EXCEEDED`), velocity limit (`ERR_VELOCITY_LIMIT_EXCEEDED`), daily aggregate limit (`ERR_DAILY_LIMIT_EXCEEDED`) and amendment rounds exhausted (`ERR_AMENDMENT_ROUNDS_EXHAUSTED`).
12. **Fiscal capacity, checked last**, in this internal order: opening prefund below the network minimum (`ERR_PREFUND_BELOW_MINIMUM`), a ledger adjustment that would drive the balance negative (`ERR_LEDGER_ADJUSTMENT_WOULD_GO_NEGATIVE`), insufficient liquidity for a send (`ERR_INSUFFICIENT_LIQUIDITY`) and an unresolved reconciliation variance at cycle closure (`ERR_VARIANCE_UNRESOLVED`).

Two consequences of this ordering are important enough to state on their own, because they are the cases operators most often misread. A send-side freeze is a *posture* condition on rung 7, so it outranks every liquidity, limit and velocity check on rungs 11 and 12: a frozen participant is told it is frozen, never that it lacks funds. Likewise, the participation-model capability check is a *network compliance* rule on rung 8, so it outranks the per-transaction, velocity and daily limit checks: a receive-only participant is told its model forbids sending, never that it exceeded a limit.

## 3. Business Logic & Workflows

### 3.1. Onboarding a Bank: Enrollment, Certification and Go-Live

Enrolment begins with the rail operator recording the institution: its `legal_name`, its `routing_number` — exactly nine digits, and unique across every enrolled participant, so a second enrolment claiming a routing number already held is refused with `ERR_DUPLICATE_ROUTING_NUMBER` — and the `settlement_agent_reference` naming the settlement agent that will hold its prefunded position. The requested `participation_model` may be supplied at enrolment and, when omitted, defaults to `RECEIVE_ONLY`; the three tiers are `SEND_AND_RECEIVE`, `RECEIVE_ONLY` and `RECEIVE_AND_REQUEST_FOR_PAYMENT`. A newly enrolled participant lands in `DRAFT` `enrollment_status` with `operational_posture` `NORMAL` and `certification_round` 0.

While the bank is still being onboarded, its own administrator may change the requested tier by supplying a replacement `participation_model`. That is permitted only while `enrollment_status` is `DRAFT`, `ATTESTATION_PENDING` or `REMEDIATION`; from any other status the change is refused with `ERR_INVALID_STATE_TRANSITION`, and a bank that is already `LIVE` must withdraw and re-enrol to change tier. A successful change replaces the stored value and increments the participant's `version`.

The first lifecycle hop is the administrator's operational-readiness attestation, which moves `DRAFT` to `ATTESTATION_PENDING`. The payload records the `attestation_document_reference` and must carry `operational_readiness_confirmed` set to true; an attestation that presents the flag as false does not confirm readiness, is rejected with `ERR_ATTESTATION_INCOMPLETE`, and leaves the participant in `DRAFT`. A successful attestation stores the document reference, increments `version` and refreshes `updated_at`.

Certification is a cycle rather than a single step. The rail operator opens a testing window against a named `certification_test_suite_version`, which moves the participant from either `ATTESTATION_PENDING` or `REMEDIATION` into `CERTIFICATION_TESTING`, stores that suite version, and increments `certification_round` by one — so the round counter records how many windows have ever been opened. Recording the window's `outcome` is only permitted while the participant sits in `CERTIFICATION_TESTING`: an outcome of `PASS` advances `CERTIFICATION_TESTING → CERTIFIED`, while `FAIL` sends it to `REMEDIATION`, from which a fresh window may be opened. That is the closed loop `CERTIFICATION_TESTING → REMEDIATION → CERTIFICATION_TESTING`, and each of the two result outcomes increments `version`.

Activation is the gate that matters commercially, and it is guarded twice over. Structurally, the hop `CERTIFIED → LIVE` requires the participant to be in `CERTIFIED`, to have a prefunded position account, for that account's `current_balance_cents` to be at least the network minimum prefund of 100,000,000 cents (one million currency units), and for that account's `alert_tier` to be `GREEN`. As a business prerequisite, activation additionally demands a position account, a recorded `attestation_document_reference`, and a `PASS` result recorded in the participant's current `certification_round`; when any of those three is missing the request is refused with `ERR_ACTIVATION_PREREQUISITES_NOT_MET`. A successful activation stores the supplied `go_live_business_date`, re-derives `operational_posture` from the account's current band — so a bank going live over an `AMBER` account is live and `THROTTLED`, not live and `NORMAL` — and increments `version`.

After go-live, the rail operator manages the relationship through a single status-change operation carrying a `target_status` and an optional `suspension_reason`. Suspending a live bank (`LIVE → SUSPENDED`) records the reason and re-derives posture: a suspended participant is `SEND_FROZEN` unless a declared outage covering it forces `OFFLINE`, and the resulting freeze parks every one of its transfers still in `INITIATED` into `QUEUED_THROTTLED`, releasing their reservations. Reinstatement (`SUSPENDED → LIVE`) clears the stored reason, re-derives posture from the account band, and — when the recomputed posture is `NORMAL` or `THROTTLED` — runs the queue release pass over that bank's parked transfers. Withdrawal is available from either `LIVE` or `SUSPENDED` and is refused unless the bank has no transfer left in any of the four in-flight clearing states `INITIATED`, `FRAUD_HOLD`, `QUEUED_THROTTLED` or `ACCEPTED`; a withdrawal records the reason, sets `operational_posture` to `SEND_FROZEN` permanently, and increments `version`. `WITHDRAWN` is terminal: no further lifecycle hop leaves it, and an attempt is answered `ERR_INVALID_STATE_TRANSITION`.

Reading a participant returns its derived `operational_posture` alongside its stored enrolment fields, and four reverse-reachability lists hang off the participant record: its zero-or-one prefunded position accounts, its segment policies (returned newest `effective_from` first, optionally narrowed by `segment`), its customer accounts (optionally narrowed by `segment` and by `status`), and the outage events scoped to it (optionally narrowed by `status`).

### 3.2. Configuring the Customer Base: Segment Limit Policies and Deposit Accounts

Transaction limits are not global settings; they are versioned policy windows published per participant and per customer segment by the bank's own administrator. Both publication and customer registration require the owning participant to be `LIVE` — a bank still in `DRAFT`, `ATTESTATION_PENDING`, `CERTIFICATION_TESTING`, `REMEDIATION`, `CERTIFIED`, `SUSPENDED` or `WITHDRAWN` cannot configure live payment controls, and the attempt is refused with `ERR_PARTICIPANT_NOT_LIVE`.

A policy publication names the `participant_id` it belongs to and the `segment` it governs — one of `CONSUMER`, `SMALL_BUSINESS`, `CORPORATE` or `HIGH_RISK` — and carries four control values plus a window. The `per_transaction_limit_cents` is the largest amount a single transfer of that segment may carry and must be greater than zero. The `daily_aggregate_limit_cents` bounds a customer account's settled-plus-in-flight outbound exposure for one business date and must be at least as large as the per-transaction limit. The `rolling_window_count_limit` is the number of prior in-window transfers a customer may already have before a new send is refused, and must be greater than zero, while `rolling_window_amount_limit_cents` bounds the summed amount inside that same rolling window and must likewise be greater than zero. The window itself runs from an inclusive `effective_from` to an exclusive `effective_to`; supplying no `effective_to` publishes an open-ended window. When an `effective_to` is supplied it must be strictly later than `effective_from`, otherwise the publication is refused with `ERR_INVALID_INTERVAL`.

Windows for the same participant-and-segment pair may not overlap. Because they are half-open, a new policy whose `effective_from` falls exactly on an incumbent's `effective_to` is adjacent and accepted, while one starting a minute earlier overlaps and is rejected with `ERR_POLICY_WINDOW_OVERLAP`. An open-ended incumbent overlaps everything after its own `effective_from`, which would make it impossible to ever publish a successor — unless the publication carries `supersede_open_ended` set to true. That flag closes the incumbent by writing the new policy's `effective_from` into the incumbent's `effective_to` and stamping the incumbent's `superseded_at` with the current logical clock, turning what would have been an overlap into adjacency. Every successful publication also increments the owning `Participant.version`, which is precisely why a second publication in the same session must re-read the participant to obtain a fresh `expected_participant_version`.

**Which policy governs a given transfer** is resolved exactly once, at origination, and then frozen. The candidate set is every policy of the originating participant whose `segment` equals the debtor customer account's `segment`, whose `superseded_at` is null, whose `effective_from` is at or before the current logical clock, and whose `effective_to` is either null or strictly after that clock. Candidates are ranked by `effective_from` descending, and ties are broken by `created_at` descending — never by record `id`. The winner's identifier is written into the transfer's `segment_policy_id`, and its four control values are the ones enforced for that transfer for the rest of its life, even if a later policy supersedes it before the transfer settles. If the candidate set is empty, the origination is refused with `ERR_NO_GOVERNING_SEGMENT_POLICY`.

Customer registration is simpler. The administrator supplies the owning `participant_id`, the customer's `segment` (drawn from the same four values, since the segment both selects the governing policy and supplies the fraud multiplier), a bank-internal `account_reference` that must be unique within that participant, and a static `fraud_risk_baseline` between 0 and 100 inclusive that feeds every fraud score computed for that customer. A registered account starts with `status` `ACTIVE`, a `daily_sent_amount_cents` of 0 and a null `restricted_at`. Reusing an `account_reference` inside the same participant, exactly like attempting to open a second prefunded position account for a participant that already has one, is refused with `ERR_DUPLICATE_RESOURCE`. Reading a customer account returns its current `status` and its rolling daily sent total.

The only other value `status` ever takes is `RESTRICTED`, and only the fraud-block cascade sets it. A `RESTRICTED` account can neither originate a transfer nor be named as the debtor of a request for payment; both attempts are refused with `ERR_CUSTOMER_ACCOUNT_RESTRICTED`.

### 3.3. The Prefunded Position: Opening, Funding and Alert Remediation

A treasury officer opens the participant's single prefunded position by naming the `participant_id` and supplying the opening deposit as `opening_balance_cents` together with the three monitoring thresholds: `warning_threshold_cents`, the balance at or below which the account bands to `AMBER`; `critical_threshold_cents`, the balance at or below which it bands to `RED`; and `floor_cents`, the regulatory floor that sends must leave the available position at or above and below which the account bands to `BREACH`. The opening deposit must be at least the network minimum of 100,000,000 cents, otherwise the request is refused with `ERR_PREFUND_BELOW_MINIMUM`. The four figures must also be ordered: the floor at or below the critical threshold, the critical threshold at or below the warning threshold, and the warning threshold at or below the opening balance — equal adjacent values are accepted, and any other arrangement is refused with `ERR_INVALID_THRESHOLD_ORDERING`. A participant may hold at most one such account.

Opening the account seeds the derived trio in a single pass: `current_balance_cents` starts equal to the opening balance because no entry has been posted yet, `reserved_cents` starts at 0 because nothing is in flight, `available_cents` follows from the two, and `last_ledger_sequence_no` starts at 0. The band is then computed, and if the thresholds were set such that the opening balance is already not `GREEN`, an alert is opened immediately as part of the same request. The owning participant's `operational_posture` is re-derived at the end of the call, which is how opening a thinly funded account can leave an otherwise healthy bank `THROTTLED` or `SEND_FROZEN` before it has sent anything.

Funding movements are posted as ledger adjustments. The officer supplies an `entry_type`, a positive `magnitude_cents`, and optionally a `reference`; the *sign* of the resulting entry is derived from the type rather than from the caller, so a magnitude of zero or a negative magnitude is refused with `ERR_INVALID_REQUEST` even though the entry it would produce is a debit. `FUNDING_CREDIT` and `RETURN_CREDIT` raise the position; `WITHDRAWAL_DEBIT` lowers it. The two remaining types, `TRANSFER_DEBIT` and `FEE_DEBIT`, are never posted by an operator — the settlement cascade and the cutoff fee assessment post those. An adjustment may take the balance below `floor_cents`, which is exactly the situation a `BREACH` band is meant to surface, but it may never take `current_balance_cents` below zero; an adjustment that would is refused with `ERR_LEDGER_ADJUSTMENT_WOULD_GO_NEGATIVE`.

A posted adjustment sets off a short chain of consequences. The entry is appended with the next `sequence_no` and with `balance_after_cents` recording the position immediately after it, the account's `last_ledger_sequence_no` advances to that ordinal, and the account's balance, reservation and availability are recomputed. The band is then re-derived: a downgrade opens a new alert for the newly reached tier, while a return to `GREEN` clears every alert on the account that is not already `CLEARED`, stamping each with `cleared_at`. Finally the owning participant's posture is re-derived, which — depending on direction — either parks that bank's remaining `INITIATED` transfers into `QUEUED_THROTTLED` or runs the queue release pass over transfers already parked. A withdrawal that tips a healthy account into `RED` therefore freezes sending and releases reservations in the same request in which the money left.

Three read channels support twenty-four-hour monitoring. The account's ledger may be listed in ascending `sequence_no` order and narrowed by `entry_type`, by `business_date`, or by `related_transfer_id` to isolate the movements a single transfer produced. The account's alerts may be listed newest first and narrowed by `status` or by `tier`. And the account exposes a forward-looking twenty-four-hour projection.

The **projection** looks out over the half-open window that begins at the current logical clock and ends at `horizon_end`, which is 1,440 minutes (twenty-four hours) later; a request whose `expiry_at` falls exactly on the clock is inside the window, while one falling exactly on `horizon_end` is outside it. `scheduled_outflow_cents` is the summed `amount_cents` of every request for payment naming one of this participant's customer accounts as `debtor_customer_account_id`, whose `status` is `DELIVERED` or `ACCEPTED`, and whose `expiry_at` falls inside that window — money the bank's customers are expected to pay out. `expected_inflow_cents` is the summed `amount_cents` of every request for payment this participant raised as `requestor_participant_id` whose `status` is `ACCEPTED` and whose `expiry_at` falls inside the same window — money it expects to receive. `projected_balance_cents` is the current balance less the scheduled outflow plus the expected inflow; `projected_available_cents` is that projected balance less the *current* `reserved_cents`; and `projected_alert_tier` is the band the projected balance would fall into under the ordinary band rules. Committed in-flight transfers are deliberately **not** added into the outflow: they already sit inside `reserved_cents`, and counting them twice is the classic misreading of this figure. The response reports `current_balance_cents`, `reserved_cents`, `available_cents`, `scheduled_outflow_cents`, `expected_inflow_cents`, `projected_balance_cents`, `projected_available_cents`, `projected_alert_tier` and `horizon_end` together, so an officer can see the current and projected position side by side.

Alerts are worked by acknowledgement. A treasury officer acknowledges an alert that is `OPEN` or `ESCALATED` by supplying a `remediation_plan`; the alert becomes `ACKNOWLEDGED`, `acknowledged_by_user_id` is taken from the acting `X-User-ID`, and neither the account's `alert_tier` nor the participant's posture changes — acknowledgement is a commitment to fund, not funding. An alert that is already `ACKNOWLEDGED` or `CLEARED` cannot be acknowledged again and the attempt is refused with `ERR_ALERT_NOT_ACKNOWLEDGEABLE`. Separation of duties applies here as it does on fraud review: the officer acknowledging the alert must not be the same user whose ledger adjustment raised it, otherwise the attempt is refused with `ERR_ALERT_SEGREGATION_OF_DUTIES`. An alert left unacknowledged is escalated by the housekeeping sweep once 60 minutes have elapsed since it was opened, which stamps `escalated_at`; escalation does not close the alert, and an `ESCALATED` alert may still be acknowledged. The only route to `CLEARED` is a balance recovery that returns the band to `GREEN`, whether that recovery comes from fresh funding or from a honoured return.

### 3.4. Originating an Instant Credit Transfer

Origination is the busiest control point in the system. A `PaymentOperator` supplies the `originator_participant_id` whose position will fund the payment, the `customer_account_id` of the debtor customer, the counterparty institution's `receiver_routing_number` as exactly nine digits, the `amount_cents` to send as a positive integer, and the `expected_position_account_version` described in §2.6. Two fields are optional: `remittance_reference`, an end-to-end reference carried with the payment, and `rfp_id`, present only when this payment discharges an accepted request for payment.

Before anything is written, the request runs the ladder of §2.11 in that exact order, and the rungs that bite here are worth naming individually. The originating bank must be `LIVE`, or the send fails with `ERR_PARTICIPANT_NOT_LIVE`. Its posture must not be `OFFLINE`, or the send fails with `ERR_PARTICIPANT_OFFLINE`. Its posture must not be `SEND_FROZEN`, or the send fails with `ERR_PARTICIPANT_SEND_FROZEN` — and because that is a posture rung, it is reported in preference to any funding, limit or velocity complaint. Its `participation_model` must permit sending: a `RECEIVE_ONLY` bank and a `RECEIVE_AND_REQUEST_FOR_PAYMENT` bank may never originate, and both are refused with `ERR_SEND_NOT_PERMITTED_FOR_MODEL` rather than with a limit error, because the model check is network compliance and outranks every limit rung. The debtor customer account must be `ACTIVE`, or the send fails with `ERR_CUSTOMER_ACCOUNT_RESTRICTED`. That customer account must also belong to the participant named in the same request — a customer of another bank cannot be debited here, and the mismatch is refused with `ERR_CUSTOMER_ACCOUNT_PARTICIPANT_MISMATCH`. A governing segment policy must resolve for the pair of originating participant and the customer's `segment`, as described in §3.2, or the send fails with `ERR_NO_GOVERNING_SEGMENT_POLICY`.

When the send names an `rfp_id`, three coherence conditions apply together: the referenced request must be in `ACCEPTED` status, its `debtor_customer_account_id` must equal the transfer's `customer_account_id`, and the transfer's `amount_cents` must equal the request's `amount_cents` exactly — partial and over-payment of a request are both refused with `ERR_RFP_FULFILMENT_MISMATCH`. A fulfilling send is also subject to the request's own closing instant: once the logical clock has reached the request's `expiry_at`, the fulfilment is refused with `ERR_RFP_EXPIRED`, and an attempt at exactly that instant is already late.

Then come the limits, in a fixed internal order. First the amount is compared with the pinned policy's `per_transaction_limit_cents`; the comparison is at-most, so an amount exactly equal to the limit is admitted and anything larger is refused with `ERR_PER_TRANSACTION_LIMIT_EXCEEDED`. Next, if the originating bank's posture is `THROTTLED`, the amount is additionally capped at 50,000,000 cents (five hundred thousand currency units) regardless of how generous the policy is; exceeding that cap is refused with `ERR_THROTTLED_CAP_EXCEEDED`. Then the velocity controls, and then the daily aggregate control, and only after all of those the liquidity test.

**Velocity** is measured over the rolling 60-minute half-open window that ends at the current logical clock: a transfer created exactly at the window's start instant counts, and one created exactly at the clock does not. The countable rows are the debtor customer account's own outbound transfers in one of five clearing states — `INITIATED`, `FRAUD_HOLD`, `QUEUED_THROTTLED`, `ACCEPTED` or `SETTLED`. Rows in `REJECTED`, `DIVERTED` or `EXPIRED` never count toward velocity, so a blocked or expired attempt does not consume the customer's headroom. The transfer being scored is not yet persisted, so it is never inside its own window. Two comparisons follow, and **count is checked before amount**: the number of countable prior rows plus one for this send must not exceed `rolling_window_count_limit`, and their summed `amount_cents` plus this amount must not exceed `rolling_window_amount_limit_cents`. Either breach is refused with `ERR_VELOCITY_LIMIT_EXCEEDED`.

**Daily exposure** is measured against the current business date and has two parts. The conserved part, mirrored on the customer account as `daily_sent_amount_cents`, is the summed `amount_cents` of that customer's outbound transfers whose `clearing_status` is `SETTLED`, whose `settlement_business_date` equals the current business date, and whose `exception_status` is anything other than `RETURN_HONORED`. The in-flight part adds the summed `amount_cents` of that customer's outbound transfers in `INITIATED`, `FRAUD_HOLD`, `QUEUED_THROTTLED` or `ACCEPTED` whose `created_at` falls on the current business date. The sum of those two parts is the customer's daily exposure, and the exposure plus this send's amount must not exceed the pinned policy's `daily_aggregate_limit_cents`, otherwise the send is refused with `ERR_DAILY_LIMIT_EXCEEDED`.

**Liquidity** is checked last of all: the originating account's `available_cents` minus this `amount_cents` must be at least `floor_cents`. Because the comparison is at-least, a send that lands availability exactly on the floor is admitted, while one cent more is refused with `ERR_INSUFFICIENT_LIQUIDITY`.

A send that clears the whole ladder is persisted with `direction` `OUTBOUND`, `rail` `INSTANT`, `clearing_status` `INITIATED`, `exception_status` `NONE`, `segment_policy_id` pinned to the governing policy, `initiated_by_user_id` taken from the acting `X-User-ID`, and `rejection_reason_code` unset. Its amount immediately enters the reservation set, so the account's `reserved_cents` rises and `available_cents` falls; the participant's daily exposure rises with it, while `daily_sent_amount_cents` stays where it was, because that counter only moves on settlement. The position account's `version` is incremented by the origination, which is why a second send in the same session must re-read the account first.

**Fraud scoring at origination.** Before the routing decision is taken, a score is computed and frozen into `fraud_score`, and it is never recomputed for the life of the transfer. The score is assembled from four terms. The *base* is the debtor customer account's `fraud_risk_baseline`. The *amount term* takes the transfer amount in cents, divides it by 100,000 cents (one thousand currency units) and discards the remainder, caps that whole number of bands at 10, and multiplies the result by a weight of 2 — so a 900,000-cent transfer contributes 18 and anything at or above 1,000,000 cents contributes the maximum 20. The *velocity term* takes the countable window count over the rolling 60-minute window described above, subtracts a free allowance of 3, treats any negative result as zero, and multiplies by a weight of 4. The *new-beneficiary term* is 12 when the debtor customer account has no other outbound transfer in `SETTLED` clearing status to the same `receiver_routing_number`, and 0 otherwise. Those four terms are summed into a raw subtotal, the subtotal is multiplied by the customer's segment multiplier — 1.00 for `CONSUMER`, 1.05 for `SMALL_BUSINESS`, 1.10 for `CORPORATE` and 1.25 for `HIGH_RISK` — the product is rounded half up to a whole number, and only then is the result capped at 100. The order is the rule: the amount and velocity terms are clamped before the multiplication, and the ceiling of 100 is applied after it. Multiplying before clamping the terms, or capping at 100 before applying the multiplier, both produce a different number and are both wrong.

Alongside the score, origination records `fraud_reason_codes` as the list of codes contributed by non-zero terms, in this fixed order: `BASELINE_RISK` when the base is at least 40, then `AMOUNT_BAND` when the amount term is greater than zero, then `VELOCITY_BURST` when the velocity term is greater than zero, then `NEW_BENEFICIARY` when the new-beneficiary term is greater than zero. Reason codes are recorded at origination only; the review-time recomputation described in §3.5 does not rewrite them.

The frozen score then routes the transfer, in the same request that created it. A score of 85 or more is blocked outright: the transfer moves `INITIATED → REJECTED`, `rejection_reason_code` is written as `FRAUD_BLOCK_AUTOMATIC`, and its amount leaves the reservation set so the account's `reserved_cents` returns to the value it had before the call. An automatic block creates **no** fraud review and leaves the debtor `CustomerAccount.status` `ACTIVE` — only a reviewer's explicit block restricts a customer. A score of at least 60 but below 85 is held: the transfer moves `INITIATED → FRAUD_HOLD`, its amount **stays** inside the reservation set because `FRAUD_HOLD` is one of the three reserving states, and one `FraudReview` is created in `QUEUED` status with `credit_transfer_id` pointing at the transfer, `score_at_origination` copied from the frozen score, `sla_deadline_at` still null, and `queue_priority` set to 1 when `score_at_origination` is at least 75 — that is, within 10 points of the block threshold — and 2 otherwise, with the lower value worked first. A score below 60 leaves the transfer in `INITIATED`, and it proceeds to the ordinary clearing path.

Transfers can be read individually, returning both dimensions along with the frozen `fraud_score` and `fraud_reason_codes`, and listed with filters on `originator_participant_id`, `customer_account_id`, `segment_policy_id`, `rfp_id`, `compensating_for_transfer_id`, `clearing_status`, `exception_status` and `settlement_business_date`. The list is the discovery channel for transfers the system created on its own — in particular the compensating inbound credits described in §3.8, which no caller ever originates directly.

### 3.5. The Fraud Hold-and-Review Queue

A held transfer waits on a review whose lifecycle is deliberately two-step, so that no analyst can silently decide an item nobody is accountable for. A `FraudReviewer` first takes the item, moving it `QUEUED → UNDER_REVIEW`; the operation carries no payload at all, binding the acting `X-User-ID` into `assigned_reviewer_user_id` and stamping `sla_deadline_at` at the assignment instant plus 60 minutes. Taking an item requires the item to be `QUEUED` and the reviewed transfer to be sitting in `FRAUD_HOLD`, and it requires the acting user to differ from that transfer's `initiated_by_user_id`: an operator may not review its own origination, and the attempt is refused with `ERR_FRAUD_SEGREGATION_OF_DUTIES`.

Deciding the item requires it to be `UNDER_REVIEW`; a decision attempted while the review is still `QUEUED` is refused with `ERR_FRAUD_REVIEW_NOT_ASSIGNED`, which is the precise reason the assignment step cannot be skipped. The decision payload carries a `decision` of either `RELEASE` or `BLOCK`, plus an optional `decision_rationale` recorded on the review. Segregation of duties tightens at this step: the acting `X-User-ID` must still differ from the transfer's `initiated_by_user_id`, and it must additionally equal the review's `assigned_reviewer_user_id`, so an analyst cannot decide an item a colleague holds. Either breach is refused with `ERR_FRAUD_SEGREGATION_OF_DUTIES`.

**The score is recomputed at decision time**, into `final_fraud_score`, using the same four terms and the same segment multiplier as at origination but with three differences. The velocity term uses a weight of 3 and a free allowance of 5 instead of 4 and 3. Its window is the rolling 1,440-minute (twenty-four hour) half-open window ending at the current clock rather than the 60-minute one, and the transfer under review is explicitly excluded from its own window even though it is now persisted. And the new-beneficiary term is re-evaluated as of decision time, so a beneficiary that has since received a `SETTLED` transfer from the same customer account drops that 12-point bonus to zero. The base and the amount term are unchanged, and the multiplier is the same — yet the final score is generally a different number from the origination score on identical stored data. That is intentional: `RELEASE` is gated on the recomputed value while the frozen origination value stays visible on the transfer for audit.

A `RELEASE` requires the recomputed `final_fraud_score` to be below 85. The review becomes `RELEASED`, the recomputed score and the rationale are written, and the transfer returns `FRAUD_HOLD → INITIATED`, closing the clearing loop `INITIATED → FRAUD_HOLD → INITIATED` and re-entering the normal clearing path. The transfer's own `fraud_score` is **not** overwritten — the origination value stays frozen.

A `BLOCK` needs no score condition and triggers the longest cascade in the system. The review becomes `BLOCKED` with `final_fraud_score` and `decision_rationale` written. The transfer moves `FRAUD_HOLD → REJECTED` with `rejection_reason_code` written as `FRAUD_BLOCK_REVIEW`, and its amount leaves the reservation set, so the account's `reserved_cents` drops and `available_cents` rises. The debtor `CustomerAccount` then flips `ACTIVE → RESTRICTED` with `restricted_at` stamped at the logical clock. And because that customer is now restricted, every *other* transfer of the same customer account still sitting in `INITIATED` is parked into `QUEUED_THROTTLED` with `queued_at` stamped, releasing their reservations too — so a single blocking decision can free a large amount of previously committed liquidity in one request.

The reviews raised for a transfer are discoverable only through that transfer's own review list, returned newest first and optionally narrowed by `status`, since a review created by the origination cascade is never announced anywhere else.

### 3.6. Clearing to Settlement and the Irrevocability Point

Clearing runs in two operator-driven hops. Rail acceptance advances a transfer `INITIATED → ACCEPTED` and is permitted only when the transfer is actually in `INITIATED`, the originating bank's `enrollment_status` is `LIVE`, that bank's `operational_posture` is either `NORMAL` or `THROTTLED`, and the debtor `CustomerAccount.status` is `ACTIVE`. Acceptance stamps both `accepted_at` and `irrevocable_at` with the logical clock — they always hold the same instant — leaves the amount inside the reservation set, and increments the transfer's `version`. From the moment `irrevocable_at` is non-null the payment can no longer be diverted or cancelled; the only remaining remedy is a return request.

Settlement advances `ACCEPTED → SETTLED` and requires an open cycle for today: a settlement cycle whose `business_date` equals the UTC date of the logical clock must exist with `status` `OPEN`, otherwise the attempt is refused with `ERR_CYCLE_NOT_OPEN`. Once the date's cycle has been cut off or closed, settlement for that date is over.

Settlement is where a single request touches five records, and every hop matters. **First**, `settled_at` is stamped and `settlement_business_date` is set to the open cycle's `business_date`, and the amount leaves the reservation set. **Second**, one ledger entry is posted with `entry_type` `TRANSFER_DEBIT` and an `amount_cents` equal to the negative of the transfer amount, with `related_transfer_id` pointing at the transfer and `sequence_no` taken as one greater than the account's `last_ledger_sequence_no`; that entry lowers `current_balance_cents` and increments the position account's `version`. Note the combined effect of the first two hops: `reserved_cents` falls by the amount while `current_balance_cents` falls by the same amount, so `available_cents` is unchanged by settlement. **Third**, the lowered balance is re-banded, and if the band degrades to `AMBER`, `RED` or `BREACH` an alert row is opened with its `status` `OPEN`, its `tier`, its `threshold_cents` and its `observed_balance_cents` set as described in §2.9. **Fourth**, a freshly opened `RED` or `BREACH` alert drives the posture derivation, moving the participant to `SEND_FROZEN`. **Fifth**, that freeze parks the bank's remaining `INITIATED` transfers into `QUEUED_THROTTLED` with `queued_at` stamped, releasing their reservations. Alongside those hops, the debtor customer's `daily_sent_amount_cents` is recomputed and rises by the settled amount, and the cycle's `settled_transfer_count` is recomputed as the number of outbound transfers in `SETTLED` whose `settlement_business_date` equals its `business_date`.

Irrevocability is enforced as an explicit rule rather than left as an implication. A settled transfer may not be cancelled, reversed, re-settled, nor have its amount amended by any operation; an acceptance, a settlement or a diversion attempted against an already `SETTLED` transfer is refused with `ERR_TRANSFER_IRREVOCABLE`. The only permitted remedy is a return request that the counterparty side may honour or decline, and even a honoured return does not rewind the original row — as §3.8 describes, the money comes back as a separate inbound payment. Attempting any of the three clearing hops from a state for which it is not declared — settling a transfer still in `INITIATED`, accepting one already `ACCEPTED`, diverting one that was never queued — is refused with `ERR_INVALID_STATE_TRANSITION`, and the four states `SETTLED`, `REJECTED`, `DIVERTED` and `EXPIRED` are terminal on the clearing dimension.

The ledger movements a single transfer produced are discoverable through that transfer's own ledger-entry list, returned in ascending `sequence_no` order and optionally narrowed by `entry_type`: for a straightforward payment that is the one settlement debit, and for a returned payment it is the settlement debit followed by the compensating credit.

### 3.7. Requests for Payment and the Message Response Obligation

A request for payment is a message asking somebody else's customer to pay, and the rail holds both sides to a response obligation. A `PaymentOperator` raises one by naming the `requestor_participant_id` that wants to be paid, the `debtor_customer_account_id` being asked to pay, the requested `amount_cents` as a positive integer, a hard `expiry_at` after which the request may no longer be answered, and optionally a free-text `memo` describing the purpose. Note carefully that the debtor customer account legitimately belongs to a *different* bank — this is one participant asking another bank's customer to pay — so the ownership-coherence rule that governs origination is deliberately **not** applied here.

Raising a request requires the requesting bank to be `LIVE` and its posture not to be `OFFLINE`, failing which the attempt is refused with `ERR_PARTICIPANT_NOT_LIVE` or `ERR_PARTICIPANT_OFFLINE` respectively. It also requires model capability on both sides: the requesting bank's `participation_model` must be `RECEIVE_AND_REQUEST_FOR_PAYMENT` or `SEND_AND_RECEIVE`, and the debtor customer's own bank must itself be on one of those two models, since a `RECEIVE_ONLY` institution does not handle request-for-payment messages at all. A failure on either side is refused with `ERR_REQUEST_NOT_PERMITTED_FOR_MODEL`. The named debtor account must be `ACTIVE`, or the request is refused with `ERR_CUSTOMER_ACCOUNT_RESTRICTED`. And the supplied `expiry_at` must be strictly later than the current logical clock, otherwise the request is refused with `ERR_INVALID_INTERVAL`. A newly raised request sits in `CREATED` with `amendment_round` 0, a null `delivered_at`, a null `response_deadline_at` and a null `last_response`.

Delivery is the rail operator's act, and it starts the response clock. `CREATED → DELIVERED` requires the request to still be in `CREATED`, its `expiry_at` to be strictly later than the clock, the requesting bank to be `LIVE`, and that bank's `participation_model` to be `SEND_AND_RECEIVE` or `RECEIVE_AND_REQUEST_FOR_PAYMENT`. Delivery stamps `delivered_at` with the clock and sets `response_deadline_at` to whichever is earlier of the request's `expiry_at` and the delivery instant plus 30 minutes — the message response service level — and increments the request's `version`.

The debtor side discharges its obligation by supplying a `response` of `ACCEPT`, `DECLINE` or `REQUEST_AMENDMENT`, and whichever branch is taken, the value is recorded in `last_response`. All three branches require the request to be `DELIVERED` and require the clock to be strictly before `response_deadline_at`; a response at or after that instant, or at or after `expiry_at`, is refused with `ERR_RFP_EXPIRED`. An `ACCEPT` additionally requires the clock to be strictly before `expiry_at` and the debtor `CustomerAccount.status` to be `ACTIVE`, and moves the request `DELIVERED → ACCEPTED`; an accepted request is what unlocks a fulfilling origination that names it in `rfp_id`, and it becomes payable exactly once that way. A `DECLINE` requires a `decline_reason_code` to be present in the payload, drawn from `ACCOUNT_CLOSED`, `AMOUNT_DISPUTED`, `NOT_RECOGNIZED` and `INSUFFICIENT_FUNDS`, and moves the request `DELIVERED → DECLINED` with that code stored. A `REQUEST_AMENDMENT` requires `amendment_round` to be strictly below 2, moves the request `DELIVERED → AMENDMENT_REQUESTED`, and clears `response_deadline_at` — the response clock stops while the requestor reworks the ask, and stays null until the amended request is redelivered.

Amendment closes the negotiation loop `DELIVERED → AMENDMENT_REQUESTED → DELIVERED`. The requesting operator supplies a replacement `amount_cents` and optionally a replacement `memo`; the operation requires the request to be in `AMENDMENT_REQUESTED`, requires `expiry_at` to be strictly later than the clock, and requires `amendment_round` to still be below 2. It replaces the amount, increments `amendment_round` by one, clears `last_response`, stamps a fresh `delivered_at`, and re-derives `response_deadline_at` as the earlier of `expiry_at` and the new delivery instant plus 30 minutes. An amendment never extends `expiry_at` — the hard expiry survives every round, which is why the recomputed deadline can be shorter than 30 minutes near the end of a request's life. At most two amendment rounds are permitted: a third attempt is refused with `ERR_AMENDMENT_ROUNDS_EXHAUSTED` even though the state machine itself would allow the hop, and an amendment attempted at or after `expiry_at` is refused with `ERR_RFP_EXPIRED`.

Requests that nobody answers are swept away rather than lingering. From any of `CREATED`, `DELIVERED` or `AMENDMENT_REQUESTED`, a request whose `expiry_at` has been reached by the clock becomes `EXPIRED` during the housekeeping sweep, and no other record is touched by that hop. `ACCEPTED`, `DECLINED` and `EXPIRED` are terminal, and any operation attempted against a request in one of them is refused with `ERR_INVALID_STATE_TRANSITION`. Requests may be read individually, exposing the current `status`, `last_response`, `delivered_at`, `response_deadline_at`, `amendment_round` and `decline_reason_code`, and listed with filters on `requestor_participant_id`, `debtor_customer_account_id` and `status`.

### 3.8. Return Requests and Compensating Credits

Because a settled instant payment cannot be rewound, the exception process runs on a *second, independent* state dimension of the same transfer row. Throughout the entire exception lifecycle the transfer's `clearing_status` stays `SETTLED`; what moves is `exception_status`, from `NONE` through `RETURN_REQUESTED` to one of the three terminal outcomes `RETURN_HONORED`, `RETURN_DECLINED` or `RETURN_EXPIRED`.

A return is lodged by the receiving side. The operator names the `credit_transfer_id` of the settled payment, the `requested_by_participant_id` raising the exception, and a `reason_code` drawn from `DUPLICATE_PAYMENT`, `WRONG_BENEFICIARY`, `FRAUD_SUSPECTED` and `TECHNICAL_ERROR`, and may add a free-text `narrative`. The lodging participant must be `LIVE`. The referenced transfer must be in `SETTLED` clearing status — an `INITIATED`, `FRAUD_HOLD`, `ACCEPTED`, `QUEUED_THROTTLED`, `DIVERTED` or `REJECTED` transfer is simply not returnable, and the attempt is refused with `ERR_TRANSFER_NOT_SETTLED`. Only the counterparty side may lodge it: the requesting participant's `routing_number` must equal the transfer's `receiver_routing_number`, so the bank that sent the payment cannot ask for its own money back, and a wrong-side attempt is refused with `ERR_RETURN_REQUESTOR_NOT_RECEIVER`. The exception dimension is one-shot: a transfer whose `exception_status` is anything other than `NONE` may not be lodged against again, whether a first request is still `REQUESTED` or the dimension has already reached `RETURN_HONORED`, `RETURN_DECLINED` or `RETURN_EXPIRED`, and the second attempt is refused with `ERR_DUPLICATE_RETURN_REQUEST`.

Timing is tight. A return must be lodged within 4,320 minutes (three days) of the transfer's `settled_at`, and the window is half-open: a request lodged 4,319 minutes after settlement is in time, while one lodged at exactly 4,320 minutes is refused with `ERR_RETURN_WINDOW_EXPIRED`.

The amount is fixed at lodgement, not at adjudication. `returned_amount_cents` is optional; when it is supplied it must be greater than zero and no greater than the original transfer's `amount_cents`, and a zero, negative or excessive figure is refused with `ERR_RETURN_AMOUNT_INVALID`. When it is omitted it defaults to the full original amount. A successful lodgement creates the request in `REQUESTED` with `original_amount_cents` copied from the transfer as it stands, with `response_deadline_at` set to the lodgement instant plus 1,440 minutes (twenty-four hours), and with a null `decline_reason_code` and null `honored_transfer_id`; the transfer's `exception_status` moves `NONE → RETURN_REQUESTED` while its `clearing_status` stays `SETTLED`, and the transfer's `version` is incremented.

Honouring is the rail operator's decision and takes **no payload at all** — it can neither raise nor lower the amount the requester asked for. It requires the request to still be `REQUESTED`, requires the clock to be strictly before `response_deadline_at` (an honour at exactly the deadline is refused with `ERR_RETURN_RESPONSE_DEADLINE_PASSED`), and requires the stored `returned_amount_cents` to be non-null and no greater than `original_amount_cents`. What follows is a five-hop cascade. **First**, the request becomes `HONORED` with its `returned_amount_cents` stored, and the original transfer's `exception_status` moves `RETURN_REQUESTED → RETURN_HONORED`. **Second**, a compensating `CreditTransfer` is minted — the only transfer in the system no caller ever originates — booked against the same originating participant and the same customer account as the original, with `direction` `INBOUND`, `rail` `INSTANT`, `clearing_status` `SETTLED`, `amount_cents` equal to `returned_amount_cents`, `compensating_for_transfer_id` pointing at the original transfer, `settlement_business_date` set to the clock's UTC date, `fraud_score` 0 and no fraud scoring performed at all; the request's `honored_transfer_id` points at that new row. **Third**, the compensating transfer posts one ledger entry with `entry_type` `RETURN_CREDIT` and an `amount_cents` equal to the positive returned amount, raising `current_balance_cents` and incrementing the position account's `version`. **Fourth**, the restored balance is re-banded, and if it comes back to `GREEN` every alert on that account whose `status` is `OPEN`, `ACKNOWLEDGED` or `ESCALATED` becomes `CLEARED` with `cleared_at` stamped. **Fifth**, with no non-cleared alert left, the posture derivation lifts the participant back to `NORMAL` and the queue release pass runs over its `QUEUED_THROTTLED` transfers in the pinned priority order.

One consequence of honouring is deliberately asymmetric and must not be smoothed over. The original transfer now carries `exception_status` `RETURN_HONORED`, which removes it from the conserved daily-sent input set, so the debtor customer's `daily_sent_amount_cents` recomputes downward by the **original** amount — the full amount that was sent — even when `returned_amount_cents` was smaller. The position, by contrast, is restored only by the returned amount, because that is all the ledger credit was worth. A partial return therefore restores the customer's velocity headroom in full while restoring the bank's funded position only in part; that is the intended behaviour, not an inconsistency.

Declining is the other adjudication path. It requires the request to be `REQUESTED`, requires the clock to be strictly before `response_deadline_at`, and requires a `decline_reason_code` in the payload drawn from `FUNDS_DISBURSED`, `BENEFICIARY_REFUSED` and `OUT_OF_TIME`. The request becomes `DECLINED`, the transfer's `exception_status` becomes `RETURN_DECLINED`, and nothing else moves: no ledger entry is posted, and `current_balance_cents`, `reserved_cents` and `daily_sent_amount_cents` are all left exactly as they were. A request nobody answers is expired by the housekeeping sweep once the clock reaches its `response_deadline_at`, which turns the request `EXPIRED` and the transfer's `exception_status` `RETURN_EXPIRED`, again with no ledger movement — so a declined or expired return leaves the customer's daily usage consumed, which is the whole reason the conserved counter is defined the way it is. Return requests may be read individually and listed with filters on `credit_transfer_id`, `honored_transfer_id`, `requested_by_participant_id` and `status`; the list is the discovery channel for the `honored_transfer_id` linkage back to the compensating credit.

### 3.9. Outage Contingency, the Throttled Send Queue and Rail Diversion

When the instant rail degrades, payment obligations do not disappear — they have to be parked safely and then either released or moved to another rail. The rail operator declares an outage by supplying its `scope`, either `PARTICIPANT` for a single institution or `NETWORK_WIDE` for the whole rail, its `severity` of `DEGRADED` or `FULL_OUTAGE`, the `fallback_rail` that operators may divert to while it is open (`FALLBACK_ACH`, `FALLBACK_WIRE`, or `NONE` when no alternate rail is offered), and the inclusive `started_at` of the incident. A `participant_id` accompanies a `PARTICIPANT`-scoped declaration and is null for a `NETWORK_WIDE` one, and an `ended_at` may be supplied up front but is normally left for resolution to write. A declaration lands in `DECLARED` status with `diverted_transfer_count` 0.

Outage intervals do not stack. They are **closed** on both ends, so two intervals that merely touch at an endpoint already conflict, and a `NETWORK_WIDE` event conflicts with every `PARTICIPANT`-scoped event just as a `PARTICIPANT`-scoped event conflicts with a network-wide one. A `RESOLVED` event additionally reserves a stabilization buffer of 15 minutes after its `ended_at`, and that reservation is half-open: a new event of conflicting scope starting at exactly 15 minutes after the earlier event's `ended_at` is admitted, while one starting 14 minutes after is refused. Any conflict is reported as `ERR_OUTAGE_WINDOW_CONFLICT`. When an `ended_at` is supplied it must be strictly later than `started_at`, otherwise the declaration is refused with `ERR_INVALID_INTERVAL`.

Declaring an outage takes every in-scope participant offline in the same request. Each covered participant's `operational_posture` becomes `OFFLINE` — a value that outranks every other posture regardless of what the account band says — and each of that participant's transfers still in `INITIATED` is parked `INITIATED → QUEUED_THROTTLED` with `queued_at` stamped, which releases its reservation and therefore raises `available_cents` without any money moving. The event's `diverted_transfer_count` is incremented by the number of transfers this declaration actually parked, which is zero when an earlier freeze had already parked them; a transfer that was already `QUEUED_THROTTLED` stays queued and is not counted again.

While a covering outage is open, a queued transfer may be moved to the alternate rail. Diversion is available to both the rail operator and payment operations staff, and the payload carries the `fallback_rail` to move to. It requires the transfer to be in `QUEUED_THROTTLED`, requires its `irrevocable_at` to still be null — an accepted or settled payment can never be diverted, and the attempt against a settled one is refused with `ERR_TRANSFER_IRREVOCABLE` — requires a `DECLARED` outage event covering the originating participant, and requires the supplied rail to equal that event's own `fallback_rail` and not to be `NONE`. A diversion writes the supplied value into the transfer's `rail`, moves it `QUEUED_THROTTLED → DIVERTED`, and increments the covering event's `diverted_transfer_count`. `DIVERTED` is terminal and non-reserving: the amount stays outside `reserved_cents` and the transfer never returns to the instant rail.

A queued transfer that is neither released nor diverted eventually times out. The housekeeping sweep moves a transfer `QUEUED_THROTTLED → EXPIRED` once its `queued_at` is at least 120 minutes (two hours) old relative to the logical clock, and an expired transfer stays outside the reservation set for good.

Resolution ends the incident. The operator supplies the `ended_at` to record, which must be strictly later than `started_at` and must not be later than the current logical clock; a value violating either condition is refused with `ERR_INVALID_INTERVAL`. Resolution is permitted only from `DECLARED` — `RESOLVED` is terminal — and it writes `ended_at`, moves the event `DECLARED → RESOLVED`, and then re-derives the posture of every participant the event covered. That re-derivation is not automatically a return to normal: a participant whose account band has meanwhile fallen to `RED` or `BREACH`, or which has been suspended, comes back from `OFFLINE` to `SEND_FROZEN`, and in that case **no** release pass runs and its transfers stay parked. Only a participant that comes back to `NORMAL` or `THROTTLED` gets the queue release pass of §2.9, which re-admits its queued transfers in the pinned order — accepted request-for-payment obligations first, then oldest first — stopping at the first transfer that does not fit under the floor. Transfers already diverted are gone from the queue and are not reconsidered.

### 3.10. The Business Day: Cutoff, Access Fees and Reconciliation with Core Deposits

Exactly one settlement cycle exists per business date. The rail operator opens one by supplying its `business_date`; a date already covered by a cycle is refused with `ERR_DUPLICATE_SETTLEMENT_CYCLE`, and a date later than the UTC date of the current logical clock is refused with `ERR_BUSINESS_DATE_NOT_REACHED` — cycles are opened for today or for a past date, never for tomorrow. A new cycle starts `OPEN` with `assessed_fee_total_cents` 0, `settled_transfer_count` 0 and a null `cutoff_at` and `closed_at`. While it is `OPEN` it is the cycle that transfers settle into, as described in §3.6.

Cutoff closes the date for settlement and is permitted only from `OPEN` and only once the clock has reached the cycle's own `business_date`; an earlier attempt is refused with `ERR_BUSINESS_DATE_NOT_REACHED`. It also requires that no transfer for that business date is still sitting in `ACCEPTED` — accepted-but-unsettled traffic must be settled or the date cannot be cut off, and a premature attempt is refused with `ERR_INVALID_STATE_TRANSITION`. Cutoff stamps `cutoff_at`, moves the cycle `OPEN → CUTOFF`, and assesses the **intraday liquidity access fee** for every participant whose `enrollment_status` is `LIVE`, processing participants in ascending `created_at` order.

The fee for one participant is built from that participant's outbound transfers in `SETTLED` clearing status whose `settlement_business_date` equals the cycle's `business_date`. The exception dimension is deliberately ignored in this input set: honouring a return does not refund the access fee already earned on the outbound leg. Each such transfer contributes its own fee of ten basis points of its `amount_cents` — that is, the amount multiplied by 10 and divided by 10,000 — **rounded half up to whole cents for that transfer individually**, and the gross fee is the integer sum of those per-transfer figures taken in ascending `created_at` order. The rounding order is pinned and is not interchangeable with the obvious alternative: three settled amounts of 1,500, 2,500 and 3,500 cents produce per-transfer fees of 2, 3 and 4 cents for a gross of 9 cents, whereas summing the amounts first and rounding once would give 8 cents. Nine is the correct answer. A volume rebate then applies: when the participant settled at least 10 transfers on that date, the rebate is one tenth of the gross fee with any fraction discarded, and otherwise the rebate is zero. The net fee is the gross fee less the rebate. When the net fee is greater than zero, one ledger entry with `entry_type` `FEE_DEBIT` and an `amount_cents` equal to the negative of the net fee is posted to that participant's position account; when the net fee is zero, no entry is posted at all. Each fee debit lowers that account's `current_balance_cents` and increments its `version`, the lowered balance is re-banded and may open an alert, and that alert may in turn move the participant's `operational_posture` and park its in-flight transfers — so a cutoff can freeze a participant that was healthy a moment earlier. The cycle's `assessed_fee_total_cents` records the sum of every net fee posted.

Reconciliation is submitted by the core deposit platform, which names the `settlement_cycle_id` and `participant_id` being reconciled, the `variant` to run, and its own `core_deposit_total_cents` — the one monetary input in this system that may be any signed integer, including zero and negatives, since a net position legitimately can be. The named participant must have a prefunded position account, because the rail net position is computed against that account's ledger; if it has none the run is refused with `ERR_POSITION_ACCOUNT_NOT_FOUND`. A `FINAL` run requires the cycle to be in `CUTOFF`, `RECONCILING` or `OUT_OF_BALANCE`; a `PROVISIONAL` run accepts those three and additionally `OPEN`; neither variant is accepted once the cycle is `RECONCILED`, and any mismatch is refused with `ERR_CYCLE_NOT_RECONCILABLE`. Repeat submissions do not fail: each run is persisted with a `revision` equal to one more than the number of runs that already exist for the same combination of cycle, participant and variant, which gives a total order over runs with no tie-break needed.

Both variants read the same stored rows and differ only in which clearing states and exception states they admit and whether fee entries are netted. The credit side is common to both: it is the summed `amount_cents` of the participant's transfers whose `direction` is `INBOUND`, whose `clearing_status` is `SETTLED` and whose `settlement_business_date` equals the cycle's business date — in practice, the compensating credits from honoured returns. The `PROVISIONAL` variant's debit side admits the participant's outbound transfers in either `ACCEPTED` or `SETTLED`, matching an accepted-but-unsettled transfer to the cycle by the UTC date of its `accepted_at` because its `settlement_business_date` is still null; it ignores `exception_status` entirely, so an already honoured return is still counted as a debit; its `fee_component_cents` is always 0; and it never changes the cycle's status. The `FINAL` variant's debit side admits outbound transfers in `SETTLED` only and excludes any whose `exception_status` is `RETURN_HONORED`, since returned money is netted out rather than counted; its `fee_component_cents` is the summed `amount_cents` of the account's ledger entries with `entry_type` `FEE_DEBIT` whose `business_date` equals the cycle's business date, a figure that is negative or zero; and it drives the cycle's status.

From those inputs, `rail_net_position_cents` is the credit total minus the debit total plus the fee component, `variance_cents` is `core_deposit_total_cents` minus that rail net position, and `included_transfer_count` is the number of debit rows plus the number of credit rows the variant admitted. The `outcome` is `BALANCED` when the magnitude of the variance is at or below the tolerance of 100 cents — a variance of exactly 100 cents in either direction is `BALANCED` — and `OUT_OF_BALANCE` otherwise. An empty input set is entirely legal: the rail net position then equals the fee component alone, which is zero under `PROVISIONAL`, so the variance equals the submitted core deposit total exactly.

A `FINAL` run drives the cycle through a small loop. The first `FINAL` run moves the cycle `CUTOFF → RECONCILING`, except that the cycle lands in `OUT_OF_BALANCE` instead when any `LIVE` participant's highest-revision `FINAL` run for the cycle reports `OUT_OF_BALANCE`. From `RECONCILING`, a `FINAL` run whose variance magnitude exceeds 100 cents moves the cycle `RECONCILING → OUT_OF_BALANCE`, and no money moves — the variance has to be resolved by a superseding run. From `OUT_OF_BALANCE`, a superseding `FINAL` run that leaves no `LIVE` participant's highest-revision `FINAL` run reporting `OUT_OF_BALANCE` moves the cycle back `OUT_OF_BALANCE → RECONCILING`, closing the loop `RECONCILING → OUT_OF_BALANCE → RECONCILING`. Runs may be read individually and listed with filters on `settlement_cycle_id`, `participant_id`, `variant` and `outcome`, ascending by `revision` within a triple, exposing `rail_net_position_cents`, `variance_cents`, `outcome`, `included_transfer_count` and `fee_component_cents`.

Closure is the terminal act of the business day. It is permitted only from `RECONCILING`, and only when every participant whose `enrollment_status` is `LIVE` has at least one `FINAL` run for the cycle and each of those participants' highest-revision `FINAL` run reports `BALANCED`; otherwise the attempt is refused with `ERR_VARIANCE_UNRESOLVED`. Closure stamps `closed_at`, moves the cycle `RECONCILING → RECONCILED` and increments its `version`. `RECONCILED` is terminal: no further cutoff and no further reconciliation run is accepted against it.

Finally, the network housekeeping sweep is the one operation that advances time-driven state, and it does exactly four things at the current logical clock, reporting a count for each: it expires every request for payment in `CREATED`, `DELIVERED` or `AMENDMENT_REQUESTED` whose `expiry_at` the clock has reached, reported as `expired_rfp_count`; it expires every `REQUESTED` return request whose `response_deadline_at` the clock has reached, setting the underlying transfer's `exception_status` to `RETURN_EXPIRED`, reported as `expired_return_request_count`; it expires every `QUEUED_THROTTLED` transfer whose `queued_at` is at least 120 minutes old, releasing its reservation, reported as `expired_transfer_count`; and it escalates every `OPEN` liquidity alert at least 60 minutes old, stamping `escalated_at`, reported as `escalated_alert_count`. Because expiring a queued transfer changes the reservation set, the sweep recomputes the balance, availability and posture of every account it touched. Setting the clock forward performs none of this work — expiry and escalation only happen when the sweep is run.
