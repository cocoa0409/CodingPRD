# Senior Check-In API — Product Requirements Document

## 1. Introduction

Area agencies on aging run telephone reassurance programs for one reason: a large share of the seniors they serve live alone, and the first sign that something has gone wrong is often a phone that rings unanswered. The Senior Check-In API is the operational backbone for such a program. It enrolls participants through a structured intake that weighs living situation, mobility, cognition, and recent life events into an acuity tier; it maintains a roster of trained, confidentiality-bound volunteer callers; it schedules recurring check-in calls and records their outcomes; and when calls go unanswered it walks a strict escalation ladder — retry the call, work through the emergency contacts, request a welfare check — until the participant is confirmed safe or handed off to community services.

The system's defining constraint is that capacity, trust, and time are all scarce resources. Program capacity is finite and partially reserved for the most critical applicants, so admission runs through a waitlist with a deterministic, auditable promotion order rather than first-come-first-served. Volunteer trust is earned and re-earned: training currency, confidentiality agreements, reliability tiers, and weekly load caps all gate who may be assigned to a call. Time itself is a governed input — every deadline, expiry, and reporting period reads a single logical clock, and time-driven transitions fire only through an explicit daily closeout run. This document specifies the resources, state machines, calculations, and governance rules of the API; it is the sole contract an implementer needs.

## 2. Global Specifications & System-Wide Principles

All endpoints described in this document are mounted under the `/api` prefix.

### 2.1. User and Role-Based Access Control

Every request must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, declaring their operational capacity. A request missing either header, or carrying a role the system does not declare, is rejected with `ERR_UNAUTHENTICATED`. Five roles exist. An `IntakeWorker` owns enrollment and waitlist operations: applications, review decisions, offers, and satisfaction surveys. A `ProgramCoordinator` runs day-to-day operations: program configuration, the volunteer roster, schedules, assignments, call logs as a coordinator fallback, escalation opening and advancement, and referrals. A `QualityReviewer` provides independent review: resolving escalations, closing referrals, generating and finalizing outcome reports, and revoking confidentiality agreements. A `VolunteerCaller` is the volunteer themselves: they manage their own availability, sign their own confidentiality agreement, and log outcomes on their own assignments. An `ExternalResponder` is the external welfare-check partner — a police or adult-protective-services liaison — who dispatches, completes, or declines welfare check requests. A caller whose role is not listed for an endpoint is rejected with `ERR_FORBIDDEN_ROLE`.

Identity semantics differ by role. When `X-User-Role` is `VolunteerCaller`, `X-User-ID` is the `id` of the acting `VolunteerCaller` record; ownership checks on any resource that references a volunteer compare the resource's `volunteer_id` field to `X-User-ID`. This rule bites on four operations: logging a call against an assignment, creating an availability window, deleting an availability window, and signing a confidentiality agreement — in each case, acting on a resource whose owning `volunteer_id` does not match the caller's `X-User-ID` is rejected with `ERR_NOT_OWN_RESOURCE`. When `X-User-Role` is `IntakeWorker`, `ProgramCoordinator`, `QualityReviewer`, or `ExternalResponder`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server may record it — most notably as `opened_by_user_id` on an escalation, where segregation of duties later compares it — but it is never matched against an entity's `id`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints paginate through two query parameters. The `limit` parameter sets the maximum number of items returned: it defaults to 10, accepts a minimum of 1, and is capped at a maximum of 100 — out-of-range values are clamped rather than rejected (a `limit` below 1 becomes 1, a `limit` above 100 becomes 100, and a negative `offset` becomes 0), while a non-integer `limit` or `offset` is rejected with `ERR_INVALID_REQUEST`. The `offset` parameter sets how many items to skip and defaults to 0. Unless stated otherwise, every list endpoint returns resources sorted by `created_at` in ascending order, with ties falling back to insertion order. The `meta` object of a list response carries the four pagination fields `limit`, `offset`, `total_count`, and `has_more`; `has_more` is true exactly when `offset` plus the number of items returned is less than `total_count`. Boolean-valued list filters accept the strings `true` and `false` (case-insensitive); any other value is rejected with `ERR_INVALID_REQUEST`.

### 2.4. The Logical Clock

All time-dependent behavior in the system — step deadlines, offer and survey expiry, training and agreement validity, reporting periods, trailing windows — reads a single logical clock, never the wall clock. At server startup, before any explicit set, the logical clock reads exactly `2026-08-01T00:00:00Z`, and the server never falls back to wall-clock time. Operators advance the clock through a test-driving capability that accepts a target instant `to_iso8601` and returns the clock's new value as `current_utc`; the capability is available to `ProgramCoordinator`, `IntakeWorker`, and `QualityReviewer`. Nothing expires lazily: reads never fire time-based transitions. Assignment expiry, offer requeue, volunteer lapse, survey expiry, escalation advancement, and rolling-metric recomputation all happen exclusively inside the daily closeout run described in §3.9.

### 2.5. Common Resource Properties

Every resource in the system — programs, participants, emergency contacts, waitlist entries, volunteers, availability windows, training records, confidentiality agreements, call schedules, call assignments, call logs, escalations, welfare checks, service referrals, satisfaction surveys, and outcome reports — carries four system-managed fields. `id` is a server-minted UUID with no type prefix. `created_at` is an ISO 8601 UTC timestamp with three fractional digits recording when the resource was created. `updated_at` is the same format, refreshed on any mutation. `version` is an integer that begins at 1 on creation and increments by one on every mutation of the resource. Consistency is immediate: a mutation recomputes every derived field it touches — counters, flags, tiers, deadlines — within the same request, and the response reflects the final state.

### 2.6. Request Validation Order

Requests are validated against a fixed, thirteen-step order, and a failure at any step surfaces before later checks are evaluated. The order is:

1. Authentication: the `X-User-Role` and `X-User-ID` headers are present and the role is a declared role, otherwise `ERR_UNAUTHENTICATED`.
2. Role authorization: the caller's role is listed in the endpoint's authorized roles, otherwise `ERR_FORBIDDEN_ROLE`.
3. Ownership: a `VolunteerCaller` caller may act only on resources they own, otherwise `ERR_NOT_OWN_RESOURCE`.
4. Existence: every identifier in the path exists (validated left to right, §2.10) and every foreign-key reference in the body exists, otherwise `ERR_NOT_FOUND`.
5. Concurrency: on the endpoints that declare an expected-version field (§2.7), the supplied version equals the parent resource's current `version`, otherwise `ERR_STALE_VERSION`.
6. State validity: the target resource is in a valid from-state for the requested transition, otherwise the state-family error `ERR_INVALID_STATE` — or its specialized siblings `ERR_OFFER_NOT_OPEN`, `ERR_NO_OPEN_ESCALATION`, or `ERR_PARTICIPANT_NOT_ENROLLED` where those apply.
7. Intake posture: application creation and approval require the program's `intake_posture` to be `OPEN`, otherwise `ERR_INTAKE_PAUSED`.
8. Safety gates: emergency-contact requirements on approval (`ERR_EMERGENCY_CONTACT_REQUIRED`, `ERR_NO_24H_CONTACT`), training and confidentiality currency on certification, reactivation, and assignment creation (`ERR_VOLUNTEER_NOT_CERTIFIED`, `ERR_CONFIDENTIALITY_NOT_CURRENT`), and the immediate-danger field triplet on call logs (`ERR_SAFETY_FIELDS_REQUIRED`).
9. Temporal rules: future-dated call logs (`ERR_FUTURE_DATED_CALL_LOG`), escalation step deadlines (`ERR_ESCALATION_STEP_NOT_DUE`), offer expiry (`ERR_OFFER_NOT_OPEN`), availability-window overlap (`ERR_AVAILABILITY_OVERLAP`), buffer-inclusive assignment conflicts (`ERR_ASSIGNMENT_WINDOW_CONFLICT`), and window containment (`ERR_WINDOW_OUTSIDE_SCHEDULE`, `ERR_WINDOW_OUTSIDE_AVAILABILITY`).
10. Cross-entity referential rules: a referral's source call log must actually be concern-flagged (`ERR_CONCERN_NOT_FLAGGED`), and a new escalation supersedes only a currently open case.
11. Aggregate constraints: the capacity admission branch (`ERR_CAPACITY_REACHED`), volunteer weekly load (`ERR_WEEKLY_LOAD_EXCEEDED`), the concurrency cap (`ERR_MAX_ASSIGNMENTS_REACHED`), one active or paused schedule per participant per weekday (`ERR_DUPLICATE_SCHEDULE`), one survey per participant per period (`ERR_SURVEY_PERIOD_DUPLICATE`), and a non-empty eligible-volunteer pool (`ERR_NO_ELIGIBLE_VOLUNTEER`).
12. Cooling-off: reapplication is allowed only once the program's cooling period has elapsed since the participant's last status change (`ERR_REAPPLICATION_TOO_SOON`).
13. Segregation of duties: the escalation resolver must differ from the opener (`ERR_SEGREGATION_OF_DUTIES`).

Independently of this ordering, a malformed payload — a missing required field, an unknown field, an invalid enum value, a blank (empty or whitespace-only) string where a name, phone, or policy version is required, a `window_start` that is not before its `window_end`, or an out-of-range value — is rejected with `ERR_INVALID_REQUEST`.

### 2.7. Optimistic Concurrency Control

Three write endpoints carry an optimistic-concurrency guard, each anchored to the version of a parent resource the caller last observed. `POST /api/escalations` requires the non-optional field `expected_participant_version`: opening a case legitimately supersedes whatever case is currently open for the participant, so the create must be anchored to the participant's current `version`; a value that no longer matches means the caller's view of the participant's escalation state is stale, and the create is rejected with `ERR_STALE_VERSION` (HTTP 412). `POST /api/programs/{id}/promotion-runs` requires `expected_program_version`: a promotion run is a legal, repeatable batch operation, but repeating it against a program version the caller read before an intervening mutation — another promotion run, an enrollment that bumped `occupied_slots` — must be rejected with `ERR_STALE_VERSION` (HTTP 412) so offers are never issued from a stale capacity snapshot. `PATCH /api/programs/{id}` requires `expected_program_version`: program configuration is freely editable at any time, so a request whose expected version no longer matches the program's current `version` is rejected with `ERR_STALE_VERSION` (HTTP 412), because an intervening mutation — another configuration change, an enrollment-driven occupancy bump, a promotion run — has advanced the program since the caller read it. No other endpoint takes a version field.

### 2.8. Program Capacity Accounting

Two system-maintained counters on the program summarize occupancy. `occupied_slots` counts the participants whose status is `ENROLLED`, `SUSPENDED`, or `WELFARE_HOLD` — suspension and welfare hold do not free a slot. `waiting_count` counts waitlist entries whose status is `WAITING` or `OFFERED`. Both appear on every program read. A third counter, `promotion_epoch`, starts at zero and is incremented by every successful promotion run. Capacity is configured through `total_capacity` (between 1 and 10000), the maximum number of concurrently served participants, and `max_reserve_slots` (defaulting to the smaller of 5 and `total_capacity`, and rejected with `ERR_INVALID_REQUEST` whenever it is set above `total_capacity`), the upper bound on slots reserved for `CRITICAL`-tier waitlisted applicants (§3.3). The program's `version` increments on configuration updates, intake-posture transitions, promotion runs, and daily closeout runs, and on every movement of `occupied_slots` (admission, offer acceptance, disenrollment); movements of `waiting_count` alone do not increment it.

### 2.9. Precision and Rounding

Scores, rates, and timestamps follow fixed precision rules. Integer arithmetic governs the intake acuity score, waitlist priority scores, weekly minutes, and streak counts. `reliability_windowed`, `reliability_streak_adj`, `rolling_acuity_score`, and `completion_rate` each carry exactly one decimal place; `survey_mean` and `satisfaction_index` each carry exactly two. Wherever a decimal result is produced, rounding is round half-up: a value whose discarded fraction is exactly one half of the final retained unit rounds up. Service-level-agreement comparisons resolve to the second, and all call-window and buffer arithmetic resolves to the minute.

### 2.10. Resource Existence and Path Validation

Every identifier appearing in a request path must correspond to an existing resource, and identifiers are validated in left-to-right order: the request is rejected with `ERR_NOT_FOUND` for the first path identifier that does not resolve, before later identifiers or body content are examined. Several collections are nested under a parent — a participant's emergency contacts, waitlist entries, call schedules, and surveys; a volunteer's availability windows, training records, and confidentiality agreements; an assignment's call logs; an escalation's welfare checks — and the parent's existence is always confirmed before the child collection is consulted. Foreign-key references supplied in request bodies (for example a `participant_id` or `source_call_log_id`) must likewise resolve to existing resources, failing with `ERR_NOT_FOUND` otherwise.

## 3. Business Logic & Workflows

### 3.1. Program Setup and Intake Posture

Everything begins with a `ProgramCoordinator` creating the program. Creation requires a display `name`, the `total_capacity` (an integer from 1 to 10000), and the `current_policy_version` that confidentiality agreements must match to count as current. Nine protocol knobs are optional and take defaults when omitted: `max_reserve_slots` (defaulting to the smaller of 5 and `total_capacity`, and rejected with `ERR_INVALID_REQUEST` when set above it), `no_answer_threshold` (default 3, at least 1), `escalation_retry_hours` (default 4), `contact_phase_hours` (default 24), `offer_ttl_hours` (default 72 — three days), `reapply_cooling_days` (default 30), `survey_valid_days` (default 30), and `doc_buffer_minutes` (default 15), the documentation allowance appended to every assignment window for load and conflict math; the numeric knobs other than `no_answer_threshold` must be non-negative, with violations rejected as `ERR_INVALID_REQUEST`. A new program starts with `intake_posture` `OPEN`, `occupied_slots` at 0, `waiting_count` at 0, and `promotion_epoch` at 0. The deployment operates a single program: wherever a workflow outside a program-scoped path refers to the program — participant intake and approval, volunteer certification and reactivation, assignment booking and logging, escalation handling, welfare-check completion — it resolves to the earliest-created program record, and fails with `ERR_NOT_FOUND` when no program exists.

Configuration stays editable afterwards. A coordinator may update any subset of `name`, `total_capacity`, `max_reserve_slots`, `no_answer_threshold`, `escalation_retry_hours`, `contact_phase_hours`, `offer_ttl_hours`, `reapply_cooling_days`, `survey_valid_days`, `doc_buffer_minutes`, and `current_policy_version`; the update is concurrency-guarded as described in §2.7 and increments the program's `version`. Bumping `current_policy_version` has an immediate semantic consequence: every `ACTIVE` confidentiality agreement signed under a different `policy_version` stops counting as current for all future checks, and volunteers who hold no current agreement lapse at the next daily closeout.

Intake can be throttled at the program level. Pausing intake moves `intake_posture` from `OPEN` to `PAUSED` and, while paused, new participant applications and approvals are rejected with `ERR_INTAKE_PAUSED`; resuming returns the posture to `OPEN`. Pausing a program whose posture is not `OPEN`, or resuming one whose posture is not `PAUSED`, fails with `ERR_INVALID_STATE`. Each of these transitions increments the program's `version`.

### 3.2. Participant Intake, Acuity, and Admission

An `IntakeWorker` opens a participant application with the intake interview: `full_name`, `date_of_birth` (an ISO `YYYY-MM-DD` date), `phone`, `address`, `referral_source` (one of `SELF`, `FAMILY`, `APS_REFERRAL`, `HOSPITAL_DISCHARGE`, `OTHER_PROVIDER`), `age_band` (`AGE_65_74`, `AGE_75_84`, or `AGE_85_PLUS`), the `lives_alone` flag, `mobility` (`NONE`, `LIMITED`, or `SEVERE`), the `cognitive_concern` flag, `chronic_conditions_count` (from 0 to 10), and two recent-life-event flags — `recent_hospitalization` for a hospitalization in the past 90 days and `recent_bereavement` for the loss of a spouse or partner in the past 12 months. `primary_language` is optional, defaults to `en`, and matters later: a participant whose language is not `en` can only be served by volunteers whose `languages` include it. Creation is only possible while intake is `OPEN` (`ERR_INTAKE_PAUSED` otherwise). The new participant starts as `APPLICANT` with `consecutive_no_answer_count` at zero and `coverage_deficient` false. Intake fields remain editable while the participant is `APPLICANT` or `UNDER_REVIEW`; each edit increments the participant's `version`, and edits made under review only take scoring effect when the review submission is run again.

Before approval can succeed, the applicant needs an emergency contact plan. Contacts are recorded with `full_name`, `phone`, `relationship`, a `contact_rank` of `PRIMARY` or `SECONDARY`, and an optional `accepts_24h` flag (default false) marking willingness to accept calls at any hour. A contact starts `ACTIVE`; deactivation moves an `ACTIVE` or `UNREACHABLE` contact to `REMOVED` (deactivating an already-`REMOVED` contact fails with `ERR_INVALID_STATE`), and reactivation returns an `UNREACHABLE` or `REMOVED` contact to `ACTIVE`. During the escalation contact phase (§3.7), contacts are attempted in a fixed courtesy order: every `PRIMARY` first, then every `SECONDARY`, earliest-`created_at` first within each rank.

Submitting the application for review moves the participant from `APPLICANT` to `UNDER_REVIEW` and computes the intake acuity score. Seven components sum into `acuity_score`: the age band contributes 0 points for `AGE_65_74`, 10 for `AGE_75_84`, or 20 for `AGE_85_PLUS`; living alone contributes 25; `mobility` contributes 0 for `NONE`, 10 for `LIMITED`, or 20 for `SEVERE`; a documented cognitive concern contributes 20; chronic conditions contribute 5 points each, counting at most 3 conditions; a recent hospitalization contributes 10; a recent bereavement contributes 5. The score is the sum of the seven components, capped at 100, and is an integer. `acuity_tier` bands the score: `LOW` at 29 or below, `MODERATE` from 30 through 59, `HIGH` from 60 through 84, and `CRITICAL` at 85 or above. This intake computation runs at review submission and is never recomputed afterwards; `last_status_change_at` is stamped at the transition.

Approval evaluates its gates in a deliberate order. First the participant must actually be `UNDER_REVIEW` (`ERR_INVALID_STATE` otherwise) and intake must be `OPEN` (`ERR_INTAKE_PAUSED` otherwise). Then the safety gates: at least one `ACTIVE` emergency contact with `contact_rank` `PRIMARY` must exist, failing with `ERR_EMERGENCY_CONTACT_REQUIRED` otherwise; and when the applicant's `effective_acuity_tier` is `HIGH` or `CRITICAL`, at least one `ACTIVE` contact with `accepts_24h` true must exist, failing with `ERR_NO_24H_CONTACT` otherwise. Safety errors fire before capacity is ever considered — an applicant missing a primary contact is rejected, not waitlisted.

Only then does the capacity branch run, in a pinned evaluation order. The system reads `occupied_slots`, computes gross free capacity as `total_capacity` minus occupied (the reserve is not subtracted at this point), counts `critical_waiting` — the `WAITING` waitlist entries whose participant's intake `acuity_tier` is `CRITICAL` — and computes the reserve as the smaller of `max_reserve_slots` and `critical_waiting`. A `CRITICAL` applicant is admitted when gross free capacity is at least 1, and may draw on reserved slots; an applicant of any other tier is admitted when gross free capacity minus the reserve is at least 1, so the reserve genuinely protects critical-only capacity. The apparently circular dependency — the reserve depends on waiting tiers, and tier-aware admission depends on the reserve — dissolves because the reserve reads only the raw intake tiers of entries already waiting, never the applicant under decision.

The two branches diverge visibly. An admitted applicant becomes `ENROLLED`: `occupied_slots` increases by one and the program's `version` increments, and `enrolled_at` and `last_status_change_at` are stamped. A non-admitted applicant becomes `WAITLISTED`: a waitlist entry is created in status `WAITING` with `waitlist_entered_at` set to the clock, `waiting_count` increases by one, and `last_status_change_at` is stamped. Approval does not recompute `coverage_deficient` in either branch — the flag keeps the value it last held, false for a first-time applicant — and the offer-acceptance enrollment of §3.3 likewise leaves it unrecomputed. Denial is the third outcome of review: with a `reason`, an `UNDER_REVIEW` applicant becomes `DENIED`, again stamping `last_status_change_at`.

### 3.3. Waitlist Offers and Promotion Runs

A participant holds at most one non-terminal waitlist entry — one in `WAITING` or `OFFERED` — at a time. While `WAITING`, the entry's `offered_at` and `offer_expires_at` are null, and `priority_score_at_offer` is null until the entry's first offer and thereafter retains the most recent offer's score; `declines_count` and `expires_count` track how often the applicant has declined an offer or let one lapse.

An `IntakeWorker` triggers a promotion run against a program, carrying the concurrency guard `expected_program_version` (§2.7). The run evaluates in a pinned order, each step consuming only the outputs of earlier steps. First it reads the program's `occupied_slots`. Then it scores every `WAITING` entry with a raw score: tier points — 100 for `CRITICAL`, 70 for `HIGH`, 40 for `MODERATE`, 10 for `LOW`, taken from the participant's intake `acuity_tier` — plus source points — 50 for `APS_REFERRAL`, 40 for `HOSPITAL_DISCHARGE`, 30 for `OTHER_PROVIDER`, 20 for `FAMILY`, 10 for `SELF` — plus 2 points per whole day waited, counting at most thirty days between `waitlist_entered_at` and the clock, plus a 15-point bonus when the participant lives alone. Next it counts `critical_waiting`, the `WAITING` entries whose participant's raw intake tier is `CRITICAL`, and computes the reserve as the smaller of `max_reserve_slots` and `critical_waiting`. Gross free capacity is `total_capacity` minus occupied, floored at zero; the non-critical budget is gross free minus the reserve, also floored at zero. Only now does the occupancy-pressure bump apply: when occupancy reaches at least ninety-five percent of `total_capacity`, every `CRITICAL`-tier entry gains 30 score points — this affects ranking only, because the reserve was already fixed from raw tiers. Entries are ranked by final score descending, ties broken by `waitlist_entered_at` ascending and then by the participant's `created_at` ascending — never by identifier.

The ranked list is then walked under budget. A `CRITICAL`-tier entry is offered while gross free capacity remaining is at least one, each such offer decrementing it; a non-critical entry is offered while the non-critical budget remaining is at least one, each such offer decrementing that budget. The two remainders are tracked independently: a `CRITICAL` offer does not decrement the non-critical budget, and a non-critical offer does not decrement the gross-free remainder. Entries beyond the offer window stay `WAITING`. Each offered entry moves to `OFFERED` with `offered_at` set to the clock, `offer_expires_at` set to the clock plus the program's `offer_ttl_hours`, and `priority_score_at_offer` recording the final score. The run increments `promotion_epoch` and the program's `version` exactly once, and returns — with HTTP 201 — the new `epoch`, the `offers_created` count, the `offered_entry_ids` in ranked order, and `gross_free_after`, defined as the run's gross free capacity minus the number of offers created.

An offer is accepted by an `IntakeWorker` against the entry. The entry must be `OFFERED` and the clock must not be past `offer_expires_at` — an offer expires only when the clock is strictly later than the expiry instant, so at the exact deadline the offer still stands; violations surface as `ERR_OFFER_NOT_OPEN` (and an offer the closeout has already requeued is simply no longer open). Capacity is re-checked at accept time under the same rule as admission: gross free at least one for a `CRITICAL` applicant, gross free minus the reserve at least one otherwise. If an intervening enrollment has exhausted the free slots, the accept fails with `ERR_CAPACITY_REACHED` and the entry stays `OFFERED`. On success the entry becomes `ACCEPTED`, the participant moves from `WAITLISTED` to `ENROLLED` with `enrolled_at` and `last_status_change_at` stamped, `occupied_slots` increases by one, `waiting_count` decreases by one, and the program's `version` increments.

Declining an offer returns the entry from `OFFERED` to `WAITING`: `declines_count` increments and `offered_at` and `offer_expires_at` are cleared. When the increment reaches two declines, the entry is removed outright with `removal_reason` `MAX_DECLINES` and the participant exits the waitlist. Offers can also lapse: the daily closeout finds every `OFFERED` entry whose expiry is strictly past, returns it to `WAITING`, increments `expires_count`, and clears `offered_at` and `offer_expires_at`; the second lapse removes the entry with `removal_reason` `MAX_EXPIRES` and likewise exits the participant. An applicant may also withdraw from either `WAITING` or `OFFERED` (`ERR_OFFER_NOT_OPEN` for anything else), which removes the entry with `removal_reason` `WITHDRAWN`. Every removal path moves the participant from `WAITLISTED` to `EXITED`, decrements `waiting_count`, and stamps `last_status_change_at` — the timestamp the reapplication clock later measures from.

### 3.4. The Volunteer Roster: Training, Confidentiality, and Reliability

A `ProgramCoordinator` registers a volunteer with a `full_name` and `phone`; `languages` (ISO 639-1 codes the volunteer can call in) defaults to English only when omitted or empty, and `max_weekly_minutes` — the weekly cap on assigned slot-plus-buffer minutes — defaults to 240 and must lie between 60 and 600. A new volunteer is an `APPLICANT` with `reliability_tier` `SILVER`, since there is no history to judge. Beginning training moves them `APPLICANT` → `IN_TRAINING`.

Certification is the gate that turns training into duty, moving a volunteer from `IN_TRAINING` (or from `LAPSED`, on recertification) to `ACTIVE`. Two currency checks must both pass. First, the volunteer must hold training records whose status is `VALID` for all three required modules — `SAFETY_PROTOCOL`, `LISTENING_SKILLS`, and `MANDATED_REPORTING` — failing with `ERR_VOLUNTEER_NOT_CERTIFIED` otherwise. Second, the volunteer must hold an `ACTIVE` confidentiality agreement whose `policy_version` equals the program's `current_policy_version` and whose `valid_until` the clock has not reached, failing with `ERR_CONFIDENTIALITY_NOT_CURRENT` otherwise. Certification also initializes the reliability fields from whatever assignment history exists — the tier stays `SILVER` while the observation pool holds fewer than ten assignments.

Training records are coordinator-entered: each names a `module` (one of the three required modules or `CONFIDENTIALITY_BASICS`, which is recordable but plays no part in the certification gate), a `completed_at` timestamp, and a `valid_until` expiry. A record's status is computed against the logical clock: `VALID` while the clock has not passed `valid_until`, `EXPIRED` once the clock is strictly past it. Confidentiality agreements are the volunteer's own act: a `VolunteerCaller` signs under their own record (ownership enforced per §2.1) by supplying the `policy_version` being signed and a `valid_until`; `signed_at` is stamped by the server. Exactly one agreement per volunteer is `ACTIVE` at any time — a new signature moves the previously `ACTIVE` agreement to `SUPERSEDED`. A `QualityReviewer` may revoke an `ACTIVE` agreement (it becomes `REVOKED`; any other state fails with `ERR_INVALID_STATE`), after which the volunteer fails every currency check until a fresh agreement is signed and lapses at the next daily closeout. An agreement whose `valid_until` is strictly past expires at closeout (becoming `EXPIRED`) and fires the same lapse cascade within that run.

Deactivation moves an `ACTIVE` volunteer to `INACTIVE`: their existing `SCHEDULED` assignments are deliberately not cancelled — the volunteer may return — but no new assignments may be created for them. Reactivation returns an `INACTIVE` volunteer to `ACTIVE` only after re-running the same training and confidentiality currency checks as certification (`ERR_VOLUNTEER_NOT_CERTIFIED` and `ERR_CONFIDENTIALITY_NOT_CURRENT` respectively). Separation is permanent: from any status except `SEPARATED` — the terminal state — a coordinator may separate a volunteer, which cancels every future-dated `SCHEDULED` assignment of theirs with `cancel_reason` `MANUAL`.

Lapse is the system's own enforcement. When the daily closeout finds an `ACTIVE` volunteer whose required training record has expired, whose `ACTIVE` agreement has expired, or whose agreement's `policy_version` no longer matches the program's `current_policy_version`, the volunteer moves `ACTIVE` → `LAPSED`; every future-dated `SCHEDULED` assignment of theirs is cancelled with `cancel_reason` `VOLUNTEER_LAPSED`, and each such cancellation marks the affected participant `coverage_deficient` (§3.5).

Reliability is recomputed after every call-log creation, after every assignment expiry at closeout, and at certification. The observation pool contains the volunteer's assignments whose `scheduled_date` falls within the trailing twenty-eight days — strictly after the date twenty-eight days before today, and on or before today — and whose status is `COMPLETED`, `UNREACHED`, or `EXPIRED`. When the pool holds fewer than ten assignments, `reliability_windowed` and `reliability_streak_adj` are null and the tier remains `SILVER`. With ten or more, the showed-up count is the pool's `COMPLETED` and `UNREACHED` rows — an `UNREACHED` row is a participant-side miss, not a volunteer no-show — and `reliability_windowed` is the showed-up count divided by the pool size, multiplied by 100, rounded half-up to one decimal place. The streak is the length of the trailing run of `EXPIRED` rows when the pool is ordered by `scheduled_date` ascending, then `window_start` ascending, then `created_at` ascending; `reliability_streak_adj` is `reliability_windowed` minus 5 points per consecutive trailing miss, floored at zero, and is strictly below `reliability_windowed` whenever the most recent rows contain an unbroken expired run. `reliability_tier` bands the windowed value: `GOLD` at 95.0 or above, `SILVER` at 80.0 or above, `BRONZE` at 60.0 or above, and `PROBATION` below that. The tier in turn sets `max_concurrent_assignments`: 12 for `GOLD`, 10 for `SILVER`, 8 for `BRONZE`, and 4 for `PROBATION`. Coordinators can filter the volunteer list by `status` or by `reliability_tier`.

### 3.5. Schedules, Availability, and Assignment Booking

A participant's call schedule expresses the intended weekly rhythm. Creating one requires the participant to be `ENROLLED` — schedule creation, assignment creation, and survey issuance demand that status and fail with `ERR_PARTICIPANT_NOT_ENROLLED` otherwise, while the later schedule transitions (pause, resume, archive) do not re-check it — and supplies a `weekday` (one of `MON`, `TUE`, `WED`, `THU`, `FRI`, `SAT`, `SUN`), a `window_start`, and a `window_end` (both `HH:MM` 24-hour strings). The window is half-open, beginning at `window_start` and ending before `window_end`; the start must be before the end, and the total window must run at least 15 and at most 120 minutes, with malformed specifications rejected as `ERR_INVALID_REQUEST`. At most one schedule per participant per weekday may be `ACTIVE` or `PAUSED` at once — a second such schedule for the same weekday is rejected with `ERR_DUPLICATE_SCHEDULE`. Schedules start `ACTIVE`; a coordinator may pause one (`ACTIVE` → `PAUSED`), resume it (`PAUSED` → `ACTIVE`), or archive it (from `ACTIVE` or `PAUSED` to `ARCHIVED`, which is terminal and leaves existing assignments untouched). Every one of these mutations recomputes the participant's `coverage_deficient`.

Coverage is measured against the participant's `effective_acuity_tier`: five sessions per week are required for `CRITICAL`, three for `HIGH`, two for `MODERATE`, and one for `LOW`. The planned weekly level is simply the count of the participant's `ACTIVE` schedules. `coverage_deficient` turns true when the planned level falls below the required level, or when a future-dated `SCHEDULED` assignment was cancelled without replacement. It clears back to false only when the planned level again meets the requirement and every `ACTIVE` weekday schedule for the coming seven days has at least one future-dated `SCHEDULED` assignment or an assignment already completed this week.

Volunteers describe when they can work through availability windows. A coordinator — or the volunteer acting on their own record — creates one with a `weekday`, a half-open `window_start`/`window_end` pair (end strictly after start), an `effective_from` date, and an optional `effective_to` date that is inclusive and may be null for an open-ended window. An `effective_to` earlier than `effective_from` is rejected with `ERR_INVALID_REQUEST`. A new window that overlaps an existing window of the same volunteer on the same weekday — overlap judged under half-open semantics, and only when their effective ranges overlap as well — is rejected with `ERR_AVAILABILITY_OVERLAP`. Windows can be listed (filterable by `weekday`) and deleted.

Booking an assignment is the system's most heavily guarded write. A coordinator supplies `participant_id`, `scheduled_date` (a `YYYY-MM-DD` date), `window_start`, and `window_end` (`HH:MM` 24-hour strings); `volunteer_id` is optional, and `source` is optional with default `REGULAR` — `MAKEUP` is available for rescheduled-style gaps, while `ESCALATION_RETRY` is system-set only, and requesting it is rejected with `ERR_INVALID_REQUEST`. The participant must be `ENROLLED`. Whether the volunteer is named explicitly or chosen by the selector, the same fitness checks apply: the volunteer must be `ACTIVE` with current training and a current confidentiality agreement (`ERR_VOLUNTEER_NOT_CERTIFIED`, `ERR_CONFIDENTIALITY_NOT_CURRENT`), the new window must lie inside an `ACTIVE` schedule of the participant for that weekday (`ERR_WINDOW_OUTSIDE_SCHEDULE`) and inside one of the volunteer's availability windows effective on the `scheduled_date` (`ERR_WINDOW_OUTSIDE_AVAILABILITY`), and when the participant's `primary_language` is not `en` the volunteer's `languages` must contain it — a language mismatch surfaces as `ERR_NO_ELIGIBLE_VOLUNTEER`, whether the volunteer was named explicitly or chosen by the selector, and never as `ERR_WINDOW_OUTSIDE_AVAILABILITY`. For a named volunteer the fitness checks evaluate in a fixed order — certification, confidentiality currency, schedule containment, availability containment, language, buffer-inclusive conflict, weekly load, concurrency cap — and the first failure surfaces.

Double-booking is judged with closed, buffer-inclusive intervals. An existing assignment occupies the span from its `window_start` through its `window_end` plus the program's `doc_buffer_minutes`, both bounds inclusive; a new assignment conflicts when its start falls at or before an existing assignment's buffered end while that existing assignment's start falls at or before the new assignment's buffered end — considering only the volunteer's `SCHEDULED` assignments on the same `scheduled_date`. Touching at the buffered endpoint is a conflict: with the default fifteen-minute buffer, an existing 09:00–09:30 assignment occupies through 09:45 inclusive, so a new assignment starting at 09:45 is rejected with `ERR_ASSIGNMENT_WINDOW_CONFLICT`, while one starting at 09:46 is not. Availability windows, by contrast, remain half-open with no buffer.

Load and concurrency caps bound the volunteer's week. A volunteer's `current_week_minutes` sums, over their assignments whose `scheduled_date` falls in the current ISO week (weeks begin Monday) and whose status is `SCHEDULED`, `COMPLETED`, or `UNREACHED`, the window length in minutes plus one `doc_buffer_minutes` allowance each; `CANCELLED` and `EXPIRED` rows contribute nothing. Admitting a new or rescheduled assignment requires that the volunteer's weekly minutes for the ISO week containing the new assignment's `scheduled_date` — the same per-assignment sum as `current_week_minutes`, but taken over the booking's own week, which differs from the clock's current week when booking ahead — plus the new slot's minutes plus its buffer allowance not exceed the volunteer's `max_weekly_minutes` — the bound is inclusive, so landing exactly on the cap is allowed, while anything strictly above is rejected with `ERR_WEEKLY_LOAD_EXCEEDED`. Separately, the volunteer's count of future-dated `SCHEDULED` assignments must be below their `max_concurrent_assignments` tier cap; at the cap, creation fails with `ERR_MAX_ASSIGNMENTS_REACHED`.

When `volunteer_id` is omitted, a deterministic selector chooses. The eligibility filter requires every clause: the volunteer is `ACTIVE`; their training records are `VALID` for `SAFETY_PROTOCOL`, `LISTENING_SKILLS`, and `MANDATED_REPORTING`; they hold an `ACTIVE` agreement matching `current_policy_version` whose `valid_until` the clock has not passed; they have an availability window containing the requested half-open window on the `scheduled_date`'s weekday, effective on that date; their `languages` cover a non-`en` `primary_language` when required; no buffer-inclusive conflict exists against their `SCHEDULED` assignments that date; the weekly-load check passes; and their future-dated `SCHEDULED` count is below their concurrency cap. The pool is then ranked by the booking-week minutes sum of the load rule above ascending (least-loaded first), then by reliability tier from `GOLD` down through `SILVER` and `BRONZE` to `PROBATION`, then by the volunteer's `created_at` ascending — never by identifier. An empty pool is rejected with `ERR_NO_ELIGIBLE_VOLUNTEER` for a direct creation; the same emptiness is absorbed differently by the system-driven uses described in §3.6 and §3.7. A created assignment lands in `SCHEDULED` with `version` 1, and the volunteer's `current_week_minutes` and the participant's `coverage_deficient` are recomputed.

Rescheduling supersedes rather than edits. The coordinator supplies `new_scheduled_date`, `new_window_start`, and `new_window_end`; the original assignment is cancelled with `cancel_reason` `RESCHEDULED` and its `version` incremented, and a fresh assignment is created carrying `rescheduled_from_id` pointing at the original, keeping the original's volunteer, `source`, and `escalation_id`, with every create-time check — certification and confidentiality currency, schedule containment, availability, language, conflict, load, caps — re-applied to the new window, the original row excluded from its own conflict check, and the participant's enrollment status not re-checked. Because the original row is no longer `SCHEDULED`, attempting to reschedule that same row a second time fails the state precondition. Plain cancellation by a coordinator moves a `SCHEDULED` assignment to `CANCELLED` with `cancel_reason` `MANUAL` and recomputes the volunteer's `current_week_minutes` and the participant's `coverage_deficient`. Cancellation also arrives through cascades with their own reasons — `PARTICIPANT_SUSPEND` on suspension, `WELFARE_HOLD` on a welfare hold, `VOLUNTEER_LAPSED` on a lapse, `MANUAL` on disenrollment or separation. Assignment lists can be filtered by `participant_id`, `volunteer_id`, `escalation_id`, `rescheduled_from_id`, `status`, or `scheduled_date`.

### 3.6. Participation Interruptions: Suspension, Holds, Disenrollment, Reapplication

An enrolled participant can be paused without being lost. Suspension by a `ProgramCoordinator` moves `ENROLLED` → `SUSPENDED` with a `reason`: every `SCHEDULED` assignment is cancelled with `cancel_reason` `PARTICIPANT_SUSPEND`, each cancellation recomputing the affected volunteer's `current_week_minutes` and the participant's `coverage_deficient` (which turns true because future coverage was removed). The participant keeps occupying a program slot — `occupied_slots` does not change. Resumption moves `SUSPENDED` → `ENROLLED` and rebuilds near-term coverage: for each `ACTIVE` call schedule whose next occurrence falls within the coming seven days, one new `REGULAR` assignment is created, its window running from the schedule's `window_start` through thirty minutes later (the end capped at 23:59) on that occurrence date, staffed by the volunteer selector. When the selector pool is empty for a weekday, no assignment is created for it and `coverage_deficient` is set true; the flag is recomputed once regeneration finishes.

A welfare hold is the system's interruption, not a coordinator's. When an escalation for the participant enters `STEP_3_WELFARE` (§3.7), an `ENROLLED` participant moves to `WELFARE_HOLD`: every future-dated `SCHEDULED` assignment is cancelled with `cancel_reason` `WELFARE_HOLD`, each cancellation recomputing its volunteer's weekly minutes, and the participant continues to occupy a slot. Release is likewise system-driven: once the escalation has resolved and no welfare check with disposition `ASSIST_NEEDED` or `NOT_FOUND` remains actionable, the participant returns from `WELFARE_HOLD` to `ENROLLED` — the no-answer streak resets to zero, assignments are regenerated exactly as a resumption would regenerate them, and `coverage_deficient` is recomputed.

Disenrollment is the deliberate exit: a coordinator may disenroll from `ENROLLED`, `SUSPENDED`, or `WELFARE_HOLD` (anything else fails with `ERR_INVALID_STATE`), recording a `reason`. The participant becomes `DISENROLLED`; `occupied_slots` decreases by one and the program's `version` increments; every still-`SCHEDULED` assignment is cancelled with `cancel_reason` `MANUAL`; and `last_status_change_at` is stamped. Every status transition in this subsection — suspension, resumption, hold entry and release, disenrollment — refreshes `last_status_change_at`.

Reapplication is the way back. From `DENIED`, `DISENROLLED`, or `EXITED`, an `IntakeWorker` may re-open the participant as `APPLICANT`, but only once the logical clock has reached `last_status_change_at` plus the program's `reapply_cooling_days` (thirty days by default); earlier attempts fail with `ERR_REAPPLICATION_TOO_SOON`. Reapplication clears the acuity fields — they are recomputed at the next review submission — and resets `consecutive_no_answer_count` to zero, stamping `last_status_change_at` anew.

### 3.7. Call Outcomes and the No-Answer Protocol

Every call ends in a log. The assigned `VolunteerCaller` records it — acting on another volunteer's assignment fails ownership with `ERR_NOT_OWN_RESOURCE` — and a `ProgramCoordinator` may log as a fallback. The log carries `called_at` (which must not be after the logical clock, failing with `ERR_FUTURE_DATED_CALL_LOG` otherwise), `duration_seconds` (zero or more), the `outcome` (`REACHED_OK`, `REACHED_CONCERN`, `NO_ANSWER`, `BUSY`, `REFUSED`, or `WRONG_NUMBER`), a `concern_level` (default `NONE`; otherwise `ROUTINE`, `URGENT`, or `IMMEDIATE_DANGER`), `concern_categories` (default empty; a subset of `HEALTH`, `SAFETY`, `MOOD`, `NUTRITION`, `MEDICATION`, `HOUSING`, `OTHER`), `follow_up_needed` (default false), an optional `follow_up_plan`, `supervisor_notified` (default false), and free-text `notes`. Each log is bound to its `assignment_id`, and exactly one log exists per assignment: the log is append-only, the first log moves the assignment out of `SCHEDULED`, and a second attempt fails the state gate. The `concern_flag` is computed — true exactly when the outcome is `REACHED_CONCERN` or the `concern_level` is anything other than `NONE`. When `concern_level` is `IMMEDIATE_DANGER`, three fields become mandatory together: `follow_up_needed` must be true, `supervisor_notified` must be true, and `follow_up_plan` must be non-empty — the triplet failing with `ERR_SAFETY_FIELDS_REQUIRED`.

Outcomes split into two families with opposite effects on the participant's `consecutive_no_answer_count`. A log of `REACHED_OK`, `REACHED_CONCERN`, or `REFUSED` moves the assignment to `COMPLETED` and resets the streak to zero. A log of `NO_ANSWER`, `BUSY`, or `WRONG_NUMBER` moves the assignment to `UNREACHED` — which still counts as showed-up for the volunteer's reliability, since the miss is participant-side — and increments the streak by one. Either way, the volunteer's reliability fields are recomputed.

The streak is what arms the no-answer protocol, and its boundary is inclusive: when an increment raises `consecutive_no_answer_count` to at least the program's `no_answer_threshold` (three by default) and the participant's `open_escalation_id` is null, the system opens an escalation with `trigger_type` `NO_ANSWER_PROTOCOL` at stage `STEP_1_RETRY`, points `open_escalation_id` at it, and creates a retry assignment whose `source` is `ESCALATION_RETRY`, whose thirty-minute window (its end capped at 23:59) starts at the logged `called_at` on that same date, staffed through the volunteer selector and linked back through `escalation_id`. If the selector pool is empty, the escalation still opens with `retry_assignment_id` left null. Logs recorded while an escalation is already open still move the streak but never open a second case.

A separate, faster path exists for immediate danger: when a logged call has outcome `REACHED_CONCERN` with `concern_level` `IMMEDIATE_DANGER`, the system opens an escalation with `trigger_type` `CONCERN_IMMEDIATE` directly at `STEP_3_WELFARE`, creating the welfare check request and running the welfare-hold cascade at once. A coordinator may also open a case by hand — the request names the `participant_id`, a `trigger_type` of `MANUAL` (which enters at `STEP_1_RETRY`) or `CONCERN_IMMEDIATE` (which enters at `STEP_3_WELFARE` with the welfare check and hold cascade), an optional `note`, and the concurrency anchor `expected_participant_version` (§2.7). Every opening records the caller's `X-User-ID` as `opened_by_user_id` — the literal value `system` for auto-opened cases — stamps `opened_at` and `stage_entered_at`, and increments the participant's `version`.

Opening a case while another is open for the same participant supersedes the old one: the prior case closes as `CLOSED_SUPERSEDED`, the new case records it in `supersedes_escalation_id`, and the participant's `open_escalation_id` repoints to the new case. A welfare check still in `REQUESTED` or `DISPATCHED` under the superseded case remains valid, and its eventual completion resolves the new case.

Once open, the case climbs a three-step ladder, advanced by a coordinator or by the daily closeout under the same eligibility rule. From `STEP_1_RETRY` to `STEP_2_CONTACT`, advancement requires either at least one no-answer-family log (`NO_ANSWER`, `BUSY`, or `WRONG_NUMBER`) recorded on the retry assignment, or the clock having reached `stage_entered_at` plus the program's `escalation_retry_hours` (four hours by default); otherwise the advance fails with `ERR_ESCALATION_STEP_NOT_DUE`. From `STEP_2_CONTACT` to `STEP_3_WELFARE`, advancement requires either every `ACTIVE` emergency contact of the participant to have at least one entry in `contact_attempts`, or the clock having reached `stage_entered_at` plus `contact_phase_hours` (twenty-four hours by default); the same `ERR_ESCALATION_STEP_NOT_DUE` guards a premature advance. Any advance, resolution, or contact-attempt recording attempted on a terminal case fails with `ERR_NO_OPEN_ESCALATION`. Advancing a case already at `STEP_3_WELFARE` fails with `ERR_INVALID_STATE`, and recording a contact attempt is valid only at `STEP_2_CONTACT` — at any other open stage it fails with `ERR_INVALID_STATE`. Each advance resets `stage_entered_at` to the clock, and entering `STEP_3_WELFARE` creates the `WelfareCheckRequest` in `REQUESTED` with the participant denormalized onto it and runs the `WELFARE_HOLD` cascade of §3.6.

During the contact phase, a coordinator records each emergency-contact attempt with a `contact_id` and an `outcome` of `REACHED`, `UNREACHABLE`, or `REFUSED`; the attempt is appended to the case's `contact_attempts` with its `attempted_at`, and an `UNREACHABLE` outcome marks that emergency contact `UNREACHABLE`. Contacts are worked in the courtesy order of §3.2. Meanwhile, if the retry call succeeds — a log of `REACHED_OK`, `REACHED_CONCERN`, or `REFUSED` on the retry assignment — while the case is still at `STEP_1_RETRY`, the case resolves itself as `RESOLVED_OK`, resetting the participant's streak to zero and clearing `open_escalation_id`. Escalations can be listed and filtered by `participant_id`, `supersedes_escalation_id`, `retry_assignment_id`, or `stage`.

### 3.8. Welfare Checks, Resolution Governance, and Service Referrals

A welfare check request is born when an escalation enters `STEP_3_WELFARE`, stamped `requested_at` with its `escalation_id` and a denormalized `participant_id` for partner queries, and carrying `disposition` `NONE` until it is completed. From there an `ExternalResponder` drives it: dispatch moves `REQUESTED` → `DISPATCHED` and stamps `dispatched_at`; completion of a dispatched request stamps `completed_at`, records the partner's optional `note` as `responder_note`, and sets a `disposition` of `OK`, `ASSIST_NEEDED`, or `NOT_FOUND`; a request in `REQUESTED` or `DISPATCHED` may instead be declined with a `reason`, becoming `DECLINED` and leaving the escalation parked at `STEP_3_WELFARE` awaiting coordinator action. Acting on a request in the wrong state fails with `ERR_INVALID_STATE`.

The completion disposition drives the owning escalation automatically. `OK` resolves the case as `RESOLVED_OK`. `ASSIST_NEEDED` resolves it as `RESOLVED_WITH_REFERRAL` and auto-creates a `ServiceReferral` that skips the draft phase entirely: it arrives already `SUBMITTED`, at priority `URGENT`, with service type `HOME_HEALTH`, its `escalation_id` set, and `submitted_at` stamped at the clock (so `sla_due_at` falls 24 hours later). `NOT_FOUND` triggers no automatic resolution — a coordinator must disenroll the participant, or a reviewer must close the case once no requested or dispatched checks remain. The resolving dispositions also release the participant from `WELFARE_HOLD` back to `ENROLLED` per §3.6, resetting the streak and clearing `open_escalation_id`.

Manual resolution belongs to the `QualityReviewer`, and it is where segregation of duties bites: the resolver's `X-User-ID` must differ from the case's `opened_by_user_id`, failing with `ERR_SEGREGATION_OF_DUTIES` otherwise, and the case must still be open, failing with `ERR_NO_OPEN_ESCALATION` on a terminal one. The reviewer supplies a `resolution` with an optional `note` recorded as `resolution_note`; the available resolutions depend on the case's stage — `RESOLVED_OK` only from `STEP_1_RETRY`, `RESOLVED_CONTACT_CONFIRMED` from `STEP_1_RETRY` or `STEP_2_CONTACT`, and `CLOSED_FALSE_ALARM` from any stage — and a resolution not available at the current stage fails with `ERR_INVALID_STATE`. Two stage-specific guards apply: from `STEP_2_CONTACT`, a resolution of `RESOLVED_CONTACT_CONFIRMED` requires at least one `contact_attempts` entry with outcome `REACHED` (`ERR_INVALID_STATE` otherwise); and from `STEP_3_WELFARE`, a `CLOSED_FALSE_ALARM` is refused while any welfare check of the case remains in `REQUESTED` or `DISPATCHED` — it must be completed or declined first, failing with `ERR_INVALID_STATE` until then. Every manual resolution resets the participant's streak to zero and clears `open_escalation_id`; a false-alarm closure from the first two stages leaves the participant's status untouched, while closing from `STEP_3_WELFARE` runs the hold-release cascade for a held participant.

Service referrals carry identified needs to outside providers. A coordinator or reviewer creates one in `DRAFT` with a `participant_id`, a `service_type` (`MEALS`, `TRANSPORT`, `HOME_HEALTH`, `ADULT_DAY`, `CAREGIVER_SUPPORT`, or `BEHAVIORAL_HEALTH`), an optional `priority` (`URGENT`, `STANDARD`, or `ROUTINE`, defaulting to `STANDARD`), an optional `source_call_log_id` pointing at the call log that identified the need, and optional `notes`. Submitting the draft requires it to be in `DRAFT` (`ERR_INVALID_STATE` otherwise) and, when `source_call_log_id` is set, requires that log's `concern_flag` to be true — a referral sourced from an unflagged log fails with `ERR_CONCERN_NOT_FLAGGED`. Submission stamps `submitted_at` and computes `sla_due_at` as `submitted_at` plus the priority's response window: 24 hours for `URGENT`, 72 for `STANDARD`, or 168 hours — one week — for `ROUTINE`. A referral reads as `overdue` exactly while its status is `SUBMITTED` and the logical clock is strictly later than `sla_due_at`; at the precise deadline instant it is not yet overdue.

The provider-facing loop continues from `SUBMITTED`: acceptance moves the referral to `ACCEPTED`; a decline moves it to `DECLINED` with the optionally supplied `reason` captured in `decline_reason` (null when omitted). A declined referral can be reworked — revision returns it `DECLINED` → `DRAFT`, clearing `decline_reason` and clearing both `submitted_at` and `sla_due_at` until it is resubmitted. Withdrawal is allowed from `DRAFT` or `SUBMITTED` and is terminal, as is closure: a `QualityReviewer` closes an `ACCEPTED` referral into `CLOSED`. Referral lists can be filtered by `participant_id`, `escalation_id`, `source_call_log_id`, `status`, or `overdue`.

### 3.9. Closeout, Surveys, and Outcome Reporting

The daily closeout run, invoked by a `ProgramCoordinator` against a program, is the sole driver of time-based transitions — nothing expires lazily on a read. A single run performs seven duties. It expires every `SCHEDULED` assignment whose `scheduled_date` is before the current date and which has no call log, moving it to `EXPIRED` — a volunteer miss for reliability purposes — and recomputing the participant's `coverage_deficient`. It requeues every `OFFERED` waitlist entry whose expiry is strictly past, per §3.3. It lapses every `ACTIVE` volunteer whose required training or agreement has expired or whose agreement's policy version has gone stale, running the cancellation cascade of §3.4. It expires every satisfaction survey still `ISSUED` past its validity. It advances escalations whose step deadline has passed under the same eligibility rule a manual advance uses. It recomputes the rolling acuity of every participant in `ENROLLED`, `SUSPENDED`, or `WELFARE_HOLD`, and refreshes volunteer reliability. And it applies the referral SLA sweep so `overdue` flags reflect the clock. The run returns the identifiers of everything it touched — `expired_assignment_ids`, `expired_offer_entry_ids`, `lapsed_volunteer_ids`, `expired_survey_ids`, and `advanced_escalation_ids` — and increments the program's `version` by one.

Rolling acuity is how outcome signals feed back into risk. The signal window covers the trailing thirty days: the participant's call logs whose `called_at` falls between thirty days before the clock and the clock itself, reached through their assignments. Four counts feed the signal — logs in the window with `concern_flag` true, weighted 15 each; logs with outcome `NO_ANSWER`, `BUSY`, or `WRONG_NUMBER`, weighted 10 each; the participant's escalations with `opened_at` in the window, weighted 25 each; and the participant's referrals with `submitted_at` in the window, weighted 10 each — and the signal itself is that weighted sum, capped at 100. `rolling_acuity_score` blends the static and the observed: seventy percent of the intake `acuity_score` plus thirty percent of the signal, rounded half-up to one decimal place. `rolling_acuity_tier` applies the same band boundaries as the intake tier — 29, 59, and 84 — to the rolling score. `effective_acuity_tier` is the more severe of the two tiers under the ordering from `LOW` through `MODERATE` and `HIGH` to `CRITICAL`; until the first post-enrollment closeout produces a rolling value, the rolling fields are null and the effective tier simply equals the intake tier.

Satisfaction is measured monthly. An `IntakeWorker` issues a survey to an enrolled participant for a `period_month` (a `YYYY-MM` string); at most one survey exists per participant per period, a duplicate failing with `ERR_SURVEY_PERIOD_DUPLICATE`. The survey is `ISSUED` with `issued_at` at the clock, and remains returnable for the program's `survey_valid_days` (thirty days by default) — the closeout moves one strictly past that boundary to `EXPIRED`. Returning the survey records `items`: exactly five integers, each from 1 to 5, in the fixed order companionship, mood, safety, usefulness, overall. Returning is valid only while the survey is `ISSUED`; a return against any other status fails with `ERR_INVALID_STATE`. The return moves the survey to `SCORED` and computes `survey_mean` as the weighted sum of the five items with weights one, two, one, one, and two respectively, divided by seven, rounded half-up to two decimal places.

The monthly outcome report aggregates all of this for a `QualityReviewer`. Generating a report for a program and a `period_month` produces a `PROVISIONAL` report stamped with its `program_id`; finalizing is allowed only once the logical clock has passed the last instant of that period — while the period is still open the request fails with `ERR_REPORT_PERIOD_OPEN` — and recomputes every metric under the final variant, leaving the report `FINALIZED`; finalizing a report that is not `PROVISIONAL` fails with `ERR_INVALID_STATE`. Five counts are variant-independent: `escalations_opened` counts escalations of the program's participants with `opened_at` in the period; `escalations_resolved` counts escalations reaching any `RESOLVED_` stage in the period; `referrals_submitted` counts referrals with `submitted_at` in the period; `unique_participants_reached` counts the distinct participants with a call log outcome of `REACHED_OK`, `REACHED_CONCERN`, or `REFUSED` and `called_at` in the period; and `calls_completed` counts assignments whose `scheduled_date` falls in the period and whose status is `COMPLETED`.

The completion rate is where the two variants diverge, and only in the denominator. Under the provisional variant, `calls_scheduled` counts assignments whose `scheduled_date` falls in the period and is not after today, and the denominator counts only those whose status is `COMPLETED`, `UNREACHED`, or `EXPIRED` — past-due rows still sitting in `SCHEDULED` are excluded. Under the final variant, `calls_scheduled` counts every assignment of the period not `CANCELLED`, and the denominator is that same count, so rows still `SCHEDULED` count as misses. In both, `completion_rate` is `calls_completed` divided by the denominator, multiplied by 100, rounded half-up to one decimal place, and null when the denominator is zero; for identical data containing a past-due still-scheduled assignment, the provisional rate strictly exceeds the final rate. The report's `satisfaction_index` is the mean of `survey_mean` over the program's `SCORED` surveys for the period, rounded half-up to two decimal places, and null when no scored surveys exist. The rounding order is pinned — each survey's mean is rounded to two decimals before the aggregation, and the alternative of pooling raw weighted item scores across surveys and dividing once is explicitly not used: the surveys [5,4,3,4,5] and [1,1,1,1,1] yield an index of 2.65 under the pinned order, where pooling would yield 2.64. Reports can be listed per program and filtered by `period_month`.
