# Home-Staging & Real-Estate Prep API — Product Requirements Document

## 1. Introduction

Selling a house well is a logistics problem dressed up as a design problem. Two families walk into the same staging company on the same morning; one is still living in the home with their own sofa, their own clutter and their own school-run schedule, and the other has already moved out and left four empty bedrooms behind. Those two engagements look identical on a brochure and share almost nothing operationally. The occupied home is prepared through a series of short, billable consultant visits inside a fixed service window, priced by the hour, using furniture that is already there. The vacant home is furnished from a warehouse and from partner rental houses, installed in a single crew day, leased in whole thirty-day cycles, photographed, and eventually de-staged by a pickup crew who inspect every returned piece for damage. This service runs both businesses at once, and this document specifies the single API that governs them.

The platform described here is mounted under `/staging`. It coordinates seven parties — the operator's own coordinators, warehouse staff and billing clerks, plus listing agents, sellers, brokerage back offices and partner rental vendors — around a shared set of records: properties, MLS listings, consultations and their room-by-room scope, projects, inventory pulls and their lines, vendor rental orders, installs, visits, leases, extensions, pickups, damage assessments, photography sessions, invoices and deposits. Money moves in every direction: deposits are taken up front at a percentage that depends on who is paying, overages are charged when a package is outgrown, holdover accrues when nobody lets the pickup crew in, damage is depreciated against the age of the piece, tax is applied to a base that differs by payer, and a deposit residue is either refunded or forfeited at the end.

Two design commitments shape everything that follows. The first is that **both pipelines walk the same numbered rejection ladder**: authentication, authorization, party scope, ancestor freezes, state preconditions, optimistic concurrency, business authority, capacity, and finally money — in that order, always, on every mutating endpoint. Nothing about the occupied arm re-orders that ladder; it merely skips the rungs about furniture that it never touches. The second is that **derived money is derived the same way every time**: fixed component order, per-line rounding before summation, half-up to two decimal places, and an evaluation order that is pinned wherever a value could otherwise appear to depend on itself. An implementation that honours those two commitments will reproduce this specification; one that improvises on either will not.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to this API carries two headers. `X-User-Role` names the role the caller is acting as, and `X-User-ID` identifies the specific actor. A request that omits `X-User-Role` entirely is rejected with `ERR_UNAUTHENTICATED` (HTTP 401), and so is a request whose `X-User-Role` names a string that is not one of the eight declared roles — the two cases share one error code deliberately, because the server does not tell an anonymous caller which role names exist.

The eight roles are `PlatformAdmin`, `StagingCoordinator`, `WarehouseManager`, `BillingClerk`, `ListingAgent`, `Seller`, `BrokerageAdmin` and `VendorRep`. They split into two identity families.

Four of them are **operator roles whose identity is opaque**. When `X-User-Role` is `PlatformAdmin`, `StagingCoordinator`, `WarehouseManager` or `BillingClerk`, the value of `X-User-ID` is an operator identifier that is not tied to any persisted entity. The server may record it in an audit sense but never compares it to any row's `id`, and no ownership check anywhere in the system consults it. `PlatformAdmin` is the operator superuser: it owns the logical clock, the configuration entities, damage-appeal adjudication, invoice voiding and deposit forfeiture. `StagingCoordinator` runs execution — consultations, scope drafting, project creation, installs, visits, pickups, photo shoots and extension application. `WarehouseManager` owns stock: inventory items, pulls, pull lines, rental orders, damage assessment and extension adjudication; under this service's segregation-of-duties model a `WarehouseManager` may never authorize a project, issue an invoice or take a payment. `BillingClerk` owns money movement — deposits, invoices and holdover accrual — and correspondingly may never adjudicate damage, run an allocation pass or authorize a project.

Four of them are **entity-backed roles**, and for these `X-User-ID` is a real primary key. When `X-User-Role` is `ListingAgent`, `X-User-ID` is the `id` of the acting `Client` row; ownership checks compare it against the `listing_agent_client_id` of the `Listing` being touched, reached either directly or through the `listing_id` of the project in the path. When `X-User-Role` is `Seller`, `X-User-ID` is likewise the `id` of the acting `Client` row, and ownership checks compare it against the `owner_client_id` of the `Property` being touched. When `X-User-Role` is `BrokerageAdmin`, `X-User-ID` is the `id` of the acting `Brokerage` row, and ownership checks compare it against the `brokerage_id` of the project being touched. When `X-User-Role` is `VendorRep`, `X-User-ID` is the `id` of the acting `VendorPartner` row, and ownership checks compare it against the `vendor_id` of the rental order being touched. If any of these four roles is presented without an `X-User-ID` header, the request is rejected with `ERR_IDENTITY_REQUIRED` (HTTP 401); the four opaque operator roles are not required to supply one.

Authorization proper is a table lookup: §4 lists, for every endpoint, the exact set of roles permitted to invoke it, and a caller whose role is absent from that set is rejected with `ERR_UNAUTHORIZED` (HTTP 403). Being permitted by role is not the same as being a party to the record, and the two are separate rungs — a `ListingAgent` who is authorized to record a listing going under contract, but who is not that listing's own agent, gets `ERR_NOT_LISTING_AGENT` (HTTP 403) rather than `ERR_UNAUTHORIZED`. The parallel codes are `ERR_NOT_PROPERTY_OWNER` (HTTP 403) when an acting `Seller` is not the property's owner, `ERR_NOT_PROJECT_PARTY` (HTTP 403) when an acting `BrokerageAdmin`'s identity does not match the project's `brokerage_id`, and `ERR_NOT_ORDER_VENDOR` (HTTP 403) when an acting `VendorRep`'s identity does not match the rental order's `vendor_id`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every collection endpoint accepts two optional query parameters. `limit` defaults to 10 when it is not supplied, may not be smaller than 1, and may not be larger than 100. `offset` defaults to 0 and counts records skipped from the start of the ordered result. A `limit` outside the range 1 through 100 inclusive, or an `offset` that is not a non-negative integer, is a shape violation and is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

Unless a subsection below says otherwise, list results are ordered by `created_at` ascending, and ties are broken by `id` ascending so that paging is stable. **That tie-break is the common case, not the corner case.** `created_at` is read from the logical clock of §2.5, which never advances on its own, so every row minted between two repositionings of the clock carries the identical `created_at` and the whole page is in fact ordered by `id` — that is, by UUID, which bears no relation to the order the rows were written in. The per-entity processing orders §3 names — "ascending order of the line's creation timestamp" for the allocation pass and the rent and extension sums, ascending `sequence_index` for scope items, ascending `visit_index` for visits — are a different rule and **do** fall back to true write order on a tie, so the sequence a calculation walks and the sequence a list endpoint returns can differ for the same set of rows. The `meta` block of every list response carries `limit`, `offset`, `total_count` and `has_more`; `total_count` is the number of records matching the filters before pagination is applied, and `has_more` is true exactly when `offset` plus the number of returned records is smaller than `total_count`. Filters named in an endpoint's parameter list narrow the result set before `total_count` is computed, and a query parameter an endpoint does not declare is ignored outright rather than refused. An `offset` at or beyond `total_count` is not an error either: it returns an empty `data` array with `has_more` false and the unchanged `total_count`. A filter value is compared for equality against the stored attribute and is **never validated against an enumeration**: an unrecognised filter value is not an error, it simply selects the records whose attribute equals it, which is ordinarily none. The one boolean filter, `is_reshoot` on the photo-shoot list, reads `true`, `1` or `yes` in any case as true and every other value as false.

### 2.4. Common Resource Properties, Timestamps and Version Semantics

Every stored record carries a server-minted `id`. It is a UUID string with no type prefix of any kind — no `proj_`, no `lease-`, nothing but the UUID itself — and clients never supply it. Every record also carries `created_at`, an ISO 8601 UTC timestamp with exactly three fractional digits, fixed at the instant of creation as read from the logical clock described in §2.5.

**One canonical rendering serves every instant in every response body.** Whether an instant was minted by the server from the logical clock, supplied by the caller in a request body, or derived by adding days or minutes to some anchor, it is rendered as ISO 8601 UTC with exactly three fractional digits and a trailing `Z`. A caller-supplied instant is parsed and re-rendered in that form rather than echoed verbatim, so a `scheduled_at` sent as `2026-06-01T00:00:00Z` reads back as `2026-06-01T00:00:00.000Z`, and a derived instant preserves the time-of-day of the anchor it was derived from. The single exception is the envelope's `meta.api_request_timestamp`, which is a transport-level stamp taken from the host's real clock and not from the logical clock.

Twenty-one of the twenty-two entity types additionally carry `updated_at` and `version`. `updated_at` is an ISO 8601 UTC timestamp with three fractional digits, refreshed on every mutation of that row. `version` is an integer that begins at 1 when the row is created and increments by exactly 1 on every mutation of that row. The rule that matters most for correctness is that **the version increment happens before the response body is serialised**: a mutating call returns the row as it stands after the write, so the `version` in the response is the new value, and a client that immediately replays that value into an optimistic-concurrency field (§2.9) must be accepted, not rejected. The same applies to every computed attribute — a response body reflects post-write state, never a snapshot taken before the handler's own effects landed.

`PackageTier` is the single exception. Package tiers are configuration, declared once and immutable thereafter; a `PackageTier` row carries `id` and `created_at` only. It has no `updated_at` field, no `version` field, and no update endpoint. Nothing in the system ever bumps a tier.

**The free-form notes this API accepts are validated and then withheld.** A listing's `termination_reason`, a consultation's `rejection_note`, an assessment's `dispute_note`, and the `reason` required on an inventory write-off, an invoice void and a deposit forfeit are each checked for presence and string type at rungs 6 and 8 and then recorded internally at most; none of them appears on any response body, and no endpoint reads one back. The same is true of the vendor line set an extension adjudication marks as returned: the decision is remembered so that `/apply` can act on it, but only the `returned_line_count` is published.

When one operation mutates several rows — and in this system that is the normal case rather than the exception — every row that changes takes its own `version` increment and its own `updated_at` refresh. A cascade that touches a `Listing`, a `Project`, a `Lease` and a `Pickup` bumps four versions, not one. **The increment is counted per row per request, not per hop**: where several numbered hops of one cascade write the same row — as hops one and two of install completion both write the lease — that row takes exactly one increment for the whole request. The single exception is a transition the specification names as a separate arc of its own: applying an extension walks the lease `ACTIVE → EXTENDED` and then, as a distinct system transition, `EXTENDED → ACTIVE`, and the lease's `version` therefore rises by two in that one request (§3.5). Where a cascade's arithmetic is described later as "re-derived", that means the derived attributes are recomputed from current inputs and stored, and the owning row is treated as mutated for versioning purposes. A field the service keeps for its own bookkeeping and never publishes on any resource — the instant a project's de-stage began, the running package-adjustment total, the running closing-escalation total — is not an attribute for this purpose, and writing one alone does not bump the row.

### 2.5. The Logical Clock

This service does not read wall-clock time for business decisions. It keeps a **logical clock**, and every temporal comparison in this document — "on or after the scheduled instant", "past the pickup window", "months overdue" — is evaluated against that clock. Before any client repositions it, the logical clock reads exactly `2026-05-01T00:00:00Z`. That default is fixed and must not fall back to the host's real time under any circumstance, including a fresh process start.

A `PlatformAdmin` may reposition the clock by supplying a `to_iso8601` instant; the response reports the new setting as `current_utc`. Repositioning the clock mutates no entity: nothing is created, no state advances, no version is bumped. It simply changes what every subsequent handler believes the current instant to be. Times may move forward or backward, and the service performs no reconciliation of records created under an earlier setting.

### 2.6. Path Resolution, Request Shape and Value Ranges

Path parameters are resolved **strictly left to right**, and the first unresolved segment decides the error. A request against a pull line nested under a pull whose pull does not exist reports the missing pull, not the missing line. Each entity has its own not-found code: `ERR_BROKERAGE_NOT_FOUND`, `ERR_CLIENT_NOT_FOUND`, `ERR_PROPERTY_NOT_FOUND`, `ERR_LISTING_NOT_FOUND`, `ERR_TIER_NOT_FOUND`, `ERR_VENDOR_NOT_FOUND`, `ERR_ITEM_NOT_FOUND`, `ERR_CONSULTATION_NOT_FOUND`, `ERR_SCOPE_ITEM_NOT_FOUND`, `ERR_PROJECT_NOT_FOUND`, `ERR_PULL_NOT_FOUND`, `ERR_PULL_LINE_NOT_FOUND`, `ERR_ORDER_NOT_FOUND`, `ERR_INSTALL_NOT_FOUND`, `ERR_VISIT_NOT_FOUND`, `ERR_LEASE_NOT_FOUND`, `ERR_EXTENSION_NOT_FOUND`, `ERR_PICKUP_NOT_FOUND`, `ERR_ASSESSMENT_NOT_FOUND`, `ERR_SHOOT_NOT_FOUND`, `ERR_INVOICE_NOT_FOUND` and `ERR_DEPOSIT_NOT_FOUND`, each answering HTTP 404. The path variables themselves are `brokerage_id`, `client_id`, `property_id`, `listing_id`, `tier_id`, `vendor_id`, `item_id`, `consultation_id`, `scope_item_id`, `project_id`, `pull_id`, `pull_line_id`, `rental_order_id`, `install_id`, `visit_id`, `lease_id`, `extension_id`, `pickup_id`, `assessment_id`, `shoot_id`, `invoice_id` and `deposit_id`.

The same not-found family answers **body** foreign keys. Any `*_id` supplied in a request payload must resolve to a stored row of the declared parent type, and failure reports that type's own not-found code with HTTP 404.

Request bodies must be JSON objects. A field the endpoint declares as required but which is absent yields `ERR_MISSING_FIELD` (HTTP 400). A field carrying a value outside its declared enumeration yields `ERR_INVALID_ENUM` (HTTP 422). A field of the wrong type, or a numeric value outside its declared range, yields `ERR_INVALID_REQUEST` (HTTP 400). The declared ranges are: `distance_miles` from 0 through 500 inclusive; `room_count` on a property from 1 through 40 inclusive; `list_price` strictly greater than 0; `authorization_cap` on a brokerage from 0.00 through 15000.00 inclusive; `tier_rank` from 1 through 3 inclusive; `payer_split_agent_pct` strictly greater than 0 and strictly smaller than 1; `crew_size` from 1 through 8 inclusive; `unit_count` on a rental order from 1 through 60 inclusive; `quantity` on a pull line exactly 1 when the line's `source` is `OWNED` and from 1 through 20 inclusive when it is `VENDOR`; `initial_cycles` on a lease from 0 through 24 inclusive at the shape gate — the shape check deliberately admits values below 3, which survive it and are rejected later, on business grounds, by rung 43's three-cycle minimum lease term, so that rung is reachable at all; `requested_cycles` on an extension from 0 through 12 inclusive at the shape gate — zero survives the shape check and is rejected later, on business grounds, by the rung that demands whole positive cycles; and the pagination `limit` from 1 through 100 inclusive. Every other numeric body field in this API is bounded below at 0 and unbounded above: a client's `personal_authorization_cap`, a tier's `room_cap`, `included_accessory_sets`, `included_photo_sessions`, `base_price` and `monthly_rent_rate`, a vendor's `lead_time_days`, `min_lease_cycles`, `cancel_cutoff_days` and `rate_multiplier`, an item's `replacement_value` and `monthly_rate`, a scope item's `estimated_hours` and `accessory_set_count`, a consultation's `estimated_hours`, a visit's `hours_logged`, an assessment's `repair_cost_estimate` and `revised_repair_cost`, an invoice payment's `amount_paid`, and each of the three expected-version fields. A negative value in any of them is rung 8's `ERR_INVALID_REQUEST`.

Two further families of rejection share `ERR_INVALID_REQUEST` (HTTP 400) with the range checks. **Uniqueness violations**: wherever this document declares a value unique — a brokerage's `license_code`, a client's `email`, a listing's `mls_number`, a tier's `tier_code`, an inventory item's `sku`, a scope item's `room_label` within its consultation, and a damage assessment's `pull_line_id` within its pickup — a duplicate is refused with `ERR_INVALID_REQUEST`, not with a conflict code of its own. **A uniqueness comparison is not evaluated at rung 8, but at the point in the handler where the narrative that declares it sits**, and for the two scoped uniqueness rules that point is *after* the state gates: a duplicate `room_label` offered to a cancelled consultation answers `ERR_CONSULTATION_INVALID_STATE`, and a duplicate `pull_line_id` offered to a pickup that is not `IN_PROGRESS` answers `ERR_PICKUP_INVALID_STATE`. The five global uniqueness rules — `license_code`, `email`, `mls_number`, `tier_code` and `sku` — are evaluated after the body foreign keys of rung 9 resolve, so a payload that is both a duplicate and carries an unresolvable `*_id` answers the 404. **Wrong-sub-type foreign keys**: a body foreign key that resolves to a stored row of the declared parent type but of the wrong sub-type — a property's `owner_client_id` naming a client who is not a `SELLER`, or a listing's `listing_agent_client_id` naming a client who is not a `LISTING_AGENT` — has already satisfied the not-found rung and is refused with `ERR_INVALID_REQUEST` rather than with a 404. No other foreign key in this system constrains the sub-type of the row it names; a project's `payer_client_id`, in particular, may name a client of any `client_type`.

### 2.7. The Ten Write Gates and the Seventy-Three-Rung Ladder

Every mutating endpoint in this system evaluates the same **total order of ten gates** and returns the error of the *first* gate that objects. A gate may be skipped for a given endpoint — the endpoint simply has nothing for that gate to inspect — but a gate is never re-ordered relative to another, and both pipelines walk the identical order. The ten gates, in evaluation order, are:

1. **G1 — Authentication** (ladder rungs 1–3): the role header is present, names a declared role, and an identity is supplied for entity-backed roles.
2. **G2 — Authorization** (rung 4): the acting role appears in the endpoint's permitted-role list.
3. **G3 — Existence and shape** (rungs 5–9): path resources resolve left to right, the body is an object, required fields are present, enums are members, types and ranges hold, and body foreign keys resolve.
4. **G4 — Party scope** (rungs 10–13): the acting entity-backed principal is genuinely a party to the record being touched.
5. **G5 — Global freeze** (rungs 14–17): the ancestor project is not closed, the ancestor listing is neither terminated nor sold-closed, and the ancestor consultation is not cancelled.
6. **G6 — State precondition** (rungs 18–34): the target entity's own state machine permits the requested transition, the endpoint's pipeline arm matches the project's pipeline, and the logical clock has reached the scheduled instant of the event being reported.
7. **G7 — Optimistic concurrency** (rungs 35–37): the supplied expected-version value matches the stored parent version.
8. **G8 — Safety and authority** (rungs 38–52): scope approval, authorization caps, seller consent, vendor lead time and minimum term, lease minimums, extension increments and totals, tier-change direction, and photography linkage.
9. **G9 — Constraint and capacity** (rungs 53–65): inventory availability, fill rate, attempt caps, pickup window, crew and shoot scheduling geometry, service window, and project uniqueness.
10. **G10 — Fiscal** (rungs 66–73): deposit held, deposit minimum, exact payment, already-paid, deferral expiry, fiscal hold, the MLS delivery payment gate, and the refund gate.

Three properties of this ordering are deliberate and load-bearing. **G7 sits between state preconditions and business authority**: a request that is already illegal for the target's current state is rejected before its version is even looked at, but a writer holding a stale version is turned away before any cap or capacity arithmetic runs. **G5 is a freeze gate, not a state gate**: it fires on ancestors — the project, the listing, the consultation — regardless of which child record the endpoint actually writes, so a terminated listing blocks a pull-line insert several levels down the tree. And **G10 is last on purpose**: a caller whose request is both structurally broken and fiscally blocked is told about the structural problem first, so that fixing the money never surfaces a second, unrelated rejection.

Within a gate, the rungs are evaluated in ascending rung number, and the first objecting rung supplies the error. The full ladder follows. Each rung states its condition, its error code, its HTTP status, and the exact set of operations it guards.

**G1 — Authentication.**
Rung 1: `X-User-Role` is present on the request; otherwise `ERR_UNAUTHENTICATED`, HTTP 401. Applies to every endpoint.
Rung 2: `X-User-Role` names one of the eight declared roles; otherwise `ERR_UNAUTHENTICATED`, HTTP 401. Applies to every endpoint.
Rung 3: `X-User-ID` is present whenever the role is one of the four entity-backed roles `ListingAgent`, `Seller`, `BrokerageAdmin` or `VendorRep`; otherwise `ERR_IDENTITY_REQUIRED`, HTTP 401. Applies to every endpoint.

**G2 — Authorization.**
Rung 4: the acting role appears in the endpoint's permitted-role list as published in §4; otherwise `ERR_UNAUTHORIZED`, HTTP 403. Applies to every endpoint.

**G3 — Existence and shape.**
Rung 5: every identifier in the path resolves to a stored row, validated left to right, returning the entity-specific not-found code of the leftmost unresolved segment with HTTP 404. Applies to every path-templated endpoint.
Rung 6: the request body is a JSON object and every field the endpoint declares as required is present; otherwise `ERR_MISSING_FIELD`, HTTP 400. Applies to every `POST`, `PUT` and `PATCH` endpoint.
Rung 7: every enum-typed body field carries a member of its declared set; otherwise `ERR_INVALID_ENUM`, HTTP 422. Applies to every `POST`, `PUT` and `PATCH` endpoint. **The enum-typed body fields are exactly these thirteen, and no others route here**: a client's `client_type`, a property's `occupancy`, a tier's `tier_code`, the `status` supplied on a vendor update, an inventory item's `category`, a scope item's `action`, the `recommended_tier_code` supplied when a scope is submitted, a project's `payer_type`, a pull line's `source`, a pull line's `category`, an assessment's `condition_at_pickup`, the `decision` supplied when an extension is adjudicated, and the `decision` supplied when a damage appeal is adjudicated. Every other string-valued body field in this API — a `termination_reason`, a `reason`, a `rejection_note`, a `dispute_note`, a `room_label`, an `sku`, a `state_code` and the rest — is a free string validated only for its type, and a bad value there is `ERR_INVALID_REQUEST` at rung 8 or no error at all; query-string values are not enum-validated at all (§2.3).
Rung 8: every body field matches its declared type and numeric range as listed in §2.6; otherwise `ERR_INVALID_REQUEST`, HTTP 400. Applies to every `POST`, `PUT`, `PATCH` and paginated `GET` endpoint.
Rung 9: every foreign key supplied in the body resolves to a stored row of the declared parent entity, returning that entity's not-found code with HTTP 404. Applies to every endpoint whose payload carries an `*_id` field.

**G4 — Party scope.**
Rung 10: when the acting role is `ListingAgent`, `X-User-ID` equals the `listing_agent_client_id` of the listing being touched, whether reached directly or through the project's `listing_id`; otherwise `ERR_NOT_LISTING_AGENT`, HTTP 403. Applies to every listing lifecycle action (`POST /staging/listings/{listing_id}/under-contract`, `/fall-out-of-escrow`, `/close`, `/terminate`), to `POST /staging/consultations/{consultation_id}/approve-scope` and `/reject-scope`, and to `POST /staging/projects/{project_id}/authorize`. On the two scope actions no listing appears in the path at all, and the test there is that the acting agent is the `listing_agent_client_id` of **at least one** listing on the consultation's property.
Rung 11: when the acting role is `Seller`, `X-User-ID` equals the `owner_client_id` of the property being touched; otherwise `ERR_NOT_PROPERTY_OWNER`, HTTP 403. Applies to `POST /staging/consultations`, `POST /staging/consultations/{consultation_id}/approve-scope` and `/reject-scope` — where the property is the consultation's — and `POST /staging/projects/{project_id}/authorize`. It also guards `POST /staging/clients/{client_id}/seller-consent`, but there no property is in play at all: the comparison is against the `{client_id}` in the path, so an acting `Seller` may only set the flag on their own client row, and any other `{client_id}` answers this same `ERR_NOT_PROPERTY_OWNER` despite the code's name. A `PlatformAdmin` on that endpoint is not compared to anything.
Rung 12: when the acting role is `BrokerageAdmin`, `X-User-ID` equals the project's `brokerage_id`; otherwise `ERR_NOT_PROJECT_PARTY`, HTTP 403. Applies to `POST /staging/projects/{project_id}/authorize` and `POST /staging/invoices/{invoice_id}/pay`.
Rung 13: when the acting role is `VendorRep`, `X-User-ID` equals the `vendor_id` of the rental order being touched; otherwise `ERR_NOT_ORDER_VENDOR`, HTTP 403. Applies to `POST /staging/rental-orders/{rental_order_id}/confirm`.

**G5 — Global freeze.**
Rung 14: the ancestor project is not in `workflow_state` `CLOSED`; otherwise `ERR_PROJECT_CLOSED`, HTTP 409. Rung 15: the ancestor listing is not in `listing_state` `TERMINATED`; otherwise `ERR_LISTING_TERMINATED`, HTTP 409. **These two are always evaluated together, in that order, and they share one scope**, which is narrower than "every mutating endpoint" and must be read as a list rather than as a universal. They guard `POST /staging/projects/{project_id}/authorize`, `/upgrade-package`, `/downgrade-package`, `/extend-window`, `/pulls`, `/installs`, `/visits`, `/pickups`, `/photo-shoots` and `/invoices`; `POST /staging/pulls/{pull_id}/lines`, `/submit` and `/commit`; `POST /staging/rental-orders` and `/rental-orders/{rental_order_id}/place`; every install, visit, pickup and damage-assessment action except assessment `/adjudicate`; `POST /staging/leases/{lease_id}/mark-term-complete` and `/extensions`; both extension actions; and `POST /staging/photo-shoots/{shoot_id}/complete` and `/request-reshoot`. **Eighteen mutating endpoints that do reach a project are nevertheless not gated by either rung**, and they are named here exhaustively so the omission is not mistaken for an oversight: `POST /staging/projects/{project_id}/close`; `POST /staging/pulls/{pull_id}/release` and `/cancel`; `POST /staging/rental-orders/{rental_order_id}/confirm` and `/cancel`; `POST /staging/leases/{lease_id}/accrue-holdover`; `POST /staging/damage-assessments/{assessment_id}/adjudicate`; `POST /staging/photo-shoots/{shoot_id}/deliver` and `/cancel`; all five invoice actions; and all four deposit actions. A closed project's invoice can therefore still be paid or voided and its deposit still refunded or forfeited. Endpoints that touch no project at all — the clock, brokerages, clients, properties, listings, tiers, vendors and inventory items — have nothing for either rung to inspect. A `Listing` is neither a project nor a project child, so the four listing lifecycle actions are **not** gated by rung 14 even though their cascades reach projects; three of them (`/under-contract`, `/fall-out-of-escrow`, `/terminate`) do walk rung 15 against the listing itself, and `/close` reaches the same answer through rung 33 instead.
Rung 16: the ancestor listing is not in `listing_state` `CLOSED_SOLD` when the endpoint writes staging execution state; otherwise `ERR_LISTING_CLOSED`, HTTP 409. Applies to `POST /staging/projects/{project_id}/pulls`, `/installs`, `/visits`, `/photo-shoots`, `/pickups`, and to `POST /staging/leases/{lease_id}/extensions`.
Rung 17: the ancestor consultation is not in state `CANCELLED`; otherwise `ERR_CONSULTATION_INVALID_STATE`, HTTP 409. Applies to every `POST /staging/consultations/{consultation_id}/...` action and to `POST /staging/projects`.

**G6 — State precondition.**
Rung 18: the consultation's `state` is a legal origin for the requested transition; otherwise `ERR_CONSULTATION_INVALID_STATE`, HTTP 409. Applies to `POST /staging/consultations/{consultation_id}/hold`, `/submit-scope`, `/approve-scope`, `/reject-scope`, `/cancel` and `/scope-items`.
Rung 19: the project's `workflow_state` is a legal origin for the requested transition; otherwise `ERR_PROJECT_INVALID_STATE`, HTTP 409. Applies to `POST /staging/projects/{project_id}/authorize` (`DRAFT`), `/pulls` (`AUTHORIZED`), `/installs` (`PULL_OPEN`), `/visits` (`AUTHORIZED` or `VISITS_OPEN`), `/invoices` (`PICKED_UP` or `STAGED`) and `/close` (`CLOSEOUT`). **Four further refusals on these same endpoints share this rung's code rather than carrying one of their own**, and each is evaluated at the position stated in its own §3 narrative: opening a pull against a project that already has a pull in `DRAFT`, `SUBMITTED`, `PARTIAL` or `COMMITTED` is `ERR_PROJECT_INVALID_STATE`, evaluated after the pipeline test of rung 20; opening closeout on a `VACANT_STAGING` project that is in `STAGED` rather than `PICKED_UP` is `ERR_PROJECT_INVALID_STATE` and *not* `ERR_PIPELINE_MISMATCH`; and closing the project answers `ERR_PROJECT_INVALID_STATE` both when its `payment_state` is neither `SETTLED` nor `WRITTEN_OFF` and when any invoice on it is neither `PAID` nor `VOID`. Because `/close` is one of the endpoints rung 14 does not guard, a project already in `CLOSED` asked to close again answers `ERR_PROJECT_INVALID_STATE` here rather than `ERR_PROJECT_CLOSED`. The three package-and-window endpoints — `/upgrade-package`, `/downgrade-package` and `/extend-window` — declare no `workflow_state` transition of their own, so this rung has nothing to inspect on them and **no `workflow_state` is an illegal origin for them**; among the ancestor rungs only rung 14's closed-project freeze constrains them.
Rung 20: the endpoint's pipeline arm matches the project's `pipeline` — pulls, installs, leases and pickups belong to `VACANT_STAGING` only, while visits and service-window extension belong to `OCCUPIED_PREP` only — and every scope item's `action` is legal for the consultation's `pipeline`; otherwise `ERR_PIPELINE_MISMATCH`, HTTP 409. Applies to `POST /staging/projects/{project_id}/pulls`, `/installs`, `/visits`, `/pickups`, `/extend-window` and `POST /staging/consultations/{consultation_id}/scope-items`.
Rung 21: the pull's `state` is a legal origin for the requested transition, and the pull is `COMMITTED` both before an install may be scheduled and before one may start; otherwise `ERR_PULL_INVALID_STATE`, HTTP 409. Applies to `POST /staging/pulls/{pull_id}/submit`, `/commit`, `/release`, `/cancel`, `/lines`, to `POST /staging/projects/{project_id}/installs` — where a project with no pull at all, or whose latest pull is not `COMMITTED`, is refused here — and to `POST /staging/installs/{install_id}/start`. On the install-scheduling endpoint this rung sits after rung 20's pipeline test and before rung 42; on `/start` it sits before rung 24, so a pull that has left `COMMITTED` is reported ahead of the install's own state.
Rung 22: the inventory item's `status` is a legal origin for the requested transition; otherwise `ERR_ITEM_INVALID_STATE`, HTTP 409. Applies to `POST /staging/inventory-items/{item_id}/repair-in`, `/repair-out` and `/write-off`.
Rung 23: the rental order's `state` is a legal origin for the requested transition — and in particular a `DELIVERED` or `RETURNED` order can no longer be cancelled at any price; otherwise `ERR_ORDER_INVALID_STATE`, HTTP 409. Applies to `POST /staging/rental-orders/{rental_order_id}/place`, `/confirm` and `/cancel`.
Rung 24: the install's `state` is a legal origin for the requested transition; otherwise `ERR_INSTALL_INVALID_STATE`, HTTP 409. Applies to `POST /staging/installs/{install_id}/start`, `/complete`, `/no-access` and `/reschedule`.
Rung 25: the visit's `state` is a legal origin for the requested transition; otherwise `ERR_VISIT_INVALID_STATE`, HTTP 409. Applies to `POST /staging/visits/{visit_id}/complete`, `/no-access`, `/reschedule` and `/cancel`.
Rung 26: the lease's `state` is a legal origin for the requested transition; otherwise `ERR_LEASE_INVALID_STATE`, HTTP 409. Applies to `POST /staging/leases/{lease_id}/extensions` (`ACTIVE`, `EXTENDED` or `ENDING`), `/mark-term-complete` (`ACTIVE` or `EXTENDED`) and `/accrue-holdover` (`ENDING` for the first accrual, `HOLDOVER` for every later one). It also guards `POST /staging/extensions/{extension_id}/apply`, where the lease must be `ACTIVE`, `EXTENDED` or `ENDING` and the test is evaluated *after* rung 27's check on the extension's own state — so an already-`APPLIED` extension is reported as `ERR_EXTENSION_INVALID_STATE` even when the lease has since ended.
Rung 27: the extension's `state` is a legal origin for the requested transition; otherwise `ERR_EXTENSION_INVALID_STATE`, HTTP 409. Applies to `POST /staging/extensions/{extension_id}/adjudicate` and `/apply`.
Rung 28: the pickup's `state` is a legal origin for the requested transition; otherwise `ERR_PICKUP_INVALID_STATE`, HTTP 409. Applies to `POST /staging/pickups/{pickup_id}/start`, `/complete`, `/no-access`, `/refuse`, `/reschedule` and `/damage-assessments`.
Rung 29: the damage assessment's `state` is a legal origin for the requested transition, and every assessment on a pickup is `FINAL` before that pickup may complete; otherwise `ERR_ASSESSMENT_INVALID_STATE`, HTTP 409. Applies to `POST /staging/damage-assessments/{assessment_id}/assess` (`DRAFT` or `REVISED`), `/dispute` (`ASSESSED`), `/adjudicate` (`DISPUTED`), `/finalize` (`ASSESSED` or `UPHELD`), and to `POST /staging/pickups/{pickup_id}/complete` and `POST /staging/projects/{project_id}/invoices`, both of which demand `FINAL` across the project's pickup. On `/assess` one further condition rides this position with rung 28's code rather than this rung's: a `DRAFT` assessment may only be assessed while its pickup is `IN_PROGRESS`, and one that is not answers `ERR_PICKUP_INVALID_STATE` — while a `REVISED` assessment coming back round the appeal loop is re-assessed whatever state the pickup has since reached.
Rung 30: the photo shoot's `state` is a legal origin for the requested transition; otherwise `ERR_SHOOT_INVALID_STATE`, HTTP 409. Applies to `POST /staging/photo-shoots/{shoot_id}/complete`, `/deliver`, `/cancel` and `/request-reshoot`.
Rung 31: the invoice's `state` is a legal origin for the requested transition; otherwise `ERR_INVOICE_INVALID_STATE`, HTTP 409. Applies to `POST /staging/invoices/{invoice_id}/issue` (`DRAFT`), `/defer-to-closing` (`DRAFT`), `/escalate` (`DEFERRED_CLOSING`), `/pay` (`ISSUED` or `ESCALATED`) and `/void` (`DRAFT`, `ISSUED`, `ESCALATED` or `DEFERRED_CLOSING`). **There is one named exception on this rung, and it covers three endpoints, not one**: on a payment, a void or an escalation, an invoice already in state `PAID` is *not* reported here. `PAID` is carried past G6 untouched on all three and answered at rung 69 with `ERR_INVOICE_ALREADY_PAID`, so that a duplicate payment — and equally a write-off or an escalation aimed at settled money — receives a fiscal answer rather than a structural one.
Rung 32: the deposit's `state` is a legal origin for the requested transition; otherwise `ERR_DEPOSIT_INVALID_STATE`, HTTP 409. Applies to `POST /staging/deposits/{deposit_id}/collect`, `/apply`, `/refund` and `/forfeit`.
Rung 33: the listing's `listing_state` is a legal origin for the requested listing action — `UNDER_CONTRACT` for `/close` and `/fall-out-of-escrow`, `ACTIVE` or `BACK_ON_MARKET` for `/under-contract` and `/terminate`. An illegal origin is reported with that origin's own terminal code where it has one: a `TERMINATED` listing answers `ERR_LISTING_TERMINATED` and a `CLOSED_SOLD` listing answers `ERR_LISTING_CLOSED`, both HTTP 409. Every other illegal origin — a still-`ACTIVE` listing asked to close, a listing already `UNDER_CONTRACT` asked to go under contract again — answers `ERR_LISTING_NOT_UNDER_CONTRACT`, HTTP 409. Applies to all four listing lifecycle actions.
Rung 34: the logical clock has reached the scheduled instant of the event being reported — the consultation's, install's, visit's, pickup's or shoot's `scheduled_at` — where "reached" means the clock is on or after that instant; otherwise `ERR_EVENT_TOO_EARLY`, HTTP 422. Applies to `POST /staging/consultations/{consultation_id}/hold`, `POST /staging/installs/{install_id}/start` and `/no-access`, `POST /staging/visits/{visit_id}/complete` and `/no-access`, `POST /staging/pickups/{pickup_id}/start`, `/no-access` and `/refuse`, and `POST /staging/photo-shoots/{shoot_id}/complete`.

**G7 — Optimistic concurrency.**
Rung 35: `expected_project_version` equals the stored project `version`; otherwise `ERR_STALE_PROJECT_VERSION`, HTTP 412. Applies to `POST /staging/pulls/{pull_id}/commit`.
Rung 36: `expected_lease_version` equals the stored lease `version`; otherwise `ERR_STALE_LEASE_VERSION`, HTTP 412. Applies to `POST /staging/leases/{lease_id}/extensions`.
Rung 37: `expected_pickup_version` equals the stored pickup `version`; otherwise `ERR_STALE_PICKUP_VERSION`, HTTP 412. Applies to `POST /staging/damage-assessments/{assessment_id}/finalize`.

**G8 — Safety and authority.**
Rung 38: the referenced consultation is in state `SCOPE_APPROVED` before a project may be created against it, and still is when that project is authorized; otherwise `ERR_SCOPE_NOT_APPROVED`, HTTP 409. Applies to `POST /staging/projects` and to `POST /staging/projects/{project_id}/authorize`, where it is evaluated after rung 19's `DRAFT` test and before the three cap rungs.
Rung 39: the acting principal's `effective_authorization_cap` is greater than or equal to the project's `contract_value`, the comparison being inclusive so that headroom of exactly 0.00 authorizes; otherwise `ERR_AUTHORIZATION_CAP_EXCEEDED`, HTTP 403. The cap compared here is the acting `Client` row's `effective_authorization_cap` when the acting role is `ListingAgent` or `Seller`; when it is `BrokerageAdmin`, whose `X-User-ID` names a `Brokerage` rather than a `Client`, the cap compared is the platform ceiling of 15000.00. **This rung is the residual cap refusal, and its condition carries three explicit carve-outs** — without them rung 40 would be entirely dead on this endpoint and rung 41 all but unreachable. It does not answer when the payer client carries `consent_on_file` true; it does not answer when the payer client is of `client_type` `SELLER`, because that case is rung 41's; and it does not answer when the `contract_value` exceeds 15000.00, because that case is rung 40's. Negative headroom is refused *here* only when none of those three carve-outs applies. Applies to `POST /staging/projects/{project_id}/authorize`.
Rung 40: the project's `contract_value` does not exceed 15000.00, regardless of who authorizes and regardless of whether seller consent is on file; otherwise `ERR_BROKERAGE_CAP_EXCEEDED`, HTTP 403. Applies to `POST /staging/projects/{project_id}/authorize`, where the figure tested is the stored one, and to `POST /staging/projects/{project_id}/upgrade-package`, where it is instead the **prospective** `contract_value` the project would carry under the target tier — computed without writing it — so an upgrade that would breach the ceiling is refused before the tier ever moves. On the upgrade endpoint this rung is walked before rung 47, so a target tier that is both too expensive and not an upgrade at all answers `ERR_BROKERAGE_CAP_EXCEEDED`.
Rung 41: when a `ListingAgent` authorizes above their own `effective_authorization_cap`, the payer client — who must be of `client_type` `SELLER` — carries `consent_on_file` true; otherwise `ERR_SELLER_CONSENT_REQUIRED`, HTTP 403. Applies to `POST /staging/projects/{project_id}/authorize`.
Rung 42: the install's `scheduled_at` is on or after every consumed rental order's `earliest_delivery_date`; otherwise `ERR_VENDOR_LEAD_TIME_VIOLATION`, HTTP 422. Applies to `POST /staging/projects/{project_id}/installs` and `POST /staging/installs/{install_id}/reschedule`.
Rung 43: the lease's `initial_cycles` is greater than or equal to 3 cycles; otherwise `ERR_BELOW_MIN_LEASE_TERM`, HTTP 422. Applies to `POST /staging/projects/{project_id}/installs`.
Rung 44: every consumed rental order's `effective_term_cycles` is less than or equal to the lease's `initial_cycles` plus 6. A vendor's own minimum term **may** exceed the project's term — that shortfall is billed rather than blocked — but a vendor minimum the project could never reach even by extending to the six-cycle ceiling is rejected outright with `ERR_VENDOR_MIN_TERM_VIOLATION`, HTTP 422. The comparison is exactly that one — `effective_term_cycles` against `initial_cycles` plus 6 — and a vendor minimum that merely exceeds `initial_cycles` is *not* refused here. Applies to `POST /staging/projects/{project_id}/installs`.
Rung 45: the extension's `requested_cycles` is a whole positive multiple of the one-cycle extension increment, so fractional requests and zero are both rejected; otherwise `ERR_PARTIAL_CYCLE_EXTENSION`, HTTP 422. Applies to `POST /staging/leases/{lease_id}/extensions`.
Rung 46: the lease's `extension_cycles` plus the cycles now in question does not exceed 6; otherwise `ERR_EXTENSION_LIMIT_REACHED`, HTTP 409. The rung runs twice on an extension's life and reads a different figure each time: at request time the cycles in question are the `requested_cycles` carried in the body, and at apply time they are the extension's stored `granted_cycles`. Applies to `POST /staging/leases/{lease_id}/extensions` and `POST /staging/extensions/{extension_id}/apply`.
Rung 47: an upgrade target has a strictly greater `tier_rank` than the project's current tier, and a downgrade target a strictly smaller one; otherwise `ERR_INVALID_TIER_CHANGE`, HTTP 422. Applies to `POST /staging/projects/{project_id}/upgrade-package` and `POST /staging/projects/{project_id}/downgrade-package`.
Rung 48: on a `VACANT_STAGING` project the shoot instant is on or after the project's `COMPLETE` install's `completed_at`; otherwise `ERR_SHOOT_BEFORE_INSTALL`, HTTP 409. Applies to `POST /staging/projects/{project_id}/photo-shoots` and `POST /staging/photo-shoots/{shoot_id}/complete`.
Rung 49: on an `OCCUPIED_PREP` project at least one visit is already in state `COMPLETED` before a shoot may be completed; otherwise `ERR_VISIT_NOT_COMPLETED`, HTTP 409. Applies to `POST /staging/photo-shoots/{shoot_id}/complete`.
Rung 50: the shoot instant is strictly before the project's de-stage start, meaning the instant at which the pickup entered `IN_PROGRESS`; otherwise `ERR_SHOOT_AFTER_DESTAGE`, HTTP 409. Applies to `POST /staging/projects/{project_id}/photo-shoots` and `POST /staging/photo-shoots/{shoot_id}/complete`.
Rung 51: the project's `reshoot_credits_remaining` is at least 1 before a reshoot may be requested; otherwise `ERR_RESHOOT_ENTITLEMENT_EXHAUSTED`, HTTP 409. Applies to `POST /staging/photo-shoots/{shoot_id}/request-reshoot`.
Rung 52: a pull line's `room_label` matches the `room_label` of some scope item on the project's consultation; otherwise `ERR_SCOPE_ITEM_NOT_FOUND`, HTTP 404. Applies to `POST /staging/pulls/{pull_id}/lines`.

**G9 — Constraint and capacity.**
Rung 53: the allocation pass fills at least one unit; otherwise `ERR_INSUFFICIENT_INVENTORY`, HTTP 409. The test is taken from the pass's point of view and not line by line: a pull that has requested at least one unit is refused exactly when, counting both the units already filled on it and the units the pass about to run would fill, the filled total is zero — that is, when no line on the pull can be satisfied from owned stock or from a rental order. It follows that a pull on which *some* line can be filled passes this rung however many of its other lines go `UNFILLED`. The test is a non-mutating look-ahead: it is decided before any line, item or order is written, and rung 55 is still evaluated after it, so a `PARTIAL` pull that is out of resubmits and can fill nothing answers `ERR_INSUFFICIENT_INVENTORY` rather than `ERR_PULL_RESUBMIT_LIMIT`. Applies to `POST /staging/pulls/{pull_id}/submit`.
Rung 54: the pull's `fill_rate` is greater than or equal to 0.70, the comparison being inclusive so that exactly 0.7000 commits; otherwise `ERR_FILL_RATE_BELOW_MINIMUM`, HTTP 409. Applies to `POST /staging/pulls/{pull_id}/commit`.
Rung 55: the pull's `resubmit_count` is strictly less than 2 before a `PARTIAL` pull may be re-submitted; otherwise `ERR_PULL_RESUBMIT_LIMIT`, HTTP 409. Applies to `POST /staging/pulls/{pull_id}/submit`.
Rung 56: the install's `attempt_count` is strictly less than 2 before a `NO_ACCESS` install may be rescheduled; otherwise `ERR_INSTALL_ATTEMPT_LIMIT`, HTTP 409. Applies to `POST /staging/installs/{install_id}/reschedule`.
Rung 57: the visit's `attempt_count` is strictly less than 2 before a `NO_ACCESS` visit may be rescheduled; otherwise `ERR_VISIT_ATTEMPT_LIMIT`, HTTP 409. Applies to `POST /staging/visits/{visit_id}/reschedule`.
Rung 58: the pickup's `attempt_count` is strictly less than 3 before a `NO_ACCESS` or `REFUSED` pickup may be rescheduled; otherwise `ERR_PICKUP_ATTEMPT_LIMIT`, HTTP 409. Applies to `POST /staging/pickups/{pickup_id}/reschedule`.
Rung 59: the assessment's `appeal_count` is strictly less than 1 before an `ASSESSED` assessment may be disputed; otherwise `ERR_APPEAL_LIMIT_REACHED`, HTTP 409. Applies to `POST /staging/damage-assessments/{assessment_id}/dispute`.
Rung 60: the pickup's `scheduled_at` falls inside the closed interval that runs from the lease's `pickup_window_start` through its `pickup_window_end`, both endpoints included; otherwise `ERR_PICKUP_OUTSIDE_WINDOW`, HTTP 422. A lease that carries no derived window at all — one still `PENDING`, or one whose window a fall-out of escrow has cleared — has no interval to fall inside and is refused with the same code. Applies to `POST /staging/projects/{project_id}/pickups` and `POST /staging/pickups/{pickup_id}/reschedule`.
Rung 61: the proposed install's UTC calendar day carries fewer than 1 install already in state `SCHEDULED` or `IN_PROGRESS`; otherwise `ERR_CREW_DOUBLE_BOOKED`, HTTP 409. The count is taken over **every install in the service**, not just those on the project in the path — there is one crew — and a reschedule excludes the install being moved from its own count. Applies to `POST /staging/projects/{project_id}/installs` and `POST /staging/installs/{install_id}/reschedule`.
Rung 62: the proposed shoot's half-open 180-minute block does not overlap any existing shoot's block plus that shoot's trailing 60-minute buffer on the same property; otherwise `ERR_SHOOT_TIME_CONFLICT`, HTTP 409. Applies to `POST /staging/projects/{project_id}/photo-shoots` **and to nothing else**: the follow-up shoot that `POST /staging/photo-shoots/{shoot_id}/request-reshoot` creates is booked at the supplied instant without this rung, and without rungs 48 and 50 either, so a reshoot may legally be placed before install completion, on or after de-stage start, and squarely on top of another shoot's block. Those three geometric and temporal rungs bite again only if that reshoot is later completed, and rungs 48 and 50 are re-tested at completion while rung 62 never is.
Rung 63: the proposed or reported visit instant is on or before the project's `service_window_end_date`; otherwise `ERR_SERVICE_WINDOW_EXPIRED`, HTTP 409. Applies to `POST /staging/projects/{project_id}/visits`, `POST /staging/visits/{visit_id}/complete` and `POST /staging/visits/{visit_id}/reschedule`.
Rung 64: the project's `window_extension_count` is strictly less than 2; otherwise `ERR_WINDOW_EXTENSION_LIMIT`, HTTP 409. Applies to `POST /staging/projects/{project_id}/extend-window`.
Rung 65: no other project on the same property sits in a `workflow_state` other than `CLOSED`; otherwise `ERR_DUPLICATE_ACTIVE_PROJECT`, HTTP 409. Applies to `POST /staging/projects`.

**G10 — Fiscal.**
Rung 66: the project's deposit is in state `HELD` before execution work may begin; otherwise `ERR_DEPOSIT_NOT_HELD`, HTTP 402. Applies to `POST /staging/projects/{project_id}/visits`, `POST /staging/projects/{project_id}/installs` and `POST /staging/installs/{install_id}/complete`.
Rung 67: the deposit's `amount` is either exactly 0.00 or at least 500.00 at collection; otherwise `ERR_DEPOSIT_BELOW_MINIMUM`, HTTP 422. Applies to `POST /staging/deposits/{deposit_id}/collect`.
Rung 68: `amount_paid` equals the invoice's `total_due` exactly — underpayment and overpayment are both refused; otherwise `ERR_OVERPAYMENT`, HTTP 422. Applies to `POST /staging/invoices/{invoice_id}/pay`.
Rung 69: the invoice is not already in state `PAID`; otherwise `ERR_INVOICE_ALREADY_PAID`, HTTP 409. Applies to `POST /staging/invoices/{invoice_id}/pay`, `/void` and `/escalate`.
Rung 70: a `DEFERRED_CLOSING` invoice is converted within 120 days of its `issued_at`; otherwise `ERR_CLOSING_DEFERRAL_EXPIRED`, HTTP 409. Applies to `POST /staging/listings/{listing_id}/close`.
Rung 71: the project's `fiscal_hold` is false before any new commitment may be made; otherwise `ERR_FISCAL_HOLD`, HTTP 402. Applies to `POST /staging/projects/{project_id}/pulls`, `/installs`, `/visits`, `/photo-shoots`, `/upgrade-package`, to `POST /staging/leases/{lease_id}/extensions` and to `POST /staging/photo-shoots/{shoot_id}/request-reshoot`.
Rung 72: when a shoot's `mls_delivery_gated` is true, the project's invoice is in state `PAID` before delivery; otherwise `ERR_MLS_DELIVERY_PAYMENT_GATE`, HTTP 402. Applies to `POST /staging/photo-shoots/{shoot_id}/deliver`.
Rung 73: a deposit may only be refunded once its project's invoice is in state `PAID`; otherwise `ERR_DEPOSIT_INVALID_STATE`, HTTP 409 — the same code rung 32 uses, reached here for a fiscal rather than a structural reason. A project with no invoice row at all is refused the same way. Applies to `POST /staging/deposits/{deposit_id}/refund`.

**Checks the ladder does not number.** The seventy-three rungs above are the refusals that recur across endpoints; a further set of one-endpoint conditions is enforced without a rung number of its own, always reusing a code already in the catalogue and always sitting at the position given here. They are listed together so the ladder is not mistaken for an exhaustive inventory of what a handler tests. In G3, at the position of rungs 6–9: a `brokerage_id` becomes a *required* field on `POST /staging/clients` when `client_type` is `LISTING_AGENT` or `BROKERAGE_ADMIN` and a `rental_order_id` becomes one on `POST /staging/pulls/{pull_id}/lines` when `source` is `VENDOR`, each absent one answering `ERR_MISSING_FIELD` — and the conditional test is read before the enum test, so an unrecognised `client_type` or `source` reaches `ERR_INVALID_ENUM` and never triggers it; a `brokerage_id` becomes required on `POST /staging/projects` when `payer_type` is `BROKERAGE` in the same way; and a consultation's `scheduled_at` earlier than the logical clock is `ERR_INVALID_REQUEST`, evaluated after rung 9 and before rung 11. Between G4 and G6, on `POST /staging/consultations`: the property is in `prep_state` `NEW` and carries no consultation in `SCHEDULED`, `HELD`, `SCOPE_DRAFTED` or `SCOPE_SUBMITTED`, either failure answering `ERR_CONSULTATION_INVALID_STATE`. Inside G6, immediately after the entity's own state rung: on `POST /staging/consultations/{consultation_id}/submit-scope` a `scoped_room_count` of zero answers `ERR_CONSULTATION_INVALID_STATE`; on `POST /staging/consultations/{consultation_id}/scope-items` a `requires_rental` of true on an `OCCUPIED_PREP` consultation answers `ERR_INVALID_REQUEST` and a duplicate `room_label` answers the same, both after rung 20; on `POST /staging/pulls/{pull_id}/submit` a `DRAFT` pull with nothing requested answers `ERR_PULL_INVALID_STATE`; on `POST /staging/rental-orders/{rental_order_id}/place` a vendor whose `status` is `SUSPENDED` answers `ERR_ORDER_INVALID_STATE`; on `POST /staging/pickups/{pickup_id}/damage-assessments` a duplicate `pull_line_id` answers `ERR_INVALID_REQUEST`; on `POST /staging/leases/{lease_id}/accrue-holdover` a lease with no derived pickup window, a clock not yet strictly past `pickup_window_end` plus the two grace days, and a project whose pickup has already `COMPLETED` each answer `ERR_LEASE_INVALID_STATE`; and on the invoice's `/issue` and `/defer-to-closing` the `payer_type` fork and the project's or listing's state each answer `ERR_INVOICE_INVALID_STATE`, as §3.9 already records. None of these re-orders a gate: each is read at the gate its narrative places it in, and the first objection still wins.

### 2.8. Money, Rounding, Units and Component Order

All monetary values in this system are carried to a precision of exactly 2 decimal places, and every rounding operation uses round-half-up. Where a formula in §3 says "rounded", that is what is meant, and where it says a value is rounded *before* entering a sum, the order is binding: rounding each component and then adding is not interchangeable with adding raw components and rounding once, and the two can differ by a cent on the same inputs. The only non-money precision declarations are the pull `fill_rate`, which is carried to 4 decimal places with the same half-up rule, and the quantities that are counted in whole units — cycles, days, months, rooms, minutes and installs — which are never fractional.

Durations are expressed in whole days unless a rule explicitly names minutes or hours. Adding "days" to an instant preserves the time-of-day component of that instant; the service window, the lease end date, the pickup window and the invoice due date are all derived by adding whole days to an anchor instant, not by truncating to midnight. Two rules work in minutes instead: the photography block geometry (§3.8), which is minute-level, and nothing else.

The invoice `line_summary` is an object keyed by component name, and the twelve components have a **fixed, pinned order**: `package`, `room_overage`, `accessory_overage`, `labour`, `travel`, `lease`, `extension`, `holdover`, `damage`, `photo`, `cancellation`, `closing_escalation`. The invoice `subtotal` is produced by walking that list in exactly that order, rounding each component to two decimal places, and accumulating; the accumulated result is then rounded once more to two decimal places. Components a given project never incurs contribute 0.00 rather than being omitted from the ordering.

The `package` component is not the tier's list price alone. It is the project's **current** tier's `base_price` plus the running total of every package adjustment booked against that project — each upgrade charge and each downgrade charge exactly as §3.2 derives them, and each 250.00 service-window extension fee — accumulated as they are booked and carried at two decimal places. A tier change therefore moves this component twice over: once because `base_price` now reads off the new tier, and once through the adjustment the change itself booked.

Two thresholds are worth stating twice because their inclusivity decides real outcomes. Travel zone boundaries are **inclusive at the top**: a property exactly 15 miles out is zone 1, and 15.1 miles is zone 2. Depreciation band boundaries are likewise inclusive at the top: an item exactly 12 months old sits in band 1, and 13 months old sits in band 2. By contrast, the vendor cancellation cutoff is **strict**: an instant exactly equal to `cancel_cutoff_date` takes the late arm, not the early one. And the damage replacement threshold is **strict**: a repair estimate exactly equal to sixty percent of the depreciated replacement value stays on the repair arm.

### 2.9. Optimistic Concurrency on Parent Records

Three write operations in this system are guarded against a client acting on a parent record it has not re-read. Each requires a non-optional version field in its request body, each compares that field against the parent's current stored `version`, and each rejects a mismatch with its own error code and HTTP 412. **No other endpoint in this API accepts a version field**; supplying one elsewhere has no effect, and omitting one elsewhere is never an error.

Committing an inventory pull requires `expected_project_version` carrying the client's last observed `version` of the pull's parent `Project`. If any writer has advanced that project's version since the client read it, the commit is rejected with `ERR_STALE_PROJECT_VERSION` (HTTP 412). This guard exists because a commit legitimately supersedes any earlier commitment posture on the same project — a re-stage after a fall-out-of-escrow commits a second pull against the very same project — so a stale writer cannot be caught by a state precondition alone.

Requesting a lease extension requires `expected_lease_version` carrying the client's last observed `version` of the parent `Lease`. A mismatch is rejected with `ERR_STALE_LEASE_VERSION` (HTTP 412). Here too a second request legitimately supersedes the first while the lease is still `ACTIVE`, so a writer holding a pre-extension view of `end_date` and `billed_cycles` must be forced back to a fresh read before it can queue another term change.

Finalizing a damage assessment requires `expected_pickup_version` carrying the client's last observed `version` of the parent `Pickup`. A mismatch is rejected with `ERR_STALE_PICKUP_VERSION` (HTTP 412). Each finalization adds to the pickup's running `damage_total` and bumps the pickup's version, so a second finalization that still carries a pre-first-finalization view of the pickup is operating on a stale total and must re-read.

In all three cases the version check happens at gate G7 — after the target's own state precondition has been satisfied, and before any authority, capacity or fiscal arithmetic runs.

### 2.10. The Two Pipelines and What They Share

Every engagement in this system belongs to exactly one of two pipelines, and the choice is **frozen at the moment the consultation is held**, copied from the property's `occupancy`. A property recorded as `OCCUPIED` produces a consultation whose `pipeline` is `OCCUPIED_PREP`; a property recorded as `VACANT` produces `VACANT_STAGING`. Changing the property's `occupancy` afterwards does not move an already-held consultation, and every project created from that consultation inherits the same `pipeline` value and can never change it.

**Pipeline O — occupied prep.** The seller still lives in the home. The consultation produces a room-by-room scope of `EDIT`, `DECLUTTER` and `REFRESH` actions over the seller's own furnishings, plus selective accessory placement. There is little or no rental pull; in fact a Pipeline O engagement never commits a pull at all, and no `Lease` row is ever created for it. Work is executed as a series of billable visits rather than one install day, billing is hourly and consultative, and "extension" on this arm means extending the project's **service window**, not a furniture lease term.

**Pipeline V — vacant staging.** The property is empty. The consultation produces a room package; an inventory pull commits owned warehouse stock and partner-vendor rental units; an install event stages the home; a lease term in whole thirty-day cycles starts at install-complete; a pickup de-stages at lease end; damage assessments are raised per line at the pickup; and extensions are granted in whole cycles subject to per-item vendor availability, which is what makes an extension able to land as a partial rather than a full grant.

The two arms diverge on exactly three things: inventory commitment, lease arithmetic, and the pickup-and-damage tail. Everything else is shared — the same authentication and authorization rungs, the same party-scope rules, the same global freeze, the same state-precondition discipline, the same optimistic-concurrency rules, the same package and pricing authority, the same payer routing, the same photography linkage, the same invoicing and the same closeout. Pipeline O closes out straight from its last completed visit; Pipeline V closes out through the pickup.

Calling a Pipeline V operation on an `OCCUPIED_PREP` project, or a Pipeline O operation on a `VACANT_STAGING` project, is rejected at rung 20 with `ERR_PIPELINE_MISMATCH` (HTTP 409). The same code answers a scope item whose `action` is illegal for its consultation's pipeline.

### 2.11. Conservation Invariants

Four quantities in this system are conserved, and each has a compensating action pair that must leave the identity intact. These are not merely descriptive; an implementation that lets one drift is wrong even when no single endpoint's rules were violated.

**Owned units are conserved across the warehouse.** The total number of owned units on hand equals the number of items in `AVAILABLE` plus those in `RESERVED` plus those in `DEPLOYED` plus those in `IN_REPAIR` plus those in `WRITTEN_OFF`. A written-off unit remains counted in the total forever; it simply stops being available. The compensating pair is a pull submission moving units from `AVAILABLE` to `RESERVED` against a pull cancellation moving them back from `RESERVED` to `AVAILABLE`. The identity is observable through the warehouse summary view, whose response reports `on_hand_total`, `available`, `reserved`, `deployed`, `in_repair` and `written_off`, optionally narrowed by `category`.

**Deposit money is conserved.** A deposit's `amount` always equals the sum of `applied_to_damage`, `applied_to_holdover`, `applied_to_balance`, `refunded_amount`, `forfeited_amount` and `held_remaining`. "Always" is meant literally, from the instant the row is created and not merely from collection: the deposit is created in state `REQUIRED` with every applied, refunded and forfeited bucket at 0.00 and `held_remaining` already carrying the full `amount`, so the identity balances before a cent has been collected. The compensating pair is applying the waterfall against refunding the residue. The identity is observable on any single deposit read.

**Package photography entitlement is conserved.** The tier's `included_photo_sessions` plus the single reshoot credit each package carries equals the project's `photo_sessions_consumed`, plus its `reshoot_credits_remaining`, plus the count of shoots on the project still in state `SCHEDULED`, plus the included sessions not yet booked. The last term is an accounting residual rather than a stored field, and it exists so that the identity balances; the compensating pair is requesting a reshoot against cancelling one, and the stored halves of the identity are visible on a project read.

**Billed lease cycles are conserved.** A lease's `billed_cycles` equals its `initial_cycles` plus the sum of `granted_cycles` over the extensions on that lease that have reached state `APPLIED`. **This identity is scoped more narrowly than the deposit's**, and the asymmetry is deliberate: it holds from the moment the lease reaches `ACTIVE` at install completion, which is where `billed_cycles` first takes the value of `initial_cycles`. A `PENDING` lease is created with `billed_cycles` 0 against a non-zero `initial_cycles` and does not satisfy it, and a lease that is cancelled out of `PENDING` never does. The compensating pair here is unusual: marking a term complete early against reversing that on a fall-out-of-escrow. **Neither may change `billed_cycles`.** An early de-stage moves the pickup window forward without reducing what the customer is billed, and the reversal moves it back without adding anything.

### 2.12. Declared Values With No Enforcing Rule

Two named values are declared as part of this service's configuration but are not consulted by any numbered rung, any calculation or any endpoint. A minimum photography lead time of 24 hours is declared; no rung on the ladder tests it, and no endpoint rejects a shoot for being booked inside it. A re-stage availability recheck horizon of 3 days is likewise declared alongside the re-stage availability recheck; the recheck itself inspects the current status of every deployed line's item at the instant of the fall-out and does not consult that horizon. Both are recorded here exactly as the specification carries them, with neither an invented enforcement nor a silent deletion.

## 3. Business Logic & Workflows

### 3.1. Parties, Properties and the Consultation That Freezes the Fork

A brokerage is registered by an operator superuser with a `name` and a `license_code`, the latter unique across all brokerages. Three optional attributes shape everything the firm's agents can later do: `authorization_cap`, which defaults to 4500.00 and may never be set below 0.00 or above 15000.00, is the ceiling any listing agent of that firm may authorize on a seller's behalf; `tax_exempt`, which defaults to false, means that projects billed to this brokerage under a brokerage payer routing carry a `tax_amount` of exactly 0.00; and `billing_email`, the invoice delivery address used for brokerage-payer projects. A brokerage also carries `open_project_count`, a derived integer that starts at 0 and counts the projects naming this brokerage whose `workflow_state` is anything other than `CLOSED`.

Clients are the people. A client's `client_type` is one of `LISTING_AGENT`, `SELLER` or `BROKERAGE_ADMIN`; each carries a `full_name` and an `email` that is unique across all clients. A `brokerage_id` is required when the client is a `LISTING_AGENT` or a `BROKERAGE_ADMIN`, and is null when the client is a `SELLER` — a `brokerage_id` supplied on a `SELLER` is ignored and stored as null rather than refused. Every client may request a `personal_authorization_cap`, which defaults to 4500.00. From these the service derives `effective_authorization_cap` at creation, and re-derives it whenever the referenced brokerage's own cap changes — a re-derivation that in practice never runs, because no endpoint in this API updates a brokerage once it is registered: for a `LISTING_AGENT` it is the smaller of the client's `personal_authorization_cap` and the brokerage's `authorization_cap`; for a `SELLER` or a `BROKERAGE_ADMIN` it is 15000.00, the hard ceiling the platform will never authorize past. In both branches the result is rounded half-up to two decimal places and is returned as an attribute of the client resource. Every client is also created with `consent_on_file` false. A seller — and only the seller in question, acting on their own record, or an operator superuser — may set that flag true; it is the standing permission that lets their listing agent authorize a project above the agent's own ceiling.

Properties record an `address_line`, a `city`, a two-letter `state_code`, an `owner_client_id` that must reference a client of type `SELLER`, a `distance_miles` road distance from the staging warehouse used to select the travel zone, an `occupancy` of either `OCCUPIED` or `VACANT`, and a `room_count` of stageable rooms. Each property carries a `prep_state` that starts at `NEW` and walks `NEW → CONSULT_BOOKED → SCOPED → IN_PREP → STAGED → DESTAGED → CLOSED`. Booking a consultation is what moves the property `NEW → CONSULT_BOOKED`, and it is refused unless the property is in `NEW` and no consultation on that property currently sits in `SCHEDULED`, `HELD`, `SCOPE_DRAFTED` or `SCOPE_SUBMITTED`; either refusal is reported as `ERR_CONSULTATION_INVALID_STATE` (HTTP 409). Scope approval moves it `CONSULT_BOOKED → SCOPED`. Project authorization moves it `SCOPED → IN_PREP`. Completing the install on the vacant arm — or completing the last open visit on the occupied arm — moves it `IN_PREP → STAGED`, and that hop requires the project to be in `INSTALL_SCHEDULED` or `VISITS_OPEN`. De-staging moves it `STAGED → DESTAGED`: on the vacant arm when the pickup completes, and on the occupied arm when the project is closed, with the project required to be in `DESTAGE_PENDING`, `VISITS_OPEN` or `STAGED`. Closing the project moves it `DESTAGED → CLOSED`, which requires the project to be in `CLOSEOUT` with a `payment_state` of `SETTLED` or `WRITTEN_OFF`. Closing the project is named as the trigger for both the `STAGED → DESTAGED` hop and the `DESTAGED → CLOSED` hop, and it **runs both of them, in that order, in the one request**. On the occupied arm, where nothing has de-staged the property earlier, the two hops walk it `STAGED → DESTAGED → CLOSED` and it ends the request in `CLOSED`; on the vacant arm the pickup cascade has already taken the first hop, so only the second one moves anything. Every one of the hops in this machine bumps the property's `version` when it actually moves the row, and each is a no-op when the property is not already sitting in that hop's origin state — so an occupied-arm close, which takes two of them, bumps the property twice. **The property-state condition is the only thing any hop tests.** The project-state preconditions recorded above describe when each hop ordinarily occurs and are never re-checked at the hop itself: the closing action re-checks the project's own `CLOSEOUT`, `payment_state` and invoice conditions and then takes both hops on nothing but the property's own state, and the `IN_PREP → STAGED` and `DESTAGED → IN_PREP` hops likewise fire off the property alone, having been reached from a caller that already moved the project. Booking a consultation is the one and only operation anywhere in this service that reads `prep_state` as a precondition; no project, listing, lease, pickup, invoice or deposit action consults it.

The property machine has one backwards arc, and it is what makes it non-linear. When escrow falls through, the property walks `DESTAGED → IN_PREP` for a re-stage, which requires the listing to be `UNDER_CONTRACT` and the project to be in `DESTAGE_PENDING`.

Listings are created against a property with a `listing_agent_client_id` referencing a client of type `LISTING_AGENT`, an `mls_number` unique across listings, and a `list_price` strictly greater than zero. A listing's `listing_state` begins at `ACTIVE` and its `fallout_count` at 0; `under_contract_at` and `closed_at` are both null until the corresponding transition sets them. The listing lifecycle is described in §3.9, where its cascades belong.

Package tiers are configuration. Each has a `tier_code` of `ESSENTIAL`, `SIGNATURE` or `LUXE` unique across tiers, a `tier_rank` of 1 for `ESSENTIAL`, 2 for `SIGNATURE` and 3 for `LUXE` used to decide whether a change is an upgrade or a downgrade, a `room_cap` of rooms included before room overage begins, an `included_accessory_sets` count, an `included_photo_sessions` count, a `base_price` that serves as the vacant-arm package price and equally as the occupied-arm consultation retainer, and a `monthly_rent_rate` charged per cycle for the owned portion of a vacant-arm package at that tier.

A consultation is booked against a property by a coordinator, an agent or the seller, naming the `property_id`, the `requested_by_client_id` of whoever booked it, and a `scheduled_at` instant that must be at or after the logical clock at creation — an earlier instant is refused with `ERR_INVALID_REQUEST` (HTTP 400). It is created in state `SCHEDULED` with `revision_count` 0, `scoped_room_count` 0, `rental_line_count` 0 and `estimated_hours` 0. **Holding the consultation is the fork.** The `SCHEDULED → HELD` transition requires the logical clock to have reached `scheduled_at`, stamps `held_at` with the logical clock, and copies the property's `occupancy` into the consultation's `pipeline` — `OCCUPIED` becoming `OCCUPIED_PREP` and `VACANT` becoming `VACANT_STAGING`. That copy is permanent.

Scope is then drafted room by room. Each scope item carries a `room_label` unique within its consultation, an `action`, an `estimated_hours` figure defaulting to 0, a `requires_rental` boolean defaulting to false, and an `accessory_set_count` defaulting to 0; the service assigns each a `sequence_index`, a 1-based creation order within the consultation that pins deterministic processing order. The legal actions split by pipeline: `EDIT`, `DECLUTTER` and `REFRESH` are `OCCUPIED_PREP`-only, `PACKAGE_ROOM` is `VACANT_STAGING`-only, and `ACCESSORY_ONLY` is legal on both. On an `OCCUPIED_PREP` consultation `requires_rental` must be false; a `true` there is refused with `ERR_INVALID_REQUEST` (HTTP 400), because rung 20's `ERR_PIPELINE_MISMATCH` is scoped to the scope item's `action` alone and never to this flag. Adding the first scope item moves the consultation `HELD → SCOPE_DRAFTED`, and further items may be added while it stays in `SCOPE_DRAFTED`; each addition recomputes `scoped_room_count`, which counts scope items whose `action` is anything other than `ACCESSORY_ONLY`, and `rental_line_count`, which counts scope items with `requires_rental` true.

Submitting the scope moves it `SCOPE_DRAFTED → SCOPE_SUBMITTED`, requires at least one scoped room — a `scoped_room_count` of zero is refused with `ERR_CONSULTATION_INVALID_STATE` (HTTP 409), the same code the origin check uses — and a non-null `recommended_tier_code` of `ESSENTIAL`, `SIGNATURE` or `LUXE`, and stores that recommendation along with the consultant's `estimated_hours`. The `estimated_hours` figure is optional: when it is absent the stored value is left exactly as it stood, which on a first submission is the 0 the consultation was created with, and a re-submission after a rejection that omits it keeps the number the earlier submission set. The client then answers. Approval moves `SCOPE_SUBMITTED → SCOPE_APPROVED` and, as its cross-entity effect, drives the property to `SCOPED`; the approver must be either the listing agent of a listing on that property or the property's own owner. Rejection moves `SCOPE_SUBMITTED → SCOPE_REJECTED` and may carry a `rejection_note`. From `SCOPE_REJECTED`, adding another scope item walks the consultation back to `SCOPE_DRAFTED` and increments `revision_count`; the loop `SCOPE_DRAFTED → SCOPE_SUBMITTED → SCOPE_REJECTED → SCOPE_DRAFTED` may repeat without limit, and `revision_count` records how deep it has gone. Abandoning a consultation from `SCHEDULED`, `HELD`, `SCOPE_DRAFTED` or `SCOPE_REJECTED` moves it to `CANCELLED` and, when no other live consultation remains on that property, returns the property to `NEW` — and this one hop is not an origin-gated hop like the rest of the machine: it sets `prep_state` to `NEW` from wherever it stands, bumping the property's `version` unless it was already there. `SCOPE_APPROVED` and `CANCELLED` are the terminal states of this machine.

### 3.2. From Approved Scope to an Authorized Project

A project is the contract. A coordinator opens one against the approved consultation, supplying the `property_id`, the `consultation_id`, the `listing_id` whose lifecycle will drive de-stage eligibility, the `package_tier_id`, the `payer_client_id` the invoice will be addressed to, and a `payer_type`; a `brokerage_id` is additionally required when the `payer_type` is `BROKERAGE`, and a `payer_split_agent_pct` may be supplied, defaulting to 0.50 and meaningful only under a split routing. Creation is refused with `ERR_SCOPE_NOT_APPROVED` unless the named consultation is in `SCOPE_APPROVED`, and refused with `ERR_DUPLICATE_ACTIVE_PROJECT` if any other project on that same property sits in a `workflow_state` other than `CLOSED`. The new row starts in `workflow_state` `DRAFT` and `payment_state` `UNBILLED`, with `window_extension_count` 0, `restage_count` 0, `photo_sessions_consumed` 0, `reshoot_credits_remaining` 1, `destage_eligible` false and `fiscal_hold` false. Its `pipeline` is copied from the consultation and is immutable thereafter.

Four numbers are computed at creation. The project's `room_count` is the count of scope items on the consultation whose `action` is not `ACCESSORY_ONLY` — accessory-only rooms are excluded from the room count while still contributing their accessory sets. The project's `accessory_set_count` is the sum of `accessory_set_count` over every scope item on that consultation. **Room overage** is the number of rooms beyond the tier's `room_cap`, floored at zero, multiplied by 375.00 and rounded half-up to two decimal places. **Accessory overage** is the number of accessory sets beyond the tier's `included_accessory_sets`, floored at zero, multiplied by 120.00 and rounded the same way. Both are computed against the tier the project currently holds, so both are re-derived whenever the tier changes.

**Travel** is a three-zone tiered fee read off the property's `distance_miles` and nothing else. A distance of at most 15 miles is zone 1 and costs 0.00. A distance greater than 15 and at most 40 miles is zone 2 and costs 145.00. Anything beyond 40 miles is zone 3 and costs 310.00. Both zone boundaries are inclusive at the top, so exactly 15.0 miles is zone 1 and exactly 40.0 miles is zone 2. The result is rounded half-up to two decimal places. Travel is evaluated wherever it is needed and is never stored: it enters `contract_value` each time that value is derived, and it is re-read off the property's current `distance_miles` every time the invoice's six evaluation steps run — which is on every read of the invoice as well as inside every operation that touches it (§3.9). No visit, install or pickup event re-derives it on its own.

**`contract_value` is the number the authorization caps are compared against**, and it is where the two pipelines first produce different money for identical inputs. It is assembled from six parts: the tier's `base_price`, the room overage, the accessory overage, the travel fee, a forward-looking rental commitment, and a labour figure. On a `VACANT_STAGING` project the forward-looking part is the tier's `monthly_rent_rate` multiplied by 3 cycles and rounded half-up to two decimal places, and the labour part is exactly 0.00 — a forward commitment to three cycles of package rent, made before any pull exists. On an `OCCUPIED_PREP` project the forward part is exactly 0.00 and the labour part is the consultation's `estimated_hours` multiplied by an hourly rate of 165.00, rounded half-up to two decimal places, with a first-visit surcharge of 95.00 added *after* that rounding. The six parts are then added and the sum rounded half-up to two decimal places. The same property with the same tier therefore yields a different `contract_value` on each arm, by construction. `contract_value` is an attribute of the project resource and is re-derived on every package upgrade and downgrade.

Authorization is the act that turns a draft into a commitment, and it may be performed by a `ListingAgent`, a `Seller` or a `BrokerageAdmin`. It requires the project to be in `DRAFT` — otherwise `ERR_PROJECT_INVALID_STATE` — and the consultation to be in `SCOPE_APPROVED`, which is rung 38's `ERR_SCOPE_NOT_APPROVED` a second time, and it runs the authority arithmetic: headroom is the acting principal's `effective_authorization_cap` minus the project's `contract_value` — for an acting `BrokerageAdmin`, whose identity names a `Brokerage` and not a `Client`, the cap used is the platform ceiling of 15000.00 — and the comparison is inclusive, so headroom of exactly 0.00 authorizes. Negative headroom is refused with `ERR_AUTHORIZATION_CAP_EXCEEDED`, but only in the residual case where neither neighbouring refusal owns it: not when the payer client carries `consent_on_file` true, not when the payer client is of `client_type` `SELLER`, and not when the contract has cleared the platform ceiling. A listing agent reaching above their own ceiling is separately refused with `ERR_SELLER_CONSENT_REQUIRED` unless the payer client is a `SELLER` carrying `consent_on_file` true — which is exactly the case rung 39's carve-outs hand on to it. And above every private arrangement sits the platform's own ceiling: a `contract_value` above 15000.00 is refused with `ERR_BROKERAGE_CAP_EXCEEDED` no matter who is acting and no matter what consent exists.

A successful authorization does five things at once. The project moves `DRAFT → AUTHORIZED`. `authorized_by_client_id` is set to the acting principal and `authorized_amount` is snapshotted from the current `contract_value`, so that a later upgrade pushing past that snapshot re-opens the cap question. `authorized_at` is stamped with the logical clock. On an `OCCUPIED_PREP` project, `service_window_end_date` is derived from that instant. And a deposit row is created in state `REQUIRED` carrying its computed `amount`. The property meanwhile advances `SCOPED → IN_PREP`. The response body is the project, not the new deposit, and the status is 200 — this endpoint is one of the two places a row is minted without a 201 (§4).

Package tier changes are available after that, and they are deliberately asymmetric. An **upgrade** must name a tier of strictly greater `tier_rank`; a **downgrade**, one of strictly smaller rank; either violation is `ERR_INVALID_TIER_CHANGE`. On an upgrade the service takes the price delta between the new tier's `base_price` and the old one's, and prorates it: if the project has a lease, the remaining days are the days from the logical clock to the lease's `end_date`, floored at zero, and the delta is multiplied by the smaller of 1.0 and those remaining days divided by a 30-day proration basis; if no lease row exists yet, the full delta is charged with no proration at all. To that prorated delta the service adds the change in room overage between the new and old tiers and the change in accessory overage between the new and old tiers, and rounds the total half-up to two decimal places. The result is booked into the invoice's `package` component and the `contract_value` is re-derived. Neither change reads or writes the project's `workflow_state`: a tier may be moved on a project still in `DRAFT`, on one already `STAGED`, and on every state in between. On a **downgrade** the credit granted for the surrendered price difference is the difference between the old and new `base_price` multiplied by a downgrade credit rate of 0.00 — that is, the customer is credited nothing — and the charge is a restocking fee of 400.00 minus that credit, plus the same room-overage and accessory-overage deltas, rounded half-up to two decimal places. Because the credit rate is zero and a restocking fee applies, an upgrade followed by the matching downgrade does not restore the project's original `contract_value`: the round trip costs the restocking fee plus the whole prorated upgrade charge, while the reverse order costs the restocking fee plus a re-charged full price delta. Moving from one tier to another is priced differently from moving back.

On the occupied arm the project also carries a **service window**. `service_window_end_date` is the authorization instant plus 45 days plus the `window_extension_count` multiplied by 15 days; on a vacant-arm project it is null. Extending the window increments `window_extension_count`, re-derives `service_window_end_date` from the authorization instant and the new count, and books an extension fee of 250.00 into the invoice's `package` component. Because no rung on this endpoint tests the project's `workflow_state`, an `OCCUPIED_PREP` project that has not been authorized may still be extended: the count rises and the 250.00 is booked, but the re-derivation has no anchor to work from and `service_window_end_date` stays null. The count may never reach 2 — the check is strictly less than 2, so at most two extensions are ever granted, and a third attempt is `ERR_WINDOW_EXTENSION_LIMIT`.

### 3.3. Who Pays, and the Deposit That Follows From It

The `payer_type` chosen at project creation is one of five values, and it routes both the deposit percentage and, much later, the tax base and the delivery gate on photography. Under `AGENT` the listing agent is billed and the deposit is 20 percent of the contract value. Under `SELLER` the homeowner is billed and the deposit is 30 percent. Under `SPLIT` the bill is divided and the deposit is 25 percent. Under `BROKERAGE` the firm is billed and the deposit is exactly 0.00 percent — which is to say exactly nothing. Under `PAY_AT_CLOSING` the deposit is 50 percent, taken up front precisely because the invoice will not be due until a closing event that may never happen.

The deposit `amount` is the project's `contract_value` at the instant of authorization multiplied by that percentage, rounded half-up to two decimal places, and **no floor is applied at this point**. A non-zero requirement below the 500.00 minimum is carried onto the deposit row exactly as computed and is refused later, at collection, by the fiscal rung: the amount is computed honestly and rejected explicitly rather than being quietly lifted. Collection accepts an amount that is either exactly 0.00 or at least 500.00, and anything in between is `ERR_DEPOSIT_BELOW_MINIMUM`. A brokerage-payer project is therefore the only routing whose deposit is legally collected below the minimum, because it is the only one that produces exactly zero.

**The deposit row is created carrying its whole `amount` in `held_remaining`.** The row that authorization creates in state `REQUIRED` already has `held_remaining` equal to the computed `amount`, with every applied, refunded and forfeited bucket at 0.00, so §2.11's conservation identity holds on the row from the instant it exists. Collecting the deposit moves it `REQUIRED → HELD`, re-asserts `held_remaining` at the full `amount` — which changes nothing, since that is what the row already carried — and drives the project's `payment_state` `UNBILLED → DEPOSIT_HELD`. That state is a gate on execution: scheduling visits, scheduling an install and completing an install all require the deposit to be `HELD`, and a request that arrives earlier is refused with `ERR_DEPOSIT_NOT_HELD` (HTTP 402).

Applying a deposit runs a strict three-bucket **waterfall** against a named `invoice_id`, and the buckets are consumed in a fixed order with no bucket ever skipped to reach a later one. Starting from the current `held_remaining`, the first bucket takes the smaller of what remains and the pickup's `damage_total` and adds it to `applied_to_damage`. What survives that then meets the second bucket, which takes the smaller of the remainder and the lease's `holdover_charge` and adds it to `applied_to_holdover`. What survives *that* meets the third bucket, which takes the smaller of the remainder and the invoice's `subtotal` plus its `tax_amount` and adds it to `applied_to_balance`. Each bucket's contribution is rounded half-up to two decimal places as it is accumulated, and `held_remaining` is set to the rounded residue. The invoice's `deposit_applied` and `total_due` are recomputed as a consequence.

A deposit that is consumed only in part after a waterfall run lands in `PARTIALLY_APPLIED`, and that state is re-entrant: each further run may consume more of the same deposit, and the deposit stays `PARTIALLY_APPLIED` for as long as the waterfall consumes strictly less than the whole `held_remaining`. When a run consumes the entire remainder, `held_remaining` becomes 0.00, `invoice_id` is set to the invoice consumed against, and the deposit reaches `APPLIED` — and that includes the degenerate run against a deposit whose `held_remaining` is already 0.00, which consumes the whole of it and therefore lands `APPLIED` rather than `PARTIALLY_APPLIED`. Both `HELD` and `PARTIALLY_APPLIED` are legal origins for a waterfall run, and both are legal origins for the two terminating arcs. A **refund** returns the residue: `refunded_amount` takes the value of `held_remaining`, which then becomes 0.00, and the deposit reaches `REFUNDED` — but only once the project's invoice is in state `PAID`, and a refund attempted earlier is refused with `ERR_DEPOSIT_INVALID_STATE`. A **forfeit** keeps the residue on the operator's side: `forfeited_amount` takes the value of `held_remaining`, which becomes 0.00, and the deposit reaches `FORFEITED`. Forfeiture happens either by explicit operator action carrying a `reason`, or as a consequence of an invoice being voided — and on that second path it is conditional rather than certain: the void forfeits only a deposit that is in `HELD` or `PARTIALLY_APPLIED`, and passes silently over one still `REQUIRED` or already `APPLIED`, `REFUNDED` or `FORFEITED`, so a void does not always leave a forfeited deposit behind. The waterfall run itself names its target invoice by `invoice_id` in the body and does not test that the invoice belongs to the deposit's own project; the damage, holdover and balance figures the three buckets are measured against are read from the deposit's project regardless.

When the payer routing is `SPLIT`, the invoice's settled total is divided at materialisation: the agent's share is the invoice `total_due` multiplied by `payer_split_agent_pct` and rounded half-up to two decimal places, and the seller's share is the `total_due` minus that agent share, itself rounded half-up to two decimal places. **The rounding remainder always lands on the seller's share, never on the agent's** — the seller share is defined as the remainder, not as its own independent percentage calculation. Neither share is a stored field or a `line_summary` component: the split is an accounting statement about how the settled `total_due` divides between the two payers, and no response body in this API carries either figure.

### 3.4. Pipeline V: Stock, Vendors and the Install Day

The warehouse holds owned units. Each inventory item is registered with a `sku` unique across items, a `category` drawn from `SOFA`, `BED`, `TABLE`, `CHAIR`, `ART`, `RUG`, `LAMP` and `ACCESSORY_SET`, an `acquired_at` purchase instant that later drives its depreciation band, a `replacement_value`, and a `monthly_rate` that is this unit's own per-cycle rent contribution. Every item is created with `condition_grade` `A`, `status` `AVAILABLE` and `times_deployed` 0. The `status` machine is genuinely non-linear, with two independent loops back to `AVAILABLE`. The deployment loop runs `AVAILABLE → RESERVED → DEPLOYED → AVAILABLE`: allocation reserves a unit, install-complete deploys it and increments `times_deployed`, and a pickup whose assessment found no charge returns it. The repair loop runs `DEPLOYED → IN_REPAIR → AVAILABLE`: a repair-disposition damage finalization sends a deployed unit to the bench and degrades its `condition_grade` one step, `A` becoming `B`, `B` becoming `C`, and `C` staying `C`; a repair-out returns it to stock. A reserved unit can also be released straight back to `AVAILABLE` when its line is released or its pull cancelled, which nulls the line's `inventory_item_id` and drops the line. An `AVAILABLE` unit may be sent to the bench directly. And a unit may be written off — from `AVAILABLE` or from `IN_REPAIR` by explicit operator action carrying a `reason`, or from `DEPLOYED` when a damage finalization's disposition is replacement, in which case the line is marked returned. `WRITTEN_OFF` is terminal, and a written-off unit is still counted in `on_hand_total` forever. The count of `AVAILABLE` units in a given category is what the allocation pass and the warehouse summary both read.

Partner rental houses are registered as vendors with a `name` and four commercial terms, each of which has a declared default: `lead_time_days` defaults to 7 and is the number of days between placing an order and the earliest legal delivery or install date; `min_lease_cycles` defaults to 4 and is the vendor's own minimum term in 30-day cycles, which may legitimately exceed the project's own term; `cancel_cutoff_days` defaults to 4 and marks how many days before the earliest delivery date a placed order stops being cancelable at the early rate; and `rate_multiplier` defaults to 1.35 and is the multiplier applied for vendor-sourced units. A vendor's `status` starts at `ACTIVE` and may be moved to `SUSPENDED`; only an `ACTIVE` vendor may have an order placed against it, and an attempt to place against a `SUSPENDED` one is refused with `ERR_ORDER_INVALID_STATE` (HTTP 409) — the same code the order's own state machine uses, since the suspension has no error of its own. Vendor terms and status may be updated after registration, by a partial update that writes only the fields the payload actually supplies and leaves every omitted or explicitly null one untouched; the vendor's `name` is not among the updatable fields and a `name` in the body is ignored. Every update bumps the vendor's `version` whether or not it changed anything, and none of it is retrospective: an order already placed keeps the `earliest_delivery_date`, `cancel_cutoff_date`, `effective_term_cycles` and `monthly_rate_total` derived from the terms as they stood at placement.

A rental order names a `project_id`, a `vendor_id` and a `unit_count` between 1 and 60 inclusive, and is created in state `DRAFT` with `cancellation_fee` 0.00 and with `placed_at`, `earliest_delivery_date`, `cancel_cutoff_date`, `effective_term_cycles` and `monthly_rate_total` all null until it is placed. Rung 20 does not reach this entity: an order may be drafted, placed, confirmed and cancelled against an `OCCUPIED_PREP` project as readily as against a vacant one, and nothing on the occupied arm will ever consume it. Placing it moves `DRAFT → PLACED` and derives four values at once. `placed_at` takes the logical clock. `earliest_delivery_date` is `placed_at` plus the vendor's `lead_time_days` days, and it is the floor for any install instant that consumes this order. `cancel_cutoff_date` is `earliest_delivery_date` minus the vendor's `cancel_cutoff_days` days. `effective_term_cycles` is the larger of the project's lease `initial_cycles` and the vendor's `min_lease_cycles`, falling back to 3 cycles as the project figure when no lease row exists yet. `monthly_rate_total` is the order's `unit_count` multiplied by a vendor unit base rate of 85.00 multiplied by the vendor's `rate_multiplier`, rounded half-up to two decimal places **once per order and not per unit**. The tier's `monthly_rent_rate` plays no part in it: a vendor order is priced off the 85.00 vendor unit base rate on every tier.

The vendor's own representative — and only that representative, matched by identity against the order's `vendor_id` — confirms the order, moving `PLACED → CONFIRMED`. Install completion then moves a confirmed order `CONFIRMED → DELIVERED`, provided the install's `scheduled_at` is on or after the order's `earliest_delivery_date`. Releasing the pull after pickup moves a delivered order `DELIVERED → RETURNED`. Cancellation is where the money turns: from `DRAFT` or `PLACED`, with the logical clock strictly before `cancel_cutoff_date`, the order moves to `CANCELLED` and its `cancellation_fee` is 25 percent of `monthly_rate_total`; from `PLACED` or `CONFIRMED`, with the clock on or after `cancel_cutoff_date`, it moves to `CANCELLED_LATE` and the fee is 100 percent of `monthly_rate_total`. In both arms the fee is rounded half-up to two decimal places and every vendor pull line on the project's current pull pointing at that order is dropped, whatever state that line held. A `DRAFT` order that was never placed has a null `monthly_rate_total`, which the fee arithmetic reads as zero, so cancelling it books a `cancellation_fee` of exactly 0.00 on the early arm. **The boundary is strict**: an instant exactly equal to `cancel_cutoff_date` takes the late arm. Crossing that one-second line multiplies the fee fourfold, and the fee is never rebated if the vendor is later re-engaged. A `DELIVERED` or `RETURNED` order can no longer be cancelled at any price. Nor is every combination covered: the early arm is open only to `DRAFT` and `PLACED`, so a `CONFIRMED` order asked to cancel while the clock is still strictly before `cancel_cutoff_date` has no declared arc at all and is refused with `ERR_ORDER_INVALID_STATE`.

An inventory pull is opened against an authorized vacant-arm project, which moves the project `AUTHORIZED → PULL_OPEN` and is refused if any pull on that project is already in `DRAFT`, `SUBMITTED`, `PARTIAL` or `COMMITTED`. The pull is created in state `DRAFT` with `requested_unit_count` 0, `filled_unit_count` 0, `fill_rate` 0, `resubmit_count` 0 and a null `committed_at`. Lines are then added to a `DRAFT` or `PARTIAL` pull, each naming a `source` of `OWNED` or `VENDOR`, a `category`, a `room_label` that must match a scope item's `room_label` on the project's consultation, a `quantity`, and — for vendor lines — the `rental_order_id` the line will draw against, which is a required field on those lines and an ignored one on owned lines. The named order need only exist; nothing checks that it belongs to this line's project. An owned line always has quantity exactly 1; a vendor line may carry 1 through 20 units. Each line is created in state `REQUESTED` with `monthly_rate` 0, a null `inventory_item_id` and a null `rental_order_id` on owned lines. Adding a line recomputes the pull's `requested_unit_count`, which sums `quantity` over every line not in state `DROPPED`, and its `fill_rate`.

**The allocation pass** runs when the pull is submitted, and it walks every `REQUESTED` line in ascending order of the line's creation timestamp. For an owned line the candidate set is every inventory item whose `status` is `AVAILABLE` and whose `category` matches the line's; candidates are ranked by `acquired_at` ascending with creation timestamp ascending as the tie-break, and the first is taken. That item's `inventory_item_id` is written onto the line, the item moves `AVAILABLE → RESERVED`, and the line moves `REQUESTED → ALLOCATED`. An empty candidate set leaves the line `UNFILLED` instead. For a vendor line the requirement is that the `rental_order_id` named on the line resolves to an order in state `PLACED` **or** `CONFIRMED` — a vendor who confirms before the pull is submitted must not thereby strand the line — carrying spare units at least equal to the line's `quantity`, where an order's spare units are its `unit_count` less the quantity already drawn against it by pull lines in state `ALLOCATED`, `DEPLOYED`, `RETURNED` or `SWAPPED`, and less whatever earlier lines in this same pass have just taken. Success allocates the line against that order, and failure leaves it `UNFILLED`. Every allocated line's `monthly_rate` is derived at that moment: an owned line takes the allocated unit's own `monthly_rate` and ignores `quantity` entirely, while a vendor line takes 85.00 multiplied by the vendor's `rate_multiplier` multiplied by the line's `quantity`; either way the result is rounded half-up to two decimal places. The same room can therefore cost different money depending only on which pool filled it.

At the end of the pass the pull's `filled_unit_count` is recomputed as the sum of `quantity` over lines in `ALLOCATED`, `DEPLOYED` or `RETURNED`, and `fill_rate` is `filled_unit_count` divided by `requested_unit_count`, rounded half-up to **four** decimal places, or exactly 0.0000 when nothing was requested. The pull lands in `SUBMITTED`, and immediately falls to `PARTIAL` when `filled_unit_count` is smaller than `requested_unit_count`. A `PARTIAL` pull may be re-submitted, which increments `resubmit_count` and re-runs the pass over the `UNFILLED` lines only, moving any line for which a candidate now exists `UNFILLED → ALLOCATED`; the retry is refused once `resubmit_count` has reached 2, with `ERR_PULL_RESUBMIT_LIMIT`.

Committing the pull is permitted from `SUBMITTED` or from `PARTIAL`, requires a `fill_rate` of at least 0.70 — exactly 0.7000 commits — and is optimistic-concurrency guarded on the parent project as described in §2.9. A commit stamps `committed_at` with the logical clock, drops every still-`UNFILLED` line to `DROPPED`, and bumps both the pull's and the project's `version` — the project's version is bumped on every commit, whether or not its `workflow_state` moves. When the commit is a re-stage after a fall-out-of-escrow it also walks the project `RESTAGE_REQUIRED → STAGED`; on an ordinary first commit the project's `workflow_state` stays at `PULL_OPEN`. Those two statements cover disjoint cases and no third case exists: a commit moves no other `workflow_state`. **The commit does not re-run the pull's counts.** `requested_unit_count`, `filled_unit_count` and `fill_rate` keep the values the allocation pass left them, so dropping the unfilled lines does not retroactively lift a partial commit's `fill_rate` to 1.0000, and the shortfall rung 54 weighed stays readable on the row afterwards. A committed pull is later released — ordinarily after the pickup has completed or the lease has been cancelled — which moves it `COMMITTED → RELEASED`, moves every `DEPLOYED` line to `RETURNED` and every `DELIVERED` rental order to `RETURNED`; the release endpoint enforces the `COMMITTED` origin and nothing else, testing no pickup or lease condition of its own, because hop one of the pickup-complete cascade has ordinarily released the pull already and a release that also demanded those conditions could never run. A pull may instead be cancelled from `DRAFT`, `SUBMITTED` or `PARTIAL`, which returns every allocated line's item `RESERVED → AVAILABLE`, nulls that line's `inventory_item_id`, and drops every line that is not already `DROPPED`. **Unlike the commit, the cancel does re-run the counts** — with every line now `DROPPED` there is nothing left to count, so a cancelled pull reads back `requested_unit_count` 0, `filled_unit_count` 0 and `fill_rate` 0.0000 no matter what it once held. `RELEASED` and `CANCELLED` are terminal.

The install is scheduled against a vacant-arm project whose pull is `COMMITTED` and whose deposit is `HELD`, supplying a `scheduled_at`, a `crew_size` between 1 and 8 inclusive, and the lease's `initial_cycles`. **Scheduling the install is what creates the lease**, in state `PENDING`, with the supplied `initial_cycles`. A **consumed rental order** — the phrase rungs 42 and 44 both turn on — is any rental order on that project whose state is `PLACED` or `CONFIRMED`; an order still in `DRAFT`, or already `DELIVERED`, `RETURNED`, `CANCELLED` or `CANCELLED_LATE`, is not consumed and constrains nothing. Three capacity and authority checks guard the install: the install instant must be on or after every consumed rental order's `earliest_delivery_date`; the requested `initial_cycles` must be at least 3; and every consumed order's `effective_term_cycles` must be no greater than `initial_cycles` plus 6. The `crew_size` is required, is bounded 1 through 8, and is stored and published on the install — but it is **inert**: capacity is one install per day whatever crew is booked, and no rule, rate or fee anywhere reads it. Crew capacity is bucketed by **UTC calendar day** with a capacity of 1 install per day and no buffer of any kind: two installs at 09:00 and at 21:00 on the same UTC date collide even though their working hours do not overlap, while an install at 23:59 and another at 00:01 the next day never collide. The install is created in state `SCHEDULED` with `attempt_count` 0 and a null `completed_at`, and the project moves `PULL_OPEN → INSTALL_SCHEDULED`.

Starting the install requires the logical clock to have reached its `scheduled_at` and the pull to be `COMMITTED`, and moves it `SCHEDULED → IN_PROGRESS`. **Completing it is the pivot of the whole vacant arm**, and it fires three cascade hops plus two propagations. The install's `completed_at` is stamped from the logical clock. Hop one moves the lease `PENDING → ACTIVE` with its `start_date` set to that very `completed_at` — the lease clock starts at install-complete, not at contract signature and not at authorization. Hop two derives the lease's `end_date` and both ends of its pickup window. Hop three moves every `ALLOCATED` pull line to `DEPLOYED` and every linked owned item `RESERVED → DEPLOYED` with `times_deployed` incremented, while every `CONFIRMED` rental order moves to `DELIVERED`. Alongside those, the project moves `INSTALL_SCHEDULED → STAGED` and the property moves `IN_PREP → STAGED`. Completion additionally requires the deposit to be `HELD`.

When the crew cannot get in, the install moves `SCHEDULED → NO_ACCESS`, which requires the clock to have reached the scheduled instant. A no-access install may be rescheduled to a new `scheduled_at`, moving `NO_ACCESS → SCHEDULED` and incrementing `attempt_count`, provided `attempt_count` is strictly below 2 and the new day still satisfies both crew capacity and vendor lead time. Reporting no access again once `attempt_count` has reached 2 does not reschedule: it moves the install `NO_ACCESS → CANCELLED`, returns every `RESERVED` item on the project's pull to `AVAILABLE`, and moves the still-`PENDING` lease to `CANCELLED`. **The pull and its lines are left exactly as they stand**: an `ALLOCATED` line keeps that state and keeps pointing at the `inventory_item_id` of a unit that is now back in `AVAILABLE`, and the pull keeps its `COMMITTED` state, its counts and its `fill_rate`. This second no-access also requires the clock to have reached the scheduled instant, exactly as the first did. Reporting no access from `NO_ACCESS` while `attempt_count` is still below 2 is not a declared arc at all — the crew has to be re-booked first — and is refused with `ERR_INSTALL_INVALID_STATE`. `COMPLETE` and `CANCELLED` are the install machine's terminal states.

### 3.5. The Lease Term, Its Extensions, and Holdover

A lease exists only on a vacant-arm project. It is created in state `PENDING` when the install is scheduled, carrying the requested `initial_cycles` — at least 3 and at most 24 — with `extension_cycles` 0, `billed_cycles` 0, `monthly_rent` 0, `holdover_days` 0, `holdover_charge` 0 and a null `start_date`. Install completion moves it `PENDING → ACTIVE` and derives everything at once: `start_date` becomes the install's `completed_at`; `billed_cycles` becomes `initial_cycles`; `end_date` becomes `start_date` plus `billed_cycles` multiplied by 30 days; the pickup window is derived; and `monthly_rent` is computed.

**`monthly_rent` is the sum of the pull lines that are actually standing in the house.** Only lines in state `ALLOCATED` or `DEPLOYED` contribute; `UNFILLED`, `DROPPED`, `SWAPPED` and `RETURNED` lines are excluded entirely. The lines are summed in ascending order of their creation timestamp, and **each line's `monthly_rate` is rounded half-up to two decimal places before it enters the sum**, with the accumulated total likewise carried at two decimal places.

**The pickup window** is derived from an anchor and is a closed interval. The anchor is the lease's `end_date` in the ordinary case, and it is the logical clock instead in exactly one case: when, **at the moment the window is being derived**, the lease is in state `ENDING` and the logical clock is **strictly** before `end_date` — that is, when an early de-stage is being triggered. Both halves of that test are read live rather than remembered. A clock standing exactly on `end_date` is not strictly before it and so anchors on `end_date`; and a lease that once reached `ENDING` early, was returned to `ACTIVE` by a fall-out of escrow and then reaches `ENDING` again on or after its `end_date` anchors on `end_date` too, because the earlier early de-stage is not carried forward. `pickup_window_start` is the anchor plus 5 days; `pickup_window_end` is `pickup_window_start` plus 7 days. A pickup may be scheduled anywhere in that closed interval, endpoints included, and outside it the scheduling is refused with `ERR_PICKUP_OUTSIDE_WINDOW`. The window is re-derived whenever the lease becomes active, whenever an extension is applied, and whenever the lease reaches `ENDING`. **An early de-stage moves the window and nothing else**: `billed_cycles` is not reduced, and the lease charge stays exactly where it was.

The lease reaches `ENDING` from `ACTIVE` or `EXTENDED` in two ways — the listing going under contract, or a coordinator or clerk marking the term complete. Either way the window is re-derived and a pickup is auto-created in state `SCHEDULED` at the newly derived `pickup_window_start`. The project hop is conditional on the project itself: it moves `STAGED → DESTAGE_PENDING` with `destage_eligible` set true only when the project is actually sitting in `STAGED`. Marking the term complete on a project that a fall-out of escrow has pulled back to `RESTAGE_REQUIRED` therefore ends the lease and books the pickup while leaving the project's `workflow_state` where it stands — rung 26 tests the lease's state and nothing else. The reverse arc, `ENDING → ACTIVE`, is taken when escrow falls through, and it clears the derived pickup window. `ENDED` and `CANCELLED` are the lease machine's terminal states; a lease reaches `ENDED` from `ENDING` or from `HOLDOVER` when the pickup completes, and reaches `CANCELLED` from `PENDING` when a repeatedly inaccessible install is finally cancelled.

**Extensions** are requested against an `ACTIVE`, `EXTENDED` or `ENDING` lease by a coordinator or the listing agent, supplying `requested_cycles` and `expected_lease_version`. The request must name a whole positive number of cycles — the extension increment is 1 cycle, so fractional requests and zero are both refused with `ERR_PARTIAL_CYCLE_EXTENSION` even though zero survives the shape gate — and granting it must not push the lease's `extension_cycles` beyond a lifetime total of 6, which is `ERR_EXTENSION_LIMIT_REACHED`. The extension is created in state `REQUESTED` with `granted_cycles` 0, `extended_line_count` 0, `returned_line_count` 0, `extension_charge` 0 and `swap_credit` 0, and the parent lease's `version` is bumped by 1 as part of the request.

The warehouse then adjudicates with a `decision`. A decision to deny moves the extension `REQUESTED → DENIED`, sets `granted_cycles` to 0, and touches nothing else. A decision to approve produces one of two outcomes, and the two are structurally different rather than being degrees of the same thing. **`APPROVED_FULL`** is taken when every deployed line on the lease's project is free for the extended window: `granted_cycles` becomes `requested_cycles`, `extended_line_count` becomes the count of deployed lines, `returned_line_count` stays 0, and the charge prices the entire deployed line set. **`APPROVED_PARTIAL`** is taken when at least one deployed line is committed to another project's install inside the extended window while at least one other deployed line is free: `granted_cycles` still becomes the full `requested_cycles`, `extended_line_count` becomes the count of free lines, `returned_line_count` becomes the count of committed-elsewhere lines, and both a charge and a swap credit are derived. The partiality is in the **line set, not in the term** — the term extends in full and the furniture shrinks. The two outcomes partition every case, and the surviving set alone decides between them: the adjudication lands `APPROVED_PARTIAL` exactly when at least one deployed line fails the survival test, and `APPROVED_FULL` otherwise. A lease with no deployed line at all therefore approves in full, with `extended_line_count` 0, `returned_line_count` 0 and an `extension_charge` of 0.00; a lease none of whose deployed lines survive approves partially, with `extended_line_count` 0 and an `extension_charge` of 0.00 while every one of its lines is counted as returned.

The specification pins the survival test twice, and both statements are recorded here. Stated as a per-line rule, a deployed line survives the extension exactly when it is an owned line, or when it is a vendor line whose rental order's `effective_term_cycles` is at least the lease's `billed_cycles` plus the `requested_cycles`; any outcome in which some but not all lines survive is a partial approval. Stated as a state-machine precondition, the returned set is the set of deployed lines committed to another project's install inside the extended window. **The per-line rule is the operative test** — it is what the adjudication actually evaluates, line by line, in creation order, treating a vendor line whose `rental_order_id` no longer resolves as not surviving — and the state-machine phrasing describes the set that rule produces rather than adding a second, independent test.

**`extension_charge`** is the surviving rate base multiplied by `granted_cycles`, rounded half-up to two decimal places. The rate base is the sum, in ascending order of line creation timestamp and with each line rounded half-up to two decimal places before it enters the sum, of the `monthly_rate` of the deployed lines being priced: every deployed line on a full approval, and only the lines not committed elsewhere inside the extended window on a partial. This makes the charge **non-monotone in `requested_cycles`**: asking for a longer window pulls more lines into another project's install and shrinks the surviving set, so a larger `requested_cycles` can produce a smaller `extension_charge`. **`swap_credit`** applies only on a partial approval and is the sum of the returned lines' rounded `monthly_rate` values multiplied by 50 percent, rounded half-up to two decimal places — a credit for the pieces that could not be swapped in. It is an attribute of the extension resource and of nothing else: no `line_summary` component carries it, and it never reduces an invoice.

Applying an approved extension moves it to `APPLIED`, and this is the only extension state that ever contributes to the lease. On a partial, each of the lines the adjudication identified as returned moves `DEPLOYED → SWAPPED` and its owned item moves `DEPLOYED → AVAILABLE`; a line the adjudication named but which has since left `DEPLOYED` is passed over. **`returned_line_count` is not touched here.** It was fixed at adjudication as the size of the non-surviving set and reads the same afterwards whether or not every one of those lines was still there to swap — it counts what the adjudication decided, not what the application moved. On both arms the lease takes the `ACTIVE → EXTENDED` transition: `extension_cycles` grows by `granted_cycles`, `billed_cycles` becomes `initial_cycles` plus `extension_cycles`, `end_date` is recomputed from the unchanged `start_date`, the pickup window is re-derived, and `monthly_rent` is recomputed over the **surviving** line set. The lease then immediately returns `EXTENDED → ACTIVE` so that a further extension can be requested; that automatic return is a system transition with its own version bump. Extensions in `REQUESTED`, `APPROVED_FULL`, `APPROVED_PARTIAL` or `DENIED` never contribute to `billed_cycles`; only `APPLIED` ones do. `APPLIED` and `DENIED` are the extension machine's terminal states.

**Holdover** is what happens when nobody hands the furniture back. A clerk accrues it against a lease whose pickup window has passed with no completed pickup. The first accrual moves the lease `ENDING → HOLDOVER` and requires the logical clock to be strictly past `pickup_window_end` plus 2 grace days; it sets `holdover_cap_period_start` to `pickup_window_end` and derives both holdover figures. Each of the three entry conditions on that first accrual — a derived pickup window to measure from, a clock strictly past the window plus those 2 days, and no pickup on the project already in `COMPLETED` — is refused with `ERR_LEASE_INVALID_STATE` (HTTP 409), the same code the origin check uses, and the 2 days here are the flat grace: a `REFUSED` pickup shortens the grace inside `holdover_days` but does not bring this eligibility test forward. Further accruals are taken from `HOLDOVER` back to `HOLDOVER`, re-deriving both figures each time and re-testing none of the three. This is one of the endpoints rungs 14 and 15 do not guard, so holdover accrues on a closed project and under a terminated listing alike.

`holdover_days` counts whole days elapsed past `pickup_window_end`, computed by taking the elapsed time from `pickup_window_end` to the logical clock, flooring it to whole days, subtracting the grace, and flooring the result at 0. **The grace depends on how the pickup failed.** If the project's latest pickup reached `REFUSED`, the grace is 0 days — an occupant who turns the crew away is charged from the first day past the window. If it reached `NO_ACCESS`, or there was no failed attempt at all, the grace is 2 days. The same calendar date therefore yields two different `holdover_days` values depending on which door the crew found.

`holdover_charge` is a **cumulative-tier accrual under a per-period cap**, and it is a pure function of the `holdover_days` count and nothing else. Days are numbered cumulatively from the first chargeable day: days 1 through 7 accrue at 45.00 each, and every day from the eighth onward accrues at 75.00 each. The tier ladder never resets. The cap, however, does: the chargeable days are taken in order and grouped into consecutive blocks of 30 **chargeable days** — the first block being days 1 through 30, the second 31 through 60, and so on — the amount accrued within each block is capped at 1800.00, and the charge is the sum of those capped block amounts, rounded half-up to two decimal places. `holdover_cap_period_start` is set to `pickup_window_end` at the first accrual and advanced by 30 days on each later accrual for as long as the logical clock stands at or past its next boundary, so the row records which calendar period the lease has reached. **That stored instant is a record and not an input**: the charge arithmetic never reads it, and because the grace days are subtracted before the day count is blocked, the block boundaries and the period-start boundaries do not in general coincide.

One further lease-side money rule belongs here even though it lands on the invoice. A vendor whose own minimum term outruns what the project ever billed produces a **shortfall charge**: for every rental order on the project in state `DELIVERED` or `RETURNED`, the shortfall is that order's `effective_term_cycles` minus the lease's `billed_cycles`, floored at 0, and the order contributes its `monthly_rate_total` multiplied by that shortfall, rounded half-up to two decimal places before accumulation; the accumulated total is rounded again and booked into the invoice's `lease` component. Cancelled and late-cancelled orders are excluded, because their money is carried in the cancellation component instead. This charge **falls as `billed_cycles` rises**, so applying an extension — which adds an `extension_charge` — simultaneously *reduces* the lease component in the very same request, and extending by exactly the shortfall zeroes this line entirely. The lease component also carries the initial lease charge itself, which is the lease's `monthly_rent` at the instant of invoice materialisation multiplied by its `initial_cycles`, rounded half-up to two decimal places; extension cycles are billed through `extension_charge` instead, so the two never double-count.

### 3.6. De-Staging: the Pickup at the Door and the Damage Tail

A pickup names its `project_id`, its `lease_id` and a `scheduled_at` that must fall inside the closed pickup window. Most pickups are not booked by hand at all: the lease reaching `ENDING` auto-creates one in state `SCHEDULED` at `pickup_window_start`. A pickup is created with `attempt_count` 0, `assessed_line_count` 0, `damage_total` 0 and a null `completed_at`. The `lease_id` in the body need only resolve; nothing checks that the lease belongs to the project in the path, and the window the `scheduled_at` is measured against is whichever lease was named. Starting it requires the logical clock to have reached its `scheduled_at` and moves it `SCHEDULED → IN_PROGRESS`; **assessments may only be raised while the pickup is in progress**. Starting a pickup is also where the project's de-stage start — the instant rungs 48 and 50 measure a shoot against — is recorded. It is stamped from the logical clock **the first time any pickup on that project starts and never again**, so a second pickup begun after a re-stage does not move it; it is bookkeeping rather than an attribute, appears on no response body, and writing it does not bump the project's `version`.

Two different things can go wrong at the door, and this system insists they are not the same event. `SCHEDULED → NO_ACCESS` means nobody was there; it increments `attempt_count` and leaves the holdover grace period intact. `SCHEDULED → REFUSED` means the occupant turned the crew away; it also increments `attempt_count`, but it makes the lease eligible for holdover accrual immediately and **forfeits the two grace days entirely**, so every day past the window is chargeable from the first. Both require the clock to have reached the scheduled instant, and both may be re-booked to a new `scheduled_at`, moving back to `SCHEDULED`, so long as `attempt_count` is strictly below 3 and the new instant is still inside the lease's pickup window. **The pickup's counter advances at the door, not at the desk.** The increment belongs to the two door events themselves, exactly as stated above; the re-booking reads `attempt_count` and does not add to it. That is the opposite of the install and the visit, whose counters advance on the reschedule rather than on the failed attempt (§3.4, §3.7), and the difference is real arithmetic: because each re-booking follows one failed door, it is the **third** re-booking — the one that follows the third failure — that is refused with `ERR_PICKUP_ATTEMPT_LIMIT`. A scheduled pickup is instead moved to `CANCELLED` when escrow falls through. `COMPLETED` and `CANCELLED` are the pickup machine's terminal states.

Each damage assessment is raised against one pull line — the `pull_line_id` is unique per pickup, so a line is assessed at most once, and the line need only exist, not belong to this pickup's own pull — and records a `condition_at_pickup` of `INTACT`, `MINOR`, `MAJOR` or `MISSING` together with a `repair_cost_estimate` that defaults to 0 and is ignored outright when the condition is `INTACT` or `MISSING`. The row is created in state `DRAFT` with `appeal_count` 0, `depreciated_replacement_value` 0, `charge_amount` 0 and `disposition` `NO_CHARGE`.

Assessing the finding moves it `DRAFT → ASSESSED` and prices it in two steps. First, **the depreciated replacement value**. For an owned line the service computes the unit's age in whole months as the elapsed time from the item's `acquired_at` to the logical clock divided by 30-day months and floored, then selects a factor: an age of at most 12 months takes a factor of 1.00, at most 36 months takes 0.70, at most 72 months takes 0.45, and anything older takes a floor factor of 0.25. **The band boundaries are inclusive at the top**, so exactly 12 months is the first band and 13 months is the second. The item's `replacement_value` is multiplied by that factor and rounded half-up to two decimal places — which means an identical sofa costs different money depending only on when the warehouse bought it. For a vendor line age is ignored entirely: the value is a flat vendor unit replacement value of 900.00 multiplied by the line's `quantity` multiplied by one plus a 15 percent vendor damage surcharge, rounded half-up to two decimal places. That is the vendor's schedule, not the operator's.

Second, **the charge and the disposition**. An `INTACT` finding charges 0.00 with disposition `NO_CHARGE`. A `MISSING` finding charges the full depreciated replacement value with disposition `REPLACE`, because there is nothing left to salvage. A `MINOR` or `MAJOR` finding compares the `repair_cost_estimate` against 60 percent of the depreciated replacement value, and the comparison is **strict**: an estimate exactly equal to sixty percent stays on the repair arm. If the estimate is strictly greater, the disposition is `REPLACE` and the charge is 50 percent of the depreciated replacement value — the salvage recovery rate — rounded half-up to two decimal places. Otherwise the disposition is `REPAIR` and the charge is the smaller of the `repair_cost_estimate` and the depreciated replacement value. The final `charge_amount` is rounded half-up to two decimal places, and both `charge_amount` and `disposition` are attributes of the assessment resource. This pricing is **non-monotone by construction**: because a written-off unit is broken for parts and recovers half its depreciated value, crossing the threshold from below *drops* the customer's bill — sixty percent of the value on the last repair cent, fifty percent on the first replace cent — so a higher repair estimate can produce a lower charge.

A client may appeal. The listing agent or the seller disputes an `ASSESSED` finding, optionally carrying a `dispute_note`, which moves it `ASSESSED → DISPUTED` and increments `appeal_count`; a second dispute is refused with `ERR_APPEAL_LIMIT_REACHED` because the cap is one appeal. The platform then rules with a `decision`, on the one damage endpoint that neither rung 14 nor rung 15 guards. Upholding moves it `DISPUTED → UPHELD` and keeps the number exactly as it was. Revising moves it `DISPUTED → REVISED`, replaces the `repair_cost_estimate` with the supplied `revised_repair_cost`, and recomputes both `charge_amount` and `disposition` from that new estimate. `revised_repair_cost` is optional even on a revision: when it is omitted the stored estimate stands unchanged, and the re-pricing still runs — re-depreciating the unit against the logical clock as it now reads, which on its own can move both the value and the disposition. A revised assessment is then re-assessed, moving `REVISED → ASSESSED` with the charge and disposition recomputed once more, so the appeal loop `ASSESSED → DISPUTED → REVISED → ASSESSED` may run at most once.

Finalizing books the money. It is permitted from `ASSESSED` or from `UPHELD`, is optimistic-concurrency guarded on the parent pickup as described in §2.9, and moves the assessment to `FINAL` — the machine's only terminal state. It adds the assessment's `charge_amount` to the pickup's `damage_total`, increments the pickup's `assessed_line_count`, bumps the pickup's `version` by 1, and sends the unit down the arc its disposition demands: a repair disposition moves the owned item `DEPLOYED → IN_REPAIR` and degrades its `condition_grade` one step, while a replace disposition moves it `DEPLOYED → WRITTEN_OFF` and marks the line returned. A `NO_CHARGE` disposition leaves the unit to return to stock with the rest.

**Completing the pickup fires the seven-hop closeout cascade**, and it is refused unless every assessment on that pickup has reached `FINAL`. The pickup's `completed_at` is stamped from the logical clock, and then, in order: hop one moves the inventory pull `COMMITTED → RELEASED`; hop two, because the pull released, moves every `DEPLOYED` pull line to `RETURNED`; hop three, because those lines returned, moves every owned item `DEPLOYED → AVAILABLE` — except those an assessment already sent to `IN_REPAIR` or `WRITTEN_OFF`, which stay where they are — and moves every `DELIVERED` rental order to `RETURNED`; hop four, because the vendor orders returned, moves the lease from `ENDING` or `HOLDOVER` to `ENDED`; hop five, because the lease ended, materialises a `DRAFT` invoice on the project with its `line_summary` populated from the lease, extension, holdover and damage components; hop six, because the invoice was materialised, runs the deposit waterfall and moves the deposit `HELD → PARTIALLY_APPLIED` or `HELD → APPLIED`; and hop seven, because the deposit was applied, moves the project `DESTAGE_PENDING → PICKED_UP` and the property `STAGED → DESTAGED`. **The "because" in that chain names the ordering, not a dependency**, and the hops do not gate one another: each tests only its own subject's state, and a hop whose subject is not in the right state is skipped while every later hop still runs. A pull that is not `COMMITTED` skips hop one and hop two still returns the `DEPLOYED` lines; a lease that is neither `ENDING` nor `HOLDOVER` skips hop four and hop five still materialises the invoice; a deposit that is neither `HELD` nor `PARTIALLY_APPLIED` skips hop six and hop seven still moves the project. The one thing all seven share is the pickup: its `state` and `completed_at` are written before hop one, so every hop, and the invoice hop five derives, sees a pickup that has already `COMPLETED`. Hop five reuses the project's existing invoice row whenever one is already there, whatever state it holds, and never mints a second.

### 3.7. Pipeline O: Billable Visits Inside a Service Window

On an occupied project the work is a sequence of visits, and there is no pull, no install, no lease and no pickup. Scheduling the first visit moves the project `AUTHORIZED → VISITS_OPEN` and requires the deposit to be `HELD`. Each visit carries a `scheduled_at` that must fall on or before the project's `service_window_end_date`, and the service assigns a `visit_index`, the 1-based creation order of that visit within its project. A visit is created in state `SCHEDULED` with `hours_logged` 0, `billable_hours` 0 and `attempt_count` 0.

Completing a visit reports its `hours_logged`. It requires the logical clock to have reached the visit's `scheduled_at` and to be no later than the project's `service_window_end_date`; a completion reported after the window has closed is refused with `ERR_SERVICE_WINDOW_EXPIRED`. On completion the visit's `billable_hours` becomes the larger of the reported `hours_logged` and the minimum billable quantum of 2.0 hours, rounded half-up to two decimal places; a visit that is not `COMPLETED` has `billable_hours` of 0. The two-hour floor means a forty-minute stop still bills two hours.

The project moves `VISITS_OPEN → STAGED` once every visit on it is terminal — that is, every visit is either `COMPLETED` or `CANCELLED` — **and at least one is `COMPLETED`**. That same moment carries the property `IN_PREP → STAGED`. This is a condition over the whole visit set and not a side effect of one endpoint: it is re-evaluated every time a visit becomes terminal, so **cancelling the last still-open visit settles the project exactly as completing it would**, and a project whose remaining visit is cancelled is never stranded in `VISITS_OPEN`. A visit in `NO_ACCESS`, and a visit re-booked back to `SCHEDULED`, are not terminal and hold the project open; a project that is not in `VISITS_OPEN` when a visit turns terminal is left where it is.

A visit at which nobody is home moves `SCHEDULED → NO_ACCESS`, again requiring the clock to have reached the scheduled instant. It may then be re-booked to a new `scheduled_at`, moving `NO_ACCESS → SCHEDULED` and incrementing `attempt_count`, provided `attempt_count` is strictly below 2 and the new instant is still on or before the service window's end; the third attempt is refused with `ERR_VISIT_ATTEMPT_LIMIT`. A visit may also be cancelled outright from `SCHEDULED` or from `NO_ACCESS`. `COMPLETED` and `CANCELLED` are the visit machine's terminal states — unlike the install, an out-of-attempts visit is not auto-cancelled; it simply stops being reschedulable.

The labour that reaches the invoice is aggregated from completed visits only; `NO_ACCESS` and `CANCELLED` visits contribute nothing. The visits are processed in ascending `visit_index`, with creation timestamp ascending as the tie-break, and their `billable_hours` are totalled. That total is multiplied by the hourly rate of 165.00 and rounded half-up to two decimal places, and then — **after that rounding, not inside it** — a first-visit surcharge of 95.00 is added when any completed visit carries `visit_index` 1. The result is booked into the invoice's `labour` component.

The service window itself is 45 days from the authorization instant, stretched by 15 days for each extension granted, with at most two extensions and a fee of 250.00 apiece, as described in §3.2. On the vacant arm `service_window_end_date` is null and none of these rules apply.

### 3.8. Photography and Delivery to the MLS

A photo shoot is booked against a project with a `scheduled_at` and an optional `is_reshoot` flag defaulting to false. Non-reshoot shoots receive a `session_index`, the 1-based creation order of non-reshoot shoots on that project; the shoot is created in state `SCHEDULED` with `overage_fee` 0, a null `delivered_at`, and `mls_delivery_gated` derived immediately.

**`mls_delivery_gated` is true exactly when the project's `payer_type` is `PAY_AT_CLOSING`, and false for `AGENT`, `SELLER`, `SPLIT` and `BROKERAGE`.** It is derived at shoot creation and re-derived on every read of the shoot, and it is an attribute of the shoot resource. Its only effect is at delivery time.

Two scheduling constraints guard the booking. Temporally, on a vacant-arm project the shoot instant must be on or after the project's completed install's `completed_at` — earlier is `ERR_SHOOT_BEFORE_INSTALL` — and on either arm the shoot instant must be **strictly** before the project's de-stage start, meaning the instant the pickup entered `IN_PROGRESS`; on or after that is `ERR_SHOOT_AFTER_DESTAGE`. Geometrically, the shoot occupies a **half-open 180-minute block** beginning at its `scheduled_at`, and it must not overlap any existing shoot on the **same property** in state `SCHEDULED` or `COMPLETED`, where each existing shoot is treated as occupying its own 180-minute block **plus a trailing 60-minute buffer**. The buffer is asymmetric: it hangs off the end of the shoot already on the books, and the newcomer contributes none of its own. A new shoot starting exactly 240 minutes after an existing one is therefore legal, and 239 minutes is not. A collision is `ERR_SHOOT_TIME_CONFLICT`. This geometry is deliberately different from the install's in every respect — minutes rather than days, half-open intervals rather than calendar-day buckets, and a trailing buffer rather than none.

Completing a shoot requires the logical clock to have reached its `scheduled_at`. It then re-tests, against the shoot's `scheduled_at` and not against the clock, exactly the two temporal rungs the booking walked: on a vacant-arm project the project must have an install in state `COMPLETE` whose `completed_at` is at or before that instant, and on either arm that instant must be strictly before the project's de-stage start — **which is the same rung-50 test as at booking, not a fresh condition about the pickup's current state**, so a shoot booked and taken before any pickup began may still be completed after that pickup has started or finished. On an occupied-arm project completion additionally requires at least one visit already in state `COMPLETED`, and a completion attempted before that is refused with `ERR_VISIT_NOT_COMPLETED`. Completion moves the shoot `SCHEDULED → COMPLETED`, raises the project's `photo_sessions_consumed` when `is_reshoot` is false, and derives the `overage_fee`: a reshoot is always 0.00 because it consumes a credit rather than a session; a non-reshoot whose `session_index` is strictly greater than the project's current tier's `included_photo_sessions` costs 285.00; and anything else costs 0.00. The result is rounded half-up to two decimal places and is stored on the shoot. The invoice's `photo` component is then the per-shoot-rounded sum of `overage_fee` over **every shoot on the project**, taken in creation order and whatever state each has since reached: a shoot later cancelled, or one whose reshoot request pulled it into `RESHOOT_REQUESTED`, keeps the fee it earned at completion and keeps contributing it. A shoot that never completed carries 0.00 and contributes nothing. `photo_sessions_consumed` is not a stored counter that completion writes once but a figure **derived on every read of the project**: it is the number of non-reshoot shoots on that project whose state is `COMPLETED` or `DELIVERED`. Completing a non-reshoot shoot therefore raises it by one, and requesting a reshoot against that same shoot lowers it again, because the source shoot leaves `COMPLETED`/`DELIVERED` for `RESHOOT_REQUESTED` and stops being counted. `reshoot_credits_remaining` is derived on every read in the same way, from the formula given below.

Delivering the images moves the shoot `COMPLETED → DELIVERED` and stamps `delivered_at` from the logical clock. It is permitted when `mls_delivery_gated` is false, or when the project's invoice is in state `PAID`; a gated shoot whose invoice is unpaid is refused with `ERR_MLS_DELIVERY_PAYMENT_GATE` (HTTP 402).

Reshoots are an entitlement, not a purchase. Each package carries exactly 1 reshoot credit, and the project's `reshoot_credits_remaining` is that entitlement minus the count of reshoot shoots on the project sitting in `SCHEDULED`, `COMPLETED` or `DELIVERED`. The listing agent or the seller may request a reshoot against a shoot in state `COMPLETED` or `DELIVERED`, supplying the new `scheduled_at`; the source shoot moves to `RESHOOT_REQUESTED`, a fresh shoot is created with `is_reshoot` true, a null `session_index` and state `SCHEDULED`, and `reshoot_credits_remaining` decreases by one because that new row joins the counted set. The response body is the **new** shoot, not the source, and it answers 201. With no credit left the request is refused with `ERR_RESHOOT_ENTITLEMENT_EXHAUSTED`. Cancelling a `SCHEDULED` shoot moves it to `CANCELLED` and, when that shoot was itself a reshoot, **returns the credit** — again by derivation rather than by any stored counter moving: `CANCELLED` is outside the counted set, so the subtraction simply stops. `DELIVERED` and `CANCELLED` are the shoot machine's terminal states.

### 3.9. The Listing Lifecycle, the Invoice, and Closing the Book

The listing is the outside world's view of the sale, and its lifecycle drives de-staging. Only the listing's own agent may move it, and every arc bumps its `version`.

**Going under contract** is taken from `ACTIVE` or from `BACK_ON_MARKET`, stamps `under_contract_at` from the logical clock, and fires three cascade hops. Hop one moves every **`VACANT_STAGING`** project on that listing whose `workflow_state` is `STAGED` to `DESTAGE_PENDING` and sets `destage_eligible` true; an `OCCUPIED_PREP` project sitting in `STAGED` is passed over by all three hops, having no lease to end and no furniture to collect. Hop two moves that project's lease — `ACTIVE` or `EXTENDED` — to `ENDING` and re-derives both ends of the pickup window. Hop three auto-creates a pickup on the project in state `SCHEDULED` with its `scheduled_at` set to the freshly derived `pickup_window_start`. Both origin states take the identical three hops. **Hops two and three are conditional on the lease and hop one is not**: a `STAGED` vacant project whose lease is neither `ACTIVE` nor `EXTENDED` — one already `ENDING`, or `ENDED`, or `CANCELLED`, or a project carrying no lease row at all — still takes hop one and comes out `DESTAGE_PENDING` with `destage_eligible` true, while no window is re-derived and no pickup is booked. **`destage_eligible` has exactly two sources, and the passage of time is not one of them.** It is set true by hop one here, and by the identical project hop that `POST /staging/leases/{lease_id}/mark-term-complete` takes; it is set back to false by hop one of a fall-out of escrow; and nothing else in this service ever writes it. In particular **no rule sets it when a lease reaches its `end_date`** — a lease may run past `end_date` indefinitely with `destage_eligible` still false, because a lease end is only ever observed through one of those two explicit actions.

**Falling out of escrow** is the cyclic arc, taken from `UNDER_CONTRACT` back to `BACK_ON_MARKET`; it requires the listing to be `UNDER_CONTRACT` and increments `fallout_count`, which records how often the sale has collapsed. It fires four hops, over **every** project on that listing and not only over one. Hop one moves a project that is in `DESTAGE_PENDING` to `RESTAGE_REQUIRED` and increments its `restage_count`, while `destage_eligible` returns to false; a project in any other state is left where it stands. **Hops two, three and four are not conditional on hop one having moved anything** — they are taken for every project on the listing regardless. Hop two moves every `SCHEDULED` pickup on the project to `CANCELLED`. Hop three moves the lease `ENDING → ACTIVE` and clears both ends of the derived pickup window. Hop four re-checks availability: every **owned** pull line on the project's current pull in state `DEPLOYED` whose inventory item is missing or no longer in status `DEPLOYED` is marked `UNFILLED` — a vendor line is never re-checked here, having no owned unit to look up — the pull's counts and `fill_rate` are recomputed from what survives, and if that rate is below 1.0000 **and the pull is still `COMMITTED`** it drops to `PARTIAL`; a pull already `RELEASED` or `CANCELLED` keeps its state. Afterwards the property is walked `DESTAGED → IN_PREP` for every project on the listing whose property is sitting in `DESTAGED`, on the property's own state alone. The cycle `UNDER_CONTRACT → BACK_ON_MARKET → UNDER_CONTRACT` may repeat. A re-staged project returns `RESTAGE_REQUIRED → STAGED` when its pull is committed again, which requires a `fill_rate` of at least 0.70.

**Closing the sale** is taken from `UNDER_CONTRACT` only and stamps `closed_at` from the logical clock. Its cascade converts deferred money into due money: every invoice on every project on the listing in state `DEFERRED_CLOSING` becomes `ISSUED` with a `due_date` of `closed_at` plus 15 days, and that project's `payment_state` moves `DEFERRED → INVOICED` — the project axis moves only if it was actually sitting in `DEFERRED`, and `fiscal_hold` is cleared alongside it. A listing whose projects hold no deferred invoice closes with nothing else happening at all. The conversion is refused with `ERR_CLOSING_DEFERRAL_EXPIRED` when the logical clock is more than 120 days past the invoice's `issued_at`, a check swept across every deferred invoice on the listing **before** the listing's own state moves, so the refusal leaves the listing `UNDER_CONTRACT`; a deferred invoice with no `issued_at` is passed over by it.

**Terminating the listing** — the expired-or-withdrawn outcome, carrying a required `termination_reason` that distinguishes the two without changing the arc — is taken from `ACTIVE` or from `BACK_ON_MARKET`. That reason is a free-form string: no enumeration is declared for it, so rung 7 never inspects it and any string value is accepted. What rung 6 requires is that the field be present and non-null; a value of any other JSON type is rung 8's `ERR_INVALID_REQUEST`. Both origins take the identical cascade: every invoice on every project on the listing in state `DEFERRED_CLOSING` moves to `ESCALATED` and accrues a closing escalation fee of 650.00 into its `closing_escalation` component, the project's `payment_state` becomes `ESCALATED`, and the project's `fiscal_hold` becomes true. **The project half of that is conditional on the invoice half having fired**: a project on which no invoice was actually escalated keeps whatever `payment_state` it had — including `DEFERRED` — and is not put on fiscal hold, so terminating a listing whose projects were never deferred moves nothing but the listing itself. Where an invoice does escalate, the project axis is driven to `ESCALATED` from whatever value it held, not only from `DEFERRED`. `CLOSED_SOLD` and `TERMINATED` are the listing machine's terminal states, and both are ancestor freezes: a terminated listing blocks every mutating operation beneath it with `ERR_LISTING_TERMINATED`, and a sold-closed listing blocks the staging-execution operations with `ERR_LISTING_CLOSED`.

**Fiscal hold** deserves its own sentence because it reaches everywhere. A project's `fiscal_hold` is true exactly while its `payment_state` is `ESCALATED`, and while it is true no new commitment may be made — no pull, no install, no visit, no photo shoot, no reshoot request, no lease extension and no package upgrade — each refused with `ERR_FISCAL_HOLD` (HTTP 402). Paying the escalated invoice clears it.

**Opening closeout** materialises or re-derives the project's single invoice, and it behaves differently on the two arms. On an occupied-arm project sitting in `STAGED`, this is where the `DRAFT` invoice is created. On a vacant-arm project the invoice already exists — hop five of the pickup-complete cascade created it — so the call **returns that same invoice row and never creates a second one**, and requires every damage assessment on the project's pickup to be in state `FINAL`. Either way the invoice's `line_summary`, `subtotal`, `tax_amount` and `total_due` are re-derived, the project advances from `PICKED_UP` or from `STAGED` to `CLOSEOUT`, and the response body is the project's single invoice. This operation answers with HTTP 201 on both arms, including the vacant arm where no row was created — and on that arm the returned invoice's `version` is unchanged, because re-derivation is not a mutation. The `STAGED` origin belongs to the occupied arm alone: a `VACANT_STAGING` project offered at `STAGED` is refused with `ERR_PROJECT_INVALID_STATE` rather than with `ERR_PIPELINE_MISMATCH`, since it is the project's position in the workflow and not the endpoint's pipeline arm that is wrong.

The invoice's `line_summary` carries the twelve components named in §2.8, and `subtotal` is their per-component-rounded, fixed-order sum. **Tax then forks on the payer.** When the `payer_type` is `BROKERAGE` and the billed brokerage carries `tax_exempt` true, `tax_amount` is exactly 0.00 regardless of subtotal. When the `payer_type` is `SELLER`, only the rental components are taxed: the `lease`, `extension` and `holdover` components are added together and multiplied by a rental-only rate of 6.25 percent. In every other case — `AGENT`, `SPLIT`, a non-exempt `BROKERAGE`, and `PAY_AT_CLOSING` — the whole `subtotal` is multiplied by the standard rate of 8.25 percent. The result is rounded half-up to two decimal places. A seller-paid and an agent-paid invoice carrying identical lines therefore carry different tax.

**Late-payment interest never compounds on itself.** Its base is the invoice's `subtotal` plus its `tax_amount` and nothing else. If the invoice has no `due_date`, or the logical clock is on or before the `due_date`, `interest_accrued` is 0.00. Otherwise the months overdue are the elapsed time from `due_date` to the clock divided by 30 days and rounded **up** to a whole number, and the rate is selected from the base: a base strictly greater than 5000.00 accrues at 1.5 percent per month, and anything at or below that accrues at the reduced rate of 0.75 percent per month. The interest is the base multiplied by the rate multiplied by the months overdue, rounded half-up to two decimal places.

The evaluation order for the whole invoice is **pinned in six steps, and no step reads a later step's output**: first the `subtotal`; second the `tax_amount`, computed from that subtotal; third the interest base, which is subtotal plus tax; fourth the interest, whose rate tier is keyed on that base and therefore excludes interest itself, so the value is well defined in a single pass; fifth `deposit_applied`, which is the sum of the deposit's `applied_to_balance`, `applied_to_damage` and `applied_to_holdover`; and sixth `total_due`, which is the interest base plus the interest minus `deposit_applied`, floored at 0.00 and rounded half-up to two decimal places.

Those six steps are re-run from current inputs **on every read of the invoice** as well as inside every operation that touches it, and the re-derivation is not itself a mutation: it refreshes `line_summary`, `subtotal`, `tax_amount`, `interest_accrued`, `deposit_applied` and `total_due` without bumping the invoice's `version` or its `updated_at`. One consequence is worth stating plainly, because nothing anywhere stops it: **interest has no stop condition**. The formula tests only the `due_date` and the clock, never the invoice's state, so an invoice already in state `PAID` read long after its due date reports a rising `interest_accrued` and a rising `total_due` — the payment settled what was owed at the instant it was made, and it does not freeze the arithmetic afterwards.

The invoice itself starts in `DRAFT`. Issuing it moves `DRAFT → ISSUED`, stamps `issued_at` from the logical clock, sets `due_date` to `issued_at` plus 15 days, and drives the project's `payment_state` to `INVOICED`; it requires the project to be in `CLOSEOUT` and the `payer_type` to be anything other than `PAY_AT_CLOSING`. Deferring it is the `PAY_AT_CLOSING`-only alternative: it moves `DRAFT → DEFERRED_CLOSING`, stamps `issued_at`, leaves `due_date` null, and drives the project's `payment_state` to `DEFERRED`; the listing must still be in `ACTIVE`, `UNDER_CONTRACT` or `BACK_ON_MARKET`. Every one of those extra preconditions answers with the same code as the invoice's own origin check — the project's `CLOSEOUT`, the `payer_type` fork on both endpoints and the listing's state on the deferral are all reported as `ERR_INVOICE_INVALID_STATE` (HTTP 409), none of them with a code of its own. A deferred invoice becomes `ISSUED` when the listing closes, with `due_date` set from `closed_at` plus 15 days. A deferred invoice becomes `ESCALATED` when the listing terminates or when a clerk escalates it directly because the deferral has run out; escalation books the 650.00 closing escalation fee, recomputes `total_due`, and sets the project's `payment_state` to `ESCALATED` and its `fiscal_hold` true. `DEFERRED_CLOSING` is the direct escalation's **only** legal origin — an `ISSUED` or `DRAFT` invoice offered to it answers `ERR_INVOICE_INVALID_STATE`, and a `PAID` one answers `ERR_INVOICE_ALREADY_PAID` — and the endpoint neither tests the elapsed deferral nor requires that it has in fact run out; the 120-day figure lives on the listing's close, not here.

Payment is exact or it is nothing: `amount_paid` must equal `total_due` to the cent — each rounded half-up to two decimal places before the comparison, so a third decimal digit that rounds onto the same cent is accepted — and both underpayment and overpayment are refused with `ERR_OVERPAYMENT`. The `total_due` compared against is re-derived from current inputs at the moment of the attempt, which on an overdue invoice means the figure has moved since it was read. A payment against an invoice already in state `PAID` is refused with `ERR_INVOICE_ALREADY_PAID` — reached at the fiscal gate rather than at the state gate, by the named exception described in §2.7 — and so are a void and an escalate against a paid invoice. Because rung 68 is walked before rung 69, that answer is reserved for the duplicate payment that carries the exact `total_due`: a second payment carrying any other figure is answered first with `ERR_OVERPAYMENT`. A successful payment is permitted from `ISSUED` or from `ESCALATED`, moves the invoice to `PAID`, stamps `paid_at` from the logical clock, drives the project's `payment_state` to `SETTLED` and clears `fiscal_hold`. **It does not touch the deposit.** The residue stays on the deposit row until someone calls the refund endpoint, which is the only trigger the deposit machine declares for `REFUNDED` and which rung 73 gates on precisely this invoice state; a payment that refunded the residue by itself would leave that endpoint permanently dead. Voiding is the operator's write-off: permitted from `DRAFT`, `ISSUED`, `ESCALATED` or `DEFERRED_CLOSING`, carrying a `reason`, it moves the invoice to `VOID`, drives the project's `payment_state` to `WRITTEN_OFF`, and forfeits the deposit with `forfeited_amount` taking the value of `held_remaining`. `PAID` and `VOID` are the invoice machine's terminal states, and `SETTLED` and `WRITTEN_OFF` are the payment axis's.

A word on why the payment axis is separate at all. A project carries **two independent state machines on the same row**: `workflow_state` advances on execution events, `payment_state` advances on billing events, and neither reads the other's current value as a precondition — with exactly one join point. Closing the project moves it `CLOSEOUT → CLOSED`, and that is the single place the two axes meet: it requires the `payment_state` to be `SETTLED` or `WRITTEN_OFF` and every invoice on the project to be `PAID` or `VOID`, both refused — like the `CLOSEOUT` origin itself — with `ERR_PROJECT_INVALID_STATE`, in that order. Closing also carries the property `DESTAGED → CLOSED`. `CLOSED` is the workflow axis's only terminal state, and a closed project freezes the mutating operations rungs 14 and 15 guard with `ERR_PROJECT_CLOSED` — which, as that rung records, is most but not all of them, and does not include closing the project a second time.

## 4. Endpoint Definitions

Endpoints that bring a genuinely new resource into existence **and return it** answer with HTTP 201; every other successful call answers with HTTP 200. The status therefore tracks the body, not the side effects: `POST /staging/projects/{project_id}/authorize` mints a `Deposit` and `POST /staging/leases/{lease_id}/mark-term-complete` mints a `Pickup`, but each returns the row named in its path and each answers 200. `POST /staging/projects/{project_id}/installs` creates both an `Install` and a `Lease` and answers 201 with the install; `POST /staging/photo-shoots/{shoot_id}/request-reshoot` answers 201 with the new reshoot rather than with the source shoot. The one place the rule reads oddly is the closeout opener, which answers 201 on both pipeline arms even though on the vacant arm it returns an invoice the pickup cascade had already created. Successful responses carry the affected resource in `data` under the envelope of §2.2, except the warehouse summary and the clock setter, whose response shapes are described in §2.11 and §2.5 respectively.
