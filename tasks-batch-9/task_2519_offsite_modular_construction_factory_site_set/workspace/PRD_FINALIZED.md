# Offsite Modular Construction Factory & Site Set API — Product Requirements Document

## 1. Introduction

Volumetric modular construction promises a building delivered in boxes: rooms finished under a roof on a moving production line, trucked to a prepared foundation, and craned into place in days rather than months. The promise fails at the seams. A design that a detailing engineer froze last month is the design the state modular program approved and stamped with insignia labels — and if a revision quietly supersedes it, every module already claiming a takt window on the line was built to a drawing nobody permitted. A load whose widest module tips it from a standard envelope into a superload needs a route survey, escort vehicles, and a fresh transport permit before it may leave the gate. A module landed on the foundation and left open to weather becomes a warranty argument between the plant and the field crew. And a lender advancing deposits against factory work in progress needs a number that an independent, accredited agency will certify — recomputed from live plant state, not copied from whatever the manufacturer requested last week.

This API is the system of record that holds those seams together for a volumetric modular manufacturer operating one or more plants. It carries the design-freeze revision chain with peer review and segregation of duties; the bifurcated permitting ladder where a state modular program approves the design and a local authority having jurisdiction permits the foundation, the set and the occupancy; factory takt scheduling with a conserved plant-capacity ledger; third-party quality inspection with agency holds that reach backwards into transport and forwards into the lender's draw basis; shipping envelope classification, route surveys and transport permits; crane pick planning against a derated capacity chart; site set sequencing with weather exposure protection; factory-versus-field defect responsibility allocation; and a financing draw structure with deposits on work in progress and retainage withheld from every certified draw.

Ten disciplines write to this system and none of them trusts the others by default. The specification below is therefore written around three commitments: every state change is guarded by an explicitly ordered ladder of checks, so two parties disagreeing about why a request failed always get the same answer; every derived quantity is recomputed from live children rather than incremented in place, so a regression walks the roll-up backwards instead of stranding it; and every conserved ledger — plant minutes, load membership, certified money — has a named compensating action that returns it exactly to its prior value. Time itself is a first-class, server-owned quantity: the system runs on a logical clock that only moves when an administrator advances it, because permit expiry, weather exposure and takt windows must be reproducible.

## 2. Global Specifications & System-Wide Principles

Everything in this section is contract-level. Where §3 tells a business story, §2 fixes the shapes: which headers identify a caller, what an envelope looks like, how a list is paged, how money is rounded, and in what order the server decides that a request has failed.

### 2.1. Access Control and Actor Identity

Every request to every endpoint — reads included — must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the discipline it acts as. If either header is absent, or if `X-User-Role` is not one of the ten declared role names, the request is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). When both headers are well formed but the named role is not among the roles authorised for the endpoint being called, the rejection is `ERR_ROLE_NOT_PERMITTED` (HTTP 403). These two checks precede every other consideration in the system, including whether the resources named in the URL exist.

The ten roles are `ProgramAdmin`, `DesignEngineer`, `FactoryProductionManager`, `ThirdPartyInspector`, `TransportCoordinator`, `SiteSuperintendent`, `StateProgramOfficer`, `AuthorityHavingJurisdiction`, `WarrantyAdjudicator`, and `LenderDrawAdministrator`. Their responsibilities partition the lifecycle. `ProgramAdmin` is the manufacturer's program office: it registers plants, inspection agencies and projects, files permit applications on both tracks, and drives the logical clock. `DesignEngineer` creates design revisions, submits them for freeze review, and reviews a peer's submission. `FactoryProductionManager` is the plant manager: it creates modules, claims and releases takt slots, advances stations, and disputes warranty allocations charged to the factory. `ThirdPartyInspector` is the accredited inspection agency: it opens in-plant and final-factory inspections, records results, and places and clears agency holds. `TransportCoordinator` builds loads, runs route surveys and transport permits, and dispatches, delivers and cancels shipments. `SiteSuperintendent` is the field superintendent: it records site weather, plans crane picks, sets modules, closes connections and raises field defect claims. `StateProgramOfficer` is the state modular program authority, deciding plan review and insignia applications and adjusting agency accreditation. `AuthorityHavingJurisdiction` is the local building department, deciding foundation, set and occupancy applications. `WarrantyAdjudicator` independently allocates factory-versus-field responsibility on defect claims. `LenderDrawAdministrator` opens, certifies, funds and rejects construction draws.

Three of the ten roles are **entity-backed**, meaning `X-User-ID` is not a free-form operator string but the identifier of a stored row, and ownership is checked against it. When `X-User-Role` is `FactoryProductionManager`, `X-User-ID` is the `id` of the acting `Factory`; ownership checks on any resource that references a `Factory` compare the resource's foreign-key field to `X-User-ID` — concretely, a module operation is permitted only when the module's project carries a `factory_id` equal to `X-User-ID`. When `X-User-Role` is `ThirdPartyInspector`, `X-User-ID` is the `id` of the acting `InspectionAgency`; ownership checks compare the `agency_id` recorded on the inspection to `X-User-ID`. When `X-User-Role` is `SiteSuperintendent`, `X-User-ID` is the `id` of the acting `Project`; ownership checks compare the `project_id` of the module or project being operated on to `X-User-ID`. A violation of any of these three ownership comparisons is `ERR_ACTOR_NOT_OWNER` (HTTP 403).

The remaining seven roles are **opaque**. When `X-User-Role` is `ProgramAdmin`, `DesignEngineer`, `TransportCoordinator`, `StateProgramOfficer`, `AuthorityHavingJurisdiction`, `WarrantyAdjudicator`, or `LenderDrawAdministrator`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server may record it — as `submitted_by_user_id` and `reviewed_by_user_id` on a design package, as `decided_by_user_id` on a permit record, as `adjudicated_by_user_id` on a defect claim — but it never compares it to any entity's `id`. Note that `recorded_by_user_id` on an inspection record likewise captures the acting `ThirdPartyInspector`'s `X-User-ID`, which in that role's case *is* an agency identifier.

Two further identity rules cut across roles and are enforced independently of the endpoint's role list. First, design review is subject to segregation of duties: the `X-User-ID` recording a review decision on a design package must differ from that package's `submitted_by_user_id`, and a self-review is rejected with `ERR_SAME_ACTOR_REVIEW` (HTTP 403). Second, permit decisions are bifurcated by track: a `StateProgramOfficer` may decide only applications whose `track` is `STATE_MODULAR_PROGRAM`, and an `AuthorityHavingJurisdiction` only applications whose `track` is `LOCAL_AHJ`. Both roles appear on the decision endpoint's role list, so a cross-track attempt passes the role check and is then rejected with `ERR_PERMIT_TRACK_ROLE_MISMATCH` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Collection reads are paged with two optional query parameters. `limit` controls page size: its default is 10, its minimum accepted value is 1, and its maximum accepted value is 100. `offset` controls the starting position: its default is 0 and its minimum is 0. A supplied `limit` below 1 or above 100, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

Unless a list endpoint states otherwise, results are ordered by `created_at` ascending — oldest row first. This ordering is not cosmetic: several calculations in this specification enumerate rows in `created_at` ascending order and depend on that determinism.

For every list response the `meta` object carries `limit` (the effective page size actually applied), `offset` (the effective starting position), `total_count` (the number of rows matching the filters before paging), and `has_more` (true when rows remain beyond the current page). Single-resource responses omit all four.

### 2.4. Resource Identity, Timestamps and Versioning

Every resource in the system — `Factory`, `InspectionAgency`, `Project`, `DesignPackage`, `ModuleUnit`, `PermitRecord`, `InspectionRecord`, `Shipment`, `DefectClaim` and `DrawRequest` — is identified by an `id` that the server mints as a UUID. Identifiers carry no type prefix and no domain-flavoured encoding; a caller must never parse an `id` to learn what kind of thing it points at.

All ten of those resource types also carry three common properties. `created_at` is the instant the row was first persisted, `updated_at` is the instant of the most recent mutation, and both are rendered as ISO 8601 UTC timestamps with exactly three fractional-second digits. `version` is an integer that begins at 1 when the resource is created and increases by exactly 1 on every mutation of that resource, including mutations the caller did not request directly. There are no resources in this system that omit `updated_at` or `version`.

That last clause is the important one, because in this domain most writes touch more than one row. When a module advances a station, the module's `version` moves; so does its project's when the project's derived `phase` is re-evaluated, and so does its factory's when the plant capacity ledger changes. When a design package is frozen, the package, its superseded predecessor, every permit record that pinned that predecessor, the project, every reverted module and the affected factory all take a `version` increment and a refreshed `updated_at`. Callers holding a cached copy of any of those rows should assume it is stale after any operation described in §3.

### 2.5. Flat Addressing and Left-to-Right Identifier Resolution

Every resource is mounted flat under the `/modular` namespace: one collection segment per entity type and one item segment beneath it. There is no URL nesting of children under parents — a design package is not addressed beneath its project, and an inspection record is not addressed beneath its module. Relationships travel in payloads and in query filters instead, which keeps every resource reachable by exactly one path.

Path identifiers are nevertheless resolved strictly left to right, and each is resolved before any body field is examined. The templates in play are `{factoryId}`, `{agencyId}`, `{projectId}`, `{packageId}`, `{moduleId}`, `{permitId}`, `{inspectionId}`, `{shipmentId}`, `{claimId}` and `{drawId}`. An unresolvable identifier produces the 404 that names the missing type: `ERR_FACTORY_NOT_FOUND`, `ERR_AGENCY_NOT_FOUND`, `ERR_PROJECT_NOT_FOUND`, `ERR_DESIGN_PACKAGE_NOT_FOUND`, `ERR_MODULE_NOT_FOUND`, `ERR_PERMIT_NOT_FOUND`, `ERR_INSPECTION_NOT_FOUND`, `ERR_SHIPMENT_NOT_FOUND`, `ERR_DEFECT_CLAIM_NOT_FOUND` or `ERR_DRAW_NOT_FOUND`.

Foreign keys arriving in a request body are resolved next, after every path identifier has been confirmed, using the same catalogue of 404 codes. The body-borne references the server resolves are `factory_id`, `project_id`, `design_package_id`, `supersedes_package_id`, `module_id`, `agency_id`, `certifying_agency_id`, `inspection_id` and `pinned_package_id`. A missing `supersedes_package_id` target reports `ERR_DESIGN_PACKAGE_NOT_FOUND`, and a missing `inspection_id` target reports `ERR_INSPECTION_NOT_FOUND`. Existence resolution answers only *does the row exist*; whether the row belongs to the right aggregate is a separate, much later check described in §2.6 and §3.

### 2.6. Rejection Precedence

Any single request may violate several rules at once. The server evaluates candidate rejections in a strict ascending rank order and returns the **first** violated rule; no later rule may pre-empt an earlier one. The ladder runs authentication, then role authorisation, then payload well-formedness, then existence, then ownership and segregation of duties, then optimistic concurrency, then link uniqueness, then state preconditions, then safety and regulatory gates, then constraint satisfaction, then temporal windows, then referential and compliance rules, and finally fiscal ceilings. Ranks are given below so that any two rules can be compared without ambiguity.

Ranks 1 through 10 form the preamble applied before any domain logic:

1. `ERR_UNAUTHENTICATED` — the `X-User-Role` and `X-User-ID` headers are present and `X-User-Role` is one of the ten declared roles. Applies to every endpoint.
2. `ERR_ROLE_NOT_PERMITTED` — the caller's `X-User-Role` appears in the endpoint's authorised role list. Applies to every endpoint.
3. `ERR_INVALID_REQUEST` — the body parses, every required input field is present, every enum-valued field carries a declared member, integer fields hold integers, percentage fields lie between 0 and 100 inclusive, and every numeric constraint stated in this document holds. Applies to every endpoint.
4. Existence of every path-template identifier, resolved left to right, reporting the matching `*_NOT_FOUND` code from §2.5. Applies to every endpoint carrying a path identifier.
5. Existence of every foreign key in the request body, reporting the matching `*_NOT_FOUND` code. Applies to the creation of projects, design packages, modules, permits, inspections, shipments, defect claims and draw requests, and to loading a module onto a shipment.
6. `ERR_ACTOR_NOT_OWNER` — the entity-backed ownership comparison of §2.1. Applies to module creation, line-slot scheduling, line-slot release, station advance, pick scheduling, set execution, connection closeout, weather observation recording, inspection creation, result recording and hold clearance.
7. `ERR_PERMIT_TRACK_ROLE_MISMATCH` — the deciding role matches the permit's `track`. Applies to permit decisions.
8. `ERR_SAME_ACTOR_REVIEW` — segregation of duties on design review. Applies to design review decisions.
9. `ERR_STALE_PROJECT_VERSION` — the optimistic-concurrency check on design package creation.
10. `ERR_STALE_SHIPMENT_VERSION` — the optimistic-concurrency check on module loading.

Rank 38 sits alone and deliberately ahead of every state precondition: `ERR_MODULE_ALREADY_LOADED` fires when the module named for loading already has a `shipment_id`. A module already aboard a load also fails the generic loadability check at rank 49, and the specific double-booking answer must win over the generic state answer.

Ranks 39 through 59 are the state preconditions, in this order: `ERR_DESIGN_REVIEW_IN_FLIGHT` (39), `ERR_DESIGN_NOT_SUBMITTABLE` (40), `ERR_DESIGN_NOT_IN_REVIEW` (41), `ERR_DRAW_NOT_DRAFT` (42), `ERR_DRAW_NOT_CERTIFIED` (43), `ERR_MODULE_NOT_PLANNED` (44), `ERR_MODULE_NOT_SLOTTED` (45), `ERR_MODULE_NOT_ON_LINE` (46), `ERR_MODULE_NOT_READY_TO_SET` (47), `ERR_MODULE_NOT_SET` (48), `ERR_SHIPMENT_NOT_LOADABLE` (49), `ERR_SURVEY_NOT_PENDING` (50), `ERR_SHIPMENT_NOT_PERMITTED` (51), `ERR_SHIPMENT_NOT_DISPATCHED` (52), `ERR_SHIPMENT_TERMINAL` (53), `ERR_PERMIT_ALREADY_DECIDED` (54), `ERR_INSPECTION_NOT_PENDING` (55), `ERR_HOLD_NOT_ACTIVE` (56), `ERR_CLAIM_NOT_ADJUDICABLE` (57), `ERR_CLAIM_NOT_ADJUDICATED` (58) and `ERR_DISPUTE_ROUND_LIMIT` (59).

Ranks 60 through 66 are the safety and regulatory gates, in this order: `ERR_FACTORY_LINE_NOT_RUNNING` (60), `ERR_PICK_RADIUS_OFF_CHART` (61), `ERR_CRANE_CAPACITY_EXCEEDED` (62), `ERR_WEATHER_EXPOSURE_LIMIT` (63), `ERR_SET_NOT_PERMITTED` (64), `ERR_QC_HOLD_BLOCKS_OPERATION` (65) and `ERR_QC_NOT_RELEASED` (66).

Ranks 67 through 75 are the constraint-satisfaction rules, in this order: `ERR_SET_SEQUENCE_VIOLATION` (67), `ERR_LINE_CAPACITY_EXCEEDED` (68), `ERR_CRANE_WINDOW_CONFLICT` (69), `ERR_ENVELOPE_EXCEEDS_ROUTE_LIMIT` (71), `ERR_QC_STAGE_OUT_OF_ORDER` (72), `ERR_DUPLICATE_CODE` (73), `ERR_DUPLICATE_MODULE_CODE` (74) and `ERR_ESCORT_NOT_CONFIRMED` (75).

Ranks 76 through 80 are the temporal rules, in this order: `ERR_LINE_SLOT_IN_PAST` (76), `ERR_LINE_SLOT_OUTSIDE_SHIFT` (77), `ERR_PICK_WINDOW_INVALID` (78), `ERR_TRANSPORT_PERMIT_EXPIRED` (79) and `ERR_CLOCK_NOT_MONOTONIC` (80).

Ranks 81 through 89 are the referential and compliance rules, in this order: `ERR_AGENCY_NOT_ACCREDITED` (81), `ERR_AGENCY_JURISDICTION_MISMATCH` (82), `ERR_PLAN_REVIEW_PREREQUISITE` (83), `ERR_NO_FROZEN_PACKAGE` (84), `ERR_PINNED_PACKAGE_MISMATCH` (85), `ERR_INVALID_SUPERSESSION` (86), `ERR_FACTORY_COMPATIBILITY_TOO_LOW` (87), `ERR_CROSS_AGGREGATE_MISMATCH` (88) and `ERR_SHIPMENT_PROJECT_MISMATCH` (89).

The fiscal rules come last, in this order: `ERR_CONTRACT_BALANCE_EXCEEDED` (90), `ERR_NO_CERTIFIABLE_WIP` (91) and `ERR_DRAW_SEQUENCE_GAP` (92). One constraint rule is ranked among them: `ERR_FIELD_SCOPE_NOT_SIGNED_OFF` sits at rank 93, below every fiscal rule, and is therefore the last check the connection-closeout operation performs.

### 2.7. Optimistic Concurrency on the Parent Version

Two write operations in this system fan out far enough that the writer must prove its view of a parent aggregate is current before the fan-out is allowed to fire. Both use the same mechanism: a non-optional input field carrying the client's last observed `version` of the parent, compared for equality against that parent's stored `version`, with a mismatch rejected before any state precondition is evaluated.

Creating a design package requires `expected_project_version` in the request body, carrying the client's last observed `version` of the `Project` named by `project_id`. If the project's stored `version` has advanced since the client read it — because a permit was decided, a module was set, a draw was certified, or a phase was re-derived — the create is rejected with `ERR_STALE_PROJECT_VERSION` (HTTP 412). The justification is concrete: a new revision legitimately supersedes a frozen predecessor and re-pins every approval that referenced it, so the writer must demonstrate that its picture of the project's permit posture, phase and certified WIP ledger is the current one before the supersession chain is permitted to run.

Loading a module onto a shipment requires `expected_shipment_version` in the request body, carrying the client's last observed `version` of the `Shipment` named in the path. A mismatch against the shipment's stored `version` is rejected with `ERR_STALE_SHIPMENT_VERSION` (HTTP 412). Every load recomputes the load's envelope class, escort obligation and permit fee, so a writer holding a stale view of the shipment would be deciding transport permitting against an obsolete envelope.

No other endpoint in this system accepts a version field, and none may be made to require one. Every other write is last-writer-wins on its own row.

### 2.8. Money, Percentages, Rounding and Conserved Ledgers

All monetary amounts in this system are integers denominated in cents, and every field name that ends in `_cents` holds such an integer. Wherever a monetary result is derived by multiplication or division, the result is rounded **half up** to a whole cent. Wherever a percentage or an hour count is derived, the result is rounded **half up** to exactly two decimal places: this applies to `factory_share_pct`, `field_share_pct`, `crane_utilization_pct` and `exposure_open_hours`. The compatibility score on a design package is the one derived number that is a clamped integer rather than a two-decimal value.

Rounding position is normative wherever a calculation rounds more than once. The draw computation in §3.9 rounds three times in a fixed order — once per module, once when the deposit rate is applied to the summed basis, once when retainage is applied to the certified amount — and collapsing any two of those roundings into one changes the answer. Two derived amounts are deliberately *not* re-rounded but pinned as exact complements: `field_share_pct` is one hundred minus `factory_share_pct`, and `field_charge_cents` is `repair_cost_cents` minus `factory_charge_cents`, which makes the field charge absorb whatever remainder the factory rounding produced and guarantees that the two charges sum exactly to the repair cost.

Three quantities in this system are **conserved ledgers**, meaning every operation that moves them has a named compensating operation that returns them exactly to their prior value, with no drift. The plant's `committed_line_minutes` is the sum of the occupancy length of every module of that plant currently holding a line slot; releasing a slot subtracts back exactly what scheduling it added, and a module completing the line releases its minutes as well. A shipment's `loaded_module_count` together with the set of modules whose `shipment_id` points at that shipment is a single referential quantity: unloading always decrements the count by exactly one per module removed. And a project's `wip_certified_cents` is the sum of `certified_cents` over that project's draws in status `CERTIFIED` or `FUNDED`; rejecting a certified draw subtracts back exactly the amount certifying it added. Alongside it, `funded_to_date_cents` accumulates `net_funded_cents` over the project's draws in status `FUNDED`.

### 2.9. Parallel State Dimensions and Derived Roll-Ups

Most entities in this system carry one lifecycle state. A `ModuleUnit` carries three, on one row, advancing independently: `production_status` tracks the factory line, `qc_status` tracks third-party quality, and `site_status` tracks logistics and the site. The dimensions are independent in the sense that each has its own transitions, but they are not isolated — most transitions in one dimension are guarded by the current value of another, and §3 states each guard where the operation lives.

Alongside those, several fields are **pure derivations**: they are recomputed by a full re-scan of the underlying children on every trigger, never incremented in place. A project's `phase` and `permit_posture` are both derivations, as is a shipment's `max_envelope_class`, a module's `envelope_class` and `exposure_open_hours`, and a design package's `factory_compatibility_score`. Because they are re-scans, they walk backwards whenever the children regress: cancelling the last dispatched load of a project moves `phase` back down the ladder, and a permit expiring at the clock moves `permit_posture` back toward blocked. Implementations that treat these fields as forward-only counters will diverge from the specification the first time a compensating action fires.

Two counters on `Project` — `modules_set_count` and `modules_connected_count` — are maintained as counts of the project's modules whose `site_status` is `SET` or `CONNECTED`, and whose `site_status` is `CONNECTED`, respectively. Two counters on `ModuleUnit` — `defect_count_factory` and `defect_count_field` — are counts of that module's defect claims by discovery phase: the factory counter covers claims whose `discovered_phase` is `FACTORY` or `TRANSIT`, and the field counter covers claims whose `discovered_phase` is `SITE_SET` or `POST_SET`.

### 2.10. The Logical Clock and Temporal Windows

The server owns a single logical clock and never consults wall-clock time. Before the clock has been set even once, it reads exactly `2026-08-01T00:00:00Z`; that startup default is mandatory and the server never falls back to real time. An administrative capability sets the clock to a supplied `current_utc` instant. The clock never moves backwards: a `current_utc` that is less than the clock's present value is rejected with `ERR_CLOCK_NOT_MONOTONIC` (HTTP 422), while a value equal to the present value is accepted.

Advancing the clock is a state-changing event with fan-out. Every permit record in status `APPROVED` whose `expires_at` is not null and is less than or equal to the new instant transitions to `EXPIRED`, and every affected project's `permit_posture` is re-derived. Every module whose `site_status` is `SET` and whose `connected_at` is still null has its `exposure_open_hours` recomputed against the new instant. Each permit record and project touched by the sweep takes a `version` increment.

Two interval conventions are used throughout and must not be interchanged. A module's factory line occupancy is **half-open**: the interval runs from `line_slot_start` inclusive to `line_slot_end` exclusive, so a slot beginning exactly at another slot's `line_slot_end` sees that other slot as already finished. A module's crane pick window is **closed**: the interval runs from `pick_window_start` to `pick_window_end` inclusive, and touching endpoints count as overlap.

## 3. Business Logic & Workflows

### 3.1. Standing Up the Plant, the Agency Panel and the Project

Nothing in this system can be built until the program office has described the physical plant. A `ProgramAdmin` registers a volumetric modular plant by supplying its display `name` and a short plant `code` that must be globally unique across all plants; a repeated code is rejected with `ERR_DUPLICATE_CODE`. The plant's production geometry follows: `takt_minutes` is the base number of minutes a module occupies a single line station and must be at least 1; `station_count` is how many sequential stations the line has and must be at least 1; and `parallel_station_capacity` is how many modules may occupy the line concurrently, again at least 1. Financial and scheduling posture completes the record. `wip_unit_value_cents` is the value of one module at full factory completion, expressed in cents and permitted to be zero or more. `shift_start_minute_of_day` is the first minute of the production shift counted in UTC minutes past midnight, accepts any value from 0 through 1439, and defaults to 360 — six o'clock in the morning. `shift_minutes_per_day` is how many productive minutes the shift makes available, accepts 1 through 1440, and defaults to 1080, which is an eighteen-hour working day. `line_state` describes the line's posture, is one of `RUNNING`, `PAUSED` or `SHUTDOWN`, and defaults to `RUNNING`. A newly registered plant begins with `committed_line_minutes` at 0 and `version` at 1. Plants may be listed with the filters `code` and `line_state`.

The plant's posture can be changed afterwards by either a `ProgramAdmin` or the plant's own `FactoryProductionManager`, who supply a replacement `line_state`. The change increments the plant's `version`. Its consequence is felt in §3.4: while `line_state` is `PAUSED` or `SHUTDOWN`, neither takt scheduling nor station advance is permitted, and both are rejected with `ERR_FACTORY_LINE_NOT_RUNNING`.

Third-party inspection agencies form a separate panel, also registered by a `ProgramAdmin`. Each agency has a `name`, an `agency_code` that must be globally unique among agencies — a repeat again yielding `ERR_DUPLICATE_CODE` — and a non-empty `accredited_state_codes` array of two-character uppercase state codes naming the jurisdictions it may work in. `per_inspection_fee_cents` records the agency's fee per recorded inspection in cents and may be zero or more. `accreditation_state` is one of `ACCREDITED`, `PROBATION` or `SUSPENDED` and defaults to `ACCREDITED`. `hold_authority` is a boolean, defaulting to true, that decides whether the agency may place an agency hold on a module. Agencies may be listed filtered by `agency_code` or `accreditation_state`, and their posture may later be revised by either a `ProgramAdmin` or a `StateProgramOfficer` supplying a new `accreditation_state` and optionally a replacement `accredited_state_codes` list; that revision increments the agency's `version`. The consequences are strict: a `SUSPENDED` agency can neither record inspections nor certify draws, and an agency merely on `PROBATION` may still record inspections but may not certify a draw.

Opening a project is where the plant, the two permitting jurisdictions, the crane and the contract all meet. A `ProgramAdmin` supplies the project `name`, the `factory_id` of the plant that will manufacture its modules, the two-character uppercase `state_code` whose modular program will approve the design, the `ahj_code` identifying the local authority having jurisdiction for site permits, the `planned_module_count` the building is split into (at least 1), and the `contract_price_cents` total contract value in cents. Financing rates are optional with defaults: `deposit_pct` is the fraction of factory work-in-progress value financeable as a deposit draw, must be greater than 0 and no more than 1, and defaults to 0.20; `retainage_pct` is the fraction of each certified draw withheld, must be at least 0 and strictly less than 1, and defaults to 0.05.

Crane and site parameters arrive with the project because they are properties of the site, not of any one pick. `crane_capacity_chart` is a required, non-empty ordered array of objects, each carrying an integer `radius_ft` and an integer `capacity_lb`; the `radius_ft` values are strictly ascending across the array and the `capacity_lb` values strictly descending, which is simply the physical fact that a crane lifts less the further out it reaches. `crane_rigging_buffer_minutes` is the rig-up and rig-down buffer applied to *both* ends of every crane pick window and defaults to 45 minutes — three quarters of an hour of exclusivity purchased on each side of every lift. `set_sequence_policy` is either `STRICT_ASCENDING` or `PAIRED_FIRST` and defaults to `STRICT_ASCENDING`. `weather_exposure_limit_hours` is the maximum number of hours a set module may remain open before protection is deemed breached, must be greater than 0, and defaults to 8.0.

Weather is carried on the project as three system-owned fields that a `SiteSuperintendent` — or a `ProgramAdmin` acting for the site — refreshes by recording an observation. The observation supplies `forecast_precip_probability_pct`, the latest precipitation probability from 0 through 100, and `forecast_wind_gust_mph`, the latest wind gust reading; both may also be seeded at project creation and both default to 0. It may optionally supply `observed_at`, and the instant of the most recent observation is retained on the project as `last_weather_observed_at`, which is null until the first observation arrives. Recording an observation increments the project's `version`. A gust of at least 20 miles per hour matters a great deal: from that reading onward, every crane feasibility evaluation in §3.7 works against a derated chart capacity rather than the published one.

A freshly opened project begins with `permit_posture` at `DUAL_BLOCKED`, `phase` at `PRECONSTRUCTION`, all four of `wip_certified_cents`, `funded_to_date_cents`, `modules_set_count` and `modules_connected_count` at 0, and `version` at 1. Reading a single project re-derives `permit_posture` and `phase` before responding, so a read is never stale even if the last mutation that should have moved them was applied elsewhere. Projects may be listed filtered by `factory_id`, `state_code`, `ahj_code`, `phase` or `permit_posture`. A heavier computed read — the set-readiness view, available to `ProgramAdmin`, `SiteSuperintendent` and `AuthorityHavingJurisdiction` — re-derives `permit_posture` and `phase`, refreshes the exposure clock on every module of the project, and refreshes the set counters before returning the project row; it is the view the field uses before deciding whether a lift may proceed.

### 3.2. Design Freeze: the Revision Loop, Compatibility Scoring and Supersession

A `DesignEngineer` opens a design revision against a project by supplying `project_id`, a `revision_index` of at least 1 chosen by the detailing engineer, the `module_split_count` naming how many volumetric modules this revision splits the building into (at least 1), and the `expected_project_version` demanded by §2.7. Three detailing fields are optional. `connection_detail_state` describes how mature the module-to-module connection detailing is and takes one of `NOT_STARTED`, `FACTORY_DETAILED`, `FIELD_COORDINATED` or `COMPLETE`, defaulting to `NOT_STARTED`. `open_connection_conflicts` counts unresolved module-to-module clashes in the revision, defaults to 0 and may not be negative. `field_scope_items_open` counts site-built scope items not yet coordinated with the factory scope, defaults to 0 and may not be negative. A revision may also declare `supersedes_package_id`, the predecessor revision it replaces; the first revision of a project leaves it null. When it is supplied, the predecessor must belong to the same project, must already be in `freeze_state` `FROZEN`, and must have a `revision_index` strictly less than the new package's `revision_index` — any of those three failing produces `ERR_INVALID_SUPERSESSION`. A new package is persisted in `freeze_state` `DRAFT` with `revision_round` at 0, `submitted_by_user_id`, `reviewed_by_user_id` and `review_note` all null, and `version` at 1; creating it also increments the project's `version`. Packages may be listed filtered by `project_id`, `supersedes_package_id`, `freeze_state` or `connection_detail_state`.

**Factory compatibility** is the number that decides whether a revision may be frozen, and it is recomputed from the package's current detailing fields whenever the package is created, submitted, or reviewed. The computation accumulates a penalty from four sources. Each unresolved module-to-module connection clash counted in `open_connection_conflicts` contributes 8 penalty points. Each uncoordinated site-built scope item counted in `field_scope_items_open` contributes 5 penalty points. The maturity of connection detailing contributes a fixed penalty by state: 40 points while `connection_detail_state` is `NOT_STARTED`, 15 points at `FACTORY_DETAILED`, 5 points at `FIELD_COORDINATED`, and nothing at `COMPLETE`. Finally, any disagreement between the revision's `module_split_count` and the project's `planned_module_count` contributes 10 penalty points for each module of difference, measured as the absolute size of the gap regardless of which number is larger. The `factory_compatibility_score` is then 100 minus the accumulated penalty, floored at 0 so it never goes negative, and it is stored as an integer in the range 0 through 100.

Submitting a revision for freeze review moves `freeze_state` from `DRAFT` to `IN_REVIEW`, and it is the same operation that closes the revision loop from `REVISION_REQUIRED` back to `IN_REVIEW`. The submitter may optionally restate `module_split_count`, `open_connection_conflicts`, `field_scope_items_open` and `connection_detail_state` in the payload, and may attach a `review_note`. Two preconditions guard the submit. The package must be in `freeze_state` `DRAFT` or `REVISION_REQUIRED`; a submit against any other state is rejected with `ERR_DESIGN_NOT_SUBMITTABLE`. And no *other* design package of the same project may already be in `freeze_state` `IN_REVIEW`, because a project may have at most one review in flight; a second concurrent review is rejected with `ERR_DESIGN_REVIEW_IN_FLIGHT`. Of the two, the in-flight check is evaluated first, so a package that is itself unsubmittable *and* whose sibling is under review reports the in-flight conflict. On success the package's `factory_compatibility_score` is recomputed, `revision_round` increases by 1 — which is what makes the two visits to `IN_REVIEW` in a revision cycle distinguishable, since the counter is 0 while a package has never been submitted — `submitted_by_user_id` is set to the submitting engineer's `X-User-ID`, and the package's `version` increments.

Review is where segregation of duties bites. A different `DesignEngineer` supplies a `decision` of either `FREEZE` or `RETURN_FOR_REVISION`, optionally with a `review_note`, and the package must be in `freeze_state` `IN_REVIEW` — otherwise `ERR_DESIGN_NOT_IN_REVIEW`. The reviewing `X-User-ID` must differ from `submitted_by_user_id`, or the attempt is `ERR_SAME_ACTOR_REVIEW`. The two decisions are genuinely divergent branches and each must be implemented in full.

`RETURN_FOR_REVISION` moves `freeze_state` from `IN_REVIEW` to `REVISION_REQUIRED`. It records `reviewed_by_user_id` as the reviewing engineer's `X-User-ID` and stores the supplied `review_note`. It then clears `submitted_by_user_id` back to null, so that the next submit records a fresh submitter and the segregation check is evaluated against that fresh identity rather than the stale one. It increments the package's `version`. Deliberately, this arm changes nothing else: the project's `phase` is untouched and no supersession fires.

`FREEZE` moves `freeze_state` from `IN_REVIEW` to `FROZEN` and carries three additional preconditions beyond the state and segregation checks. The `factory_compatibility_score` must be at least 70 — a score of exactly 70 is freezable. The `connection_detail_state` must be anything other than `NOT_STARTED`. And the revision's `module_split_count` must equal the project's `planned_module_count` exactly. Any of those three failing yields `ERR_FACTORY_COMPATIBILITY_TOO_LOW`. On success, `reviewed_by_user_id` and `review_note` are recorded, the project's `phase` is re-derived — which lifts a project sitting at `PRECONSTRUCTION` to `DESIGN_FROZEN` when no module has yet reached the line — and both the package's `version` and the project's `version` increment.

A freeze that supersedes a predecessor fires a five-link cascade, and every link must land. First, the predecessor design package named by `supersedes_package_id` transitions from `FROZEN` to `SUPERSEDED` and takes a `version` increment. Second, because that predecessor left `FROZEN`, every permit record whose `pinned_package_id` points at it and whose `status` is `APPROVED` transitions from `APPROVED` to `CONDITIONS_ISSUED`, has its `conditions_count` increased by 1 and its `decided_at` stamped with the current clock instant, and takes a `version` increment. Third, because a state plan-review approval has left `APPROVED`, the project's `permit_posture` is re-derived. Fourth, every module of the project whose `production_status` is `SLOTTED` reverts from `SLOTTED` back to `PLANNED`, clearing its `line_slot_start` and `line_slot_end` and setting its `line_slot_minutes` to 0. Fifth, the minutes those reverted modules were holding are subtracted from the plant's `committed_line_minutes`, with the plant taking a `version` increment. Every module reverted, the affected plant, the affected permit records and the project all take `version` increments; the project's `phase` is re-derived as part of the same operation. A superseded package is terminal — it has no onward transition — and note that for the purpose of deriving a project's `phase`, a package in `SUPERSEDED` still counts as having been frozen.

### 3.3. The Bifurcated Permit Ladder and the Project's Permit Posture

Modular buildings are permitted twice over, by two authorities that do not coordinate with each other. The state modular program approves the *design* and releases insignia labels for the factory to apply; the local authority having jurisdiction permits the *site* — the foundation, the set operation and finally occupancy. This system models the bifurcation on a single application record whose `track` field is the discriminator, taking either `STATE_MODULAR_PROGRAM` or `LOCAL_AHJ`.

A `ProgramAdmin` files an application by supplying `project_id`, the `track`, and the `scope` of what the application covers, optionally with an `expires_at` instant. Scope is bound to track: `PLAN_REVIEW` and `INSIGNIA` are valid only on the `STATE_MODULAR_PROGRAM` track, while `FOUNDATION`, `SET` and `OCCUPANCY` are valid only on the `LOCAL_AHJ` track. A filed application starts in `status` `SUBMITTED` with `conditions_count` at 0, `insignia_count_issued` at 0, `pinned_package_id` null, `decided_at` and `decided_by_user_id` null, and `version` at 1. An `expires_at` of null means the approval, once granted, never expires. Applications may be listed filtered by `project_id`, `pinned_package_id`, `track`, `scope` or `status` — that listing is the bifurcation view the program office watches.

Decisions are recorded by the officer of the matching track, supplying a `decision` and optionally `conditions_count` and `expires_at`. The `decision` is one of `START_REVIEW`, `ISSUE_CONDITIONS`, `APPROVE` or `DENY`, and each demands a compatible current `status`; an incompatible pairing, or any decision at all against a record already in `DENIED` or `EXPIRED`, is rejected with `ERR_PERMIT_ALREADY_DECIDED`. Specifically, `START_REVIEW` requires `SUBMITTED`; `ISSUE_CONDITIONS` requires `SUBMITTED` or `UNDER_REVIEW`; and `APPROVE` and `DENY` each accept `SUBMITTED`, `UNDER_REVIEW` or `CONDITIONS_ISSUED`. Every accepted decision stamps `decided_at` with the current clock instant and `decided_by_user_id` with the deciding officer's `X-User-ID`, and increments the record's `version`.

`START_REVIEW` moves `status` from `SUBMITTED` to `UNDER_REVIEW` and does nothing further beyond the decision stamps and the version increment.

`ISSUE_CONDITIONS` moves `status` to `CONDITIONS_ISSUED` from either `SUBMITTED` or `UNDER_REVIEW`. It increases `conditions_count` by the greater of 1 and the `conditions_count` supplied in the payload, so an officer who omits the field or supplies zero still records one condition set. It then re-derives the project's `permit_posture` and increments the project's `version` alongside the record's. Note the asymmetry that makes this branch distinct from its siblings: issuing conditions leaves any existing `pinned_package_id` exactly where it is.

`DENY` moves `status` to `DENIED`, which is terminal. Beyond the decision stamps it clears `pinned_package_id` back to null, re-derives the project's `permit_posture`, and increments the project's `version`. The contrast with the approval branch is deliberate: approval *sets* the pin, denial *clears* it, and issuing conditions *leaves it alone*.

`APPROVE` moves `status` to `APPROVED` and is the branch with the most machinery. When the payload supplies `expires_at`, that value is persisted as the approval's expiry. Two scope-specific preconditions apply. When the `scope` is `PLAN_REVIEW`, exactly one design package of the project must be in `freeze_state` `FROZEN`; zero frozen packages, or more than one, is rejected with `ERR_NO_FROZEN_PACKAGE`. When the `scope` is `INSIGNIA`, a permit record of the same project on the `STATE_MODULAR_PROGRAM` track with `scope` `PLAN_REVIEW` and `status` `APPROVED` must already exist and its approval must still be live — that is, its `expires_at` is either null or later than the current clock instant; otherwise the approval is rejected with `ERR_PLAN_REVIEW_PREREQUISITE`. On success, an approval whose `scope` is `PLAN_REVIEW` sets `pinned_package_id` to the `id` of the project's single frozen design package. That is **version pinning on approval**: from that moment the state has approved one specific revision, and §3.7 will refuse to set any module that was detailed against a different one. An approval whose `scope` is `INSIGNIA` instead sets `insignia_count_issued` to the project's `planned_module_count`, releasing one insignia label per planned module. Every approval re-derives the project's `permit_posture` and increments the project's `version` alongside the record's.

Two transitions out of `APPROVED` are driven by the system rather than by an officer. The first was described in §3.2: when the design package named by `pinned_package_id` transitions from `FROZEN` to `SUPERSEDED`, the approval falls back from `APPROVED` to `CONDITIONS_ISSUED` with `conditions_count` increased by 1 and `decided_at` restamped, the project's `permit_posture` is re-derived, and — because a live state plan-review approval was the precondition for occupying the line at all — every module of the project in `production_status` `SLOTTED` reverts to `PLANNED` and gives its minutes back to the plant's `committed_line_minutes`. The second is clock-driven: when the logical clock is advanced to an instant at or beyond a non-null `expires_at`, an approval in `APPROVED` transitions to `EXPIRED`, which is terminal, the project's `permit_posture` is re-derived, and both records take `version` increments.

**Permit posture** is the project's single summary of where the bifurcation stands, and every derivation of it is a full re-scan of the project's permit records. A track-and-scope pair counts as *live* when the project has a permit record with that `track` and that `scope` whose `status` is `APPROVED` and whose `expires_at` is either null or strictly later than the current clock instant. Records in `DENIED`, `SUBMITTED`, `UNDER_REVIEW`, `CONDITIONS_ISSUED` or `EXPIRED` contribute nothing at all. From those live pairs the derivation reads five facts — whether state plan review is live, whether state insignia is live, whether the local foundation permit is live, whether the local set permit is live, and whether local occupancy is live — plus one composite: the *site side* counts as cleared when either the local foundation permit or the local set permit is live.

The branches below are evaluated in exactly this order and the first one that matches wins; the ordering is normative, not a presentation choice. If local occupancy, the local set permit, state plan review and state insignia are **all** live, `permit_posture` is `OCCUPANCY_CLEARED`. Otherwise, if the local set permit, state plan review and state insignia are all live, it is `SET_CLEARED`. Otherwise, if state plan review is live and the site side is not cleared, it is `STATE_CLEARED_ONLY`. Otherwise, if the site side is cleared and state plan review is not live, it is `SITE_CLEARED_ONLY`. Otherwise, if state plan review is live and the site side is also cleared, it is again `STATE_CLEARED_ONLY` — this fifth branch is the bifurcation tie-break, and it reports the state track because the state track is the one that releases factory production, even though both tracks are partially cleared. If none of those match, `permit_posture` is `DUAL_BLOCKED`. The posture is re-derived on every permit decision, on any clock advance that expires a permit, on any design supersession that unpins an approval, whenever a module's connections are closed, and whenever the project's `phase` reaches `CLOSEOUT`.

Two downstream gates read the posture directly, and it is worth stating them here even though they are enforced elsewhere. Occupying a takt slot on the production line requires a live state plan-review approval, enforced as `ERR_PLAN_REVIEW_PREREQUISITE`. Setting a module on the foundation requires `permit_posture` to be either `SET_CLEARED` or `OCCUPANCY_CLEARED`, enforced as `ERR_SET_NOT_PERMITTED` — which is to say both tracks must have delivered, the state having approved the design and released insignia and the local authority having permitted the set.

### 3.4. Takt Scheduling, Line Capacity and Station Progress

A `FactoryProductionManager` creates a volumetric module against a frozen-or-otherwise design revision by supplying `project_id`, the `design_package_id` of the revision it is detailed against, a `module_code` shop code that must be unique within the project, and a `set_sequence_index` of at least 1 giving its position in the crane set order, which must also be unique within the project. A repeat of either the code or the sequence position is rejected with `ERR_DUPLICATE_MODULE_CODE`. The shipping envelope is declared with four required integers, each at least 1: `width_in`, `length_in`, `height_in` — the height measured as the module will sit on the carrier — and `gross_weight_lb`. Three fields are optional. `pair_role` describes the module's role in a mated pair sharing a corridor wall and takes `SINGLE`, `PAIR_A` or `PAIR_B`, defaulting to `SINGLE`. `pair_group_code` is the shared code linking a `PAIR_A` to its `PAIR_B` and is null when `pair_role` is `SINGLE`. `connection_scope_owner` names who owns the module-to-module connection scope at this module's interface and takes `FACTORY`, `FIELD` or `SHARED`, defaulting to `FIELD`. The referenced design revision must belong to the project named by `project_id`; a cross-project reference is rejected with `ERR_CROSS_AGGREGATE_MISMATCH`.

The **shipping envelope class** is classified at creation and re-read whenever the module's dimensions or weight are restated, and it is a pure function of the module alone with no aggregation. The tiers are evaluated widest-first, so that a single dimension breaching the overwidth ceiling classifies the whole module as a superload. If `width_in` is greater than 216 inches — eighteen feet — or `height_in` is greater than 174 inches, or `gross_weight_lb` is greater than 120,000 pounds, then `envelope_class` is `SUPERLOAD`. Otherwise, if `width_in` is greater than 192 inches — sixteen feet — or `height_in` is greater than 162 inches, or `gross_weight_lb` is greater than 80,000 pounds, then `envelope_class` is `OVERWIDTH`. Otherwise it is `STANDARD`. Every comparison is strictly greater-than against the ceiling, so a module measuring exactly 192 inches wide, exactly 162 inches high and weighing exactly 80,000 pounds is still `STANDARD`. The `length_in` measurement never affects the class at all; it exists only to feed route-survey judgement downstream.

A newly created module begins with `production_status` `PLANNED`, `qc_status` `PENDING`, `site_status` `AT_FACTORY`, `station_index` at 0, `wip_earned_cents` at 0, `exposure_open_hours` at 0, `shipment_id` null, `line_slot_start`, `line_slot_end`, `pick_window_start`, `pick_window_end`, `pick_radius_ft`, `rigging_weight_lb`, `crane_utilization_pct`, `set_at` and `connected_at` all null, `line_slot_minutes` at 0, `defect_count_factory` and `defect_count_field` at 0, and `version` at 1. Reading one module returns all three status dimensions together with its line slot, its pick window and its work-in-progress value, and refreshes `exposure_open_hours` against the current clock as it does so. Modules may be listed filtered by `project_id`, `design_package_id`, `shipment_id`, `production_status`, `qc_status`, `site_status` or `envelope_class`.

Claiming a takt window moves `production_status` from `PLANNED` to `SLOTTED`, and the only payload field is `line_slot_start`, the instant at which the module wants the line. Six preconditions guard it. The module must be in `production_status` `PLANNED`, or the request is `ERR_MODULE_NOT_PLANNED`. Its `qc_status` must not be `HOLD`, or the request is `ERR_QC_HOLD_BLOCKS_OPERATION`. The plant resolved through the project's `factory_id` must have `line_state` `RUNNING`, or the request is `ERR_FACTORY_LINE_NOT_RUNNING`. The project must have a live state plan-review approval as defined in §3.3, or the request is `ERR_PLAN_REVIEW_PREREQUISITE`. The requested `line_slot_start` must be at or after the current logical clock instant — a start exactly equal to the present instant is acceptable — or the request is `ERR_LINE_SLOT_IN_PAST`. And the aggregate line capacity must not be exceeded, as described next, or the request is `ERR_LINE_CAPACITY_EXCEEDED`. A seventh, temporal constraint applies as well: the minute-of-day of the requested `line_slot_start` must fall inside the plant's shift window, meaning it is at or after `shift_start_minute_of_day` and strictly before `shift_start_minute_of_day` plus `shift_minutes_per_day`; a start outside that window is rejected with `ERR_LINE_SLOT_OUTSIDE_SHIFT`. Per the precedence ladder of §2.6, the capacity check at rank 68 is evaluated before either temporal check, and the past-instant check before the shift-window check.

**Line capacity** is measured as an instantaneous count at the requested start. The server counts every *other* persisted module of the same plant — same plant meaning the module's project carries the same `factory_id` — whose `production_status` is `SLOTTED` or `IN_LINE` and whose own occupancy interval contains the requested start, where containment means the other module's `line_slot_start` is at or before the requested start and its `line_slot_end` is strictly after it. The requesting module itself is never counted. Modules that have reached `LINE_COMPLETE` have left the line and are excluded even though their `line_slot_start` and `line_slot_end` remain on the row as history. That count must be strictly less than the plant's `parallel_station_capacity`.

**The takt actually achieved degrades with congestion**, and the same count feeds the schedule. Let the concurrency count be the number computed above. The effective takt in minutes is the plant's `takt_minutes` plus 5 minutes for each concurrent module — a five-minute congestion penalty per module already on the line at that instant. The module's `line_slot_minutes` is then the plant's `station_count` multiplied by that effective takt, in whole minutes. Its `line_slot_start` is the requested instant and its `line_slot_end` is that instant plus `line_slot_minutes` minutes. Because the interval is half-open, a slot beginning exactly at another slot's `line_slot_end` neither collides with it nor counts it as concurrent. On success the plant's `committed_line_minutes` increases by the module's `line_slot_minutes` and the plant's `version` increments; the module's `wip_earned_cents` is recomputed under the station-progress rule, which at `station_index` 0 yields 0; and the module's `version` increments.

Releasing a takt window is the compensating action, available with an optional `reason` and also fired by the system as part of the design-supersession cascade. It requires `production_status` `SLOTTED`, or the request is `ERR_MODULE_NOT_SLOTTED`. It moves `production_status` from `SLOTTED` back to `PLANNED`, subtracts exactly the module's `line_slot_minutes` from the plant's `committed_line_minutes` so the ledger returns to its pre-schedule value, increments the plant's `version`, clears `line_slot_start` and `line_slot_end` and sets `line_slot_minutes` to 0, re-derives the project's `phase`, and increments the module's and the project's `version`.

Advancing the module along the line takes an optional `stations_advanced` count that defaults to 1, and it drives three different transitions depending on where the count lands. In all three cases the module must be in `production_status` `SLOTTED` or `IN_LINE` — otherwise `ERR_MODULE_NOT_ON_LINE` — its `qc_status` must not be `HOLD` — otherwise `ERR_QC_HOLD_BLOCKS_OPERATION` — and the plant's `line_state` must be `RUNNING` — otherwise `ERR_FACTORY_LINE_NOT_RUNNING`. The first advance from `SLOTTED` moves `production_status` to `IN_LINE`, increases `station_index` by `stations_advanced` capped at the plant's `station_count`, recomputes `wip_earned_cents`, re-derives the project's `phase` from `DESIGN_FROZEN` up to `IN_PRODUCTION`, and increments both the module's and the project's `version`. An intermediate advance, where `station_index` plus `stations_advanced` remains strictly less than the plant's `station_count`, keeps `production_status` at `IN_LINE`, increases `station_index` by `stations_advanced`, recomputes `wip_earned_cents`, recomputes the `basis_earned_cents` and `requested_cents` of every draw request of the project still in status `DRAFT`, and increments the module's `version`. A terminating advance, where `station_index` plus `stations_advanced` reaches or exceeds the plant's `station_count`, moves `production_status` to `LINE_COMPLETE`, sets `station_index` exactly to the plant's `station_count`, subtracts the module's `line_slot_minutes` from the plant's `committed_line_minutes` and increments the plant's `version` — the line is released, and the interval stays on the module as history while no longer occupying capacity — recomputes `wip_earned_cents`, which under the station-progress rule now yields the plant's full `wip_unit_value_cents`, recomputes the `basis_earned_cents` and `requested_cents` of the project's `DRAFT` draw requests, and increments the module's `version`. `LINE_COMPLETE` is terminal on the production dimension.

**Station-progress earned value** is the number persisted in a module's `wip_earned_cents`, and it is recomputed on takt scheduling, on every station advance, on shipment delivery, on set execution, on connection closeout, and whenever a draw basis is computed. When the module's `production_status` is `SLOTTED`, `IN_LINE` or `LINE_COMPLETE` *and* its `qc_status` is not `HOLD`, the earned value is the plant's `wip_unit_value_cents` multiplied by the module's `station_index`, divided by the plant's `station_count`, and rounded half up to a whole cent. In every other case — a module still `PLANNED`, or any module under an agency hold — the earned value is 0. A module under hold earns nothing even though its `station_index` is non-zero, and that is the intended consequence of a hold: the lender's basis shrinks the moment quality stops. This station-progress figure is the only variant ever written to the module row; the alternative delivery-milestone valuation described in §3.9 is materialised inside the draw computation and never persisted on the module.

### 3.5. Third-Party Quality Inspection, Agency Holds and Release

Quality on a modular line is certified by an independent agency, not by the plant, and the quality dimension of a module advances only when that agency acts. A `ThirdPartyInspector` opens an inspection by supplying the `module_id` under inspection, the `agency_id` of the agency performing it — which must equal the caller's own `X-User-ID` — and the `stage`, which is either `IN_PLANT` or `FINAL_FACTORY`. The two stages are ordered: `IN_PLANT` is stage one and `FINAL_FACTORY` is stage two.

Four gates guard opening a record. The agency's `accreditation_state` must be `ACCREDITED` or `PROBATION`; a `SUSPENDED` agency cannot record inspections at all and is rejected with `ERR_AGENCY_NOT_ACCREDITED`. The agency's `accredited_state_codes` array must contain the project's `state_code`, or the attempt is `ERR_AGENCY_JURISDICTION_MISMATCH`. Inspection staging must be respected: a `FINAL_FACTORY` record may be opened only when an `IN_PLANT` record of the same module already carries a `result` of `PASS` or `CONDITIONAL`, and no other record of the same module may still be sitting at `result` `PENDING`; either failure is `ERR_QC_STAGE_OUT_OF_ORDER`. And the module must have reached the line: the first record opened against a module moves its `qc_status` from `PENDING` to `IN_PROGRESS`, and that transition requires the module's `production_status` to be `IN_LINE` or `LINE_COMPLETE`. A new record is persisted with `result` `PENDING`, `hold_state` `NONE`, `defect_count` 0, `severity_max` 0, `corrective_note`, `recorded_at` and `recorded_by_user_id` all null, and `version` 1; the module's `version` increments when the first record flips its quality dimension. The agency's `per_inspection_fee_cents` is the fee it charges per recorded inspection. Records may be listed filtered by `module_id`, `agency_id`, `stage`, `result` or `hold_state`.

Recording an outcome supplies a `result` of `PASS`, `CONDITIONAL` or `FAIL`, and optionally `defect_count` — the number of nonconformances observed, defaulting to 0 and never negative — `severity_max`, the worst nonconformance severity from 0 through 5, defaulting to 0, and a `corrective_note` narrative. The record itself must still be at `result` `PENDING` and its module's `qc_status` must be either `IN_PROGRESS` or `CONDITIONAL_RELEASE`; otherwise the attempt is `ERR_INSPECTION_NOT_PENDING`. Recording stamps `recorded_at` with the current clock instant and `recorded_by_user_id` with the inspector's `X-User-ID`, and increments the record's `version`.

Four quality transitions follow from the recorded result, and each carries its own preconditions and its own consequences. A `PASS` recorded on a `FINAL_FACTORY` record moves the module's `qc_status` from `IN_PROGRESS` to `RELEASED`, and requires that the module's `IN_PLANT` record carry a `result` of `PASS` or `CONDITIONAL`; the module's `version` increments. A `CONDITIONAL` recorded on a `FINAL_FACTORY` record moves `qc_status` from `IN_PROGRESS` to `CONDITIONAL_RELEASE` under exactly the same `IN_PLANT` precondition, and likewise increments the module's `version`. `CONDITIONAL_RELEASE` is a genuinely distinct state, not a softer `RELEASED`: it is loadable for transport, but it is also the only state from which a second `FINAL_FACTORY` record may be opened, which makes a conditionally released module re-inspectable. A `FAIL` moves `qc_status` to `HOLD` — from `IN_PROGRESS` on a first pass, or from `CONDITIONAL_RELEASE` on a re-opened `FINAL_FACTORY` record — and requires the recording agency's `hold_authority` to be true. Both hold arms set the record's `hold_state` to `AGENCY_HOLD` and increment the module's `version`. `RELEASED` is terminal on the quality dimension.

Whenever a module's `qc_status` becomes `HOLD`, a three-link cascade fires. First, if the module currently carries a `shipment_id` and that shipment's `status` is `DRAFT`, `SURVEY_REQUIRED` or `PERMITTED`, the module is unloaded: its `shipment_id` is cleared to null, its `site_status` moves from `LOADED` back to `AT_FACTORY`, the shipment's `loaded_module_count` decreases by 1, and the shipment's `status` is set back to `DRAFT`. In practice this link only has work to do when the hold arrives from `CONDITIONAL_RELEASE`, because a module in `IN_PROGRESS` was never loadable in the first place. Second, because the load changed, the shipment's `max_envelope_class` is recomputed over the modules still aboard and its `route_survey_state`, `escort_required`, `permit_expires_at` and `permit_fee_cents` are all reset accordingly by the rules in §3.6. Third, the `basis_earned_cents` and `requested_cents` of every draw request of the project still in status `DRAFT` are recomputed, because a held module leaves the work-in-progress basis entirely. The module's `version` increments, and the shipment's `version` increments when an unload actually occurred.

Clearing a hold is how the quality cycle closes. The inspector supplies a required `corrective_note`, and three preconditions apply: the module's `qc_status` must be `HOLD` and the record's `hold_state` must be `AGENCY_HOLD` — otherwise the attempt is `ERR_HOLD_NOT_ACTIVE` — and the clearing agency's `accreditation_state` must be `ACCREDITED` or `PROBATION`. On success the record's `hold_state` becomes `CLEARED`, its `result` is reset to `PENDING`, its `defect_count` and `severity_max` are both reset to 0, and the supplied `corrective_note` is stored. The module's `qc_status` returns from `HOLD` to `IN_PROGRESS`, closing the cycle from `IN_PROGRESS` through `HOLD` and back to `IN_PROGRESS`. The module's `wip_earned_cents` and the `basis_earned_cents` and `requested_cents` of the project's `DRAFT` draw requests are recomputed — the held module rejoins the basis — and both the record's and the module's `version` increment.

An agency hold is not confined to the quality dimension. Four operations across the factory, transport and site refuse to proceed against a module whose `qc_status` is `HOLD`, and in all four the rejection is `ERR_QC_HOLD_BLOCKS_OPERATION`: claiming a takt window, advancing a station, loading the module onto a shipment, and setting the module on the foundation. Two further operations read the quality dimension without being blocked by a hold as such: loading requires `qc_status` to be `RELEASED` or `CONDITIONAL_RELEASE`, reported as `ERR_QC_NOT_RELEASED` when it is `PENDING` or `IN_PROGRESS`, and closing connections requires `qc_status` not to be `HOLD`.

### 3.6. Loads, Shipping Envelopes, Route Surveys and Transport

A `TransportCoordinator` opens a transport load for a project by supplying `project_id`, the trucking `carrier_code`, a non-empty ordered `route_state_codes` array of two-character uppercase state codes with the origin state first, and the two planning instants `planned_departure_at` and `planned_arrival_at`, where the planned arrival must be strictly after the planned departure. A new load begins with `status` `DRAFT`, `route_survey_state` `NOT_REQUIRED`, `max_envelope_class` `STANDARD`, `loaded_module_count` 0, `permit_fee_cents` 0, `escort_required` false, `escort_confirmed` false, `survey_completed_at`, `permit_expires_at`, `dispatched_at`, `delivered_at` and `cancel_reason` all null, and `version` 1. Loads may be listed filtered by `project_id`, `status`, `route_survey_state`, `carrier_code` or `max_envelope_class`.

A shipment carries two independent state dimensions. `status` is the transport lifecycle, running `DRAFT`, `SURVEY_REQUIRED`, `PERMITTED`, `DISPATCHED` and `DELIVERED`, with `CANCELLED` as the other terminal outcome alongside `DELIVERED`. `route_survey_state` is the survey axis, running `NOT_REQUIRED`, `REQUIRED` and `COMPLETED`. The axes are independent by design: a load can gain and then lose its survey obligation without the transport axis moving forward at all.

Loading a module supplies the `module_id` and the `expected_shipment_version` required by §2.7. Six domain gates apply on top of the concurrency check. The module must not already carry a `shipment_id`; a double booking is rejected with `ERR_MODULE_ALREADY_LOADED`, and that specific answer deliberately outranks the generic loadability answer below. The shipment's `status` must be `DRAFT` or `SURVEY_REQUIRED`, and the module's `site_status` must be `AT_FACTORY` with `production_status` `LINE_COMPLETE`; any of those failing is `ERR_SHIPMENT_NOT_LOADABLE`. The module's `qc_status` must not be `HOLD`, reported as `ERR_QC_HOLD_BLOCKS_OPERATION`, and must be `RELEASED` or `CONDITIONAL_RELEASE`, reported as `ERR_QC_NOT_RELEASED`. The module's `project_id` must equal the shipment's `project_id`, or the attempt is `ERR_SHIPMENT_PROJECT_MISMATCH`. And a load whose recomputed `max_envelope_class` would be `SUPERLOAD` may not traverse more than two states: if the shipment's `route_state_codes` array holds three or more entries, the load is rejected with `ERR_ENVELOPE_EXCEEDS_ROUTE_LIMIT`. On success the module's `site_status` moves from `AT_FACTORY` to `LOADED`, its `shipment_id` is set to the shipment, the shipment's `loaded_module_count` increases by 1, and both rows take `version` increments.

**The load's envelope, fee and escort obligation are recomputed from scratch on every load and on every unload.** The shipment's `max_envelope_class` is the widest `envelope_class` among the modules currently aboard, ordering the classes `STANDARD` below `OVERWIDTH` below `SUPERLOAD`, and it is `STANDARD` whenever the load is empty. The permit fee follows from a class multiplier: the multiplier is 0 for a `STANDARD` load, 2 for an `OVERWIDTH` load and 5 for a `SUPERLOAD`. `permit_fee_cents` is then a base state permit fee of $250.00 — that is 25,000 cents — multiplied by the number of entries in `route_state_codes`, multiplied again by that class multiplier. Because the standard multiplier is zero, a standard load is fee-free no matter how many states the route crosses. `escort_required` becomes true when `max_envelope_class` is `SUPERLOAD`, and also when `max_envelope_class` is `OVERWIDTH` and the route crosses two or more states; otherwise it is false, and whenever it is false the shipment's `escort_confirmed` is forced back to false as well.

The survey axis moves off those same recomputations. When a load in `route_survey_state` `NOT_REQUIRED` acquires a module that raises `max_envelope_class` to `OVERWIDTH` or `SUPERLOAD`, the survey axis moves from `NOT_REQUIRED` to `REQUIRED` and the fee and escort obligation are recomputed; if the transport axis was still at `DRAFT`, it moves in the same operation from `DRAFT` to `SURVEY_REQUIRED`. When the last non-standard module leaves the load — whether through the quality-hold cascade of §3.5 or through cancellation — and the recomputed `max_envelope_class` falls back to `STANDARD`, the survey axis moves from `REQUIRED` back to `NOT_REQUIRED`, `escort_required` is set false, and `permit_fee_cents` is set to 0 while `permit_expires_at` and `survey_completed_at` are both cleared to null. That backward arm is what makes the survey axis genuinely independent of the transport axis.

Recording the route survey and the transport permit it produced supplies `survey_completed_at`, the instant the survey was completed, `permit_expires_at`, the expiry of the issued transport permit, and optionally `escort_confirmed`, stating whether escort vehicles were confirmed. Three gates apply. The shipment's `status` must be `DRAFT` or `SURVEY_REQUIRED`, its `route_survey_state` must not already be `COMPLETED`, and its `loaded_module_count` must be at least 1; an empty load, an already-completed survey or a dispatched load is rejected with `ERR_SURVEY_NOT_PENDING`. When the shipment's `escort_required` is true, the payload's `escort_confirmed` must be true, or the attempt is `ERR_ESCORT_NOT_CONFIRMED`. And the supplied `permit_expires_at` must be strictly later than the current logical clock instant, or the attempt is `ERR_TRANSPORT_PERMIT_EXPIRED`. On success `route_survey_state` becomes `COMPLETED` — from `REQUIRED` on a load that acquired the obligation, or directly from `NOT_REQUIRED` on a standard load that never needed one — the transport axis moves to `PERMITTED` from either `DRAFT` or `SURVEY_REQUIRED`, `survey_completed_at`, `permit_expires_at` and `escort_confirmed` are persisted from the payload, and the shipment's `version` increments.

Dispatching the load takes an optional `departed_at`. The shipment's `status` must be `PERMITTED` and its `loaded_module_count` at least 1, or the attempt is `ERR_SHIPMENT_NOT_PERMITTED`, and the current clock instant must be strictly before `permit_expires_at`, or the attempt is `ERR_TRANSPORT_PERMIT_EXPIRED`. On success `status` moves from `PERMITTED` to `DISPATCHED`, `dispatched_at` is stamped with the current clock instant, every module aboard moves its `site_status` from `LOADED` to `IN_TRANSIT`, the project's `phase` is re-derived up to `SHIPPING`, and the shipment, every module aboard and the project all take `version` increments.

Delivery — recordable by either the `TransportCoordinator` or the receiving `SiteSuperintendent` — takes an optional `arrived_at` and requires `status` `DISPATCHED`, or the attempt is `ERR_SHIPMENT_NOT_DISPATCHED`. On success `status` moves to `DELIVERED`, which is terminal, `delivered_at` is stamped with the current clock instant, every module carried moves its `site_status` from `IN_TRANSIT` to `DELIVERED`, the `basis_earned_cents` and `requested_cents` of every `DRAFT` draw request of the project are recomputed because delivered modules enter the milestone basis, and the shipment and every module take `version` increments.

Cancellation takes a required `reason` and requires `status` to be `DRAFT`, `SURVEY_REQUIRED` or `PERMITTED`; cancelling a load that has already been dispatched, delivered or cancelled is rejected with `ERR_SHIPMENT_TERMINAL`. On success `status` becomes `CANCELLED`, which is terminal, and the supplied reason is stored as `cancel_reason`. Every module aboard is unloaded — `shipment_id` cleared to null and `site_status` moved from `LOADED` back to `AT_FACTORY` — and the load's aggregate fields are reset wholesale: `loaded_module_count` to 0, `max_envelope_class` to `STANDARD`, `route_survey_state` to `NOT_REQUIRED`, `escort_required` to false, `permit_fee_cents` to 0 and `permit_expires_at` to null. The project's `phase` is re-derived, which is where it may walk backwards from `SHIPPING` to `IN_PRODUCTION`, and the shipment, every module unloaded and the project all take `version` increments.

### 3.7. Crane Pick Planning, Site Set Sequencing and Weather Exposure

Before a module can be landed on the foundation, the `SiteSuperintendent` plans the lift. Planning a pick supplies four required values: `pick_window_start` and `pick_window_end` bounding the closed window during which the crane is committed to this module, `pick_radius_ft` giving the crane working radius selected for the lift in feet, and `rigging_weight_lb` giving the spreader and rigging weight that will hang below the hook in addition to the module itself. A pick may be planned while the module's `site_status` is `AT_FACTORY`, `LOADED`, `IN_TRANSIT` or `DELIVERED` — planning ahead of delivery is normal practice — but not once it is `SET` or `CONNECTED`; an attempt against an already-set module is rejected with `ERR_MODULE_NOT_READY_TO_SET`. The window must be coherent and in the future: `pick_window_end` must be strictly after `pick_window_start`, and `pick_window_start` must be at or after the current logical clock instant, or the request is `ERR_PICK_WINDOW_INVALID`.

**Crane feasibility** is evaluated in three steps against the project's chart. First, the server looks up the chart entry with the *smallest* `radius_ft` that is greater than or equal to the requested `pick_radius_ft`. If the chart holds no such entry — the requested radius reaches further out than the chart covers — the request is rejected with `ERR_PICK_RADIUS_OFF_CHART`. The capacity in play is that entry's `capacity_lb`. Second, a wind derate may apply: when the project's `forecast_wind_gust_mph` is at least 20 miles per hour, the capacity is multiplied by 0.75 and truncated downwards to a whole pound, so the crane is treated as having only three quarters of its published capacity. Third, the rigged weight is the module's `gross_weight_lb` plus its `rigging_weight_lb`. The module's `crane_utilization_pct` is stored as the rigged weight multiplied by 100, divided by the derated capacity, rounded half up to two decimal places — but that stored figure is display only. The feasibility gate is an exact integer comparison that never sees the rounded value: the pick is infeasible when the rigged weight multiplied by 100 is strictly greater than 85 multiplied by the derated capacity. A lift that displays exactly 85.00 percent after rounding can therefore still be infeasible, and an infeasible lift is rejected with `ERR_CRANE_CAPACITY_EXCEEDED`.

**Crane exclusivity** is the last constraint on planning, and it is where the project's `crane_rigging_buffer_minutes` earns its place. The requested window is expanded by that buffer on both ends — subtracted from `pick_window_start` and added to `pick_window_end` — and compared against the identically expanded window of every *other* module of the same project that already has a pick window planned and whose `site_status` is not yet `CONNECTED`. Both intervals are closed, so touching endpoints count as an overlap. Any overlap is rejected with `ERR_CRANE_WINDOW_CONFLICT`. On success the module's `pick_window_start`, `pick_window_end`, `pick_radius_ft` and `rigging_weight_lb` are persisted along with the computed `crane_utilization_pct`, and the module's `version` increments.

Landing the module on the foundation — the operation that moves `site_status` from `DELIVERED` to `SET` — takes only an optional `set_note` in its payload, because every input it needs is already on the module and the project. It is also the most heavily guarded operation in the system. The module's `site_status` must be `DELIVERED`, or the attempt is `ERR_MODULE_NOT_READY_TO_SET`. Its `qc_status` must not be `HOLD`, or the attempt is `ERR_QC_HOLD_BLOCKS_OPERATION`. Its `pick_window_start` must not be null — a lift that was never planned cannot be executed. The project's `permit_posture` must be `SET_CLEARED` or `OCCUPANCY_CLEARED`, or the attempt is `ERR_SET_NOT_PERMITTED`. The module's `design_package_id` must equal the `pinned_package_id` carried by the project's live state plan-review approval, or the attempt is `ERR_PINNED_PACKAGE_MISMATCH` — a module built to a revision the state never approved does not go on the building. Crane feasibility is re-evaluated from scratch against the project's *current* `forecast_wind_gust_mph`, using the module's stored `pick_radius_ft`, so a lift that was feasible when it was planned in still air can fail here with `ERR_PICK_RADIUS_OFF_CHART` or `ERR_CRANE_CAPACITY_EXCEEDED` after a windy forecast arrives. Weather exposure across the whole site is checked: no already-set, not-yet-connected module of the project may have an `exposure_open_hours` greater than the project's `weather_exposure_limit_hours`, because open modules must be closed in before another one is landed; a breach is `ERR_WEATHER_EXPOSURE_LIMIT`. And set order must respect the project's `set_sequence_policy`, or the attempt is `ERR_SET_SEQUENCE_VIOLATION`.

Set order is worth spelling out. Under `STRICT_ASCENDING`, the module's `set_sequence_index` must equal the project's current `modules_set_count` plus 1 — modules go on in exactly the numbered order, with no gaps and no reordering. Under `PAIRED_FIRST`, that same ascending requirement holds *and* an additional rule applies: a module whose `pair_role` is `PAIR_B` may not be set before its `PAIR_A` sibling — the module of the same project sharing its `pair_group_code` — has itself been set. Per the precedence ladder, the sequence check at rank 67 is evaluated after the permitting and weather gates and before the crane-window rule.

A successful set stamps `set_at` with the current clock instant, resets the module's `exposure_open_hours` to 0 because the exposure clock starts now, increases the project's `modules_set_count` by 1, re-derives the project's `phase` up to `SETTING`, and increments both the module's and the project's `version`.

**Weather exposure** is the number of hours a set module has stood open, and it is recomputed on set execution, on connection closeout, on every clock advance, and on any read of the module or of the project's set-readiness view. While the module's `site_status` is `SET` and its `connected_at` is still null, `exposure_open_hours` is the difference between the current logical clock instant and `set_at`, taken in whole minutes, divided by 60, and rounded half up to two decimal places. Once the module's `site_status` is `CONNECTED`, the value freezes as the difference between `connected_at` and `set_at`, again in whole minutes divided by 60 and rounded half up to two decimals. In every other case it is 0.00. Because the elapsed time is measured against the logical clock, exposure only ages when an administrator advances the clock. The project's `weather_exposure_limit_hours` — 8.0 hours by default, which is one working shift of exposure — is compared with a strict greater-than, so a module sitting at exactly 8.00 hours is still compliant.

Closing the connections moves `site_status` from `SET` to `CONNECTED` and requires `field_scope_signed_off` in the payload, optionally alongside a replacement `connection_scope_owner` and a `connected_note`. Five preconditions apply. The module's `site_status` must be `SET`, or the attempt is `ERR_MODULE_NOT_SET`. Its `qc_status` must not be `HOLD`. Every other module of the same `pair_group_code` must already have a `site_status` of `SET` or `CONNECTED` when this module's `pair_role` is anything other than `SINGLE` — a mated pair is connected together or not at all. The weather gate is a disjunction rather than a hard stop: the module's `exposure_open_hours`, recomputed at the current instant, must be less than the project's `weather_exposure_limit_hours`, **or** the project's `forecast_precip_probability_pct` must be below 40, so a module that has stood open too long may still be closed in while the forecast is dry. And `field_scope_signed_off` must be true — the site-built scope adjoining the module must be signed off before its connections are closed — or the attempt is rejected with `ERR_FIELD_SCOPE_NOT_SIGNED_OFF`, which by its rank of 93 is the very last check this operation performs, below even the fiscal rules.

Closing connections stamps `connected_at` with the current clock instant and freezes `exposure_open_hours` at the elapsed span between `set_at` and `connected_at`. It increases the project's `modules_connected_count` by 1 and re-derives both the project's `permit_posture` and its `phase`. It also closes out warranty: every defect claim of this module in status `ADJUDICATED` transitions to `CLOSED`, freezing its allocation permanently so that no further dispute is possible, and each such claim takes a `version` increment. The module's and the project's `version` both increment. `CONNECTED` is terminal on the site dimension.

**Project phase** is derived by a full re-scan of the project's design packages, modules and shipments, never by an increment, and the branches below are evaluated in order with the first match winning. If the project's `planned_module_count` is greater than 0 and its `modules_connected_count` is greater than or equal to that count, `phase` is `CLOSEOUT`; reaching `CLOSEOUT` also re-derives `permit_posture`, since occupancy becomes eligible at that point. Otherwise, if any module of the project has `site_status` `SET` or `CONNECTED`, `phase` is `SETTING`. Otherwise, if any shipment of the project has `status` `DISPATCHED` or `DELIVERED`, `phase` is `SHIPPING`. Otherwise, if any module of the project has `production_status` `IN_LINE` or `LINE_COMPLETE`, `phase` is `IN_PRODUCTION`. Otherwise, if any design package of the project has `freeze_state` `FROZEN` or `SUPERSEDED`, `phase` is `DESIGN_FROZEN`. Otherwise `phase` is `PRECONSTRUCTION`. Because it is a re-scan, the phase walks backwards whenever its children regress: cancelling the project's last dispatched load with no module yet set returns the phase from `SHIPPING` to `IN_PRODUCTION`, and releasing the last takt slot can return it from `IN_PRODUCTION` to `DESIGN_FROZEN`. The derivation runs on design freeze, on takt scheduling and release, on station advance, on shipment dispatch, delivery and cancellation, on set execution and on connection closeout. `CLOSEOUT` is the terminal phase.

### 3.8. Factory Versus Field: Defect Responsibility and Warranty Allocation

Either the plant or the field may raise a defect claim, so both `FactoryProductionManager` and `SiteSuperintendent` can open one. The claim supplies the `module_id` the defect was found on, the `discovered_phase` in which it was discovered — one of `FACTORY`, `TRANSIT`, `SITE_SET` or `POST_SET` — a free-text `description` narrative, and the `repair_cost_cents` total cost to allocate, which may be zero or more. It may optionally reference an `inspection_id`, the inspection record that evidences the defect; that reference, when supplied, must belong to the same module named by `module_id`, or the claim is rejected with `ERR_CROSS_AGGREGATE_MISMATCH`. A new claim is persisted with `status` `OPEN`, `responsibility` `UNDETERMINED`, `adjudication_round` 0, all four of `factory_share_pct`, `field_share_pct`, `factory_charge_cents` and `field_charge_cents` at 0, `warranty_bucket` at its default of `SPLIT`, `adjudicated_by_user_id` and `dispute_note` null, and `version` 1. Claims may be listed filtered by `module_id`, `inspection_id`, `status`, `responsibility`, `discovered_phase` or `warranty_bucket`.

Allocation is the exclusive province of an independent `WarrantyAdjudicator`, who runs it with an optional `adjudication_note`. The claim's `status` must be `OPEN` or `DISPUTED`, or the attempt is `ERR_CLAIM_NOT_ADJUDICABLE`. Which of the two states the claim arrives in decides *which allocation variant runs*, and the two variants can reach materially different answers from identical claim data.

The **first** adjudication runs from `OPEN`, moves `status` to `ADJUDICATED`, sets `adjudication_round` to 1, and allocates by **discovery-phase presumption**. The presumption table is fixed: a defect discovered in the `FACTORY` phase puts `factory_share_pct` at 100.00, one discovered in `TRANSIT` puts it at 50.00, one discovered in `SITE_SET` puts it at 25.00, and one discovered in `POST_SET` puts it at 0.00. This variant reads `discovered_phase` and nothing else — inspection evidence, exposure history and connection scope ownership are all ignored on the first pass.

The **second** adjudication runs from `DISPUTED`, moves `status` back to `ADJUDICATED`, sets `adjudication_round` to 2, and discards the presumption table entirely in favour of an **additive evidence score**. Two running scores start at zero. The factory score gains 6 points when the referenced inspection record's `result` is `FAIL` or `CONDITIONAL`; a further 3 points when that record's `severity_max` is at least 3; and a further 2 points when the module's `defect_count_factory` is strictly greater than its `defect_count_field`. The field score gains 4 points when the claim's `discovered_phase` is `SITE_SET` or `POST_SET`; a further 3 points when the module's `site_status` is `SET` or `CONNECTED` and its `exposure_open_hours` is strictly greater than the project's `weather_exposure_limit_hours`; and a further 2 points when the module's `connection_scope_owner` is `FIELD`. When no evidence lands on either side and both scores are zero, `factory_share_pct` is 50.00. Otherwise `factory_share_pct` is the factory score multiplied by 100, divided by the sum of the two scores, rounded half up to two decimal places. When the claim carries no `inspection_id` at all, the two inspection-driven contributions simply do not apply. Because the evidence route is available, a claim that first landed at a 50/50 split can move to a 100/0 factory allocation on re-adjudication, and the reverse is equally possible.

Both variants then share one identical tail. `field_share_pct` is 100 minus `factory_share_pct`, taken as the exact complement and never re-rounded. `factory_charge_cents` is the claim's `repair_cost_cents` multiplied by `factory_share_pct`, divided by 100, rounded half up to a whole cent. `field_charge_cents` is `repair_cost_cents` minus `factory_charge_cents`, which makes the field charge absorb the rounding remainder so that the two charges always sum exactly to the repair cost. `responsibility` is `FACTORY` when `factory_share_pct` is exactly 100.00, `FIELD` when it is exactly 0.00, and `SHARED` at every value in between. `warranty_bucket` follows directly: `FACTORY_WARRANTY` when responsibility is `FACTORY`, `FIELD_WARRANTY` when it is `FIELD`, and `SPLIT` when it is `SHARED`. Finally, and strictly *after* the allocation has been computed, the module's counters are updated — `defect_count_factory` increases by 1 when responsibility landed on `FACTORY`, and `defect_count_field` increases by 1 when it landed on `FIELD` — so that an adjudication never feeds its own evidence back into itself. The adjudicating `X-User-ID` is recorded as `adjudicated_by_user_id`, and both the claim's and the module's `version` increment.

Disputing an allocation is available to whichever side is unhappy — both `FactoryProductionManager` and `SiteSuperintendent` may raise one — and requires a `dispute_note` narrative. The claim's `status` must be `ADJUDICATED`, or the attempt is `ERR_CLAIM_NOT_ADJUDICATED`, and its `adjudication_round` must be strictly less than 2, or the attempt is `ERR_DISPUTE_ROUND_LIMIT`: a claim already re-adjudicated on evidence is final and may be disputed no further. A successful dispute moves `status` from `ADJUDICATED` to `DISPUTED`, stores the `dispute_note`, and increments the claim's `version`. That closes the adjudication cycle — `ADJUDICATED` to `DISPUTED` and back to `ADJUDICATED` — with the second pass switching the allocation variant. The other way out of `ADJUDICATED` is closure, described in §3.7: when the claim's module has its connections closed, the claim moves from `ADJUDICATED` to `CLOSED`, which is terminal, and its allocation is frozen for good.

### 3.9. Financing: Deposits on Factory Work in Progress and Milestone Draws

A construction lender does not wait for a finished building. It advances money against work it can see — either partially built modules sitting on the plant floor, or finished modules delivered to the site — and it wants an independent agency to certify the number before it releases cash. The `LenderDrawAdministrator` opens a draw by supplying `project_id`, a `draw_index`, a `basis_mode`, and the `certifying_agency_id` of the independent agency that must certify the basis.

`draw_index` is a one-based draw number supplied by the lender and must equal exactly one more than the highest `draw_index` already recorded against the project, so the first draw of a project is 1 and there are never gaps or repeats; anything else is rejected with `ERR_DRAW_SEQUENCE_GAP`. `basis_mode` is either `WIP_DEPOSIT` or `MILESTONE_SET`, and it decides which earned-value variant computes this draw's basis. The certifying agency must be more strictly qualified than an inspecting agency: its `accreditation_state` must be exactly `ACCREDITED`, so an agency on `PROBATION` — acceptable for recording inspections — cannot certify a draw and produces `ERR_AGENCY_NOT_ACCREDITED`. Its `accredited_state_codes` must also contain the project's `state_code`, or the attempt is `ERR_AGENCY_JURISDICTION_MISMATCH`. A new draw is persisted with `status` `DRAFT`, `certified_at`, `funded_at` and `reject_reason` null, and `version` 1. Draws may be listed filtered by `project_id`, `certifying_agency_id`, `status` or `basis_mode`.

**The basis** is the set of modules the draw is drawn against, and which modules qualify depends entirely on `basis_mode`. Under `WIP_DEPOSIT`, the basis is every module of the project whose `production_status` is `SLOTTED`, `IN_LINE` or `LINE_COMPLETE` and whose `qc_status` is not `HOLD`; each such module contributes its station-progress earned value as defined in §3.4 — the plant's `wip_unit_value_cents` pro-rated by completed stations — and a module that has never left the plant contributes normally. Under `MILESTONE_SET`, the basis is every module of the project whose `site_status` is `DELIVERED`, `SET` or `CONNECTED`, and each such module contributes the plant's full `wip_unit_value_cents`, ignoring `station_index` entirely. The two variants diverge sharply: a `LINE_COMPLETE` module still standing at the factory contributes its full unit value under the work-in-progress variant and nothing at all under the milestone variant, while a delivered module contributes the full unit value under both.

**Rounding order in the basis is normative.** The qualifying modules are enumerated in `created_at` ascending order — ordering by `id` is forbidden, because the rounding remainder must be assigned deterministically — and each module's contribution is rounded half up to a whole cent *before* anything is summed. `basis_module_count` is the number of modules in the basis and `basis_earned_cents` is the sum of those already-rounded per-module terms. Rounding each module before summing is observably different from summing exact fractions and rounding once, and this specification requires the former.

At creation the draw's provisional ask is computed from that basis. Under `WIP_DEPOSIT`, `requested_cents` is `basis_earned_cents` multiplied by the project's `deposit_pct` — 20 percent of work in progress by default — rounded half up to a whole cent. Under `MILESTONE_SET`, `requested_cents` is simply `basis_earned_cents`, because milestone draws are funded in full against delivered modules rather than deposited against. Both `basis_earned_cents` and `requested_cents` are refreshed on every event that changes what the basis would contain while the draw is still in `DRAFT`: an intermediate or terminating station advance, a delivery, a quality hold arriving, and a hold being cleared all recompute them.

Certification is the moment the numbers stop being the lender's estimate. It takes an optional `certification_note` and requires the draw's `status` to be `DRAFT`; certifying anything else is `ERR_DRAW_NOT_DRAFT`. The whole basis computation is then **re-run from live module state and never copied** from the provisional figures. `certified_basis_cents` is the result of that re-run — same basis selection, same per-module rounding, same `created_at` ascending enumeration. `certified_cents` is `certified_basis_cents` multiplied by the project's `deposit_pct` and rounded half up to a whole cent under `WIP_DEPOSIT`, and is equal to `certified_basis_cents` under `MILESTONE_SET`. `retainage_held_cents` is `certified_cents` multiplied by the project's `retainage_pct` — 5 percent by default — rounded half up to a whole cent. `net_funded_cents` is `certified_cents` minus `retainage_held_cents`. That is the three-rounding sequence promised in §2.8: once per module, once when the deposit rate meets the summed basis, once when retainage meets the certified amount.

Two fiscal gates then apply, in this order. The **contract ceiling** first: the sum of `certified_cents` across every *other* draw request of the project whose `status` is `CERTIFIED` or `FUNDED`, added to this draw's own `certified_cents`, must not exceed the project's `contract_price_cents` multiplied by one minus the project's `retainage_pct`, that product rounded half up to a whole cent. Exceeding it is `ERR_CONTRACT_BALANCE_EXCEEDED`. The **substance test** second: `certified_basis_cents` must be strictly greater than 0, because a draw with no qualifying module work cannot be certified; a zero basis is `ERR_NO_CERTIFIABLE_WIP`. A successful certification moves `status` from `DRAFT` to `CERTIFIED`, stamps `certified_at` with the current clock instant, adds `certified_cents` to the project's `wip_certified_cents`, and increments both the draw's and the project's `version`.

Funding releases the money. It takes an optional `funded_at` and requires `status` to be exactly `CERTIFIED`, or the attempt is `ERR_DRAW_NOT_CERTIFIED`. It moves `status` to `FUNDED`, stamps `funded_at` with the current clock instant, adds `net_funded_cents` to the project's `funded_to_date_cents`, and increments the draw's and the project's `version`.

Rejection is the compensating action on the money ledger. It takes a required `reject_reason` and accepts a draw in `status` `DRAFT` or `CERTIFIED`; a draw already `FUNDED` or already `REJECTED` cannot be rejected, and the attempt reports `ERR_DRAW_NOT_CERTIFIED` — the same code that guards funding, since both are the draw-lifecycle gate at rank 43. Rejection moves `status` to `REJECTED`, stores the supplied reason, and resets `certified_cents`, `retainage_held_cents` and `net_funded_cents` to 0. When the draw being rejected was in `CERTIFIED`, the project's `wip_certified_cents` is reduced by exactly the amount that certifying it added, so the ledger returns to its prior value with no drift; rejecting a `DRAFT` draw touches no ledger because nothing was ever added. Both the draw's and the project's `version` increment.
