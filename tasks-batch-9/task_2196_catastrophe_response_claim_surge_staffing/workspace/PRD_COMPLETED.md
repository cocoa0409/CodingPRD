# Catastrophe Response & Claim Surge Staffing API — Product Requirements Document

## 1. Introduction

When a hurricane makes landfall or a wildfire jumps a containment line, an insurer's routine claim organisation is overwhelmed within hours. Thousands of first notices of loss arrive against a footprint whose accessibility is unknown, hotel inventory in the staging city evaporates, and the state regulator issues bulletins that change what the carrier is legally allowed to do — sometimes retroactively. The catastrophe team's job is to stand up a temporary parallel operation: declare the event under an industry catastrophe code, surge licensed adjusters into the field with housing behind them, triage claims by severity so the worst losses get money first, book reserves that survive audit, activate a mitigation vendor network, obey every regulatory bulletin binding the jurisdiction, and then wind the whole thing down and hand the surviving files back to routine handling without losing a dollar of the ledger.

This document specifies the API that runs that operation. It is deliberately a system of record rather than a workflow suggestion engine: every dollar movement is an append-only ledger entry, every state change is gated by explicit preconditions, and the event itself carries a computed **posture** that tightens automatically as operational strain accumulates and refuses child operations outright when the event is frozen. Segregation of duties is structural, not advisory — the examiner who issued an advance payment on a claim may not be the examiner who closes it, and the examiner who submits a file-transfer batch may not be the manager who accepts it.

Three properties are load-bearing for correctness and are asserted throughout. First, **conservation**: incurred dollars at the event level and physical hotel rooms at the block level are conserved quantities, and every forward action that moves them has a compensating action that restores them exactly. Second, **determinism**: the server owns a logical clock, all selectors have fully specified ranking and tie-break orders, and all rounding orders are pinned. Third, **ordered rejection**: when a request violates several rules at once, the response carries the error of the lowest-numbered rule in the validation ladder, never an arbitrary one.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to every endpoint must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the role that principal is acting in. If either header is absent or empty, the request fails with `ERR_MISSING_AUTH_HEADERS` (HTTP 401). If `X-User-Role` carries a string that is not one of the six roles defined below, the request fails with `ERR_UNKNOWN_ROLE` (HTTP 401). If the role is recognised but is not among the roles authorised for the target endpoint in §4, the request fails with `ERR_ROLE_NOT_PERMITTED` (HTTP 403).

The six roles are `CatastropheManager`, `DeploymentCoordinator`, `ClaimsExaminer`, `ComplianceOfficer`, `Adjuster`, and `VendorCoordinator`. Their duties are deliberately disjoint. A `CatastropheManager` owns the event lifecycle, loss estimation and reserve governance: creating events, declaring them, activating surge, demobilizing, closing, minting loss-estimate snapshots, and accepting or rejecting file-transfer batches. A `DeploymentCoordinator` owns adjuster supply, housing logistics and inspection scheduling, and may not triage, pay or close claims. A `ClaimsExaminer` owns claim handling end to end: intake, cat-code assignment, triage, manual reserve movements, advance payments, vendor dispatch, closure, and batch assembly and submission. A `ComplianceOfficer` owns regulatory bulletins and emergency licence waivers, and may not declare events, pay claims or schedule work. An `Adjuster` acts only on their own inspection assignments. A `VendorCoordinator` registers and activates vendor firms and acts on its own dispatched jobs.

Identity binding differs by role, and this is what ties `X-User-ID` to resource ownership. When `X-User-Role` is `CatastropheManager`, `DeploymentCoordinator`, `ClaimsExaminer`, or `ComplianceOfficer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; the server records it where a transition demands an audit anchor — as `closing_examiner_user_id` and `advance_issuing_examiner_user_id` on a claim, and as the recorded submitter of a file-transfer batch — but never compares it to any entity's `id`. When `X-User-Role` is `Adjuster`, `X-User-ID` is the `id` of the acting `Adjuster` row; ownership checks on any resource that references an adjuster compare the resource's adjuster reference to `X-User-ID`, so starting, completing or reporting no access on an inspection assignment whose `adjuster_id` differs from `X-User-ID` is rejected with `ERR_NOT_ASSIGNED_ADJUSTER` (HTTP 403). When `X-User-Role` is `VendorCoordinator`, `X-User-ID` is the `id` of the acting `VendorFirm` row; accepting, declining or completing a vendor assignment whose `vendor_firm_id` differs from `X-User-ID` is rejected with `ERR_NOT_ASSIGNED_VENDOR` (HTTP 403).

All six roles may drive the server's logical clock, because the clock is a test-driving capability rather than a business operation.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits; this envelope field alone is read from real wall-clock time rather than from the logical clock of §2.6, which governs business behaviour only.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every list endpoint accepts two optional query parameters. `limit` controls page size: its default is 10, its minimum accepted value is 1, and its maximum accepted value is 100. `offset` controls the starting position: its default is 0 and its minimum accepted value is 0. A `limit` below 1 or above 100, a non-integer or blank value for either, or a negative `offset`, is a schema violation and is rejected with `ERR_VALIDATION` (HTTP 422). The other, resource-specific filter parameters are never schema-validated: their values are compared literally against the stored field, so an unrecognised status or enum value simply matches no rows rather than failing. The one exception is the boolean `stale` filter on loss-estimate snapshots, which accepts `true`, `false`, `1` or `0` and rejects anything else with `ERR_VALIDATION`.

Unless a specific endpoint states otherwise, list results are ordered by `created_at` ascending. Two collections deliberately depart from that default because their business meaning is sequential: the reserve ledger is returned in `sequence_no` ascending order, and loss-estimate snapshots are returned in `computed_at_utc` ascending order. Because `created_at` is stamped from the logical clock, several rows routinely share the same value; every ordering above therefore carries a final, non-observable tie-break on insertion order, so rows created earlier in the same clock instant sort first. The ledger's `sequence_no` is per-event, so an unfiltered ledger listing interleaves events and falls back to that same insertion-order tie-break where sequence numbers collide across events. List responses populate `limit`, `offset`, `total_count` and `has_more` inside `meta`, where `total_count` is the number of rows matching the filters before pagination is applied and `has_more` is true when rows remain beyond the current page.

### 2.4. Flat Collection Topology and Reference Resolution

This API has no nested resource paths and no common URL prefix. Thirteen record types are stored: the `CatastropheEvent`, the `RegulatoryBulletin` that binds it, the `Adjuster` who works it, the `HousingBlock` that beds that adjuster down, the `Deployment` that joins the two, the `Claim` that arrives against the event, the `InspectionAssignment` that scopes the claim's damage, the `ReserveEntry` that records money movements on it, the `AdvancePayment` that pays part of it early, the `VendorFirm` and the `VendorAssignment` that dispatch mitigation work on it, the `LossEstimateSnapshot` that values the whole event, and the `FileTransferBatch` that hands closed files back to routine handling. Every collection — events, bulletins, adjusters, housing blocks, deployments, claims, inspection assignments, advance payments, reserve entries, vendor firms, vendor assignments, loss estimates and file-transfer batches — is a peer sitting at the root of the URL space, and relationships are expressed by identifier fields carried in request bodies and by identifier query parameters on list endpoints rather than by path nesting. A caller who wants every deployment for an event filters the deployment collection by that event; a caller who wants every bulletin binding an event filters the bulletin collection the same way.

Because references travel in bodies rather than paths, existence checking has a fixed order: a path identifier is resolved before a body identifier of the same entity type. If a request names an event both in its path and in its body, the path segment is checked first; likewise a claim named by path is resolved before a claim named by `claim_id` in the body. A reference that does not resolve produces the corresponding not-found error at HTTP 404: `ERR_EVENT_NOT_FOUND`, `ERR_CLAIM_NOT_FOUND`, `ERR_ADJUSTER_NOT_FOUND`, `ERR_HOUSING_BLOCK_NOT_FOUND`, `ERR_DEPLOYMENT_NOT_FOUND`, `ERR_ASSIGNMENT_NOT_FOUND`, `ERR_ADVANCE_NOT_FOUND`, `ERR_VENDOR_FIRM_NOT_FOUND`, `ERR_VENDOR_ASSIGNMENT_NOT_FOUND`, `ERR_BULLETIN_NOT_FOUND`, and `ERR_BATCH_NOT_FOUND`. Optional identifier fields are only existence-checked when they are supplied and non-null — a deployment request that omits the adjuster reference entirely is asking the server to select one, and must not fail with an adjuster-not-found error. Two read endpoints address collections the list above gives no identifier of their own: reading a reserve ledger row by an unknown `reserveEntryId` answers `ERR_CLAIM_NOT_FOUND` (HTTP 404), borrowing the parent claim's identifier, and reading a loss-estimate snapshot by an unknown `snapshotId` answers `ERR_EVENT_NOT_FOUND` (HTTP 404), borrowing the parent event's.

### 2.5. Record Identity, Audit Fields and the Ledger Exception

Every resource carries an `id` that is a server-minted UUID with no type prefix, and a `created_at` timestamp in ISO 8601 UTC form with exactly three fractional digits, stamped from the logical clock of §2.6 rather than from wall-clock time. Most resources additionally carry `updated_at`, refreshed to the mutation instant on every change, and an integer `version` that starts at 1 when the resource is created and increases by exactly 1 on each mutation of that resource. Clients never supply `id`, `created_at`, `updated_at` or `version`.

Two collections are exceptions, and their shape must not be padded out to match the others. `ReserveEntry` rows and `LossEstimateSnapshot` rows are immutable once written: they carry `id` and `created_at` only, and both `updated_at` and `version` are absent from their representations. This is a direct consequence of the ledger being append-only — a reserve entry is never edited, and a mistaken movement is corrected by appending a compensating entry rather than by mutating the original.

Version increments cascade upward, and the pattern matters because clients use versions as optimistic-concurrency tokens. Every computed roll-up in this system is derived at read time rather than stored, so a `version` advances only where an operation is declared to advance it, never as a silent consequence of a roll-up's value changing. Exactly the following operations increment the parent event's `version` by 1: declaring, activating surge on, demobilizing or closing the event; activating a `CANCELLATION_MORATORIUM` bulletin; opening a housing block; taking first notice of a claim that already names the event, cat-coding, triaging, closing or reopening a claim; confirming, demobilizing or cancelling a deployment; scheduling, completing or cancelling an inspection assignment; appending a manual reserve entry; issuing or voiding an advance payment; minting a loss-estimate snapshot; and submitting or rejecting a file-transfer batch. Everything else leaves the event's `version` untouched, including releasing a housing block, checking a deployment in, starting an inspection, reporting no access, activating or withdrawing a bulletin of any other type, a bulletin expiring, adding a claim to a batch, accepting a batch, reopening a batch, every vendor-firm and vendor-assignment operation, and moving the clock. Any operation that changes a claim's own fields, its handling or payment axis, or its reserve position increments that claim's `version` by 1 — and dispatching a vendor assignment on the claim does too — but a purely clock- or bulletin-driven recomputation of `deadline_utc` does not, and neither does first notice of loss itself, which creates the claim at `version` 1. A single request may therefore increment two versions — triaging a claim, for example, advances both the claim's `version` and its parent event's `version`.

### 2.6. The Logical Clock

All time-dependent behaviour in this system reads a server-owned logical clock rather than wall-clock time. On startup the clock reads exactly 2026-08-01T00:00:00Z, and until a caller moves it, every rule that consults the current instant observes that default. Implementations must not fall back to real system time under any circumstance.

An operator of any role may set the clock to an arbitrary instant by supplying a `to_iso8601` value. Moving the clock is not a passive assignment: it re-evaluates every time-driven system transition for every affected row. Bulletins whose binding window has ended move from `EFFECTIVE` to `EXPIRED`; adjusters whose licence enters its warning window move from `VALID` to `EXPIRING`, and from `EXPIRING` to `EXPIRED` once the licence lapses; adjusters whose rest buffer has elapsed move from `RESTING` back to `AVAILABLE`; and adjusters sustained only by a licence waiver that has stopped covering the current instant fall from `WAIVED` back to `EXPIRED`, which also clears the waiver's recorded event from the adjuster. The credential axis outside `WAIVED` is a pure function of the clock and the licence expiry rather than a one-way ratchet, so it re-derives in both directions: an operator who winds the clock back before the warning window sees an `EXPIRED` or `EXPIRING` adjuster read `VALID` again. Bulletin expiry, in contrast, is one-way — an `EXPIRED` bulletin never returns to `EFFECTIVE`. After those transitions land, every affected event has its moratorium flag, its posture and its claims' acknowledgement deadlines recomputed. The same time-driven re-evaluation is applied lazily on every read and every write, so a caller never observes a row whose state is stale with respect to the clock.

### 2.7. Monetary Precision, Counting and Rounding Order

Unless a rule states otherwise, every monetary quantity is carried and stored to 2 decimal places and every rounding operation rounds half up. Counts — rooms, claims, adjusters, jobs, ledger sequence numbers, whole days — are exact integers and are never rounded. Client-supplied rate inputs that are not money are an exception in the other direction: `expected_severity_index` on an event and `mandated_advance_pct` on a bulletin are stored and echoed back exactly as supplied, never re-quantised to a fixed number of places, and they enter their formulas at full supplied precision.

Where a calculation rounds more than once, the order of rounding is pinned and is part of the contract, because the alternatives produce different cents. Two rules in this system are deliberate opposites of each other, and confusing them is the single most common source of off-by-a-penny divergence. The advance-payment cap rounds **each coverage line to cents first** and then sums the already-rounded line values; the initial case reserve sums **raw line values** and rounds **once at the end**. Neither order may be substituted for the other.

Clamping likewise precedes rounding wherever both appear: the claim severity score and the adjuster surge-capacity score are both clamped into the range from 0 to 100 inclusive *before* the single rounding to 2 decimal places, never after.

### 2.8. Stale-Version Rejection on Reserve and Estimate Writes

Two write endpoints operate under optimistic concurrency control against a parent record's `version`, and on those two endpoints the version field is a required input rather than an optional hint.

A request that creates a loss-estimate snapshot must carry `expected_event_version` holding the client's last observed `version` of the target `CatastropheEvent`. If that value does not equal the event's current `version`, the request is rejected with `ERR_STALE_EVENT_VERSION` (HTTP 412) and nothing is created. A new snapshot legitimately supersedes the previous latest snapshot as the event's headline gross estimate, so the write itself is valid product behaviour; what is not acceptable is computing that estimate from a stale view of the event's reserve roll-ups.

A request that appends a manual reserve entry to a claim must carry `expected_claim_version` holding the client's last observed `version` of that `Claim`. If that value does not equal the claim's current `version`, the request is rejected with `ERR_STALE_CLAIM_VERSION` (HTTP 412) and no ledger row is written. A later revision legitimately supersedes the previous reserve position; rejecting the stale-version form prevents a revision computed against a superseded case reserve from landing.

No other endpoint in this API accepts a version field. Confirming a deployment, closing a claim, issuing an advance, submitting a batch and every other mutation take no `expected_*_version` input at all, and supplying one has no effect.
### 2.9. Event Posture: the Automatic Gate over Child Operations

Alongside its lifecycle `status`, every `CatastropheEvent` carries a read-only `posture` taking one of three values — `OPEN`, `RESTRICTED` or `FROZEN` — ordered from most permissive to most restrictive. Posture is never set by a caller. It is recomputed at the end of every mutation that touches an event or any of its claims, deployments, loss-estimate snapshots or regulatory bulletins, and it is also recomputed on every read of the event, so a caller always observes a posture consistent with the current data and the current clock.

The recompute proceeds in four steps. **Step one establishes a floor from the lifecycle status:** an event whose `status` is `CLOSED` has a floor of `FROZEN`; an event whose `status` is `DEMOBILIZING` has a floor of `RESTRICTED`; every other status — `MONITORING`, `DECLARED`, `SURGE_ACTIVE` — has a floor of `OPEN`.

**Step two accumulates three strain terms.** The first term is the number of claims belonging to the event whose `triage_tier` is either `COMPLEX` or `CAT_SEVERE` and whose `handling_status` is either `TRIAGED` or `REOPENED` — in other words, severe claims that have been triaged but have no live inspection work. Claims in `INTAKE`, `INSPECTION_PENDING`, `INSPECTED`, `CLOSED` or `TRANSFERRED` never contribute to this count. The second term contributes 3 when the event's latest loss-estimate snapshot is stale, and 0 otherwise; the latest snapshot is the one with the greatest `computed_at_utc`, and if several share that instant, the one with the earliest `created_at` wins. When the event has no snapshot at all, this term contributes 0. The third term contributes 4 when the event's `moratorium_active` flag is true, and 0 otherwise. The strain total is the count of unassigned severe claims plus the stale contribution plus the moratorium contribution, and it is an exact integer that is never rounded.

**Step three bands the strain total.** A strain of 8 or more bands as `FROZEN`; a strain of 3 or more but below 8 bands as `RESTRICTED`; a strain below 3 bands as `OPEN`. Both boundaries are inclusive on their lower edge. **Step four takes the stricter of the floor and the band** as the event's `posture`, so a `DEMOBILIZING` event whose strain bands `OPEN` still reads `RESTRICTED`, and any event whose strain reaches 8 reads `FROZEN` even while `SURGE_ACTIVE`.

A `FROZEN` posture blocks child mutation. Seven operations are refused with `ERR_EVENT_POSTURE_FROZEN` (HTTP 409) when the parent event's posture is `FROZEN`: triaging a claim, appending a manual reserve entry to a claim, requesting a deployment, confirming a deployment, scheduling an inspection assignment, issuing an advance payment, and dispatching a vendor assignment. A `RESTRICTED` posture blocks nothing by itself — it is a signal to the catastrophe manager and a floor that keeps a demobilizing event from reading `OPEN` — and confirming a deployment explicitly tolerates both `OPEN` and `RESTRICTED`.

### 2.10. Two Conserved Quantities

**Incurred dollars.** At any instant, an event's `incurred_total` equals the sum, over every reserve entry belonging to that event, of the entry's change to case reserve plus its change to paid loss, rounded to 2 decimal places. The ledger has no status filter and no time window: it is append-only, entries are never retracted, and a reversal is itself an entry that participates in the sum rather than deleting its target. The compensating-action guarantee that follows is exact, not approximate: issuing an advance payment on a claim and then voiding that same advance leaves the event's `incurred_total`, the claim's `case_reserve` and the claim's `paid_amount` each exactly equal to their pre-issuance values. Only the number of ledger rows and the ledger's high-water sequence number advance. This is asserted after every mutation that appends a reserve entry — triage, advance issuance, advance void, a manual entry, and an inspection-driven revision.

**Hotel rooms.** For every housing block, `rooms_total` equals `rooms_available` plus `rooms_occupied`, and `rooms_occupied` equals the sum of `rooms_reserved` over the deployments drawing on that block whose status is `CONFIRMED` or `ON_SITE`. Deployments in `REQUESTED`, `DEMOBILIZED` or `CANCELLED` hold zero rooms. Room counts are integers and are never rounded, and both `rooms_occupied` and `rooms_available` are derived from the deployment population on every read rather than stored, so a block's own `version` advances only when its `status` changes and not when occupancy alone moves. The compensating-action guarantee is again exact: confirming a deployment and then cancelling it leaves the block's `rooms_available` and its `status` exactly equal to their pre-confirm values, and the same holds for confirming and then demobilizing. This is asserted after every mutation that changes a deployment's status and after every change to a housing block's status.

### 2.11. Order of Rejection

A request can violate several rules simultaneously. The response always carries the error belonging to the **lowest-numbered** rule in the ladder below; evaluation stops at the first failure, so a later, more interesting violation is masked by an earlier one. The ladder is global, and the rules that apply to a given request are those whose scope covers it. This ladder, and only this ladder, fixes evaluation order: where §3 narrates a transition's preconditions in some other sequence it is describing the set of conditions, not the order they are tested in.

Positions 1 through 3 are authentication and authorisation: header presence (`ERR_MISSING_AUTH_HEADERS`), role recognition (`ERR_UNKNOWN_ROLE`), then endpoint permission (`ERR_ROLE_NOT_PERMITTED`). Positions 4 through 14 are existence checks in a fixed entity order — event, claim, adjuster, housing block, deployment, inspection assignment, advance payment, vendor firm, vendor assignment, regulatory bulletin, file-transfer batch — each producing its own not-found error. Position 15 is request-schema validation, covering required fields, type correctness, enum membership and numeric ranges: `rooms_total` from 0 through 400, `max_open_claims` from 1 through 60, `expected_severity_index` from 0.0 through 1.0, `mandated_advance_pct` from 0.0 through 1.0, `deadline_extension_days` from 0 through 365, `coverage_lines` holding 1 through 6 entries with no repeated coverage code, `performance_score` from 0 through 100, and `limit` and `offset` within their pagination bounds; the failure is `ERR_VALIDATION` (HTTP 422). Two payload checks that carry their own 422 identifiers rather than `ERR_VALIDATION` sit at this same position 15 and are therefore evaluated ahead of the ownership check at 17 and the state check at 19: `ERR_VERIFIED_AMOUNT_REQUIRED` on inspection completion, and `ERR_REJECTION_REASON_REQUIRED` on batch rejection. Position 16 checks interval well-formedness on bulletin creation, deployment creation, housing-block creation and inspection-assignment creation: a bulletin's `effective_to` must be strictly later than its `effective_from`, a deployment's or assignment's `window_end_utc` strictly later than its `window_start_utc`, and a block's `block_end_date` strictly later than its `block_start_date`, otherwise `ERR_INVALID_WINDOW` (HTTP 422).

Position 17 enforces entity-backed ownership: an `Adjuster` starting, completing or reporting no access on an assignment must be that assignment's adjuster (`ERR_NOT_ASSIGNED_ADJUSTER`), and a `VendorCoordinator` accepting, declining or completing a vendor assignment must be that assignment's firm (`ERR_NOT_ASSIGNED_VENDOR`). Position 18 is the optimistic-concurrency check described in §2.8, on the two endpoints that carry a version field. Position 19 is the state check: the target must currently be in a state from which the requested transition is declared, and the error returned is the specific one named by that transition's preconditions rather than a generic one; `ERR_INVALID_STATE` (HTTP 409) is the fallback used only when a state-transition endpoint is invoked from a from-state that no declared transition covers and no more specific error applies. Position 20 is the frozen-posture gate of §2.9. Position 21 is the moratorium gate. Position 22 is segregation of duties.

Positions 23 through 26 are the temporal rules — the adjuster rest-buffer conflict, the housing aggregate-capacity conflict, the inspection window conflict, and the assignment-inside-deployment containment rule. Positions 27 through 30 are referential rules — adjuster state licensing, vendor state licensing, inspection-mode agreement, and cross-aggregate event scope. Positions 31 through 37 are structural business constraints — uniqueness, adjuster assignment capacity, vendor job capacity, the reopen ceiling, selector pool emptiness, the empty-block rule, and the batch submission gates. Positions 38 through 41 are the fiscal rules — housing room availability at confirm, advance headroom, the advance mandate floor on void, and the non-negative case-reserve rule on manual entries.

Three consequences of this ordering are worth stating outright, because each is a case where the intuitive answer is wrong. Closing a claim that is still `TRIAGED` while a cancellation moratorium is in force returns `ERR_CLAIM_NOT_INSPECTED`, not `ERR_MORATORIUM_ACTIVE`, because the state check at position 19 precedes the safety check at position 21. Confirming a deployment that both breaches the 12-hour rest buffer and asks for more rooms than the block has available returns `ERR_DEPLOYMENT_WINDOW_CONFLICT`, not `ERR_HOUSING_CAPACITY_EXCEEDED`, because the temporal rule at position 23 precedes the fiscal rule at position 38. Scheduling a field-mode inspection against a claim whose resolved mode is aerial, using an adjuster who is already at their assignment ceiling, returns `ERR_INSPECTION_MODE_MISMATCH`, not `ERR_ADJUSTER_AT_CAPACITY`, because the referential rule at position 29 precedes the constraint at position 32.
## 3. Business Logic & Workflows

### 3.1. Standing Up, Escalating and Standing Down a Catastrophe Event

A `CatastropheManager` opens the file on a developing storm by registering a catastrophe event. The registration payload carries the industry `cat_code` the carrier intends to use (between 3 and 24 characters, and unique across all events in the system, compared case-sensitively — a collision is refused with `ERR_CAT_CODE_TAKEN`), the `peril_type` driving the loss, which is one of `HURRICANE`, `WILDFIRE`, `HAIL`, `FLOOD`, `WINTER_STORM` or `EARTHQUAKE`; the `jurisdiction_state` whose regulator will govern the response, as a two-letter uppercase state code; the `event_start_utc` first-loss instant of the footprint; and three underwriting inputs describing the exposed book — `exposure_count`, the number of insured risks inside the footprint, which may be zero but never negative; `avg_insured_value`, the average total insured value per exposed risk in whole dollars, likewise never negative; and `expected_severity_index`, the damage-ratio expectation for this peril footprint, a value from 0.0 through 1.0 inclusive carried to 4 decimal places. A newly registered event begins with `status` of `MONITORING`, a `posture` of `OPEN`, a `version` of 1, and a `declared_at_utc` of null.

Reading an event exposes a wall of computed roll-ups that no caller may write. `open_claim_count` is the number of claims on the event whose `handling_status` is neither `CLOSED` nor `TRANSFERRED`. `case_reserve_total` and `paid_total` are the sums of the case-reserve and paid movements of every ledger entry belonging to the event, each to 2 decimal places, and `incurred_total` is their sum — the conserved quantity of §2.10. `housing_committed_cost` sums, over every housing block on the event whose `status` is `PENDING`, `ACTIVE` or `EXHAUSTED`, that block's `nightly_rate` multiplied by its `rooms_total` multiplied by its `block_night_count`, to 2 decimal places; released blocks drop out of the sum entirely. `deployment_settled_cost` sums the `final_settled_cost` of every deployment on the event that has reached `DEMOBILIZED`, to 2 decimal places. `gross_loss_estimate` mirrors the `gross_estimate` of the event's latest loss-estimate snapshot — the one with the greatest `computed_at_utc`, with ties broken in favour of the earliest `created_at` — and reads 0.00 when the event has no snapshot. `moratorium_active` is true exactly when at least one bulletin on the event has `bulletin_type` of `CANCELLATION_MORATORIUM`, `status` of `EFFECTIVE`, and a binding window that contains the current instant with `effective_from` inclusive and `effective_to` exclusive. `surge_adjuster_count` is the number of deployments on the event whose status is `CONFIRMED` or `ON_SITE`. Listing events supports narrowing by `status`, by `peril_type`, by `jurisdiction_state` and by `posture`, alongside the standard `limit` and `offset`.

**Declaration** moves the event `MONITORING → DECLARED`. It requires that the event still be in `MONITORING` — otherwise `ERR_EVENT_NOT_MONITORING` — and re-checks that the `cat_code` is set and held by no other event, refusing with `ERR_CAT_CODE_TAKEN` if another event has taken it in the meantime. Declaration stamps `declared_at_utc` with the current logical-clock instant and recomputes posture; an event still in `MONITORING` always reads `OPEN`. Declaration is the gate for everything downstream: until it lands, no claim may be cat-coded to the event, no housing block on the event may be opened, no bulletin may take force, and no vendor firm may be activated onto it.

**Surge activation** moves the event `DECLARED → SURGE_ACTIVE` and is where the operational readiness bar sits. The event must be in `DECLARED`, or the request fails with `ERR_EVENT_NOT_DECLARED`. At least one housing block on the event must be in `ACTIVE`, or the request fails with `ERR_NO_ACTIVE_HOUSING` — a carrier does not surge people into a market it has not booked rooms in. And at least one loss-estimate snapshot on the event must be non-stale, or the request fails with `ERR_LOSS_ESTIMATE_STALE`; an event with no snapshots at all fails this check too, since zero rows satisfy the requirement vacuously in the wrong direction. Activation recomputes posture.

**Demobilization** moves the event `SURGE_ACTIVE → DEMOBILIZING`. The event must be in `SURGE_ACTIVE` (`ERR_EVENT_NOT_SURGE_ACTIVE`); the event's `moratorium_active` flag must be false (`ERR_MORATORIUM_ACTIVE`), because a carrier may not wind down its catastrophe operation while the regulator's cancellation moratorium is still in force; and no claim on the event may sit in `INTAKE` or `TRIAGED` (`ERR_UNTRIAGED_CLAIMS_REMAIN`), because those are files nobody has scheduled work on. When it lands, every deployment on the event still in `REQUESTED` is cancelled — those deployments never drew rooms, so no block's `rooms_occupied` changes — and posture is recomputed with a floor of `RESTRICTED`, meaning a demobilizing event can never read `OPEN` again.

**Closure** has two branches, and their side-effect sets are deliberately different. The full path closes the event `DEMOBILIZING → CLOSED` and demands four things: the event is in `DEMOBILIZING` (`ERR_EVENT_NOT_DEMOBILIZING`); no deployment on the event remains in `REQUESTED`, `CONFIRMED` or `ON_SITE` (`ERR_DEPLOYMENTS_STILL_OPEN`); every claim on the event sits in `CLOSED` or `TRANSFERRED` (`ERR_CLAIMS_STILL_OPEN`); and every file-transfer batch on the event has reached `ACCEPTED` (`ERR_TRANSFER_BATCH_UNACCEPTED`). Landing it releases every housing block on the event that is `PENDING`, `ACTIVE` or `EXHAUSTED`, moving each to `RELEASED` — the deployments-still-open precondition guarantees each such block has zero occupied rooms — returns every vendor firm whose activation points at this event **and whose own `status` is `ACTIVATED`** to `NETWORK_INACTIVE` and clears that firm's `activated_for_event_id` — a firm sitting in `CAPACITY_HOLD` is left exactly as it stands, activation pointer included — and sets `posture` to `FROZEN`.

The **stand-down branch** closes the event `DECLARED → CLOSED` for a storm that veered away and never surged. It requires the event to be in `DECLARED` with `open_claim_count` of zero and `surge_adjuster_count` of zero; a `DECLARED` event failing either count is refused with `ERR_EVENT_NOT_STANDDOWN_ELIGIBLE`. Its side-effect set is strictly smaller than the full path's: every housing block on the event in `PENDING` or `ACTIVE` moves to `RELEASED`, and `posture` becomes `FROZEN`. There is no vendor deactivation on this branch and no file-transfer-batch gate, because a stand-down event has no vendor jobs and no transferred files to account for. Attempting closure from any other status, when the stand-down conditions do not apply, is refused with `ERR_EVENT_NOT_DEMOBILIZING`. `CLOSED` is terminal for an event.
### 3.2. Regulatory Bulletins: Moratoriums, Deadline Extensions, Payment Mandates and Licence Waivers

The regulator, not the carrier, decides much of what a catastrophe response may do, and a `ComplianceOfficer` is the only role that may record and operate the resulting instruments. Recording a bulletin takes the `event_id` of the event it regulates, the regulator's own `bulletin_number` (which must be unique within that event — a repeat is refused with `ERR_BULLETIN_NUMBER_TAKEN`), the `jurisdiction_state` the bulletin binds as a two-letter uppercase code, the `bulletin_type`, and the half-open binding window given by `effective_from` and `effective_to`. Two type-specific numeric fields may accompany it: `mandated_advance_pct`, defaulting to 0.0, is the minimum fraction of a claim's reported loss that must be advanced under an advance-payment mandate, expressed from 0.0 through 1.0 inclusive to 4 decimal places; and `deadline_extension_days`, defaulting to 0, is the whole number of days a deadline-extension bulletin adds to a claim's acknowledgement deadline, from 0 through 365 inclusive. A recorded bulletin begins in `DRAFT` with `activated_at_utc` of null, and lists of bulletins may be narrowed by `event_id`, `bulletin_type` and `status`.

Four bulletin types exist and each bites in a different place. `CANCELLATION_MORATORIUM` forbids the carrier from winding down: while one is effective and covering the current instant, the parent event's `moratorium_active` reads true, which both adds 4 to the event's strain total and blocks claim closure and event demobilization with `ERR_MORATORIUM_ACTIVE`. `CLAIM_DEADLINE_EXTENSION` pushes statutory acknowledgement deadlines outward. `ADVANCE_PAYMENT_MANDATE` imposes a floor on how much must be advanced against a claim and, symmetrically, a floor below which advances may not be voided. `ADJUSTER_LICENSE_WAIVER` permits an emergency waiver of an expired adjuster licence.

**Activation** moves a bulletin `DRAFT → EFFECTIVE`. The bulletin must be in `DRAFT` (`ERR_BULLETIN_NOT_DRAFT`); its parent event must be in `DECLARED` or `SURGE_ACTIVE` (`ERR_EVENT_NOT_DECLARED`), since a bulletin cannot bind an event the carrier has not yet declared or has already closed out; and the bulletin's `jurisdiction_state` must equal the parent event's `jurisdiction_state` (`ERR_JURISDICTION_MISMATCH`) — a Florida bulletin does not bind a Texas event. Activation stamps `activated_at_utc` with the current logical-clock instant. If the activated bulletin is a `CLAIM_DEADLINE_EXTENSION`, every claim on the same event whose `handling_status` is neither `CLOSED` nor `TRANSFERRED` has its `deadline_utc` recomputed. If it is a `CANCELLATION_MORATORIUM`, the parent event's `moratorium_active` flag is recomputed and its posture is recomputed with it, which by itself can push an otherwise calm event from `OPEN` to `RESTRICTED`, since the moratorium term alone contributes 4 to strain.

**Withdrawal** is available from either `DRAFT` or `EFFECTIVE`, and any other status — `EXPIRED` or already `WITHDRAWN` — is refused with `ERR_BULLETIN_NOT_WITHDRAWABLE`. Withdrawing from `DRAFT` has no downstream effect, since a draft bulletin never bound anything. Withdrawing from `EFFECTIVE` reverses the instrument's effects: the parent event's `moratorium_active` and posture are recomputed, and `deadline_utc` is recomputed for every claim on the event whose `handling_status` is neither `CLOSED` nor `TRANSFERRED`. Expiry works the same way and needs no operator: once the clock reaches or passes `effective_to`, the bulletin moves `EFFECTIVE → EXPIRED` on the next read or write, the event's `moratorium_active` and posture are recomputed, and the same population of claims has `deadline_utc` recomputed. Both `EXPIRED` and `WITHDRAWN` are terminal.

**The acknowledgement deadline** is a computed field on the claim, refreshed whenever a claim is triaged, whenever a claim is reopened, whenever a deadline-extension bulletin takes force, and whenever an effective bulletin expires or is withdrawn. Its anchor is the claim's `reported_at_utc` when the claim has never been reopened — that is, when `reopen_count` is zero — and otherwise the logical-clock instant stamped by the claim's most recent reopen. The base deadline is that anchor advanced by 15 whole days. To it the system adds the **sum** of `deadline_extension_days` over every bulletin on the claim's event whose `bulletin_type` is `CLAIM_DEADLINE_EXTENSION`, whose `status` is `EFFECTIVE`, and whose binding window contains the current instant with `effective_from` inclusive and `effective_to` exclusive, iterating in `created_at` ascending order. Concurrently effective extensions therefore **stack** rather than competing: two effective ten-day extensions produce twenty days of relief, not ten. Bulletins in `DRAFT`, `EXPIRED` or `WITHDRAWN` contribute zero days. Whole days are added to the anchor instant, and the anchor's time-of-day component is preserved exactly. The population swept whenever a bulletin takes force, expires or is withdrawn, and whenever the clock moves, needs one qualification that applies everywhere in this section: it is every claim on the event whose `handling_status` is neither `CLOSED` nor `TRANSFERRED`, **less** those still sitting in `INTAKE` with a `deadline_utc` of null — an untriaged claim has no anchor the statute recognises yet, so it keeps `deadline_utc` null until triage stamps one, no matter how many extensions are in force meanwhile. These bulletin- and clock-driven refreshes rewrite `deadline_utc` in place without incrementing the claim's `version`.
### 3.3. Adjuster Supply: Two Independent Axes, Rest, Fatigue and Capacity Ranking

A `DeploymentCoordinator` registers the adjuster roster before a storm and maintains it during one. Registration carries the adjuster's `full_name`; their `employment_type`, which is either `STAFF` or `INDEPENDENT` and drives both cost formulas and waiver eligibility; their `home_state` as a two-letter uppercase resident state code; `licensed_states`, the array of two-letter uppercase codes in which they hold an active licence, which must carry at least one entry; the `license_expiry_utc` instant at which that licence lapses; `max_open_claims`, the hard ceiling on concurrently open inspection assignments, from 1 through 60 inclusive; `daily_rate`, the contracted day rate in whole dollars, which must be greater than zero; and `per_diem_rate`, the daily per-diem in whole dollars, which may be zero but never negative. Two optional booleans, `desk_certified` and `aerial_certified`, each default to false and gate the adjuster out of desk and aerial inspection work respectively. A newly registered adjuster is `AVAILABLE` on the deployment axis and `VALID` on the credential axis — except that the licence windows are evaluated against the clock at registration time, so an adjuster registered with an already-lapsed `license_expiry_utc` is stamped `EXPIRED` immediately, and one registered inside the warning window is stamped `EXPIRING` immediately. The surge-capacity score is computed at registration. Adjuster lists may be narrowed by `deployment_status`, by `credential_status`, by `employment_type` and by `licensed_state`, the last matching adjusters holding a licence in the named state.

Each adjuster row carries **two state axes that evolve independently and never gate each other**. The deployment axis — `deployment_status` — takes `AVAILABLE`, `DEPLOYED`, `RESTING` or `UNAVAILABLE`. The credential axis — `credential_status` — takes `VALID`, `EXPIRING`, `EXPIRED` or `WAIVED`. A `WAIVED` adjuster can be `DEPLOYED`; an `AVAILABLE` adjuster can be `EXPIRED`. Neither axis has a terminal state.

On the deployment axis, confirmation of a deployment for an available adjuster moves them `AVAILABLE → DEPLOYED` and recomputes their score. Demobilization of that deployment moves them `DEPLOYED → RESTING`, stamps `last_demobilized_at_utc` with the current logical-clock instant, and — because the adjuster has left `DEPLOYED` — cancels every inspection assignment of theirs still in `SCHEDULED` or `IN_PROGRESS`. Twelve hours of rest later, meaning once the clock reaches or passes `last_demobilized_at_utc` advanced by the rest buffer, they return `RESTING → AVAILABLE` on the next read or write with their score recomputed. That is the full cycle: `AVAILABLE → DEPLOYED → RESTING → AVAILABLE`. Separately, a coordinator may park an available adjuster out of the pool, moving them `AVAILABLE → UNAVAILABLE` — attempted on an adjuster who is not `AVAILABLE`, this is refused with `ERR_ADJUSTER_NOT_AVAILABLE` — and may return them `UNAVAILABLE → AVAILABLE`, which recomputes the score and is refused with `ERR_ADJUSTER_NOT_UNAVAILABLE` when the adjuster was not parked in the first place.

On the credential axis, time does the work. Thirty days before the licence lapses — that is, once the clock reaches or passes `license_expiry_utc` less the warning period while still being earlier than `license_expiry_utc` — the adjuster moves `VALID → EXPIRING` and their score is recomputed with a 15-point credential penalty. Once the clock reaches or passes `license_expiry_utc`, they move `EXPIRING → EXPIRED`, their score is recomputed, and every inspection assignment of theirs still in `SCHEDULED` is cancelled. An expired independent adjuster can be rescued: a `ComplianceOfficer` applies an emergency licence waiver, naming the `event_id` whose regulator issued the waiver, which moves the adjuster `EXPIRED → WAIVED` and recomputes the score with an 8-point credential penalty. Three conditions guard it — the adjuster's `credential_status` must be `EXPIRED` (`ERR_CREDENTIAL_NOT_EXPIRED`); a bulletin of type `ADJUSTER_LICENSE_WAIVER` must be `EFFECTIVE`, must bind the named event's `jurisdiction_state`, and must cover the current instant with `effective_from` inclusive and `effective_to` exclusive (`ERR_NO_LICENSE_WAIVER_IN_FORCE`); and the adjuster's `employment_type` must be `INDEPENDENT`, since a staff adjuster's licence is the carrier's own problem (`ERR_WAIVER_NOT_ELIGIBLE`). A waiver is not permanent, and the event named when it was applied is remembered as the waiver's anchor. Once no `ADJUSTER_LICENSE_WAIVER` bulletin **on that remembered event**, binding that event's `jurisdiction_state`, is `EFFECTIVE` and covering the current instant — the adjuster's own `licensed_states` and `home_state` play no part in the test — they fall back `WAIVED → EXPIRED` on the next read or write, the remembered anchor is cleared, their score is recomputed, and every `SCHEDULED` assignment of theirs is cancelled — the same credential-axis cycle running in reverse: `EXPIRED → WAIVED → EXPIRED`.

**The surge-capacity score** is the ranking key the deployment selector sorts on, and it is recomputed whenever either of the adjuster's axes changes, whenever an inspection assignment for them is created or leaves `SCHEDULED` or `IN_PROGRESS`, and whenever a deployment for them reaches `ON_SITE` or `DEMOBILIZED`. It is built from four terms. The **availability term** starts from the adjuster's `open_assignment_count` — the number of their inspection assignments currently in `SCHEDULED` or `IN_PROGRESS` — divided by their `max_open_claims`; that load ratio is capped at 1, subtracted from 1, and multiplied by 100, so an idle adjuster contributes 100 points and a fully loaded one contributes zero. From that, the **credential penalty** for the adjuster's current `credential_status` is subtracted: zero points for `VALID`, 15 points for `EXPIRING`, 8 points for `WAIVED`, and 100 points for `EXPIRED`. Then the **fatigue penalty** is subtracted: the adjuster's `cumulative_deployed_hours` divided by 24 and rounded down to a whole number of full days, multiplied by 3 points per full day, and capped at 30 points — so fatigue stops biting after ten full days of accumulated deployment. Finally the **certification bonus** is added: 5 points if `desk_certified` is true plus a further 5 points if `aerial_certified` is true, for a maximum of 10. The result is clamped so that it is not below 0 and not above 100, and only then rounded half up to 2 decimal places into `surge_capacity_score`. The `cumulative_deployed_hours` input is itself computed: the sum, over the adjuster's deployments whose status is `ON_SITE` or `DEMOBILIZED`, of the number of hours from that deployment's `window_start_utc` to its `window_end_utc`, to 2 decimal places. Deployments in other statuses contribute nothing.
### 3.4. Housing Logistics: Room Blocks and the Nightly Capacity Rule

Rooms in the staging city are the scarcest resource in a catastrophe response, and a `DeploymentCoordinator` holds them in blocks. Creating a block names the `event_id` it supports, the `hotel_name` of the property, the `city` it is staged in, the `rooms_total` held in the block (from 0 through 400 inclusive), the per-room `nightly_rate` in whole dollars (which must be greater than zero), and the block's date span: `block_start_date` is the first night, inclusive, and `block_end_date` is the checkout morning — exclusive as a night but inclusive as a same-day turnover date — with both midnight-aligned and `block_end_date` strictly later than `block_start_date`. From that span the system computes `block_night_count`, the number of whole days from `block_start_date` up to but not including `block_end_date`. A newly held block is `PENDING`, with `rooms_occupied` of zero and `rooms_available` equal to `rooms_total`. Blocks may be listed filtered by `event_id`, by `status` and by `city`.

Opening a block moves it `PENDING → ACTIVE` and is refused with `ERR_HOUSING_NOT_PENDING` from any other status. Two further conditions apply, and the ladder of §2.11 tests them in the reverse of the order they read most naturally in: the parent event must be `DECLARED` or `SURGE_ACTIVE`, otherwise `ERR_EVENT_NOT_DECLARED`, checked first as a state check at position 19; and the block must hold at least one room, so a block created with `rooms_total` of zero can never be opened and any attempt is refused with `ERR_HOUSING_BLOCK_EMPTY` at position 36. Opening recomputes the parent event's `housing_committed_cost`, because the block now sits in the committed population.

Occupancy drives the middle of the block's life automatically. When a deployment confirmation draws the last free room and `rooms_available` lands on exactly zero, the block moves `ACTIVE → EXHAUSTED`. When rooms come back — a confirmed deployment is cancelled or demobilized — and `rooms_available` rises to 1 or more, the block moves `EXHAUSTED → ACTIVE`. That cycle, `ACTIVE → EXHAUSTED → ACTIVE`, can run any number of times.

Releasing a block hands the inventory back to the hotel and is available from `PENDING`, `ACTIVE` or `EXHAUSTED`; a block already `RELEASED` is refused with `ERR_HOUSING_NOT_RELEASABLE`. In every case `rooms_occupied` must be exactly zero, otherwise the release is refused with `ERR_HOUSING_STILL_OCCUPIED`. The three release branches differ only in bookkeeping. Releasing from `ACTIVE` recomputes the parent event's `housing_committed_cost`, since released blocks drop out of that sum. Releasing from `PENDING` has no further effect, because a pending block was never committed against a deployment. And `EXHAUSTED → RELEASED` also happens without an operator, when the parent event closes from either `DEMOBILIZING` or `DECLARED`; that path likewise recomputes `housing_committed_cost`, and its zero-occupancy requirement is guaranteed by the event's own no-open-deployments precondition. `RELEASED` is terminal.

The capacity rule on a block is **aggregate and nightly**, not exclusive. Overlap between deployments is entirely legal — a block exists precisely so that many adjusters can share it — and a confirmation is refused only when the total `rooms_reserved` across the deployments occupying any shared night would exceed the block's `rooms_total`. The night set of an interval is the set of whole days from its start date up to but not including its end date, so a deployment checking out on the same date another deployment arrives shares no night with it and can never conflict with it. The rejection carries `ERR_HOUSING_CAPACITY_EXCEEDED` (HTTP 409).

### 3.5. Deploying the Surge Workforce and Settling What It Cost

A deployment request from a `DeploymentCoordinator` names the `event_id` the adjuster is surged onto, the `role_type` — `FIELD`, `DESK` or `AERIAL` — and the half-open occupancy window given by `window_start_utc`, inclusive, and `window_end_utc`, exclusive and strictly later. Three fields are optional. `housing_block_id` names the room block backing the deployment and is null for desk work. `rooms_reserved` ranges from 0 through 4 inclusive and must be exactly 0 when `role_type` is `DESK`, a violation being `ERR_VALIDATION`; its default when omitted is role-dependent rather than fixed, reading 0 for a `DESK` deployment and 1 for a `FIELD` or `AERIAL` one, so a desk request never has to state it and never trips the zero-rooms rule by silence. And `adjuster_id` may either pin a specific adjuster or be omitted entirely, which is the caller's way of asking the server to choose. Cross-aggregate scope is enforced here at request time rather than at confirmation: a `housing_block_id` naming a block that belongs to some other event than the one the deployment is requested against is refused with `ERR_EVENT_SCOPE_MISMATCH` (HTTP 409), at ladder position 30 and so after the frozen-posture gate. The created deployment is `REQUESTED`, its `selection_reason` records `EXPLICIT_ADJUSTER` when the caller pinned an adjuster and `SELECTOR_RANKED` when the server chose, both `provisional_cost` and `final_settled_cost` read 0.00 because a requested deployment has not been priced and has drawn no rooms, and `surge_premium_tier` reads `TIER_NONE` until confirmation stamps a real band. Deployment lists may be filtered by `event_id`, `adjuster_id`, `housing_block_id`, `status` and `role_type`.

**The selector** runs whenever the adjuster reference is omitted. Its eligibility filter admits an adjuster only when all of the following hold: their `deployment_status` is `AVAILABLE`; their `credential_status` is `VALID`, `EXPIRING` or `WAIVED`; either the event's `jurisdiction_state` appears in their `licensed_states` or their `credential_status` is `WAIVED`; their `open_assignment_count` is strictly below their `max_open_claims`; the requested role is not `DESK` unless `desk_certified` is true; the requested role is not `AERIAL` unless `aerial_certified` is true; and no deployment of theirs in `CONFIRMED`, `ON_SITE` or `DEMOBILIZED` violates the twelve-hour rest separation described below. All adjuster rows in the system pass through this filter — there is no pre-filtering by event. Survivors are ranked by `surge_capacity_score` descending, comparing the stored two-decimal values exactly. When scores tie exactly, the higher `max_open_claims` wins; when that ties too, the earlier `created_at` wins. Record identifiers are never used as a tie-break. The first row is selected. If the candidate set is empty, nothing is created and the request is rejected with `ERR_NO_ELIGIBLE_ADJUSTER` (HTTP 409).

**Confirmation** moves the deployment `REQUESTED → CONFIRMED` and is where every eligibility question is asked again, in earnest. The deployment must be in `REQUESTED` (`ERR_DEPLOYMENT_NOT_REQUESTED`). The parent event's posture must be `OPEN` or `RESTRICTED`, never `FROZEN` (`ERR_EVENT_POSTURE_FROZEN`). The adjuster's `deployment_status` must be `AVAILABLE` (`ERR_ADJUSTER_NOT_AVAILABLE`) and their `credential_status` must be `VALID`, `EXPIRING` or `WAIVED` (`ERR_ADJUSTER_CREDENTIAL_INVALID`). The event's `jurisdiction_state` must appear in the adjuster's `licensed_states`, unless their `credential_status` is `WAIVED`, in which case the licensing requirement is satisfied by the waiver (`ERR_ADJUSTER_NOT_LICENSED_IN_STATE`, HTTP 422). The **rest-buffer rule** must hold: for the window being confirmed, no other deployment of the same adjuster in `CONFIRMED`, `ON_SITE` or `DEMOBILIZED` may sit closer than twelve hours on either side. Concretely, a conflict exists when the new window's start is earlier than the other window's end extended forward by twelve hours *and* the other window's start is earlier than the new window's end extended forward by twelve hours. Exact adjacency is therefore **rejected**: a full twelve-hour gap must separate the windows, and the rejection is `ERR_DEPLOYMENT_WINDOW_CONFLICT`. Finally, unless `role_type` is `DESK`, the deployment must name a housing block, that block must be `ACTIVE`, and its `rooms_available` must be at least the deployment's `rooms_reserved`, failing which the answer is `ERR_HOUSING_CAPACITY_EXCEEDED` — as is the aggregate-nightly test of §3.4, which is re-run here at ladder position 24 and so ahead of the licensing check, while this simple availability test sits at position 38 and so behind it. Cross-aggregate scope needs no re-asking at confirmation because deployment creation already refused any block belonging to another event.

Confirmation then does five things at once. It stamps `provisional_cost` and `surge_premium_tier` from the provisional variant of the cost rule. It adds the deployment's `rooms_reserved` to the block's `rooms_occupied` and recomputes `rooms_available`, taking the block `ACTIVE → EXHAUSTED` if availability lands on zero. It moves the adjuster `AVAILABLE → DEPLOYED` and recomputes their surge-capacity score. And it recomputes the parent event's `surge_adjuster_count` and posture.

**Check-in** moves the deployment `CONFIRMED → ON_SITE` once the adjuster physically arrives. The deployment must be `CONFIRMED` (`ERR_DEPLOYMENT_NOT_CONFIRMED`) and the clock must have reached or passed `window_start_utc` (`ERR_DEPLOYMENT_WINDOW_NOT_STARTED`). Check-in recomputes the adjuster's `cumulative_deployed_hours` and, with it, their surge-capacity score; both are derived at read time, so the only `version` that advances is the deployment's own — neither the adjuster's nor the event's moves.

**Demobilization** is available from either `CONFIRMED` or `ON_SITE` — from anything else it is refused with `ERR_DEPLOYMENT_NOT_DEMOBILIZABLE` — and both source states run the identical five-link cascade. Link one stamps `demobilized_at_utc` with the current logical-clock instant, stamps `final_settled_cost` from the final-settled variant of the cost rule, and re-stamps `surge_premium_tier`; the block's `rooms_occupied` falls by the deployment's `rooms_reserved`, `rooms_available` is recomputed, and a block that was `EXHAUSTED` returns to `ACTIVE` once availability is 1 or more. Link two, caused by link one, moves the adjuster `DEPLOYED → RESTING` and stamps their `last_demobilized_at_utc` with the same instant. Link three, caused by the adjuster leaving `DEPLOYED`, cancels every inspection assignment of that adjuster still in `SCHEDULED` or `IN_PROGRESS`. Link four, caused by those cancellations, regresses each affected claim that is `INSPECTION_PENDING` and now has no assignment left in `SCHEDULED` or `IN_PROGRESS` back to `TRIAGED`. Link five, caused by those regressions raising the count of unassigned severe claims, recomputes the parent event's posture, which may flip it from `OPEN` to `RESTRICTED`. Alongside the chain, the event's `deployment_settled_cost` and `surge_adjuster_count` are recomputed.

**Cancellation** is available from `REQUESTED` or `CONFIRMED`, and any other status is refused with `ERR_DEPLOYMENT_NOT_CANCELLABLE`. From `REQUESTED` it is nearly free: no rooms were ever drawn, so the block's `rooms_occupied` does not move. From `CONFIRMED` it is the compensating action for the room-conservation invariant, and it carries one extra precondition — no inspection assignment funded by this deployment may be in `IN_PROGRESS` or `COMPLETED`, otherwise `ERR_ASSIGNMENTS_IN_FLIGHT`. Its links run in order: `final_settled_cost` is set to 0.00 while `provisional_cost` and the `surge_premium_tier` stamped at confirmation are both retained for audit; the release of the draw returns `rooms_reserved` to the block, restoring `rooms_available` to exactly its pre-confirm value; that restoration takes a block that was `EXHAUSTED` back to `ACTIVE` when availability reaches 1 or more; the adjuster moves `DEPLOYED → RESTING` with `last_demobilized_at_utc` stamped at the current instant; and the event's `surge_adjuster_count`, `housing_committed_cost` and posture are recomputed. Both `DEMOBILIZED` and `CANCELLED` are terminal.

**Deployment cost** is computed in one pass, in a pinned order, and produces both a dollar total and the `surge_premium_tier` band. Step one establishes the number of nights: the whole days from the deployment's `window_start_utc` up to but not including a settle-end instant, with a floor of 1 night so that a same-day deployment is never free. Step two computes labour: the adjuster's `daily_rate` multiplied by a rate factor and by the nights, rounded to 2 decimal places, where the rate factor is exactly 1 for a `STAFF` adjuster and 1.35 for an `INDEPENDENT` one. Step three computes the two remaining direct costs: per-diem is the adjuster's `per_diem_rate` multiplied by the nights and by a per-diem eligibility flag of 1 or 0, rounded to 2 decimal places; and the housing share is the block's `nightly_rate` multiplied by the deployment's `rooms_reserved` and by the nights, rounded to 2 decimal places, or exactly 0.00 when `role_type` is `DESK` or no housing block is named. The subtotal before premium is the rounded sum of labour, per-diem and housing share. Step four picks the tier **from that subtotal alone, never from the post-premium total**, so no iteration is needed and the answer is well-defined in a single pass: a subtotal of 20000.00 or more is `TIER_HIGH` at a premium rate of 11 percent; a subtotal of 5000.00 or more but below 20000.00 is `TIER_MID` at 6 percent; anything below 5000.00 is `TIER_NONE` at zero. The surge premium is the subtotal multiplied by that rate, rounded to 2 decimal places, and the total is the rounded sum of subtotal and premium. Only the deployment row, its adjuster and — for non-desk roles — its housing block feed the computation; sibling deployments never participate.

The two variants differ in exactly two inputs, and for identical stored data they produce different money. The **provisional** variant, stamped into `provisional_cost` at confirmation, uses the deployment's full requested `window_end_utc` as the settle-end instant and treats per-diem eligibility as 1 unconditionally, so an independent adjuster with a hotel room is charged per-diem *and* housing. The **final-settled** variant, stamped into `final_settled_cost` at demobilization, uses the earlier of the deployment's `window_end_utc` and its `demobilized_at_utc` as the settle-end instant, so an early demobilization shortens the nights; and it grants per-diem eligibility of 1 only when the adjuster's `employment_type` is `STAFF` or the deployment names no housing block, so an independent adjuster in company housing loses per-diem entirely. Because both differences move the nights and the per-diem, either can also move the deployment into a different `surge_premium_tier`.
### 3.6. First Notice of Loss, Cat Coding and Triage

A `ClaimsExaminer` takes first notice of loss. The intake payload carries the `policy_number`, the `loss_state` in which the loss occurred as a two-letter uppercase code, the `loss_date_utc` date of loss, the `reported_loss_amount` first-notice estimate in whole dollars (which may be zero but never negative), and `coverage_lines`. That last field is an **ordered array of 1 through 6 entries**, each holding a `coverage_code` of `DWELLING`, `CONTENTS`, `ALE` or `OTHER_STRUCTURES`, a `limit_amount`, a `deductible_amount` and an `estimated_damage_amount` — all three of those amounts being required numbers on every entry and none of them permitted to be negative; no coverage code may repeat within the array, and the array order as supplied at intake is the pinned iteration order for the advance-payment computation. Two fields are optional: `event_id` may be supplied at intake if the catastrophe code is already known, or left null and attached later; and `access_status` defaults to `ACCESSIBLE` and otherwise takes `INACCESSIBLE` or `RESTRICTED`, asserting how reachable the property is. Another claim already holding the same `policy_number` and `loss_date_utc` pair makes the intake a duplicate, refused with `ERR_DUPLICATE_CLAIM`.

A new claim is `INTAKE` on the handling axis and `NONE` on the payment axis, with `reported_at_utc` stamped at the current logical-clock instant, `severity_score` of 0.00, `reopen_count` of 0, and `triage_tier`, `inspection_mode`, `deadline_utc` and `verified_damage_amount` all null. When `event_id` was supplied, the parent event's `open_claim_count` and posture are recomputed at once. Claim lists may be filtered by `event_id`, `transfer_batch_id`, `handling_status`, `payment_status`, `triage_tier` and `loss_state`.

Like the adjuster, a claim carries **two independent state axes**. The handling axis — `handling_status` — runs `INTAKE`, `TRIAGED`, `INSPECTION_PENDING`, `INSPECTED`, `CLOSED`, `REOPENED` and `TRANSFERRED`, with `TRANSFERRED` terminal. The payment axis — `payment_status` — runs `NONE`, `ADVANCE_ISSUED`, `PARTIAL_PAID` and `SETTLED`. Neither axis gates the other: a claim may be `TRIAGED` while its payment axis already reads `ADVANCE_ISSUED`, and equally a claim may be `INSPECTED` while its payment axis still reads `NONE`.

**Cat coding** attaches an intake claim to a declared or surge-active catastrophe event by supplying that event's `event_id`; the claim's own `event_id` is set, and the event's `open_claim_count` and posture are recomputed. The claim must still be in `INTAKE`, or the attempt is refused with `ERR_CLAIM_NOT_IN_INTAKE`; that check is evaluated first, and only then is the named event's own `status` tested, an event that is neither `DECLARED` nor `SURGE_ACTIVE` being refused with `ERR_EVENT_NOT_DECLARED`.

**Triage** moves the claim `INTAKE → TRIAGED` and is the moment every derived property of the claim comes into existence. Four preconditions guard it: the claim must be in `INTAKE` (`ERR_CLAIM_NOT_IN_INTAKE`); its `event_id` must not be null (`ERR_CLAIM_NOT_CAT_CODED`); the parent event's `status` must be `DECLARED` or `SURGE_ACTIVE` (`ERR_EVENT_NOT_DECLARED`); and the parent event's posture must not be `FROZEN` (`ERR_EVENT_POSTURE_FROZEN`). Triage stamps `severity_score` and `triage_tier`, stamps `inspection_mode`, stamps `deadline_utc`, and appends an `INITIAL_CASE` entry to the reserve ledger whose case-reserve movement comes from the initial-reserve rule and whose paid movement is exactly 0.00, taking the next per-event sequence number. It then recomputes the claim's `case_reserve` and the event's `case_reserve_total` and `incurred_total`, flips every loss-estimate snapshot on the event whose recorded ledger high-water mark is below the new sequence number to stale, and recomputes posture.

**The severity score** is a weighted composite of five inputs. Start from the claim's exposure: sum `limit_amount` across every coverage line, divide the `reported_loss_amount` by that total (or by 1 if the total is smaller than 1, which protects the division), cap the resulting ratio at 1, and multiply by 100 to get the base. Multiply the base by the peril weight of the parent event's `peril_type` — 1.15 for `HURRICANE`, 1.25 for `WILDFIRE`, 1.20 for `FLOOD`, 0.95 for `HAIL`, 0.90 for `WINTER_STORM`, and 1.30 for `EARTHQUAKE`. To that product add the access adjustment for the claim's `access_status`: nothing for `ACCESSIBLE`, 6 points for `RESTRICTED`, and 12 points for `INACCESSIBLE`. Add a further 10 points when any coverage line has a `coverage_code` of `ALE` and an `estimated_damage_amount` greater than zero, and nothing otherwise. Finally add 20 times the parent event's `expected_severity_index`. Clamp the result so it is not below 0 and not above 100, and only then round half up to 2 decimal places — a single rounding, applied after the clamp. Every coverage line participates in both the limit sum and the ALE test, and the event's `peril_type` and `expected_severity_index` are read at triage time and never re-read afterwards.

The score then selects the band recorded in `triage_tier`: a score of 75.00 or more is `CAT_SEVERE`, a score of 50.00 or more but below 75.00 is `COMPLEX`, a score of 25.00 or more but below 50.00 is `STANDARD`, and anything below 25.00 is `FAST_TRACK`.

**The initial case reserve** is deliberately rounded the other way round from the advance cap. First compute the eligible damage of each coverage line as the line's `estimated_damage_amount` capped at its `limit_amount`, less its `deductible_amount`, with a floor of zero; sum those **raw, unrounded** line values; take the greater of that sum and the claim's `reported_loss_amount` as the basis; multiply the basis by the tier reserve factor for the claim's `triage_tier` — 0.85 for `CAT_SEVERE`, 0.65 for `COMPLEX`, 0.45 for `STANDARD`, 0.25 for `FAST_TRACK` — and round half up to 2 decimal places **once, at the end**. The paid movement of the entry is 0.00. The tier used is the one stamped moments earlier in the same request, since the score and tier are computed before the ledger entry is appended.

**The inspection mode** is resolved by taking the first matching branch, top to bottom, and is recomputed at triage, on reopen, and when an adjuster reports the property inaccessible. If the claim's `access_status` is `INACCESSIBLE` and its `triage_tier` is `COMPLEX` or `CAT_SEVERE`, the mode is `AERIAL` — a severe loss nobody can drive to gets flown. Otherwise, if `access_status` is `INACCESSIBLE`, the mode is `DESK`. Otherwise, if `access_status` is `RESTRICTED` and the tier is `FAST_TRACK`, the mode is `DESK`. Otherwise, if the tier is `FAST_TRACK` and the `reported_loss_amount` is 10000.00 or less, the mode is `DESK` — the boundary is inclusive, so a reported loss of exactly 10000.00 resolves to `DESK` while 10000.01 resolves to `FIELD`. In every remaining case the mode is `FIELD`.

**Closure** moves the claim `INSPECTED → CLOSED`, and five conditions guard it. The claim must be `INSPECTED` (`ERR_CLAIM_NOT_INSPECTED`). The parent event's `moratorium_active` must be false (`ERR_MORATORIUM_ACTIVE`). The acting `X-User-ID` must differ from the claim's `advance_issuing_examiner_user_id`, so that whoever released advance money on this file is not also the person who signs it shut (`ERR_SEGREGATION_OF_DUTIES`, HTTP 403). The claim's `payment_status` must be either `NONE` or `SETTLED` — a file sitting in `ADVANCE_ISSUED` or `PARTIAL_PAID` has money out the door and unfinished settlement, and closing it is refused with `ERR_ADVANCE_OUTSTANDING`. And no vendor assignment on the claim may be in `DISPATCHED` or `ACCEPTED` (`ERR_VENDOR_JOB_OPEN`). Closure records the acting `X-User-ID` in `closing_examiner_user_id` and recomputes the event's `open_claim_count` and posture.

**Reopening** moves the claim `CLOSED → REOPENED` and may happen at most twice in a claim's life. The claim must be `CLOSED` (`ERR_CLAIM_NOT_CLOSED`); then the parent event must not be `CLOSED` (`ERR_EVENT_CLOSED`); and only then is the count tested, `reopen_count` having to be strictly below 2, so a claim that has already been reopened twice is refused with `ERR_REOPEN_LIMIT_REACHED`. Reopening increments `reopen_count` by 1, clears `closing_examiner_user_id` back to null, and recomputes `deadline_utc` against the new anchor along with `severity_score`, `triage_tier` and `inspection_mode`. The event's `open_claim_count` and posture are recomputed, since the file is live again. The resulting handling-axis cycle is `INSPECTED → CLOSED → REOPENED → INSPECTION_PENDING → INSPECTED → CLOSED`.
### 3.7. Inspecting the Loss: Field, Desk and Aerial Work

Scheduling an inspection is a `DeploymentCoordinator` action. The payload names the `claim_id` to be inspected, the `mode` the work will be performed in — `FIELD`, `DESK` or `AERIAL` — and the half-open assignment window given by `window_start_utc`, inclusive, and `window_end_utc`, exclusive and strictly later. Optionally it names `adjuster_id` to pin a specific adjuster, or omits it so the server selects one using the same eligibility filter, `surge_capacity_score` descending ranking, and `max_open_claims` descending then `created_at` ascending tie-break described for deployments — with the requested `mode` playing the role the deployment's `role_type` plays there, so desk work needs `desk_certified` and aerial work needs `aerial_certified`. An empty candidate pool is `ERR_NO_ELIGIBLE_ADJUSTER` and nothing is created. Optionally it also names `deployment_id`, the deployment that funds the work; desk assignments leave this null. Assignment lists may be filtered by `claim_id`, `adjuster_id`, `deployment_id`, `status` and `mode`.

Six checks stand between the request and a scheduled assignment, beyond the frozen-posture gate. The submitted `mode` must equal the claim's `inspection_mode` **as currently computed**, not as it stood at triage — a claim whose access has since degraded needs the mode the resolver returns now, and a mismatch is `ERR_INSPECTION_MODE_MISMATCH` (HTTP 422); an untriaged claim has no tier to resolve a mode from, so its stored null `inspection_mode` is what the submitted mode is compared against, and every submitted mode therefore mismatches. Three of the remaining checks — licensing, capacity and the window conflict — police an adjuster the caller **explicitly pinned**, and are skipped entirely when `adjuster_id` was omitted, because the selector's own eligibility filter already excludes unlicensed, at-capacity and window-clashing candidates and an empty result is reported as `ERR_NO_ELIGIBLE_ADJUSTER` instead. The event's `jurisdiction_state` must appear in the named adjuster's `licensed_states` unless their `credential_status` is `WAIVED` (`ERR_ADJUSTER_NOT_LICENSED_IN_STATE`). The named adjuster's `open_assignment_count` must be strictly below their `max_open_claims`, evaluated before this new assignment is counted, otherwise `ERR_ADJUSTER_AT_CAPACITY` (HTTP 409). The window must not clash with the named adjuster's other live inspection work: under **strict half-open, zero-buffer** semantics, a conflict exists when the new window's start is earlier than another `SCHEDULED` or `IN_PROGRESS` assignment's end *and* that assignment's start is earlier than the new window's end. Because the buffer is zero, exact adjacency is **accepted** — an assignment starting at the precise instant another ends is legal, in deliberate contrast to the twelve-hour rest buffer that governs deployments — and a genuine overlap is `ERR_ASSIGNMENT_WINDOW_CONFLICT`. When a funding deployment is named, the assignment window must be fully **contained** in it: the deployment's `window_start_utc` must be at or before the assignment's `window_start_utc`, and the assignment's `window_end_utc` must be at or before the deployment's `window_end_utc`, otherwise `ERR_ASSIGNMENT_OUTSIDE_DEPLOYMENT` (HTTP 422). And the funding deployment must belong to the same event as the claim, otherwise `ERR_EVENT_SCOPE_MISMATCH`.

A created assignment is `SCHEDULED`, records `EXPLICIT_ADJUSTER` or `SELECTOR_RANKED` in `selection_reason`, and starts with `report_submitted_at_utc` and `verified_damage_amount` both null. Creation also pulls the claim onto the inspection track: a claim in `TRIAGED` moves `TRIAGED → INSPECTION_PENDING`, and a claim in `REOPENED` moves `REOPENED → INSPECTION_PENDING`, while a claim sitting in any other handling status is left exactly where it is, with no error raised and the assignment still created; both branches are driven by the same event — an assignment for the claim coming into existence in `SCHEDULED` — and both leave no further side effects of their own. The adjuster's `open_assignment_count` and `surge_capacity_score` are recomputed, and the event's posture is recomputed, since the claim has just stopped counting as unassigned.

The assigned `Adjuster` — and only they, since `X-User-ID` must equal the assignment's `adjuster_id` or the call is refused with `ERR_NOT_ASSIGNED_ADJUSTER` — drives the assignment from there. **Starting** the inspection moves it `SCHEDULED → IN_PROGRESS`; the assignment must be `SCHEDULED` (`ERR_ASSIGNMENT_NOT_SCHEDULED`), the clock must have reached or passed `window_start_utc` (`ERR_ASSIGNMENT_WINDOW_NOT_STARTED`), and the adjuster's `credential_status` must be `VALID`, `EXPIRING` or `WAIVED` (`ERR_ADJUSTER_CREDENTIAL_INVALID`) — a licence that lapsed between scheduling and arrival stops the work at the door.

**Completing** the inspection moves it `IN_PROGRESS → COMPLETED` and requires a `verified_damage_amount` in the payload that is present and not negative; omitted or negative, the answer is `ERR_VERIFIED_AMOUNT_REQUIRED` (HTTP 422). From a status other than `IN_PROGRESS` the call is refused with `ERR_ASSIGNMENT_NOT_IN_PROGRESS`. Completion stamps `report_submitted_at_utc` at the current logical-clock instant, recomputes the adjuster's `open_assignment_count` and `surge_capacity_score`, and pushes the claim `INSPECTION_PENDING → INSPECTED`. The claim's own `verified_damage_amount` is refreshed from the completed assignment with the greatest `report_submitted_at_utc`, with ties broken by the earliest `created_at`, and a `REVISION` entry is appended to the reserve ledger.

**Reporting no access** moves the assignment `IN_PROGRESS → NO_ACCESS` — the adjuster arrived and could not reach the property — and is guarded by the same `IN_PROGRESS` requirement and the same ownership check. It stamps `report_submitted_at_utc`, flips the claim's `access_status` to `INACCESSIBLE`, re-resolves the claim's `inspection_mode` through the branch ladder of §3.6 (which for a severe claim now yields `AERIAL` and for a lighter one `DESK`), and pushes the claim `INSPECTION_PENDING → INSPECTED` — but with `verified_damage_amount` left null and **no** `REVISION` ledger entry, because nothing was verified. This asymmetry between the two ways an inspection can end is deliberate: a completed inspection revises the reserve, a no-access inspection revises the claim's routing.

**The reserve revision** that accompanies a completed inspection is computed as follows. Sum the `deductible_amount` of every coverage line on the claim. Subtract that total from the claim's newly refreshed `verified_damage_amount`, floor the result at zero, and round half up to 2 decimal places to obtain the target case reserve. The entry's case-reserve movement is that target less the claim's `case_reserve` as it stands immediately before the append, rounded half up to 2 decimal places — a figure that is frequently **negative**, when an inspection verifies less damage than the first notice suggested. The entry's paid movement is 0.00. The pre-append `case_reserve` already reflects any `INITIAL_CASE` entry, any `PAYMENT` entry from an issued advance, and any `REVERSAL` entry from a voided one, so the revision always lands the claim exactly on its target rather than on a figure that ignores payments.

**Cancelling** an assignment is available from `SCHEDULED` or `IN_PROGRESS`, and any other status is refused with `ERR_ASSIGNMENT_NOT_CANCELLABLE`. A `DeploymentCoordinator` may cancel directly, and the system cancels assignments on its own behalf as link three of the demobilization cascade and as the credential-lapse and waiver-loss cascades of §3.3. Either source state behaves identically: the adjuster's `open_assignment_count` and `surge_capacity_score` are recomputed, and when the claim has no assignment left in `SCHEDULED` or `IN_PROGRESS`, the claim regresses `INSPECTION_PENDING → TRIAGED` and the event's posture is recomputed — which is how a mass demobilization can tighten an event's posture without anyone touching the event. `COMPLETED`, `NO_ACCESS` and `CANCELLED` are all terminal.
### 3.8. The Reserve Ledger, Advance Payments, Settlement and Loss Estimation

Every dollar in this system moves through one append-only ledger. A ledger row records the `event_id` it rolls up to (denormalised from the claim so event-level totals need no join), the `claim_id` whose reserve moved, an `entry_type` of `INITIAL_CASE`, `REVISION`, `PAYMENT` or `REVERSAL`, the signed `delta_case_reserve` and signed `delta_paid` movements in dollars to 2 decimal places, a `sequence_no` that is a per-event monotone integer starting at 1 and assigned in append order, an `effective_utc` stamped at the current logical-clock instant when the row is written, a machine-generated `memo` describing the originating action, and a `reverses_entry_id` that is populated only on a `REVERSAL` row and null on every other type. Rows are never edited or deleted, which is why they carry no `updated_at` and no `version`. The ledger may be listed filtered by `event_id`, by `claim_id`, by `reverses_entry_id` and by `entry_type`, and it is returned in `sequence_no` ascending order — the same order the incurred-development estimator replays.

A `ClaimsExaminer` may append a movement manually, and this is one of the two operations in the system carrying an optimistic-concurrency token: the payload must include `expected_claim_version` matching the claim's current `version`, or the append is rejected with `ERR_STALE_CLAIM_VERSION` (HTTP 412) and no row is written. Alongside it the payload carries the `entry_type`, the signed `delta_case_reserve` and `delta_paid`, an optional `memo` that must be a string when present, and an optional `settles_claim` flag that only matters on a `PAYMENT` entry and defaults to false. Only `REVISION` and `PAYMENT` may be appended by hand — `INITIAL_CASE` and `REVERSAL` rows are minted solely by triage and by voiding an advance, so submitting either of those two types as `entry_type` is an `ERR_VALIDATION` rejection. The append is written with the next per-event `sequence_no`, an `effective_utc` of the current instant, and a null `reverses_entry_id`, and the call answers HTTP 201 with the created ledger row itself in `data`. One fiscal guard applies: the claim's `case_reserve` plus the submitted `delta_case_reserve`, rounded to 2 decimal places, must be at least 0.00, otherwise the append is refused with `ERR_RESERVE_WOULD_GO_NEGATIVE` (HTTP 422). Afterwards the claim's `case_reserve` and `paid_amount`, and the event's `case_reserve_total`, `paid_total` and `incurred_total`, are recomputed, snapshots below the new high-water mark go stale, and posture is recomputed.

**The payment axis** advances off those `PAYMENT` entries. From `NONE` or from `ADVANCE_ISSUED`, a `PAYMENT` entry whose `settles_claim` flag is false moves the claim to `PARTIAL_PAID` — both source states behave identically, recomputing the claim's `paid_amount` and `case_reserve` and the event's roll-ups and staling snapshots. A `PAYMENT` entry whose `settles_claim` flag is true moves the claim to `SETTLED` from **whichever** payment status it currently holds — `NONE`, `ADVANCE_ISSUED`, `PARTIAL_PAID` and `SETTLED` all behave identically, the payment axis placing no precondition of its own on settlement: the settling entry additionally zeroes the residual reserve, its case-reserve movement being the negation of the claim's `case_reserve` at that moment and the submitted `delta_case_reserve` being discarded outright, so the reserve-negativity guard can never fire on a settling entry; the same roll-ups and staling follow. Settlement carries one extra precondition — the claim's `handling_status` must be `INSPECTED`, otherwise `ERR_CLAIM_NOT_INSPECTED` — because a carrier does not settle a file nobody has looked at.

**Issuing an advance payment** is the fast money that makes catastrophe response tolerable for policyholders. The payload names the `claim_id`, the `requested_amount` the examiner asked for (which must be greater than zero), and the `basis` for the advance, one of `ALE_MANDATE`, `STRUCTURE_PARTIAL` or `CONTENTS_PARTIAL`. The issued `amount` is computed, may be less than the amount requested, and is derived as follows — with the **rounding order pinned**, because summing first and rounding once at the end lands on different cents and is explicitly not what this rule does.

For each coverage line, in the array order supplied at intake, take the line's `estimated_damage_amount` capped at its `limit_amount`, subtract its `deductible_amount`, floor the result at zero, multiply by the line's advance percentage — 30 percent for `DWELLING`, 25 percent for `CONTENTS`, 50 percent for `ALE`, and 20 percent for `OTHER_STRUCTURES` — and **round that line to 2 decimal places immediately**. Sum the already-rounded line values to get the line-derived cap. Separately, find the governing advance mandate: among the bulletins on the claim's event with `bulletin_type` of `ADVANCE_PAYMENT_MANDATE`, `status` of `EFFECTIVE`, and a binding window containing the current instant with `effective_from` inclusive and `effective_to` exclusive, take the one with the greatest `mandated_advance_pct`, breaking ties by the earliest `created_at`; the mandate floor is the claim's `reported_loss_amount` multiplied by that percentage and rounded to 2 decimal places, or exactly 0.00 when no such bulletin exists. Multiply the line-derived cap by the tier multiplier for the claim's `triage_tier` — 1.00 for `CAT_SEVERE`, 0.85 for `COMPLEX`, 0.60 for `STANDARD`, 0.40 for `FAST_TRACK` — and round to 2 decimal places. The claim's `advance_cap` is the greater of that tiered figure and the mandate floor. The headroom is the `advance_cap` less the claim's `advance_paid_total`, rounded to 2 decimal places; if the headroom is 0.00 or less the issuance is refused with `ERR_ADVANCE_CAP_EXCEEDED` (HTTP 422) — the exact-zero-headroom case is a rejection, not a zero-dollar payment. A claim that has not been triaged has no `triage_tier` to multiply by, so its `advance_cap` reads exactly 0.00 on every read regardless of its coverage lines or of any mandate in force, and an advance against it is refused by that same headroom gate. Otherwise the issued `amount` is the lesser of the `requested_amount` and the headroom. Only the coverage lines present on the claim at issuance time participate, and `advance_paid_total` counts only advances whose `status` is `ISSUED`, so a voided advance does not consume cap — which is exactly what makes issue-then-void-then-reissue land on the same figure.

Issuance creates the advance in `ISSUED`, refreshes the claim's `advance_cap`, and appends a `PAYMENT` ledger entry whose paid movement is the issued `amount` and whose case-reserve movement is the negation of that amount, recording that row's identifier in the advance's `reserve_entry_id`. The claim moves `NONE → ADVANCE_ISSUED` on the payment axis and, when `advance_issuing_examiner_user_id` was previously null, the acting `X-User-ID` is recorded there as the segregation-of-duties anchor that will later block this same user from closing the claim. The claim's `advance_paid_total`, `paid_amount` and `case_reserve` and the event's `paid_total` and `case_reserve_total` are all recomputed — but the event's `incurred_total` is **unchanged**, because the two movements on the entry are equal and opposite. Snapshots below the new sequence high-water go stale and posture is recomputed.

**Voiding an advance** is the compensating action, and it fires a four-link cascade. Three preconditions guard it: the advance's `status` must be `ISSUED` (`ERR_ADVANCE_NOT_ISSUED`); the claim's `payment_status` must not be `SETTLED` (`ERR_CLAIM_ALREADY_SETTLED`); and the void must not drop the claim's `advance_paid_total` below the mandated floor of any `EFFECTIVE` `ADVANCE_PAYMENT_MANDATE` bulletin covering the current instant, so the void is permitted either when no such mandate is in force or when the remaining advanced total still satisfies the floor (`ERR_ADVANCE_MANDATE_FLOOR`, HTTP 409). A `void_reason` is recorded from the payload, where it is a **required** non-empty string validated ahead of all three preconditions — omitted, blank or non-string, the answer is `ERR_VALIDATION`. Link one moves the advance `ISSUED → VOIDED` and stamps `voided_at_utc` at the current instant. Link two, caused by link one, appends a `REVERSAL` ledger entry whose `reverses_entry_id` points at the advance's `reserve_entry_id`, whose paid movement is the negation of the issued `amount`, and whose case-reserve movement is the positive `amount`, taking the next per-event `sequence_no`; the event's `incurred_total` is therefore again unchanged. Link two-b, caused by link two, moves the claim `ADVANCE_ISSUED → NONE` on the payment axis when `advance_paid_total` returns to exactly 0.00 — and `advance_issuing_examiner_user_id` is **retained**, because a void does not erase the fact that this user once released money on the file. Link three, caused by link two raising the event's ledger high-water mark, flips every loss-estimate snapshot on the claim's event whose `input_reserve_sequence_high_water` is below the new `sequence_no` from non-stale to stale. Link four, caused by link three staling the latest snapshot, recomputes the event's posture, which may flip it from `OPEN` to `RESTRICTED` — three strain points arrive purely from the estimate going stale. `VOIDED` is terminal.

**Loss-estimate snapshots** are the event-level view of ultimate loss, minted by a `CatastropheManager`. The payload names the `event_id`, the `method`, and `expected_event_version` carrying the client's last observed event `version`; a mismatch is `ERR_STALE_EVENT_VERSION` (HTTP 412) and nothing is created. Both methods share a common base: the `reported_component` is the event's `incurred_total`, that is its `case_reserve_total` plus its `paid_total`. They differ in the `ibnr_component` — the incurred-but-not-reported loading — and the `gross_estimate` is the rounded sum of the two components to 2 decimal places. Every ledger row for the event participates with no status filter, since entries are append-only and a void is represented by a reversal row that also participates; where replay order matters it is `sequence_no` ascending, which is unique per event and needs no tie-break.

The `EXPOSURE_BASED` method is the catastrophe-modelling view used before enough claims have developed, and it ignores how many claims have actually reported. Multiply the event's `exposure_count` by its `avg_insured_value`, by its `expected_severity_index`, and by the peril development factor — 1.40 for `HURRICANE`, 1.55 for `WILDFIRE`, 1.65 for `FLOOD`, 1.20 for `HAIL`, 1.10 for `WINTER_STORM`, 1.80 for `EARTHQUAKE` — to obtain the modelled ultimate. The `ibnr_component` is that modelled figure less the `reported_component`, floored at 0.00 and rounded to 2 decimal places.

The `INCURRED_DEVELOPMENT` method is the chronological view that develops observed reserves forward. Count the distinct claims among the event's `INITIAL_CASE` ledger entries to get the reported claim count. Divide the `reported_component` by that count — or by 1 when the count is zero — to get the average incurred per reported claim. Separately, multiply the event's `exposure_count` by its `expected_severity_index` by a report rate of 35 percent and round the product **up** to the next whole number to get the ultimate claim count; this ceiling is taken on the exact value, never via a floating-point shortcut. The `ibnr_component` is the average incurred per claim multiplied by the ultimate claim count less the reported claim count (with that difference floored at zero), the whole product floored at 0.00 and rounded to 2 decimal places. For identical stored inputs this yields a different `gross_estimate` from the exposure-based method whenever the observed average severity per reported claim differs from the modelled per-risk severity.

Each snapshot records `input_reserve_sequence_high_water`, the greatest ledger `sequence_no` on the event at snapshot time, or 0 when the event had no entries, and `computed_at_utc` at the current logical-clock instant, and is born non-stale. Its `stale` flag is a computed property re-evaluated on every read: it reads true exactly when a ledger entry exists on the event whose `sequence_no` is greater than the snapshot's recorded high-water mark. Minting a snapshot refreshes the event's `gross_loss_estimate` and recomputes posture. Snapshot lists may be filtered by `event_id`, by `method` and by `stale`, and are returned in `computed_at_utc` ascending order.
### 3.9. Work That Leaves the Catastrophe Team: Vendor Dispatch and File Transfer

**Registering a firm.** A `VendorCoordinator` puts a mitigation or contractor firm on the panel by supplying its `firm_name`, which must be unique across the whole network (a repeat is `ERR_VENDOR_NAME_TAKEN`); its `vendor_type`, one of `MITIGATION`, `TARP`, `TREE_REMOVAL` or `CONTRACTOR`; `service_states`, the array of two-letter uppercase codes it is licensed to work in, which must carry at least one entry; `max_concurrent_jobs`, its concurrency ceiling from 1 through 200 inclusive; and `performance_score`, the network scorecard from 0 through 100 inclusive carried to 2 decimal places, which is the ranking key the vendor selector sorts on. A registered firm sits in `NETWORK_INACTIVE` with `activated_for_event_id` null and `open_job_count` of zero. `open_job_count` is never stored: it is derived on every read as the number of the firm's vendor assignments currently in `DISPATCHED` or `ACCEPTED` — that pair is the firm's open population — so a firm with no assignments reads zero. Firms may be listed filtered by `activated_for_event_id`, `vendor_type`, `status` and `service_state`.

**Activation** moves a firm `NETWORK_INACTIVE → ACTIVATED` against a named `event_id`, which is stored in `activated_for_event_id`. The firm must be `NETWORK_INACTIVE` (`ERR_VENDOR_NOT_INACTIVE`), the target event must be `DECLARED` or `SURGE_ACTIVE` (`ERR_EVENT_NOT_DECLARED`), and the event's `jurisdiction_state` must appear in the firm's `service_states` (`ERR_VENDOR_NOT_LICENSED_IN_STATE`, HTTP 422). A firm is activated onto one event at a time. Occupancy then drives the firm automatically: when a job acceptance drives `open_job_count` to exactly `max_concurrent_jobs`, the firm moves `ACTIVATED → CAPACITY_HOLD`; when a job leaves the open population and `open_job_count` falls back below the ceiling, the firm moves `CAPACITY_HOLD → ACTIVATED`. That cycle may repeat indefinitely. When the parent event closes from `DEMOBILIZING`, every firm activated onto it moves `ACTIVATED → NETWORK_INACTIVE` and its `activated_for_event_id` is cleared.

**Suspension** is available from `ACTIVATED`, `CAPACITY_HOLD` or `NETWORK_INACTIVE`, and a firm already `SUSPENDED` is refused with `ERR_VENDOR_NOT_SUSPENDABLE`. From `ACTIVATED` and from `CAPACITY_HOLD` the effects are identical: `activated_for_event_id` is cleared and every vendor assignment of the firm still in `DISPATCHED` is cancelled, with `open_job_count` recomputed. From `NETWORK_INACTIVE` there is nothing to unwind, so suspension has no further effect. `SUSPENDED` is terminal — a suspended firm never returns to the panel.

**Dispatching work** is a `ClaimsExaminer` action, since it is the claim that needs a tarp on its roof. The payload names the `claim_id`, the `scope_amount` of authorised work in whole dollars (greater than zero), and the `required_vendor_type` the job calls for. `vendor_firm_id` is optional: supply it to dispatch to a specific firm, or omit it to let the selector choose. The selector's eligibility filter admits a firm only when its `status` is `ACTIVATED` — `NETWORK_INACTIVE`, `CAPACITY_HOLD` and `SUSPENDED` firms are excluded even when they have spare capacity — and its `activated_for_event_id` matches the claim's event, and the claim's `loss_state` appears in the firm's `service_states`, and its `open_job_count` is strictly below its `max_concurrent_jobs`, and its `vendor_type` equals the requested `required_vendor_type`. Survivors are ranked by `performance_score` descending, comparing stored two-decimal values exactly; ties are broken by the greatest spare capacity, meaning `max_concurrent_jobs` less `open_job_count`, and remaining ties by the earliest `created_at`, never by identifier. The first row is taken. An empty candidate pool is `ERR_NO_ELIGIBLE_VENDOR` (HTTP 409) and nothing is created. When the firm was **pinned** by identifier, those same two conditions are checked directly and named: its `service_states` must contain the claim's `loss_state` (`ERR_VENDOR_NOT_LICENSED_IN_STATE`) and its `open_job_count` must be strictly below `max_concurrent_jobs` (`ERR_VENDOR_CAPACITY_EXCEEDED`); when the firm was chosen by the selector the eligibility filter has already guaranteed both, so neither error can arise on that path and an unsatisfiable request surfaces as the empty-pool rejection instead. A created assignment is `DISPATCHED`, stamps `dispatched_at_utc` at the current logical-clock instant, records `EXPLICIT_VENDOR` or `SELECTOR_RANKED` in `selection_reason`, and triggers a recompute of the firm's `open_job_count` — the new job joins the open population immediately, but the dispatch itself never moves the firm's own `status`, so a firm whose ceiling is filled by a dispatch alone stays `ACTIVATED`. Vendor assignment lists may be filtered by `claim_id`, `vendor_firm_id`, `status` and `required_vendor_type`.

The dispatched firm — acting as `VendorCoordinator` with `X-User-ID` equal to the assignment's `vendor_firm_id`, or else `ERR_NOT_ASSIGNED_VENDOR` — then responds. **Accepting** moves the assignment `DISPATCHED → ACCEPTED`; the assignment must be `DISPATCHED` (`ERR_VENDOR_ASSIGNMENT_NOT_DISPATCHED`), the firm's own `status` must be `ACTIVATED` and not `CAPACITY_HOLD` or `SUSPENDED` (`ERR_VENDOR_NOT_ACTIVATED`), and its `open_job_count` must leave room for this job — because the assignment being accepted is already `DISPATCHED` and so already inside the open population, the ceiling here is measured against the firm's *other* open jobs, meaning `open_job_count` less one must be strictly below `max_concurrent_jobs` (`ERR_VENDOR_CAPACITY_EXCEEDED`); the firm's `open_job_count` is then recomputed, taking it `ACTIVATED → CAPACITY_HOLD` when the count reaches the ceiling, so an acceptance that consumes the last slot does hold the firm rather than being refused. **Declining** moves it `DISPATCHED → DECLINED` under the same dispatched-status and ownership checks, and recomputes `open_job_count`. **Completing** moves it `ACCEPTED → COMPLETED`; from any other status the answer is `ERR_VENDOR_ASSIGNMENT_NOT_ACCEPTED`; `open_job_count` is recomputed and the firm returns `CAPACITY_HOLD → ACTIVATED` when the count falls below the ceiling. **Cancelling** belongs to the `ClaimsExaminer` rather than the firm, is available from `DISPATCHED` or `ACCEPTED` (`ERR_VENDOR_ASSIGNMENT_NOT_CANCELLABLE` otherwise), and is the examiner's route to unblocking a claim closure that `ERR_VENDOR_JOB_OPEN` is holding up; from `DISPATCHED` it simply recomputes `open_job_count`, and from `ACCEPTED` it also returns the firm `CAPACITY_HOLD → ACTIVATED` when the count falls below the ceiling. `COMPLETED`, `DECLINED` and `CANCELLED` are terminal. The system also cancels dispatched assignments on its own initiative when their firm is suspended.

**Handing files back to routine handling** is the last act of a catastrophe response. A `ClaimsExaminer` opens a batch by naming the `event_id` being wound down and the `target_unit`, the receiving routine-handling unit code. A new batch is `OPEN` with `claim_count` and `blocking_claim_count` of zero and `rejection_reason` null; batches may be listed filtered by `event_id` and `status`. Adding a claim to an open batch takes the `claim_id` in the payload and sets that claim's `transfer_batch_id`, then recomputes the batch's two counts and increments the claim's `version`; the call answers HTTP 200 with the **batch** in `data`, not the claim, and the batch's own `version` does not move, since nothing on the batch record itself changed. Three conditions apply in this order: the batch must be `OPEN` (`ERR_BATCH_NOT_OPEN`), the claim must be `CLOSED` (`ERR_CLAIM_NOT_TRANSFERABLE`), and the claim must belong to the same event as the batch (`ERR_EVENT_SCOPE_MISMATCH`). `claim_count` is simply the number of claims pointing at the batch; `blocking_claim_count` is the number of those whose `payment_status` is `ADVANCE_ISSUED` **or** whose `case_reserve` is exactly zero — the first because money is still out on the file, the second because a file carrying no reserve at all is a bookkeeping error the receiving unit will not accept.

**Submitting** the batch moves it `OPEN → SUBMITTED` and hands every member claim over. The batch must be `OPEN` (`ERR_BATCH_NOT_OPEN`); the parent event must be in `DEMOBILIZING` (`ERR_EVENT_NOT_DEMOBILIZING`), since file transfer is a wind-down activity; `claim_count` must be at least 1, so an empty batch is refused with `ERR_BATCH_EMPTY` (HTTP 422); and `blocking_claim_count` must be exactly zero, otherwise `ERR_BATCH_HAS_BLOCKING_CLAIMS` (HTTP 409). Submission stamps `submitted_at_utc` at the current instant, records the submitting `X-User-ID` for the later segregation-of-duties check, moves every member claim `CLOSED → TRANSFERRED` — a member found in any other handling status, or whose `transfer_batch_id` no longer points at this batch, makes the submission fail with `ERR_CLAIM_NOT_TRANSFERABLE` — and recomputes the event's `open_claim_count` and posture. `TRANSFERRED` is terminal for a claim.

**Acceptance** by a `CatastropheManager` moves the batch `SUBMITTED → ACCEPTED` and is the gate the event's own closure waits on. The batch must be `SUBMITTED` (`ERR_BATCH_NOT_SUBMITTED`), and the accepting `X-User-ID` must differ from the `X-User-ID` recorded at submission (`ERR_SEGREGATION_OF_DUTIES`, HTTP 403) — nobody signs off their own hand-off. `ACCEPTED` is terminal. **Rejection**, also a manager action from `SUBMITTED`, requires a `rejection_reason` that is present and non-empty (`ERR_REJECTION_REASON_REQUIRED`, HTTP 422) and tests it **before** the batch's own status, so a missing reason on a batch that is not `SUBMITTED` answers the reason error rather than `ERR_BATCH_NOT_SUBMITTED`; it records the reason, moves the batch to `REJECTED`, returns every member claim `TRANSFERRED → CLOSED`, and recomputes the event's `open_claim_count` and posture. A rejected batch is not dead: the examiner returns it `REJECTED → OPEN` (`ERR_BATCH_NOT_REJECTED` from any other status), which clears `rejection_reason` back to null so the membership can be corrected and resubmitted — the cycle `OPEN → SUBMITTED → REJECTED → OPEN`.
