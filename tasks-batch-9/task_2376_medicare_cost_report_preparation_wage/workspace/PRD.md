# Medicare Cost Report Wage Index API — Product Requirements Document

## 1. Introduction

A hospital reimbursement department lives inside a paradox. The Medicare cost report is an accounting artifact — a trial balance folded into worksheet cost centers, overhead stepped down through statistical allocation bases, a Medicare share applied to the reimbursable pool — but it is also a regulatory filing with a hard calendar, an adversarial review by a Medicare administrative contractor, and an appeal path that can reopen a settlement three years after the money changed hands. Today most departments run this process across a spreadsheet workbook, an email thread with the contractor's audit team, and a shared drive of workpaper PDFs. Nobody can answer, on demand, whether the numbers in the filed report still reflect the current cost center structure, or which of eleven statistical bases a given overhead pool was distributed on, or whether a resident rotation was double-counted against two teaching cost centers.

This API replaces that workbook. It models the cost report as a single aggregate with two independent lifecycles running side by side: a filing-and-settlement lifecycle that carries the report from preparation through tentative and final settlement, and a wage-index-review lifecycle that cycles the S-3 wage data through contractor desk review however many times the contractor asks. Beneath the report sit the accounting objects — cost centers, trial balance lines, reclassification and adjustment workpapers, stepdown runs — plus the wage index submission with its occupational mix survey, the graduate medical education resident and rotation records, and the disproportionate share and uncompensated care data set. Above it sit the contractor's settlements, audit adjustments, reopening requests and Provider Reimbursement Review Board appeals, and the interim payment rate requests that price the next period off the last settled one.

Two design commitments shape almost every rule that follows. First, **derived cost is never trusted stale**: any change to a cost center, a workpaper entry or a mapped ledger line invalidates the allocation that was computed from it, and the report refuses to file or settle until the allocation has been re-run. Second, **preparation is separated from attestation and from audit**: the analyst who builds the workpapers cannot file the report, the officer who files it cannot issue the settlement, and the contractor auditor who proposes an audit exception cannot be the one who resolves it. Both commitments are enforced by the server, not by convention, because in a reimbursement dispute the audit trail is the product.

## 2. Global Specifications & System-Wide Principles

This section defines the contract-level rules that hold across every endpoint: authentication, response shape, pagination, identity and version semantics, the logical clock, the freshness cascades, concurrency control, rounding discipline, and the order in which validations are evaluated.

### 2.1. User and Role-Based Access Control

Every request must carry the `X-User-Role` header naming the caller's operational capacity. A request with no `X-User-Role` header, or with a value that is not one of the five recognized role names, is rejected with `ERR_UNAUTHENTICATED` (HTTP 401). The five roles are `SystemAdmin`, `ReimbursementAnalyst`, `ReimbursementManager`, `MacAuditor` and `ReviewBoardClerk`. Each endpoint publishes the set of roles permitted to invoke it (see §4); a recognized role that is not in that set receives `ERR_FORBIDDEN_ROLE` (HTTP 403).

The companion header `X-User-ID` carries the caller's identity, and what that identifier *means* depends on the role:

- When `X-User-Role` is `ReimbursementAnalyst`, `X-User-ID` is the `id` of the acting `Provider` — the hospital the analyst prepares reports for. The header is optional for this role; when it is supplied, ownership checks on any target resource compare the `Provider` that ultimately owns that resource (a cost report's `provider_id`, a cost center's owning report, a resident's `provider_id`, and so on) against `X-User-ID`, and a mismatch is rejected with `ERR_PROVIDER_SCOPE_VIOLATION` (HTTP 403). When the header is absent, this check does not fire at all.
- When `X-User-Role` is `ReimbursementManager`, `X-User-ID` is likewise the `id` of the acting `Provider`, optional in the same way, and subject to the same `ERR_PROVIDER_SCOPE_VIOLATION` comparison against the owning provider of the target resource.
- When `X-User-Role` is `SystemAdmin`, `X-User-ID` is an opaque platform-operator identifier not tied to any persisted entity. The server does not compare it to any entity's `id`.
- When `X-User-Role` is `MacAuditor`, `X-User-ID` is an opaque contractor-auditor identifier not tied to any persisted entity. It is **required** when proposing an audit adjustment and when resolving one, because the server records it (as `proposed_by_user_id` at proposal time and `resolved_by_user_id` at resolution time on the `AuditAdjustment`) and compares the two values to enforce segregation of duties. It is never compared to any entity's `id`.
- When `X-User-Role` is `ReviewBoardClerk`, `X-User-ID` is an opaque review-board identifier not tied to any persisted entity. The server may record it in no field; it exists only to attribute the call.

The role split is a segregation-of-duties control, not a convenience. A `ReimbursementAnalyst` prepares: cost centers, trial balance loading and mapping, workpaper entries and their reversal, wage index data collection and occupational mix responses, residents and rotation assignments, and the uncompensated care data set. A `ReimbursementManager` attests and disputes: submitting the wage data, filing the report, responding to an audit adjustment, opening an appeal case, and requesting an interim rate adjustment. Neither role may perform the other's exclusive operations — an analyst attempting to file, or a manager attempting to load a trial balance line, receives `ERR_FORBIDDEN_ROLE`. A `MacAuditor` reviews and settles: desk review of the wage submission, issuance of settlements, proposal and resolution of audit adjustments, granting or denying reopenings, and deciding interim rate requests. Analysts and auditors both may trigger a stepdown run and a recompute of the uncompensated care figures. A `ReviewBoardClerk` is deliberately near-blind: it may read appeal cases and settlements and record board hearings and board decisions, and nothing else — a clerk reading a cost report receives `ERR_FORBIDDEN_ROLE`. Finally, within the contractor's own staff, the auditor who proposed an audit adjustment may not resolve it; a resolution request whose `X-User-ID` equals the adjustment's `proposed_by_user_id` is rejected with `ERR_SEGREGATION_OF_DUTIES` (HTTP 403).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and List Filtering

List endpoints are paginated through two query parameters. `limit` caps the number of rows returned; it defaults to 10, may not be smaller than 1, and may not be larger than 100. `offset` is the number of rows to skip before the window begins; it defaults to 0 and may not be negative. A `limit` outside the inclusive range 1 through 100, or a non-integer value for either parameter, is a schema failure and is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

Unless a specific endpoint says otherwise, every list is sorted by `created_at` in ascending order — oldest first. The response envelope's `meta` object carries `limit`, `offset`, `total_count` (the number of rows matching the filter before the window is applied) and `has_more` (whether rows remain beyond the current window).

Most list endpoints also accept equality filters drawn from the listed entity's own fields, and those filters are how a client traverses a relationship backwards. Providers may be filtered by `ccn`, `cbsa_code` and `teaching_status`. Cost reports may be filtered by `provider_id`, `status`, `wage_data_status` and `allocation_status`. A report's cost centers may be narrowed by `center_type`, its trial balance lines and its stepdown runs by `status`, its stepdown runs also by `method`, its workpaper entries by `entry_type`, `status` and `source`, and its wage index submissions and settlements by `status` (settlements additionally by `stage`). Occupational mix responses may be filtered by `category`; residents by `irp_status`; rotation assignments by `resident_id`, `cost_center_id` and `status`; audit adjustments by `settlement_id`, `target_cost_center_id` and `status`; appeal cases by `cost_report_id`, `settlement_id`, `kind` and `status`; and interim rate requests by `provider_id`, `basis_cost_report_id` and `status`. An unrecognized enum value supplied to any of these filters is an `ERR_INVALID_REQUEST`.

### 2.4. Common Resource Properties and the Version Counter

Every persisted resource in this system — `Provider`, `CostReport`, `CostCenter`, `TrialBalanceLine`, `WorkpaperEntry`, `StepdownRun`, `WageIndexSubmission`, `OccMixResponse`, `Resident`, `RotationAssignment`, `UccDataSet`, `Settlement`, `AuditAdjustment`, `AppealCase` and `InterimRateRequest` — carries the same four system-managed properties:

- **`id`** (string): a server-minted UUID. It carries no type prefix and is never supplied by the client.
- **`created_at`** (string): an ISO 8601 UTC timestamp with three fractional digits, stamped when the row is first written.
- **`updated_at`** (string): an ISO 8601 UTC timestamp in the same format, refreshed on every mutation of the row, including mutations of purely derived fields.
- **`version`** (integer): a monotonically increasing counter that begins at 1 and increments by one on every mutation of the row. There is no entity in this system that omits `updated_at` or `version`.

The `version` counter is not decorative: a recomputation of a derived total *is* a mutation. When a stepdown run rewrites a cost center's allocated figures, that cost center's `updated_at` and `version` both advance. When the same run recomputes the report's `total_allowable_cost_cents`, the `CostReport` row's `version` advances too. Because two of the write endpoints in this system are guarded by optimistic concurrency against exactly those counters (§2.8), a client that reads a report, then triggers any intervening derived-field recomputation, must re-read before it writes.

### 2.5. The Logical Clock and Calendar Arithmetic

Every deadline, window and issuance timestamp in this system is measured against a **logical clock** rather than wall-clock time, so that a filing deadline, a 180-day appeal window and a three-year reopening window are all reachable in a test. A `SystemAdmin` may set the clock by supplying a `current_utc` instant; any authenticated role may read it. On a fresh database the clock reads `2026-08-01T00:00:00Z`. The clock is the source for `filed_at`, `reversed_at`, `completed_at`, `issued_at`, `decided_at` and for every date comparison described below.

Date-typed fields (`fiscal_year_begin`, `fiscal_year_end`, `filing_deadline`, `start_date`, `end_date`, `effective_from`, `effective_to`) are calendar dates in `YYYY-MM-DD` form, and every comparison involving them is performed on whole calendar dates in UTC — the time-of-day part of the logical clock is discarded for these comparisons. Two interval conventions are used and they are not interchangeable. Rotation intervals and the cost reporting period are **half-open**: `[start_date, end_date)` includes the start day and excludes the end day, so two rotations where one's `end_date` equals the other's `start_date` do not overlap. Interim rate periods are **closed**: `[effective_from, effective_to]` includes both endpoints.

### 2.6. The Two State Dimensions of a Cost Report

A `CostReport` row carries two independent lifecycle dimensions plus a freshness flag, and conflating them is the single most common modelling mistake in this domain.

The **filing and settlement dimension** is `status`, which begins at `DRAFT` and takes one of `DRAFT`, `FILED`, `TENTATIVE_SETTLED`, `FINAL_SETTLED`, `REOPENED`, `AMENDED_FILED` or `CLOSED`. `CLOSED` is the only terminal value. This dimension is driven exclusively by filing, settlement and appeal-decision actions.

The **wage index data dimension** is `wage_data_status`, which begins at `NOT_STARTED` and takes one of `NOT_STARTED`, `COLLECTED`, `UNDER_REVIEW`, `VERIFIED`, `REVISION_REQUESTED` or `REJECTED`. This dimension is driven *only* by the transitions of the report's `WageIndexSubmission`, and never by a `status` transition. The two dimensions interleave freely: a report may already be `FILED` on the `status` axis while a later desk review pushes `wage_data_status` back to `UNDER_REVIEW` and then to `REVISION_REQUESTED`. Combinations such as `FILED` paired with `REVISION_REQUESTED` are legitimate reachable states, and neither of them rolls the `status` axis backwards.

The third field, `allocation_status`, is not a lifecycle but a freshness marker on the overhead allocation. It begins at `NOT_RUN` and thereafter reads `CURRENT` or `STALE` (§2.7).

Editability of the accounting tree is governed by `status` alone. The report's accounting children may only be created, mapped, revised, reversed or voided while `status` is `DRAFT` or `REOPENED`; in any other status the attempt is rejected with `ERR_COST_REPORT_NOT_EDITABLE` (HTTP 409). This gate guards eleven operations: creating a cost center, revising a cost center, loading a trial balance line, mapping a trial balance line, creating a workpaper entry, reversing a workpaper entry, creating a rotation assignment, voiding a rotation assignment, opening a wage index submission, correcting a wage index submission's hours and salary figures, and creating the uncompensated care data set. Note the deliberate exception: when the contractor resolves an audit adjustment by incorporating it, the server synthesizes a workpaper entry *even though the report is not `DRAFT` or `REOPENED`*, because that write originates on the contractor's side of the wall and is not a provider edit.

### 2.7. Allocation Freshness and the Recompute Cascades

The overhead allocation is the hinge of the whole report, and it is treated as a cached derivation that any upstream change invalidates. Whenever a stepdown run reaches `COMPLETED`, `allocation_status` becomes `CURRENT` and exactly one `COMPLETED` `StepdownRun` exists for the report. Whenever any input to that allocation changes, the run is demoted to `STALE`, its `stale_reason` records why, and `allocation_status` becomes `STALE` unless a newer `COMPLETED` run already exists. The three reasons are `SUPERSEDED_BY_NEWER_RUN` (a later run completed), `COST_CENTER_INPUT_CHANGED` (a cost center was revised, or the report was reopened) and `WORKPAPER_ENTRY_CHANGED` (a workpaper entry was created or reversed, including one synthesized by an incorporated audit adjustment).

Three cascades in this system reach across more than one entity, and each link must fire:

**The completed-stepdown cascade (four links).** Link one writes each cost center's `allocated_in_cents`, `allocated_out_cents` and `allocated_total_cost_cents`. Link two recomputes the report's `total_allowable_cost_cents` and `cost_to_charge_ratio` and sets `allocation_status` to `CURRENT`. Link three, driven by the new `cost_to_charge_ratio`, recomputes the report's `UccDataSet` — its snapshot `cost_to_charge_ratio`, its `uncompensated_care_cost_cents` and its `ucc_payment_cents` — and clears that data set's `recompute_required` back to false. Link four, driven by that data set recompute, sets `recompute_required` to true on every `Settlement` of the report whose `status` is `ISSUED` and whose `basis_allowable_cost_cents` no longer equals the newly computed `total_allowable_cost_cents`. The run additionally demotes any previously `COMPLETED` run of the report to `STALE` with `stale_reason` `SUPERSEDED_BY_NEWER_RUN`, and increments the report's `version`.

**The incorporated-audit-adjustment cascade (five links).** Link one creates a workpaper entry of type `ADJUSTMENT` with `source` `AUDIT`, its `source_audit_adjustment_id` pointing back at the adjustment and a single leg placing the proposed amount on the adjustment's target cost center. Link two updates that cost center's `adjustment_amount_cents` and `post_adjustment_cost_cents`. Link three demotes every `COMPLETED` stepdown run of the report to `STALE` with `stale_reason` `WORKPAPER_ENTRY_CHANGED`. Link four sets the report's `allocation_status` to `STALE`. Link five sets `recompute_required` to true on every `Settlement` of the report whose `status` is `ISSUED` or `APPEALED`. The report's `version` is incremented.

**The reopening cascade (four links).** Link one sets the appeal case to its granted or provider-favourable state. Link two, driven by that appeal-case change, sets the referenced `FINAL` settlement's `status` to `RESETTLED`. Link three, driven by the settlement becoming `RESETTLED`, sets the report's `status` to `REOPENED` and its `allocation_status` to `STALE`. Link four, driven by `allocation_status` becoming `STALE`, sets every `COMPLETED` stepdown run of the report to `STALE` with `stale_reason` `COST_CENTER_INPUT_CHANGED`. The report's `version` is incremented.

Because a `STALE` allocation blocks both filing and settlement, the practical effect of all three cascades is the same: after any of them, the report must be re-stepped before it can move forward again.

### 2.8. Optimistic Concurrency on Cost Reports and Providers

Two write operations in this system are guarded by optimistic concurrency control, and only those two. Both take a non-optional version token in the request body; every other endpoint takes no version field at all and performs no version check.

**Triggering a stepdown run** requires `expected_cost_report_version` in the body, carrying the `version` of the target `CostReport` as the client last observed it. If that value does not equal the report's current `version`, the request is rejected with `ERR_STALE_COST_REPORT_VERSION` and HTTP 412, and nothing is written. The guard exists because a new run legitimately supersedes the prior `COMPLETED` run and demotes it to `STALE`: a request built on a version the client no longer holds would silently discard an allocation the client never saw.

**Creating an interim rate request** requires `expected_provider_version` in the body, carrying the `version` of the target `Provider` as the client last observed it. If that value does not equal the provider's current `version`, the request is rejected with `ERR_STALE_PROVIDER_VERSION` and HTTP 412. The guard exists because a new request supersedes the provider's outstanding `PENDING` request and is priced directly off `current_interim_rate_cents`: a stale view of the provider would price the projection against a rate that no longer holds.

### 2.9. Cents, Fractions and Rounding Discipline

Money is integer cents everywhere in this system. No monetary field is a decimal number, and aggregating cents therefore needs no rounding at all — `direct_cost_cents`, `total_direct_cost_cents`, `post_adjustment_cost_cents` and their kin are exact sums. Rounding only enters where a ratio, a percentage or a weight is applied, and where it does, the rule is **round half up** unless the text explicitly says the value is floored or truncated.

The concrete precisions are as follows. Ratios of cost to charges (`cost_to_charge_ratio` on both the report and the uncompensated care data set) carry six decimal places. Patient-day fractions and percentages (`medicaid_fraction`, `ssi_fraction`, `dsh_patient_percentage`), the Medicare share (`medicare_utilization_ratio`), the inflation input (`trend_factor`), the projection variance (`variance_ratio`), a rotation's `fte_fraction` and a rotation's `fte_days` all carry four decimal places. Report-level full-time-equivalent totals (`unweighted_fte_total`, `capped_unweighted_fte`, `weighted_fte_total`, `rolling_average_fte`) and a provider's `fte_cap` carry two decimal places. Hour figures (`total_paid_hours`, `contract_labor_hours`, `excluded_area_hours`, `reported_hours`, `reported_hours_total`) carry two decimal places. Occupational mix category weights are rounded to six decimal places. Hourly wages (`unadjusted_ahw_cents`, `occ_mix_adjusted_ahw_cents`, `effective_ahw_cents`, `category_ahw_cents`) are whole cents.

Three places deliberately floor rather than round, and they are the ones implementers most often get wrong: the cap on wage-related costs, the per-receiver share inside a stepdown distribution, and both the uncompensated care payment and the interim rate cap. Each is called out where it occurs.

### 2.10. Path Resolution and the Validation Precedence Ladder

When a path contains more than one identifier, identifiers are resolved strictly left to right, and the first one that does not resolve decides the 404. A request naming a cost report that does not exist fails with `ERR_COST_REPORT_NOT_FOUND` before the server ever looks at the child identifier. The per-entity 404 codes are `ERR_PROVIDER_NOT_FOUND`, `ERR_COST_REPORT_NOT_FOUND`, `ERR_COST_CENTER_NOT_FOUND`, `ERR_TRIAL_BALANCE_LINE_NOT_FOUND`, `ERR_WORKPAPER_ENTRY_NOT_FOUND`, `ERR_STEPDOWN_RUN_NOT_FOUND`, `ERR_WAGE_INDEX_SUBMISSION_NOT_FOUND`, `ERR_OCC_MIX_RESPONSE_NOT_FOUND`, `ERR_RESIDENT_NOT_FOUND`, `ERR_ROTATION_ASSIGNMENT_NOT_FOUND`, `ERR_UCC_DATA_SET_NOT_FOUND`, `ERR_SETTLEMENT_NOT_FOUND`, `ERR_AUDIT_ADJUSTMENT_NOT_FOUND`, `ERR_APPEAL_CASE_NOT_FOUND` and `ERR_INTERIM_RATE_REQUEST_NOT_FOUND`. A foreign key supplied in a request *body* that does not resolve produces the generic `ERR_REFERENCED_ENTITY_NOT_FOUND` (HTTP 404) instead; this applies when opening a cost report, mapping a trial balance line, creating a workpaper entry, creating a rotation assignment, proposing an audit adjustment, opening an appeal case, and creating an interim rate request.

All validation on a request is evaluated in a strict ascending priority order, and **the first violated rule decides the response; nothing is written**. Two rules sharing a priority band are mutually exclusive in practice — no single endpoint can violate both. The ladder is:

1. **Authentication** — a recognized `X-User-Role` header is present, else `ERR_UNAUTHENTICATED` (401). Applies to every endpoint.
2. **Authorization by role** — the caller's role appears in the endpoint's permitted set, else `ERR_FORBIDDEN_ROLE` (403). Applies to every endpoint.
3. **Schema** — the payload parses, every required input field is present, and every field satisfies its declared type, enum membership, numeric range and decimal-place constraint, else `ERR_INVALID_REQUEST` (400). Applies to every endpoint with a body or query parameters.
4. **Path existence** — every path identifier resolves to a row of the expected entity, else the matching per-entity 404 above.
5. **Referential existence in the body** — every foreign key in the body resolves, else `ERR_REFERENCED_ENTITY_NOT_FOUND` (404).
6. **Provider scope** — when a `ReimbursementAnalyst` or `ReimbursementManager` supplies `X-User-ID`, it equals the `id` of the `Provider` owning the target resource, else `ERR_PROVIDER_SCOPE_VIOLATION` (403). When the header is absent this rule does not fire.
7. **Segregation of duties** — on an audit adjustment resolution, `X-User-ID` differs from the adjustment's `proposed_by_user_id`, else `ERR_SEGREGATION_OF_DUTIES` (403).
8. **Concurrency** — `expected_cost_report_version` equals the report's `version` on a stepdown run creation, else `ERR_STALE_COST_REPORT_VERSION` (412); and `expected_provider_version` equals the provider's `version` on an interim rate request creation, else `ERR_STALE_PROVIDER_VERSION` (412).
9. **State** — the target entity is in a state from which the requested transition exists, else `ERR_INVALID_STATE_TRANSITION` (409); this covers every action (filing, wage submission, review start, review decision, settlement issuance, audit response, audit resolution, appeal decision, rotation void, workpaper reversal and ledger mapping). In the same band, the parent cost report is editable before any accounting child is created, mapped, revised, reversed or voided, else `ERR_COST_REPORT_NOT_EDITABLE` (409).
10. **Compliance windows** — the filing deadline (`ERR_FILING_DEADLINE_PASSED`, 422), the 180-day board appeal window (`ERR_APPEAL_WINDOW_EXPIRED`, 422) and the three-year reopening window (`ERR_REOPENING_WINDOW_EXPIRED`, 422).
11. **Business referential integrity** — a referenced cost center, settlement or basis report belongs to the right parent: `ERR_COST_CENTER_FOREIGN_TO_REPORT` (422) when creating a workpaper entry, when mapping a trial balance line, or when proposing an audit adjustment; `ERR_COST_CENTER_FOREIGN_TO_PROVIDER` (422) when creating a rotation assignment; `ERR_SETTLEMENT_FOREIGN_TO_REPORT` (422) when opening an appeal case; `ERR_BASIS_REPORT_FOREIGN_TO_PROVIDER` (422) when creating an interim rate request.
12. **Temporal capacity** — the resident daily full-time-equivalent cap (`ERR_RESIDENT_DAILY_FTE_EXCEEDED`, 409) and the fiscal-year intersection test (`ERR_ROTATION_OUTSIDE_FISCAL_YEAR`, 409) on rotation creation, and the interim period buffer (`ERR_INTERIM_PERIOD_OVERLAP`, 409) on interim rate request creation.
13. **Business constraints** — the large band of domain preconditions, each described beside the workflow it guards in §3: `ERR_UNMAPPED_TRIAL_BALANCE`, `ERR_ALLOCATION_NOT_CURRENT`, `ERR_WAGE_SUBMISSION_NOT_ACCEPTED`, `ERR_UCC_DATA_MISSING`, `ERR_RECLASS_NOT_BALANCED`, `ERR_NON_ALLOWABLE_MUST_BE_NEGATIVE`, `ERR_STEPDOWN_ORDER_CONFLICT`, `ERR_COST_CENTER_CODE_DUPLICATE`, `ERR_STEPDOWN_STRUCTURE_INCOMPLETE`, `ERR_OCC_MIX_HOURS_EXCEED_TOTAL`, `ERR_OCC_MIX_INCOMPLETE`, `ERR_OCC_MIX_CATEGORY_DUPLICATE`, `ERR_DUPLICATE_CHILD_RECORD`, `ERR_FINAL_REQUIRES_DOUBLE_APPORTIONMENT`, `ERR_AUDIT_ADJUSTMENT_UNRESOLVED`, `ERR_SETTLEMENT_STAGE_INVALID`, `ERR_PRRB_AMOUNT_BELOW_MINIMUM`, `ERR_BASIS_REPORT_NOT_FINAL_SETTLED` and `ERR_NO_CURRENT_INTERIM_RATE` — all 422.
14. **Fiscal viability** — the projection variance gate (`ERR_INTERIM_VARIANCE_BELOW_THRESHOLD`, 422) and the fiscal period / certification-number uniqueness test (`ERR_FISCAL_PERIOD_INVALID`, 422).

The ordering is load-bearing in several places. Because state (band 9) precedes business constraints (band 13), an attempt to file a report that is already `FILED` surfaces as `ERR_INVALID_STATE_TRANSITION`, not as whichever business precondition also happens to be unmet. Because concurrency (band 8) precedes state, a stepdown run carrying a stale report version is rejected on the version token even if the trial balance is also unmapped. And because compliance windows (band 10) precede business referential integrity (band 11), a board appeal filed after its window closes reports `ERR_APPEAL_WINDOW_EXPIRED` rather than any settlement-ownership complaint.

## 3. Business Logic & Workflows

### 3.1. Opening a Cost Report and the Filing Calendar

A hospital enters the system as a **Provider**, registered by a `SystemAdmin` with its CMS certification number `ccn` (exactly six characters, digits only, and unique across all providers), its legal `name` (between 1 and 200 characters), and the `cbsa_code` of its labor market area (exactly five characters, digits only) which is what groups it for wage index purposes. Three further inputs are optional at registration. `teaching_status` declares whether the hospital operates approved graduate medical education programs and is either `TEACHING` or `NON_TEACHING`, defaulting to `NON_TEACHING`. `fte_cap` is the provider-specific unweighted resident full-time-equivalent ceiling, a non-negative number to two decimal places defaulting to 0. `current_interim_rate_cents` is the interim payment rate per Medicare discharge in cents, a non-negative integer defaulting to 0. Two fields are never supplied: `approved_interim_period_count`, which the server maintains as the count of that provider's interim rate requests in `APPROVED` status and which starts at 0, and the provider's own `version`. Attempting to register a second provider with a certification number already in use is rejected with `ERR_FISCAL_PERIOD_INVALID`.

Opening a **CostReport** is the one creation shared between the platform operator and the hospital officer: either a `SystemAdmin` or a `ReimbursementManager` may do it, supplying the `provider_id` of the filing hospital and the two boundaries of the cost reporting period, `fiscal_year_begin` and `fiscal_year_end`. The period must be well formed — the begin date strictly earlier than the end date, and the span from begin to end no shorter than 1 day and no longer than 366 days — and a period that fails either test is rejected with `ERR_FISCAL_PERIOD_INVALID`. Four optional inputs may be seeded at creation and each has a default: `apportionment_method`, either `SINGLE_APPORTIONMENT` or `DOUBLE_APPORTIONMENT`, defaulting to `SINGLE_APPORTIONMENT`, which is the method a later stepdown run inherits when the run does not name one itself; `medicare_utilization_ratio`, the Medicare share of reimbursable cost, a value from 0.0000 through 1.0000 inclusive at four decimal places, defaulting to 0.4000; `interim_payments_received_cents`, the interim payments the contractor has already advanced for the period, a non-negative integer defaulting to 0; `total_charges_cents`, total facility charges for the period and the denominator of the cost-to-charge ratio, a non-negative integer defaulting to 0; and `medicare_discharges`, the period's Medicare discharge count and the denominator of allowable cost per discharge, a non-negative integer defaulting to 0.

At creation the server stamps `status` to `DRAFT`, `wage_data_status` to `NOT_STARTED`, `allocation_status` to `NOT_RUN`, and computes the `filing_deadline`. The deadline is the fiscal year end advanced by five calendar months, clamped to the last day of the target month when the source day-of-month does not exist there. A period ending 2026-06-30 therefore carries a deadline of 2026-11-30, and a period ending 2026-09-30 carries a deadline of 2027-02-28. All the derived cost and full-time-equivalent figures start at zero: `total_direct_cost_cents`, `unmapped_tb_total_cents`, `total_allowable_cost_cents` and `allowable_cost_per_discharge_cents` at 0, `cost_to_charge_ratio` at 0.000000, `unweighted_fte_days_total` at 0.0000, `unweighted_fte_total`, `capped_unweighted_fte`, `weighted_fte_total` and `rolling_average_fte` at 0.00, `amendment_count` at 0, and `filed_at` at null.

Filing is the `ReimbursementManager`'s act, and it is the same action twice over: from `DRAFT` it advances the report to `FILED`, and from `REOPENED` it advances the report to `AMENDED_FILED`. Both paths demand the same four readiness conditions. The report's `unmapped_tb_total_cents` must be exactly 0, else `ERR_UNMAPPED_TRIAL_BALANCE`. Its `allocation_status` must be `CURRENT`, else `ERR_ALLOCATION_NOT_CURRENT`. Its wage index submission must have reached `ACCEPTED`, equivalently `wage_data_status` must read `VERIFIED`, else `ERR_WAGE_SUBMISSION_NOT_ACCEPTED`. And exactly one uncompensated care data set must exist for the report, else `ERR_UCC_DATA_MISSING`. The two paths differ in exactly one respect: the `DRAFT` filing additionally requires that the logical clock's date fall on or before `filing_deadline`, and a later date is rejected with `ERR_FILING_DEADLINE_PASSED`; the amended filing out of `REOPENED` skips the deadline test entirely, because a reopening granted years after the fact could never satisfy the original calendar. Either filing recomputes the graduate medical education totals described in §3.6 and increments the report's `version`. The first successful filing stamps `filed_at` from the logical clock; every successful filing after the first increments `amendment_count` by one. Attempting to file from any status other than `DRAFT` or `REOPENED` is an `ERR_INVALID_STATE_TRANSITION`.

### 3.2. Worksheet A Structure: Cost Centers and Statistical Bases

A `ReimbursementAnalyst` builds the report's worksheet A skeleton as a set of **cost centers**, each belonging to the report through its `cost_report_id`. A center is created with a worksheet line `code` (exactly five characters, digits only, and unique within the report — a reused code is rejected with `ERR_COST_CENTER_CODE_DUPLICATE`), a human-readable `name`, and a `center_type` of `GENERAL_SERVICE`, `ANCILLARY`, `ROUTINE` or `NONREIMBURSABLE`. The type determines the center's role in the overhead waterfall: general service centers are overhead pools that close into the others, ancillary and routine centers are the reimbursable destinations, and nonreimbursable centers absorb cost that Medicare will not pay for.

Two inputs exist solely for general service centers and are conditional on the type. `allocation_basis` names the statistic on which that center distributes its accumulated cost and is one of `SQUARE_FEET`, `MEALS_SERVED`, `POUNDS_LAUNDRY`, `NURSING_HOURS` or `NONE`, defaulting to `NONE`. `stepdown_order` is a positive integer giving the ascending sequence in which general service centers close. At creation, a `GENERAL_SERVICE` center must supply an `allocation_basis` other than `NONE` and a `stepdown_order` that no other general service center of the report already holds, and a center of any other type must supply neither field; every violation of that shape — a missing basis, a missing order, a duplicate order, or either field present on a non-general-service center — is rejected with `ERR_STEPDOWN_ORDER_CONFLICT`.

The complementary input is `statistics`, an object recording how many base units this center *receives* on, keyed by basis name. Its keys must be a subset of `SQUARE_FEET`, `MEALS_SERVED`, `POUNDS_LAUNDRY` and `NURSING_HOURS` and its values must be numbers no less than zero; it defaults to an empty object, and an unrecognized basis key is rejected with `ERR_COST_CENTER_CODE_DUPLICATE`. A laundry pool with `allocation_basis` `POUNDS_LAUNDRY` therefore looks at each candidate receiver's `statistics` entry for `POUNDS_LAUNDRY` to decide that receiver's share, and a center with no such entry receives nothing from the laundry pool.

Every cost center carries a nine-figure cost waterfall, all of it server-computed and all of it integer cents starting at 0: `direct_cost_cents`, `reclassified_amount_cents`, `adjustment_amount_cents`, `post_reclass_direct_cost_cents`, `post_adjustment_cost_cents`, `allocated_in_cents`, `allocated_out_cents` and `allocated_total_cost_cents`. §3.3 explains the first five; §3.4 explains the last three.

Revising an existing cost center is also the analyst's privilege and accepts any subset of `name`, `allocation_basis`, `stepdown_order` and `statistics`. A revision is a deliberately looser operation than a creation, for one reason: renumbering a stepdown sequence cannot be done atomically through single-resource edits. Swapping orders 1 and 2 must pass through a moment where two general service centers both hold the same `stepdown_order`, so revision does **not** enforce `stepdown_order` uniqueness and never raises `ERR_STEPDOWN_ORDER_CONFLICT`. A stepdown attempted while such a collision stands does not fail with a validation error either — it is recorded as a `FAILED` run, as §3.4 describes. Revision does still reject a `GENERAL_SERVICE` center's `allocation_basis` being set to `NONE`, and rejects any `allocation_basis` or `stepdown_order` on a non-general-service center, both as schema failures reported as `ERR_INVALID_REQUEST`. Every revision demotes each `COMPLETED` stepdown run of the report to `STALE` with `stale_reason` `COST_CENTER_INPUT_CHANGED`, sets the report's `allocation_status` to `STALE`, and increments the report's `version`. Creating a *new* cost center while a `COMPLETED` run already exists likewise sets `allocation_status` to `STALE`.

### 3.3. The Trial Balance Ledger and Its Workpaper Adjustments

**Loading and mapping the ledger.** The hospital's general ledger arrives as **trial balance lines**, loaded one at a time by the analyst against the report identified by `cost_report_id`. A line records the ledger account number `gl_account` as the hospital filed it, a `description` label, and an `amount_cents` figure. That amount is an integer number of cents and it **may be negative** — a credit balance is a legitimate ledger line, and nothing in the mapping machinery rejects one.

A line may be loaded already mapped, by supplying `mapped_cost_center_id` at creation, or loaded unmapped by omitting it, in which case the field is null. The line's `status` is set accordingly: `MAPPED` when a cost center was supplied and `UNMAPPED` when it was not. An unmapped line can be mapped later through a dedicated mapping action that carries a `cost_center_id` in its payload and advances the line from `UNMAPPED` to `MAPPED`; mapping a line that is already `MAPPED` is an `ERR_INVALID_STATE_TRANSITION`. Whether the association is made at load time or later, the named cost center must belong to the same cost report as the line — a cost center drawn from a different report is rejected with `ERR_COST_CENTER_FOREIGN_TO_REPORT`.

Loading a line and mapping a line both trigger the same rollup, which is pure aggregation over integer cents and needs no rounding. For each cost center of the report, `direct_cost_cents` becomes the sum of `amount_cents` over the report's trial balance lines whose `mapped_cost_center_id` is that center and whose `status` is `MAPPED`. The report's `total_direct_cost_cents` becomes the sum of `direct_cost_cents` across all its cost centers, and the report's `unmapped_tb_total_cents` becomes the sum of `amount_cents` over the report's lines whose `status` is `UNMAPPED`. That last figure is the gate on both filing and stepdown: while any ledger dollar remains unassigned to a cost center, neither operation may proceed, and both reject with `ERR_UNMAPPED_TRIAL_BALANCE`. Mapping a line while a `COMPLETED` stepdown run exists sets the report's `allocation_status` to `STALE` and increments the report's `version`.

**Reclassifications and adjustments.** Between the ledger and the allocation sit the **workpaper entries** — the A-6 reclassifications that move cost between centers and the A-8 adjustments that add or remove it. An analyst creates an entry against a report with an `entry_type` of either `RECLASSIFICATION` or `ADJUSTMENT`, a workpaper reference `code`, a narrative `description` giving the basis for the entry, and a `legs` array. Each element of `legs` is an object pairing a `cost_center_id` with an `amount_cents` figure, and every named cost center must belong to the same cost report as the entry; a leg pointing at a foreign center is rejected with `ERR_COST_CENTER_FOREIGN_TO_REPORT`. No leg may carry an `amount_cents` of zero.

The two entry types have deliberately asymmetric shape rules, and both are enforced. A `RECLASSIFICATION` must have at least two legs and its leg amounts must sum to exactly zero — it moves cost, it never creates or destroys it — and an entry that has fewer than two legs or whose legs do not net to zero is rejected with `ERR_RECLASS_NOT_BALANCED`. An `ADJUSTMENT` must have exactly one leg and is exempt from the net-zero test entirely, because adding or removing cost is the whole point of an A-8 adjustment.

A fifth input, `is_non_allowable`, is a boolean defaulting to false that marks an A-8 adjustment as removing non-allowable cost. When it is set to true, every leg's `amount_cents` must be strictly less than zero; a non-negative leg amount on such an entry is rejected with `ERR_NON_ALLOWABLE_MUST_BE_NEGATIVE`. Two further fields are server-managed. `source` is `MANUAL` for analyst-entered entries and `AUDIT` for entries the server synthesizes when the contractor incorporates an audit adjustment; `source_audit_adjustment_id` points back at the originating adjustment on `AUDIT`-sourced entries and is null on `MANUAL` ones. The entry's own `status` begins at `ACTIVE`.

Reversal is the compensating operation, available to the analyst and taking no payload. It advances the entry from `ACTIVE` to `REVERSED`, stamps `reversed_at` from the logical clock, and removes the entry from every cost center rollup; reversing an entry that is already `REVERSED` is an `ERR_INVALID_STATE_TRANSITION`. While `ACTIVE`, `reversed_at` is null.

Only `ACTIVE` entries contribute to cost center balances; `REVERSED` entries contribute nothing. On that basis each cost center's `reclassified_amount_cents` is the signed sum of leg amounts targeting it across the report's `ACTIVE` entries of type `RECLASSIFICATION`, and its `adjustment_amount_cents` is the signed sum of leg amounts targeting it across the report's `ACTIVE` entries of type `ADJUSTMENT`. From those two figures, `post_reclass_direct_cost_cents` is `direct_cost_cents` plus `reclassified_amount_cents`, and `post_adjustment_cost_cents` is `post_reclass_direct_cost_cents` plus `adjustment_amount_cents`. That last figure — the post-adjustment pool — is what the overhead stepdown starts from.

There is a conserved quantity here worth stating explicitly, because it is the test of a correct implementation. Summing `post_reclass_direct_cost_cents` across the report's cost centers always equals summing `amount_cents` across the report's `MAPPED` trial balance lines, and that equality survives every reclassification create and every reversal precisely because reclassification legs are required to net to zero. Creating an entry and then reversing it must return every affected figure to its exact pre-create value. Both creating and reversing an entry additionally demote every `COMPLETED` stepdown run of the report to `STALE` with `stale_reason` `WORKPAPER_ENTRY_CHANGED`, set the report's `allocation_status` to `STALE`, and increment the report's `version`.

### 3.4. The Overhead Stepdown: Single and Double Apportionment

Running the stepdown is the one write shared between the hospital and the contractor: either a `ReimbursementAnalyst` or a `MacAuditor` may trigger it, supplying the required `expected_cost_report_version` token described in §2.8 and, optionally, a `method` of `SINGLE_APPORTIONMENT` or `DOUBLE_APPORTIONMENT`. When `method` is omitted the run inherits the report's `apportionment_method`. A **StepdownRun** is created in `QUEUED` status and resolves synchronously within the same request, so a caller never observes `QUEUED`.

Two structural preconditions decide whether the run can execute at all. The report must contain at least one `GENERAL_SERVICE` cost center and at least one cost center whose `center_type` is `ROUTINE` or `ANCILLARY`, else the request is rejected with `ERR_STEPDOWN_STRUCTURE_INCOMPLETE`. And the report's `unmapped_tb_total_cents` must be exactly 0, else `ERR_UNMAPPED_TRIAL_BALANCE`. There is exactly one way for a run to be created and *not* succeed: if two or more `GENERAL_SERVICE` centers of the report share the same `stepdown_order` — the transient collision that revision permits — the run resolves to `FAILED` with `failure_reason` set to the string `DUPLICATE_STEPDOWN_ORDER`, is returned with HTTP 201 as the audit record of the attempt, leaves the report's `allocation_status` untouched, and still increments the report's `version`. A `FAILED` run writes no allocation lines and touches no cost center.

**The distribution primitive.** Both apportionment variants are built from one operation: distributing a pool of cents from one allocating general service center to a set of receivers. A receiver's weight under a given allocator is the receiver's `statistics` value keyed by that allocator's `allocation_basis`, and a receiver with no entry for that key has weight zero. Eligible receivers are those whose weight is strictly greater than zero. If no receiver is eligible, no division is performed and the entire pool remains on the allocator as residual. Otherwise, let the total weight be the sum of the eligible receivers' weights. Each eligible receiver's exact share is the pool multiplied by that receiver's weight and divided by the total weight, evaluated as an exact rational number; that receiver's provisional share is the exact share rounded **down** to a whole cent. The remainder is the pool minus the sum of the provisional shares, and it is at least zero and strictly less than the number of eligible receivers. The eligible receivers are then ordered by the fractional part they lost — exact share minus provisional share — in descending order, with ties broken by `created_at` ascending, and one additional cent is given to each of the first *remainder* receivers in that order. The residual in this branch is zero.

This ordering is normative: distribute, then round down per receiver, then spread the leftover cents. Summing the exact shares and rounding the total instead, or rounding the weight ratio to six decimal places before multiplying, produces a different number of cents and is wrong.

**The `SINGLE_APPORTIONMENT` variant** runs one pass. Every cost center's accumulator begins at its `post_adjustment_cost_cents`. The general service centers are processed in ascending `stepdown_order`. For each one, the receiver set is every ancillary, routine and nonreimbursable center plus every general service center whose `stepdown_order` is strictly greater — already-closed general service centers receive nothing. The pool distributed is the allocator's *current accumulated* balance, which therefore includes everything it received from earlier general service centers. Each receiver's accumulator grows by its share, the allocator's accumulator becomes the residual, and each resulting movement is recorded with `pass` equal to 1.

**The `DOUBLE_APPORTIONMENT` variant** runs two passes. In pass one, the general service centers are processed in ascending `stepdown_order`, and for each the receiver set is *every other center in the report, including general service centers that have already closed*; the pool distributed is the allocator's own `post_adjustment_cost_cents`, not an accumulated balance. Every movement is recorded with `pass` equal to 1, and the amounts each center received in pass one are tallied separately. After pass one, each non-general-service center's accumulator is set to its own `post_adjustment_cost_cents` plus what it received in pass one. In pass two, the general service centers are again processed in ascending `stepdown_order`, and each distributes *the amount it received during pass one* to the non-general-service centers only. Receivers' accumulators grow by their shares, each allocator keeps its residual, and every movement is recorded with `pass` equal to 2. Because pass one lets overhead pools cross-charge each other and pass two redistributes those cross-charges, identical inputs produce different per-center figures and a different report-level allowable cost under this variant than under single apportionment — the two are not related by any constant factor.

**Publishing the result.** The run records its movements in `allocation_lines`, an array of objects each carrying `pass`, `from_cost_center_id`, `to_cost_center_id` and `amount_cents`, held in execution order. Its `total_allocated_cents` is the sum of `amount_cents` across those lines, starting from 0 when there are none. Its `residual_unallocated_cents` is the sum of the residuals left across every allocator step — cost stranded on a general service center because no eligible receiver had a positive statistic, plus any second-pass residual. Its `stale_reason` is null while the run stands, and `completed_at` is stamped from the logical clock at completion and is null otherwise; `failure_reason` is null on any run that is not `FAILED`.

Each cost center's `allocated_in_cents` becomes the sum of `amount_cents` over allocation lines whose `to_cost_center_id` is that center, its `allocated_out_cents` becomes the sum over lines whose `from_cost_center_id` is that center, and its `allocated_total_cost_cents` becomes `post_adjustment_cost_cents` plus `allocated_in_cents` minus `allocated_out_cents`. The report's `total_allowable_cost_cents` is then the sum of `allocated_total_cost_cents` over the cost centers whose `center_type` is `ROUTINE` or `ANCILLARY` only — nonreimbursable centers do receive allocations, and are deliberately excluded from this total. While `allocation_status` is `NOT_RUN`, `total_allowable_cost_cents` is 0. Finally the report's `cost_to_charge_ratio` becomes `total_allowable_cost_cents` divided by `total_charges_cents`, rounded half up to six decimal places, and is 0.000000 whenever `total_charges_cents` is 0. The full four-link cascade this triggers is set out in §2.7.

A completed run is invalidated — demoted to `STALE` with the matching `stale_reason` — by any of five events: a newer run completing, a cost center revision, a workpaper entry creation, a workpaper entry reversal, or the contractor incorporating an audit adjustment. In each case the report's `allocation_status` becomes `STALE` unless a newer `COMPLETED` run already exists. Both `FAILED` and `STALE` are terminal for a run.

### 3.5. Wage Index Data Collection and Contractor Desk Review

The wage index side of the report runs on its own clock and its own state axis. A `ReimbursementAnalyst` opens a **WageIndexSubmission** against the report, supplying the worksheet S-3 part II figures: `total_salaries_cents`, a non-negative integer, and `total_paid_hours`, a number strictly greater than zero at two decimal places, are required. Five further inputs are optional and each defaults to 0: `wage_related_costs_cents` (pension and benefit costs claimed as wage-related), `contract_labor_cents` and `contract_labor_hours`, and `excluded_area_salaries_cents` and `excluded_area_hours` (the salaries and hours of non-acute areas removed from the wage index). The monetary figures are non-negative integers; the hour figures are non-negative numbers at two decimal places. At most one submission with a `status` other than `REJECTED` may exist per report, and a second one is rejected with `ERR_DUPLICATE_CHILD_RECORD`. A new submission begins at `status` `DRAFT` with `revision_number` at 0 and `review_note` at null.

The analyst may correct the salary and hour figures while the submission is in collection or after a change request, submitting any subset of those seven inputs. This correction path exists because the hours-verification boundary — reported occupational mix hours exactly equal to total paid hours — is only reachable by editing the totals after the survey responses already exist. Each correction recomputes both average-hourly-wage variants.

**The occupational mix survey.** Alongside the submission the analyst records one **OccMixResponse** per nursing category. The `category` is one of `RN`, `LPN`, `NURSE_AIDE`, `MEDICAL_ASSISTANT` or `NURSE_PRACTITIONER` and must be unique within the submission identified by `wage_index_submission_id`; a repeat category is rejected with `ERR_OCC_MIX_CATEGORY_DUPLICATE`. Each response carries `reported_hours`, a non-negative number at two decimal places where 0 means the category was not staffed, and `reported_salaries_cents`, a non-negative integer. The server computes that response's `category_ahw_cents` as `reported_salaries_cents` divided by `reported_hours`, rounded half up to a whole cent, leaving it null when `reported_hours` is 0.

The submission's `reported_hours_total` is the sum of `reported_hours` across its responses, and it may never exceed `total_paid_hours`; **equality is permitted**. This check guards three separate operations — recording a survey response, submitting the wage data, and recording the contractor's accept decision — and in all three the rejection is `ERR_OCC_MIX_HOURS_EXCEED_TOTAL`. The submission's `occ_mix_category_count` is the number of its responses whose `reported_hours` is strictly greater than zero.

**Computing the average hourly wage.** Both variants are recomputed whenever the submission is corrected, whenever a survey response is recorded, and whenever the submission is submitted. First, `allowed_wage_related_costs_cents` is the lesser of `wage_related_costs_cents` and one quarter of `total_salaries_cents` rounded down to a whole cent — the wage-related cost cap is 25 percent of total salaries, and it floors rather than rounds. Next, undocumented contract labor is dropped from *both* sides of the ratio: when `contract_labor_hours` is exactly 0, the contract labor contribution to the numerator and to the denominator are both taken as 0 regardless of what `contract_labor_cents` says; otherwise both `contract_labor_cents` and `contract_labor_hours` contribute at face value. The numerator in cents is `total_salaries_cents` plus `allowed_wage_related_costs_cents` plus the contract labor cents contribution, minus `excluded_area_salaries_cents`. The denominator in hours is `total_paid_hours` plus the contract labor hours contribution, minus `excluded_area_hours`. `unadjusted_ahw_cents` is that numerator divided by that denominator, rounded half up to a whole cent. This is the pooled variant: one ratio over all hours, occupational mix ignored entirely.

The occupational-mix-adjusted variant works from the active survey responses — those with `reported_hours` strictly greater than zero. When `occ_mix_category_count` is fewer than 3, `occ_mix_adjusted_ahw_cents` is null and no weighting is attempted. When it is 3 or more, each active category is weighted by a renormalized national target percentage. The national target percentages are 0.5600 for `RN`, 0.2000 for `NURSE_AIDE`, 0.1000 for `LPN`, 0.1000 for `NURSE_PRACTITIONER` and 0.0400 for `MEDICAL_ASSISTANT`. Let the renormalization base be the sum of the national target percentages over the *active* categories only, so that an unstaffed category's share is redistributed pro rata across the rest. Each active category's weight is its national target percentage divided by that base, rounded half up to six decimal places. Those rounded weights will generally not sum to exactly 1.000000, and the residual drift — 1.000000 minus the sum of the weights — is added, with its sign, to the weight of the active category holding the largest national target percentage, ties broken by category name in ascending alphabetical order. `occ_mix_adjusted_ahw_cents` is then the sum over active categories of each weight multiplied by that category's `category_ahw_cents`, rounded half up to a whole cent. Because per-category wages are weighted rather than pooled, identical submission data yields a different cents-per-hour result under this variant than under the unadjusted one.

`effective_ahw_cents` resolves the choice: it is `occ_mix_adjusted_ahw_cents` when `occ_mix_category_count` is at least 3, and `unadjusted_ahw_cents` otherwise.

**The review cycle.** Attestation is the `ReimbursementManager`'s act. Submitting advances the submission from `DRAFT` to `SUBMITTED`, and it also advances a submission from `CHANGE_REQUESTED` back to `SUBMITTED`. Both paths require that `reported_hours_total` not exceed `total_paid_hours`, recompute the average hourly wage figures, set the report's `wage_data_status` to `COLLECTED`, and increment the report's `version`. They differ in two respects: the `DRAFT` path additionally requires that at least one survey response exist for the submission, while the `CHANGE_REQUESTED` path does not; and the `CHANGE_REQUESTED` path increments `revision_number` by one, which is why `revision_number` counts submissions after the first rather than submissions in total.

Desk review belongs to the `MacAuditor`. Starting a review moves the submission to `UNDER_REVIEW` from either of two origins. From `SUBMITTED` it is the ordinary first review. From `ACCEPTED` it is a re-opened desk review — the entry point that makes this lifecycle cyclic — permitted only while the report's `status` is not `CLOSED`, and it does **not** touch the report's `status`, which may well already read `FILED`. Either way, the report's `wage_data_status` becomes `UNDER_REVIEW` and the report's `version` increments.

From `UNDER_REVIEW` the auditor records a `decision` together with a `review_note`, and there are three mutually exclusive outcomes with different preconditions. `ACCEPT` advances the submission to `ACCEPTED`, and requires both that `occ_mix_category_count` be at least 3 — fewer than three staffed categories is rejected with `ERR_OCC_MIX_INCOMPLETE` — and that `reported_hours_total` not exceed `total_paid_hours`; it sets `review_note`, sets the report's `wage_data_status` to `VERIFIED`, and increments the report's `version`. `REQUEST_CHANGE` advances the submission to `CHANGE_REQUESTED` with no additional precondition; it sets `review_note`, sets the report's `wage_data_status` to `REVISION_REQUESTED` while leaving the report's `status` untouched, and increments the report's `version`. `REJECT` advances the submission to the terminal `REJECTED` state, but only while the report's `status` is still `DRAFT`; it sets the report's `wage_data_status` to `REJECTED` and increments the report's `version`. Any of these three attempted from a status other than `UNDER_REVIEW` is an `ERR_INVALID_STATE_TRANSITION`. The full cycle a contested submission travels is therefore from `ACCEPTED` into a re-opened `UNDER_REVIEW`, out to `CHANGE_REQUESTED`, back to `SUBMITTED`, into `UNDER_REVIEW` a second time, and finally to `ACCEPTED` again.

### 3.6. Graduate Medical Education: Residents, Rotations and FTE Counts

A teaching hospital's direct graduate medical education payment turns on resident full-time-equivalent counts, and those counts are built from rotations rather than declared. A `ReimbursementAnalyst` registers a **Resident** under a provider identified by `provider_id`, supplying `full_name` and the approved GME `program` name, plus an optional `irp_status` of `WITHIN_IRP` or `BEYOND_IRP` defaulting to `WITHIN_IRP`. A resident's `assigned_fte_days` is server-computed, starts at 0.0000, and always equals the sum of `fte_days` over that resident's `ACTIVE` rotation assignments.

A **RotationAssignment** places a resident, named by `resident_id`, at a rotation site named by `cost_center_id`, for a half-open date interval running from an inclusive `start_date` to an exclusive `end_date`, at an `fte_fraction` share of the resident's time. The end date must be strictly later than the start date, and `fte_fraction` must be strictly greater than 0.0000 and no greater than 1.0000, at four decimal places. Three business tests then apply in order. The rotation site's cost center must belong to a cost report of the *resident's own* provider, else `ERR_COST_CENTER_FOREIGN_TO_PROVIDER`. The resident's aggregate `fte_fraction` across all `ACTIVE` assignments must not exceed 1.0000 on any single day of the half-open interval `[start_date, end_date)` — a resident cannot be more than fully deployed — and a violation is rejected with `ERR_RESIDENT_DAILY_FTE_EXCEEDED`; note that adjacency is not overlap, so an assignment whose `end_date` equals another's `start_date` contributes nothing on that shared date. And the rotation must actually intersect the cost report's fiscal year, meaning its computed `overlap_days` must be strictly greater than zero, else `ERR_ROTATION_OUTSIDE_FISCAL_YEAR`. A new assignment begins at `status` `ACTIVE`.

Voiding is the compensating operation, taking no payload, available to the analyst while the assignment is `ACTIVE` and while the owning cost report's `status` is `DRAFT` or `REOPENED`. It advances the assignment to the terminal `VOID` state, sets its `fte_days` to 0.0000, decrements the resident's `assigned_fte_days` by the assignment's pre-void `fte_days`, decrements the report's `unweighted_fte_days_total` by the same figure, and recomputes the report's full-time-equivalent outputs. Voiding an assignment that is already `VOID` is an `ERR_INVALID_STATE_TRANSITION`.

**The FTE computation.** The report's period is the half-open interval from `fiscal_year_begin` up to but excluding the day after `fiscal_year_end`, and the number of days in that interval is the period day count. For every `ACTIVE` rotation assignment whose `cost_center_id` names a cost center of this report, `overlap_days` is the number of days in the intersection of `[start_date, end_date)` with that period, and `fte_days` is `fte_fraction` multiplied by `overlap_days`, rounded half up to four decimal places. A `VOID` assignment contributes `fte_days` of 0.0000. The report's `unweighted_fte_days_total` is the sum of `fte_days` over those assignments.

Per resident, `assigned_fte_days` is the sum of `fte_days` over that resident's `ACTIVE` assignments, and the resident's own FTE figure is `assigned_fte_days` divided by the period day count, rounded half up to four decimal places, then capped at 1.0000 — no resident counts as more than one full-time equivalent in a period, whatever the arithmetic says. The report's `unweighted_fte_total` is the sum of those per-resident FTE figures, rounded half up to two decimal places. The report's `capped_unweighted_fte` is the lesser of `unweighted_fte_total` and the provider's `fte_cap`, at two decimal places. The report's `weighted_fte_total` applies the initial residency period weighting: each resident's FTE figure is multiplied by 1.00 when their `irp_status` is `WITHIN_IRP` and by 0.50 when it is `BEYOND_IRP`, and the products are summed and rounded half up to two decimal places.

The rolling average smooths the count across three years. The prior periods are the *same provider's* cost reports whose `status` is `FINAL_SETTLED` and whose `fiscal_year_end` is strictly earlier than this report's `fiscal_year_end`, ordered by `fiscal_year_end` descending, taking at most the first two. The report's `rolling_average_fte` is this report's `capped_unweighted_fte` plus the `capped_unweighted_fte` of each prior period, divided by one plus the number of prior periods found, rounded half up to two decimal places. A provider with no settled history therefore divides by 1 and its rolling average equals its own capped count.

These figures are recomputed whenever a rotation assignment is created, whenever one is voided, whenever the report is filed, and whenever the GME summary is read. The summary read returns `cost_report_id`, `period_days`, `unweighted_fte_days_total`, `unweighted_fte_total`, `capped_unweighted_fte`, `weighted_fte_total`, `rolling_average_fte` and `prior_period_count`, the last being the number of prior settled periods actually found (0, 1 or 2). There is a conserved quantity to honour here, measured in time-weighted FTE-days rather than dollars: the report's `unweighted_fte_days_total`, the sum of `assigned_fte_days` across the provider's residents, and the sum of `fte_days` across the report's `ACTIVE` assignments must always be the same number. A create followed by its compensating void must return all three figures to their exact pre-create values, with no one-ten-thousandth drift.

### 3.7. Disproportionate Share and Uncompensated Care Compilation

Each report carries at most one **UccDataSet**, compiled by the analyst, and a second one is rejected with `ERR_DUPLICATE_CHILD_RECORD`. Five inputs are required and one is optional. `medicaid_non_medicare_days` counts Medicaid-eligible non-Medicare inpatient days and must be non-negative. `total_inpatient_days` is the denominator of the Medicaid fraction and must be strictly greater than zero. `ssi_days` counts Medicare Part A days for patients entitled to Supplemental Security Income and must be non-negative. `medicare_part_a_days` is the denominator of the SSI fraction and must be strictly greater than zero. `charity_care_charges_cents` carries the worksheet S-10 charity care charges as a non-negative integer. `non_medicare_bad_debt_cents` is the optional non-Medicare bad debt expense, a non-negative integer defaulting to 0.

The compilation runs at creation, on an explicit recompute, and as link three of the completed-stepdown cascade. `medicaid_fraction` is `medicaid_non_medicare_days` divided by `total_inpatient_days`, rounded half up to four decimal places. `ssi_fraction` is `ssi_days` divided by `medicare_part_a_days`, rounded half up to four decimal places. `dsh_patient_percentage` is the sum of those two **already-rounded** fractions, itself rounded half up to four decimal places — rounding each fraction first and then adding is normative, because summing the raw quotients and rounding once produces a different four-decimal value right at the eligibility boundary. `dsh_eligible` is true exactly when `dsh_patient_percentage` is greater than or equal to 0.1500, the fifteen-percent disproportionate share threshold, and false otherwise; it starts as false.

The data set's own `cost_to_charge_ratio` is a snapshot of the report's `cost_to_charge_ratio` taken at the moment of the compilation, held to six decimal places, and it reads 0.000000 until a stepdown run has completed. `uncompensated_care_cost_cents` is the sum of two separately rounded terms: `charity_care_charges_cents` multiplied by that snapshot ratio, rounded half up to a whole cent, plus `non_medicare_bad_debt_cents` multiplied by 0.65 — sixty-five percent of non-Medicare bad debt is allowable — rounded half up to a whole cent. The two products are rounded individually and only then added.

`ucc_payment_cents` is 0 whenever `dsh_eligible` is false. When `dsh_eligible` is true, it is the national uncompensated care pool of 800,000,000,000 cents (eight billion dollars) multiplied by this hospital's `uncompensated_care_cost_cents`, divided by the national aggregate uncompensated care cost of 4,000,000,000,000 cents (forty billion dollars), with the result rounded **down** to a whole cent.

The `recompute_required` flag records whether these figures have gone stale: the server sets it to true when the report's allocation went `STALE` after the data set was last recomputed, and clears it to false on every recompute — whether triggered explicitly by an analyst or auditor, or as part of the completed-stepdown cascade. It starts as false. An explicit recompute is the way to observe the uncompensated care figures under a new cost-to-charge ratio without re-filing the report.

### 3.8. Settlement Stages and the Audit Adjustment Cycle

Settlement belongs entirely to the `MacAuditor`, who issues a **Settlement** by naming a `stage` of either `TENTATIVE` or `FINAL`. A settlement begins at `status` `ISSUED`, stamps `issued_at` from the logical clock, and takes `recompute_required` as false. Two preconditions apply to both stages: the report's `allocation_status` must be `CURRENT`, else `ERR_ALLOCATION_NOT_CURRENT`, and the report must be in a status from which the requested stage is reachable, else `ERR_INVALID_STATE_TRANSITION`.

Issuing the tentative settlement advances the report from `FILED` to `TENTATIVE_SETTLED`, and additionally requires that no settlement of this report with `stage` `TENTATIVE` and `status` `ISSUED` already exist. Issuing the final settlement advances the report from `TENTATIVE_SETTLED` to `FINAL_SETTLED`, and also advances a reopened-and-refiled report from `AMENDED_FILED` to `FINAL_SETTLED`, closing the reopening cycle that runs from `FINAL_SETTLED` into `REOPENED`, on into `AMENDED_FILED`, and back to `FINAL_SETTLED`. The `TENTATIVE_SETTLED` path to `FINAL_SETTLED` demands three further things: that a settlement with `stage` `TENTATIVE` and `status` `ISSUED` exist; that the report's `COMPLETED` stepdown run have `method` `DOUBLE_APPORTIONMENT`, since a single-pass allocation is not an acceptable basis for a final settlement and a request made against one is rejected with `ERR_FINAL_REQUIRES_DOUBLE_APPORTIONMENT`; and that no audit adjustment of the tentative settlement remain in `PROPOSED`, `ACCEPTED_BY_PROVIDER` or `PROTESTED`, else `ERR_AUDIT_ADJUSTMENT_UNRESOLVED`. The `AMENDED_FILED` path to `FINAL_SETTLED` keeps the double-apportionment requirement and the current-allocation requirement, but does not require a tentative settlement to exist. Reaching `FINAL_SETTLED` by either path stamps the report's `allowable_cost_per_discharge_cents` as `total_allowable_cost_cents` divided by `medicare_discharges`, rounded half up to a whole cent, taking the value 0 when `medicare_discharges` is 0; before final settlement that field reads 0. Every settlement issuance increments the report's `version`.

**Computing the settlement amount.** The basis is the report's one `COMPLETED` stepdown run — exactly one exists while `allocation_status` is `CURRENT`. The settlement's `basis_method` is a snapshot of that run's `method`, and its `basis_allowable_cost_cents` is a snapshot of the report's `total_allowable_cost_cents` at issuance. Its `reimbursable_cost_cents` is `basis_allowable_cost_cents` multiplied by the report's `medicare_utilization_ratio`, rounded half up to a whole cent.

The two stages then diverge. For a `TENTATIVE` settlement, `ucc_payment_cents` is 0 — the tentative stage ignores uncompensated care entirely — and `prior_tentative_paid_cents` is 0, and `amount_due_provider_cents` is three quarters of the difference between `reimbursable_cost_cents` and the report's `interim_payments_received_cents`, rounded half up to a whole cent. The tentative stage will accept a `SINGLE_APPORTIONMENT` basis run.

For a `FINAL` settlement, `ucc_payment_cents` is taken from the report's uncompensated care data set — which is 0 whenever `dsh_eligible` is false — and `prior_tentative_paid_cents` is the sum of `amount_due_provider_cents` over this report's settlements whose `stage` is `TENTATIVE` and whose `status` is anything other than `SUPERSEDED`. Then `amount_due_provider_cents` is the difference between `reimbursable_cost_cents` and `interim_payments_received_cents`, plus `ucc_payment_cents`, minus `prior_tentative_paid_cents`. The final stage pays the whole net rather than three quarters of it, adds the uncompensated care payment, and credits back what the tentative stage already advanced — so a report never settles to a naive four-thirds of its tentative figure. Note that `prior_tentative_paid_cents` sums only `TENTATIVE` rows, which is precisely why a `RESETTLED` prior `FINAL` settlement is not double-counted when the reopening cycle produces a second final settlement. A positive `amount_due_provider_cents` means the contractor owes the provider; a negative figure means the reverse. A settlement's `status` moves among `ISSUED`, `APPEALED`, `SUPERSEDED` and `RESETTLED` as the audit and appeal machinery below dictates.

**Proposing an audit adjustment.** After settlement, the auditor may propose an **AuditAdjustment** against the settlement named in `settlement_id`, landing on the cost center named in `target_cost_center_id` — which must belong to that settlement's cost report, else `ERR_COST_CENTER_FOREIGN_TO_REPORT`. The proposal carries an audit exception `code`, a `rationale` narrative, and a signed `proposed_amount_cents` that may not be zero. The adjustment begins at `status` `PROPOSED`, records `proposed_by_user_id` from the proposing auditor's `X-User-ID`, leaves `resolved_by_user_id` and `provider_response_note` null, and increments the parent settlement's `version`.

**The provider's response.** A `ReimbursementManager` responds with a `response` of either `ACCEPT` or `PROTEST` together with a `provider_response_note`. Both branches require the parent settlement's `status` to be `ISSUED` or `APPEALED`, set `provider_response_note`, and increment the settlement's `version`. `ACCEPT` moves the adjustment to `ACCEPTED_BY_PROVIDER` and additionally requires that the settlement's cost report be in `TENTATIVE_SETTLED`; it leaves the settlement's own `status` unchanged. `PROTEST` moves the adjustment to `PROTESTED`, imposes no additional report-status requirement, and — this is the branch-specific effect absent from the accept path — sets the parent settlement's `status` to `APPEALED`.

**The contractor's resolution.** From either `ACCEPTED_BY_PROVIDER` or `PROTESTED`, a `MacAuditor` resolves the adjustment with an `outcome` of `INCORPORATE` or `WITHDRAW` and an optional `resolution_note`. All four combinations require that the resolving `X-User-ID` differ from `proposed_by_user_id` (`ERR_SEGREGATION_OF_DUTIES`), and all four stamp `resolved_by_user_id` from that header.

`INCORPORATE` moves the adjustment to the terminal `INCORPORATED` state and drives the full five-link cost cascade of §2.7 — a synthesized `ADJUSTMENT` workpaper entry with `source` `AUDIT` and a single leg placing `proposed_amount_cents` on the target cost center, the target center's `adjustment_amount_cents` and `post_adjustment_cost_cents` updated, every `COMPLETED` stepdown run demoted to `STALE` with `stale_reason` `WORKPAPER_ENTRY_CHANGED`, the report's `allocation_status` set to `STALE`, and `recompute_required` set to true on every settlement of the report whose `status` is `ISSUED` or `APPEALED` — and increments the report's `version`. The cascade is identical whichever branch it is reached from; resolving from `PROTESTED` does one thing more, restoring the parent settlement's `status` to `ISSUED`, because the protest has been overruled.

`WITHDRAW` moves the adjustment to the terminal `WITHDRAWN` state and has no cost impact whatsoever: no workpaper entry is created, and every cost center, stepdown run and cost report field is left untouched. Resolving from `PROTESTED` by withdrawal restores the parent settlement's `status` to `ISSUED`; resolving from `ACCEPTED_BY_PROVIDER` by withdrawal leaves the settlement's status alone. The workpaper entries synthesized by a given resolution are retrievable by traversing back from the adjustment.

### 3.9. Reopening, the Review Board, and the Interim Rate Reset

**Disputing a final settlement.** A provider that disputes a final settlement has two instruments, and a single **AppealCase** row models both, selected by `kind`. A `ReimbursementManager` opens the case against the report, naming the disputed `settlement_id`, the `kind` (`REOPENING` for a contractor reopening request or `PRRB_APPEAL` for a Provider Reimbursement Review Board appeal), an `issue_description` narrative, and `amount_at_issue_cents`, the dollars in controversy, which must be strictly greater than zero. The named settlement must belong to the same cost report as the case, else `ERR_SETTLEMENT_FOREIGN_TO_REPORT`, and must have `stage` `FINAL`, else `ERR_SETTLEMENT_STAGE_INVALID`. A board appeal carries two extra requirements: it must be opened within 180 days of the final settlement's `issued_at`, else `ERR_APPEAL_WINDOW_EXPIRED`, and its `amount_at_issue_cents` must be at least 1,000,000 cents — ten thousand dollars in controversy — else `ERR_PRRB_AMOUNT_BELOW_MINIMUM`. That minimum is a business rule and not a schema bound, so a board appeal naming 500,000 cents is a 422 on `ERR_PRRB_AMOUNT_BELOW_MINIMUM`, never a 400. A new case begins at `status` `REQUESTED` with `decided_at` and `decision_note` null.

Deciding a case takes an `outcome` and a `decision_note`, and which outcomes are available depends on `kind` and on who is calling. The contractor path is the `MacAuditor`'s. From `REQUESTED` on a case of `kind` `REOPENING`, `GRANT` advances the case to `GRANTED`; it requires that the referenced settlement have `stage` `FINAL` and `status` either `ISSUED` or `APPEALED`, and that the logical clock's date fall on or before three years after that settlement's `issued_at` date, else `ERR_REOPENING_WINDOW_EXPIRED`. It sets `decided_at` and `decision_note` and drives the four-link reopening cascade of §2.7, taking the settlement to `RESETTLED`, the report to `REOPENED` with `allocation_status` `STALE`, and every `COMPLETED` stepdown run to `STALE` with `stale_reason` `COST_CENTER_INPUT_CHANGED`. `DENY`, also from `REQUESTED` on a `REOPENING` case, advances the case to the terminal `DENIED` state and sets `decided_at` and `decision_note`, leaving the report's `status` and the settlement entirely untouched.

The board path is the `ReviewBoardClerk`'s and runs in two steps. `HEAR`, from `REQUESTED` on a case of `kind` `PRRB_APPEAL` whose referenced settlement has `status` `APPEALED`, advances the case to `HEARD`; it records the hearing in `decision_note` and deliberately leaves `decided_at` at null, since a hearing is not a decision. From `HEARD`, the clerk then records one of two terminal outcomes on a `PRRB_APPEAL`. `DECIDE_FOR_PROVIDER` advances the case to `DECIDED_FOR_PROVIDER`, sets `decided_at` and `decision_note`, and runs the same reopening cascade as a granted reopening: the referenced settlement becomes `RESETTLED`, the report's `status` becomes `REOPENED` and its `allocation_status` becomes `STALE`. `DECIDE_FOR_CONTRACTOR` advances the case to `DECIDED_FOR_CONTRACTOR`, sets `decided_at` and `decision_note`, restores the referenced settlement's `status` to `ISSUED` because the appeal resolved without change, and moves the report's `status` to the terminal `CLOSED`. Both board decisions increment the report's `version`. Any decision attempted from a status that does not offer the requested outcome — a `HEAR` on a case already `HEARD`, a `GRANT` on a `PRRB_APPEAL`, a board decision on a case still `REQUESTED` — is an `ERR_INVALID_STATE_TRANSITION`.

After a reopening puts the report back into `REOPENED`, the accounting tree becomes editable again, the allocation must be re-run, and the amended filing described in §3.1 carries the report to `AMENDED_FILED` and then on to a second `FINAL_SETTLED`.

**Resetting the interim payment rate.** The last workflow looks forward rather than back. A `ReimbursementManager` asks the contractor to reset the hospital's interim payment rate by creating an **InterimRateRequest** for the provider named in `provider_id`, carrying the `expected_provider_version` token of §2.8, the `basis_cost_report_id` of the settled period the projection is built on, the `projected_discharges` expected in the requested period (strictly greater than zero), a `trend_factor` cost inflation factor from 0.0000 through 0.5000 inclusive at four decimal places, and the closed period `[effective_from, effective_to]` over which the new rate would apply, with `effective_to` strictly later than `effective_from`.

Four business gates precede the arithmetic. The basis report must belong to the named provider, else `ERR_BASIS_REPORT_FOREIGN_TO_PROVIDER`. The requested closed interval must not come within 30 days of the closed interval of any of that provider's existing interim rate requests whose `status` is neither `DENIED` nor `SUPERSEDED`; boundaries are inclusive on both ends, and a violation is rejected with `ERR_INTERIM_PERIOD_OVERLAP`. The basis report's `status` must be `FINAL_SETTLED`, so that its `allowable_cost_per_discharge_cents` has actually been stamped, else `ERR_BASIS_REPORT_NOT_FINAL_SETTLED`. And the provider's `current_interim_rate_cents` must be strictly greater than zero, since a variance cannot be measured against a rate of zero, else `ERR_NO_CURRENT_INTERIM_RATE`.

**The projection, in a normative order.** The cap and the eligibility gate each depend on the other's input, so the sequence is what makes the result well defined. First, `projected_cost_per_discharge_cents` is the basis report's `allowable_cost_per_discharge_cents` multiplied by one plus `trend_factor`, rounded half up to a whole cent — this is the *uncapped* projection. Second, `variance_ratio` is the absolute difference between that uncapped projection and the provider's `current_interim_rate_cents`, divided by `current_interim_rate_cents`, rounded half up to four decimal places. Third, the eligibility gate is applied to that pre-cap variance: a `variance_ratio` below 0.1000 — a swing of less than ten percent — is not worth a rate change and the request is rejected with `ERR_INTERIM_VARIANCE_BELOW_THRESHOLD`. Fourth, and only after the gate, the cap is applied: the rate ceiling is the provider's `current_interim_rate_cents` multiplied by 1.10 — a hundred and ten percent of the standing rate — rounded down to a whole cent, and `approved_rate_cents` is the lesser of the uncapped projection and that ceiling. Fifth, `adjustment_amount_cents` is the difference between `approved_rate_cents` and the provider's `current_interim_rate_cents` at request time, multiplied by `projected_discharges`.

Computing `variance_ratio` from `approved_rate_cents` instead — that is, after the cap — would collapse every capped request to exactly ten percent, changing both the stored variance and which requests pass the gate. The stored `variance_ratio` is always the pre-cap figure.

A new request begins at `status` `PENDING` with `decision_note` null, and it supersedes the provider's outstanding work: any prior request of the same provider still in `PENDING` is moved to the terminal `SUPERSEDED` state with its `decision_note` set to the string `SUPERSEDED_BY_NEWER_REQUEST`, and the provider's `current_interim_rate_cents` is not touched by that superseding. Creating a request increments the provider's `version`.

Deciding is the `MacAuditor`'s act and takes a `decision` of `APPROVE` or `DENY` with a `decision_note`. Both require the request to still be `PENDING`, else `ERR_INVALID_STATE_TRANSITION`. `APPROVE` advances the request to the terminal `APPROVED` state; it requires the basis report's `status` to be `FINAL_SETTLED` (`ERR_BASIS_REPORT_NOT_FINAL_SETTLED`), sets `decision_note`, writes `approved_rate_cents` onto the provider as its new `current_interim_rate_cents`, increments the provider's `approved_interim_period_count` by one, and increments the provider's `version`. Note that `approved_rate_cents` and `adjustment_amount_cents` were both computed at creation time against the rate then standing, and approval applies the stored figure rather than re-projecting. `DENY` advances the request to the terminal `DENIED` state and sets `decision_note`, leaving every provider field untouched.
