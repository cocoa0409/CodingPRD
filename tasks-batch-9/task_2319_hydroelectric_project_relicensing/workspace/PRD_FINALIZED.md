# Hydroelectric Project Relicensing API — Product Requirements Document

## 1. Introduction

A hydroelectric license runs for decades, and the process of renewing one runs for years. A licensee that intends to keep operating must file a pre-application document more than five years before its existing license lapses, negotiate a study programme with resource agencies, run field studies across fish passage, water quality, recreation and cultural resources, bargain a settlement with agencies, tribes and nongovernmental organizations, obtain a water-quality certification from the state, price every protection, mitigation and enhancement measure that comes out of those processes, file the application, survive environmental review, and then live under an order full of dam-safety, public-safety and emergency-action obligations for the next licence term. Missing any one of these gates does not merely delay the project — it can extinguish the licensee's right to operate the plant.

This document specifies the Hydroelectric Project Relicensing API, the system of record for that entire arc. Every resource in the system lives as a peer collection beneath the `/relicensing` namespace: projects, dams, field sites, study plans, resource studies, consultation comments, settlement parties, settlements, signatures, water-quality certifications, mitigation measures, license applications, license orders and compliance obligations. Cross-resource relationships are expressed as explicit reference fields in request payloads rather than as nested ownership paths, which keeps each collection independently addressable while leaving the burden of referential consistency on the server.

Two design commitments drive most of the complexity that follows. First, the project carries two **derived postures** — one for statutory deadlines and one for regulatory standing — that are recomputed from stored counters at the end of any request that touches the project or any of its children, and that gate what the licensee is allowed to do next. Second, the economic weight of mitigation is tracked continuously in a **burden ledger** on the project, so that the regulator, the licensee and the consulted parties are always looking at the same number when they argue about whether relicensing remains economically feasible. Because relicensing is fundamentally a negotiation among parties who do not trust each other's clocks, the system also exposes a controllable logical clock so that deadline behaviour, statutory waivers and overdue obligations can be exercised deterministically.

## 2. Global Specifications & System-Wide Principles

This section defines the contracts that hold everywhere in the API: authentication, envelope shape, pagination, time, precision, the two posture gates, cascade semantics, reference integrity, stale-version protection, and the order in which rejections are decided.

### 2.1. User and Role-Based Access Control

Every request carries two mandatory headers. `X-User-ID` identifies the acting user and `X-User-Role` declares the capacity in which that user is acting. When `X-User-ID` is absent or names no known user, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 401); this identification requirement applies to every endpoint in the system except the two logical-clock endpoints described in §2.4. When the acting role is not among the roles the target endpoint permits, the request is rejected with `ERR_ROLE_NOT_PERMITTED` (HTTP 403). The role check applies to every endpoint that declares a role list, the logical-clock endpoints included.

Five roles exist, spelled exactly as follows: `Licensee`, `AgencyReviewer`, `Stakeholder`, `StateCertifier`, and `Regulator`.

How `X-User-ID` binds to persisted data differs by role, and the difference matters for every ownership check in the system:

- When `X-User-Role` is `Licensee`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it where a transition demands provenance — as `created_by_user_id` and `definitive_estimate_by_user_id` on a mitigation measure, as `report_submitted_by_user_id` on a resource study, and as `certified_by_user_id` on a compliance obligation — and it compares those recorded values against each other to enforce segregation of duties, but it never compares the header to any entity's `id`.
- When `X-User-Role` is `AgencyReviewer`, `X-User-ID` is the `id` of the acting `SettlementParty`, resolved through that party's `contact_user_id`, and the backing party must have `party_type` equal to `AGENCY`. Ownership checks on any resource that references a `SettlementParty` compare the resource's party reference field to `X-User-ID`: a consultation comment must be filed with its `party_id` equal to the acting user, and a settlement signature must likewise be recorded with its `party_id` equal to the acting user.
- When `X-User-Role` is `Stakeholder`, `X-User-ID` is likewise the `id` of the acting `SettlementParty` resolved through `contact_user_id`, and the backing party must have `party_type` equal to `TRIBE` or `NGO`. The same `party_id` ownership comparison applies to comments and signatures.
- When `X-User-Role` is `StateCertifier`, `X-User-ID` is an opaque identifier for the state water-quality certifying authority, not tied to any persisted entity and never compared to any entity's `id`.
- When `X-User-Role` is `Regulator`, `X-User-ID` is an opaque identifier for the federal licensing authority, not tied to any persisted entity and never compared to any entity's `id`.

For `AgencyReviewer` and `Stakeholder` there is a second, project-scoped access rule: the acting user must resolve to a `SettlementParty` registered on the same project as the target entity. Because one `contact_user_id` may back a party on each of several projects, resolution is a narrowing rather than a single lookup: it collects every party whose `contact_user_id` equals `X-User-ID` — an `X-User-ID` matching no party at all is the "names no known user" case and yields `ERR_UNAUTHORIZED` (HTTP 401) — then keeps only those whose `party_type` suits the declared role, `AGENCY` for `AgencyReviewer` and `TRIBE` or `NGO` for `Stakeholder`, rejecting with `ERR_ROLE_NOT_PERMITTED` (HTTP 403) when none of them does; and then, wherever the request has a target entity to be scoped against, it acts as whichever of the surviving parties is registered on that entity's project, taking the earliest-registered one when more than one is. That selected party is the acting party for the request: its `id` satisfies the `party_id` ownership comparison described above, and its `has_conditioning_authority` is the flag a study-plan determination tests. A party of a different project is treated as not permitted and receives `ERR_ROLE_NOT_PERMITTED` (HTTP 403), not a not-found error.

The five roles divide the work as follows. The `Licensee` owns everything the applicant files: dams, field sites, the pre-application document, study plans and their submissions, resource studies and their fieldwork and reports, the disposition of consultation comments, settlements and their circulation, tallies and withdrawal, water-quality certification requests, mitigation measures including amendments and definitive cost estimates, license applications and their cures, annual compliance reports, and obligation scheduling and certification. The `Licensee` cannot make agency determinations, sign settlements, decide water-quality certifications, register projects or parties, advance environmental review, raise deficiency notices, issue orders, or run the compliance sweep. An `AgencyReviewer` alone makes study-plan determinations and study review decisions, and shares comment filing and settlement signing with `Stakeholder`; a study-plan determination additionally requires the backing party's `has_conditioning_authority` to be true, and an `AgencyReviewer` whose party lacks that authority receives `ERR_ROLE_NOT_PERMITTED`. A `Stakeholder` may comment and sign but may never make a study-plan determination or a study review decision, even when it has a comment of its own on file. The `StateCertifier` holds exactly one authority — the water-quality decision — and may not request a certification, create measures, or touch applications, orders or obligations. The `Regulator` owns project registration and amendment, party registration, environmental review, deficiency notices, order issuance and the compliance sweep, and may not file anything on the licensee's behalf, make agency study determinations, or sign settlements. Every read endpoint under `/relicensing` is open to all five roles.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints are paginated through two query parameters. `limit` caps the number of items returned; it defaults to 10, may be no smaller than 1 and no larger than 100. `offset` is the number of items to skip; it defaults to 0 and may not be negative. A `limit` outside the range 1 through 100, or a negative `offset`, is rejected with `ERR_VALIDATION` (HTTP 400).

Unless a specific endpoint says otherwise, list results are ordered by `created_at` ascending.

List responses carry `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the envelope.

### 2.4. The Logical Clock and Date Arithmetic

Relicensing is a calendar-driven domain, so the server does not read the wall clock. Every `created_at`, `updated_at` and `*_at` timestamp, every date comparison and every deadline evaluation is taken from a single server-side **logical clock**. A `Regulator` sets it by submitting a `to_iso8601` instant to the clock-setting endpoint, which answers with the resulting `current_utc`; any role may read `current_utc` from the clock-reading endpoint. Until the clock is ever set, it reads `2026-08-01T00:00:00Z`. These two endpoints are the only paths in the system outside the `/relicensing` namespace, and they are the only endpoints exempt from the `X-User-ID` identification requirement.

Wherever this specification adds or subtracts a whole number of months from a date, the arithmetic is calendar-month arithmetic with day-of-month clamping: the resulting day-of-month is the requested day, or the last day of the target month when the target month is shorter. Partial months never arise. Where this specification measures a gap in days, it means whole days between two calendar dates.

### 2.5. Common Resource Properties

Most resources in the system carry a standard set of server-managed fields:

- **`id`** (string): a server-minted UUID. It carries no type prefix.
- **`created_at`** (string): the logical-clock instant of creation, rendered as an ISO 8601 UTC timestamp with three fractional digits.
- **`updated_at`** (string): the logical-clock instant of the most recent modification, in the same format.
- **`version`** (integer): a counter that starts at 1 on creation and increments by 1 on every mutation of the resource, including mutations that only rewrite derived fields.

`RelicensingProject`, `Dam`, `StudySite`, `StudyPlan`, `ResourceStudy`, `SettlementParty`, `Settlement`, `WaterQualityCertification`, `PmeMeasure`, `LicenseApplication`, `LicenseOrder` and `ComplianceObligation` all carry the full set.

Lifecycle state is spelled differently from resource to resource, and the spelling matters because it is also the name of the filter a client passes when listing. Five resources name their lifecycle field plainly as `status`: `StudyPlan`, `Settlement`, `WaterQualityCertification`, `PmeMeasure` and `ComplianceObligation`. The others qualify it — a project carries `stage`, a resource study carries the two independent fields `fieldwork_status` and `review_status`, a license application carries `filing_status` alongside `ea_stage`, and a license order carries `compliance_state`. A `SettlementParty` has no lifecycle field at all.

Two resources are append-only records of a moment rather than mutable entities, and they carry only `id` and `created_at`: a `ConsultationComment` and a `SettlementSignature`. Neither exposes `updated_at` and neither exposes `version`. A comment's disposition state does change over its life, but the record is treated as a ledger entry rather than a versioned resource, so mutations of a comment are reflected on the owning study plan's `version` rather than on the comment itself.

### 2.6. Numeric Precision: Dollars, Megawatt-Hours and Percentages

Three families of numbers flow through the system, each with its own precision rule, and all three use **round half up**:

- Dollar amounts are carried to exactly 2 decimal places.
- Energy quantities in megawatt-hours are carried to exactly 1 decimal place.
- Percentages — support percentages, per-party shares, burden ratios and compliance scores — are carried to exactly 2 decimal places.

Rounding is applied at each step a formula names, not once at the end. Where §3 spells out a multi-step derivation, the intermediate value is rounded before it feeds the next step, and re-deriving the result from unrounded intermediates is a wrong answer even when the final digits happen to agree.

### 2.7. Statutory Deadlines and the Timeline Posture

Every deadline in relicensing is anchored on the project's `license_expiration_date`. Two milestones are derived from it. The **pre-application document deadline** falls 66 months — five and a half years — before expiration. The **application deadline** falls 24 months — two years — before expiration. Both are computed by subtracting whole months from the expiration date with day-of-month clamping.

A project's `timeline_posture` reports how it stands against whichever of those two milestones is still outstanding. When `pad_filed_at` has not been set, the outstanding milestone is the pre-application document deadline. Once `pad_filed_at` is set but `application_filed_at` is not, the outstanding milestone becomes the application deadline. Once both are set, no milestone remains outstanding and the posture is `ON_TRACK` unconditionally.

Where a milestone is outstanding, the system counts the whole days from the logical clock's date to the milestone date. When that count is negative — the milestone date is already in the past — the posture is `DELINQUENT`. When the count is zero or more but no greater than 180 days, the posture is `AT_RISK`; the milestone date itself therefore yields a count of zero and reads `AT_RISK`, not `DELINQUENT`. Otherwise the posture is `ON_TRACK`. The posture is persisted on the project with an initial value of `ON_TRACK`, and it is refreshed at exactly four moments: when a project is registered, when the pre-application document is filed, when a license application is filed, and when the compliance sweep runs. No other operation touches it.

### 2.8. Regulatory Posture: The Project-Wide Gate

Alongside the timeline posture, each project carries a `regulatory_posture` whose value is one of `OPEN`, `RESTRICTED` or `FROZEN`, starting at `OPEN`. It is not a state a client sets; it is recomputed from stored counters at the end of every request that mutates a project or any of its children, and it is always recomputed from scratch rather than nudged in one direction.

The recomputation evaluates two tiers in a fixed order, and the first tier that matches wins. The posture is `FROZEN` when any of the following holds: the project's `wqc_status` is `DENIED`, or its `compliance_flag_count` is greater than zero, or its `timeline_posture` is `DELINQUENT`. Otherwise the posture is `RESTRICTED` when any of the following holds: its `unresolved_mandatory_comment_count` is greater than zero, or its `open_deficiency_count` is greater than zero, or its `economically_infeasible` flag is true while `infeasibility_waiver_granted` is false, or its `timeline_posture` is `AT_RISK`. When neither tier matches, the posture is `OPEN`.

The gate semantics are as follows. Under `OPEN` there is no posture gate at all. Under `FROZEN`, every licensee-initiated and agency-initiated mutation of the project or any of its children is rejected with `ERR_PROJECT_POSTURE_FROZEN` (HTTP 409), with five exemptions that exist precisely so the licensee can dig itself out: curing an application, scheduling an obligation, certifying an obligation, filing an annual compliance report, and running the compliance sweep. Under `RESTRICTED`, study work, settlement work and application filing all proceed normally — application filing carries its own explicit economic check rather than relying on the posture — but order issuance is rejected with `ERR_PROJECT_POSTURE_RESTRICTED` (HTTP 409).

Because the posture is derived from counters that child transitions themselves recompute, a single child write can move the posture two tiers within one request. Certifying the last overdue obligation on a project whose only problem was that obligation takes the posture from `FROZEN` straight to `OPEN` in the same response.

### 2.9. Derived Counters, Cascade Propagation and Version Semantics

The system keeps a substantial amount of derived state, and it keeps it eagerly. A single request routinely rewrites derived fields on several resources at several levels, and every resource so rewritten has its `updated_at` refreshed and its `version` incremented, exactly as though a client had modified it directly. There is no lazy reconciliation and no background job: by the time a response is emitted, every counter, ledger figure and posture affected by the request already reflects the new reality.

The propagation chains that recur throughout §3 are worth naming up front. Comment activity on a study plan rewrites that plan's `open_comment_count` and `unresolved_mandatory_comment_count`; the plan's counters in turn rewrite the project's `unresolved_mandatory_comment_count`; and that project counter rewrites `regulatory_posture`. Anything that changes which mitigation measures are economically live, or changes the cost inputs of a live measure, re-runs the whole project burden ledger described in §3.7, whose final output `economically_infeasible` again rewrites `regulatory_posture`. Anything that changes an obligation's status rewrites the owning order's `open_violation_count`, which can flip the order's `compliance_state`, which rewrites the project's `compliance_flag_count`, which once again rewrites `regulatory_posture`.

Three project counters are maintained purely by counting rows and are named here so their definitions are unambiguous. `unresolved_mandatory_comment_count` is the number of consultation comments with `is_mandatory_condition` true and `resolution_status` `OPEN` whose study plan belongs to the project and whose plan status is anything other than `SUPERSEDED`. `open_deficiency_count` is the number of the project's license applications whose `filing_status` is `DEFICIENT`. `compliance_flag_count` is the number of the project's license orders whose `compliance_state` is `COMPLIANCE_FLAGGED`.

### 2.10. Reference Integrity in a Flat Namespace

Because collections are peers rather than nested, references travel in request bodies. Three integrity layers apply, and they are applied in this order.

First, identifiers that appear in the URL are resolved left to right, and the first identifier that names no existing row decides the response: a request naming `project_id`, `dam_id`, `site_id`, `study_plan_id`, `study_id`, `comment_id`, `party_id`, `settlement_id`, `signature_id`, `wqc_id`, `measure_id`, `application_id`, `obligation_id` or `order_id` that resolves to nothing is answered with that entity's not-found code — `ERR_PROJECT_NOT_FOUND`, `ERR_DAM_NOT_FOUND`, `ERR_SITE_NOT_FOUND`, `ERR_STUDY_PLAN_NOT_FOUND`, `ERR_STUDY_NOT_FOUND`, `ERR_COMMENT_NOT_FOUND`, `ERR_PARTY_NOT_FOUND`, `ERR_SETTLEMENT_NOT_FOUND`, `ERR_WQC_NOT_FOUND`, `ERR_MEASURE_NOT_FOUND`, `ERR_APPLICATION_NOT_FOUND`, `ERR_OBLIGATION_NOT_FOUND` or `ERR_ORDER_NOT_FOUND` respectively — all at HTTP 404.

Second, every reference supplied in a request body is resolved the same way and yields the same not-found code for the referenced entity. This covers dam and site creation, study-plan creation, study creation, comment filing, party registration, settlement creation, signature recording, water-quality certification requests, measure creation and application filing. `prerequisite_measure_id` that names no measure yields `ERR_MEASURE_NOT_FOUND`, and `amends_order_id` that names no order yields `ERR_ORDER_NOT_FOUND`.

Third, when a single request body carries two references that both hang off a project, those references must hang off the *same* project. Mixing projects is a bad reference, not a state error, and it is rejected with `ERR_CROSS_PROJECT_REFERENCE` (HTTP 422). This applies to study creation, where the study plan and the field site must share a project; to comment filing, where the study plan and the authoring party must share a project; to signature recording, where the settlement and the signing party must share a project; to measure creation, where the settlement and the prerequisite measure must belong to the measure's own project; and to application filing, where the amended order must belong to the project being filed on.

### 2.11. Stale-Version Protection on Project-Scoped Creates

Two creates in this system can silently destroy work a client never saw, so both take a project version pin as a non-optional input field named `expected_project_version`.

Opening a settlement — the create at `POST /relicensing/settlements` — must carry `expected_project_version` matching the target project's current `version`. If the project's version has advanced since the client last read it, the create is rejected with `ERR_STALE_PROJECT_VERSION` (HTTP 412). The protection is necessary because a new settlement legitimately supersedes a prior settlement that is still `NEGOTIATING` or `CIRCULATED` and cascades that settlement's `PROPOSED` measures to `SUPERSEDED`; no state precondition blocks the write, so the version pin is the only thing that stops a writer whose view of the project predates an earlier supersede from discarding work it never observed.

Filing a license application — the create at `POST /relicensing/applications` — likewise must carry `expected_project_version` matching the target project's current `version`, and a mismatch is likewise rejected with `ERR_STALE_PROJECT_VERSION` (HTTP 412). Here the exposure is different: an amendment filing supersedes a prior pending amendment on the same order, and every filing snapshots the study plan, settlement, measure set and burden total as they stand at that instant. A stale view would pin a snapshot the client never observed.

No other endpoint in the system takes a version field. Endpoints not named above perform no stale-version check.

### 2.12. Validation Precedence and Segregation of Duties

When a single request violates more than one rule, the response is determined by a fixed precedence ladder rather than by whichever check the implementation happens to reach first. Reading top to bottom, the first violated rule wins:

1. The request carries an `X-User-ID` header naming a known user — `ERR_UNAUTHORIZED` (401), on every endpoint except the two logical-clock endpoints.
2. The acting role appears among the endpoint's permitted roles — `ERR_ROLE_NOT_PERMITTED` (403), on every endpoint that declares a role list.
3. For `AgencyReviewer` and `Stakeholder`, the acting user resolves to a party registered on the project the target entity belongs to — `ERR_ROLE_NOT_PERMITTED` (403), on comment filing, signature recording, study-plan determination and study review decision, which are the only mutating endpoints open to those two roles; read endpoints apply no project scoping. Because this rung needs the target entity's project, it is evaluated only once that one entity has been resolved: the determination and review-decision endpoints resolve their path identifier first, and comment filing and signature recording read and resolve the body's `study_plan_id` or `settlement_id` first, so an omitted or unresolvable identifier of that entity is answered with `ERR_INVALID_REQUEST` or that entity's not-found code ahead of this rung. Every other reference of the request — including the `party_id` in the body — is still resolved after it.
4. Every identifier in the URL resolves to an existing row of its expected entity — the corresponding not-found code at 404, on every endpoint with a path identifier.
5. Every reference in the request body resolves to an existing row — the referenced entity's not-found code at 404.
6. References in one body belong to the same project — `ERR_CROSS_PROJECT_REFERENCE` (422).
7. Required body fields are present and non-null — `ERR_INVALID_REQUEST` (400), on every create and amend operation.
8. Field types, enum membership and numeric domains hold — `ERR_INVALID_REQUEST` (400), on every create and amend operation. Dollar amounts and megawatt-hour quantities must be zero or greater; `installed_capacity_mw` and `base_annual_generation_mwh` must be greater than zero; `vote_weight` must be at least 1; `implementation_months` must be zero or greater; `release_days` must be between 0 and 365 inclusive; `inspection_interval_months` must be at least 6 and at most 60; `min_rest_buffer_days` must be zero or greater; `max_concurrent_field_activities` must be at least 1; and date fields must be ISO 8601.
9. Interval payloads are ordered — `ERR_INVALID_REQUEST` (400). On study creation, `fieldwork_window_start` must be strictly earlier than `fieldwork_window_end`, because the fieldwork window is half-open. On obligation scheduling, `activity_window_start` must be earlier than or equal to `activity_window_end`, because the activity window is closed at both ends.
10. Pagination parameters are in range — `ERR_VALIDATION` (400), on every list endpoint.
11. `has_conditioning_authority` is true only for a party whose `party_type` is `AGENCY` — `ERR_INVALID_REQUEST` (400), on party registration.
12. `expected_project_version` equals the target project's `version` — `ERR_STALE_PROJECT_VERSION` (412), on settlement creation and application filing.
13. Uniqueness holds — `ERR_DUPLICATE_KEY` (409). `license_number` is unique across all projects, `dam_code` is unique within a project, `site_code` is unique within a project, and `order_number` is unique globally.
14. A project holds at most one water-quality certification in `REQUESTED` status, and a certification may be requested only while the project's `stage` is `STUDY_PHASE`, `APPLICATION_FILED` or `UNDER_ENVIRONMENTAL_REVIEW` — `ERR_WQC_STATE_INVALID` (409).
15. The project's `regulatory_posture` is not `FROZEN` — `ERR_PROJECT_POSTURE_FROZEN` (409), on every licensee-initiated or agency-initiated mutation of a project or a child of a project, other than the five cure paths named in §2.8.
16. The project's `stage` permits the operation — `ERR_PROJECT_STAGE_INVALID` (409).
17. The target entity's own status permits the requested transition — the matching state error at 409: `ERR_STUDY_PLAN_STATE_INVALID`, `ERR_STUDY_STATE_INVALID`, `ERR_SETTLEMENT_STATE_INVALID`, `ERR_WQC_STATE_INVALID`, `ERR_APPLICATION_STATE_INVALID`, `ERR_ORDER_STATE_INVALID` or `ERR_OBLIGATION_STATE_INVALID`.
18. A comment is resolved only while it is `OPEN` — `ERR_COMMENT_ALREADY_RESOLVED` (409).
19. A new settlement is not opened while an `EXECUTED` settlement exists on the project — `ERR_SETTLEMENT_STATE_INVALID` (409).
20. A settlement is not withdrawn while an order of the project is `EFFECTIVE` or `COMPLIANCE_FLAGGED` — `ERR_ORDER_STATE_INVALID` (409).
21. A signature is recorded only while its settlement is `CIRCULATED` — `ERR_SIGNATURE_ROUND_CLOSED` (409).
22. A party has not already signed the current round — `ERR_DUPLICATE_SIGNATURE` (409).
23. Study-plan approval requires that plan's `unresolved_mandatory_comment_count` to be zero — `ERR_UNRESOLVED_MANDATORY_COMMENTS` (409).
24. Settlement execution requires the project to have a study plan in `APPROVED` status — `ERR_STUDY_PLAN_NOT_APPROVED` (409).
25. Filing an original relicense application requires the project to have exactly one study plan in `APPROVED` status — `ERR_STUDY_PLAN_NOT_APPROVED` (409).
26. Filing an original relicense application requires every resource study of that approved plan to have `review_status` `ACCEPTED` — `ERR_STUDY_NOT_ACCEPTED` (409).
27. Filing an original relicense application requires the project to have a water-quality certification on file, meaning `wqc_status` is anything other than `NONE` — `ERR_WQC_STATE_INVALID` (409).
28. Advancing an application to `FINAL_EA` requires every measure of the project whose `source` is `WQC_CONDITION` to carry a `DEFINITIVE` estimate — `ERR_DEFINITIVE_ESTIMATE_REQUIRED` (409).
29. Order issuance requires the project's `wqc_status` to be `CERTIFIED_WITH_CONDITIONS` or `WAIVED` — `ERR_WQC_CONDITION_NOT_INCORPORATED` (422).
30. Scheduling a measure-implementation obligation whose measure names a `prerequisite_measure_id` requires that prerequisite measure to be `IMPLEMENTED` — `ERR_PREREQUISITE_NOT_IMPLEMENTED` (409).
31. `prerequisite_measure_id` belongs to the same project and closes no cycle in the prerequisite graph — `ERR_PREREQUISITE_CYCLE` (422), on measure creation and measure amendment.
32. A study's buffered fieldwork window does not overlap another active study's buffered window at the same site — `ERR_SITE_WINDOW_CONFLICT` (409).
33. An annual report's period has started and has not already been filed for the same basis and year — `ERR_REPORT_PERIOD_INVALID` (409).
34. An obligation is certified only on or after its `activity_window_start` — `ERR_CERTIFICATION_TOO_EARLY` (409).
35. The pre-application document is not filed after its deadline, and an original relicense application is not filed after its deadline — `ERR_FILING_DEADLINE_PASSED` (409).
36. A study at a site whose `cultural_sensitivity` is `HIGH` supplies a non-empty `cultural_clearance_reference` — `ERR_CULTURAL_CLEARANCE_MISSING` (422).
37. Dam field-activity capacity is respected — `ERR_DAM_ACTIVITY_CAPACITY_EXCEEDED` (409).
38. The user recording a `DEFINITIVE` cost estimate is not the user who created the measure — `ERR_SEGREGATION_OF_DUTIES` (409).
39. The user certifying an obligation did not submit a study report in the same resource category on the same project — `ERR_SEGREGATION_OF_DUTIES` (409).
40. Settlement execution requires the tallied support percentage to reach the execution threshold — `ERR_SUPPORT_THRESHOLD_NOT_MET` (422).
41. Settlement execution is rejected when a party holding conditioning authority recorded an opposing position in the current round — `ERR_CONDITIONING_PARTY_VETO` (422).
42. Application filing is rejected when the project's `burden_ratio_pct` has reached the economic-feasibility ceiling and no infeasibility waiver is in force — `ERR_BURDEN_RATIO_EXCEEDED` (422).
43. Order issuance is rejected when the project's `regulatory_posture` is `RESTRICTED` — `ERR_PROJECT_POSTURE_RESTRICTED` (409).

Two rules in that ladder implement **segregation of duties** within the licensee's own organisation, and both are worth restating because they compare one `X-User-ID` against another rather than against a role. The licensee employee who created a mitigation measure may not be the licensee employee who signs off its definitive cost estimate: the server keeps `created_by_user_id` from the creating request and refuses a definitive estimate from that same user, storing `definitive_estimate_by_user_id` only when the two differ. Separately, the licensee employee who submitted a resource study's report — recorded as `report_submitted_by_user_id` — may not later certify a compliance obligation whose measure sits in that same `resource_category` on that same project. Both rejections carry `ERR_SEGREGATION_OF_DUTIES` (HTTP 409).

## 3. Business Logic & Workflows

### 3.1. Standing Up a Relicensing Project

The `Regulator` opens the file. Registering a **RelicensingProject** requires the `license_number` of the existing license being relicensed, which must be non-empty and unique across every project in the system, a human-readable `project_name`, the plant's nameplate `installed_capacity_mw`, the plant's `base_annual_generation_mwh` — its average annual generation before any mitigation, which later serves as the denominator of the economic-feasibility ratio — and the `license_expiration_date` of the existing license as an ISO 8601 calendar date that must fall strictly after the logical clock's date at the moment of registration. A sixth input, `infeasibility_waiver_granted`, is optional and defaults to false; it carries forward a conditional finding from the prior license order, and while it is true the economic-feasibility ceiling is not enforced at application filing.

A freshly registered project begins in `stage` `PRE_FILING` with `wqc_status` `NONE` and `version` 1. Its `pad_filed_at`, `pad_year` and `application_filed_at` are all unset, and its entire burden ledger — `total_pme_annual_cost_usd`, `total_generation_loss_mwh`, `administrative_annual_charge_usd`, `total_annual_burden_usd` and `burden_ratio_pct` — reads zero with `economically_infeasible` false. Its `unresolved_mandatory_comment_count`, `open_deficiency_count` and `compliance_flag_count` all read zero, and `last_sweep_at` is unset. Registration immediately computes `timeline_posture` against the pre-application document milestone and then `regulatory_posture`, so a project registered fewer than 181 days before its pre-application deadline is `RESTRICTED` from birth.

The `Regulator` may later amend three fields of a project: `project_name`, `base_annual_generation_mwh` and `infeasibility_waiver_granted`. Changing either of the latter two re-runs the burden ledger and then the regulatory posture, because both are ledger inputs; every amendment increments the project's `version`.

Two kinds of physical infrastructure hang off the project, and both are filed by the `Licensee`. A **Dam** is registered with a `project_id`, a `dam_code` that must be unique within that project, a `hazard_class` of `HIGH`, `SIGNIFICANT` or `LOW`, and an `inspection_interval_months` between 6 and 60 inclusive that fixes how long after the license takes effect the first dam-safety inspection falls due. Two optional inputs shape later obligations: `eap_exercise_required` defaults to true and, when true, causes order issuance to generate an emergency-action-plan exercise obligation for that dam; and `max_concurrent_field_activities` defaults to 1 and caps how much overlapping field activity the dam can absorb, as §3.9 details.

A **StudySite** is likewise registered with a `project_id` and a `site_code` unique within the project, plus a `river_mile` that is carried for reporting only and drives no rule. Two optional inputs govern the site's fieldwork calendar: `min_rest_buffer_days` defaults to 0 and imposes a mandatory quiet period in days that must elapse after an occupying fieldwork window ends before the next window may begin at that site, and `cultural_sensitivity` defaults to `NONE` with `MODERATE` and `HIGH` as its other values. A site marked `HIGH` demands tribal or state historic-preservation clearance on every study placed there.

### 3.2. The Pre-Application Document and Deadline Posture

The first thing the `Licensee` files is the **pre-application document**, and filing it advances the project's `stage` from `PRE_FILING` to `PAD_FILED`. The payload is nearly empty: an optional `filing_note` is the only input. The operation is permitted only while `stage` is `PRE_FILING`, so a second filing attempt is rejected with `ERR_PROJECT_STAGE_INVALID`, and only while the logical clock's date is on or before the pre-application deadline — 66 months before `license_expiration_date` — with a late attempt rejected as `ERR_FILING_DEADLINE_PASSED`.

Filing stamps `pad_filed_at` with the logical clock and derives `pad_year` as the calendar year of that instant. That year matters far beyond the filing itself: it is the base year against which every mitigation measure's capital cost is escalated, as §3.7 explains. With `pad_filed_at` now set, the outstanding milestone shifts to the application deadline, so the filing recomputes `timeline_posture` against that later date and then recomputes `regulatory_posture`, and it increments the project's `version`.

Consider a project whose existing license expires on the last day of 2033. Its pre-application deadline lands on the last day of June 2028 and its application deadline on the last day of December 2031. With the clock at the first of August 2026 and nothing filed, the slack to the pre-application milestone is 699 days and the posture is `ON_TRACK`. Move the clock to the second of January 2028 and the slack is exactly 180 days, which reads `AT_RISK`; a day later it is 179 days and still `AT_RISK`. Move the clock to the first of July 2028 with the document still unfiled and the slack is negative one day: the posture becomes `DELINQUENT`, which in turn drives `regulatory_posture` to `FROZEN` and locks the project out of everything except the five cure paths.

### 3.3. Study Plan Development, Consultation Comments and Agency Determination

Once the project is at `PAD_FILED` or beyond, the `Licensee` files **study plans**. Creating one requires only the owning `project_id` and a `plan_title`, and the new plan begins in `DRAFT` with `revision_round` 0, unset `submitted_at` and `approved_at`, and `open_comment_count`, `unresolved_mandatory_comment_count` and `attached_study_count` all zero. The very first plan created for a project performs an automatic bubble-up, advancing the project's `stage` from `PAD_FILED` to `STUDY_PHASE` and incrementing the project's `version`; later plans leave the stage alone. Creating a plan before the pre-application document has been filed is rejected with `ERR_PROJECT_STAGE_INVALID`.

Only one plan is allowed to be in flight at a time, and the system enforces that by superseding rather than refusing. When a new plan is created for a project that already has a plan in `DRAFT`, `UNDER_AGENCY_REVIEW` or `REVISION_REQUIRED`, that prior plan's status becomes `SUPERSEDED` and its `version` is incremented. Its comments keep their own `resolution_status` untouched but stop counting toward the project's `unresolved_mandatory_comment_count`, which is recomputed, followed by `regulatory_posture` — so superseding a plan burdened with open mandatory comments can move a project out of `RESTRICTED`. A plan that has reached `APPROVED` is never superseded, and a second `APPROVED` plan cannot arise, because submission is impossible from `APPROVED`.

Submitting a plan for agency review moves it `DRAFT → UNDER_AGENCY_REVIEW` or, on a later cycle, `REVISION_REQUIRED → UNDER_AGENCY_REVIEW`. Both paths carry the same requirements and the same effects: an optional `submission_note` is the only body input, the plan must have `attached_study_count` of at least 1 — an empty plan is rejected with `ERR_INVALID_REQUEST` — and the project's `regulatory_posture` must not be `FROZEN`. Submission stamps `submitted_at` with the logical clock and increments the plan's `version`. Submitting from `UNDER_AGENCY_REVIEW`, `APPROVED` or `SUPERSEDED` is rejected with `ERR_STUDY_PLAN_STATE_INVALID`.

While a plan is open, consulted parties weigh in. An `AgencyReviewer` or a `Stakeholder` files a **ConsultationComment** with a payload carrying the `study_plan_id` it is filed against, the `party_id` of the authoring party — which must be the acting user's own party — the `resource_category` the comment concerns, drawn from `FISH_PASSAGE`, `WATER_QUALITY`, `RECREATION` and `CULTURAL`, and a non-empty `comment_text`. The payload also admits an `is_mandatory_condition` flag, but the stored value is not the client's: the server sets `is_mandatory_condition` to true exactly when the authoring party's `has_conditioning_authority` is true at the moment of filing, and to false otherwise, whatever the request said. A new comment begins with `resolution_status` `OPEN`, `disposition` unset and `reopen_count` 0. Filing increments the plan's `open_comment_count` and, for a mandatory comment, also the plan's `unresolved_mandatory_comment_count`, together with the plan's `version`; the project's `unresolved_mandatory_comment_count` and then its `regulatory_posture` are recomputed, so the first mandatory comment on a project takes it from `OPEN` to `RESTRICTED`.

The `Licensee` disposes of comments one at a time. Resolving a comment moves it `OPEN → RESOLVED`, requires a `disposition` of `ADOPTED`, `DEFERRED` or `REJECTED` in the body alongside an optional `resolution_note`, and is permitted only while the parent plan's status is `DRAFT`, `UNDER_AGENCY_REVIEW` or `REVISION_REQUIRED`. A comment that is already `RESOLVED` is rejected with `ERR_COMMENT_ALREADY_RESOLVED`. Resolution stores the supplied `disposition` and stamps `resolved_at` with the logical clock; it decrements the plan's `open_comment_count` and, when the comment was mandatory, also the plan's `unresolved_mandatory_comment_count`, incrementing the plan's `version`; and it recomputes the project's `unresolved_mandatory_comment_count` and then `regulatory_posture`, which returns a project from `RESTRICTED` to `OPEN` once the count reaches zero and nothing else restricts it.

A determination closes the review round, and only an `AgencyReviewer` whose backing party holds `has_conditioning_authority` may make one — an agency reviewer without that authority receives `ERR_ROLE_NOT_PERMITTED`, and a `Stakeholder` receives the same regardless of what comments it has on file. The body carries a `determination` of either `APPROVE` or `REQUIRE_REVISION`, an optional `reopen_deferred_comments` flag and an optional `determination_note`. Either determination requires the plan to be in `UNDER_AGENCY_REVIEW`; a determination on any other status is rejected with `ERR_STUDY_PLAN_STATE_INVALID`. The two branches then diverge completely.

An `APPROVE` determination moves the plan `UNDER_AGENCY_REVIEW → APPROVED`. It is permitted only when the plan's `unresolved_mandatory_comment_count` is zero, and a plan still carrying an open mandatory comment is rejected with `ERR_UNRESOLVED_MANDATORY_COMMENTS`. On success it stamps `approved_at` with the logical clock, recomputes the project's `unresolved_mandatory_comment_count` and then `regulatory_posture`, and increments the plan's `version`. `APPROVED` is terminal for the plan.

A `REQUIRE_REVISION` determination moves the plan `UNDER_AGENCY_REVIEW → REVISION_REQUIRED` and increments the plan's `revision_round` by 1. It imposes no comment precondition at all. When `reopen_deferred_comments` is true, it also performs a compensating sweep over the plan's comments: every comment whose `resolution_status` is `RESOLVED` and whose `disposition` is `DEFERRED` goes back `RESOLVED → OPEN`, has its `disposition` cleared to unset, and has its `reopen_count` incremented by 1. Comments dispositioned `ADOPTED` or `REJECTED` are never reopened. That reopening recomputes the plan's `open_comment_count` and `unresolved_mandatory_comment_count`, which recompute the project's `unresolved_mandatory_comment_count`, which recomputes `regulatory_posture` — taking a project from `OPEN` back to `RESTRICTED` when the restored count is greater than zero. The determination increments the plan's `version` in either branch. The cycle `REVISION_REQUIRED → UNDER_AGENCY_REVIEW → REVISION_REQUIRED` may repeat without bound.

### 3.4. Resource Studies: Fieldwork Calendars and Report Review

A **ResourceStudy** is the unit of actual field science, and it carries two entirely independent status dimensions. `fieldwork_status` tracks the physical effort through `PLANNED`, `IN_PROGRESS`, `SUSPENDED` and `COMPLETED`, starting at `PLANNED`. `review_status` tracks the agency's assessment of the written report through `NOT_SUBMITTED`, `UNDER_REVIEW`, `ACCEPTED` and `ADDITIONAL_REQUIRED`, starting at `NOT_SUBMITTED`. A study is finished only when it is `COMPLETED` on the first dimension and `ACCEPTED` on the second.

The `Licensee` creates a study with a payload naming the `study_plan_id` it belongs to, the `site_id` whose fieldwork calendar it will occupy, a `resource_category` from `FISH_PASSAGE`, `WATER_QUALITY`, `RECREATION` and `CULTURAL`, a `study_title`, and the `fieldwork_window_start` and `fieldwork_window_end` dates that bound the field effort. That window is **half-open**: the start date is inside the window and the end date is outside it, and the end must be strictly after the start. An optional `cultural_clearance_reference` records a tribal or state historic-preservation clearance; it is stored verbatim wherever it is supplied, but it is *required* — non-empty — whenever the named site's `cultural_sensitivity` is `HIGH`, whatever the study's own `resource_category` may be. A study at a `HIGH`-sensitivity site without one is rejected with `ERR_CULTURAL_CLEARANCE_MISSING`. Creation sets `fieldwork_status` `PLANNED` and `review_status` `NOT_SUBMITTED`, leaves `additional_round_count` at 0 and `report_submitted_at` and `report_submitted_by_user_id` unset, and increments the owning plan's `attached_study_count` and `version`.

Field sites are physically exclusive, and the rule that enforces this is the tightest temporal constraint in the system. Extend the new study's half-open window at its end by the site's `min_rest_buffer_days` to obtain its **buffered window**. That buffered window must not overlap the buffered window of any other study at the same site whose `fieldwork_status` is anything other than `COMPLETED` — a `PLANNED`, `IN_PROGRESS` or `SUSPENDED` study all continue to occupy the calendar, and a suspended study is emphatically not a vacancy. Two buffered windows that touch exactly at the boundary do not overlap, so a new window may begin on the very day a predecessor's buffer expires. A conflict is rejected with `ERR_SITE_WINDOW_CONFLICT`.

The fieldwork dimension advances through a single action endpoint whose body carries an `action` and an optional `fieldwork_note`. An `action` of `START` moves `PLANNED → IN_PROGRESS` and additionally requires that the parent plan's status be `UNDER_AGENCY_REVIEW`, `REVISION_REQUIRED` or `APPROVED`, and that the project's `regulatory_posture` not be `FROZEN`. `SUSPEND` moves `IN_PROGRESS → SUSPENDED`. `RESUME` moves `SUSPENDED → IN_PROGRESS`. `COMPLETE` moves `IN_PROGRESS → COMPLETED`. Each of the four increments the study's `version` and touches `fieldwork_status` alone — `review_status` is never modified by a fieldwork action. An action that does not match the current `fieldwork_status` is rejected with `ERR_STUDY_STATE_INVALID`.

Submitting the study report is the one place where the two dimensions are coupled on the forward path. A report submission, whose body carries only an optional `report_note`, moves `review_status` `NOT_SUBMITTED → UNDER_REVIEW` on the first pass and `ADDITIONAL_REQUIRED → UNDER_REVIEW` on any subsequent pass. Either way it requires `fieldwork_status` to be `COMPLETED`: a report filed while the field effort is still `PLANNED`, `IN_PROGRESS` or `SUSPENDED` is rejected with `ERR_STUDY_STATE_INVALID`, and so is a report filed while `review_status` is already `UNDER_REVIEW` or `ACCEPTED`. Submission stamps `report_submitted_at` with the logical clock, records `report_submitted_by_user_id` from the acting `X-User-ID`, and increments the study's `version`. That recorded user identity is what later constrains obligation certification under the segregation-of-duties rule of §2.12.

An `AgencyReviewer` closes the review with a decision whose body carries a `decision` and an optional `review_note`, and which requires `review_status` to be `UNDER_REVIEW`. A `decision` of `ACCEPT` moves `review_status` `UNDER_REVIEW → ACCEPTED` and increments the study's `version`; nothing else changes, and `ACCEPTED` is where the review dimension comes to rest. A `decision` of `REQUIRE_ADDITIONAL` moves `review_status` `UNDER_REVIEW → ADDITIONAL_REQUIRED`, increments `additional_round_count` by 1, and — uniquely among the study transitions — reaches across dimensions to move `fieldwork_status` `COMPLETED → IN_PROGRESS` on the same row, because more data means more field effort. It too increments the study's `version`. The additional-study loop is bounded at two rounds: once `additional_round_count` has reached 2, a further `REQUIRE_ADDITIONAL` decision is rejected with `ERR_STUDY_STATE_INVALID`, forcing the reviewer either to accept or to leave the study unaccepted. A decision taken while `review_status` is anything other than `UNDER_REVIEW` is likewise rejected with `ERR_STUDY_STATE_INVALID`.

### 3.5. Settlement Negotiation with Agencies, Tribes and Organizations

Before anyone can negotiate, the `Regulator` registers the consulted parties. A **SettlementParty** is created with a `project_id`, a `party_name` for the agency, tribe or nongovernmental organization, and a `party_type` of `AGENCY`, `TRIBE` or `NGO`, which also determines the role its people act in — `AGENCY` parties back `AgencyReviewer` users while `TRIBE` and `NGO` parties back `Stakeholder` users. Three optional inputs complete the registration: `has_conditioning_authority` defaults to false and may be set true only for a party whose `party_type` is `AGENCY`, with any other combination rejected as `ERR_INVALID_REQUEST`; `vote_weight` defaults to 1 and must be at least 1; and `contact_user_id` binds the `X-User-ID` of the party's agency-reviewer or stakeholder user to this party row. A party has no lifecycle beyond registration — it is configuration data that reaches its `REGISTERED` state at creation and stays there. Registering a party nonetheless has a downstream consequence: it changes the denominator that the support tally will use on every future round of every non-terminal settlement of that project.

Mandatory conditioning authority is the single most consequential flag on a party. A party holding it files comments that are automatically mandatory conditions, it alone may render study-plan determinations, and its opposition alone can veto settlement execution.

The `Licensee` opens a **Settlement** with a `project_id`, a `title` and the `expected_project_version` pin described in §2.11. The settlement starts in `NEGOTIATING` with `round_number` 1, unset `circulated_at`, `executed_at` and `withdrawn_at`, and `support_pct`, `total_vote_weight` and `included_measure_count` all zero. Opening a settlement while the project already has one in `EXECUTED` status is rejected with `ERR_SETTLEMENT_STATE_INVALID`. Opening one while a prior settlement of the project is `NEGOTIATING` or `CIRCULATED` is allowed and supersedes that prior settlement: its status becomes `SUPERSEDED`, every mitigation measure attached to it that is still `PROPOSED` cascades to `SUPERSEDED`, and its `version` is incremented. Because those `PROPOSED` measures were never economically live, no ledger figure moves. The create also increments the project's `version`.

Circulating a settlement for signature moves it `NEGOTIATING → CIRCULATED`, with an optional `circulation_note` as its only body input. It requires that the settlement be `NEGOTIATING`, that the project's `regulatory_posture` not be `FROZEN`, and that the project have at least two registered parties — a settlement among fewer than two parties is rejected with `ERR_SETTLEMENT_STATE_INVALID`. Circulation stamps `circulated_at` with the logical clock, sets `total_vote_weight` to the sum of `vote_weight` over all of the project's parties, and increments the settlement's `version`. Circulating from any other status is rejected with `ERR_SETTLEMENT_STATE_INVALID`.

While a settlement is `CIRCULATED`, an `AgencyReviewer` or `Stakeholder` records a **SettlementSignature** by naming the `settlement_id`, its own `party_id` — which must equal the acting `X-User-ID` — and a `position` of `SUPPORT`, `OPPOSE` or `ABSTAIN`. The signature is immutable once written: it copies `round_number` from the settlement's current round, stamps `signed_at` from the logical clock, and leaves `share_pct` unset until the round is tallied. Recording a signature while the settlement is not `CIRCULATED` is rejected with `ERR_SIGNATURE_ROUND_CLOSED`, and a second signature by the same party within the same round is rejected with `ERR_DUPLICATE_SIGNATURE`. Signatures from earlier rounds are retained forever as an append-only ledger.

Tallying the round is where the negotiation mathematics lives. The body carries an `intended_outcome` and an optional `tally_note`, and the tally itself runs for every outcome before any branch-specific check. First, the denominator: `total_vote_weight` is the sum of `vote_weight` over **all** of the project's registered parties, including parties that never signed at all — non-signers dilute support because they stay in the denominator. Then, for each signature of the current round whose `position` is `SUPPORT`, that signature's `share_pct` is computed as 100 multiplied by the signing party's `vote_weight`, divided by `total_vote_weight`, rounded half up to two decimal places, and persisted on the signature row. Finally the settlement's `support_pct` is the sum of those already-rounded per-party shares, itself rounded half up to two decimal places. The evaluation order is pinned and it is not an accounting nicety: each share is rounded *before* summation, never after.

The arithmetic consequences are easy to state and easy to get wrong. Three parties each weighted 1, with two of them supporting, yield per-party shares of 33.33 each, a sum of 66.66, and a `support_pct` of 66.66 — below the execution threshold of 66.67, so execution is refused. Summing the unrounded two-thirds first would have produced 66.67 and wrongly executed. Parties weighted 1, 3 and 2 for a total of 6, with the weight-1 and weight-3 parties supporting, yield 16.67 plus 50.00 for a `support_pct` of exactly 66.67 — precisely at the threshold, which is sufficient. Four parties each weighted 1 with three supporting yield 25.00 three times over, a `support_pct` of 75.00, and comfortable execution.

An `intended_outcome` of `EXECUTE` attempts to move the settlement `CIRCULATED → EXECUTED`, and it clears four hurdles in this order. The settlement must be `CIRCULATED`, or the request is rejected with `ERR_SETTLEMENT_STATE_INVALID`. The project must already have a study plan in `APPROVED` status, or the request is rejected with `ERR_STUDY_PLAN_NOT_APPROVED` — settlements cannot be locked in before the study programme is settled. The tallied `support_pct` must be at least 66.67, or the request is rejected with `ERR_SUPPORT_THRESHOLD_NOT_MET`. And no party with `has_conditioning_authority` true may have recorded a `position` of `OPPOSE` in the current round, or the request is rejected with `ERR_CONDITIONING_PARTY_VETO`; a conditioning agency's opposition defeats the settlement no matter how much weight supports it. On success, the tally persists `support_pct` and `total_vote_weight`, stamps `executed_at` from the logical clock, moves every mitigation measure attached to this settlement that is still `PROPOSED` to `INCLUDED`, sets `included_measure_count` to the number of measures so moved, and increments the settlement's `version`. Those newly `INCLUDED` measures enter the economic picture, so the whole project burden ledger of §3.7 is recomputed — `total_pme_annual_cost_usd`, `total_generation_loss_mwh`, `administrative_annual_charge_usd`, `total_annual_burden_usd`, `burden_ratio_pct` and `economically_infeasible` — and the recomputed `economically_infeasible` then recomputes `regulatory_posture`, which is how a generous settlement can push a project into `RESTRICTED` at the very moment it succeeds.

An `intended_outcome` of `CLOSE_ROUND` ends the round without executing, and its effect depends on which round the settlement is in. Negotiation is capped at three rounds. Below round 3, closing the round moves the settlement `CIRCULATED → NEGOTIATING`: it persists the closed round's `support_pct`, increments `round_number` by 1, clears `circulated_at` back to unset, retains every prior-round signature unchanged, and increments the settlement's `version`. At round 3, there is nowhere left to go: closing the round moves the settlement `CIRCULATED → FAILED`, persists `support_pct`, cascades every attached measure still in `PROPOSED` to `SUPERSEDED`, and increments the settlement's `version`. No ledger figure moves on failure either, because `PROPOSED` measures were never in the ledger. The negotiation cycle `NEGOTIATING → CIRCULATED → NEGOTIATING` therefore runs at most three times.

Withdrawal is the compensating action for execution, and it is deliberately hard. It moves an `EXECUTED` settlement to `WITHDRAWN`, requires a `withdrawal_reason` in the body, and is permitted only while no license order of the project has a `compliance_state` of `EFFECTIVE` or `COMPLIANCE_FLAGGED` — once a license is live, its settlement cannot be unwound, and the attempt is rejected with `ERR_ORDER_STATE_INVALID`. Withdrawal from any status other than `EXECUTED` is rejected with `ERR_SETTLEMENT_STATE_INVALID`. On success it stamps `withdrawn_at` from the logical clock, resets `included_measure_count` to 0, moves every measure attached to this settlement whose `source` is `SETTLEMENT` and whose status is `INCLUDED` to `WITHDRAWN`, and moves every compliance obligation pointing at one of those measures whose status is `PENDING`, `SCHEDULED` or `OVERDUE` to `WAIVED`. Each waived obligation increments its own `version`, and where a waived obligation had been `OVERDUE` the owning order's `open_violation_count` is recomputed. Because the burden ledger is always rebuilt from the current measure set rather than adjusted incrementally, the withdrawal restores every ledger figure to exactly its pre-execution value, and `regulatory_posture` is then recomputed from those restored figures. The settlement's `version` is incremented.

### 3.6. State Water Quality Certification

The state's water-quality certification is a statutory precondition to a federal license, and the licensee cannot proceed to an order without one — or without the state having let its clock run out. The `Licensee` requests a **WaterQualityCertification** by naming the `project_id` and the `certifying_agency_name` of the state agency. A request is permitted only while the project's `stage` is `STUDY_PHASE`, `APPLICATION_FILED` or `UNDER_ENVIRONMENTAL_REVIEW`, and only while the project holds no other certification already in `REQUESTED` status; either violation is rejected with `ERR_WQC_STATE_INVALID`.

The new record begins in `REQUESTED` with `condition_count` 0, `decided_at` and `denial_reason` unset. It stamps `requested_at` from the logical clock and derives `statutory_waiver_date` as the date of `requested_at` plus 12 calendar months, with day-of-month clamping. It sets the project's `wqc_status` to `REQUESTED`, recomputes `regulatory_posture`, and increments the project's `version`. The project's `wqc_status` is always a mirror of the status of the project's most recently created certification, taking the newest by `created_at`, and it reads `NONE` when the project has never requested one; its possible values are therefore `NONE`, `REQUESTED`, `CERTIFIED_WITH_CONDITIONS`, `DENIED` and `WAIVED`.

Only the `StateCertifier` decides, and the decision body carries a `decision` plus, depending on the branch, `conditions` or `denial_reason`. Either branch requires the certification to be in `REQUESTED` status; a decision on an already-decided certification is rejected with `ERR_WQC_STATE_INVALID`. Both branches stamp `decided_at` from the logical clock and increment the project's `version`.

A `decision` of `ISSUE_WITH_CONDITIONS` moves the certification `REQUESTED → CERTIFIED_WITH_CONDITIONS` and requires the `conditions` array to be non-empty, rejecting an empty or absent array with `ERR_INVALID_REQUEST`. Each element of `conditions` describes a mitigation measure the state is imposing, and carries `measure_name`, `resource_category`, `capital_cost_usd`, `annual_om_cost_usd`, `construction_start_year`, `implementation_months`, `flow_release_cfs`, `gross_head_ft` and `release_days`. The system sets `condition_count` to the number of elements and then, for each element, creates a mitigation measure whose `source` is `WQC_CONDITION`, whose status is `INCLUDED` immediately — state conditions are not proposals to be negotiated — and whose `cost_estimate_variant` is `PRELIMINARY`, with all six derived cost and generation figures computed under the preliminary variant of §3.7. Because those measures are `INCLUDED` on arrival, each insertion feeds the project burden ledger: `total_pme_annual_cost_usd`, `total_generation_loss_mwh`, `administrative_annual_charge_usd`, `total_annual_burden_usd` and `burden_ratio_pct` are all recomputed, the recomputed `burden_ratio_pct` sets `economically_infeasible`, and that flag recomputes `regulatory_posture` — moving the project from `OPEN` to `RESTRICTED` the moment the ratio reaches 15.00 with no infeasibility waiver in force. Finally the project's `wqc_status` becomes `CERTIFIED_WITH_CONDITIONS`.

A `decision` of `DENY` moves the certification `REQUESTED → DENIED` and requires a non-empty `denial_reason`, rejecting an empty or absent one with `ERR_INVALID_REQUEST`. The reason text is stored on the record. The project's `wqc_status` becomes `DENIED`, which by itself drives `regulatory_posture` to `FROZEN`. That freeze does not stop at the project: every license application of the project whose `filing_status` is `FILED`, `UNDER_REVIEW` or `DEFICIENT` is moved to `SUSPENDED`, each such application incrementing its own `version`. A denial therefore halts the entire relicensing effort in a single request, and only the cure paths of §2.8 remain open.

The state does not get to sit on a request forever. When the compliance sweep of §3.9 runs at a logical-clock date on or after a `REQUESTED` certification's `statutory_waiver_date`, the certification moves `REQUESTED → WAIVED` by operation of the statutory clock rather than by anyone's decision: `decided_at` is stamped from the logical clock, the project's `wqc_status` becomes `WAIVED`, `regulatory_posture` is recomputed and the project's `version` is incremented. `WAIVED` is the only certification status no endpoint can produce directly, and — like `CERTIFIED_WITH_CONDITIONS` — it satisfies the certification precondition for order issuance.

### 3.7. Mitigation Measures: Dual-Variant Estimation and the Burden Ledger

A **PmeMeasure** is a protection, mitigation or enhancement measure: a fish ladder, a minimum-flow release, a boat ramp, a cultural-resources management plan. Measures are where relicensing becomes expensive, and the system prices each one and then rolls the prices into a project-level ledger that determines whether relicensing is still worth doing.

The `Licensee` creates a measure with a `project_id`, a `measure_name`, a `resource_category` from `FISH_PASSAGE`, `WATER_QUALITY`, `RECREATION` and `CULTURAL`, and a `source` that records where the measure came from. Three sources are accepted as request input — `SETTLEMENT`, `AGENCY_PRESCRIPTION` and `LICENSEE_PROPOSED` — while the fourth, `WQC_CONDITION`, is producible only by the water-quality cascade of §3.6 and is rejected when supplied by a client. The economic inputs are `capital_cost_usd` and `annual_om_cost_usd`, both of which must be zero or greater, a `construction_start_year`, and an `implementation_months` of zero or greater that fixes how long after the license takes effect this measure must be implemented. Three hydraulic inputs describe the generation the measure gives up: `flow_release_cfs` is the instream flow release in cubic feet per second and defaults to 0, `gross_head_ft` is the gross head bypassed by that release in feet and likewise defaults to 0, and `release_days` is the number of days per year the release applies, defaulting to 0 and capped at 365. Two optional references complete the payload: `settlement_id` names the settlement whose execution will include the measure and is required exactly when `source` is `SETTLEMENT`, and `prerequisite_measure_id` names another measure of the same project that must be implemented first.

The initial status depends entirely on the source. A measure whose `source` is `SETTLEMENT` begins in `PROPOSED` — it is a bargaining chip, not yet a commitment, and it contributes nothing to the ledger. Every other source begins in `INCLUDED` and counts immediately. Creation records `created_by_user_id` from the acting `X-User-ID`, leaves `definitive_estimate_by_user_id` unset, sets `cost_estimate_variant` to `PRELIMINARY`, requires the project's `regulatory_posture` not to be `FROZEN`, and requires that any `prerequisite_measure_id` belong to the same project and introduce no cycle into the prerequisite graph, which must remain acyclic — a self-reference or a cycle is rejected with `ERR_PREREQUISITE_CYCLE`. Creating an `INCLUDED` measure recomputes the project burden ledger and then `regulatory_posture`, and increments the project's `version`.

A measure's inputs may be amended while its status is `PROPOSED` or `INCLUDED`, and never once it is `IMPLEMENTED`, `WITHDRAWN` or `SUPERSEDED`. The amendable fields are `measure_name`, `capital_cost_usd`, `annual_om_cost_usd`, `construction_start_year`, `implementation_months`, `flow_release_cfs`, `gross_head_ft`, `release_days` and `prerequisite_measure_id`. An amendment re-runs the measure calculation under the measure's *current* `cost_estimate_variant` rather than resetting the variant, rejects a `prerequisite_measure_id` that would close a cycle with `ERR_PREREQUISITE_CYCLE`, recomputes the project burden ledger and `regulatory_posture` when the measure is `INCLUDED`, and increments the measure's `version`.

**The measure calculation.** Every measure carries six derived figures — `escalated_capital_usd`, `annualized_capital_usd`, `annual_cost_usd`, `annual_generation_loss_mwh`, `annual_generation_value_usd` and `annual_burden_usd` — and there are two variants of the arithmetic that produces them, tracked in `cost_estimate_variant`. Both variants share the cost skeleton and differ in one factor within it; they differ far more sharply in how generation loss is modelled.

Both variants begin with escalation. The number of escalation years is `construction_start_year` minus the project's `pad_year`, floored at zero so that a measure built before or during the pre-application year is never de-escalated. `escalated_capital_usd` is `capital_cost_usd`, multiplied by one plus the contingency allowance, multiplied by 1.03 raised to the power of the escalation years — a 3 percent annual escalation compounded over the interval — and the product is rounded half up to two decimal places. The contingency allowance is 25 percent under the preliminary variant and 10 percent under the definitive variant; a firmer estimate carries less padding. Next, `annualized_capital_usd` is `escalated_capital_usd` divided by the amortization life of the measure's `resource_category`, rounded half up to two decimal places. Those lives are 30 years for `FISH_PASSAGE`, 20 years for `WATER_QUALITY`, 15 years for `RECREATION` and 10 years for `CULTURAL`. Then `annual_cost_usd` is `annualized_capital_usd` plus `annual_om_cost_usd`, which is already exact to two decimal places and needs no further rounding.

Generation loss is where the two variants part company. Under the **preliminary** variant, loss is a flow-duration proxy that ignores head entirely: `annual_generation_loss_mwh` is `flow_release_cfs` multiplied by `release_days` multiplied by 0.048 megawatt-hours per cubic-foot-per-second-day, rounded half up to one decimal place. Under the **definitive** variant, loss is derived from the physical hydraulics: take `flow_release_cfs`, multiply by `gross_head_ft`, multiply by a plant efficiency of 0.85, divide by a hydraulic constant of 11.8 to obtain kilowatts, multiply by 24 hours and by `release_days` to obtain kilowatt-hours per year, divide by 1000 to convert to megawatt-hours, and round half up to one decimal place. `gross_head_ft` is consulted only by the definitive variant and is otherwise inert.

Both variants close identically. `annual_generation_value_usd` is `annual_generation_loss_mwh` multiplied by an energy price of 42.00 dollars per megawatt-hour, rounded half up to two decimal places. `annual_burden_usd` is `annual_cost_usd` plus `annual_generation_value_usd`.

Work an example to see why the variants cannot be reconciled by any single scaling factor. A `FISH_PASSAGE` measure with `capital_cost_usd` of 1,200,000.00, `annual_om_cost_usd` of 45,000.00, a project `pad_year` of 2026, a `construction_start_year` of 2029, `flow_release_cfs` of 120, `gross_head_ft` of 85 and `release_days` of 180 yields, under the preliminary variant, an `escalated_capital_usd` of 1,639,090.50, an `annualized_capital_usd` of 54,636.35, an `annual_cost_usd` of 99,636.35, an `annual_generation_loss_mwh` of 1036.8, an `annual_generation_value_usd` of 43,545.60 and an `annual_burden_usd` of 143,181.95. The same measure under the definitive variant yields an `escalated_capital_usd` of 1,442,399.64, an `annualized_capital_usd` of 48,079.99, an `annual_cost_usd` of 93,079.99, an `annual_generation_loss_mwh` of 3174.1, an `annual_generation_value_usd` of 133,312.20 and an `annual_burden_usd` of 226,392.19. The cost component falls while the generation component rises, and the two move independently.

**Recording the definitive estimate.** Switching a measure to the definitive variant is a distinct operation, restricted to the `Licensee` and gated by segregation of duties: the acting `X-User-ID` may not equal the measure's `created_by_user_id`, and an attempt by the creating user is rejected with `ERR_SEGREGATION_OF_DUTIES`. The body may revise `capital_cost_usd`, `annual_om_cost_usd` and `gross_head_ft` — the three inputs a firm engineering estimate typically sharpens — alongside an optional `estimate_note`. The operation flips `cost_estimate_variant` from `PRELIMINARY` to `DEFINITIVE`, stores `definitive_estimate_by_user_id` from the acting user, and re-runs all six derived figures under the definitive variant. When the measure is `INCLUDED` or `IMPLEMENTED`, the rewrite feeds straight through: the project burden ledger is recomputed and then `regulatory_posture`, so a single request moves both the cost path, downward through the smaller contingency, and the generation path, generally upward through the head-based physical model. The measure's `version` is incremented.

**The project burden ledger.** The project-level ledger is recomputed, in full, from the current measure set on every trigger — never adjusted incrementally — which is precisely why settlement withdrawal restores exact prior values. The triggers are every request that changes which measures are economically live or changes a live measure's cost inputs: measure creation, measure amendment, the water-quality conditions cascade, settlement execution, settlement withdrawal, a definitive-estimate switch, obligation certification, and an amendment of the project's own `base_annual_generation_mwh` or `infeasibility_waiver_granted`. The live set is every measure of the project whose status is `INCLUDED` or `IMPLEMENTED`; measures in `PROPOSED`, `WITHDRAWN` or `SUPERSEDED` are excluded.

The six steps run in this pinned order.

1. `total_pme_annual_cost_usd` is the sum of `annual_cost_usd` over the live set, rounded half up to two decimal places.
2. `total_generation_loss_mwh` is the sum of `annual_generation_loss_mwh` over the same live set, rounded half up to one decimal place.
3. The administrative charge tier is selected by comparing the step-1 total and nothing else — the charge never re-enters its own tier lookup. A `total_pme_annual_cost_usd` of 500,000.00 or less attracts a rate of 2 percent; a total above 500,000.00 but not above 2,000,000.00 attracts 3.5 percent; a total above 2,000,000.00 attracts 5 percent. `administrative_annual_charge_usd` is `total_pme_annual_cost_usd` multiplied by the selected rate, rounded half up to two decimal places.
4. The energy value of the forgone generation is `total_generation_loss_mwh` multiplied by 42.00 dollars per megawatt-hour, rounded half up to two decimal places. `total_annual_burden_usd` is then `total_pme_annual_cost_usd` plus `administrative_annual_charge_usd` plus that energy value.
5. Gross annual revenue is `base_annual_generation_mwh` multiplied by the same 42.00 dollars per megawatt-hour, rounded half up to two decimal places. `burden_ratio_pct` is 100 multiplied by `total_annual_burden_usd`, divided by that gross revenue, rounded half up to two decimal places.
6. `economically_infeasible` is true when `burden_ratio_pct` has reached 15.00 or more, and false below it.

A worked case makes the tier boundary and the ratio boundary concrete. Take a single definitive `WATER_QUALITY` measure with `capital_cost_usd` of 1,000,000.00, a `construction_start_year` equal to the project's `pad_year`, `annual_om_cost_usd` of 155,102.94, `flow_release_cfs` of 250, `gross_head_ft` of 100 and `release_days` of 229. Its `escalated_capital_usd` is 1,100,000.00, its `annualized_capital_usd` is 55,000.00, its `annual_cost_usd` is 210,102.94, its `annual_generation_loss_mwh` is 9897.5 and its `annual_generation_value_usd` is 415,695.00. At step 3, 210,102.94 does not exceed 500,000.00, so the rate is 2 percent and `administrative_annual_charge_usd` is 4,202.06. At step 4, `total_annual_burden_usd` is 210,102.94 plus 4,202.06 plus 415,695.00, or exactly 630,000.00. With `base_annual_generation_mwh` of 100,000 the gross revenue is 4,200,000.00 and `burden_ratio_pct` is exactly 15.00, which makes `economically_infeasible` true. With `base_annual_generation_mwh` of 120,000 instead, the gross revenue is 5,040,000.00, the ratio is 12.50, and the project remains feasible.

### 3.8. Application Filing and Environmental Review

Filing the **LicenseApplication** is the moment the accumulated work becomes a formal request. The body carries the `project_id`, an `application_type` of either `ORIGINAL_RELICENSE` or `AMENDMENT`, the `expected_project_version` pin of §2.11, an optional `amends_order_id` and an optional `filing_note`. An application is created with `filing_status` `FILED` and `ea_stage` `NOT_STARTED`, `deficiency_count` 0 and `last_deficiency_note` unset, and `filed_at` stamped from the logical clock.

Filing also takes a **snapshot** of everything the regulator will be reviewing, and those snapshot fields are deliberately not navigational references. `pinned_study_plan_id` and `pinned_study_plan_version` record the identity and observed `version` of the project's study plan in `APPROVED` status, so that a later mutation of that plan makes the pin visibly stale. `pinned_settlement_id` and `pinned_settlement_version` do the same for the project's settlement in `EXECUTED` status, and both remain unset when the project files without a settlement. `pinned_measure_ids` records the identifiers of every measure that is `INCLUDED` or `IMPLEMENTED` at filing time, ordered by `created_at` ascending. `pinned_total_annual_burden_usd` records the project's `total_annual_burden_usd` as observed at filing.

An `ORIGINAL_RELICENSE` filing clears a long gate, and every hurdle carries its own code. The project's `stage` must be `STUDY_PHASE`, or the filing is rejected with `ERR_PROJECT_STAGE_INVALID`. The project's `regulatory_posture` must not be `FROZEN`, or it is rejected with `ERR_PROJECT_POSTURE_FROZEN`. The project must have exactly one study plan in `APPROVED` status, or `ERR_STUDY_PLAN_NOT_APPROVED`. Every resource study of that approved plan must have `review_status` `ACCEPTED`, or `ERR_STUDY_NOT_ACCEPTED`. The project's `wqc_status` must be something other than `NONE` — `REQUESTED`, `CERTIFIED_WITH_CONDITIONS` or `WAIVED` all suffice at this stage — or `ERR_WQC_STATE_INVALID`. The logical clock's date must be on or before the application deadline, 24 months before `license_expiration_date`, or `ERR_FILING_DEADLINE_PASSED`. And the economics must hold: a `burden_ratio_pct` that has reached 15.00 while `infeasibility_waiver_granted` is false is rejected with `ERR_BURDEN_RATIO_EXCEEDED`, which is exactly the point of carrying the waiver flag forward from the prior order. On success the project's `stage` advances `STUDY_PHASE → APPLICATION_FILED`, `application_filed_at` is stamped from the logical clock, `timeline_posture` is recomputed — with both milestone timestamps now set, no milestone remains outstanding and the posture becomes `ON_TRACK` — and `regulatory_posture` is recomputed. The project's `version` is incremented.

An `AMENDMENT` filing works differently in almost every respect. It is permitted only while the project's `stage` is `LICENSED`, and it never changes the stage. It requires `amends_order_id` naming a license order of the same project whose `compliance_state` is `EFFECTIVE`; an amendment against an order in any other compliance state is rejected with `ERR_ORDER_STATE_INVALID`. Filing it sets that order's `amendment_pending` to true. Where a prior amendment application against the same order is still in `FILED`, `UNDER_REVIEW` or `DEFICIENT`, the newer filing supersedes it: the prior application's `filing_status` becomes `SUPERSEDED`, the project's `open_deficiency_count` and then `regulatory_posture` are recomputed, and the superseded application's `version` is incremented. Conversely, `amends_order_id` is forbidden on an `ORIGINAL_RELICENSE` filing.

Environmental review runs on its own dimension, driven by the `Regulator`, and it advances one step at a time. The body carries a `target_stage` and an optional `review_note`. A `target_stage` of `SCOPING` moves `ea_stage` `NOT_STARTED → SCOPING` and requires `filing_status` to be `FILED`; it also moves `filing_status` `FILED → UNDER_REVIEW` and, for an `ORIGINAL_RELICENSE` application, moves the project's `stage` `APPLICATION_FILED → UNDER_ENVIRONMENTAL_REVIEW`, incrementing the project's `version`. A `target_stage` of `DRAFT_EA` moves `ea_stage` `SCOPING → DRAFT_EA` and requires `filing_status` to be `UNDER_REVIEW`. A `target_stage` of `FINAL_EA` moves `ea_stage` `DRAFT_EA → FINAL_EA`, requires `filing_status` to be `UNDER_REVIEW`, and imposes one cross-entity condition: every measure of the project whose `source` is `WQC_CONDITION` must carry a `cost_estimate_variant` of `DEFINITIVE`. A state condition still priced at a preliminary estimate blocks the final environmental document, and the attempt is rejected with `ERR_DEFINITIVE_ESTIMATE_REQUIRED`. Each advance increments the application's `version`. Skipping or repeating a stage is rejected with `ERR_APPLICATION_STATE_INVALID`.

Deficiency notices and cures form an unbounded loop over the administrative dimension. The `Regulator` raises a deficiency with a required `deficiency_note`, moving `filing_status` `UNDER_REVIEW → DEFICIENT`, incrementing `deficiency_count` by 1, storing the note as `last_deficiency_note`, recomputing the project's `open_deficiency_count` and then `regulatory_posture` — which takes the project from `OPEN` to `RESTRICTED` — and incrementing the application's `version`. A deficiency raised outside `UNDER_REVIEW` is rejected with `ERR_APPLICATION_STATE_INVALID`.

The `Licensee` cures, with an optional `cure_note` as the only input, moving `filing_status` `DEFICIENT → UNDER_REVIEW` or `SUSPENDED → UNDER_REVIEW`. Curing is one of the five paths not subject to the blanket freeze gate, but its own precondition still requires the project's `regulatory_posture` no longer to be `FROZEN`, and a cure attempted while the project is still frozen is rejected with `ERR_PROJECT_POSTURE_FROZEN` — the licensee must clear whatever froze the project before reviving the application. A cure re-pins the snapshot from current state, rewriting `pinned_study_plan_version`, `pinned_settlement_version`, `pinned_measure_ids` and `pinned_total_annual_burden_usd`, then recomputes the project's `open_deficiency_count` and `regulatory_posture` and increments the application's `version`. A cure attempted from a `filing_status` other than `DEFICIENT` or `SUSPENDED` is rejected with `ERR_APPLICATION_STATE_INVALID`. The cycle `UNDER_REVIEW → DEFICIENT → UNDER_REVIEW` may repeat without bound.

Suspension is never requested; it is imposed. Whenever a project's `regulatory_posture` becomes `FROZEN` within a request — whether from a water-quality denial, from a compliance flag, or from the sweep discovering a delinquent timeline — every application of that project whose `filing_status` is `FILED`, `UNDER_REVIEW` or `DEFICIENT` is moved to `SUSPENDED`, and each such application increments its own `version`.

### 3.9. Order Issuance and Post-License Compliance

Issuing the **LicenseOrder** is the `Regulator`'s final act on an application, and it moves `filing_status` `UNDER_REVIEW → LICENSED`. The body carries a non-empty `order_number` that must be unique across every order in the system — a duplicate is rejected with `ERR_DUPLICATE_KEY` — and an optional `order_note`. Four preconditions apply beyond the filing status. `ea_stage` must be `FINAL_EA`, or the request is rejected with `ERR_APPLICATION_STATE_INVALID`. The project's `regulatory_posture` must not be `FROZEN`, rejected with `ERR_PROJECT_POSTURE_FROZEN`, and must not be `RESTRICTED` either, rejected with `ERR_PROJECT_POSTURE_RESTRICTED` — order issuance is the one operation the restricted tier blocks. And the project's `wqc_status` must be `CERTIFIED_WITH_CONDITIONS` or `WAIVED`, so that the state's conditions are actually reflected in the license; a `wqc_status` still reading `REQUESTED` is rejected with `ERR_WQC_CONDITION_NOT_INCORPORATED`.

Issuance creates one order with `compliance_state` `EFFECTIVE`, an `application_id` referencing the application it was issued on, and an `effective_date` set to the logical clock's date — the anchor for every obligation due date and for the anniversary reporting basis. The order starts with `open_violation_count` 0, `amendment_pending` false, `compliance_score` 100, and `last_report_basis`, `last_report_period_year` and `last_report_filed_at` all unset. The project's `stage` advances to `LICENSED`, `regulatory_posture` is recomputed, and both the application's and the project's `version` are incremented.

**Generating the obligation schedule.** Issuance also generates the order's **ComplianceObligation** set, and `article_count` records how many obligations were generated. Every generated obligation starts with status `PENDING`, with `activity_window_start`, `activity_window_end`, `certified_at`, `certified_by_user_id` and `overdue_marked_at` all unset.

One obligation of type `PME_IMPLEMENTATION` is created for each measure of the project whose status is `INCLUDED` or `IMPLEMENTED`, with the obligation's `pme_measure_id` referencing that measure and its `dam_id` unset. Measures are processed in topological order of the prerequisite graph, roots first, because a dependent measure's due date depends on its prerequisite's. A measure with no `prerequisite_measure_id` sits at depth zero and its `due_date` is the order's `effective_date` plus that measure's `implementation_months`. A measure that names a prerequisite has a `due_date` equal to the later of two candidates: the order's `effective_date` plus its own `implementation_months`, and the prerequisite's already-computed `due_date` plus a 6-month prerequisite lag. A dependent measure is therefore never due before its prerequisite's due date plus that lag, and a prerequisite chain pushes dependents strictly later even when the dependent's own `implementation_months` is short.

Three further obligations are generated per dam of the project, each with its `dam_id` referencing that dam and its `pme_measure_id` unset. A `DAM_SAFETY_INSPECTION` obligation falls due at the order's `effective_date` plus that dam's `inspection_interval_months`. A `PUBLIC_SAFETY_SIGNAGE` obligation falls due at the order's `effective_date` plus 12 months. An `EAP_EXERCISE` obligation falls due at the order's `effective_date` plus 24 months, and is created only where the dam's `eap_exercise_required` is true. All of these dates are whole-month additions with day-of-month clamping; partial months never arise.

Suppose an order takes effect on the fifteenth of March 2027. A root measure with `implementation_months` of 6 falls due on the fifteenth of September 2027. A measure whose prerequisite is that root, with `implementation_months` of 9, has candidates of the fifteenth of December 2027 and the fifteenth of March 2028, so it falls due on the later — the fifteenth of March 2028. A third measure whose prerequisite is the second, with `implementation_months` of 11, has candidates of the fifteenth of February 2028 and the fifteenth of September 2028, and falls due on the fifteenth of September 2028. A dam with `inspection_interval_months` of 12 and `eap_exercise_required` true adds an inspection obligation due the fifteenth of March 2028, a signage obligation due the fifteenth of March 2028, and an emergency-action exercise obligation due the fifteenth of March 2029.

**Amendment supersedes.** Where the order is being issued on an `AMENDMENT` application, the order named by that application's `amends_order_id` moves `EFFECTIVE → SUPERSEDED`, its `amendment_pending` clears to false, and its `version` is incremented. Its obligations are carried across rather than lost: every obligation of the superseded order whose status is `PENDING` or `SCHEDULED` is re-created against the new order, and the originals — along with any remaining obligations of the superseded order — are moved to `WAIVED`, each incrementing its own `version`. Where a waived obligation had been `OVERDUE`, the superseded order's `open_violation_count` is recomputed.

**Scheduling field activity.** The `Licensee` schedules an obligation by supplying an `activity_window_start` and an `activity_window_end` — a **closed** interval, both ends inclusive, with the start no later than the end — plus an optional `schedule_note`. Scheduling moves an obligation `PENDING → SCHEDULED` or, on a reschedule, `OVERDUE → SCHEDULED`; from any other status it is rejected with `ERR_OBLIGATION_STATE_INVALID`. Both paths store the window and increment the obligation's `version`, and both apply the same two checks. For a dam-bound obligation — one of type `DAM_SAFETY_INSPECTION`, `PUBLIC_SAFETY_SIGNAGE` or `EAP_EXERCISE` — the count of dam-bound obligations at that same dam whose status is `SCHEDULED` and whose closed activity windows overlap the requested closed window, plus the one now being scheduled, must not exceed that dam's `max_concurrent_field_activities`; exceeding it is rejected with `ERR_DAM_ACTIVITY_CAPACITY_EXCEEDED`. For a `PME_IMPLEMENTATION` obligation whose measure names a `prerequisite_measure_id`, that prerequisite measure's status must be `IMPLEMENTED`, and anything else is rejected with `ERR_PREREQUISITE_NOT_IMPLEMENTED`. Rescheduling from `OVERDUE` differs from a first schedule in two ways: `overdue_marked_at` is retained as evidence rather than cleared, and the owning order's `open_violation_count` is deliberately *not* changed — rescheduling relieves nothing, and only certification clears a violation. Scheduling is one of the five cure paths and is therefore permitted even while the project is `FROZEN`.

**Certifying completion.** Certifying an obligation, with an optional `certification_note` as its only input, moves it `SCHEDULED → CERTIFIED`; from any other status it is rejected with `ERR_OBLIGATION_STATE_INVALID`. The logical clock's date must have reached the obligation's `activity_window_start`, and an earlier attempt is rejected with `ERR_CERTIFICATION_TOO_EARLY`. Segregation of duties applies here too: the acting `X-User-ID` must not be a user who submitted a resource study report in the same `resource_category` as the obligation's measure on the same project, and a violation is rejected with `ERR_SEGREGATION_OF_DUTIES`. On success, `certified_at` is stamped from the logical clock and `certified_by_user_id` records the acting user. Where the obligation's `obligation_type` is `PME_IMPLEMENTATION`, its linked measure moves `INCLUDED → IMPLEMENTED`; the measure remains economically live, since `IMPLEMENTED` counts in the ledger exactly as `INCLUDED` does, but the project burden ledger is nonetheless re-run. The owning order's `open_violation_count` is recomputed, and when it reaches zero an order sitting in `COMPLIANCE_FLAGGED` moves back to `EFFECTIVE`, which recomputes the project's `compliance_flag_count` and then `regulatory_posture` — the two-tier jump described in §2.8. The obligation's `version` is incremented. Certification is a cure path and is permitted while the project is `FROZEN`.

**Annual compliance reporting.** The `Licensee` files an annual report against an order by supplying a `report_basis` of either `CALENDAR` or `LICENSE_ANNIVERSARY`, a `period_year`, and an optional `report_note`. The chosen basis fixes the assessment window, and the two bases genuinely disagree. Under `CALENDAR`, the window runs from the first of January of `period_year` through the thirty-first of December of `period_year`. Under `LICENSE_ANNIVERSARY`, the window starts on the month and day of the order's `effective_date` in `period_year` and runs to the day before the next anniversary — that is, the start date plus 12 months, minus one day. Both windows are inclusive at both ends. A report whose window has not yet started, meaning its period start is later than the logical clock's date, is rejected with `ERR_REPORT_PERIOD_INVALID`, as is a second report for the same basis and the same `period_year` on the same order.

Once the window is fixed, the assessment is common to both bases. The **assessed** set is every obligation of the order whose `due_date` falls inside the window, inclusive of both bounds, and whose status is anything other than `WAIVED`. Within that set, an obligation is **noncompliant** when its status is anything other than `CERTIFIED`, or when its status is `CERTIFIED` but the date of its `certified_at` is later than its `due_date` — a late certification counts as a violation for the period. `assessed_obligation_count` is the size of the assessed set and `noncompliant_obligation_count` is the size of the noncompliant subset. `compliance_score` is 100 multiplied by the assessed count minus the noncompliant count, divided by the assessed count, rounded half up to two decimal places; when the assessed count is zero the score is exactly 100.00, never 0.00. Filing also stores `last_report_basis`, `last_report_period_year` and `last_report_filed_at` from the logical clock, and increments the order's `version`.

The disagreement between the two bases is the point of offering both. For an order effective on the fifteenth of March 2027, an obligation due the fifteenth of February 2028 falls inside the `CALENDAR` window for 2028 but inside the `LICENSE_ANNIVERSARY` window for 2027, which runs from the fifteenth of March 2027 to the fourteenth of March 2028 — never inside both. A report with a `noncompliant_obligation_count` greater than zero moves the order `EFFECTIVE → COMPLIANCE_FLAGGED`, incrementing the order's `version`, which recomputes the project's `compliance_flag_count` and thence `regulatory_posture` to `FROZEN`, which in turn suspends the project's pending applications as described in §3.8. Reporting is a cure path, permitted even while the project is already `FROZEN`, and it never clears `COMPLIANCE_FLAGGED` by itself — only certifying the last outstanding violation does that.

**The compliance sweep.** Time does not pass on its own in this system; the `Regulator` makes it pass by advancing the logical clock and then running the project's compliance sweep, an operations checkpoint that takes no body input. The sweep is idempotent for a fixed clock value: running it twice without moving the clock changes nothing the second time.

The sweep does four things in sequence. First, every obligation belonging to one of the project's non-superseded orders whose status is `PENDING` or `SCHEDULED` and whose `due_date` is earlier than the logical clock's date moves to `OVERDUE`, with `overdue_marked_at` stamped from the logical clock and its own `version` incremented; each owning order's `open_violation_count` is recomputed and an order carrying at least one violation moves `EFFECTIVE → COMPLIANCE_FLAGGED`, incrementing that order's `version`. Second, a water-quality certification of the project still in `REQUESTED` status whose `statutory_waiver_date` the clock has reached or passed moves to `WAIVED` as described in §3.6, with the project's `wqc_status` set to `WAIVED`. Third, the project's `timeline_posture` is recomputed against its outstanding milestone, its `compliance_flag_count` is recomputed, and then `regulatory_posture` is recomputed from all its inputs; where the result is `FROZEN`, every application of the project whose `filing_status` is `FILED`, `UNDER_REVIEW` or `DEFICIENT` moves to `SUSPENDED`. Fourth, `last_sweep_at` is stamped from the logical clock and the project's `version` is incremented. The sweep is the fifth cure path and runs regardless of the project's posture.
