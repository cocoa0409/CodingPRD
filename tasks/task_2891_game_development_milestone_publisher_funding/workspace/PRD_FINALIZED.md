# Game Milestone Publisher Funding API — Product Requirements Document

## 1. Introduction

Externally funded game development runs on a document nobody enjoys reading: the development agreement. It fixes an advance, chops the project into milestones, attaches acceptance criteria and a payment to each one, and then spends the next two years being renegotiated. The studio wants money released the moment a build lands. The publisher wants a stability bar, a content bar, a cure period before it writes off a late milestone, a holdback against quality risk, and the right to recover every cent of its advance out of revenue before a single royalty point is paid. Both sides want scope changes — the studio asks for more funding, the publisher asks for features to be cut — and both changes move the ship date. This API is the system of record where those competing interests are reduced to states, ledgers and dated decisions.

The service governs a single funding relationship end to end. A platform operator registers the developing studio, the publisher, and the publisher-side operators who will act on the publisher's behalf. A funding operator drafts a development agreement, the parties define a milestone schedule that must exhaust the committed advance exactly, and activation turns the paper deal into a live production. From there the system tracks every build submitted against a milestone and grades it against a gate profile; every publisher verdict and the cure window a conditional verdict opens; every milestone payment, its contractor-overrun deduction and its quality holdback; every scope change and the days it adds to or removes from the ship date; every outsourcing engagement drawn against a milestone's contractor budget and every vendor invoice billed against it; and, after launch, every royalty statement that walks revenue down the waterfall of platform fees, capped publisher costs, advance recoupment and finally the developer's royalty.

Two design commitments run through the whole specification and should be read as constraints on every endpoint below. First, **money is conserved**: the funding pool, the committed total, the accepted value, the disbursed advance and the withheld balance are all derived quantities recomputed from the underlying rows on every mutation, never incremented blindly, so a suspend followed by a reinstatement leaves the ledger exactly where it started. Second, **authority is divided**: the publisher-side operator who records an accepting verdict on a milestone may never be the operator who authorizes the payment that acceptance created, and an operator licensed only for review work can never act in a funding capacity at all. Every rule in this document exists to make one of those two commitments testable.

## 2. Global Specifications & System-Wide Principles

This section defines the contracts that hold for every endpoint: authentication, the response envelope, pagination, identity and timestamp conventions, arithmetic discipline, cascade semantics, concurrency control, and the precedence order the server uses when a single request breaks several rules at once.

### 2.1. User and Role-Based Access Control

Every request to the API must carry two headers: `X-User-ID`, which identifies the acting principal, and `X-User-Role`, which declares the capacity that principal is acting in. If either header is absent, empty, or contains only whitespace, the request is rejected with `ERR_MISSING_AUTH_HEADERS` (401) before anything else is examined — this is the first check the server performs, ahead of every other rule in this document.

The system recognizes exactly four roles, and the comparison against `X-User-Role` is case-sensitive: `PlatformAdmin`, `Developer`, `PublisherReviewer`, and `PublisherFinance`. Any other value, including a differently-cased spelling of a valid role, is rejected with `ERR_UNKNOWN_ROLE` (401).

Three of the four roles are backed by a persisted row, which is what ties `X-User-ID` to resource ownership:

- When `X-User-Role` is `Developer`, `X-User-ID` is the `id` of the acting `Studio`; ownership checks on any resource that reaches a development agreement compare that agreement's `studio_id` to `X-User-ID`.
- When `X-User-Role` is `PublisherReviewer`, `X-User-ID` is the `id` of the acting `PublisherUser`; ownership checks compare the agreement's `publisher_id` to the `publisher_id` recorded on that `PublisherUser`.
- When `X-User-Role` is `PublisherFinance`, `X-User-ID` is likewise the `id` of the acting `PublisherUser`, and ownership is resolved the same way — through that operator's `publisher_id`.
- When `X-User-Role` is `PlatformAdmin`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server neither resolves it against any table nor compares it to any entity's `id`; a `PlatformAdmin` identifier always resolves successfully.

For the three entity-backed roles, an `X-User-ID` that matches no row of the backing table is rejected with `ERR_ACTOR_NOT_FOUND` (401). This resolution step is skipped on the four bootstrap operations that necessarily precede the existence of any actor row: studio registration, publisher registration, publisher-user creation, and setting the logical clock (`POST /studios`, `POST /publishers`, `POST /publisher-users`, `POST /_clock/set_current_utc`). On every other endpoint, actor resolution is mandatory.

Once the actor resolves, the server checks that the acting role appears in the endpoint's authorized-role list as published in §4; if it does not, the answer is `ERR_ROLE_NOT_PERMITTED` (403). A second, subtler authorization gate then applies to the publisher side. Every `PublisherUser` carries a `function` declaring which publisher-side work that operator is licensed for, drawn from `REVIEW`, `FINANCE`, and `DUAL`. Acting as `PublisherReviewer` requires a `function` of `REVIEW` or `DUAL`; acting as `PublisherFinance` requires a `function` of `FINANCE` or `DUAL`. A mismatch — a `FINANCE`-only operator presenting itself as a reviewer, or a `REVIEW`-only operator presenting itself as finance — is rejected with `ERR_ROLE_FUNCTION_MISMATCH` (403) on every endpoint whose authorized roles include either publisher-side role. A `DUAL` operator passes this gate in both capacities, which is precisely why the payment-level separation described in §2.11 exists.

Finally, business access is confined to the parties of the agreement a request reaches. A `Developer` whose `Studio` `id` differs from the agreement's `studio_id`, or a `PublisherReviewer` or `PublisherFinance` whose `PublisherUser` `publisher_id` differs from the agreement's `publisher_id`, receives `ERR_NOT_AGREEMENT_PARTY` (403). The agreement is reached transitively: a build resolves through its milestone to the agreement, an invoice through its engagement and that engagement's milestone, a payment through its milestone, and a royalty statement directly through its `agreement_id`. `PlatformAdmin` is exempt from this check. This rule deliberately outranks every state, temporal and fiscal rule in the system: an outsider must never be able to probe a milestone's internal state by reading the error code that comes back.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

List endpoints are paginated through two query parameters. `limit` caps the number of records returned; it defaults to 10 when omitted, accepts a minimum of 1 and a maximum of 100, and a value outside that range is a structural error. `offset` is the number of records to skip and defaults to 0. Unless a specific endpoint states otherwise, list results are ordered by `created_at` ascending — the one documented exception is the per-milestone build listing, which is ordered by `build_number` descending so the newest delivery appears first.

Every list response repeats `limit` and `offset` in the `meta` object alongside `total_count`, the number of records matching the filter before pagination is applied, and `has_more`, a boolean that is true when records remain beyond the current window.

Filter parameters are additive: supplying several narrows the result set, and supplying none returns everything the caller is entitled to see. A filter value that matches nothing yields an empty array with `total_count` of 0, not an error.

### 2.4. Resource Identity, Timestamps and the Logical Clock

Every resource the API persists carries an `id`: a server-minted UUID string with no type prefix, never supplied by the client. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with exactly three fractional digits, recorded when the row is first written.

Most resources additionally carry `updated_at`, refreshed on every mutation of that resource, and `version`, an integer that starts at 1 on creation and increments by one on each mutation. `Studio`, `Publisher`, `PublisherUser`, `DevelopmentAgreement`, `Milestone`, `MilestoneBuild`, `MilestonePayment`, `ChangeOrder`, `ContractorEngagement`, `ContractorInvoice` and `RoyaltyStatement` all expose the full quartet. `PublisherReview` is the single exception: a review is immutable from the instant it is written, so it exposes only `id` and `created_at` — it has neither `updated_at` nor `version`, and clients must not expect either field on a review payload.

Time in this system is entirely logical. The server holds a logical clock that reads exactly `2026-08-01T00:00:00Z` before any call is made, and it never falls back to wall-clock time. A `PlatformAdmin` moves that clock by supplying a `current_utc` instant to the clock-setting endpoint; the call sets the clock and nothing else — no entity is modified, no cascade runs, and the response carries no resource. Every deadline, cure window, review window, vendor cooldown and settlement instant in this document is evaluated against the logical clock, never against the host's real time. All system-recorded instants — `submitted_at`, `decided_at`, `accepted_at`, `authorized_at`, `finalized_at`, `terminated_at`, `cure_deadline_at` — are ISO 8601 UTC with three fractional digits and are read from the logical clock at the moment of the write.

Two fields are calendar dates rather than instants: a contractor engagement's `start_date` and `end_date`, and a milestone's contractual `ship_date_original` and derived `ship_date_current`, plus an invoice's `period_end_date`. These are plain ISO 8601 dates in the form YYYY-MM-DD, and arithmetic on them is in whole calendar days.

### 2.5. Money, Basis Points and Percentages

All monetary amounts in this system are integer counts of cents. There are no fractional cents anywhere in a request or a response, and a client that sends a decimal where cents are expected has sent a structural error. Rates are expressed in basis points — hundredths of one percent — so a `royalty_rate_bps` of 1500 is a fifteen percent royalty and a `platform_fee_bps` of 3000 is a thirty percent storefront cut. Wherever a rate is applied to an amount, the product is divided by 10000 and the result rounded half up to a whole number of cents. Rounding is always half up, never banker's rounding and never truncation.

The number of rounding operations, and the point at which each happens, is part of the contract rather than an implementation detail — a settlement that rounds once at the end is a different number from one that rounds per line and sums, and §3 states for each calculation exactly where the rounding sits. Wherever a derived amount is described as floored at zero, the floor is applied after the subtraction, so the stored value is never negative.

Percentage-valued fields — `feature_completeness_pct`, `crash_free_sessions_pct`, `content_completeness_pct`, `content_threshold_relief_pct` and the derived `readiness_score` — carry two decimal places and are compared exactly, with no tolerance or epsilon. A build whose `crash_free_sessions_pct` is 97.99 against a bar of 98.00 has missed the bar. The derived `accepted_milestone_ratio` is the one quantity carried to four decimal places, rounded half up.

### 2.6. The Agreement Funding Ledger

Every `DevelopmentAgreement` carries a funding ledger: a family of derived integer-cent fields that are **recomputed from the underlying rows** on every mutation that touches the agreement's scope or money, never adjusted by blind increment. The mutations that trigger a full recomputation are: creating a milestone, activating the agreement, suspending it, reinstating it, terminating it, deciding a change order, accepting a milestone, cancelling a milestone as part of termination, and authorizing a milestone payment. A `DRAFT` agreement computes exactly the same fields as a live one, which is why `committed_cents` can already be non-zero before activation.

The ledger is defined as follows. `uplift_funded_cents` is the sum of `requested_amount_cents` over every change order of the agreement whose `state` is `APPROVED_UPLIFT`. `funding_pool_cents` is `advance_total_cents` plus `uplift_funded_cents`. `committed_cents` is the sum, over every milestone of the agreement whose `status` is anything other than `CANCELLED`, of that milestone's `funded_amount_cents` plus its `uplift_cents`. `available_funding_cents` is `funding_pool_cents` minus `committed_cents`, and it is the conserved headroom of the funding pool: after any cascade whatsoever, the available figure must still equal the pool minus the committed total. `accepted_value_cents` applies the same sum of `funded_amount_cents` plus `uplift_cents` but restricted to milestones whose `status` is `ACCEPTED`. `advance_disbursed_cents` is the sum of `net_amount_cents` over payments whose `status` is `AUTHORIZED`, and `holdback_reserve_cents` the sum of `holdback_cents` over that same set. `withheld_payment_cents` is the sum of `scheduled_amount_cents` over payments whose `status` is either `HELD_PENDING_CURE` or `WITHHELD`. `breach_count` is the count of milestones whose `status` is `BREACHED`.

From `accepted_value_cents` the server derives `funding_posture`, a three-valued gate on new scope. The posture is `FROZEN` whenever the agreement's `status` is `SUSPENDED` or `TERMINATED` — that test comes first and overrides the others. Otherwise the posture is `RESTRICTED` when `accepted_value_cents` has reached or passed thirty percent of `funding_pool_cents`, where the threshold is computed by multiplying `funding_pool_cents` by 3000 basis points, dividing by 10000 and rounding half up to whole cents; the comparison is inclusive, so hitting the threshold exactly is enough to restrict. In every other case the posture is `OPEN`. Because the threshold is a fraction of the pool, growing the pool through an approved uplift can legitimately move a `RESTRICTED` agreement back to `OPEN`.

Three conservation invariants must hold at all times, and the suspend/reinstate and engagement-cancel operations exist as their exact compensating counterparts. Funding-pool conservation: `available_funding_cents` always equals `funding_pool_cents` minus `committed_cents`. Payment-obligation conservation: the sum of `scheduled_amount_cents` across all milestone payments of an agreement equals `accepted_value_cents`, both before and after a suspend/reinstate pair. Contractor-budget conservation: cancelling an engagement restores the milestone's contractor-budget headroom exactly, leaving no residue.

Two derived ledger fields belong to the recoupment side rather than the funding side and are described in §3.9: `advance_recouped_cents`, `unrecouped_advance_cents` and `royalties_paid_to_date_cents`, together with the `recoupment_state` they drive, which walks `PRE_RECOUP` → `RECOUPING` → `RECOUPED`.

### 2.7. Agreement-Version Freshness on Scope and Revenue Writes

Two write operations require the client to prove it is working from a current view of the agreement, because in both cases a fresh write legitimately supersedes an existing row and therefore cannot be blocked by any state precondition. Both use the same mechanism: a mandatory `expected_agreement_version` field in the request body carrying the `version` of the parent `DevelopmentAgreement` as the client last observed it. If that value does not equal the agreement's current `version`, the request is rejected with `ERR_STALE_AGREEMENT_VERSION` and HTTP 412, and nothing is written.

The first is change-order creation (`POST /change-orders`). A newly created proposal supersedes any still-`PROPOSED` order on the same target milestone, so no state check stands in its way; the version test is the only thing that stops a client from silently superseding a proposal it never saw. The second is royalty-statement creation (`POST /royalty-statements`). A fresh `DRAFT` supersedes the prior `DRAFT` for the same period, and the ledger figures the new statement is computed from — `advance_disbursed_cents`, `unrecouped_advance_cents`, `royalties_paid_to_date_cents` — may have moved since the client read them, so a stale view must be refused.

`expected_agreement_version` is not optional on those two endpoints: omitting it is a structural error, not a bypass. No other endpoint in this API accepts a version field, and no other endpoint performs a version check; every other write is guarded by state and fiscal preconditions alone.

### 2.8. Cascade Discipline

Many operations in this system change more than one row. Wherever §3 describes a cascade, the numbered steps are **ordered**, and the order is part of the specification: a later step may legitimately observe and overwrite what an earlier step wrote. The clearest example is milestone acceptance, where a dependent milestone is unlocked and its proposed engagements promoted before the funding posture is re-evaluated — so an engagement that step two just made `ACTIVE` can be suspended again by step four in the same request.

Any cascade that changes a field on the `DevelopmentAgreement` refreshes that agreement's `updated_at` and increments its `version` by one, exactly once per request, no matter how many rows the cascade touched. The same holds for the child rows the cascade rewrites: each mutated row gets its own refreshed `updated_at` and incremented `version`. Cascades are applied immediately and synchronously within the triggering request; there is no deferred reconciliation and no eventual consistency window. If any precondition of the triggering operation fails, nothing is written at all — neither the primary change nor any cascade step.

The server also performs state transitions no client ever requests. Milestones move from `DEFINED` to `IN_DEVELOPMENT` when their predecessor is accepted; builds move from `PASSED` to `SUPERSEDED` when a newer build lands; proposals move to `SUPERSEDED` when a newer proposal replaces them; and the agreement moves from `ACTIVE` to `COMPLETED` on its own once the gold milestone is accepted and nothing is left open. These are legitimate outcomes of somebody else's request, not defects.

### 2.9. Reverse-Lookup Reads and Path Resolution Order

The resource model is flat: every business collection is addressed as a top-level path segment and children carry their parent's identifier in the request body rather than in the URL. There are only three nested read paths, and all three are reverse-lookup channels rather than ownership hierarchies: the builds of one milestone, the invoices of one engagement, and the royalty statements of one agreement. Where a path contains an identifier, the server resolves that identifier before it examines the request body or any business rule, and reports the not-found error belonging to that path segment's own resource type. A request naming a milestone that does not exist is answered with `ERR_MILESTONE_NOT_FOUND` whatever else may also be wrong with it.

Identifiers arriving in the request body are resolved after the path identifier and after authorization, and when a body carries more than one foreign key they are resolved strictly left to right in the order the owning entity declares them. Agreement creation resolves `studio_id` before `publisher_id`, so a payload naming neither an existing studio nor an existing publisher reports `ERR_STUDIO_NOT_FOUND`. Milestone creation resolves `agreement_id` before `depends_on_milestone_id`, reporting `ERR_AGREEMENT_NOT_FOUND` before `ERR_MILESTONE_NOT_FOUND`. Change-order creation resolves `agreement_id` before `target_milestone_id`, with the same pair of errors. Publisher-user creation resolves `publisher_id` to `ERR_PUBLISHER_NOT_FOUND`; build creation resolves `milestone_id` to `ERR_MILESTONE_NOT_FOUND`; review creation resolves `build_id` to `ERR_BUILD_NOT_FOUND`; engagement creation resolves `milestone_id` to `ERR_MILESTONE_NOT_FOUND`; invoice creation resolves `engagement_id` to `ERR_ENGAGEMENT_NOT_FOUND`; royalty-statement creation resolves `agreement_id` to `ERR_AGREEMENT_NOT_FOUND`. Every one of these is HTTP 404.

### 2.10. Rule Precedence: Which Error the Server Reports

A single malformed request frequently breaks several rules at once. The system's validation rules are **totally ordered**, and the contract is unambiguous: the server evaluates them in the order below, returns the error of the first rule that the request violates, and does not evaluate any later rule. There are no ties. The list below fixes the order; the business meaning of each rule, and the state it inspects, is developed in §3 near the workflow it guards.

1. Both authentication headers present and non-blank, on every endpoint — `ERR_MISSING_AUTH_HEADERS`.
2. `X-User-Role` is a recognized role, on every endpoint — `ERR_UNKNOWN_ROLE`.
3. The acting principal resolves to a row of its backing entity, on every endpoint except studio registration, publisher registration, publisher-user creation and the clock setter — `ERR_ACTOR_NOT_FOUND`.
4. The acting role is authorized for the endpoint, on every endpoint — `ERR_ROLE_NOT_PERMITTED`.
5. The operator's `function` matches the publisher-side role being claimed, on every endpoint whose authorized roles include `PublisherReviewer` or `PublisherFinance` — `ERR_ROLE_FUNCTION_MISMATCH`.
6. The request body is structurally valid, on every endpoint that takes a body — `ERR_INVALID_REQUEST`.
7. A studio identifier in the path resolves — `ERR_STUDIO_NOT_FOUND`.
8. A publisher identifier in the path resolves — `ERR_PUBLISHER_NOT_FOUND`.
9. A publisher-user identifier in the path resolves — `ERR_PUBLISHER_USER_NOT_FOUND`.
10. An agreement identifier in the path resolves, on the agreement read, the agreement's royalty-statement and recoupment-summary reads, and on activate, suspend, reinstate, terminate, cure-sweep and live-ops-draw — `ERR_AGREEMENT_NOT_FOUND`.
11. A milestone identifier in the path resolves, on the milestone read, its build listing and its budget summary — `ERR_MILESTONE_NOT_FOUND`.
12. A build identifier in the path resolves — `ERR_BUILD_NOT_FOUND`.
13. A review identifier in the path resolves — `ERR_REVIEW_NOT_FOUND`.
14. A payment identifier in the path resolves, on the payment read and on authorization — `ERR_PAYMENT_NOT_FOUND`.
15. A change-order identifier in the path resolves, on the change-order read and on its decision — `ERR_CHANGE_ORDER_NOT_FOUND`.
16. An engagement identifier in the path resolves, on the engagement read, its invoice listing, completion and cancellation — `ERR_ENGAGEMENT_NOT_FOUND`.
17. An invoice identifier in the path resolves, on the invoice read and on its decision — `ERR_INVOICE_NOT_FOUND`.
18. A statement identifier in the path resolves, on the statement read and on finalization — `ERR_STATEMENT_NOT_FOUND`.
19. Every foreign key in the request body resolves, left to right, on every creation endpoint that carries one — the parent-specific not-found error listed in §2.9.
20. The acting principal is a party to the agreement the request reaches, on every agreement-scoped read and mutation — `ERR_NOT_AGREEMENT_PARTY`.
21. `expected_agreement_version` equals the agreement's current `version`, on change-order creation and royalty-statement creation — `ERR_STALE_AGREEMENT_VERSION`.
22. The agreement is `DRAFT`, on activation — `ERR_AGREEMENT_NOT_DRAFT`.
23. The agreement is `ACTIVE`, on build submission, review creation, payment authorization, change-order creation, change-order decision, engagement creation, invoice submission, invoice decision, suspension and cure-sweep. Payment authorization carries the single declared widening: there, an agreement whose `status` is `ACTIVE` **or** `COMPLETED` is admissible, because the gold-acceptance cascade can complete the agreement in the very request that creates the final payment and that payment must stay authorizable afterwards — `ERR_AGREEMENT_NOT_ACTIVE`.
24. The agreement is `SUSPENDED`, on reinstatement — `ERR_AGREEMENT_NOT_SUSPENDED`.
25. The agreement is not already `TERMINATED` or `COMPLETED`, on termination and on milestone creation — `ERR_AGREEMENT_TERMINAL`. Royalty statements and live-ops draws are deliberately *not* subject to this rule; they are post-launch operations gated instead by rules 64 and 44 respectively.
26. The agreement has at least one milestone in `DEFINED`, on activation — `ERR_AGREEMENT_HAS_NO_MILESTONES`.
27. `committed_cents` equals `funding_pool_cents` exactly, on activation — `ERR_FUNDING_ALLOCATION_INCOMPLETE`.
28. The submitted `sequence_index` is free within the agreement, on milestone creation — `ERR_SEQUENCE_INDEX_TAKEN`.
29. `depends_on_milestone_id` names a valid predecessor, on milestone creation — `ERR_INVALID_DEPENDENCY`.
30. `funding_posture` is not `RESTRICTED`, on milestone creation — `ERR_FUNDING_POSTURE_RESTRICTED`.
31. The milestone is open for delivery, on build submission — `ERR_MILESTONE_NOT_OPEN_FOR_BUILD`.
32. The milestone is open for outsourcing, on engagement creation — `ERR_MILESTONE_NOT_OPEN_FOR_OUTSOURCING`. This state rule deliberately outranks the contractor-budget cap at 60, so an over-budget engagement aimed at an already-accepted milestone reports the state error and never the fiscal one.
33. The milestone is `UNDER_REVIEW`, on review creation — `ERR_MILESTONE_NOT_UNDER_REVIEW`.
34. The reviewed build is the current one, on review creation — `ERR_BUILD_SUPERSEDED`.
35. The payment is `PENDING_AUTHORIZATION`, on authorization — `ERR_PAYMENT_NOT_PENDING`.
36. The change order is `PROPOSED`, on its decision — `ERR_CHANGE_ORDER_NOT_PROPOSED`.
37. The target milestone is amendable, on change-order creation and on its decision — `ERR_MILESTONE_NOT_AMENDABLE`.
38. The engagement can carry the invoice action, on invoice submission and on invoice decision — `ERR_ENGAGEMENT_NOT_INVOICEABLE`.
39. The engagement is in a state the requested lifecycle action allows, on engagement completion and cancellation — `ERR_ENGAGEMENT_STATE_INVALID`.
40. The invoice is `SUBMITTED`, on its decision — `ERR_INVOICE_NOT_SUBMITTED`.
41. The submitted `invoice_number` is free within the engagement, on invoice submission — `ERR_INVOICE_NUMBER_TAKEN`.
42. The statement is `DRAFT`, on finalization — `ERR_STATEMENT_NOT_DRAFT`.
43. No statement for the same period is already finalized, on statement creation — `ERR_PERIOD_ALREADY_FINALIZED`.
44. `post_launch_support_state` is `ACTIVE`, on a live-ops draw — `ERR_POST_LAUNCH_NOT_ACTIVE`.
45. The authorizing operator is not the accepting reviewer, on payment authorization — `ERR_SEGREGATION_OF_DUTIES`.
46. The build clears its acceptance gate, on build submission — `ERR_BUILD_GATE_NOT_MET`. This outranks the cure-window check at 51, so a build that both misses its gate and arrives after the cure deadline reports the gate failure.
47. The milestone's predecessor has been accepted, on build submission — `ERR_DEPENDENCY_NOT_ACCEPTED`.
48. `build_number` strictly exceeds the milestone's `latest_build_number`, on build submission — `ERR_BUILD_NUMBER_NOT_INCREASING`.
49. A cure resubmission addresses every open condition, on build submission — `ERR_CONDITIONS_NOT_ADDRESSED`.
50. The milestone has cure rounds left, on review creation — `ERR_CURE_LIMIT_EXCEEDED`.
51. The cure window is still open, on build submission — `ERR_CURE_WINDOW_EXPIRED`.
52. At least one cure window has actually expired, on cure-sweep — `ERR_CURE_WINDOW_STILL_OPEN`.
53. The reviewer's window is free, on review creation — `ERR_REVIEWER_WINDOW_CONFLICT`.
54. The submitted review window is well formed, on review creation — `ERR_INVALID_DATE_RANGE`. This sits deliberately *below* the overlap check at 53: a degenerate window that also overlaps an existing one reports the conflict, matching the reviewer-capacity-first reading of the agreement.
55. The submitted engagement dates are well formed, on engagement creation — `ERR_INVALID_DATE_RANGE`.
56. The vendor cooldown is clear, on engagement creation — `ERR_VENDOR_COOLDOWN_CONFLICT`.
57. The uplift cap is respected, on change-order decision — `ERR_UPLIFT_CAP_EXCEEDED`.
58. The ship-date slip limit is respected, on change-order decision — `ERR_SHIP_DATE_SLIP_EXCEEDED`.
59. The milestone's funding fits the pool, on milestone creation — `ERR_AGREEMENT_FUNDING_EXCEEDED`.
60. The contractor budget is respected, on engagement creation — `ERR_CONTRACTOR_BUDGET_EXCEEDED`.
61. The engagement invoice tolerance is respected, on invoice decision — `ERR_INVOICE_EXCEEDS_ENGAGEMENT`.
62. The live-ops caps are respected, on a live-ops draw — `ERR_LIVE_OPS_CAP_EXCEEDED`.
63. The submitted `period_label` does not regress, on statement creation — `ERR_PERIOD_OUT_OF_ORDER`.
64. The agreement is revenue-eligible, on statement creation and on finalization — `ERR_AGREEMENT_NOT_REVENUE_ELIGIBLE`. This sits below the statement-level rules at 42 and 43 on purpose: statement identity errors are reported before agreement eligibility.
65. No invoice of the engagement is still `SUBMITTED`, on engagement completion — `ERR_ENGAGEMENT_HAS_OPEN_INVOICES`.
66. No invoice of the engagement has ever been approved, on engagement cancellation — `ERR_ENGAGEMENT_HAS_APPROVED_INVOICES`.
67. A feature cut does not exceed the milestone's funding, on change-order decision — `ERR_CUT_EXCEEDS_MILESTONE_FUNDING`.
68. The agreement carries no breach, on reinstatement — `ERR_AGREEMENT_HAS_BREACH`.
69. Every submitted condition index is valid, on review creation — `ERR_INVALID_CONDITION_INDEX`.

Structural validation at position 6 covers a missing required field, an unknown enum value, a value of the wrong JSON type, an integer outside its declared range, a string failing its declared length or pattern, an array longer than its declared maximum, and a malformed ISO 8601 instant or date. It also covers *conditionally* required fields, which become required the moment their trigger value is present: rejecting an invoice requires a present, non-blank `rejection_reason`; a `CONDITIONAL` verdict requires `conditions` to be a non-empty array; an `ACCEPTED` or `REJECTED` verdict requires `conditions` to be absent or an empty array; a `FUNDING_UPLIFT` change order requires `requested_amount_cents` of at least 1; and a `FEATURE_CUT` change order requires `content_threshold_relief_pct` to be present. Conversely, fields the server computes or manages itself are **silently ignored** if a client sends them — their presence is not a structural error and never overrides the server's own value.

### 2.11. Segregation of Duties Across the Review/Pay Boundary

The publisher side is deliberately split. Recording an acceptance verdict is reviewer work; releasing money is finance work; and the two must not be performed by the same human on the same milestone. Two independent mechanisms enforce this. The first is the licence check of §2.1: an operator whose `function` is `REVIEW` can never act as `PublisherFinance`, and one whose `function` is `FINANCE` can never act as `PublisherReviewer`.

The second closes the loophole the first leaves open. An operator whose `function` is `DUAL` passes the licence check in both capacities, so the system additionally compares identities at the moment money moves: the operator authorizing a milestone payment must not be the same `PublisherUser` recorded as `reviewer_user_id` on the accepting review of that milestone. When they match, the authorization is refused with `ERR_SEGREGATION_OF_DUTIES` (403). A `DUAL` operator may therefore accept a milestone or pay for it, but never both.

## 3. Business Logic & Workflows

### 3.1. Parties, Operators and Deal Formation

Nothing in this system can happen until the parties exist. A `PlatformAdmin` registers the developing studio by supplying a `legal_name` of one to 120 characters that is not blank, a `contact_email` of one to 160 characters containing exactly one at-sign with a non-empty local part before it and a non-empty domain part after it, and optionally a `country_code` giving the ISO 3166-1 alpha-2 country of incorporation as exactly two uppercase letters. The identifier the registration returns is significant beyond bookkeeping: it is the value a `Developer` presents as `X-User-ID` for the rest of the project. Publisher registration takes the same three attributes, except that a publisher's `country_code` records the primary distribution territory rather than a place of incorporation.

Publisher-side humans are modelled separately from the publisher company. A `PlatformAdmin` creates each one against a `publisher_id`, with a `display_name` of one to 80 non-blank characters and a `function` fixing what that person is licensed to do — `REVIEW` for acceptance work, `FINANCE` for funding work, or `DUAL` for someone trusted with both. The returned identifier is that operator's `X-User-ID`. Publisher operators can be listed and narrowed by `publisher_id`, by `function`, or by both, which is the only way to discover who on a publisher's bench is licensed for what.

The development agreement itself is drafted by a `PlatformAdmin` or a `PublisherFinance` operator. The payload names the two parties through `studio_id` and `publisher_id`, gives the funded game a working `title` of one to 160 non-blank characters, and commits the money: `advance_total_cents` is the total recoupable advance in cents and must be at least 100000, that is one thousand currency units, so a token advance is not expressible. `royalty_rate_bps` is the post-recoupment royalty rate in basis points and must fall between 500 and 5000 inclusive — a royalty of at least five and at most fifty percent. Two rate fields may be omitted and then take contractual defaults: `recoupable_cost_cap_bps`, which caps the publisher costs deductible from distributable revenue, accepts 0 through 4000 and defaults to 2000, meaning a twenty percent cost cap unless negotiated otherwise; and `platform_fee_bps`, the storefront cut withheld from net revenue before anything is distributed, accepts 0 through 5000 and defaults to 3000, a thirty percent storefront. `live_ops_quarterly_funding_cents` sets the per-quarter live-operations envelope that becomes drawable after launch, must not be negative, and defaults to 0 — an agreement that never negotiated live-ops money simply has nothing to draw. Finally `ship_date_original` fixes the contractual ship date as a plain calendar date, and it must fall strictly after the logical clock's date at the moment of creation; a ship date already in the past or landing on today is a structural rejection.

Creation leaves the agreement in `DRAFT` with a `version` of 1 and a completely initialised ledger: `funding_posture` is `OPEN`, `recoupment_state` is `PRE_RECOUP`, `post_launch_support_state` is `PENDING`, `ip_reversion_state` is `NONE` and `sequel_rights_holder` is `PUBLISHER`. `funding_pool_cents` equals `advance_total_cents` because `uplift_funded_cents` starts at 0; `committed_cents` starts at 0 and therefore `available_funding_cents` starts equal to the whole pool. `accepted_value_cents`, `advance_disbursed_cents`, `holdback_reserve_cents`, `withheld_payment_cents`, `advance_recouped_cents`, `unrecouped_advance_cents`, `royalties_paid_to_date_cents`, `breach_count`, `live_ops_drawn_cents` and `schedule_slip_days` all start at 0, `accepted_milestone_ratio` at 0.0, `ship_date_current` equal to `ship_date_original`, and `terminated_at` is null until the deal is actually torn up. Agreements can be listed and filtered by `studio_id`, by `publisher_id`, or by `status`, and read individually — the individual read is also how a client obtains the `version` it will need for the two writes described in §2.7.

### 3.2. The Payment Schedule: Milestones, Dependencies and Activation

A development agreement is worth nothing until its advance is carved into milestones, and the studio, the funding operator or a `PlatformAdmin` may all do the carving. Each milestone names its `agreement_id`, takes a `sequence_index` of at least 1 giving its 1-based position in the payment schedule, a `title` of one to 120 non-blank characters, and a `gate_profile` of `ALPHA`, `BETA` or `GOLD` that fixes how harshly its builds will be graded. `funded_amount_cents` is the scheduled payment at signature and must be at least 10000 — no hundred-cent milestones. `contractor_budget_cents` is the ceiling for external contractor commitments inside this milestone and may be zero for work the studio intends to keep in house. `acceptance_criteria` is an ordered array of between one and twenty non-blank strings; its ordering matters, because a publisher's conditional verdict later refers to criteria by their zero-based position in this array. `depends_on_milestone_id` is optional and names the predecessor that must be accepted before this milestone may leave `DEFINED`; the first milestone of a schedule leaves it null.

A milestone is born `DEFINED` with `uplift_cents` at 0, `cure_count` at 0, `content_threshold_relief_pct` at 0.00, `latest_build_number` at 0, `open_condition_indexes` an empty array, and `cure_deadline_at` and `accepted_at` both null. Creation immediately recomputes the agreement's `committed_cents` and `available_funding_cents`, and, that being a change to the agreement, it also refreshes the agreement's `updated_at` and increments the agreement's `version` by one, exactly as §2.8 requires — so a `version` a client read before a milestone creation is stale afterwards.

Four rules police the definition of scope, and they are checked in the order §2.10 fixes. Scope cannot be added to a deal that is already over: an agreement whose `status` is `TERMINATED` or `COMPLETED` refuses new milestones with `ERR_AGREEMENT_TERMINAL`. The `sequence_index` must be free within the agreement, and cancelled milestones keep their index reserved forever, so reusing the index of a `CANCELLED` milestone still earns `ERR_SEQUENCE_INDEX_TAKEN`. A supplied `depends_on_milestone_id` must name a milestone of the same agreement, must not name the milestone being created, and must name a milestone whose `sequence_index` is strictly smaller than the one being submitted; a predecessor from another agreement, a self-reference, or a predecessor at or after this milestone's own position is `ERR_INVALID_DEPENDENCY`. Once the agreement's `funding_posture` has become `RESTRICTED`, fresh milestones are refused outright with `ERR_FUNDING_POSTURE_RESTRICTED`, because at that point additional scope is a renegotiation and must arrive as a change order rather than as a new line in the original schedule. Last, the money must fit: a `funded_amount_cents` greater than the agreement's current `available_funding_cents` is `ERR_AGREEMENT_FUNDING_EXCEEDED`.

Bringing the deal live is exclusively a `PublisherFinance` act, and it is the one place in the system where the funding arithmetic must balance to the cent. Activation requires the agreement to still be in `DRAFT` — otherwise `ERR_AGREEMENT_NOT_DRAFT` — and requires at least one milestone in `DEFINED`, without which the answer is `ERR_AGREEMENT_HAS_NO_MILESTONES`. Then the schedule must exhaust the advance **exactly**: `committed_cents` has to equal `funding_pool_cents`, and any discrepancy in either direction — an under-allocated schedule that leaves headroom or an over-allocated one — is refused with `ERR_FUNDING_ALLOCATION_INCOMPLETE`. On success the agreement moves `DRAFT → ACTIVE` with `funding_posture` set to `OPEN`, and a two-step cascade runs. Step one promotes every milestone of this agreement that is still `DEFINED` and has no predecessor from `DEFINED → IN_DEVELOPMENT`, opening the front of the schedule for delivery. Step two, because those milestones became `IN_DEVELOPMENT`, promotes each of their contractor engagements sitting in `PROPOSED` to `ACTIVE`; at a first activation this step finds nothing to do, since an engagement cannot be created before its agreement is active, but it is specified in full because the identical promotion does fire when a later milestone is unlocked by its predecessor's acceptance. The funding ledger is then recomputed and the agreement's `version` increments by one.

Milestones can be listed and filtered by `agreement_id`, by `depends_on_milestone_id` — which is how a client finds the successors waiting on a given milestone — or by `status`, and each can be read individually to inspect its cure state and accumulated gate relief.

### 3.3. Freezing and Unfreezing a Live Agreement

A publisher that has lost confidence in a production does not have to terminate it. A `PublisherFinance` operator may suspend an agreement whose `status` is `ACTIVE`, optionally recording a free-text `reason`; anything other than `ACTIVE` is `ERR_AGREEMENT_NOT_ACTIVE`. Suspension moves the agreement `ACTIVE → SUSPENDED` and forces `funding_posture` to `FROZEN`, and then a three-step cascade freezes everything downstream. Step one moves every milestone payment of this agreement whose `status` is `PENDING_AUTHORIZATION` to `HELD_PENDING_CURE`. Step two, because those payments have moved, recomputes `withheld_payment_cents` as the sum of their `scheduled_amount_cents`. Step three moves every contractor engagement whose milestone belongs to this agreement and whose `status` is `ACTIVE` to `SUSPENDED`. No invoice is voided by a suspension: invoices already sitting in `SUBMITTED` stay pending, but they cannot be approved while their engagement is not `ACTIVE`. The agreement's `version` increments once.

Reinstatement is the exact compensating counterpart, and it is specified as an ordered restoration rather than a fresh evaluation. Only an agreement whose `status` is `SUSPENDED` may be reinstated — otherwise `ERR_AGREEMENT_NOT_SUSPENDED` — and reinstatement is additionally refused while `breach_count` is greater than zero, with `ERR_AGREEMENT_HAS_BREACH`; a breached milestone must be resolved through a change order or through termination, never by quietly un-suspending the deal. An optional `reason` may be recorded. Step one of the restoration returns every payment in `HELD_PENDING_CURE` to `PENDING_AUTHORIZATION` and recomputes `withheld_payment_cents` down to 0. Step two restores each engagement that is currently `SUSPENDED`, and the branches are evaluated in this order: the engagement **stays** `SUSPENDED` when the recomputed `funding_posture` is `RESTRICTED` and its milestone's `status` is `DEFINED` or `IN_DEVELOPMENT`, and it also stays `SUSPENDED` when its milestone's `status` is `CANCELLED` or `BREACHED`; otherwise it returns to `PROPOSED` when its milestone is `DEFINED`, and to `ACTIVE` when its milestone's `status` is `IN_DEVELOPMENT`, `UNDER_REVIEW`, `CURE_PENDING` or `ACCEPTED`. Step three recomputes `funding_posture`, which after a reinstatement can only be `OPEN` or `RESTRICTED` and never `FROZEN`. Across the whole suspend-then-reinstate pair the payment-obligation invariant holds: the sum of `scheduled_amount_cents` over the agreement's payments equals `accepted_value_cents` before the freeze and after the thaw, because a held payment's `scheduled_amount_cents` never changes across the cycle. The `version` increments once on each leg.

The system does not police cure deadlines on a timer; the publisher asks it to. A `PublisherFinance` operator on an `ACTIVE` agreement may run a cure sweep, which examines every milestone of the agreement whose `status` is `CURE_PENDING` and whose `cure_deadline_at` the logical clock has passed strictly, and moves each one `CURE_PENDING → BREACHED`. If no `CURE_PENDING` milestone has actually run out of time — that is, if every open cure deadline is still greater than or equal to the logical clock — there is nothing to sweep and the request is refused with `ERR_CURE_WINDOW_STILL_OPEN`. A successful sweep escalates in four ordered steps. Step one recomputes `breach_count` from the milestones that just breached. Step two, because `breach_count` has reached at least one, moves the agreement `ACTIVE → SUSPENDED` with `funding_posture` set to `FROZEN`. Step three, because the agreement is now suspended, applies the ordinary suspension consequences: `PENDING_AUTHORIZATION` payments become `HELD_PENDING_CURE` and `ACTIVE` engagements become `SUSPENDED`. Step four recomputes `withheld_payment_cents`. A breached milestone is terminal — it never returns to development — and the sweep is therefore the mechanism by which a missed cure period converts into a frozen production.

### 3.4. Build Delivery and the Acceptance Gate

Delivering a build is the studio's privilege and nobody else's: only a `Developer` may submit one. The submission names the `milestone_id` it is delivered against and a `build_number` of at least 1 that must strictly exceed the milestone's `latest_build_number`, and then declares four measurements of the build's actual condition. `feature_completeness_pct` is the share of the milestone's features implemented, `crash_free_sessions_pct` the share of play sessions that ended without a crash, and `content_completeness_pct` the share of shippable content present — all three carried to two decimal places within 0.00 through 100.00. `known_blocker_count` is the number of open blocker-severity defects the studio is willing to declare, and cannot be negative. A cure resubmission additionally carries `addressed_condition_indexes`, the acceptance-criteria positions this build claims to have fixed, which defaults to an empty array. `release_notes` may be attached for the reviewer's benefit and affects nothing.

The gate is where a milestone's `gate_profile` earns its keep, and the three profiles are deliberately far apart. An `ALPHA` milestone demands feature completeness of at least 70.00 percent, crash-free sessions of at least 95.00 percent, content completeness of at least 50.00 percent, and no more than 20 known blockers. A `BETA` milestone raises those to 90.00, 98.00 and 80.00 percent with at most 5 blockers. A `GOLD` milestone is the ship candidate and admits no slack whatsoever: 100.00 percent features, 99.50 percent crash-free sessions, 100.00 percent content, and zero known blockers.

Two adjustments are applied to the profile's raw bars before the build is compared against them, and their order is fixed. The content bar is computed first: start from the profile's content figure, subtract the milestone's accumulated `content_threshold_relief_pct` — the relief that approved feature cuts have bought — then, and only when the milestone's `status` is `CURE_PENDING`, add back 5.00 percentage points, because a cure round is expected to have shipped more content than the round that failed. The result is then clamped: never below 0.00 and never above 100.00. The feature bar is computed second, and it is where a stability surplus can buy a little feature slack. When the milestone's `gate_profile` is not `GOLD` and the build's `crash_free_sessions_pct` is at least half a percentage point above the profile's crash-free figure, the effective feature bar is the profile's feature figure less 2.00 percentage points; otherwise it is the profile's feature figure unchanged. A `GOLD` milestone never earns this concession, however stable the build.

The build then passes only if all four conditions hold simultaneously, and every comparison is inclusive: `feature_completeness_pct` is at least the effective feature bar, `crash_free_sessions_pct` is at least the profile's crash-free figure — the raw one, never adjusted — `content_completeness_pct` is at least the effective content bar, and `known_blocker_count` is at most the profile's blocker allowance. If any of the four fails, the submission is rejected with `ERR_BUILD_GATE_NOT_MET` and no build row is persisted at all. Only the one submitted payload and the target milestone's `gate_profile`, `status` and `content_threshold_relief_pct` participate in this evaluation; no earlier build row influences it.

Every build that passes also records a `readiness_score`, a single weighted figure for reviewers to skim: `feature_completeness_pct` weighted at 0.45, plus `crash_free_sessions_pct` weighted at 0.35, plus `content_completeness_pct` weighted at 0.20, with the total of those three weighted terms rounded half up to two decimal places. Note that the score is informational — it is computed from the raw measurements and never itself gates anything.

Delivery is guarded by a short chain of state rules ahead of the gate arithmetic. The agreement must be `ACTIVE`, or the answer is `ERR_AGREEMENT_NOT_ACTIVE`. The milestone must be open for delivery, meaning its `status` is `DEFINED`, `IN_DEVELOPMENT` or `CURE_PENDING`; anything else, and in particular a milestone already `UNDER_REVIEW`, `ACCEPTED`, `BREACHED` or `CANCELLED`, is `ERR_MILESTONE_NOT_OPEN_FOR_BUILD`. A milestone that is still `DEFINED` inside an active agreement is by construction one whose predecessor has not been accepted, and that is reported separately: when the milestone has a `depends_on_milestone_id` whose target has not reached `ACCEPTED`, the submission is refused with `ERR_DEPENDENCY_NOT_ACCEPTED`. A `build_number` that fails to exceed `latest_build_number` is `ERR_BUILD_NUMBER_NOT_INCREASING`. On a cure resubmission, `addressed_condition_indexes` must cover every entry of the milestone's `open_condition_indexes` — it may cover more, but it may not omit one — and a shortfall is `ERR_CONDITIONS_NOT_ADDRESSED`. Finally the cure window itself must still be open: if the milestone is `CURE_PENDING` and the logical clock has moved strictly past its `cure_deadline_at`, the submission is `ERR_CURE_WINDOW_EXPIRED`. Note that the gate arithmetic is evaluated *before* the cure window, so a late build that also misses its thresholds reports the gate failure rather than the expiry.

A successful submission writes the build with `gate_state` of `PASSED` and `submitted_at` from the logical clock, drives the milestone `IN_DEVELOPMENT → UNDER_REVIEW` or `CURE_PENDING → UNDER_REVIEW`, and sets the milestone's `latest_build_number` to the new `build_number`. Every earlier build of the same milestone still sitting at `PASSED` is moved `PASSED → SUPERSEDED`; superseded builds remain fully readable, they simply can no longer be reviewed. When the submission was a cure resubmission, the milestone's `open_condition_indexes` is cleared to an empty array and its `cure_deadline_at` back to null — the cure obligation has been discharged by delivery, and earlier windows on the same milestone are closed for good and never reopen. Because a milestone may be rejected or conditioned repeatedly, it may re-enter `UNDER_REVIEW` any number of times.

Builds are readable individually, including their `readiness_score` and `gate_state`, and the full delivery history of a milestone is available as a list that may be narrowed by `gate_state` and is ordered by `build_number` descending so the current build appears first.

### 3.5. The Publisher Verdict: Acceptance, Cure Rounds and Rejection

Recording a verdict is the exclusive act of a `PublisherReviewer`. The submission names the `build_id` under review and a `verdict` of `ACCEPTED`, `CONDITIONAL` or `REJECTED`, and it must also declare the review window the reviewer is occupying while doing the work: `review_window_start_at` and `review_window_end_at`, both ISO 8601 UTC instants with three fractional digits. A `CONDITIONAL` verdict additionally carries `conditions`, and may carry `cure_days`; free-text `notes` are always optional. The server stamps `reviewer_user_id` from the acting `X-User-ID` and `decided_at` from the logical clock. A review is immutable from that instant: there is no way to amend, retract or delete one, which is why it is the single resource in this API with neither `updated_at` nor `version`.

Before any verdict is applied, the reviewer's calendar is checked. A review window is treated as a half-open instant interval that includes its start and excludes its end, and each reviewer has a concurrent capacity of exactly one: no two reviews of the same `reviewer_user_id` may occupy overlapping windows, across every agreement that reviewer works on, and because reviews are immutable none is ever excluded from the comparison. Two windows conflict when the new window's start falls strictly before the existing window's `review_window_end_at` and the existing window's `review_window_start_at` falls strictly before the new window's end; a conflict is `ERR_REVIEWER_WINDOW_CONFLICT`. Because both comparisons are strict, back-to-back windows are legal — a new window may begin at the exact instant an existing one ends, or end at the exact instant an existing one begins. Separately, the window must be well formed: `review_window_end_at` must fall strictly after `review_window_start_at`, and a degenerate or inverted window is `ERR_INVALID_DATE_RANGE`. As §2.10 fixes, the overlap check is evaluated before the well-formedness check, so a zero-length window that also collides with an existing one reports the collision.

Two further state rules apply to any verdict. The milestone must currently be `UNDER_REVIEW`, and anything else — including a second attempt to review a build whose milestone has already moved on — is `ERR_MILESTONE_NOT_UNDER_REVIEW`. And the reviewed build must be the current one: a build whose `gate_state` has become `SUPERSEDED`, equivalently one whose `build_number` is no longer the milestone's `latest_build_number`, is refused with `ERR_BUILD_SUPERSEDED`. Where a verdict is `CONDITIONAL`, every value in `conditions` must be a valid zero-based index into the target milestone's `acceptance_criteria` array, and an out-of-range or otherwise invalid index is `ERR_INVALID_CONDITION_INDEX`.

An **acceptance** is the most consequential single request in the system. It sets the milestone's `status` to `ACCEPTED`, stamps `accepted_at` from the logical clock, and clears `open_condition_indexes` to an empty array. Five cascade steps then run, strictly in this order. Step one creates exactly one milestone payment in `PENDING_AUTHORIZATION` whose `scheduled_amount_cents` is the milestone's `funded_amount_cents` plus its `uplift_cents` frozen at the instant of acceptance. Step two, because this milestone became `ACCEPTED`, promotes every milestone whose `depends_on_milestone_id` points at it and whose `status` is still `DEFINED` from `DEFINED → IN_DEVELOPMENT`, which in turn promotes each of those milestones' `PROPOSED` engagements to `ACTIVE`. Step three, because `accepted_value_cents` has grown, re-evaluates `funding_posture`: the posture flips `OPEN → RESTRICTED` as soon as `accepted_value_cents` reaches the thirty-percent-of-pool threshold described in §2.6. Step four, and only when the posture has become `RESTRICTED`, moves every contractor engagement of this agreement whose `status` is `PROPOSED` or `ACTIVE` and whose milestone's `status` is `DEFINED` or `IN_DEVELOPMENT` to `SUSPENDED`; engagements belonging to a milestone that is itself `ACCEPTED` are left untouched. Note that step two runs before step four, so an engagement that step two has just promoted to `ACTIVE` can legitimately be suspended again by step four inside the same request. Step five, evaluated last of all after the funding ledger has been recomputed, tests the agreement for completion, as described in §3.9.

A **conditional** verdict opens a cure period instead of paying anything. It moves the milestone `UNDER_REVIEW → CURE_PENDING`, increments the milestone's `cure_count` by one, and copies the submitted `conditions` into the milestone's `open_condition_indexes` so the studio knows exactly which acceptance criteria remain outstanding. The window's length comes from `cure_days`, a whole number of days between 1 and 30 that defaults to 14 when omitted and is meaningful only for this verdict; the deadline is the review's `decided_at` advanced by that many days — that is, by `cure_days` multiplied by 86400 seconds — and it is written both to the review's own `cure_deadline_at` and to the milestone's `cure_deadline_at`. The bound is inclusive at millisecond granularity: a resubmission arriving at exactly the deadline instant is admissible, one arriving a millisecond later is not. No milestone payment is created by a conditional verdict and not one funding-ledger field changes. Cure rounds are also finite: a milestone whose `cure_count` has already reached two refuses a third conditional verdict with `ERR_CURE_LIMIT_EXCEEDED`, and because `cure_count` is never decremented, the two rounds a milestone is granted are spent permanently. For a verdict that is not `CONDITIONAL`, the review's `cure_deadline_at` stays null.

A **rejection** sends the milestone back to the studio. It moves the milestone `UNDER_REVIEW → IN_DEVELOPMENT`, clears `open_condition_indexes` to an empty array and `cure_deadline_at` to null, and moves the reviewed build `PASSED → SUPERSEDED` so that it can never be reviewed again. Like a conditional verdict, a rejection creates no payment and moves no money. The studio's remedy is an ordinary redelivery: submit a higher `build_number` and the milestone re-enters `UNDER_REVIEW`, and the loop `UNDER_REVIEW → IN_DEVELOPMENT → UNDER_REVIEW` may repeat as often as the parties can stand it.

Whichever branch fires, the agreement's `version` increments by one. Reviews can be read individually and listed with narrowing by `build_id`, by `reviewer_user_id` or by `verdict` — the last of which is the practical way to audit how a given reviewer has been deciding.

### 3.6. Authorizing Milestone Payments

No client ever creates a milestone payment. A payment exists only because an acceptance cascade created it, which means the payment list — narrowable by `milestone_id`, by `authorized_by_user_id` or by `status` — is the sole discovery channel for a payment a client did not watch being born. A freshly created payment carries its `milestone_id`, its frozen `scheduled_amount_cents`, and a `status` of `PENDING_AUTHORIZATION`; `authorized_by_user_id`, `contractor_overrun_cents`, `gross_amount_cents`, `holdback_bps`, `holdback_cents`, `net_amount_cents` and `authorized_at` are all null until somebody authorizes it, because every one of them is computed at authorization time rather than at acceptance time.

Authorization is a `PublisherFinance` act and may carry an optional `memo`. The payment must be in `PENDING_AUTHORIZATION`, and a payment already `AUTHORIZED`, `HELD_PENDING_CURE` or `WITHHELD` is refused with `ERR_PAYMENT_NOT_PENDING`. The milestone the payment settles must be `ACCEPTED` — which it always is unless a termination has intervened, in which case the payment itself will already have been withheld. The agreement must be `ACTIVE` or `COMPLETED`, the single widened state window in this API, for the reason set out in §2.10 rule 23. The acting operator must be licensed for funding work and must belong to the agreement's publisher. And, above all, the acting `X-User-ID` must differ from the `reviewer_user_id` recorded on the accepting review of that milestone; when they are the same person the request dies with `ERR_SEGREGATION_OF_DUTIES`.

The disbursement arithmetic then runs in four pinned steps, and no other evaluation order is admissible. **Step one** determines the gross. The milestone's contractor spend on the incurred basis — the sum of `amount_cents` over every invoice in `APPROVED` status belonging to any engagement of that milestone — is compared against the milestone's `contractor_budget_cents`, and `contractor_overrun_cents` is the excess, floored at zero, so a milestone that stayed inside its outsourcing budget records an overrun of 0. `gross_amount_cents` is then `scheduled_amount_cents` less `contractor_overrun_cents`: the publisher recovers a contractor blowout out of the milestone payment itself. **Step two** selects the quality holdback tier, and it reads the *step-one gross*, never the scheduled amount — this distinction matters precisely when an overrun drags a payment down across a tier boundary. A gross of at most 2500000 cents, that is 25000 currency units, attracts a tier rate of 0 basis points; a gross above that but at most 10000000 cents, 100000 currency units, attracts 500 basis points, a five percent holdback; anything larger attracts 1000 basis points, ten percent. Both tier comparisons are inclusive at their upper bound. **Step three** adds the cure penalty to the rate *before* any rounding happens: the penalty is 250 basis points for each time the milestone entered a cure period, as counted by its `cure_count`, capped at 500 basis points however many rounds were consumed, and `holdback_bps` is the tier rate plus that capped penalty. `holdback_cents` is then `gross_amount_cents` multiplied by `holdback_bps`, divided by 10000, and rounded half up to whole cents — the single rounding operation in the entire calculation. **Step four** is simply the remainder: `net_amount_cents` is `gross_amount_cents` less `holdback_cents`, and that is what the studio actually receives.

Authorization writes all five computed components onto the payment, sets its `status` to `AUTHORIZED`, stamps `authorized_at` from the logical clock and `authorized_by_user_id` from the acting `X-User-ID`, and then cascades onto the agreement. Step one adds `net_amount_cents` to `advance_disbursed_cents` and `holdback_cents` to `holdback_reserve_cents`. Step two, because the disbursed figure moved, recomputes `unrecouped_advance_cents` as `advance_disbursed_cents` less `advance_recouped_cents`, and moves `recoupment_state` from `PRE_RECOUP` to `RECOUPING` as soon as `advance_disbursed_cents` is greater than zero — the moment any real money has left the publisher, the agreement is in recoupment. The agreement's `version` increments by one.

Payments also move without anybody authorizing them. A suspension parks a pending payment at `HELD_PENDING_CURE` and a reinstatement releases it back to `PENDING_AUTHORIZATION`, a cycle that may repeat indefinitely and that never alters `scheduled_amount_cents`. A termination is final in the other direction: a payment in either `PENDING_AUTHORIZATION` or `HELD_PENDING_CURE` moves to `WITHHELD` and stays there. Both `AUTHORIZED` and `WITHHELD` are terminal. Every one of these movements recomputes `withheld_payment_cents` on the agreement. Individual payments are readable in full, including every disbursement component.

### 3.7. Scope Change Management: Uplifts, Cuts and the Ship Date

Renegotiation is a first-class workflow rather than an exception, and either side may open it: a `Developer`, a `PublisherReviewer` or a `PublisherFinance` operator may all propose a change order. The proposal names the `agreement_id` and the `target_milestone_id` whose scope is moving, declares an `order_type` of `FUNDING_UPLIFT` for extra money or `FEATURE_CUT` for scope removed, and records a `rationale` of one to 500 non-blank characters that becomes the audit trail for the decision. `requested_amount_cents` is the additional funding sought under an uplift or the funding credited back under a cut; it must not be negative, defaults to 0, and an uplift specifically must ask for at least 1 cent. `ship_date_delta_days` is the whole-day shift the change will apply to the agreement's `ship_date_current` when approved; it defaults to 0, may be negative when a cut pulls the date in, and is bounded to the range from -60 to 60 inclusive. `content_threshold_relief_pct` is the number of percentage points to be removed from the target milestone's content bar, carried to two decimal places between 0.00 and 25.00 inclusive, defaulting to 0.0 and mandatory on a `FEATURE_CUT`. Every proposal must also carry `expected_agreement_version`, as §2.7 requires.

A proposal is written in state `PROPOSED`, and creating it cascades: any other change order with the same `target_milestone_id` still sitting in `PROPOSED` is moved to `SUPERSEDED` immediately. A superseded proposal can never be decided — attempting to decide one, or to decide an order already resolved, is `ERR_CHANGE_ORDER_NOT_PROPOSED`. The agreement's `version` increments on creation, which is exactly why the version check exists: without it a client could unknowingly displace a proposal it had never read. The target milestone must be amendable both when the order is created and again when it is decided, meaning its `status` is `DEFINED`, `IN_DEVELOPMENT`, `UNDER_REVIEW` or `CURE_PENDING`; a target that is `ACCEPTED`, `BREACHED` or `CANCELLED` is `ERR_MILESTONE_NOT_AMENDABLE`. An *approval* narrows that set further — the target must be `DEFINED`, `IN_DEVELOPMENT` or `CURE_PENDING`, so an approval aimed at a milestone currently `UNDER_REVIEW` is likewise refused with `ERR_MILESTONE_NOT_AMENDABLE` — while a decline remains available for all four amendable states.

Deciding is exclusively a `PublisherFinance` act. The request carries a `decision` of either approval or decline, plus an optional `decision_note`, and the outcome forks into three structurally different side-effect sets.

**Branch A — approving a funding uplift.** The uplift is capped: the agreement's existing `uplift_funded_cents` plus this order's `requested_amount_cents` must not exceed twenty-five percent of `advance_total_cents`, computed by multiplying `advance_total_cents` by 2500 basis points, dividing by 10000 and rounding half up to whole cents. Breaching the cap is `ERR_UPLIFT_CAP_EXCEEDED`, and nothing is written. On approval the order's `state` becomes `APPROVED_UPLIFT` with `decided_at` stamped from the logical clock; the target milestone's `uplift_cents` grows by `requested_amount_cents`; and the agreement's `uplift_funded_cents`, `funding_pool_cents`, `committed_cents` and `available_funding_cents` are all recomputed. The ship date is then recomputed, and `funding_posture` is re-evaluated — a pool that has just grown can carry an agreement from `RESTRICTED` back to `OPEN`.

**Branch B — approving a feature cut.** A cut may not push a milestone's funding below zero: `requested_amount_cents` must not exceed the target milestone's `funded_amount_cents` plus its current `uplift_cents`, and an over-large cut is `ERR_CUT_EXCEEDS_MILESTONE_FUNDING`. On approval the order's `state` becomes `APPROVED_CUT` with `decided_at` stamped; the target milestone's `uplift_cents` is *reduced* by `requested_amount_cents`, crediting that money back to the pool; and the milestone's `content_threshold_relief_pct` grows by the order's own `content_threshold_relief_pct`, permanently lowering the content bar every future build of that milestone will face. The agreement's `committed_cents` and `available_funding_cents` are recomputed, but `uplift_funded_cents` is deliberately **not** touched — a cut returns money to the pool by shrinking the commitment, not by unwinding a previously granted uplift. The ship date is recomputed exactly as in branch A.

**Branch C — declining.** A decline writes the order's `state` as `DECLINED` and its `decided_at`, and nothing else at all: no funding field, no content threshold and no ship date moves.

All three branches increment the agreement's `version` by one. The ship-date recomputation shared by the two approval branches works from scratch rather than incrementally: take every change order of the agreement whose `state` is `APPROVED_UPLIFT` or `APPROVED_CUT`, process them in ascending `decided_at` order with ties broken by ascending `created_at`, and set `ship_date_current` to `ship_date_original` advanced by the sum of their `ship_date_delta_days` in whole calendar days. `schedule_slip_days` is then the difference in whole days between `ship_date_current` and `ship_date_original`, and it is negative when accumulated cuts have pulled the date earlier than the contract's original. Orders in `PROPOSED`, `DECLINED` or `SUPERSEDED` never move the ship date. The slip is bounded in both directions: an approval whose resulting `schedule_slip_days` would exceed 45 days of slip, or 45 days of acceleration, is refused with `ERR_SHIP_DATE_SLIP_EXCEEDED` and no field is written. Change orders can be read individually and listed with narrowing by `agreement_id`, by `target_milestone_id` or by `state`.

### 3.8. Outsourcing: Engagements, Vendor Cooldown and Contractor Invoices

Milestone budgets are what make outsourcing safe, and only a `Developer` may spend one. Engaging a vendor names the `milestone_id` whose budget will fund the work, a `vendor_code` of two to 40 characters drawn from uppercase letters, digits and dashes that stably identifies the external contractor, a `scope_summary` of one to 300 non-blank characters describing what is being outsourced, a `committed_cents` of at least 1 cent reserving part of the milestone's outsourcing budget, and the closed calendar interval the vendor will work across as `start_date` and `end_date`, where the end may equal but never precede the start. The server denormalises `studio_id` onto the engagement from the milestone's agreement, because the vendor-cooldown rule below is scoped by studio rather than by milestone, and initialises `approved_invoice_total_cents` to 0. A new engagement is born `PROPOSED` when its milestone is still `DEFINED`, and born `ACTIVE` when the milestone has already reached `IN_DEVELOPMENT`, `UNDER_REVIEW` or `CURE_PENDING` — in the latter case the engagement never uses the `PROPOSED → ACTIVE` promotion at all.

Four checks stand between the request and the engagement, in this order. The agreement must be `ACTIVE`, which is what makes it impossible for an engagement to predate activation. The milestone must be open for outsourcing, meaning its `status` is `DEFINED`, `IN_DEVELOPMENT` or `CURE_PENDING`; anything else is `ERR_MILESTONE_NOT_OPEN_FOR_OUTSOURCING`, and note that this state rule deliberately outranks the budget cap, so an over-budget engagement pointed at an already-accepted milestone reports the state problem and never the money problem. The dates must be well formed, with an `end_date` earlier than `start_date` reported as `ERR_INVALID_DATE_RANGE`. Then the vendor cooldown is evaluated, and only afterwards the budget.

The **vendor cooldown** exists because a studio that churns the same outsourcing house back to back is usually hiding a schedule problem. The candidate set is every engagement sharing this engagement's `studio_id` and `vendor_code` whose `status` is `PROPOSED`, `ACTIVE`, `SUSPENDED` or `COMPLETED`; engagements that were cancelled or terminated early release their dates immediately and are ignored. Each candidate is treated as a closed date interval and padded symmetrically by a three-day buffer on both sides: a conflict exists when the new engagement's `start_date` falls on or before the candidate's `end_date` plus three days **and** the candidate's `start_date` falls on or before the new engagement's `end_date` plus three days. Because the intervals are closed and both sides carry the buffer, adjacency is illegal rather than legal here — three days after a prior engagement's `end_date` is still blocked, and the fourth day after it is the earliest lawful `start_date`. A conflict is `ERR_VENDOR_COOLDOWN_CONFLICT`.

The **budget** is then checked on the committed basis. A milestone's committed basis is the sum of `committed_cents` over every engagement of that milestone whose `status` is `PROPOSED`, `ACTIVE`, `SUSPENDED` or `COMPLETED` — a forward-looking figure that counts the full commitment of each live engagement whether or not a single invoice has ever been approved against it. Admission requires that basis plus the new engagement's `committed_cents` to be no greater than the milestone's `contractor_budget_cents`; exceeding it is `ERR_CONTRACTOR_BUDGET_EXCEEDED`. The complementary figure is the **incurred basis**: the sum of `amount_cents` over every invoice in `APPROVED` status whose engagement belongs to the milestone, computed without regard to the engagement's own status — so a cancelled or terminated engagement leaves the committed basis but its already-approved invoices remain on the incurred basis forever. From those two, the milestone's budget summary exposes `milestone_id`, `contractor_budget_cents`, `committed_basis_cents`, `incurred_basis_cents`, an `available_committed_cents` that is the budget less the committed basis floored at zero, and an `overrun_cents` that is the incurred basis less the budget, likewise floored at zero. The incurred figure can legitimately exceed both the committed figure and the milestone's budget, which is exactly how `contractor_overrun_cents` comes to bite at payment authorization.

Engagements have two developer-driven exits. Completing one requires it to be `ACTIVE`, moving it `ACTIVE → COMPLETED`; a completion attempted from any other status is `ERR_ENGAGEMENT_STATE_INVALID`, and a completion attempted while any invoice of the engagement is still `SUBMITTED` is `ERR_ENGAGEMENT_HAS_OPEN_INVOICES`. A completed engagement's `committed_cents` stays counted on the committed basis — closing out work does not hand budget back. Cancelling, by contrast, is the compensating action: it is available from `PROPOSED`, `ACTIVE` or `SUSPENDED`, may carry an optional `reason`, and moves the engagement to `CANCELLED`, at which point it leaves the committed basis and restores the milestone's outsourcing headroom exactly. Cancellation is only lawful while no money has been incurred: an `approved_invoice_total_cents` greater than zero is `ERR_ENGAGEMENT_HAS_APPROVED_INVOICES`, since spend already approved cannot be un-committed. Cancelling also cascades onto paperwork — every invoice of that engagement still in `SUBMITTED` moves to `VOIDED`. Engagements are readable individually and listable with narrowing by `milestone_id`, by `studio_id`, by `vendor_code` and by `status`.

Vendors bill through invoices, and again only a `Developer` submits them. An invoice names its `engagement_id`, an `invoice_number` of one to 40 characters that must be unique within that engagement, an `amount_cents` of at least 1, and the `period_end_date` closing the billed period; a free-text `description` is optional. Uniqueness is absolute rather than status-scoped: a number already used by an invoice of that engagement in *any* status, including a `VOIDED` one, is `ERR_INVOICE_NUMBER_TAKEN`. An invoice may only be submitted against an engagement whose `status` is `ACTIVE` or `COMPLETED`; a `SUSPENDED`, `CANCELLED` or `TERMINATED_EARLY` engagement accepts no new billing and answers `ERR_ENGAGEMENT_NOT_INVOICEABLE`. New invoices land in `SUBMITTED`.

Deciding an invoice belongs to `PublisherFinance` and carries a `decision` plus, on a rejection, a `rejection_reason` that must be present and non-blank. Only a `SUBMITTED` invoice can be decided; one already `APPROVED`, `REJECTED` or `VOIDED` is `ERR_INVOICE_NOT_SUBMITTED`, and a voided invoice can never be decided at all. Approving additionally requires the engagement to be `ACTIVE` — not merely `COMPLETED` — and requires the engagement's milestone not to be `CANCELLED`; either failure is `ERR_ENGAGEMENT_NOT_INVOICEABLE`. Approval is also bounded by a tolerance that intentionally exceeds the commitment: the engagement's `approved_invoice_total_cents` plus this invoice's `amount_cents` must not exceed 12500 basis points of the engagement's `committed_cents` — one hundred and twenty-five percent, computed by multiplying `committed_cents` by 12500, dividing by 10000 and rounding half up — and a breach is `ERR_INVOICE_EXCEEDS_ENGAGEMENT`. That headroom is what lets an outsourcing bill legitimately overshoot its engagement and therefore what lets a milestone overrun its contractor budget. An approval sets the invoice's `status` to `APPROVED`, stamps `decided_at` from the logical clock, adds `amount_cents` to the engagement's `approved_invoice_total_cents`, and grows the milestone's incurred basis. A rejection sets `status` to `REJECTED` with `decided_at` and the recorded `rejection_reason`, and changes neither basis; rejecting is always available while the invoice is still `SUBMITTED`, and never trips the tolerance check. Invoices are readable individually and the full billing history of one engagement is listable with narrowing by `status`.

### 3.9. Revenue, Recoupment, Termination and the Post-Launch Phase

Once a game earns, the money walks down a waterfall: the storefront takes its cut, the publisher deducts capped costs, the publisher then recovers the advance it has actually disbursed, and only what survives all three is charged with the developer's royalty. Reporting is exclusively a `PublisherFinance` act. A statement names its `agreement_id`, a `period_label` matching the pattern of four digits, a dash, the letter Q and a quarter digit from 1 to 4 — `2027-Q3`, for instance — and `revenue_lines`, an array of between zero and twelve per-platform objects each carrying a `platform_code` string, a non-negative `gross_cents` and a non-negative `returns_cents` that must not exceed that line's own `gross_cents`, with `platform_code` unique within the statement. An empty array is legal and describes a quarter with no revenue at all. `recoupable_cost_cents` declares the publisher costs claimed against this period before any cap is applied, defaults to 0 and must not be negative. `expected_agreement_version` is mandatory, per §2.7.

Three gates guard creation, in the order §2.10 fixes: a period that already has a `FINALIZED` statement cannot be reported again, which is `ERR_PERIOD_ALREADY_FINALIZED`; a `period_label` that sorts strictly before the `period_label` of the agreement's most recently finalized statement is a regression and earns `ERR_PERIOD_OUT_OF_ORDER`; and the agreement must be revenue-eligible, meaning its `status` is `ACTIVE` or `COMPLETED`, since a `DRAFT`, `SUSPENDED` or `TERMINATED` agreement has no reporting surface and answers `ERR_AGREEMENT_NOT_REVENUE_ELIGIBLE`. Creation also cascades: any other statement of the same agreement and the same `period_label` still in `DRAFT` moves to `SUPERSEDED`, and a superseded statement can never be finalized. The agreement's `version` increments.

Creation computes the **provisional** settlement, which is period-scoped and stored once, never rewritten. First, the distributable revenue is built line by line, iterating `revenue_lines` in the order submitted. For each line, the net is that line's `gross_cents` less its `returns_cents`; the platform fee for that line is the net multiplied by the agreement's `platform_fee_bps`, divided by 10000 and rounded half up to whole cents; and the line's distributable amount is its net less its own rounded platform fee. `distributable_total_cents` is the sum of those per-line distributable amounts, and it is 0 when `revenue_lines` is empty. The rounding happens per line and only then are the lines summed — rounding a single combined net once would produce a different figure and is not the specified behaviour. Second, the cost cap is applied: the period's cap is `distributable_total_cents` multiplied by the agreement's `recoupable_cost_cap_bps`, divided by 10000 and rounded half up, and `cost_deduction_cents` is the smaller of the claimed `recoupable_cost_cents` and that cap. Third, `recoupment_base_cents` is `distributable_total_cents` less `cost_deduction_cents`, floored at zero. Fourth, `recoup_applied_cents` is the smaller of the agreement's `unrecouped_advance_cents` as observed at creation time and `recoupment_base_cents`. Fifth, `royalty_base_cents` is `recoupment_base_cents` less `recoup_applied_cents` — the only money the developer's royalty rate ever touches. Finally `provisional_royalty_payable_cents` is computed with a pinned rounding order: the royalty base is pro-rated onto each revenue line in proportion to that line's distributable amount over `distributable_total_cents`, each pro-rated share is multiplied by the agreement's `royalty_rate_bps` and divided by 10000, **each line's result is rounded half up on its own**, and only then are the per-line results summed. When `distributable_total_cents` is 0 the sum is empty and the provisional royalty is therefore 0.

Finalizing a statement is a separate, later act, again by `PublisherFinance`. The statement must still be `DRAFT` — a `FINALIZED` or `SUPERSEDED` statement answers `ERR_STATEMENT_NOT_DRAFT` — and the agreement must still be revenue-eligible under the same `ACTIVE`-or-`COMPLETED` test. Finalization recomputes the settlement on a **life-to-date** basis, which is where the second variant of the waterfall differs materially from the first. The working set is every statement of this agreement whose `state` is `FINALIZED`, ordered by ascending `finalized_at` with ties broken by ascending `created_at`, together with the statement now being finalized; statements in `DRAFT` or `SUPERSEDED` are excluded entirely. Cumulative distributable revenue is the sum of `distributable_total_cents` across that set, and cumulative claimed cost the sum of `recoupable_cost_cents` across it. The cumulative allowed cost is the smaller of that cumulative claim and the cap taken on the *cumulative* distributable figure — cumulative distributable multiplied by `recoupable_cost_cap_bps`, divided by 10000, rounded half up — which is why a cost disallowed in an earlier period can legitimately soak up a later period's headroom. The cumulative recoupment base is cumulative distributable less cumulative allowed cost, floored at zero. The cumulative recoupment applied is the smaller of the agreement's life-to-date `advance_disbursed_cents` and that cumulative base; note the advance basis here is the total disbursed, not the per-period unrecouped balance the provisional variant used. The cumulative royalty base is the cumulative base less the cumulative recoupment applied, and the cumulative royalty owed is that base multiplied by `royalty_rate_bps`, divided by 10000 and rounded half up **exactly once** — a single rounding on the cumulative figure, not a per-line sum. `final_royalty_payable_cents` is then that cumulative owed figure less the agreement's `royalties_paid_to_date_cents`, so each finalization pays only the increment. The provisional fields are retained untouched throughout, so the two variants can be compared afterwards.

Finalization then posts to the agreement ledger in order. Step one sets `advance_recouped_cents` to the cumulative recoupment applied, then recomputes `unrecouped_advance_cents` as `advance_disbursed_cents` less that figure, floored at zero. Step two, because the unrecouped balance moved, advances `recoupment_state` from `RECOUPING` to `RECOUPED` the moment `unrecouped_advance_cents` reaches 0. Step three adds `final_royalty_payable_cents` to `royalties_paid_to_date_cents`. The statement's `state` becomes `FINALIZED` with `finalized_at` stamped from the logical clock, and the agreement's `version` increments. Statements are readable individually — showing both the provisional and the final payable figures — and the statements of one agreement are listable with narrowing by `state` and by `period_label`. A separate computed read exposes the whole recoupment and rights position of an agreement in one payload: `agreement_id`, `funding_pool_cents`, `advance_disbursed_cents`, `advance_recouped_cents`, `unrecouped_advance_cents`, `royalties_paid_to_date_cents`, `recoupment_state`, `accepted_milestone_ratio`, `ip_reversion_state`, `sequel_rights_holder`, `post_launch_support_state` and `live_ops_drawn_cents`. That read is a projection of the agreement's stored position rather than a fresh derivation: every one of those fields is reported exactly as the agreement currently holds it, and nothing is recomputed at read time. In particular `accepted_milestone_ratio`, `ip_reversion_state` and `sequel_rights_holder` read back whatever the rights settlement below last wrote, and therefore still read `0.0`, `NONE` and `PUBLISHER` on an agreement that has neither terminated nor completed — however many of its milestones have been accepted in the meantime.

Termination is the unhappy ending, available to `PublisherFinance` on an agreement whose `status` is `ACTIVE` or `SUSPENDED`, optionally with a `reason`; an already-`TERMINATED` or `COMPLETED` agreement answers `ERR_AGREEMENT_TERMINAL`. It sets `status` to `TERMINATED`, forces `funding_posture` to `FROZEN` and stamps `terminated_at` from the logical clock, and the cascade from either starting state is identical and runs in four ordered steps. Step one cancels unfinished work: every milestone whose `status` is `DEFINED`, `IN_DEVELOPMENT`, `UNDER_REVIEW` or `CURE_PENDING` moves to `CANCELLED`, which releases its committed funding and forces a recomputation of `committed_cents` and `available_funding_cents`; a milestone cancelled out of `UNDER_REVIEW` voids the pending review round while the build it was reviewing keeps its `gate_state` of `PASSED`, and one cancelled out of `CURE_PENDING` keeps its `cure_deadline_at` on the record for audit. Step two stops the money and the vendors: every milestone payment of the agreement whose `status` is `PENDING_AUTHORIZATION` or `HELD_PENDING_CURE` moves to `WITHHELD` — a terminated agreement disburses nothing further, whatever its milestone's status — and every contractor engagement of a now-cancelled milestone whose `status` is `PROPOSED`, `ACTIVE` or `SUSPENDED` moves to `TERMINATED_EARLY`. Step three, because those engagements were terminated early, moves each of their invoices still in `SUBMITTED` to `VOIDED`. Step four, because the milestone set has changed, recomputes `committed_cents`, `available_funding_cents` and `accepted_milestone_ratio`, and then settles the rights position described below. After the whole cascade the funding-pool invariant still holds: `available_funding_cents` equals `funding_pool_cents` less `committed_cents`. The agreement's `version` increments once.

Rights settlement is a single threshold calculation, evaluated both at termination and at completion, and always **after** the termination cascade has cancelled whatever it was going to cancel. `accepted_milestone_ratio` is the count of the agreement's milestones whose `status` is `ACCEPTED` divided by the count of *all* milestones ever created for the agreement — every status, `CANCELLED` and `BREACHED` included — rounded half up to four decimal places, and defined as 0.0 when the agreement never had a milestone at all. A ratio strictly below 0.5000 sets `ip_reversion_state` to `REVERTED_TO_DEVELOPER` and `sequel_rights_holder` to `DEVELOPER`: the publisher funded too little of the game to keep it. A ratio of at least 0.5000 but strictly below 0.8000 sets `ip_reversion_state` to `PARTIAL_REVERSION` and `sequel_rights_holder` to `SHARED` — the band is inclusive at its lower edge, so a ratio of exactly 0.5000 yields shared rights rather than full reversion. A ratio of 0.8000 or more sets `ip_reversion_state` to `RETAINED_BY_PUBLISHER` and `sequel_rights_holder` to `PUBLISHER`.

Completion, unlike termination, is something the system does on its own. Evaluated as the last step of an acceptance cascade, after the funding ledger has been recomputed, it fires when the agreement's `status` is `ACTIVE`, some milestone with a `gate_profile` of `GOLD` has reached `ACCEPTED`, and no milestone of the agreement remains in `DEFINED`, `IN_DEVELOPMENT`, `UNDER_REVIEW`, `CURE_PENDING` or `BREACHED` — in other words the ship candidate is accepted and every other line of the schedule has been either accepted or cancelled. The agreement then moves `ACTIVE → COMPLETED`, `post_launch_support_state` becomes `ACTIVE`, which is what unlocks live-operations funding, and the same rights settlement above writes `ip_reversion_state` and `sequel_rights_holder`. Payments already sitting in `PENDING_AUTHORIZATION` stay authorizable across this transition, which is the whole reason the authorization state window admits a `COMPLETED` agreement. The `version` increments.

Live-operations funding is the last money to move. A `PublisherFinance` operator draws against it by supplying an `amount_cents` and an optional `memo`. The draw is refused with `ERR_POST_LAUNCH_NOT_ACTIVE` unless `post_launch_support_state` is `ACTIVE` — a `PENDING` agreement has not shipped and an `EXPIRED` one has spent its envelope. Two caps then apply, and both report `ERR_LIVE_OPS_CAP_EXCEEDED`: a single draw may not exceed `live_ops_quarterly_funding_cents`, and the agreement's `live_ops_drawn_cents` plus this draw may not exceed the total envelope, which is `live_ops_quarterly_funding_cents` multiplied by the four quarters of post-launch support the agreement funds. A permitted draw adds `amount_cents` to `live_ops_drawn_cents`, and the moment `live_ops_drawn_cents` equals the four-quarter total exactly, `post_launch_support_state` flips to `EXPIRED` and no further draw will ever succeed. The `version` increments. Note that neither a royalty statement nor a live-ops draw is blocked by the terminal-agreement rule that guards scope changes: both are post-launch operations deliberately governed by their own eligibility gates instead.

## 4. Endpoint Definitions

Every endpoint below is rooted at the API base path, so the paths given are absolute and flat: the identifier segments are opaque server-minted UUIDs and never composite keys. Status codes follow one consistent rule. An endpoint that creates a new resource answers `201 Created` and returns the created resource in the `data` field; every other successful call answers `200 OK`, whether it is a read, a list, or a state-changing action such as an activation, a decision, an authorization or a finalization. State-changing actions return the resource they mutated, so an activation returns the agreement, a review decision returns the review, and a payment authorization returns the payment. List endpoints return an array in `data` together with the pagination `meta` described in §2.3. Failures follow §2.10: the first rule in the total order whose condition holds determines both the error identifier and, via §5, the HTTP status code. Unless a row's description says otherwise, the authorization requirements in the final column are evaluated after the authentication checks of §2.1 and before any input validation.

| Method | Path | Description | Authorized Role(s) |
