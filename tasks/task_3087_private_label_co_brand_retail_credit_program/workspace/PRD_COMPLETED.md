# Private Label Retail Credit Program API — Product Requirements Document

## 1. Introduction

Retail credit programs sit at an intersection of two businesses that rarely share a vocabulary: a retailer that wants its customers financed at the point of sale, and an issuer that carries the receivable, the promotional subsidy, and the regulatory disclosure burden. This API is the servicing backbone of such a partnership. It holds the economic agreement between the two parties, the credit program issued under that agreement, the accounts and purchases that flow through the program, and the promotional financing machinery that makes the whole arrangement profitable for the retailer without becoming a one-sided subsidy for the issuer.

The commercial heart of the product is the deferred-interest promotion: a purchase above a minimum threshold is financed at no interest for a fixed term, and the interest that would have accrued is carried as an exposure the two parties have agreed to share. Modeling that exposure correctly — at the moment the promotion is written, and again when it is settled — is the single most important behavior in the system, because every partner-facing invoice, every reconciliation variance, and every wind-down purchase price is read off those two numbers. Alongside it sits a second, subtler requirement: the cardholder experience is branded as the retailer, so dispute handling, servicing correspondence, and loyalty accrual must all look and behave as though the retailer were the creditor.

What follows specifies the partner onboarding and agreement lifecycle, the program and account servicing flows, the application and instant-decisioning path, the promotional settlement and partner chargeback reconciliation, the dispute and loyalty benefit subsystem, and the wind-down and portfolio transfer process. It defines behavior only; no implementation structure is prescribed beyond the API contract itself.

## 2. Global Specifications & System-Wide Principles

### 2.1. User and Role-Based Access Control

Every request to the API must carry two headers. `X-User-ID` identifies the acting user, and `X-User-Role` declares the operational capacity in which they are acting. A request that omits or malforms either header is rejected with `ERR_UNAUTHENTICATED` (HTTP 401); a header value that is present but does not name one of the seven recognized role strings is treated as malformed and is likewise rejected with `ERR_UNAUTHENTICATED`, not `ERR_UNAUTHORIZED`. A request that carries a valid role which is not permitted for the requested operation is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

The system recognizes seven roles, spelled exactly as follows: `ProgramAdmin`, `RetailPartnerAnalyst`, `Underwriter`, `CardholderService`, `Cardholder`, `Applicant`, and `CoBrandIssuer`.

`ProgramAdmin` is the issuer-side operations administrator. `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity; the server may record it on resources where a transition names the acting operator, but it is never compared against any entity's `id`. The same is true of `Underwriter`, `CardholderService`, and `Applicant` — for each of these role values, `X-User-ID` is an opaque identifier with no corresponding entity row, and no ownership comparison is performed against it.

`RetailPartnerAnalyst` is a retail-partner-side analyst, and for this role `X-User-ID` is the `id` of the acting `RetailPartner`. Where an ownership check applies, it compares the resource's partner foreign-key field to `X-User-ID`. The check is enforced on exactly three reads and no others: reading one partner, reading one program agreement, and reading one program's economics summary; each rejects a resource belonging to another retailer with `ERR_UNAUTHORIZED` (HTTP 403). No ownership check runs when the analyst reads a credit program directly, nor when the analyst reads or lists settlement batches, so those reads are not restricted to the analyst's own retailer.

`Cardholder` is the consumer acting on their own account, and for this role `X-User-ID` is the `id` of the acting `Account`. Any operation a `Cardholder` performs that is anchored to an account — reading the account, posting a purchase on it, paying it, opening a dispute on it, or reading its loyalty view — is ownership-checked against that account identifier; a `Cardholder` may act only on the account named by `X-User-ID`, and a mismatch is rejected with `ERR_UNAUTHORIZED` (HTTP 403). Read operations on a transaction, a promotional plan, a benefit posting, or a dispute case are not ownership-checked.

`CoBrandIssuer` is a co-brand issuer partner holding a delegated portfolio purchase right; `X-User-ID` for this role is an opaque identifier not tied to a persisted entity, and it is not compared against any entity's `id`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.
- A request whose path does not resolve to any defined operation is reported as `ERR_RESOURCE_NOT_FOUND` (HTTP 404), and a request to a defined path under a method that path does not support is reported as `ERR_INVALID_REQUEST` (HTTP 400). Paths are matched with or without a trailing slash. A `POST` body that is present but is not well-formed JSON is likewise `ERR_INVALID_REQUEST` (HTTP 400).

### 2.3. Pagination

List endpoints accept two query parameters. `limit` sets the maximum number of items returned in one page; it defaults to 10 and must be an integer between 1 and 100 inclusive. `offset` sets the number of leading items to skip and defaults to 0. A `limit` that is not an integer or that falls outside 1–100, and an `offset` that is not an integer or that is negative, are rejected with `ERR_INVALID_REQUEST` (HTTP 400); an absent or empty parameter takes its default.

Unless a business rule states otherwise, list endpoints return resources sorted by `created_at` in ascending order.

List responses carry four pagination fields in the `meta` object of the envelope: `limit`, `offset`, `total_count`, and `has_more`. `total_count` reports the total number of matching resources before pagination is applied, and `has_more` reports whether further pages remain.

### 2.4. Retailer-Branded Servicing and Ownership Boundaries

Servicing correspondence in this program is issued in the retailer's name, never the issuer's. Every dispute case carries a `servicing_brand_name` field whose value is the owning retailer's `retailer_name`; it is a read-only projection computed at case creation and never accepted from a client. Nothing in the dispute workflow may cause an issuer name to surface in a cardholder-facing field.

Ownership enforcement applies to the roles described in §2.1. A `Cardholder` may only act against the `Account` named by their `X-User-ID`, a `RetailPartnerAnalyst` may only read the resources tied to their `RetailPartner`, and the opaque operator roles carry no per-resource ownership restriction beyond the role permission itself. The cardholder comparison is enforced on exactly these operations: reading one account, posting a purchase, applying a payment, opening a dispute, and reading an account's loyalty view. A `Cardholder`'s list operations, its reads of a transaction, a promotional plan, a benefit posting, a dispute case, or the principal-balance rows on an account, and its scheduling of a payment due date, carry no ownership comparison and are not filtered to the cardholder's own account.

### 2.5. Logical Clock and Scheduled Effects

The system runs on a logical clock rather than wall-clock time. Before any clock operation is performed the clock reads exactly `2026-09-01T00:00:00Z`, and the server must never fall back to real system time. Two test-driving capabilities administer it. The first sets the logical clock to a supplied ISO-8601 instant via the `to_iso8601` field. The second advances the clock by a whole number of days supplied in `days`; the accepted range is 1 to 3650 inclusive, and a request outside that range is rejected with `ERR_INVALID_ADVANCE_DAYS` (HTTP 422). A successful advance responds with the resulting `current_utc` and the `advanced_days` actually applied.

An advance is not merely a counter increment. It must run every scheduled effect that falls due inside the advanced window, in chronological order: accounts whose scheduled minimum payment was missed past its due date move from `ACTIVE` to `DELINQUENT`, and statement close and payment-due dating fire on the account's `cycle_day`. Concretely, the account is marked delinquent on the first logical day after its scheduled due date — the due-date instant itself does not trigger the mark — and only when its outstanding balance is greater than zero; a statement close fires on each instant within the window that falls on the program's `cycle_day`, and only recomputes that program's rollups. Promotional plans are not expired by the advance itself: an advance never changes a plan's `plan_status` or its `subsidy_at_risk_cents`, and a plan leaves `ACTIVE` for `EXPIRED` only through the explicit expiry path of §3.4 and the charge-off cascade of §3.5.

Both clock operations take their input from a JSON request body. A `days` value that is not a whole number, or that falls outside 1–3650 inclusive, is rejected with `ERR_INVALID_ADVANCE_DAYS` (HTTP 422) — this is also how a required `days` that is missing or non-integer reports, rather than the generic malformed-request error — and a `to_iso8601` that is not a parseable ISO-8601 instant is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

The `cycle_day` field on a program is a required integer from 1 to 31, and a value outside that range is rejected with `ERR_INVALID_REQUEST` (HTTP 400). When it is set to 29, 30, or 31 and the current month is shorter, the statement close clamps to the last real day of that month.

### 2.6. Common Resource Properties

Every top-level resource in this API — `RetailPartner`, `ProgramAgreement`, `CreditProgram`, `Account`, `Application`, `Transaction`, `PromoPlan`, `SettlementBatch`, `DisputeCase`, `BenefitPosting`, `ScheduledBalance`, and `WindDownTransfer` — shares a common set of system-managed properties, because every one of these entities declares `common_fields: true`:

- `id` (string) — a server-minted UUID with no type prefix or namespace segment.
- `created_at` (string) — an ISO 8601 UTC timestamp with three fractional digits, set once at creation.
- `updated_at` (string) — an ISO 8601 UTC timestamp with three fractional digits, refreshed on every mutation of the resource.
- `version` (integer) — a system-managed counter that increments by one on every mutation of the resource, used for optimistic concurrency control.

No entity in this program omits `updated_at` or `version`; all twelve carry the full common set. The `version` counter advances only on an explicit client-visible transition of that resource; when a denormalized rollup field (§3.2) is recomputed as a consequence of an operation on some other resource, the new figure is written in place without refreshing `updated_at` or bumping `version`.

### 2.7. Monetary Precision, Rates, and Rounding

All monetary amounts in this API are integer cents. Fields carrying the `_cents` suffix — `partner_portfolio_exposure_cents`, `minimum_charge_cents`, `outstanding_receivable_cents`, `free_look_exposure_cents`, `program_profitability_cents`, `credit_limit_cents`, `outstanding_balance_cents`, `requested_credit_limit_cents`, `approved_credit_limit_cents`, `amount_cents`, `subsidy_at_application_cents`, `subsidy_at_risk_cents`, `net_subsidy_cents`, `gross_subsidy_cents`, `retailer_liability_cents`, `issuer_subsidy_cents`, `variance_cents`, `chargeback_amount_cents`, `program_exposure_delta_cents`, `principal_balance_cents`, `portfolio_book_value_cents`, `purchase_price_cents`, and `payment_amount_cents` — hold whole cents and are never fractional.

Rate and multiple fields are decimal numbers rather than cents: `revenue_share_rate` and `promo_subsidy_rate` are shares whose sum may not exceed 1.0 (§3.1), `purchase_right_rate` is a price multiple over book value, and the promotional term rates in the internal rate table are four-decimal decimal fractions. The only constraint the system enforces on the two rates is that sum ceiling — neither is independently bounds-checked against 0.0–1.0 — and `purchase_right_rate` is accepted exactly as supplied. These configuration values preserve their input precision and are not cents.

Every computed monetary result is expressed to exactly 2 decimal places using round-half-up. Where a calculation rounds a per-item figure and then sums, the per-item rounding happens first and the sum of the already-rounded figures is the result; the system never sums unrounded values and rounds once at the end.

### 2.8. Optimistic Concurrency Control

Two write operations in this API are guarded by optimistic concurrency control, and both use the same rejection contract. The first is the execution of a negotiated program agreement, which must carry `expected_agreement_version`; if that value does not match the agreement's current `version`, the execution is rejected with `ERR_STALE_VERSION` (HTTP 412). The second is the opening of a renewal round against a credit program, which must carry `expected_program_version`; if that value does not match the program's current `version`, the request is rejected with `ERR_STALE_VERSION` (HTTP 412). In both cases the expected-version field is a non-optional input — the request is not processed without it — and the check exists precisely so that a client which has not observed the entity's latest state cannot overwrite it.

No other write endpoint in this API accepts an expected-version field. A version mismatch on any other endpoint is not a defined rejection path.

### 2.9. Referential Integrity and Left-to-Right Path Validation

Every path-segment identifier and every body-referenced foreign key must resolve to an existing resource before an operation proceeds, and a failure to resolve is reported with `ERR_RESOURCE_NOT_FOUND` (HTTP 404). When a request path contains more than one identifier, the identifiers are validated strictly left to right and the request is abandoned at the first failure, so a request against a child of a nonexistent parent never evaluates the child at all. This same left-to-right discipline applies to body references: a payload that carries a `program_id` and an `agreement_id`, for instance, resolves the program before the agreement.

Cross-entity references declared in payloads are `partner_id` (agreement to retailer, program to retailer), `agreement_id` (program to agreement, settlement batch to agreement), `program_id` (account, application, promo plan, and wind-down transfer to program), `account_id` (transaction and benefit posting to account, promo plan to account, dispute to account), `transaction_id` (promo plan to transaction, dispute to transaction, benefit posting to transaction), and `supersedes_program_id` (a program to its own predecessor program, a self-referential chain).

### 2.10. State Enumeration Reference

State fields throughout the API take values from closed enumerations. `partner_status` on a retail partner is one of `ACTIVE`, `SUSPENDED`, or `OFFBOARDING`. `agreement_status` on a program agreement is one of `DRAFT`, `NEGOTIATION`, `ACTIVE`, `SUSPENDED`, or `TERMINATED`. `program_status` on a credit program is one of `ACTIVE`, `RENEWAL_NEGOTIATION`, `WINDING_DOWN`, or `CLOSED`. `account_status` on an account is one of `ACTIVE`, `DELINQUENT`, `CHARGED_OFF`, `PAID_OFF`, or `TRANSFERRED`. `application_status` on an application is one of `PENDING`, `APPROVED`, or `DECLINED`, and its `source_channel` is one of `IN_STORE`, `DIGITAL`, or `PRESCREENED`. `transaction_status` on a transaction is one of `POSTED` or `DISPUTED`, and its `transaction_channel` is one of `IN_STORE` or `DIGITAL`. `plan_status` on a promotional plan is one of `ACTIVE`, `SETTLED`, or `EXPIRED`. On a settlement batch, `settlement_method` is one of `FORWARD_LOOKING` or `AS_CHARGED`, `reconciliation_method` is one of `PROJECTED` or `AS_CHARGED`, and `batch_status` is one of `OPEN` or `SETTLED`. On a dispute case, `case_status` is one of `OPEN`, `UNDER_REVIEW`, `RESOLVED_FAVOR_CARDHOLDER`, `RESOLVED_FAVOR_MERCHANT`, or `CLOSED`, `dispute_reason` is one of `FRAUD`, `GOODS_NOT_RECEIVED`, `UNAUTHORIZED`, `DUPLICATE_CHARGE`, or `SERVICE_NOT_RENDERED`, and `resolution_outcome` is one of `CARDHOLDER` or `MERCHANT`. On a benefit posting, `posting_reason` is one of `PURCHASE_EARN`, `PROMO_BONUS`, or `DISPUTE_CLAWBACK`, and `posted_status` is one of `POSTED` or `REVERSED`. `balance_bucket` on a scheduled balance is one of `PRINCIPAL` or `PROMO_PRINCIPAL`. On a wind-down transfer, `buyer_role` and `accepted_by_role` are each one of `RETAILER` or `ISSUER`, and `transfer_status` is one of `PROPOSED`, `AGREEMENT_REACHED`, `COMPLETED`, or `WITHDRAWN`.

### 2.11. Validation Ordering

Every request passes through a fixed validation sequence, and the order determines which error a given malformed request reports. Authentication is evaluated first, so a request that both lacks headers and names a missing resource reports `ERR_UNAUTHENTICATED` (HTTP 401) rather than a not-found error. Authorization is evaluated second, so a request from a permitted-but-insufficient role reports `ERR_UNAUTHORIZED` (HTTP 403) before any resource is loaded. Existence resolution is third, reporting `ERR_RESOURCE_NOT_FOUND` (HTTP 404).

Only after those three system-wide gates do business rules run, and they run in the following order. For opening a dispute, the duplicate-dispute check (no other `DisputeCase` on the same transaction may be in `OPEN` or `UNDER_REVIEW`) is evaluated before the filing-window check. For posting a purchase, the promotional term membership check precedes the minimum-charge check, which precedes the credit-limit check. For finalizing a settlement batch, the in-scope dispute hold is evaluated before the batch's own state. State-admission checks — whether the target resource is in the from-state named in §3 — sit between existence resolution and the business rules. Within any single operation these business rules are evaluated in priority order, so the first rule that fails determines the reported `error_id`; a request that violates two business rules reports the higher-priority one. Notably, a parental-state gate such as `ERR_PROGRAM_CLOSED` sits after the operation's own business rules rather than before them, so a purchase that is both on an unsupported promotional term and aimed at a closed program reports the term error; a late gate can therefore only be reached once the earlier ones have passed. The relative order of the expected-version check of §2.8 and an operation's state admission is fixed per operation: on an agreement execution the state admission is evaluated first and the version check follows it, while on an agreement reinstatement or termination the version check is evaluated first; in every case the check precedes the actual state transition. On an agreement execution or reinstatement the revenue-share ceiling is re-checked alongside the version, and on a program's closure the version check follows both the state admission and the account-settled check.

## 3. Business Logic & Workflows

### 3.1. Onboarding a Retail Partner and Drafting Its Economic Agreement

A `ProgramAdmin` begins a partnership by creating a `RetailPartner` with a `retailer_name`, a `loyalty_program_code` naming the retailer's own rewards scheme, and an optional `loyalty_link_enabled` flag that defaults to true. The `loyalty_link_enabled` flag governs whether cardholder reward points earned on this program may post into the retailer's own loyalty balances at all; while it is true, accruals flow across, and while it is false, every attempt to post a loyalty benefit against an account on this retailer's program is rejected with `ERR_LOYALTY_LINK_DISABLED` (HTTP 422). That rejection is raised only for a posting that would actually flow across — a posting explicitly marked as not posting to the retailer's loyalty scheme is accepted even when the link is disabled. A new partner starts in `ACTIVE`. The partner also carries a computed `partner_portfolio_exposure_cents` field, which is the sum of `free_look_exposure_cents` across every program whose `partner_id` points at this retailer; it is never supplied by a client and is recomputed whenever any of the retailer's programs changes its exposure.

The partner's `partner_status` moves along four paths. An explicit administrative suspension or reinstatement by a `ProgramAdmin` toggles between `ACTIVE` and `SUSPENDED`, and an administrative suspension is rejected unless the partner is currently `ACTIVE`, while a reinstatement is rejected unless it is currently `SUSPENDED`; a violation of either is reported as `ERR_INVALID_STATE` (HTTP 409). Separately, once every program governed by the partner's agreements has reached `WINDING_DOWN` or `CLOSED` — that is, once no program with this `partner_id` remains in either `ACTIVE` or `RENEWAL_NEGOTIATION` — the system suspends the partner on its own, without any client request. This bubble-up is evaluated when a credit program closes, so merely rolling a program into `WINDING_DOWN` does not by itself suspend the partner; it applies only while the partner is still `ACTIVE`, and leaves an already-`SUSPENDED` partner untouched. That bubble-up suspension is distinct from the administrative one and is reachable only after the portfolio has fully wound down. Finally, a `ProgramAdmin` may move a partner from `ACTIVE` to the terminal `OFFBOARDING` state, but only when every program with this `partner_id` is already `CLOSED`; the partner must itself still be `ACTIVE` for the offboarding to be admitted, and a partner already `SUSPENDED` is refused with `ERR_INVALID_STATE` rather than offboarded. The partner carries no cascade of its own into program status, because program cascading is driven by the agreement, not by the partner.

The economic terms of the partnership live in a `ProgramAgreement`, drafted against the partner via `partner_id`. The agreement captures `revenue_share_rate` — the share of credit-card net revenue the retailer retains — and `promo_subsidy_rate` — the share of deferred-interest promotional interest subsidy the retailer funds. Their sum may never exceed 1.0, and a draft or an execution that would breach that ceiling is rejected with `ERR_REVENUE_SHARE_INVALID` (HTTP 422). Beyond the two rates, the agreement sets a default `promo_term_months`, a `minimum_charge_cents` purchase floor that defaults to 29900, a `settlement_terms_days` invoice window that defaults to 30, a `dispute_grace_days` allowance that defaults to 0, a `renewal_notice_days` advance-notice requirement that defaults to 90, and a `purchase_right_rate` price multiple that defaults to 1.04.

A drafted agreement sits in `DRAFT` until a `ProgramAdmin` opens negotiation on it, which requires that the agreement currently be `DRAFT` and that `revenue_share_rate` plus `promo_subsidy_rate` be at most 1.0; the agreement then becomes `NEGOTIATION`. Opening negotiation takes no body at all and is not version-guarded. Executing a negotiated agreement into force requires the agreement to be in `NEGOTIATION`, re-checks the revenue-share ceiling before it proceeds, and requires the caller to supply the agreement's expected version; on success the agreement becomes `ACTIVE` and its `version` increments by one. The agreement's expected-version check is evaluated after the agreement-state admission check and after the revenue-share guard; a `supersedes_program_id` on a credit program records a predecessor link only — it never re-points or attaches a program to the executed agreement, and no agreement transition changes any program's `agreement_id`. A second route back to `ACTIVE` exists for a suspended agreement: reinstatement by a `ProgramAdmin`, again re-checking the revenue-share ceiling and requiring the expected agreement version, with the same version increment.

An agreement does not remain `ACTIVE` indefinitely on its own. The aggregate `free_look_exposure_cents` is summed across every program whose `agreement_id` points at the agreement, regardless of program status, and is re-evaluated whenever any of those programs has its exposure rollup recomputed. When that aggregate reaches 5,000,000,000 cents or more, the system suspends the agreement, transitioning it `ACTIVE` to `SUSPENDED` and incrementing its version by one; this is an automatic safeguard driven by the exposure rollup, not a client action. The safeguard is asymmetric on the way back: once the same aggregate has fallen strictly below 4,000,000,000 cents, the system restores the agreement from `SUSPENDED` to `ACTIVE`, again incrementing the version. Two further transitions are defined around `ACTIVE`. A `ProgramAdmin` may terminate a `NEGOTIATION`-state agreement, which requires the expected agreement version and moves it to the terminal `TERMINATED` state with a version increment. The bubble-up that would return an agreement to `NEGOTIATION` by itself — when no credit program under it remains in `ACTIVE` or `RENEWAL_NEGOTIATION`, or when the agreement is within `renewal_notice_days` of expiry — is not an automatic transition this API performs: no agreement ever re-enters `NEGOTIATION` on its own, any credit program that is not `CLOSED` keeps the agreement in place regardless of `renewal_notice_days`, and `renewal_notice_days` is recorded on the agreement and never read. From `NEGOTIATION` an agreement may only be executed into `ACTIVE` or terminated.

### 3.2. Issuing a Credit Program Under an Agreement

A credit program is the operational issuance vehicle for a partnership. A `ProgramAdmin` creates a `CreditProgram` with a `partner_id`, an `agreement_id`, and a `cycle_day`, and may optionally name a `supersedes_program_id` to record the predecessor program this one replaces in a renewal chain. A first-generation program carries no predecessor at all and leaves the field null. When a predecessor is named it must resolve to a program that exists and whose `program_status` is not `CLOSED`; a named predecessor that is missing or already closed is rejected with `ERR_SUPERSEDES_INVALID` (HTTP 422). New programs start in `ACTIVE`.

Three computed figures hang off the program and are maintained by the system rather than by clients. `outstanding_receivable_cents` is the sum of `outstanding_balance_cents` across every account on the program whose `account_status` is not `CHARGED_OFF`. `free_look_exposure_cents` is the sum of `subsidy_at_risk_cents` across every promotional plan on the program whose `plan_status` is `ACTIVE`. `program_profitability_cents` is the net program profit produced by the profitability calculation of §3.6 and is recomputed on every settlement, payment, and write-off. All three are denormalized rollups: they move as a consequence of operations on other resources, never through a direct client write.

A program's lifecycle has a distinctive shape because a renewal round is a negotiation that may succeed or fail. Opening a renewal round against an `ACTIVE` program moves it to `RENEWAL_NEGOTIATION`, requires the caller to supply the expected program version, and increments the version. From `RENEWAL_NEGOTIATION` there are two exits. If the round succeeds, a `ProgramAdmin` completes the renewal, which requires the program to still be in `RENEWAL_NEGOTIATION` and an expected version match; the renewal round closes, the original program returns to `ACTIVE` with its version incremented, and a successor program whose `supersedes_program_id` names this one — a program created separately through the normal issuance path, since closing the round itself mints nothing — becomes the governing program. If the round fails, the same renewal-opening capability is invoked again against the `RENEWAL_NEGOTIATION` program, this time supplying a `to_status` of `WINDING_DOWN`; this is the second arm of the same operation, distinguished by the requested target status. The cycle is therefore `ACTIVE` → `RENEWAL_NEGOTIATION` → either `ACTIVE` (renewed) or `WINDING_DOWN` (failed). Rolling into `WINDING_DOWN` triggers a cascade at its first hop: every account whose `program_id` names this program, whose `outstanding_balance_cents` is zero, and whose `account_status` is either `ACTIVE` or `DELINQUENT` is moved to `PAID_OFF`. Accounts still carrying principal are deliberately left untouched, because they must be either paid off or transferred before the program can close. The program's status, `updated_at` and version all move together when it rolls. The operation's two arms share one implementation: a target of `WINDING_DOWN` is accepted against either an `ACTIVE` program or one already in `RENEWAL_NEGOTIATION` and in both cases rolls it straight into wind-down, while any other target against a program that is not `ACTIVE` is refused.

Closure is the terminal step and it is deliberately hard to reach. Moving from `WINDING_DOWN` to the terminal `CLOSED` state requires that the program currently be `WINDING_DOWN`, that every wind-down transfer with this `program_id` has reached `COMPLETED` — a program carrying no wind-down transfer at all satisfies this vacuously — that every account on the program have reached `TRANSFERRED` or `PAID_OFF`, and an expected-version match. The `WINDING_DOWN` admission is evaluated first; a wind-down transfer that is not yet `COMPLETED` is then reported as `ERR_INVALID_STATE` (HTTP 409); a program closure attempted while any account is still neither transferred nor paid off is rejected with `ERR_ACCOUNT_NOT_SETTLED` (HTTP 422); and the expected-version check follows those. On success the program's `free_look_exposure_cents` is forced to zero, the version increments, and the program becomes `CLOSED`.

### 3.3. Cardholder Acquisition: Applications, Prescreened Offers, and Instant Decisioning

Applications arrive through one of three `source_channel` values: `IN_STORE`, `DIGITAL`, or `PRESCREENED`. A submission names the target `program_id` and a `requested_credit_limit_cents`, and an application captured through the prescreened channel must additionally carry a `prescreen_reference`; a `PRESCREENED` application that omits the reference is rejected with `ERR_PRESCREEN_REQUIRED` (HTTP 422) — the reference is not itself resolved against any offer registry, so no failure path exists for one that does not resolve. The reference, when supplied at all, is persisted whether or not the channel is `PRESCREENED`. The prescreen requirement is evaluated before the per-applicant ceiling. Independently of channel, the requested line may not exceed the program's per-applicant ceiling of 5,000,000 cents; a request above that ceiling is rejected with `ERR_CREDIT_LIMIT_OUT_OF_BAND` (HTTP 422). A newly created application has no linked `Account` yet, so its `cardholder_ref` is not in response until it is approved. A new application starts in `PENDING` with no decision yet stamped; once decisioned, the machine-readable reason is recorded on the application as its `decision_code` — `APPROVED_WITHIN_BAND` on approval and `DECLINED_LIMIT_OUT_OF_BAND` on decline. When the target program has already reached `CLOSED`, the submission is refused with `ERR_PROGRAM_CLOSED` (HTTP 422), after the channel and ceiling checks.

Instant decisioning is performed by an `Underwriter` and is the point at which the application splits into one of two terminal outcomes. Approval requires the application to still be `PENDING` and the `requested_credit_limit_cents` to be at most 1,500,000 cents — the boundary is inclusive, so a request of exactly 1,500,000 cents is approved. On approval the application becomes `APPROVED`, its `approved_credit_limit_cents` is set equal to the requested limit, and a brand-new `Account` is synthesized with `account_status` `ACTIVE`, the same `program_id` as the application, `credit_limit_cents` equal to the approved limit, and `outstanding_balance_cents` of zero. That synthesized account is discoverable only by listing accounts filtered to the application's program — it is not returned by the decision response and has no independent creation path. A request above the 1,500,000-cent threshold takes the other branch: the application becomes `DECLINED` and its `approved_credit_limit_cents` is set to null, with no account synthesized. The decision instant, `instant_decision_at`, is stamped before either branch is taken, so it is recorded on both the approved and the declined outcome.

Accounts created through this path carry an opaque masked `cardholder_ref` printed on correspondence, and their `linked_loyalty_balance` begins at zero and grows only through benefit accruals.

### 3.4. Purchases, Promotional Qualification, and the Exposure Mesh

One last behavioral rule governs program closure: an account may be serviced only while its program's `program_status` is not `CLOSED`. Posting a purchase, submitting an application, and applying an account payment are all refused with `ERR_PROGRAM_CLOSED` (HTTP 422) once the account's or application's program has reached the terminal closed state. This gate is evaluated last within each of those operations, after the operation's own body validation, its business rules, and its credit-limit or ceiling checks, so an operation that would also breach an earlier rule reports that earlier error instead.

Posting a purchase names an `account_id`, a `merchant_name`, an `amount_cents`, and a `transaction_channel` of `IN_STORE` or `DIGITAL`. Every request is also expected to carry the standard input fields of its endpoint, and a request whose body omits a required input or sends a value that does not match its declared type is refused with `ERR_INVALID_REQUEST` (HTTP 400). A value that is of the right type but falls outside its field's enumerated set is likewise refused with `ERR_INVALID_REQUEST` (HTTP 400). A new transaction starts in `POSTED`. Two business rules police the posting of a promotional purchase, in a fixed order. First, if the cardholder elected promotional financing, the requested term must be a member of the supported term set — the only permissible values are 6, 12, 18, and 24 months — and a term outside that set, including an omitted or null term, is rejected with `ERR_INVALID_PROMO_TERM` (HTTP 422). Second, the purchase amount must meet the governing agreement's `minimum_charge_cents`; a deferred-interest purchase below that floor is rejected with `ERR_PROMO_MINIMUM_CHARGE` (HTTP 422). The term check is evaluated before the minimum-charge check, so a purchase that is both below the floor and on an unsupported term reports the term error. These two rules apply only to a promotional election; the credit check below is applied to every purchase regardless of promotional election. The new `amount_cents` added to the account's current `outstanding_balance_cents` may not exceed the account's `credit_limit_cents`, and a purchase that would breach the line is rejected with `ERR_CREDIT_LIMIT_EXCEEDED` (HTTP 422); a purchase landing exactly on the limit is accepted.

The `promo_requested` flag on the purchase is what elects deferred-interest financing; it defaults to false, and it is only when it is true that the purchase synthesizes a `PromoPlan`. A new plan starts in `ACTIVE`. The plan records the `program_id`, the `account_id`, and the `transaction_id` it is tied to, along with the agreed `promo_term_months`, the `promo_principal_cents` placed under the promotional balance, and a `qualifying_flag` capturing whether the purchase met the agreement minimum at qualification time. The term requested on the purchase is carried onto the plan as its `promo_term_months`, and the term must be a member of the same four-value rate table. The purchase itself persists both `promo_requested` and the requested `promo_term_months`; for a non-promotional purchase the persisted `promo_term_months` is null.

The plan's timing is derived, not supplied. `promo_start_at` is the logical-clock instant the plan qualified, and `promo_expires_at` is that instant advanced by the term length multiplied by 30 days. Two monetary figures are attached at creation and behave very differently afterwards. `subsidy_at_application_cents` is the projected subsidy struck once from the transaction-specific term rate; it is the quote the cardholder is shown and is never revised — not by a later rate change, not by a dispute, not by anything. `subsidy_at_risk_cents` is the live, partner-funded figure the retailer carries, and it moves. It is zero when `promo_start_at` has reached or passed `promo_expires_at`, zero when `promo_principal_cents` is below the agreement's `minimum_charge_cents`, and zero when `qualifying_flag` is false; otherwise it is the plan's principal multiplied by its term rate, multiplied by its term in months, divided by twelve, multiplied by the agreement's `promo_subsidy_rate`, rounded half-up to two decimal places. The rate table maps 6 months to 0.1299, 12 months to 0.1599, 18 months to 0.1899, and 24 months to 0.2199. A third figure, `net_subsidy_cents`, is the as-charged subsidy asset and is written only at settlement; it stays null for as long as `plan_status` is anything other than `SETTLED`.

Because `free_look_exposure_cents` is the sum of `subsidy_at_risk_cents` over `ACTIVE` plans, every event that changes a plan's risk figure ripples up to the program. Four such events are wired through the plan itself. A cardholder-service operator can expire a plan explicitly, but only once the clock is at or after `promo_expires_at`; an attempt to expire a plan early is rejected with `ERR_PROMO_NOT_EXPIRED` (HTTP 422), and only a plan still `ACTIVE` can be expired at all — any other status is rejected with `ERR_INVALID_STATE` (HTTP 409). The explicit expiry sets the risk figure to zero and recomputes exposure. An in-term payoff that is later reversed reopens an `EXPIRED` plan back to `ACTIVE` and recomputes its `subsidy_at_risk_cents` from its principal and the agreement subsidy rate, then recomputes the program exposure. And when a plan settles, it leaves the `ACTIVE` exposure set and the program's exposure is recomputed.

Two further events reach the plan's risk figure from outside it. Charging off an account transitions every promotional plan on that account, including its risk figure. And a dispute against a purchase transitions any plan on that purchase to a zero risk figure; the exposure recompute that follows is driven by the risk figure change, not by the case object. Both are described with their own workflows below. The account's own `outstanding_balance_cents` is a rollup of its principal balance slices rather than a directly writable field.

### 3.5. Statement Balances, Minimum Payments, Delinquency, and Charge-Off

Account principal is recorded as statement slices rather than as a single mutable number. A `ProgramAdmin` records a `ScheduledBalance` against an `account_id` with a `principal_balance_cents` amount and a `balance_bucket` of either `PRINCIPAL` or `PROMO_PRINCIPAL`, and the system stamps `recorded_at` with the logical-clock instant. Recording a slice recomputes the account's `outstanding_balance_cents` as the sum of its `principal_balance_cents` rows — taken over every slice on the account and regardless of the account's status — and also recomputes the owning program's rollups. The account's `outstanding_balance_cents` is therefore always the sum of its principal balance slices while the account is not charged off, and it is never accepted as a client-supplied value.

The minimum payment due on an account is computed, not stored, and it has a zero-balance boundary that is easy to get wrong. If the account's `outstanding_balance_cents` is exactly zero, the minimum due is exactly zero — never the floor. If the account is `DELINQUENT`, the minimum due is the entire `outstanding_balance_cents`. Otherwise the minimum is the greater of the absolute floor of 3,500 cents and two percent of `outstanding_balance_cents` rounded half-up to two decimal places. The two-percent figure is taken on the balance before any same-day payment is applied, and the floor applies only when the computed percentage figure is strictly less than it. A `CHARGED_OFF` account is a special case of the same computation: it carries no serviced minimum at all and returns zero even when a residual balance remains.

An account becomes delinquent on its own when its scheduled minimum payment stays unpaid past its statement due date; only an `ACTIVE` account is eligible, the transition requires that `outstanding_balance_cents` be greater than zero, and it is driven by the clock rather than by a client. A scheduled payment due date is set explicitly against an `account_id` with a `due_date`, but only a due date at or after the current logical clock is accepted; a due date in the past is rejected with `ERR_PAYMENT_DUE_IN_PAST` (HTTP 422). Each account holds at most one scheduled due date, so scheduling again replaces the previous one.

Payments are applied by a `Cardholder` or a `ProgramAdmin` and carry a `payment_amount_cents`. The payment reduces the account's `principal_balance_cents` rows by the payment amount, taken oldest slice first until the amount is exhausted, floored at zero so that no slice goes negative, and then recomputes both the account's `outstanding_balance_cents` and the program's `program_profitability_cents`. The payment amount is applied to the slices as given; a payment larger than the outstanding balance floors the slices at zero rather than erroring, and it is the transition rules below rather than the amount itself that zero a paid-off balance. The servicing date used as the account's last-payment point is refreshed on every accepted payment. A payment produces one of three outcomes depending on the account's state and size, measured against the balance as it stood before the payment. A `DELINQUENT` account whose payment at least covers the entire outstanding balance moves to `PAID_OFF` with its slices zeroed; otherwise, a `DELINQUENT` account whose payment at least covers the overdue minimum due returns to `ACTIVE`. An `ACTIVE` account whose payment covers the whole outstanding balance moves to `PAID_OFF` and its `outstanding_balance_cents` is set to zero. A `PAID_OFF` account receiving a payment that covers its remaining balance stays `PAID_OFF`, with its slices zeroed.

Charge-off is the terminal write-off path and it cascades in three hops. A `ProgramAdmin` may charge off an account only when it is `DELINQUENT` and its payment due date is 180 or more logical days in the past; the state admission is evaluated first, so an account that is not `DELINQUENT` is rejected with `ERR_INVALID_STATE` (HTTP 409), and a charge-off attempted before the window is met — including on an account that has never had a payment date scheduled, whose elapsed days are taken as zero — is rejected with `ERR_CHARGEOFF_WINDOW_NOT_MET` (HTTP 422). The first hop sets the account's `account_status` to `CHARGED_OFF`, which is the origin of the chain. The second hop is caused by the first: every promotional plan whose `account_id` names this account has its `plan_status` set to `EXPIRED` and its `subsidy_at_risk_cents` set to zero. The third hop is caused by the second: because those plans have left the `ACTIVE` exposure set, the owning program's `free_look_exposure_cents` is recomputed, and because the account is now `CHARGED_OFF` its `ScheduledBalance` rows stop summing into the program's `outstanding_receivable_cents`, so the program's `program_profitability_cents` is recomputed as well.

### 3.6. Program Economics: Delinquency Risk Scoring and Profitability

Every account carries a computed delinquency risk score, recomputed whenever its status or balance changes and surfaced through the program economics rollup. The score is the minimum of 1,000 and the sum of four contributions. A `DELINQUENT` account contributes 400 points; any other status contributes nothing. An account whose `outstanding_balance_cents` exceeds its `credit_limit_cents` contributes 300 points; the comparison is strictly greater, so an account sitting exactly at its limit contributes nothing extra, and the score at that exact boundary is a full 300 points lower than one cent above it. Utilization contributes the smaller of 200 points and the number of whole 500,000-cent units in the outstanding balance multiplied by 25, where the unit count is rounded down to a whole number before multiplication. Finally, days since the account's last payment contributes the smaller of 100 points and twice the number of days elapsed. The days-elapsed count is measured from the account's scheduled payment due date to the current logical clock, and is zero when no payment date has been scheduled; it is therefore the same anchor that drives the delinquency and charge-off windows, not a separately recorded last-payment instant. The ceiling of 1,000 applies to each individual account's score.

The per-account scores are also rolled up to the program level for program economics reporting. The program rollup averages the per-account scores over accounts whose `account_status` is not `CHARGED_OFF` and rounds the average half-up; charged-off accounts are excluded from the denominator entirely, not merely treated as zero, and when the program has no eligible account the rollup reads zero. This rollup is exposed as the integer `program_risk_score` on the program economics summary read, which also carries the program's `program_status`, its three denormalized rollups in their `_cents` form, the count of accounts on the program, and the count of settlement batches on the program's agreement that have reached `SETTLED`. That summary is a derived read rather than the resource itself, and reading the credit-program resource returns the same rollup figures directly.

Program profitability is the top of the economic pyramid and is recomputed whenever a settlement finalizes, an account is charged off or paid off, or a program is wound down. It is the sum, over every settlement batch that is `SETTLED` and whose `agreement_id` equals the program's own `agreement_id`, of the batch's net contribution, with the total acquisition cost of the program's accounts subtracted at the end. A batch's net contribution is the difference between its `gross_subsidy_cents` and its `retailer_liability_cents`, multiplied by a revenue-share multiplier, where the multiplier is one plus the product of `revenue_share_rate` and the smaller of two figures: a program-wide average balance and the cap multiple of 2.5. That average balance is the sum of the outstanding balances of every account on the program divided by one million, taken unrounded, and the cap multiple of 2.5 bounds it from above. The batch contribution is rounded half-up to a whole cent before it is summed. The final subtraction is the account count of the program — every account on the program, whatever its status — multiplied by a per-account acquisition cost of 4,200 cents, and the whole result is rounded half-up to a whole cent.

The profitability figure has a deliberate evaluation-order dependency. The average balance it keys on is read from the program's accounts as they stand at the moment the figure is recomputed — the pinned order is to settle the batch, then let the settlement's effects on balances land, then score — and because the revenue-share multiplier is keyed on a balance figure that itself moves as batches settle, the order is fixed rather than incidental. The figure is maintained by recomputing every settled batch from scratch, which is the authoritative full recomputation; the reason each batch contribution is rounded before the outer sum is precisely so that repeated recomputations do not accumulate rounding drift.

### 3.7. Promotional Settlement and the Partner Chargeback Reconciliation

Settlement is a two-stage process with a genuinely different number struck at each stage, and the difference between the two is the product's central economic fact. A `ProgramAdmin` opens a `SettlementBatch` against an `agreement_id` with a `period_start` instant that is inclusive and a `period_end` instant that is exclusive. At creation the batch is `OPEN` and the system computes and exposes `transaction_count`, the forward-looking `gross_subsidy_cents`, the as-charged `net_subsidy_cents`, and the `variance_cents`, while carrying `retailer_liability_cents` and `issuer_subsidy_cents` at zero until the batch is finalized. Later, a `ProgramAdmin` finalizes the batch, which strikes the as-charged figures, records the retailer and issuer shares, and posts the partner-funded chargeback invoice — the invoice's amount is the batch's `retailer_liability_cents`, its terms are the agreement's `settlement_terms_days`, and the invoice itself is not exposed as a resource. The batch becomes `SETTLED`, every in-scope promotional plan on a `POSTED` purchase moves to `SETTLED` with its `net_subsidy_cents` stamped, and the program's `program_profitability_cents` is recomputed.

The batch carries two method selectors, each optional and each validated against its closed enumeration at creation, with a value outside the enumeration refused as `ERR_INVALID_REQUEST` (HTTP 400). `settlement_method` is `FORWARD_LOOKING` or `AS_CHARGED` and defaults to `AS_CHARGED`; it is recorded on the batch but governs no computed figure. `reconciliation_method` is `PROJECTED` or `AS_CHARGED` and defaults to `PROJECTED`; it is the selector that actually decides how `retailer_liability_cents` and `issuer_subsidy_cents` are split, and the projected view is the one most partner agreements write.

The input set for both variants is the same. It is every promotional plan, belonging to a program on the agreement, whose `promo_start_at` falls within the half-open window running from `period_start` inclusive to `period_end` exclusive, and whose `transaction_id` resolves to a purchase that is `POSTED`. The window is applied to the plan's own `promo_start_at` instant, so a purchase posted inside the window whose promotion started outside it is not in scope. Plans whose purchase is `DISPUTED` at settle time are excluded from both variants entirely. The batch's own `transaction_count` is the size of this full input set, counting every in-scope plan regardless of its plan status, and it is refreshed at finalize. The input set is not frozen at creation: it is re-resolved against the batch's stored `period_start` and `period_end` each time the batch is finalized, and both passes are struck from scratch at that point. The forward-looking variant additionally requires the plan to be `ACTIVE` at evaluation time; the as-charged variant does not, because it deliberately replays plans that may since have reached `EXPIRED`.

Both variants evaluate plans in a fixed order — ascending by `promo_start_at`, then by `transaction_id` as a tiebreaker — and both round each plan's figure to two decimal places half-up before summing, never after. The forward-looking pass, struck when the batch is opened, projects each plan's full-term interest as the principal multiplied by the plan's term rate, multiplied by its term in months, divided by twelve, rounded half-up; `gross_subsidy_cents` is the sum of those per-plan figures. This projection assumes the balance runs the full term and therefore over-states the exposure whenever a balance is paid in full inside the promotional window. The as-charged pass, struck only at finalize, replays each plan's actual accrued interest: the number of days accrued is the smaller of the days elapsed from `promo_start_at` to `period_end` and the plan's term in months multiplied by 30; the accrued interest is the principal multiplied by the plan's term rate, multiplied by that day count, divided by 365, rounded half-up; and `net_subsidy_cents` is the sum of those per-plan figures. This is the legally payable subsidy, and a balance paid in full early drives it toward zero while `gross_subsidy_cents` is untouched. `variance_cents` is `gross_subsidy_cents` minus `net_subsidy_cents`, signed, and it is the figure the program variance series is read from.

The chargeback reconciliation then splits the subsidy between the two parties under the reconciliation method. Under the projected view, the retailer's liability is the sum over selected plans of the plan's principal multiplied by its term rate, multiplied by its term in months, divided by twelve, multiplied by the agreement's `promo_subsidy_rate`; the issuer's subsidy is the same expression with the complement of the subsidy rate — one minus `promo_subsidy_rate` — in place of the rate itself; and each of the two totals is rounded half-up to two decimal places. Under the as-charged view, the retailer's liability is the sum over selected plans of each plan's accrued interest multiplied by `promo_subsidy_rate`, rounded half-up per plan, and the issuer's subsidy is the sum over selected plans of each plan's accrued interest multiplied by one minus `promo_subsidy_rate`, likewise rounded per plan. In the as-charged view the accrued interest is the per-plan figure from the as-charged subsidy pass, not the batch-cumulative `net_subsidy_cents` total. The projected view bills the retailer its share of the full projected subsidy and gives no credit for early payoffs inside the window, so the two variants differ by the rounded difference between gross and net subsidy multiplied by `promo_subsidy_rate`.

One invariant holds across both views and violating it is a defect: `retailer_liability_cents` plus `issuer_subsidy_cents` must equal that variant's total promotional subsidy to the cent.

Finalizing is admitted only from the `OPEN` state — any other batch status is rejected with `ERR_INVALID_STATE` (HTTP 409) — and that state admission is evaluated before the dispute hold. Once the batch is `OPEN`, finalizing is blocked whenever any purchase in the batch's input set carries a dispute that is still `OPEN` or `UNDER_REVIEW`; the attempt is then rejected with `ERR_SETTLEMENT_DISPUTE_HOLD` (HTTP 422). Because a plan only moves to `SETTLED` as part of a finalized batch, the plan-level rule is subsumed by the batch-level hold rather than evaluated as a separate gate. On a successful finalize the agreement's `version` is incremented once for the settlement day, and the batch's `retailer_liability_cents` is posted as a partner-funded chargeback invoice payable by the retailer within the agreement's `settlement_terms_days`.

### 3.8. Disputes, Chargeback Discharge, and Loyalty Benefit Clawback

A dispute is opened by a `CardholderService` operator or by the cardholder acting on their own account, naming a `transaction_id`, an `account_id`, and a `dispute_reason` from `FRAUD`, `GOODS_NOT_RECEIVED`, `UNAUTHORIZED`, `DUPLICATE_CHARGE`, or `SERVICE_NOT_RENDERED`. The dispute may be raised against an account whose `account_status` is `CHARGED_OFF`. Two checks gate the opening, in order. No other `DisputeCase` on the same transaction may already be in `OPEN` or `UNDER_REVIEW`; a duplicate attempt is rejected with `ERR_DISPUTE_ALREADY_OPEN` (HTTP 409). Then the filing window applies: the disputed purchase must have posted no more than 60 logical days plus the agreement's `dispute_grace_days` before the current clock, and an out-of-window filing is rejected with `ERR_DISPUTE_PERIOD_EXPIRED` (HTTP 422). A new case starts in `OPEN` and is branded with the named account's owning retailer's `retailer_name` in `servicing_brand_name`. The account and the transaction are each resolved independently, and no check requires the disputed purchase to belong to the named account. At creation the case carries a null `chargeback_amount_cents` and is stamped with the signed change its own opening contributed to the program's exposure.

Opening the case is itself the trigger that moves the disputed purchase from `POSTED` to `DISPUTED`, and that move is the origin of a three-hop chain. The first hop is the transaction status change; the case object itself does not touch downstream rows. The second hop is caused by the first: because the purchase is now `DISPUTED`, every promotional plan with this `transaction_id` has its `subsidy_at_risk_cents` set to zero. The third hop is caused by the second: because a plan's risk figure changed, the owning program's `free_look_exposure_cents` is recomputed.

Resolution runs through review. A `CardholderService` operator moves an `OPEN` case to `UNDER_REVIEW`, and the instant the case leaves `UNDER_REVIEW` is stamped on it as `resolved_at`. From `UNDER_REVIEW` the operator resolves the case with a `resolution_outcome` of `CARDHOLDER` or `MERCHANT`, and the case lands in the matching terminal state; the outcome value is validated as a member of that pair before the case's state admission, so an unrecognized outcome reports `ERR_INVALID_REQUEST` (HTTP 400) rather than the state error. Resolution for the cardholder additionally requires that the disputed transaction posted no more than 60 logical days plus the agreement's `dispute_grace_days` before the current clock. On that branch the case records `chargeback_amount_cents` equal to the disputed purchase's `amount_cents`, and the case becomes `RESOLVED_FAVOR_CARDHOLDER`. Two consequences follow in sequence. First, a clawback benefit posting is raised against the purchase's original earn posting; second, applying that clawback decrements the account's `linked_loyalty_balance` by the original points amount and marks the original posting `REVERSED`. The disputed purchase's `transaction_status` is set back to `POSTED` — permanently chargeback-discharged — and its promotional plan keeps a `subsidy_at_risk_cents` of zero rather than being recomputed.

Resolution for the merchant takes a different path with a different downstream effect. There is no chargeback amount and no loyalty clawback. The disputed promotional plan's `subsidy_at_risk_cents` is recomputed from its principal and the agreement's `promo_subsidy_rate`, which is the first hop; the purchase's `transaction_status` returns to `POSTED`; and the owning program's `free_look_exposure_cents` is recomputed as the second hop. So the two resolution branches differ precisely in whether the exposure is restored or permanently discharged. A third exit exists for a case that never reaches review: an `OPEN` case may be withdrawn, which closes it in the terminal `CLOSED` state and returns the disputed purchase to `POSTED`. A case's `program_exposure_delta_cents` is overwritten on resolution with the signed change that resolution contributed to the program's exposure — zero on the cardholder-favored branch, and the restored amount on the merchant-favored branch — while a case that is never resolved keeps the opening change recorded at creation.

Loyalty benefits are posted independently of disputes through a `BenefitPosting` against an `account_id` and a `transaction_id`, with a `posting_reason` of `PURCHASE_EARN`, `PROMO_BONUS`, or `DISPUTE_CLAWBACK` and a signed `points_amount`; a clawback posting carries a negative value. A posting carries a `posts_to_retailer_loyalty` flag that defaults to true, and a computed `loyalty_program_code` field that copies the retailer's own `loyalty_program_code` at posting time and is null when `posts_to_retailer_loyalty` is false. A new posting is `POSTED` and stamps `posted_at` with the logical-clock instant. An accepted posting increments the account's `linked_loyalty_balance` by `points_amount` — which is exactly how a negative clawback decrements it. The cardholder-facing loyalty view for an account reports the account's current `linked_loyalty_balance`, the count of benefit postings recorded against the account, and the most recent posting instant, or null when none exist.

A clawback arises from the cardholder-favored dispute branch just described. It requires that a benefit posting with reason `PURCHASE_EARN` and a `posted_status` still `POSTED` exists on the disputed transaction; an earn that has already been reversed raises no clawback. When more than one such earn exists, the one with the earliest `created_at` is the one clawed back. When it fires, it creates a new `BenefitPosting` with reason `DISPUTE_CLAWBACK` whose `points_amount` is negative one times the original posting's points, decrements the account's `linked_loyalty_balance` by the original points amount, and marks the original posting's `posted_status` as `REVERSED`. The clawback posting is itself stamped `POSTED` and copies the original earn's `posts_to_retailer_loyalty` and `loyalty_program_code`, so a clawback of an earn that did not route to the retailer's scheme does not route either. A posting so reversed is terminal.

### 3.9. Wind-Down, the Portfolio Purchase Right, and Partnership Termination

When a partnership ends, the portfolio does not simply evaporate — it is negotiated, priced, and transferred. The process begins when a `ProgramAdmin` proposes a `WindDownTransfer` against a `program_id`, naming the `buyer_role` as `RETAILER` or `ISSUER` and optionally supplying a `proposed_price_cents`. At proposal time the system copies two figures: `portfolio_book_value_cents`, which is the program's `outstanding_receivable_cents` at the instant of the proposal, and `purchase_right_rate`, which is the governing agreement's rate. The accepted `purchase_price_cents` is the supplied `proposed_price_cents` when one was given, and otherwise the floor price derived below, which is the book value multiplied by the rate, rounded half-up to the nearest cent. A transfer starts in `PROPOSED` with `accepted_by_role` null and no execution timestamp. A proposal is admitted from any program status and takes no version guard.

A proposed price is not free to be arbitrary. The floor is the program's book value multiplied by the agreement's `purchase_right_rate`, rounded half-up to the nearest cent, and any proposed price must be at least that floor; a lower proposal is rejected with `ERR_PURCHASE_PRICE_BELOW_FLOOR` (HTTP 422). The delegated purchase right held by a `CoBrandIssuer` is exercised through the acceptance step rather than through proposal, and a `CoBrandIssuer` may accept only as the `ISSUER` buyer.

Acceptance carries the accepting role in `accepted_by_role`, which must be one of the two buyer roles. Within acceptance the membership of that value is validated first, a `CoBrandIssuer` is refused with `ERR_UNAUTHORIZED` (HTTP 403) unless the value is `ISSUER`, and the `PROPOSED` admission is applied last, so an unrecognized role reports `ERR_INVALID_REQUEST` (HTTP 400) and a non-`ISSUER` co-brand acceptance reports `ERR_UNAUTHORIZED` even against a transfer that is not currently `PROPOSED`. Acceptance then moves the transfer to `AGREEMENT_REACHED`, recording the accepting party's role. Execution then follows from `AGREEMENT_REACHED` — that admission is evaluated against the transfer first, before the program is resolved — and requires that every account whose `program_id` names this program is already in `PAID_OFF` or `TRANSFERRED`; a program still carrying live accounts cannot complete its transfer, and the refusal is `ERR_INVALID_STATE` (HTTP 409). On execution the first hop cascades every account on the program to `TRANSFERRED`, the program's `program_status` is set to `WINDING_DOWN`, and the program's version increments; the transfer becomes `COMPLETED` and stamps `transfer_executed_at`. Note the direction of that dependency: the transfer is the precondition for wind-down, and the program is then closed once the transfer has completed.

The negotiation is reversible up to a point. An accepted transfer may be withdrawn, which returns it from `AGREEMENT_REACHED` to `PROPOSED` — clearing `accepted_by_role` back to null — and reopens the negotiation against the same program. A transfer that is still merely `PROPOSED` may also be withdrawn, which takes it to the terminal `WITHDRAWN` state instead. A `COMPLETED` transfer cannot be withdrawn; the attempt is rejected with `ERR_INVALID_STATE` (HTTP 409). `COMPLETED` and `WITHDRAWN` are the two terminal outcomes.

Partner offboarding closes the loop, but only at the very end. A partner may be moved to the terminal `OFFBOARDING` state only once every program with this `partner_id` is `CLOSED`. And a program may reach `CLOSED` only from `WINDING_DOWN`, with every wind-down transfer on it `COMPLETED`, and with an expected-version match on the program itself. The sequence from partnership termination to final closure is therefore: negotiate and accept transfer terms, execute the transfer so the accounts cascade to `TRANSFERRED`, let the program sit in `WINDING_DOWN`, close the program, and only then offboard the partner.

## 4. Endpoint Definitions

Operations that create a new stand-alone resource or add a distinct new resource to a collection return `201 Created`. Operations that modify an existing resource return `200 OK`. All paths below are mounted under the `/servicing` prefix. Roles are the exact strings defined in §2.1. Resource creation is restricted to the stand-alone create operations and to the balance-slice recording under an account; every other operation, including every state transition and the clock operations, returns `200 OK` on success. A successful clock operation responds with an empty object in `data`, except that an advance responds with the resulting `current_utc` and the `advanced_days` actually applied. No delete operation exists anywhere in the API.
