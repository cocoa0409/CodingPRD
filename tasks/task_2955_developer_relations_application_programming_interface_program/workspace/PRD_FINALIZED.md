# Developer Relations API Program — Product Requirements Document

## 1. Introduction

Platform companies that expose their capabilities through public APIs eventually discover that the hard part is not the API — it is the programme around it. Developers arrive with no idea which documentation revision is current, ask for scopes they cannot legally be given, exhaust shared rate-limit capacity that nobody is accounting for, and are surprised when a version they built against disappears. Meanwhile the platform team cannot tell which of its partners are trustworthy, which support tickets carry a contractual response commitment, or which feedback actually deserves roadmap capacity. This specification describes the backend service that turns that chaos into an auditable programme.

The service governs the whole arc of a third-party developer's relationship with the platform: self-registration and documentation acknowledgement, sandbox provisioning with seeded sample applications, access applications reviewed and decided under segregation of duties, quota and burst allowance provisioned out of finite product-level capacity pools, hour-by-hour traffic attribution with soft and hard throttling, upgrade requests settled by a deterministic waterfall, versioning with data-sensitivity-driven deprecation notice periods, partner support with escalation channels and service-level credits, terms-of-service enforcement culminating in restriction or revocation, and ecosystem recognition through certification, hackathon awards, directory listings and feedback-driven roadmap prioritisation.

Two properties shape almost every rule that follows. First, **capacity is finite and centrally owned**: every unit of sustained requests-per-minute and every monthly call an entitlement enjoys was reserved out of a named product's declared pool, and the reservation must be returned when the entitlement stops serving. Second, **enforcement is compensating rather than destructive**: penalty points can be reversed on appeal, suspended entitlements can be reinstated, and a declined roadmap item is subtracted back out of the demand index it contributed to. Every collection in this API is a root-level peer resource; the whole surface is mounted at the server root, and relationships between resources are carried by explicit identifier references rather than by deep URL nesting.

## 2. Global Specifications & System-Wide Principles

This section defines the contract-level rules that hold for the entire API surface. Where a later business narrative appears to restate a rule from this section, the two are reinforcing, not competing.

### 2.1. User and Role-Based Access Control

Every request carries its caller identity in two mandatory HTTP headers: `X-User-ID` identifies the acting principal and `X-User-Role` declares the capacity in which that principal is acting. Both headers must be present and non-empty on every endpoint in this specification with exactly one exception — reading the logical programme clock requires no authentication headers at all. A request that is missing either header, or that supplies an empty string for either, is rejected with `ERR_MISSING_AUTH_HEADERS` (HTTP 401). A request whose `X-User-Role` is not one of the six role names declared below is rejected with `ERR_UNKNOWN_ROLE` (HTTP 401), and this check applies to every endpoint including the clock read. When the acting role does not appear in the authorised-roles list for the endpoint being called, the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

The six recognised values of `X-User-Role` are `Developer`, `DevRelManager`, `PlatformAdmin`, `TrustAndSafetyOfficer`, `PartnerSupportAgent` and `Anonymous`.

- A `Developer` is a registered platform developer acting on its own onboarding, applications, entitlements, sandboxes, appeals, tickets and feedback.
- A `DevRelManager` is the developer-relations owner: reviews access applications, runs the upgrade allocation waterfall, curates the public directory, records ecosystem outcomes and triages feedback into the roadmap.
- A `PlatformAdmin` is the platform operator: owns the product catalogue and version lifecycle, provisions and suspends entitlements, decides applications, adjudicates violation cases, revokes access, and drives the logical clock and the programme checkpoint.
- A `TrustAndSafetyOfficer` handles terms-of-service enforcement: monitors usage and opens and investigates violation cases, but never adjudicates them.
- A `PartnerSupportAgent` owns support cases, escalation channels, incident communications and resolution with service credits.
- `Anonymous` is the unauthenticated self-service surface: developer self-registration and reading the logical clock. `Anonymous` is a real, spellable value of `X-User-Role`, so a self-registration request still sends both headers with `X-User-Role` set to `Anonymous`.

Identity semantics differ by role. When `X-User-Role` is `Developer`, `X-User-ID` is the `id` of the acting `Developer` record; if that value is not the `id` of an existing `Developer`, the request is rejected with `ERR_UNKNOWN_DEVELOPER_IDENTITY` (HTTP 401). Ownership checks on any resource that references a `Developer` compare the resource's developer reference to `X-User-ID` — directly for a developer-scoped resource, or transitively through the entitlement, application, lease or case that the resource hangs from. A `Developer` acting on a resource owned by a different developer is rejected with `ERR_NOT_RESOURCE_OWNER` (HTTP 403); this applies both to `Developer`-role writes and to `Developer`-role single-resource reads. When `X-User-Role` is `DevRelManager`, `PlatformAdmin`, `TrustAndSafetyOfficer`, `PartnerSupportAgent` or `Anonymous`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity; the server may record it on a resource — for instance as `reviewer_user_id` or `approver_user_id` on an access application, as `opened_by_user_id`, `investigator_user_id` or `adjudicator_user_id` on a violation case, or as `triaged_by_user_id` on a feedback item — but never compares it to any entity's `id`.

Two workflows enforce **segregation of duties** by comparing `X-User-ID` values. The operator who claimed an access application review may not be the operator who decides it, and the officer who investigated a violation case may not be the operator who adjudicates it or who revokes the developer's access. Both violations surface as `ERR_SEGREGATION_OF_DUTIES` (HTTP 422).

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Every endpoint that returns a list of resources accepts two optional query parameters. `limit` caps the number of items returned; when omitted it defaults to 10, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` skips a number of leading items and defaults to 0; its minimum accepted value is 0. A `limit` outside the range 1 to 100 inclusive, or a negative `offset`, is a malformed request and is rejected with `ERR_INVALID_REQUEST` (HTTP 400).

Unless a specific endpoint states another ordering, list results are sorted by `created_at` in ascending order.

List responses carry `limit`, `offset`, `total_count` and `has_more` inside the `meta` object of the envelope. `total_count` is the number of items matching the request's filters before pagination is applied, and `has_more` is true exactly when items matching the filters remain beyond the returned page.

### 2.4. Resource Identity, Timestamps and Revision Counters

Every persisted resource exposes an `id`, which is a server-minted UUID string carrying no type prefix. Clients never supply an `id` for a resource they are creating.

Most resources — `Developer`, `ApiProduct`, `ApiVersion`, `AccessApplication`, `QuotaAssignment`, `UpgradeRequest`, `SandboxLease`, `ViolationCase`, `SupportCase` and `FeedbackItem` — additionally carry the full common property set:

- `created_at` (string): the ISO 8601 UTC instant the resource was first created, rendered with exactly three fractional-second digits, for example `2026-08-01T00:00:00.000Z`.
- `updated_at` (string): the ISO 8601 UTC instant, in the same format, at which the resource was last modified. Any change to any stored property refreshes it — including changes the server makes on its own initiative, such as a derived counter moving or a cascade reaching the resource.
- `version` (integer): a monotonically increasing revision counter that increments by one on every mutation of the resource, whether that mutation was requested directly by a client or applied by a cascade. It is the value the optimistic-concurrency mechanism in §2.8 compares against.

`UsageWindow` is the single exception. A usage window is an immutable measurement record, so it carries only `id` and `created_at`; it has neither `updated_at` nor `version`, and neither field appears in its response payload.

Timestamps supplied by clients — `starts_at`, `window_start`, `started_at`, `sent_at`, `certification_expires_at`, `current_utc` — are ISO 8601 UTC instants and are echoed back in the same three-fractional-digit form.

### 2.5. The Logical Programme Clock

All deadlines, expiries, notice periods and window comparisons in this system are evaluated against a **logical UTC clock** owned by the server, never against wall-clock time. Before any client sets it, the clock reads exactly `2026-08-01T00:00:00Z`; this startup default is mandatory and the server never falls back to real time.

A `PlatformAdmin` moves the clock by submitting `current_utc`. The response reports both the new `current_utc` and the `previous_utc` that was replaced. The clock only ever moves forward: a submitted instant strictly earlier than the current one is rejected with `ERR_CLOCK_REWIND` (HTTP 422), while an instant equal to the current one is accepted and leaves the clock where it is. Reading the clock returns `current_utc` and, uniquely in this API, requires no authentication headers.

Nothing in this system advances time on its own. Leases do not expire, versions do not sunset, appeal windows do not close and monthly counters do not reset until either the clock is moved and a programme checkpoint is run, or a request whose own logic reads the clock is made.

### 2.6. Rejection Precedence: The Validation Ladder

When a single request violates several rules at once, exactly one error is returned, and which one is fully determined. The server evaluates checks in the fixed order below, from the top, and returns the first failure it finds. This ordering is contractual: a caller must be able to predict, for example, that a malformed body surfaces as `ERR_INVALID_REQUEST` rather than as a not-found error for an identifier the body never parsed, and that a standing block surfaces before any pool-capacity complaint.

The ladder runs in eight bands, and within each band in the listed order.

**Band 1 — transport and authentication (rungs 1–4).** (1) Both `X-User-ID` and `X-User-Role` present and non-empty — `ERR_MISSING_AUTH_HEADERS`, 401, on every endpoint except the clock read. (2) `X-User-Role` is one of the six declared roles — `ERR_UNKNOWN_ROLE`, 401, on every endpoint. (3) When the acting role is `Developer`, `X-User-ID` names an existing developer — `ERR_UNKNOWN_DEVELOPER_IDENTITY`, 401, on every endpoint whose authorised roles include `Developer`. (4) The acting role appears in the endpoint's authorised-roles list — `ERR_UNAUTHORIZED`, 403, on every endpoint.

**Band 2 — request shape (rung 5).** The body parses, every required field is present, and every field satisfies its declared type, enum domain and length or range constraint; pagination `limit` lies between 1 and 100 inclusive and `offset` is at least 0. Any violation is `ERR_INVALID_REQUEST`, 400, on every endpoint.

**Band 3 — existence (rungs 6–7).** (6) Every identifier appearing in the URL path resolves to an existing resource, checked strictly left to right, yielding whichever of `ERR_DEVELOPER_NOT_FOUND`, `ERR_API_PRODUCT_NOT_FOUND`, `ERR_API_VERSION_NOT_FOUND`, `ERR_ACCESS_APPLICATION_NOT_FOUND`, `ERR_QUOTA_ASSIGNMENT_NOT_FOUND`, `ERR_UPGRADE_REQUEST_NOT_FOUND`, `ERR_SANDBOX_LEASE_NOT_FOUND`, `ERR_VIOLATION_CASE_NOT_FOUND`, `ERR_SUPPORT_CASE_NOT_FOUND` or `ERR_FEEDBACK_ITEM_NOT_FOUND` matches the first unresolvable segment — all HTTP 404. (7) Every foreign-key identifier supplied in the request body resolves to an existing resource, checked in the order the fields are declared for that endpoint, yielding whichever of `ERR_DEVELOPER_NOT_FOUND`, `ERR_API_PRODUCT_NOT_FOUND`, `ERR_API_VERSION_NOT_FOUND`, `ERR_ACCESS_APPLICATION_NOT_FOUND` or `ERR_USAGE_WINDOW_NOT_FOUND` applies — HTTP 404. Body-identifier resolution applies to the developer sub-resource actions and to the creation endpoints for access applications, quota assignments, sandbox leases, violation cases, support cases and feedback items.

**Band 4 — ownership (rung 8).** When the acting role is `Developer`, `X-User-ID` must equal the developer that owns the target resource — `ERR_NOT_RESOURCE_OWNER`, 403, on all `Developer`-role writes and all `Developer`-role single-resource reads.

**Band 5 — optimistic concurrency (rungs 9–10).** (9) `expected_api_product_version` equals the product's current `version` — `ERR_STALE_PRODUCT_VERSION`, 412, when provisioning an entitlement. (10) `expected_quota_assignment_version` equals the entitlement's current `version` — `ERR_STALE_ASSIGNMENT_VERSION`, 412, when creating an upgrade request. Because these rungs sit above every state and business check, a caller holding a stale view learns that fact before learning anything about the target's state.

**Band 6 — resource state (rungs 11–19).** (11) The access application is in a state the requested transition permits — `ERR_APPLICATION_STATE_INVALID`, 409, on submit, claim-review, request-changes and decide. (12) The target entitlement is in `entitlement_state` `ACTIVE` — `ERR_ASSIGNMENT_NOT_ACTIVE`, 409, on usage-window ingestion, on upgrade-request creation and on suspension. (13) The target entitlement is in the state its lifecycle action requires, namely `PROVISIONED` for activation, `SUSPENDED` for reinstatement, and not `RETIRED` for any write — `ERR_ASSIGNMENT_STATE_INVALID`, 409, on activation and reinstatement. (14) The target version is in the `lifecycle_state` its action requires, namely `PREVIEW` for promotion, `GENERAL_AVAILABILITY` for a deprecation announcement, and not `SUNSET` for migration-guide publication — `ERR_VERSION_STATE_INVALID`, 409, on promotion, deprecation announcement and guide publication. (15) The violation case is in the state its action requires, namely `OPENED` for investigation, `INVESTIGATING` or `APPEALED` for adjudication, and `UPHELD` for an appeal — `ERR_CASE_STATE_INVALID`, 409, on investigate, adjudicate and appeal. (16) The support case is in the state its action requires, namely `OPEN`, `RESPONDING` or `ESCALATED` to record a communication and `RESPONDING` or `ESCALATED` to escalate or to resolve — `ERR_SUPPORT_CASE_STATE_INVALID`, 409, on communications, escalate and resolve. (17) The sandbox lease is in state `ACTIVE` — `ERR_LEASE_NOT_ACTIVE`, 409, on release and on validation. (18) The feedback item is in the state its action requires, namely `SUBMITTED` for triage and `TRIAGED` for a roadmap decision — `ERR_FEEDBACK_STATE_INVALID`, 409, on triage and roadmap-decision. (19) An allocation run finds at least one `PENDING` upgrade request for the product — `ERR_NO_PENDING_UPGRADE_REQUESTS`, 409.

**Band 7 — safety, compliance and segregation of duties (rungs 20–28).** (20) The acting or target developer's `standing` is `GOOD_STANDING` — `ERR_DEVELOPER_STANDING_BLOCKED`, 422, on application submission, entitlement provisioning, entitlement activation, entitlement reinstatement, sandbox-lease creation and directory submission. (21) The target developer's `standing` is not `REVOKED` — `ERR_DEVELOPER_REVOKED`, 422, on every `Developer`-role write. (22) The developer's `tos_version_accepted` is at least the target product's `required_tos_version` — `ERR_TOS_VERSION_STALE`, 422, on application submission, entitlement provisioning and sandbox-lease creation. (23) The developer's `docs_version_acknowledged` equals the platform's current documentation revision — `ERR_DOCS_NOT_ACKNOWLEDGED`, 422, on entitlement provisioning and sandbox-lease creation. (24) Scope sensitivity is permitted at the tier — `ERR_SCOPE_SENSITIVITY_NOT_PERMITTED`, 422, on application creation and on the application decision. (25) `justification_text` meets the minimum length for the tier — `ERR_JUSTIFICATION_INSUFFICIENT`, 422, on application submission and on upgrade-request creation. (26) An `S1` or `S2` partner ticket is opened only by an entitled developer — `ERR_SEVERITY_NOT_ENTITLED`, 422, on support-case creation. (27) The deciding operator is not the recorded `reviewer_user_id` — `ERR_SEGREGATION_OF_DUTIES`, 422, on the application decision. (28) The adjudicating operator is not the recorded `investigator_user_id`, and the revoking operator is not the investigator of any of that developer's cases — `ERR_SEGREGATION_OF_DUTIES`, 422, on adjudication and on access revocation.

**Band 8 — temporal, referential, constraint and fiscal (rungs 29–57).** These run in the numeric order set out across §3, and each is stated with its trigger condition in the workflow narrative it guards: (29) `ERR_CLOCK_REWIND`; (30) `ERR_WINDOW_NOT_ALIGNED`; (31) `ERR_WINDOW_IN_FUTURE`; (32) `ERR_WINDOW_OUT_OF_ORDER`; (33) `ERR_WINDOW_DUPLICATE`; (34) `ERR_NOTICE_PERIOD_TOO_SHORT`; (35) `ERR_DEPRECATION_WINDOW_FULL`; (36) `ERR_SANDBOX_INTERVAL_OVERLAP`; (37) `ERR_INCIDENT_COALESCE_WINDOW`; (38) `ERR_COMMUNICATION_OUT_OF_ORDER`; (39) `ERR_APPEAL_WINDOW_CLOSED`; (40) `ERR_CERTIFICATION_EXPIRED`; (41) `ERR_VERSION_NOT_GRANTABLE`; (42) `ERR_MIGRATION_GUIDE_MISSING`; (43) `ERR_EVIDENCE_NOT_ATTRIBUTABLE`; (44) `ERR_SUPPORT_CASE_KIND_MISMATCH`; (45) `ERR_ESCALATION_NOT_ENTITLED`; (46) `ERR_DIRECTORY_PREREQUISITES_UNMET`; (47) `ERR_DUPLICATE_APPLICATION`; (48) `ERR_ASSIGNMENT_ALREADY_EXISTS`; (49) `ERR_REVISION_LIMIT_REACHED`; (50) `ERR_TIER_ESCALATION_NOT_PERMITTED`; (51) `ERR_UPGRADE_NOT_AN_INCREASE`; (52) `ERR_NO_COMMUNICATION_RECORDED`; (53) `ERR_APPEAL_ALREADY_FILED`; (54) `ERR_TIER_CEILING_REACHED`; (55) `ERR_SUSTAINED_POOL_EXHAUSTED`; (56) `ERR_MONTHLY_POOL_EXHAUSTED`; (57) `ERR_POOL_BELOW_ALLOCATED`.

Note two consequences of this ordering that the workflows rely on. Ordering of usage windows is checked before duplication, so submitting a window whose `window_start` exactly repeats the assignment's most recent one is a duplicate (rung 33) rather than an out-of-order submission (rung 32). And the fiscal rungs sit at the very bottom, so a developer whose standing has been restricted always hears about the standing block, never about the pool.

### 2.7. Path Resolution for Sub-Resource Reads and Writes

A handful of paths carry a parent identifier and address a child collection — a product's versions, a product's roadmap, a product's allocation run, an entitlement's usage windows, an entitlement's upgrade requests, and the sub-resource actions hanging off a developer, an application, a version, a lease, a case or a feedback item. For all of these the server resolves path identifiers strictly left to right and fails on the first segment that does not resolve, with the not-found error belonging to that segment's resource type. A request for the usage windows of a non-existent entitlement therefore returns `ERR_QUOTA_ASSIGNMENT_NOT_FOUND` and never attempts anything further. The same left-to-right discipline applies to writes: the parent must exist before any child-level state, ownership or business rule is considered.

### 2.8. Optimistic Concurrency on Product Capacity and on Entitlements

Two write operations in this system allocate against state that other writers are actively moving, and both are protected by optimistic concurrency control on the **parent** resource's `version`. In each case the client must prove that the view it computed its request from is still current; a client whose view has been overtaken is told so before anything is mutated.

**Provisioning an entitlement.** A `POST /quota-assignments` request must carry `expected_api_product_version` as a required, non-optional field holding the `version` the client last observed on the `ApiProduct` whose pools the entitlement will draw from. Provisioning draws sustained requests-per-minute and monthly call allowance out of that product's finite pools, so the caller must prove it observed the pool state it is allocating against. If `expected_api_product_version` does not equal the product's current `version`, the request is rejected with `ERR_STALE_PRODUCT_VERSION` (HTTP 412): the pools have moved since the caller read them, and the clamped figures the caller computed from that stale view are no longer valid. Re-reading the product and resubmitting with its current `version` succeeds. A successful provisioning itself increments the product's `version` by one, so the next caller working from the older number is likewise refused.

**Requesting an upgrade.** A `POST /quota-assignments/{id}/upgrade-requests` request must carry `expected_quota_assignment_version` as a required, non-optional field holding the `version` the client last observed on the target `QuotaAssignment`. A newly created upgrade request legitimately supersedes that entitlement's prior `PENDING` request, so a second create against unchanged state would itself succeed — this is not a state precondition but a staleness guard. The caller must prove it observed the entitlement as it now stands, including its current `sustained_rpm` and any request it is about to supersede. If `expected_quota_assignment_version` does not equal the entitlement's current `version`, the request is rejected with `ERR_STALE_ASSIGNMENT_VERSION` (HTTP 412). A successful create increments the entitlement's `version` by one.

No other endpoint in this specification takes a version field. Operations not listed above are not version-guarded and must not require, accept or infer one.

### 2.9. Custody of Finite Capacity Pools

Each `ApiProduct` declares two finite capacities at creation: `sustained_rpm_pool`, the total sustained requests-per-minute it is willing to hand out across all entitlements, and `monthly_call_pool`, the total monthly calls it is willing to hand out. Against these the product maintains two reservation counters, `allocated_sustained_rpm` and `allocated_monthly_calls`, each defined as the sum over the product's entitlements in `entitlement_state` `PROVISIONED` or `ACTIVE` of that entitlement's `sustained_rpm` and `monthly_call_allowance` respectively; both counters start at 0. Two derived read-only figures follow: `available_sustained_rpm` is `sustained_rpm_pool` less `allocated_sustained_rpm`, and `available_monthly_calls` is `monthly_call_pool` less `allocated_monthly_calls`.

Reservations are taken when an entitlement is provisioned and returned when it stops serving. Suspension returns both of an entitlement's reservations to its product by decrementing the two allocated counters; reinstatement re-deducts them by incrementing the counters again, and is only permitted when the product can still cover them. Retirement releases both reservations as well — but **release is idempotent across the suspension boundary**: an entitlement that moves from `SUSPENDED` to `RETIRED` already released its reservations at suspension time and must not release them a second time, whereas an entitlement moving from `ACTIVE` straight to `RETIRED` releases them exactly once at that moment. Getting this wrong inflates a product's availability beyond its declared pool, which is the single most damaging accounting error the service can make.

Pools may be resized after the fact, but never below what is already committed. A programme adjustment that would set `sustained_rpm_pool` below the product's current `allocated_sustained_rpm`, or `monthly_call_pool` below its current `allocated_monthly_calls`, is rejected with `ERR_POOL_BELOW_ALLOCATED` (HTTP 422). Burst headroom is deliberately outside this accounting: `burst_rpm` and `burst_credit_balance` are derived from an entitlement's own clamped sustained rate and are never drawn from, nor returned to, any product pool. So too is `bonus_call_credit`, which is granted by incident resolution and never touches `monthly_call_pool`.

### 2.10. Cascades, Compensation and Server-Initiated Movement

Many operations in this system mutate more than the resource named in the request. Restricting a developer suspends its entitlements, revokes its sandbox leases, delists its directory entry and voids its pending upgrade requests. Sunsetting a version retires the entitlements pinned to it, voids their pending upgrade requests and rejects the applications targeting it. Resolving a platform incident credits every affected entitlement and may relax each one's throttling. Each such secondary mutation is a real mutation: the affected resource's `updated_at` is refreshed and its `version` increments by one, exactly as if a client had written to it directly. Callers must therefore expect a resource's `version` to advance without them having touched it — which is precisely the condition the optimistic-concurrency guards in §2.8 exist to surface.

Enforcement in this programme is **compensating**, not destructive. Points applied to a developer's penalty ledger by an upheld case are subtracted back out if that case is later dismissed, and the case's own `points_applied` is zeroed so the reversal cannot be applied twice. Entitlements suspended by a standing restriction are restored when standing returns, and their reservations are re-deducted from the product pools at that moment. A feedback item declined off the roadmap has its contribution subtracted back out of the product's `demand_index`. Not everything is reversible, however, and where it is not, this document says so explicitly: sandbox leases revoked by a standing cascade are **not** restored when standing recovers.

### 2.11. Numeric Precision, Rounding and Threshold Inclusivity

Rate limits, call counts, penalty points, notice periods, escalation tiers and service credits are whole numbers and are represented in responses as integers. Where a formula produces a fractional intermediate, this document states in each case whether the result is floored, ceilinged or rounded half up, and no other rounding is permitted anywhere in the chain.

- Sustained rate limits are floored to a whole number after the multiplicative factors are applied. Burst uplift is rounded **up** to a whole number. Service credits are rounded half up to a whole call, and — critically — rounded once per entitlement **before** summation, never by summing the raw products and rounding once at the end.
- Scores that carry decimals — `raw_impact`, `priority_score` and `demand_index` — are held and returned at exactly 2 decimal places using round-half-up, and the rounding is applied at each of the three stages of the roadmap calculation rather than only at the end.
- `trust_score` and `audited_trust_score` are integers clamped to the closed interval from 0 to 100 at both ends; the single fractional term inside the audited variant is rounded half up to a whole number before it is subtracted.
- Consumption ratios are compared as exact rational values with no intermediate rounding; a ratio is never rounded before being tested against a threshold.
- Durations expressed in minutes or days are floored to whole units.

Threshold inclusivity is never left to inference. Throttle thresholds are inclusive lower bounds: a ratio of exactly 0.80 soft-throttles and a ratio of exactly 1.00 hard-throttles. Notice-period comparison is inclusive: a submitted notice period exactly equal to the requirement passes. The restriction threshold is inclusive: reaching exactly 50 penalty points restricts. The service-level breach comparisons, by contrast, are strict: a first response landing exactly at the commitment, or a communication gap exactly equal to the cadence allowance, does **not** breach.

### 2.12. Standing as the Master Gate

A `Developer` carries three completely independent state dimensions. `onboarding_state` tracks documentation and sandbox progress through `REGISTERED`, `DOCS_ACKNOWLEDGED`, `SANDBOX_VALIDATED` and `PRODUCTION_ACTIVE`. `standing` tracks terms-of-service compliance through `GOOD_STANDING`, `UNDER_REVIEW`, `RESTRICTED` and `REVOKED`, of which `REVOKED` is terminal. `directory_state` tracks the public ecosystem listing through `NOT_LISTED`, `PENDING_REVIEW`, `LISTED` and `DELISTED`. A transition on one dimension never implies a transition on another unless an explicit cascade in §3 says so; in particular, restriction does not roll back onboarding progress.

`standing` is the gate that guards forward motion across the whole programme. Submitting an access application, provisioning an entitlement, activating one, reinstating one, creating a sandbox lease and submitting a directory listing all require the relevant developer to sit at `GOOD_STANDING`; any of `UNDER_REVIEW`, `RESTRICTED` or `REVOKED` blocks them with `ERR_DEVELOPER_STANDING_BLOCKED` (HTTP 422). Separately and more bluntly, a developer whose `standing` is `REVOKED` may not perform any write at all, in any workflow, and every such attempt yields `ERR_DEVELOPER_REVOKED` (HTTP 422). Note the asymmetry that follows: an entitlement already `ACTIVE` when its developer moves to `UNDER_REVIEW` keeps serving traffic and keeps accepting usage windows — it merely becomes ineligible to receive upgrade grants — whereas restriction proper suspends it.

Two further compliance gates sit alongside standing. Provisioning an entitlement or creating a sandbox lease requires `docs_version_acknowledged` to equal the platform's current documentation revision, failing with `ERR_DOCS_NOT_ACKNOWLEDGED` (HTTP 422). Submitting an application, provisioning an entitlement and creating a sandbox lease all require the developer's `tos_version_accepted` to be at least the target product's `required_tos_version`, failing with `ERR_TOS_VERSION_STALE` (HTTP 422).

## 3. Business Logic & Workflows

### 3.1. Joining the Programme: Registration, Documentation and Sandbox Validation

Entry into the programme is deliberately cheap. An unauthenticated caller acting as `Anonymous`, or a `DevRelManager` onboarding a partner on their behalf, registers a developer account by supplying three facts: `org_name`, the registered organisation name, between 1 and 120 characters; `contact_email`, the primary technical contact address, between 5 and 160 characters and required to contain an `@` character; and `region_code`, the data-residency region the account is provisioned in, which must be exactly one of `US`, `EU` or `APAC`. The new record starts at `onboarding_state` `REGISTERED`, `standing` `GOOD_STANDING`, `directory_state` `NOT_LISTED` and `certification_level` `NONE`, with `certification_expires_at`, `directory_summary`, `docs_version_acknowledged`, `tos_version_accepted` and `revoked_at` all null, with `hackathon_award_count`, `clean_window_count`, `throttled_window_count` and `violation_points` all 0, and with both `trust_score` and `audited_trust_score` seeded at 50. Registration is the only creation in this system that an unauthenticated role may perform.

Operators browsing the population can narrow the developer list by `directory_state` — which is how the public directory view is assembled — and by `standing` and `onboarding_state`, alongside the usual `limit` and `offset`.

**Acknowledging the documentation.** Before a developer can be given anything, it must acknowledge what it is signing up to. The acknowledgement submits `docs_version`, the documentation revision being acknowledged, and `tos_version`, the terms-of-service revision being accepted. Only the developer itself may act. The submitted `docs_version` must equal the platform's current documentation revision, which is **2**; the submitted `tos_version` must equal the `required_tos_version` of at least one product in the catalogue. On success the two submitted numbers are recorded on the developer as `docs_version_acknowledged` and `tos_version_accepted`, `onboarding_state` advances `REGISTERED → DOCS_ACKNOWLEDGED`, and the developer's `trust_score` is recomputed under the onboarding-snapshot variant described below. Acknowledgement is repeatable: a developer already sitting at `DOCS_ACKNOWLEDGED` may acknowledge again, which leaves `onboarding_state` at `DOCS_ACKNOWLEDGED` — the transition is `DOCS_ACKNOWLEDGED → DOCS_ACKNOWLEDGED` — but advances the recorded `docs_version_acknowledged` and `tos_version_accepted`; that repeat is admissible only when the submitted `docs_version` is strictly greater than the currently recorded `docs_version_acknowledged`. Each of those submitted-version checks — the documentation revision on a first acknowledgement, the strictly-greater rule on a repeat, and the terms-of-service match against the catalogue — rejects the acknowledgement with `ERR_INVALID_REQUEST` (HTTP 400) when it fails; they are evaluated once the developer named in the path has resolved and before the ownership check. A catalogue holding no product at all therefore contains no matching `required_tos_version`, so no acknowledgement can succeed until at least one product exists.

**Leasing a sandbox.** A developer provisions a sandbox environment by naming the `developer_id` it is acting as, the `api_product_id` whose sandbox it wants, the `starts_at` instant at which occupation begins, a `lease_days` length between 1 and 30 whole days inclusive, and a `sample_app_slug` naming the sample application to seed into the environment. The slug must appear in the product's `sample_app_slugs` list. The server derives `expires_at` as `starts_at` advanced by `lease_days` whole days, and the lease occupies the half-open interval that includes `starts_at` and excludes `expires_at`. A lease begins in `state` `ACTIVE` with `released_at` and `closed_reason` null. Because a sandbox is a production-adjacent grant, lease creation is gated on the developer sitting at `GOOD_STANDING`, on `docs_version_acknowledged` matching the current documentation revision, and on `tos_version_accepted` reaching the product's `required_tos_version`.

One developer may hold several leases on one product over time but never two overlapping ones. If the requested interval overlaps the interval of an existing `ACTIVE` lease held by the same developer on the same product, the request is rejected with `ERR_SANDBOX_INTERVAL_OVERLAP` (HTTP 409). Because the interval excludes its own end instant, exact adjacency is legitimate: a new lease whose `starts_at` equals an existing lease's `expires_at` does not overlap and is accepted. Leases can be filtered by `developer_id`, `api_product_id` and `state`.

Two developer-driven lease actions exist, and both require the lease to be `ACTIVE` — otherwise `ERR_LEASE_NOT_ACTIVE` (HTTP 409) — and require the acting developer to own it. **Validating** the lease declares the seeded sample application successfully exercised; the lease records the validated sample application, the developer's `onboarding_state` advances `DOCS_ACKNOWLEDGED → SANDBOX_VALIDATED`, and `trust_score` is recomputed under the onboarding-snapshot variant. Validation requires the lease's `sample_app_slug` to be present. **Releasing** the lease hands the environment back early: `state` moves `ACTIVE → RELEASED`, `released_at` is set from the logical clock and `closed_reason` becomes `DEVELOPER_RELEASE`, which frees the interval so a replacement lease may be taken. Two other paths close a lease without the developer asking: a checkpoint run whose clock has reached `expires_at` moves it `ACTIVE → EXPIRED` with `released_at` set and `closed_reason` `CHECKPOINT_EXPIRY`, and a standing cascade moves it `ACTIVE → REVOKED` with `released_at` set and `closed_reason` `STANDING_CASCADE`.

The last onboarding step is not a developer action at all. When a developer's first entitlement reaches `entitlement_state` `ACTIVE`, the server bubbles the developer's `onboarding_state` from `SANDBOX_VALIDATED` up to `PRODUCTION_ACTIVE`, which is the state that makes the developer eligible to submit a public directory listing. A developer that has not yet reached `SANDBOX_VALIDATED` when an entitlement activates keeps whatever `onboarding_state` it had.

**How trust is scored.** Both `trust_score` and `audited_trust_score` are computed from the same six components, and both are integers clamped into the closed range 0 to 100 at both ends. The shared components are: a base of **50 points**; a certification component worth 0 points at `certification_level` `NONE`, **8 points** at `ASSOCIATE` and **15 points** at `PROFESSIONAL`, which counts for nothing at all when `certification_expires_at` is null or strictly earlier than the logical clock; a documentation component worth **6 points** when `docs_version_acknowledged` is at least the current documentation revision of 2 and 0 points otherwise; a hackathon component worth **4 points** for each recorded award, counting at most **3 awards** — so `hackathon_award_count` values above 3 contribute the same 12 points as exactly 3; and a clean-traffic component worth **1 point** for each clean usage window, counting at most **10 windows**, taken from `clean_window_count`. From the sum of those five, the developer's **settled penalty** — its current `violation_points` — is subtracted.

The two variants diverge in what else they charge.

- The **onboarding-snapshot** variant is the one written to `trust_score`, and it is recomputed on documentation acknowledgement, on sandbox validation and on any ecosystem-participation update. It stops there: base plus certification plus documentation plus hackathon plus clean-window points, minus settled penalty, clamped to 0 through 100. It ignores penalty exposure from cases that are still running and ignores `throttled_window_count` entirely. This is the value the entitlement-provisioning calculation reads.
- The **enforcement-audit** variant is the one written to `audited_trust_score`, and it is recomputed only by the audited-rescoring step of a programme checkpoint. It starts from the same five positive components minus the settled penalty and then subtracts two more terms. First, **pending exposure**: the sum of `penalty_points` across the developer's violation cases whose `state` is `OPENED`, `INVESTIGATING` or `APPEALED`, multiplied by **0.50** and rounded half up to a whole number of points. Second, a **throttling penalty** of **5 points**, charged whenever `throttled_window_count` is at least **2** and 0 points otherwise. The result is clamped identically. Because of those two extra subtractions, identical underlying data yields an `audited_trust_score` strictly lower than `trust_score` whenever any case is pending or any throttling has occurred, and equal to it otherwise. Cases in `state` `DISMISSED` or `UPHELD_FINAL` contribute nothing beyond what is already settled in `violation_points`.

### 3.2. The Product Catalogue, Version Lifecycle and Deprecation Timelines

A `PlatformAdmin` publishes an **API product** by declaring its `name` (1 to 120 characters), its `data_sensitivity` — the highest data class it exposes, one of `PUBLIC`, `PERSONAL` or `FINANCIAL` — its `scope_catalog`, its `sample_app_slugs`, and the two finite pools `sustained_rpm_pool` and `monthly_call_pool`, each at least 1. The `scope_catalog` is an array of 1 to 20 entries, each an object with a `scope` string and a `sensitivity` of `PUBLIC`, `PERSONAL` or `FINANCIAL`; scope values must be unique within the array, and the catalogue is the *only* set of scopes any application may request against this product. `sample_app_slugs` is an array of 1 to 10 strings naming the sample applications a sandbox lease may seed. An optional `required_tos_version` of at least 1 defaults to 1 when omitted. At creation both allocated counters sit at 0, so `available_sustained_rpm` and `available_monthly_calls` equal the declared pools, and `demand_index` starts at 0.00. The catalogue list may be filtered by `data_sensitivity`.

Pools are resizable through a **programme adjustment**, which accepts any combination of a new `sustained_rpm_pool`, a new `monthly_call_pool` and a new `required_tos_version`, together with a mandatory `adjustment_reason`. The adjustment recomputes `available_sustained_rpm` and `available_monthly_calls` and increments the product's `version` by one — which is exactly why a caller holding an older product `version` is refused when it later tries to provision against these pools. An adjustment that would leave either pool below the matching allocated counter is refused with `ERR_POOL_BELOW_ALLOCATED`.

**Versions.** Each product carries one or more versions, created by a `PlatformAdmin` with a `semver` label matching the three-part major-dot-minor-dot-patch shape (for example `2.1.0`) and a `breaking_change` boolean that defaults to false. A newly created version enters `lifecycle_state` `PREVIEW` with `migration_guide_url`, `migration_guide_published_at`, `deprecation_announced_at`, `sunset_at`, `required_notice_days`, `notice_days_at_announcement` and `sunset_completed_at` all null. Its `api_product_id` records the product it belongs to, and a product's versions can be listed and filtered by `lifecycle_state`. Promotion moves a version `PREVIEW → GENERAL_AVAILABILITY`, which is what makes it grantable to the `STANDARD`, `PARTNER` and `PRIVILEGED` tiers; attempting to promote a version that is not in `PREVIEW` yields `ERR_VERSION_STATE_INVALID`.

Grantability is a function of `lifecycle_state` and requested tier, and it is checked both when an application is submitted and when an entitlement is provisioned from it. A `PREVIEW` version is grantable only to `SANDBOX`. A `GENERAL_AVAILABILITY` version is grantable to all four tiers. A version in `DEPRECATION_ANNOUNCED` or `SUNSET` is grantable to no tier at all. Any mismatch is rejected with `ERR_VERSION_NOT_GRANTABLE` (HTTP 422).

**Publishing a migration guide** records `migration_guide_url` on the version together with `migration_guide_published_at` taken from the logical clock. A guide may be published while the version is in any lifecycle state except `SUNSET`; attempting it on a sunset version yields `ERR_VERSION_STATE_INVALID`.

**Announcing deprecation** is the most heavily gated operation in the catalogue, and it exists to guarantee that partners are never surprised. The announcement submits a single field, `notice_days`, the number of whole days of notice being given. The version must be in `GENERAL_AVAILABILITY`, or the announcement fails with `ERR_VERSION_STATE_INVALID`.

The required notice period is computed as follows. Start from the baseline for the product's `data_sensitivity`: **30 days** for `PUBLIC`, **60 days** for `PERSONAL`, **90 days** for `FINANCIAL`. If the version's `breaking_change` flag is true, add a further **30 days**. If at least one entitlement pinned to this version is in `entitlement_state` `ACTIVE` and holds `tier` `PARTNER` or `PRIVILEGED`, add another **30 days**. The total is stored on the version as `required_notice_days`. The submitted `notice_days` must be at least `required_notice_days`; the comparison is inclusive, so submitting exactly the required number passes, and submitting fewer is rejected with `ERR_NOTICE_PERIOD_TOO_SHORT` (HTTP 422). A worked illustration: a breaking version of a `FINANCIAL` product with one `ACTIVE` `PARTNER` entitlement pinned to it requires ninety plus thirty plus thirty, that is 150 days of notice.

Two further gates apply. A version whose `breaking_change` is true must already have a published `migration_guide_url` before its deprecation may be announced, otherwise `ERR_MIGRATION_GUIDE_MISSING` (HTTP 422) — a breaking change with no migration path is not a notice, it is an outage. And a product may carry at most **two** versions sitting in `DEPRECATION_ANNOUNCED` at any one time; an announcement that would make a third is rejected with `ERR_DEPRECATION_WINDOW_FULL` (HTTP 422). That check is an aggregate over the whole product, counting the versions other than the one being announced.

On success the version records `deprecation_announced_at` from the logical clock, sets `sunset_at` to that instant advanced by the submitted `notice_days` whole days, records `notice_days_at_announcement` as the floor of the whole days between the logical clock and `sunset_at` at announcement time, and moves `GENERAL_AVAILABILITY → DEPRECATION_ANNOUNCED`. The version keeps serving the entitlements already pinned to it but stops being grantable to new applications.

**Sunset** is never a client action. When a programme checkpoint finds a `DEPRECATION_ANNOUNCED` version whose `sunset_at` is at or before the logical clock, the version moves `DEPRECATION_ANNOUNCED → SUNSET` — a terminal state — and records `sunset_completed_at`. Three cascades follow, and all three must land. Every entitlement pinned to this version whose `entitlement_state` is `ACTIVE` or `SUSPENDED` becomes `RETIRED`, releasing its pool reservations subject to the idempotency rule in §2.9. Every `PENDING` upgrade request on those entitlements becomes `VOIDED`. And every access application targeting this version whose `state` is `SUBMITTED`, `UNDER_REVIEW` or `CHANGES_REQUESTED` becomes `REJECTED`, with `decision_reason` recorded as `TARGET_VERSION_SUNSET`.

### 3.3. Access Applications: Justification, Review Rounds and Tiered Decisions

Access to a production version is never granted implicitly; it is applied for, reviewed, and decided by two different operators. A developer drafts an **access application** by naming the `developer_id` it is acting as, the `target_api_version_id` it wants access to — whose own product reference identifies the product whose catalogue and pools are in play — the `requested_tier` it is asking for, one of `SANDBOX`, `STANDARD`, `PARTNER` or `PRIVILEGED`, the `requested_scopes` it needs as an array of 1 to 20 unique scope strings each of which must appear in that product's `scope_catalog`, the `requested_monthly_calls` volume it expects (at least 1), and `justification_text`. The draft is created in `state` `DRAFT` with `revision_round` 0 and with `reviewer_user_id`, `approver_user_id`, `approved_tier`, `granted_scopes`, `data_access_limit`, `changes_requested_note`, `decision_reason` and `decided_at` all null.

`justification_text` is optional in the general case but becomes mandatory at draft time whenever the `requested_tier` is `PARTNER` or `PRIVILEGED`, or whenever any requested scope carries a catalogue `sensitivity` other than `PUBLIC`; where it is mandatory it must be at least 40 characters long.

Two checks bite at draft time. Sensitivity must match ambition: a scope whose catalogue `sensitivity` is `PERSONAL` may only be requested at `tier` `STANDARD` or above, and a scope whose `sensitivity` is `FINANCIAL` may only be requested at `tier` `PARTNER` or above, with `ERR_SCOPE_SENSITIVITY_NOT_PERMITTED` (HTTP 422) otherwise. And a developer may not hold two applications that are still live for the same target version: if any application of this developer against this `target_api_version_id` sits in a non-terminal `state` — that is, anything other than `APPROVED` or `REJECTED` — the new draft is rejected with `ERR_DUPLICATE_APPLICATION` (HTTP 409). Applications may be listed filtered by `developer_id`, by `target_api_version_id` and by `state`.

**Submission.** The developer submits the draft for review, optionally supplying a revised `justification_text` alongside. The application must be in `DRAFT` or `CHANGES_REQUESTED`, otherwise `ERR_APPLICATION_STATE_INVALID` (HTTP 409); the acting developer must own it; the developer's `standing` must be `GOOD_STANDING`; its `tos_version_accepted` must reach the target version's product `required_tos_version`; and the target version's `lifecycle_state` must be grantable for the `requested_tier`. Submission also applies the tier-scaled justification floor: the length of `justification_text` must be at least **0 characters** for `SANDBOX`, **40 characters** for `STANDARD`, **120 characters** for `PARTNER` and **240 characters** for `PRIVILEGED`, with `ERR_JUSTIFICATION_INSUFFICIENT` (HTTP 422) when it falls short. On success the application moves `DRAFT → SUBMITTED` and `revision_round` increments — reaching 1 on the very first submission.

**Claiming the review.** A `DevRelManager` claims a `SUBMITTED` application, moving it `SUBMITTED → UNDER_REVIEW` and recording the claiming operator's `X-User-ID` as `reviewer_user_id`. That recorded value is the anchor of the whole segregation-of-duties rule for this workflow.

**Requesting changes.** The claiming reviewer may send the application back with a mandatory `changes_requested_note`, moving it `UNDER_REVIEW → CHANGES_REQUESTED`. Three conditions apply: the application must be in `UNDER_REVIEW`; the acting operator's `X-User-ID` must equal the recorded `reviewer_user_id`; and `revision_round` must still be below the cap of **3** completed rounds, otherwise `ERR_REVISION_LIMIT_REACHED` (HTTP 422). A developer answering a change request resubmits, which moves the application `CHANGES_REQUESTED → SUBMITTED`, increments `revision_round` and clears `changes_requested_note`; that resubmission is likewise refused with `ERR_REVISION_LIMIT_REACHED` once `revision_round` has reached 3. The loop `UNDER_REVIEW → CHANGES_REQUESTED → SUBMITTED` may therefore run several times but is bounded by three rounds.

**The decision.** Only a `PlatformAdmin` decides, and never the operator who reviewed. The decision submits `decision` — approve or reject — and, for an approval, `approved_tier` and `granted_scopes`; a `decision_reason` note may accompany either outcome. The acting operator's `X-User-ID` must differ from the recorded `reviewer_user_id`, otherwise `ERR_SEGREGATION_OF_DUTIES` (HTTP 422).

An approval requires the application to be in `UNDER_REVIEW`. The `approved_tier` may equal or sit below the `requested_tier` in rank — the ranks running `SANDBOX` 1, `STANDARD` 2, `PARTNER` 3, `PRIVILEGED` 4 — but may never outrank it; and `granted_scopes` must be a subset of both `requested_scopes` and the product's `scope_catalog`. Either breach is `ERR_TIER_ESCALATION_NOT_PERMITTED` (HTTP 422). The granted scopes' sensitivities must also be permitted at the `approved_tier` under the same `PERSONAL`-needs-`STANDARD`, `FINANCIAL`-needs-`PARTNER` rule, which at decision time surfaces as `ERR_SCOPE_SENSITIVITY_NOT_PERMITTED`. On approval the application moves `UNDER_REVIEW → APPROVED`, records `approver_user_id` from `X-User-ID`, stores `approved_tier` and `granted_scopes`, sets `decided_at` from the logical clock, and computes `data_access_limit` — the highest data sensitivity the approved tier may touch, which is `PUBLIC` at `SANDBOX`, `PERSONAL` at `STANDARD`, and `FINANCIAL` at both `PARTNER` and `PRIVILEGED`. An `APPROVED` application becomes the sole eligible basis for exactly one entitlement.

A rejection from `UNDER_REVIEW` moves the application `UNDER_REVIEW → REJECTED`, recording `decision_reason` and `decided_at`; the same segregation-of-duties rule applies. There is one further rejection path: an application stuck in `CHANGES_REQUESTED` whose `revision_round` has reached exactly 3 may be rejected outright, moving `CHANGES_REQUESTED → REJECTED` with `decision_reason` recorded as `REVISION_LIMIT_EXHAUSTED`. Both `APPROVED` and `REJECTED` are terminal.

Applications can also be rejected without any operator acting. A version sunset rejects the applications targeting it with `decision_reason` `TARGET_VERSION_SUNSET`, and a developer revocation rejects that developer's live applications with `decision_reason` `ACCESS_REVOKED`.

### 3.4. Provisioning an Entitlement: Quota, Burst Headroom and the Trust Multiplier

An approved application is turned into a live **entitlement** by a `PlatformAdmin`, who supplies only two fields: the `access_application_id` being realised and the `expected_api_product_version` proving which view of the product's pools the caller is allocating against. Everything else is derived. The entitlement copies `developer_id` from the application, freezes `pinned_api_version_id` from the application's `target_api_version_id`, copies `tier` from `approved_tier` and `granted_scopes` from the application's granted set, starts `entitlement_state` at `PROVISIONED` and `throttle_state` at `NORMAL`, sets `bonus_call_credit` and `monthly_calls_consumed` to 0, sets `last_reset_at` from the logical clock, and leaves `activated_at`, `suspended_at`, `suspension_reason` and `retired_at` null. The pinning is permanent: when that version is eventually sunset, this entitlement is retired with it.

An approved application may back exactly one entitlement; a second attempt against the same application is refused with `ERR_ASSIGNMENT_ALREADY_EXISTS` (HTTP 409). Provisioning further requires the developer to be at `GOOD_STANDING`, to have `docs_version_acknowledged` at the current documentation revision, to have `tos_version_accepted` at the product's `required_tos_version`, and requires the pinned version to still be grantable at the entitlement's tier.

**The provisioning calculation** runs in a pinned, observable order — sustained rate, then pool deduction, then burst, then monthly allowance — and no later step ever revises an earlier one.

*Step one: the desired sustained rate.* Three multiplicative factors are combined and the product is floored once, at the end. The **tier base** is 60 requests per minute at `SANDBOX`, 600 at `STANDARD`, 3,000 at `PARTNER` and 12,000 at `PRIVILEGED`. The **trust multiplier** is selected from the developer's onboarding-snapshot `trust_score` in four bands: 1.25 when `trust_score` is at least 80; 1.00 when it is from 60 through 79; 0.75 when it is from 40 through 59; and 0.50 when it is 39 or below. Whichever band applies is recorded on the entitlement as `trust_multiplier_applied`, so the figure that produced the quota is auditable afterwards. The **scope factor** discounts the rate for every sensitive scope granted: count the granted scopes whose catalogue sensitivity is `PERSONAL` and those whose sensitivity is `FINANCIAL`, then start from 1 and subtract 0.05 for each `PERSONAL` scope and 0.10 for each `FINANCIAL` scope; if the result would fall below the floor of **0.60**, the floor is used instead. The desired sustained rate is the tier base multiplied by the trust multiplier multiplied by the scope factor, with the final product floored to a whole number.

*Step two: clamp against the pool and reserve.* The entitlement's `sustained_rpm` is the smaller of the desired sustained rate and the product's current `available_sustained_rpm`. If that clamped value is 0 or less, provisioning is refused with `ERR_SUSTAINED_POOL_EXHAUSTED` (HTTP 422). Otherwise `sustained_rpm` is added to the product's `allocated_sustained_rpm`.

*Step three: burst headroom, derived from the clamped value.* This is the step implementers most often get wrong: `burst_rpm` is built from the **clamped** `sustained_rpm` of step two, never from the unclamped desire of step one. The **burst factor** is 1.5 at `SANDBOX`, 2.0 at `STANDARD`, 3.0 at `PARTNER` and 4.0 at `PRIVILEGED`. `burst_rpm` equals `sustained_rpm` plus the uplift, where the uplift is `sustained_rpm` multiplied by one less than the tier's burst factor, rounded **up** to a whole number. `burst_rpm` therefore already contains the sustained component. The entitlement's opening `burst_credit_balance` is `burst_rpm` multiplied by **10**, representing ten windows' worth of burst-attributed calls, and that same figure is restored at every monthly reset.

*Step four: the monthly allowance.* `monthly_call_allowance` is the smallest of three numbers: the application's `requested_monthly_calls`, the tier's monthly cap — 50,000 at `SANDBOX`, 1,000,000 at `STANDARD`, 10,000,000 at `PARTNER` and 60,000,000 at `PRIVILEGED` — and the product's current `available_monthly_calls`. If that figure is 0 or less, provisioning is refused with `ERR_MONTHLY_POOL_EXHAUSTED` (HTTP 422). Otherwise it is added to the product's `allocated_monthly_calls`. Finally, the product's `version` increments by one, which invalidates every other caller's older observation of these pools.

**The entitlement lifecycle.** `entitlement_state` runs `PROVISIONED`, `ACTIVE`, `SUSPENDED` and the terminal `RETIRED`. Activation by a `PlatformAdmin` requires `entitlement_state` `PROVISIONED` — otherwise `ERR_ASSIGNMENT_STATE_INVALID` (HTTP 409) — requires the developer at `GOOD_STANDING`, and requires the pinned version's `lifecycle_state` not to be `SUNSET`. It moves `PROVISIONED → ACTIVE`, sets `activated_at` from the logical clock, and bubbles the developer's `onboarding_state` from `SANDBOX_VALIDATED` to `PRODUCTION_ACTIVE` if it was sitting there.

Suspension moves an `ACTIVE` entitlement to `SUSPENDED`. It may be requested administratively with a `suspension_reason`, in which case the entitlement must be `ACTIVE` or the request fails with `ERR_ASSIGNMENT_NOT_ACTIVE` (HTTP 409); or it may arrive as a standing cascade, in which case `suspension_reason` is recorded as `STANDING_RESTRICTION`. Either way `suspended_at` is set, the entitlement's `sustained_rpm` is subtracted from the product's `allocated_sustained_rpm` and its `monthly_call_allowance` from `allocated_monthly_calls`, and every `PENDING` upgrade request on this entitlement becomes `VOIDED`.

Reinstatement moves `SUSPENDED → ACTIVE`. It requires `entitlement_state` `SUSPENDED` (otherwise `ERR_ASSIGNMENT_STATE_INVALID`), the developer at `GOOD_STANDING`, the pinned version not `SUNSET`, and enough room in both pools — the product's `available_sustained_rpm` must be at least this entitlement's `sustained_rpm` and its `available_monthly_calls` at least this entitlement's `monthly_call_allowance`, failing with `ERR_SUSTAINED_POOL_EXHAUSTED` or `ERR_MONTHLY_POOL_EXHAUSTED` respectively. On success `suspended_at` and `suspension_reason` are cleared and both reservations are re-deducted from the product's counters. Reinstatement can also arrive as a cascade, when an appeal dismissal restores a developer's standing.

Retirement is only ever server-initiated, arriving either from a version sunset or from a developer revocation, and it applies to `ACTIVE` and `SUSPENDED` entitlements alike: `retired_at` is set and `PENDING` upgrade requests are voided. An entitlement moving `ACTIVE → RETIRED` releases both pool reservations at that moment; an entitlement moving `SUSPENDED → RETIRED` released them already at suspension and must **not** release them again.

Entitlements are readable individually with their live consumption ledger and both state dimensions, and the collection can be filtered by `developer_id`, `access_application_id`, `pinned_api_version_id`, `entitlement_state` and `throttle_state`.

### 3.5. Metering Traffic: Attribution, Throttling and Rate-Limit Breach

Traffic is not measured continuously; it is **ingested** one hour at a time. A `PlatformAdmin` or `DevRelManager` records a **usage window** against an entitlement by submitting `window_start`, the beginning of the one-hour measurement bucket, `total_calls`, the calls observed in that hour (at least 0), and `burst_calls`, the subset of those calls served above the sustained rate (at least 0 and never greater than `total_calls`). The server derives `window_end` as `window_start` advanced by 60 minutes, and records the entitlement it was measured against as the window's `quota_assignment_id`. A usage window is an immutable record: it has no `updated_at` and no `version`.

Four temporal gates guard ingestion, and they are evaluated in this order. `window_start` must be exactly hour-aligned — its minute, second and millisecond components all zero — and `window_end` must equal `window_start` plus 60 minutes, otherwise `ERR_WINDOW_NOT_ALIGNED` (HTTP 422). `window_end` must be at or before the current logical clock, so no future traffic can be claimed, otherwise `ERR_WINDOW_IN_FUTURE` (HTTP 422). `window_start` must be at or after the most recent `window_start` already recorded for this entitlement, so windows arrive in non-decreasing chronological order, otherwise `ERR_WINDOW_OUT_OF_ORDER` (HTTP 422). And finally no window may already exist for this entitlement with the same `window_start`, otherwise `ERR_WINDOW_DUPLICATE` (HTTP 409). Because ordering is checked before duplication, an exact repeat of the latest `window_start` passes the ordering gate and lands on the duplicate gate. Ingestion additionally requires the entitlement to be in `entitlement_state` `ACTIVE`, failing with `ERR_ASSIGNMENT_NOT_ACTIVE` otherwise — note that this remains true while the developer sits at `UNDER_REVIEW`, since an active entitlement keeps serving during an investigation.

**Attribution comes in two variants**, and which one applied is permanently recorded on the window as `attribution_variant`.

- The window is attributed **`BURST_ISOLATED`** when — and only when — the entitlement's `tier` is `PARTNER` or `PRIVILEGED` *and* its current `burst_credit_balance` is at least the window's `burst_calls`. Under this variant `calls_charged_to_allowance` is `total_calls` less `burst_calls`, and `burst_credit_consumed` equals `burst_calls`. Burst traffic is thus paid for out of burst credit rather than out of the monthly allowance, so the monthly ratio grows more slowly for an identical hour of traffic.
- The window is attributed **`BURST_INCLUSIVE`** in every other case — that is, whenever the `tier` is `SANDBOX` or `STANDARD`, or whenever `burst_credit_balance` is smaller than `burst_calls`. Under this variant `calls_charged_to_allowance` equals the whole `total_calls` figure and `burst_credit_consumed` is 0, leaving `burst_credit_balance` untouched.

The running ledger is then updated: `burst_credit_consumed` is subtracted from the entitlement's `burst_credit_balance`, `calls_charged_to_allowance` is added to its `monthly_calls_consumed`, and the resulting total is copied onto the window as `monthly_calls_consumed_after`.

**Throttling** is decided from a consumption ratio, and the denominator is the *effective* allowance — the entitlement's `monthly_call_allowance` **plus** its `bonus_call_credit`, so service credits genuinely buy headroom. The ratio is `monthly_calls_consumed_after` divided by that effective allowance, compared as an exact rational value with no intermediate rounding. If the ratio is at least **1.00**, the window's `resulting_throttle_state` is `HARD_THROTTLED` and its `overage_calls` is `monthly_calls_consumed_after` less the effective allowance. If the ratio is at least **0.80** but below 1.00, `resulting_throttle_state` is `SOFT_THROTTLED` and `overage_calls` is 0. Otherwise `resulting_throttle_state` is `NORMAL` and `overage_calls` is 0. Whatever the window resolves to is written through to the entitlement's own `throttle_state`, which is why the same value appears in both places.

`throttle_state` is a second, fully independent dimension of the entitlement: it moves without regard to `entitlement_state`, and vice versa. Its transitions are `NORMAL → SOFT_THROTTLED` when a window's ratio reaches 0.80 while remaining below 1.00; `SOFT_THROTTLED → HARD_THROTTLED` when a window's ratio reaches 1.00; and `NORMAL → HARD_THROTTLED` when a single window's ratio reaches 1.00 in one step, skipping the soft band entirely. Relief runs the other way: `HARD_THROTTLED → SOFT_THROTTLED` when a credit lowers the recomputed ratio to at least 0.80 but below 1.00, and `SOFT_THROTTLED → NORMAL` when a credit or a monthly reset lowers the recomputed ratio below 0.80. Crossing into the soft band increments the developer's `throttled_window_count` and resets its `clean_window_count` to 0; crossing into the hard band records `overage_calls` on the window and increments `throttled_window_count`.

**Rate-limit breach is a separate, instantaneous check** and is recorded on the window as the boolean `rate_limit_breach`. It compares the window's average rate against the entitlement's burst ceiling: the window breaches when `total_calls` divided by the 60 minutes of the window exceeds `burst_rpm` — equivalently, when `total_calls` is strictly greater than `burst_rpm` multiplied by 60. Because `burst_rpm` already contains the sustained component, the sustained rate is **not** added again for this comparison. A breach has no direct effect on `throttle_state`; its consequence is bookkeeping and, potentially, a rate-abuse investigation.

Finally the developer's traffic-quality counters are updated exactly once per window: when `resulting_throttle_state` is `NORMAL` **and** `rate_limit_breach` is false, `clean_window_count` increments by one; in every other case `throttled_window_count` increments by one and `clean_window_count` is reset to 0. Those two counters are the ones the trust calculation in §3.1 reads.

An entitlement's usage windows can be listed in `window_start` order.

### 3.6. Asking for More: Upgrade Requests and the Allocation Waterfall

A developer that has outgrown its sustained rate asks for more by creating an **upgrade request** against one of its own entitlements. The request submits `requested_sustained_rpm`, the target sustained rate (at least 1), a `justification_text` of at least 40 characters, and `expected_quota_assignment_version` proving the caller has observed the entitlement as it now stands. The server computes `requested_delta_rpm` as `requested_sustained_rpm` less the entitlement's `sustained_rpm` at creation time, and creates the request in `state` `PENDING` with `granted_delta_rpm` 0 and with `denial_reason`, `run_sequence` and `decided_at` null.

Four gates apply beyond the staleness check. The entitlement must be in `entitlement_state` `ACTIVE`, otherwise `ERR_ASSIGNMENT_NOT_ACTIVE`. `requested_sustained_rpm` must be strictly greater than the entitlement's current `sustained_rpm` — an upgrade that is not an increase is rejected with `ERR_UPGRADE_NOT_AN_INCREASE` (HTTP 422). The justification floor applies, surfacing as `ERR_JUSTIFICATION_INSUFFICIENT`. And the entitlement must have room to grow at all: its `sustained_rpm` must be strictly below its **tier ceiling**, which is exactly **twice** the tier's base sustained rate — 120 for `SANDBOX`, 1,200 for `STANDARD`, 6,000 for `PARTNER` and 24,000 for `PRIVILEGED`. An entitlement already at or above its ceiling is refused with `ERR_TIER_CEILING_REACHED` (HTTP 422).

One entitlement carries at most one live request. Creating a new one moves the entitlement's prior `PENDING` request to `SUPERSEDED`, and increments the entitlement's `version` by one. Requests can be listed per entitlement and filtered by `state`, and read individually with their `granted_delta_rpm`, `denial_reason` and `run_sequence`.

**The allocation run** is where requests are settled, and it is a `DevRelManager` operation scoped to one product. The run considers every `PENDING` request whose entitlement is pinned to a version of this product; if there is not at least one such request, the run is refused with `ERR_NO_PENDING_UPGRADE_REQUESTS` (HTTP 409). Only requests whose entitlement is in `entitlement_state` `ACTIVE` and whose developer sits at `GOOD_STANDING` are eligible — requests on suspended entitlements were already voided by the suspension itself, and a developer under investigation is ineligible for grants.

The queue is ordered deterministically by three keys in sequence: first by the entitlement's tier rank **descending**, so `PRIVILEGED` requests are served before `PARTNER`, `PARTNER` before `STANDARD`, and `STANDARD` before `SANDBOX`; then, within one tier, by `requested_delta_rpm` **ascending**, so the cheapest ask is filled first; and finally by `created_at` ascending as the tie-break. Each request in the queue is stamped with a 1-based `run_sequence` in that order, including requests that end up deferred, and with `decided_at` from the logical clock.

The run starts with a working figure of remaining capacity equal to the product's `available_sustained_rpm` at the moment the run begins, and walks the queue in order. For each request: if the remaining capacity is exactly 0 when this request's turn arrives, the request moves `PENDING → DEFERRED` with `denial_reason` `POOL_EXHAUSTED` and the run continues to the next one — a deferred request may be re-run later once the pool grows. Otherwise the granted amount is the smallest of three numbers: the request's `requested_delta_rpm`, the remaining capacity, and the entitlement's current headroom, being its tier ceiling less its current `sustained_rpm`. That amount is stored as `granted_delta_rpm`; the request moves `PENDING → GRANTED` when it equals `requested_delta_rpm` exactly and `PENDING → PARTIALLY_GRANTED` when it is smaller. The entitlement's `sustained_rpm` increases by the granted amount, its `burst_rpm` is then recomputed from the new `sustained_rpm` using the same tier burst factor and the same round-up rule as at provisioning, the product's `allocated_sustained_rpm` increases by the granted amount, and the remaining capacity falls by it. Because earlier grants shrink the remaining capacity, a single run legitimately produces all three outcomes across its queue.

The run reports `run_sequence_count`, the number of requests it walked; `granted_count`, `partially_granted_count` and `deferred_count`; `allocated_sustained_rpm_delta`, the total rate granted across the run; and `available_sustained_rpm_after`, the product's remaining availability once the run has finished.

A `PENDING` request can also die without a run touching it. Suspension or retirement of its entitlement, and sunset of the pinned version, all move it `PENDING → VOIDED`; when the cause was a standing cascade, `denial_reason` is recorded as `STANDING_BLOCKED`. `GRANTED`, `PARTIALLY_GRANTED`, `DEFERRED`, `VOIDED` and `SUPERSEDED` are all terminal.

### 3.7. Terms-of-Service Enforcement: Investigation, Adjudication, Appeal and Revocation

Enforcement is a two-operator discipline from end to end. A `TrustAndSafetyOfficer` may open and investigate a case but may never decide it; a `PlatformAdmin` decides but never investigates.

**Opening a case.** An officer opens a **violation case** against a developer by naming the `developer_id`, the `category` of terms-of-service clause allegedly breached — one of `RATE_ABUSE`, `SCOPE_OVERREACH`, `DATA_RETENTION` or `RESALE` — the `severity` band, one of `LOW`, `MEDIUM` or `HIGH`, and a `summary` of the allegation between 10 and 500 characters. Two optional fields narrow the allegation: `quota_assignment_id`, naming the entitlement the abuse was observed on, which is left null for cases not tied to a single entitlement; and `evidence_window_ids`, an array of usage-window identifiers cited as evidence. Each cited identifier must reference an existing usage window, failing with `ERR_USAGE_WINDOW_NOT_FOUND` (HTTP 404), and each must belong to an entitlement of the *target developer*, failing with `ERR_EVIDENCE_NOT_ATTRIBUTABLE` (HTTP 422) — the same pair of checks is applied again when evidence is supplied at investigation time. The case is created in `state` `OPENED` with `points_applied` 0, `appeal_count` 0, `opened_by_user_id` taken from `X-User-ID`, and `investigator_user_id`, `adjudicator_user_id`, `remediation_deadline`, `appeal_deadline`, `outcome`, `appeal_reason` and `decision_note` all null. Cases can be listed filtered by `developer_id`, `quota_assignment_id` and `state`.

`penalty_points` — the points an upheld outcome *would* apply — is computed at creation and recomputed at adjudication as the category's base points multiplied by the severity factor. Category base points are 10 for `RATE_ABUSE`, 15 for `SCOPE_OVERREACH`, 20 for `DATA_RETENTION` and 25 for `RESALE`. The severity factor is 1 for `LOW`, 2 for `MEDIUM` and 3 for `HIGH`. A `HIGH`-severity resale allegation therefore carries 75 points, while a `LOW`-severity rate-abuse allegation carries 10.

**Starting the investigation** requires the case to be in `OPENED`, otherwise `ERR_CASE_STATE_INVALID` (HTTP 409). The case moves `OPENED → INVESTIGATING`, records the acting officer's `X-User-ID` as `investigator_user_id` — the segregation-of-duties anchor for the rest of the case — and sets `remediation_deadline` to the logical clock advanced by the severity's remediation allowance: **30 days** for `LOW`, **14 days** for `MEDIUM` and **7 days** for `HIGH`, so the more serious the allegation, the less time the developer is given. Opening an investigation also moves the developer's `standing` from `GOOD_STANDING` to `UNDER_REVIEW`. That has an immediate, deliberately narrow consequence: the developer's `ACTIVE` entitlements keep serving traffic and keep accepting usage windows, but they become ineligible to receive upgrade grants.

**Adjudication** is a `PlatformAdmin` operation submitting `outcome` — either `UPHELD` or `DISMISSED` — together with a `decision_note`. The case must be in `INVESTIGATING` or `APPEALED`, otherwise `ERR_CASE_STATE_INVALID`, and the acting operator's `X-User-ID` must differ from the recorded `investigator_user_id`, otherwise `ERR_SEGREGATION_OF_DUTIES`. The acting operator is recorded as `adjudicator_user_id`, `outcome` stores the decision and `decision_note` the accompanying note.

Upholding a case from `INVESTIGATING` moves it `INVESTIGATING → UPHELD`, adds its `penalty_points` to the developer's `violation_points` ledger, records the same figure as the case's own `points_applied` so the contribution can later be reversed exactly, and sets `appeal_deadline` to the logical clock advanced by the **14-day** appeal window. A developer's `violation_points` is by construction the sum of `points_applied` across its cases in `state` `UPHELD` or `UPHELD_FINAL`.

If that addition brings `violation_points` to **50 or more** — the comparison is inclusive — the developer's `standing` moves `UNDER_REVIEW → RESTRICTED` and a four-part cascade fires. Every entitlement of the developer in `entitlement_state` `ACTIVE` becomes `SUSPENDED` with `suspension_reason` `STANDING_RESTRICTION`, and its `sustained_rpm` and `monthly_call_allowance` are returned to the product's allocated counters. Every `PENDING` upgrade request on those entitlements becomes `VOIDED`. A `directory_state` of `LISTED` becomes `DELISTED`. And every `SandboxLease` of the developer in `state` `ACTIVE` becomes `REVOKED` with `closed_reason` `STANDING_CASCADE`. Each of these secondary mutations refreshes the affected resource's `updated_at` and increments its `version`. If the addition leaves `violation_points` below 50, `standing` stays at `UNDER_REVIEW` — an upheld case is not by itself a restriction.

Dismissing a case from `INVESTIGATING` moves it `INVESTIGATING → DISMISSED`, a terminal state, and applies no points. The developer's `standing` returns `UNDER_REVIEW → GOOD_STANDING`, but only when no other case of that developer is in `state` `OPENED`, `INVESTIGATING` or `APPEALED`; if another live case remains, standing stays `UNDER_REVIEW`. A dismissal also compensates any points the case had previously applied: `points_applied` is subtracted back out of the developer's `violation_points` and the case's own `points_applied` is reset to 0, so the reversal can never be applied twice.

**Appealing.** The developer itself — and only the developer the case is against — may appeal an upheld case, submitting an `appeal_reason`. The case must be in `UPHELD`, otherwise `ERR_CASE_STATE_INVALID`; the logical clock must be at or before the case's `appeal_deadline`, otherwise `ERR_APPEAL_WINDOW_CLOSED` (HTTP 422); and `appeal_count` must still be 0, otherwise `ERR_APPEAL_ALREADY_FILED` (HTTP 409). On success the case moves `UPHELD → APPEALED`, records `appeal_reason` and increments `appeal_count` to 1. Exactly one appeal is permitted per case, so the cycle `UPHELD → APPEALED → UPHELD` can occur at most once.

An appealed case is adjudicated a second time. Dismissing it moves `APPEALED → DISMISSED` and compensates in full: `points_applied` is subtracted from the developer's `violation_points` and zeroed on the case. If that leaves `violation_points` below 50 and standing was `RESTRICTED`, the developer's `standing` moves `RESTRICTED → GOOD_STANDING`, and every entitlement of that developer sitting at `SUSPENDED` **whose `suspension_reason` is `STANDING_RESTRICTION`** is restored to `ACTIVE`, re-deducting its `sustained_rpm` and `monthly_call_allowance` from the product's counters. Entitlements suspended for any other reason are left alone. Sandbox leases revoked by the cascade are explicitly **not** restored. Upholding an appealed case instead moves `APPEALED → UPHELD`: the points that were already applied remain applied, nothing further is added, and `appeal_deadline` is **not** extended.

**Finalisation** is not an operator action. When a programme checkpoint finds a case in `UPHELD` whose `appeal_deadline` is strictly behind the logical clock, and which is not awaiting an appeal decision — meaning either `appeal_count` is 0, or the single filed appeal has already been adjudicated `UPHELD` — the case moves `UPHELD → UPHELD_FINAL`, which is terminal. A finalised case can no longer be appealed, and it becomes independent grounds for revoking access.

**Revocation** is the end of the road, performed by a `PlatformAdmin` with a mandatory `revocation_reason`. The developer's `standing` must be `RESTRICTED`, and one of two grounds must hold: either the developer's `violation_points` has reached **100 or more**, or the developer has at least one case in `state` `UPHELD_FINAL`. The revoking operator must not be the recorded investigator of *any* of that developer's cases, otherwise `ERR_SEGREGATION_OF_DUTIES`. On success `standing` moves `RESTRICTED → REVOKED`, which is terminal, and `revoked_at` is set from the logical clock. Four cascades fire: every entitlement of the developer that is not already `RETIRED` becomes `RETIRED` and releases its pool reservations, subject to the rule that reservations already released at suspension are not released a second time; every `PENDING` upgrade request on those entitlements becomes `VOIDED`; `directory_state` becomes `DELISTED`; every `ACTIVE` sandbox lease becomes `REVOKED` with `closed_reason` `STANDING_CASCADE`; and every access application of the developer in `state` `SUBMITTED`, `UNDER_REVIEW` or `CHANGES_REQUESTED` becomes `REJECTED` with `decision_reason` `ACCESS_REVOKED`. From that point the developer may perform no write of any kind.

### 3.8. Partner Support, Incident Communication and Service Credits

Support in this programme is contractual, and the contract is expressed in minutes. A support case comes in two kinds, and the `kind` field decides which of the other fields are required and which are forbidden. Both kinds name the affected `api_product_id`, a `severity` of `S1`, `S2`, `S3` or `S4`, and a `title` between 5 and 200 characters.

- A **`PARTNER_TICKET`** must name the reporting `developer_id`, and that developer must hold at least one `ACTIVE` entitlement on the named product. Its `started_at` is not supplied by the caller; the server sets it to the case's own `created_at`.
- A **`PLATFORM_INCIDENT`** must **not** name a `developer_id`, and it **must** supply `started_at`, the instant the incident began.

Any violation of that shape — a partner ticket with no entitled `developer_id`, or a platform incident that names a `developer_id` or omits `started_at` — is rejected with `ERR_SUPPORT_CASE_KIND_MISMATCH` (HTTP 422). A second entitlement gate applies to urgency: an `S1` or `S2` `PARTNER_TICKET` may only be opened by a developer holding an `ACTIVE` entitlement whose `tier` is `PARTNER` or `PRIVILEGED`, otherwise `ERR_SEVERITY_NOT_ENTITLED` (HTTP 422). Support cases may be opened by a `PartnerSupportAgent` or by a `Developer`, and the collection may be filtered by `developer_id`, `api_product_id`, `kind` and `state`.

Platform incidents are also coalesced, so that one outage does not become a dozen records. A new `PLATFORM_INCIDENT` for the same `api_product_id` and the same `severity` must begin at least **60 minutes** after the `resolved_at` of the most recent such incident; one opened inside that buffer is rejected with `ERR_INCIDENT_COALESCE_WINDOW` (HTTP 409), and the update belongs on the existing incident as a communication instead.

A new case starts in `state` `OPEN` with `escalation_tier` 0, `communication_count` 0, `max_communication_gap_minutes` 0, `first_response_breached` false, and `first_response_at`, `last_communication_at`, `resolved_at`, `downtime_minutes`, `credit_uplift_applied` and `resolution_note` null, `affected_assignment_count` 0 and `total_credit_calls` 0. At creation the server fixes `first_response_due_minutes` from the pair of `kind` and `severity`. For a `PARTNER_TICKET` the commitment is **30 minutes** at `S1`, **60 minutes** at `S2`, **240 minutes** at `S3` and **480 minutes** at `S4`. For a `PLATFORM_INCIDENT` the platform holds itself to a tighter standard: **15 minutes** at `S1`, **30 minutes** at `S2`, **120 minutes** at `S3` and **240 minutes** at `S4`.

**Communications** are recorded by a `PartnerSupportAgent` with a `sent_at` instant and a `body`. The case must be in `OPEN`, `RESPONDING` or `ESCALATED`, otherwise `ERR_SUPPORT_CASE_STATE_INVALID` (HTTP 409). `sent_at` must be at or after the case's `started_at`, at or after the existing `last_communication_at` where one exists, and at or before the current logical clock; any violation is `ERR_COMMUNICATION_OUT_OF_ORDER` (HTTP 422). Each communication increments `communication_count` and updates `last_communication_at`. The first one additionally sets `first_response_at` and moves the case `OPEN → RESPONDING`; subsequent ones leave the case in `RESPONDING` — the self-transition `RESPONDING → RESPONDING` — while re-evaluating the cadence figures.

`first_response_breached` becomes true when the whole minutes elapsed from `started_at` to the first communication's `sent_at` **exceed** `first_response_due_minutes`. The comparison is strict, so a first response landing exactly at the commitment does not breach.

The cadence figure walks the case as a chain of checkpoints: `started_at` first, then every communication's `sent_at` in ascending order, and — once the case is `RESOLVED` — `resolved_at` last. `max_communication_gap_minutes` is the largest whole-minute gap, floored, between consecutive checkpoints in that chain; with only a single checkpoint it is 0. Before resolution the trailing segment from the last communication onwards is not yet counted, which is why the figure can grow at resolution time. `comms_gap_breached` becomes true when `max_communication_gap_minutes` **exceeds** the severity's cadence allowance: **30 minutes** at `S1`, **60 minutes** at `S2`, **240 minutes** at `S3` and **1,440 minutes** at `S4`. This comparison too is strict — a gap exactly equal to the allowance does not breach.

**Escalation** walks the partner escalation channel one tier at a time and is capped at tier 3. The case must be in `RESPONDING` or `ESCALATED`, otherwise `ERR_SUPPORT_CASE_STATE_INVALID`, and `escalation_tier` must be below 3. An optional `escalation_note` may accompany the request. Each escalation increments `escalation_tier` by one and puts the case in `ESCALATED`, whether it came from `RESPONDING → ESCALATED` or from the self-transition `ESCALATED → ESCALATED`. For a `PARTNER_TICKET`, escalating beyond `escalation_tier` 1 requires the reporting developer to hold an `ACTIVE` entitlement of `tier` `PARTNER` or `PRIVILEGED`; without it the escalation is refused with `ERR_ESCALATION_NOT_ENTITLED` (HTTP 422).

**Resolution** submits a `resolution_note`. The case must be in `RESPONDING` or `ESCALATED`; either way the transition ends at `RESOLVED`, which is terminal, and the effects are identical for both origins. At least one communication must already exist — resolving with `communication_count` still 0 is refused with `ERR_NO_COMMUNICATION_RECORDED` (HTTP 422) — and `resolved_at`, taken from the logical clock, must be strictly after `started_at`. Resolution sets `resolved_at`, computes `downtime_minutes` as the whole minutes between `started_at` and `resolved_at`, floored, recomputes `max_communication_gap_minutes` and `comms_gap_breached` now that the trailing segment counts, and records `credit_uplift_applied` as **1.5** when `comms_gap_breached` is true at resolution and **1.0** otherwise.

For a `PARTNER_TICKET`, that is where resolution ends. For a `PLATFORM_INCIDENT`, the platform pays. Every entitlement in `entitlement_state` `ACTIVE` whose pinned version belongs to the incident's `api_product_id` is credited; entitlements in `PROVISIONED`, `SUSPENDED` or `RETIRED` are excluded. The severity credit rate is **0.10** for `S1`, **0.05** for `S2`, **0.02** for `S3` and **0.00** for `S4`. For each affected entitlement, taken in ascending `created_at` order, the raw credit is that entitlement's `monthly_call_allowance` multiplied by the severity credit rate, multiplied by `credit_uplift_applied`, multiplied by `downtime_minutes`, then divided by the **1,440 minutes in a day**. **The rounding order is pinned**: each entitlement's raw credit is rounded half up to a whole number of calls *before* anything is summed, and the sum of those per-entitlement whole numbers is `total_credit_calls`, which is never re-rounded. Summing the raw products and rounding once at the end would give a different answer and is wrong. Each rounded credit is added to its entitlement's `bonus_call_credit`, `affected_assignment_count` records how many entitlements were credited, and each credited entitlement's `throttle_state` is then re-evaluated against its enlarged effective allowance — which is how an entitlement can fall from `HARD_THROTTLED` back to `SOFT_THROTTLED` or all the way to `NORMAL` without any new traffic being ingested.

### 3.9. Ecosystem Recognition, the Public Directory and the Feedback Roadmap

The programme rewards participation, and it does so through fields on the developer record rather than through separate resources. A `DevRelManager` records ecosystem outcomes on a developer by submitting `certification_level` — `NONE`, `ASSOCIATE` or `PROFESSIONAL` — together with `certification_expires_at`, the instant the recorded certification lapses, and optionally `hackathon_awards_delta`, the number of newly recorded hackathon awards. The recorded level and expiry replace the stored `certification_level` and `certification_expires_at`; the delta is added to `hackathon_award_count`, which is left unchanged when the field is omitted. Whenever a certification level is recorded, `certification_expires_at` must be **strictly after** the current logical clock — recording a certification that has already lapsed is refused with `ERR_CERTIFICATION_EXPIRED` (HTTP 422). Every ecosystem update then recomputes the developer's `trust_score` under the onboarding-snapshot variant, so a fresh certification or a new hackathon award can immediately raise the trust multiplier the next entitlement provisioning will read.

Certification lapses silently rather than destructively. A developer whose `certification_expires_at` has fallen behind the clock **keeps** its recorded `certification_level`; what it loses is the certification's contribution to trust scoring, which the trust calculation voids whenever the expiry is null or strictly earlier than the clock. Nothing rewrites the level back to `NONE`.

**The public directory** is the visible reward, and it is the one place where all three developer dimensions must line up at once. A developer submits or resubmits its own listing by supplying a `directory_summary`, a public blurb of between 20 and 400 characters when present. Three prerequisites are checked together: `onboarding_state` must be `PRODUCTION_ACTIVE`, `standing` must be `GOOD_STANDING`, and `certification_level` must be something other than `NONE` and unexpired. A submission failing any of them is refused with `ERR_DIRECTORY_PREREQUISITES_UNMET` (HTTP 422). On success `directory_state` moves `NOT_LISTED → PENDING_REVIEW` on a first submission, or `DELISTED → PENDING_REVIEW` on a resubmission after standing has recovered; both transitions record the supplied `directory_summary`, and the two are governed by exactly the same prerequisites.

A `DevRelManager` then reviews the pending listing by submitting a `decision` of `APPROVE` or `REJECT`, with an optional `review_note`. `directory_state` must be `PENDING_REVIEW` for either decision. Approval additionally requires the developer to still be in `GOOD_STANDING` at review time, and moves `PENDING_REVIEW → LISTED`. Rejection moves `PENDING_REVIEW → NOT_LISTED` and clears `directory_summary` back to null, so a rejected developer must supply a fresh blurb to try again. Only a standing cascade can take a listing down: `LISTED → DELISTED` fires when standing moves to `RESTRICTED` or `REVOKED`, and there is no operator action that delists directly. `directory_state` has no terminal state — a delisted developer whose standing recovers can re-enter review.

**Feedback** is how developers buy influence over the roadmap, weighted by how much they have invested in the platform. A developer submits an item naming `developer_id`, the `api_product_id` the feedback targets, a `category` of `DEFECT`, `MISSING_FEATURE`, `DX_FRICTION` or `DOC_GAP`, and a `body` of between 10 and 2,000 characters. The item starts in `state` `SUBMITTED` with `author_top_tier`, `raw_impact`, `priority_score`, `triaged_by_user_id`, `decision_note` and `triaged_at` all null. Items may be listed filtered by `developer_id`, `api_product_id` and `state`.

**Triage** is a `DevRelManager` action carrying an optional `decision_note`. The item must be in `SUBMITTED`, otherwise `ERR_FEEDBACK_STATE_INVALID` (HTTP 409). Triage moves the item `SUBMITTED → TRIAGED`, records `triaged_by_user_id` from `X-User-ID` and `triaged_at` from the logical clock, resolves `author_top_tier`, and then runs the roadmap prioritisation. `author_top_tier` is the **highest tier rank among the author's entitlements in `entitlement_state` `ACTIVE` at triage time**, using the same ranking as everywhere else — `SANDBOX` 1, `STANDARD` 2, `PARTNER` 3, `PRIVILEGED` 4 — and is `NONE` when the author holds no active entitlement at all. It is frozen at triage and is not revisited when the author's entitlements later change.

The prioritisation runs in four steps, and each of the first three rounds to **2 decimal places using round half up**.

1. **Per-item raw impact**, which depends on nothing but the item and its author. The category's severity weight is **40** for `DEFECT`, **25** for `MISSING_FEATURE`, **15** for `DX_FRICTION` and **10** for `DOC_GAP`. The author's tier weight is **0.25** at `NONE`, **0.50** at `SANDBOX`, **1.00** at `STANDARD`, **1.50** at `PARTNER` and **2.00** at `PRIVILEGED`. The certification bonus, read from the author's *current* `certification_level`, is **0** at `NONE`, **2.50** at `ASSOCIATE` and **5.00** at `PROFESSIONAL`. `raw_impact` is the severity weight multiplied by the tier weight, **plus** the certification bonus — the bonus is added after the product, not multiplied into it — rounded to 2 decimal places. A `DEFECT` from a `PARTNER`-tier author holding a `PROFESSIONAL` certification therefore scores 40 × 1.50 + 5.00 = 65.00.
2. **The product demand index.** `demand_index` on the product is the sum of `raw_impact` across that product's feedback items in `state` `TRIAGED` or `ROADMAP_ACCEPTED`, rounded to 2 decimal places. Items in `SUBMITTED` are not yet scored and do not count; items in `DECLINED` have been removed from the index and do not count. The index is summed over `raw_impact` only and **never** over `priority_score`, precisely so that the index cannot feed back into itself.
3. **Re-scoring every counted item against the shared index.** The demand factor is 1 plus the lesser of `demand_index` divided by **500** and the uplift cap of **0.50**, so a product's demand can lift its items by at most 50 percent no matter how much feedback accumulates. Each counted item's `priority_score` is its own `raw_impact` multiplied by that shared factor, rounded to 2 decimal places. Because the factor is shared, triaging one item re-scores every other counted item of the same product — this is a ledger-wide recomputation, not a single-row update.
4. **Ranking.** The product's roadmap read returns the product's `TRIAGED` and `ROADMAP_ACCEPTED` items ordered by `priority_score` descending, then `raw_impact` descending, then `created_at` ascending, and is available to a `DevRelManager` or a `PlatformAdmin`. It is a computed read: it recomputes the ranking from current data rather than returning a stored ordering, and it accepts `limit` and `offset` like any other list.

**The roadmap decision** closes the item. A `DevRelManager` submits a `decision` of `ACCEPT` or `DECLINE` with an optional `decision_note`; the item must be in `TRIAGED`, otherwise `ERR_FEEDBACK_STATE_INVALID`. Accepting moves the item `TRIAGED → ROADMAP_ACCEPTED`, which leaves it inside the counted set, so the `demand_index` and every `priority_score` are unchanged. Declining moves it `TRIAGED → DECLINED` and compensates: the item's `raw_impact` is subtracted from the product's `demand_index`, the item's own `priority_score` is set back to null while its `raw_impact` is retained as the record of what was withdrawn, and every remaining counted item of the product is re-scored against the reduced index. `ROADMAP_ACCEPTED` and `DECLINED` are both terminal.

### 3.10. The Programme Checkpoint: Server-Initiated Movement in a Fixed Order

Nothing in this system moves with the passage of wall-clock time. Deadlines, expiries, sunsets and monthly resets are all evaluated only when a `PlatformAdmin` runs a **programme checkpoint**, which takes no request body and reports what it changed. The checkpoint's six steps run in exactly the order below, and the order is observable: a lease expired in step 1 is already expired when step 6 rescores, and a version sunset in step 3 has already retired its entitlements before step 5 looks for entitlements to reset.

1. **Sandbox lease expiry.** Every lease in `state` `ACTIVE` whose `expires_at` has passed becomes `EXPIRED` with `closed_reason` `CHECKPOINT_EXPIRY`. Their identifiers are returned in `expired_lease_ids`.
2. **Certification lapse.** Developers whose `certification_expires_at` has passed are noted in `expired_certification_developer_ids`. They keep their `certification_level`; what changes is that the certification stops earning trust points, which step 6 then reflects.
3. **Version sunset.** Every version in `lifecycle_state` `DEPRECATION_ANNOUNCED` whose `sunset_at` has passed becomes `SUNSET` and sets `sunset_completed_at`, and the full sunset cascade fires for each: entitlements pinned to that version in `entitlement_state` `ACTIVE` or `SUSPENDED` become `RETIRED` and release their pool reservations under the release-once rule, their `PENDING` upgrade requests become `VOIDED`, and access applications targeting that version in `SUBMITTED`, `UNDER_REVIEW` or `CHANGES_REQUESTED` become `REJECTED` with `decision_reason` `TARGET_VERSION_SUNSET`. The version identifiers are returned in `sunset_version_ids`, the retired entitlements in `retired_assignment_ids` and the voided requests in `voided_upgrade_request_ids`.
4. **Case finalisation.** Every violation case in `state` `UPHELD` whose `appeal_deadline` is strictly behind the clock, and which is not awaiting an appeal decision — `appeal_count` is 0, or the single filed appeal was already adjudicated `UPHELD` — becomes `UPHELD_FINAL`. Their identifiers are returned in `finalised_case_ids`.
5. **Monthly reset.** Every entitlement in `entitlement_state` `ACTIVE` whose `last_reset_at` is **30 or more whole days** before the logical clock is reset: `monthly_calls_consumed` and `bonus_call_credit` are zeroed, `burst_credit_balance` is restored to `burst_rpm` multiplied by 10, `last_reset_at` is set to the logical clock, and `throttle_state` is re-evaluated — which, with consumption back at zero, returns the entitlement to `NORMAL` from `SOFT_THROTTLED` or `HARD_THROTTLED`. `monthly_call_allowance` itself is not touched. Entitlements still inside the 30-day period are left completely untouched and are **not** listed. Only the entitlements actually reset appear in `reset_assignment_ids`, and entitlements in `PROVISIONED`, `SUSPENDED` or `RETIRED` are never reset.
6. **Audited rescoring.** Every developer's `audited_trust_score` is recomputed under the enforcement-audit variant, which is the only way that field ever changes. Because it runs last, it sees the lapsed certifications from step 2 and the case finalisations from step 4. Every developer that was rescored is reported in `rescored_developer_ids`.

The logical clock itself is moved by a separate `PlatformAdmin` action that submits `current_utc` and returns both the new `current_utc` and the `previous_utc` it replaced, rejecting any instant at or before the current one with `ERR_CLOCK_REWIND` (HTTP 422). Moving the clock performs no checkpoint work of its own: a clock jump past a dozen sunset dates changes nothing until a checkpoint is run. The current clock reading is also available as an open read that requires no authentication headers and is permitted to every role including `Anonymous`.
