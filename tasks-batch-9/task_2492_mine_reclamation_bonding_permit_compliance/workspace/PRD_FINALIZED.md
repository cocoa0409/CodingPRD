# Mine Reclamation Bonding API — Product Requirements Document

## 1. Introduction

A state mining regulatory program carries an obligation that outlives every company it regulates: if an operator walks away from a disturbed hillside, the public treasury must not be the party that pays to put it back. The instrument that makes this promise enforceable is the reclamation bond, and the program's credibility rests entirely on whether that bond is sized correctly, secured by an instrument the state can actually collect against, released only against inspected and completed reclamation, and forfeited promptly when an operator defaults. Today those judgements are made across disconnected spreadsheets, paper cost estimates, and a filing cabinet of surety riders — with the predictable result that bond amounts drift years behind construction-cost inflation, self-bonded operators accumulate exposure nobody has totalled, and phase releases are approved by the same specialist who accepted the bond in the first place.

This document specifies the Mine Reclamation Bonding API, the system of record for the program's permitting, bonding, inspection, enforcement, forfeiture, and legacy-reclamation-funding functions. Every business collection is served under the `/mining` umbrella prefix. The API is deliberately opinionated about arithmetic: bond amounts, instrument credit, release ceilings, civil penalties, and legacy priority scores are all computed by the server from stored inputs, never supplied by a client, so that two reviewers looking at the same permit on the same day see the same number. It is equally opinionated about sequence: a permit cannot be issued before its bond is fully posted, a release cannot be decided before its public notice period has run, and a forfeiture cannot be finalised while the operator's contest window is still open.

The reader should expect a system with an unusually dense web of consequences. Accepting one bond instrument can re-price a permit's compliance standing; approving one expansion revision can suspend a release application that was already out for public comment; finalising one forfeiture can disqualify an operator statewide and thereby strip the credited value from self-bonds posted on entirely different permits. Those propagation chains are not incidental — they are the product, and they are specified explicitly in §3.

## 2. Global Specifications & System-Wide Principles

This section defines the contracts that hold across every endpoint: authentication, response shape, pagination, precision, concurrency, and the ordering in which a malformed or impermissible request is rejected.

### 2.1. Regulatory Actors and Role-Based Access Control

Every request — without exception, including the logical-clock utility described in §2.4 — must carry two headers. `X-User-ID` identifies the acting user and `X-User-Role` declares the capacity in which they act. If either header is absent or present but empty, the request is rejected with `ERR_MISSING_AUTH_HEADERS` (HTTP 401) before anything else about the request is examined. If both headers are present but the declared role does not appear in the authorised-role list for the addressed endpoint (see the table in §4), the request is rejected with `ERR_UNAUTHORIZED` (HTTP 403).

Six roles exist, spelled exactly as follows: `Operator`, `PermitReviewer`, `BondSpecialist`, `Inspector`, `ProgramDirector`, and `PublicParticipant`.

The relationship between `X-User-ID` and stored data differs by role, and the difference is load-bearing:

- When `X-User-Role` is `Operator`, `X-User-ID` is the `id` of the acting mining company's `Operator` record. Ownership checks on any resource that references an `Operator` compare the resource's foreign-key field to `X-User-ID` — concretely, the `operator_id` of the permit the request targets, or the `operator_id` carried in the body when a permit is being created.
- When `X-User-Role` is `Inspector`, `X-User-ID` is the `id` of the acting `InspectorProfile`. Ownership checks compare `X-User-ID` to the `inspector_id` of the inspection being acted on or cited.
- When `X-User-Role` is `PermitReviewer`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity; no ownership rule reads it and the server does not compare it to any entity's `id`.
- When `X-User-Role` is `ProgramDirector`, `X-User-ID` is likewise an opaque identifier not tied to any persisted entity, and no ownership rule reads it.
- When `X-User-Role` is `PublicParticipant`, `X-User-ID` is an opaque identifier standing for a member of the public. Public comments are counted, never attributed to a stored row, so the server does not compare this id to any entity's `id`.
- When `X-User-Role` is `BondSpecialist`, `X-User-ID` is an opaque identifier not backed by any entity row — but unlike the other opaque roles it is **recorded**. Accepting a bond instrument writes the acting id into that instrument's `accepted_by_user_id`, and deciding a bond release writes it into the application's `decided_by_user_id`. The server never compares either value to an entity `id`; it compares them to each other, which is the basis of the segregation-of-duties rule in §2.10.

Role authority is exclusive rather than hierarchical. A `ProgramDirector` cannot accept a bond instrument, and a `BondSpecialist` cannot issue a permit; there is no super-role that subsumes the others. Read endpoints are shared more widely than writes, and the exact per-endpoint role lists are given in §4.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination

Endpoints that return collections accept two query parameters. `limit` caps the number of rows in the response; when omitted it defaults to 10, its minimum accepted value is 1, and its maximum accepted value is 100. `offset` is the number of rows to skip and defaults to 0; its minimum accepted value is 0. A `limit` outside the range from 1 to 100 inclusive, or a negative `offset`, is a schema violation and is rejected with `ERR_INVALID_REQUEST`.

Unless a specific endpoint says otherwise, every list endpoint returns rows sorted by `created_at` in ascending order. The single documented exception is the legacy funding queue read described in §3.8, which is returned in queue order rather than creation order.

List responses populate four fields in the `meta` object of the envelope: `limit`, `offset`, `total_count`, and `has_more`. `total_count` is the number of rows matching the filter before pagination is applied, and `has_more` is true exactly when rows matching the filter remain beyond the returned page.

### 2.4. Resource Identity, Versioning, and the Logical Clock

Every stored resource in this system — `Operator`, `MineSite`, `InspectorProfile`, `Permit`, `ReclamationCostEstimate`, `BondInstrument`, `BondReleaseApplication`, `Inspection`, `ViolationNotice`, `PermitRevision`, and `ForfeitureProceeding` — carries the same four common properties. `id` is a server-minted UUID with no type prefix; clients never supply it. `created_at` and `updated_at` are ISO 8601 UTC timestamps rendered with three fractional digits. Every other temporal value the server returns is rendered in exactly that same shape — a full ISO 8601 UTC instant with three fractional digits and a trailing `Z`, preserving whatever time-of-day the stored value carries instead of being reduced to a bare calendar date — whichever way the field happens to be named: the `*_at` stamps (`issued_at`, `accepted_at`, `approved_at`, `completed_at`, `decided_at`, `cessation_ordered_at`, `abated_at`, `vacated_at`, `finalized_at`), the inspection window bounds (`scheduled_start`, `scheduled_end`), the `*_date` fields (`proposed_start_date`, `estimate_effective_date`, `notice_start_date`, `notice_end_date`, `last_notice_end_date`), the derived deadlines (`abatement_deadline`, `contest_deadline`), and the `current_utc` echoed by the clock endpoint. A temporal field that holds no value is rendered as null. `version` is an integer that begins at 1 when the row is created and increases by exactly 1 on every mutation of that row, whether the mutation was requested directly by a client or applied by the server as a downstream consequence of some other operation. There is no entity in this system that omits `updated_at` or `version`.

The `version` counter is not a cosmetic audit field. It is the value clients echo back on the two bond-determination endpoints described in §2.9, and its increments are the mechanism by which a client learns that a permit it was reasoning about has moved underneath it. Consequently, every cascade documented in §3 states explicitly which rows it bumps.

All temporal reasoning in the system reads a **logical clock** rather than wall-clock time. Deadlines, notice windows, contest windows, escalation years, penalty history lookbacks, and every `*_at` stamp are evaluated against the clock's current value. Before any client sets it, the clock reads `2026-08-01T00:00:00Z`. Any of the six roles may advance or rewind the clock by supplying a `current_utc` instant to the test-driving clock endpoint; the response echoes the resulting `current_utc`. This capability exists so that multi-year bonding lifecycles can be exercised deterministically.

### 2.5. The Order in Which a Request Is Rejected

Many requests violate more than one rule at once. The system evaluates checks in strict ascending priority order, short-circuits at the **first** violated rule, and returns that rule's error and nothing else. Implementers must treat this ordering as part of the contract, because a request that trips two rules has exactly one correct response body. The fifteen priority bands are:

1. **Header presence.** `X-User-ID` and `X-User-Role` both present and non-empty, else `ERR_MISSING_AUTH_HEADERS`.
2. **Role authorisation.** The declared role appears in the endpoint's authorised-role list, else `ERR_UNAUTHORIZED`.
3. **Schema and constraint validity** of the request body and query string, else `ERR_INVALID_REQUEST`. This band covers required-field presence, declared types, membership of every enum value in its declared value set, and the numeric bounds stated with each field in §3 — acreages and monetary amounts strictly above zero or at or above zero as declared, the two `MineSite` scores and `completion_pct` within 0 to 100 inclusive, `duration_hours` strictly above zero, `limit` within 1 to 100 inclusive, `offset` at or above zero — plus the requirement that every ISO 8601 date or timestamp string parses.
4. **Path-id existence.** Any `{id}` in the URL must resolve to a stored row of the addressed collection, else that collection's not-found code: `ERR_OPERATOR_NOT_FOUND`, `ERR_MINE_SITE_NOT_FOUND`, `ERR_INSPECTOR_PROFILE_NOT_FOUND`, `ERR_PERMIT_NOT_FOUND`, `ERR_ESTIMATE_NOT_FOUND`, `ERR_INSTRUMENT_NOT_FOUND`, `ERR_RELEASE_APPLICATION_NOT_FOUND`, `ERR_INSPECTION_NOT_FOUND`, `ERR_VIOLATION_NOTICE_NOT_FOUND`, `ERR_REVISION_NOT_FOUND`, or `ERR_PROCEEDING_NOT_FOUND`.
5. **Body reference existence.** Every reference carried in a request body must resolve to a stored row — `permit_id`, `operator_id`, `mine_site_id`, `inspector_id`, `inspection_id`, and `replaces_instrument_id` — and an unresolvable reference returns the not-found code of the collection it points at, so an unknown `permit_id` yields `ERR_PERMIT_NOT_FOUND` and an unknown `replaces_instrument_id` yields `ERR_INSTRUMENT_NOT_FOUND`.
6. **Ownership.** Two sibling rules share this band. For a request whose `X-User-Role` is `Operator`, `X-User-ID` must equal the `operator_id` of the permit the request targets, else `ERR_NOT_PERMIT_OPERATOR`. For a request whose `X-User-Role` is `Inspector`, `X-User-ID` must equal the `inspector_id` of the inspection addressed or cited, else `ERR_NOT_ASSIGNED_INSPECTOR`. The exact operations each rule guards are enumerated in §3.
7. **Segregation of duties** on a bond-release decision, else `ERR_SEGREGATION_OF_DUTIES` (see §2.10).
8. **Stale bond determination** on the two version-bearing endpoints, else `ERR_STALE_PERMIT_VERSION` (see §2.9).
9. **Own-state admissibility.** The addressed row's own current state must admit the requested transition; terminal states admit nothing. The code names the dimension that refused: `ERR_PERMIT_STATE_INVALID`, `ERR_ESTIMATE_STATE_INVALID`, `ERR_INSTRUMENT_STATE_INVALID`, `ERR_RELEASE_STATE_INVALID`, `ERR_INSPECTION_STATE_INVALID`, `ERR_NOTICE_STATE_INVALID`, `ERR_PENALTY_STATE_INVALID`, `ERR_REVISION_STATE_INVALID`, `ERR_PROCEEDING_STATE_INVALID`, or `ERR_SITE_FUNDING_STATE_INVALID`.
10. **Cross-entity state.** The state of a *related* row must admit the operation. Five sibling rules occupy this band, producing `ERR_OPERATOR_DISQUALIFIED`, `ERR_PERMIT_STATE_INVALID`, `ERR_INSPECTION_NOT_ELIGIBLE`, or `ERR_PERMIT_HAS_OPEN_PROCEEDING` as detailed in §3.
11. **Business safety.** Standing and eligibility gates that protect the public interest, producing `ERR_UNABATED_VIOLATION`, `ERR_PERMIT_NOT_COMPLIANT`, `ERR_NO_ACCEPTED_ESTIMATE`, or `ERR_CESSATION_CRITERIA_NOT_MET`.
12. **Business timing.** Window and deadline checks against the logical clock, producing `ERR_NOTICE_PERIOD_NOT_ELAPSED`, `ERR_RESCISSION_WINDOW_CLOSED`, `ERR_CONTEST_WINDOW_CLOSED`, `ERR_CONTEST_WINDOW_OPEN`, `ERR_ESTIMATE_EXPIRED`, or `ERR_ESTIMATE_DATE_IN_FUTURE`.
13. **Business constraints** on body shape and magnitude, producing `ERR_DECISION_REASON_REQUIRED`, `ERR_COLLATERAL_DETAILS_REQUIRED`, `ERR_SURETY_RATING_INELIGIBLE`, `ERR_REVISION_FIELDS_MISMATCH`, `ERR_REVISION_ROUND_LIMIT`, `ERR_ACRES_EXCEED_DISTURBED`, or `ERR_PENALTY_AMOUNT_MISMATCH`.
14. **Business referential integrity**, producing `ERR_SUBSTITUTION_TARGET_INVALID`, `ERR_SELF_BOND_NOT_QUALIFIED`, `ERR_OBJECTIONS_UNRESOLVED`, or `ERR_FUNDING_QUEUE_ORDER`.
15. **Fiscal and resource-exclusion ceilings**, producing `ERR_BOND_BELOW_REQUIRED`, `ERR_SELF_BOND_CAPACITY_EXCEEDED`, `ERR_RELEASE_EXCEEDS_AVAILABLE`, `ERR_NOTICE_WINDOW_CONFLICT`, `ERR_INSPECTOR_DOUBLE_BOOKED`, or `ERR_LEGACY_FUND_CAP_EXCEEDED`.

Two consequences of this ladder deserve to be called out because they are easy to get backwards. First, because business safety sits at priority 11 and business timing at priority 12, a release decision on an application that is *both* still inside its public notice period *and* burdened by an unabated violation reports the violation — `ERR_UNABATED_VIOLATION` — and never the timing error. Public money is not returned while an unabated violation stands, and that judgement outranks the calendar. Second, because the stale-determination check sits at priority 8 while own-state admissibility sits at priority 9, a client that tries to accept an already-accepted cost estimate while holding a stale permit version is told about the stale version, not about the estimate's state; a client wanting to see the state error must re-read the permit's `version` first.

### 2.6. Monetary Precision and the Rounding Discipline

Every monetary and score-bearing quantity the server computes is carried to exactly **2 decimal places**, and every rounding operation uses **round half up**: a value whose third decimal digit is 5 rounds away from zero, so 54124.875 becomes 54124.88. Point arithmetic on violation notices is the sole exception — `severity_points`, `negligence_points`, `duration_points`, `history_points`, and `total_points` are integers and no rounding occurs anywhere in their derivation.

Where a formula in §3 names an intermediate rounding step, that step is normative and may not be deferred or hoisted. This matters most in the bond determination, where the loaded per-acre cost is rounded to two decimals *before* it is multiplied by the acreage basis. Multiplying first and rounding once at the end produces a different, wrong answer on many inputs. Any formula stated as a sequence of named steps should be implemented as that sequence.

### 2.7. The Bond Ledger and the Deficiency Figure

Each permit carries a small ledger of four monetary fields whose relationship is invariant. `bond_required_amount` is the state's current determination of what the permit must be secured for. `bond_held_amount` is the total credited value of the instruments currently securing the permit — specifically, the sum of `credited_amount` over every `BondInstrument` on that permit whose status is `ACCEPTED`, less `bond_released_to_date`. `bond_released_to_date` is the cumulative amount actually released back to the operator through approved phase releases, net of any rescissions. `bond_deficiency_amount` is derived, never supplied: it is the required amount minus the held amount, rounded half up to two decimals, floored at zero, so a permit holding more than it needs shows a deficiency of exactly 0.00 rather than a negative figure.

The held-bond sum is maintained from the moment the first instrument is accepted, including while the permit is still in `APPLICATION_SUBMITTED`. This is deliberate: the fiscal gate that refuses to issue a permit whose bond is short reads `bond_held_amount` at a point in the lifecycle when the permit has not yet been issued, so the figure must already be live.

### 2.8. Compliance Posture: Precedence Bands and Suspension Propagation

A permit's regulatory standing is tracked on a second, independent dimension called `compliance_posture`, whose value is always derived — never set directly by a client. Whenever a triggering operation completes, the server recomputes the posture by evaluating five bands **in order** and taking the first that matches:

1. `FORFEITURE_PENDING`, when any forfeiture proceeding exists for the permit.
2. `CESSATION`, when any violation notice on the permit has `notice_status` of `CESSATION_ORDERED`.
3. `BOND_DEFICIENT`, when `bond_deficiency_amount` is greater than zero.
4. `NOTICE_ACTIVE`, when any violation notice on the permit has `notice_status` of `ISSUED`.
5. `COMPLIANT`, otherwise.

Because the bands are ordered, a permit that is simultaneously short of bond and carrying an unabated notice reads `BOND_DEFICIENT`, not `NOTICE_ACTIVE`; and a permit under a cessation order reads `CESSATION` even if it is also short of bond. New permits begin at `COMPLIANT`, and the posture dimension has no terminal value — a permit can move out of any posture other than by way of its own `status` reaching a terminal state.

Recomputation of the posture is triggered by permit issuance or denial, bond recalculation, cessation of mining, cost-estimate acceptance, bond-instrument acceptance, bond-release decision and rescission, violation-notice creation, cessation orders, abatements, and vacaturs, approval of a permit revision, and both the creation and finalisation of a forfeiture proceeding.

One propagation rule attaches to the recomputation. Whenever the newly computed posture lands in `CESSATION`, `BOND_DEFICIENT`, or `FORFEITURE_PENDING`, every bond release application on that permit whose status is `SUBMITTED` or `PUBLIC_NOTICE` is driven to `SUSPENDED`. An application that was in `PUBLIC_NOTICE` additionally has its `notice_start_date` and `notice_end_date` cleared to null, and the permit's `last_notice_end_date` is recomputed as the greatest `notice_end_date` still held by a non-suspended application on that permit, or null when none remains. The propagation settles in a single pass, because a `SUSPENDED` application has no further downstream effect of its own. Suspended applications are never reinstated automatically: recovering one requires an explicit reinstatement, described in §3.5.

### 2.9. Guarding Bond Determinations Against Stale Reads

Two endpoints re-price a permit's bond, and both require the client to prove it is reasoning about the permit as it currently stands. Each takes `expected_permit_version` as a required, non-optional body field carrying the client's last observed `version` of the target `Permit`.

`POST /mining/reclamation-cost-estimates/{id}/accept` must carry an `expected_permit_version` equal to the current `version` of the permit named by the estimate's `permit_id`. If some other writer has advanced that permit's `version` since the client last read it, the acceptance is rejected with `ERR_STALE_PERMIT_VERSION` at HTTP 412. Nothing in the estimate state machine blocks a second acceptance on a permit — two distinct `SUBMITTED` estimates are each independently acceptable, and accepting the second legitimately supersedes the first and re-prices the bond — so the stale-version check is the only signal that tells the second reviewer the cost basis they were pricing against has already moved.

`POST /mining/permits/{id}/recalculate-bond` must likewise carry an `expected_permit_version` equal to the addressed permit's current `version`, and a mismatch is rejected with `ERR_STALE_PERMIT_VERSION` at HTTP 412. A recalculation is always permissible on an `ISSUED` or `RECLAMATION_PHASE` permit and legitimately supersedes the previous determination, so no state rule blocks a second recalculation; the version check is what stops a determination computed from an outdated disturbance report or an outdated estimate from overwriting a newer one.

No other endpoint in this system accepts a version field. Requests to endpoints outside these two must not be expected to carry one, and supplying one there has no defined meaning.

### 2.10. Segregation of Duties in Bond Administration

The program's internal control principle is that the specialist who accepted a permit's financial security may not be the person who later decides to give it back. When a bond release decision is submitted, the acting `X-User-ID` is compared against the `accepted_by_user_id` of **every** bond instrument on the application's permit whose status is `ACCEPTED`. If the acting id matches any one of them, the decision is refused with `ERR_SEGREGATION_OF_DUTIES` at HTTP 409. Completing a full post-bond-then-release lifecycle therefore requires two distinct `BondSpecialist` user identifiers. The check sits at priority 7, ahead of every state and business rule, so a specialist who is barred from deciding at all is told so rather than being walked through the substantive gates first.

### 2.11. Cascade Discipline and Reverse-Discovery Reads

No resource in this API is addressed for writing through a parent-nested path. Every business collection is a peer under `/mining`, and parent-child relationships are expressed by references carried in request bodies. A number of read endpoints do nest — for example the permits belonging to an operator, or the inspections belonging to an inspector profile — and these exist purely so a client holding a parent id can discover its children. Where a path does nest, its parameters are validated left to right: the parent id must resolve to a stored row before anything to its right is considered, so a request naming a non-existent permit reports `ERR_PERMIT_NOT_FOUND` regardless of what its query string contains.

Server-initiated transitions are first-class. Many operations in §3 mutate rows the client never named, and each such mutation independently refreshes that row's `updated_at` and increments its `version`. Where the specification says a cascade fires, the implementation must apply every link of it inside the same request, and the response returned to the client is the resource the client addressed — the cascade's other effects are observable only through subsequent reads.

## 3. Business Logic & Workflows

### 3.1. Building the Regulatory Register

Before any permit can exist, three registers must be populated, and all three are the `ProgramDirector`'s responsibility to create.

An **operator** is the regulated mining company. Registration captures the company's `legal_name` together with the four audited financial figures the self-bonding tests read: `tangible_net_worth`, `fixed_assets_in_state`, and `total_liabilities` — each of which must be at or above zero — and `net_income_prior_year`, which is the only financial figure permitted to be negative, since a loss-making year is a fact the program needs to record rather than reject. Registration also captures `elected_financial_test`, the operator's choice between `NET_WORTH_TEST` and `FIXED_ASSET_TEST`. A newly registered operator begins with `registry_status` of `ACTIVE`, `self_bond_status` of `UNTESTED`, and every derived ledger at zero: `self_bond_capacity_amount`, `self_bond_exposure_amount`, `outstanding_penalty_balance`, and `refund_due_amount` all start at 0, while `violation_points_total` and `forfeiture_count` start at 0 as integers.

Those derived ledgers are maintained continuously and are worth defining precisely, because several gates read them. `self_bond_exposure_amount` is the sum of `credited_amount` over every bond instrument whose `instrument_type` is `SELF_BOND` and whose status is `ACCEPTED`, taken across *every* permit held by the operator — self-bonding exposure is a statewide figure, not a per-permit one. `violation_points_total` is the sum of `total_points` over the operator's violation notices whose `notice_status` is either `ISSUED` or `CESSATION_ORDERED`. `outstanding_penalty_balance` is the sum of `penalty_amount` over the operator's notices whose `penalty_status` is `ASSESSED`. `forfeiture_count` is the number of forfeiture proceedings on the operator's permits that have reached `FINAL`. `refund_due_amount` accumulates the surplus returned to the operator when state-conducted reclamation costs less than the bond that was forfeited.

Financial figures go stale, so a `ProgramDirector` may replace any subset of the five financial inputs — `tangible_net_worth`, `fixed_assets_in_state`, `total_liabilities`, `net_income_prior_year`, and `elected_financial_test` — on an existing operator. Replacing them invalidates whatever the last self-bonding test concluded: `self_bond_status` resets to `UNTESTED` from either `QUALIFIED` or `FAILED`, and `self_bond_capacity_amount` resets to 0.00. A fresh test is then required. This is refused with `ERR_OPERATOR_DISQUALIFIED` when the operator's `registry_status` is `DISQUALIFIED`, because a disqualified operator's numbers no longer matter.

Running the self-bonding **financial test** is a `BondSpecialist` capability, permitted whenever `self_bond_status` is `UNTESTED`, `QUALIFIED`, or `FAILED` — the test is re-runnable — and refused with `ERR_OPERATOR_DISQUALIFIED` once the operator has been disqualified, which is the one terminal value of that dimension. The test takes no request body; everything it needs is already stored. Two conditions are common to both elected tests. The **leverage condition** holds when `tangible_net_worth` is greater than or equal to the operator's `total_liabilities` multiplied by 2.5 and then rounded half up to two decimals; note that the comparison is made against the *rounded* product, and the rounding is load-bearing at the boundary. The **profitability condition** holds when `net_income_prior_year` is strictly greater than zero. Under `NET_WORTH_TEST`, the operator passes when the leverage condition holds, the profitability condition holds, and `tangible_net_worth` is at least ten million dollars (10000000.00); on passing, `self_bond_capacity_amount` becomes `tangible_net_worth` multiplied by 0.25 and rounded half up to two decimals. Under `FIXED_ASSET_TEST`, the operator passes when the leverage condition holds, the profitability condition holds, and `fixed_assets_in_state` is at least twenty million dollars (20000000.00); on passing, `self_bond_capacity_amount` becomes `fixed_assets_in_state` multiplied by 0.10 and rounded half up to two decimals. A passing test moves `self_bond_status` to `QUALIFIED`; a failing test moves it to `FAILED` and sets `self_bond_capacity_amount` to 0.00. Both outcomes bump the operator's `version`.

A **mine site** is the physical land. Its registration captures a `name`, the `county` of record, and `total_acres`, which must be strictly greater than zero. An optional `site_class` may be supplied at creation, choosing between `ACTIVE_PERMITTED` and `ABANDONED_LEGACY`; when omitted it defaults to `ACTIVE_PERMITTED`. Everything else on a new site starts at its floor: `hazard_class` defaults to `H3_MODERATE` (the three legacy hazard bands are `H1_EXTREME`, `H2_HIGH`, and `H3_MODERATE`), `public_safety_score` and `water_quality_score` default to 0 and are each constrained to the range 0 through 100 inclusive, `acres_affected` defaults to 0 and may not be negative, `legacy_priority_score` and `awarded_funding_amount` and `unfunded_reclamation_need` all default to 0, and `funding_status` begins at `NOT_APPLICABLE`.

An **inspector profile** is the field staff record. It captures `full_name`, a `certification_level` chosen from `CERT_I`, `CERT_II`, and `CERT_III`, and a `region` field-office code. Its one derived field, `scheduled_inspection_count`, starts at 0 and always equals the number of that inspector's inspections currently in `SCHEDULED`.

Each register is readable individually and as a filtered collection. Operators may be filtered by `registry_status` and by `self_bond_status`; mine sites by `site_class`, `funding_status`, `county`, and `hazard_class`; inspector profiles by `region` and `certification_level`. An operator's permits and a mine site's permits are each discoverable through a parent-scoped read that accepts a `status` filter, and an inspector's workload is discoverable through a parent-scoped read that accepts a `status` filter as well.

### 3.2. Permit Application, Third-Party Cost Estimation, and the Bond Determination

An `Operator` opens the permitting process by filing an application. The payload names the `mine_site_id` of the land to be disturbed and the `operator_id` of the intended permit holder, and describes the plan through `mining_plan_acres` — the approved plan acreage, which must be strictly greater than zero — a `post_mining_land_use` designation chosen from `CROPLAND`, `FORESTLAND`, `RANGELAND`, `INDUSTRIAL`, `WATER_IMPOUNDMENT`, and `WILDLIFE_HABITAT`, and a `proposed_start_date` giving the intended start of disturbance as an ISO 8601 UTC instant. The ownership rule at priority 6 applies to this creation in a slightly special form: the acting `X-User-ID` must equal the `operator_id` in the body, and a mismatch is `ERR_NOT_PERMIT_OPERATOR`. An operator whose `registry_status` is `DISQUALIFIED` may not apply at all, which is `ERR_OPERATOR_DISQUALIFIED` at priority 10.

A new permit begins with `status` of `APPLICATION_SUBMITTED`, `compliance_posture` of `COMPLIANT`, and `bond_basis` of `FULL_PLAN`. Every derived monetary field — `bond_required_amount`, `bond_held_amount`, `bond_released_to_date`, `bond_deficiency_amount` — and every acreage counter — `disturbed_acres`, `reclaimed_acres_credited`, `phase1_released_acres`, `phase2_released_acres`, `phase3_released_acres` — starts at 0. The three nullable stamps `issued_at`, `denial_reason`, and `last_notice_end_date` start as null. Permits are readable individually and as a collection filterable by `operator_id`, `mine_site_id`, `status`, `compliance_posture`, and `bond_basis`.

A permit cannot be priced until a third party has priced the reclamation. The operator files a **reclamation cost estimate** whose payload names the `permit_id` it prices, identifies the firm through `estimator_firm` and `estimator_license_no`, and supplies the cost basis as `estimate_effective_date` — the ISO 8601 UTC date the pricing is effective as of, which drives inflation escalation — together with `direct_cost_per_acre`, the third-party direct reclamation cost per acre in dollars, which must be strictly greater than zero. An `estimate_effective_date` later than the logical clock's current instant is nonsense and is rejected with `ERR_ESTIMATE_DATE_IN_FUTURE`. Filing an estimate is ownership-checked at priority 6 — the acting `X-User-ID` must equal the target permit's `operator_id`, else `ERR_NOT_PERMIT_OPERATOR`. Estimates may only be filed against a permit whose `status` is `APPLICATION_SUBMITTED`, `ISSUED`, or `RECLAMATION_PHASE`, and against any other permit status the filing fails with `ERR_PERMIT_STATE_INVALID`. A filed estimate starts in `SUBMITTED` with `accepted_at` null; estimates are readable individually and as a collection filterable by `permit_id` and `status`, and the estimates for one permit are also reachable through a parent-scoped read that accepts a `status` filter.

Acceptance of an estimate is a `PermitReviewer` act and moves the estimate `SUBMITTED → ACCEPTED`, stamping `accepted_at` with the logical clock's current value. The estimate must be in `SUBMITTED`, else `ERR_ESTIMATE_STATE_INVALID`; the permit must be in `APPLICATION_SUBMITTED`, `ISSUED`, or `RECLAMATION_PHASE`, else `ERR_PERMIT_STATE_INVALID`; the `estimate_effective_date` must be no more than three years — 1095 days — before the logical clock's current instant, else `ERR_ESTIMATE_EXPIRED`; and the request must carry the `expected_permit_version` described in §2.9. Acceptance is the point at which the whole bond determination is re-run. Any *other* estimate on the same permit that was in `ACCEPTED` moves `ACCEPTED → SUPERSEDED` and has its own `version` bumped, so a permit never has two accepted estimates at once and `SUPERSEDED` is a terminal condition for an estimate. The permit's `bond_required_amount` is then recomputed under its current `bond_basis`, `bond_deficiency_amount` is recomputed from it, `compliance_posture` is recomputed, and the permit's `version` increments by 1.

The **bond determination** itself proceeds in five named steps, and the order of the roundings is normative. First, the escalation term: take the number of whole days between the accepted estimate's `estimate_effective_date` and the logical clock's current date, divide by 365, and discard any fractional part, giving a whole number of escalation years that is never below zero. Second, the loaded per-acre cost: multiply the estimate's `direct_cost_per_acre` by 1.185 — that is, the direct cost plus an indirect-cost loading of 18.5 percent — then multiply by 1.03 raised to the power of the escalation-year count, applying three percent annual construction-cost inflation for each full year elapsed, and round the result half up to two decimals. Third, the acreage basis, which depends on the permit's `bond_basis`: under `FULL_PLAN` the basis is the permit's `mining_plan_acres`; under `INCREMENTAL` the basis is `disturbed_acres` minus `reclaimed_acres_credited`, rounded half up to two decimals and floored at zero. Fourth, the subtotal: multiply the loaded per-acre cost by the acreage basis and round half up to two decimals. Fifth, the administrative fee: take 1.5 percent of the subtotal rounded half up to two decimals, raise it to 2500.00 if it falls below that floor, and cap it at 25000.00 if it rises above that ceiling. The permit's `bond_required_amount` is then the subtotal plus the administrative fee, rounded half up to two decimals, and raised to the statutory minimum bond of 10000.00 if the sum falls below it. Because the loaded per-acre cost is rounded before it is multiplied by the acreage basis, a determination that defers that rounding to the subtotal will disagree with this specification on many inputs; the rounding sequence above is the specification.

The determination is re-run on exactly three occasions: acceptance of a cost estimate, an explicit bond recalculation, and approval of an `EXPANSION` revision. Nothing else re-prices a permit — notably, reporting new disturbance figures does not.

Issuance is the `PermitReviewer`'s decision and is expressed as a `decision` of either `ISSUE` or `DENY`, with an optional `denial_reason`. The permit must be in `APPLICATION_SUBMITTED` for either branch, and any other `status` — including a permit already `ISSUED`, or one that reached the terminal `DENIED`, `TERMINATED`, or `FORFEITED` — yields `ERR_PERMIT_STATE_INVALID`. The `decision` and `denial_reason` fields are coupled: a `DENY` requires a `denial_reason` that is present and non-empty, and any decision that is not `DENY` requires that `denial_reason` be absent entirely; either violation is `ERR_DECISION_REASON_REQUIRED`. An `ISSUE` decision faces three further gates, and their relative order matters because a hopeless application can fail more than one. The operator's `registry_status` must still be `ACTIVE`, checked at priority 10 and reported as `ERR_OPERATOR_DISQUALIFIED`; an `ACCEPTED` cost estimate must exist for the permit, checked at priority 11 and reported as `ERR_NO_ACCEPTED_ESTIMATE`; and the permit's `bond_held_amount` must be at least its `bond_required_amount`, checked last at priority 15 and reported as `ERR_BOND_BELOW_REQUIRED`. An application with no accepted estimate and no bond therefore reports the missing estimate, not the missing bond.

The two branches of the decision have deliberately disjoint effects. `APPLICATION_SUBMITTED → ISSUED` sets `status` to `ISSUED`, stamps `issued_at` with the logical clock's current value, recomputes `compliance_posture`, and increments the permit's `version` by 1. `APPLICATION_SUBMITTED → DENIED` sets `status` to `DENIED`, stores the supplied `denial_reason`, and increments `version` by 1 — it performs no bond determination and leaves `issued_at` null. `DENIED` is terminal.

For day-to-day supervision, a permit exposes a computed bond summary read that returns six figures: `bond_required_amount`, `bond_held_amount`, `bond_released_to_date`, `bond_deficiency_amount`, and — evaluated for a `phase` supplied as a query parameter, defaulting to `PHASE_I` when omitted — the `retention_floor` and the `releasable_amount` that the release arithmetic in §3.5 would produce for that phase right now.

### 3.3. Posting the Bond: Instruments, Credit, and Substitution

Financial security is posted as one or more **bond instruments**, proposed by the `Operator` and accepted by a `BondSpecialist`. A proposal names the `permit_id` it secures, declares an `instrument_type` from `SURETY`, `CASH`, `COLLATERAL`, and `SELF_BOND`, and states a `face_amount` in dollars that must be strictly greater than zero. Type-conditional detail follows: a `SURETY` proposal must carry both `surety_company_name` and `surety_naic_rating` and nothing from the collateral group; a `COLLATERAL` proposal must carry both `collateral_type` and `collateral_market_value` and nothing from the surety group; and `CASH` and `SELF_BOND` proposals must carry neither group and are refused if they supply either. Any deviation from that shape is `ERR_COLLATERAL_DETAILS_REQUIRED` at priority 13. The rating scale for `surety_naic_rating` runs `A_PLUS_PLUS`, `A_PLUS`, `A`, `B_PLUS_PLUS`, `B`; the collateral kinds for `collateral_type` are `US_TREASURY`, `MUNICIPAL_BOND`, `IRREVOCABLE_LOC`, and `REAL_PROPERTY`. A proposal may optionally name `replaces_instrument_id`, identifying an instrument already on the same permit that this one is intended to substitute for; a plain addition to the bond leaves it null. Proposing an instrument is ownership-checked at priority 6 against the target permit's `operator_id`, else `ERR_NOT_PERMIT_OPERATOR`, and proposals are only accepted against a permit whose `status` is `APPLICATION_SUBMITTED`, `ISSUED`, or `RECLAMATION_PHASE`, else `ERR_PERMIT_STATE_INVALID`. A proposed instrument begins in `PROPOSED` with `credited_amount` at 0, and with `accepted_by_user_id` and `accepted_at` both null. Instruments are readable individually and as a collection filterable by `permit_id`, `replaces_instrument_id`, `status`, and `instrument_type`, and a permit's instruments are reachable through a parent-scoped read accepting a `status` filter.

Acceptance moves the instrument `PROPOSED → ACCEPTED` and is where the state decides how much the paper is actually worth. The instrument must be in `PROPOSED`, else `ERR_INSTRUMENT_STATE_INVALID`, and the permit must still be in one of the three admitting statuses, else `ERR_PERMIT_STATE_INVALID`. Four further gates then apply, in ascending priority. At priority 13, a `SURETY` instrument's `surety_naic_rating` must be one of `A_PLUS_PLUS`, `A_PLUS`, `A`, or `B_PLUS_PLUS` — the `B` rating is writable at proposal time but not acceptable, and an attempt to accept it is `ERR_SURETY_RATING_INELIGIBLE`. At priority 14, when `replaces_instrument_id` is set, the referenced instrument must belong to the same permit, must currently be in `ACCEPTED` or `SUBSTITUTION_REQUIRED`, and must not already have been superseded by another accepted substitution; a target that is on a different permit, in a terminal state, or already replaced is `ERR_SUBSTITUTION_TARGET_INVALID`. Also at priority 14, a `SELF_BOND` instrument requires the holding operator's `self_bond_status` to be exactly `QUALIFIED`, else `ERR_SELF_BOND_NOT_QUALIFIED`. Finally at priority 15, a `SELF_BOND` instrument's `face_amount` must not exceed the operator's `self_bond_capacity_amount` minus its `self_bond_exposure_amount`, else `ERR_SELF_BOND_CAPACITY_EXCEEDED`.

The credited value written into `credited_amount` at acceptance depends entirely on the instrument type, and once written it is frozen — later changes to ratings, market values, or capacity never re-price an already-accepted instrument. A `CASH` instrument credits its `face_amount` in full. A `SURETY` instrument credits its `face_amount` multiplied by the multiplier for its rating and rounded half up to two decimals, where `A_PLUS_PLUS` and `A_PLUS` both multiply by 1.00, `A` multiplies by 0.90, and `B_PLUS_PLUS` multiplies by 0.75. A `COLLATERAL` instrument applies a haircut to the **market value** and only then applies the face amount as a cap: multiply `collateral_market_value` by one minus the haircut for its `collateral_type`, round half up to two decimals, and take the lesser of that figure and `face_amount`; the haircuts are 0.00 for `US_TREASURY`, 0.05 for `MUNICIPAL_BOND`, 0.00 for `IRREVOCABLE_LOC`, and 0.30 for `REAL_PROPERTY`. A `SELF_BOND` instrument credits 0.00 whenever the operator's `self_bond_status` is anything other than `QUALIFIED`; otherwise it credits the lesser of `face_amount` and the operator's remaining self-bond headroom, that headroom being `self_bond_capacity_amount` minus `self_bond_exposure_amount`, rounded half up to two decimals and floored at zero.

Acceptance then does five further things. It stamps `accepted_by_user_id` with the acting `X-User-ID` and `accepted_at` with the logical clock's current value. If `replaces_instrument_id` was set, the referenced instrument transitions to `REPLACED` — from `ACCEPTED → REPLACED` for a live instrument or from `SUBSTITUTION_REQUIRED → REPLACED` for one the state had already flagged as needing substitution — and its `credited_amount` consequently leaves the permit's held-bond sum, with the replaced row's own `version` incremented. It recomputes the permit's `bond_held_amount`, then `bond_deficiency_amount`, then `compliance_posture`, and increments the permit's `version` by 1. When the instrument type is `SELF_BOND`, it recomputes the holding operator's `self_bond_exposure_amount`. And where the acceptance raises `bond_held_amount` to at least `bond_required_amount`, the posture recomputation moves the permit out of `BOND_DEFICIENT` — to `COMPLIANT` when no notice on the permit remains in `ISSUED` or `CESSATION_ORDERED` and no forfeiture proceeding exists, or to `NOTICE_ACTIVE` when the deficiency is cured but a notice in `ISSUED` still stands and no forfeiture proceeding exists.

An instrument's remaining states are all reached by cascade rather than by request. `ACCEPTED → RELEASED` fires when the holding permit reaches `TERMINATED` at the end of a final-phase release, `ACCEPTED → FORFEITED` fires when the holding permit reaches `FORFEITED`, and `ACCEPTED → SUBSTITUTION_REQUIRED` fires for a self-bond when its operator is disqualified by a forfeiture elsewhere in the portfolio, all as described in §3.7. `REPLACED`, `RELEASED`, and `FORFEITED` are terminal; `SUBSTITUTION_REQUIRED` is not, since it exists precisely so that a replacement instrument can be accepted against it.

### 3.4. Keeping the Determination Current: Disturbance, Recalculation, and Revisions

Ground truth changes faster than paperwork, so the `Operator` reports progress by replacing the two acreage counters `disturbed_acres` and `reclaimed_acres_credited`, either or both of which may be supplied. This report deliberately does **not** re-price the bond: the counters change, the permit's `updated_at` and `version` advance, and `bond_required_amount` stays exactly where it was until someone runs a recalculation explicitly. Reporting is ownership-checked against the permit's `operator_id` at priority 6 with `ERR_NOT_PERMIT_OPERATOR`, and is admitted only while the permit's `status` allows it, else `ERR_PERMIT_STATE_INVALID`.

A `BondSpecialist` performs the **periodic recalculation** by supplying a `basis` of either `FULL_PLAN` or `INCREMENTAL` along with the `expected_permit_version` guard of §2.9. The supplied `basis` is written to the permit's `bond_basis`, and `bond_required_amount` is then re-derived by the five-step determination of §3.2 under that basis, followed by `bond_deficiency_amount` and `compliance_posture`. Switching to `INCREMENTAL` is how a permit that has reclaimed most of its footprint stops paying for acreage it has already put back: the basis becomes the unreclaimed remainder, `disturbed_acres` minus `reclaimed_acres_credited`, rounded half up to two decimals and floored at zero — and note that when that remainder is zero, the subtotal is 0.00, the administrative fee is nonetheless floored at 2500.00, and `bond_required_amount` is then floored at the statutory minimum of 10000.00. A recalculation requires an `ACCEPTED` estimate on the permit, else `ERR_NO_ACCEPTED_ESTIMATE`, and that estimate must still be within its three-year currency, else `ERR_ESTIMATE_EXPIRED`. The permit's `status` must admit the operation, else `ERR_PERMIT_STATE_INVALID`. Where the new determination outruns the held bond, the posture recomputation drives the permit `COMPLIANT → BOND_DEFICIENT` — or `NOTICE_ACTIVE → BOND_DEFICIENT`, since `BOND_DEFICIENT` outranks `NOTICE_ACTIVE` in the band order of §2.8 — provided no notice on the permit is in `CESSATION_ORDERED` and no forfeiture proceeding exists, and the suspension propagation of §2.8 then drives the permit's open release applications to `SUSPENDED` and recomputes `last_notice_end_date`.

When active mining finishes, the `Operator` declares the transition into reclamation, moving the permit `ISSUED → RECLAMATION_PHASE`. This is admitted only from `ISSUED`, requires `disturbed_acres` to be strictly greater than zero — a permit that never broke ground has nothing to reclaim — and is ownership-checked against the permit's `operator_id`. It increments the permit's `version` by 1.

Substantive changes to the approved plan travel through a **permit revision**. The operator files one against a `permit_id`, choosing a `revision_type` of `EXPANSION`, `SEQUENCE_CHANGE`, or `PMLU_CHANGE`, and the body shape is conditional on that choice: an `EXPANSION` must carry `acreage_delta` — additional plan acreage, strictly greater than zero when present — and must not carry `new_post_mining_land_use`; a `PMLU_CHANGE` must carry `new_post_mining_land_use` and must not carry `acreage_delta`; and a `SEQUENCE_CHANGE` must carry `sequence_note`, a description of the mining-sequence change, and must carry neither of the other two. Any mismatch is `ERR_REVISION_FIELDS_MISMATCH` at priority 13. Revisions may only be filed against a permit whose `status` is `ISSUED` or `RECLAMATION_PHASE`, else `ERR_PERMIT_STATE_INVALID`, and filing is ownership-checked. A new revision starts in `SUBMITTED` with `round_count` at 1, and with `info_request_note`, `response_note`, `denial_reason`, and `decided_at` all null. Revisions are readable individually and as a collection filterable by `permit_id`, `status`, and `revision_type`, and a permit's revisions are reachable through a parent-scoped read accepting `status` and `revision_type` filters.

Review of a revision may cycle. A `PermitReviewer` who needs more material moves the revision `SUBMITTED → INFO_REQUESTED` while recording an `info_request_note`. The operator answers by moving it `INFO_REQUESTED → SUBMITTED` with a `response_note`, which increments `round_count` by 1. That cycle is bounded: a resubmission is admitted only while `round_count` is strictly below 2, so a revision that has already consumed its rounds is refused with `ERR_REVISION_ROUND_LIMIT` at priority 13. Resubmission is also ownership-checked against the permit's `operator_id`.

The reviewer's decision on a revision carries a `decision` of `APPROVE` or `DENY` and an optional `denial_reason`, governed by the same coupling rule as permit issuance — `DENY` requires a non-empty reason, a non-`DENY` decision requires its absence, and either violation is `ERR_DECISION_REASON_REQUIRED`. Both branches require the revision to be in `SUBMITTED`, else `ERR_REVISION_STATE_INVALID`; a revision sitting in `INFO_REQUESTED` cannot be decided until it is resubmitted. Both branches also require the permit's `status` to be `ISSUED` or `RECLAMATION_PHASE`, else `ERR_PERMIT_STATE_INVALID`, and an `APPROVE` additionally requires the permit's `compliance_posture` to be `COMPLIANT` or `NOTICE_ACTIVE`, else `ERR_PERMIT_NOT_COMPLIANT` at priority 11 — the state does not enlarge a permit that is already short of bond or under a cessation order.

`SUBMITTED → APPROVED` sets `status` to `APPROVED`, stamps `decided_at` with the logical clock's current value, and then applies exactly one revision-type-specific mutation to the permit. For an `EXPANSION`, the permit's `mining_plan_acres` becomes its old value plus `acreage_delta`, rounded half up to two decimals, and `bond_required_amount` is re-derived under the permit's current `bond_basis`. For a `PMLU_CHANGE`, the permit's `post_mining_land_use` is replaced by the revision's `new_post_mining_land_use`. For a `SEQUENCE_CHANGE`, no permit field changes other than `updated_at` and `version`. An `EXPANSION` approval is the system's cleanest illustration of a three-link cascade: enlarging the plan raises `bond_required_amount` (link one); because the raised requirement now exceeds `bond_held_amount`, `bond_deficiency_amount` becomes greater than zero and `compliance_posture` is recomputed to `BOND_DEFICIENT` (link two); and because the posture entered `BOND_DEFICIENT`, every bond release application on the permit whose status is `SUBMITTED` or `PUBLIC_NOTICE` is driven to `SUSPENDED`, with any notice window cleared and the permit's `last_notice_end_date` recomputed (link three). The revision's `version` and the permit's `version` are each incremented by 1. `SUBMITTED → DENIED` sets `status` to `DENIED`, stores the `denial_reason`, stamps `decided_at`, increments only the revision's `version`, and changes no field on the permit at all. Both `APPROVED` and `DENIED` are terminal for a revision.

### 3.5. Incremental Bond Release: Notice, Comment, Inspection, and Decision

Reclamation bonds are returned in slices rather than all at once, and each slice is tied to a reclamation phase. The `Operator` opens a **bond release application** by naming the `permit_id`, declaring a `phase` of `PHASE_I`, `PHASE_II`, or `PHASE_III`, and claiming `acres_requested`, which must be strictly greater than zero. Applications are only admitted against a permit whose `status` is `ISSUED` or `RECLAMATION_PHASE`, else `ERR_PERMIT_STATE_INVALID`, and the filing is ownership-checked against the permit's `operator_id`. One acreage sanity check applies at creation, at priority 13: `acres_requested` plus the acreage the permit has already had released for that same phase must not exceed the permit's `disturbed_acres`, else `ERR_ACRES_EXCEED_DISTURBED`. A new application begins in `SUBMITTED` with `approved_amount` at 0, `comment_count` and `objection_count` at 0, `objections_resolved` false, and `notice_start_date`, `notice_end_date`, `inspection_id`, `decided_by_user_id`, `approved_at`, `denial_reason`, and `rescission_reason` all null. Applications are readable individually and as a collection filterable by `permit_id`, `inspection_id`, `status`, and `phase`, and a permit's applications are reachable through a parent-scoped read accepting `status` and `phase` filters.

The application's `requested_amount` is computed by the server at creation and is a **waterfall against a retention floor**, in four named steps. First, the per-acre bond: divide the permit's `bond_required_amount` by its `disturbed_acres` and round half up to two decimals. Second, the phase-eligible amount: multiply that per-acre bond by `acres_requested` and then by the phase release percentage — 60 percent for `PHASE_I`, 25 percent for `PHASE_II`, and 15 percent for `PHASE_III` — rounding the product half up to two decimals. Third, the retention floor: take the permit's `bond_required_amount` multiplied by the phase retention rate — 40 percent for `PHASE_I`, 15 percent for `PHASE_II`, and 0 percent for `PHASE_III` — round half up to two decimals, and then raise the result to the statutory minimum bond of 10000.00 if it falls below that, which means the floor is never lower than 10000.00 even for a final-phase release whose nominal retention rate is zero. Fourth, the available headroom: subtract the retention floor from the permit's `bond_held_amount`, round half up to two decimals, and floor the result at zero. The `requested_amount` is then the lesser of the phase-eligible amount and the available headroom. The floor is a hard waterfall boundary rather than a rejection criterion: an application whose eligible amount exceeds the remaining headroom is *clipped* down to the headroom, not refused.

Publishing the **public notice** is a `BondSpecialist` act that moves the application `SUBMITTED → PUBLIC_NOTICE`. It requires the permit's `compliance_posture` to be `COMPLIANT` or `NOTICE_ACTIVE`, else `ERR_PERMIT_NOT_COMPLIANT` at priority 11. It also enforces a temporal-exclusion rule over the permit's notice windows at priority 15: the new window, running from the logical clock's current instant through thirty days later, must not begin within fifteen days of the `notice_end_date` of any *other* application on the same permit whose status is `PUBLIC_NOTICE` or `APPROVED`. The buffer is treated as a closed interval — a new window beginning exactly fifteen days after a prior window's end is permitted, while one beginning a single day earlier is refused with `ERR_NOTICE_WINDOW_CONFLICT`. On success, `notice_start_date` is set to the logical clock's current value, `notice_end_date` is set to thirty days after `notice_start_date`, the permit's `last_notice_end_date` is recomputed, and the application's `version` increments by 1.

While an application is out for notice, a `PublicParticipant` may file a comment consisting of `comment_text` and a boolean `is_objection`. Each comment increments `comment_count` by 1, and a comment whose `is_objection` is true additionally increments `objection_count` by 1. Comments are counted, not stored as attributable rows. A `BondSpecialist` disposes of objections by recording a `resolution_note`, which sets `objections_resolved` to true; this is the only way that flag ever becomes true.

The **release decision** carries a `decision` of `APPROVE` or `DENY`, a mandatory `inspection_id` citing the release inspection the decision rests on, and an optional `denial_reason` governed by the usual coupling rule. Both branches require the application to be in `PUBLIC_NOTICE`, else `ERR_RELEASE_STATE_INVALID`, and both are blocked outright for a specialist who accepted any currently-`ACCEPTED` instrument on the permit, per the segregation rule of §2.10 at priority 7. The remaining gates then run in ascending priority. At priority 10, the cited inspection must belong to the same permit as the application, must have `inspection_type` of `RELEASE`, and must be in `COMPLETED`; for an `APPROVE` decision its `result` must additionally be `PASS`. Any of those failing is `ERR_INSPECTION_NOT_ELIGIBLE`. At priority 11, no violation notice on the permit may be in `notice_status` of `ISSUED` or `CESSATION_ORDERED`, else `ERR_UNABATED_VIOLATION`. At priority 12, the logical clock's current instant must be strictly after the application's `notice_end_date`, else `ERR_NOTICE_PERIOD_NOT_ELAPSED` — and, as §2.5 stresses, an application that trips both this and the unabated-violation check reports the violation. At priority 13 the `denial_reason` coupling is checked, yielding `ERR_DECISION_REASON_REQUIRED`. At priority 14, an `APPROVE` requires either that `objection_count` be 0 or that `objections_resolved` be true, else `ERR_OBJECTIONS_UNRESOLVED`. And at priority 15, an `APPROVE` requires that `requested_amount` — frozen at creation — not exceed the permit's `bond_held_amount` minus the phase retention floor recomputed at decision time, else `ERR_RELEASE_EXCEEDS_AVAILABLE`. That last gate is the one that catches an application whose economics were valid when it was filed but have since been invalidated by a re-priced bond.

The two branches diverge sharply. `PUBLIC_NOTICE → APPROVED` sets `status` to `APPROVED`, copies `requested_amount` into `approved_amount`, stamps `approved_at` with the logical clock's current value, records the cited inspection into the application's `inspection_id`, and writes the acting `X-User-ID` into `decided_by_user_id`. It then moves money on the parent: the permit's `bond_released_to_date` becomes its old value plus the approved amount, rounded half up to two decimals; `bond_held_amount` and `bond_deficiency_amount` are recomputed; and the phase acreage counter for the application's phase — `phase1_released_acres`, `phase2_released_acres`, or `phase3_released_acres` — is incremented by `acres_requested`. Finally the terminal check described below is evaluated, and the application's `version` and the permit's `version` are each incremented by 1. `PUBLIC_NOTICE → DENIED` sets `status` to `DENIED`, stores the `denial_reason`, still records the cited inspection into `inspection_id` and the acting user into `decided_by_user_id`, and touches **no** bond ledger field on the permit — the permit's `version` does not move at all, and only the application's `version` increments. `DENIED` is terminal for an application.

The final phase can retire the permit. Immediately after an approval, the system evaluates whether the permit should move `RECLAMATION_PHASE → TERMINATED`: this fires when the permit's `status` is `RECLAMATION_PHASE`, the approved application's `phase` was `PHASE_III`, and, after the approval has been applied, the permit's `phase3_released_acres` equals its `disturbed_acres`. When it fires, every bond instrument on the permit still in `ACCEPTED` moves to `RELEASED`; the permit's `bond_released_to_date` becomes its old value plus its `bond_held_amount`, rounded half up to two decimals; `bond_held_amount` and `bond_deficiency_amount` are both set to 0.00; and the permit's `status` becomes `TERMINATED` with its `version` incremented by 1. This is a bubble-up transition — a decision on a child application drives the parent permit into a terminal state without any request naming the permit.

An application driven to `SUSPENDED` by the propagation of §2.8 is not lost, but it is not automatic to recover either. A `BondSpecialist` reinstates it, moving `SUSPENDED → SUBMITTED`, which is admitted only when the application is actually in `SUSPENDED` (else `ERR_RELEASE_STATE_INVALID`) and the permit's `compliance_posture` is back in `COMPLIANT` or `NOTICE_ACTIVE` (else `ERR_PERMIT_NOT_COMPLIANT`). Reinstatement recomputes `requested_amount` against the permit's *current* figures rather than restoring the stale figure, which is the point of the exercise, and increments the application's `version` by 1. Because reinstatement returns the application to `SUBMITTED` rather than to `PUBLIC_NOTICE`, the public notice must be published afresh, and republishing re-runs the fifteen-day window-conflict check. The full cycle an application can travel is therefore `SUBMITTED → PUBLIC_NOTICE → SUSPENDED → SUBMITTED`.

An approval can also be undone. A `ProgramDirector` may rescind an approved release by supplying a `rescission_reason`, moving the application `APPROVED → RESCINDED`. This is admitted only while the application is in `APPROVED` (else `ERR_RELEASE_STATE_INVALID`), only while the permit's `status` is `ISSUED` or `RECLAMATION_PHASE` (else `ERR_PERMIT_STATE_INVALID`), and only while the logical clock's current instant is at or before sixty days after `approved_at` — a rescission attempted after that window has closed is `ERR_RESCISSION_WINDOW_CLOSED` at priority 12. Rescission is a compensating action that restores the bond ledger to its pre-approval values: the permit's `bond_released_to_date` becomes its old value minus the application's `approved_amount`, rounded half up to two decimals; the phase acreage counter for the application's phase is decremented by `acres_requested`; the application's `approved_amount` is reset to 0.00 and its `rescission_reason` stored; and `bond_held_amount`, `bond_deficiency_amount`, and `compliance_posture` are all recomputed. The application's `version` and the permit's `version` are each incremented by 1. `RESCINDED` is terminal.

### 3.6. The Inspection Program, Violation Notices, and Civil Penalties

Field oversight begins with scheduling. A `ProgramDirector` books an **inspection** by naming the `permit_id` to be inspected and the `inspector_id` to conduct it, declaring an `inspection_type` of `ROUTINE`, `RELEASE`, `COMPLAINT`, or `ABATEMENT_FOLLOWUP`, and fixing the on-site window through `scheduled_start` — an ISO 8601 UTC instant — and `duration_hours`, a length in hours that must be strictly greater than zero. The server derives `scheduled_end` as `scheduled_start` advanced by `duration_hours`. Inspections may only be booked against a permit whose `status` is `APPLICATION_SUBMITTED`, `ISSUED`, or `RECLAMATION_PHASE`, else `ERR_PERMIT_STATE_INVALID`. An inspector's calendar is exclusive: at priority 15, the requested interval from `scheduled_start` through `scheduled_end` must not overlap the interval of any other inspection assigned to the same `inspector_id` and still in `SCHEDULED`, else `ERR_INSPECTOR_DOUBLE_BOOKED`. Abutment is explicitly allowed — one inspection ending exactly when the next begins is not an overlap. A booked inspection starts in `SCHEDULED` with `result`, `findings_note`, and `completed_at` all null, and the assigned inspector's `scheduled_inspection_count` is incremented by 1. Inspections are readable individually and as a collection filterable by `permit_id`, `inspector_id`, `status`, and `inspection_type`, and a permit's inspections are reachable through a parent-scoped read accepting `status` and `inspection_type` filters.

The assigned `Inspector` closes the loop by recording a `result` of either `PASS` or `VIOLATIONS_FOUND` together with a `findings_note`, moving the inspection `SCHEDULED → COMPLETED`. This is ownership-checked at priority 6: the acting `X-User-ID` must equal the inspection's `inspector_id`, else `ERR_NOT_ASSIGNED_INSPECTOR`. Recording stamps `completed_at` with the logical clock's current value and decrements the inspector's `scheduled_inspection_count` by 1. `COMPLETED` and `CANCELLED` are both terminal for an inspection, and a second attempt to record a result is `ERR_INSPECTION_STATE_INVALID`.

An inspection that found problems becomes a **violation notice**, issued by the same `Inspector`. The payload cites the `inspection_id` and classifies the violation through `violation_class`, chosen from `NON_COMPLIANCE`, `IMMINENT_HARM`, and `PERMIT_DEFECT`. It supplies three penalty-point components, each with its own ceiling: `severity_points` within 0 through 40 inclusive, `negligence_points` within 0 through 30 inclusive, and `duration_points` within 0 through 25 inclusive. It also supplies `abatement_days`, the number of days the operator is allowed to fix the problem, which must be at least 1. The cited inspection must be in `COMPLETED` with a `result` of `VIOLATIONS_FOUND`, else `ERR_INSPECTION_NOT_ELIGIBLE` at priority 10, and issuance is ownership-checked against the cited inspection's `inspector_id` at priority 6 with `ERR_NOT_ASSIGNED_INSPECTOR`. The notice copies `permit_id` from the cited inspection rather than accepting one from the client.

Two derived point figures are frozen at creation. `history_points` counts the operator's recent record: take every *other* violation notice whose permit belongs to the same operator, whose `notice_status` is not `VACATED`, and whose `created_at` is at or after the logical clock's current instant less 365 days; multiply that count by 2 points per prior notice; and cap the result at 10. History accrues across **all** of the operator's permits, not just the permit being cited, and a notice that has been vacated drops out of the count for any notice created after the vacatur. `total_points` is then `severity_points` plus `negligence_points` plus `duration_points` plus `history_points`, capped at 100. All of this is integer arithmetic with no rounding. The notice's `abatement_deadline` is set to its `issued_at` stamp advanced by `abatement_days`, where `issued_at` is the logical clock's current value at creation. A new notice begins with `notice_status` of `ISSUED` and `penalty_status` of `NONE`, with `good_faith_level` null, `penalty_amount` and `penalty_paid_amount` at 0, and `cessation_ordered_at`, `abated_at`, `vacated_at`, `cessation_reason`, `abatement_note`, and `vacate_reason` all null. Creation recomputes the operator's `violation_points_total` and the permit's `compliance_posture`, which for an otherwise clean permit with no bond deficiency and no forfeiture proceeding drives `COMPLIANT → NOTICE_ACTIVE`. Notices are readable individually and as a collection filterable by `permit_id`, `inspection_id`, `notice_status`, `penalty_status`, and `violation_class`, with a permit's notices also reachable through a parent-scoped read accepting `notice_status` and `penalty_status` filters.

A notice tracks two **independent** dimensions. `notice_status` is the enforcement dimension and runs `ISSUED`, `CESSATION_ORDERED`, `ABATED`, and `VACATED`, with the last two terminal. `penalty_status` is the civil-penalty dimension and runs `NONE`, `ASSESSED`, `PAID`, and `VACATED`, with the last two terminal. Their independence is deliberate: a notice whose enforcement side has already been abated can still carry an unpaid civil penalty.

An `Inspector` escalates by ordering **cessation of mining**, recording a `cessation_reason` and moving the notice `ISSUED → CESSATION_ORDERED`. At least one of three criteria must hold, checked at priority 11: the notice's `total_points` is at least 70, or the logical clock's current instant is past the notice's `abatement_deadline`, or the notice's `violation_class` is `IMMINENT_HARM`. A notice meeting none of them is refused with `ERR_CESSATION_CRITERIA_NOT_MET`. On success the notice stamps `cessation_ordered_at`, and a two-link cascade fires: the permit's `compliance_posture` is recomputed to `CESSATION`, and because the posture entered `CESSATION`, every bond release application on the permit whose status is `SUBMITTED` or `PUBLIC_NOTICE` is driven to `SUSPENDED` with its `notice_start_date` and `notice_end_date` cleared to null, after which the permit's `last_notice_end_date` is recomputed. Each affected row's `version` increments.

The `Operator` clears a notice by **abating** it, recording an `abatement_note` and moving the notice to `ABATED` from either `ISSUED` or `CESSATION_ORDERED` — both source states carry the identical effect set. Abatement is ownership-checked against the permit's `operator_id`. It stamps `abated_at`, recomputes the operator's `violation_points_total` so that this notice's points leave the running sum, and recomputes the permit's `compliance_posture`. When no notice on the permit remains in `ISSUED` or `CESSATION_ORDERED`, the permit's `bond_deficiency_amount` is 0, and no forfeiture proceeding exists, the posture returns to `COMPLIANT` — whether it was sitting in `NOTICE_ACTIVE` or in `CESSATION`. Release applications suspended earlier are **not** revived by this recovery; they still require the explicit reinstatement described in §3.5.

A `ProgramDirector` may instead **vacate** a notice, recording a `vacate_reason`. Vacatur is admitted from `ISSUED` or `CESSATION_ORDERED` — again with an identical effect set from either source — and is refused with `ERR_PENALTY_STATE_INVALID` when the notice's `penalty_status` is already `PAID`, since money the state has banked is not unwound this way. On success the notice's `notice_status` becomes `VACATED` and `vacated_at` is stamped; and if the notice's `penalty_status` was `ASSESSED`, that dimension also moves `ASSESSED → VACATED` with `penalty_amount` reset to 0.00. Both the operator's `violation_points_total` and its `outstanding_penalty_balance` are recomputed, the permit's `compliance_posture` is recomputed on the same terms as abatement, and the notice's `version` increments by 1.

**Civil penalty assessment** is a separate `ProgramDirector` act, admitted only while `penalty_status` is `NONE` (else `ERR_PENALTY_STATE_INVALID`) and only while `notice_status` is `ISSUED`, `CESSATION_ORDERED`, or `ABATED` (else `ERR_NOTICE_STATE_INVALID`) — note that an already-abated notice remains assessable, but a vacated one does not. The request supplies `good_faith_level`, chosen from `RAPID`, `PARTIAL`, and `NONE`, which is stored on the notice and drives the credit. The assessment computes `penalty_amount` in five named steps, and the two thresholds involved are keyed on *different* quantities, which is the easiest part of this system to get wrong. First, the base: multiply `total_points` by 60.00 dollars per point and round half up to two decimals. Second, the credit ceiling, which is keyed on the **base**: 1500.00 when the base is strictly above 3000.00, otherwise 750.00 when the base is strictly above 1500.00, otherwise 0.00. Third, the good-faith credit: multiply the base by the rate for the supplied `good_faith_level` — 0.30 for `RAPID`, 0.10 for `PARTIAL`, and 0.00 for `NONE` — round half up to two decimals, and take the lesser of that figure and the credit ceiling. Fourth, the subtotal: the base minus the credit, rounded half up to two decimals. Fifth, the imminent-harm surcharge, which is keyed on the **post-credit subtotal**, not on the base: for any `violation_class` other than `IMMINENT_HARM` the surcharge rate is 0.00; for `IMMINENT_HARM` it is 0.25 when the subtotal is strictly above 5000.00, otherwise 0.10 when the subtotal is strictly above 2000.00, otherwise 0.00. The surcharge is the subtotal multiplied by that rate and rounded half up to two decimals. The stored `penalty_amount` is then the subtotal plus the surcharge, rounded half up to two decimals, and raised to a minimum penalty of 750.00 if it falls below that. Assessment moves `NONE → ASSESSED`, recomputes the operator's `outstanding_penalty_balance`, and increments the notice's `version` by 1. The amount is frozen at assessment; only a vacatur zeroes it.

The `Operator` settles by paying. The request carries `amount_paid`, which must equal the notice's `penalty_amount` exactly — partial payment is not a concept this system models, and any mismatch is `ERR_PENALTY_AMOUNT_MISMATCH` at priority 13. Payment is admitted only from `ASSESSED` (else `ERR_PENALTY_STATE_INVALID`) and is ownership-checked against the permit's `operator_id`. On success the supplied figure is stored in `penalty_paid_amount`, `penalty_status` moves `ASSESSED → PAID`, the operator's `outstanding_penalty_balance` is recomputed so the notice leaves the outstanding sum, and the notice's `version` increments by 1.

### 3.7. Forfeiture, State-Conducted Reclamation, and the Four-Link Cascade

When an operator defaults, the state takes the bond and does the work itself. A `ProgramDirector` opens a **forfeiture proceeding** against a `permit_id`, recording an `initiation_reason` of `UNABATED_CESSATION`, `BOND_DEFICIENCY_UNCURED`, or `OPERATOR_DISQUALIFIED`. Only one proceeding may ever exist per permit, and a second attempt is refused with `ERR_PERMIT_HAS_OPEN_PROCEEDING` at priority 10; the permit's `status` must also admit the operation, else `ERR_PERMIT_STATE_INVALID`. A new proceeding begins in `INITIATED` with `contest_deadline` set to thirty days after its `created_at`, with `contest_note`, `finalized_at`, and `completed_at` null and `forfeited_bond_amount`, `state_reclamation_cost_estimate`, `actual_cost_incurred`, `completion_pct`, `deficiency_amount`, and `surplus_amount` all at 0. Creation immediately recomputes the permit's `compliance_posture`, which lands in `FORFEITURE_PENDING` because that is the highest band — so a permit sitting in `CESSATION` moves `CESSATION → FORFEITURE_PENDING` and one sitting in `BOND_DEFICIENT` moves `BOND_DEFICIENT → FORFEITURE_PENDING`, with identical consequences in both cases — and the suspension propagation drives the permit's `SUBMITTED` and `PUBLIC_NOTICE` release applications to `SUSPENDED`, clearing their notice windows. Proceedings are readable individually and as a collection filterable by `permit_id` and `status`, with a permit's proceedings reachable through a parent-scoped read accepting a `status` filter.

The `Operator` may **contest**, supplying a `contest_note` and moving the proceeding `INITIATED → CONTESTED`. Contesting is ownership-checked against the permit's `operator_id`, and is admitted only while the logical clock's current instant is at or before `contest_deadline`; an attempt after that instant is `ERR_CONTEST_WINDOW_CLOSED` at priority 12.

**Finalisation** is the pivot of the whole system. A `ProgramDirector` finalises by supplying the state's own `state_reclamation_cost_estimate`, and the proceeding moves to `FINAL` from either `INITIATED` or `CONTESTED` — a contest changes who has been heard, not what happens next, so the two source states carry an identical effect set. Finalisation is admitted only while the logical clock's current instant is strictly after `contest_deadline`; finalising while the window is still open is `ERR_CONTEST_WINDOW_OPEN` at priority 12, and the mirror-image of the contest rule means the exact boundary instant belongs to the operator, not the state.

At finalisation the proceeding stamps `finalized_at` with the logical clock's current value, stores the supplied `state_reclamation_cost_estimate`, and captures `forfeited_bond_amount` as the permit's `bond_held_amount` **as observed before** the permit is transitioned — the sequence matters, because the transition zeroes that figure. The settlement at this stage sets `deficiency_amount` to the `state_reclamation_cost_estimate` minus `forfeited_bond_amount`, rounded half up to two decimals and floored at zero, and sets `surplus_amount` to 0.00; no surplus is recognised until the work is actually done.

Four cascade links then fire in sequence, and every one of them must be applied inside the same request:

- **Link 1** is the proceeding's own transition to `FINAL`, with its `version` incremented by 1.
- **Link 2** transitions the permit to `FORFEITED`, from either `ISSUED → FORFEITED` or `RECLAMATION_PHASE → FORFEITED` with an identical effect set. Every bond instrument on that permit still in `ACCEPTED` moves to `FORFEITED`; the permit's `bond_held_amount` and `bond_deficiency_amount` are both set to 0.00; every inspection on that permit still in `SCHEDULED` moves to `CANCELLED`, each cancellation decrementing its inspector's `scheduled_inspection_count` by 1; the permit's `status` becomes `FORFEITED`; and the permit's `version` increments by 1. `FORFEITED` is terminal.
- **Link 3** fires because the permit became `FORFEITED`, and lands on the permit's operator. The operator's `forfeiture_count` increments by 1, its `self_bond_status` becomes `DISQUALIFIED` from whichever of `UNTESTED`, `QUALIFIED`, or `FAILED` it held — all three source states carry the identical effect set — its `registry_status` becomes `DISQUALIFIED`, its `self_bond_capacity_amount` is set to 0.00, and its `version` increments by 1. `DISQUALIFIED` is terminal on both operator dimensions: a disqualified operator can no longer apply for permits, cannot have its financials replaced, and cannot be re-tested.
- **Link 4** fires because the operator became `DISQUALIFIED`, and reaches across the operator's entire portfolio. Every bond instrument with `instrument_type` of `SELF_BOND` and status `ACCEPTED` sitting on the operator's **other** permits moves `ACCEPTED → SUBSTITUTION_REQUIRED`; each such instrument's `credited_amount` thereby leaves its permit's held-bond sum; and each of those permits recomputes `bond_deficiency_amount` and `compliance_posture`, landing in `BOND_DEFICIENT` where the resulting deficiency is greater than zero. Every instrument and permit touched has its `version` incremented. This is the mechanism by which one default anywhere in a portfolio converts every self-bond in that portfolio into a demand for real collateral.

Once a proceeding is `FINAL`, the `ProgramDirector` records progress on the state-conducted reclamation by supplying `actual_cost_incurred` and `completion_pct`, the latter constrained to the range 0 through 100 inclusive. A report with `completion_pct` below 100 simply stores the two figures and leaves the proceeding in `FINAL`, so progress can be recorded as often as needed. A report with `completion_pct` exactly 100 closes the file: the proceeding moves `FINAL → COMPLETED`, stamps `completed_at`, and the settlement is recomputed for the completion stage, where `deficiency_amount` becomes `actual_cost_incurred` minus `forfeited_bond_amount`, rounded half up to two decimals and floored at zero, and `surplus_amount` becomes `forfeited_bond_amount` minus `actual_cost_incurred`, rounded half up to two decimals and floored at zero. The two are mutually exclusive — at most one of them is non-zero — and their difference always reconciles to the actual cost less the forfeited bond.

Completion has two downstream consequences. Any `surplus_amount` is returned to the operator's books: the operator's `refund_due_amount` becomes its old value plus the surplus, rounded half up to two decimals. And where a `deficiency_amount` remains — the state spent more than it collected — the land itself is reclassified into the legacy inventory: the mine site's `site_class` becomes `ABANDONED_LEGACY`, its `funding_status` becomes `NOMINATED`, its `unfunded_reclamation_need` is set to the proceeding's `deficiency_amount`, its `acres_affected` is set to the permit's `disturbed_acres` minus its `reclaimed_acres_credited` rounded half up to two decimals, and its `legacy_priority_score` is recomputed. The proceeding's `version` increments by 1, and `COMPLETED` is terminal.

### 3.8. The Legacy Inventory, Prioritisation, and Funding Awards

Sites the state must clean up without a solvent operator behind them form the **abandoned legacy inventory**, and the program's scarce annual appropriation is rationed across them by score rather than by whoever asks first. A `ProgramDirector` nominates a site by supplying its `hazard_class`, its `public_safety_score` and `water_quality_score` — each an integer within 0 through 100 inclusive — its `acres_affected`, being the unreclaimed acreage, and its `unfunded_reclamation_need`, the reclamation cost still to be paid for. Nomination moves the site `NOT_APPLICABLE → NOMINATED`, and is admitted only when the site's `funding_status` is `NOT_APPLICABLE` and its `site_class` is already `ABANDONED_LEGACY` — set either at registration or by the forfeiture-completion cascade of §3.7. A site failing either condition is refused with `ERR_SITE_FUNDING_STATE_INVALID`. Nomination writes the supplied figures onto the site, computes `legacy_priority_score`, and increments the site's `version` by 1.

The **priority score** is a capped weighted sum computed in two named steps. First, the acreage component: multiply `acres_affected` by 0.05 points per acre, round half up to two decimals, and cap the result at 15 points — so twenty acres earn one point and any site beyond three hundred unreclaimed acres earns the same 15. Second, the score itself: add the hazard-band weight for the site's `hazard_class` — 50 for `H1_EXTREME`, 30 for `H2_HIGH`, and 15 for `H3_MODERATE` — plus `public_safety_score` multiplied by 0.30, plus `water_quality_score` multiplied by 0.20, plus the acreage component; round the sum half up to two decimals; and cap it at 100.00. A site whose raw components would exceed the cap simply reads 100.00.

The **funding queue** consists of every mine site whose `site_class` is `ABANDONED_LEGACY` and whose `funding_status` is `NOMINATED`, ordered by `legacy_priority_score` descending, then by `unfunded_reclamation_need` descending, then by `created_at` ascending. That queue is exposed as its own read, returned in queue order rather than the creation order that governs every other list endpoint, and it accepts the standard `limit` and `offset` parameters.

Awarding money is deliberately constrained to the head of that queue. A `ProgramDirector` supplies an `award_amount`, and the site moves `NOMINATED → FUNDED`. Three gates apply. The site's `funding_status` must be `NOMINATED`, else `ERR_SITE_FUNDING_STATE_INVALID`. At priority 14, the addressed site must be the current head of the funding queue as ordered above, else `ERR_FUNDING_QUEUE_ORDER` — the program cannot skip a higher-scoring site. And at priority 15, the sum of `awarded_funding_amount` across all sites plus the new `award_amount`, rounded half up to two decimals, must not exceed the annual legacy fund cap of five million dollars (5000000.00), else `ERR_LEGACY_FUND_CAP_EXCEEDED`. On success the site's `awarded_funding_amount` is set to the supplied `award_amount`, its `unfunded_reclamation_need` becomes its old value minus the award, rounded half up to two decimals and floored at zero, its `funding_status` becomes `FUNDED`, and its `version` increments by 1. `FUNDED` is terminal, which is what keeps a funded site out of the queue and lets the next site come to the head.
