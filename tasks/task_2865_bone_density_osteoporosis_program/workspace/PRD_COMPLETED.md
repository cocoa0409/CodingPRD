# Bone Density & Osteoporosis Program API — Product Requirements Document

## 1. Introduction

A bone densitometry program lives or dies on comparability. A dual-energy X-ray absorptiometry number is clinically meaningless in isolation: the question a referring clinician actually asks is whether *this* patient's bone mineral density has moved since *last* time, and that question can only be answered when the two acquisitions came off the same scanner, in the same calibration state, with a known measurement precision behind them. Today that chain of custody is maintained by hand — a technologist remembers which device the baseline was on, a physicist keeps the phantom control chart in a spreadsheet, and the least significant change threshold lives in a laminated card taped to the console. When any link breaks, the program silently reports change that is really noise, or funds a scan the payer will never reimburse.

This document specifies the API for a system that makes the whole chain explicit and machine-enforced. It covers the equipment side — device registry, daily phantom quality control with out-of-control detection, precision assessment and least-significant-change certification, and phantom cross-calibration whenever hardware or software changes underneath the program — and the patient side: clinical risk factor intake, payer frequency and lifetime-cap arbitration at order entry, slot booking against device capacity, acquisition of skeletal sites, an independent positioning quality review that can send a study back for repeat, and a diagnostic report that classifies the patient, compares against the correct prior, and derives the next screening interval. It closes the loop with treatment initiation and periodic adherence follow-up driven by a medication possession ratio computed from a refill ledger.

Two design commitments run through every section. First, **the program is auditable**: every derived number is stored on the resource that owns it, every state change names its actor, and every rejection carries a stable machine-readable identifier so that a denial can be explained to a payer months later. Second, **the program is deterministic**: time advances only when an operator moves a logical clock, and every threshold, tie-break, rounding step and evaluation order in this document is fixed rather than left to implementation taste. The system is mounted under the `/bone-density` path prefix.

## 2. Global Specifications & System-Wide Principles

### 2.1. Users, Roles and Access Control

Every request — without exception, including read-only ones and the clock-advance capability — must carry two headers: `X-User-ID`, identifying the acting user, and `X-User-Role`, naming the role that user is acting as. If either header is absent, or present but empty, or present but consisting only of whitespace, the request fails immediately with `ERR_UNAUTHENTICATED` (HTTP 401), before any path parameter is resolved and before any body is parsed. If `X-User-Role` carries a string that is not one of the six recognised role names, or names a role that the addressed operation does not admit, the request fails with `ERR_FORBIDDEN_ROLE` (HTTP 403); the two cases are indistinguishable to the client, since both return that one identifier. The role is matched by exact string equality with no trimming and no case-folding, so `programadmin` and `ProgramAdmin ` are both unrecognised roles. `X-User-ID`, once the emptiness test has passed, is taken verbatim: it is neither trimmed nor normalised before it is recorded for provenance or compared for segregation of duties or patient scope.

The six roles are `ProgramAdmin`, `Scheduler`, `Technologist`, `QualityReviewer`, `InterpretingPhysician` and `PatientPortalUser`, spelled exactly as shown.

A `ProgramAdmin` administers the program and its equipment: payer policy registration, device registry, precision certification, cross-calibration adjudication and device retirement, and shares phantom quality-control acquisition with technologists and patient registration with schedulers. A `Scheduler` runs the front office: patient registration, risk factor intake, order entry, and — exclusively — slot booking and slot cancellation. A `Technologist` acquires phantom runs and patient scans, records skeletal sites and the vertebral fracture assessment add-on, and submits or repeats acquisitions; a technologist may also sit as a positioning reviewer, but only ever for a study somebody else acquired. A `QualityReviewer` exists solely to perform that independent positioning review. An `InterpretingPhysician` runs fracture risk assessments, authors, patches, finalizes and amends diagnostic reports, initiates therapy and conducts adherence reviews, and shares order entry and risk factor intake with schedulers and refill recording with patients. A `PatientPortalUser` is the patient.

Identity semantics differ between the staff roles and the patient role, and the distinction is load-bearing. When `X-User-Role` is `ProgramAdmin`, `Scheduler`, `Technologist`, `QualityReviewer` or `InterpretingPhysician`, `X-User-ID` is an opaque operator identifier that is not tied to any persisted entity. The server records it where a workflow calls for provenance — as `performed_by_user_id` on a phantom run, `precision_technologist_user_id` on a device, `ordered_by_user_id` on an order, `technologist_user_id` on a session, `reviewer_user_id` on a positioning review, `assessed_by_user_id` on a risk assessment, `finalized_by_user_id` on a report, or `recorded_by_user_id` on a refill — and it compares that recorded value against the caller's `X-User-ID` where segregation of duties demands it, but it never resolves an opaque identifier to a row's `id`. When `X-User-Role` is `PatientPortalUser`, by contrast, `X-User-ID` is the `id` of the acting `Patient`; ownership checks on any resource that references a `Patient` compare the resource's patient foreign key to `X-User-ID`, and a mismatch is rejected with `ERR_PATIENT_SCOPE_VIOLATION` (HTTP 403) rather than with `ERR_FORBIDDEN_ROLE`. For a self-reported refill the server writes the acting patient's `id` into `recorded_by_user_id`.

Role admission is a property of the operation, not of the resource, and it is checked before existence. A role that is simply not admitted to an operation receives `ERR_FORBIDDEN_ROLE` even when the addressed resource does not exist; conversely, a `PatientPortalUser` who is admitted to an operation but addresses another patient's data receives the scope violation, not the role error. A `PatientPortalUser` has no visibility at all into densitometers, phantom quality-control runs, calibration events, appointments, sessions, site measurements, positioning reviews or fracture risk assessments, and attempting any of those reads yields `ERR_FORBIDDEN_ROLE`.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_` followed by exactly twenty characters drawn from the uppercase letters `A`–`Z` and the digits `0`–`9`, chosen independently per request.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with exactly three fractional digits. It is read from the logical clock of §2.4 rather than from wall-clock time, so two requests issued without an intervening clock-set carry the identical `api_request_timestamp`.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints and for those endpoints only; on every other 2xx response `meta` carries exactly `api_request_id` and `api_request_timestamp` and nothing else. The body always has exactly the three top-level keys `meta`, `response_type` and `data`, serialised in that order, and this includes the HTTP 204 clock response, which carries `response_type` `"object"` and an empty object in `data`.

#### Standard Error Response Format

All error API responses (any non-2xx status code, including the 5xx fallback) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination, Ordering and List Filters

Every collection endpoint is paginated through two optional query parameters. `limit` controls page size: it defaults to 10 when omitted, accepts a minimum of 1 and a maximum of 100, and a value outside that inclusive range is a malformed request. `offset` controls the starting position, defaults to 0, and has a minimum of 0 with no upper bound. Either parameter may be supplied as an empty string, which is treated exactly as if it had been omitted and yields the default. A value that is not an optionally signed run of decimal digits — text, a fraction, a bare sign — and a value that parses but falls outside the permitted range both fail with `ERR_INVALID_REQUEST` (422); the same code and status answer any boolean query parameter, such as `include_superseded`, whose value is neither an accepted true spelling (`true`, `1`, `yes`) nor an accepted false spelling (`false`, `0`, `no`), matched case-insensitively. An `offset` beyond the end of the filtered set is legal and returns an empty `data` array. Both values are echoed back in `meta` alongside `total_count`, the number of rows the filter matched before pagination was applied, and `has_more`, which is true exactly when rows remain beyond the current page.

Unless a collection declares otherwise below, list results are ordered by `created_at` ascending. Because the logical clock advances only when a caller moves it, `created_at` ties are routine rather than exotic, and the tie-break is not uniform: the device inventory, the patient roster and the policy catalogue break the tie on the row `id` ascending, whereas the order worklist, the session worklist, the report list and the plan list break it on the server's internal creation sequence — the order in which the rows were inserted, which is monotonic per process and is never exposed as a response field. Every collection that declares its own order below breaks any tie left over after its declared keys on that same internal creation sequence, oriented the same way as the declared order, so a newest-first chart is also newest-inserted first among rows sharing every declared key. The collections that declare their own order are: the phantom quality-control chart, ordered by `performed_at_utc` descending and then `created_at` descending, because a control chart is read newest-first; a device's calibration history, ordered by `created_at` descending; a patient's risk factor history, ordered by `recorded_at_utc` descending and then `created_at` descending; the device schedule, ordered by `start_utc` ascending and then `created_at` ascending; a session's skeletal site results, ordered by `created_at` ascending; a session's positioning reviews, ordered by `reviewed_at_utc` ascending and then `created_at` ascending; the fracture risk assessment history, ordered by `assessed_at_utc` descending and then `created_at` descending; and a plan's refill ledger, ordered by `dispensed_date` ascending and then `created_at` ascending.

Collections also accept domain filters, all optional and all combinable with pagination. The device inventory filters on `status` and `site_code`. The quality-control chart filters on `densitometer_id`, `calibration_event_id`, `purpose` and `result`, which is also how a caller reverses the device and calibration-event relationships. A device's calibration history filters on `status`. The patient roster filters on `primary_payer_policy_id`, `baseline_report_id`, `last_finalized_report_id` and `mrn`. A patient's risk factor history filters on `status`. The policy catalogue filters on `payer_code`. The order worklist filters on `patient_id`, `required_densitometer_id`, `status` and `indication`. The device schedule filters on `scan_order_id`, `densitometer_id`, `status`, and on the half-open instant window `from_utc` and `to_utc`, both of which are compared against the appointment's `start_utc` alone — `from_utc` inclusive, `to_utc` exclusive — so a slot whose interval overlaps the window but which started before it is not returned. The session worklist filters on `scan_appointment_id`, `prior_session_id`, `densitometer_id`, `patient_id`, `acquisition_status` and `review_status`. A session's site results filter on `site_code` and on the boolean `include_superseded`, which defaults to false — superseded rows are hidden from the list unless the caller explicitly asks for them. The assessment history filters on `patient_id`, `risk_factor_profile_id`, `scan_session_id` and `variant`. The report list filters on `scan_session_id`, `frax_assessment_id`, `amends_report_id` and `status`. The plan list filters on `patient_id`, `initiating_report_id` and `status`. A plan's refill ledger filters on `source`. Every one of these filters other than the two instant-window bounds and the boolean `include_superseded` is matched by exact string equality against the stored field value, so a filter value outside a field's enumerated set, or one differing only in letter case, is not a malformed request: it simply matches nothing and the endpoint answers HTTP 200 with an empty `data` array and `total_count` 0. A filter parameter that is absent, or present with an empty string, is ignored rather than treated as a request for rows whose field is null. The two exceptions are held to a stricter standard because they are parsed rather than compared: a non-empty `from_utc` or `to_utc` that is not a valid instant under §2.4 fails with `ERR_INVALID_REQUEST` (422), and so does a malformed `include_superseded`. Filter values are never checked for existence — a `patient_id` filter naming no patient is not a 404, it simply matches nothing.

### 2.4. Resource Identity, the Logical Clock and Record Versioning

Every resource carries an `id` that is a server-minted random (version 4) UUID with no type prefix, rendered in the canonical lower-case hyphenated 8-4-4-4-12 form, generated by the server and never accepted from a client; because it is random it carries no creation order. Identity is identity only: apart from the presentational tie-break §2.3 assigns to three of the top-level collections, no business decision anywhere in this specification reads an `id` as an ordering key or a tie-break. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with exactly three fractional digits, stamped from the logical clock at the moment of creation, and used as a stable secondary sort key wherever rows must be totally ordered.

Most resources additionally carry `updated_at`, an ISO 8601 UTC timestamp with the same format that is refreshed on every mutation, and `version`, an integer that begins at 1 on creation and increments by exactly one on every mutation of that resource — including mutations caused indirectly by a cascade from another resource. Five resource types are exceptions, because they are append-only records rather than mutable state: `PayerPolicy`, `QcRun`, `SiteMeasurement`, `PositioningReview` and `AdherenceRefill` carry, out of these four audit fields, only `id` and `created_at`. For those five, `updated_at` and `version` are absent from the response entirely — not null, not zero, absent. A payer policy is immutable once registered; a phantom run, a site measurement, a positioning review and a refill row are historical facts that are recorded and never edited afterwards. (A site measurement can be marked `superseded`, which is the one bookkeeping flag the system flips on it; that flip does not introduce `updated_at` or `version` onto the resource.)

All time in this system is logical. A fresh server starts its clock at `2026-08-01T00:00:00Z` and the clock never advances on its own; it moves only when a caller of any role invokes the clock-setting capability with a `to_iso8601` instant, which returns HTTP 204 with an empty data payload. The clock is set, not advanced: any well-formed instant is accepted, including one earlier than or equal to the clock's current value, and no monotonicity is checked or enforced. Only the parse and the six role names gate that call; there is no other precondition on it. Every `created_at`, every `api_request_timestamp`, every field whose name ends in `_at_utc`, every age computation, every date comparison and every interval arithmetic step reads that clock.

Instants and dates are read and written in a fixed way. An inbound instant — `to_iso8601`, `start_utc`, `end_utc`, the `from_utc`/`to_utc` query bounds — is accepted in a deliberately tolerant subset of ISO 8601: `YYYY-MM-DD`, then either the letter `T` (in either case) or a single space, then `HH:MM`, with the seconds `:SS` optional, with a fractional part of one to nine digits optional after the seconds, and with an optional zone suffix that may be `Z` (in either case) or a numeric `±HH:MM` or `±HHMM` offset. Surrounding whitespace is trimmed. An instant with no zone suffix at all is read as UTC rather than rejected; an instant with a numeric offset is normalised to UTC before anything else looks at it, so `2026-09-01T12:00:00+02:00` and `2026-09-01T10:00:00Z` are the same instant to every subsequent rule. Anything outside that grammar, and any value inside it that is not a real calendar moment such as month 13 or 30 February, is `ERR_INVALID_REQUEST` (422). An inbound date field is accepted, likewise after trimming, only as exactly `YYYY-MM-DD` with four-digit year and zero-padded two-digit month and day and a real calendar day — no time part, no zone, and no abbreviated forms such as `2026-9-1`. On the way out, every instant is rendered with exactly three fractional digits and a literal `Z`, and precision finer than a millisecond is **truncated, not rounded**, so a clock set to `2026-09-01T10:00:00.987654Z` reports `2026-09-01T10:00:00.987Z`; every date is rendered as bare `YYYY-MM-DD`. Age is always **completed whole years** between a birth date and the clock's calendar date, never a fractional or rounded-up value. Where a date is advanced by a whole number of calendar months, the day of the month is preserved and clamped to the last day of the target month when the target month is shorter — advancing 31 January by one month yields 28 February in a common year.

### 2.5. Densitometric Precision and Rounding Discipline

Bone densitometry is an arithmetic discipline where the third decimal place decides a diagnosis, so this specification fixes not just how many decimals each quantity carries but *when* the rounding happens. Every rounding operation in this document is **round half up** on the magnitude — a value exactly at the midpoint rounds away from zero, so 0.12345 at four places becomes 0.1235 and −0.12345 becomes −0.1235.

Two mechanical consequences hold everywhere. First, on the way in, wherever this document fixes the decimal width of a client-supplied quantity — including the places where §3 words it as "with exactly four decimal places" — that width is an **upper bound**, not a required width: a literal with fewer decimals is accepted as written and a literal with more decimals than the declared width is rejected with `ERR_INVALID_REQUEST` (422) rather than being silently rounded down to fit. Trailing zeros in the literal count toward the width, so `0.10000` is five places and fails a four-place field. Second, on the way out, a rounded quantity is serialised as a bare JSON number at exactly the scale this section assigns it, with trailing zeros preserved and never in exponent notation: a device least significant change of three hundredths appears as `0.0300` and not as `0.03`, a T-score of minus two appears as `-2.0` and not as `-2`, and a very small factor appears as `0.0001` and not as `1e-4`. Quantities this section calls whole integers are serialised as integers with no decimal point at all. A quantity the client supplied that the server merely stores without a rounding step of its own is echoed back at the scale of the client's own literal — `1.20` in, `1.20` out, `1.2` in, `1.2` out — because no rounding rule intervened to fix its scale. Quantities that are not yet determined are serialised as JSON `null`, never as `0` and never as an empty string.

Bone mineral density quantities and their derived deviations carry **four decimal places**: phantom deviation in absolute units, device least significant change, phantom means, the proposed and applied cross-calibration factors, the cross-calibration-adjusted prior density, and the absolute density change on a report. One value escapes that width by construction: the unity factor a device is *given* rather than computed. A newly registered densitometer carries `cross_cal_factor` as the exact literal `1.0`, an approved within-tolerance event resets it to that same `1.0`, and a session snapshotting either of those carries `applied_cross_cal_factor` `1.0` as well — only a factor a calibration event actually derived from its two phantom means is four-place, so an event's `proposed_cross_cal_factor` is always four-place (`1.0000` in the within-tolerance case) while the device field it feeds may read `1.0`. Phantom deviation expressed in control-limit units carries **three decimal places**, as does a plan's medication possession ratio. Percentages carry **two decimal places** — the cross-calibration percent difference and the report's percentage density change — as do body mass index, every fracture-risk points term and the raw risk score. T-scores and Z-scores carry **exactly one decimal place**, as do height loss in centimetres and the two ten-year fracture probabilities. Interval months, degrees of freedom, defect severity, day counts, vertebral counts, grades and every conserved counter are whole integers with no rounding at all.

Three ordering rules matter more than the digit counts themselves, and they are restated where they apply. First, **classification always reads the rounded value, never the unrounded quotient**: a raw T-score of −2.45 becomes −2.5 and therefore does classify as osteoporosis, while a raw −2.0166 becomes −2.0 and does not. Second, **intermediate quantities are rounded before they are combined** wherever this document says so — the two phantom means are rounded to four places before a percent difference is taken from them, the cross-calibration-adjusted prior density is rounded to four places before it is differenced, and every fracture-risk points term is rounded to two places before the terms are summed. Third, and in deliberate contrast, **a percentage change is derived in one step from its two four-decimal inputs**, not from an already-rounded difference.

### 2.6. Optimistic Concurrency on Patients and Densitometers

Two write operations in the program supersede a record that other decisions already depend on, and both are therefore guarded by optimistic concurrency control. In each case the guard is a mandatory body field — not an optional one, and not a header — carrying the `version` the client last observed on the *parent* resource. When the supplied value does not equal the parent's current `version`, the write is refused and nothing is persisted.

Recording a new clinical risk factor profile at `POST /bone-density/patients/{id}/risk-factor-profiles` requires `expected_patient_version` matching the addressed `Patient`'s current `version`. If any writer has advanced that patient's version since the client last read it, the request is rejected with `ERR_STALE_PATIENT_VERSION` (HTTP 412). The reason is that a new profile legitimately supersedes the incumbent `ACTIVE` profile: a writer holding a stale view of the patient would silently discard risk factors another writer has already recorded, and would silently change the inputs of any fracture risk assessment keyed on the `ACTIVE` profile.

Accepting a precision assessment at `POST /bone-density/densitometers/{id}/precision-assessment` requires `expected_densitometer_version` matching the addressed `Densitometer`'s current `version`. A mismatch is rejected with `ERR_STALE_DENSITOMETER_VERSION` (HTTP 412). Here the stake is the least significant change: a new assessment overwrites the device's `rms_sd_g_cm2` and `lsc_g_cm2`, and a writer holding a stale view would overwrite a least-significant-change value that has already moved, silently changing the threshold every subsequently created acquisition snapshots.

No other endpoint accepts a version field of any kind. Where this document does not name `expected_patient_version` or `expected_densitometer_version`, the request body has no version input and no version check is performed.

### 2.7. The Rejection Ladder — the Order in Which a Request Is Refused

When a single request violates several rules at once, exactly one error is returned, and which one is fully determined: the system evaluates checks in the fixed order below and returns the first failure. Priority is a global property of the check, not of the endpoint, so a check that appears earlier in this ladder always masks a later one on the same request. The ladder is stated here once; the sections that follow describe what each check means in its business context rather than repeating the ordering.

**Authentication, role and shape (1–3).** (1) Missing or empty `X-User-ID` or `X-User-Role` on any endpoint — `ERR_UNAUTHENTICATED`, 401. (2) An unrecognised role, or a role not admitted to the addressed operation, on any endpoint — `ERR_FORBIDDEN_ROLE`, 403. (3) On any write endpoint: a required body field absent, a field of the wrong JSON type, a string outside its declared length bounds, an enum value outside its declared set, a numeric value outside its declared range or carrying more decimal places than its declared width, an array field that is not a JSON array or that breaks the endpoint's declared emptiness, membership, range or distinctness rule for its entries, or a date or instant string that is not valid ISO-8601 — `ERR_INVALID_REQUEST`, 422. Four conventions make this check precise. A request body that is absent or entirely whitespace is read as the empty JSON object `{}`, so such a request fails only if the endpoint declares a required field. On an endpoint that parses its body, a body that is not parseable JSON, a body whose top-level JSON value is not an object, and a request whose media type the server will not parse all fail with this same `ERR_INVALID_REQUEST` and 422 — never 400 and never 415. The seven endpoints §4 documents as taking no request body never parse one at all, so they accept and ignore anything sent, including a syntactically invalid body, and this rung cannot fire on them. An explicit JSON `null` is treated exactly as an absent field: `null` in a required field is the "required field absent" failure, and `null` in an optional field takes that field's documented default rather than storing null. And a field the endpoint does not declare is silently ignored, never rejected — there is no unknown-field error anywhere in this API, so a client that misspells an optional field gets the default for the field it meant, not a 422. Within one endpoint the declared fields are validated in the order the endpoint lists them in §4, and the first one that fails is the one reported. Boolean and integer query parameters are held to the same code and status, as described in §2.3.

**Existence of addressed resources (4–15), evaluated left to right along the path.** (4) No densitometer with that id, on every endpoint whose path contains a densitometer id — `ERR_DENSITOMETER_NOT_FOUND`, 404. (5) No phantom run with that id, on `GET /bone-density/qc-runs/{id}` — `ERR_QC_RUN_NOT_FOUND`, 404. (6) No calibration event with that id, on `GET /bone-density/calibration-events/{id}`, `POST /bone-density/calibration-events/{id}/close` and `POST /bone-density/calibration-events/{id}/adjudicate` — `ERR_CALIBRATION_EVENT_NOT_FOUND`, 404. (7) No patient with that id, on every endpoint whose path contains a patient id — `ERR_PATIENT_NOT_FOUND`, 404. (8) No order with that id, on `GET /bone-density/scan-orders/{id}` — `ERR_SCAN_ORDER_NOT_FOUND`, 404. (9) No appointment with that id, on every endpoint whose path contains a scan appointment id — `ERR_SCAN_APPOINTMENT_NOT_FOUND`, 404. (10) No session with that id, on every endpoint whose path contains a scan session id — `ERR_SCAN_SESSION_NOT_FOUND`, 404. (11) No assessment with that id, on `GET /bone-density/frax-assessments/{id}` — `ERR_FRAX_ASSESSMENT_NOT_FOUND`, 404. (12) No report with that id, on every endpoint whose path contains a diagnostic report id — `ERR_DIAGNOSTIC_REPORT_NOT_FOUND`, 404. (13) No plan with that id, on every endpoint whose path contains a treatment plan id — `ERR_TREATMENT_PLAN_NOT_FOUND`, 404. (14) `primary_payer_policy_id` not referencing an existing policy, on `POST /bone-density/patients` — `ERR_PAYER_POLICY_NOT_FOUND`, 404. (15) `risk_factor_profile_id` not referencing an existing profile, on `POST /bone-density/frax-assessments` — `ERR_RISK_FACTOR_PROFILE_NOT_FOUND`, 404.

**Existence of body foreign keys (16).** After every path parameter has resolved, body foreign keys are resolved in the order the endpoint declares its input fields, and a miss returns the same per-entity not-found code declared at priorities 4 through 15. This applies to `POST /bone-density/scan-orders`, `POST /bone-density/scan-appointments`, `POST /bone-density/frax-assessments`, `POST /bone-density/diagnostic-reports`, `PATCH /bone-density/diagnostic-reports/{id}`, `POST /bone-density/treatment-plans` and `POST /bone-density/densitometers/{id}/qc-runs`, and covers `patient_id`, `scan_order_id`, `densitometer_id`, `scan_session_id`, `frax_assessment_id`, `initiating_report_id` and `calibration_event_id`. A dangling `scan_session_id` in a body therefore yields `ERR_SCAN_SESSION_NOT_FOUND` (404), a dangling `initiating_report_id` yields `ERR_DIAGNOSTIC_REPORT_NOT_FOUND`, and so on. One endpoint departs from declaration order: on `POST /bone-density/frax-assessments` the `risk_factor_profile_id` is resolved **before** the `patient_id`, so a request naming neither an existing profile nor an existing patient reports `ERR_RISK_FACTOR_PROFILE_NOT_FOUND` rather than `ERR_PATIENT_NOT_FOUND`, and the optional `scan_session_id` is resolved after both.

**Patient scope (17).** A `PatientPortalUser` whose `X-User-ID` is not the owning patient's `id` is rejected with `ERR_PATIENT_SCOPE_VIOLATION` (403) on every singular resource it is admitted to and on its one write: `GET /bone-density/patients/{id}`, `GET /bone-density/patients/{id}/risk-factor-profiles`, `GET /bone-density/scan-orders/{id}`, `GET /bone-density/diagnostic-reports/{id}`, `GET /bone-density/treatment-plans/{id}`, `GET /bone-density/treatment-plans/{id}/adherence-refills` and `POST /bone-density/treatment-plans/{id}/adherence-refills`. For a report the owning patient is the one on the report's session, reached through `scan_session_id`; for a refill or a plan it is the plan's `patient_id`.

Collection reads work by narrowing rather than by refusal, which is the deliberate exception to the rung above. ### 2.8. Path Hierarchy and Nested Resource Resolution

Several resources are addressed through their parent. A phantom run and a calibration event are created beneath a densitometer; a risk factor profile beneath a patient; a session beneath an appointment; site measurements, the vertebral fracture assessment add-on, positioning reviews, submission and repeat beneath a session; refills and adherence reviews beneath a treatment plan. In every such case the path segments are validated **strictly left to right**, and the leftmost failure is what the caller sees. A request naming a nonexistent densitometer and a nonexistent calibration event reports the densitometer as missing; a request naming a real densitometer but a nonexistent event reports the event.

Parent-derived foreign keys are taken from the path and never from the body. A phantom run's `densitometer_id`, a calibration event's `densitometer_id`, a risk factor profile's `patient_id`, a session's `scan_appointment_id`, a site measurement's `scan_session_id`, a positioning review's `scan_session_id` and a refill's `treatment_plan_id` are all read from the URL; if a client also supplies one of them in the body it is ignored rather than honoured. Foreign keys that identify a *sibling* rather than a parent do travel in the body, and are resolved after every path segment has resolved, in the order the operation declares its inputs.

Nested list reads are scoped to their parent and never leak across it: a device's calibration history contains only that device's events, a patient's risk factor history only that patient's profiles, a session's site measurements only that session's rows.

### 2.9. Conserved Counters, Cascades and Compensating Actions

Two counters on the `Patient` record are **conserved quantities**, meaning the system must be able to prove them from the rows they summarise at any instant, not merely increment them optimistically. `open_scheduled_order_count` must always equal the number of that patient's orders whose `status` is `SCHEDULED`. `lifetime_screening_scan_count` must always equal the number of `FINALIZED` reports whose session belongs to that patient. Every operation that could disturb either identity carries an explicit compensating step, and those steps are spelled out where the workflows are described: booking a slot increments the open-order counter and cancelling that slot decrements it, so book-then-cancel returns the counter to its pre-booking value; finalizing a report increments the lifetime tally and amending that report decrements it, so finalize-then-amend leaves the tally exactly as it was before the finalize, and finalizing the successor report restores it.

Three cascades in this program touch more than one aggregate, and each is referred to by name throughout §3 so that its links can be traced. **Cascade A** begins when a report is finalized and propagates through the patient's screening counters into the re-evaluation and possible denial of that patient's open orders and the cancellation of their booked slots. **Cascade B** begins when a phantom quality-control run drives a device onto hold and propagates into the cancellation of imminent slots on that device and the reversion of the orders behind them. **Cascade C** begins when a cross-calibration event is approved and propagates into the device's calibration generation and correction factor, and from there into how every later acquisition scores its prior. Each cascade link is a genuine mutation of the affected resource: it refreshes that resource's `updated_at` and increments its `version` exactly as a direct write would, and cascade-driven mutations of resources that carry neither field simply write the field values.

Cascade ordering is deterministic wherever more than one row is affected. Orders re-evaluated by cascade A are processed in `created_at` ascending order, with the server's internal creation sequence ascending as the final tie-break. Slots cancelled by cascade B are processed in `start_utc` ascending order with `created_at` ascending as the tie-break, and again the internal creation sequence ascending behind that. Wherever a device's day of appointments changes — a booking, a cancellation, a system cancellation — the `slot_index` of every remaining non-cancelled slot on that device and that UTC calendar date is recomputed, so inserting a slot earlier in the day shifts the later ones up and removing one shifts them down; the numbering walks that day's live slots in `start_utc` ascending, then `created_at` ascending, then internal creation sequence ascending order and hands out 1, 2, 3 positionally. Renumbering is not blanket rewriting: an already-existing slot whose recomputed index equals the index it already holds is left completely alone, so its `updated_at` and `version` do not move, and only the existing rows whose position genuinely shifted count as mutated. A slot receiving its very first index as part of its own booking takes it without that counting as a further mutation, so a freshly booked appointment is returned at `version` 1. The same restraint applies to cascade A's re-evaluation of an order — an order whose recomputed `frequency_eligibility` and `earliest_allowed_date` both come back unchanged, and which therefore is not denied, is not mutated at all and keeps its `updated_at` and `version`.

### 2.10. Snapshot Semantics and the Comparability Invariant

Serial comparison only means something when the two studies being compared were produced under the same measurement conditions, and the system enforces that by **snapshotting** device state onto each acquisition at the moment the acquisition begins, rather than reading device state at report time. A session freezes the device's `calibration_generation`, its least significant change into `applied_lsc_g_cm2`, and its correction factor into `applied_cross_cal_factor`. It also freezes its serial-comparison prior — both the chosen `prior_session_id` and the comparability verdict `prior_comparison_status` — at creation, and never revisits either. The consequence is that a precision assessment accepted tomorrow cannot retroactively change how a study acquired today is interpreted, and that a study acquired before an equipment change keeps being interpreted against the calibration it was actually taken under.

Comparability is never assumed across hardware. Manufacturers differ irreconcilably in their reference databases and acquisition geometry, so a prior acquired on a different device is never treated as directly comparable, and a prior acquired on the *same* device but at an earlier calibration generation is comparable only after the device's correction factor is applied to it. Where the system cannot establish comparability, it says so explicitly on the report rather than quietly reporting a change, and it requires the interpreting physician to write a narrative explaining the gap before that report can be finalized.

## 3. Business Logic & Workflows

### 3.1. Program Foundations: Payer Policies, Patients and Clinical Risk Intake

Before any imaging can be scheduled, the program administrator registers the payers it bills. A payer policy is created with a short `payer_code` of 1 to 16 characters that must be unique across the whole catalogue — a collision is refused with `ERR_PAYER_CODE_TAKEN` — and a human-readable `name` of 1 to 120 characters. The policy then carries the three coverage floors that arbitrate how often the payer will fund a scan, each expressed in whole months between 1 and 120 inclusive: `baseline_screening_min_interval_months`, which defaults to two years and governs both baseline screening and routine serial monitoring; `high_risk_min_interval_months`, which defaults to one year and governs high-risk case finding; and `treatment_monitoring_min_interval_months`, which also defaults to one year and governs monitoring of a patient already on therapy. Policies are immutable once registered: there is no update operation, and a policy row exposes only its `id` and `created_at`, with no `updated_at` and no `version`.

Four further policy fields shape behaviour further downstream and are worth reading together. `vfa_covered` defaults to true; when it is false the payer never funds the vertebral fracture assessment add-on, whatever the clinical picture. `vfa_requires_height_loss_cm` defaults to 4.0 centimetres, must lie between 0.0 and 20.0 inclusive with at most one decimal place, and names the historical height loss that on its own establishes clinical eligibility for that add-on. `repeat_scan_grace_days` defaults to 30 days, accepts 0 through 180 inclusive, and defines how far *before* a patient's next eligible date a scan is still funded — inside that window coverage is not lost, it is merely downgraded. `max_lifetime_screening_scans` defaults to 6, accepts 1 through 40 inclusive, and is a hard cap on the number of finalized reports the payer will ever fund for one patient. Finally, `appeal_allowed` defaults to false and is a conditional feature flag: it decides whether an order the payer would refuse is rejected outright or is instead persisted in a denied, appealable state.

A `Scheduler` or `ProgramAdmin` registers each patient with an `mrn` of 1 to 24 characters, unique across the roster — a duplicate is refused with `ERR_MRN_TAKEN` — together with `primary_payer_policy_id` naming the policy that supplies every frequency, grace and lifetime limit applied to them, a `birth_date` in year-month-day form that must be a valid calendar date strictly earlier than the logical clock's date, a `sex` of either `FEMALE` or `MALE`, an optional `postmenopausal` flag defaulting to false, and `baseline_height_cm`, the patient's historical maximum recorded height, which must be greater than 80.0 and at most 230.0 centimetres with at most one decimal place. A freshly registered patient has `open_scheduled_order_count` and `lifetime_screening_scan_count` both at zero and `baseline_report_id`, `last_finalized_report_id`, `current_screening_interval_months` and `next_eligible_scan_date` all null — which is precisely why a patient's very first order is unconditionally covered.

Clinical risk factors are recorded as a **profile**, not as patient columns, because they change over time and because fracture risk arithmetic must be reproducible against the exact profile it consumed. Either a `Scheduler` or an `InterpretingPhysician` records one, supplying `expected_patient_version` as described in §2.6, the patient's current standing `height_cm` (greater than 80.0, at most 230.0, at most one decimal place) and `weight_kg` (greater than 20.0, at most 300.0, at most one decimal place), and then the risk factors themselves: `prior_fragility_fracture` for a previous low-trauma fracture after age forty, `parental_hip_fracture`, `current_smoker`, `glucocorticoid_use` for current or past systemic steroid exposure, `rheumatoid_arthritis`, `secondary_osteoporosis` for a disorder strongly associated with bone loss — all six booleans defaulting to false — and `alcohol_units_per_day`, a number defaulting to zero — echoed back as the bare integer `0` when it defaults, since no rounding rule fixes its scale — accepted from 0.0 through 40.0 inclusive with at most one decimal place.

Three values are derived at intake. `bmi` is the weight in kilograms divided by the square of the height expressed in metres — that is, the height in centimetres divided by one hundred — rounded half up to two decimal places. `height_loss_cm` is the patient's `baseline_height_cm` minus the profile's `height_cm`, rounded half up to one decimal place; it is allowed to be negative, because a patient may measure taller than their recorded historical maximum. `clinical_risk_factor_count` is the number of the six booleans that are true, plus one more when `alcohol_units_per_day` is at least 3.0. The profile stamps `recorded_at_utc` from the logical clock and is created with `status` `ACTIVE`; any profile that was previously `ACTIVE` for that patient is moved to `SUPERSEDED` in the same operation, so exactly one profile per patient is ever `ACTIVE`. Superseding is a real write to the incumbent row, so the displaced profile comes back with its `updated_at` refreshed and its `version` incremented rather than untouched at `version` 1. Recording a profile is a mutation of the patient as well, so the patient's `version` increments — a caller who holds the pre-call version must re-read the patient before its next optimistic write.

### 3.2. The Densitometer Registry and Precision Certification

A densitometer enters the registry with its `serial_number` as printed on the gantry, 1 to 32 characters and unique across every device — a repeat registration is refused with `ERR_SERIAL_NUMBER_TAKEN`. Its `manufacturer` is one of `HOLOGIC`, `GE_LUNAR` or `NORLAND`; its `model` is the vendor designation, 1 to 64 characters; its `site_code`, 1 to 16 characters, names the imaging site the device physically lives at. Two phantom constants establish the device's quality-control chart: `phantom_baseline_bmd_g_cm2`, the established phantom mean that serves as the centre line, greater than 0.0 and at most 2.0 with exactly four decimal places, and `phantom_baseline_sd_g_cm2`, the established phantom standard deviation that serves as the control-limit unit, greater than 0.0 and at most 0.2, also with exactly four decimal places. Two scheduling parameters complete the record: `appointment_buffer_minutes`, defaulting to fifteen minutes and accepted from 0 through 120, applied on **both** sides of every occupied interval when testing for slot collisions, and `daily_scan_capacity`, defaulting to twelve and accepted from 1 through 60, capping how many live appointments the device will take on a single UTC calendar day.

A newly registered device is `ACTIVE`, at `calibration_generation` 1, with `cross_cal_factor` 1.0 and `consecutive_qc_pass_count` 0. Everything precision-related is still empty: `rms_sd_g_cm2`, `precision_degrees_of_freedom`, `lsc_g_cm2`, `precision_technologist_user_id` and `precision_certified_at` are all null, as are `last_qc_result`, `last_qc_run_at`, `qc_hold_started_at` and `qc_hold_reason_code`. A device in that condition cannot acquire anything: a null `lsc_g_cm2` blocks every acquisition on the device, because without a least significant change there is no way to interpret a change against noise. Attempting to start an acquisition on such a device is refused with `ERR_DEVICE_PRECISION_NOT_CERTIFIED`.

Certification comes from a **precision assessment**: an in-vivo duplicate-scan study in which a single technologist rescans a cohort of patients and reports the root-mean-square standard deviation of the repeats. A `ProgramAdmin` submits it with `expected_densitometer_version`, the opaque `technologist_user_id` of the technologist who performed the study — a string of at least one character, with no upper length bound — `patient_count` and `scans_per_patient`, each a whole number of at least 1 with no upper bound, and the study's `rms_sd_g_cm2`, which need only be greater than 0.0: it carries no upper bound and no declared decimal width, so it is stored and echoed at whatever scale the client wrote it while the least significant change derived from it is rounded to four places. The study's statistical power is the number of degrees of freedom it carries: `precision_degrees_of_freedom` is the patient count multiplied by one less than the scans per patient. That product must be **at least thirty**; below thirty the study is refused with `ERR_PRECISION_STUDY_UNDERPOWERED` and nothing whatsoever is persisted — the device keeps whatever precision state it already had. Thirty patients scanned twice yields exactly thirty degrees of freedom and is accepted; twenty-nine patients scanned twice yields twenty-nine and is refused; fifteen patients scanned three times also yields thirty and is accepted, because it is the product and not the patient count that carries the power.

When the study is accepted, the device's least significant change in absolute units is the reported root-mean-square standard deviation multiplied by 2.77 — the two-sided ninety-five-percent coefficient for a paired measurement — rounded half up to four decimal places, and written to `lsc_g_cm2`. A study reporting 0.0100 therefore certifies a least significant change of 0.0277. The device also records the supplied `rms_sd_g_cm2`, the acting study's `precision_technologist_user_id`, and `precision_certified_at` from the logical clock, and its `version` increments. Because sessions snapshot the threshold at creation, a later assessment moves the threshold only for acquisitions started after it: studies already in flight keep the value they froze.

Retirement is terminal. A `ProgramAdmin` may retire a device from `ACTIVE`, from `QC_HOLD` or from `CROSS_CAL_PENDING`; the one and only precondition is that the device is not already `RETIRED`, so a scan still `IN_PROGRESS` on the instrument does not refuse the retirement — it merely shelters its own slot from the unwind. Retiring the device drives its `status` to `RETIRED` and unwinds the schedule around it: every appointment on the device whose `status` is `BOOKED` or `CHECKED_IN` moves to `CANCELLED` with `cancellation_reason_code` `DEVICE_QC_HOLD` and `cancelled_at_utc` stamped, and a `CHECKED_IN` slot is cancelled only when it holds no `IN_PROGRESS` acquisition. Each order behind a cancelled slot reverts from `SCHEDULED` to `REQUESTED` with `reschedule_required` set true, and the patient's `open_scheduled_order_count` decrements once per such order. Any calibration event on the device still `OPEN` or `PHANTOM_SET_COMPLETE` is closed out to `REJECTED` with `outcome_code` `REJECTED_EXCESSIVE_DRIFT` and `adjudicated_at_utc` stamped. Nothing else on the device is disturbed: `last_qc_result`, `last_qc_run_at`, `consecutive_qc_pass_count`, `qc_hold_started_at`, `qc_hold_reason_code`, `cross_cal_factor`, `calibration_generation` and every precision field are left reading exactly what they read before the retirement, since retirement is a permanent parking of the instrument rather than a reset of its history. Once `RETIRED`, the device refuses phantom runs, calibration events, precision assessments, a second retirement, any booking that names it and any acquisition on it, all with `ERR_DENSITOMETER_RETIRED`.

### 3.3. Phantom Quality Control, Out-of-Control Holds, and Cross-Calibration on Equipment Change

Each scanning day opens with a phantom scan. A `Technologist` — or a `ProgramAdmin` standing in — records the run against the device with a `purpose` of `DAILY_QC`, `CROSS_CAL_BASELINE` or `CROSS_CAL_NEW`, the measured `phantom_bmd_g_cm2` (greater than 0.0, at most 2.0, exactly four decimal places), and the `scan_mode` the phantom was acquired in, one of `ARRAY`, `FAST_ARRAY` or `HIGH_DEFINITION`. The `purpose` is polymorphic: it decides which control chart the run feeds, and it governs one conditional input. `calibration_event_id` is **required** when the purpose is `CROSS_CAL_BASELINE` or `CROSS_CAL_NEW`, and **must be absent** when the purpose is `DAILY_QC`; violating either half of that rule is a malformed request. The run stamps `performed_by_user_id` from the caller and `performed_at_utc` from the logical clock, and `performed_at_utc` is the primary sort key for every quality-control ordering, with `created_at` as the tie-break. A phantom run is an immutable historical fact: it exposes `id` and `created_at` and carries neither `updated_at` nor `version`.

Scoring is the same for every purpose. `deviation_g_cm2` is the measured phantom density minus the device's established `phantom_baseline_bmd_g_cm2`, rounded half up to four decimal places. `deviation_sd_units` is that deviation — the already-rounded four-decimal figure, not the raw subtraction — divided by the device's `phantom_baseline_sd_g_cm2`, rounded half up to three decimal places, and it keeps its sign. The `result` then reads the **already-rounded** three-decimal figure, never the raw quotient: an absolute value of at most 1.000 is a `PASS`, an absolute value greater than 1.000 but at most 1.500 is a `WARN`, and an absolute value greater than 1.500 is a `FAIL`. Both boundaries are inclusive on the gentler side, so exactly 1.000 passes and exactly 1.500 warns rather than failing.

A single out-of-limit reading is one kind of trouble; a sustained one-sided drift is another, and the chart detects it separately. `shift_detected` is computed only for `DAILY_QC` runs, and is true when this run together with the **two immediately preceding** `DAILY_QC` runs on the same device — the two ranked highest by `performed_at_utc` descending, then `created_at` descending, then the server's internal creation sequence descending among the runs recorded before it, the run being scored not yet counting itself among them — all show an absolute `deviation_sd_units` of at least 1.000 *and* all three share the same sign. A deviation of exactly zero has no sign and therefore breaks the chain. When fewer than two preceding daily runs exist the flag is false, so a device with only two daily runs in its whole history can never trip it. Note the deliberate asymmetry with the `PASS` band: the shift test is "at least 1.000" while the pass test is "at most 1.000", so a run whose own `result` is `PASS` at exactly 1.000 still counts toward a shift and can be the run that takes the device offline.

The device is then updated in exactly this order, and the first matching rule wins. A `FAIL` drives `status` from `ACTIVE` to `QC_HOLD` with `qc_hold_reason_code` `OUT_OF_CONTROL_FAIL`, `qc_hold_started_at` set to the run's `performed_at_utc`, and `consecutive_qc_pass_count` reset to zero. Otherwise a true `shift_detected` drives `status` to `QC_HOLD` with `qc_hold_reason_code` `SUSTAINED_SHIFT`, the same `qc_hold_started_at`, and the same reset — and this fires even when the run's own `result` is `PASS`, because three consecutive same-sided runs at or beyond the warning limit are an out-of-control condition regardless of any single reading. Otherwise a `WARN` leaves `status` untouched but still resets `consecutive_qc_pass_count` to zero. Otherwise, on a `PASS`, `consecutive_qc_pass_count` increments by one; and if the device was in `QC_HOLD` and the new count has reached two, the device returns to `ACTIVE` with `qc_hold_started_at` and `qc_hold_reason_code` both cleared to null. Two consecutive clean runs are required for release, so the first passing run inside a hold only advances the counter and the device stays on hold; the counter is left standing at the value that earned the release rather than being reset to zero on the way out. Three consequences of reading those rules against the device's *current* status are worth stating. A device already sitting in `QC_HOLD` that fails again, or trips the shift test again, has its `qc_hold_reason_code` and `qc_hold_started_at` overwritten by the new run, so the recorded reason is always the most recent one — but **cascade B** fires only on the transition into the hold, never again while the hold persists. A device in `CROSS_CAL_PENDING` cannot be driven onto hold by a daily run at all: the run is recorded and scored normally and `consecutive_qc_pass_count` still moves, but the `status`, `qc_hold_reason_code` and `qc_hold_started_at` are left untouched, because the device is already unusable for a different and more specific reason. And a `PASS` streak on a device that is not in `QC_HOLD` simply accumulates, since there is no hold to release. In every case the device's `last_qc_result` and `last_qc_run_at` are refreshed from the most recent daily run, and the device is mutated exactly once per daily run — one `updated_at` refresh and one `version` increment covering the scoring, the counter and any status move together.

**Cascade B** is what makes a hold consequential rather than advisory. When a device enters `QC_HOLD`, every appointment on that device whose `status` is `BOOKED` and whose `start_utc` falls **within forty-eight hours** of `qc_hold_started_at` is cancelled — that is the imminent-work horizon — processed in `start_utc` ascending order with `created_at` ascending and then the server's internal creation sequence ascending as the tie-breaks, each moving `BOOKED` to `CANCELLED` with `cancellation_reason_code` `DEVICE_QC_HOLD` and `cancelled_at_utc` stamped from the logical clock. The horizon is a single strict upper bound and nothing else: a slot qualifies exactly when its `start_utc` is **strictly earlier** than `qc_hold_started_at` plus forty-eight hours, so a slot starting at exactly that boundary instant survives, and there is no lower bound at all, so a slot whose `start_utc` already lies in the past but which is somehow still `BOOKED` is swept up as well. Each cancellation in turn reverts its owning order from `SCHEDULED` to `REQUESTED` with `reschedule_required` set true, and decrements that patient's `open_scheduled_order_count` by one. Slots further out than the horizon are left alone; they will be blocked at acquisition time if the hold persists. The `slot_index` of every remaining non-cancelled slot on the device and each affected UTC calendar date is recomputed. Releasing the device later does **not** restore anything: cancelled appointments stay cancelled and must be rebooked.

Cross-calibration runs behave differently in exactly two respects: they are scored identically but never change the device's `status`, its `consecutive_qc_pass_count`, its `last_qc_result` or its `last_qc_run_at` — a cross-calibration run leaves the device row entirely unmutated, so its `updated_at` and `version` do not move — and they never participate in shift detection. Not participating means the field is still present and still concrete: `shift_detected` is recorded as `false` on every cross-calibration run, never as null. What they do instead is accumulate on the calibration event they name, incrementing its `baseline_run_count` or its `new_run_count` and refreshing that event's `updated_at` and `version`. The named event is checked for existence only. It is not required to sit on the densitometer being addressed, and its `status` is not inspected, so a run tagged to an event belonging to another device, or to one already `PHANTOM_SET_COMPLETE`, `APPROVED` or `REJECTED`, is still accepted and still moves that event's count — the only state test on this endpoint is that the addressed densitometer is not `RETIRED`, which means a device in `ACTIVE` or `QC_HOLD` may record cross-calibration runs just as freely as one in `CROSS_CAL_PENDING`.

An equipment change invalidates the device's calibration outright, and the program handles it as a three-step adjudicated workflow. A `ProgramAdmin` opens a **calibration event** on the device with a `change_type` of `DETECTOR_REPLACEMENT`, `SOFTWARE_UPGRADE`, `XRAY_TUBE_REPLACEMENT` or `DEVICE_REPLACEMENT`, plus an optional free-text `change_note` of up to 240 characters referencing the service record. Opening is permitted only when the device is `ACTIVE` or `QC_HOLD` and no event on that device is currently `OPEN` or `PHANTOM_SET_COMPLETE`; because opening moves the device to `CROSS_CAL_PENDING`, an attempt to open a second concurrent event is refused with `ERR_DENSITOMETER_NOT_ACTIVE` rather than with any event-state error. The event is created with `status` `OPEN` and a `required_phantom_runs` count keyed to the severity of the change: three runs for a software upgrade, five for a detector replacement, five for an X-ray tube replacement, and ten for a whole-device replacement — required on **each** side of the change, not in total. The device's `consecutive_qc_pass_count` resets to zero. When the event is opened from `QC_HOLD`, the device's `qc_hold_started_at` and `qc_hold_reason_code` are deliberately preserved, so the original hold reason survives the calibration detour. Existing booked appointments are deliberately *not* cancelled here; they are blocked at acquisition time by `ERR_DENSITOMETER_NOT_ACTIVE` instead.

The technologist then scans the phantom repeatedly on the old configuration, tagging each run `CROSS_CAL_BASELINE`, and again on the new configuration, tagging each `CROSS_CAL_NEW`. Closing the event demands that both sides be complete: if either `baseline_run_count` or `new_run_count` is below `required_phantom_runs`, the close is refused with `ERR_PHANTOM_SET_INCOMPLETE`, and closing an event that is not `OPEN` is refused with `ERR_CALIBRATION_EVENT_NOT_OPEN`. On a successful close the event moves `OPEN` to `PHANTOM_SET_COMPLETE`, stamps `closed_at_utc`, and computes its comparison. `baseline_mean_bmd_g_cm2` is the arithmetic mean of `phantom_bmd_g_cm2` across the baseline runs, rounded half up to four decimal places; `new_mean_bmd_g_cm2` is the same mean across the new-configuration runs, likewise rounded to four places. "The baseline runs" means **every** run tagged to this event with `purpose` `CROSS_CAL_BASELINE`, not merely the first `required_phantom_runs` of them, so a technologist who records extra phantom scans sees all of them averaged in; and since the event is the only thing a run is matched on, a run recorded against a different densitometer but tagged to this event is averaged in too. Both means are rounded **before** anything is derived from them. `percent_difference` is one hundred multiplied by the new mean minus the baseline mean, divided by the baseline mean, rounded half up to two decimal places. From that figure the event precomputes its verdict: an absolute percent difference **below** 1.00 is `WITHIN_TOLERANCE_NO_FACTOR` with `proposed_cross_cal_factor` set to exactly 1.0000; an absolute percent difference from 1.00 through 5.00 inclusive is `FACTOR_APPLIED` with `proposed_cross_cal_factor` equal to the baseline mean divided by the new mean, rounded half up to four decimal places; and an absolute percent difference above 5.00 is `REJECTED_EXCESSIVE_DRIFT` with a null `proposed_cross_cal_factor`. A baseline mean of 1.0000 against a new mean of 1.0200 therefore gives a percent difference of 2.00, a `FACTOR_APPLIED` outcome, and a factor of 0.9804. Exactly 1.00 is `FACTOR_APPLIED`, not within tolerance; exactly 5.00 is still `FACTOR_APPLIED`, while 5.01 is excessive drift.

Adjudication is the final step and takes no request body at all — the verdict is derived entirely from the stored `percent_difference`, so there is nothing for a caller to influence. Adjudicating an event that is not `PHANTOM_SET_COMPLETE` is refused with `ERR_CALIBRATION_EVENT_NOT_CLOSED`. **Cascade C** runs when the absolute percent difference is at most 5.00: the event moves `PHANTOM_SET_COMPLETE` to `APPROVED` and stamps `adjudicated_at_utc`; the device's `cross_cal_factor` is set to exactly 1.0 when the `outcome_code` is `WITHIN_TOLERANCE_NO_FACTOR` and to the event's `proposed_cross_cal_factor` otherwise; the device's `calibration_generation` increments by one; the device returns from `CROSS_CAL_PENDING` to `ACTIVE`; and `qc_hold_started_at`, `qc_hold_reason_code` and `consecutive_qc_pass_count` are cleared to null, null and zero respectively. The third link of the cascade is the one that reaches into clinical interpretation: because the generation counter has moved, every acquisition created from now on snapshots the higher generation, and any prior study sitting at a lower generation is scored as cross-calibration-adjusted and has its density multiplied by the new factor before it is compared. Note that a within-tolerance outcome forces the device factor to exactly 1.0 even though the raw ratio of the two means is not exactly one.

The rejecting branch is deliberately not symmetric, and the difference matters. When the absolute percent difference exceeds 5.00 the event moves `PHANTOM_SET_COMPLETE` to `REJECTED` with `outcome_code` `REJECTED_EXCESSIVE_DRIFT` and `adjudicated_at_utc` stamped — but there is no generation bump, no change to `cross_cal_factor`, and no return to `ACTIVE`. The device stays in `CROSS_CAL_PENDING` and therefore stays unusable for acquisition until a fresh calibration event is opened, populated and approved. Drift that large means the new configuration is not a corrected version of the old one; it is a different instrument, and no multiplicative factor can honestly bridge it.

### 3.4. Ordering a Study and Booking It onto a Device

A `Scheduler` or an `InterpretingPhysician` opens a study by creating a **scan order** naming the `patient_id`, the clinical `indication` — one of `BASELINE_SCREENING`, `SERIAL_MONITORING`, `TREATMENT_MONITORING` or `HIGH_RISK_CASE_FINDING` — the `requested_sites` to be measured, the `requested_scan_date`, and optionally `vfa_requested`. The `requested_sites` array must be non-empty with unique members drawn from `LUMBAR_SPINE`, `FEMORAL_NECK`, `TOTAL_HIP` and `FOREARM_33`, and every site listed there must eventually be measured before the acquisition can be submitted, so the order is a binding checklist rather than a suggestion. The `requested_scan_date` is a `YYYY-MM-DD` calendar date on or after the logical clock date; a date in the past is refused with `ERR_INVALID_REQUEST` (422), and that refusal belongs to the shape rung of §2.7 rather than to any later band, so it is decided before `patient_id` is resolved and a past date on an order naming an unknown patient reports the malformed request rather than the missing patient. `vfa_requested` defaults to false, and a vertebral fracture assessment offered on a session whose order did not request one is refused. The order records `ordered_by_user_id` from the caller and `ordered_at_utc` from the clock, and starts in `status` `REQUESTED`.

Two derived fields are written at creation. `required_densitometer_id` pins serial work to one instrument: for an `indication` of `SERIAL_MONITORING` or `TREATMENT_MONITORING` it is the `densitometer_id` of the scan session behind the patient's `baseline_report_id`, and it is null for `BASELINE_SCREENING` and `HIGH_RISK_CASE_FINDING` and null whenever `baseline_report_id` is itself null. `reschedule_required` starts false and is set true only when a system cascade reverts the order from `SCHEDULED` back to `REQUESTED`; a scheduler who cancels a slot on the patient's own initiative leaves it false, which is how the queue distinguishes "we broke this booking" from "the patient changed their mind".

The payer frequency test is then evaluated, and its order of operations is fixed. The **lifetime cap is checked first**: if the patient's `lifetime_screening_scan_count` has reached the policy's `max_lifetime_screening_scans`, `frequency_eligibility` is `INELIGIBLE_LIFETIME_CAP` and `earliest_allowed_date` is copied from `next_eligible_scan_date`, even if the requested date is years past that point. Otherwise, if `next_eligible_scan_date` is null — which is the case for every patient with no finalized report — the verdict is `ELIGIBLE` with a null `earliest_allowed_date`, so a patient's first study is unconditionally eligible. Otherwise `earliest_allowed_date` is set from `next_eligible_scan_date` and the requested date is compared against it: on or after it the verdict is `ELIGIBLE`; earlier than it but no earlier than that date less the policy's `repeat_scan_grace_days` whole days the verdict is `ELIGIBLE_WITH_GRACE`; earlier still the verdict is `INELIGIBLE_TOO_SOON`. Both comparisons are inclusive, so a request landing exactly on `earliest_allowed_date` is plainly eligible and one landing exactly the full grace window before it still qualifies for grace, while one day earlier than that does not. `payer_floor_months` is recorded from the policy at the same moment, selected by indication: `baseline_screening_min_interval_months` for `BASELINE_SCREENING` and `SERIAL_MONITORING`, `high_risk_min_interval_months` for `HIGH_RISK_CASE_FINDING`, and `treatment_monitoring_min_interval_months` for `TREATMENT_MONITORING`.

What happens to an ineligible verdict at creation depends on the policy's `appeal_allowed` flag, and the two branches differ in whether anything is stored at all. When `appeal_allowed` is false the request is rejected outright with `ERR_PAYER_FREQUENCY_LIMIT` for a too-soon verdict or `ERR_LIFETIME_SCAN_CAP_EXCEEDED` for a cap verdict, both carrying HTTP 402 Payment Required, and no order is persisted. When `appeal_allowed` is true the order **is** created, immediately in `status` `DENIED`, with `denial_reason_code` set to `PAYER_FREQUENCY_LIMIT` or `LIFETIME_CAP_EXCEEDED` — a durable record the program can appeal against. `denial_reason_code` is populated exactly when `status` is `DENIED` and is null otherwise, and its third value, `INTERVAL_REVISED_BY_REPORT`, is reserved for orders denied later by the finalization cascade described in §3.8.

A `Scheduler` books the order onto a device by creating a **scan appointment** carrying `scan_order_id`, `densitometer_id`, `start_utc` and `end_utc`. The window must be well formed: `start_utc` **strictly after** the logical clock instant — a slot starting exactly at the current clock reading is already in the past for this purpose — `end_utc` strictly after `start_utc`, and no more than 240 minutes after it. Those three refusals do not share a band. The first two are the ladder's own `ERR_APPOINTMENT_IN_PAST` and `ERR_INVALID_INTERVAL`, decided late, after both foreign keys have resolved and after the device and order state checks; the 240-minute ceiling is instead a shape failure answered with `ERR_INVALID_REQUEST` (422) before either foreign key is resolved, and it is tested only when `end_utc` is already after `start_utc`, so a window that is both inverted and absurdly long reports the inversion. The interval is treated as half-open — inclusive of `start_utc`, exclusive of `end_utc` — and `scheduled_duration_minutes` is the whole number of minutes between them, truncated downwards, so a window of ninety minutes and thirty seconds records 90. Booking is permitted only when the order is in `status` `REQUESTED` and its `frequency_eligibility` is `ELIGIBLE` or `ELIGIBLE_WITH_GRACE`; a `DENIED` order can never be scheduled. The device, by contrast, is tested only for retirement: a `RETIRED` densitometer is refused with `ERR_DENSITOMETER_RETIRED`, while one sitting in `QC_HOLD` or `CROSS_CAL_PENDING` may still be booked, since the hold may well be lifted before the slot arrives — the `ACTIVE` requirement bites later, when the technologist opens the session on it. If the order carries a non-null `required_densitometer_id` that differs from the requested `densitometer_id`, the booking is refused with `ERR_SERIAL_DEVICE_MISMATCH`, because a serial comparison performed on a different instrument is not a comparison at all.

Three separate capacity rules then guard the device's day. The overlap test applies the device's own `appointment_buffer_minutes` symmetrically, on **both** sides of every occupied interval: an existing appointment on the same `densitometer_id` in `status` `BOOKED` or `CHECKED_IN` conflicts when the new start falls before the existing end extended by the buffer **and** the existing start falls before the new end extended by the buffer, which is refused with `ERR_DEVICE_SLOT_CONFLICT`. Separately, a patient may hold only one live slot per UTC calendar date: another appointment for the same patient in `status` `BOOKED` or `CHECKED_IN` whose `start_utc` falls on the same UTC date is refused with `ERR_PATIENT_DOUBLE_BOOKED`. And a device may not exceed its `daily_scan_capacity`: when the device already holds that many appointments in `status` `BOOKED`, `CHECKED_IN` or `COMPLETED` starting on the requested UTC date, the booking is refused with `ERR_DEVICE_DAILY_CAPACITY_FULL`. Note that the capacity count includes `COMPLETED` slots while the overlap test does not, so a fully worked day blocks further booking even though none of its intervals collide.

A successful booking creates the slot in `status` `BOOKED`, moves the order from `REQUESTED` to `SCHEDULED`, increments the patient's `open_scheduled_order_count` by one — the forward half of the open-order invariant — and clears `reschedule_required` to false. It also assigns `slot_index`: the 1-based position of this appointment among all appointments on the same `densitometer_id` whose `start_utc` falls on the same UTC calendar date and whose `status` is `BOOKED`, `CHECKED_IN` or `COMPLETED`, ordered by `start_utc` ascending, then `created_at` ascending, then the server's internal creation sequence ascending. Because the index is positional rather than assigned, it is recomputed for every affected sibling whenever that day's set changes: inserting a slot earlier in the day shifts the later ones up, and cancelling one shifts them back down. Cancelled slots are excluded from the numbering entirely. The renumbering is deliberately economical about optimistic-concurrency metadata: a sibling is re-stamped — its `updated_at` refreshed and its `version` incremented — only when its computed index actually differs from the one it already held, so booking a slot at the end of a day leaves every earlier slot's `version` untouched, while booking one at the start of a busy day bumps all of them. The newly created slot receives its own index as part of its creation and is not re-stamped for it, so a freshly booked appointment is always returned at `version` 1 whatever position it landed in.

A `Scheduler` may cancel a booked slot. Cancellation takes no request body: it moves `status` from `BOOKED` to `CANCELLED`, sets `cancellation_reason_code` to `PATIENT_REQUEST`, stamps `cancelled_at_utc` from the clock, reverts the owning order from `SCHEDULED` to `REQUESTED`, and decrements the patient's `open_scheduled_order_count`. That decrement is the compensating half of the open-order invariant: after a book-then-cancel pair the counter reads exactly its pre-booking value, and it must never drift below zero. The remaining non-cancelled slots on that device and UTC date have their `slot_index` recomputed. The other two values of `cancellation_reason_code` — `DEVICE_QC_HOLD` and `ORDER_DENIED` — are written only by system cascades, never by a scheduler, so the reason code identifies who broke the appointment.

### 3.5. Acquisition at the Device

A `Technologist` starts work by creating a **scan session** on a booked appointment, supplying only the `scan_mode` — `ARRAY`, `FAST_ARRAY` or `HIGH_DEFINITION` — since everything else is derived. The appointment must be in `status` `BOOKED` and moves to `CHECKED_IN`; the device must be `ACTIVE`, so a device on quality-control hold or awaiting cross-calibration adjudication is refused with `ERR_DENSITOMETER_NOT_ACTIVE`; and the device's `lsc_g_cm2` must not be null, so an uncertified instrument is refused with `ERR_DEVICE_PRECISION_NOT_CERTIFIED`. Those four tests are taken in the ladder's order — retirement, then device status, then the appointment's `BOOKED` requirement, then precision certification — and there is no separate rule forbidding a second session on the same appointment: the first session moves the appointment out of `BOOKED`, so a second attempt is turned away by that requirement with `ERR_APPOINTMENT_NOT_BOOKED`. The session is created with `acquisition_status` `IN_PROGRESS`, `review_status` `NOT_REVIEWED` and `repeat_count` zero, with `scan_appointment_id` taken from the path rather than the body, and with `technologist_user_id` taken from the caller's `X-User-ID`. That user is the only one permitted to post measurements, record a vertebral fracture assessment, submit or repeat this session — and, by the segregation-of-duties rule, the one user forbidden from reviewing its positioning.

Creation snapshots four values from the device onto the session, and the snapshot is the whole point: `densitometer_id`, `calibration_generation`, `applied_lsc_g_cm2` and `applied_cross_cal_factor`. `patient_id` is likewise denormalized from the owning order. None of them is ever refreshed. A precision assessment run tomorrow cannot retroactively change how today's study was interpreted, and a cross-calibration approved next week cannot silently redefine what today's session considered comparable.

The comparison prior is also fixed at creation, by a three-stage waterfall, and it is never recomputed afterwards. The candidate pool is every other session of the same patient whose `acquisition_status` is `SUBMITTED` or `ARCHIVED`, whose `review_status` is `ACCEPTED` or `ACCEPTED_WITH_LIMITATION`, and which carries at least one report in `status` `FINALIZED` — an unreviewed, repeat-required or unreported study is not a clinical prior no matter how recent. **Stage one** looks only at candidates on the same `densitometer_id` and takes the one with the highest `submitted_at_utc`, breaking ties by the highest `created_at` and then by the highest internal creation sequence; `prior_comparison_status` is then `PRIOR_CROSS_CAL_ADJUSTED` when that prior's `calibration_generation` is lower than the new session's, and `COMPARABLE_SAME_DEVICE` when the generations match. **Stage two** runs only when stage one found nothing: it ranks the whole pool the same way regardless of device and marks the result `NOT_COMPARABLE_DEVICE_MISMATCH`. **Stage three** applies when the pool is empty: `prior_session_id` stays null and `prior_comparison_status` is `BASELINE_NO_PRIOR`. A same-device prior always beats a more recent prior on another device, because the ranking never runs across the two stages at once.

For each site the technologist posts a **site measurement** carrying `site_code`, the acquired `bmd_g_cm2`, `area_cm2` and `bmc_g`, and the four reference figures from the vendor database — `reference_mean_bmd_g_cm2`, `reference_sd_g_cm2`, `age_matched_mean_bmd_g_cm2` and `age_matched_sd_g_cm2`. Density values are greater than 0.0 and at most 2.5 with at most four decimal places; reference standard deviations are greater than 0.0 and at most 0.5 with at most four decimal places; `area_cm2` is greater than 0.0 and at most 200.0 with at most two decimals, and `bmc_g` greater than 0.0 and at most 400.0 with at most two decimals. `included_vertebrae` is **required** when `site_code` is `LUMBAR_SPINE` and **must be absent** for every other site; its entries must be drawn from `L1`, `L2`, `L3` and `L4`, and that membership rule is the only part of the array the shape rung enforces — an empty array and a repeated level are both accepted there and refused instead by the vertebral-count rule below, so they report `ERR_INSUFFICIENT_VALID_VERTEBRAE` (422) rather than `ERR_INVALID_REQUEST`. `valid_vertebral_count` is the length of that array for a lumbar row and zero for every other site. At most one non-superseded measurement may exist per session per site, and a second one is refused with `ERR_DUPLICATE_SITE_MEASUREMENT`; the site must also appear in the order's `requested_sites`, or the row is refused with `ERR_SITE_NOT_REQUESTED`. A lumbar row with fewer than two valid vertebrae is refused outright with `ERR_INSUFFICIENT_VALID_VERTEBRAE`, which is why the stored `site_usable_for_diagnosis` flag — false for `LUMBAR_SPINE` below two valid vertebrae, true otherwise — reads true on every row the system actually accepted. Each accepted row computes `t_score` as the measured density minus `reference_mean_bmd_g_cm2` divided by `reference_sd_g_cm2`, rounded half up to **one** decimal place, and `z_score` the same way against `age_matched_mean_bmd_g_cm2` and `age_matched_sd_g_cm2`. That one-decimal value, not the unrounded quotient, is what diagnosis and fracture-risk scoring consume downstream. `superseded` starts false, and `measured_site_count` on the session counts the non-superseded rows — which makes accepting a measurement a mutation of the session too, refreshing its `updated_at` and incrementing its `version`, even though the measurement row itself carries neither field.

When the order requested the vertebral add-on, the technologist records it by supplying `genant_grades`, a non-empty array of integers from 0 through 3, one per assessed vertebral level; repeated grades are perfectly legal, since two vertebrae may well be deformed to the same degree. Three refusals are checked in this exact order: the add-on was never ordered, giving `ERR_VFA_NOT_ORDERED`; the patient does not meet clinical eligibility, giving `ERR_VFA_NOT_ELIGIBLE`; and the payer policy does not cover it, giving `ERR_VFA_NOT_COVERED`. Clinical eligibility precedes coverage deliberately — the program refuses to tell a payer it declined a study the patient did not qualify for. `vfa_eligibility_code` is decided by the first matching test against the patient's active risk-factor profile: a `height_loss_cm` at or above the policy's `vfa_requires_height_loss_cm` gives `ELIGIBLE_HEIGHT_LOSS`; otherwise a true `glucocorticoid_use` gives `ELIGIBLE_GLUCOCORTICOID`; otherwise an age of at least seventy years, counted in completed years from `birth_date` to the logical clock's date, gives `ELIGIBLE_AGE_THRESHOLD`; otherwise the code is `NOT_ELIGIBLE` and the request is refused. A patient with no `ACTIVE` profile at all is not failed on that account: the first two tests, both of which read profile fields, are simply **skipped**, and the age threshold is evaluated on its own — so such a patient qualifies as `ELIGIBLE_AGE_THRESHOLD` at seventy and is `NOT_ELIGIBLE` below it, rather than being refused for want of a profile. The height-loss test is a plain numeric comparison with no lower guard, so a negative `height_loss_cm` — a patient who has grown taller than the recorded baseline — merely fails it and falls through to the glucocorticoid test. On success `vfa_max_genant_grade` is the largest grade submitted, `vfa_fracture_count` is the number of entries at grade 1 or above, and `vfa_performed` becomes true. The call is not one-shot and stores no resource of its own: it answers HTTP 200 with the affected session, and while that session is still `IN_PROGRESS` it may be repeated, in which case the eligibility and coverage tests are re-run against current data and `vfa_eligibility_code`, `vfa_max_genant_grade` and `vfa_fracture_count` are simply overwritten from the new grades.

Submitting the acquisition is the technologist's last act on the session and is gated on completeness. The session must be `IN_PROGRESS`, the caller must be its own `technologist_user_id`, `measured_site_count` must be at least one, **every** entry in the order's `requested_sites` must have a non-superseded measurement — otherwise `ERR_REQUESTED_SITES_INCOMPLETE` — and when `vfa_requested` is true, `vfa_performed` must also be true, otherwise `ERR_VFA_NOT_PERFORMED`. On success `submitted_at_utc` is stamped from the clock, and its calendar date becomes the scan date all later interval arithmetic is measured from. The diagnostic selection then runs, `acquisition_status` moves `IN_PROGRESS` to `SUBMITTED`, the appointment moves `CHECKED_IN` to `COMPLETED`, the owning order moves `SCHEDULED` to `COMPLETED`, and the patient's `open_scheduled_order_count` decrements — the second compensating path for that counter. Each of those last three effects is conditional on actually finding its source status: the appointment is advanced only from `CHECKED_IN` and the order only from `SCHEDULED`, and the counter decrements only alongside that order transition and never below zero. A session submitted a second time after a repeat cycle, when the appointment and the order are already `COMPLETED`, therefore leaves both of them and the counter exactly where they stand.

The diagnostic selection that runs at submission decides which single number carries the diagnosis. The candidate set is the non-superseded measurements with `site_usable_for_diagnosis` true whose `site_code` is one of the three central sites `LUMBAR_SPINE`, `FEMORAL_NECK` and `TOTAL_HIP`. Only when that set is empty do non-superseded `FOREARM_33` rows become the candidate set — the forearm is a fallback skeletal site, never a competitor to a central one, so a session with a central measurement never diagnoses off the forearm even when the forearm reads lower. `lowest_t_score` is the minimum `t_score` over the candidate set, and `lowest_t_score_site` is the `site_code` that supplied it, with ties broken by the fixed precedence `LUMBAR_SPINE`, then `FEMORAL_NECK`, then `TOTAL_HIP`, then `FOREARM_33` — never by `created_at` and never by `id`, so the answer does not depend on the order the technologist happened to enter the sites. `lowest_z_score` is the minimum `z_score` over that same candidate set and may well come from a different site than the one that supplied the lowest T-score.

### 3.6. Independent Positioning Review and the Repeat Cycle

Densitometry results are only as good as the patient's positioning, so every submitted study is reviewed for acquisition quality by someone other than the person who acquired it. A `QualityReviewer` may review any submitted session, and a `Technologist` may review a **colleague's** session — but if the caller's `X-User-ID` equals the session's `technologist_user_id` the review is refused with `ERR_SEGREGATION_OF_DUTIES`, which is the entire reason the technologist role appears on this operation at all. The session must be `SUBMITTED`, and its `review_status` must still be `NOT_REVIEWED`; a second review of the same session is refused with `ERR_SESSION_ALREADY_REVIEWED`. The review records `reviewer_user_id` from the caller and `reviewed_at_utc` from the clock, and like a phantom run it is an immutable observation carrying only `id` and `created_at` alongside its own fields.

The reviewer submits `defect_codes`, a possibly empty array of unique members drawn from `ROTATION_FEMUR`, `ABDUCTION_FEMUR`, `SPINE_NOT_STRAIGHT`, `ARTIFACT_IN_FIELD`, `INCORRECT_ROI`, `MOTION_ARTIFACT` and `INADEQUATE_SCAN_LENGTH`, plus an optional `reviewer_note` of up to 240 characters. `severity_score` is the weighted sum over the distinct codes present, and the weights encode how badly each defect corrupts the measurement: `ROTATION_FEMUR`, `INCORRECT_ROI` and `INADEQUATE_SCAN_LENGTH` weigh three each; `ABDUCTION_FEMUR`, `SPINE_NOT_STRAIGHT` and `MOTION_ARTIFACT` weigh two each; and `ARTIFACT_IN_FIELD` weighs one. An empty array scores zero. Because the members are unique the same defect can never be double-counted.

`repeat_criterion_met` is true when `severity_score` reaches three, so any single heavy defect is enough on its own, while two light defects — an artefact in the field plus a motion artefact, scoring three together — reach the threshold jointly. The `outcome` then depends on how many repeats the session has already been through: when the criterion is not met the outcome is `ACCEPTED`; when it is met and `repeat_count` is below two the outcome is `REPEAT_REQUIRED`; and when it is met but `repeat_count` has already reached two the outcome is `ACCEPTED_WITH_LIMITATION`. That third branch is the program's concession to reality — after two repeats the patient has absorbed enough radiation and enough of the schedule, so the study is accepted with its limitations documented rather than repeated a third time. Whatever the outcome, it is copied straight onto the session's `review_status`.

A `REPEAT_REQUIRED` verdict sends the session backwards, and only its own technologist may drive it there: the caller must be the session's `technologist_user_id`, or the request is refused with `ERR_NOT_SESSION_TECHNOLOGIST`. Repeating moves `acquisition_status` from `SUBMITTED` back to `IN_PROGRESS` and `review_status` from `REPEAT_REQUIRED` back to `NOT_REVIEWED`, increments `repeat_count` by one, resets `submitted_at_utc`, `lowest_t_score`, `lowest_t_score_site` and `lowest_z_score` to null, and marks **every** existing measurement on the session `superseded`, which returns `measured_site_count` to zero and requires the whole site set to be re-acquired from scratch. Superseded rows are excluded from every aggregate and from the duplicate-site check, so the same `site_code` may be posted again. The vertebral add-on is deliberately **not** unwound: `vfa_performed`, `vfa_eligibility_code`, `vfa_max_genant_grade` and `vfa_fracture_count` all survive the repeat untouched, so an assessment already recorded still satisfies the submission gate on the second pass without being performed again — only the skeletal measurements are discarded. The appointment stays `COMPLETED` and the order stays `COMPLETED` throughout — the patient is still on the table for the same visit, so nothing about the schedule is undone. This is what makes the session's two state dimensions genuinely independent: `review_status` evolves on its own except for this one coupling, where `REPEAT_REQUIRED` drags `acquisition_status` back with it.

The two refusals around repeating are deliberately distinct. A session whose `review_status` is neither `REPEAT_REQUIRED` nor `ACCEPTED_WITH_LIMITATION` is refused with `ERR_SESSION_REPEAT_NOT_REQUIRED`, because there is nothing to repeat. An `ACCEPTED_WITH_LIMITATION` session falls through that check and is refused instead with `ERR_REPEAT_LIMIT_EXCEEDED`, because it reached that status precisely by exhausting its two repeats — the more specific answer, and the one that tells the technologist the door is closed rather than merely unopened.

### 3.7. Fracture Risk Assessment and Drafting the Diagnostic Report

An `InterpretingPhysician` may compute a **FRAX assessment** — a ten-year fracture probability — naming the `patient_id`, the `risk_factor_profile_id` it reads its clinical factors from, and optionally a `scan_session_id`. That last field alone selects between the two variants: supplying it produces `variant` `WITH_BMD`, omitting it produces `WITHOUT_BMD`. The profile must belong to the named patient and must be in `status` `ACTIVE`, so a `SUPERSEDED` profile is refused with `ERR_RISK_PROFILE_NOT_ACTIVE` and a profile or session belonging to a different patient is refused with `ERR_FRAX_PATIENT_MISMATCH`. When a session is supplied it must carry a usable, non-superseded `FEMORAL_NECK` measurement, since that is the only site FRAX accepts; otherwise the request is refused with `ERR_FEMORAL_NECK_REQUIRED`. That measurement is the only thing the assessment asks of the session: neither `acquisition_status` nor `review_status` is tested at all, so a `WITH_BMD` assessment may be computed against a session still `IN_PROGRESS` as soon as its femoral neck row exists. The assessment records `assessed_by_user_id` and `assessed_at_utc`.

Scoring is an additive points model, and every term is rounded to **two** decimal places before the terms are summed. `age_years` is the completed whole years between the patient's `birth_date` and the logical clock date. `age_points` is the years above the reference age of fifty multiplied by one tenth of a point per year, clamped at zero from below, so a patient younger than fifty contributes 0.00 rather than a negative amount. `sex_points` is 0.60 for a `FEMALE` patient and 0.00 for a `MALE` one. `bmi_used` is copied from the referenced profile's `bmi`, and `bmi_points` reads it in three tiers: 0.80 points below 20.00, 0.00 points from 20.00 through 30.00 inclusive, and −0.40 points above 30.00 — so exactly 20.00 sits in the middle tier while 19.99 falls into the low-BMI tier. `clinical_risk_points` is the sum of the weights of the risk factors that are true on the profile: 1.90 for `prior_fragility_fracture`, 1.30 for `parental_hip_fracture`, 0.90 for `current_smoker`, 1.60 for `glucocorticoid_use`, 1.20 for `rheumatoid_arthritis`, 0.80 for `secondary_osteoporosis`, and 1.00 when `alcohol_units_per_day` is at or above 3.0 — exactly 3.0 counts, 2.9 does not. `bmd_points` is 0.00 for the `WITHOUT_BMD` variant, and for `WITH_BMD` it is the femoral-neck `t_score` multiplied by −1.20. Watch the sign: the T-score of a low-density patient is negative, and multiplying it by a negative coefficient **increases** the score, so omitting the BMD term for an osteopenic patient lowers the estimated probability rather than raising it.

`raw_score` is the sum of those five already-rounded terms, itself rounded to two decimals. The two probabilities are then linear functions of it, each clamped and only then rounded to one decimal place: `major_osteoporotic_10yr_pct` is 3.0 plus 6.0 times the raw score, floored at 0.5 and capped at 60.0; `hip_fracture_10yr_pct` is 0.4 plus 1.6 times the raw score, floored at 0.1 and capped at 30.0. The clamps are applied before the final rounding, never after. `treatment_threshold_met` is true when the major-osteoporotic probability reaches 20.0 **or** the hip probability reaches 3.0, and `threshold_basis` records which: `BOTH` when both thresholds are met, `MAJOR_OSTEOPOROTIC` when only the major one is, `HIP` when only the hip one is, and `NONE` when neither is. A sixty-seven-year-old female with a `bmi_used` of 20.31, no clinical risk factors and a femoral-neck `t_score` of −2.0 therefore scores `age_points` 1.70, `sex_points` 0.60, `bmi_points` 0.00, `clinical_risk_points` 0.00 and `bmd_points` 2.40, for a `raw_score` of 4.70, a major probability of 31.2, a hip probability of 7.9 and a `threshold_basis` of `BOTH`. The same patient assessed `WITHOUT_BMD` scores a `raw_score` of 2.30, a major probability of 16.8 and a hip probability of 4.1 — still treatment-eligible, but on the hip threshold alone.

The physician then drafts a **diagnostic report** on the session, naming `scan_session_id` and optionally `frax_assessment_id`, `non_comparability_note` and `vfa_narrative`, the last two being free text of up to 480 characters each. The session must be `SUBMITTED`, so reporting a study still `IN_PROGRESS` is refused with `ERR_SESSION_NOT_SUBMITTED`, and at most one report per session may be in `status` `DRAFT` or `FINALIZED` at a time, so a second draft is refused with `ERR_REPORT_ALREADY_EXISTS`. Any attached assessment must belong to the same patient as the session. The report is created in `status` `DRAFT` with a null `amends_report_id`, and the entire interpretation is computed at that moment. The same three fields — `frax_assessment_id`, `non_comparability_note` and `vfa_narrative` — are the **only** writable ones on an update, and every computed field is fully re-derived on each update, so attaching a FRAX assessment to an existing draft can flip its `recommended_action` outright. An update writes only those of the three that are actually present and non-null in its body: an omitted field and an explicit `null` are treated alike and leave the stored value exactly as it was, so an update can set or replace a narrative or a FRAX link but can never clear one back to null. Updating a report that is no longer `DRAFT` is refused with `ERR_REPORT_NOT_DRAFT`, and the body's `frax_assessment_id` is resolved before that status test, so a `frax_assessment_id` naming no assessment reports `ERR_FRAX_ASSESSMENT_NOT_FOUND` even when the addressed report is no longer a draft.

The interpretation runs as seven ordered steps, each reading the outputs of the ones before it. **Step one** classifies the density. `patient_age_years` is the completed whole years from `birth_date` to the clock date **at the moment the interpretation runs** — it is a derived field like every other one, so it is recomputed from the current clock at creation and again on every update, and a draft updated after the clock has been advanced past the patient's birthday comes back a year older rather than frozen at its creation-time age. The WHO T-score path applies when the patient is a `FEMALE` with `postmenopausal` true, or a `MALE` aged at least fifty; `classification_basis` is then `T_SCORE_WHO` and `diagnostic_category` reads the session's `lowest_t_score`: `OSTEOPOROSIS` at −2.5 or below, `OSTEOPENIA` above −2.5 and at or below −1.0, and `NORMAL` above −1.0. Both boundaries are inclusive on the more severe side, so exactly −2.5 is osteoporosis and exactly −1.0 is osteopenia. Otherwise the age-matched path applies, `classification_basis` is `Z_SCORE_AGE_MATCHED`, and `diagnostic_category` reads `lowest_z_score`: `BELOW_EXPECTED_RANGE_FOR_AGE` at −2.0 or below and `WITHIN_EXPECTED_RANGE_FOR_AGE` otherwise. A premenopausal woman or a man under fifty is never given a WHO label, because the young-adult reference is not the right comparison for them.

**Step two** interprets the serial change against the least significant change. When the session's `prior_session_id` is null, `lsc_interpretation` is `NO_PRIOR` and the change fields stay null. When `prior_comparison_status` is `NOT_COMPARABLE_DEVICE_MISMATCH`, it is `NOT_COMPARABLE_DEVICE` and the change fields stay null — a comparison across instruments is refused outright rather than attempted with a correction factor. Otherwise `lsc_site_code` is chosen as the first entry in the fixed precedence `TOTAL_HIP`, `LUMBAR_SPINE`, `FEMORAL_NECK` that has a non-superseded, diagnosis-usable measurement on **both** the current and the prior session; if no site in that precedence qualifies, `lsc_interpretation` is `NO_COMMON_SITE` with null change fields. With a site chosen, `current_bmd_used_g_cm2` is the current session's raw `bmd_g_cm2` at that site and `prior_bmd_used_g_cm2` is the prior session's density at that site multiplied by the cross-calibration factor — 1.0000 unless `prior_comparison_status` is `PRIOR_CROSS_CAL_ADJUSTED`, in which case it is the session's snapshotted `applied_cross_cal_factor` — rounded to four decimal places **before** any differencing. `bmd_change_g_cm2` is the current value minus that adjusted prior, signed, rounded to four decimals. `bmd_change_pct` is one hundred times the same difference divided by the adjusted prior, rounded to two decimals and derived in one step from the two four-decimal densities, never from the already-rounded change. The verdict then compares the change against the session's `applied_lsc_g_cm2`, which the report also carries under that same name — the report's `applied_lsc_g_cm2` is a copy of the session's snapshot, re-copied on every derivation and therefore present with the same value even in the `NO_PRIOR`, `NOT_COMPARABLE_DEVICE` and `NO_COMMON_SITE` cases where every other change field is null: an absolute change below the LSC is `NO_SIGNIFICANT_CHANGE`, a change at or below the negated LSC is `SIGNIFICANT_LOSS`, and a change at or above the LSC is `SIGNIFICANT_GAIN`. A prior total-hip density of 0.7000 carried at a cross-calibration factor of 0.9804 gives an adjusted prior of 0.6863, so a current 0.6700 is a change of −0.0163 against an LSC of 0.0277 and reads `NO_SIGNIFICANT_CHANGE` — whereas differencing against the unadjusted 0.7000 would have wrongly reported −0.0300 and declared a significant loss. A change of exactly −0.0277 against an LSC of 0.0277 is a `SIGNIFICANT_LOSS`; −0.0276 is not.

**Step three** sets `clinical_interval_months` from the category and then caps it. `OSTEOPOROSIS` gives twelve months. `OSTEOPENIA` gives twelve months when `lowest_t_score` is at or below −2.0 and twenty-four otherwise, so exactly −2.0 takes the shorter branch. `NORMAL` gives sixty months, `BELOW_EXPECTED_RANGE_FOR_AGE` twenty-four and `WITHIN_EXPECTED_RANGE_FOR_AGE` sixty. Then, if `lsc_interpretation` is `SIGNIFICANT_LOSS`, the interval is capped at twelve months; then, if `lsc_interpretation` is `NOT_COMPARABLE_DEVICE` or `NO_COMMON_SITE`, it is capped at twenty-four. The caps are minimums taken in that order and never lengthen the interval. **Step four** sets `payer_floor_months` from the order's `indication` and the patient's policy, exactly as at ordering time. **Step five** sets `recommended_interval_months` to the larger of the clinical interval and the payer floor, so the payer can delay a rescan but never bring one forward.

**Step six** picks `recommended_action`, and the first matching branch wins. A `diagnostic_category` of `OSTEOPOROSIS`, or an attached assessment with `treatment_threshold_met` true, yields `CONTINUE_TREATMENT` when the patient already has a plan in `ON_THERAPY`, `ADHERENCE_HOLD` or `DRUG_HOLIDAY`, and `INITIATE_TREATMENT` otherwise. Failing that, a `SIGNIFICANT_LOSS` yields `REFER_SECONDARY_WORKUP`. Failing that, a `recommended_interval_months` greater than `clinical_interval_months` yields `PAYER_LIMITED_INTERVAL`, which is how the report says out loud that the payer, not the clinician, set the interval. Otherwise the action is `ROUTINE_INTERVAL`. Because the branches are ordered, an osteoporotic patient held to a twenty-four-month payer floor still reads `INITIATE_TREATMENT` rather than `PAYER_LIMITED_INTERVAL`, and an osteopenic patient whose FRAX crosses only the hip threshold still reads `INITIATE_TREATMENT`.

**Step seven** audits the report for mandatory narrative. `missing_element_codes` lists, in this fixed order, `LSC_NON_COMPARABILITY_NOTE` when `lsc_interpretation` is `NOT_COMPARABLE_DEVICE` or `NO_COMMON_SITE` and `non_comparability_note` is null, then `VFA_FINDINGS` when the session's `vfa_performed` is true and `vfa_narrative` is null. `required_elements_complete` is true exactly when that list is empty. Both are recomputed at creation, on every update and again at finalization.

### 3.8. Finalization, the Interval Cascade and Amendment

Finalizing a report is the single most consequential act in the program: it is what makes the interpretation official, what advances the patient's screening clock, and what can retroactively invalidate work already scheduled. An `InterpretingPhysician` finalizes a report that is in `status` `DRAFT` on a session whose `acquisition_status` is `SUBMITTED` and whose `review_status` is `ACCEPTED` or `ACCEPTED_WITH_LIMITATION`. A session still `NOT_REVIEWED` or sitting at `REPEAT_REQUIRED` is refused with `ERR_POSITIONING_NOT_ACCEPTED` — unreviewed positioning may never be reported, and a study accepted with documented limitations may. The report's `required_elements_complete` must be true, otherwise the request is refused with `ERR_REPORT_ELEMENTS_INCOMPLETE`; the physician cannot sign a report that is still missing a non-comparability explanation or a vertebral narrative.

**Cascade A** then runs, in four links, and every link is caused by the one before it. **Link one**: the report moves `DRAFT` to `FINALIZED` with `finalized_at_utc` taken from the clock and `finalized_by_user_id` from the caller, and the session moves `SUBMITTED` to `ARCHIVED`. **Link two**, caused by the finalization: the patient's `lifetime_screening_scan_count` increments by one, `last_finalized_report_id` is set to this report, `baseline_report_id` is set to this report **only when it was null**, `current_screening_interval_months` is set to the report's `recommended_interval_months`, and `next_eligible_scan_date` is set to the calendar date of the session's `submitted_at_utc` advanced by that many calendar months. The interval is measured from the date the images were acquired, not from the date the physician got round to signing. **Link three**, caused by `next_eligible_scan_date` moving: every order of this patient in `status` `REQUESTED` or `SCHEDULED` is re-evaluated against the new date and the new lifetime count, processed in `created_at` ascending order, and any whose verdict is now `INELIGIBLE_TOO_SOON` or `INELIGIBLE_LIFETIME_CAP` moves to `DENIED` — with `denial_reason_code` `INTERVAL_REVISED_BY_REPORT` for a too-soon verdict and `LIFETIME_CAP_EXCEEDED` for a cap verdict. Here the policy's `appeal_allowed` flag is **irrelevant**: the order already exists, so there is nothing to reject and no request to fail; the existing order is simply denied. That is how an order created perfectly `ELIGIBLE` can end up `DENIED` without anyone touching it. **Link four**, caused by each denial: the `BOOKED` appointments of every denied order move to `CANCELLED` with `cancellation_reason_code` `ORDER_DENIED`, and the patient's `open_scheduled_order_count` decrements by one for each denied order that had been `SCHEDULED`.

A finalized report is immutable, but medicine is not, so it can be **amended**. An `InterpretingPhysician` amends a `FINALIZED` report by supplying an `amendment_reason` of 1 to 240 characters, and only when no report on the same `scan_session_id` other than the one addressed is already open in `status` `DRAFT` or `FINALIZED`; otherwise the request is refused with `ERR_REPORT_ALREADY_EXISTS`. The addressed report moves `FINALIZED` to `AMENDED` — a terminal status; an amended report is never revised again, only superseded — and a successor report is created in `status` `DRAFT` with `amends_report_id` pointing at its predecessor, the supplied `amendment_reason` recorded on the successor alone — the predecessor's own `amendment_reason` stays null — the predecessor's `frax_assessment_id`, `non_comparability_note` and `vfa_narrative` carried across unchanged so the physician need not retype them, and every computed field re-derived from the session's current state. That re-derivation runs last, after the session has already been returned to `SUBMITTED` and after the patient tallies described below have been compensated, so the successor is derived against the post-compensation picture rather than the finalized one. The successor, not the predecessor, is the response body.

Amendment also **compensates** the patient-level tallies that finalization moved, which is what keeps the numbers honest. The patient's `lifetime_screening_scan_count` decrements by one; `last_finalized_report_id` and `baseline_report_id` are re-derived from whatever `FINALIZED` reports remain, and either may become null; and `current_screening_interval_months` and `next_eligible_scan_date` are re-derived from the new `last_finalized_report_id`, or reset to null when no finalized report remains. The re-derivation is positional over the surviving `FINALIZED` reports of that patient ranked by `finalized_at_utc` ascending, then `created_at` ascending, then the server's internal creation sequence ascending: the **first** of that ranking becomes `baseline_report_id` and the **last** becomes `last_finalized_report_id`, so amending the only finalized report nulls both while amending the newest of several walks `last_finalized_report_id` back to its predecessor and leaves `baseline_report_id` pointing at the oldest survivor — `baseline_report_id` is re-derived rather than preserved, so the patient's baseline can move even when the amended report was not the baseline. `current_screening_interval_months` comes from that latest survivor's `recommended_interval_months`, and `next_eligible_scan_date` from its session's `submitted_at_utc` date advanced by the same number of calendar months. What amendment deliberately does **not** do is re-run the third link of cascade A: no order is re-evaluated and no denial is reversed, so an order that finalization pushed to `DENIED`, and any slot that denial cancelled, stay exactly where they are even though the interval that denied them has just been rolled back. The session moves `ARCHIVED` back to `SUBMITTED` so the successor can itself be finalized. A finalize followed immediately by an amend therefore leaves `lifetime_screening_scan_count` at exactly its pre-finalization value, and finalizing the successor restores it — the counter counts finalized studies, never finalization events.

### 3.9. Treatment Initiation, Refill Capture and Adherence Follow-Up

When a report recommends starting therapy, an `InterpretingPhysician` opens a **treatment plan** naming the `patient_id`, the `initiating_report_id`, the `drug_class`, the `start_date` and optionally the `adherence_source_policy`. The initiating report must be in `status` `FINALIZED` — a draft is refused with `ERR_REPORT_NOT_FINALIZED` — must belong to a session of the same patient — a report whose session names another patient, or whose session no longer exists at all, is refused with `ERR_FRAX_PATIENT_MISMATCH` and 409 — and must carry `recommended_action` `INITIATE_TREATMENT`, so a plan can never be opened off a routine-interval report. The `start_date` is a calendar date on or after the calendar date of the report's `finalized_at_utc`; therapy cannot be backdated behind the report that justified it. The last two conditions are content rules rather than status rules: a report that does not recommend `INITIATE_TREATMENT`, and a `start_date` that precedes finalization, are each refused with `ERR_INVALID_REQUEST` and 422, and both are evaluated only after the `FINALIZED` test and the patient-match test have passed, in exactly that order — so a draft report whose recommendation is also wrong reports `ERR_REPORT_NOT_FINALIZED`, and a report belonging to another patient reports the mismatch rather than the recommendation. `drug_class` is one of `BISPHOSPHONATE_ORAL`, `BISPHOSPHONATE_IV`, `DENOSUMAB`, `ANABOLIC_PTH` or `SERM`, and it selects `followup_interval_months`: three months for `BISPHOSPHONATE_ORAL` and `ANABOLIC_PTH`, six for `DENOSUMAB` and `SERM`, and twelve for `BISPHOSPHONATE_IV`. The plan is created in `status` `INITIATED` with `next_followup_due_date` set to `start_date` advanced by that many calendar months, `adherence_review_count` and `consecutive_nonadherent_reviews` at zero, `adherence_status` `NOT_ASSESSED`, and `last_review_date`, `adherence_window_days`, `covered_days_supplied`, `medication_possession_ratio`, `denosumab_gap_days` and `discontinuation_reason_code` all null. `cumulative_therapy_months` starts at zero and `holiday_eligible` at false; both are numbers rather than nulls from the outset and are only refreshed at review time. `adherence_source_policy` defaults to `CLAIMS_ONLY`.

Refills accumulate between reviews. A `PatientPortalUser` may record their own, and an `InterpretingPhysician` may record any; a portal user posting to another patient's plan is refused with `ERR_PATIENT_SCOPE_VIOLATION`. Each **adherence refill** carries `dispensed_date`, `days_supplied` from 1 through 400, and `source` of `PHARMACY_CLAIM` or `PATIENT_REPORT`. The `dispensed_date` must fall on or after the plan's `start_date` and strictly before the logical clock date, otherwise the request is refused with `ERR_REFILL_DATE_OUT_OF_WINDOW`. The row computes `source_weight` — 1.0 for a pharmacy claim and 0.5 for a patient report — and `coverage_end_date`, the `dispensed_date` advanced by `days_supplied` days. `recorded_by_user_id` holds the caller's `X-User-ID`, or the patient's own `id` when the recorder is a portal user. Recording a refill deliberately does **not** recompute the plan's ratio: the refill is evidence, and evidence is only scored at review time. Like a phantom run, a refill is an immutable observation with only `id` and `created_at`. A refill posted to a `DISCONTINUED` plan is refused with `ERR_TREATMENT_PLAN_TERMINAL`, and that refusal is reached only after the portal caller's own patient scope has been checked, so a portal user posting to another patient's discontinued plan still sees `ERR_PATIENT_SCOPE_VIOLATION`.

An `InterpretingPhysician` performs an **adherence review**, optionally supplying a `requested_action`, a free-text `note` and a `discontinuation_reason_code`. A review is accepted only when the logical clock date is at or after `next_followup_due_date` less seven days — a one-week early window — and is otherwise refused with `ERR_FOLLOWUP_NOT_DUE`. Reviewing a `DISCONTINUED` plan is refused with `ERR_TREATMENT_PLAN_TERMINAL`, since that status is terminal, and that refusal is evaluated **before** the due-date test, so a discontinued plan reports the terminal status rather than `ERR_FOLLOWUP_NOT_DUE` even when its next review is still months away. The `note` is bounded at 480 characters and is validated like any other field, but it is not stored anywhere on the plan and does not appear in the response: it is accepted for the caller's convenience and then discarded. A `requested_action` of `DISCONTINUE` sent without a `discontinuation_reason_code` is refused with `ERR_INVALID_REQUEST` and 422 at the shape rung, before `plan_id` is resolved, so that combination is reported even when the addressed plan does not exist.

The medication possession ratio is then recomputed from scratch. `adherence_window_days` is the whole number of days from the plan's `start_date` to the clock date at review time. Eligible refills are those dispensed on or after the start date and strictly before the review date, so a refill dispensed on the review date itself is excluded — the window is half-open at its upper end, and because the refill entity already forbids a `dispensed_date` at or after the clock date, that edge is never actually contested. `covered_days_supplied` is the sum over eligible refills of `days_supplied` multiplied by the applicable weight, and this is where the plan's `adherence_source_policy` splits into two variants over the very same stored rows. Under `CLAIMS_ONLY`, rows whose `source` is `PATIENT_REPORT` are **dropped entirely**. Under `ALL_SOURCES_WEIGHTED` they contribute half of their supplied days. Overlapping coverage is deliberately **not** de-duplicated: two refills covering the same calendar days both count in full, which is exactly why the ratio is capped. `medication_possession_ratio` is `covered_days_supplied` divided by `adherence_window_days`, clamped to a maximum of 1.5, and then rounded half up to three decimal places; because of the half-weight, `covered_days_supplied` keeps one decimal place. Two hundred supplied days across a ninety-one-day window therefore reads 1.500, not 2.198. A ninety-one-day window holding two thirty-day pharmacy claims and one thirty-day patient report reads 0.659 and `PARTIAL` under `CLAIMS_ONLY` but 0.824 and `ADHERENT` under `ALL_SOURCES_WEIGHTED` — identical rows, different verdict, decided solely by the policy chosen when the plan was opened.

`adherence_status` reads the rounded ratio: `ADHERENT` at 0.800 or above, `PARTIAL` from 0.500 up to but not including 0.800, and `NON_ADHERENT` below 0.500. Exactly 0.800 is adherent and 0.799 is partial; exactly 0.500 is partial and 0.499 is non-adherent. A ninety-day window with forty-two plus thirty claimed days lands on exactly 0.800.

Denosumab is handled specially because a lapsed injection carries a rebound-fracture risk that a possession ratio does not capture. For a `drug_class` of `DENOSUMAB` only, `denosumab_gap_days` is the whole number of days from the latest eligible refill's coverage end — its `dispensed_date` advanced by `days_supplied` — to the review date, "latest" meaning the eligible refill ranked highest by `dispensed_date`, then by `created_at`, then by the server's internal creation sequence, so two refills dispensed on the same date are separated by which was recorded second and the coverage end is taken from that one alone rather than from the longest supply, floored at zero so live coverage reads 0 rather than a negative number; it is null for every other drug class and null when no eligible refill exists. When that gap exceeds 210 days `adherence_status` is **overridden** to `NON_ADHERENT` regardless of the computed ratio, and the plan is then advanced by exactly the status rules a `NON_ADHERENT` verdict follows, described below — so a denosumab plan with a possession ratio of 1.000 can still be put on hold when the last injection lapsed more than 210 days ago.

Two further figures are refreshed at each review. `cumulative_therapy_months` is the completed whole calendar months between `start_date` and `last_review_date`. `holiday_eligible` is true only when all three conditions hold: the `drug_class` is `BISPHOSPHONATE_ORAL` or `BISPHOSPHONATE_IV`, `cumulative_therapy_months` has reached sixty, and the session behind the patient's `last_finalized_report_id` has a `lowest_t_score` above −2.5. The third condition is evaluated as a genuine test on real data rather than being waived when the data is absent: a patient with no `last_finalized_report_id` at all, and a patient whose latest finalized session carries a null `lowest_t_score`, both fail it, so `holiday_eligible` reads false in either case. Exactly −2.5 also fails, the comparison being strictly greater than. Only bisphosphonates have the residual skeletal effect that makes a planned interruption safe, and only a patient who is no longer osteoporotic on their most recent study should be interrupted at all.

The plan's `status` then advances. An `ADHERENT` or `PARTIAL` verdict resets `consecutive_nonadherent_reviews` to zero whatever the plan's current status, but only a plan in `INITIATED` or `ADHERENCE_HOLD` is moved to `ON_THERAPY` by it: a plan already `ON_THERAPY` simply stays there, and a plan in `DRUG_HOLIDAY` keeps its holiday and merely has its counter cleared. From `INITIATED` or `ON_THERAPY`, a `NON_ADHERENT` verdict — or a denosumab gap beyond its limit — moves the plan to `ADHERENCE_HOLD` and increments `consecutive_nonadherent_reviews`. From `ADHERENCE_HOLD`, a further `NON_ADHERENT` verdict that brings `consecutive_nonadherent_reviews` to two moves the plan to `DISCONTINUED` with `discontinuation_reason_code` `ADHERENCE_FAILURE`. A plan sitting in `DRUG_HOLIDAY` is left entirely alone by a `NON_ADHERENT` verdict or an exceeded denosumab gap — its status does not change and `consecutive_nonadherent_reviews` does not move — because a patient on a planned interruption is not expected to be dispensing anything; only the explicit actions below take such a plan out of its holiday. That closes the first cycle in this entity — `ON_THERAPY` to `ADHERENCE_HOLD` and back to `ON_THERAPY` — with a bounded escape hatch after two consecutive failures.

Three explicit `requested_action` values override the automatic resolution, and `AUTO` is the default that lets the verdict decide. `START_DRUG_HOLIDAY` moves an `ON_THERAPY` plan to `DRUG_HOLIDAY`, but only when `holiday_eligible` is true **and** the current verdict is `ADHERENT` — and the `holiday_eligible` consulted is the one this very review has just recomputed, not the value the plan carried on arrival, so a plan that crosses sixty cumulative months at this review may begin its holiday in the same call — a patient who is not taking their medication is not granted a holiday from it — and sets `next_followup_due_date` to the review date advanced by twenty-four calendar months, since a holiday is monitored on a much longer cycle. `RESUME_THERAPY` moves a `DRUG_HOLIDAY` plan back to `ON_THERAPY` and restores the drug's own `followup_interval_months` cadence, closing the entity's second cycle. `DISCONTINUE` moves a plan in any of `INITIATED`, `ON_THERAPY`, `ADHERENCE_HOLD` or `DRUG_HOLIDAY` to `DISCONTINUED` and requires an explicit `discontinuation_reason_code` of `ADVERSE_EVENT`, `GOAL_MET`, `PATIENT_REQUEST` or `ADHERENCE_FAILURE` in the body. An explicit action whose preconditions are not all met is neither refused nor a silent no-op: it falls through to the automatic resolution above and is answered exactly as an `AUTO` review would have been, so `START_DRUG_HOLIDAY` against a plan that is not `ON_THERAPY`, or that is not `holiday_eligible`, or whose current verdict is not `ADHERENT`, and `RESUME_THERAPY` against a plan that is not in `DRUG_HOLIDAY`, all answer HTTP 200 with whatever the verdict alone dictates. `DISCONTINUE` never falls through, since every status a reviewable plan can be in is discontinuable. The twenty-four-month cadence belongs to the review that actually starts the holiday and to no other: a later review taken while the plan already sits in `DRUG_HOLIDAY` advances `next_followup_due_date` by the drug's own `followup_interval_months` again. A `discontinuation_reason_code` sent alongside any action other than `DISCONTINUE` is validated against the enumeration and then ignored, and an automatic discontinuation after two consecutive failures always records `ADHERENCE_FAILURE` whatever the body carried. Every review, whatever its outcome, increments `adherence_review_count`, sets `last_review_date` to the clock date, and advances `next_followup_due_date` from that review date by the plan's `followup_interval_months` — the holiday-starting review, with its twenty-four months, being the one exception — so even a review that discontinues the plan leaves a due date in the future. `discontinuation_reason_code` is populated exactly when `status` is `DISCONTINUED` and null otherwise, and `DISCONTINUED` is terminal — the plan accepts neither refills nor reviews afterwards.

## 4. Endpoint Definitions

Every endpoint below is mounted under the `/bone-density` prefix, requires both the `X-User-ID` and `X-User-Role` headers, and returns the standard envelope described in §2.2. Creation endpoints return HTTP 201 with the created resource in `data`; action endpoints that transition an existing resource return HTTP 200 with the affected resource; list endpoints return HTTP 200 with an array in `data` and the pagination fields in `meta`; the logical-clock endpoint returns HTTP 204 with an empty `data` object. The test that separates the first two kinds is what the call persists: a mutating endpoint answers HTTP 201 only when it stores a brand-new resource row and returns that new row in `data`, and otherwise answers HTTP 200 with the pre-existing resource it affected. `POST /bone-density/densitometers/{id}/precision-assessment` therefore answers HTTP 200 with the addressed `Densitometer`, since a precision study is recorded onto the device rather than stored as a resource of its own. Path identifiers resolve after the body's own shape has been checked but before any foreign key carried *inside* the body is resolved — the shape rung of §2.7 sits at priority 3, the path-identifier rungs at 4 through 15 and the body foreign keys at 16 — so a request that both names an unknown resource in its path and sends a malformed body is answered with `ERR_INVALID_REQUEST` and 422 rather than with the not-found code. Beyond that, the rejection ordering of §2.7 governs which error surfaces when more than one rule is broken.

## 5. Error Code Catalogue

Every failure response carries one of the error identifiers below in `data.error_id`, together with the HTTP status code paired with it here. The identifier is the contract: clients match on it rather than on the human-readable `message`. When a single request breaks more than one rule, the identifier returned is the one whose validation sits earliest in the rejection ladder of §2.7.

Three further identifiers sit outside the business catalogue below because they answer requests that never reach a business rule, and they are still delivered in the same error envelope of §2.2. A request whose method and path match no endpoint in §4 at all returns `ERR_NOT_FOUND` with HTTP 404 — distinct from the per-entity 404s below, which mean a real endpoint was addressed with an unknown id. A request whose path matches an endpoint but whose HTTP method that endpoint does not support returns `ERR_METHOD_NOT_ALLOWED` with HTTP 405. An unanticipated server fault returns `ERR_INTERNAL` with HTTP 500. These three sit *above* the whole ladder of §2.7, routing being what happens before any check in it: a request to an unrouted path or with an unsupported method is answered with `ERR_NOT_FOUND` or `ERR_METHOD_NOT_ALLOWED` even when it also carries no `X-User-ID` and `X-User-Role` at all, so it never reports `ERR_UNAUTHENTICATED`. Paths are matched with a trailing slash treated as insignificant, so `/bone-density/patients` and `/bone-density/patients/` address the same endpoint rather than the second one falling through to `ERR_NOT_FOUND`.
