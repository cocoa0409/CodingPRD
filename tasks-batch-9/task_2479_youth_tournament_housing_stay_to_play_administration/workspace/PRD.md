# Youth Tournament Housing API — Product Requirements Document

## 1. Introduction

Amateur youth sports events live or die on hotel economics. A regional tournament brings hundreds of families into a destination for a long weekend, and the event's ability to pay for referees, venues and awards depends almost entirely on the rebate the host hotels return on the room nights those families consume. To make that revenue predictable, organizers operate an **official housing program**: hotels are contracted at negotiated rates with committed room blocks and rebate terms, and participating teams are required to book through the program rather than shopping independently. That requirement — the **stay-to-play policy** — is the single most contested rule in youth sports administration, because it is simultaneously the mechanism that funds the event and the mechanism that families experience as a constraint on their own money.

This document specifies the API for a youth tournament housing administration platform that runs both sides of that bargain. On the supply side it manages host hotel contracting, room block inventory, per-night capacity, block release at cutoff, attrition exposure, rebate invoicing against actualized room nights, and the split of collected revenue between the event organizer, the sanctioning rights holder and the destination marketing organization. On the demand side it manages team registration, roster-derived room requirements, booking deadlines, rooming list collection, change and cancellation penalties graded by how close to arrival the change lands, exception requests for local teams and family circumstances, and complaints about pricing and policy fairness.

Two design commitments run through every requirement below. The first is that **compliance is derived, never asserted**: a team's stay-to-play posture is recomputed from its bookings and its granted exemptions every time either changes, and the event's own posture is likewise a function of its contracts, its invoices and its payouts. The second is **segregation of duties**: the reviewer who denies an exemption may not decide its appeal, the rights holder who upholds a rebate-transparency complaint may not approve that event's payout, and the adjudicator of a complaint may not be the person whose exemption decision the complaint disputes. Every service in this API is mounted under the `/housing` prefix, with the sole exception of the logical-clock control endpoint described in §2.5.

## 2. Global Specifications & System-Wide Principles

### 2.1. Actors, Headers and Role-Based Access Control

Every request to this API must carry two headers: `X-User-ID`, identifying the acting principal, and `X-User-Role`, naming the role that principal is acting under. If either header is absent or present but empty, the request is rejected with `ERR_MISSING_AUTH_HEADERS` and HTTP 401. If `X-User-Role` carries a value that is not one of the five roles enumerated below, the request is rejected with `ERR_UNKNOWN_ROLE` and HTTP 401. If the role is recognised but does not appear in the authorised-role list of the endpoint being called (§4), the request is rejected with `ERR_ROLE_NOT_PERMITTED` and HTTP 403.

The five roles are spelled exactly as follows.

- **`HousingManager`** — the amateur sports event housing manager who runs the official housing program. This role creates tournaments, hotels and teams, drafts and submits hotel contracts, holds and releases room blocks, confirms bookings, closes the housing window, triages complaints, raises rebate invoices, issues and writes off those invoices, creates revenue distributions and pays them out. It also drives the logical clock.
- **`ExceptionReviewer`** — the independent reviewer of stay-to-play exception requests. This role holds the only decision authority over exemptions: it starts reviews, requests further information, approves and denies.
- **`RightsHolder`** — the event rights holder, which adjudicates fairness complaints and approves the organizer / rights-holder / destination revenue split.
- **`TeamManager`** — the manager of a participating team, who registers the team for an event, books rooms, submits rooming lists, cancels bookings, files exception requests and appeals, and files complaints.
- **`HotelRepresentative`** — the representative of a host hotel, who countersigns or revises its own contracts, reports the room nights actually consumed, and remits or disputes rebate invoices.

Identity binding differs by role. When `X-User-Role` is `TeamManager`, `X-User-ID` is the `id` of the acting `Team`; ownership checks on any resource that references a `Team` compare the resource's team reference to `X-User-ID`. When `X-User-Role` is `HotelRepresentative`, `X-User-ID` is the `id` of the acting `Hotel`; ownership checks on any resource that references a `Hotel` compare the resource's hotel reference to `X-User-ID`. For both of these entity-backed roles, an `X-User-ID` that matches no row of the backing entity — no `Team` for a `TeamManager`, no `Hotel` for a `HotelRepresentative` — is rejected with `ERR_ACTOR_IDENTITY_UNKNOWN` and HTTP 403. This check applies to every endpoint whose authorised roles include `TeamManager` or `HotelRepresentative`.

When `X-User-Role` is `HousingManager`, `ExceptionReviewer` or `RightsHolder`, `X-User-ID` is an opaque operator identifier not tied to any persisted entity. The server records it wherever a state transition captures the acting operator — as `triaged_by_user_id` and `adjudicated_by_user_id` on a complaint, as `decided_by_user_id` on an exception request, and as `approved_by_user_id` on a revenue distribution — but it never compares those values to any entity's `id`. It does compare them to each other, which is how segregation of duties is enforced (§2.10). The one operator identifier that *is* entity-bound is `countersigned_by_hotel_id` on a hotel contract: it stores the `X-User-ID` of the `HotelRepresentative` that countersigned, and because that role is backed by `Hotel`, its value is a hotel identifier.

Two scope rules narrow entity-backed roles to their own data. A `TeamManager` may only act where `X-User-ID` equals the team reference of the registration the target resource belongs to; a violation yields `ERR_TEAM_SCOPE_VIOLATION` and HTTP 403. This guards seven operations: `POST /housing/team-registrations`, `POST /housing/bookings`, `POST /housing/bookings/{id}/rooming-list`, `POST /housing/bookings/{id}/cancel`, `POST /housing/exception-requests`, `POST /housing/exception-requests/{id}/team-action` and `POST /housing/complaints`. A `HotelRepresentative` may only act where `X-User-ID` equals the hotel reference of the contract the target resource belongs to; a violation yields `ERR_HOTEL_SCOPE_VIOLATION` and HTTP 403. This guards four operations: `POST /housing/hotel-contracts/{id}/negotiation`, `POST /housing/bookings/{id}/actualizations`, `POST /housing/rebate-invoices/{id}/lifecycle` and `POST /housing/rebate-invoices/{id}/remit`.

Three endpoints accept several different `action` values from two different roles, and on those endpoints role authorisation is per-action rather than per-endpoint. On `POST /housing/hotel-contracts/{id}/negotiation`, the value `SUBMIT` requires `HousingManager` while `COUNTERSIGN` and `REVISE` require `HotelRepresentative`. On `POST /housing/rebate-invoices/{id}/lifecycle`, the values `ISSUE` and `WRITE_OFF` require `HousingManager` while `DISPUTE` requires `HotelRepresentative`. On `POST /housing/revenue-distributions/{id}/advance`, the value `APPROVE` requires `RightsHolder` while `PAY` requires `HousingManager`. A permitted role asking for an action that belongs to the other role is rejected with `ERR_ACTION_ROLE_MISMATCH` and HTTP 403.

### 2.2. API Response Structure

#### Standard Success Response Format

All successful API responses (those with 2xx status codes) follow this standard envelope format in their JSON body:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z",
    "limit": 10,
    "offset": 0,
    "total_count": 100,
    "has_more": true
  },
  "response_type": "object" | "array",
  "data": { }
}
```

- The `api_request_id` is a server-generated unique identifier for the request that starts with `req_`.
- The `api_request_timestamp` is a server-generated ISO 8601 UTC timestamp with three fractional digits.
- The `response_type` is either "object" for a single resource or "array" for a list of resources.
- The `data` field contains the resource object or an array of resource objects. For 2xx responses with no data, it contains an empty object. Unless otherwise noted, operations that create or modify a resource will return the created or updated resource object in the data field.
- Pagination-related fields in `meta` (`limit`, `offset`, `total_count`, `has_more`) are included for list endpoints.

#### Standard Error Response Format

All error API responses (4xx status codes) follow this standard envelope format:

```json
{
  "meta": {
    "api_request_id": "req_RANDOMALPHANUM123456",
    "api_request_timestamp": "2025-05-24T10:30:00.123Z"
  },
  "response_type": "error",
  "data": {
    "error_id": "UNIQUE_ERROR_IDENTIFIER_STRING",
    "message": "A human-readable explanation of the error."
  }
}
```

- The `meta` object for error responses contains only `api_request_id` and `api_request_timestamp`.
- The `error_id` is a unique, machine-readable string that identifies the specific error.
- The `message` provides a human-readable explanation of what went wrong.

### 2.3. Pagination and List Ordering

Every list endpoint accepts two optional query parameters. `limit` controls page size: its default is 10, its minimum accepted value is 1 and its maximum accepted value is 100. `offset` controls the starting position: its default is 0 and its minimum accepted value is 0. A `limit` below 1 or above 100, or a negative `offset`, is a schema violation and is rejected with `ERR_INVALID_REQUEST` and HTTP 400.

List results are ordered by `created_at` ascending unless a subsection states otherwise. The one documented exception is the list of actualization reports for a booking, which is ordered by `sequence_no` ascending; because sequence numbers are assigned in creation order, the two orderings coincide. For every list response, the `meta` block carries `limit`, `offset`, `total_count` and `has_more`, where `total_count` is the number of rows matching the filters before pagination and `has_more` indicates whether rows remain beyond the current page. List endpoints additionally accept the domain filters named in their §4 descriptions; a filter that is supplied narrows the result set by exact match on the named field, and filters combine conjunctively.

### 2.4. Resource Identity, Timestamps and Record Versions

Every persisted resource carries a server-minted `id`, which is a UUID string with no type prefix and no client-supplied component. Every resource also carries `created_at`, an ISO 8601 UTC timestamp with three fractional digits recording when the row was inserted.

Most resources additionally carry `updated_at`, an ISO 8601 UTC timestamp in the same format, and `version`, an integer that starts at 1 when the row is created and is incremented by exactly 1 on every mutation of that row. The resources that carry the full set of `id`, `created_at`, `updated_at` and `version` are: `Tournament`, `Hotel`, `HotelContract`, `RoomBlock`, `Team`, `TeamRegistration`, `Booking`, `ExceptionRequest`, `Complaint`, `RebateInvoice` and `RevenueDistribution`.

Two resources are append-only records of a moment rather than mutable rows, and they carry only `id` and `created_at`. Neither `updated_at` nor `version` exists on a `RoomingListEntry`, and neither exists on an `ActualizationReport`. A rooming list is revised by replacing its entries wholesale rather than by editing them, and an actualization figure is restated by filing a further report rather than by editing the prior one, so there is nothing on either record to version.

Version increments are not confined to the row the request names. Whenever an operation changes a field on a related resource — a registration's committed room count, a block's utilization, a contract's block posture, a tournament's pressure indicator — that related resource's own `updated_at` is refreshed and its own `version` is incremented by 1. A resource whose fields are re-derived to the same values it already held is not re-versioned. §2.9 governs how far these propagations reach.

### 2.5. The Logical Housing Clock

Every deadline in this domain — the booking deadline, the contract cutoff, the block release deadline, the cancellation penalty tiers — is evaluated against a **logical UTC clock** maintained by the server rather than against wall-clock time. The clock's startup value is exactly `2026-08-01T00:00:00Z`. Before any call that moves it, the logical clock reads that value, and at no point does the server fall back to real wall-clock time.

A `HousingManager` moves the clock by calling `POST /_clock/set_current_utc` with a body carrying `to_iso8601`, the instant the clock should read. The response body reports `current_utc`, the instant now in effect. Note that this endpoint sits outside the `/housing` prefix. Every timestamp the server stamps onto a resource — `created_at`, `updated_at`, `cancelled_at`, `compliance_evaluated_at` — reads the logical clock, so a test-driven sequence of operations produces deterministic timestamps.

### 2.6. Path Resolution and Reference Integrity

Path parameters are resolved left to right. For a path with more than one templated segment, the outer resource is looked up before the inner one, and the first segment that resolves to nothing determines the error. The 404 error identifier is chosen by the type of resource that was not found: `ERR_TOURNAMENT_NOT_FOUND`, `ERR_CONTRACT_NOT_FOUND`, `ERR_ROOM_BLOCK_NOT_FOUND`, `ERR_REGISTRATION_NOT_FOUND`, `ERR_BOOKING_NOT_FOUND`, `ERR_EXCEPTION_REQUEST_NOT_FOUND`, `ERR_COMPLAINT_NOT_FOUND`, `ERR_INVOICE_NOT_FOUND` or `ERR_DISTRIBUTION_NOT_FOUND`.

References supplied in a request body are resolved by the same principle after path resolution completes. Each reference must resolve to an existing row, and the 404 identifier is again chosen by referenced type, drawn from `ERR_TOURNAMENT_NOT_FOUND`, `ERR_HOTEL_NOT_FOUND`, `ERR_TEAM_NOT_FOUND`, `ERR_CONTRACT_NOT_FOUND`, `ERR_ROOM_BLOCK_NOT_FOUND`, `ERR_REGISTRATION_NOT_FOUND`, `ERR_BOOKING_NOT_FOUND`, `ERR_EXCEPTION_REQUEST_NOT_FOUND` and `ERR_INVOICE_NOT_FOUND`. Body-reference resolution is performed on `POST /housing/hotel-contracts`, `POST /housing/room-blocks`, `POST /housing/team-registrations`, `POST /housing/bookings`, `POST /housing/exception-requests`, `POST /housing/complaints`, `POST /housing/rebate-invoices` and `POST /housing/revenue-distributions`.

Requests are also checked against the endpoint's input schema: required fields must be present, unknown fields are refused, enum-typed fields must carry a declared member, integer counts must respect their declared non-negativity, dates and datetimes must be well-formed ISO 8601 values, and pagination parameters must fall in range. Any of these failures produces `ERR_INVALID_REQUEST` with HTTP 400.

### 2.7. Rooms, Cents and Rounding Discipline

All money in this system is carried in **whole cents** as integers. There are no fractional-cent fields and no floating-point currency. Wherever a monetary amount is derived from a multiplication involving a fraction, the result is rounded **half up** to a whole cent — that is, a computed value whose fractional part is exactly one half rounds away from zero to the next whole cent.

Two deliberate departures from half-up rounding exist, and both matter. First, when a single collected amount is divided into party shares, each share is computed by **truncating toward zero** — taking the whole-cent floor of the product — and the cents left over by that truncation are then reassigned in full, as described in §3.9. Second, wherever room *nights* are derived from a fractional threshold, the result is rounded **up to the next whole room night** rather than half up, because a partial night of contractual exposure is still a night of exposure.

Room counts, room-night counts, roster head counts and night counts are all exact integers. Ratios are the only non-integer quantities in the system. A block's `utilization_pct` is carried as a decimal fraction rounded half up to **four** decimal places. A contract's `rebate_percent` is a decimal fraction with **four** decimal places, and its `attrition_threshold_pct` is a decimal fraction with **two** decimal places. A tournament's three revenue-share percentages — `share_pct_organizer`, `share_pct_rights_holder` and `share_pct_destination` — are decimal fractions with **two** decimal places. A distribution's `admin_fee_pct` is a decimal fraction selected from a fixed tier table.

One further ordering rule governs any aggregate that sums money derived per line: **each line is rounded to whole cents first, and the rounded lines are then summed.** Summing unrounded products and rounding the single total at the end is not equivalent and is not what this system does.

### 2.8. Stale-Version Guards on Booking and Distribution Creation

Two creation endpoints participate in optimistic concurrency control, and they are the only two. Each requires the client to declare the `version` of a parent resource it last observed, as a non-optional field of the request body. Every other endpoint in this API takes no version field at all.

`POST /housing/bookings` requires `expected_registration_version`, carrying the client's last observed `version` of the `TeamRegistration` named by the booking's registration reference. If that value does not equal the registration's current `version`, the create is rejected with `ERR_STALE_REGISTRATION_VERSION` and HTTP 412. This guard exists because booking creation may legitimately supersede an earlier booking for the same registration, so it cannot be barred by a state precondition; a client whose view of the registration predates another writer's supersede would otherwise re-house a roster that has already been re-housed. Successful booking creation itself increments the registration's `version` by 1, so a client holding a stale view learns of it deterministically.

`POST /housing/revenue-distributions` requires `expected_invoice_version`, carrying the client's last observed `version` of the `RebateInvoice` named by the distribution's source-invoice reference. If that value does not equal the invoice's current `version`, the create is rejected with `ERR_STALE_INVOICE_VERSION` and HTTP 412. A second distribution against the same invoice is legitimate once further remittance has raised the collected amount, so again a state precondition cannot serve; the version check instead pins the snapshot of collected cents the split was computed from. Successful distribution creation increments the invoice's `version` by 1.

### 2.9. Posture Propagation and Cascade Discipline

This system has no single ownership tree. Room block inventory is shared across teams through bookings, a booking may point at the booking it replaces, a complaint may point at a registration, at an exception decision and at a booking, and a revenue distribution joins a tournament to an invoice. Consistency is therefore maintained not by a hierarchy but by **derivation chains**: a small number of persisted aggregate fields are recomputed, in a fixed order, every time a fact underneath them changes.

Four such chains recur throughout §3, and each is named there so it can be referred to compactly.

- **The confirm chain.** Confirming a booking recomputes the registration's committed room total and re-derives its compliance status; that same recompute epoch refreshes the block's committed, available and utilization figures, which may flip the block's own status; the flip recomputes the owning contract's block posture, which may reach a sold-out reading; and that in turn recomputes the tournament's executed and sold-out contract counters and its housing pressure indicator. Four links deep, from one booking to one tournament.
- **The close chain.** Closing the housing window re-evaluates every pending registration of the event, which forces some of them to a non-compliant reading; every still-open exception request belonging to a registration that just became non-compliant is denied by the system; and each touched registration is then re-derived again, because denying its exception request changed its exempt-room total.
- **The remit chain.** Paying an invoice in full settles the invoice, which advances every booking in that invoice's scope along its money axis, which allows the released blocks of the contract to reach a settled reading, which allows the contract itself to close, which allows the event to settle.
- **The remedy chain.** Upholding an escalated complaint with a policy exemption approves the denied exception request the complaint cites, which recomputes the registration's exempt-room total and effective requirement, which re-derives that registration's compliance status.

Every resource whose fields a chain actually changes has its `updated_at` refreshed and its `version` incremented by 1, including resources several links away from the one the request named. Where a chain link is described as "re-evaluated", the meaning is that the transition's own preconditions are tested and the transition fires only if they all hold; a re-evaluation whose preconditions fail is not an error and leaves the resource untouched.

### 2.10. Segregation of Duties Across Exemptions, Complaints and Payouts

Three independence rules prevent one operator from both making a decision and reviewing it.

First, an exemption appeal must be decided by a different reviewer than the original decision. When an exception request's appeal counter is at least 1, an approve or deny action whose `X-User-ID` equals the request's recorded `decided_by_user_id` is rejected with `ERR_SOD_SAME_REVIEWER` and HTTP 403. Before any appeal has been filed, the same reviewer may freely decide, request information and decide again.

Second, a complaint that disputes an exemption decision may not be adjudicated by the operator who made that decision. When a complaint carries a cited exception request, an adjudication whose `X-User-ID` equals that request's `decided_by_user_id` is rejected with `ERR_SOD_ADJUDICATOR_CONFLICT` and HTTP 403.

Third, a rights holder that has upheld a rebate-transparency complaint on an event may not approve that event's payout. If any complaint on the same tournament has category `REBATE_TRANSPARENCY`, status `UPHELD`, and an `adjudicated_by_user_id` equal to the acting `X-User-ID`, the approve action on a revenue distribution of that tournament is rejected with `ERR_SOD_DISTRIBUTION_APPROVER_CONFLICT` and HTTP 403.

Note that the system itself is a permitted decider. When the platform decides an exemption without a human — auto-approving a local team under housing pressure, denying an undecided request at window close, or approving a request as a complaint remedy — it records the literal string `SYSTEM_AUTO` as `decided_by_user_id`. Because no operator's `X-User-ID` can equal that literal, a system decision never blocks a later human reviewer or adjudicator.

### 2.11. Rejection Precedence

When a single request violates more than one rule, exactly one error is returned, and which one is fully determined. Checks are evaluated in the fixed order below, and the first failing check produces the response; later checks are not evaluated and cannot mask an earlier one. The order is global: a check that appears earlier in this ladder outranks a check that appears later regardless of which endpoint they meet on.

1. Both `X-User-ID` and `X-User-Role` are present and non-empty — otherwise `ERR_MISSING_AUTH_HEADERS`.
2. `X-User-Role` names one of the five declared roles — otherwise `ERR_UNKNOWN_ROLE`.
3. The acting role appears in the endpoint's authorised-role list — otherwise `ERR_ROLE_NOT_PERMITTED`.
4. For the entity-backed roles, `X-User-ID` resolves to a row of the backing entity — otherwise `ERR_ACTOR_IDENTITY_UNKNOWN`.
5. Every path-templated resource exists, resolved left to right — otherwise the not-found identifier for that resource type.
6. Every reference supplied in the request body resolves — otherwise the not-found identifier for the referenced type.
7. A `TeamManager` is acting within its own team's registration scope — otherwise `ERR_TEAM_SCOPE_VIOLATION`.
8. A `HotelRepresentative` is acting within its own hotel's contract scope — otherwise `ERR_HOTEL_SCOPE_VIOLATION`.
9. The request body conforms to the endpoint's input schema, including pagination ranges — otherwise `ERR_INVALID_REQUEST`.
10. On a multi-action endpoint, the requested `action` belongs to the acting role — otherwise `ERR_ACTION_ROLE_MISMATCH`.
11. `expected_registration_version` matches the registration's current `version` on booking creation — otherwise `ERR_STALE_REGISTRATION_VERSION`.
12. `expected_invoice_version` matches the source invoice's current `version` on distribution creation — otherwise `ERR_STALE_INVOICE_VERSION`.
13. The target resource's current state is a declared source state of the requested transition — otherwise `ERR_INVALID_STATE`.
14. The governing tournament's `posture` is `OPEN`, where the operation requires it — otherwise `ERR_TOURNAMENT_NOT_OPEN`.
15. The governing tournament's `posture` is `BOOKING_CLOSED` or `RECONCILING`, where the operation requires it — otherwise `ERR_TOURNAMENT_NOT_RECONCILING`.
16. The governing hotel contract's `status` is `EXECUTED`, where the operation requires it — otherwise `ERR_CONTRACT_NOT_EXECUTED`.
17. The target room block's `status` is `OPEN` or `RESTRICTED`, where the operation requires it — otherwise `ERR_BLOCK_NOT_BOOKABLE`.
18. An actualization report targets a booking whose `booking_status` is `CONFIRMED` for the first report or `CHECKED_OUT` for a later one — otherwise `ERR_BOOKING_NOT_CONFIRMED`.
19. A revenue distribution's source invoice is `PARTIALLY_PAID` or `PAID` — otherwise `ERR_INVOICE_NOT_COLLECTED`.
20. An appeal is filed against a request whose appeal counter is still below the cap of one — otherwise `ERR_APPEAL_LIMIT_REACHED`.
21. Every rooming list entry lodging at least one minor names a chaperone — otherwise `ERR_CHAPERONE_REQUIRED`.
22. Every rooming list entry respects the four-occupant room ceiling and reports no more minors than occupants — otherwise `ERR_ROOM_OCCUPANCY_EXCEEDED`.
23. An appeal decision is taken by a different reviewer than the original decision — otherwise `ERR_SOD_SAME_REVIEWER`.
24. A complaint adjudicator is not the decider of the exception request the complaint cites — otherwise `ERR_SOD_ADJUDICATOR_CONFLICT`.
25. A distribution approver has not upheld a `REBATE_TRANSPARENCY` complaint on the same tournament — otherwise `ERR_SOD_DISTRIBUTION_APPROVER_CONFLICT`.
26. The logical clock is at or before the tournament's `booking_deadline` on booking creation — otherwise `ERR_BOOKING_DEADLINE_PASSED`.
27. In every supplied date pair, the later date is strictly after the earlier one — otherwise `ERR_INVALID_DATE_RANGE`.
28. A requested stay falls within its block's held window — otherwise `ERR_STAY_OUTSIDE_BLOCK_WINDOW`.
29. A new block's window falls within the padded event window — otherwise `ERR_BLOCK_OUTSIDE_EVENT_WINDOW`.
30. A block release happens at or after the block's `release_deadline` — otherwise `ERR_RELEASE_BEFORE_DEADLINE`.
31. A new block's `release_deadline` is at or after its contract's `cutoff_date` — otherwise `ERR_RELEASE_DEADLINE_BEFORE_CUTOFF`.
32. The booking team has no live stay at another block whose dates touch the requested stay — otherwise `ERR_TEAM_STAY_OVERLAP`.
33. A new block does not push the property past its physical inventory on any night — otherwise `ERR_HOTEL_NIGHT_CAPACITY_EXCEEDED`.
34. Submitted rooming list room indices form the required contiguous sequence — otherwise `ERR_ROOMING_LIST_INDEX_INVALID`.
35. The number of submitted rooming list entries equals the booking's requested room count — otherwise `ERR_ROOMING_LIST_ROOM_COUNT_MISMATCH`.
36. Total submitted occupants fall within the permitted range — otherwise `ERR_ROOMING_LIST_OCCUPANT_MISMATCH`.
37. A restricted block is being booked by a team that is not yet housed — otherwise `ERR_BLOCK_RESTRICTED_TO_UNHOUSED_TEAMS`.
38. A supplied `supersedes_booking_id` names an eligible booking of the same registration — otherwise `ERR_SUPERSEDE_TARGET_INVALID`.
39. The rebate parameter fields match the declared `rebate_model` — otherwise `ERR_REBATE_MODEL_FIELDS_INVALID`.
40. The three revenue-share percentages sum to exactly one — otherwise `ERR_REVENUE_SHARE_NOT_UNITY`.
41. The invoice's `period_label` is unused on that contract — otherwise `ERR_DUPLICATE_INVOICE_PERIOD`.
42. A `LOCAL_TEAM` exemption is requested by a registration flagged local — otherwise `ERR_LOCAL_EXEMPTION_NOT_ELIGIBLE`.
43. A `FAMILY_MEDICAL` exemption asks for no more than one room — otherwise `ERR_EXEMPTION_SCOPE_TOO_BROAD`.
44. `requested_rooms_exempt` does not exceed the registration's pooled compliance minimum — otherwise `ERR_EXEMPTION_EXCEEDS_REQUIREMENT`.
45. The registration has no other open or approved exception request — otherwise `ERR_DUPLICATE_OPEN_EXCEPTION`.
46. On approval, `approved_rooms_exempt` is supplied and falls in the permitted range — otherwise `ERR_APPROVED_EXEMPTION_OUT_OF_RANGE`.
47. A `LOCAL_TEAM` approval grants the full requested amount — otherwise `ERR_PARTIAL_LOCAL_EXEMPTION_FORBIDDEN`.
48. `rooms_requested` does not exceed the registration's segregated-occupancy room requirement — otherwise `ERR_ROOMS_EXCEED_ROSTER_REQUIREMENT`.
49. The booking does not push the block past its held room count on any night of the stay — otherwise `ERR_BLOCK_CAPACITY_EXCEEDED`.
50. A remittance amount is at least one cent and no more than the invoice's outstanding balance — otherwise `ERR_REMITTANCE_EXCEEDS_OUTSTANDING`.
51. A new invoice's scope contains at least one booking and at least one billable room night — otherwise `ERR_NO_BILLABLE_ROOM_NIGHTS`.
52. An invoice being issued has a positive amount due — otherwise `ERR_INVOICE_TOTAL_NOT_POSITIVE`.
53. The remedy amount and the complaint's affected booking match the chosen `remedy_type` — otherwise `ERR_REMEDY_FIELDS_INVALID`.
54. The chosen `remedy_type` belongs to the triage branch's remedy vocabulary — otherwise `ERR_REMEDY_NOT_AVAILABLE_ON_ROUTE`.
55. A complaint cites at least one subject — otherwise `ERR_COMPLAINT_SUBJECT_MISSING`.

The consequences of this ordering are worth spelling out on the endpoints where several of these checks converge. Booking creation, for example, meets checks 4, 6, 7, 9, 11, 14, 16, 17, 26, 27, 28, 32, 37, 38, 48 and 49; a request that is both past the booking deadline and oversells the block returns `ERR_BOOKING_DEADLINE_PASSED`, because the deadline check outranks the capacity check. Rooming list submission meets 9, 13, 14, 21, 22, 34, 35 and 36; an entry set that both omits a chaperone and has the wrong room count returns `ERR_CHAPERONE_REQUIRED`. Exception request filing meets 6, 7, 9, 14, 42, 43, 44 and 45; an ineligible local request that also duplicates an open request returns `ERR_LOCAL_EXEMPTION_NOT_ELIGIBLE`. Complaint adjudication meets 9, 13, 24, 53 and 54; a conflicted adjudicator supplying an out-of-vocabulary remedy is rejected on the conflict, not on the remedy.

### 2.12. Conservation Invariants

Two quantities in this system are conserved, and both must hold after every operation that touches them. They are the fixed points against which forward-and-compensating pairs of operations are judged.

**Room inventory conservation.** While a room block's `status` is `OPEN` or `RESTRICTED`, its `rooms_committed` and `rooms_available` sum to exactly `block_size_rooms`, and its `rooms_released_unsold` is 0. Once the block's `status` is `RELEASED` or `SETTLED`, its `rooms_committed` and `rooms_released_unsold` sum to exactly `block_size_rooms`, and its `rooms_available` is 0. A confirmation followed by the cancellation of that same booking must restore `rooms_committed`, `rooms_available` and `utilization_pct` to the values they held before the confirmation; no drift is permitted across such a pair.

**Rebate ledger conservation.** On every rebate invoice, `collected_cents`, `written_off_cents` and `outstanding_cents` sum to exactly `total_due_cents`, and none of the three is ever negative. The amount due is frozen when the invoice is created and is never re-derived by a remittance or by a lifecycle action. A partial remittance followed by a write-off must therefore leave `total_due_cents` unchanged, drive `outstanding_cents` to exactly 0, and park the abandoned cents in `written_off_cents`.

## 3. Business Logic & Workflows

### 3.1. Standing Up an Event and Its Participants

A `HousingManager` opens the season by creating the tournament record itself. The payload carries the event `name`, the `rights_holder_org` that sanctions it, the `destination_org` that markets the destination, the competition window as `start_date` and `end_date` (ISO 8601 calendar dates in `YYYY-MM-DD` form), the `booking_deadline` after which no further rooms may be booked for this event, and the three revenue-share fractions `share_pct_organizer`, `share_pct_rights_holder` and `share_pct_destination`. An optional `stay_to_play_required` boolean may be supplied; when it is omitted it defaults to `true`, meaning every registered team must end up either housing-compliant or exception-granted.

Two arithmetic conditions govern event creation. The `end_date` must be strictly after the `start_date`; a pair where the later date is not strictly greater is rejected with `ERR_INVALID_DATE_RANGE`. The three share fractions, each expressed with two decimal places, must add up to exactly one; any other total is rejected with `ERR_REVENUE_SHARE_NOT_UNITY`. When both hold, the server computes `night_count` as the number of whole days from `start_date` up to but not including `end_date` — the event window is half-open, so the night that begins on `end_date` is not part of the event. A five-day window from the 10th to the 15th therefore yields five nights. This value is stamped once at creation and never changes.

A new tournament begins with `posture` at `OPEN`, `housing_pressure` at `NORMAL`, and both derived contract counters — `executed_contract_count` and `sold_out_contract_count` — at 0. The `posture` field is the master gate for everything else in the system and it advances **monotonically** through `OPEN`, `BOOKING_CLOSED`, `RECONCILING` and `SETTLED`, never regressing. `OPEN` admits contracting, block creation, registration, booking, rooming-list and exception traffic. `BOOKING_CLOSED` admits actualization reporting and invoice creation. `RECONCILING` admits collection and payout work. `SETTLED` admits nothing further and is terminal. Operations that require `OPEN` and find something later are rejected with `ERR_TOURNAMENT_NOT_OPEN`; operations that require `BOOKING_CLOSED` or `RECONCILING` and find `OPEN` or `SETTLED` are rejected with `ERR_TOURNAMENT_NOT_RECONCILING`.

Properties and teams are registered independently of any one event, because both are reused across a season. A hotel record carries its `name`, its `city`, its `total_rooms` — the physical room inventory of the property, which must be at least 1 and which acts as the ceiling on aggregate per-night block capacity — and its `distance_miles_from_venue`, a non-negative driving distance used to order candidate host hotels. A team record carries its `name`, its `home_city`, its `home_state` as a two-letter state code, the `org_contact_email` of its manager, and its own non-negative `distance_miles_from_venue` measured from the team's home city to the competition venue. That last figure is the sole input to the local-team determination described in §3.3, and it is read from the team rather than from the registration that references it.

### 3.2. Host Hotel Contracting and Room Block Inventory

Contracting begins with a draft. A `HousingManager` drafts a host-hotel contract by supplying `tournament_id`, `hotel_id`, the `negotiated_nightly_rate_cents` (at least 1 cent per room per night), the `rebate_model`, the `attrition_threshold_pct`, the `attrition_penalty_rate_cents_per_room_night` (at least 0), and the `cutoff_date` — the instant after which unsold rooms in this contract's blocks may be handed back to the hotel. Drafting requires the tournament's `posture` to be `OPEN`. The `attrition_threshold_pct` is a two-decimal fraction that must be greater than zero and no greater than one: it is the share of contracted room nights the event must actually consume before damages apply.

The `rebate_model` selects one of three rebate structures, and the parameter fields must match the choice exactly. Under `PER_ROOM_NIGHT_FLAT`, `rebate_flat_cents_per_room_night` is required and must be at least 1, and `rebate_percent` must be omitted. Under `PERCENT_OF_ROOM_REVENUE`, `rebate_percent` is required and must be greater than zero and no greater than one, expressed with four decimal places, and `rebate_flat_cents_per_room_night` must be omitted. Under `TIERED_PER_ROOM_NIGHT`, both fields must be omitted, because the rate is derived from volume rather than declared. Any mismatch between the declared model and the supplied fields is rejected with `ERR_REBATE_MODEL_FIELDS_INVALID`. Whichever fields are omitted default to 0 on the stored record.

A freshly drafted contract sits at `status` `DRAFT` with `block_posture` `AVAILABLE`, `revision_round` at 0, `contracted_room_nights` at 0 and `countersigned_by_hotel_id` null. Negotiation is a three-action loop on a single capability. The housing manager's `SUBMIT` action moves the contract from `DRAFT` to `NEGOTIATING`, and it requires the tournament to be `OPEN` and at least one room block to already exist under the contract — a contract with no inventory has nothing to negotiate. From `NEGOTIATING`, the hotel's representative may take one of two actions, and in both cases `X-User-ID` must equal the contract's hotel reference. A `REVISE` action returns the contract to `DRAFT` and increments `revision_round` by 1; this cycle may repeat without bound, so a heavily negotiated contract may pass through `DRAFT → NEGOTIATING → DRAFT` many times, with `revision_round` counting exactly how many times it has done so. A `COUNTERSIGN` action moves the contract `NEGOTIATING → EXECUTED`, again requiring the tournament to be `OPEN`; it records `countersigned_by_hotel_id` as the acting `X-User-ID`, then recomputes the tournament's `executed_contract_count` and `sold_out_contract_count` and re-derives its `housing_pressure`.

Later in the event's life, an executed contract closes itself. The system re-evaluates the `EXECUTED → CLOSED` transition whenever any room block of the contract changes status; the transition fires only once at least one block exists under the contract and every one of them has reached `SETTLED`. Closing again recomputes the tournament's `executed_contract_count` and `sold_out_contract_count`, since both counters admit contracts in either `EXECUTED` or `CLOSED`.

Inventory is held in room blocks. Creating one requires `contract_id`, a `room_type` of `DOUBLE_QUEEN`, `KING` or `SUITE`, a `block_size_rooms` of at least 1 held on every night of the block window, the window itself as `arrival_date` and `departure_date`, and a `release_deadline`. The block window is half-open: `arrival_date` is the first night held and the night beginning on `departure_date` is **not** held, so a block from the 10th to the 13th holds three nights. The `departure_date` must be strictly after the `arrival_date`, or the request is rejected with `ERR_INVALID_DATE_RANGE`. The `release_deadline` must fall at or after the owning contract's `cutoff_date`; an earlier deadline is rejected with `ERR_RELEASE_DEADLINE_BEFORE_CUTOFF`. The block window must also sit inside the event window padded by two days on each side — that is, `arrival_date` must be no earlier than two days before the tournament's `start_date`, and `departure_date` no later than two days after its `end_date`; a window outside that envelope is rejected with `ERR_BLOCK_OUTSIDE_EVENT_WINDOW`. Block creation also requires the tournament to be `OPEN`.

The property's physical inventory constrains blocks in aggregate, per night, across every contract that property holds. For each night in the new block's half-open window, the system sums `block_size_rooms` over all existing room blocks whose contract points at the same hotel and whose own `status` is `OPEN` or `RESTRICTED` and whose own half-open window covers that night; if that sum plus the new `block_size_rooms` would exceed the hotel's `total_rooms` on any single night, the request is rejected with `ERR_HOTEL_NIGHT_CAPACITY_EXCEEDED`. Because the interval is half-open, adjacency is permitted: a block departing on the 13th and a block arriving on the 13th share no night and never collide. Note that this is a per-night **sum** against a ceiling, not an exclusive-occupation test — several blocks may cover the same night as long as their combined size fits the property.

A new block starts at `status` `OPEN` with `rooms_committed` at 0, `rooms_available` equal to `block_size_rooms`, `rooms_released_unsold` at 0, `utilization_pct` at 0 and `actualized_room_nights` at 0. The server also stamps `threshold_room_nights`, the block's attrition floor: multiply `block_size_rooms` by the number of whole nights in the block window, multiply by the contract's `attrition_threshold_pct`, and round the product **up** to the next whole room night. Finally, the block's contracted volume — `block_size_rooms` multiplied by its night count — is added into the contract's `contracted_room_nights`, which stands as the sum of that product over every block of the contract whose `status` is `OPEN`, `RESTRICTED`, `RELEASED` or `SETTLED`.

Two derived postures sit above block status and both are recomputed whenever a block is created or changes status. A contract's `block_posture` considers only its **live** blocks — those in `OPEN` or `RESTRICTED`; blocks in `RELEASED` or `SETTLED` are excluded from both the numerator and the denominator. If the contract has no live blocks at all, `block_posture` is `AVAILABLE`. If every live block is `RESTRICTED`, it is `SOLD_OUT`. If at least one live block is `RESTRICTED` but not all of them are, it is `TIGHT`. Otherwise it is `AVAILABLE`. A tournament's `housing_pressure` then aggregates upward: `executed_contract_count` is the number of its contracts whose `status` is `EXECUTED` or `CLOSED`, and `sold_out_contract_count` is the number of those same contracts whose `block_posture` is `SOLD_OUT`. Contracts still in `DRAFT` or `NEGOTIATING` are excluded from both counts. `housing_pressure` reads `CONSTRAINED` when `executed_contract_count` is at least 1 and `sold_out_contract_count` equals `executed_contract_count`; in every other case, including the case of no executed contracts at all, it reads `NORMAL`.

Releasing a block hands its unsold remainder back to the hotel. A `HousingManager` may release a block whose `status` is `OPEN` or `RESTRICTED`, provided the owning contract's `status` is `EXECUTED` — otherwise `ERR_CONTRACT_NOT_EXECUTED` — and provided the logical clock has reached or passed the block's `release_deadline`. An attempt before that instant is rejected with `ERR_RELEASE_BEFORE_DEADLINE`; note the comparison is inclusive, so a release exactly at the deadline is permitted. Both source states behave identically: the transition freezes `rooms_released_unsold` at `block_size_rooms` minus `rooms_committed`, sets `rooms_available` to 0, leaves `rooms_committed` untouched, then recomputes the contract's `block_posture` and, from that, the tournament's `housing_pressure`. Because a released block is no longer live, releasing the last restricted block of a sold-out contract can move that contract's posture back toward `AVAILABLE` and relieve the event's `CONSTRAINED` pressure. A released block later reaches `SETTLED`; see §3.8 for the conditions.

### 3.3. Team Registration and Roster-Based Room Requirements

Registration ties a team to an event. Either a `HousingManager` or the team's own `TeamManager` submits `tournament_id`, `team_id`, `roster_player_count` (at least 1) and `roster_staff_count` (at least 0), and the tournament must be `OPEN`. A `TeamManager` may only register the team whose `id` equals its `X-User-ID`; otherwise the request is rejected with `ERR_TEAM_SCOPE_VIOLATION`.

At creation the server derives `local_team_flag` by reading the referenced team's `distance_miles_from_venue` and testing it against a local radius of thirty miles: the flag is `true` when the team's home city lies at or within thirty miles of the venue, and `false` otherwise. The interesting property of this field is that it is stored on the registration but derived from a different record entirely, so a team's geography — not anything about the registration — decides it.

The roster then produces **two different room requirements**, and the distinction between them is the most consequential piece of arithmetic in the housing program. Both are computed at registration and re-derived on every subsequent registration recompute.

The first is the **segregated-occupancy** requirement, stored as `required_rooms_registered`. Players and staff are housed in separate rooms with different capacities: players share at most four to a room, staff at most two to a room. Take `roster_player_count`, divide by four and round **up** to a whole number of player rooms; take `roster_staff_count`, divide by two and round **up** to a whole number of staff rooms; add the two counts. Because the rounding-up happens once per bucket, the partial-room remainder is paid twice. The registration also stores `required_room_nights`, which is `required_rooms_registered` multiplied by the tournament's `night_count`. `required_rooms_registered` is the **ceiling** on how many rooms any single booking may request (§3.4).

The second is the **pooled-occupancy** requirement, stored as `minimum_rooms_for_compliance`. Here players and staff share rooms at the four-per-room capacity: add `roster_player_count` and `roster_staff_count`, divide the single pooled total by four, and round **up** once. Because the rounding-up happens once over the combined head count, the remainder is paid only once. `minimum_rooms_for_compliance` is the **floor** that stay-to-play compliance is judged against. The two numbers differ for most rosters. A roster of 13 players and 3 staff yields four player rooms plus two staff rooms, so `required_rooms_registered` is 6, while the pooled computation divides 16 by four and yields `minimum_rooms_for_compliance` of 4 — six rooms bookable at most, four rooms required at least, from identical inputs.

The rest of the registration record is initialised to `exempt_rooms_granted` of 0, `effective_required_rooms` equal to `minimum_rooms_for_compliance`, `committed_rooms` of 0 and `status` `PENDING_HOUSING`.

Compliance is then recomputed from scratch — never patched incrementally — after team registration, after a booking is confirmed, after a booking is cancelled, after an exception request is approved by a reviewer, after one is denied by a reviewer, after one is auto-approved at filing, and during the close chain when the housing window shuts. Each recompute proceeds in this order. First, `exempt_rooms_granted` becomes the sum of `approved_rooms_exempt` across the registration's exception requests whose `status` is `APPROVED`; requests sitting at `SUBMITTED`, `UNDER_REVIEW`, `INFO_REQUESTED` or `DENIED` contribute nothing. Second, `effective_required_rooms` becomes `minimum_rooms_for_compliance` less `exempt_rooms_granted`, floored at 0 so it can never go negative. Third, `committed_rooms` becomes the sum of `rooms_requested` across the registration's bookings whose `booking_status` is `CONFIRMED` or `CHECKED_OUT`; bookings at `DRAFT`, `ROOMING_LIST_SUBMITTED` or `CANCELLED` contribute nothing. Both sums are order-insensitive.

The `status` is then chosen by the first matching branch of a five-way decision. If the tournament's `stay_to_play_required` is `false`, the registration is `HOUSING_COMPLIANT` outright — the policy is not in force. Otherwise, if `effective_required_rooms` has fallen to 0 **and** `exempt_rooms_granted` is at least 1, the registration is `EXCEPTION_GRANTED`, recording that it was excused rather than that it complied. Otherwise, if `committed_rooms` is greater than or equal to `effective_required_rooms`, the registration is `HOUSING_COMPLIANT`; the comparison is inclusive, so a team that has committed exactly its effective requirement is compliant. Otherwise, if the tournament's `posture` is still `OPEN`, the registration is `PENDING_HOUSING` — it has time left to book. Otherwise it is `NON_COMPLIANT`. Every recompute, whatever its outcome, refreshes `compliance_evaluated_at` to the current logical instant. Note the ordering consequence: a fully exempted team reads `EXCEPTION_GRANTED` even when it has also booked enough rooms to satisfy the compliance test, because the exemption branch is examined first.

### 3.4. Booking Rooms, Rooming Lists and Confirmation

Booking is the operation the whole stay-to-play policy exists to funnel teams into, and it carries the largest set of preconditions in the system. Either a `HousingManager` or the team's own `TeamManager` creates a booking with `registration_id`, `room_block_id`, `rooms_requested` (at least 1), the stay as `check_in_date` and `check_out_date`, and the mandatory `expected_registration_version` described in §2.8. An optional `supersedes_booking_id` names the booking this one replaces.

The gauntlet a booking must pass runs, in the precedence order of §2.11, as follows. The governing tournament must be `OPEN`. The logical clock must be at or before the tournament's `booking_deadline`; a booking attempted after that instant is rejected with `ERR_BOOKING_DEADLINE_PASSED`, and the comparison is inclusive so a booking landing exactly on the deadline is accepted. The contract owning the target block must be `EXECUTED`, or `ERR_CONTRACT_NOT_EXECUTED`. The block itself must be `OPEN` or `RESTRICTED`; a `RELEASED` or `SETTLED` block no longer sells rooms and yields `ERR_BLOCK_NOT_BOOKABLE`. The `check_out_date` must be strictly after the `check_in_date`, or `ERR_INVALID_DATE_RANGE`. The stay must sit inside the block's held window: `check_in_date` at or after the block's `arrival_date` and `check_out_date` at or before the block's `departure_date`, or `ERR_STAY_OUTSIDE_BLOCK_WINDOW`.

Next comes **team exclusivity**, and its interval semantics are deliberately different from every other date test in this document. A team may not be checked in at two different properties on the same calendar day. The system looks for any other booking whose registration belongs to the same team, whose `room_block_id` differs from the one being booked, whose `booking_status` is `DRAFT`, `ROOMING_LIST_SUBMITTED`, `CONFIRMED` or `CHECKED_OUT`, and whose stay interval — treated as **closed** at both ends, from `check_in_date` through `check_out_date` inclusive — intersects the new stay's equally closed interval. Because both endpoints are inclusive, adjacency is **forbidden**: an existing stay ending on 2026-09-12 collides with a new stay starting on 2026-09-12. Any such intersection is rejected with `ERR_TEAM_STAY_OVERLAP`. Two bookings on the *same* block are exempt from this test, which is what lets a team hold two room types at one property.

A `RESTRICTED` block is reserved for teams that still need housing. When the target block's `status` is `RESTRICTED`, the referenced registration's `status` must be `PENDING_HOUSING`; a team that already reads `HOUSING_COMPLIANT`, `EXCEPTION_GRANTED` or `NON_COMPLIANT` is turned away with `ERR_BLOCK_RESTRICTED_TO_UNHOUSED_TEAMS`. A supplied `supersedes_booking_id` must name a booking of the **same** `registration_id` whose `booking_status` is `DRAFT`, `ROOMING_LIST_SUBMITTED` or `CONFIRMED`; pointing at another registration's booking, or at one already `CHECKED_OUT` or `CANCELLED`, is rejected with `ERR_SUPERSEDE_TARGET_INVALID`.

The last two gates are the fiscal ones. `rooms_requested` may not exceed the registration's `required_rooms_registered` — the segregated-occupancy figure, deliberately not the pooled `minimum_rooms_for_compliance` — or the request is rejected with `ERR_ROOMS_EXCEED_ROSTER_REQUIREMENT`. Then the block's per-night capacity is checked. For every night in the half-open range from `check_in_date` up to but not including `check_out_date`, the system computes the block's **held** occupancy on that night: the sum of `rooms_requested` over every booking on this block whose `booking_status` is `DRAFT`, `ROOMING_LIST_SUBMITTED`, `CONFIRMED` or `CHECKED_OUT` and whose own half-open stay range covers that night. If that held occupancy plus the new `rooms_requested` would exceed the block's `block_size_rooms` on any single night, the request is rejected with `ERR_BLOCK_CAPACITY_EXCEEDED`. Cancelled bookings are excluded and free their rooms immediately. The held set intentionally counts unconfirmed bookings, so a block cannot be oversold at creation time even though the persisted committed counters do not move until confirmation.

A booking that clears all of that is created with `booking_status` `DRAFT` and `rebate_status` `NOT_DUE`. The server computes `nights` as the whole days from `check_in_date` up to but not including `check_out_date`, and `projected_room_nights` as `rooms_requested` multiplied by `nights` — the pre-stay estimate that cancellation penalties are assessed against. It initialises `actualized_room_nights`, `rebate_accrued_cents`, `penalty_cents`, `penalty_room_nights` and `penalty_credit_cents` all to 0, leaves `cancellation_reason` and `cancelled_at` null, and increments the parent registration's `version` by 1. Creation alone leaves the block's `rooms_committed`, `rooms_available` and `utilization_pct` **untouched** — confirmation is the only trigger that moves them. When `supersedes_booking_id` was supplied, the named booking is moved to `CANCELLED` as a side effect, with its `cancellation_reason` set to `SUPERSEDED` and the deadline-tier penalty of §3.5 assessed against it exactly as if it had been cancelled directly.

Rooming list collection turns a held booking into a named manifest. The team manager (or a housing manager acting for it) submits `entries`, an array in which each element carries a `room_index`, an `occupant_count`, a `minor_occupant_count` and an optional `chaperone_name`. Each stored `RoomingListEntry` records the `booking_id` it belongs to. A first submission moves the booking `DRAFT → ROOMING_LIST_SUBMITTED`, creating one row per submitted element. A further submission while the booking is already `ROOMING_LIST_SUBMITTED` is a self-loop: the booking stays in `ROOMING_LIST_SUBMITTED`, every existing entry for that booking is deleted, and a fresh row is created for each submitted element. Rooming lists may be re-collected any number of times before confirmation. Both the first submission and the replacement require the governing tournament to be `OPEN` and, for a team manager, `X-User-ID` to equal the registration's team reference.

Four content rules police the manifest, and they are checked in this order. Every entry that reports at least one minor must supply a non-empty `chaperone_name`, naming the adult responsible for that room; otherwise `ERR_CHAPERONE_REQUIRED`. Every entry must keep `occupant_count` at or below the four-occupant room ceiling and must not report more minors than occupants — `minor_occupant_count` must be at least 0 and no greater than `occupant_count` — otherwise `ERR_ROOM_OCCUPANCY_EXCEEDED`. The `room_index` values across the submitted entries must form the contiguous sequence from 1 through the booking's `rooms_requested`, with no duplicates and no gaps; anything else is `ERR_ROOMING_LIST_INDEX_INVALID`. The number of submitted entries must equal the booking's `rooms_requested`, or `ERR_ROOMING_LIST_ROOM_COUNT_MISMATCH`. Finally the total occupancy is bounded: the sum of `occupant_count` across the submitted entries must be at least 1 and no more than the registration's `roster_player_count` plus `roster_staff_count`, or `ERR_ROOMING_LIST_OCCUPANT_MISMATCH`. Each entry must also carry an `occupant_count` of at least 1.

Confirmation is a `HousingManager` action, and it is the moment the event commits rooms to the hotel. It moves a booking `ROOMING_LIST_SUBMITTED → CONFIRMED`, and it requires the governing tournament to be `OPEN`, the owning contract to be `EXECUTED`, and the block's `status` to still be `OPEN` or `RESTRICTED`. Confirmation fires the four-link confirm chain of §2.9, in this order.

The first link recomputes the registration's `committed_rooms` and re-derives its `status` per the compliance rules of §3.3, refreshing `compliance_evaluated_at`; the registration's own `updated_at` is refreshed and its `version` incremented by 1. The second link, in the same recompute epoch, refreshes the block's three occupancy counters. `rooms_committed` is the **peak-night** committed occupancy over the block's own half-open window: for each night from `arrival_date` up to but not including `departure_date`, sum `rooms_requested` over the bookings on this block whose `booking_status` is `CONFIRMED` or `CHECKED_OUT` and whose own half-open stay covers that night, then take the maximum of those per-night sums across the whole window. With no such bookings the peak is 0. Note that this committed set is narrower than the held set used by the oversell guard above: `DRAFT` and `ROOMING_LIST_SUBMITTED` bookings count toward held occupancy but not toward `rooms_committed`. `rooms_available` is then `block_size_rooms` less `rooms_committed` while the block is `OPEN` or `RESTRICTED`, and exactly 0 once it is `RELEASED` or `SETTLED`. `utilization_pct` is `rooms_committed` divided by `block_size_rooms`, rounded half up to four decimal places.

That recompute may flip the block along its utilization axis. While a block's `status` is `OPEN` or `RESTRICTED`, it reads `RESTRICTED` whenever `utilization_pct` is at or above 0.90 — ninety percent of the held rooms committed — and `OPEN` otherwise. The comparison is inclusive: a `utilization_pct` of exactly 0.9000 restricts the block, and 0.8999 does not. The axis is cyclic in both directions: a confirmation can drive `OPEN → RESTRICTED`, and a later cancellation that drops utilization back below 0.90 drives `RESTRICTED → OPEN`. Blocks that have reached `RELEASED` or `SETTLED` are never revisited by this rule. The third link recomputes the owning contract's `block_posture`, which may flip it to `SOLD_OUT`. The fourth link recomputes the tournament's `sold_out_contract_count` and its `housing_pressure`, which may move from `NORMAL` to `CONSTRAINED`. Every resource whose values actually changed along that chain has its `updated_at` refreshed and its `version` incremented by 1.

### 3.5. Superseding, Cancelling and the Deadline-Tier Penalty

Cancellation is available to a `HousingManager` or to the team's own `TeamManager`, and it accepts a free-text `cancellation_reason`. A booking may be cancelled from `DRAFT`, from `ROOMING_LIST_SUBMITTED` or from `CONFIRMED` — three distinct transitions into the same `CANCELLED` terminal state — and in all three the governing tournament's `posture` must be either `OPEN` or `BOOKING_CLOSED`. A booking that has already reached `CHECKED_OUT` or `CANCELLED` cannot be cancelled, since neither is a declared source state; such an attempt is rejected with `ERR_INVALID_STATE`.

Penalties are graded by how close to arrival the cancellation lands. The system first computes the **days out**: take the instant of `check_in_date` at midnight UTC, subtract the current logical instant, and take the whole number of 86,400-second days in that difference, rounding **down**. The figure may be negative when the stay has already begun. Four tiers then select the chargeable room nights, and every tier comparison is inclusive at its lower bound. At forty-five days out or more, `penalty_room_nights` is 0 — cancellation is free. From twenty-one days out up to forty-four, `penalty_room_nights` is one quarter of `projected_room_nights`, rounded **up** to a whole room night. From seven days out up to twenty, it is one half of `projected_room_nights`, rounded up. Fewer than seven days out — including any negative figure — charges the full `projected_room_nights`. Because the boundaries are inclusive, a cancellation at exactly forty-five days out is free while one at forty-four days out falls into the quarter tier.

`penalty_cents` is then `penalty_room_nights` multiplied by the `negotiated_nightly_rate_cents` of the contract that owns the booking's room block — reached from the booking through its block, since the rate lives on the contract rather than on the block. The server also stamps `cancelled_at` with the current logical instant. Note that `penalty_credit_cents`, the relief a complaint remedy may grant, is tracked separately and **never** reduces `penalty_cents` itself; the two figures coexist on the booking so that the charge and the relief remain independently auditable.

Cancelling also gives rooms back. Every `RoomingListEntry` belonging to the booking is deleted when the cancellation comes from `ROOMING_LIST_SUBMITTED` or from `CONFIRMED`; a cancellation from `DRAFT` has no entries to delete. The block's `rooms_committed`, `rooms_available` and `utilization_pct` are recomputed, which may fire the `RESTRICTED → OPEN` flip and, through it, recompute the contract's `block_posture` and the tournament's `housing_pressure` — the confirm chain run in reverse from the block downstream. The registration's `committed_rooms` and `status` are recomputed too, and a team may legitimately fall back from `HOUSING_COMPLIANT` to `PENDING_HOUSING` when the rooms it was relying on disappear. This forward-and-compensating symmetry is the case the room inventory invariant of §2.12 pins: confirming a booking and then cancelling that same booking must restore all three block counters to their pre-confirmation values exactly.

### 3.6. Stay-to-Play Exceptions, Information Loops and Appeals

Not every family can or should be routed through the official housing program, and the exception process is where that judgement is made. A `HousingManager` or the team's own `TeamManager` files a request against a registration with `registration_id`, a `reason_code`, a `requested_rooms_exempt` of at least 1, and a narrative `justification`. The `reason_code` is one of `LOCAL_TEAM`, `FAMILY_MEDICAL`, `ADA_ACCOMMODATION`, `FINANCIAL_HARDSHIP` or `RELATIVE_HOSTING`. Filing requires the tournament to be `OPEN`.

Four eligibility rules apply at filing, in this order. A `LOCAL_TEAM` request is admissible only when the registration's `local_team_flag` is `true`; a non-local team asking for the local exemption is rejected with `ERR_LOCAL_EXEMPTION_NOT_ELIGIBLE`. A `FAMILY_MEDICAL` request may ask for at most one room, because it is meant to cover a single household circumstance; asking for more is rejected with `ERR_EXEMPTION_SCOPE_TOO_BROAD`. In every case, `requested_rooms_exempt` may not exceed the registration's `minimum_rooms_for_compliance` — a team cannot be excused from more rooms than the policy ever required of it — or the request is rejected with `ERR_EXEMPTION_EXCEEDS_REQUIREMENT`. And a registration may have only one live request at a time: if any other request on the same registration sits at `SUBMITTED`, `UNDER_REVIEW`, `INFO_REQUESTED` or `APPROVED`, the new filing is rejected with `ERR_DUPLICATE_OPEN_EXCEPTION`. A previously `DENIED` request does not block a new filing.

A request normally lands at `SUBMITTED` with `review_round` 0, `appeal_count` 0, `approved_rooms_exempt` 0 and `decided_by_user_id` null. There is one short-circuit. When the `reason_code` is `LOCAL_TEAM`, the registration's `local_team_flag` is `true`, **and** the tournament's `housing_pressure` reads `CONSTRAINED`, the request is auto-approved at filing time: it goes straight from `SUBMITTED` to `APPROVED`, `approved_rooms_exempt` is set to the full `requested_rooms_exempt`, `decided_by_user_id` is set to the literal `SYSTEM_AUTO`, and `review_round` stays at 0 because no human review ever began. The registration's `exempt_rooms_granted`, `effective_required_rooms` and `status` are then recomputed. The business logic is straightforward: when every executed contract in the event is sold out, there is no room for a local team to book anyway, so requiring it to try is pointless.

Human review runs through a four-action capability reserved to the `ExceptionReviewer`, which supplies an `action` and optionally `approved_rooms_exempt` and a `decision_note`. `START_REVIEW` moves the request `SUBMITTED → UNDER_REVIEW` and increments `review_round` by 1; it requires the tournament to be `OPEN`. `REQUEST_INFO` moves it `UNDER_REVIEW → INFO_REQUESTED` and records the supplied `decision_note`. `APPROVE` moves it `UNDER_REVIEW → APPROVED`, requires the tournament to be `OPEN`, sets `approved_rooms_exempt` from the payload and `decided_by_user_id` to the acting `X-User-ID`, then recomputes the registration's `exempt_rooms_granted`, `effective_required_rooms` and `status` — which may move to `EXCEPTION_GRANTED` or to `HOUSING_COMPLIANT` — and refreshes the registration's `updated_at` and increments its `version` by 1. `DENY` moves it `UNDER_REVIEW → DENIED`, sets `approved_rooms_exempt` to 0, `decided_by_user_id` to the acting `X-User-ID` and `decision_note` from the payload, and likewise recomputes the registration. Note the asymmetry between the two decisions: approval and start-of-review are gated on the tournament being `OPEN`, whereas requesting information and denying are not.

Approval carries its own range rules. When the `action` is `APPROVE`, `approved_rooms_exempt` must be supplied and must be at least 1 and no more than the original `requested_rooms_exempt`; a missing, zero, or oversized value is rejected with `ERR_APPROVED_EXEMPTION_OUT_OF_RANGE`. Partial approval is the norm — a reviewer may grant two of four requested rooms — with one exception: when the request's `reason_code` is `LOCAL_TEAM`, `approved_rooms_exempt` must equal `requested_rooms_exempt` exactly, because a local exemption is all-or-nothing. A partial local grant is rejected with `ERR_PARTIAL_LOCAL_EXEMPTION_FORBIDDEN`.

The lifecycle is cyclic twice over. The **information loop** lets a team answer a reviewer's questions: a `RESUBMIT` action on the team-side capability moves the request `INFO_REQUESTED → UNDER_REVIEW`, replaces the stored `justification` with the newly supplied one, and increments `review_round` by 1. That loop is unbounded — a request may cycle `UNDER_REVIEW → INFO_REQUESTED → UNDER_REVIEW` as many times as the reviewer needs, with `review_round` counting each entry into review. The **appeal loop** lets a team contest a denial: an `APPEAL` action moves the request `DENIED → UNDER_REVIEW` and increments both `appeal_count` and `review_round` by 1. That loop is capped at one appeal: an `APPEAL` against a request whose `appeal_count` already stands at 1 is rejected with `ERR_APPEAL_LIMIT_REACHED`, which is what makes the cycle terminate. Both team-side actions require `X-User-ID` to equal the registration's team reference and require the tournament to be `OPEN`, and both are exclusive to the `TeamManager` role; the payload carries the `action` and, for a resubmission, the replacement `justification`.

Filing an appeal arms the segregation-of-duties rule of §2.10. Once `appeal_count` is at least 1, the reviewer who recorded the original decision may no longer approve or deny this request; an attempt yields `ERR_SOD_SAME_REVIEWER`. Before any appeal, the same reviewer may take every action freely. `APPROVED` is the terminal state of this lifecycle; `DENIED` is not terminal, because it can be appealed once and, as §3.9 describes, can also be reopened by a complaint remedy.

### 3.7. Closing the Housing Window, Actualization and Rebate Accrual

Closing the housing window is the pivot of the whole event. A `HousingManager` moves the tournament `OPEN → BOOKING_CLOSED`, which requires that at least one hotel contract of the event has reached `EXECUTED` or `CLOSED` — an event with no signed inventory has no housing program to close.

The close fires a three-link cascade whose links are causally ordered. The first link re-evaluates every registration of the event whose `status` is `PENDING_HOUSING` against the compliance rules of §3.3; because the tournament's `posture` is no longer `OPEN`, any registration whose `committed_rooms` falls short of its `effective_required_rooms` now lands on `NON_COMPLIANT` rather than staying pending. The second link, caused by the first, deals with the exception requests of exactly those registrations that just became `NON_COMPLIANT`: every such request sitting at `SUBMITTED`, `UNDER_REVIEW` or `INFO_REQUESTED` is moved to `DENIED` by the system, with `decided_by_user_id` set to the literal `SYSTEM_AUTO` and `decision_note` set to the literal `closed without decision`. The third link, caused by the second, recomputes each touched registration's `exempt_rooms_granted` and `effective_required_rooms` and refreshes its `compliance_evaluated_at`, since denying a pending request changes the inputs the second link's own outcome was derived from. The `version` of every registration and every exception request the cascade mutates is incremented by 1.

The same close also sweeps inventory. Every room block that belongs to an `EXECUTED` contract of this tournament, whose own `status` is `OPEN` or `RESTRICTED`, and whose `release_deadline` the logical clock has already reached or passed, is transitioned to `RELEASED` with the same effects as a manual release: `rooms_released_unsold` frozen at `block_size_rooms` less `rooms_committed`, `rooms_available` driven to 0, and the contract's `block_posture` and tournament's `housing_pressure` recomputed. Blocks whose `release_deadline` still lies in the future are left alone and must be released explicitly later. Closing the window refreshes the tournament's own `updated_at` and increments its `version` by 1.

With the window closed, the hotels report what actually happened. A `HotelRepresentative` files an actualization report against a booking, supplying `reported_room_nights` (at least 0) and an optional `report_note`. This is the one write in the system reserved entirely to hotels, and it is scoped: `X-User-ID` must equal the hotel reference of the contract that owns the booking's block, or the request is rejected with `ERR_HOTEL_SCOPE_VIOLATION`. The governing tournament's `posture` must be `BOOKING_CLOSED` or `RECONCILING`, or the request is rejected with `ERR_TOURNAMENT_NOT_RECONCILING`. The booking's `booking_status` must be `CONFIRMED` for the first report on that booking and `CHECKED_OUT` for any subsequent report; anything else is rejected with `ERR_BOOKING_NOT_CONFIRMED`.

Each accepted report is an immutable record carrying the `booking_id` it describes, its `reported_room_nights`, its optional `report_note`, and a server-assigned `sequence_no` equal to one more than the number of reports already filed against that booking — so the first report is number 1 and numbering rises monotonically per booking. The booking's `actualized_room_nights` is always taken from the report with the **greatest** `sequence_no`, and is 0 while no report exists. A later report therefore *restates* the figure rather than adding to it. The block's own `actualized_room_nights` is then re-derived as the sum of `actualized_room_nights` over the bookings on that block whose `booking_status` is `CHECKED_OUT`.

Here the booking's two independent state axes separate. The **reservation axis**, `booking_status`, runs `DRAFT → ROOMING_LIST_SUBMITTED → CONFIRMED → CHECKED_OUT` with `CANCELLED` as an alternate terminal, and the first accepted actualization report is what advances it `CONFIRMED → CHECKED_OUT` — provided no report already exists for that booking. Once at `CHECKED_OUT` the reservation axis never moves again. The **money axis**, `rebate_status`, runs `NOT_DUE → ACCRUED → INVOICED` and then to one of `COLLECTED`, `SHORT_PAID` or `WRITTEN_OFF`, and every one of its transitions is system-driven and leaves `booking_status` untouched. The first report with `reported_room_nights` greater than 0 moves the money axis `NOT_DUE → ACCRUED`, provided `booking_status` is `CONFIRMED` or `CHECKED_OUT`, and computes `rebate_accrued_cents`. Each subsequent report is an `ACCRUED → ACCRUED` self-loop: `actualized_room_nights` is re-derived from the greatest `sequence_no` and `rebate_accrued_cents` is recomputed, while `booking_status` stays frozen at `CHECKED_OUT`.

`rebate_accrued_cents` — the booking's rebate line — is computed from the `rebate_model` of the contract owning the booking's block, applied to the booking's current `actualized_room_nights`. Under `PER_ROOM_NIGHT_FLAT`, the line is `actualized_room_nights` multiplied by the contract's `rebate_flat_cents_per_room_night`. Under `PERCENT_OF_ROOM_REVENUE`, the line is `actualized_room_nights` multiplied by the contract's `negotiated_nightly_rate_cents` multiplied by its `rebate_percent`, with the product rounded half up to a whole cent. Under `TIERED_PER_ROOM_NIGHT`, the rate is a function of the contract's total volume: sum `actualized_room_nights` over every booking whose block belongs to this contract and whose `booking_status` is `CHECKED_OUT` — `CONFIRMED` and `CANCELLED` bookings are excluded, and the sum is order-insensitive — then select a single rate from that contract-wide total. Fewer than 30 total room nights selects 500 cents per room night; from 30 up to 89 selects 750 cents; 90 or more selects 1,000 cents. The tier boundaries are inclusive at the lower edge, so a contract total of exactly 30 room nights selects the 750-cent rate. That single selected rate is then applied to **all** of this booking's room nights — an average-rate selection, not a marginal allocation in which the first thirty nights would bill at one rate and the rest at another.

### 3.8. Rebate Invoicing, Attrition and Collection

Rebate collection is a per-contract, per-period exercise. A `HousingManager` raises an invoice by supplying `contract_id` and a `period_label`, a human label for the billing period. The tournament's `posture` must be `BOOKING_CLOSED` or `RECONCILING`, the contract's `status` must be `EXECUTED`, and the `period_label` must be unused among the invoices already raised against that same contract; a repeat is rejected with `ERR_DUPLICATE_INVOICE_PERIOD`.

The invoice **scope** is the set of bookings whose `room_block_id` belongs to a block of this contract, whose `booking_status` is `CHECKED_OUT`, and whose `rebate_status` is `ACCRUED`, taken in ascending `created_at` order so that line emission is reproducible. Bookings already at `INVOICED`, `COLLECTED`, `SHORT_PAID` or `WRITTEN_OFF` are excluded, which means a second invoice against the same contract finds an empty scope until new actualization reports arrive. If the scope contains no booking at all, or if the resulting `invoiced_room_nights` is 0, the request is rejected with `ERR_NO_BILLABLE_ROOM_NIGHTS`.

`invoiced_room_nights` is the sum of `actualized_room_nights` across the scope. `invoiced_rebate_cents` is the sum of each scoped booking's rebate line, computed exactly as in §3.7 and — this ordering is fixed — **rounded to whole cents per line before the lines are summed**. Summing unrounded products and rounding the single total at the end is not equivalent and can differ by one or more cents from the correct answer.

Attrition damages are then netted off. The invoice reports the shortfall under **two different clamping conventions**, and only one of them is billed. Both start from the same per-block figures, computed over every room block of the contract whose `status` is `OPEN`, `RESTRICTED`, `RELEASED` or `SETTLED`: a block's contracted nights are `block_size_rooms` multiplied by the whole nights in its window, its threshold nights are that product multiplied by the contract's `attrition_threshold_pct` and rounded **up**, and its actual nights are its own `actualized_room_nights`. Blocks that consumed nothing still carry their full threshold.

The **billed** variant, stored as `attrition_shortfall_room_nights_per_block`, clamps each block independently: for each block take its threshold nights less its actual nights, floor that difference at 0, and sum the clamped per-block results. Because each block is clamped on its own, a block that over-performed cannot offset a block that under-performed. The **reported-only** variant, stored as `attrition_shortfall_room_nights_aggregate`, clamps once over the contract totals: sum every block's threshold nights, sum every block's actual nights, subtract the second total from the first, and floor that single difference at 0. Here over-performance does offset under-performance. Two blocks with thresholds of 10 and 10 and actuals of 12 and 3 give a per-block shortfall of 7 and an aggregate shortfall of 5 from identical inputs. The aggregate figure exists purely so that a hotel disputing the bill can see the more favourable reading; it is never billed.

`attrition_penalty_cents` is `attrition_shortfall_room_nights_per_block` multiplied by the contract's `attrition_penalty_rate_cents_per_room_night`. `total_due_cents` is `invoiced_rebate_cents` less `attrition_penalty_cents`, floored at 0 — a penalty larger than the rebate zeroes the claim rather than turning it into a debt owed by the event. The ledger fields open at `collected_cents` 0, `written_off_cents` 0, `outstanding_cents` equal to `total_due_cents`, and `distributed_cents` 0, with `status` at `DRAFT` and `dispute_note` null. `distributed_cents` is maintained as the sum of `gross_collected_cents` across the revenue distributions whose source is this invoice, and is updated whenever such a distribution is created. Raising the invoice also moves every in-scope booking's `rebate_status` from `ACCRUED` to `INVOICED`, leaving each booking's `booking_status` at `CHECKED_OUT`.

Three non-payment moves make up the invoice's lifecycle capability, which takes an `action` and an optional `dispute_note`. `ISSUE`, a housing-manager action, moves the invoice `DRAFT → ISSUED` and requires `total_due_cents` to be at least 1; issuing a zero-value invoice is rejected with `ERR_INVOICE_TOTAL_NOT_POSITIVE`. Issuing also re-evaluates the tournament's `BOOKING_CLOSED → RECONCILING` transition, so the first invoice of any contract of the event to reach `ISSUED` is what tips the event into `RECONCILING`. `DISPUTE`, a hotel-representative action scoped to its own contract, moves the invoice from `ISSUED` or from `PARTIALLY_PAID` to `DISPUTED` and records the supplied `dispute_note`. `WRITE_OFF`, a housing-manager action, moves the invoice from `ISSUED`, from `PARTIALLY_PAID` or from `DISPUTED` to `WRITTEN_OFF`: it sets `written_off_cents` to whatever `outstanding_cents` then stood at and drives `outstanding_cents` to 0, leaving `total_due_cents` and `collected_cents` untouched, exactly as the rebate ledger invariant of §2.12 requires.

A write-off also resolves the money axis of every booking in the invoice's scope, and **which** terminal state it picks depends on whether any money was ever collected. Every booking of the contract whose `rebate_status` is `INVOICED` moves to `WRITTEN_OFF` when the invoice's `collected_cents` is 0, and to `SHORT_PAID` when `collected_cents` is greater than 0. A write-off from `ISSUED` therefore always yields `WRITTEN_OFF` bookings, since nothing was collected; a write-off from `PARTIALLY_PAID` always yields `SHORT_PAID` bookings; a write-off from `DISPUTED` yields whichever fits, because a disputed invoice may or may not have received an instalment before the dispute. In every case the block's `RELEASED → SETTLED` transition and the tournament's `RECONCILING → SETTLED` transition are re-evaluated afterwards.

Remittance is the hotel's own capability and takes a single `amount_cents`. The acting `HotelRepresentative` must be scoped to the contract, and `amount_cents` must be at least 1 and no more than the invoice's current `outstanding_cents`; a zero, negative or oversized amount is rejected with `ERR_REMITTANCE_EXCEEDS_OUTSTANDING`. A remittance smaller than `outstanding_cents` moves the invoice from `ISSUED` to `PARTIALLY_PAID`, or keeps it at `PARTIALLY_PAID` as an instalment self-loop; in either case `collected_cents` is increased by `amount_cents` and `outstanding_cents` is recomputed. A remittance exactly equal to `outstanding_cents` clears the invoice to `PAID` from `ISSUED`, from `PARTIALLY_PAID` or from `DISPUTED` — a dispute does not bar payment, and remitting in full closes the dispute. Note that there is no partial-payment transition out of `DISPUTED`: a disputed invoice accepts only a full clearing remittance, and a partial one is rejected with `ERR_INVALID_STATE`.

Clearing an invoice fires the four-link remit chain. The first link sets `collected_cents` to `total_due_cents` and `outstanding_cents` to 0. The second link, caused by the first, moves every booking whose block belongs to this contract and whose `rebate_status` is `INVOICED` from `INVOICED` to `COLLECTED`, again without touching `booking_status`. The third link, caused by the second, re-evaluates the `RELEASED → SETTLED` transition of each affected block: a released block settles once at least one booking on it is not `CANCELLED` and every one of its non-cancelled bookings has a `rebate_status` of `COLLECTED`, `SHORT_PAID` or `WRITTEN_OFF`. The fourth link, caused by the third, re-evaluates the contract's own `EXECUTED → CLOSED` transition, which fires once every block of the contract has settled. Finally the tournament's `RECONCILING → SETTLED` transition is re-evaluated.

An event settles only when both its collection and its payout are complete. Evaluated only while `posture` is `RECONCILING`, the event moves to `SETTLED` when every rebate invoice reachable through any of its hotel contracts has a `status` of `PAID` or `WRITTEN_OFF`, **and** at least one revenue distribution exists for the event, **and** every one of those distributions has a `status` of `PAID`. `SETTLED` is terminal for the tournament and admits no further operations on any of its children.

### 3.9. Complaints, Remedies and Revenue Distribution

Stay-to-play policy generates disputes, and the platform gives them a formal channel. A `HousingManager` or a `TeamManager` files a complaint with `tournament_id`, a `category` of `PRICING_FAIRNESS`, `POLICY_FAIRNESS`, `BLOCK_AVAILABILITY` or `REBATE_TRANSPARENCY`, and a `narrative` statement. Up to three optional subject references may accompany it: a `registration_id` naming the complaining registration (null for hotel-side complaints), a `cited_exception_request_id` naming the exemption decision the complaint disputes, and an `affected_booking_id` naming the booking whose penalty a granted remedy would credit. At least one of those three must be supplied, or the filing is rejected with `ERR_COMPLAINT_SUBJECT_MISSING`. A new complaint opens at `status` `FILED` with `route` null, `remedy_type` `NONE`, `remedy_amount_cents` 0, `remedy_credit_cents` 0 and both `triaged_by_user_id` and `adjudicated_by_user_id` null.

Triage forks the complaint onto one of two branches. A `HousingManager` supplies a `route` of either `INVESTIGATE`, moving the complaint `FILED → INVESTIGATING`, or `ESCALATE`, moving it `FILED → ESCALATED`. Both require the complaint to be at `FILED` and the tournament's `posture` to be anything other than `SETTLED`, and both record the chosen `route` and set `triaged_by_user_id` to the acting `X-User-ID`. The branches are not symmetric in their effects. The `INVESTIGATE` branch has no cross-entity effect at all. The `ESCALATE` branch carries one: when the complaint names a `cited_exception_request_id` and that exception request's `status` is `DENIED`, the request's `appeal_count` is reset to 0 and its `version` incremented by 1, restoring one appeal cycle to a team whose single appeal has already been spent. Escalation therefore has real value to a complainant independent of the eventual outcome.

Adjudication is reserved to the `RightsHolder` and closes the fork. The payload supplies an `outcome` of `UPHOLD` or `DISMISS`, a `remedy_type`, and — only for a fee waiver — a `remedy_amount_cents`. Segregation of duties applies first: when the complaint carries a `cited_exception_request_id`, the acting `X-User-ID` may not equal that request's `decided_by_user_id`, or the request is rejected with `ERR_SOD_ADJUDICATOR_CONFLICT`.

The `remedy_type` field is constrained twice over. Structurally, `FEE_WAIVER` requires a `remedy_amount_cents` of at least 1 **and** a non-null `affected_booking_id` on the complaint, while `NONE`, `RATE_ADJUSTMENT` and `POLICY_EXEMPTION` forbid `remedy_amount_cents` entirely; a mismatch is rejected with `ERR_REMEDY_FIELDS_INVALID`. Additionally, the remedy must belong to the vocabulary its triage branch permits. A complaint routed `INVESTIGATE` may only be resolved with `NONE` or `FEE_WAIVER` — the narrow, money-only vocabulary. A complaint routed `ESCALATE` may be resolved with any of `NONE`, `FEE_WAIVER`, `RATE_ADJUSTMENT` or `POLICY_EXEMPTION`. A remedy outside the branch's vocabulary is rejected with `ERR_REMEDY_NOT_AVAILABLE_ON_ROUTE`. This is why triage matters: only escalation unlocks a rate adjustment or a policy exemption.

Upholding a complaint sets `remedy_type` from the payload, computes `remedy_credit_cents`, and sets `adjudicated_by_user_id` to the acting `X-User-ID`. The credit is computed against the booking named by `affected_booking_id`, and it is clamped by how much of that booking's penalty is still uncredited: take the booking's `penalty_cents` less its `penalty_credit_cents`, floored at 0. A complaint with no `affected_booking_id` always credits 0. With that in hand: a remedy of `NONE` credits 0. A `FEE_WAIVER` credits the smaller of the requested `remedy_amount_cents` and the uncredited penalty. A `RATE_ADJUSTMENT` credits the smaller of the uncredited penalty and one tenth of the booking's notional room revenue — that is, the booking's `projected_room_nights` multiplied by the `negotiated_nightly_rate_cents` of the contract owning that booking's block, multiplied by one tenth, with the product rounded half up to a whole cent before the clamp is applied. A `POLICY_EXEMPTION` credits 0, because its relief is policy relief rather than money. Since the clamp floor is 0, a booking whose penalty has already been fully credited yields a further credit of 0.

Where the credit lands differs by branch, and each branch must be read on its own terms. On the `INVESTIGATING → UPHELD` transition, only a `FEE_WAIVER` moves money: when `remedy_type` is `FEE_WAIVER` and `affected_booking_id` is non-null, the affected booking's `penalty_credit_cents` is increased by `remedy_credit_cents` and that booking's `version` is incremented by 1. On the `ESCALATED → UPHELD` transition, both `FEE_WAIVER` and `RATE_ADJUSTMENT` move money in exactly that way: when `remedy_type` is either of those and `affected_booking_id` is non-null, the booking's `penalty_credit_cents` is increased by `remedy_credit_cents` and its `version` incremented by 1. The escalated branch additionally carries the three-link remedy chain, which fires only when `remedy_type` is `POLICY_EXEMPTION`, the complaint names a `cited_exception_request_id`, and that request's `status` is `DENIED`: the first link moves that request `DENIED → APPROVED` with `approved_rooms_exempt` set to its full `requested_rooms_exempt` and `decided_by_user_id` set to the literal `SYSTEM_AUTO`; the second link, caused by the first, recomputes that request's registration's `exempt_rooms_granted` and `effective_required_rooms`; and the third link, caused by the second, re-derives that registration's `status`, which may move `NON_COMPLIANT → EXCEPTION_GRANTED`.

Dismissal is symmetric across both branches and simpler. Whether the complaint sat at `INVESTIGATING` or at `ESCALATED`, a `DISMISS` outcome sets `remedy_type` to `NONE`, `remedy_credit_cents` to 0 and `adjudicated_by_user_id` to the acting `X-User-ID`, and carries no cross-entity effect whatsoever. Both `UPHELD` and `DISMISSED` are terminal.

Revenue sharing is the last act. A `HousingManager` creates a distribution against a collected invoice by supplying `tournament_id`, `source_invoice_id` and the mandatory `expected_invoice_version` of §2.8. The source invoice's `status` must be `PARTIALLY_PAID` or `PAID`; a distribution requested from an invoice that has collected nothing is rejected with `ERR_INVOICE_NOT_COLLECTED`. Creation increments the invoice's `version` by 1.

The split follows a fixed six-step waterfall, and its step order matters because the dependency looks circular. Step one snapshots `gross_collected_cents` as the source invoice's `collected_cents` at that instant. Step two selects `admin_fee_pct` from a three-tier table **keyed on `gross_collected_cents`**, never on the post-fee amount: below 50,000 cents the fee is 0.08; from 50,000 cents up to but not including 200,000 cents it is 0.06; at 200,000 cents or above it is 0.045. Step three computes `admin_fee_cents` as `gross_collected_cents` multiplied by `admin_fee_pct`, rounded half up to a whole cent. Step four computes `distributable_cents` as `gross_collected_cents` less `admin_fee_cents`. Step five allocates the three party buckets from `distributable_cents` in the fixed order organizer, then rights holder, then destination, each by multiplying `distributable_cents` by that party's share fraction on the tournament — `share_pct_organizer`, `share_pct_rights_holder` and `share_pct_destination` respectively — and truncating the product down to a whole cent; the rights-holder and destination results are stored directly as `rights_holder_cents` and `destination_cents`. Step six computes `rounding_remainder_cents` as `distributable_cents` less the three truncated allocations, and stores `organizer_cents` as the organizer's truncated allocation **plus that entire remainder**. The remainder is never split between parties, never assigned by bucket size, and never assigned by any other rule. The invariant this guarantees is that `organizer_cents`, `rights_holder_cents` and `destination_cents` always sum to exactly `distributable_cents`.

A new distribution opens at `status` `CALCULATED` with `approved_by_user_id` null. Advancing it is a two-action capability. `APPROVE`, a rights-holder action, moves it `CALCULATED → APPROVED` and sets `approved_by_user_id` to the acting `X-User-ID` — but only after the distribution-approver conflict check of §2.10 clears: if any complaint on the same `tournament_id` has `category` `REBATE_TRANSPARENCY`, `status` `UPHELD`, and an `adjudicated_by_user_id` equal to the acting `X-User-ID`, the approval is refused with `ERR_SOD_DISTRIBUTION_APPROVER_CONFLICT`. `PAY`, a housing-manager action, moves the distribution `APPROVED → PAID` and re-evaluates the tournament's `RECONCILING → SETTLED` transition. `PAID` is terminal, and once every invoice of the event is resolved and every distribution is `PAID`, the event itself settles and the season's books are closed.

## 4. Endpoint Definitions

Every endpoint in the table below is mounted under the `/housing` prefix, with the single exception of the logical clock control described in §2.5. Status codes follow one uniform rule: an endpoint that creates a new resource responds with `201 Created` and returns the created resource in `data`, while an endpoint that reads a resource, lists resources, or modifies or transitions an existing resource responds with `200 OK` and returns the read or updated resource in `data`. The five creation endpoints that add a child under a parent — room blocks, bookings, rooming-list actualization reports, exception requests and rebate invoices — return `201 Created` as well, since each produces a new record; note by contrast that submitting a rooming list returns `200 OK`, because the operation transitions the parent booking rather than creating a new addressable resource. All error responses use the status codes catalogued in §5.
